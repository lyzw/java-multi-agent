# rag_ops 授权变更说明（2026-11-02）

## 一句话

`rag_ops` 通道新增 **`rag_inspection_record` 的 INSERT-only 授权**。
原因是「平台全局语料签发 VERIFIED」需要人工抽检，而抽检记录是全局行，应用角色写不进去。

---

## 1. 为什么要改

签发 `VERIFIED` 前有一道**抽检前置守卫**（`InspectionGuard`，方案 V1.0.2 §5 R2）。
它对**租户档与平台全局档一视同仁**——这条治理底线不能因为作用域不同而豁免。

但抽检记录要落 `rag.rag_inspection_record`，而：

| 角色 | 写策略 | 结果 |
|---|---|---|
| `rag_app`（应用） | `tenant_id = rag_current_tenant() AND scope='TENANT'` | 写**全局行**被 RLS 拒绝：`new row violates row-level security policy` |
| `rag_ops`（运维，BYPASSRLS） | 无策略限制 | 可写，但**当时没有该表的 INSERT 授权**：`permission denied for table rag_inspection_record` |

原来 `04_rag_ops_role.sql` 的写面是「6 张表、一律不含 DELETE」，**抽检记录不在其中**——
于是平台全局语料**永远抽不了检**，也就**永远签不出 VERIFIED**（实测 500 → 修复作用域后 → 403）。

`rag_app` 那条策略正是「应用角色写不出全局行」的**越权闸门本身**，
所以正确做法不是放宽它，而是把这一格写入能力交给已经在同一通道上的 `rag_ops`。

---

## 2. 改了什么

### 2.1 `deploy/sql/rag/04_rag_ops_role.sql`

```sql
-- 只给 INSERT：抽检记录是「结论的证据」，只追加不修改
SELECT format('GRANT INSERT ON rag.rag_inspection_record TO %I', :'rag_ops_role') \gexec
```

同时新增两处**校验输出**（跑脚本时直接可见，不是装饰）：

- 3.2 授权面提示文案更新为「6 张 + 抽检记录 INSERT-only」；
- 3.4 新增断言：抽检记录应 `可插入=t、可修改=f、可删除=f、可清空=f`。

### 2.2 `scripts/tools/CheckRagOpsRole.java`

写面巡检**没有**简单地把 `6` 改成 `7` —— 那会让「扩面」变成无约束的敞口。
改为两条独立断言：

| 检查 | 含义 |
|---|---|
| **③ 写面恰好 6 张**（显式排除 `rag_inspection_record`） | 其余 6 张表的 INSERT/UPDATE 面不得变化 |
| **③b 抽检记录只追加** | 必须有 INSERT；UPDATE / DELETE / TRUNCATE **必须全为 false** |

这样「新增一格能力」被精确地限在 INSERT 上，任何夹带 UPDATE 的尝试会被 ③b 拦下。

### 2.3 `deploy/sql/README.md`

补充执行纪律：**04 是「先 REVOKE ALL 再 GRANT」的自收敛脚本，授权变更只改 04 并重跑**，
不要手工 `GRANT`（手工授权不会被 REVOKE 收敛掉，表现为「改了脚本却仍漂移」）。

---

## 3. 执行方式

> ⚠️ **必须用库 owner（`ai_agent`）执行**。
> 用 `rag_ops` 自己跑 `GRANT` 会被**静默忽略**——它既不是表 owner 也不是其成员，
> 却能不报错地跑完（本次实测踩到：`GRANT` 报 OK，`has_table_privilege` 仍是 false）。

```bash
# 整脚本重跑（自收敛，可重复执行）
psql -h <host> -U ai_agent -d study_rag -v ON_ERROR_STOP=1 \
     -v rag_ops_password='<口令>' -f deploy/sql/rag/04_rag_ops_role.sql

# 复核（必须 13 项全绿，含新增 ③b）
scripts/check-rag-ops-role.sh
```

### 增量执行（只为已存在的环境补这一格）

若不便整脚本重跑，最小等价操作是**一条**授权：

```sql
-- 以库 owner 身份执行
GRANT INSERT ON rag.rag_inspection_record TO rag_ops;
```

⚠️ 不要顺手给 UPDATE/DELETE：那会让抽检记录可被改写，等于伪造审核证据。

## 5. 与「不再新增增量脚本」纪律的关系

`deploy/sql/README.md` 明确写着「不要再新增增量 patch 脚本」，
因此**本次没有新建 `07_*.sql`**，而是把变更收敛进既有的自收敛脚本 `04_rag_ops_role.sql`。

授权类变更与结构类变更不同：它天然是「先 REVOKE ALL 再 GRANT」的**终态声明**，
重跑即达成目标状态，不需要迁移链。

---

## 6. 遗留事项

- 本变更**只涉及授权，不涉及表结构**，因此 `01_rag_ddl.sql` 终态快照无需改动。
- `rag.rag_inspection_record` 的建表语句本就存在于 `06_v1_0_2_s3_alter.sql` 与活库中，无需迁移。
