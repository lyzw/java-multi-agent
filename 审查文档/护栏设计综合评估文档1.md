# 护栏（Guardrails）设计综合评估文档

> **评估对象**: `cn.studykid.multiagent` 平台（platform / agent-* 模块）
> **技术基线**: Spring Boot 4.1.1 · PostgreSQL 17（RLS）· Java 21 · RabbitMQ 4.3.6
> **参照系**: OWASP LLM Top 10 · NeMo Guardrails · Azure AI Content Safety · Lakera
> **评估日期**: 2026-10-30
> **评估依据**: 源码静态审查（platform 8 模块 + deploy/sql）+ 架构评审报告

---

## 一、总体结论

### 1.1 核心判断

本平台的护栏是一套以 **「纵深防御 + fail-closed」** 为核心纪律、覆盖 **租户隔离、能力授权、资源控制、可观测审计** 四类的成熟设计，工程完成度远高于一般自研 Agent 框架。其**骨架与纪律是一流水准**：

- **租户隔离**: `TenantContext` + `TenantSessionBinder` 钉会话变量 + PostgreSQL `FORCE RLS` 双层，全仓库统一遵循；
- **能力闭环**: `PermissionResolver` → `InvocationValidator` → `ToolInvocationGate` 的全链路「谁能调用哪个工具/参数/风险上限」判定，与委派边界（深度/次数/超时/预算）配合严密；
- **资源与生命周期**: 限流、预算（执行前原子预留）、背压、超时、租约恢复、零保留擦除、追加即写审计一应俱全且多数已接调用链；
- **fail-closed 纪律**: 未知风险、授权不可用、缓存失效、超时缺省均默认拒绝。

**但存在三类会动摇护栏有效性的结构性缺口**，使当前状态从「生产可用」降为「演示可用」。

### 1.2 量化总览

| 维度 | 数量 | 说明 |
|------|------|------|
| 护栏层次 | 5 层 + 横切纪律 | 接入 / 控制面 / 运行时安全 / 资源生命周期 / 数据面 |
| P0 结构性高危缺漏 | **3 项** | 默认态不成立 |
| P1 运行时安全/合规缺口 | **4 项** | 输出安全、注入拦截、审批断链、幻觉窄化 |
| P2/P3 细节/可观测缺口 | **5 项** | 超时、审计、限流、Schema 漂移等 |
| 代码级缺陷（独立发现） | **5 项** | sanitize 黑名单、flatten 数据丢失、循环引用等 |

## 二、护栏整体架构（分层模型）

### 2.1 五层架构

```
┌─────────────────────────────────────────────────────────────────┐
│  L0 接入层：认证/JWT · 限流 · 零保留闸门 · 租户上下文建立        │
│  L1 控制面：PermissionResolver · AgentOverrides ·               │
│            InvocationValidator · ToolInvocationGate ·           │
│            DelegationGuard · MCP/HTTP 网关(SSRF)                │
│  L2 运行时安全面：PromptGuard(注入) · HallucinationDetector(编造)│
│                  RiskEvent(观测) · Approval(HITL) · DecisionAudit│
│  L3 资源与生命周期：预算 · 背压 · 超时 · 租约恢复 · 零保留擦除   │
│                   · 追加审计                                    │
│  L4 数据面：TenantSessionBinder + TransactionalConnectionHolder  │
│            + FORCE RLS + 显式 WHERE tenant_id                  │
│  横切纪律：fail-closed · 审计可追溯 · 不可信数据包裹             │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 与主流护栏框架的对位

| 维度 | 本平台 | 主流参照（NeMo / Azure / Lakera） |
|------|--------|-----------------------------------|
| 租户数据隔离 | **双层 RLS + 绑定 + 构建门禁**（实现强，默认态危险） | 普遍弱 |
| 输入/Prompt 注入 | 净化 + 边界硬拒；**检测只观测不拦截**；工具结果净化分叉 | NeMo input rails · Lakera |
| 工具/动作授权 | 精细闭包设计完备，但**默认关闭**，生产走粗粒度 | NeMo action guardrails |
| 输出内容安全 | 仅供应商侧过滤；**平台侧无 moderations**，敏感输出只观测 | Azure Content Safety · OpenAI Moderation |
| 幻觉/事实性 | 仅引用正则；无 RAG grounding；可绕过 | RAG grounding · NeMo factuality |
| HITL 审批 | 判定健全；**运行时人工审批未接线** | 主流 agent 框架 |
| 资源控制 | 四项齐备且接链；超时非抢占、限流仅入口 | 主流成本/速率护栏 |
| 可观测/审计/擦除 | 追加审计 + 决策审计 + 零保留擦除齐备；审计「不可篡改」依赖 GUC | OWASP LLM 治理 |

## 三、关键机制详述

### 3.1 租户隔离（L4 数据面）

`TenantContext` 为不可变 record，租户标识只从可信认证上下文推导。`TenantSessionBinder` 用 `set_config('app.tenant_id', ?, true)` 强制绑定到连接上（每次取连无条件重置，防连接池串租户）。`TransactionalConnectionHolder` 用 `ThreadLocal` 复用/自开连接，顺序为「先 setAutoCommit(false) 再 bind」。持久化层 42 张租户表均有 `FORCE ROW LEVEL SECURITY` + 对称读写策略。

**角色模型**: `app_agent`（NOBYPASSRLS，运行时角色）/ `platform_ops`（BYPASSRLS，仅运维发布通道，由 `GuardedPlatformOpsDataSource` + `PlatformOpsSessionGuard` 包裹）/ `ai_agent`（迁移/owner，**带 BYPASSRLS**）。

### 3.2 能力闭环（L1 控制面）

`PermissionResolver.build()` 计算 Agent→Skill→{Tool, MCP} 的 `EffectiveClosure`，深度上限 8，含环检测；`AgentOverrides` 仅能收紧（移除 Skill/工具/风险上限）；未知风险 `continue` 剔除（fail-closed）。`InvocationValidator` 校验：授权版本新鲜度 → 闭包解析 → Skill/Tool 声明 → 风险上限 → MCP 绑定 → 参数策略 → 指纹。委派经 `DelegationGuard` 五步闸门（深度/次数/超时/预算/逐跳授权），父子权限互不继承。

### 3.3 运行时安全（L2）

`PromptGuard`：用户输入包裹 `<user_input>`，`sanitize` 剥离零宽/ANSI/控制符，长度/深度/元素硬上限。`detectSuspicious` 命中只打 WARN。`HallucinationDetector.assertNoFabricatedSource` 在终答阶段校验「编造引用」正则，命中即 `commitFailure` + 发射 `SAFETY_BLOCK`。`RiskBasedApprovalPolicy` 按风险等级判定是否需人工审批。

### 3.4 资源与生命周期（L3）

**限流** `JdbcRateLimiter`：判定+计数同条原子 SQL。**预算**：执行前原子预留，UNKNOWN 不释放待对账。**背压** `BackpressureController` 滞回状态机，探测失败=fail-closed 停发。**超时** 每轮开头查 `deadlineAt()`，`maxSteps` 兜底。**租约/恢复** `FOR UPDATE SKIP LOCKED` + fencing_token 双保险。**擦除** 真删/置空+凭证。**审计** 追加即写由 DB 触发器强制。

### 3.5 横切纪律

全链路 **fail-closed**：授权不可用=拒绝；未知风险不降级；默认-拒绝；不可信数据包裹。

## 四、缺漏 / 错误 / 不完善（按严重度）

### 4.1 P0 — 结构性高危（默认态不成立）

#### P0-1: 精细能力闭环默认关闭

**位置**: `ApplicationConfiguration.java:1672-1675`，`ToolInvocationGate.java:515-521,1089,1556-1564`，`RoleBasedAuthorizationService.java:101-115`

**问题**: `cap-authorization-enforced` 默认 `false`，`ToolInvocationGate` 路由到 `invokeAllLegacy`；legacy 的 `isAuthorized(systemContext, TOOL_INVOKE, toolName)` 中 `systemContext` 携带 `WORKER` 角色（恒含 TOOL_INVOKE），而 `RoleBasedAuthorizationService` **从不引用 resourceId（工具名）**。结果：**任何已注册工具对该租户任何 Agent 均可被调用**，模型闭包（声明工具/风险上限/参数策略）在执行点不被校验。

**影响**: 主流「最小权限工具护栏」失效。是「呈现层限制、强制层未校验」的典型缺陷。测试注释（`DelegationGateBranchTest`）已自认 LEGACY=生产默认路径。

#### P0-2: 租户隔离被静默绕过

**位置**: `deploy/sql/README.md:273-280`，`JdbcStatisticsRepository.java:44-46`

**问题**: 主数据源在 dev（及按 `platform.env` 模板的配置）使用带 `BYPASSRLS` 的 `ai_agent` 角色，**RLS 在主链路完全失效**，仅剩各仓库显式 `WHERE tenant_id` 兜底。平台侧**缺少启动时拒绝 BYPASSRLS 角色的自检**（RAG 侧有 `RagStartupSelfCheck`，平台侧无）。

**影响**: 任何「只依赖 RLS」的查询会跨租户泄漏；且测试以 `app_agent`（NOBYPASSRLS）跑全绿，产生「隔离生效」的**虚假安全感**。

#### P0-3: 零保留闸门硬编码 SYNTHETIC

**位置**: `RunController.java:137-141`，`ZeroRetentionGate.java:47-49`

**问题**: `RunController` 把 `DataClassification` **硬编码为 SYNTHETIC**，`ZeroRetentionGate.assertAllowed` 内 `if(!classification.containsRealStudentData()) return;` 使真实学生数据分支整段被跳过。且闸门**仅在 API 入口**，Worker/子 Agent 执行层完全不经过。

**影响**: 合规闸门形同虚设——接入真实数据时不会自动生效。对照 PIPL/未成年人保护属高危缺位。

### 4.2 P1 — 运行时安全/合规缺口

#### P1-1: 输出侧内容安全缺失

**位置**: `RunExecutionLoop.emitSensitiveOutputIfHit`（~:699-718）

**问题**: 全仓**无平台侧** PII/毒性/越狱/违规内容过滤服务。`SENSITIVE_OUTPUT` 风险事件**只观测不阻断**：命中后内容仍 `commitSuccess` 正常返回用户。唯一的「内容安全」是 LLM 供应商自带的模型侧过滤。

**影响**: 对照 Azure Content Safety / OpenAI Moderation / NeMo output rails 均有输出侧 moderations。本平台对含身份证号的输出「照常下发，仅后台记一笔」。

#### P1-2: Prompt 注入仅观测 + 工具结果净化分叉

**位置**: `RunExecutionLoop.renderInput`（~:797-815），`ToolOutcomeRenderer.java:113-127`，`PromptInjectionRedTeamTest` R-7

**问题**: ① `detectSuspicious` 命中只打 WARN 不拦截。② 红队测试 R-7 验证的 `PromptGuard.wrapToolResult`（结构化 `trust="untrusted"` 标记 + 净化）**在生产主路径无调用方**；真实工具结果走 `ToolOutcomeRenderer.outcomeText`，仅加自然语言前缀 + 8000 字符截断，**未调用 sanitize，无结构化标记**。测试验证的是死代码 → 虚假保证。

**影响**: 对照 Lakera/NeMo input rails：缺**主动拦截**；零宽字符注入载体未被剥离；工具结果「不可信」仅依赖一句自然语言提示。

#### P1-3: 运行时人工审批未接线

**位置**: `WorkerExecutionConfig.java:224-226`，`RiskBasedApprovalPolicy.java:165-167`

**问题**: `approvalSource()` 返回空 `PolicyEngineApprovalSource`（空 map → 全部 `FAIL_CLOSED`）。任何 `WRITE_EXTERNAL` 副作用工具在运行时**永被拒绝**，但 `agent-api` 的 `ApprovalController` 人工决策端点操作的是**另一条链路**（能力/配置发布域），**不覆盖工具副作用执行域**——无活体人工放行通道。

**影响**: 判定「谁需审批」健全，但「运行时 HITL」缺位。要么接上，要么明确产品决策（全拒=安全默认）并文档化+加开关。

#### P1-4: 幻觉检测窄且可绕过

**位置**: `HallucinationDetector.java`，`RunExecutionLoop.java:448-462`

**问题**: 仅校验「编造引用/出处」（8 条正则黑名单），**纯事实性幻觉**（给出错误知识点但不引用出处）完全不检测；且只在终答阶段、中间步骤不校验。可构造「如我们教材所言」这类不命中规则的表述绕过。

**影响**: 对照 RAG grounding / NeMo 事实护栏：本平台 DEC-5 无 RAG，故「输出接地」整体缺席，仅靠引用正则。

### 4.3 P2/P3 — 细节与可观测性缺口

#### P2-1: 超时非抢占 + 缺省无超时

**位置**: `RunExecutionLoop.java:359-368`

**问题**: 超时检查只在**每轮迭代开头**，单次长调用（模型/工具）不会被中断；`if(task.deadlineAt()!=null …)` 表示**未传 timeoutMs 则完全跳过超时检查**，仅依赖 maxSteps+租约续期。

**影响**: 单步长调用可越过根截止；需确认创建路径强制 timeoutMs。

#### P2-2: 审计「不可篡改」依赖可自设 GUC

**位置**: `01_platform_ddl.sql:4236-4239,528-552`

**问题**: 审计追加即写由触发器 `forbid_audit_mutation()` 强制，但其放行 DELETE 的条件是会话声明 `agent.retention.actor` GUC——DDL 注释自承「任何持有 DB 凭据的会话都可自行 set_config」。真正的防线在 DB 凭据隔离，而非触发器本身；`erasure_certificate` 亦可用同通道删。

**影响**: 「不可篡改」是条件性的；持有 DB 凭据者（含潜在 SQL 注入上下文）可删审计行。

#### P3-1: 限流与恢复的细节

**位置**: `JdbcRateLimiter.java` / `RunEventController.java:128` / `01_platform_ddl.sql:5295` / `RunRecoverySweeper.java:96-103`

**问题**: ① 固定窗口（非滑动）边界突发；② 仅 API 入口限流，Worker 执行层无限流；③ `RunEventController` 残留 `NEVER_LIMIT` 测试桩；④ `rate_limit_bucket` 策略直接用 `current_setting` 未走 `current_tenant_id()` 函数；⑤ `RunRecoverySweeper` 在 `PlatformTenantPort` 不可用时只 WARN 静默关闭崩溃恢复。

#### P3-2: Schema 漂移风险

**位置**: `PlatformDdl.java:15-17`；`db/migration` 仅含 `verify/`

**问题**: 迁移链已删，schema 由 `pg_dump` 快照带外恢复；CI 中无「活库 == 提交快照」强制比对。

**影响**: 结构漂移会使 RLS 策略/CHECK 在运行库与实际不符。

### 4.4 代码级缺陷（独立发现，评审报告未覆盖）

#### BUG-1: PromptGuard.sanitize 是黑名单，存在已知绕过路径

**位置**: `PromptGuard.java:221-242`

**缺漏**: Unicode 同形字（西里尔 а vs 拉丁 a）、组合字符/变音序列、HTML 实体编码、URL 编码、大小写变体（`<USER_INPUT>`）、零宽空格变种（U+2062）、标记属性变体（`<tool_result\ntrust="untrusted">`）均无法被黑名单覆盖。类注释自己承认「这是黑名单，不可能完备」。

**影响**: 攻击者可构造绕过标记隔离的 Prompt 注入载荷。

#### BUG-2: PromptGuard.flatten() 数据丢失

**位置**: `PromptGuard.java:314-338`

**问题**: Map 的 key 完全丢失（只递归 value 不记录路径）；多个数组合并到同一个 `"value"` 键（后写入覆盖前）。扁平化结果完全不可用。

**影响**: 用于「诊断/审计」的扁平化输出数据不可信。

#### BUG-3: detectSuspicious 在 sanitize 之后匹配

**位置**: `PromptGuard.java:198-211`

**问题**: 模式匹配在 `sanitize()` 之后执行。检测应在原始文本上运行以保留可追溯性。

#### BUG-4: safeRender 无循环引用检测

**位置**: `PromptGuard.java:245-288`

**问题**: 递归渲染 Map/List 无循环引用检测，精心构造的循环引用可导致 StackOverflowError。

#### BUG-5: IdempotencyGuard IN_FLIGHT 悬挂无自动恢复

**位置**: `IdempotencyGuard.java:38-43`

**问题**: Worker 崩溃后 IN_FLIGHT 状态不会自动恢复，所有后续重试被挡住，直到人工介入。类注释将此归为 P3 故障恢复，但生产环境中一次 OOM 可导致一批操作永久悬挂。

## 五、优化方案（具体可落地）

### 5.1 P0 — 让护栏在默认态真正成立

#### ① 开启并兜底精细能力闭环

- 生产暴露前：在 `platform.env` / `application.yml` 显式设 `config.flag.cap-authorization-enforced=true`。
- **防回退**：在 `ToolInvocationGate.invokeAll` 的 legacy 分支补「工具名 ∈ 闭包」成员校验作为兜底；或在开关缺失/关闭且未装配 CAP 时 **fail-closed 拒所有副作用工具**，消除「看似授权、实则恒放行」的伪防线。

#### ② 启动自检拒绝 BYPASSRLS 应用角色（仿 RAG `RagStartupSelfCheck`）

```sql
-- platform-bootstrap 启动时执行
SELECT rolbypassrls OR rolsuper FROM pg_roles WHERE rolname = current_user;
-- 若为 true → 拒绝启动（fail-closed），并告警运维改用 app_agent(NOBYPASSRLS)
```

- 同时在健康检查/启动中接入 `AdminTenantRepository.verifyIsolation()`（已有，改为启动+周期自检）。
- 中长期：让主数据源改用 `app_agent`，或将 `ai_agent` 的 `BYPASSRLS` 移除。

#### ③ 零保留闸门按真实分类派生

```java
DataClassification classification =
    DataClassification.fromRequest(request, currentPrincipal); // 不再硬编码 SYNTHETIC
retentionGate.assertAllowed(currentPrincipal.providerId(), requestText(request), classification);
```

- 并把 `ZeroRetentionGate.assertAllowed` 前移到 **Worker 执行层 / 子 Agent 调用前**（不仅 API 入口）。

### 5.2 P1 — 补齐运行时安全面

#### ④ 新增平台侧输出内容安全层

- 在 `RunExecutionLoop` 终答/工具结果回写前接入 moderation（可接 LLM 供应商安全接口或自建 classifier），覆盖 PII/毒性/越狱/违规。
- `SENSITIVE_OUTPUT` 由「只观测」改为**可配置阻断**（默认对未成年人场景阻断并返回脱敏/拒绝）。

#### ⑤ 注入防御升级 + 修复工具结果净化分叉

- `detectSuspicious` 命中对**高置信模式默认拦截**（至少阻断明显指令注入），低置信保留观测。
- 让生产主路径真正调用 `PromptGuard.wrapToolResult`（结构化 `<tool_result trust="untrusted">` 标记 + `sanitize` 零宽/ANSI 净化），并**删除或改写 R-7 死代码测试**，使红队测试覆盖真实渲染器 `ToolOutcomeRenderer`。
- 统一「不可信数据包裹」契约，避免自然语言提示被绕过。

#### ⑥ 运行时人工审批接线（或明确产品决策）

- 将 `agent-api` 的 `ApprovalController` 经 `ApprovalSource` 接入 `ToolInvocationGate` 的 `WRITE_EXTERNAL` 闸门，形成「需要审批→挂起→人工决策→放行」闭环。
- 若产品选择「副作用工具一律禁止」，则**显式文档化**该决策并加开关。

#### ⑦ 幻觉/质量检测扩面

- RAG 落地后接入 `ReferencedContentResolver` 做真实 grounding 校验。
- 当前至少要扩展编造检测规则或接入轻量事实性分类器，覆盖「无引用的事实性错误」。

### 5.3 P2/P3 — 细节加固

- **超时**：确认 Run 创建路径 `timeoutMs` 必填；对单次长调用评估异步 Future + 硬中断。
- **审计不可篡改**：将「受控删除通道」从可自设 GUC 改为**DB 凭据隔离**（独立 retention 角色 + REVOKE 普通会话的删权限）。
- **限流**：Worker 执行层补限流；移除 `RunEventController.NEVER_LIMIT` 桩；统一 `rate_limit_bucket` 策略走 `current_tenant_id()` 函数。
- **恢复**：`RunRecoverySweeper` 在 `PlatformTenantPort` 不可用时由「只 WARN」升级为**可观测告警 + 健康标记降级**。
- **Schema 漂移**：CI 增加「活库结构 == 01_platform_ddl.sql 快照」的比对门禁。

### 5.4 代码级缺陷修复

| BUG | 修复方案 |
|-----|---------|
| sanitize 黑名单 | 升级为白名单策略：只保留 `[A-Za-z0-9._:@-]` + CJK 汉字 + 常见标点，未知字符替换为 `?` 占位符；标记匹配用大小写不敏感正则 + 允许空白变体 |
| flatten 数据丢失 | 重写：用 `prefix` 参数传递完整路径，Map 保留 key，数组用 `[idx]` 下标 |
| detectSuspicious 净化后匹配 | 改为原始文本上匹配，保留审计可追溯性 |
| safeRender 循环引用 | 添加 `Set<IdentityKey>` 循环检测，命中输出 `<cycle>` |
| IN_FLIGHT 悬挂恢复 | 添加 `recoverStaleInFlight(tenantId, staleThreshold)` 方法，由定时任务自动恢复 |

## 七、总结

**一句话总结**: 本平台的护栏「骨架与纪律是一流水准」，但**三处默认态缺位（能力闭环关、BYPASSRLS 绕过、零保留硬编码）把它从「生产可用」拉回到「演示可用」**；而**输出内容安全与主动注入拦截的缺失**，使其相对 NeMo/Azure 这类主流护栏在「防有害内容」维度存在代差。

**优先级排序**:

| 优先级 | 事项 | 预计工作量 |
|--------|------|-----------|
| **P0** | 开启能力闭环 + 防回退兜底 | 2-3 天 |
| **P0** | BYPASSRLS 启动自检 | 1-2 天 |
| **P0** | 零保留闸门按真实分类派生 + 前移到 Worker 层 | 2-3 天 |
| **P1** | 输出内容安全层（moderation） | 3-5 天 |
| **P1** | 注入拦截升级 + 修复工具结果净化分叉 | 3-4 天 |
| **P1** | 运行时人工审批接线 | 3-5 天 |
| **P1** | 幻觉检测扩面 | 2-3 天 |
| **P2** | 超时抢占 + 审计 GUC 隔离 | 3-4 天 |
| **P3** | 限流补全 + 恢复可观测 + Schema 漂移门禁 | 3-5 天 |
| **BUG** | sanitize 白名单 + flatten 重写 + 循环引用 + 悬挂恢复 | 4-6 天 |

**优先修 P0（让默认态成立），再补 P1（运行时安全面），即可达到主流生产级。**
