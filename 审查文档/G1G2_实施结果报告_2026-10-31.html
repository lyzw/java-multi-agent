2. 实施后的运行流程（legacy 路径）

1
ALLOCATE：模型返回后立刻 ledger.register，取得 operationId —— 身份在任何判定之前存在（复用既有 idempotency_key，不新造 UUID）。
2
DECIDE：需审批时先 approvalPort.consume —— 命中 APPROVED 即执行；REJECTED/EXPIRED 直接拒绝（终态结论，不得复活）。
3
REQUEST：无已批准审批 → 登记待办（approval.request，写 PENDING）。登记失败即拒绝，不挂起（挂起的前提是「人能在审批台看到并批准」）。
4
PARK：Run → WAITING_APPROVAL、写 RUN_PARKED 事件、释放租约、让出 worker 线程。
5
RESUME：审批台批准 → ApprovalController#decide 同步唤醒 → claimParkedRunForResume（CAS，世代 +1）→ resume() 用账本里的原始调用重入闸门（不重跑模型）→ 消费已批准审批 → 执行。
6
兜底：RunRecoverySweeper 每轮把挂起超过 parked-timeout-seconds（默认 1800s）的 Run 收敛为 FAILED / APPROVAL_TIMEOUT（工具未执行、无副作用）—— 防「决定已落库但唤醒窗口崩溃」造成的永久挂起。

4. 方案原文被实跑否决的一项（重要）

项内容
方案原文 M0-2 建议「新增部分唯一索引 UNIQUE(tenant_id, operation_id) WHERE state IN ('PENDING','APPROVED')（同 operation 同时只允许一条活动审批）」。
实跑否决 既有测试 GovernanceQueryIT.denyRequiresReason 对同一 operation 插入两条 PENDING（第一条因「拒绝未填理由」被拒，第二条带理由后成功决定）—— 唯一索引直接让该用例失败。 既有语义是「同一 operation 允许多条活动审批，每条独立决定」，而 lockApproval 的 ORDER BY (state='APPROVED') DESC, created_at DESC LIMIT 1 正是为此设计（优先取已批准的那条，否则取最新）。
裁决 只保留 ORDER BY 修复，删除唯一索引。ORDER BY 才是「人批了也不生效」的真正修法；唯一索引与既有语义冲突，且会误伤合法的多条待批。 方案文档已同步更新，防止后人按原文加回。

5. 两处有意的语义变更（G2 的核心，不是缺陷）

场景旧行为新行为红线实质是否改变
需审批且未获批准 工具拒绝 → Run 直接 FAILED 工具挂起（PARK，Run → WAITING_APPROVAL）+ 登记待办 → 人批准后 RESUME 执行 否 —— 工具在任何情况下都不得执行；变的只是 Run 的终态（FAILED → WAITING_APPROVAL）。
审批来源明确 APPROVED （旧链路无来源概念）一律拒绝 权威批准即放行（M2-1 的存在意义：让审批真正能放行） 语义收窄了红线 —— 故新增用例 requiredWithoutAuthoritativeSourceParks 守住「查不到权威结论 → 工具不得执行」这条 Sev-0 断言。
⚠️ 由此带来的运维约束：agent.approval.source.mode=policy-engine 的策略表若被写成「全 APPROVED」＝恒批＝漏洞。已加一致性 fail-closed 校验：source.mode 与 live-source-enabled 错位即拒绝启动（杜绝「以为接上了、实际恒拒/恒批」这类静默失效）。

6. 实连库与全量实跑抓到的缺陷（静态审查发现不了）

缺陷现象与根因处置
jspecify 注解位置 5 处 @NonNull java.util.Set<X> / @NonNull A.B → javac「无法使用 type-use 批注来批注确定作用域结构」。 改为 java.util.@NonNull Set<X> / A.@NonNull B。
快照 ≠ 活库 CAP Skill 三级描述改造同时改了代码与 01 快照，但既没写迁移也没落库 → 48 个 CAP 集成测试整片报 column "content" does not exist。 补 08_cap_skill_def_content.sql 并落库。
INSERT 绑定位次错乱 加 content 列后，content 与 declaredTools 都绑到第 7 位，其后各列未 +1（schema_version 会写进 published_at…）。不报错，静默写坏数据。 逐位核对修正为 content=7 … published_at=17。
fail-closed 被削弱 子代理把 6 处 authzVersions.require() 改成 currentOrInitialize() —— 后者在缺行时补建版本 1 并继续，等于把「该主体从未被授权」从「明确拒绝（AUTHZ_UNAVAILABLE，既有 IT 锁定 S3d）」变成「假设一个版本继续」。 执行期/快照期一律恢复 require；补建只允许出现在写侧。
platform schema 从未授权 角色脚本只授 public schema → platform_ops 与 app_agent 对 platform 域都无 USAGE → 平台审计通道是断的。 补 09_platform_schema_grants.sql（授 platform_ops，不授 app_agent）。
挂起泄漏风险 待办登记失败/未装配登记参数时仍挂起 → 没人能在审批台看到待办 → Run 永久悬在 WAITING_APPROVAL。 requestApproval 改返回 boolean；登记不成功 → 拒绝而非挂起。

7. 残余缺口（勿遗忘）

  • G1 CAP 开关仍 false：数据模型与状态机能力已就位，但 CAP 链路的运行期 HITL 接线依赖 P5 的指针读路径（按方案与纪律，翻转开关属 P5 验收项，本次未翻转）。
  • G2 legacy 路径已通；CAP 路径的运行期接线未做（同上）。
  • G3 04_retention_role.sql（审计凭据隔离）仍未落库 —— 性价比最高，待授权。
  • G4 ai_agent 仍 BYPASSRLS（本次 IT 用它做 admin 夹具，是「造夹具」而非「验隔离」的角色）。
  • G5 输出 moderation 仍是黑名单级 —— 对外不可宣称「内容安全」。
  • G6 无系统提示词泄漏检测（LLM07）。
  • G7 平台级路径无限流。　G9 PlatformOpsSessionGuard 零测试引用。
  • G11 RAG 受 A-008 阻断，LLM04/08 属未覆盖。

8. 验证方式与结论

  • 全量实跑：七模块同一 reactor mvn -o clean verify，带齐 5 个库凭证 + MQ 凭据，实连远程 RDS。
  • 凭证组合（本轮实测有效）： IT_PG_USER=app_agent（受 RLS 约束，验隔离用它）｜IT_PG_ADMIN_USER=ai_agent（表 owner：dropTrigger / dropUniqueIndex / 建角色 / 写 platform schema 都需 owner，platform_ops 不行）｜RABBITMQ_USER/PASSWORD/VHOST（缺 RABBITMQ_PASSWORD → RealBrokerEndToEndIT ACCESS_REFUSED）。
  • 漂移门禁：SchemaDriftIT（活库 vs 01 快照：表集合 + RLS 开关）在本轮 DDL 后仍通过。
  • 新增测试：ToolInvocationGateParkedTest（7 例：挂起语义 / PENDING 拆分 / 拒绝与过期不得复活 / 来源批准即执行）｜ApprovalDecidedWakeupConsumerTest（5 例：唤醒器的四种 fail-closed 分支）｜ArgumentDigestTest（5 例：稳定 / 顺序无关 / 不含原文）｜ApprovalSourceContextTest（3 例：上下文精确放行）｜ApprovalStateMachineHumanDecisionTest（5 例：AWAITING_HUMAN 登记与区分语义）。
