G1 + G2 合并解法：操作标识前移与审批可暂停

让「能力闭环校验」与「人工审批」共用同一个执行前身份，从而把两条恒拒/空转的链路真正接通

日期 2026-10-31 关联缺口 G1（CAP 未启用）· G2（HITL 恒拒） 代码基线 工作区当前未提交变更（1834 例全绿） 性质 结构性改动 · 需评审后再实施

一句话结论：G1 与 G2 不是「两个待办」，而是同一处时间序矛盾的两个出口—— 操作身份 operationId 产生在判定之后，而判定必须发生在执行之前， 人的响应又必然发生在请求之后。三者被压在同一个同步代码段里，于是审批在设计上不可达。 解法是把「一次工具调用」从「一个执行动作」改造成「一个有身份、可暂停、可恢复的意图」， 分四个阶段落地：分配身份 → 请求审批 → 挂起 → 恢复。

⚠️ 阅读前须知：本方案的三个结论会改变既有认知

① 审批台（/api/approvals）的待办队列在生产中结构性为空——全仓没有任何生产代码写入 PENDING 审批行；

② 即使有人注入「全部批准」的审批来源，工具仍然会被拒——因为第二步 consume 查的是同一张表里并不存在的行；

③ CAP 开启后 WRITE_EXTERNAL 会全灭，这不是配置问题——cap_approval 表在物理上无法表示「等待人决定」。

01根因：不是「缺一个 ID」，是四道锁串成的一把死锁

原评估把根因写成「operationId 每次调用动态生成，而判定发生在调用之前」。 实读代码后可以更精确：有四道独立的锁，任意一道都足以让 HITL 恒拒。只挪 ID 只能开其中一道。

#锁代码事实单独后果
E1 身份产生在判定之后 ToolInvocationGate#1096-1114 先算幂等键、ledger.register，才有 registration.operationId()； #1170-1213 的审批消费用的正是它。人无法在「这行已 INSERT、下一行就 consume」之间插入任何决定。 审批窗口 = 0 毫秒
E2 审批来源契约没有调用上下文 ApprovalSource.verdictFor(tenantId, handler) 只拿到租户和工具句柄， 拿不到 runId / 参数 / operationId。任何实现都无法回答「这一次调用是否被批准」， 只能恒 FAIL_CLOSED 或恒 APPROVED（后者是安全漏洞）。 当前装配 WorkerExecutionConfig#approvalSource() 返回空策略。 判无可判
E3 没有代码创建「审批请求」 全仓 INSERT INTO approval 只有 JdbcApprovalRepository#grant 一处， 且直接写 state='APPROVED'；grant 在生产代码中零调用方（仅测试调用）。 而审批台的 decide() 要求当前状态必须是 PENDING。 于是待办队列永远为空，consume 永远返回 NO_APPROVAL。 无行可批 · 无行可放
E4 能力域审批表无法表示「未决」 cap_approval 的 approver_id、decided_at 均为 NOT NULL —— 建表即写死「审批必然已经有人做过」。同时它绑定 closure_fingerprint 与 authz_version，两者只能在 Run 启动后确定，人不可能提前授予。 CAP 原生不支持 HITL

时间序矛盾：一个不可能被满足的因果

所以「把 ID 前移」本身不够

即使把 operationId 提前到模型返回后立刻生成，只要闸门仍然「在同一毫秒内请求并消费审批」， HITL 依旧恒拒——因为没有暂停的位置。方案必须同时提供三样东西：前置身份、可拦截的请求、可恢复的暂停点。

02目标与非目标

目标 本期
  • 操作身份在任何判定之前存在且可被外部引用
  • 「需审批」的调用会生成一条人能看见、能处置的待办
  • 待办未决时 Run 让出资源，不占用 worker 线程与租约
  • 决定到达后 Run 从暂停点继续，不重跑已完成步骤
  • 上述四点全部 fail-closed，且每条都有可反证的测试
非目标 明确不做
  • 不做审批流引擎（多级会签、代理、转交）
  • 不替换 CAP 的发布指针读（G1 的 P5 前提仍是独立工作）
  • 不改「反馈只来自用户显式动作」等既有产品纪律
  • 不为 OPTIONAL 等级引入阻塞（默认仍不阻塞）
  • 不做审批内容的自然语言摘要（本期只显示摘要前缀）

03设计主张：把「动作」改成「意图」

核心是引入一个贯穿四阶段的实体——操作意图（Operation Intent）。 它不是新表：身份就是既有的 tool_operation 行，只是把它提前创建并允许它以 PENDING（已登记、未派发）状态存活到审批完成。

为什么身份用「幂等键」而不是新造一个 UUID

既有幂等键已经是 run_id + [agentRef/] + tool_name + call_id，并且已有 UNIQUE (tenant_id, idempotency_key) 这个租户级唯一约束。这意味着：

  • 同一次调用重放必得同一行——不需要应用侧 UUIDv5，也不需要改列默认值；
  • 登记可以改成 INSERT … ON CONFLICT (tenant_id, idempotency_key) DO UPDATE SET updated_at = now() RETURNING operation_id， 崩溃后重放天然收敛，不会产生第二行；
  • 「身份前移」的真实含义因此是：把 register 的调用时机前移，并允许它在不派发的前提下返回。 这是最小改动，不引入新的 ID 生成规则。
关键澄清：operationId 不必「预先算出来」

只要在闸门内任何判定之前完成登记，operationId 就已存在，审批请求即可在同一事务内绑定它。 真正需要前移的不是 ID 的计算，而是登记的时点，以及让这条记录能停留在 PENDING。

04五个关键决策

D1登记前移 + 允许 PENDING 存活
问题
operationId 与审批消费在同一段同步代码里，审批窗口为 0。
选择
把 ledger.register 从「执行前一刻」前移到「模型返回、进入任何判定之前」，并把它落成的状态从 IN_FLIGHT 改为 PENDING；PENDING → IN_FLIGHT 的迁移推迟到真正调用 handler 之前。 登记改用 ON CONFLICT … RETURNING 幂等收敛。
理由
ToolOperationState 的文档早已写明 PENDING =「已登记幂等键，尚未发出外部调用」， 但 JdbcToolOperationLedger#77-99 直接 INSERT 成 IN_FLIGHT，把这一状态跳过了。 恢复它的真实语义，是 park 能存在的前提。
代价
任何以「非 IN_FLIGHT 即异常」为前提的既有测试需要重新表达；recordResult 的状态机前置条件要放宽为 PENDING/IN_FLIGHT 二者皆可。
D2「请求」与「决定」分离，且一个 operation 只有一行
问题
grant 一次性写 APPROVED，审批台的 decide 只接受 PENDING——两者永远接不上； 且 approval 表没有 (tenant_id, operation_id) 唯一约束，lockApproval 又无 ORDER BY。
选择
新增 requestApproval(...) 语义：写一行 PENDING（approver_id/decided_at 为空， 现有 CHECK 已允许）；人工处置走既有 decide 把它推进到 APPROVED/REJECTED； 同时加 UNIQUE (tenant_id, operation_id)，把「一行 = 一次调用的审批」变成硬约束。
理由
三处不确定同时消掉：待办队列有了真实来源；consume 的择行不再依赖未定义顺序； 「先 PENDING 后 APPROVED」不再可能产生两行而读到旧行。
代价
存量数据可能重复（当前生产无 grant 调用方，实际为空，风险可忽略）；需在 DDL 前做一次重复检查。
D3挂起用「显式状态 + 检查点」，不用「原地阻塞等待」
问题
人在几分钟到几小时后才决定，worker 不可能一直占着线程和租约。
选择
新增 Run 状态 WAITING_APPROVAL；在 run_step 写一条 step_type='TOOL_BATCH_PENDING'、completed_at IS NULL 的检查点， input_payload 存本批 tool calls 原文（含 callId）与 operationId 列表； 随后清空 lease_owner/lease_expires_at，不调用 commitResult。
理由
⚠️ 这条不是优化而是正确性要求：恢复时绝不能重新调用模型——模型不会再返回同样的 callId， 于是幂等键全变，副作用会被重复执行（Sev-0）。检查点让恢复精确落在「工具批次已确定、尚未派发」这一点上。
代价
run_state 是 PG 枚举，需 ALTER TYPE … ADD VALUE（不可回滚）并重建 run_completed_at_consistent CHECK；RunRecoverySweeper 必须显式排除该状态，否则会把「等人」误判为「崩溃」接管重跑。
D4删掉 ApprovalSource 这条并行通道，审批只认一张表
问题
现在有两套审批判定：verdictFor（来源策略）与 consume（数据行）。 两者可以给出矛盾结论——比如来源说「批准」，表里却没有行。
选择
ApprovalSource 降级为纯策略前置判定（只回答「这个工具是否需要人批准」）， 不再承担放行；放行唯一依据是 approval 行被 consume 成功。 PolicyEngineApprovalSource 的 APPROVED 语义直接删除，避免「配置里点一下就能放行副作用」。
理由
「两个真相」是这类缺陷的温床：E2 与 E3 之所以能各自成立而不被测试发现，正是因为存在一条看起来能放行的旁路。
代价
破坏性契约变更（Verdict.APPROVED 消失）；需同步 ApprovalReadinessGuard 的判据与相关测试。
D5CAP 与工具域共用同一张审批表（G1 的真正前置）
问题
cap_approval 与 approval 语义重叠但结构不同；前者物理上无法表示未决， 且绑定闭包指纹/授权版本，只能在 Run 内授予——这就是「CAP 一开，副作用工具全灭」的机制。
选择
保留 cap_approval 作为能力域审计视图（只读），CAP 的 approve() 步骤改为读 approval 表， 闭包指纹与 authzVersion 存入 approval 的扩展字段（本期用 jsonb detail，不新增列）。
理由
只有合并，G2 的暂停/恢复才能同时服务 CAP 链路；否则要写两套暂停逻辑——那必然漂移。
代价
属 M3，依赖 P5 发布指针读落地；本期只预留接口形状，不动 CAP 开关。

建议的验收顺序

M1 全绿后再动 M2；M2 必须以 SYNC 模式上线并跑满一个观察周期，确认「每次 park 都能被唤醒」之后才切 PARK。 否则一旦唤醒链路有洞，表现会是「Run 静默卡死」——比现在的恒拒更难排查。

10风险与未决

#风险说明与缓解
R1Run 静默卡死 决定写入后唤醒事件丢失 → Run 永远停在 WAITING_APPROVAL。 缓解：sweeper 增加「待办已终态但 Run 未推进」的兜底扫描；并对 WAITING_APPROVAL 设置整体超时（超时即 TIMED_OUT）。
R2恢复点歧义 同一 Run 出现两个未完成检查点 → 不知从哪恢复。缓解：应用层断言 + 部分唯一索引 (tenant_id, run_id) WHERE step_type='TOOL_BATCH_PENDING' AND completed_at IS NULL。
R3fencing token 漂移 park 后重新 claim 会拿到新 token，旧 token 的账本写入会被拒。缓解：恢复时统一使用新 token 写账本， 并在 promote 时校验 token 一致。
R4审批台暴露参数 现有 argumentDigest 实际是参数原文。M2 起统一为哈希；但存量行仍是原文 → 需要一次数据清理或标记遗留。
R5枚举不可回滚 WAITING_APPROVAL 一旦加入无法移除。缓解：先在 dev/staging 验证 sweeper/API/前端三处都能处理该状态， 再进生产；前端需先支持展示该状态（否则 Run 列表会显示未知状态）。
R6与 CAP 的双轨期 M2 完成而 M3 未完成时，CAP 链路仍是旧审批语义。缓解：PARK 模式仅在 CAP 关闭时生效， 两者同时开启时启动期 fail-closed 拒绝（守卫里加一条组合校验）。

11需要你拍板的三件事

决策 1 · 挂起模型选哪个

建议：检查点挂起（D3）。备选是「原地阻塞等待（租约续期 + 线程等待）」，优点是零 schema 变更、当天可上线， 缺点是占线程、审批超时即失败、无法跨小时。如果你的场景是「运维在旁边看着点批准」，原地等待其实够用且风险最低； 如果是「审批人几小时后才看」，必须走检查点。

决策 2 · 被拒绝之后 Run 怎么办

建议：把拒绝当失败调用回灌模型，3 次后终止 Run。备选是「直接判 Run 失败」——更简单、更保守，但一次参数不合规的人工拒绝会让整单作废。

决策 3 · 实施节奏

建议：先只做 M1。M1 零行为变化、可独立验收、且能顺手修掉「PENDING 被当 unknown」「择行不确定」「摘要两套口径」三个既有缺陷。 M2 是否现在开工，取决于你对「副作用工具本期是否必须可用」的判断——如果 record_weakness 之外的写外部工具还没上线，M2 可以等。
