# Agent 平台管理控制台 — 前端全流程体验评测报告

**评测对象**：admin-console（React 18 + Ant Design 5 + Vite，独立前端工程）
**访问地址**：http://localhost:5186/admin/
**账号角色**：plat-superadmin（平台超级管理员）
**评测日期**：2026-10-30
**评测方式**：以真实终端用户身份，从登录页开始逐页点击、填表、提交、切换，全程截图 + DOM 断言 + 后端接口交叉验证
**覆盖页面**：13 个功能页 + 登录页 + 租户详情 + 4 个弹窗流程（登录、开通租户、登记 Tool、生命周期变更）

> 证据截图见同目录 `screenshots-2026-10-30/`。
> 本报告只记录**页面实际可观测到的表现**；未实现的功能一律不臆测。

## 一、总体评价

这套控制台在**"数据诚实性"**和**"边界显式化"**两条线上做得明显高于同类后台系统：未采集的指标显示「—」而不是 0，样本不足明确标注，dry-run 因权限拿不到结论时页面直接说「这不是策略有问题」，审计页写明「仅追加，无任何写/删入口」，生命周期弹窗只列合法迁移并说明非法迁移会返回 409。这些承诺经交叉验证基本都兑现了。

主要问题集中在**前端布局工程**和**会话/路由生命周期管理**两侧：多列表格在窄容器下不设列宽、不开横向滚动，导致文字逐字竖排；右侧固定「操作」列压住末尾数据列；路由匹配用前缀比较，导致 `/metrics-entry` 的导航高亮、页面标题、面包屑三者全部指向 `/metrics`；平台会话 15 分钟硬过期且全程零提示，我作为用户在走查中途被直接踢回登录页并丢失现场。

**结论**：核心业务流程（登录 → 开通租户 → 配额 → 生命周期 → 能力目录 → 审计追溯）贯通可用，未发现整页不可用的阻断；但**租户生命周期状态机存在一个无法闭合的断点**，加上多处 P1 级布局缺陷，建议在下个迭代集中修复。

- 风险等级选项双语对照：`READ（只读）`、`WRITE_PROFILE（内部写）`、`WRITE_EXTERNAL（外部写）`。

### 2.2 组件一致性问题

1. **「停用」按钮的危险色三页不一致**（P3）：Skill 目录页是红色 danger 样式，Tool / MCP Server 页是灰色 default 样式。同名同义动作在兄弟页面上视觉权重不同，容易让用户误判风险等级。
2. **页面标题与页内 H1 重复**（P3）：平台用户、平台审计两页，顶部标题与内容区大标题文字完全一致，垂直占用两行。
3. **面包屑用词与页内标题不一致**（P3）：RAG 页面包屑为「RAG 语料管理」，页内 H1 为「RAG 语料数据管理」。
4. **侧栏折叠后 logo 变成「PC」**（P3）：展开态是「平台管理控制台」，折叠态缩为两个字母，「PC」易被理解为 personal computer，语义反而变弱。

### 3.2 阻断点：租户生命周期状态机在 UI 上无法闭合 🔴

**现象**
把租户从 `ACTIVE` 迁到 `DECOMMISSIONING` 后，该行的「生命周期」按钮**直接消失**，且此后无法通过控制台把它推到终态 `DECOMMISSIONED`。

**根因（前后端双向确认）**
- 后端状态机 `TenantLifecycle.java` 明确声明：
  ```
  ACTIVE ──► DECOMMISSIONING ──► DECOMMISSIONED
  PENDING_SETUP ──► CANCELLED
  ```
- 前端 `pages/TenantRegistryPage.tsx:82-99` 的 `nextActions()` 写成：
  ```ts
  default:
    return [] // DECOMMISSIONING / DECOMMISSIONED / CANCELLED：无前端动作
  ```
  把 `DECOMMISSIONING` 当成了终态。`default` 分支同时吞掉了 `PENDING_SETUP → CANCELLED`。
- 后端 `PlatformTenantController` 只暴露 `/suspend`、`/resume`、`/decommission` 三个迁移端点，**没有** `DECOMMISSIONING → DECOMMISSIONED` 的端点。

**矛盾点**：同一个弹窗里的提示语写着「终态（DECOMMISSIONED / CANCELLED）无出边」，言下之意 `DECOMMISSIONING` 是有出边的——但实现里恰好没有出边。页面文案与实现自相矛盾。

**影响**：退役流程一旦启动就停在中途，租户既不终态也不可回收，只能靠带外运维改库。

**修复建议**
1. 后端补 `POST /api/platform/v1/tenants/{id}/finalize-decommission`（校验 `DECOMMISSIONING → DECOMMISSIONED`），或让 `/decommission` 在处置完成后由流程自动推进到终态。
2. 前端 `nextActions()` 补 `case 'DECOMMISSIONING': return [{ value: 'DECOMMISSIONED', label: 'DECOMMISSIONED（退役完成）' }]` 与 `case 'PENDING_SETUP'` 的 `CANCELLED` 选项。
3. 长期做法：后端提供 `GET /tenants/{id}/allowed-transitions`，前端不再硬编码迁移表——当前前后端各写一份状态机，漂移是必然的。

### 3.3 RAG 语料管理后端全量 500 🟠

选中租户后，语料来源列表返回：

> 读取语料来源失败 — 请求失败（500）

直连后端复现（`GET :8081/api/v1/management/sources`）：

| 作用域 | 结果 |
|---|---|
| `X-Rag-Scope: TENANT` + `X-Tenant-Id` | 500 |
| `X-Rag-Scope: PLATFORM` | 500 |
| 不带 scope | 500 |
| `GET /api/v1/management/statistics` | 500 |

→ **RAG 管理面 API 整体不可用**，属后端故障，非前端问题。前端处理正确：红色 Alert + 「重试」按钮，未把失败伪装成「没有数据」。

**不足**：错误文案只有「请求失败（500）」，未区分「服务端故障」与「配置/权限问题」，运维无法据此判断该查哪一侧。建议按状态码分流文案（5xx → 服务端异常，请联系 RAG 服务维护者；4xx → 权限或参数问题）。

### 3.4 路由策略：dry-run 的失败是"设计正确"的 🟢

在 `/admin/routing-policies` 填好 `policyId` 后点「试跑（不提交）」，页面返回：

> 试跑未取得结论 — 平台令牌对租户域端点 /api/cap/config/routing-policies/dry-run 不可达（401/403）：本租户的租户级令牌通道尚未接入平台控制台。这不是策略有问题。

这条提示精准兑现了导航说明里「不会把『没跑成』显示成『没问题』」的承诺，值得肯定。

### 3.5 侧栏折叠后无可发现性 🟠

折叠为 80px 后只剩图标。实测 hover 侧栏图标：**无 tooltip 弹出**（`tooltipObserved: false`），DOM 里菜单项也没有 `title` 属性。对不熟悉本控制台的运维，折叠态导航基本不可用。

**修复**：折叠时用 AntD `Tooltip` 包裹（折叠态常用 `title` 兜底），或至少给 `li` 补 `title={label}`。

### 3.6 路由切换不重置滚动位置 🟠

在「Agent 效果指标」页向下滚动 1000px，再点击「效果数据录入」，新页面**直接停在中段**（首屏看不到页面标题与第一个分区），用户不知道自己在哪。

**修复**：路由变化时 `window.scrollTo(0, 0)`，或在 `Content` 外包一个随 `location.pathname` 重置的 `ScrollRestoration`。

### 3.7 账号身份不可见 🟠

顶栏恒显示泛化的「管理员」，下拉菜单**只有「退出登录」**一项。看不到当前账号名、角色、权限范围，也没有自助改密入口（超管改自己密码只能去「平台用户」页改别人）。

在多管理员并发的平台控制台里，"我现在以谁的身份在操作"是高频需要确认的信息。

### 8.1 P0-1 租户生命周期断头 → 已闭合

**问题**：状态机与 DB 触发器都允许 `DECOMMISSIONING → DECOMMISSIONED` 与 `PENDING_SETUP → CANCELLED`，
但**没有任何端点能执行这两条迁移**；前端 `nextActions()` 也把 `DECOMMISSIONING` 当终态。
结果：租户一旦进入 `DECOMMISSIONING` 就永久停在半路——既推不到终态，也无法回收。

**修复（后端）**

- `PlatformTenantService`：新增 `finalizeDecommissionTenant()`（→ `DECOMMISSIONED`）
  与 `cancelTenant()`（→ `CANCELLED`）。
- `PlatformTenantController`：新增 `POST /api/platform/v1/tenants/{id}/finalize-decommission`、
  `POST /api/platform/v1/tenants/{id}/cancel`。
- **授权复用 `platform.tenant.decommission`**——角色权限矩阵是冻结的，复用既有命名空间
  可让超管与租户生命周期管理员立即获得能力，且不触碰冻结矩阵。
  审计动作则用**独立字符串** `platform.tenant.decommission.finalize` / `.cancel`，
  以便事后区分「启动退役」与「退役收尾」。

**修复（前端）**：`TenantRegistryPage.tsx` 的 `nextActions()` 移为模块级函数并补齐两条迁移，
`confirmLifecycle()` 同步两个分支。

**实测**

- 接口：`ux-review-probe`（`DECOMMISSIONING`）→ `finalize-decommission` → HTTP 200 → `DECOMMISSIONED`；
  新建探针租户（`PENDING_SETUP`）→ `cancel` → HTTP 200 → `CANCELLED`。
- 界面：终态租户不再出现「生命周期」按钮；`PENDING_SETUP` 租户的迁移下拉同时给出
  `ACTIVE（启用上线）` 与 `CANCELLED（取消开通）`（截图 03）。
- 审计：平台审计事件落 `platform.tenant.decommission.finalize` / `.cancel`。

### 8.2 P0-2 RAG 管理面全量 500 → 已打通（两层叠加根因）

**根因 1：RAG 进程跑在被删掉的构建产物上（表现为「所有路径一律 500」）**

- 现象：`/`、`/actuator/health`、`/api/v1/management/sources`，甚至**不存在的路径**
  全部返回同一个 `{"status":500,…}`。连 404 都变成 500，说明异常发生在**路由之前**（Filter 链），
  而不是某个端点的实现问题。
- 定位：运行中的 JVM（IDEA 调试启动）classpath 指向 `rag/*/target/classes`，
  而**这 8 个目录在磁盘上已被删除**（构建产物被清理）。JVM 按需懒加载类，
  文件缺失 → 类初始化失败 → **该类被 JVM 标记为错误类，此后每次访问都抛 `NoClassDefFoundError`**。
- 关键证据：**把 class 文件重新编译回原路径并不能恢复**（错误类不可重新初始化）——
  这也是它「看起来像应用 bug 却始终修不好」的原因。唯一解是重启进程。

**根因 2：平台与 RAG 的 JWT 密钥不同源（表现为 401，且长期掩盖了根因 1）**

- 现象：RAG 进程恢复健康后，所有管理端点返回 **401「令牌无效、过期或受众不符」**——
  尽管平台令牌的 `iss`/`aud` 与 RAG 的期望**完全一致**。
- 定位：平台实例**没有加载 `jwt.env`** → `AuthConfiguration.resolveKeyPair()`
  走「dev profile 启动生成临时密钥对」的分支 → 平台实际签发用的密钥与 `jwt.env` 里
  `RAG_PLATFORM_JWT_PUBLIC_KEY` **不是同一把**
  （运行时 JWKS 公钥指纹 `0deff367522fc36f` ≠ `jwt.env` 公钥指纹 `340be45292284d01`）。
- 该分支的代码注释与 `scripts/dev-backend.sh` 的脚本注释其实早就写明了风险
  （*"缺它 = dev profile 每次启动生成新密钥 → 平台一重启，RAG 配的验签公钥就作废"*），
  但**启动时没有任何提示**，故障只表现为「另一个服务连不上」，排查方向极易被带偏。

**修复**

- 部署方式统一：平台改用 `scripts/dev-backend.sh`、RAG 改用 `scripts/dev-rag.sh`
  （两者自动 source `platform.env`/`rag.env` + `jwt.env`）。
- 后端：`AuthConfiguration.resolveKeyPair()` 在生成临时密钥对时打**启动告警**，
  点名配置键、对端验签键名与后果——不再静默降级。
- 前端：`api/ragClient.ts` 新增 `ragErrorMessage()`，按 4xx / 5xx 分流文案：
  - `401` → 「RAG 服务拒绝了平台令牌（验签未通过…）」并点名 `PLATFORM_JWT_PRIVATE_KEY`
    与 `RAG_PLATFORM_JWT_PUBLIC_KEY` 必须同源；
  - `5xx` → 「RAG 服务内部错误（HTTP n）…这是服务端故障，请查看 RAG 服务日志」；
  - `0`（网络层）→ 「连不上 RAG 服务…请确认 RAG 服务已启动（默认端口 8081）」。
  - ⚠️ 此前通用 fetch 层把 RAG 的 401 归因成「平台令牌对该端点不可达（身份域隔离）」——
    **对 RAG 是错的归因**（RAG 与平台之间并不存在租户身份域边界）。

**实测**：4 个管理端点（statistics / sources / issues / dictionaries）浏览器实测**全部 200**，
页面显示真实空态「全局语料桶还没有来源」而非错误（截图 02）。
