## 一、护栏整体架构与关键机制

### 1.1 架构分层总览

本项目护栏设计遵循 **纵深防御（Defense-in-Depth）** 原则，形成六层防线：

```
┌─────────────────────────────────────────────────────────┐
│  Layer 0: 配置期静态守卫（PublishGuards V1-V10）         │  agent-routing
│  Layer 1: API 入口护栏（PromptGuard + ZeroRetentionGate）│  api / application
│  Layer 2: 授权/能力闭包（PermissionResolver + ForcedSafety）│  application
│  Layer 3: 执行时护栏（DelegationGuard + IdempotencyGuard）│  application / cap
│  Layer 4: 工具调用门禁（ToolInvocationGate）             │  worker
│  Layer 5: 传输层护栏（McpEndpointGuard + McpAddressPolicy）│  infrastructure/mcp
│  Layer 6: 输出不可信封装（UntrustedOutputEnvelope × 3）  │  application/cap
│  Layer 7: 运行时资源护栏（BackpressureController）       │  application/backpressure
│  Layer 8: 合规/数据生命周期（RetentionPurgeService）     │  application/retention
│  Layer 9: 输出质量护栏（HallucinationDetector）          │  application/evaluation
└─────────────────────────────────────────────────────────┘
```

### 1.2 关键护栏逐一解析

#### 1.2.1 PromptGuard（P3-D09 / FR-016）— Prompt 注入防护

**位置**: `application/prompt/PromptGuard.java`

**核心机制**:
- **标记隔离**: 用户输入用 `<user_input>` / `</user_input>` 包裹，工具输出用 `<tool_result trust="untrusted">` 包裹
- **长度/深度/元素数上限**: 默认 8192 字符 / 5 层 / 100 元素，递归前置校验避免 DoS
- **净化（sanitize）**: 剥离 ANSI 转义、零宽/方向控制字符、标记字面量防伪造
- **注入检测 `detectSuspicious()`**: 仅观测不拦截（D-5），避免误杀合法数学题
- **fail-closed**: 超限抛 `PromptRejectedException`，携带枚举原因码

**设计亮点**:
- 明确声明「净化是黑名单不可能完备」，真正兜底是硬上限
- `validateBounds` 在序列化前递归执行，避免大字符串先被渲染
- 注入检测与硬拦截分离，符合教育场景「忽略第 3 小问的负号」合法用例

#### 1.2.2 DelegationGuard（FR-024/FR-025）— 委派守卫

**位置**: `application/orchestration/DelegationGuard.java`

**核心机制**:
- **五步判定顺序（契约化）**: ①授权版本新鲜度 → ②父 Agent 编排声明 → ③目标声明与版本固定 → ④边界（深度/次数/超时/预算）→ ⑤逐跳授权
- **逐跳重新授权**: 每跳用自己的主体上下文与当前 authzVersion 重新判定
- **有效时间预算**: `min(根 Run 剩余时间, 本级 timeoutMs)`，拒绝时返回 0
- **BudgetProbe 必须显式注入**: 不提供默认值（MA-T17）

**设计亮点**:
- 判定顺序保证原因码最贴近根因
- `evaluateWithBudget` 同时返回有效预算，防止「根 Run 超时被架空」
- 编排声明解析失败 fail-closed，不降级成 LEAF

#### 1.2.3 IdempotencyGuard（P2-T2 §5.3）— 幂等守卫

**位置**: `application/cap/IdempotencyGuard.java`

**核心机制**:
- 四种情形全覆盖: 已完成→返回首次结果 / 进行中→返回进行中 / 同键不同参数→冲突 / 存储不可用→fail-closed
- 唯一放行路径: 键不存在（`PROCEED`）
- 优先从结果事件取首次 reasonCode，退回账本状态

#### 1.2.4 McpEndpointGuard + McpAddressPolicy（SSRF 防护）

**位置**: `infrastructure/mcp/McpEndpointGuard.java`, `application/cap/McpAddressPolicy.java`

**核心机制**:
- **解析后校验**: 域名再正常，解析结果落在 `169.254.169.254` 即拒
- **DNS rebinding 检测**: 两次解析结果必须一致，不一致即拒
- **连接地址 = 已校验地址**: 传输层按已校验 IP 集合连接
- **云元数据绝对禁止**: 169.254.169.254 / 169.254.170.2 / fd00:ec2::254 / 100.100.100.200
- **IPv4-mapped IPv6 剥离**: `::ffff:127.0.0.1` 按内层 IPv4 判定
- **按字节比对元数据**: 避免 IPv6 展开形式导致假检查

#### 1.2.5 PublishGuards（V1-V10）— 发布期静态守卫

**位置**: `agent-routing/PublishGuards.java`

**10 道守卫**:
| 编号 | 守卫 | 类型 |
|------|------|------|
| V1/V2 | 文法/目标 ∈ 父声明 | 构造期（不合法造不出） |
| V3 | 词汇表对齐（input_schema 路径+类型） | 拒绝 |
| V4 | 永假规则（DNF 全部子句矛盾） | 拒绝 |
| V5 | 被遮蔽规则 | 拒绝 |
| V6 | 死目标（RULES_ONLY 下无可满足规则） | 拒绝 |
| V7 | 必选子无规则覆盖 | 警告 |
| V8 | 样本回放比对 | 拒绝 |
| V9 | 规则目标必须有样本覆盖 | 拒绝 |
| V10 | DNF 展开超限 | 拒绝 |

#### 1.2.6 ZeroRetentionGate（DEC-10 GATE-1/2）— 合规闸门

**位置**: `core/compliance/ZeroRetentionGate.java`

**核心机制**:
- 按供应商分别判定，不提供「全局已确认」短路
- 合成/模拟数据不受限制（P1 工作模式）
- 纵深防御: 正则检测可识别学生信息（身份证/手机号/学号/邮箱）
- fail-closed: 未登记/未确认/已过期一律拒绝

#### 1.2.7 ToolInvocationGate — 工具调用总门禁

**位置**: `worker/execute/ToolInvocationGate.java`

**执行链**: Schema 校验 → 执行时重新授权 → 幂等键 → 账本 → 审批 → 预算 → 执行 → 账本更新

**关键子护栏**:
- **RiskBasedApprovalPolicy**: 风险等级→审批要求，`maxWith` 单调性合并
- **BudgetPolicy**: 预留额配置期校验，DB 原子条件更新兜底
- **CancelGuard**: 双保险取消（循环级+工具级）

#### 1.2.8 其他护栏

| 护栏 | 位置 | 职责 |
|------|------|------|
| BackpressureController | `application/backpressure/` | 队列深度滞回控制，fail-closed |
| RetentionPolicy / RetentionPurgeService | `application/config/` + `application/retention/` | 数据保留期配置校验+清理 |
| HallucinationDetector | `application/evaluation/` | 编造出处检测（模式匹配） |
| LogContext.sanitize | `application/observability/` | 日志注入防护（白名单净化） |
| McpServerConfigValidator | `application/cap/` | MCP 配置期校验（dynamicDiscovery/传输/endpoint） |
| UntrustedOutputEnvelope × 3 | `application/cap/` | 不可信输出信封化（MCP/HTTP/通用） |
| McpOpAllowlistNormalizer | `application/cap/` | 三态清单规范化（全仓库唯一实现） |

### 1.3 统一设计原则（贯穿所有护栏）

1. **Fail-Closed**: 「拿不准」一律拒绝，无一例外
2. **纵深防御**: 没有单一防线被依赖为唯一防线
3. **配置期 vs 运行期分离**: 静态守卫在发布期完成，运行期只做动态判定
4. **枚举原因码**: 拒绝原因用枚举而非 boolean，便于诊断
5. **单调性约束**: 权限/审批只能收紧不能放松
6. **不可绕过**: 关键入口（如 `ToolInvocationGate`）标注为「唯一入口」
7. **公共实现唯一化**: `UntrustedOutputEnvelope` 一处实现，多处复用

## 二、发现的问题与缺陷

### 🔴 严重（Sev-0/1）

#### 问题 1: PromptGuard.sanitize 是黑名单，存在已知绕过路径

**位置**: `PromptGuard.java` 第 221-242 行

**问题描述**:
`sanitize()` 方法使用黑名单策略（5 条 replace/replaceAll），仅覆盖了 ANSI、零宽字符、C0/C1 控制字符和 4 种标记字面量。类注释自己也承认「这是黑名单，不可能完备」。

**具体缺漏**:
- **Unicode 同形字攻击**: `а` (U+0430 西里尔小写 a) vs `a` (U+0061 拉丁 a)，黑名单无法检测
- **组合字符/变音序列**: `e\u0301` (e + 组合重音) 视觉上 = `é`，但绕过关键词匹配
- **HTML 实体编码**: `&lt;user_input&gt;` 不会被中和
- **URL 编码**: `%3Cuser_input%3E` 不会被中和
- **大小写变体**: `<USER_INPUT>` / `<User_Input>` 不会被中和（`replace` 是大小写敏感的）
- **零宽空格变种**: U+200B（零宽空格）已被覆盖，但 U+2062（不可见乘法符）等不在列表中
- **标记属性变体**: `replace("<tool_result", "[tool_result")` 只匹配精确前缀，`<tool_result\ntrust="untrusted">` 不会被替换

**影响**: 攻击者可构造绕过标记隔离的 Prompt 注入载荷。虽然类注释声明「硬上限才是兜底」，但标记伪造绕过后，模型可能看到「看起来像系统指令」的内容，硬上限只能限制长度不能阻止内容被渲染。

#### 问题 2: PromptGuard.flatten() 方法存在数据丢失 bug

**位置**: `PromptGuard.java` 第 314-338 行

**问题描述**:
`flattenInto` 方法对 Map 和 Iterable 的递归处理有严重缺陷：

```java
// 对 Map 的处理 — 只递归 value，不记录 key
if (value instanceof Map<?, ?> map) {
    for (Map.Entry<?, ?> e : map.entrySet()) {
        flattenInto(e.getValue(), out, depth + 1);  // ← 丢失了 key 路径
    }
}
// 对 Iterable 的处理 — 每个元素都覆盖写入 "value"
else if (value instanceof Iterable<?> it) {
    for (Object o : it) {
        flattenInto(o, out, depth + 1);
        items.add(o);
    }
    out.put("value", items);  // ← 所有数组都写到同一个 "value" 键
}
```

**具体 bug**:
1. Map 的 key 完全丢失 — `{"a": 1, "b": 2}` 扁平化后只剩 `{value=...}`，无法区分来源
2. 多个数组合并到同一个 `"value"` 键 — 后写入的覆盖前面的
3. 嵌套结构中只有叶子节点写入 `"value"`，中间层数据全部丢失

**影响**: `flatten()` 方法用于「诊断/审计使用」，但输出结果是完全错误的，可能导致基于扁平化结果的审计数据不可用。

#### 问题 3: PromptGuard.detectSuspicious() 在 sanitize 之后才匹配模式

**位置**: `PromptGuard.java` 第 198-211 行

```java
public @Nullable String detectSuspicious(@NonNull String text) {
    String sanitized = sanitize(text);  // ← 先净化
    for (Pattern p : SUSPICIOUS_PATTERNS) {
        Matcher m = p.matcher(sanitized);  // ← 在净化后的文本上匹配
        ...
    }
}
```

**问题描述**:
模式匹配在 `sanitize()` 之后执行。这意味着：
- 攻击者用零宽字符分隔关键词（`igno​re\u200B instructions`）→ sanitize 剥离零宽 → 变成 `ignore instructions` → 反而**更容易**命中
- 但反过来，如果 sanitize 改变了文本结构（如剥离 ANSI），模式中的 `(?i)` 大小写不敏感匹配不受影响
- 更关键的是：**sanitize 是黑名单，模式匹配也是黑名单**，两层黑名单串联并不能增加安全性

**影响**: 这不是安全漏洞（因为检测只观测不拦截），但语义上不合理——检测应在原始文本上运行，否则审计日志中记录的是「净化后的文本命中了模式」，而非「原始文本命中了模式」，降低了可追溯性。

#### 问题 4: PromptGuard.safeRender 不处理循环引用

**位置**: `PromptGuard.java` 第 245-288 行

**问题描述**:
`safeRender` 递归渲染 Map/List，但没有循环引用检测。如果用户输入包含自引用结构（如 `Map.of("self", someMap)` 其中 someMap 包含指向自身的引用），递归将无限进行直到 StackOverflowError。

虽然 `validateBounds` 有深度限制，但它在 `safeRender` **之前**调用，且只检查深度不检查引用相等性。一个精心构造的循环引用可以绕过深度检查（因为每次递归都是新的 Map 实例，深度递增），但实际上不会终止。

**影响**: 潜在的 StackOverflowError，导致 Worker 崩溃。

#### 问题 5: IdempotencyGuard 的 IN_FLIGHT 悬挂无自动恢复

**位置**: `IdempotencyGuard.java` 第 38-43 行（类注释）

```java
代价是：上一次尝试若崩溃留下悬挂的 IN_FLIGHT 行，重试会被挡住。
该恢复场景属 P3 的 COMP-* 故障恢复范围，本阶段刻意选择「宁可挡住也不重复执行」。
```

**问题描述**:
Worker 崩溃后，`IN_FLIGHT` 状态的幂等记录不会自动恢复。所有后续重试都会被 `IN_PROGRESS` 挡住，直到人工介入。类注释将此归类为 P3 故障恢复，但在生产环境中，这意味着：
- 一次 Worker OOM 可能导致一批操作永久悬挂
- 没有自动超时恢复机制（如 `IN_FLIGHT` 超过 N 分钟自动标记为 `FAILED`）
- 没有告警机制通知运维有悬挂操作

**影响**: 可用性风险。P3 级别的故障恢复在 P1 生产环境中可能升级为 P2。

### 🟡 中等（Sev-2）

#### 问题 6: LogContext.sanitize 白名单过于严格

**位置**: `LogContext.java` 第 206-219 行

**问题描述**:
白名单只允许 `[A-Za-z0-9._:@-]`。这意味着：
- **中文 traceId / 租户名** 会被全部丢弃 → 返回 `NONE` → 日志中出现 `-`
- 空格、连字符以外的标点、中文、emoji 全部被丢弃
- 对于包含中文的 `principalId`（如中文姓名），净化后可能变成空串

虽然 traceId/tenantId/principalId 预期是英文标识符，但 `principalId` 可能来自用户输入（如姓名），白名单过于严格可能导致信息丢失。

**影响**: 中文环境下的日志上下文可能丢失有用信息。

#### 问题 7: BackpressureController 缺乏 warm-up 机制

**位置**: `BackpressureController.java`

**问题描述**:
控制器启动时 `lastDepth = -1`，首次调用 `allowPublish()` 会探测队列深度。但如果首次探测时队列已经处于高水位，系统会立即进入降级状态，没有 warm-up 期。

**影响**: 服务重启后可能立即进入降级，即使队列深度在正常范围内波动。

#### 问题 8: McpEndpointGuard 的重定向处理未在代码中显式可见

**位置**: `McpEndpointGuard.java`

**问题描述**:
类注释声明了「禁止未经授权 HTTP 重定向跳内网/云元数据；每次连接与重定向重新校验目标地址」，但 `McpEndpointGuard` 本身没有重定向处理逻辑。重定向校验依赖于传输层（如 `HttpBackedToolHandler`）在每次重定向时**主动调用** `validate()` 方法。

代码中没有强制机制保证「每次重定向都重新校验」，如果传输层实现者忘记在重定向时调用 `validate()`，SSRF 防护就被绕过。

**影响**: 设计正确但实现依赖人工遵守约定，缺乏编译期/运行期强制。

#### 问题 9: 两套风险等级枚举并存可能引发混淆

**位置**: `core/config/ToolRiskLevel.java` 与 `core/cap/CapabilityRiskLevel.java`

**问题描述**:
`ToolRiskLevel`（旧平台）与 `CapabilityRiskLevel`（新统一配置）是两套并存模型：
- `ToolRiskLevel.resolve()` 对未登记工具降级为 `WRITE_EXTERNAL`（fail-closed）
- `CapabilityRiskLevel.parse()` 对非法值返回 `UNKNOWN`（不降级）
- 二者的语义不同但命名相似，容易混淆

类注释中已有警告，但代码中没有编译期强制隔离机制。

**影响**: 开发者可能误用枚举，导致安全判定不一致。

#### 问题 10: HallucinationDetector 的正则规则存在误报/漏报

**位置**: `HallucinationDetector.java`

**具体问题**:
- **H-1c `p[0-9]{1,4}`**: 匹配「page 42」这类正常英文表述，误报率高
- **H-3「根据检索结果」**: 正常教学场景中「根据检索到的资料」是合法表述
- **H-1d 图/表引用**: 「如图 3-1 所示」是数学题中的正常表述
- 缺少对「人教版」等教材名的大小写变体覆盖

**影响**: 误报可能导致合法输出被阻断（fail-closed），漏报则编造出处未被检测。

### 🟢 轻微（Sev-3）

#### 问题 11: PromptGuard.flatten() 的 depth 参数语义不一致

`flattenInto` 中 `depth > maxDepth` 时直接 return（不抛异常），但 `walk` 中同条件抛异常。同一类中两种深度处理语义不一致。

#### 问题 12: RetentionPurgeService 的 `monthsAgo` 实现注释与代码位置不匹配

注释提到「实测缺陷 F-12」，但修复代码 `now.atZone(WINDOW_ZONE).minus(months, ChronoUnit.MONTHS).toInstant()` 位于 `RetentionPurgeService`，而 `RetentionPolicy` 中可能还有类似问题未被检查。

#### 问题 13: 部分护栏缺少单元测试覆盖

- `McpAddressPolicy` 的 `isAbsolutelyForbidden` 和 `metadataAddressOf` 方法缺少对 IPv6 元数据地址的测试

- `CapabilityRiskLevel.stricter` 的 UNKNOWN 分支缺少测试

## 三、优化方案

### 3.1 严重问题修复方案

#### 修复 1: PromptGuard.sanitize 升级为白名单 + 黑名单混合策略

```java
// 方案 A: 白名单优先——只保留已知安全字符
public @NonNull String sanitize(@NonNull String raw) {
    StringBuilder sb = new StringBuilder(raw.length());
    for (int i = 0; i < raw.length(); i++) {
        char c = raw.charAt(i);
        // 白名单: 可打印 ASCII + 中文 + 常见标点
        if ((c >= 0x20 && c <= 0x7E) ||           // ASCII 可打印
            (c >= 0x4E00 && c <= 0x9FFF) ||       // CJK 统一汉字
            (c >= 0x3000 && c <= 0x303F) ||       // CJK 标点
            (c >= 0xFF00 && c <= 0xFFEF)) {     // 全角字符
            sb.append(c);
        } else {
            sb.append('?');  // 替换为占位符而非静默丢弃
        }
    }
    String result = sb.toString();
    
    // 黑名单兜底: 标记字面量（大小写不敏感 + 变体）
    result = result.replaceAll("(?i)<\\s*user_input\\s*[\\/]?", "[user_input]");
    result = result.replaceAll("(?i)<\\s*tool_result\\b", "[tool_result");
    
    return result;
}
```

**关键改进**:
1. 白名单策略：只保留已知安全字符范围，未知字符替换为 `?`（可追溯）
2. 标记匹配使用大小写不敏感正则 + 允许空白字符变体
3. 保留原始长度信息（通过 `?` 占位），便于审计

#### 修复 2: 重写 flatten() 方法

```java
private void flattenInto(Object value, Map<String, Object> out, int depth, String prefix) {
    if (depth > maxDepth) return;
    if (value instanceof Map<?, ?> map) {
        for (Map.Entry<?, ?> e : map.entrySet()) {
            String key = String.valueOf(e.getKey());
            flattenInto(e.getValue(), out, depth + 1, 
                prefix.isEmpty() ? key : prefix + "." + key);
        }
    } else if (value instanceof Iterable<?> it) {
        int idx = 0;
        for (Object o : it) {
            flattenInto(o, out, depth + 1, prefix + "[" + (idx++) + "]");
        }
    } else {
        out.put(prefix.isEmpty() ? "value" : prefix, value);
    }
}
```

## 四、总结评估

### 4.1 整体评价

本项目的护栏设计**整体质量很高**，体现了成熟的安全架构思维：

**优点**:
1. **纵深防御体系完整**：从配置期到运行期、从输入到输出、从合规到资源，全链路覆盖
2. **Fail-Closed 原则贯彻彻底**：几乎所有护栏都遵循 fail-closed，没有发现 fail-open 路径
3. **设计文档与代码高度一致**：类注释中大量引用设计文档章节号，代码即文档
4. **公共实现唯一化**：`UntrustedOutputEnvelope` 一处实现多处复用，避免漂移
5. **枚举原因码**：拒绝原因全部使用枚举而非 boolean，便于诊断
6. **可测试性**：护栏依赖注入接口，单测可注入桩实现

**主要风险**:
1. `PromptGuard.sanitize` 的黑名单策略是已知弱点，需要升级为白名单
2. `flatten()` 方法的数据丢失 bug 可能影响审计可用性
3. `IdempotencyGuard` 的悬挂恢复需要从 P3 提升优先级
