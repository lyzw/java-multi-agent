## 1 · 判定口径与原则

本轮修复遵守四条原则，写在代码注释里，也写在这里：

1. **fail-closed 优先于可用性** —— 解析不出、查不到、预留被拒，一律拒绝执行。唯一例外是「未配模型单价」，代价是**成本按 0 记但 token 如实记录并打 WARN**：缺配置必须可见，而不能把「漏配」静默变成「这次调用不存在」。用可见性换可用性在这里比反过来划算。
2. **不静默改变既有契约** —— 每个新开关都有默认值且默认**不改变当前线上行为**；需要改变行为的场景（闭包 enforce）通过显式开关 + 显式开启步骤完成。
3. **不制造假防线** —— 「呈现层裁剪了 Schema」不等于「强制层校验了闭包」；「登记了待办」不等于「审批通过」。文档与代码必须择一对齐，不能两头留着。
4. **测试替身与生产路径同形** —— 测试替身的读写计数、不可用语义随生产读路径同步调整，避免出现「测试验证的是另一条分支」这种自欺。

## 2 · P0 修复逐项明细

### 2.1 P0-1a · 能力闭包校验进入强制层（默认链路）

#### 原状

`ToolInvocationGate.invokeAllLegacy` 里 `grep closure` **零命中** —— 既有链路完全没有闭包校验。legacy 授权只判角色不判工具名（`RoleBasedAuthorizationService` 从不读 `resourceId`），上下文硬编码 `principal="worker", roles={WORKER}, authzVersion=0`，而 `WORKER` 持有 `TOOL_INVOKE`。结论是：**任何已注册工具都可被任意 Agent 调用**。闭包只在呈现层生效（`AgentModelConfigAssembler` 按闭包裁剪给模型看的 Schema），强制层没有这道校验。

#### 改动

**新增** `platform/agent-worker/src/main/java/cn/studykid/multiagent/worker/execute/CapabilityClosureGuard.java`

- `Mode = OFF | WARN | ENFORCE`（`:57-77`）：非法值按 `WARN` 处理（**不得静默放行**）。
- 解析路径：按 `CapabilitySnapshotPort.find(tenantId, runId)` → `ClosureResolver.resolveCurrent` 定位根 Agent 闭包；子 Agent 走 `scope.agentId() / agentVersion()` 固定 release，避免用「当前发布头」误判历史 Run。
- **闭包解析不出来 → 一律按「未声明」处理（fail-closed）**（`:134`）：无法证明「已声明」就不能放行。
- `denyOrWarn`（`:189-194`）：`ENFORCE` 下拒绝；`WARN` 下放行但打 `SECURITY` 级 WARN —— 把「能力目录未装载」这个缺口变成**可见**的，而不是悄悄放行。

**接入点** `ToolInvocationGate.java:1150-1169`

- 插在 `findHandler` **之后**、Schema 校验**之前**：既区分「未登记工具」与「越权调用」两个拒绝原因，又在真正执行前拦（不必走完校验/授权/审批/预算）。
- 拒绝原因文案含「无权」，以对齐 `RunExecutionLoop.isAuthorizationDenial` 的 SEC-2 归类（否则会被统计成普通工具失败）。
- `ToolInvocationGate` 新增 `closureGuard` 字段（`:133`）与「最完整构造器」（`:499`）；既有构造器传 `null` = 保持历史行为。

**装配** `WorkerExecutionConfig.java:316` 新增 `capabilityClosureGuard` Bean，读 `config.flag.cap-closure-enforcement`（默认 `warn`）；非 enforce 时打 SECURITY WARN。

#### 为什么默认是 `warn` 而不是 `enforce`

闭包判定的输入是**能力目录**（`cap_tool_def` / `cap_skill_def`）。当前 live DB 里这两张表**都是 0 行**（实测 `cap_tool_def=0, cap_skill_def=0, cap_agent_def=0, cap_config_pointer=0, cap_config_release=0, cap_authz_version=0, execution_capability_snapshot=0`）。目录为空时 `enforce` 会把**所有**工具调用拒掉 —— 那不是「校验生效」，是「平台不可用」。所以本轮的做法是：

- 默认 `warn` → 缺口可见、可观测，不炸平台；
- 装载能力目录后 → 切 `enforce` + 开 `cap-enforcement-required` → 真正关闭这个洞；
- 两条通路都没开时 → 可选硬失败拒绝启动（P0-1c）。

#### 测试

`ToolInvocationGateClosureGuardTest`（6 例，全绿）：越权工具被拒且闭包内工具不受影响 / 闭包内工具照常执行 / 解析不出 fail-closed / 无能力快照 fail-closed / WARN 模式只告警 / 子 Agent 用自己的闭包。

### 2.2 P0-1b · `cap_authz_version` 补上生产写入方

#### 原状

六处生产读点全部用 `require()`（缺行即失败），但仓内**没有任何生产写入方** —— 只有测试在写。后果是能力目录一旦装载、读路径一旦真的走到 `require()`，就必然全拒。这是 P0-1 能被「打开」的前置。

#### 改动

**`AuthzVersionPort.java:88`** 新增：

```java
default @NonNull AuthzVersion currentOrInitialize(String tenantId, String principalId)
```

- 先 `find` —— 命中则**只读不写**（不产生无谓的写放大）；
- 缺行才 `initialize` —— `ON CONFLICT DO NOTHING`，**绝不重置既有版本**。

**六处生产读点全部切换**为 `currentOrInitialize`：

| 读点 | 位置 |
|---|---|
| `InvocationValidator` | `agent-application/.../cap/InvocationValidator.java:245` |
| `CapExecutionFlow.phaseA` | `agent-application/.../cap/CapExecutionFlow.java:799` |
| `DelegationGuard.checkAuthzFreshness` | `agent-application/.../orchestration/DelegationGuard.java:268` |
| `DelegationExecutor`（"worker"） | `agent-application/.../orchestration/DelegationExecutor.java:885` |
| `CapDualWriteService`（Run 创建事务内 → 调用主体） | `agent-application/.../cap/CapDualWriteService.java:168` |
| `ExecutionAdmissionChecker` | `agent-application/.../cap/ExecutionAdmissionChecker.java:141` |

`require()` 的严格语义**保持不变**（缺行即失败），它仍是「授权必须存在」的正确表达。

#### 安全性依据

- `initialize` 是 `ON CONFLICT DO NOTHING` → 补建**不会降级**既有版本。
- 平台的撤权语义是 `bump` 递增（不是删行）；仓内**没有**删除 `cap_authz_version` 的路径 → 按需补建不会丢撤权历史。

#### 测试

`AuthzVersionProvisioningTest`（4 例，全绿）：缺行补建 / 撤权版本不降级 / 存储不可用 fail-closed / 幂等。

同时把测试替身同步为真实语义：`CapFixture.authzVersions()` 的 `find`/`initialize` 在 `authzUnavailable` 时**也**抛异常；`BumpingAuthzVersions` 的读次数计数移到 `find`（原先挂在写路径上，与生产读路径不符）。

### 2.4 P0-2 · 审批闭环接通（待办可见）

#### 原状

`ApprovalPort.grant()` 是唯一写入 `approval` 表的入口，**生产代码零调用**（grep 全部命中在 `*/src/test/*`）。审批台读 `approval` 表的 `PENDING` 行 → 永远返回空列表。需要审批的工具（如 `WRITE_EXTERNAL` 的 `tool-parent-notification`）在生产**恒被拒**。

#### 改动

**`ApprovalPort.java:74`** 新增：

```java
default Optional<String> request(tenantId, operationId, argumentDigest,
                                 targetResource, requirement, approverScope, expiresAt)
```

默认返回空（未覆写的实现安全降级），**只登记不放行**。

**`JdbcApprovalRepository.java:157-197`** 实现：

- 单条 `INSERT ... SELECT ... WHERE NOT EXISTS (同 tenant + 同 operation 的 PENDING 行)` —— 由 PG 原子完成，天然幂等（避免审批台出现重复待办，运营要处理同一件事 N 次）。
- **不写「已批准」类的审计**：审计口径是「审批决定可追溯」，登记待办不是决定（真正被决定时由 `JdbcApprovalQueryRepository` 写决定审计）。

**`ToolInvocationGate.java:1306 / 1538-1562`**：

- 审批 verdict 非 `APPROVED` 时 → **先登记待办，再 fail-closed 拒绝**（verdict 为 `REJECTED` 时不登记 —— 被明确拒绝的调用不需要再让人工看一眼）。
- `requestApproval` 辅助方法捕获登记异常并打 ERROR 日志，**登记失败不改变调用结局**（本次调用照样被拒）。
- 外键安全性：`approval.operation_id` 有 FK 指向 `tool_operation(tenant_id, operation_id)`；审批登记发生在 `ledger.register()`（`:1211`，写 `tool_operation` 行并 `RETURNING operation_id`）**之后**，FK 必然满足。

**新增** `agent-application/.../approval/ApprovalRequestSettings.java`：承载 `approverScope` + `ttl`，TTL 下界 1 分钟、上界 24 小时，**超界拒绝启动**（不是静默夹紧）。

**装配** `WorkerExecutionConfig.java:253/289`：读 `agent.approval.ttl` / `agent.approval.approver-scope`，**缺配置即拒绝启动**。

**配置可见性** `ConfigReadService.java:130/132`：两个键的 `effective` 由 `false` 改为 `true`，说明改为「P0-2 已接入运行时」。

#### 语义对齐（文档与代码择一）

`docs/业务架构图.md:155-187` 的 Run 状态迁移表原先把 `WAITING_APPROVAL → QUEUED` 写成既成设计，而代码里这个状态与这条迁移**都不存在**。本轮选择**改文档承认现状**：

- 删去未实现的 `WAITING_APPROVAL` / `RETRYING` 迁移行；

- 加脚注说明「挂起后自动恢复」尚未实现及原因（见 §5.2）。

#### 测试

`ToolInvocationGateApprovalRequestTest`（3 例，全绿）：待办已登记且工具仍被拒 / `REJECTED` 不产生待办 / 未装配登记参数时安全姿态不变。

### 2.5 P0-3a · `maxLlmCalls` 真正被执行

#### 原状

`maxLlmCalls=12` 有配置、有快照字段、有判定方法 `RunConfigSnapshot.allowsLlmCall()`，但**生产代码零调用**（只在 `ConfigFailClosedTest` 里）。`maxSteps=20` 意味着理论上可发起 20 次模型调用，是 `maxLlmCalls` 的近 2 倍，**没有任何一处会拦**。

#### 改动 `RunExecutionLoop.java`

- 新增 `llmCalls` 计数器（`:394-396`）。
- **在发起模型调用之前**判定（`:543-553`）：`!snapshot.allowsLlmCall(llmCalls)` → `commitFailure(..., "MAX_LLM_CALLS")` + `RUN_FAILED` 事件 + 事件载荷带 `errorCode`。
- **仅在调用成功后 `llmCalls++`**（`:615`）—— 失败的调用不占额度（否则一次网络抖动就白白吃掉一次预算，用户体验莫名其妙）。
- 计数与 `steps`（轮次）分离：`:543` 注释明确「steps 数轮次、llmCalls 数模型调用。一轮里可能有多次模型调用」。

#### 失败原因归类

`AgentMetricCollector.deriveFailedReason` 新增 `MAX_LLM_CALLS → TerminationReason.MAX_ROUNDS` 映射（`:196`）。否则它会落进 `OTHER` 黑洞 —— 指标面板上「触顶」和「未知错误」混在一起，等于没有告警。

#### 测试

`RunExecutionLoopLlmCallLimitTest`（3 例，全绿）：恰好调用 N 次 / 未超限不误伤 / 上限为 1。

### 2.6 P0-3b · 模型 token 与真实成本入账

#### 原状

- 预算预留/结算**只发生在工具调用路径**（`ToolInvocationGate.reserve` / `settle`，`CapExecutionFlow`）。
- 结算金额是**固定值** `reserve-per-tool-call = ¥0.50`，与真实成本无关。
- `usage_record.input_tokens` / `output_tokens` **没有任何写入方**（全仓唯一 INSERT 不含这两列）。
- `usage_record.model_id` 存的是**工具名**（如 `record_weakness`），不是模型名。
- 真正的模型 Token 只进了 Micrometer 指标与 run_event 载荷，**没有进任何账表**。
- `maxCostPerRun`（¥2.00）在快照里，但只用于配置展示，**不参与任何拦截**。

#### 改动

**新增单价模型**

- `agent-core/.../core/config/ModelPricing.java`：每千 token 单价，`cost(in, out)`，`HALF_UP` 6 位小数。
- `agent-application/.../application/config/ModelPricingPolicy.java`：匹配优先级 = **精确匹配 → 最长前缀匹配 → `default` 兜底**。查不到返回空（而非「按 0 元」）。`of(Map)` 解析非法值 **fail-closed**。
  - 为什么需要前缀匹配：模型标识常带日期/版本后缀（`gpt-4o-2024-08-06`），只做精确匹配会让「配了价却用不上」。

**端口扩展** `BudgetPort`

- 新增 `default settle(..., long inputTokens, long outputTokens)`（默认丢弃 token，生产覆写）。
- 新增 `default recordModelUsage(...)`（**无预留时的只计量路径**，默认返回 false —— 只记账不扣款）。
- 新增 `TOOL_ROW_PREFIX = "tool:"` 与 `toolRowModelId(toolName)`。

**仓储实现** `JdbcBudgetRepository`

- `insertUsageOnce` 增写 `input_tokens` / `output_tokens`（`:406-422`）。
- `settle` 新增 token 重载（`:311` / `:327`），内部收敛到 `settleInternal`（`:331`）。
- 新增 `recordModelUsage`（`:465-482`）：`operation_id` 存模型调用标识，幂等靠唯一索引 `idx_usage_operation_once (tenant_id, operation_id) WHERE operation_id IS NOT NULL`。
- **工具行与模型行可区分**：工具行 `model_id` 写 `tool:<name>`（`ToolInvocationGate.java:1582`），模型行写真实模型 id。
- `JdbcTraceFactRepository.readUsage`（`:228`）聚合时**优先取模型行**（`min(model_id) FILTER (WHERE model_id NOT LIKE 'tool:%')`，回退整体 min）。

**执行链路** `RunExecutionLoop`

三段式：**预留 → 结算 / 释放**。

| 阶段 | 行为 |
|---|---|
| 预留（`:1075`） | 金额 = 单价 × **保守上界**（输入估算 × 安全系数 2 + `maxTokens`）。多预留的部分在结算时自动退回 —— 预留额**全额扣回、只计实结额**，避免撞 `CHECK (settled <= reserved)`。 |
| 结算（`:1135`） | 按**真实 token** 计价，写入 `input_tokens`/`output_tokens` + 真实 `cost_amount`。 |
| 释放（`:1175`） | 模型调用**失败**时释放预留，避免失败调用白占额度。 |

**拦截**：`maxCostPerRun` 真正参与判定 —— 累计成本超 `snapshot.maxCostPerRun()` → `MAX_COST` + Run FAILED（`:620-635`）；预留被拒 → `BUDGET_EXHAUSTED`（fail-closed，`:577`）。

**幂等键**：`UUID.nameUUIDFromBytes(runId|attempt|ordinal)`（`:1060`）。含 `attempt` 以免同一 Run 重投时命中前一次的幂等键导致**漏记账**。

**未配价模型**：token 如实记录、成本按 0 记并打 WARN（`:1086-1090`）。不 fail-closed —— 拿可用性换可观测性不划算；但**绝不静默**。

## 4 · 本次修复中新增发现（原审查报告未覆盖）

以下是修复过程中实测发现的、原报告没有记录的问题。它们不阻塞本轮 P0，但影响「下一步该做什么」的判断，一并记录：

1. **CAP 目录 id ≠ 运行时 handler 名 —— 两套命名宇宙。**
   `02_platform_seed.sql` 的 seed 用 `tool-profile-read` / `tool-profile-update`，而注册的原生 handler 是 `get_student_profile` / `record_weakness`；`agent-permission-demo/config/skills.json` 的 `declaredTools` 用的却是**运行时 handler 名**。
   → 说明正确约定是：**native 工具的 `cap_tool_def.id` 必须等于 handler 的 `toolName()`**。seed 目前违反此约定，且 `tool-profile-update` 根本没有对应实现。这是「装载能力目录」这一步的前置必修项。

2. **live DB 里两套能力模型并存。**
   `agent_version`=1689 行、`execution_snapshot`=1906 行、`run`=1009 行，而 `cap_tool_def` / `cap_skill_def` / `cap_agent_def` / `cap_config_pointer` / `cap_config_release` / `cap_authz_version` / `execution_capability_snapshot` **全为 0 行**。且 `execution_snapshot.tool_contracts` **恒为 `{}`**。
   → 结论：CAP 目录在这套环境里从未装载过，本轮 P0-1 的 enforce 无法在此库直接开启（印证 §5.1）。

3. **`usage_record` / `budget_reservation` 的外键缺口。**
   `usage_record` 无 `operation_id` 外键、无 `reservation_id` 外键；唯一索引是 `idx_usage_operation_once (tenant_id, operation_id) WHERE operation_id IS NOT NULL`。`budget_reservation.operation_id` 也无外键，且 `findOrphaned` 对 `tool_operation` 是 **INNER JOIN** → 非工具操作 id 的预留不会出现在悬挂扫描里。
   → 影响本轮新增的**模型调用**预留行（其 `operation_id` 是模型调用标识，不是 `tool_operation`）：它们**不会被悬挂扫描发现**。需要单独口径，否则模型侧的钱泄漏无人回收。

4. **`releaseLease` 只清租约、不改状态 → 热循环。**
   `JdbcRunClaimRepository.releaseLease` 只清 `lease_owner` / `lease_expires_at`，**不改 state**；而 claim 查询会把 `state='RUNNING' AND lease_expires_at IS NULL` 重新领取 → 「释放租约」等于「回到队列」，且会造成热循环。
   → 这是 P0-2「挂起后自动恢复」不能简单复用租约机制的原因之一（见 §5.2）。

5. **`agent.approval.ttl` / `agent.approval.approver-scope` 原本是零运行时读取点。**
   `ConfigReadService` 里 `effective=false`。本轮 P0-2 已把两者接入运行时并改为 `effective=true`。

6. **`ApprovalSource.Verdict` 只有 `APPROVED` / `REJECTED` / `FAIL_CLOSED`，无 `PENDING`。**
   → 审批来源目前**无法表达「挂起等待」**，只能表达「通过 / 拒绝 / 闭锁」。这是 §5.2 需要动 `ApprovalSource` 接口的原因。

7. **`approval` 表无 `operation_id` 唯一约束**；CHECK 要求 `state != PENDING → approver_id IS NOT NULL`。
   → 幂等靠本轮新增的 `WHERE NOT EXISTS` 原子语句保证，而不是靠唯一索引。
