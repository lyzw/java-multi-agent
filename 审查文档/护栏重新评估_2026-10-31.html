1　评估方法与口径

本次复评不重复上一轮的问题清单，而是回答三个新问题：加固是否真的生效、是否引入了新的薄弱面、与主流方案的距离有没有缩小。为此采用三条相互独立的证据线，避免「读代码得出结论」这种自证式评估。

证据线做法为什么必须这样做
① 静态结构 枚举全部 Guard / SelfCheck / Gate / Policy / Detector / Moderation / Validator 生产类（共 21 个关键守卫），逐个核对其调用方是否存在——即「守卫写了，但没人调用」这类虚假保证。 上一轮最大的发现正是这类：wrapToolResult 是零调用方的公开方法，红队测试却在验证它。
② 实连库验证 以非特权角色 app_agent 直连 agent_dev：验证 RLS 隔离（0 / 5 / 4 / 0 行）、验证审计删除拦截的两层防线、验证限流滑动窗口 SQL 的原子性。全部在事务内执行并回滚。 RLS 与权限的结论在代码里看不出来，只能拿真实角色实连。
③ 全量测试实跑 七个模块一次 reactor 全量跑，带齐 5 个 DB 凭证，让 IT 真正执行而非跳过。 项目铁律：「跳过 ≠ 通过」。无凭证跑出全绿，是最容易骗过自己的绿灯。

5　残余缺口（按严重度）

以下均为本次确认仍然存在的缺口，不含已修复项。每条都写明「为什么不现在修」，因为「没做」和「不该现在做」是两件不同的事。

编号级别缺口现实影响为何未在本次修复
G1高 CAP 授权闭环在生产未启用：开关仍为关闭，运行期走兼容路径，不校验工具名是否在能力清单内 「能力闭环」在代码里成立、在运行时未成立。越权执行的最后一道门实际上是开着的。 启用依赖 P5 能力目录发布链路完成（开关的既定前提），强行翻转会让现有 Agent 全部无法调用工具。
G2高 HITL 活体审批通道未接：approvalSource 为空策略，需审批的工具运行时恒被拒 安全上无风险（fail-closed），但「外部写入」类能力实质不可用，产品功能受限。 真正接线要改 ApprovalSource 契约——operationId 每次调用动态生成，而判定发生在调用之前，需先在设计阶段把 ID 前移。属结构性改动，不宜塞进加固批次。
G3中 审计删除的凭据隔离脚本尚未落库（04_retention_role.sql） 任何持有应用凭据者仍可删除审计行。这是当前性价比最高的剩余项：脚本已通过 dry-run 双层验证，执行一次即关闭。 该脚本会撤销应用角色的 DELETE 权限，属共享 dev 库上的破坏性变更，需你确认后执行。
G4中 ai_agent 仍持有 BYPASSRLS，且是库 owner 它已不作应用角色，但凭据一旦泄露即可绕过全部 RLS；爆炸半径是「所有租户的全部数据」。 它是运维脚本的执行身份，收回需同步改造备份/运维流程，超出本次范围。
G5中 输出内容安全是黑名单正则，无严重度分级、无分类器、无供应商接口 拼音、谐音、拆字、多语言变体均可绕过；「不宣称内容安全」应作为对外口径。 接入真实分类器涉及供应商选型与调用成本，属产品决策而非工程修复。
G6中 无系统提示词泄漏检测（新发现）：平台没有任何机制识别「模型复述了系统指令」 提示词中含能力清单与安全规则的表述，泄漏后可被用于构造更精准的绕过。对应 OWASP LLM07，原报告未覆盖。 需先定义「什么算泄漏」——系统提示词本身是动态拼装的，无稳定指纹可匹配。需设计而非补丁。
G7中 平台级路径无限流：仅有租户级 Run 限流，运维与配置发布端点没有 配置发布是低频高危操作，被脚本刷时的后果比 Run 刷更大。 平台级限流的桶键语义与租户级不同（无 tenant_id），需先定 key 设计。
G8低 限流滑动窗口默认关闭 固定窗口在边界处实际放行量可达 2×limit。已有实现与开关，只是未开。 保持默认不变以免影响既有容量基线；建议在下个调优窗口打开。
G9低 PlatformOpsSessionGuard 无任何测试触达（21 个守卫里唯一一个） 平台运维会话的防线靠人工审阅保证，重构时静默退化不会被发现。 本次复评新发现，属补测工作量，不影响当前行为正确性。
G10低 恢复扫描器已有健康事实，但未接入健康端点（项目未引入 actuator） 「崩溃恢复事实上不工作」目前只能靠翻日志发现。 接入需要新增依赖与端点暴露面，须与运维侧对齐口径。
G11低 RAG 相关护栏受 A-008 阻断，LLM04 / LLM08 属未覆盖而非「已覆盖」 知识库一旦上线，投毒与向量脆弱面即刻暴露，而当前无任何对应机制。 RAG 本身未就绪（缺 Docling / BGE-M3），护栏无从挂载。占位不等于生产就绪，这一点必须诚实标注。

7　与主流方案的相对位置

能力本平台差距说明
输入 / 输出护栏分层对齐 与 NeMo Guardrails 的 input / output rails 同构：入口做边界与分级，出口做内容判定与处置。
内容判定手段落后 主流用分类器或供应商接口（Azure 按 0–7 严重度分级处置）；本平台是正则黑名单、二值处置。这是唯一仍存在代差的维度。
越权执行防护领先 多数 Agent 框架只有「工具白名单」；本平台是「能力清单 + 风险分级 + 审批 + 预算 + 快照准入」的纵深，粒度高一个量级。
多租户数据隔离领先 数据库层 FORCE RLS + 非特权角色 + 启动自检 + 结构漂移门禁，比应用层过滤（多数框架做法）强。
人工介入（HITL）落后 LangGraph 的 interrupt / 恢复模型已是标准能力；本平台有审批数据模型与消费逻辑，但缺活体通道（G2）。
护栏失效的可观测性领先 「守卫是否真被调用」「配置键是否真存在」「活库是否等于快照」都做了门禁。主流方案极少把护栏自身当作被测对象。

8　下一步建议

  1. 立刻可做（成本最低、收益最高）：执行 04_retention_role.sql 关闭 G3。脚本已通过 dry-run 双层验证，属一次性动作。执行后把 agent.retention.require-isolated-credential 置为 true，让「回落应用凭据」变成拒绝启动。
  2. 下个迭代主线：解开 G1 + G2。两者其实是同一个问题的两面——能力闭环与人工审批都缺一个「执行前已确定的操作标识」。建议一次设计解决：在编排阶段先生成操作 ID 并落库，审批与 CAP 校验都基于它，顺带把审批台与运行期打通。
  3. 与产品侧对齐：G5 的内容安全要不要接真实分类器，取决于「是否对外宣称内容安全」。若宣称，必须接；若不宣称，应在文档中明确「本平台提供黑名单级兜底，不提供内容安全保证」。
  4. 补测：G9 的 PlatformOpsSessionGuard 补一组单测，把 20/21 补到 21/21。
  5. RAG 上线前的前置条件：LLM04 / LLM08 必须在 RAG 解禁之前设计好，否则知识库一上线就是裸奔。
一句话总结：这一轮把「写了但没生效」的虚假保证清掉了，也把「生效但没人知道」的静默缺口变成了启动即报。护栏的可信度提升，主要来自可验证性而不是规则数量——这也应当是后续所有加固的主线。
