## 1. 综合定性结论（一句话）

> **本平台护栏"骨架与纪律是一流水准"，但三处默认态缺位（能力闭环默认关闭、BYPASSRLS 静默绕过 RLS、零保留闸门硬编码 SYNTHETIC）将其从「生产可用」拉回「演示可用」；而输出内容安全与主动注入拦截的缺失，使其相对 NeMo / Azure 等主流护栏在"防有害内容"维度存在代差。**

两个核心判断：

- **防越权执行（横向）：强**。最小权限闭包、委派边界、SSRF、预算/限流/背压/超时、审计/擦除，设计与接线均属上乘。
- **防有害内容（纵向）：弱**。输出侧无平台级 moderation，输入侧注入检测"只观测不拦截"且工具结果净化与测试分叉。这正是主流 GenAI 护栏（NeMo input/output rails、Azure Content Safety）最看重、而本平台最薄弱的环节。

## 2. 成熟度评估（按层）

将护栏拆为 5 层 + 1 横切纪律，逐层给出成熟度与判语：

| 层 | 范围 | 成熟度 | 判语 |
|----|------|--------|------|
| **L0 接入层** | 认证 / 限流 / 零保留闸门 / 租户上下文 | **B-** | 认证与限流齐备；但零保留闸门硬编码 SYNTHETIC（P0）使其失效，限流仅入口（P3）。 |
| **L1 控制面** | 谁能调哪个工具/参数/风险上限 | **C** | 精细闭包设计一流，**但 `cap-authorization-enforced=false` 默认走 legacy 粗粒度授权，工具名不校验（P0）**，等于设计未生效。 |
| **L2 运行时安全** | 注入 / 幻觉 / 风险 / 审批 / 审计 | **C+** | 输入净化与边界硬拒强；但**注入只观测不拦截、工具结果净化分叉（P1）**，输出无内容安全层（P1）。 |
| **L3 资源与生命周期** | 限流/预算/背压/超时/恢复/擦除/审计 | **A-** | 四项资源护栏 + 追加审计 + 零保留擦除齐备；超时非抢占、限流仅入口、审计"不可篡改"依赖可自设 GUC（P2/P3）。 |
| **L4 数据面** | 租户隔离（RLS 纵深） | **B-** | 双层 RLS + 会话绑定 + 构建门禁设计强；**但主数据源用 BYPASSRLS 的 `ai_agent`，RLS 主链路被静默绕过且无启动自检（P0）**。 |
| **横切纪律** | fail-closed / 可追溯 / 不可信包裹 | **A** | 全链路"未知=拒绝/不可用=拒绝/缺省=拒绝"贯彻到位，是本平台最稳的底座。 |

**整体成熟度：B-（偏下）**——设计分可达 A，默认生效分仅 C。差距集中在"默认就生效"与"防有害内容"两点。

## 3. 关键机制评估（提炼，非复述）

### 3.1 租户隔离（L4）——设计强、默认危险
- **优点**：`TenantContext`（不可变、拒绝客户端 tenant_id 作为授权依据）+ `TenantSessionBinder`（`set_config('app.tenant_id',?,true)` 每取连重置，防连接池串租户）+ `FORCE RLS` + 显式 `WHERE tenant_id` 双层；42 张租户表统一；构建期 `SchemaStructureTest` + `verify/*.sql` 反证脚本（须非特权 `app_agent` 跑）。
- **致命短板**：dev 及按模板配置的主数据源用带 `BYPASSRLS` 的 `ai_agent`，主链路 RLS 完全失效，仅剩显式 `WHERE` 兜底；**平台侧缺 `RagStartupSelfCheck` 那样的启动自检**，而测试用 `app_agent`（NOBYPASSRLS）跑全绿，制造"隔离生效"的虚假安全感。

### 3.2 能力闭环（L1）——完备但未生效
- **优点**：`PermissionResolver.build()` 算 EffectiveClosure（深度≤8、带环检测）；`AgentOverrides` 只收紧不放松；`InvocationValidator` 七步有序校验；`DelegationGuard` 五步闸门（深度/次数/超时/预算/逐跳授权，父子互不继承）；MCP/HTTP 经 `McpEndpointGuard` 做 SSRF 双重解析（每次连接执行，无旁路）。
- **致命短板**：`cap-authorization-enforced` 默认 `false` → 路由 `invokeAllLegacy`；legacy `isAuthorized` 只按 `WORKER` 角色判 `TOOL_INVOKE`，**`RoleBasedAuthorizationService` 从不引用 resourceId（工具名）**。结果：任何已注册工具对任意 Agent 均可调用，模型闭包在执行点不被校验，属"呈现层限制、强制层未校验"典型缺陷。

### 3.3 运行时安全（L2）——半截子工程
- **优点**：`PromptGuard` 净化零宽/ANSI/控制符、长度/深度/元素硬上限（超界 `PromptRejectedException`，fail-closed）；`HallucinationDetector` 终答阶段"编造引用"校验真阻断（`commitFailure` + `SAFETY_BLOCK`）；`RiskEvent` 只落 `detailDigest` 不落原文（隐私友好）；`RiskBasedApprovalPolicy` 未知风险 fail-closed 最严。
- **短板**：① `detectSuspicious` 只 WARN 不拦截（设计声明 D-5"只观测"）；② 红队 R-7 验证的 `wrapToolResult`（结构化 `trust="untrusted"` + sanitize）**在生产主路径无调用方**，真实走 `ToolOutcomeRenderer.outcomeText` 仅加自然语言前缀 + 8000 字符截断——测试验证的是死代码；③ 全仓**无平台侧输出内容安全层**，`SENSITIVE_OUTPUT` 只观测不阻断。

### 3.4 资源与生命周期（L3）——最稳的一层
- **优点**：`JdbcRateLimiter` 判定+计数同条原子 SQL（fail-closed，已接多控制器）；预算执行前原子预留（`reserve` 单条条件 UPDATE，UNKNOWN 不释放待对账）；`BackpressureController` 滞回状态机（探测失败=fail-closed 停发）；`RunExecutionLoop` 每轮查 `deadlineAt()`；`claimTasks` 用 `FOR UPDATE SKIP LOCKED` + fencing_token；`RetentionJob` 真删/置空+凭证；审计追加即写由 DB 触发器强制。
- **短板**：超时非抢占（`deadlineAt()==null` 时完全跳过检查）；限流固定窗口+仅入口；审计"不可篡改"依赖任意会话可自设的 GUC `agent.retention.actor`；`RunRecoverySweeper` 在端口不可用时仅 WARN 静默关闭恢复；schema 由快照带外恢复无 CI 比对。

### 3.5 横切纪律——最强底座
全链路 fail-closed：授权不可用=拒绝（`AuthzUnavailableException`）、未知风险不降级、默认拒绝、不可信数据包裹（委派输出/工具结果）。这是本平台相对多数自研框架**最显著的工程优势**，也是 P0/P1 缺陷仍属"可修复"而非"结构性垮塌"的根本原因——纪律在，补丁能补。

| 护栏维度 | 主流参照 | 本平台现状 | 评级 | 差距性质 |
|----------|----------|------------|------|----------|
| 租户数据隔离（多租户 RLS） | Azure/主流 GenAI 框架普遍弱 | 双层 RLS + 绑定 + 构建门禁；但默认角色 BYPASSRLS 绕过 + 无启动自检 | **B-** | 实现强 / 默认态危险 |
| 输入校验 / Prompt 注入 | NeMo input rails · Lakera | 净化+边界硬拒；检测只观测不拦截；工具结果净化分叉 | **C+** | 缺主动拦截 |
| 工具/动作授权（最小权限） | NeMo action guardrails | 精细闭包完备，**默认关闭**，生产走粗粒度 | **C** | 默认失效 |
| 输出内容安全（PII/毒性/越狱） | Azure Content Safety · OpenAI Moderation | 仅供应商侧；平台侧无 moderations，敏感输出只观测 | **D** | 缺失 |

| 资源控制（限流/预算/背压/超时） | 主流成本/速率护栏 | 四项齐备且接链；超时非抢占、限流仅入口 | **A-** | 细节待补 |

## 6. 综合评判：优势 / 劣势 / 风险等级

### 6.1 核心优势（保持，作为评估基线）
1. **fail-closed 纪律贯穿全链路**——这是多数自研框架缺失的，也是本平台缺陷"可修复而非崩溃"的根因。
2. **租户隔离设计一流**——会话级 GUC 绑定 + FORCE RLS + 显式 tenant_id 双层 + 构建期门禁，是生产级多租户范本。
3. **资源护栏齐备且接链**——限流/预算/背压/超时/恢复/擦除/审计，覆盖主流"成本与速率"护栏全谱。
4. **委派边界严密**——深度/次数/超时/预算/逐跳授权 + 父子互不继承 + 子输出按不可信包裹。

### 6.2 核心劣势（必须正视）
1. **设计 ≠ 生效**：L1 精细授权、L4 RLS、零保留闸门三处"配了也不生效"，且**无报错无告警**（静默失效），比"没做"更危险——因为它制造安全感。
2. **内容安全代差**：输出侧零防护、注入只观测，是主流护栏最基础的两道防线，本平台基本空白。
3. **测试保障被"死代码"稀释**：R-7 等红队测试验证的是生产无调用方的代码，给出虚假保证。

### 6.3 风险等级判定
- **当前真实风险（P2 合成数据阶段）**：低。P0-3 因无真实数据暂不触发；P0-1/P0-2 在隔离上靠显式 `WHERE` 兜底 + 单层测试仍可控。
- **接入真实学生数据 / 公网暴露后风险**：**高**。P0-2（跨租户泄漏）、P0-3（合规闸门失效）、P1-1（敏感输出下发）将同时点亮，且均无告警。
- **结论**：**不可在"未修 P0"的前提下接入真实数据或公网开放**。这是评估给出的硬性红线。

## 7. 优化方案优先级路线图

按"先让默认态成立 → 再补运行时安全面 → 最后细节加固"三阶段推进，每阶段给出可验收标准。

### 阶段一：P0 修复（让护栏在默认态真正成立）——最高优先级，约 1~2 周
| 项 | 动作 | 验收标准 |
|----|------|----------|
| P0-1 | `platform.env` 显式 `cap-authorization-enforced=true`；legacy 分支补"工具名 ∈ 闭包"兜底或 fail-closed 拒副作用工具 | 用非授权工具调用 → 被拒；回归 `DelegationGateBranchTest` 全绿 |
| P0-2 | 新增启动自检：查 `rolbypassrls OR rolsuper`，true → 拒绝启动；接入 `verifyIsolation()` 启动+周期自检；中长期主数据源切 `app_agent` | 用 BYPASSRLS 角色启动 → 启动失败并告警；`mvn -o clean verify` 通过 |
| P0-3 | `RunController` 改用 `DataClassification.fromRequest(...)`；`ZeroRetentionGate.assertAllowed` 前移到 Worker 执行层 | 真实学生数据请求 → 触发供应商确认/拒绝；合成数据通道不受影响 |

### 阶段二：P1 修复（补齐运行时安全面，达主流生产级）——约 2~3 周
| 项 | 动作 | 验收标准 |
|----|------|----------|
| P1-1 | 接入平台侧输出 moderation（供应商安全接口或自建 classifier），`SENSITIVE_OUTPUT` 改可配置阻断（默认对未成年人场景阻断/脱敏） | 含身份证号输出 → 默认阻断或脱敏，非原样下发 |
| P1-2 | `detectSuspicious` 高置信模式默认拦截；生产主路径真正调用 `wrapToolResult`；删除/改写 R-7 死代码测试覆盖 `ToolOutcomeRenderer` | 零宽注入载体被剥离；红队测试覆盖真实渲染器 |
| P1-3 | `ApprovalController` 经 `ApprovalSource` 接入 `WRITE_EXTERNAL` 闸门形成 HITL 闭环；或显式文档化"全拒"决策并加开关 | 需审批副作用 → 挂起→人工决策→放行 闭环可用 |
| P1-4 | RAG 落地后接 `ReferencedContentResolver` 做 grounding；扩展编造检测或接轻量事实分类器 | 无引用事实性错误可被检出 |

### 阶段三：P2/P3 细节加固——约 1 周，可与阶段二并行
- 超时：`timeoutMs` 创建路径必填；单步长调用评估 `Future.get(deadline)` 抢占。
- 审计：受控删除从可自设 GUC 改为 DB 凭据隔离（独立 retention 角色 + REVOKE 普通会话删权限）；补威胁模型文档。
- 审计覆盖：静态/集成断言"每个敏感动作都调 `recordRequired`"。
- 限流：Worker 执行层补限流或将预算视为并发上限；移除 `NEVER_LIMIT` 桩；统一走 `current_tenant_id()`。
- 恢复：`RunRecoverySweeper` 端口不可用时升级为可观测告警 + 健康标记降级。
- Schema：CI 增加"活库结构 == `01_platform_ddl.sql` 快照"比对门禁。

## 8. 最终判定

**综合评级：B-（偏下），"演示可用、生产待修"。**

- **设计成熟度**：A 级——分层清晰、fail-closed 纪律强、隔离与资源护栏完备，是工程范本。
- **生效成熟度**：C 级——三处 P0 使核心护栏在默认态不成立，且静默失效无告警。
- **内容安全成熟度**：D~C+ 级——输出 moderation 与主动注入拦截缺失，相对主流存在代差。

**核心结论**：  
本平台护栏的"骨架与纪律"已达到或超过多数主流 GenAI 框架，但**三处默认态缺位（P0）将其从「生产可用」拉回「演示可用」**，而**输出内容安全与主动注入拦截的缺失（P1）使其相对 NeMo / Azure 在「防有害内容」维度存在代差**。

**硬性建议（红线）**：
1. **不得在未修复 P0 的前提下接入真实学生数据或公网开放**——届时 P0-2/P0-3/P1-1 将同时点亮且无告警。
2. 优先修 P0（让默认态成立），再补 P1（运行时安全面），即可达到主流生产级；预计总投入 4~6 周。
3. 修复实施后必须跑 `mvn -o clean verify` 全回归，并补充"启动自检失败 / 跨租户泄漏 / 敏感输出下发"三类端到端冒烟测试，避免再次落入"配了也不生效"的静默陷阱。
