# AI 全流程梳理与合理性评估报告

> **审查范围**：`java-multi-agent` 全仓（`platform/` 797 个 Java 文件 + `rag/` 131 个 + `frontend/` + `admin-console/` + `deploy/sql/`）
> **审查方式**：文档基线提取 → 代码逐环节验证 → 三路并行专项审计（RAG 集成 / 权限治理 / 前端契约）→ 关键结论独立复核
> **审查日期**：2026-10-31
> **结论摘要**：**工程底座优秀，业务闭环未合拢**。骨架、闸门、可靠性、租户隔离均在水准之上；真正的缺口集中在**「治理能力未在运行期生效」**与**「AI 主链路缺少成本与语料闭环」**两处。

---

## 0 · 一页结论

| 维度 | 评价 | 依据 |
|---|---|---|
| 分层架构 | **优秀** | 六边形架构干净，`core`/`ports` 零框架依赖，反向依赖 0 处 |
| 执行可靠性 | **优秀** | 租约 + fencing、Outbox 同事务、UNKNOWN 对账、单步抢占式超时 |
| 多租户隔离 | **优秀** | 43 张租户表 `ENABLE+FORCE RLS`、复合外键、启动自检拒绝特权连接 |
| 安全纵深 | **良好** | 注入防护、SSRF 绝对禁链路本地、内容分级、零保留闸门 |
| **能力治理生效性** | **🔴 未生效** | CAP 开关默认关闭且**任何配置源都未开启** → 能力闭包在运行期不校验工具 |
| **人工审批闭环** | **🔴 未接通** | 无生产代码创建审批行 → 审批台永远查不到待办 |
| **成本与用量计量** | **🔴 失真** | 只计工具调用费，**模型 Token 完全不入账**；`maxLlmCalls` 声明但从不执行 |
| **语料/引用闭环** | **🔴 未接入** | `rag/` 与 `platform/` 零依赖边，无 `search_knowledge_base` 工具 |
| **业务闭环（错题归因）** | **🟡 半开** | 有画像/薄弱点写入，但无知识点图谱、无掌握度、无复习闭环 |
| **多轮会话** | **🟡 缺失** | 消息序列仅存内存，`agent_conversation`/`agent_message` 只存在于 ERD 图 |
| 文档一致性 | **🟡 有陈旧** | 3 处文档描述的模型与代码不符（Run 状态机、ERD 表、门禁顺序） |

**一句话**：平台把「怎么安全地执行一次 AI 调用」做到了工业级，但「这次调用算不算数、准不准、值不值」三件事还没接上。

### 1.2 治理期（能力发布）

```
Agent 定义 → enabled_skills → Skill → tool_ids / mcp_server_ids
   → ClosureResolver（fail-closed，深度上限 8）
   → ConfigPublishWorkflowService.requestPublish → decide（双人复核）→ apply（CAS 切指针）
   → config_publish_seq 单调递增 → 发布后不可变快照
```

**评价**：治理期设计**严谨且完整**，双人复核在应用层 + DB CHECK 双重落实，CAS 切指针带 rebase 重试，生命周期状态机只有一条合法回退边。这一层是全仓最强实现。

**问题**：治理期产出的是「能力闭包」，但运行期**不消费**它（见 F-02）。治理与执行之间断了一根线。

## 2 · 缺失与错误清单（按严重度）

### 🔴 P0-1 · 能力闭包在运行期完全不被校验

**事实链（三重独立验证）**

| # | 证据 | 位置 |
|---|---|---|
| 1 | 开关默认 `false`，且**任何配置源都没有开启它** | `ApplicationConfiguration.java:1683-1687`（`@Value("...:false")`）；`application.yml:499-517` 只有 `cap-dual-write`；`platform.env` 无 `cap*` 键 |
| 2 | 开关关闭时走 legacy 链，legacy 链**完全没有闭包校验** | `ToolInvocationGate.java:515-521`（分支点）、`:1029`（`invokeAllLegacy`）；全文件 grep `closure` → **0 命中** |
| 3 | legacy 授权**只判角色，不判工具名** | `ToolInvocationGate.java:1089-1094` 传入 `call.toolName()` 作为 `resourceId`；但 `RoleBasedAuthorizationService.java:100-115` **从不读取 `resourceId`**，只查 `authzVersion` + 角色→动作表 |
| 4 | 上下文硬编码为 `principal="worker", roles={WORKER}, authzVersion=0` | `ToolInvocationGate.java:1555-1569` |
| 5 | `WORKER` 角色持有 `TOOL_INVOKE` | `RoleBasedAuthorizationService.java:81-89` |

**结论**：**任何已注册工具都可被任意 Agent 调用**。`math-tutor` 只声明了 `skill-profile-view` + `skill-report-brief`，但模型若（被注入诱导地）报出 `tool-parent-notification`（`WRITE_EXTERNAL`），legacy 链照样放行——闭包只在**呈现层**生效（`AgentModelConfigAssembler.java:106,190-196` 按闭包裁剪给模型看的工具 Schema），**强制层没有这道校验**。

**这正是本仓反复消除的「看起来有防线、实际不存在」的一类**，且 `CapEnforcementReadinessGuard.java:66-70` 只打印一行 WARN，兜底开关 `config.flag.cap-enforcement-required` 也默认 `false`（`:1709`）→ 生产启动时**没有任何机制拒绝**带着这个缺口运行。

**连带影响**：`docs/权限管控体系/02_分层授权设计评估.md:29` 声明的「即便 Agent 被注入恶意指令，它也只能在其已启用 Skill 的能力闭包内活动」——**在默认链路上不成立**。

### 🔴 P0-2 · 人工审批闭环从未接通（审批台永远查不到待办）

**事实链**

| # | 证据 | 位置 |
|---|---|---|
| 1 | `ApprovalPort.grant()` 是唯一写入 `approval` 表的入口，**生产代码零调用**（仅测试调用） | grep `\.grant(` 全仓 → 命中全部在 `*/src/test/*` |
| 2 | 审批台列表读的是 `approval` 表的 `PENDING` 行 | `JdbcApprovalQueryRepository.java:43-47` |
| 3 | 生产审批来源是**空策略** → 所有需审批工具恒返回 `FAIL_CLOSED` | `WorkerExecutionConfig.java:224-226`（`new PolicyEngineApprovalSource()` 空 map）；`application.yml:323` `live-source-enabled: false` |
| 4 | 后端 Run 状态枚举**没有 `WAITING_APPROVAL`**，也没有 `RETRYING` | `RunState.java`（仅 6 值）；`01_platform_ddl.sql:214-221` `run_state` 枚举同样 6 值 |

**结论**：需要审批的工具（如 `WRITE_EXTERNAL` 的 `tool-parent-notification`）在生产**恒被拒**；而 `ApprovalController` 的 `/api/approvals` 与 `/api/approvals/{id}/decision` 因为**没有任何代码创建待审批行**而永远返回空列表。审批台是一扇**装好了门把手但通向墙壁的门**。

**文档矛盾**：`docs/业务架构图.md:154-171` 的 Run 状态迁移表把 `WAITING_APPROVAL → QUEUED`（审批通过后重新入队）写成既成设计，代码里**这个状态与这条迁移都不存在**。当前实现是「审批不通过 → 工具被拒 → 整轮失败」，没有「挂起等待」语义。

### 🔴 P0-3 · 模型成本完全不入账，`maxLlmCalls` 声明但从不执行

**事实链**

| # | 证据 | 位置 |
|---|---|---|
| 1 | 预算预留/结算**只发生在工具调用路径** | `ToolInvocationGate.java:1333`（reserve）、`:1423`（settle）；`CapExecutionFlow.java:525,1233` |
| 2 | 结算金额是**固定值** `reserveAmountPerToolCall = ¥0.50`，与真实成本无关 | `application.yml:301` `reserve-per-tool-call: "0.50"`；`ToolInvocationGate.java:1417-1423` |
| 3 | `usage_record` 的 `input_tokens`/`output_tokens` 列**没有任何写入方**（全仓唯一 INSERT 不含这两列） | `JdbcBudgetRepository.java:368-376` |
| 4 | `usage_record.model_id` 存的是**工具名**（如 `record_weakness`），不是模型名 | `ToolInvocationGate.java:1423` `budget.settle(..., toolName)` |
| 5 | 真正的模型 Token 只进了 **Micrometer 指标**与 **run_event 载荷**，没有进任何账表 | `MicrometerModelCallObserver.java:93-99`；`EventPortModelCallObserver.java:74-75` |
| 6 | `maxLlmCalls` 有配置（12）、有快照字段、有判定方法，**但判定方法在生产代码中零调用** | `application.yml:283`；`RunConfigSnapshot.java:35,79` `allowsLlmCall()`；grep `allowsLlmCall` → 仅 `ConfigFailClosedTest.java:241-242` |
| 7 | `maxCostPerRun`（¥2.00）在快照里，但**只用于配置展示**，不参与任何拦截 | `RunConfigSnapshot.java:31`；无生产引用 |

**结论**：
- **单次 Run 的模型开销没有任何上限**。`maxSteps=20` 意味着最多 20 次模型调用，理论上可以是 `maxLlmCalls=12` 的近 2 倍，而**没有任何一处会拦**。
- **费用报表失真**：`usage_record` 里记的 `cost_amount` 是「工具调用次数 × ¥0.50」的固定代理值，`model_id` 列存工具名。用它做计费或成本分析会得到完全错误的结论。
- **代码注释与实现自相矛盾**：`ToolInvocationGate.java:1421-1422` 写着「真实成本由 usage_record 独立记录（P3-D04 §6 L-5）」——但 `usage_record` 恰恰是**唯一没有记录真实成本**的地方。

### 🟠 P1-1 · `rag/` 与 `platform/` 零依赖边，语料能力在 AI 主链路上完全不可达

**三重独立验证**

| 检查 | 结果 |
|---|---|
| Maven 依赖 | `platform/**/pom.xml` 中 `artifactId>rag-*` → **0 命中** |
| Java 导入 | `platform/**` 中 `import cn.studykid.rag` → **0 命中**；反向亦 0 |
| 工具定义 | `search_knowledge_base` 全仓**只存在于文档**，无实现、无 `cap_tool_def` 行 |

**为什么现有 HTTP 工具机制也走不通**：`CapHttpToolConfig` 只有 method/url/timeoutMs，**没有 header 字段**；`HttpToolExecutor.java:330-343` 写死请求头。而 RAG 侧 `RagRetrievalController.requireTenant()` 要求 `X-Tenant-Id`（否则 400），`RagJwtAuthFilter` 要求 Bearer JWT（否则 401）。**即使管理员手工种一条指向 RAG 的 `cap_tool_def`，调用也会在两个维度上失败。**

**已识别的规则冲突（量化）**：RAG 生成的答案会带 `《人教版·七年级上册·2024修订》第 3 章 > 3.2 二次函数的图像 · 第 45 页 · 第 12 题`（`GroundedGenerationService.java:158-160` + `Chunk.java:114-121`），而平台侧 `HallucinationDetector` 的 **H-1a**（`第\s*[0-9一二三四五六七八九十百]+\s*[章节讲课]`）、**H-1b**（`人教版|苏教版|…`）、**H-2a**（`第\s*[0-9]+\s*页`）**必然命中** → Run 被判 `SAFETY_FABRICATED_SOURCE` 直接 FAILED。**任何正确引用都会被拦截。**

> **重要澄清**：这是**已登记在册的已知状态**，不是新发现的缺陷。`rag/docs/RAG-D09_阶段门禁与主平台接入计划.md:136` 明确写着「🔴 未通过——A-008 结论未产出；M-1～M-4 未实施」，并已列出 M-1（检测器模式开关）→ M-2（`GroundedCitationVerifier`）→ M-3（提交前分级）的改造清单与顺序约束。代码与文档**一致**。此处列出是为说明「接入前必须先改哪几处」，而非追究遗漏。

**额外的、文档未记录的缺口**：
- `rag_answer_citation` 表（注释写「引用溯源链路…使回答可回溯到具体位置并可复核」）**无任何生产写入方** → 「可回溯」当前**不成立**，引用只存在于内存中的 Java record。
- `GroundingService.verify()`（存在性→角色→冲突→蕴含→裁决 五步溯源闸门）**零调用**，且被 `rag.local-ports.enabled`（默认 false）挡在启动期之外 → 既不生效也不可见。
- `platform/agent-infra` 里还有**第三套**检索实现（`RetrievalService`/`RetrievalEndpoint`/`VectorSearchEngine`/`TfIdfRanker`），但**没有任何模块依赖它**（只在 `dependencyManagement` 里出现）→ 永不上线classpath，且其 `RetrievalEndpoint` 从**请求体**取 `tenantId`、用 `@GetMapping` + `@RequestBody`（HTTP 规范违规）。三套并行检索栈是明确的维护陷阱。

### 🟠 P1-2 · 多轮会话无持久化

`docs/系统架构图.md:360-365` 的 ERD 画着 `AGENT_CONVERSATION` 与 `AGENT_MESSAGE`。实测：**这两个名字在全仓 DDL 与 Java 中均不存在**（`grep -rn "agent_conversation|AGENT_MESSAGE"` → 0 命中）。`agent_message_queue` 存在但它是 **PG 队列**，不是对话表。

当前对话消息序列是 `RunExecutionLoop` 里的一个**局部 `ArrayList<ModelMessage>`**（`:347-348`），随 Run 结束即消失。后果：**同一学生第二次提问时，Agent 对上一次对话一无所知**；「个性化辅导」这一业务定位在多轮场景下无法成立。

---

### 🟠 P1-3 · 业务闭环缺失：错题归因只写入、不回读、不形成复习闭环

现有数据模型只有两张表：
- `student_profile`（`student_id` / `grade` / `subject`）—— 仅 3 个业务字段
- `weakness_record`（`knowledge_point` / `error_type` / `confidence`）—— 写入端是 `record_weakness` 工具

**缺失的关键环节**：
1. **知识点体系**：`knowledge_point` 是自由文本（`char_length` 1..100，无词表约束），与 `TutoringVocabulary` 的学科/年级词表**不共享**——「一次函数」与「函数」会被算成两个知识点。
2. **回读路径**：`get_student_profile` 只读 `student_profile`，**不读 `weakness_record`** → Agent 查不到学生「到底哪里弱」，归因与辅导两张皮。
3. **掌握度/复习**：`weakness_record` 无 `mastery`、无 `next_review_at`、无 `resolved` → 没有「什么时候该再练这题」的机制。
4. **效果度量**：反馈只落 `agent_trace_feedback`（`kind` 枚举，无自由文本），且注释自陈「不能单独当真值」；而 `AgentMetricCollector.java:129-131` 的效果类字段（`auto_checked`/`auto_verified`/`human_verdict`/`hallucination`/`instruction_followed`）**全部硬编码为 `null`，注释写「待 P7-3 接入」**。

**结论**：`docs/项目进度台账` 与 `P6_AI-Agent效果测试与执行效果度量` 描述的「效果度量体系」在代码里是空壳。这不是实现 bug，而是**业务闭环尚未设计完成**。

### 🟠 P1-4 · `agent.roles` 声明了但从不校验

`CapAgentDef.roles` 的 Javadoc 写「适用主体角色范围（**非授权授予**）」（`CapAgentDef.java:30`），`docs/业务架构图.md:123` 也说「仅声明适用主体范围」。

实测：`cap_agent_def.roles` 在**运行期从不被与调用主体角色比对**——`RunCreationService` 的快照解析（`JdbcExecutionSnapshotResolver`）只按 `tenant_id` 过滤，`AgentPublishClosureValidator` 也不校验 roles。

种子数据里 `profile-reviewer` 声明 `roles=["teacher"]`，但学生令牌同样能创建它的 Run（只要有 `RUN_CREATE`）。文档用「非授权授予」措辞规避了矛盾，但**结果上这个字段对安全没有任何作用**——要么落实校验，要么从模型里删掉，避免治理者误以为它在起作用。

## 3 · 做得好、不要再动的部分

这部分质量很高，**任何整改都应绕开它们**：

1. **闸门不可绕过** — 全仓 `handler.execute()` 仅 2 处调用点，且有架构测试 `ToolBypassArchitectureTest` 静态扫描所有模块 `src/main/java` 守护白名单；无 Spring AI `ToolCallingAdvisor` 自动执行路径。
2. **闭包 fail-closed 且只能收紧** — `PermissionResolver` 对任何不可解析对象抛 `ClosureResolutionException`（绝不跳过）；`AgentOverrides` 只有 `removeSkills`/`removeTools`/`lowerRiskCeiling` 三个动词，无「添加」；深度上限 8。
3. **版本钉死** — 经「当前指针 → 发布头 → 对象版本行」解析，明确不用 `max(config_publish_seq)`；引用行拒绝 `latest` 别名。
4. **双人复核** — 应用层 + DB CHECK 双重落实，CAS 切指针带 rebase 重试，`config_publish_seq` 用 DB 序列保证单调。
5. **TOCTOU 线性化边界** — `ExecutionAdmissionChecker` 在外部副作用前重读权威 `authzVersion` 并重算闭包指纹，任一失败即 `AUTHZ_UNAVAILABLE`/`EXEC_ADMISSION_STALE`。
6. **逐跳重新授权** — `DelegationGuard` 不继承父授权结论；深度/次数/超时/预算**整棵调用树共享**（同 `run_id` 聚合），子 Agent 工具调用**重入同一闸门**。
7. **UNKNOWN 纪律** — 超时/断连一律进对账，绝不当普通失败重试、绝不释放预算预留；补偿动作本身也要幂等+授权+审批+审计。
8. **单步抢占式超时** — `preemptionExecutor` 把每次模型/工具调用包进 `Future.get(剩余时间)`，解决「单次卡 10 分钟越过根 deadline」；Worker 侧唯一重试实现（不引入 Spring `@Retryable` 防双重重试）。
9. **租户隔离** — 43 张表 `ENABLE+FORCE RLS`（`01_platform_ddl.sql` 42 张 + `patch_cap_release_head.sql` 1 张）；`current_tenant_id()` 未绑定即 fail-closed；复合外键防跨租户引用；启动自检拒绝特权连接（BYPASSRLS 只给受会话守卫的运维通道）。
10. **注入与 SSRF 纵深** — 工具结果按不可信数据标记 + 净化 + 长度封顶（父子共用同一渲染器，杜绝语义漂移）；`McpAddressPolicy` 对 `169.254.0.0/16`/私有 CIDR **绝对禁止**（含云元数据 `169.254.169.254`）。
11. **零保留分级** — `DataClassification.fromContent` 从内容推导分级（不硬编码 SYNTHETIC），未确认供应商 + 真实学生数据 → 拒绝。
12. **预算防超发** — 单条条件 UPDATE + Run 级行锁聚合，`budget_no_overspend` CHECK 兜底；失败原因用枚举区分「额度不足」与「未开户」/「Run 级耗尽」。
13. **前端契约与状态机严谨** — `runState.ts` 以**后端枚举实际取值**为准并显式补上 `TIMED_OUT`（此前漏判导致 SSE 永不关闭）；SSE 用 `fetch` + `Last-Event-ID` 而非 `EventSource`（后者不支持自定义头）；`CreateRunRequest.KNOWN_FIELDS` 拒收未知字段。

## 4 · 优化建议（分批、可执行）

### 第一批 · P0 止血（建议 1 周内）

> 目标：**让文档承诺的控制真实生效**，而不是新增功能。

**1.1 补上 `cap_authz_version` 的生产写入方**（P0-1 前置）
- 在 `AuthzVersionPort` 增加并实现「首次见到主体时按需 `initialize()`」的调用方（Run 创建时对调用主体、Worker 身份各写一行）。
- 或让 `JdbcAuthzVersionRepository.require()` 在「表为空/首见」时降级为 `initialize()` 并返回版本 1 —— **但必须是显式的、幂等的、且写审计**，不能是隐式兜底。
- 验收：`SELECT count(*) FROM cap_authz_version` 在跑通一次 Run 后 > 0；`CapDualWriteService` 能写出 `execution_capability_snapshot`。

**1.2 打开硬失败开关**
- `application.yml` 增加 `config.flag.cap-enforcement-required: true`（先于 `cap-authorization-enforced` 打开），使「未启用能力闭包校验」在生产**拒绝启动**而非 WARN。
- 验收：缺配置或关闭开关时启动失败并给出可操作提示。

**1.3 legacy 链补闭包校验（与 1.1 解耦，可先行）**
- 在 `invokeAllLegacy` 的 `findHandler` 之后、Schema 校验之前，加一步「工具名 ∈ 该 Agent 生效闭包」判定；不通过则 `recordRejected(tool, "工具不在该 Agent 能力闭包内")`。
- 这样**不必等 CAP 开关就能先关闭「越权调用工具」这个洞**，且是纯增量、可灰度。
- 验收：给 `math-tutor` 配置一个不在其 skills 里的工具，模型报出后被拒绝（红队用例入 `ToolBypassArchitectureTest` 同级）。

**1.4 审批闭环接通**
- 补一个生产路径创建审批行：在 legacy/CAP 链判定「需审批且权威未批准」时，**先写 `approval` 行（PENDING，绑定 argumentDigest + targetResource + runId + expiresAt）再拒绝**，让审批台能看到待办。
- 补 `WAITING_APPROVAL` 状态与「审批通过后从 `WAITING_APPROVAL` 恢复」的迁移（与 `docs/业务架构图.md` 的状态机对齐），或**改文档**承认当前是「拒绝即失败」语义。**两者必须择一，不能文档与代码各说一套。**
- 验收：端到端跑通「需审批工具 → 审批台出现待办 → 人工批准 → 工具执行」。

**1.5 模型调用纳入预算与用量**
- 在 `RunExecutionLoop` 模型调用前后接入预算：`reserve(modelEstimatedCost)` → 调用 → `settle(actualCost)`，成本由 `usage.inputTokens()/outputTokens()` × 单价表算出（单价按模型 id 配置）。
- 让 `usage_record` **分开记两类行**：工具调用行与模型调用行（模型行写 `model_id`=真实模型、`input_tokens`/`output_tokens`=真实值、`cost_amount`=真实成本）。
- 激活 `maxLlmCalls`：在 `RunExecutionLoop` 循环条件里用 `snapshot.allowsLlmCall(callsSoFar)`，超限即 `commitFailure(..., "MAX_LLM_CALLS")`。
- 让 `maxCostPerRun` 参与判定（与 Run 级 `budget_amount` 合并取更严者）。
- 验收：一个跑 15 次模型调用的 Run 被 `MAX_LLM_CALLS` 拦住；`usage_record` 里能查到该 Run 的模型名与真实 token。
