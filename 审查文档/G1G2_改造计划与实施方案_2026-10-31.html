操作标识前移与审批可暂停 · 内部评审稿 · 2026-10-31 · 关联缺口：G1（CAP 未启用）· G2（HITL 恒拒）

2. 现状与根因（代码证据）

原评估把根因概括为「operationId 动态生成、判定发生在调用之前」。实读代码后可精确为 四道独立锁，只前移 ID 只能开其中一道。

锁代码事实单独后果阶段
E1 ToolInvocationGate.java：invokeAllLegacy 在 #1211 ledger.register 拿到 operationId，紧接着 #1279–1331 同步完成审批判定与 #1318 approvalPort.consume。人无法在「INSERT 下一行就 consume」之间插入决定。 审批窗口 = 0 毫秒，HITL 在设计上不可达M1
E2 RiskBasedApprovalPolicy.java：ApprovalSource.verdictFor(tenantId, handler)（#131）只拿租户与工具句柄，拿不到 runId / 参数 / operationId。当前装配 WorkerExecutionConfig#approvalSource() 返回空策略（恒 FAIL_CLOSED）。 判无可判；任何实现只能恒拒或恒批（后者为漏洞）M2
E3 审批行的生产写入方是 JdbcApprovalRepository#request（#157，写 PENDING，已被 requestApproval#1538 调用），但消费端 consume（#200）只接受 state='APPROVED'（#227），而生产代码从不存在把 PENDING→APPROVED 的「重入」——Run 在登记待办后已 fail-closed 结束，无人把它重新拉回闸门。 待办虽被创建却永不生效；审批台「批准」动作无闭环M1
E4 01_platform_ddl.sql：cap_approval 的 approver_id、decided_at 均为 NOT NULL，且绑定只能在 Run 启动后才确定的 closure_fingerprint / authz_version。CAP-HITL 无法表示「等待人决定」。 CAP 原生不支持 HITL，G1 在 P5 前无法接通M3
关键澄清（纠正原评估一处偏差）：当前 request() 确实会写 PENDING 行，审批台 /api/approvals 端点也已存在（ApprovalController.java #51/#81）。所以「待办队列结构性为空」已不成立；真正阻塞 G2 的是缺少 PARK/RESUME——Run 在登记待办后立即结束，审批决定到达时没有任何代码把它重新拉回闸门重消费审批。

3. 总体方案：把「动作」改成「意图」

引入贯穿四阶段的实体「操作意图 Operation Intent」——它不是新表，身份就是既有的 tool_operation 行（已含 tool_arguments jsonb 与 idempotency_key），只是把它提前创建并允许以 PENDING 状态存活到审批完成。

A
P0 · ALLOCATE（分配身份）：模型返回后立刻 ledger.register 落 PENDING，取得 operationId——身份在任何判定之前存在。
R
P1 · REQUEST（请求审批）：若需审批，写 approval 行（PENDING），绑定参数摘要与目标资源。
P
P2 · PARK（挂起）：Run → WAITING_APPROVAL，写检查点（复用 tool_operation.tool_arguments），释放租约，交还 worker 线程。
R
P3 · RESUME（恢复）：决定到达 → 唤醒 → 从检查点重入闸门（不调用模型）→ 消费已批准的审批 → 执行。
身份复用既有 idempotency_key（run_id + [agentRef/] + tool_name + call_id，已有 UNIQUE(tenant_id, idempotency_key)）。登记改为 INSERT … ON CONFLICT (tenant_id, idempotency_key) DO UPDATE … RETURNING operation_id，崩溃重放天然收敛，不产生第二行。「前移」的真实含义是移动 register 的调用时机，而非新造 ID。

6. 风险与回退

  • 不可逆 DDL（M1#2 / M3#1）：ALTER TYPE … ADD VALUE 与 DROP NOT NULL 不可回滚。对策：低峰执行；SchemaDriftIT 先在全量实跑通过后执行；一旦需回退，用全新 schema 重建，不依赖删枚举。
  • 挂起泄漏：Run 进入 WAITING_APPROVAL 后若唤醒事件丢失 → 永久挂起。对策：RunRecoverySweeper 增加 WAITING_APPROVAL 超时兜底（超时→FAILED 且工具未执行），与现有 RUNNING 接管同构。
  • 审批过期竞态：人批瞬间恰过期。对策：consume 与 decide 同走 DB 事务 + 触发器校验 expires_at，过期即 EXPIRED，resume 失败安全。
  • M3 前置依赖：G1 翻转依赖 P5 指针读路径，M3 不在本期翻转开关，避免回滚场景授权语义不一致。

8. 待你决策的三件事

  1. 挂起模型：建议用检查点挂起（P2/P3）。若场景是「运维在旁边盯着点批准」，原地阻塞等待也能当天上且零 schema 变更——但会占用 worker 线程。默认推荐检查点挂起。
  2. 拒绝后 Run 怎么办：建议把「拒绝」作为失败调用回灌给模型，3 次后终止整单；否则一次参数不合规的拒绝会让整个 Run 直接失败。
  3. 节奏：建议先只做 M0（零对外行为变化 + 修 3 缺陷），再开 M1（接通 G2）。M2/M3 是否本期开工取决于「写外部工具（WRITE_EXTERNAL）本期是否必须可用」与 P5 进度。
⚠️ 执行纪律：M1#2、M3#1 属不可逆/破坏性 DDL，未获你明确授权前我不会执行任何 SQL。所有改动须带回归测试、走七模块同一 reactor 实跑（JAVA_HOME=/opt/homebrew/opt/openjdk@21 mvn -o -f platform/pom.xml …），platform-bootstrap 不可单独 -pl 跑。
