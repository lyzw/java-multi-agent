## 一、严重问题（P0 — 必须修复）

### 问题 1：`DelegationExecutor.buildContext()` 方法截断导致授权版本校验失效

**位置**：`platform/agent-application/src/main/java/cn/studykid/multiagent/application/orchestration/DelegationExecutor.java` 第 875-880 行附近

**问题描述**：
`buildContext()` 方法中 `authzVersions.require()` 的返回值未被完整消费。从代码片段可见：
```java
authzVersions.require(command.tenantId(), "worker").authzVersion();
```
此处调用了 `require()` 但仅取其 `authzVersion()`。如果 `require()` 内部在版本校验失败时**抛出异常**，调用方 `catch (RuntimeException e)` 块会捕获并返回 `null`，但 `require()` 的语义是**版本不存在时返回默认值还是抛异常**尚不明确。更关键的是，`require()` 返回的 `AuthorizationVersion` 对象中 `authzVersion()` 若返回 `-1` 或 `0` 等哨兵值，下游 `checkAuthzFreshness()` 的比较逻辑 `context.authzVersion() < current` 会**恒为 false**，导致陈旧上下文被放行。

**原因**：
1. `AuthzVersionPort.require()` 的契约不清晰 — 是 fail-fast 抛异常还是返回带哨兵值的对象？
2. `buildContext()` 对 `require()` 的返回值没有做"读不到 = fail-closed"的显式校验。
3. `checkAuthzFreshness()` 中 `current` 的默认值语义不明确。

**修复建议**：
```java
private @Nullable TenantContext buildContext(@NonNull DelegationCommand command) {
    long authzVersion;
    try {
        AuthzVersionPort.AuthzVersion authz = authzVersions.require(command.tenantId(), "worker");
        if (authz == null || authz.authzVersion() < 0) {
            log.error("权威授权版本不可用: tenant={}", command.tenantId());
            return null; // fail-closed
        }
        authzVersion = authz.authzVersion();
    } catch (RuntimeException e) {
        log.error("权威授权版本读取失败，fail-closed: tenant={}", command.tenantId(), e);
        return null;
    }
    // ... 构造 TenantContext
}
```

### 问题 2：`BearerTokenFilter` 对非 Bearer 格式的头部处理过于宽松

**位置**：`platform/platform-bootstrap/src/main/java/cn/studykid/multiagent/bootstrap/config/SecurityConfiguration.java` 第 208-210 行

**问题描述**：
```java
String token = header.startsWith(BEARER_PREFIX)
        ? header.substring(BEARER_PREFIX.length()).trim()
        : header.trim();
```
当 `Authorization` 头不是以 `Bearer ` 开头时（如 `Basic xxx`、`Token xxx`），代码会将整个 header 值当作 token 提交给 `authenticationService.authenticateToken()`。虽然 `authenticateToken` 内部大概率会验签失败，但这给了攻击者一个**侧信道**：通过观察不同格式的响应时间差异（JWT 验签 vs Basic 解析 vs 空值），可以探测令牌格式。

**原因**：
`JwtCurrentPrincipal.extractToken()` 在 API 层有严格的三段式校验，但 `SecurityConfiguration.BearerTokenFilter` 作为基础设施层的过滤器，实现更为宽松，两者不一致。

**修复建议**：
过滤器应严格匹配 `Bearer ` 前缀，非 Bearer 格式直接清空上下文（不尝试验证）：
```java
if (header == null || !header.startsWith(BEARER_PREFIX)) {
    SecurityContextHolder.clearContext();
    chain.doFilter(request, response);
    return;
}
```

### 问题 3：`ApiExceptionHandler` 中 `IllegalArgumentException` 处理泄漏内部信息

**位置**：`platform/agent-api/src/main/java/cn/studykid/multiagent/api/error/ApiExceptionHandler.java` 第 184-188 行

**问题描述**：
```java
@ExceptionHandler(IllegalArgumentException.class)
public ResponseEntity<ErrorResponse> handleInvalidArgument(IllegalArgumentException e) {
    return ResponseEntity.badRequest()
            .body(new ErrorResponse("INVALID_REQUEST", e.getMessage()));
}
```
`e.getMessage()` 直接回传给客户端。虽然代码中多处使用 `IllegalArgumentException` 携带固定文案（如 `"idempotencyKey 不能为空"`），但项目中**任何地方**抛出的 `IllegalArgumentException` 都会被此处理器捕获，包括第三方库或未来新增代码。若某个开发者传入了包含 SQL 片段、表名、内部路径的异常消息，将直接泄漏。

**原因**：
过于宽泛的异常捕获 + 直接透传消息。

**修复建议**：
为业务参数异常引入专用的 `InvalidRequestException`（类似 `ConfigPublishRejectedException`），此处理器仅处理该专用异常；兜底处理器改为返回固定文案：
```java
@ExceptionHandler(IllegalArgumentException.class)
public ResponseEntity<ErrorResponse> handleInvalidArgument(IllegalArgumentException e) {
    log.warn("参数校验失败: {}", e.getMessage()); // 仅记日志
    return ResponseEntity.badRequest()
            .body(new ErrorResponse("INVALID_REQUEST", "请求参数不合法"));
}
```

### 问题 4：`CreateRunRequest.flatten()` 递归无深度限制，可被恶意输入 DoS

**位置**：`platform/agent-api/src/main/java/cn/studykid/multiagent/api/run/CreateRunRequest.java` 第 177-192 行

**问题描述**：
`flatten()` 方法递归遍历嵌套 Map/List 结构。如果客户端传入一个**深度极深**（如 10000 层）或**循环引用**的输入，会导致 `StackOverflowError` 或 OOM。

**原因**：
递归无深度限制、无 visited 集合防循环、无节点数上限。

**修复建议**：
增加深度限制和节点数上限。

### 问题 5：`ConfigPublishService` 中 `doRollback` 的审计日志 Kind 错误

**位置**：`platform/agent-application/src/main/java/cn/studykid/multiagent/application/cap/ConfigPublishService.java` 第 546-551 行

**问题描述**：
回滚操作的审计日志中 `Kind` 写的是 `PUBLISH`，动作描述也是 `"发布"`。这会导致审计记录中**回滚操作被错误地归类为发布操作**，违反审计可追溯性要求。

**原因**：
复制粘贴错误，从 `doPublish` 复制过来后未修改 Kind 和描述。

**修复建议**：
将 `Kind.PUBLISH` 改为 `Kind.ROLLBACK`，动作描述改为 `"回滚"`。
