一、总体结论

该平台的护栏是一套以 「纵深防御 + fail-closed」 为核心纪律、覆盖 租户隔离、能力授权、资源控制、可观测审计 四类的成熟设计，工程完成度远高于一般自研 Agent 框架。其强项在于：

  • 租户隔离：应用层 TenantContext + TenantSessionBinder 钉会话变量 + PostgreSQL FORCE RLS 双层，全仓库仓库统一遵循；
  • 能力闭环：PermissionResolver → InvocationValidator → ToolInvocationGate 的全链路「谁能调用哪个工具/参数/风险上限」判定，与委派边界（深度/次数/超时/预算）配合严密；
  • 资源与生命周期：限流、预算（执行前原子预留）、背压、超时、租约恢复、零保留擦除、追加即写审计一应俱全且多数已接调用链；
  • fail-closed 纪律：未知风险、授权不可用、缓存失效、超时缺省均默认拒绝。
但存在三类会动摇护栏有效性的结构性缺口（详见第三节）：
  • ① 默认态不成立：精细能力闭环 cap-authorization-enforced=false 默认关闭，生产实际走粗粒度 legacy 授权（工具名不校验）；零保留闸门被硬编码为 SYNTHETIC；主数据源在 dev 用带 BYPASSRLS 的 ai_agent，RLS 在主链路被静默绕过。
  • ② 运行时安全面薄弱：无任何平台侧输出内容安全层（PII/毒性/越狱），敏感输出「只观测不阻断」；Prompt 注入检测「只观测不阻断」且工具结果净化实现与测试分叉（测试验证的是死代码）。
  • ③ 部分闸门形同虚设或静默失效：运行时人工审批未接线（副作用工具被全拒，但无活体放行通道）；审计「不可篡改」依赖一个任意会话可自设的 GUC。

二、护栏整体架构（分层模型）

平台护栏可归纳为 5 个层次 + 1 条横切纪律。请求从 L0 进入，经控制面与运行时安全面判定后落到 Worker 执行，数据面（RLS）贯穿所有持久化。

与主流护栏框架的对位： L1≈NeMo 的 action/tool guardrails 与「最小权限闭包」；L2≈NeMo input/output rails + Lakera 注入检测 + 幻觉 grounding；L3≈主流的「成本/速率/超时」资源护栏；L4 是主流 GenAI 框架普遍弱、但本平台做得很重的多租户数据隔离。主流框架（尤其开源）普遍缺失 L4，而本平台缺的是 L2 的输出侧内容安全与主动注入拦截——即「只防越权执行、未防有害内容」。

三、关键机制详述（带代码证据）

3.1 租户隔离（L4 数据面）

TenantContext（agent-core/.../tenant/TenantContext.java）为不可变 record，租户标识只从可信认证上下文推导，并警告「客户端传入 tenant_id 不作为授权依据」。绑定在连接上由 TenantSessionBinder 用 set_config('app.tenant_id',?,true) 强制（每次取连无条重置，防连接池串租户）。TransactionalConnectionHolder 用 ThreadLocal 复用/自开连接，顺序为「先 setAutoCommit(false) 再 bind」。持久化层 42 张租户表均有 FORCE ROW LEVEL SECURITY + 对称读写策略；平台目录表（cap_tool_def 等）显式豁免。构建期 SchemaStructureTest + 真实 PG verify/*.sql 反证脚本（须以非特权 app_agent 运行）。

角色模型：app_agent(NOBYPASSRLS，应为运行时角色) / platform_ops(BYPASSRLS，仅运维发布通道，由 GuardedPlatformOpsDataSource+PlatformOpsSessionGuard 包裹，fail-closed) / ai_agent(迁移/owner，带 BYPASSRLS)。

3.2 能力闭环（L1 控制面）

PermissionResolver.build() 计算 Agent→Skill→{Tool,MCP} 的 EffectiveClosure，深度上限 8，含环检测；AgentOverrides 仅能收紧（移除 Skill/工具/风险上限）；未知风险 continue 剔除（fail-closed）。InvocationValidator（Phase A 七步有序）校验：授权版本新鲜度 → 闭包解析 → Skill/Tool 声明 → 风险上限 → MCP 绑定 → 参数策略(ParamPolicyEngine) → 指纹。委派经 DelegationGuard 五步闸门（深度/次数/超时/预算/逐跳授权），父子权限互不继承，子输出按「不可信数据」包裹回父。外部 MCP/HTTP 经 McpEndpointGuard 在 transport 层做 SSRF 双重解析防护（每次连接执行，无旁路）。

配置期 ConfigValidationGate 拒绝未知风险/作用域泄漏；执行期 ExecutionAdmissionChecker 做 Phase B（TOCTOU 二次校验 + 重算指纹）；CachingClosureResolver 权威重查防缓存陈旧。

3.3 运行时安全（L2）

PromptGuard：用户输入包裹 <user_input>、sanitize 剥离零宽/ANSI/控制符、长度/深度/元素硬上限（超界抛 PromptRejectedException fail-closed）。detectSuspicious 命中只打 WARN。幻觉检测 HallucinationDetector.assertNoFabricatedSource 在终答阶段校验「编造引用」正则，命中即 commitFailure + 发射 SAFETY_BLOCK（真正阻断）。RiskEvent 三类（SAFETY_BLOCK/UNAUTHORIZED_CALL/SENSITIVE_OUTPUT）只落摘要 detailDigest 不落原文。RiskBasedApprovalPolicy 按风险等级判定是否需人工审批（未登记=fail-closed 最严）。DecisionAudit 记录每次授权决策（不存 payload），AuthzWatermark 监控撤权。

3.4 资源与生命周期（L3）

限流 JdbcRateLimiter：判定+计数同条原子 SQL，按租户+动作分桶，fail-closed，已接入多控制器。预算：执行前原子预留（reserve 单条条件 UPDATE），Run 级上限用行锁+同事务聚合，UNKNOWN 不释放待对账。背压 BackpressureController 滞回状态机，探测失败=fail-closed 停发，接入 OutboxRelay。超时 RunExecutionLoop 每轮开头查 task.deadlineAt()，maxSteps 兜底，委派下传共享超时。租约/恢复 claimTasks 用 FOR UPDATE SKIP LOCKED+fencing_token 双保险，RunRecoverySweeper 接管过期 RUNNING。擦除 RetentionJob(@Bean(initMethod="start")) 真删/置空+凭证。审计 追加即写由 DB 触发器 trg_audit_record_append_only 强制，敏感信息拒写。

3.5 横切纪律

全链路 fail-closed：授权不可用=拒绝（AuthzUnavailableException）；未知风险不降级；默认-拒绝（角色矩阵/闭包/配置校验）；不可信数据包裹（委派输出、工具结果）。

五、优化方案（具体可落地）

5.1 P0 — 让护栏在默认态真正成立

① 开启并兜底精细能力闭环
• 生产暴露前：在 platform.env / application.yml 显式设 config.flag.cap-authorization-enforced=true。
• 防回退：在 ToolInvocationGate.invokeAll 的 legacy 分支补「工具名 ∈ 闭包」成员校验作为兜底；或在开关缺失/关闭且未装配 CAP 时 fail-closed 拒所有副作用工具，消除「看似授权、实则恒放行」的伪防线。
② 启动自检拒绝 BYPASSRLS 应用角色（仿 RAG RagStartupSelfCheck）
// platform-bootstrap 启动时执行
SELECT rolbypassrls OR rolsuper FROM pg_roles WHERE rolname = current_user;
// 若为 true → 拒绝启动（fail-closed），并告警运维改用 app_agent(NOBYPASSRLS)
• 同时在健康检查/启动中接入 AdminTenantRepository.verifyIsolation()（已有，按需调用→改为启动+周期自检）。
• 中长期：让主数据源改用 app_agent，或将 ai_agent 的 BYPASSRLS 移除（保留其迁移角色、另设非特权应用角色）。
③ 零保留闸门按真实分类派生
DataClassification classification =
    DataClassification.fromRequest(request, currentPrincipal); // 不再硬编码 SYNTHETIC
retentionGate.assertAllowed(currentPrincipal.providerId(), requestText(request), classification);
• 并把 ZeroRetentionGate.assertAllowed 前移到 Worker 执行层 / 子 Agent 调用前（不仅 API 入口），防止合成数据通道外的真实数据漏过。

5.2 P1 — 补齐运行时安全面（对照主流 output/input rails）

④ 新增平台侧输出内容安全层
• 在 RunExecutionLoop 终答/工具结果回写前接入 moderation（可接 LLM 供应商安全接口或自建 classifier），覆盖 PII/毒性/越狱/违规。
• SENSITIVE_OUTPUT 由「只观测」改为可配置阻断（默认对未成年人场景阻断并返回脱敏/拒绝，命中即 commitFailure 或脱敏替换，而非原样下发）。
⑤ 注入防御升级 + 修复工具结果净化分叉
• detectSuspicious 命中对高置信模式默认拦截（至少阻断明显指令注入），低置信保留观测；
• 让生产主路径真正调用 PromptGuard.wrapToolResult（结构化 <tool_result trust="untrusted"> 标记 + sanitize 零宽/ANSI 净化），并删除或改写 R-7 死代码测试，使红队测试覆盖真实渲染器 ToolOutcomeRenderer；
• 统一「不可信数据包裹」契约，避免自然语言提示被绕过。
⑥ 运行时人工审批接线（或明确产品决策）
• 将 agent-api 的 ApprovalController 经 ApprovalSource 接入 ToolInvocationGate 的 WRITE_EXTERNAL 闸门，形成「需要审批→挂起→人工决策→放行」闭环；
• 若产品选择「副作用工具一律禁止」，则显式文档化该决策并加开关，避免「空配置=全拒」被误读为 bug。
⑦ 幻觉/质量检测扩面
• RAG 落地后接入 ReferencedContentResolver 做真实 grounding 校验（当前名字易误导，非输出溯源）；
• 当前至少要扩展编造检测规则或接入轻量事实性分类器，覆盖「无引用的事实性错误」。

5.3 P2/P3 — 细节加固

  • 超时：确认 Run 创建路径 timeoutMs 必填；对单次长调用评估异步 Future + 硬中断（抢占），或至少把模型/工具调用包进带超时的 Future.get(deadline)。
  • 审计不可篡改：将「受控删除通道」从可自设 GUC 改为DB 凭据隔离（独立 retention 角色 + REVOKE 普通会话的删权限），并在合规文档显式声明威胁模型（持 DB 凭据者可删）。
  • 审计覆盖：增加静态/集成断言，确保「每个敏感动作（审批/取消/配置变更）都调用 recordRequired」。
  • 限流：Worker 执行层补限流或将预算视为并发上限；移除 RunEventController.NEVER_LIMIT 桩；统一 rate_limit_bucket 策略走 current_tenant_id() 函数。
  • 恢复：RunRecoverySweeper 在 PlatformTenantPort 不可用时由「只 WARN」升级为可观测告警 + 健康标记降级（暴露而非静默）。
  • Schema 漂移：CI 增加「活库结构 == 01_platform_ddl.sql 快照」的比对门禁（复用 PlatformDdl/SchemaStructureTest 解析逻辑）。

一句话总结：本平台的护栏「骨架与纪律是一流水准」，但三处默认态缺位（能力闭环关、BYPASSRLS 绕过、零保留硬编码）把它从「生产可用」拉回到「演示可用」；而输出内容安全与主动注入拦截的缺失，使其相对 NeMo/Azure 这类主流护栏在「防有害内容」维度存在代差。优先修 P0（让默认态成立），再补 P1（运行时安全面），即可达到主流生产级。
