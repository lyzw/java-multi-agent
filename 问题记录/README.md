# 问题记录 · 分类索引

> **本目录目标**：把散落在代码、评审报告、实测实录、提交信息里的开发期问题，按**问题类型**归类沉淀，
> 做到「同一个坑只踩一次」「后来人不用重新查一遍」。
>
> **每条问题固定三段**：
> 1. **问题描述** —— 现象是什么（可观察的事实，不含推测）
> 2. **产生原因** —— 为什么会这样（根因链，落到具体代码/配置/库结构）
> 3. **相关解决方案** —— 怎么修的 / 打算怎么修 / 为什么不这么修
>
> **来源**：`docs/`、`审查文档/`、`platform/问题记录/`、`git log`（含提交说明中的根因分析）。
> **边界**：本文档只记录**开发过程中实际遇到并登记过**的问题，不做前瞻性设计建议。
> 设计文档的权威结论改写仍回原文档，此处只追加指针。

## 三、高频根因模式（跨分类的共性）

从既有条目里抽出的 7 条**反复出现**的形态。判断新问题归属时先对一遍这 7 条：

### M1 · 开关默认关 + 读侧硬依赖 → 出厂即不可用
**出现**：CFG-01 / CFG-02 / CFG-03 / CFG-11、DAT-01、GOV-01、SEC-01
**形态**：灰度开关默认 `false`，同时读侧把「该开关的产物」当硬前置。两侧各看各的，
合起来的效果是「按默认配置启动的进程，一件事都干不成」。
**教训**：开关的默认值必须与读侧的依赖方向一起评审；只写「默认关是为了灰度」是不够的。

### M2 · 「看起来有防线，实际不存在」
**出现**：SEC-01（闭包只在呈现层生效）、SEC-09（测试验证的是死代码）、
GOV-01（审批台装了门把手通向墙壁）、GOV-06（人工端点走的是另一条链路）、
RAG-10（五步溯源闸门零调用）、DOC-04（文档声称按工具名校验）、FE-14（孤儿页面零引用却仍在仓库里）
**形态**：防线写在**呈现层**（给模型看的 Schema、给用户看的文档、测试里验证的死代码），
**强制层**那一道没写或没接线。
**教训**：每条安全声明都要能回答「这条校验在生产代码的哪个调用点上被执行」。

### M3 · 静默失败：链路断了，但不体现为失败
**出现**：DAT-01（三层 catch 吞掉）、DAT-02 / DAT-03 / DAT-04、CON-06（降级只 WARN）、
TST-04（IT 清库）、API-12 / API-13 / API-14（值悄悄变了）
**形态**：`catch (RuntimeException) { log.warn(...) }` 或「表一直是空的」「值悄悄变了」。
**教训**：链路的失败必须体现为**显式失败**，或至少有一个可告警的「健康位」被置位。

### M4 · 夹具 / 种子 / 基准本身是错的
**出现**：DAT-04 / DAT-07、RAG-09、TST-12、TST-14
**形态**：脚本用裸 `INSERT` 绕过正规写入路径造出畸形数据；测试夹具手工插数据把缺陷盖住；
「和基准库一致」的校验在基准本身就错时给出假绿灯。
**教训**：夹具必须走和被测系统**同一条**写入路径。

### M5 · 值来源被覆盖 / 前提没写出来
**出现**：CFG-07 / CFG-08、TST-02 / TST-03 / TST-17、DOC-07、ENV-04
**形态**：命令行覆盖掩盖了 env 里的错值；「我这边好、你那边坏」；
「全量构建通过」这句话本身携带「当前没有运行实例占用 DB/MQ」的隐藏前提。
**教训**：凡「我这边好、你那边坏」先核对**取值来源**；基线必须连同其成立条件一起记录。

### M6 · 授权漏了一张表 / 漏了一个动作
**出现**：DBP-01 / DBP-02 / DBP-06 / DBP-07 / DBP-10、SEC-24
**形态**：`GRANT` 只覆盖了当时已存在的对象；角色切换后另一套 schema 整域失读；
`REVOKE` 被后续脚本的 `GRANT` 静默覆盖；列表型 GUC 用了单值转义。
**教训**：授权顺序（DLL → GRANT → REVOKE → 回填）是**有向的**，不是集合。

### M7 · 文档与代码各说各话
**出现**：DOC-01 ~ DOC-12、GOV-01（文档写了 `WAITING_APPROVAL`，代码里没有）
**形态**：文档描述了「打算做 / 应该做」，读者以为「已经做」。
**教训**：能力声明要么落实，要么删掉；**不允许用措辞规避矛盾**。
