## 二、根因链

### R1 · `/api/chat/**` 未纳入平台安全链（身份域错配）

`@Order(0)` 的平台链只 `securityMatcher("/api/platform/**")`，`/api/chat/**` 落进默认租户链：

- 平台令牌：`aud=admin-console-api` / `principal_type=PLATFORM_USER`
- 租户链校验：`aud=agent-platform`

两者受众不同 → **每次发送必然 401**，与令牌是否过期无关。
控制器还注入 `CurrentPrincipal`（要求 `TenantContext`），而平台主体刻意不持有 `tenantId`，
即使把端点放行也会在身份解析处再次失败 —— 不能靠「加个白名单」绕过。

### R2 · 前端把 401 一律当登录过期

`client.ts` 早已按 `code` 分支处理 401（见 FE-01 / API-06），但直接对话通道自己用裸 `fetch`
写了一套独立分支：

```ts
if (res.status === 401 && loadSession() !== null) {
  clearSession(); redirectLogin()
}
```

`clearSession()` 清掉有效会话并硬跳登录页；对话草稿只存内存，一并丢失。
**同类问题在新端点复发**，因为新通道没复用统一请求层。

### R3 · SSE 帧被 Spring Framework 7 二次包裹（数据不显示的直接原因）

`ConsoleChatController.sendFrame` 手工拼字符串再调 `emitter.send(String)`：

```java
emitter.send("event: " + name + "\ndata: " + safe + "\n\n");
```

Spring 7 覆写了 `SseEmitter#send(Object)`，语义等价于 `send(event().data(object))` ——
整段字符串被当作**一条 data 值**，框架再逐行补 `data:` 前缀。实测原始字节：

```
data:event: thinking
data:data: We need answer Chinese
data:
```

对应 DevTools EventStream 面板：`Type=message`，`Data=event: thinking data: …`。
**事件名全部丢失**，`thinking` / `delta` / `done` 都退化成匿名 message，前端零分派。

### R4 · ASYNC dispatch 二次授权 → chunked 流写不出终止块

修好帧格式后，帧能逐条到达，但浏览器视角 `fetch` 读流 **15 秒等不到 EOF**，
页面会一直停在「正在生成」。后端日志有响应提交后的 `AuthorizationDeniedException`。

`emitter.complete()` 触发 Tomcat 的 ASYNC dispatch；Bearer 过滤器是 `OncePerRequestFilter`，
异步派发时不重复执行，`SecurityContext` 为空，`AuthorizationFilter` 二次授权抛 Access Denied，
而响应已提交 → chunked 终止块写不出。直连 curl 报 `transfer closed`。

### R5 · 运行实例是旧字节码（环境干扰）

源码与 exec jar 都已含新 `securityMatcher`，但 8080 上是 IDEA 调试进程（带 debugger agent），
项目**没有 spring-boot-devtools**，HotSwap 不会重建 `SecurityFilterChain`（过滤链只在启动时装配）。
因此「已提交的修复」在运行中的进程里并不存在。

### R6 · 样本令牌本身不可用（诊断干扰）

用户贴的令牌 `exp=1794057994` → **2026-11-07 21:26:34 +08 已过期**；
用服务端 `/api/platform/v1/auth/jwks` 公钥验 RS256 签名为 `Verification failure`；
payload 里是 `authoz_version`，服务端 `PlatformJwtTokenService#issue` 签的是 `authz_version`。
**拿它打任何平台端点都会 401**，不能用来判断代码是否正确。
此外诊断中曾手工转录令牌改错一个字符，制造过一轮「平台令牌整体失效」的假信号。

## 三、关键实测证据

### 端点对照（决定性一步：让服务端自己签一枚新令牌）

| 请求（同一枚服务端现场签发的平台令牌） | 旧实例 | 重启后新实例 |
|---|---|---|
| `GET /api/platform/v1/auth/me` | 200 | 200 |
| `POST /api/chat/stream`（空 `messages`） | **401** | **400** `INVALID_REQUEST` |

401 → 400 说明请求已穿过安全链进入控制器（空消息在调用模型前就被拒），零模型调用、零副作用。

### 修复后的字节级验证（经 `localhost:5183` vite 代理，浏览器同源视角）

```

STREAM DONE normally in 1357 ms
event 帧 = thinking ×2 / delta ×3 / done ×1
双重包裹（^data:event:）= 0 行
后端 AuthorizationDeniedException = 0 条
```

直连 8080 的 curl 亦 1.07s 干净退出。
注：Spring Security 7.1.1 源码确认 `securityMatcher(String...)` = `OrRequestMatcher`，
多个前缀是**并集**语义，所以「两个精确前缀」的写法本身成立，不需要改回单前缀。

## 六、方法论沉淀

1. **「全绿」不是证据**：后端单测断言手工拼的 SSE 字符串、前端测试用 mock fetch 喂同样格式的手写帧，
   两侧全绿却都没碰到框架真实序列化（TST-20）。夹具必须经过**被测系统同一条路径**。
2. **有数据 ≠ 能渲染**：SSE / WebSocket / 流式协议的问题，要看原始字节和事件名，不能只看响应体有内容。
3. **先核对「跑的是哪份字节码」**：安全链、过滤器、Bean 装配类改动必须完整重启，
   热替换不生效；诊断时先确认运行实例形态与产物版本（ENV-14）。
4. **基线样本必须可信**：令牌从原文精确提取、不手工转录；宁可让服务端现场签发一枚新令牌做对照（ENV-15）。
5. **fail-closed 会伪装成业务错误**：限流键类型不匹配表现为 429，看起来像「限流策略生效」，
   实为 uuid 解析失败（CON-12）。
