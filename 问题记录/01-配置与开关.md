# 01 · 配置与开关类

> **判据**：根因是**配置项 / 开关 / 命名空间 / 环境变量**取错、默认错、或干脆没有读取点。
> 典型形态：灰度开关默认关、yml 与 `@Value` 缺省不一致、配置键挂错命名空间、env 文件含不可解析语法。

## CFG-01 · 灰度开关默认关闭 + 读侧硬依赖 → 出厂默认启动的进程一个 Run 都跑不了 ⛔→

**问题描述**
`execution_capability_snapshot` 表自 2026-10-28 22:29 起**恒为 0 行**，同期**每一个** Run 都收敛到
`FAILED / CONFIG_UNAVAILABLE`。日志连着两条：
```
RootAgentModelConfigProvider : Run 能力快照缺失，根 Agent 配置不可用: run=1858c9e1-…
WorkerExecutionConfig        : 根 Agent 模型配置不可用，Run 拒绝执行并收敛终态
```
Run 建得出来，跑不起来；现场看着像「配置缺失」。

**产生原因**
不是单点 bug，而是**写侧默认关、读侧硬依赖**的结构性错配：

| 环节 | 实测 |
|---|---|
| 写侧开关键 | `config.flag.cap-dual-write` |
| 唯一写入点 | `CapDualWriteService.onExecutionSnapshotCreated` 第一行 `if (!dualWriteSwitch.isEnabled()) return;`（修复前**静默返回、零日志**） |
| 装配缺省 | `ApplicationConfiguration#capDualWriteSwitch` 的 `@Value("${…:false}")` —— **缺省也是 false** |
| yml | `application.yml:459` `cap-dual-write: "false"`，`git log -L457,461` 显示自 `0d20d9e`(10-23) 起从未改成 true |
| profile 覆盖 | 只有 `application.yml` 一个文件，无 `application-dev.yml` |
| env | `platform.env` 无 `CONFIG_FLAG_CAP_DUAL_WRITE` |
| 运行期开启 | 生产代码**没有任何** `enable()` 调用点（仅 IT 夹具用） |

读侧 `RootAgentModelConfigProvider` 把「有快照」升级成执行准入的**硬前置**，读不到就 fail-closed
（刻意不回落 `fake-model` 占位）。两侧各看各的，合起来 = 按出厂默认启动的进程跑不了任何 Run。

**相关解决方案**
改**默认值，不改 fail-closed**（fail-closed 本身是对的，它要拦的正是「配置缺失伪装成配置正常」）：

| # | 改动 | 位置 |
|---|---|---|
| 1 | `cap-dual-write` 默认 `false → true`，写成 `"${CONFIG_FLAG_CAP_DUAL_WRITE:true}"`，保留 env 回退口 | `application.yml:462` |
| 2 | `@Value` 缺省同步改 `:true` | `ApplicationConfiguration.java:676` |
| 3 | 补偿控制：装配期开关为关时**一次性 WARN**（原来连这条都没有）；挂起期闭包算不出来时 `log.debug` → **`log.warn`** + 行号级上下文 | `CapDualWriteService.java:94` / `:184` |
| 4 | 类注释与 yml 注释同步改写 | `CapDualWriteSwitch.java` |

> ⚠️ 该问题的**完整形态**（五层断链）后来在 2026-10-31 被彻底定位，见 [DAT-01](02-数据一致性与写链.md#dat-01--execution_capability_snapshot-全库-0-行--写入链五层断链)。
> 本条只记「默认关 + 读侧硬依赖」这一层。
>
> ⚠️ 2026-10-28 白天那 19 行快照是谁写的**未能确定**（最可能是带着未提交的 yml 改动启动的进程）。
> **登记为未闭环，不编故事** —— 这条只影响「历史怎么来的」，不影响「现在怎么修」。

**来源**：`docs/RAG检索与端到端实测问题记录_20261028.md` §11

## CFG-02 · yml 默认值与 `@Value` 缺省不一致 → 键一丢就静默回落 ⛔→

**问题描述**
`application.yml` 里 `cap-dual-write: "true"`，而 `ApplicationConfiguration` 的
`@Value("${config.flag.cap-dual-write:false}")` 缺省是 `false`。两条同名配置说两件事。

**产生原因**
迁移期常见的「双写默认值」写法：yml 先改、注解后改（或反之）。配置键一旦因为拼写/命名空间调整而
读不到，**读侧静默回到注解里的缺省**，不报错、不告警。

**相关解决方案**
两处默认值必须**同源同改**，并在测试里钉死。参照 `ApplicationConfigKeyAlignmentTest` 的做法：
把键加进 `NAMESPACES` 白名单，保证「键在 yml 存在」且「不在其它命名空间下留残枝」。

**来源**：`docs/RAG检索与端到端实测问题记录_20261028.md` §11.4 第 2 条
**状态**：✅ 已修

## CFG-03 · 配置键挂错命名空间 → 读取静默落回默认值，通道永远关闭

**问题描述**
`platform.security.execution-ticket.*` 系列配置必须挂在**顶层 `platform:` 段**。此前 `platform-ops`
相关键误挂在 `config:` 段下，读取时静默落回默认值，**执行票证通道永远处于关闭状态**。

**产生原因**
项目里同时存在 `auth.` / `agent.` / `config.` / `platform.` 多套命名空间，键名迁移时容易挂错前缀。
Spring 的 `@Value` 对「找不到就取缺省」是**静默**的 —— 不匹配到任何 bean、不报错。

**相关解决方案**
1. 把 `"platform."` 加进 `ApplicationConfigKeyAlignmentTest` 的 `NAMESPACES` 白名单
   —— **不加就等于让这道守卫对「恰好是它存在理由的那种失误」失明**。
2. 配套：`platform.security.execution-ticket.enabled` 关闭时签发端点返 503 +
   `DENY/CHANNEL_DISABLED` 审计（关掉的通道被人敲要留痕）。

**来源**：`docs/RAG检索与端到端实测问题记录_20261028.md` §8.5「配置键踩过的坑（已有先例，这次主动防住）」
**状态**：✅ 已修

## CFG-04 · 嵌入维度配置漏配（默认 1024 vs 模型 4096）→ 索引期 fail-fast 报 500

**问题描述**
`RAG_EMBEDDING_DIMENSION` 未配置时默认 1024，而 `qwen3-embedding:8b` 返回 4096 维。
重索引直接失败，报「Embedding 维度不匹配：模型 X 返回 4096 维，配置与向量列期望 1024 维，三者必须同时改」。

**产生原因**
三处维度值（模型实际输出 / `RAG_EMBEDDING_DIMENSION` 配置 / 向量列类型 `halfvec(4096)`）必须同时改，
缺一处就对不上。默认 1024 是一个「看起来合理」的猜测值。

**相关解决方案**
保持 fail-fast（**这是本轮最值钱的报错**）：它把「新旧向量混在同一 `<=>` 空间里静默错乱」的整类事故
关在了启动/索引期。运行期请求失败返 500 合理。三处维度统一后正常。

**来源**：`docs/RAG检索与端到端实测问题记录_20261028.md` §3.3
**状态**：✅ 记录为「非缺陷」（行为正确），配置需同步

## CFG-05 · 嵌入地址没进 IDEA 环境变量 → 报错却指向「占位实现」

**问题描述**
IDEA 起 `rag-bootstrap` 报：
```
Failed to instantiate EmbeddingPort: [RAG fail-closed] 本地占位端口未获显式启用，拒绝装配：
EmbeddingPort → LocalDeterministicEmbeddingPort
```
看文案像是「忘了设 `RAG_LOCAL_PORTS_ENABLED`」，**实际不是**。

**产生原因**
`EmbeddingPorts.create()` 的分支是「**`rag.embedding.base-url` 为空**」才走本地占位。
真实原因是 IDEA 挂的那两个 env 文件里**没有嵌入配置** —— 它们此前只写在仓库外的启动脚本
`/tmp/rag-run.sh` 里，**EnvFile 插件读不到仓库外的东西**。

按提示去设 `RAG_LOCAL_PORTS_ENABLED=true` 会把问题**藏起来而不是解决**：占位向量是确定性的假语义，
且维度（1024）与库里的 `halfvec(4096)` 不符，下一步就在装配期被维度校验拒掉，错误还更费解。

**相关解决方案**
1. 新增 `rag-local.env`（嵌入模型、批次、维度、向量列类型、占位闸门），IDEA 与 shell 启动脚本**读同一份**，杜绝两处漂移；
2. 模板提交为 `.env.example`。

**来源**：`docs/RAG检索与端到端实测问题记录_20261028.md` §7.1
**状态**：✅ 已修

## CFG-06 · env 文件含 shell 语法 → IDEA EnvFile 插件解析出脏值

**问题描述**
IDEA 的 EnvFile 插件只做 dotenv 式逐行解析，**不认 shell**：
`export ` 前缀、`$(...)`、`if [ -f ... ]; then ... fi` 会被整行当成变量值塞进环境；值两端的引号也不保证被剥掉。

**产生原因**
把「shell 脚本能跑」等同于「dotenv 能解析」。两种格式的语法子集不重合。

**相关解决方案**
1. `platform.env` 里原先加的 `if … source jwt.env; fi` **撤掉**，改由 `scripts/dev-backend.sh` 负责加载（shell 通道），
   `platform.env` 恢复成插件可解析的纯键值；
2. `scripts/gen-jwt-keys.sh` 产出的 `jwt.env` 值**不再加单引号**（base64url 字母表本身不含空格，无需引用）。

**来源**：`docs/RAG检索与端到端实测问题记录_20261028.md` §7.2
**状态**：✅ 已修

## CFG-07 · env 文件名与属主错配：内容是平台配置的副本，名字却像 RAG

**问题描述**
原 `rag.env` 里其实是**平台配置的副本**（含 `SPRING_*` / `RABBITMQ_*`，且是 `config.env` 的子集），
名字却像 RAG 的配置。

**产生原因**
文件拆分时按「谁在用」而不是「谁拥有」命名。**挂错文件比缺文件更难查** —— 缺文件会立刻报错，
挂错文件则静默用着另一套配置。

**相关解决方案**
按**属主**收敛为三份文件，并各留一份 `.example` 模板入库：

| 文件 | 属主 | 内容 | 是否入库 |
|---|---|---|---|
| `platform.env` | 平台 8080 | DB/MQ/ops 通道/MiniMax | ❌（模板 `platform.env.example` ✅） |
| `rag.env` | RAG 8081 + worker | PG 连接、端口、嵌入模型/维度/向量列、占位闸门 | ❌（模板 `rag.env.example` ✅） |
| `jwt.env` | 两侧共用 | 两域私钥（平台签）+ 两域公钥（RAG 验），**同源一个文件** | ❌（模板 `jwt.env.example` ✅） |

**来源**：`docs/RAG检索与端到端实测问题记录_20261028.md` §7.3
**状态**：✅ 已修

## CFG-09 · dev profile 下私钥留空 → 每次平台重启都生成新密钥，对端验签公钥随之作废

**问题描述**
`AuthConfiguration.resolveKeyPair()` 在 dev profile 下允许 `JWT_PRIVATE_KEY` 留空、**启动时生成新密钥**。
本机平台一直是这个状态，所以 RAG 侧无论配哪把公钥，平台一重启就验不过 —— 表现为
「登录正常、调 RAG 全部 401」，而 401 看着像 RAG 的缺陷，**实际是两侧密钥漂移**。

**产生原因**
「dev profile 自动生成密钥」省事，但让密钥的生命周期与**进程**绑定，而不是与**部署**绑定。
凡有第二个消费者（RAG 验签），这个便利就是故障源。

**相关解决方案**
1. `scripts/gen-jwt-keys.sh` 生成两对 RSA-2048（租户域 / 平台域），
   一把私钥同时产出「平台签发用 `私钥.公钥`」与「RAG 验签用公钥」，**同源写入同一个 `jwt.env`**
   （0600，被 `.gitignore` 的 `*.env` 忽略），两侧各自 source，杜绝手工搬运公钥；
2. `--check` 拉运行中平台的 JWKS 比对指纹；
3. ⚠️ 换密钥后必须**两侧同步重启**，只重启一边就是上面那个故障。
   本机生效顺序：平台先重启（`platform.env` 已 source `jwt.env`）→ 再起 RAG。

**来源**：`docs/RAG检索与端到端实测问题记录_20261028.md` §4.4
**状态**：✅ 已生成配套密钥并留 `--check`；**待平台重启生效**

## CFG-10 · 占位端口开关设为 true 只会把问题藏起来，不是解决

**问题描述**
`rag.local-ports.enabled`（或 `RAG_LOCAL_PORTS_ENABLED`）默认 `false` = fail-closed：
占位 bean 在**创建期**抛异常，应用拒绝启动。三个占位实现的风险：

| Port | 具体风险 |
|---|---|
| `LocalDeterministicDocumentParserPort` | 答案区靠关键词启发式（「答案/解/解析」即判答案区）→ **误判=泄题**；`PLACEHOLDER_PAGE=1` 使**页码全假** |
| `LocalDeterministicEmbeddingPort` | 字符 bigram 哈希，自注「『二次函数』与『反二次函数』也会因共享字相似」→ **串知识点/错误归因** |
| `LocalLexicalEntailmentPort` | `verifyExistence` 占位放行（return true）、`detectConflict` 返回 null → **幻觉引用与冲突检测实际关闭** |

**产生原因**
占位实现是为了让工程能跑起来，但在 dev 环境很容易被「打开开关让服务起来」的直觉击穿。

**相关解决方案**
1. 统一开关 `rag.local-ports.enabled` 缺省 `false`，占位 bean 创建期抛异常 → 应用拒绝启动；
2. 显式 `true` 才放行，且打 **ERROR 横幅**；
3. 覆盖三处装配（`LocalRagPortsConfig` / `RagInfrastructureConfig` / `WorkerInfraConfig`）+ 两份 application.yml + 4 项钉死测试；
4. **替换**（Docling / BGE-M3 / NLI）后应绕过本闸门。

**来源**：`docs/系统优化建议-全量评审.md` §7.2

## CFG-11 · `cap-authorization-enforced` 默认 false 且无任何配置源开启 → 强制层等于没有

**问题描述**
精细能力闭环的强制开关默认 `false`，`ToolInvocationGate` 因此路由到 `invokeAllLegacy`，
而 legacy 链**完全没有闭包校验**（全文件 grep `closure` → 0 命中）。legacy 授权**只判角色、不判工具名**：
`isAuthorized(systemContext, TOOL_INVOKE, toolName)` 里 `toolName` 作为 `resourceId` 传入，

**产生原因**
迁移期灰度开关 + 读侧硬依赖（与 CFG-01 同型，见 [README §三 M1](README.md#三高频根因模式跨分类的共性)）。

`CapEnforcementReadinessGuard` 只打印一行 WARN → **生产启动时没有任何机制拒绝**带着这个缺口运行。

**相关解决方案**
1. 修 seed 的工具 id（`tool-profile-read`/`tool-profile-update` → 运行时 handler 名
   `get_student_profile`/`record_weakness`）；
2. 重算 `config_fingerprint`（`cap_obj_fp_v1:` 前缀，不含时间戳，含 id/version/名称/声明集）；
3. 在目标库复放 seed 装载能力目录 → 切 `CONFIG_FLAG_CAP_CLOSURE_ENFORCEMENT=enforce` +
   `CONFIG_FLAG_CAP_ENFORCEMENT_REQUIRED=true`；
4. ⚠️ **不建议**在 CAP 目录为空的库直接翻 `cap-authorization-enforced=true`：会全拒绝。

**来源**：`审查文档/AI全流程审查报告_2026-10-31.md` P0-1、`审查文档/护栏设计综合评估文档1.md` P0-1

## CFG-12 · HikariCP 生产配置缺失 → 全部落默认 10 连接且无泄漏检测

3. 长期：把 IT 的公共属性抽成基类/共享配置（当前 25 个 IT 类各带一份 `@TestPropertySource`）。
