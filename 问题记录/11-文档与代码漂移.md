# 11 · 文档与代码漂移类

> **判据**：根因是**文档说的和代码做的不是一回事**。
> 危害不亚于代码缺陷：它让**下一个做这件事的人按错的假设工作**。
> 本类的处置原则：**文档与代码不一致时，先确认哪边是对的，再改另一边** ——
> 不是把文档改成「和代码一样」就算完。

## DOC-01 · 业务架构图的 Run 状态机含 `WAITING_APPROVAL` / `RETRYING`，代码里没有

**问题描述**
`docs/业务架构图.md:154-171` 的 Run 状态迁移表把
`WAITING_APPROVAL → QUEUED`（审批通过后重新入队）写成**既成设计**。
实际：`RunState` 枚举 + DDL `run_state` 均**只有 6 值**（无这两个）。

**产生原因**
文档描述的是**打算做**的语义，实现落后了；文档没有标注「规划中」。
读者会以为存在「挂起等审批」语义，实际是「拒绝即失败」。

**相关解决方案**
本轮 HITL 改造（GOV-01）已把 `WAITING_APPROVAL` 真正落地，
文档口径同步对齐为「登记待办 → fail-closed 拒绝 → Run 收敛 FAILED」，
并加脚注说明挂起恢复的实现边界。

**来源**：`审查文档/AI全流程审查报告_2026-10-31.md` P2 第 1 条
**状态**：✅ 已对齐

## DOC-02 · 系统架构图 ERD 含 `AGENT_CONVERSATION` / `AGENT_MESSAGE`，两表不存在

**问题描述**
`docs/系统架构图.md:360-365` 的 ERD 画着 `AGENT_CONVERSATION` 与 `AGENT_MESSAGE`。
实测：**这两个名字在全仓 DDL 与 Java 中均不存在**
（`grep -rn "agent_conversation|AGENT_MESSAGE"` → 0 命中）。
`agent_message_queue` 存在，但它是 **PG 队列**，不是对话表。

**产生原因**
ERD 画的是**目标架构**，没有标注「未实现」。读者据此做容量与存储规划。

**相关解决方案**
对齐为实际状态（对话序列当前是 `RunExecutionLoop` 里的局部 `ArrayList<ModelMessage>`），
或明确标注「规划中，未实现」。会话持久化本身的缺口见
[BIZ-01](13-业务模型缺口.md#biz-01--多轮会话无持久化--同一学生第二次提问时-agent-对上次一无所知)。

**来源**：`审查文档/AI全流程审查报告_2026-10-31.md` P2 第 2 条
**状态**：✅ 已对齐

## DOC-03 · 权限管控文档的 Phase B 顺序与代码不一致（文档内部还有第三种）

**问题描述**
`docs/权限管控体系/05_分层授权决策规范.md:87-115` 写 Phase B 顺序：
`8 Schema → 9 Approval → 10 Idempotency → 11 Budget → 12 Ledger(PRE)`；
代码实际顺序（`CapExecutionFlow.java:436,463,474,490,522`）：
`8 Idempotency → 9 Schema → 10 Ledger(PRE) → 11 Approval → 11.5 RunBudget → 12 Budget`；
而 `01_现状分析.md:43` 还描述了**第三种**顺序。

**产生原因**
三处文档分别在不同时间点写，没有单一真源；代码顺序调整时没有回写。

**影响**
非安全弱化，但**改变 reason-code 优先级** —— 同一个拒绝场景，
不同顺序下最先命中的闸门不同 → 原因码不同 → 运维排查路径不同。

**相关解决方案**
以代码为准统一三处文档顺序（或反过来把代码调成文档顺序），
并在文档里标明「这是唯一真源」。

**来源**：`审查文档/AI全流程审查报告_2026-10-31.md` P2 第 3 条
**状态**：🟡 已定位未修

## DOC-04 · 现状分析高估了现有控制强度（「每次工具执行前 `isAuthorized(..., toolName)`」）

**问题描述**
`docs/权限管控体系/01_现状分析.md:61` 写：
「每次工具执行前 `isAuthorized(..., TOOL_INVOKE, toolName)`」。
实测：`RoleBasedAuthorizationService` **从不读 `resourceId`**，工具名被丢弃。

**产生原因**
文档按「接口签名」描述能力，而接口签名允许传 `resourceId` ≠ 实现会用它。
这正是 [SEC-01](04-安全与合规.md) 的根源 —— 文档让所有读者都以为「按工具名校验」是有的。

**相关解决方案**
本轮在强制层真实落地了「按工具名校验」，该描述**首次与代码相符**
（但需同步补上「仅在 `cap-closure-enforcement=enforce` 时成立」的限定条件）。

**来源**：`审查文档/AI全流程审查报告_2026-10-31.md` P2 第 4 条
**状态**：✅ 已对齐（补限定条件）

**来源**：`docs/RAG检索与端到端实测问题记录_20261028.md` §8.4

> **本类统一教训**：本类的危害是**认知污染** ——
> 读者按文档做出错误假设，然后按错误假设工作，最后把「文档说错了」当成「代码坏了」。
> 处置原则（不能反）：**先确认哪边是对的**。
> 文档低报进度（DOC-06）与高估控制强度（DOC-04）方向相反，
> 但**都是漂移**，都不能靠「把文档改成和代码一样」草草了事 ——
> 要么改代码到文档，要么改文档到代码，**并留下「为什么这一边是对的」的判断**。
