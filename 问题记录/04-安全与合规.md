# 04 · 安全与合规类

> **判据**：根因是**权限边界被绕过 / 校验缺失 / 敏感数据失控 / 对外暴露面过宽**。
> 典型形态：防线只写在呈现层、强制层没接线；占位实现默认可用；审计只观测不阻断。

## SEC-01 · 能力闭包在运行期完全不被校验 —— 任何已注册工具都可被任意 Agent 调用

**问题描述**
`math-tutor` 只声明了 `skill-profile-view` + `skill-report-brief`，
但模型若（被注入诱导地）报出 `tool-parent-notification`（`WRITE_EXTERNAL`），
legacy 链**照样放行**。闭包只在**呈现层**生效
（`AgentModelConfigAssembler.java:106,190-196` 按闭包裁剪给模型看的工具 Schema），
**强制层没有这道校验**。

**产生原因**
五重独立验证串起来的结论：

| # | 证据 | 位置 |
|---|---|---|
| 1 | 开关默认 `false`，且**任何配置源都没有开启它** | `ApplicationConfiguration.java:1683-1687`（`@Value("...:false")`）；`application.yml:499-517` 只有 `cap-dual-write`；`platform.env` 无 `cap*` 键 |
| 2 | 开关关闭时走 legacy 链，legacy 链**完全没有闭包校验** | `ToolInvocationGate.java:515-521`（分支点）、`:1029`（`invokeAllLegacy`）；全文件 grep `closure` → **0 命中** |
| 3 | legacy 授权**只判角色，不判工具名** | `ToolInvocationGate.java:1089-1094` 传入 `call.toolName()` 作为 `resourceId`；但 `RoleBasedAuthorizationService.java:100-115` **从不读取 `resourceId`**，只查 `authzVersion` + 角色→动作表 |
| 4 | 上下文硬编码为 `principal="worker", roles={WORKER}, authzVersion=0` | `ToolInvocationGate.java:1555-1569` |
| 5 | `WORKER` 角色持有 `TOOL_INVOKE` | `RoleBasedAuthorizationService.java:81-89` |

**相关解决方案**
1. 在**强制层**落地「按工具名校验」（不是呈现层裁剪）；
2. 配套兜底开关 `config.flag.cap-enforcement-required` 与
   `CapEnforcementReadinessGuard` —— 生产启动时**必须拒绝**带着缺口运行；
3. 条件：`cap-closure-enforcement=enforce` 时才成立（文档口径已同步补上该限定）。

> ⚠️ **连带影响**：`docs/权限管控体系/02_分层授权设计评估.md:29` 声明的
> 「即便 Agent 被注入恶意指令，它也只能在其已启用 Skill 的能力闭包内活动」
> —— **在默认链路上不成立**。

**来源**：`审查文档/AI全流程审查报告_2026-10-31.md` P0-1
**状态**：✅ 已修（强制层落地）；`enforce` 在 live DB 开启仍剩前置（见 CFG-11）

## SEC-02 · RAG 服务裸奔 + `X-Tenant-Id` 不校验归属

**问题描述**
`rag-bootstrap/pom.xml` **无 Spring Security 依赖、全目录无 `SecurityFilterChain`**。
`RagManagementController` 读取 `X-Tenant-Id`，唯一校验 `requireTenantContext` = 只 `UUID.fromString()`，
**不校验「该主体是否属于该租户」** → 能触达 8081 者**改一个头**即可对任意租户
登记/校验/撤回/删字典/重索引。
`X-Tenant-Min-Trust-Tier` 同样可伪造 → 放行未核验语料进检索。

**产生原因**
RAG 是后建的服务，鉴权（平台侧有 JWT 过滤器链）没有跟着补上；
而「客户端传的头」被当成了「可信的身份」。

**相关解决方案**
`RagJwtAuthFilter`（**纯 JDK RS256 验签，无新增运行时依赖**）：
- 双令牌域：租户令牌**强制** `X-Tenant-Id` == 令牌 `tenant_id` claim，归属不符 → 403；
  平台令牌跨租户豁免；
- **先验签再比 aud/iss**；校验 `exp`；
- 健康探针豁免；**未配公钥时 fail-closed**（构造期抛异常）；
- `enabled=false` 显式逃生门打 ERROR 横幅；
- 12 项过滤器测试。

trust-tier 门槛改由**服务端配置** `rag.retrieval.min-trust-tier`（默认 OFFICIAL_TUTORIAL），
**绝不读可伪造的请求头**。

**来源**：`docs/系统优化建议-全量评审.md` §5.1
**状态**：✅ 已修（2026-10-27）

## SEC-04 · 令牌无吊销 / 无登出 / 无刷新 → 截获令牌 900s 内全效

**问题描述**
`AuthController` 仅 `/token`、`/jwks`、`/roles`；`SecurityConfiguration.java:172` 显式 `logout.disable()`。
签发时生成 `jti`（`JwtTokenService.java:147`）但 `verify()` **从不校验** → 无黑名单。
`authzVersion` 撤权依赖**内存** `ConcurrentHashMap`（`RoleBasedAuthorizationService.java:98/133-135`）
→ **多实例部署撤权不跨节点**。

**产生原因**
JWT 的「自包含」特性被当成了「无状态即可信」：
签了 `jti` 却没有消费它的机制。

**相关解决方案**
1. 补 `jti` 黑名单（吊销）+ 登出端点 + 刷新端点；
2. `authzVersion` 迁 DB（`JdbcAuthzVersionRepository` 已有现成实现）。

**来源**：`docs/系统优化建议-全量评审.md` §5.3

## SEC-05 · MFA 形同虚设 → `mfaRequired` 账号被撞库即直达超管

**问题描述**
`PlatformCredentialAuthenticationService.java:74`：
```java
mfaVerified = !record.mfaRequired()
```
`mfaRequired=true` 时**不发起任何质询即置 false 并签发令牌**；
而且授权链**从未读 `mfaVerified()`**。

**产生原因**
把「该账号要求 MFA」与「本次认证完成了 MFA」混为一谈。
前者是策略，后者是事实 —— 代码把策略的**否定**当成了事实。

**相关解决方案**
强制 MFA 真实质询：未完成质询不得签发令牌，且**授权链必须读 `mfaVerified()`**。

**来源**：`docs/系统优化建议-全量评审.md` §5.4
**状态**：🟡 已定位未修（P1 第 11 项）

## SEC-07 · 零保留闸门硬编码 SYNTHETIC → 合规闸门形同虚设

**问题描述**
`RunController` 把 `DataClassification` **硬编码为 SYNTHETIC**，
`ZeroRetentionGate.assertAllowed` 内 `if (!classification.containsRealStudentData()) return;`
使**真实学生数据分支整段被跳过**。
且闸门**仅在 API 入口**，Worker / 子 Agent 执行层完全不经过。

**产生原因**
占位值（`SYNTHETIC`）没有跟着「数据分类」这条链路一起接线，
而 `containsRealStudentData()` 返回 false 时是**早退**而不是**早进** —— 写错了也不报错。

**相关解决方案**
数据分类从 Run 的实际输入推导，不再硬编码；
闸门下沉到 Worker / 子 Agent 执行层（不能只在入口拦）。

**来源**：`审查文档/护栏设计综合评估文档1.md` P0-3
**状态**：✅ 已修（护栏加固，`86c267b`）

## SEC-08 · 输出侧内容安全缺失 —— 敏感输出「照常下发，仅后台记一笔」

**问题描述**
全仓**无平台侧** PII / 毒性 / 越狱 / 违规内容过滤服务。
`SENSITIVE_OUTPUT` 风险事件**只观测不阻断**：命中后内容仍 `commitSuccess` 正常返回用户。
唯一的「内容安全」是 LLM 供应商自带的模型侧过滤。

**产生原因**
把「输出侧安全」默认交给了模型供应商，而供应商的过滤口径与本平台的合规要求并不一致。
本平台的 `CredentialRedactor` / `DataClassification` 体系只覆盖**输入侧**。

**相关解决方案**
引入输出侧 moderations（对照 Azure Content Safety / OpenAI Moderation / NeMo output rails），
并把 `SENSITIVE_OUTPUT` 从「风险事件」升级为「可阻断的闸门」。

**来源**：`审查文档/护栏设计综合评估文档1.md` P1-1

## SEC-09 · Prompt 注入只观测不拦截 + 工具结果净化分叉 → 测试验证的是死代码

**问题描述**
① `RunExecutionLoop.detectSuspicious` 命中**只打 WARN 不拦截**；
② 红队测试 R-7 验证的 `PromptGuard.wrapToolResult`（结构化 `trust="untrusted"` 标记 + 净化）
**在生产主路径无调用方**；真实工具结果走 `ToolOutcomeRenderer.outcomeText`，
仅加自然语言前缀 + 8000 字符截断，**未调用 sanitize，无结构化标记**。

**产生原因**

**相关解决方案**
1. `PromptGuard.wrapToolResult` 接入生产工具结果渲染路径；
2. 注入检测改为**可阻断**（至少对高危模式）；
3. 零宽字符等注入载体在渲染层剥离。

## SEC-10 · 幻觉检测窄且可绕过 → 纯事实性幻觉完全不检测

**问题描述**
`HallucinationDetector` 仅校验「编造引用/出处」（12 条正则黑名单），
**纯事实性幻觉**（给出错误知识点但不引用出处）完全不检测；
且只在**终答阶段**校验，中间步骤不校验。
可构造「如我们教材所言」这类不命中规则的表述绕过。

**产生原因**
把「输出接地」的责任压在**正则黑名单**上。
黑名单只能拦住「看起来像编造引用的形式」，拦不住「内容本身错」。

**相关解决方案**
1. 接入 RAG grounding（`GroundedCitationVerifier`，M-2）；
2. 提交前分级（把「引用不可核验」与「事实可疑」分开处理，M-3）；
3. 中间步骤也做校验（不只终答）。

**来源**：`审查文档/护栏设计综合评估文档1.md` P1-4

## SEC-11 · `BearerTokenFilter` 对非 Bearer 格式的头部过于宽松 → 侧信道

**问题描述**
```java
String token = header.startsWith(BEARER_PREFIX)
        ? header.substring(BEARER_PREFIX.length()).trim()
        : header.trim();
```
当 `Authorization` 头不是 `Bearer ` 开头时（如 `Basic xxx`），代码会把整个 header 值当 token 提交给
`authenticateToken()`。虽然内部大概率验签失败，但这给了攻击者一个**侧信道**：
通过观察不同格式的响应时间差异（JWT 验签 vs Basic 解析 vs 空值），可探测令牌格式。

**产生原因**
`JwtCurrentPrincipal.extractToken()` 在 API 层有严格的三段式校验，
但 `SecurityConfiguration.BearerTokenFilter` 作为基础设施层过滤器实现更宽松 ——
**同一件事在两处实现，宽松的那处成了实际入口**。

**相关解决方案**
过滤器严格匹配 `Bearer ` 前缀，非 Bearer 格式直接清空上下文（不尝试验证）：
```java
if (header == null || !header.startsWith(BEARER_PREFIX)) {
    SecurityContextHolder.clearContext();
    chain.doFilter(request, response);
    return;
}
```

**来源**：`审查文档/审查-2026-10-30.md` 问题 2
**状态**：✅ 已修

## SEC-12 · `IllegalArgumentException` 处理直接回显 `e.getMessage()` → 泄漏内部信息

**问题描述**
```java
@ExceptionHandler(IllegalArgumentException.class)
public ResponseEntity<ErrorResponse> handleInvalidArgument(IllegalArgumentException e) {
    return ResponseEntity.badRequest().body(new ErrorResponse("INVALID_REQUEST", e.getMessage()));
}
```
项目中**任何地方**抛出的 `IllegalArgumentException` 都会被此处理器捕获，
包括第三方库或未来新增代码。若某处异常消息含 SQL 片段、表名、内部路径，将直接泄漏。

**产生原因**
**过于宽泛的异常捕获 + 直接透传消息。**
当前代码里的 `IllegalArgumentException` 都带固定文案，这个「安全」是**巧合**，不是设计。

**相关解决方案**
兜底处理器改为返回**固定文案**，只把细节记进日志：
```java
log.warn("参数校验失败: {}", e.getMessage());
return ResponseEntity.badRequest().body(new ErrorResponse("INVALID_REQUEST", "请求参数不合法"));
```
（更彻底的方案是引入专用 `InvalidRequestException`，只处理该类型。）

**来源**：`审查文档/审查-2026-10-30.md` 问题 3
**状态**：✅ 已修

## SEC-13 · `PromptGuard.sanitize` 是黑名单，存在已知绕过路径

**问题描述**
以下绕过方式黑名单均无法覆盖：
Unicode 同形字（西里尔 `а` vs 拉丁 `a`）、组合字符/变音序列、HTML 实体编码、URL 编码、
大小写变体（`<USER_INPUT>`）、零宽空格变种（U+2062）、
标记属性变体（`<tool_result\ntrust="untrusted">`）。
类注释**自己承认**「这是黑名单，不可能完备」。

**产生原因**
用**黑名单**做标记隔离。攻击方只需找到一种编码就能绕过，而黑名单永远追不上编码空间。

**相关解决方案**
1. 结构化标记（而非文本标记）+ 解析器侧识别（不靠字符串匹配）；
2. 零宽/同形字符在输入侧**规范化**（NFC + 零宽剥离）而不是在检测侧拉黑；
3. 保留黑名单作为**纵深防御**的一层，不作为唯一一层。

**来源**：`审查文档/护栏设计综合评估文档1.md` BUG-1
**状态**：✅ 已修（护栏加固）

## SEC-14 · `PromptGuard.flatten()` 数据丢失 —— Map key 全丢、数组合并覆盖

**问题描述**
Map 的 key **完全丢失**（只递归 value 不记录路径）；多个数组合并到同一个 `"value"` 键

## SEC-16 · `agent.roles` 声明了但从不校验 —— 治理者会误以为它在起作用

**问题描述**
`CapAgentDef.roles` 的 Javadoc 写「适用主体角色范围（**非授权授予**）」，
`docs/业务架构图.md:123` 也说「仅声明适用主体范围」。
但实测：`cap_agent_def.roles` 在**运行期从不被与调用主体角色比对** ——
`RunCreationService` 的快照解析（`JdbcExecutionSnapshotResolver`）只按 `tenant_id` 过滤，

**相关解决方案**
**要么落实校验，要么从模型里删掉。**
建议删除（成本低、风险低），除非确定要引入「按角色限定可创建哪些 Agent」的语义。

**来源**：`审查文档/AI全流程审查报告_2026-10-31.md` P1-4

## SEC-17 · 平台令牌越进租户域 —— admin-console AI 实验室点执行恒 401

**问题描述**
用户在 AI 实验室点「运行」，`POST http://localhost:5185/api/runs` 带一枚**平台令牌** → **401**。

**产生原因**
**401 本身不是缺陷**：域隔离在令牌层就成立 ——
那枚令牌 `aud=admin-console-api`、`principal_type=PLATFORM_USER`、`roles=[PLATFORM_SUPER_ADMIN]`、未过期，
而 `/api/runs` 属**租户域**：

| 事实 | 证据 |
|---|---|
| 租户侧验签把 `aud` 与自身配置的 `agent-platform` 硬比对，不等即拒 | `JwtTokenService.java:208` |
| 租户**只能**取自已验签令牌，请求体里没有也不该有 `tenantId` | `RunController.java:137-139`（「绝不从请求参数或请求体取租户」） |
| 平台链反之拒租户令牌，两向都堵 | `SecurityConfiguration.java:112-113` / `:309` |

所以「按 curl 的 401 去放宽租户链、或给请求体塞 tenantId」**都是错的方向** ——
这条边界是**防平台令牌越进租户域的设计**。

**相关解决方案**
定案并落地「跨域执行票证」通道（**生产默认开**，覆盖了「默认关」的建议），
形态不是「平台域代发起 Run」，而是「**平台域签发短时租户令牌**」，租户侧六道闸门一律照旧：

**四道签发闸门 + 一次留痕**（闸门顺序即代码顺序）：

| 顺序 | 闸门 | 不过时 | 为什么在这个位置 |
|---|---|---|---|
| 1 | 平台权限 `platform.tenant.execution_ticket`（只绑 `PLATFORM_SUPER_ADMIN`） | 403，**不写审计** | 未授权的探测不该污染审计流；只有过了授权才说明「有人试图扮演租户」 |
| 2 | 开关 `…execution-ticket.enabled` | 503 + `DENY/CHANNEL_DISABLED` 审计 | 关掉的通道被人敲要留痕，否则「有没有人在试」不可知 |
| 3 | 按**目标租户**限流（桶 `PLATFORM_EXECUTION_TICKET`，继承全局 30 次/60 秒） | 429；限流器不可用也 **429**（fail-closed，不放行） | 桶键是**被扮演的租户**而不是平台用户：防的是「单个租户身份被刷」 |
| 4 | 租户存在且非 SUSPENDED/DECOMMISSIONED、成员 ACTIVE、角色交集非空 | 404/409 + 对应 `DENY` 原因码 | 票证的 `principalId` 必须是真实存在的租户成员 |

**一处比设计更紧**：设计要求「角色固定 `[AGENT_AUTHOR]`」，实现是
**与库中该成员已登记角色取交集，交集为空即拒** ——
否则任何一次取票都会凭空给主体注入一个它没有的角色，`authz_version` 与撤权传播也就失去意义。

**TTL 由调用方逐次指定**：`JwtTokenService` 原来只有构造期的 15 分钟 TTL；
新增 `issueDetailed(context, now, ttl)` 返回 `(token, jti, expiresAt)`，`issue()` 保持原语义委派过去
—— 而不是再造一个 60 秒的第二签发器（那会出现两个 bean 共用 `aud`/`iss`/密钥配置，
「哪把钥匙签的」变成隐性事实）。构造期下限校验 `ttl-seconds >= 60`。

**前端**：Lab 从「粘贴令牌」改为「取票证」；票证租户绑的是**选中 Agent 自己的租户**
（`selectedAgent.tenantId`），不是上方过滤下拉 —— 租户来自验签令牌，给 A 取票跑 B 的 Agent
只会在执行时授权那步被拒。票证**只在内存**（`executionTicketApi.ts` 模块态），
React state 里存的是**不含 accessToken 的快照**，否则令牌会出现在 React DevTools 的渲染树里。
发租户域请求必须 `auth=false` + 第 4 个 `extraHeaders` 参数：
`client.ts::_request` 在合并完 extraHeaders **之后**才用平台会话覆盖 Authorization，
用 `auth=true` 等于把票证扔掉 —— 那正是原始 401 的成因。

**仍不假装做到的事**：票证解决「能不能拿到租户身份」，**不解决**「凭据不落 URL」。
`EventSource` 依旧带不了 Authorization 头，所以 Lab 仍然轮询，SSE 没有被声称支持。
续取节奏实测：轮询 2 秒一次、TTL 60 秒、提前 15 秒续 → **约每 45 秒一次签发**，
一次 300 秒的观察上限约 7 条审计。这条断言写在测试里（每 tick 取票会把审计流刷成噪音）。

**来源**：`docs/RAG检索与端到端实测问题记录_20261028.md` §8.1 / §8.5
**状态**：✅ 已落地

## SEC-18 · 工具参数 / 输入 JSON 手写转义漏控制字符 → jsonb 落库整批回滚

**问题描述**
票证通了之后，多行输入的 Run 创建 **500**：
```
JdbcRunCreationRepository : Run 原子写入失败（外层事务将回滚）: runId=c568d13f…,
  原因=ERROR: invalid input syntax for type json
  详细：Character with value 0x0a must be escaped.
```
`run.input_payload` 与 `outbox_event.payload` 都以 `?::jsonb` 落库，
PG 在解析阶段就拒裸 `0x0a`（JSON 规范：U+0000–U+001F 必须转义）。
于是红线 3 的四条 INSERT（Run + 初始事件 + 幂等记录 + Outbox）**整批回滚** ——
症状是 500，不是「某一条没写」。

**产生原因**
`JdbcRunCreationRepository.toJson` 的链式 `replace` **只处理 `\` 和 `"`**：
```java
String s = String.valueOf(v).replace("\\", "\\\\").replace("\"", "\\\"");
```
而方法上的注释写着「避免引入完整 JSON 库到基础设施层」——
**但前提是假的**：本模块 pom 早已依赖 Jackson 3（`tools.jackson`），
`JdbcRunInputRepository` 等同目录十几个类都在用 `ObjectMapper`。

**相关解决方案**
1. 改用 `MAPPER.writeValueAsString` / `MAPPER.readValue(…, MAP_TYPE)`，
   读回侧顺带修掉「按逗号裸切分」的解析（值里含逗号时原本会错位）；
2. **同族缺陷**：另外两处「转义了 `\n`/`\r` 但没转义 `\t`」——
   `JdbcToolOperationLedger.quote`（工具调用参数 `?::jsonb`，模型生成的参数里制表符极常见）、
   `RunEventController.escape`（SSE 事件体，载荷含制表符时客户端 `JSON.parse` 失败）——
   各补一行 `.replace("\t", "\\t")`；
3. `RequestDigest.escape` 同样漏控制字符，但**刻意不动**：
   它的产物是幂等摘要的输入，改了会让在途请求的摘要全部对不上（幂等冲突），而它从不被当 JSON 解析。

**同库只读实测**（`SELECT (?::jsonb)->>'userMessage'`，不写任何表）：
```
旧手写 : ✗ ERROR: invalid input syntax for type json   详细：Character with value 0x0a must be escaped.
新输出 : ✓ jsonb 通过，回读逐字相等=true（utf8 往返无损=true）
```
回归测试补在 `RunCreationAtomicityIT.multilineInputSurvivesJsonb`（用 `->>` 断言，让 PG 自己出具合法性证明）。
⚠️ 该类挂 `@EnabledIfEnvironmentVariable(IT_PG_URL)`，**日常 `mvn test` 不跑** ——
所以这条修复的单测证据是 0，**上面那次只读实测才是真正的证据**（见 [TST-09](07-测试基建与验证方法论.md)）。

**来源**：`docs/RAG检索与端到端实测问题记录_20261028.md` §10
**状态**：✅ 已修

## SEC-19 · `CreateRunRequest.flatten()` 递归无深度限制 → 可被恶意输入 DoS

**问题描述**
`flatten()` 递归遍历嵌套 Map/List 结构。客户端传入**深度极深**（如 10000 层）或**循环引用**的输入，
会导致 `StackOverflowError` 或 OOM。

**产生原因**
递归无深度限制、无 visited 集合防循环、无节点数上限。
（同类问题见 SEC-15 `PromptGuard.safeRender`。）

**相关解决方案**
增加深度限制和节点数上限。

**来源**：`审查文档/审查-2026-10-30.md` 问题 4
**状态**：✅ 已修

## SEC-21 · `authzVersion` 校验存在竞态窗口 + 内存实现导致多实例撤权不跨节点

**问题描述**
- `authzVersion` 在 `TenantContext` 创建后**不再更新**，请求处理中途的撤销存在约 **10–100ms** 的窗口；
- 撤权依赖**内存** `ConcurrentHashMap` → 多实例部署撤权不跨节点。

**产生原因**
把「请求开始时读到的版本」当成「请求全程有效的版本」。
并发撤销是异步事件，快照式读取天然有窗口。

**相关解决方案**
1. 高风险操作在 `DelegationGuard` 中**每次重新读取权威版本**；
2. `authzVersion` 迁 DB（`JdbcAuthzVersionRepository` 已有）；
3. `ExecutionAdmissionChecker` 已在外部副作用前重读权威 `authzVersion` 并重算闭包指纹（TOCTOU 线性化边界）。

**来源**：`审查文档/审查-2026-10-30.md` 问题 8、`docs/系统优化建议-全量评审.md` §5.3
**状态**：🟡 部分已修（准入检查已重读；内存实现迁 DB 未做）

## SEC-22 · `DelegationExecutor.buildContext()` 授权版本校验失效（哨兵值恒假）

**问题描述**
`authzVersions.require(command.tenantId(), "worker").authzVersion()` ——
调用了 `require()` 但仅取其 `authzVersion()`。若 `require()` 内部在版本校验失败时抛出异常，
调用方 `catch (RuntimeException e)` 块会捕获并返回 `null`；更关键的是，
若 `require()` 返回的 `authzVersion()` 是 `-1` 或 `0` 等**哨兵值**，
下游 `checkAuthzFreshness()` 的比较 `context.authzVersion() < current` 会**恒为 false**
→ **陈旧上下文被放行**。

**产生原因**
1. `AuthzVersionPort.require()` 的契约不清晰 —— 是 fail-fast 抛异常还是返回带哨兵值的对象？
2. `buildContext()` 对 `require()` 的返回值没有做「读不到 = fail-closed」的显式校验；
3. `checkAuthzFreshness()` 中 `current` 的默认值语义不明确。

**相关解决方案**
```java
long authzVersion;
try {
    AuthzVersionPort.AuthzVersion authz = authzVersions.require(command.tenantId(), "worker");
    if (authz == null || authz.authzVersion() < 0) {
        log.error("权威授权版本不可用: tenant={}", command.tenantId());
        return null; // fail-closed
    }
    authzVersion = authz.authzVersion();
} catch (RuntimeException e) {
    log.error("权威授权版本读取失败，fail-closed: tenant={}", command.tenantId(), e);
    return null;
}
```
配套：`require()` 契约明确写为「不可用即抛异常」，不再返回哨兵值。

**来源**：`审查文档/审查-2026-10-30.md` 问题 1
**状态**：✅ 已修

## SEC-23 · `IdempotencyGuard` IN_FLIGHT 状态悬挂无自动恢复

**问题描述**
Worker 崩溃后 IN_FLIGHT 状态**不会自动恢复**，所有后续重试被挡住，直到人工介入。
类注释将此归为 P3 故障恢复，但生产环境中一次 OOM 可导致一批操作**永久悬挂**。

**产生原因**
把「崩溃恢复」当成罕见事件，没意识到 IN_FLIGHT 是一个**没有超时**的状态。

**相关解决方案**
给 IN_FLIGHT 加超时/租约，过期自动释放；或由恢复扫描器统一回收。

**来源**：`审查文档/护栏设计综合评估文档1.md` BUG-5
**状态**：✅ 已修

## SEC-24 · `platform_ops` / `rag_ops` 运维通道 BYPASSRLS 的补偿措施散在应用侧

**问题描述**
BYPASSRLS 意味着**库层不再限制该角色写哪个桶**。补偿完全靠应用侧三道约束：
① `GuardedRagOpsDataSource`（会话窗外取不到连接）；
② ops 事务入口**不接收租户参数**，哨兵桶由实现内部绑定；
③ A 档窗口只发 SELECT。
另加库内 CHECK（`scope='PLATFORM' ⇔ tenant_id=哨兵`，CHECK 不是策略，BYPASSRLS 绕不掉）。

**产生原因**
BYPASSRLS 是必要的（平台级对象的写策略只放行本租户 TENANT 行，平台行必须由此角色写入），
但它天然绕开行级安全 —— 补偿只能落在别处。

**相关解决方案**
维持现状并把约束固化为**架构测试**：
`PlatformOpsDataSourceArchitectureTest` 明确禁止新增运维数据源消费者
（运维连接装到业务读路径 = 租户隔离整体失效）。
**本角色不得用于任何其他用途**：不给 `rag_app` 加成员、不给 DELETE、不给 schema 建对象权。

**来源**：`docs/数据库用户与权限梳理_2026-11-01.md` §2.3
**状态**：🟡 设计内，靠架构测试约束
