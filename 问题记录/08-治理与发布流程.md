# 08 · 治理与发布流程类

> **判据**：根因是**审批 / 发布 / 复核流程本身没接通**，而不是某个接口有 bug。
> 典型形态：能力声明写在文档/模型里，但强制层没有对应的执行路径。

---

## GOV-01 · 人工审批闭环从未接通 —— 审批台永远查不到待办

**问题描述**
需要审批的工具（如 `WRITE_EXTERNAL` 的 `tool-parent-notification`）在生产**恒被拒**；
而 `ApprovalController` 的 `/api/approvals` 与 `/api/approvals/{id}/decision`
因为**没有任何代码创建待审批行**而**永远返回空列表**。
审批台是一扇**装好了门把手但通向墙壁的门**。

**产生原因**
四重事实链：

| # | 证据 | 位置 |
|---|---|---|
| 1 | `ApprovalPort.grant()` 是唯一写入 `approval` 表的入口，**生产代码零调用**（仅测试调用） | grep `\.grant(` 全仓 → 命中全部在 `*/src/test/*` |
| 2 | 审批台列表读的是 `approval` 表的 `PENDING` 行 | `JdbcApprovalQueryRepository.java:43-47` |
| 3 | 生产审批来源是**空策略** → 所有需审批工具恒返回 `FAIL_CLOSED` | `WorkerExecutionConfig.java:224-226`（`new PolicyEngineApprovalSource()` 空 map）；`application.yml:323` `live-source-enabled: false` |
| 4 | 后端 Run 状态枚举**没有 `WAITING_APPROVAL`**，也没有 `RETRYING` | `RunState.java`（仅 6 值）；`01_platform_ddl.sql:214-221` `run_state` 枚举同样 6 值 |

**相关解决方案**
G1/G2 HITL 改造（`86c267b`，2026-11-01）落地：
- `RunState.WAITING_APPROVAL` + **PARK/RESUME 检查点**挂起/恢复 + 审批决定同步唤醒；
- `ApprovalSource` **配置化**（`none` / `policy-engine`），与 `live-source-enabled` 保持**一致性 fail-closed**；
- CAP 数据模型放宽待人工决策（`AWAITING_HUMAN` / `approver_id`·`decided_at` 可空）；
- 新增 `ApprovalReadinessGuard` 等 fail-closed 守卫及回归测试。

> ⚠️ **文档矛盾（同时修正）**：`docs/业务架构图.md:154-171` 的 Run 状态迁移表把
> `WAITING_APPROVAL → QUEUED`（审批通过后重新入队）写成既成设计，
> 代码里**这个状态与这条迁移都不存在**。
> 当前实现是「审批不通过 → 工具被拒 → 整轮失败」，没有「挂起等待」语义。

**来源**：`审查文档/AI全流程审查报告_2026-10-31.md` P0-2
**状态**：✅ 已修（待办可见 + 挂起/恢复检查点）

## GOV-02 · `ApprovalSource.Verdict` 只有三种取值，接口表达不了「挂起等待」

**问题描述**
`ApprovalSource.Verdict` 只有 `APPROVED` / `REJECTED` / `FAIL_CLOSED`，**无 `PENDING`**。
→ 审批来源目前**无法表达「挂起等待」**，只能表达「通过 / 拒绝 / 闭锁」。

**产生原因**
接口设计时（审批只有「批 / 不批」两种结果）没有预留「挂起」这一态；
后续要加挂起时，接口本身成了阻塞项。

**相关解决方案**
HITL 改造中扩展 Verdict 语义（配合 `RunState.WAITING_APPROVAL` 与 PARK/RESUME）。

**来源**：`审查文档/AI全流程修复报告_2026-10-31.md` §4 第 6 条
**状态**：✅ 已修

## GOV-03 · Run 状态缺 `WAITING_APPROVAL` → 要加一个状态得动三层

**问题描述**
Run 状态枚举在 **DDL `run_state`（`01_platform_ddl.sql:214`）、后端 `RunState`、前端 `RUN_STATES`** 三处锁死，
加一个状态要动三层。

**产生原因**
状态定义在**三处各写一份**，没有单一真源。

**相关解决方案**
HITL 改造同步改三层 + 前后端契约文档对齐。

**来源**：`审查文档/AI全流程修复报告_2026-10-31.md` §5.2
**状态**：✅ 已修

## GOV-04 · 审批按 `operation_id` 绑定，工具幂等键含模型 call id → 审批行孤儿化

**问题描述**
审批按 `operation_id` 绑定，而工具幂等键**含模型 call id**
→ Run 重投未必产生同一 `operation`，**审批行会孤儿化**。

**产生原因**
审批的关联键与幂等的关联键**粒度不同**：
幂等键绑到「模型的一次 call」，审批绑到「一次操作」。重投时前者变、后者不变（或反之）。

**相关解决方案**
HITL 改造中把审批与 Run 的关联改为**稳定标识**（Run 级 + 挂起点），而非模型 call 级。

**来源**：`审查文档/AI全流程修复报告_2026-10-31.md` §5.2 第 2 条
**状态**：✅ 已修

## GOV-05 · 配置发布旁路：`/agents/{id}/versions` 无门禁无复核直写

**问题描述**
`api/governance/AgentController.java:170-195` 的 `POST /api/agents/{id}/versions`
以 `AGENT_MANAGE` 权限**直写自由 JSONB definition**，**无门禁无复核**；
`CapDualWriteService` 双写会把它带进权威表。
与「三步发布」（草稿→审批→发布）自相矛盾。

**产生原因**
旧模型链（`agent_version` 直写）与新模型链（CAP 三步发布）并存，
旧入口没有被下线 —— **能力声明与执行入口脱节**。

**相关解决方案**
**端点下线**（而非补门禁）：唯一消费方是孤儿页，无门禁直写不可留。

**来源**：`docs/系统优化建议-全量评审.md` §6.3
**状态**：✅ 已修（端点下线）

## GOV-06 · 运行时人工审批未接线 —— `ApprovalController` 走的是另一条链路

**问题描述**
`WorkerExecutionConfig.approvalSource()` 返回空 `PolicyEngineApprovalSource`
（空 map → 全部 `FAIL_CLOSED`）。
任何 `WRITE_EXTERNAL` 副作用工具在运行时**永被拒绝**，
但 `agent-api` 的 `ApprovalController` 人工决策端点操作的是**另一条链路**
（能力/配置发布域），**不覆盖工具副作用执行域** —— **无活体人工放行通道**。

**产生原因**
「审批」在本项目里有**两套实现**（`approval` / `cap_approval`），人工端点只接了其中一套。

**相关解决方案**
要么接上（工具副作用域的 HITL），要么明确产品决策（**全拒 = 安全默认**）并文档化 + 加开关。
HITL 改造（GOV-01 ~ GOV-04）已接通主路径。

**来源**：`审查文档/护栏设计综合评估文档1.md` P1-3
**状态**：🟡 部分已修

## GOV-07 · `approverId` 是 `@Nullable`，双人复核只在「调用方 + DB CHECK」

**问题描述**
`ConfigPublishCommand.approverId` 是 `@Nullable`，
`ConfigPublishService` 内**无该校验**；`01_platform_ddl.sql:1754` 的 CHECK 允许 approver 为 NULL。
→ 双人复核**完全依赖调用方自觉** + DB 约束。

**产生原因**
「双人复核」被实现成「审批时带一个 approverId」，
而没有校验「这个 approverId 不能等于 requesterId、且不能为空」。

**相关解决方案**
应用层校验 + DB CHECK 双重落实（DB CHECK 的双 NULL 放行问题见 [DBP-15](03-数据库权限与RLS.md#dbp-15--cap_config_release_two_person_ck-谓词允许双-null-放行--名不符实)）。

**来源**：`审查文档/AI全流程审查报告_2026-10-31.md` P3 第 3 条
**状态**：🟡 部分已修

## GOV-08 · 两套审批模型并存（`approval` / `cap_approval`），申请-审批-执行权未分离

**问题描述**
legacy `approval` / `JdbcApprovalRepository` 与 `cap_approval` 双轨；
**申请/审批/执行权未分离**（`CONFIG_PUBLISH` 共用），
而 legacy `ConfigChangeController` 反而用 `config:change` / `config:approve` 分离。
→ **SoD（职责分离）不彻底**。

**产生原因**
新模型链建设时没有下线旧模型链的审批部分，导致两套并存且口径不一。

**相关解决方案**
统一到 CAP 审批模型；把 `CONFIG_PUBLISH` 拆成「申请 / 审批 / 执行」三个权限。
HITL 改造中把 `agent.approval.approver-scope` 接入运行时（见 [CFG-13](01-配置与开关.md)）。

**来源**：`docs/系统优化建议-全量评审.md` §6.2
**状态**：🟡 已定位未修

## GOV-09 · `approval` 表无 `operation_id` 唯一约束 → 幂等靠应用层保证

**问题描述**
`approval` 表无 `operation_id` 唯一约束；
CHECK 要求 `state != PENDING → approver_id IS NOT NULL`。
→ 幂等靠本轮新增的 `WHERE NOT EXISTS` 原子语句保证，**而不是靠唯一索引**。

**产生原因**
表结构设计时把「同一操作只应有一条待审批」这件事交给应用层，
没在库里立约束。

**相关解决方案**
应用层用 `WHERE NOT EXISTS` 的原子 INSERT 保证幂等；
后续可考虑加唯一索引（`WHERE state='PENDING'` 的部分唯一索引）。

**来源**：`审查文档/AI全流程修复报告_2026-10-31.md` §4 第 7 条
**状态**：✅ 已修

## GOV-10 · 生命周期迁移的原状态不符被误当作「迁移非法」

**问题描述**
`executeLifecycle` 中 `lifecycle.transition` 返回 `false` 时，
抛 `ConfigPublishBaselineConflictException`。
⚠️ **原状态不符 = 并发竞争（CAS 前置条件不满足）**，
这不是「迁移非法」，而是「别人先动了」—— 两者必须能分开。

**产生原因**
把「CAS 失败」和「迁移非法」用同一个异常表达，运维无法区分
「我的操作撞车了，重试即可」和「这个迁移根本不允许」。

**相关解决方案**
1. 区分两类失败：`ConfigPublishBaselineConflictException`（基线冲突，可重试）
   与「非法迁移」（不可重试）；
2. `executeLifecycle` 用 try-catch 包裹并**保留原始异常信息**（记日志 + 原样抛出），
   避免原始栈被吞；
3. 配套：按**可重试/不可重试**给出不同的前端提示与退避建议。

**来源**：`platform/问题记录/记录-2026-10-30.md` 问题 6/7
**状态**：✅ 已修（异常信息保留）；分类细化 🟡
