> **判据**：根因是**测试自己骗了自己** —— 假绿、假阴性、夹具把缺陷盖住、基线不可复现。

> 「反证工具自身的假阴性比产品缺陷更危险，因为它会让整套反证退化成『永远全绿』的仪式」。

## TST-01 · platform-bootstrap IT 管理员连接池永久泄漏

**问题描述**
本轮修复后的**第一次全量构建**在 `ConfigEndpointIT` 处整体失败（4 项 ERROR）：
```
Caused by: ... Error creating bean with name 'retentionJob' ...
  解析租户 slug 失败（fail-closed）: slug=t-a →
  SQL 异常 [53300] FATAL: remaining connection slots are reserved for roles with the SUPERUSER attribute
```

**产生原因**
两层叠加：
1. **JUnit 默认每个测试方法新建一个测试类实例** → `private HikariDataSource adminPool` 是**实例字段**，
   「每个方法都是 null」→ **每个测试方法都新建一个连接池**；
2. Hikari 的 `minimumIdle` **默认等于** `maximumPoolSize`（此处 2）→ 每个池常驻 2 条连接；
   而池**从不关闭** → 连接**永不归还**。

实测：platform-bootstrap 的 failsafe 阶段在 2 秒内创建了 **54 个池**、只关闭了 5 个；
PG 侧 `pg_stat_activity` 达 **99 条**（全部为超管 `agent` 身份）→ 打满 `max_connections=100`
→ **普通角色 `app_agent` 无连接可用** → 后续 IT 类的 Spring 上下文启动失败。

> ⚠️ **报错点与真因相隔一个类**：真因在 `GovernanceEndpointIT` 等类的池泄漏，报错在 `ConfigEndpointIT` 的上下文启动。
> 且 PostgreSQL 把**连接槽位优先留给超管** ——
> **泄漏者正是超管，被拒者却是普通角色**，故障现场极具误导性。

**相关解决方案**
对 platform-bootstrap 的 6 个 IT 类统一收口：
1. 管理员池改为 **`private static`**（生命周期跨测试方法）；
2. 新增 **`@AfterAll` 关闭池**（static 只把泄漏从「每方法一个」降到「每类一个」，**不关闭则泄漏依旧**）。

> ⚠️ **只做其中一项都无效：两个动作缺一不可。**

**效果**：
| 指标 | 修复前 | 修复后 |
|---|---|---|
| PG `pg_stat_activity` 连接峰值 | **99** | **10** |

**来源**：`docs/E2E实测缺陷修复与复验_20261023.md` §5
**状态**：✅ 已修

## TST-02 · `RealBrokerEndToEndIT` 默认连**生产 vhost** → 与运行实例互相消费

**问题描述**
`messageSentAndReceivedWithIntegrity` 断言「发一条后深度 +1」得到 **0**
（`expected: 1 but was: 0`）。

**产生原因**
该 IT 用 `env("RABBITMQ_VHOST", "agent")` 取 vhost —— **默认值就是生产 vhost**；
而 `set -a; . platform.env` 会把 `RABBITMQ_VHOST=agent` 导入，**覆盖掉隔离意图**。
8080 上的运行实例正在消费同一队列 `agent.run.execute`，消息**瞬间被取走** → 深度不增。

**性质**：**测试隔离缺陷**，不是产品缺陷。
队列深度探测本身是对的 —— 它**如实反映了「消息被消费了」**。

**相关解决方案**
1. IT 默认 vhost 改为 `agent-test`；
2. 在 `dev-it-db.sh` / `dev-rabbitmq.sh` 里显式导出 `RABBITMQ_VHOST=agent-test`；
3. 深度断言前先确认无外部消费者。

> ⚠️ 与 `scripts/dev-it-db.sh` 头部记载的**同形态**：「IT 与运行实例共用一套基建 → 双方互相污染」。
> **该脚本只解决了数据库侧，没解决 MQ 侧。**

**来源**：`docs/开发进度总览.md` §八 F-1
**状态**：✅ 已修

## TST-03 · 全量 `mvn clean verify` 在运行实例占用连接时不可复现

**问题描述**
`platform-bootstrap` 4 项错误（`ConfigEndpointIT` 全类），
根因链末端 `PSQLException: FATAL: sorry, too many clients already`。

**产生原因**
三层叠加突破 `max_connections=100`：
1. Hikari 默认 `maximumPoolSize=10` 且 **`minimumIdle` 默认等于 `maximumPoolSize`**
   → 每个池「急切占满」10 条；
2. 各 IT 的 `@TestPropertySource` **互不相同** → Spring 上下文缓存里存在**多份上下文**，
   **每份各持一个独立 DataSource 池**，且上下文**直到 JVM 退出才关闭**；
3. 本机同时有运行实例（`PostgreSQL JDBC Driver` **10 条**）+ Navicat 4 条 + 保留 3 条。

**为什么测试自建池没事**
IT 里用 `HikariConfig` 手工建的池**都限了大小**（1/2/4/8），
例如 `FaultInjectionSupport.appPool(1)`；
**唯独 Spring 上下文注入的那个 `spring.datasource.*` 池没限** —— 这正是漏掉的那一个。

**相关解决方案**
1. IT 的 `@TestPropertySource` 统一加 `spring.datasource.hikari.maximum-pool-size=2` + `minimum-idle=0`；
2. 或提高容器 `max_connections`；
3. 长期：把 IT 的公共属性抽成基类/共享配置（当前 25 个 IT 类各带一份 `@TestPropertySource`）。

> ⛔ **本项目第四次同形态**：F-14（测试没跑起来）、CP-1/CP-2（反证假阴性）、
> A-2（断言无判别力）、**本次（绿灯的条件不可复现）**。
> **共同点：都不是「红」，而是「在别人复现时未必还绿」。**

> 📌 **教训**：
> 「全量构建通过」这句话**本身携带一个没说出来的前提** —— 「当前没有运行实例占用 MQ 与 DB」。
> 前提不写出来，下一个人（或下一轮的我）就会在**条件不同**时得出「怎么红了」的错误结论，
> 甚至反过来怀疑代码。**基线必须连同其成立条件一起记录**，否则它就不是基线，是运气。

**来源**：`docs/开发进度总览.md` §八 F-2
**状态**：✅ 已修

## TST-04 · `CapITBase` 取真实业务租户并整租户清 CAP 表 → 生产种子数据被反复清零

**问题描述**
实测 `cap_agent_def` **1176 → 1**、`cap_authz_version` **10 → 0**、`cap_config_pointer` → **0**。
每跑一轮 IT 就抹掉真实业务租户（t-a / t-b）的生产种子数据。
症状出现在**生产链路**上（快照永远 0 行），**真因在测试基座的清理语句里**。

**产生原因**
`CapITBase` 取的是**真实业务租户** t-a / t-b，且 `@BeforeEach` 按 `tenant_id` **整租户清** CAP 表。
测试基座假设「测试库 = 生产库的副本」，但清理动作是**破坏性**的。

**相关解决方案**
1. IT 自建**专用租户** `it-cap-it-a` / `it-cap-it-b`，写入与清理都只落在这两个租户；
   「清空后再断言」的老契约原样成立，**真实租户零污染**；
2. 连带修正若干 IT 的**全表计数断言**（如 `count(*) FROM cap_config_release == 0`）——
   那类断言的前提是「表是空的」，改为按 IT 专用租户 / IT 对象集合计数后，
   **语义反而更准**：「本次操作有没有留下半成品」而非「表里除了我写的还有没有别人的」。

**数据稳定性实测**：跑完全量 IT 后 `cap_agent_def(407)` / `cap_authz_version(12)` / 指针(2) **不变**。

**来源**：`git log 312818e`（2026-11-01）
**状态**：✅ 已修

## TST-05 · `mvn -q` 连带抑制 `[INFO] Tests run:` 汇总行 → 反证假阴性

**问题描述**
反证脚本用 `mvn -q` 跑测试并 grep `[INFO] Tests run:` 汇总行，
`-q` 会连带**抑制**该行 → grep 永不匹配 → **5/7 反证被误报为「如期保持绿」**。

**产生原因**
`-q`（quiet）抑制的不只是 stdout 噪音，**也包括被 grep 依赖的那一行**。
脚本与构建工具的输出契约没有对齐。

**相关解决方案**
脚本改为**数 XML 的 `<testcase>`**，不读 `.txt` 的 `Tests run`（JUnit5 分组会让该值显示为 0）。
脚本内置「本轮确实跑了用例」断言，否则一律判**无效**而非**绿**。

**来源**：`docs/开发进度总览.md` §3.2 CP-1
**状态**：✅ 已修

## TST-07 · 三类「假不变式」写法

**问题描述**
以下断言写法看起来在验证隔离性，实际**恒真**：

| 写法 | 为何错 | 改为 |
|---|---|---|
| `list(tenantB).isEmpty()` | 隔离 IT 库**跨运行累积**，tenantB 自己也有数据 | 断言「B 看不到 A 的**任何一行**」+ 管理连接对照 |
| 夹具用 `snapshot_id LIMIT 1` | `execution_snapshot` 有 `tenant_id`，跨租户复用会撞约束，而失败现场指向 Run 代码 | 按租户取快照并缓存 |
| 端点 IT 用注入的 `DataSource` 造夹具 | Spring 注入的是**非特权 app_agent + 强制 RLS**，读不到快照 | 夹具另开**管理连接** |

**产生原因**
把「测试通过」当成「断言有判别力」的证明。**恒真的断言永远通过**。

**相关解决方案**
改写为有判别力的形式（见右列）。

**来源**：`docs/开发进度总览.md` §3.3
**状态**：✅ 已修

## TST-08 · 反证断言夹具无判别力（A-2 长期「假绿」）

**问题描述**
反证 A-2 的注入因 `sed` **行首锚定**从未匹配；且即使修好注入也抓不住
（全序由「ORDER BY + 游标谓词」两处共同保证）；且断言夹具**无同刻多行**，本就不具判别力。

**产生原因**

**相关解决方案**
三处（注入行首锚定 / 排序保证 / 夹具同刻多行）全部修复，并**双向复验**：
证明「注入生效时确实转红」+「注入未生效时不转红」。

**来源**：`docs/开发进度总览.md` §三（2026-10-21 09:35 复核）

## TST-10 · 状态码相同不代表根因相同 → 误报「缺 `revisionCode` 返 500」

**问题描述**
曾登记一条缺陷：「缺 `edition.revisionCode` 返回 500」。
**实测是 400** —— `RetrievalRequestDto` 上有 `@Valid @RequestBody`，

教训：**状态码相同不代表根因相同，先看错误体里的消息再登记缺陷。**

## TST-11 · 排除法要按「读方实际查的那张表」来验

**问题描述**
排查 `CONFIG_UNAVAILABLE` 时，表里写「能力快照双写没落 → `cap_agent_def` 对该 agent 有 1 行」，
但执行准入读的是 `execution_capability_snapshot`（Run 级），
`cap_agent_def` 是 Agent 级定义投影，由**另一个挂点**（`onAgentVersionPublished`）写。
用后者的存在推断前者没缺，是**一次无效的排除**。

**产生原因**
用**同族表名**（`cap_*`）做推断。同族前缀让两张语义完全不同的表看起来像一回事。

**相关解决方案**
**教训：排除法要按读方实际查的那张表来验。**
找表的标准动作：先读**读侧代码**（`RootAgentModelConfigProvider` / `WorkerExecutionConfig`），
确认它到底查哪张表，再去库里查那张表。

**来源**：`docs/RAG检索与端到端实测问题记录_20261028.md` §8.3
**状态**：⚪ 方法论已固化

## TST-12 · 「和基准库一致」不等于「能执行」

**问题描述**
两类现成校验都放行了「有目录、不能跑」的库：

| 校验 | 为什么放行 |
|---|---|
| 空库复放 `ON_ERROR_STOP=1` → 0 错误 | 它验的是**脚本能跑完**，定义表 INSERT 本来就能跑完 |
| `scripts/compare-db-schema.sh` 基准 vs 复放逐项一致 | 它比的是**一致性**，而**基准库本身就是错的** —— 错得很一致 |

**产生原因**
「一致」是**结构性质**，「能执行」是**语义性质**。用前者代替后者。

**相关解决方案**
结论：「**和基准库一致 ≠ 能执行**」。
可执行性要靠**语义巡检**（`check-cap-release-head.sh` 5 项、
`check-tenant-registry.sh` 4 项、`check-rag-ops-role.sh` 13 项）。
这些巡检都做成**只读 + 退出码**（0 一致 / 1 违规 / 2 连不上），可挂 CI。

**来源**：`docs/RAG检索与端到端实测问题记录_20261028.md` §12.1
**状态**：✅ 已修（语义巡检已落地）

## TST-13 · 聚合计数方式错误 → 得到假数字「3651 条」

**问题描述**
中途用 `awk` 把 per-class 汇总行也加进去，得到过一个「**3651 条**」的假数字
（真实值是 9 个模块 **1713 条**）。

**产生原因**
surefire/failsafe 的输出里，per-class 行形如 `Tests run: N, Failures: F, ... -- in XxxTest`，
汇总行形如 `Tests run: N, Failures: F, Errors: E, Skipped: S`（**行尾无 `-- in`**）。
`awk` 匹配时没区分两种形态。

**相关解决方案**
聚合计数必须按 `^\[INFO\] Tests run: N, Failures: F, Errors: E, Skipped: S$`
（**行尾无 `-- in`**）这一种形态取。

**来源**：`docs/RAG检索与端到端实测问题记录_20261028.md` §11.4
**状态**：✅ 已修

## TST-14 · 夹具手工插数据把缺陷盖住

**问题描述**
两处典型：
1. `execution_snapshot` 的所有 IT 夹具都是**手工插**的 →
   「发布 → 运行」这条真实链路**从未被任何 IT 覆盖过**，
   于是「经 API 发布的 Agent 永远不可运行」这个缺陷**测试全绿**；
2. `RunCreationEndpointIT.creatingRunWritesCapabilitySnapshot` 若自带 `cap_agent_def` 夹具，
   真正的缺陷（回填缺失）它**一条都测不出来**。

**产生原因**
夹具比被测路径更「方便」—— 直接插库比走一遍发布链省事得多。

**相关解决方案**
1. `apiPublishedAgentCanCreateRun` 全程走**真实 HTTP 端点**
   （`POST /api/agents` → `POST /api/agents/{id}/versions` → `POST /api/runs`），
   **不手工插快照** —— 手工插就等于把缺陷盖住；
2. 快照用例**刻意不带夹具**，改用**真实业务 Agent**；
3. **红→绿已验证**：临时把 PLATFORM 指针移回空发布头 → 测试转红。

**来源**：`docs/E2E实测缺陷修复与复验_20261023.md` §3.3、`git log 312818e`
**状态**：✅ 已修

## TST-18 · 本仓库存在并行会话的未提交改动 → 全量构建不可复现

**问题描述**
隔离 worktree 的原因：本仓库存在**并行会话的未提交改动**
（`platform/agent-ports` 的 `statistics` 新模块当时处于编译错误状态）。
为不触碰他人未提交的代码，验证在 `git worktree add --detach <path> HEAD` +
**仅叠加本轮改动**的工作区中进行。

**产生原因**
多人/多会话共用一个工作区，未提交改动会**污染全量构建**。

**相关解决方案**
隔离 worktree 验证：`git worktree add --detach <path> HEAD` + 仅叠加本轮改动，
证明「**本轮改动相对 HEAD 自洽**」。

**来源**：`docs/E2E实测缺陷修复与复验_20261023.md` §6.1
**状态**：✅ 已修（方法）

## TST-20 · mock 字符串帧测试全绿，却从未覆盖框架真实序列化

**问题描述**
`ConsoleChatControllerTest` 用 `RecordingEmitter` 捕获 `send(String)` 并断言
`"event: delta\ndata: …"`，前端 `aiChatApi.test.ts` 也用 mock fetch 喂同样格式的手写帧。
两侧单测全绿（后端 2893 例 / 前端 543 例），但真实 HTTP 字节是
`data:event: delta` —— 缺陷被夹具**完整盖住**，直到看真实 DevTools 才暴露。

**产生原因**
夹具绕过了 `SseEmitter` 的序列化路径：测试断言的是「自己拼的字符串」，
而不是「框架写出的字节」。这是 M4「夹具本身是错的」的又一实例，
也再次说明 mock 越贴近实现细节、越容易和实现对着一起错。

**相关解决方案**
1. 后端替身改捕获 `SseEventBuilder`（`name` / `data` 分字段），
   并加一条「禁止 `send(String)` 双重包裹」的反向守卫；
2. 前端补「Spring 原生无空格帧 `event:delta`」与「流不 close 也靠 done 帧收口」两例
   （后者若用旧实现会直接挂到超时，有判别力）；
3. 补**真实重启后的字节级 E2E**：curl 看原始字节、Node `fetch` 看浏览器视角流收尾，
   帧统计 + 双重包裹计数 + 后端异常计数一起断言；
4. 结论纪律：涉及序列化 / 协议帧的改动，单测之外必须留一次真实链路取证。

**来源**：`git log eac390d`、[`记录-2026-11-07_AI直接对话链路.md`](记录-2026-11-07_AI直接对话链路.md) §六
**状态**：✅ 已修
