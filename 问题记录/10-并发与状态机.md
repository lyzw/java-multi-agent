# 10 · 并发与状态机类

> **判据**：根因是**并发窗口 / 状态流转未强制 / 超时 / 限流 / 停机顺序**。
> 典型形态：状态机方法写好了但没人调、裸 SQL 绕过状态机、租约与状态混为一谈。

---

## CON-01 · 状态机在生产代码**零调用**，真实迁移靠裸 SQL

**问题描述**
`RunState.requireTransitionTo` 在生产代码**零调用**，
真实迁移靠 **5+ 处裸 SQL `SET state=?`**（`JdbcRunClaimRepository.java:164-177` 等）。
合法流转靠 SQL 的 WHERE 条件**偶然挡住** → **非法流转没有统一守卫**。

**产生原因**
状态机被写成了**领域类里的一个方法**，而迁移逻辑实际在**持久化层的 SQL 里**。
两处各说各话，SQL 是实际生效的那一套。

**相关解决方案**
1. 新增 **V34 完整迁移表触发器**（在 DB 层统一守卫）+ Java 侧 fail-fast；
2. `tenant.status` 改枚举 + 转移表（见 CON-02）；
3. 下线 `PUT status` 直改通道。

**来源**：`docs/系统优化建议-全量评审.md` §3.3 / §6.1
**状态**：✅ 已修（V34 触发器 + Java fail-fast）

## CON-02 · `tenant.status` 是裸 `String`，无枚举无转移表

**问题描述**
`TenantRegistry.java:38` 的 `tenant.status` 是**裸 `String`**，
无枚举、无转移表，直接 `SET status=?`（`JdbcPlatformTenantRepository.java:184/206`）。

**产生原因**
状态用字符串存 → 「什么是合法状态」「什么能迁移到什么」都失去编译期与运行期约束。

**相关解决方案**
改枚举 + 转移表（与 CON-01 的 V34 触发器配套）。

**来源**：`docs/系统优化建议-全量评审.md` §6.1
**状态**：✅ 已修

## CON-03 · 预算校验与 Run 写入之间存在竞态窗口

**问题描述**
`RunCreationService` 中预算校验与 Run 写入分离 → 并发下可超支。

**产生原因**
「先查余额，再写记录」不是原子的。两个并发 Run 都能通过校验。

**相关解决方案**
在 `RunCreationPort.insertRunAtomically()` **内部**增加预算条件更新
（把「校验 + 扣减」变成一条原子语句），而不是在应用层分两步做。

**来源**：`审查文档/审查-2026-10-30.md` 问题 11
**状态**：✅ 已修（原子化写入口 + 代码注释记录遗留口径）

## CON-04 · `authzVersion` 校验存在竞态窗口 ✅/

**问题描述**
`authzVersion` 在 `TenantContext` 创建后**不再更新**，
请求处理中途的撤销存在约 **10–100ms** 的窗口。

**产生原因**
快照式读取授权版本 + 请求处理是长事务。
「我进来的时候有权限」不等于「我做完的时候还有权限」。

**相关解决方案**
高风险操作在 `DelegationGuard` 中**每次重新读取权威版本**。
`ExecutionAdmissionChecker` 已在外部副作用前重读权威 `authzVersion` 并重算闭包指纹
（TOCTOU 线性化边界）。

**来源**：`审查文档/审查-2026-10-30.md` 问题 8
**状态**：✅（准入检查已重读）/ 🟡（内存实现迁 DB 未做，见 SEC-21）

## CON-05 · `releaseLease` 只清租约不改状态 → 热循环

**问题描述**
`JdbcRunClaimRepository.releaseLease` 只清 `lease_owner` / `lease_expires_at`，**不改 `state`**；
而 claim 查询会把 `state='RUNNING' AND lease_expires_at IS NULL` 重新领取
→ 「释放租约」等于「回到队列」，且会造成**热循环**。

**产生原因**
「释放租约」（我还没做完）与「回到队列」（任务重新排队）在数据层被写成了同一件事。
而 Run 的状态机里**没有「待领取」这个态**来区分它们。

**相关解决方案**
HITL 改造引入 `RunState.WAITING_APPROVAL` + PARK/RESUME 检查点，
把「挂起」与「释放租约」在状态机上分开。

**来源**：`审查文档/AI全流程修复报告_2026-10-31.md` §4 第 4 条
**状态**：✅ 已修

## CON-06 · 崩溃恢复扫描器的**降级漏网** —— 「恢复链路已死」无处告警

**问题描述**
`RunRecoverySweeper` 的租户枚举调用原本**裸奔在 try/catch 之外** ——
异常一路抛到 Spring 的调度线程包装器（表现为「Unexpected error occurred in scheduled task」），
而本类的健康状态（`unhealthyReason`）**从未被置位**：
「恢复链路已死」这件事**没有落到任何可告警的地方**，健康检查端点照样报 healthy。

**产生原因**
「记录错误」与「让健康检查知道」是两件事。
异常被 Spring 的调度包装器兜住了 → 程序不崩 → 健康位永远绿。

**相关解决方案**
1. 降级路径**必须置位健康状态**（`unhealthyReason`），让健康检查端点能报出来；
2. 权限缺口一并修（见 [DBP-02](03-数据库权限与RLS.md)）；
3. 配套：`RunRecoverySweeper` 在 `PlatformTenantPort` 不可用时**不能只 WARN 静默关闭崩溃恢复**。

**影响**
worker 崩溃后其持有的 RUNNING 租约过期却无人接管 → **Run 永久卡死**；
而系统表面完全正常（API 正常、无告警）。

**来源**：`git log b31963f`（2026-11-01）
**状态**：✅ 已修

## CON-07 · 停机竞态：守护线程命中已关闭连接池

**问题描述**
停机时 `RetentionJob` / `OutboxRelay` / `PgQueueListener` 的守护线程正在执行 DB 操作，
而 `DataSource` 已关闭 → `HikariDataSource has been closed`。

**产生原因**
停机顺序：`stop()` 只是「设置停止标志」，**没有等待在途轮次退出**；
连接池的关闭与守护线程的退出是**两条独立的生命周期**。

**相关解决方案**
1. `stop()` 增加 `join(30s)`，等待在途轮次**干净退出**；
2. `RetentionPurgeService.beginShutdown()` + `shuttingDown` 标志：
   停机窗口内的清理/消费异常由 **ERROR 降级为 DEBUG**，
   避免误判为真实合规失败污染告警；
3. 回归测试 `RetentionJobTest#J-4a` / `OutboxRelayTest#R-7a`
   （模拟在途 DB 操作须**保留中断状态** —— JDBC 不可被 interrupt 打断）。

**来源**：`git log 86c267b`（2026-11-01）
**状态**：✅ 已修

## CON-08 · 超时非抢占 + 未传 `timeoutMs` 则**完全跳过**超时检查

**问题描述**
`RunExecutionLoop.java:359-368`：
- 超时检查只在**每轮迭代开头**，单次长调用（模型/工具）不会被中断；
- `if (task.deadlineAt() != null …)` 表示**未传 timeoutMs 则完全跳过超时检查**，
  仅依赖 `maxSteps` + 租约续期。

**产生原因**
把「超时」实现为「循环边界检查」而不是「每次阻塞调用都带 deadline」。
两个缺口叠加：不传超时 = 无超时；单步卡住 = 越过根截止。

**相关解决方案**
1. 单步抢占式超时：把每次模型/工具调用包进 `Future.get(剩余时间)`，
   解决「单次卡 10 分钟越过根 deadline」；
2. 创建路径**强制** timeoutMs（不给「无超时」这个选项）；
3. Worker 侧保持**唯一**重试实现（不引入 Spring `@Retryable` 防双重重试）。

**来源**：`审查文档/护栏设计综合评估文档1.md` P2-1
**状态**：🟡 部分已修（抢占式超时已落地；timeoutMs 强制待确认）

## CON-09 · `JdbcRateLimiter` 全局单一限额，无桶级覆盖

**问题描述**
限流只有一个全局桶：
- 治理桶与学生桶**互相蚕食**；
- 按**租户**限流 → 多个运维互相限流。

**产生原因**
限流器的维度设计是「单桶」，而业务需要「多桶，各自独立配额」。

**相关解决方案**
1. 限流改为**滑动窗口**（固定窗口在边界有突发）；
2. 支持桶级覆盖（`rate_limit_bucket` 表已存在）；
3. 执行票证按**目标租户**分桶（桶键是**被扮演的租户**而不是平台用户 ——
   防的是「单个租户身份被刷」）；限流器不可用时 **429**（fail-closed，不放行）。

**来源**：`docs/开发进度总览.md` §3.1 第 4 条、`审查文档/护栏设计综合评估文档1.md` P3-1
**状态**：✅ 已修

## CON-11 · `PlatformTenantService.transition()` 缺少退避建议

**问题描述**
状态迁移因 CAS 失败（并发竞争）而报错时，错误消息里**没有「建议等待后重试」**。
用户/调用方看到的是一个不可行动的错误。

**产生原因**
把「并发冲突」当成「非法操作」来报（与 [GOV-10](08-治理与发布流程.md) 同源）。

**相关解决方案**
在错误消息中增加「建议等待 1 秒后重试」等退避建议。

**来源**：`审查文档/审查-2026-10-30.md` 问题 13
**状态**：✅ 已修

> **本类统一教训**：**并发缺陷的共同形态是「一个动作被拆成了两半」** ——
> 校验与写入分离、租约与状态分离、设置停止标志与等待退出分离、
> 异常记录与健康置位分离。
> 判据：**这两个「半」之间有没有一个原子点把它们绑在一起。**
