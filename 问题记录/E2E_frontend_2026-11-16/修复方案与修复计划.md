## 1. P0-1｜数学公式零渲染（报告问题 1）

### 根因
- `frontend/src/shared/ModelText.tsx:23`：`const INLINE_TOKEN = /(\*\*[^*\n]+\*\*|`[^`\n]+`)/g` —— 只有两级行内语法。
- `frontend/src/shared/ModelText.tsx:10-18` 注释明确「刻意不支持标题、链接、表格、图片」，**未提及数学**，说明是能力盲区而非有意决策。
- `frontend/package.json:17-21` 依赖仅 `react`/`react-dom`/`react-router-dom`；**无 katex / react-markdown / remark-math / rehype-katex**（`admin-console/package.json:19-26` 已有全套）。
- 调用点：`RunResultPage.tsx:258`（经 ModelText）、`AgentChatPage.tsx:265-269`（**完全裸显示**，`white-space:pre-wrap`）。
- `\[`/`\]` 单独占行来自**模型原始输出**，非前端切分（已复核 `RunResultPage`/`AgentChatPage` 均无 splitLines）。

### 修复方案
**方案 A（推荐）：迁移 admin-console 已验证的渲染栈到 frontend**
1. `frontend/package.json` 新增依赖，版本对齐 admin-console：
   `katex ^0.16.47`、`react-markdown ^10.1.0`、`remark-math ^6.0.0`、`rehype-katex ^7.0.1`、`remark-gfm ^4.0.1`。
2. 迁移 `admin-console/src/features/aiChat/markdownText.ts`（289 行）到 `frontend/src/shared/markdownText.ts`：
   - `normalizeMathDelimiters`（:227）—— 把单独占行的 `\[`/`\]` 归一化为 `$$…$$`
   - `normalizeBareLatex`（:271）—— 处理裸 LaTeX
   - `closeUnclosedFence`（:78）/ `maskCodeBlocks`（:99）—— 代码区遮罩，避免公式定界符被代码块内容干扰
   - `prepareAnswerText`（:283）—— 流式场景的预处理入口
3. 新建 `frontend/src/shared/MathText.tsx`：封装 `react-markdown` + `remark-math` + `rehype-katex`，**懒加载**（`React.lazy` + `Suspense`），保证首屏不因 KaTeX CSS/JS 变慢。
4. 替换三处渲染点：
   - `RunResultPage.tsx:258` `<ModelText text={explanation} />` → `<MathText text={explanation} />`
   - `AgentChatPage.tsx:265-269` 裸 `{message.content}` → `<MathText text={message.content} />`
   - `RunResultPage.tsx:293-296` `steps[].output` → `<MathText>`（顺带修一个遗漏：步骤输出当前完全不过 ModelText）
5. **保留 `ModelText` 不删**：它有 5 条契约测试（`frontend/tests/modelText.test.tsx:42-49` 锁定「HTML 转义为字面量」的安全契约）。新组件必须继承该安全契约。
6. 安全约束（必须写进实现）：
   - **禁止 `dangerouslySetInnerHTML`**（ModelText 现有约定）
   - `rehype-katex` 默认不执行 HTML；如需 `rehype-raw` 须单独评估，**本次不引入**
   - KaTeX 抛错时降级为显示原始文本，不得整页崩溃

**方案 B（兜底，不单独实施）：模型侧约束输出纯文本**
在 agent instructions 里加「不要使用 LaTeX 定界符」。**不推荐单独使用**——模型不遵守时体验依旧崩，且牺牲公式表达力。

### 附加修复：模型输出格式契约（与方案 A 配套）
- 在 `deploy/sql/platform/02_platform_seed.sql:297` 对应 agent 的 instructions 增加格式约束：
  - 公式统一用 `\(...\)` 行内 / `\[...\]` 块级，**花括号必须完整**（修掉实测到的 `\fracbax` 这类缺括号输出）
  - 明确「不要输出原始 `\begin{aligned}` 之外的裸环境」
- ⚠️ 该 SQL 改动需同步：01 终态 + 02 种子 + 活库 ALTER（沿用项目既有结构变更纪律）。

### 验收标准
| 层级 | 内容 |
|------|------|
| 单元 | `MathText` 对 `\[x=\frac{b}{2a}\]`、`\(x\)`、`$$x$$`、裸 LaTeX 渲染为 KaTeX DOM；HTML 输入仍被转义为字面量（继承 ModelText 契约） |
| 契约 | 新增「模型输出渲染契约」测试：给定含 `\[ \boxed{} \frac{}{} \]` 的样例，断言输出含 `.katex` 节点且**不含**裸 `\[` 文本 |

## 2. P0-2｜匿名编号契约不一致（报告问题 2）

### 根因（三方冲突，不是单点 bug）
| 层 | 期望格式 | 位置 |
|---|---------|------|
| 前端提示 | 「平台生成的匿名编号」，无格式说明 | `NewRunPage.tsx:338` |
| 前端扫描 | 任何 8–12 位数字 = 学号 → 拦截 | `frontend/src/features/compliance/scan.ts:60` |
| 后端工具 | **必须** `^stu_[a-z0-9]{16}$` | `RecordWeaknessTool.java:54`、`GetStudentProfileTool.java:34`、`MemoryEntry.STUDENT_ID` |

**关键连锁（⚠️ 经实跑后已修正，勿再按此旧表述理解）**：
`studentId` 不匹配 `^stu_[a-z0-9]{16}$` 会导致 `RecordWeaknessTool.validate()` 抛 `studentId 格式非法`、`RunExecutionLoop.studentIdOf()` 返回 null（跳过记忆召回）——**这是真实存在的次生阻塞**，但它**不是**「没写入薄弱点」的主因。

**实跑结论**：用 `stu_a1b2c3d4e5f6g7h8`（合法格式）创建 Run → **HTTP 201 + SUCCEEDED**，证明合规层放行无误；但 `tool_operation` **零工具调用** ⇒ 薄弱点仍未写入 ⇒ **主因在能力目录未纳管该工具（见第 5 章 P0-5），不是编号格式**。

⚠️ 因此本项修复的价值在于：**它是 P0-5 的必要前提**（工具入参必须合法才可能落库），而非 P0-5 的替代。

### 修复方案（**不做扫描豁免**）
豁免扫描是错的方向：`studentId` 会随 `renderInput` 进入发给供应商的 Prompt（`RunExecutionLoop.java:1976-1977`），放行后学生可把真实学号（8–12 位数字）当匿名编号填入，**真实 PII 会出境**，直接违反零保留意图（`DataClassification.java:23-29`）。

**正确修法：统一契约到 `stu_` 格式 + 前端引导与校验**

1. **契约收敛**：以 `^stu_[a-z0-9]{16}$` 为**唯一**合法格式（后端已有三处一致，无异议）。
2. **前端提供格式引导**（`NewRunPage.tsx`）：
   - hint 改为：`请填写平台生成的匿名编号（形如 stu_a1b2c3d4e5f6g7h8），不要填姓名`
   - 新增**客户端格式校验**（非合规扫描）：不匹配 `^stu_[a-z0-9]{16}$` 时，给出**精确提示**「匿名编号格式应为 stu_ 开头 + 16 位小写字母数字」，而不是含糊的合规拦截
   - `studentId` **仍留在 `textFields` 参与 scan**（`stu_` 格式天然不匹配学号正则，天然放行，无需豁免）
3. **编号来源改造（根治「学生不知道怎么填」）**：
   - 提供「生成一个匿名编号」按钮：前端本地生成 `stu_` + 16 位随机十六进制，**一键带入**
   - 理想方案：后端签发匿名编号（`POST /api/auth/anonymous-id` 或登录响应回带），保证跨会话稳定
   - ⚠️ 若后端签发，需评估是否与 `profile` 的反枚举设计冲突（`GetStudentProfileTool.java:82-85` 刻意「不存在返回空画像而非报错」）
4. **画像查询页同样收敛**：`App.tsx:68-73` 的 `ProfileLookup` 当前**完全不 scan**，任意字符串都能查——须加同一格式校验，否则成为绕过口。
5. **⚠️ 必须同步后端**：`CreateRunRequest.assertNoIdentifyingContent`（:224-273）会递归扫 `studentId` 的 value。`stu_` 格式不被 8–12 位数字正则命中 ⇒ **无需改后端**。这是选 `stu_` 格式的最大收益：**零后端改动、零合规风险**。
   - 仅需确认：`flatten` 检 key+value，`stu_xxx` 的 key 与 value 均不命中任何 `IdentifyingPattern` ⇒ 天然通过。

### 验收标准
| 层级 | 内容 |
|------|------|
| 单元 | `stu_a1b2c3d4e5f6g7h8` 通过 scan 与格式校验；`20261116001` 给「格式应为 stu_…」的精确提示；`S2026-4f8a2b` 同样给格式提示（**不再**误报「疑似学号」） |
| 集成 | 用合法 `stu_` 编号跑完一次辅导，断言：`record_weakness` 被调用成功、记忆召回发生、`profile` 可查到该编号的薄弱点 |
| 反向验证 | 把 `studentIdOf` 的格式正则改回不接受 `stu_` → 集成测试必须红（证明薄弱点写入依赖此契约） |
| 合规 | 断言 `20261116001` **仍被拒绝**（防止修复顺手放宽了学号防护） |

## 3. P0-3｜知识检索永远空（报告问题 3）

### 根因
**两条链路 scope 策略不同**，不是 RAG 后端缺陷：

| 链路 | edition 坐标 | scopeMode | 结果 |
|------|-------------|-----------|------|
| 独立检索页 | 前端硬编码 `数学/七年级/上册/人教版/2024`（`RagSearchPage.tsx:102-106`） | `''` → **STRICT**（`RagRetrievalController.java:200-206`） | STRICT 要求五轴全等，库中无此组合 → `afterVersion=0` |
| Agent 编排 | 中性占位 `未指定/全学段/全一册/未指定/未指定`（`HttpRagRetrievalGateway.java:154-161`） | **CROSS_EDITION**（:167，注释「避免占位坐标锁死 0 命中」） | `EditionScope.admits` 恒 true → 能召回 |

叠加因素：公共库 8891 块中 **2145 块正文是 `[图]` 占位符**（`LayoutPredicates.java:135` 的设计，非脏数据），稠密/词法两通道都无法从占位符取到语义。

### 修复方案
1. **【必须】空结果归因分级**（体验最大伤害点）
   - `RetrievalFunnel` 已提供 `candidates/afterVersion/afterRole/afterGate` 四段计数（`RetrievalOrchestrator.java:144-154`），**直接用它分流提示**：
     | funnel 形态 | 归因 | 给学生的文案 |
     |-----------|------|-------------|
     | `candidates=0` | 语料/准入层为空 | 「你所在的班级还没有上传对应教材内容」 |
     | `candidates>0, afterVersion=0` | 版本坐标不匹配 | 「当前版本范围内没有匹配内容，可切到『跨版本查找』」 |
     | `afterGate=0` | 相关性门禁拦下 | 「找到了相关段落但置信度不足，试试更贴近教材的问法」 |
   - 文案落点：`RagSearchPage.tsx:467-472`（Empty hint）、`useRagSearch.ts:181-187`（硬编码 disclaimer）
   - ⚠️ `RetrievalFunnel` 计数**不得事后重算**（`:145-147` 注释明确禁止）——前端只能消费后端已算好的值
2. **【必须】提供「跨版本查找」选项**
   - 前端 `scopeMode` 增加 `CROSS_EDITION` 档位（当前只有 STRICT / PREFERRED_WITH_FALLBACK）
   - ⚠️ `revisionCode` 必须非空（后端 `@NotBlank`，空串必 500）——跨版本时填 `'任意'` 或沿用占位值
   - 与 Agent 链路语义对齐：同一 query 两边结果应一致（当前差 3 条 vs 0 条）
3. **【必须】默认值对齐真实语料**
   - 默认年级 `七年级`（`RagSearchPage.tsx:103`）→ 改为库中实际存在的组合；或
   - 更稳的做法：**默认 `scopeMode='PREFERRED_WITH_FALLBACK'`**（回退同册），比 STRICT 宽容又不完全放开
   - ⚠️ 不可动：`topK` 1–50 边界（对齐后端 `@Min(1)@Max(50)`）、`revisionCode` 非空、检索/生成共用 scopeMode（防「检索锁版本、生成不锁」的串版本事故）
4. **【P1】`[图]` 占位块可检索性治理**
   - 摄取期给占位块打标（复用 `LayoutFacts` 的 `BlockType`，或新增 `retrievable=false` 列），检索侧过滤
   - ⚠️ 影响可召回语料规模，须与 P0-3 的 1–3 项**同批**评估、单独验收
   - ⚠️ 不可动：公式块回退读 `orig`（`DoclingResponseMapper.java:209-217`，有「不能退化成 `[图]`」断言）；空白块跳过逻辑（`IngestionPipeline.java:200-209`）
5. **【P1】OCR 乱码治理**
   - 实测召回片段含 `犘 叫作圆锥的顶点`、`两边同除以狓` —— OCR 质量差
   - 与「中文教材PDF切分方案调研.md」联动，非本次范围

## 6. P1-1｜用量恒 0 tokens（报告问题 6）★ 复核新发现

### 根因（已实测确认）
- `AgentChatOrchestrator.java:305` 正常发射 `AgentChatEvent.Usage(state.inputTokens(), state.outputTokens())`，帧本身没问题。
- `state.inputTokens += response.usage().inputTokens()`（`:760`）—— 取值来自供应商。
- **实测 MiniMax 流式响应 `"usage":null`**（我用真实 API 验证，每一帧都是 null）；**非流式响应 usage 完整**（`prompt_tokens:205, completion_tokens:20`）。
- 网关判空缺陷：`OpenAiCompatibleModelGateway.java:164` `if (!usage.isMissingNode())` —— JSON `"usage":null` 时 `isMissingNode()=false`（**节点存在但值为 null**），判定「有 usage」，但 `usage.path("prompt_tokens").asLong(0)` 取到 0。
- 已用独立 Java 探针验证：`isMissingNode=false, isNull=true, asLong=0`。

### 修复方案
1. **【必须】判空修正**（两处：`OpenAiCompatibleModelGateway.java:163-168` 流式分支、`:363-366` 非流式分支；`MiniMaxModelGateway.java:207-210`、`:572-575` 同样）
   ```java
   JsonNode usage = root.path("usage");
   if (usage.isObject()) {                    // ← 关键：判对象而非判「节点存在」
       promptTokens = usage.path("prompt_tokens").asLong(promptTokens);
       completionTokens = usage.path("completion_tokens").asLong(completionTokens);
   }
   ```
   ⛔ 不可用 `!usage.isMissingNode()`：那是本次缺陷本身
2. **【必须】本地估算兜底**（流式供应商不给 usage 是常态）
   - 流式收尾时按「已产出字符数 / 4 + 请求体估算」给出**近似值**
   - ⚠️ 必须在 UI 标注为「估算」，不能冒充精确值（铁律 #15：不伪装）
   - 或改用非流式补一次 usage 查询（成本高，不推荐）
3. **【P1】可选：MiniMax 是否支持流式 usage 开关**
   - 若供应商支持 `stream_options.include_usage`，则请求体带上即可精确获取 —— 需实测确认（本次实测未带该参数）

### 验收标准
| 层级 | 内容 |
|------|------|
| 单元 | 给定 `{"usage":null}` 的 JSON → `ModelUsage(0,0)` 而**非**误判为「有 usage」；给定 `{"usage":{"prompt_tokens":205}}` → 正确取 205 |
| 契约 | 真实 MiniMax 流式调用一次，断言 `usage` 帧 `inputTokens > 0`（或明确标注为估算） |
| 反向验证 | 把判空改回 `!usage.isMissingNode()` → 单元必须红 |

## 7. P1-2｜登录锁定无提示（报告问题 7）
