## 2. P0 处置明细

### 2.1 `S4502` CSRF 防护关闭 ×2（CRITICAL · 漏洞）— **未开启，改为显式豁免 + 论证**

- **位置**：`platform-bootstrap/.../bootstrap/config/SecurityConfiguration.java:172`（平台链 `@Order(0)`）、`:226`（租户链 `@Order(1)`）
- **核查结论**：两条链均为 `SessionCreationPolicy.STATELESS` + **Bearer JWT**（无 Cookie 会话、无 `JSESSIONID`），浏览器不会自动附带凭据 ⇒ CSRF 前提不成立。
- **为什么不能直接开启**：开启后 Spring Security 要求每个写请求携带 CSRF token，**非浏览器客户端与 SSE 长连接会全量 403**（SSE 的 ASYNC dispatch 更是本项目已知坑，见该文件 `:188` 注释）。
- **处置**：两处 `@Bean` 方法加 `@SuppressWarnings("java:S4502")` 并在注释中写明上述理由——**这是有据可查的架构决策，不是静默忽略**。
- ⚠️ **遗留风险声明**：CSRF 防护在本平台**仍为关闭态**。若未来引入 Cookie 会话 / 表单登录，必须同步开启 CSRF，否则即是真实漏洞。

### 2.2 `S3078` / `VO_VOLATILE_INCREMENT` volatile 非原子自增 ×3 + `AT_NONATOMIC_OPERATIONS_ON_SHARED_VARIABLE` ×2 — **真实并发缺陷，已修**

| 文件 | 原写法 | 现写法 |
|---|---|---|
| `agent-persistence/.../messaging/PgQueueListener.java` | `volatile long totalProcessed` / `totalDeadLettered`，`++` 自增 | `AtomicLong`，`addAndGet(...)` / `incrementAndGet()` |
| `agent-worker/.../worker/dispatch/OutboxRelay.java` | `volatile long totalPublished`，`+=` | `AtomicLong.addAndGet(published)` |
| `platform-bootstrap/.../bootstrap/worker/RunRecoverySweeper.java` | `volatile int portUnavailableStreak`，`++` | `AtomicInteger.incrementAndGet()` |

- **为什么是真缺陷**：`volatile` 只保证可见性，不保证复合操作原子性；并发下自增会**丢计数**（本项目 `PgQueueListener` 与 `OutboxRelay` 都是多线程入口）。
- **复扫证据**：SpotBugs `VO_VOLATILE_INCREMENT` 3→0、`AT_NONATOMIC_OPERATIONS_ON_SHARED_VARIABLE` 2→0，`MT_CORRECTNESS` 类别 **5→0**。

### 2.5 SpotBugs High `NP_NULL_ON_SOME_PATH_FROM_RETURN_VALUE`（`AgentChatOrchestrator.emitToolResults`）— **真实契约违例，已修**

- **根因**（由 SpotBugs XML 的 `LocalVariable`/`SOURCE_LINE_KNOWN_NULL` 定位）：`ModelResponse.ToolCallRequest.callId()` 的契约是 **`@Nullable`**（模型可能不返回工具调用 id），而 `AgentChatEvent.Tool.toolCallId` 是 **`@NonNull`**；`emitToolResults` 直接把 `call.callId()` 灌进去 ⇒ **null 流入非空契约**。
- **处置**：本类已有唯一归一入口 `withStableCallIds(...)`，它把缺失/空白 id 补为 `"call-" + index`，且**以该 id 作为 Map 的 key**。故把两处读取（`:783` 的 "call" 阶段事件、`:947` 的结果事件）从 `call.callId()` 改为**取 Map 的 key**（`entry.getKey()`）：
  - 值完全等价（`normalized.put(callId, …)` ⇒ key ≡ 归一后的 callId）；
  - 类型上恒非 null（`Map<String, …>` 的 key）⇒ 契约不再被违反；
  - 同时堵住了 `:783` 处同源的潜在隐患（SpotBugs 只报了其中一处）。
- **复扫证据**：`NP_NULL_ON_SOME_PATH_FROM_RETURN_VALUE` 241→239，**SpotBugs High 4→0**。
