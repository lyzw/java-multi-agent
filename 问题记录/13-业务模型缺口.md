# 13 · 业务模型缺口类

> **判据**：根因是**业务模型 / 数据语义尚未设计完成**，不是实现 bug。
>
> 本类的特殊之处：**代码「做对了」，但做的不是业务真正需要的事**。
> 因此不能靠「加个断言」「改个 if」解决 —— 需要产品口径先定。

---

## BIZ-01 · 多轮会话无持久化 —— 同一学生第二次提问时 Agent 对上次一无所知

**问题描述**
`docs/系统架构图.md:360-365` 的 ERD 画着 `AGENT_CONVERSATION` 与 `AGENT_MESSAGE`。
实测：**这两个名字在全仓 DDL 与 Java 中均不存在**（`grep -rn "agent_conversation|AGENT_MESSAGE"` → 0 命中）。
`agent_message_queue` 存在，但它是 **PG 队列**，不是对话表。

当前对话消息序列是 `RunExecutionLoop` 里的一个**局部 `ArrayList<ModelMessage>`**（`:347-348`），
**随 Run 结束即消失**。

**产生原因**
会话是「一次 Run 内部的上下文」，而业务上的会话是**跨 Run 的**。
两者被当成了同一件事。

**影响**
「个性化辅导」这一业务定位在多轮场景下**无法成立**。

**相关解决方案**
需要设计表结构 + 读写路径 + 与 Run 的关联模型（不是简单加两张表）。
文档口径先对齐（见 [DOC-02](11-文档与代码漂移.md#doc-02--系统架构图-erd-含-agent_conversation--agent_message两表不存在)）。

**来源**：`审查文档/AI全流程审查报告_2026-10-31.md` P1-2
**状态**：🟡 未动工（阶段级任务）

## BIZ-02 · 知识点体系缺失 —— `knowledge_point` 是 1–100 字自由文本

**问题描述**
`weakness_record.knowledge_point` 是 **1–100 字自由文本**，无字典、无层级、无教材版本；
真正的 `KnowledgePoint` 实体只在 `rag-core`，**平台侧不通**。
且与 `TutoringVocabulary` 的学科/年级词表**不共享** —— 「一次函数」与「函数」会被算成两个知识点。

**产生原因**
平台侧（业务数据）与 RAG 侧（知识点本体）各自设计了知识点概念，**没有对齐**。
自由文本是「先记下来，以后再治理」的典型临时形态。

**相关解决方案**
1. 先定知识点字典与教材映射（RAG-D10 的活）—— `kp_ids` 现在两册全是 `{}`；
2. 平台侧 `knowledge_point` 改为**引用**字典（而非自由文本）；
3. 与 RAG 侧 `KnowledgePoint` 实体统一。

**来源**：`审查文档/AI全流程审查报告_2026-10-31.md` P1-3、`docs/系统优化建议-全量评审.md` §6.4
**状态**：🟡 未动工（需产品口径）

## BIZ-03 · 归因结论非结构化 —— 仅 `error_type` 六值 + `confidence`

**问题描述**
`weakness_record` 只有 `error_type`（六值枚举）+ `confidence`，
且 SQL 注释自陈「不可靠不参与判定」→ **归因本质纯文本，不可评估 / 统计 / 回放**。

**产生原因**
「让模型先记下来」的阶段产物被当成了最终数据模型。

**相关解决方案**
结构化归因模型（错误类型体系 + 归因链 + 证据片段），
并定义「可评估」的判据（能被规则复算，而不是模型自评）。

**来源**：`docs/系统优化建议-全量评审.md` §6.4、`审查文档/AI全流程审查报告_2026-10-31.md` P1-3
**状态**：🟡 未动工

## BIZ-04 · 效果闭环缺失 —— 「学生是否进步」当前**无数据**

**问题描述**
- `weakness_record` **单向写入**，无 `resolved` / `mastered` / `next_review_at` / 复测机制
  → 没有「什么时候该再练这题」的机制；
- `agent_task_outcome` / `agent_eval_sample` 未落地；
- `AgentMetricCollector.java:129-131` 的效果类字段
  （`auto_checked` / `auto_verified` / `human_verdict` / `hallucination` / `instruction_followed`）
  **全部硬编码为 `null`**，注释写「待 P7-3 接入」；
- 反馈只落 `agent_trace_feedback`（`kind` 枚举，无自由文本），注释自陈「不能单独当真值」。

**产生原因**
度量体系被当成「采集模块」，但**没有定义「什么是真值」**，
所以采集出来的字段不能被当结论用。

**结论**
`docs/项目进度台账` 与 `P6_AI-Agent效果测试与执行效果度量` 描述的「效果度量体系」
**在代码里是空壳**。

**相关解决方案**
需要产品口径先定：**什么样的证据算「学生进步了」**。然后才是采集。
**这不是实现 bug，而是业务闭环尚未设计完成。**

**来源**：`docs/系统优化建议-全量评审.md` §6.4、`审查文档/AI全流程审查报告_2026-10-31.md` P1-3
**状态**：🟡 未动工

## BIZ-05 · 平台 ↔ RAG 通路**完全不可达**（零依赖边）

**问题描述**
三重独立验证：

| 检查 | 结果 |
|---|---|
| Maven 依赖 | `platform/**/pom.xml` 中 `artifactId>rag-*` → **0 命中** |
| Java 导入 | `platform/**` 中 `import cn.studykid.rag` → **0 命中**；反向亦 0 |
| 工具定义 | `search_knowledge_base` 全仓**只存在于文档**，无实现、无 `cap_tool_def` 行 |

**为什么现有 HTTP 工具机制也走不通**
`CapHttpToolConfig` 只有 method/url/timeoutMs，**没有 header 字段**；
`HttpToolExecutor.java:330-343` **写死请求头**。
而 RAG 侧 `RagRetrievalController.requireTenant()` 要求 `X-Tenant-Id`（否则 400），
`RagJwtAuthFilter` 要求 Bearer JWT（否则 401）。
→ **即使管理员手工种一条指向 RAG 的 `cap_tool_def`，调用也会在两个维度上失败。**

**产生原因**
RAG 与平台是**两个独立建设的子系统**，各自完整、彼此不通。
接入需要跨子系统的契约（认证、租户上下文、工具协议），没有人在做这一层。

**相关解决方案**
受 `rag/docs/RAG-D09_阶段门禁与主平台接入计划.md` 的 **M-1 → M-4 顺序硬约束**；
前置还包括 `CapHttpToolConfig` 补 header 支持。

**来源**：`审查文档/AI全流程审查报告_2026-10-31.md` P1-1
**状态**：🟡 未动工（A-008 硬阻断）

## BIZ-07 · `get_student_profile` 不回读 `weakness_record` → 归因与辅导两张皮

**问题描述**
`get_student_profile` 工具只读 `student_profile`，**不读 `weakness_record`**
→ Agent 查不到学生「到底哪里弱」。

**产生原因**
两个工具被当成两个独立的数据视图，但业务上它们是**同一个学生的同一个画像**。

**相关解决方案**
1. `get_student_profile` 回读 `weakness_record`（依赖 BIZ-02 的知识点字典才能表达「哪里弱」）；
2. 或新增 `get_weaknesses` 工具，让模型主动调用。

**来源**：`审查文档/AI全流程审查报告_2026-10-31.md` P1-3
**状态**：🟡 未动工

> **本类统一教训**：**本类不能靠加断言或改 if 解决**。
> 这些问题的正确解法顺序是：
> ① **先定口径**（什么算「进步」、什么算「同一个知识点」）；
> ② 再改**数据模型**（表结构、字典、关联）；
> ③ 最后才是**代码**。
>
> 本项目已经吃过一次亏：
> `weakness_record` 里的 `error_type` 六值 + `confidence` 就是「先记下来，以后再治理」的产物 ——
> 后来它既不能评估也不能统计，**因为「真值」从未被定义过**。
>
> 对照一句话：**代码可以跑通，但跑通不等于业务成立。**
> 当前系统能「跑通 Agent 执行」，**但不能证明「辅导有效」**——
> 这正是 P7 文档里 BIZ-1~BIZ-5 标 P7-3 的原因。
