## 0. 执行摘要

本轮对 admin-console 做了 **30 个菜单页 + 6 个异常/深链入口 + 75 项首轮交互用例 + 26 项最终回归用例 + 93 个 API 契约/权限请求 + 数据库存储核验** 的端到端实测，
采集 **154 张截图**、30 份逐页网络日志、完整请求/响应 JSONL 与数据库快照。

- **最终裁定**（77 项：75 项首轮用例按回归结果覆盖 + 2 项新增回归用例）：**通过 76 / 失败 0 / 阻塞 1 / 不适用 0**；另有 5 类阻塞或不适用范围项单列；
- 最终回归批次 8：**26 项，通过 25 / 阻塞 1 / 失败 0**，唯一阻塞为 I-A04「新会话清空」（需真实模型对话，见 BLK-02）；
- 菜单导航：**30/30 页真实渲染成功**，其中 28 项由侧栏菜单点击直达，2 项首轮点击未生效后以地址栏直达完成；
- 页面级控制台错误：**0**；逐页 API 请求 **无 4xx/5xx**（身份域隔离与权限拒绝类请求在受控 API 矩阵中单列）；
- API 矩阵：6 角色 × 12 只读端点 = 72 次请求，登录 6/6 成功、身份域隔离 4/4 按设计 401、越权写 3/3 按设计 403；
- **写路径真实闭环**：新建用户 `POST /platform/v1/users` → 201 + DB 落库、重复名 → 409 + 明确提示、停用经 Popconfirm 确认 → DB 状态 DISABLED；取消/关闭弹窗与空表单均确认无写入；
- 发现 **6 个缺陷/观察项**（测试当时点：P2 × 2、P3 × 4）、**9 项文档与实现差异**；其中 DEF-01/02/03/04/06 已于同日修复并回归通过（§10），DEF-05 仍为治理待办；
- **发布结论（v1.1）：仍不满足「无条件发布」，但 P2 阻断项已闭环**。剩余阻断来自 DOC-08 禁区数据边界待安全评审、§6 五类跨租户写路径缺端到端证据、以及文档与实现不同步；建议「有条件放行（只读/展示类 + 平台用户写链路）」，详见 §9.3。

> ⚠️ **判定纪律**：首轮自动化脚本出现多起「元素定位/弹窗动画残留/长弹窗离屏按钮/用例数据不合规」造成的连锁失败，全部经 **批次 8 最终回归**（每条用例整页重载 + 真实点击 + 网络/DB 证据）重跑，报告以最终裁定为准；工具偏差逐条列于 §7.4，**未把工具误操作记成产品缺陷，也未把脚本通过当成产品通过**。

## 5. 缺陷清单（含可复现步骤）

严重度口径：**P1** 阻断发布/安全边界待确认；**P2** 主要功能或权限口径受损；**P3** 轻微/体验/治理项。

### DEF-01　未认证 / 伪造令牌访问 /api/platform/v1/auth/me 返回 500 而非 401（P2）

- **复现步骤**：1) 不带 Authorization 执行 GET /api/platform/v1/auth/me；2) 用伪造 Bearer 令牌重复一次
- **测试数据**：无令牌 / Bearer forged.token.e2e
- **预期结果**：401 UNAUTHENTICATED（与登录端点、其它平台链端点一致）
- **实际结果**：两次均 500 {"code":"INTERNAL_ERROR","message":"服务暂时不可用"}，X-Trace-Id 见 http/api_probe.jsonl A05/A06；curl 复现 09:37:52 trace=3dd442126d1049558647f8f67b4b76f5
- **影响范围**：前端 client.ts 只对 401 做「清会话 + 跳登录」；500 走通用错误分支，可能出现「无有效会话却停留在受保护页」的状态不一致；同时把认证失败伪装成服务端故障，干扰排障与告警
- **证据**：`http/api_probe.jsonl（A05/A06）、logs/api_probe_run.log；修复后：http/api_probe_after_fix.jsonl、logs/regression_after_fix.jsonl（FIX-01/02/10）`
- **状态**：**已修复并回归通过**（平台链 permitAll 精确到 login/jwks + 绑定异常 401 归一化，见 §10.1）

### DEF-02　前端审计角色门禁漏配 PLATFORM_SECURITY_ADMIN（v1.0 证据误判更正）（P3）

- **复现步骤**：1) 查源码 PlatformRolePermissionMatrix.ROLE_PERMISSIONS 与 DB platform_role_permission；2) 用 plat-security 登录取令牌，GET /api/platform/v1/audit-events；3) 浏览器干净会话打开 /admin/audit 深链与侧栏「平台审计」；4) 对照另外 5 个角色
- **测试数据**：账号 plat-security（roles=["PLATFORM_SECURITY_ADMIN"]）
- **预期结果**：源码冻结矩阵、DB 播种、运行时授权、前端 AUDIT_SCOPE / navConfig 四者口径一致
- **实际结果**：**更正后的实测**：后端对该角色为 **200** —— 源码冻结矩阵与 DB 播种均授予 `platform.audit.read`，PlatformAuditController.require(AUDIT_READ) 与 PlatformAuthorizationServiceImpl 均放行；API 矩阵中 403 只属于 plat-lifecycle / plat-resource / plat-support。真正的差异是前端：`AUDIT_SCOPE` 与 `navConfig` 审计节点只放行 [SUPER_ADMIN, AUDITOR]，使 SECURITY_ADMIN 无审计菜单、深链 /audit 被 RequireRole 拦成 403（浏览器矩阵稳定复现）。⚠️ v1.0 把其它角色的 403 误归到 SECURITY_ADMIN，并据此写成「运行时授权分叉/需改矩阵与播种」，属证据读取错误，本版更正；修复方向因此从「改后端矩阵」变为「前端补角色」
- **影响范围**：不越权（后端从未拒绝合法角色），但安全管理员在控制台里看不见、进不去审计页，与其风险处置职责冲突；同时错误结论会误导合规举证与权限评审。前端导航与后端矩阵保持一致即可消除
- **证据**：`http/api_probe.jsonl（RBAC:plat-security:平台审计=200）、http/api_probe_after_fix.jsonl、evidence/role_matrix_browser.json（修复前）、evidence/role_matrix_after_fix.json（修复后）、logs/regression_after_fix.jsonl（FIX-05-security）、admin-console/src/router.tsx、src/layout/navConfig.tsx`
- **状态**：**已修复并回归通过**（前端 AUDIT_SCOPE / navConfig 补 SECURITY_ADMIN，见 §10.2）
