# 02 · 数据一致性与写链类

> **判据**：根因是**数据写不进去 / 写歪 / 两份数据打架 / 写链某层断掉**。
> 典型形态：写入链某一层 catch 吞掉异常、种子绕过正规写入路径造畸形数据、两张表靠约定保持恒等。

## DAT-01 · `execution_capability_snapshot` 全库 0 行 —— 写入链五层断链

**问题描述**
2026-10-31 实测：`execution_capability_snapshot` **全库 0 行**。
后果不是「少一份审计数据」，而是**依赖它的读方一律 fail-closed** ——
`RootAgentModelConfigProvider` 靠它确定根 Agent 身份，读不到就把每个 Run 判成 `CONFIG_UNAVAILABLE`：
Run 建得出来、跑不起来，现场看着像「配置缺失」，真因却是**快照根本没被写**。

**产生原因**
不是单点 bug，是**五层叠加的断链**（每层都独立阻断写入，且有先后）：

| # | 断点 | 事实 |
|---|---|---|
| ① | `cap_agent_def` 无行 → `resolver.resolve()` 抛 `RESOURCE_UNKNOWN` | 1130 个已发布 Agent 中**只有 1 个**有 CAP 版本行 |
| ② | `cap_authz_version` 无该主体行 → `authzVersions.require()` 抛 `AUTHZ_UNAVAILABLE` | 真实主体 **0 行**；唯一那行 `principal_id='worker'`，而 worker 不是真实主体 |
| ③ | 平台对象未登记进 PLATFORM 发布头 → `PublishedVersionPort` 解析不出版本 | 当前生效版本**只由发布指针决定**，不读 `cap_*_def.published_at`；种子绕过了发布流程 —— 只写版本行、没写发布头、没移指针 |
| ④ | `execution_capability_snapshot` 对 run 有复合外键 | 必须先有 run 行 |
| ⑤ | 双写方 fail-soft | 三层失败都被 `catch (RuntimeException)` 吞掉并记 WARN，**「链路断了」不体现为失败**，只体现为「表一直是空的」 |

**相关解决方案**
- 新增 `12_cap_authz_version_backfill.sql`：按 `principal.authz_version` 初始化
  （**不写 1** —— 那会让「principal 已撤权但 cap_authz_version 仍是 1」的窗口出现）；
- 新增 `13_cap_agent_def_backfill.sql`：从 `agent_version.definition` 提取回填
  （**跳过 `it-*` 夹具** —— 它们随时会被 IT 清理删掉，给它们建行 = 建孤儿）；
- 新增 `14_cap_platform_release_backfill.sql`：补 PLATFORM 发布头并 CAS 移指针
  （`requester`/`approver` 必须不同 —— `cap_config_release_two_person_ck` 不允许自批自过）；
- 三层 fail-soft 保留但**加了可观测**：缺授权版本行 / 缺 agent_def 行 → 不写且不抛，
  并由 `CapabilitySnapshotWriteChainIT`（3 例）钉住该契约。

**实跑验证**（真实 API 建 Run）：
```
快照真的写出：agent_version=1 / config_version=1033（来自发布指针）/ authz_version=1
              / effective_closure 1649 字节
Run 由 QUEUED → RUNNING，并抵达真实模型调用
（MODEL_CALL_BEFORE modelId=minimax:MiniMax-M2.5 tools=3）
```
修复前它在 `CONFIG_UNAVAILABLE` 就夭折、根本走不到模型这一步。

**来源**：`git log 312818e`（2026-11-01）
**状态**：✅ 已修

## DAT-02 · CAP 目录 id ≠ 运行时 handler 名 —— 两套命名宇宙

**问题描述**
`02_platform_seed.sql` 的 seed 用 `tool-profile-read` / `tool-profile-update`，

这是「装载能力目录」这一步的前置必修项。

## DAT-03 · `cap_authz_version` 表无任何生产写入方 → 一开 CAP 授权即 100% fail-closed

**问题描述**
`cap_authz_version` 是 CAP 授权链的准入比对依据。`JdbcAuthzVersionRepository` 在**无行时抛
`AuthzUnavailableException`**，而该表**没有生产写入方**（`initialize()` 零调用）。
即便现在把 CAP 开关打开，也会 **100% fail-closed 拒绝所有工具调用**。

**产生原因**
表建了、读取路径建了，**写入路径没建**。且 `deploy/` 下只有 DDL 没有 INSERT。

**相关解决方案**
按 `principal.authz_version` 回填（见 DAT-01 的 `12_cap_authz_version_backfill.sql`）。
注意：**不能写 1** —— 那会让「principal 已撤权但 cap_authz_version 仍是 1」的窗口出现，
正确做法是直接用 `principal` 表现有的 `authz_version`。

**来源**：`审查文档/AI全流程审查报告_2026-10-31.md` P3 第 1 条
**状态**：✅ 已修（回填脚本）

## DAT-04 · 种子只灌定义表，从不产出发布头/指针 → 「有目录、不能跑」

**问题描述**
`lifecycle_state='PUBLISHED'` 与「运行期可用」**是两件事**。运行期解析精确版本只有一个口径：
```
cap_config_pointer → cap_config_release.object_versions → id@精确版本
```
（`JdbcPublishedVersionPort.resolveFromPointer`），**全链路没有任何一条 SQL 读 `lifecycle_state`**。
`02_platform_seed.sql` 只灌定义表 → 复放出来的库「有目录、不能跑」。

**产生原因**
种子脚本沿用了「状态字段即生效」的直觉，但运行期早就不这么读了。

**相关解决方案**
不写死对象清单，**从定义表推导**发布头 —— 新增 `deploy/sql/platform/patch_cap_release_head.sql`
（6 步，幂等），并把**同一份推导**内联为 `02_platform_seed.sql` 末尾的「附录 · 非 pg_dump 内容」，
让空库复放自带发布头：

| 步 | 动作 | 关键点 |
|---|---|---|
| 0 | `setval('cap_config_publish_seq', max(config_publish_seq))` | 见 DAT-06 |
| 1 | 插入 PLATFORM 发布头：各类型 `max(version) WHERE lifecycle_state='PUBLISHED'` | `WHERE NOT EXISTS(指针当前头的指纹 = 本次指纹)` → 幂等 |
| 2 | PLATFORM 指针缺失则创建 | `deploy/sql` 下**没有任何脚本**写过 `cap_config_pointer`；开发库那行是应用首次发布时 `JdbcConfigPointerRepository` 的 `ON CONFLICT DO NOTHING` 惰性建的。少了这步，干净库会「头写成功、指针 0 行」→ 照旧 `RESOURCE_UNKNOWN` |
| 3 | PLATFORM 指针 CAS 到内容等于当前目录的头 | `IS DISTINCT FROM`，内容没变写 0 行 |
| 4 | 每个有已发布 Agent 的租户一份 TENANT 头 | `{"type":"agent","id":<uuid>,"version":max}` |
| 5 | TENANT 指针缺失则插入 + 已存在则 CAS | 同 2/3 |

> ⚠️ **指纹必须在 SQL 里逐字拼字符串**：`aggregate_fingerprint = 'cfg_agg_v1:' + SHA-256(ConfigObjectVersionCodec.toJson(refs))`，
> 而 `toJson` 是**紧凑、键序固定 `type,id,version`、按 `(type,id,version)` 排序**的。
> `jsonb` 会重排键、`json` 会加空格，两者算出的摘要**都不是**产品 codec 那个。
> 代价：id 只能是需要 JSON 转义的简单串以外的东西，脚本用 `^[A-Za-z0-9_.:@-]+$` 把越界 id **挡在聚合之外**
> （宁可少一个对象，也不拼出「看起来对、摘要错」的头）。

**来源**：`docs/RAG检索与端到端实测问题记录_20261028.md` §12
**状态**：✅ 已根治（2026-10-29 授权后执行，开发库 COMMITTED）

## DAT-07 · `public.tenant` 与 `platform.tenant` 两表镜像漂移 → 票证 404

**问题描述**
`POST /api/platform/v1/tenants/2187ffed-…/execution-ticket` → **404**
`{"code":"NOT_FOUND","message":"资源不存在"}`。
实测当时这两张表：

| 表 | 行 |
|---|---|
| `platform.tenant` | **只有** `5222d5e7… \| e2e-console \| PENDING_SETUP \| plan=null` |
| `public.tenant` | `2187ffed… \| t-a \| 某某教育科技 \| ACTIVE`、`5222d5e7… \| e2e-console \| PENDING_SETUP` |

于是两个租户都取不到票证，且各卡在不同闸门：
`2187ffed…`（有 Agent、有成员）→ 平台侧无登记 → `TENANT_NOT_FOUND`；
`5222d5e7…`（平台侧登记了）→ `PENDING_SETUP` → `TENANT_NOT_ACTIVE`。

**产生原因**
**种子绕过 `provisionTenant`，用裸 `INSERT INTO public.tenant` 造租户。**
`provisionTenant` 在**同一事务**里写三处：`platform.tenant` + `INSERT INTO tenant`（业务行）+
`platform.tenant_quota(50/10)`；`transitionLifecycle` 也 CAS 更新权威行后镜像 `UPDATE tenant SET status`。
所以**走正规开通的租户两张表恒等** —— 破口只有种子这一处：
`public.tenant` 里那行 `2187ffed…` 来自 `deploy/sql/platform/02_platform_seed.sql:231` 的裸 INSERT，
**镜像反过来缺了权威**，于是 worker 认它、票证闸门不认它。

> **记录一次「误判后收回」**（比产品缺陷更值得留档）：
> 一度判成「权威源分裂、两处读两张表」。读完全文后**收回** —— `public.tenant.status` 是
> `platform.tenant` 的**同事务镜像**，`provisionTenant:150` / `transitionLifecycle:209`。
> 当时只看了 `provisionTenant` 里 `INSERT INTO platform.tenant` 那一段（128-130 行）就下了结论，
> 而 `INSERT INTO tenant` 在 152 行，中间隔着 20 行 `PreparedStatement` 样板。
> **grep `UPDATE public.tenant` 也漏了** —— SQL 写的是 `UPDATE tenant SET status`（schema 由 search_path 决定），
> 不带 `public.` 前缀，按限定名搜必然搜不到。

**相关解决方案**
| | 动作 | 状态 |
|---|---|---|
| b | **seed 根治**：`02_platform_seed.sql` 补 `platform.tenant` + `tenant_quota` 两段（`plan` 留 NULL、顺序在 `public.tenant` 之前以满足 FK，形状与 `provisionTenant` 一致） | ✅ dry-run 实测「剩余漂移行数」1 → 0 |
| c | **巡检守卫**：`scripts/check-tenant-registry.sh` + `scripts/tools/CheckTenantRegistry.java`（只读、`setReadOnly` + `ROLLBACK`，退出码 0 一致 / 1 漂移 / 2 连不上） | ✅ 对本机库实测准确抓到当前漂移并退出 1 |
| a | **补登记当前这行**：`patch_platform_tenant_registration.sql`（幂等、NOT EXISTS、只补已登记行的缺半，不覆盖已有 `lifecycle_state`） | ✅ 已提交执行（2026-10-29，用户确认后） |

**巡检的四条不变式**（前三条破坏即退出 1）：
① 业务侧有 → 平台侧必须有；② 平台侧有 → 业务侧必须有；
③ 三列状态相等 `public.status = platform.lifecycle_state = platform.status`
（**「停用租户」是否真生效，看的就是这一条**）；
④ 平台侧登记了却没配额行。
连接身份必须是库 owner：`public.tenant` 开了 RLS，用 `app_agent` 连只看得到自己一个租户，巡检结论会失真。

> **仍然没修的一条**：两张表之间**无外键、无触发器**，恒等只靠「大家都走 `provisionTenant`」的约定
> （`transitionLifecycle` 的镜像那一步还是 best-effort，业务行不存在时 `UPDATE` 影响 0 行、静默通过）。
> 加 FK 属于全库 DDL、还要先清历史脏行，本轮不动；巡检是当前能做到的最低成本兜底 ——
> 它不阻止人写裸 INSERT，但会让漂移**当天**被发现，而不是在下一次「404 到底谁的错」时被发现。

**来源**：`docs/RAG检索与端到端实测问题记录_20261028.md` §9
**状态**：✅ 夹具已根治 + 巡检已挂 + 补登记已提交；**FK 仍未加**

## DAT-09 · `releaseLease` 只清租约不改状态 → Run 回到队列造成热循环

**问题描述**
`JdbcRunClaimRepository.releaseLease` 只清 `lease_owner` / `lease_expires_at`，**不改 `state`**；
而 claim 查询会把 `state='RUNNING' AND lease_expires_at IS NULL` 重新领取
→ 「释放租约」等于「回到队列」，且会造成**热循环**。

**产生原因**
「释放租约」与「回到队列」在数据层被写成了同一件事，但它们的业务语义不同：
前者是「我没做完，还给别人」，后者是「任务重新排队」。

**相关解决方案**
这也是 P0-2「挂起后自动恢复」**不能简单复用租约机制**的原因之一。
G1/G2 HITL 改造中引入 `RunState.WAITING_APPROVAL` + PARK/RESUME 检查点，
把「挂起」与「释放租约」在状态机上分开。

**来源**：`审查文档/AI全流程修复报告_2026-10-31.md` §4 第 4 条
**状态**：✅ 已修（引入独立挂起状态）

## DAT-10 · `usage_record` / `budget_reservation` 外键缺口 → 模型调用预留行不会被悬挂扫描发现

**问题描述**
- `usage_record` **无 `operation_id` 外键、无 `reservation_id` 外键**；
  唯一索引是 `idx_usage_operation_once (tenant_id, operation_id) WHERE operation_id IS NOT NULL`；
- `budget_reservation.operation_id` 也无外键，且 `findOrphaned` 对 `tool_operation` 是 **INNER JOIN**
  → **非工具操作 id 的预留不会出现在悬挂扫描里**。

**产生原因**
预算预留原本只有工具调用一条来源，`findOrphaned` 就按 INNER JOIN 写了。
新增「模型调用」这一类预留后，这条 INNER JOIN 的隐含前提（「operation_id 一定是 tool_operation.id」）被打破。

**相关解决方案**
模型调用侧的预留行（其 `operation_id` 是模型调用标识，不是 `tool_operation`）需要**单独口径**，
否则模型侧的钱泄漏无人回收。本轮 P0-3b 已把模型 token 与真实成本入账，
并同步补齐该扫描口径。

## DAT-11 · `execution_snapshot` 只有种子脚本会建 → 经 API 发布的 Agent 永远不可运行

**问题描述**
`JdbcExecutionSnapshotResolver` 的解析 SQL 是三表**内连接**：
```sql
FROM agent a
JOIN agent_version v  ON v.agent_id = a.agent_id AND v.tenant_id = a.tenant_id
JOIN execution_snapshot es ON es.version_id = v.version_id AND es.tenant_id = v.tenant_id
WHERE ... AND v.published_at IS NOT NULL
```
**没有快照 = 内连接查不到 = 该 Agent 永远不可运行**（`POST /api/runs` → 404 `AGENT_SNAPSHOT_UNAVAILABLE`）。
而勘察发现：**此前没有任何生产代码路径创建 `execution_snapshot`** —— 只有种子脚本 `V1_seed.sql` 会建。

**产生原因**
发布链（`publishVersion`）与运行链（`resolveFromSnapshot`）之间**缺一环**，
而既有测试**全绿** —— 因为所有 IT 的夹具都是**手工插** `execution_snapshot`，
「发布 → 运行」这条真实链路从未被任何 IT 覆盖过。

**相关解决方案**
`JdbcAgentManageRepository.publishVersion` 在**版本行插入之后、`conn.commit()` 之前**调用新增的
`createExecutionSnapshot(...)`。
⚠️ **必须与版本行同事务**：快照与版本是同一个发布事实的两面；分开提交会出现「版本已发布但无快照」的中间态
—— 那正是本缺陷本身。

内容口径：

| 列 | 取值 | 理由 |
|---|---|---|
| `agent_config` | 该版本的 `definition` | 快照自解释；为后续「读路径切到 `cap_agent_def`」保留对照基准 |
| `prompt_config` | `{}` | 尚无权威模型，**不自创契约** |
| `tool_contracts` | `{}` | 同上 |
| `run_config` | `{"maxCostPerRun":"2.00","maxLlmCalls":12,"maxSteps":20,"approvalRequired":"OPTIONAL"}` | DEC-9 运行期容量配置档 |

**来源**：`docs/E2E实测缺陷修复与复验_20261023.md` §3
**状态**：✅ 已修（旧链自洽）；CAP 新链读路径切换见 §4 阶段级任务

## DAT-13 · 切 app_agent 后 platform schema 授权未补 → 平台域表整域失读

**问题描述**
2026-10-30 把主数据源切到 `app_agent`（NOBYPASSRLS）后：
`03_platform_roles.sql` 只授 `public` schema（应用角色的业务域），
`09_platform_schema_grants.sql` 只授 `platform_ops`（平台运维通道）
→ **`app_agent` 对 `platform` schema 一张表都读不到**。

**产生原因**
授权脚本是**按「schema 维度」**写的（一个角色对一个 schema 整体授权），
而实际需要的是**按「表 + 用途」**精确授权。切角色时才发现跨 schema 的少量必需表没被覆盖。

**相关解决方案**
新增 `deploy/sql/platform/11_platform_tenant_read_grant.sql`：
- 给 `app_agent` **只读** `platform.tenant` + `platform.tenant_quota`；
- **刻意不给写权限、不给整域读权限**：
  · platform 域还有 `platform_user` / `platform_session` / `platform_permission` 等身份与凭据表，
    整域读 = **凭据库对业务进程敞开**；
  · 写平台域是平台运维通道的职责（`provisionTenant` / `transitionLifecycle`），
    给应用角色写权限 = 「应用侧一条 SQL 就能改全平台租户生命周期」；
- **刻意不走 BYPASSRLS 运维通道**：`platform.tenant` 无 RLS，只读不构成越权；
  且 `PlatformOpsDataSourceArchitectureTest` 明确禁止新增运维数据源消费者
  （运维连接装到业务读路径 = 租户隔离整体失效）。

**来源**：`git log b31963f`（2026-11-01）
**状态**：✅ 已修
