## 二、逐项说明

### D-01　平台全局档 `ingest-jobs` 500

- **根因**：`RagManagementController.listIngestJobs` 沿用租户档写法 `ctx.requireTenant().tenantId()`；同文件其它端点已注明「平台全局档没有本租户概念，`requireTenant()` 会抛」，属作用域改造漏改。
- **修复**：平台档不再找「本租户」，改为走与全局建单相同的 `rag_ops` 运维通道。原因不是图省事：`rag_ingest_job` 的 RLS 是 `tenant_id = rag_current_tenant()`，平台档会话按设计置空，应用角色对全局行恒读 0 行（静默「暂无任务」）；把哨兵写进 `app.tenant_id` 又会撞 42501（500）。因此列表必须走 BYPASSRLS 的运维会话，且谓词 `tenant_id = rag_global_tenant_id()` 写死在 SQL 里，签名里没有租户参数可填。
- **装配纪律**：`GlobalIngestJobPort` 从函数式接口变为双方法（建单 + 列表），`RagManagementConfig` 不能再使用方法引用，改为显式匿名实现委托同一仓储，避免平台档列表在装配期缺失实现。
- **实测**：平台档 `GET /ingest-jobs?limit=20` → **200 / 2 行 / tenantId 全为全局哨兵**（与只读 SQL 统计的 2 行一致）；租户档仍 200 / 0 行（该租户确实无 job）；`X-Rag-Scope: ALL` 仍 501（未开放的边界未变）。

### D-02　平台全局档 `knowledge-points` 500

- **根因**：原代码注释说「用 `queryTenantId()` 而非 `requireTenant()`」，但平台档 `queryTenantId()` 是**全局哨兵**，它被直接 `set_config('app.tenant_id', ?, true)` 后，`rag_current_tenant()` 按 V8 §1 的越权封堵抛 SQLSTATE 42501。注释方向对、实现方向错。
- **修复**：统一改用 `RagSessionScope.apply(jdbcTemplate, context)`——这是 `listSources` 等已改造端点使用的同一入口，平台档置空会话租户，租户档绑真实租户。置空后 RLS 读策略只剩「全局行」一支，正是平台档要读的数据。
- **数据事实核对（防静默失真）**：只读直连库确认 `rag_knowledge_point` **全表 0 行**，因此平台档返回 `[]` 是真值，不是「读不到而假装空」。租户档 A/B 同样 `[]`，与全表统计一致。
- **残留边界**：当前没有「全局知识点非空」的造数，因此本轮只验证了「平台档不再 500 + 会话绑定口径正确 + 空列表是真值」；有数据时的非空读取由 SQL 谓词与单测守卫覆盖，未做真实非空 E2E。

### D-03　AI 对话语料问答 500（两层）

1. **第一层：外部依赖未启动 + 错误类型错误**
   - 本机 Ollama（`127.0.0.1:11434`，`qwen3-embedding:8b`）未运行；`OpenAiCompatibleEmbeddingPort` 把 `ConnectException` 抛成泛化 `IllegalStateException`，Spring 默认给出无名 500。
   - 修复：新增 `EmbeddingUnavailableException`（`rag-ports`，不引 Spring），只表达「上游暂时不可用」；响应格式错误/维度不匹配等契约问题仍是 `IllegalStateException`，不会被伪装成「稍后重试」。控制器捕获后转 503，且**不降级为纯词法检索**（那会让分数口径悄悄变化、页面却显示成功）。
   - 排错记录：首次 503 回归误用非法枚举 `EXPLANATION`（合法仅 `OVERVIEW/EXPLAIN/VERIFY/SOLVE`），请求在反序列化阶段就被 400 拦下，是**假阴性**；改用 `EXPLAIN` 后才真正打到嵌入链路。
2. **第二层：503 的原因完全丢失**
   - 实测发现 Spring 默认 `/error` 只回 `{timestamp,status,error,path}`，`ResponseStatusException` 的 `reason` 既没进响应体，服务端日志也搜不到——运维拿到一个无原因的 503 仍无从下手，与管理面已有的 `RagManagementExceptionHandler` 语义不一致。
   - 修复：新增 `RagRetrievalExceptionHandler`，用 `assignableTypes` 限定到 `RagRetrievalController`，避免污染同容器的管理面；把 `reason` 放进 `message`，5xx 记 ERROR 日志、4xx 记 INFO；不回堆栈、不回上游响应体原文（可能含凭据或语料片段）。
- **恢复动作**：启动本机 Ollama（`RAG_EMBEDDING_BASE_URL` 指向 11434）。这是环境侧依赖，不是代码内开关；生产部署必须保证嵌入服务与模型可用。
- **实测**：
  - 停 Ollama → `POST /api/v1/retrieval` **503**，响应体 `message` 含「嵌入模型服务不可用」与 `RAG_EMBEDDING_BASE_URL`；服务端日志同文案可检索（`X-Trace-Id: 1c36d81821ef4fdc944a9689c539269e`）。
  - 启 Ollama → 用有语料的租户 A（`2187ffed-…`，4,326 个分块）+ 沪教版六年级上册请求 → **200**，命中 3+ 片段，最高分 `0.8253`，`channel=DENSE_VECTOR`、`reason=DIRECT_MATCH`。
  - 浏览器：AI 对话页选租户 A、同版本坐标 → `/retrieval` 200 ×3 + `/retrieval/generate` 200，展示 7 条逐字依据与 `EXCERPT_ASSEMBLY` 生成方式；选无语料的租户 B 时正常显示「依据不足」分支（诚实失败，不编造）。

### D-04　审计页 Select `value=null` 警告

- 用显式数值哨兵 `0` 表达「不限」，`windowFrom(0) → null`（请求仍不带 `from` 参数），其余时间窗给出 ISO 起始时刻；`WINDOW_FILTERS` 与 `windowFrom` 导出供守卫直接断言。
- 浏览器复核 `/admin/audit`：控制台只有 Vite/React DevTools 提示，无 `value in Select options should not be null`。

### D-05　侧栏重复 Menu key

- 删除「知识与数据 / RAG 语料管理」遗留入口（与「RAG · 录入与校对 / Dashboard 总览」完全同路由、零功能差别），不造第二个假路由。
- 守卫覆盖：全量 `NAV_NODES` 唯一性、分组内唯一性、`/rag/dashboard` 唯一归属 `rag-ingest`、扁平视图与分组展开数量一致。
- 浏览器复核登录后侧栏与 4 个 RAG 页面：无 `Duplicated key` 警告。

## 四、诚实边界与残留风险

1. **嵌入服务是外部依赖**：本轮把本机 Ollama 拉起来才恢复检索；代码只保证「不可用时 fail-closed 给 503 + 明确原因」，不提供内置降级向量。生产必须保证 `RAG_EMBEDDING_BASE_URL` 指向的服务与模型已就绪。
2. **D-02 未做「全局知识点非空」的真实 E2E**：全表 0 行是数据事实；修复验证的是作用域绑定口径与不再 500。若后续灌入全局知识点，建议补一条非空读取的跨租户闭环 IT。
3. **租户 B 无语料**：AI 对话页选租户 B 会正确显示「依据不足」；这不是缺陷。要复现命中需选租户 A 并配沪教版六年级上册（历史存量版次）。
4. **未扩范围**：本轮未做 RAG 真实写入、三步审批/执行、平台用户删除（原报告 §4 已声明不在范围）；未在平台库新增任何测试数据，AI 对话仅内存会话。
5. **非本轮改动**：工作区另有 `07_agent_definition_upgrade.sql`、`TransactionalConnectionHolder` 等 4 个已修改文件，属于 2026-11-10 更早的独立修复，本报告未触碰。
