# Agent 定义体系审查（2026-11-09）

## 0. 结论

当前项目的 Agent 定义**在结构上是完整的**（系统提示词、业务提示词、工具描述三类信息都有承载位），
但**存在一条会导致 Run 无法执行的断链**，以及若干处「设计契约 / 结构化真源 / 运行期读取」三者不一致。

严重度分级：

| 级别 | 问题 |
|---|---|
| **P0** | 运行期提示词/模型的读取源（`agent_version`）与权威定义源（`cap_agent_def`）是两套表，而三步发布流**不写**运行期那张表 → 经治理通道发布的 Agent 一律跑不起来 |
| **P1** | `cap_tool_def` 无 `description` 列，工具描述被「借用」Skill 的 1 级 purpose 顶替，同一 Tool 被多个 Skill 声明时描述失真 |
| **P1** | 治理发布通道（`AgentSpec` / `AgentRequest`）**完全没有模型与提示词字段**，管理台无法配置 Agent 的模型、提示词、生成参数 |
| **P1** | `enabledSkills` 形态不一致：契约要求 `{id, version}` 对象，`CapDefinitionProjector.stringList()` 只认字符串 → 按契约书写会被静默解析为空集 = Agent 零能力 |
| **P2** | `instructions.systemPromptRef`（契约中提示词的主载体）无任何实现；提示词只有内联一条路 |
| **P2** | `generationParams`（temperature/maxOutputTokens 的契约位置）运行期不读，读的是根级 `temperature` / `maxOutputTokens` / `timeoutMs` |
| **P2** | Agent 内容指纹不含提示词/模型字段；`additionalProperties: false` 与 `security.denyByDefault` 等契约约束没有校验器兜底 |

## 1. Agent 定义由哪些部分组成（实际实现）

### 1.1 结构化真源：`cap_agent_def`

`platform/agent-core/.../core/cap/CapAgentDef.java:42-58`

| 字段 | 语义 | 归类 |
|---|---|---|
| `name` / `description` | 名称与业务描述 | 业务提示 |
| `roles` | 适用主体角色（注释明确「非授权授予」） | 治理 |
| `enabledSkills` | **V1 唯一启用途径** | 能力 |
| `skillBundles` / `capabilityTags` | V1 **忽略语义**（预留） | 能力 |
| `overrides` | 收紧覆盖（移除 Skill/Tool、下调 riskCeiling） | 能力/安全 |
| `orchestration` | 编排声明（`{}` = LEAF） | 编排 |
| `configFingerprint` / `schemaVersion` / `publishedAt` | 版本与指纹 | 治理 |

**注意：`cap_agent_def` 里没有系统提示词字段，也没有模型字段。** 见 §3。

### 1.2 运行期实际读取源：`agent_version.definition`（自由 JSONB）

`AgentModelConfigAssembler.java:102-137` 装配出 `AgentModelSettings`（:404-410）
= `modelId` + `systemPrompt` + `temperature` + `maxTokens` + `timeout` + `toolSchemas`。

它读的键（注意是**另一张表**，见 §3）：

- 模型：`modelRef` / `modelId`（:117）
- 提示词：`instructions.inlineInstructions` → 回落扁平 `systemPrompt`（:278-288）
- 生成参数：根级 `temperature` / `maxOutputTokens` / `timeoutMs`（:134-136）

### 1.3 业务提示词 / 能力指引：Skill 三级描述

`CapSkillDef.java:24-37` 携带 `SkillDescription`（:31-34），
落在 `cap_skill_def.purpose / usage / content` 三列：

| 级别 | 字段 | 消费者 |
|---|---|---|
| 1 级 | `purpose` | 路由/选型 → 注入**工具的 description** |
| 2 级 | `usage[{when,how}]` | 执行 → 注入系统提示词【技能使用指引】节 |
| 3 级 | `content` | 执行 → 同上一并注入 |

注入逻辑：`AgentModelConfigAssembler.java:172-211`
（该函数注释、变量、返回值描述本身是合格的 fail-closed 设计：「描述不是授权」「无 2/3 级内容则提示词一字不改」）。

### 1.4 工具描述：来自闭包

`AgentModelConfigAssembler.java:221-238`

闭包由 `PermissionResolver.java:180-250` 沿 `Agent → Skill → {Tool, MCP}` 求交，
`overrides` 只收紧；MCP 走 `declaredMcp` + 清单交集 + ForcedSafety。
委派工具**不进闭包**，由 `DelegationToolSchemaAssembler` 并列装配。

### 1.5 运行期最终拼装

`RunExecutionLoop.java:734-766`

```
systemPrompt = Agent 定义提示词 + Skill 2/3 级指引
             + 记忆块（每轮重拼）
             + 上下文裁剪留痕 notice
```

这段拼装是干净的（记忆块每轮重拼、裁剪说明走系统提示而非消息序列，注释也交代了理由）。

## 2. 设计契约（schema）怎么说

`docs/多级 Agent优化/agent-capability-contracts-v1/schemas/agent.schema.json` 的 required 共 14 项：

```
schemaVersion, id, tenantId, name, status, enabled,
instructions, contract, modelRef, enabledSkills,
roles, security, executionPolicy, revision
```

与定义内容直接相关的几处：

- `instructions`：required `systemPromptRef`，可选 `systemPromptVersion` / `inlineInstructions`（:66-84）
- `modelRef` + `generationParams{temperature, topP, maxOutputTokens}` + `fallbackPolicy`（:109-148）
- `contract{inputSchema, outputSchema, responseFormat}`（:85-108）
- `security{riskCeiling, authorizationPolicyRef, denyByDefault: true, allowPrivilegeEscalation: false}`（:282-310）
- `executionPolicy{timeoutMs, retryPolicy}` / `resourceLimits` / `contextPolicy` / `knowledgeRefs` / `memoryPolicyRef`
- `additionalProperties: false`（:6）

对照实现，**未被任何地方承载的契约字段**：
`instructions.systemPromptRef` / `systemPromptVersion`、`contract.inputSchema` / `responseFormat`、
`generationParams.topP`、`fallbackPolicy`、`security.*`、`executionPolicy.*`、`resourceLimits`、`contextPolicy`、
`memoryPolicyRef`、`knowledgeRefs`、`observabilityPolicy`。

> 判断：这些字段「未实现」本身可以接受（分阶段交付），但**前提是有人说明哪些是 V1 范围内、哪些是预留**。
> 现状是实现读一套键（扁平 `systemPrompt`/根级 `temperature`），契约写另一套键，两者都没有交叉引用，
> 于是「按契约写的配置」和「跑得起来的配置」不是同一份东西。

## 3. P0 — 运行期读的那张表，发布流根本不写

### 现象

- 运行期提示词/模型的唯一来源是 `agent_version.definition`：
  `AgentModelConfigAssembler.java:260-272` 走 `AgentQueryPort.listVersions()`，
  SQL 落在 `JdbcAgentQueryRepository.java:195`（`FROM agent_version`）。
- `cap_agent_def` 是注释宣称的「结构化真源」，`CapAgentDef.java:12-15`
  说二者「双写、最终读路径切到本对象」。
- 但当前唯一的 Agent 发布入口是三步工作流：
  `CapConfigPublishController.java:101-113` → `ConfigPublishService.java:397-405`
  只 `agentDefs.insert(...)`。
- 反向双写不存在：全仓 `INSERT INTO agent_version` 只有两处
  （`JdbcAgentManageRepository.java:156` 与 `ItTenantProvisioner.java:117`），
  而写它的那个端点 `POST /api/agents/{id}/versions` **已在 P0-5 下线**
  （`AgentController.java:36-46` 与 :186-192）。

### 后果

经治理通道（管理台 / 三步发布）发布的 Agent：

1. `cap_agent_def` 有行 → 闭包、闸门、指纹、委派都正常；
2. `agent_version` **没有对应版本行** → `definitionOf()` 返回空 →
   `AgentModelConfigAssembler.java:103-105` 返回 `Optional.empty()`；
3. `RootAgentModelConfigProvider` 与 `WorkerChildAgentModelConfigProvider` 都 fail-closed 拒绝执行
   （`WorkerExecutionConfig.java:1141-1152`）
   → **Run 一步都跑不了，报错点是 worker 侧，离真因（发布没落对表）很远。**

反过来，只有种子/夹具写入 `agent_version` 的历史 Agent 才「跑得起来」，
而它跑起来时读到的提示词、模型，和 `cap_agent_def` 里那份权威定义**毫无关系**。

> 这正是 `CapAgentDef.java:12-15` 与 `AgentModelConfigAssembler.java:29-38`
> 两处注释反复声明要消除的「两套语义」——根与子已经统一到一份装配器了，
> **但「配置面」与「执行面」这两套仍然并存**。

### 建议

按优先级二选一：

- **A（推荐，与注释里既定的终态一致）**：把运行期读取切到 `cap_agent_def` + 一个 Agent 级
  「提示词/模型」承载位，`agent_version` 降级为纯归档；同时补齐 §4 的字段缺口。
- **B（迁移期最小修）**：三步发布流在写 `cap_agent_def` 的**同事务**内补写 `agent_version`（反向双写），
  并让 `definition` 由 `cap_agent_def` 生成而非由客户端提交，避免两套真值。

无论哪条，都要有 CI/集成测试断言「经治理通道发布的 Agent 可建 Run 且读到预期提示词与模型」——
现在的测试覆盖不到这个跨表面接缝（§5.1）。

## 4. P1 — 三类信息各自的缺口

### 4.1 系统提示词：治理通道无字段

`ConfigPublishPayload.java:228-236`（`AgentSpec`）与
`CapConfigPublishController.java:440-449`（`AgentRequest`）的字段集 =
`agentId / name / description / roles / enabledSkills / skillBundles / capabilityTags / overrides / orchestration`。

**没有 `systemPrompt`、没有 `instructions`、没有 `modelRef`、没有任何生成参数。**
前端同口径：`admin-console/src/api/types.ts:308-325`（`PublishAgentSpec`）与
`admin-console/src/pages/agents/agentDraftForm.ts:48-79` 的表单也没有这些项。

后果：管理台**无法为 Agent 配置提示词和模型**。提示词只能靠历史 `agent_version` 里的自由 JSON 或改库。
这把「业务提示词」这一等公民挡在了治理面之外——而这恰好是本节审查对象的核心组成之一。

另外 `CapDefinitionProjector.java:24-36` 的映射表把 `definition` 投影到 `cap_agent_def` 时
**也刻意丢弃 `systemPrompt` / `modelRef`**。
所以即使旧表里有提示词，结构化真源里也没有它 —— 两侧都不是「权威」，
权威实际上是「旧表的自由 JSON」。

### 4.2 工具描述：没有自己的字段，被 Skill purpose 顶替

`cap_tool_def` 无 `description` 列（DDL `deploy/sql/platform/01_platform_ddl.sql:2277-2303`：
`id, version, name, kind, risk_level, mcp_*, input_schema, param_policies, ...`，没有 description），
`CapToolDef.java:22-36` 同样只有 `name`。
而契约 `tool.schema.json` 的 `description` 是 `maxLength: 4000` 的一等字段。

实现的处理方式（`AgentModelConfigAssembler.java:216-232` + `purposesOf()` :243-255）：

> 工具 description ← **第一个**声明它的 Skill 的 1 级 purpose；没有则回退工具名。

三个问题：

1. **语义错位**：purpose 描述的是「这个 Skill 做什么」，被当成「这个工具做什么」。
   一个 `tool-profile-read` 挂在「档案查看」与「成绩简报」两个 Skill 下，
   模型看到的工具描述永远只有先出现那个 Skill 的说法
   （注释说「闭包顺序即口径」解决了不确定性，但没解决失真——工具本身的描述仍然缺失）。
2. **契约字段无处安放**：Tool 的 `description` / `outputSchema` / `timeoutMs` / `idempotency` 在表里没有列。
3. **指纹不覆盖**：`CapObjectFingerprint.java:61-81` 入指纹的是
   id/version/name/description/roles/enabledSkills/skillBundles/capabilityTags/overrides/orchestration ——
   因为结构里根本没有提示词与模型字段，所以「改了 Agent 的提示词或模型」这件事
   **在 Agent 内容指纹上不可见**。
   （Skill 侧相反：三级描述确实入指纹，:263-274。）

### 4.3 `enabledSkills` 形态不一致 → 静默零能力

契约要求 `enabledSkills: [{id, version}]`（`$defs/ref`，
`agent.schema.json:149-156` 与示例 `examples/agent.example.json`）。

而 `CapDefinitionProjector.java:215-225` 的 `stringList()` **只收集 `instanceof String` 的元素，其余一律丢弃**：

```java
if (item instanceof String s && !s.isBlank()) { out.add(s.trim()); }
```

于是按契约书写的 `enabledSkills: [{"id":"skill-x","version":"1.0.0"}]` 会被投影成 **空集**，
`cap_agent_def.enabled_skills = []` → 闭包无任何 Skill/Tool → **一个看似发布成功、实际零能力的 Agent**。
这与本仓一贯的 fail-closed 纪律（「跳过等于把『声明了但解析不出』当成『没声明』」，
`PermissionResolver.java:52-57`）直接矛盾。

> 现场佐证：能跑的种子数据用的是**字符串数组**
> （`deploy/sql/platform/02_platform_seed.sql:270-272`），
> 而当前已下线的正是唯一会写 `agent_version` 的通道 ——
> 这条不一致现在被「双写不可达」掩盖住了，一旦按 §3 恢复双写就会立刻暴露。

同类：`skillBundles` / `capabilityTags` 在契约里不存在（代码注释标为「V1 忽略语义」，可接受）；
`overrides` 的契约键名 `removeSkills/removeTools/lowerRiskCeiling` 与实现一致 —— 这条是对的。

## 5. P2 与其他观察

### 5.1 测试夹具掩盖了跨接缝缺陷

`AgentModelConfigAssemblerTest.java:135-137` 用扁平形态
`{"modelRef":..., "systemPrompt":..., "temperature":..., "maxOutputTokens":..., "timeoutMs":...}`，
且测试自己伪造 `AgentQueryPort.listVersions()` 的返回。
→ 单测全绿，**但没有任何测试覆盖「治理发布 → 运行期能读到提示词与模型」这条接缝**（§3）。

同时，种子数据的 definition（`02_platform_seed.sql:270-272`）**既没有 `modelRef` 也没有 `systemPrompt`**。
按 `AgentModelConfigAssembler.java:117-122` 取不到模型标识即返回空 → fail-closed。
要么这些 Agent 实际跑不了，要么真实库里存在与本仓种子不同的配置 —— 两种情况都值得确认并留证据。

### 5.2 没有契约校验器

契约里大量 `additionalProperties: false` + `required`，实现侧只做逐键取值，
没有 JSON Schema 校验器（未发现 `networknt/json-schema-validator` 之类依赖），
也没有 `schemaVersion: "1.0"` 判定。
→ 未知键静默忽略、拼错的键（`enabled_skills` 做了兼容，`model_ref` 没做）静默丢、多余字段不拒。
契约声明的 `security.denyByDefault: const true`、`allowPrivilegeEscalation: const false`
这类**约束性常量**也没有任何地方断言。

### 5.3 `execution_snapshot.prompt_config` 全为 `{}`

`02_platform_seed.sql:628-634` 与 `JdbcAgentManageRepository.java:254-270`
都写死 `prompt_config = '{}'`，注释自陈「尚无权威模型」。
即：**平台有一张专门放提示词配置的表，但没人往里放东西** —— 提示词的权威源悬空，
这正好是 §3 / §4.1 那个问题的结构性表现。

### 5.4 还有一条平行的提示词通道

`ConsoleChatController.java:351` 直接取请求体的 `systemPrompt`，
而前端把提示词**硬编码在 React 组件里**：
`frontend/src/pages/chat/GeneralChatPage.tsx:40-62` 的 `SCENES[].prompt`。
即业务提示词有一部分**活在代码中、不在任何配置表里**。
这与 Agent 定义体系是并行的两套，不冲突（不同产品面），但
「Agent 定义 = 系统提示词 + 业务提示词 + 工具描述」这个心智模型下，它属于漏管的那一类。

### 5.5 小问题

- `CapAgentDef.java:60-84` 兼容构造器把缺省编排写成 `{}` 并注释为「按 LEAF 解析」—— 口径清晰，✓。
- `AgentModelConfigAssembler.java:209`
  `String base = basePrompt == null ? "" : basePrompt.trim();`
  在已声明 `@NonNull` 的参数上做 null 判断（且入参 `systemPrompt(root)` 永不为 null）→ 死代码，
  建议删掉以免传递「这里可能是 null」的错误信号。
- `toolSchemas()` 在闭包解析失败时返回空 Map（:141-158）。注释理由是
  「不因一条边读不出来让 Agent 全瘫」，可接受；但配合 §4.3 的静默空集，
  两种「工具表为空」在模型侧看起来完全一样，排查时不可区分
  → 建议把「闭包解析失败」显式记入 Run 事件，而不只 WARN 日志。
- 类名易误读：`AgentModelConfigAssembler` 实际产出含 `systemPrompt` 的**完整执行配置**，不是只有 model 配置。
- 表名易误读：`cap_skill_def.description` 是**遗留单级列**，
  `JdbcCapSkillDefRepository.java:71-116` 明确「新入库一律 NULL」，
  真正的三级描述在 `purpose/usage/content`。列名与语义不符，
  建议改名或把说明收敛到一处（现在只有仓储侧有说明，DDL 的 `description` 列没有注释）。

## 6. 做得好的部分（保留）

1. **三级描述的消费者划分**（purpose→工具 description，usage/content→执行期注入）清晰且成文，
   `SkillDescription.java:10-21`。
2. **「描述不是授权」**在提示词里对模型明示（`AgentModelConfigAssembler.java:192-194`），
   且冲突时以声明为准 —— 提示词与闸门语义一致。
3. **固定版本装配**：根/子都按 Run 快照里的 `agentVersion` 精确取那一版，不解析「当前已发布」，
   注释交代了「在途 Run 静默漂移」这个理由（MA-T08）。
4. **根与子共用一份装配器 + 共用一份委派 Schema 装配器**，把历史「父子两套语义」真正收敛了。
5. **闭包只解析一次**同时供工具表与 Skill 指引（:127-129），避免「一边读得到描述、另一边读不到」。
6. 记忆块每轮重拼、裁剪 notice 走系统提示而非消息序列，这两处细节有理由有注释。
7. `CapToolDef` 紧凑构造器把 `kind` 与 `httpConfig` 的「三态不可归一化」写成异常，
   DB 侧同款 CHECK 兜底 —— 好的双层防线。

## 7. 建议动手顺序

1. **定一个权威源**（§3 选 A 或 B）并加一条跨表面集成测试：
   「三步发布一个带提示词与模型的 Agent → 建 Run → 断言 worker 侧读到该提示词与该模型」。
   这一步不做，其余都是在一个跑不起来的体系上修细节。
2. **补齐治理面字段**（§4.1）：`AgentSpec` / `AgentRequest` / `PublishAgentSpec` / 草稿表单加上
   `instructions`（内联 + 引用）、`modelRef`、`generationParams`，并把它们纳入 Agent 内容指纹（§4.2-3）。
3. **`enabledSkills` 兼容 `{id, version}` 且解析不出时报错而不是静默空集**（§4.3）。
4. **给 Tool 加 `description` 列**，purpose 只作为可选补充；顺带落契约里的
   `outputSchema` / `timeoutMs` / `idempotency`。
5. **加契约校验器**（§5.2），至少把 `additionalProperties:false` 与
   `denyByDefault` / `allowPrivilegeEscalation` 这类常量约束在配置期拒住；
   同时明确「V1 实现 / V1 预留」的字段清单，写进 06 号文档，与代码注释对齐。
6. 清理 §5.5 的死代码与命名，把「闭包解析失败」升级为 Run 事件。
