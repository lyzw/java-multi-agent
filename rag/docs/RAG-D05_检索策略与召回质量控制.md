## 1. 检索流水线的七步与顺序约束

```mermaid
flowchart LR
    S1[① 知识点解析] --> S2[② 多路召回] --> S3[③ 版本过滤] --> S4[④ 角色过滤]
    S4 --> S5[⑤ 知识点补全] --> S6[⑥ 排序] --> S7[⑦ 分数门禁]
```

> ⚠️ **顺序不可调换**，这是本文最重要的一条约束。
> 下面每一步都说明「为什么必须在这个位置」。

| 步 | 动作 | 为什么必须在此位置 |
|---|---|---|
| ① | 知识点解析 | 决定后续补全与扩展的范围；必须在召回前，否则补全无从进行 |
| ② | 多路召回 | 需要尽可能宽的候选集，过滤是排除而非筛选 |
| ③ | **版本过滤** | 必须在**重排之前**。重排模型只懂相关性，**不懂**哪些是别的版本 |
| ④ | **角色过滤** | 同上。必须在重排与截断之前，否则被滤内容已流入上下文 |
| ⑤ | 知识点补全 | 在角色过滤**之后**——补全不能绕过泄题闸门 |
| ⑥ | 排序 | 需要在最终集合上排序；版本惩罚在此叠加 |
| ⑦ | **分数门禁** | 必须在最后——门禁依据最终分数判定 |

> ⚠️ **若 ③④ 放到 ⑥ 之后会怎样**：
> 重排取 top-20 → 滤掉其中的答案与异版本 → 只剩 5 条，
> 而被滤掉的 15 条**已经进入过上下文**（若在截断前组装 prompt）。
> 闸门形同虚设。这是最常见的实现顺序错误。

## 2. 多路召回

| 通道 | 技术 | 解决什么 |
|---|---|---|
| 稠密向量 | pgvector HNSW（余弦） | 同义改写、语义相近 |
| 词法 | PostgreSQL `tsvector` + 应用层中文分词 | 专有名词、公式、精确术语 |
| 知识点 | 沿 `kp_ids` 聚合 | 碎片化补全 |
| 先修扩展 | 沿 `prerequisites` | 诊断知识缺口 |
| 邻接扩展 | 同章节相邻片段 | 被切碎的上下文 |

> ⚠️ **为什么必须要有词法通道**：
> 教辅术语精确匹配是**词法问题**。「二次函数」与「反二次函数」、
> 「相似三角形」与「全等三角形」——纯稠密向量会把它们靠得很近，
> 而它们在教学上是完全不同的知识点。词法通道在此不可替代。

### 2.1 融合方式

采用 **RRF（Reciprocal Rank Fusion）**：

```
score(d) = Σ_c  1 / (k + rank_c(d))      k = 60
```

> ⚠️ **为什么用 RRF 而不是分数加权**：
> 稠密余弦距离与 BM25 分数量纲不同、分布不同，
> 直接加权需要人工标定两者的相对系数，而该系数随语料变化。
> RRF 只用**排名**，无需标定，跨语料稳定。
> 代价是丢失了「第一名比第二名强多少」的信息——
> 因此 RRF 之后**必须**接重排器。

### 2.2 重排

用 cross-encoder 重排（`bge-reranker-v2-m3` 类）：

| 阶段 | 模型 | 候选数 | 产出 |
|---|---|---|---|
| 一阶段召回 | 双塔（稠密+词法 RRF） | 100 | 粗排 |
| 二阶段重排 | cross-encoder | 100 → 20 | 精排 |
| 三阶段过滤 | 规则（版本/角色） | 20 → n | 硬约束 |

> ⚠️ **重排必须在过滤之前还是之后？**
> 本设计选择**过滤（③④）在重排之前**（见 §1）。
> 代价是：被滤掉的候选不参与重排，可能本该进入 top-20 的好内容被提前丢弃。
> 这个代价可接受，因为：
> 1. 异版本与答案类内容即便重排分很高，也是**不可用**的；
> 2. 过滤后候选仍足够（召回 100 条，过滤后通常仍 > 30 条）。

## 3. 检索模式：模式即过滤条件

```java
public enum RetrievalMode { EXPLAIN, SOLVE, VERIFY, OVERVIEW }
```

| 模式 | 用途 | 答案类内容 | 典型问题 |
|---|---|---|---|
| `EXPLAIN` | 讲解知识点 | ❌ 全部排除 | 「二次函数的顶点怎么求」 |
| `SOLVE` | 解题 | ❌ 排除习题标准答案（✅ 允许例题解答） | 「这道题怎么做」 |
| `VERIFY` | 核对答案 | ✅ 全部允许 | 「第 12 题的答案是什么」 |
| `OVERVIEW` | 概览 | ❌ 全部排除 | 「这一章讲了什么」 |

> ⚠️ **模式不是生成期提示，是检索期过滤条件**。
> 模式由调用方（主平台 Tool 调用时根据会话意图判定）显式指定，
> 平台不传则**默认 `EXPLAIN`**（最严格的一档）。
>
> 默认取严格档的理由：默认宽松的失败形态是「意外泄题」，
> 而默认严格的失败形态是「回答不够完整」——后者可补救，前者不可。

## 4. 版本范围与召回

版本范围（`EditionScope`）在检索中同时扮演三个角色：

| 角色 | 机制 | 实现 |
|---|---|---|
| **过滤** | 非允许范围的片段不得进入结果 | `EditionScope.admits` |
| **排序** | 非首选版本降权 | `EditionScope.rankPenalty`（0 / 10 / 50） |
| **标注** | 非首选版本须提示差异 | `EditionScope.requiresVersionDisclaimer` |

> ⚠️ **过滤与降权必须分开**。混淆二者会导致「降权后仍被召回」——
> 那正是版本串扰的成因。
> 已通过单测锁定（`EditionIsolationTest`）。

## 5. 泄题闸门

见 RAG-D04 §3.3。此处只强调其在检索流水线中的位置：

```java
// ④ 角色过滤（硬过滤）——泄题闸门
List<ScoredChunk> roleFiltered = versionFiltered.stream()
        .filter(s -> RetrievalPolicy.allowsRole(s.chunk().role(), request.mode()))
        .toList();
```

**双重保障**：

| 层 | 机制 | 强度 |
|---|---|---|
| 应用层 | `RetrievalPolicy.allowsRole` 硬过滤 | 强（可测） |
| 存储层 | `rag_chunk_retrievable_idx` 部分索引 | 弱（纵深防御） |
| 生成层 | prompt 提示 | ❌ **不可靠**，仅作补充 |

## 6. 分数门禁：让「找不到」成为合法输出

```java
List<ScoredChunk> above = scored.stream()
        .filter(s -> s.score() >= minScore)
        .toList();
```

### 6.0 ⛔ 门禁读的必须是「相关性分」，不是「排名分」

> **2026-10-23 实测缺陷**：门禁恒不通过，检索永远返回「未找到依据」。

`ScoredChunk` 带**两个量纲不同**的分数，混用会直接废掉门禁：

| 字段 | 含义 | 量纲 | 用途 |
|---|---|---|---|
| `score` | **相关性分**——检索器给出的真实相关性（稠密通道=余弦相似度、词法通道=`ts_rank`）| 0~1 | **门禁作用于此**（阈值按相关性标定）|
| `fusionScore` | **融合排序分**——RRF 值，只用排名、跨语料稳定 | 双通道命中时最大约 2/61 ≈ 0.033 | **排序与版本降权作用于此** |

⚠️ **曾经的实现把 RRF 融合分写进了 `score`**：
门禁阈值 0.2/0.35 是按相关性量纲标定的，而 RRF 上限只有约 0.033
→ **门禁恒不通过** → 检索永远返回「未找到依据」，
**语料再全也召不回任何东西**（端点返回 200、零报错，最难查的一类缺陷）。

> 这正是端口契约所说的「门禁必须作用于检索器给出的**真实相关性分数**」：
> 若由编排层用「排名」反推分数，top-1 恒为满分，门禁形同虚设。
> **实现层一旦改写分数语义，必须同时复核门禁阈值。**

### 6.1 为什么必须有门禁

没有门禁时，语义检索**总会**返回「最不相似的那一条」。
模型随后会基于这条弱相关内容编答案——这是 RAG 系统
「自信地胡说」的主要来源。

门禁把「**未在已授权语料中找到依据**」变成一个**正当的、系统的输出**，
而不是需要被掩盖的失败。

### 6.2 阈值

| 项 | 初值 | 校准方式 |
|---|---|---|
| `minRetrieverScore` | **0.35** | 由评测集实测标定（RAG-D08 §4） |
| `entailmentThreshold` | **0.75** | 同上 |

> ⚠️ **初值不得当作结论**。
> 主平台 `P0-D00` DEC-9 明确：「配置化解决『后续谁来调』，**不解决『初始值是多少』**。
> 初值本身就是决策——否则系统在上线首日就可能因缺省过大而失控。」
> 本项目的初值取保守档，**必须**在评测集上标定后才可放行。

### 6.3 分数的来源必须真实

```java
public interface RetrievalPort {
    @NonNull List<ScoredChunk> search(@NonNull RetrievalRequest request);
}
```

> ⚠️ 端口返回**带分数**的片段，而非裸片段。
> 若编排层用「排名」反推分数，则 top-1 恒为满分，门禁永远不触发——
> 「找不到依据」将成为**不可能事件**。
> 本项目在实现中曾犯此错误，由失败的单测
> `scoreGateDropsWeakMatches` 暴露并修正。

### 6.4 补全片段的分数基准

| 片段来源 | 分数 |
|---|---|
| 检索直接命中 | 检索器给出的真实分数 |
| 知识点补全 | `COMPLETION_BASE_SCORE = 0.5`（统一基准） |
| 先修扩展 | 同上 |

> ⚠️ 补全基准分必须**低于**典型命中分，否则补全内容会挤掉直接命中的高价值片段。

## 7. 召回质量的可观测性

每次检索须记录（进入 `rag_access_audit` 与指标）：

| 项 | 用途 |
|---|---|
| 查询摘要 | 回放定位 |
| 召回通道与命中原因 | 归因「为什么召回了这条」 |
| 过滤前后数量 | 识别「是召回不足还是过滤过严」 |
| 版本不一致标记 | 统计串版本风险 |
| 答案内容抑制标记 | 区分「语料没有答案」与「策略不给答案」 |
| 门禁触发标记 | 统计「依据不足」的发生率 |

> ⚠️ **「过滤前后数量」是调参的关键指标**：
> 若过滤后剩余比例过高（如 < 30%），说明召回阶段放进了太多不该放的，
> 应调整召回策略（提高 topK 或收紧查询），而不是放松过滤。
