## 0. 与主平台 DEC-5 的关系（必须先读）

主平台 `P0-D00` DEC-5 决策为「**首期不纳入 RAG/知识库**」，理由是首个业务场景
（BR-01 初中生错题归因）使用模型参数内知识即可，不引入向量库、不做文档切分入库、
不引用外部教材原文。

**本项目的存在即是对 DEC-5 的重审。** 重审不是推翻，而是**在 DEC-5 所定义的
「重新纳入条件」被满足后，启动独立子项目**。DEC-5 原文给出的重新纳入条件是：

> 需同时满足：数据 owner、评测集、访问模型、收益指标；且 A-008 评测显示参数内知识
> 不足以支撑归因准确性

| DEC-5 重新纳入条件 | 本项目的对应交付 | 状态 |
|---|---|---|
| 数据 owner | RAG-D07 §2 语料来源登记表 + 权威等级分级 | 🟡 制度已定义，数据待接入 |
| 评测集 | RAG-D08 评测集（可执行，非文档表格） | 🟡 框架已定义，样本待标注 |
| 访问模型 | RAG-D03 租户隔离 + RAG-D02 §5 访问模式 | ✅ 已定义并实测（见 §5） |
| 收益指标 | RAG-D08 §3 指标定义 | 🟡 待基线测量 |
| A-008 评测结论 | 需主平台 P2 评测集实测产出 | 🔴 **未产出** |

> ⚠️ **诚实边界**：最后一项（主平台 A-008）**尚未产出**。
> 主平台 `P3-D11` §4 明确记载「SB-01～03 的实际达标结论未产出」。
> 因此本项目当前定位是**可独立建设、可独立验收的 RAG 子系统**，
> **尚未与主平台形成端到端业务闭环**。接入主平台需待 A-008 结论。
> 见 RAG-D09 §2.3 阶段门禁 **G3**（第 ⑦ 条：A-008 结论产出前**不得接入主平台**）。

**并且，DEC-5 还留下一个必须处理的连带问题**：

> `P0-D03` §4 红线 13：「模型输出不得编造出处（DEC-5/R-018）——首期不使用外部知识库，
> Agent 不得输出教材引用、页码或资料出处；编造即判失败。」

主平台 `P3-D11` 已据此实现 `HallucinationDetector`（`agent-application`），
把**任何**引用形态（`第N章`/`人教版`/`第45页`/`ISBN`/`根据检索结果`）一律判为编造。

> ⚠️ **这是本项目与主平台最直接的技术冲突点**：
> 一旦接入真实语料并要求输出可溯源引用，主平台的检测器会把**每一个正确引用**
> 判为编造。
>
> 本项目的处置是**反转判据**而非放宽判据：
> **无语料时禁止引用** → **有语料时强制可核验引用**。
> 详见 RAG-D06 §1 与 RAG-D09 §3 的接入改造清单。

## 1. 范围

### 1.1 本项目交付

| 能力域 | 交付内容 |
|---|---|
| 语料治理 | 来源登记、权威等级分级、校验准入、版权状态、撤回机制 |
| 数据处理 | 版面感知解析、结构化切分、知识点挂接、题答配对、索引代际 |
| 检索 | 多路召回（稠密 + 词法）、版本硬过滤、角色硬过滤、知识点补全、分数门禁 |
| 生成约束 | 强制引用、逐字引文、版本坐标快照、存在性/蕴含/冲突三重校验 |
| 溯源 | 回答→声明→引用→片段→位置→来源的完整链路，落库可审计 |
| 评测 | 可执行评测集、召回与接地双指标、CI 不变式门禁 |

### 1.2 本项目**不做**（非目标）

| 非目标 | 原因 |
|---|---|
| 把 RAG 代码放进 `platform/` 模块 | 独立子项目，可独立部署与验收；接入方式见 RAG-D02 §6 |
| 通用/开放式问答（脱离教辅语料） | 超出「基于指定教材讲解」的定位 |
| 教材全文对外分发 | 版权风险；只做「定位 + 短引文」，全文不入库（对象存储受控读取） |
| 作业批改与自动打分 | 涉及评分公平性与申诉链路，属主平台另立需求 |
| 自动生成题目/讲解（无原文依据的原创内容） | 与「可溯源」目标根本冲突 |
| 图像/音视频语料 | 首期只做文本与公式表格；多模态另立范围 |
| OCR 之外的复杂版面（手写体、几何图形的精确还原） | 精度不足时宁可标记为「低置信」而非强行入库 |

### 2.1 RD-01 补充：为什么是 pgvector 而不是专用向量库

| 维度 | pgvector（本项目选择） | 专用向量库（Milvus/Qdrant/Elasticsearch） |
|---|---|---|
| 租户隔离 | **RLS 沿用主平台已验证方案**，FORCE 后连表 owner 也受约束 | 需另建一套租户过滤机制，与主平台 RLS 体系割裂 |
| 事务一致性 | 片段元数据与向量**同事务**——「已下架内容仍可召回」这类缺陷被结构性消除 | 需应用层双写或补偿事务 |
| 运维面 | **零新增中间件**（主平台已有 PG17，DEC-13 已冻结版本） | 新增一套部署/升级/备份/监控（主平台 R-022 已在 MQ 上吃过一次停维亏） |
| 规模上限 | 约 5×10⁷ 向量前性能可接受（HNSW，m=16/ef_construction=64） | 十亿级场景才有优势 |
| 混合检索 | 全文检索（`tsvector`/PG 中文分词扩展）+ 向量同库，可用 RRF 融合 | 需跨系统融合 |

> ⚠️ **决策边界**：本决策在「语料为教材/教辅/论文，规模在千万级片段以内」时成立。
> 超出该规模必须重开 ADR 评估（见 RAG-D02 §7 演进路径）。
> 教辅语料的规模估算：一套人教版初中数学教材体系约 3 万页，
> 按每页 8 个片段计约 **24 万片段/年级/版本**；覆盖 3 个学段 × 2 版本 × 6 学科
> 约 **1500 万片段**——在 pgvector 舒适区内，但**已接近需要调优的量级**，
> 故 RAG-D08 §6 要求在 100 万片段规模做一次实测。

### 2.2 RD-02 补充：权威等级与「可被检索」是两件事

`UNVERIFIED` 等级的资料**可以入库**（供人工审核比对），
但**不可被普通用户检索到**，更不可作为教学结论的唯一依据。

> ⚠️ 理由：教辅市场上存在大量**盗版教材扫描件**与**无授权教辅 PDF**。
> 一旦系统允许它们参与回答，等于把盗版内容包装成「权威讲解」输出。
> 但完全禁止入库也不现实——审核人员需要比对。
> 故采用「**入库可、检索不可**」的分离策略。

## 3. 不可妥协的原则

1. **无语料不回答**。没有可核验依据时，输出「依据不足」，**不得**退回模型参数内知识补写。
2. **引用先于结论**。回答中的每条实质断言都必须绑定一条可核验引用，否则不予交付。
3. **过滤早于生成**。版本过滤、角色过滤必须在内容进入 prompt **之前**完成。
4. **不進 prompt 即不泄露**。泄题防护靠「不进上下文」，不靠「要求模型别说」。
5. **逐字引文不可省**。只给页码不给原文的引用不可核对，等同装饰。
6. **准入 fail-closed**。未校验语料不可检索；配置缺失拒绝启动而非取默认值。
7. **判据只增不减**。接地判定只能变严；任何放宽都需走变更流程 + 外部抽检。
8. **租户上下文不可信**。`tenant_id` 只取自认证上下文，RLS 以会话变量为准。

## 4. 与主平台的技术边界

| 关注点 | 归属 | 说明 |
|---|---|---|
| Agent 执行、Run 生命周期、审批、预算 | `platform/` | RAG 不重复实现 |
| 模型调用（生成/嵌入/蕴含判定） | `platform/` 的 `ModelGateway` | RAG 通过端口使用，不自建 SDK 通道 |
| 语料、索引、检索、引用 | `rag/` | 本项目 |
| 检索的触发与结果消费 | 双方 | RAG 提供 Tool SPI 实现；platform 负责授权、预算、审计 |
| 引用完整性校验 | `rag/`（判定）+ `platform/`（拒绝交付） | 判定在 RAG，交付闸门在 platform |
| 租户与身份 | `platform/` | RAG 只消费 `TenantContext`，不自建认证 |

> ⚠️ RAG **不引入第二套认证**。租户身份、权限、审计的权威源始终是 platform。
> 这条边界一旦模糊，就会出现两套权限体系（RAG 自己的 + platform 的），
> 而「两套权限」几乎必然产生一处遗漏。

## 5. 已完成的实测证据（2026-10-20）

> ⚠️ 本节只记录**实际执行过**的验证。计划中但未执行的项一律不写入此处。

| 验证项 | 方法 | 结果 |
|---|---|---|
| DDL 可在 PG 17 上执行 | 真实 PG 17.11 实例执行 V1 迁移 | ✅ 10 表 + 全部约束 + 10 条 RLS 策略创建成功 |
| 教材等级缺 ISBN 被拒 | `check_violation` 反证 | ✅ PASS |
| `VERIFIED` 缺校验证据被拒 | `check_violation` 反证 | ✅ PASS |
| 审计表 UPDATE/DELETE 被拒 | 触发器反证 | ✅ PASS |
| 自我先修关系被拒 | `check_violation` 反证 | ✅ PASS |
| 跨租户**读**隔离 | 非特权角色 `app_agent` | ✅ 租户 1 看不到租户 2 的来源 |
| 跨租户**写**隔离 | 非特权角色 `app_agent` | ✅ 跨租户 INSERT 被 RLS 拒绝 |
| 领域层零框架依赖 | `RagCorePurityTest` | ✅ 3 项全绿 |
| 核心不变式 | 单元测试 | ✅ **46 项全绿**（含 2 项反证） |

### 5.1 ⚠️ 实测发现：超级用户会绕过 RLS

验证 RLS 隔离时，用 `agent` 角色（**PostgreSQL 超级用户**）执行，
**租户 1 能看到租户 2 的数据**。改用非特权角色 `app_agent` 后隔离才生效。

> 这与主平台 `P1-D08` §3.6 记载的 **E-3 风险完全一致**：
> 「超级用户与 `BYPASSRLS` 角色会绕过所有策略，`FORCE ROW LEVEL SECURITY` 对它们无效」。

> ⚠️ **对本项目的强制约束**：
> 1. 生产连接**必须**使用 `NOSUPERUSER NOBYPASSRLS` 角色；
> 2. 集成测试**必须**用非特权角色跑（主平台 `TenantSessionBinderIT` 同纪律）；
> 3. 应用启动时**自检**当前连接角色是否为特权角色，是则拒绝启动——
>    主平台 P4-D03 记录过「启动不校验 broker 可达致静默积压」这一类
>    「表面正常、实际失效」的缺陷，RAG 不得重蹈。

### 5.2 ⚠️ 实测发现：官方 `postgres:17` 镜像不含 pgvector

执行 `CREATE EXTENSION vector` 失败：
`pg_available_extensions` 中无 `vector` 条目。

> 部署影响：生产与 CI 必须使用 `pgvector/pgvector:pg17` 镜像，
> 或在基础镜像上安装 pgvector 扩展。**不可假设 `postgres:17` 自带扩展。**
> 见 RAG-D02 §3.1 部署要求。
