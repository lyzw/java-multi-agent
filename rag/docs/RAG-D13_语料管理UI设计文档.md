## 文档说明

> 本文档是 RAG-D12 的用户界面承接：RAG-D12 从**业务流程**层面给出了简化后的
> 写面（语料入库）、读面（检索→生成）、治理面（审核/抽检）设计；

> 而是收敛为「任务三态 + 单进度条」，把用户的注意力还给"内容对不对"这一件事。

## 一、设计目标与设计原则

### 1.1 设计目标

围绕 RAG-D12 的三面（写面 / 读面 / 治理面）与四域（录入与校对 / 审核 / 规则配置 / 运维），
本模块要达成的体验目标如下：

| # | 目标 | 说明 | 对应 RAG-D12 |
|---|---|---|---|
| G-1 | **能力分层可见** | 三面各自有清晰入口，用户进入后知道自己"在录入、在审核、还是在看任务" | §1.1 三面全景 |
| G-2 | **进度语言统一为三态** | 摄取任务/来源/载体/片段统一用「三态/四态」表达，消除五阶段 + 双状态线的心智负担 | §3.2、靶点 A/G |
| G-3 | **召回可解释、分数可读** | 抽检与质检页直接展示"这条为什么被召回"（通道＋分数＋命中原因），且分数只有**一个** `relevance` 值 | §3.3、靶点 C/E |
| G-4 | **泄题风险显性化** | 答案类角色在界面上用稳定警示色高亮，让"可能泄题"这件事不靠记忆，靠视觉 | 靶点 D |
| G-5 | **不接调用点的能力不出现** | 界面只暴露"确定性两查（存在性＋角色）"等真正生效的能力，占位/NLI 逻辑不进 UI | §3.4、靶点 F |

### 1.2 设计原则

| 原则 | 内涵 | 对界面的约束 |
|---|---|---|
| **PU-1 单一真源可视化** | 过滤规则、分数量纲、状态模型各只存在一份 | 同一事实在任意页面展示口径一致：`relevance` 只有一个值、状态只有一套枚举 |
| **PU-2 先看内容，再看状态** | 用户的第一动作是"核对内容对不对"，状态是辅助 | 页面主区始终是"内容/片段/依据"，状态在侧栏或角标 |
| **PU-3 fail-closed 可见** | 被过滤、被撤回、被门禁拦截都是**合法且可见**的结果 | 灰态/空态不是空白，而是带原因的说明（"答案类内容已按策略排除"，而非静默空列表） |
| **PU-4 术语与领域一致** | 界面用语与 `rag-core` 枚举同源 | 角色、模式、版本范围、治理状态直接用枚举名 + 中文别名，不自造新词 |
| **PU-5 按角色分域、按任务分流** | 不同职责入口互不干扰 | 侧边栏按四域分区；Dashboard 按角色给"下一步该做什么" |
| **PU-6 状态少而稳** | 状态枚举收敛，少即多 | 任务三态、治理四态、返回三态，全站仅此三套 |

## 二、信息架构

### 2.1 导航结构

依据 RAG-D12 §3.5「单控制器 → 按角色分域」，侧边栏按**四个治理域**分区，
顶部加一个**总览**。这是"过分复杂"靶点 G（34 端点单控制器）在导航层的消解：

```text
RAG 语料管理
│
├── ① 总览（Dashboard）
│
├── ② 录入与校对域
│     ├── 来源登记
│     ├── 来源列表
│     ├── 载体上传与解析预览
│     └── 片段校对
│
├── ③ 审核域
│     ├── 校验决定
│     ├── 抽检队列
│     └── 召回解释（质检）
│
├── ④ 规则配置域
│     ├── 审核员名录（ReviewerRoster）
│     ├── 知识点别名（kp-alias）
│     └── 字典（dictionary）
│
└── ⑤ 运维域
      ├── 摄取任务
      └── 重索引（索引代际 / 蓝绿）
```

> 域的划分与 RAG-D12 §3.5 一一对应：来源/载体/片段归「录入与校对」，
> 校验/抽检归「审核」，审核员/字典归「规则配置」，任务/重索引归「运维」。

### 2.2 页面层级与模块划分

| 层级 | 页面 | 承载的业务面 | 核心用户 |
|---|---|---|---|
| L0 总览 | Dashboard | 三面健康度一览 | 全角色 |
| L1 录入与校对 | 来源登记 / 来源列表 / 载体上传与解析预览 / 片段校对 | **写面**（语料入库）前半段 | 录入员、校对员 |
| L1 审核 | 校验决定 / 抽检队列 / 召回解释（质检） | **治理面** + **读面**（检索质检） | 审核员、质检员 |
| L1 规则配置 | 审核员名录 / 知识点别名 / 字典 | 治理面支撑 | 管理员 |
| L1 运维 | 摄取任务 / 重索引 | **写面**（语料入库）后半段 + 索引代际 | 运维 |
| L2 详情 | 来源详情 / 载体详情 / 片段详情 | 各域的纵深查看 | 对应角色 |

### 2.3 角色与权限视图

| 角色 | 可进入的域 | 默认落地页 | 与 RAG-D02 §5 访问模型一致 |
|---|---|---|---|
| 录入员 | 录入与校对（登记/上传） | 载体上传与解析预览 | 登记/提交语料，不直接改校验状态 |
| 校对员 | 录入与校对（片段校对） | 片段校对 | 角色纠错，不决定 VERIFY/REVOKE |
| 审核员 | 审核域（校验决定/抽检） | 抽检队列 | 校验状态、权威等级、撤回 |
| 质检员 | 审核域（召回解释） | 召回解释（质检） | 检索口径与转operational质量的核对 |
| 运维 | 运维域 | 摄取任务 | 任务重试、重索引 |
| 管理员 | 全部 | Dashboard | 规则配置 + 全域只读 |

## 三、关键页面规划

> 每个页面按「用途 / 主要区域布局 / 核心操作」三栏描述。
> 区域布局以文字分区 + 低保证线框辅助说明，不含视觉稿。

### 3.1 总览（Dashboard）

- **用途**：一屏看到三面的健康度，并按角色给出"下一步该做什么"，把流量引向正确的域。
- **主要区域布局**：

```text
┌────────────────────────────────────────────────────────────┐
│  顶部：模块名 + 当前角色 + 租户/作用域指示                      │
├────────────────────────────────────────────────────────────┤
│  KPI 行（5 卡）：待校对片段数 / 待审核来源数 / 进行中任务数     │
│                / 门禁触发率(依据不足) / 答案类抑制数           │
├──────────────────────────────┬─────────────────────────────┤
│  左：四域入口卡（录入/审核/    │  右：近期待处理事项流           │
│       规则/运维，带未办数）    │      （抽检待办/任务失败/召回异常）│
├──────────────────────────────┴─────────────────────────────┤
│  底部：最近摄取任务三态 + 最近抽检异常 Top N                    │
└────────────────────────────────────────────────────────────┘
```

- **核心操作**：点击域入口卡跳转；点击待办流条目直达对应详情；KPI 卡支持下钻到筛选后的列表。
- **设计要点**：KPI「门禁触发率」把 RAG-D12 的"依据不足是合法输出"这一理念量化为可见指标，
  让"拒答"成为管理者可观察的行为，而非被掩盖的失败。

### 3.2 录入与校对域

#### 3.2.1 来源登记

- **用途**：录入员登记一个新**来源（Source，作品级）**，录入**版本五轴**、权威等级与版权状态。
- **主要区域布局**：

```text
┌────────────────────────────────────────────────┐
│  表单区（分节）：                                  │
│   ① 基本信息：书名/出版信息                        │
│   ② 版本五轴：学科·年级·册次·出版社·版次（必填，缺一不可入库）│
│   ③ 授权与权威：权威等级(TrustTier) + 版权状态(license_status)│
│   ④ 对象存储引用：上传教材正文 PDF                   │
├────────────────────────────────────────────────┤
│  右侧说明卡：五轴缺失的后果 / 权威等级对"可被检索"的影响 │
└────────────────────────────────────────────────┘
```

- **核心操作**：登记（`POST /sources`）；批量登记（`POST /sources/batch`）；保存后进入"待校验"。
- **设计要点**：**版本五轴缺一不可入库**（RAG-D00 RD-03）在表单上以"五轴完整性提示"呈现，
  任一轴为空即无法提交并给出原因。

#### 3.2.2 来源列表

- **用途**：浏览/筛选全部来源，快速定位治理状态。
- **主要区域布局**：

```text
┌────────────────────────────────────────────────┐
│  筛选栏：治理状态 / 学科 / 年级 / 权威等级 / 版权状态  │
├────────────────────────────────────────────────┤
│  来源表格（列：名称 · 五轴 · 权威等级 · 载体数 ·       │
│           校验状态 · 生命周期时间线）                  │
├────────────────────────────────────────────────┤
│  行操作：进入详情 / 发起校验 / 查看载体               │
└────────────────────────────────────────────────┘
```

- **核心操作**：筛选；进入来源详情；发起校验决定（跳转 §3.3.1）。
- **设计要点**：治理状态用统一四态徽标（见 §4.6），来源行内直接显示生命周期时间线，
  不再要求用户去多个页面拼状态。

#### 3.2.3 载体上传与解析预览（重点页面）

- **用途**：上传一个**载体（Document，PDF 级）**，实时看到**解析预览**——切片结果、角色着色、页码/题号，
  确认无误后才提交入库。这是 RAG-D12 §4.2「写面交互聚焦人而非状态机」的核心落地页。
- **主要区域布局**：

```text
┌───────────────────────────────┬─────────────────────────────────┐
│  左列（约 1/3）                 │  右列（约 2/3，主区）             │
│  ① 上传区：拖拽 PDF / 补传       │  ③ 解析预览：                    │
│  ② 载体元数据：标题 + 版本五轴   │     片段列表（按页顺序）           │
│  ③ 任务三态进度条（见 §4.2）     │     每条：文本摘录 + 角色着色标签   │
│      SUBMITTED→PROCESSING      │            + 页码 + 题号 + 章节路径 │
│      →READY/FAILED             │  ④ 侧栏：角色统计 + 噪声丢弃统计      │
│  ④ 提交入库按钮（仅预览确认后亮起）│                                 │
└───────────────────────────────┴─────────────────────────────────┘
```

- **核心操作**：上传 → 查看解析预览 → 逐条确认/纠错 → 提交入库。
- **设计要点**：
  1. **先看内容、再看状态**（PU-2）：主区是片段列表，任务进度只在左列一条进度条，不含"解析/切分/嵌入/索引"四节点；
  2. **角色着色**（见 §4.1）：答案类片段（`EXAMPLE_SOLUTION` / `EXERCISE_ANSWER`）红色高亮，
     录入员第一眼就能发现"答案区被误并入正文"的泄题风险；
  3. 空白/噪声块（`BOILERPLATE`）显示为"已丢弃"灰态，符合 RAG-D12 §1.1 中"空白文本块直接丢弃"的实现口径。

#### 3.2.4 片段校对

- **用途**：校对员对已入库/待入库片段的**角色**进行纠错，重点处理"疑似答案区误判"的高亮项。
- **主要区域布局**：

```text
┌───────────────────────────────┬─────────────────────────────────┐
│  左：片段列表                  │  右：片段详情                     │
│    （按角色分组，答案类置顶）    │     ① 原文（逐字，不可编辑）        │
│    （筛选：仅看疑似误判 / 全部） │     ② 版面事实：答案区标识 inAnswerZone│
│                               │        + 题号 + 块类型(BlockType) │
│                               │     ③ 角色重判操作区               │
└───────────────────────────────┴─────────────────────────────────┘
```

- **核心操作**：一键纠错（如将误判为 `EXPLANATION` 的答案重判为 `EXERCISE_ANSWER`）；标记为 `BOILERPLATE`（噪声丢弃）；批量重判。
- **设计要点**：角色判定**只基于版面事实**（RAG-D12 §1.1 步骤3），详情区因此同时展示原文与版面事实，
  让校对员"看懂系统为什么这么判"，而不是只给一个角色标签——这是把判定规则"翻译"给用户。

### 3.3 审核域

#### 3.3.1 校验决定

- **用途**：审核员对来源/载体做 `VERIFIED` / `REVOKED` 决定，并维护权威等级与撤回。
- **主要区域布局**：

```text
┌────────────────────────────────────────────────┐
│  来源/载体详情：权威等级 · 版权状态 · 校验历史 · 片段预览 │
├────────────────────────────────────────────────┤
│  校验决定区：                                     │
│    VERIFIED（须填校验证据） / REVOKED（须填撤回原因）│
│    + 权威等级调整 + 有效期(ver_valid_days)          │
├────────────────────────────────────────────────┤
│  审计流：本来源全部校验/撤回动作留痕                   │
└────────────────────────────────────────────────┘
```

- **核心操作**：校验决定（`POST /sources/{id}/verification`、`POST /documents/{id}/verification`）；撤回。
- **设计要点**：`VERIFIED` 需填「校验证据」、`REVOKED` 需填「撤回原因」——对应 fail-closed 理念，
  审查动作不能"无痕一句话"。撤回后的内容在后续检索/质检页统一显示为"已下架，不可检索"。

#### 3.3.2 抽检队列

- **用途**：审核员对已入库片段做人工抽检，看到**召回解释**（这条为什么被召回）。
- **主要区域布局**：

```text
┌────────────────────────────────────────────────┐
│  顶部：抽检任务队列（随机样本 / 按角色过滤 / 按权威等级） │
├────────────────────────────────────────────────┤
│  抽检片段详情：                                   │
│     ① 原文 + 角色着色 + 页码/题号/章节路径            │
│     ② 召回解释卡：通道(RetrievalChannel) + 分数(relevance)│
│        + 命中原因(HitReason)                      │
│     ③ 判定操作：通过 / 驳回（驳回须填理由）             │
└────────────────────────────────────────────────┘
```

- **核心操作**：通过；驳回（记录 `InspectionRecord`）；跳转片段详情。
- **设计要点**：这是 RAG-D12 §4.3「抽检面板」的落地——审核员看的是"召回解释"而非内部管线日志，
  "通道＋分数＋命中原因"三者齐备，让"这条为什么会出现在学生答案里"可被人工核对。

#### 3.3.3 召回解释（质检页，读面的管理端承载）

- **用途**：质检员模拟一次检索，验证"某条查询会召回什么、为什么、是否触发门禁"。
  这是 RAG-D12 §4.1 读面 `ask_textbook` 单一契约在管理端的**调试视图**。
- **主要区域布局**：

```text
┌────────────────────────────────────────────────┐
│  ① 查询输入区：question + student_context          │
│             （学科/年级/册次/出版社/版次 + 意图 intent）│
│              【执行检索】                          │
├────────────────────────────────────────────────┤
│  ② 检索摘要：过滤前候选数 → 过滤后命中数              │
│              + 门禁状态（通过 / 依据不足）+ relevance 阈值刻度│
├────────────────────────────────────────────────┤
│  ③ 命中片段列表（每条带：relevance 值 + 通道 + 命中原因  │
│                    + 角色着色 + 版本标记）             │
│     空态：显示"未在已授权语料中找到依据"，非空白          │
└────────────────────────────────────────────────┘
```

- **核心操作**：输入 `student_context` + `question` 执行检索；查看命中解释；切换 `intent` 复现不同模式效果。
- **设计要点**：
  1. **单分数量纲可视化**（靶点 C）：每条命中只展示**一个 `relevance`**（0~1），配一条带 0.38 阈值的刻度线，
     对齐 RAG-D12 §3.3"排序与门禁同源同一个数"；
  2. **过滤前后数量**（靶点 D）：把 RAG-D12 §4.3"诊断是召回不足还是过滤过严"落成一等指标；
  3. **空态即合法结果**（PU-3）：门禁拦截时展示"依据不足"原因，而不是空白命中列表。

### 3.4 规则配置域

#### 3.4.1 审核员名录（ReviewerRoster） / 知识点别名（kp-alias） / 字典（dictionary）

- **用途**：三张配置表的增删改查，承载治理面的"支撑数据"。
- **主要区域布局**：统一为「左列表 + 右编辑/新建」或「表格 + 行内编辑」两段式，不引入额外复杂形态。
- **核心操作**：
  - 审核员名录：增删审核员、分配审核范围（对应 `ReviewerRosterEntry`）；
  - 知识点别名：维护知识点别名（`POST/GET/DELETE /kp-aliases`）；
  - 字典：维护条目（`GET/POST/DELETE /dictionaries/{type}/entries`）。
- **设计要点**：三者归入一个域但**各自独立页面**，避免在单控制器里混杂；每张表都是"列表 + 编辑"的简单形态。

### 3.5 运维域

#### 3.5.1 摄取任务

- **用途**：查看语料入库任务的**三态**，并对失败任务重试。承载 RAG-D12 §3.2 的写路径改造成果。
- **主要区域布局**：

```text
┌────────────────────────────────────────────────┐
│  筛选栏：任务状态（SUBMITTED / PROCESSING / READY / FAILED）│
├────────────────────────────────────────────────┤
│  任务列表（列：来源/载体 · 任务三态 · 进度条 0-100% · 失败原因）│
├────────────────────────────────────────────────┤
│  行操作：重试（FAILED）/ 查看失败详情（error_detail）       │
└────────────────────────────────────────────────┘
```

- **核心操作**：重试（`POST /ingest-jobs/{id}/retry`）；查看失败详情。
- **设计要点**：**只展示三态 + 单进度条**，不再暴露"解析/切分/嵌入/索引"四节点——这是靶点 A（五阶段状态机）在界面上的直接消解。
  失败详情展示 `error_detail` 全文，让"整册失败、可能残留部分片段"这类原因可直接复制给运维。

#### 3.5.2 重索引（索引代际 / 蓝绿）

- **用途**：换嵌入模型时的**索引代际**管理与蓝绿切换，运维不感知向量列迁移细节。
- **主要区域布局**：

```text
┌────────────────────────────────────────────────┐
│  索引代际列表（列：代际名 · 嵌入模型 modelVersion · 维度 │
│               · 片段数 · 状态（蓝/绿/构建中））         │
├────────────────────────────────────────────────┤
│  操作：新建代际 / 切换（蓝绿）/ 回滚                   │
└────────────────────────────────────────────────┘
```

- **核心操作**：新建代际；切换；回滚。
- **设计要点**：交互语言用"蓝绿切换"而非"迁向量列"，对齐 RAG-D12 §4.3，
  把底层机制（`rag_chunk_embedding` 向量列迁移）藏在代际卡片后面。

## 四、贯穿全流程的核心交互与状态

> 本节集中说明跨页面复用的一套交互与状态，保证全站口径一致（PU-1）。

### 4.1 角色着色体系

片段角色（`ChunkRole`，10 类）在**所有展示片段的页面**（解析预览、片段校对、抽检、召回解释）
统一用同一套色系与标签。色系按教学敏感度分组，而非逐类配色，便于一眼识别风险：

| 分组 | `ChunkRole` 成员 | 色系语义 | UI 呈现 |
|---|---|---|---|
| **答案类（敏感）** | `EXAMPLE_SOLUTION`、`EXERCISE_ANSWER` | 警示红 | 红色标签 + 文字左缘竖条，全站最醒目，提示"泄题风险" |
| **习题提示** | `EXERCISE_HINT` | 警示黄 | 黄色标签（介于题干与答案之间，讲解模式唯一可接受的答案类） |
| **题目/例题** | `EXERCISE`、`EXAMPLE` | 信息蓝 | 蓝色标签 |
| **可引用正文** | `EXPLANATION`、`APPENDIX`、`PAPER_BODY`、`PAPER_METHOD` | 成功绿 | 绿色标签（`citableAsExplanation` 为真） |
| **噪声（丢弃）** | `BOILERPLATE` | 中性灰 | 灰色标签，解析预览中显示为"已丢弃" |

> 角色着色是**泄题闸门可视化**的主角：同样的红色标签在任何页面出现，
> 都意味着"这条内容在讲解模式下会被检索期硬过滤掉"（RAG-D12 §1.1 ③④ 步）。

### 4.2 入库异步进度（三态）

承载 RAG-D12 §3.2「写路径五阶段状态机 → 三态任务」的全站统一进度语言：

| 状态 | 含义 | UI 呈现 |
|---|---|---|
| `SUBMITTED` | 已提交，等待处理 | 灰态竖条 + "已提交" |
| `PROCESSING` | 处理中 | 蓝色 + 单条进度条 `0–100%`（整数百分比，无内部阶段名） |
| `READY` | 入库成功 | 绿色 + "已就绪" |
| `FAILED` | 入库失败 | 红色 + 可展开的 `error_detail` 全文 + 「重试」按钮 |

- 进度"由任务状态派生"（RAG-D12 §3.2），载体 `parse_status` 不再作为独立可见状态；
- 用户在任何页面看到的都只有这**四枚徽标（其中三态 + 失败）**，概率一致。

### 4.3 单分数量纲与门禁可视化

承载 RAG-D12 §3.3「两套分数量纲 → 单一 relevance」：

- 全站凡展示检索质量分数，只用**一个 `relevance ∈ [0,1]`**，不再出现 `fusionScore`（RRF 值）；
- 命中条目旁配一条**带阈值刻度的迷你条**：0 到 1，阈值线固定在 `0.38`（RAG-D12/RAG-D05 标定值），
  命中点落在阈值线右侧为"通过门禁"，左侧为"将被判定依据不足"；
- 门禁结果作为**合法状态**呈现：`通过 / 依据不足（INSUFFICIENT）/ 已抑制（SUPPRESSED）` 三态（对应 RAG-D12 §4.1 返回三态）。

### 4.4 泄题闸门可视化

- 凡涉及"角色过滤"的结果展示，`EXAMPLE_SOLUTION` / `EXERCISE_ANSWER` 一律红色 + 「已按策略排除」标记；
- 管理端（运营视角）仍可看到这些片段（审核需要），但附「讲解模式下不进入 prompt」的固定说明；
- 结构化空态：当一次检索因答案类抑制而无结果时，展示"部分依据属于答案类内容，已按当前讲解策略排除"（PU-3），
  而非静默空白——对齐 `GroundedGenerationService.buildDisclaimer` 的语义。

### 4.5 审核与抽检流程

承载 RAG-D12 治理面，围绕「校验决定」与「抽检」两条动线：

```text
录入/上传 ──► PENDING ──► 审核员 VERIFIED ──► 可检索
                    │
                    └──► REVOKED ──► 不可检索（撤回）
     （校验/抽检/撤回全程落 rag_access_audit，逐动作留痕）

抽检：已入库样本 ──► 审核员查阅"召回解释" ──► 通过 / 驳回（驳回须填理由）
```

- 校验决定与抽检都**必须填理由**（校验证据 / 撤回原因 / 驳回理由），无痕操作不可提交；
- 抽检的"召回解释卡"与 §3.3.3 质检页复用同一套呈现，保证口径一致。

### 4.6 治理状态机

全站统一使用 RAG-D12 §3.5 的四态，取代原先分散的状态分支：

| 状态 | 徽标 | 可检索性 | 下一可动作 |
|---|---|---|---|
| `PENDING` | 灰 | 不可 | 校验 VERIFIED / 撤回 REVOKED |
| `VERIFIED` | 绿 | 可（条件：载体经校验、未撤回、版权非 RESTRICTED、有效期未过期） | 撤回 REVOKED |
| `REVOKED` | 红 | 不可 | 重新校验 |
| `FAILED` | 橙 | 不可 | 重试 / 修正后重提交 |

## 五、与「过分复杂」靶点（A–G）及新业务流程的对应关系

> 本节是本文档对 RAG-D12 §1.2 的直接应答：每一个靶点 → RAG-D12 给出的新设计 → 本 UI 如何简化或承载。

| 靶点 | 原复杂度（RAG-D12 §1.2） | 新业务流程（RAG-D12 §3） | UI 承载/简化方式 |
|---|---|---|---|
| **A** 写路径状态机过细 | `PARSING→CHUNKING→EMBEDDING→INDEXING→SUCCEEDED` 五阶段 + 载体双状态线 | 三态任务 `SUBMITTED/PROCESSING/READY\|FAILED` | §4.2 入库进度只用三态 + 单进度条；§3.5.1 摄取任务页不再有四个中间节点 |
| **B** 知识点补全执行两次 | 第②步与第⑤步重复补全，靠去重保幂等 | 一次"召回增强器"，只做一次 | §3.3.3 召回解释只展示最终一次融合结果，不暴露内部两次补全过程 |
| **C** 两套分数量纲并存 | `score` + `fusionScore`，门禁/排序各用一个 | 单一 `relevance`，排序与门禁同源 | §4.3 全站只用 `relevance` 一个值 + 单阈值刻度线，消灭 `fusionScore` |
| **D** 过滤规则四层重复 | SQL/端口/编排/生成各写一套，靠幂等约定 | 过滤谓词 `F` 进 SQL，单一真源 | §3.3.3 把"过滤前后数量"提为一等指标，规则效果可验证；§4.4 让被过滤内容显式可见 |
| **E** 两步式 API 外溢复杂度 | 调用方存 `hitIds` 回传 + 区分 400/200 双语义 | `ask_textbook` 单端点，服务端封两阶段 | §3.3.3 质检页"一个查询输入 → 一个结果"；§4.3 返回三态 `GROUNDED/INSUFFICIENT/SUPPRESSED` 取代 400/200 双语义 |
| **F** 能力"写了但不生效" | `GroundingService.verify` 零调用、占位 Port fail-closed | 移除或显式接入，只留"确定性两查" | UI 只暴露存在性校验 + 角色校验两个确定性结果；占位/NLI 不进入任何页面（G-5） |
| **G** 治理面过重 | 34 端点单控制器，状态/权限/审计交织 | 按角色四域分域，治理四态收敛 | §2.1 侧边栏四域分区 + Dashboard 分流；§4.6 全站统一四态徽标 |

**设计如何"简化"而非"隐藏"复杂度**：

1. 靶点 A/G 是**状态复杂度** → 用"状态语言统一"（三态/四态/返回三态）简化，不靠折叠面板藏细节；
2. 靶点 C/D 是**规则/分数复杂度** → 用"可视化单一真源"（一个 `relevance`、过滤前后数量、角色着色）把它转成可核对内容；
3. 靶点 B/E/F 是**流程/能力复杂度** → 用"流程一段式 + 不生效能力不出现"直接削减，而非在 UI 里堆更多开关。
