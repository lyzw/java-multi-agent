## 一、这条线从哪里来（问题 → 结论）

### 1.1 起点：RAG-D12 的诊断

改造前 `rag/` 子系统已相当完整（检索、入库、治理三条链路俱在），
但代码与问题记录暴露出**七个"过分复杂"靶点**：

| 靶点 | 一句话 | 本质 |
|---|---|---|
| **A** | 写路径 5 阶段状态机 + 载体双状态线 | 状态太多，用户只关心"能不能用" |
| **B** | 知识点补全执行两次 | 同源数据走两条路径 |
| **C** | `score` 与 `fusionScore` 两套量纲 | 门禁与排序不是一个数，极易混用 |
| **D** | 过滤规则在 SQL/端口/编排/生成**四层重复** | 同一规则复制而非收敛 |
| **E** | 两步式 API 把 `hitIds` 管理外溢给调用方 | 服务端该封装的没封装 |
| **F** | `GroundingService.verify` **零调用**、三个占位 Port、第三套检索栈死代码 | 写了但不生效 |
| **G** | 34 端点单控制器、5 个 Tab 混装 | 治理面过重 |

**核心结论**：
> 当前的复杂度不是"环节多"，而是**同一套规则在四层复制、一套门禁顶着两种分数量纲、
> 关键能力写了不接调用点**。

### 1.2 路线：D13 → D14 → D15 → D16~D20

```
RAG-D12  业务诊断  ──┐
RAG-D13  UI 设计     ├─ 设计层
RAG-D14  高保真视觉稿┘
        ↓
RAG-D15  视觉稿落地（13 页 + 前后端同步）
        ↓
RAG-D16~D20  逐项补齐后端缺口（6 项）
```

## 三、几个关键设计判断（值得记住的）

### 3.1 一致性优先于完整性

| 场景 | 做法 | 为什么 |
|---|---|---|
| 召回归因 | 放后端 `dominantDrop()` | 前端比较三个差值必然漂移；**诊断结论错比不显示更危险** |
| 门禁阈值 | 由 `RetrievalResult` 携带 | 界面另读配置 → "明明过线却被判依据不足" |
| 版面事实 | 存快照不重算 | 解析器升级后重算结果会变，抹掉历史 |
| 前缀判定 | `matchedSolutionPrefix` 与判定共用正则 | 两份正则 → 展示的判据与实际判定不符 |

### 3.2 fail-closed 与"不伪造"

| 场景 | 做法 |
|---|---|
| 五轴部分填写 | 直接 400（否则静默退化成默认坐标） |
| 版面事实缺失 | 显示"未采集"，**不显示"不在答案区"** |
| 漏斗/阈值旧后端缺失 | 显示"未返回"，**不编造数字** |
| 代际 BUILDING | 按钮置灰（只建一半的代际上线 = 部分片段永远召回不到） |
| 构建器写哪个代际 | 显式参数，**仓储层不猜** |

### 3.3 沿用的既有纪律（未破坏）

作用域显式声明（TENANT/PLATFORM）、治理票据、双人复核、抽检前置守卫、
职责分离（SoD）、RLS FORCE、平台档写走运维通道——全部原样保留。

## 五、剩余风险（按严重度）

| # | 风险 | 严重度 | 说明 |
|---|---|---|---|
| 1 | **两个迁移未在真实库执行过** | 🔴 高 | 09 改向量表主键，锁表时间未实测；**上线顺序颠倒会让所有检索报错** |
| 2 | **索引代际构建器同步执行** | 🟠 中 | 数万片段会阻塞数十分钟；无并发保护、无分布式锁 |
| 3 | **三个占位 Port 仍 fail-closed** | 🟠 中 | 解析器/嵌入/蕴含未接真实模型（RAG-07），检索质量结论不可用于生产 |
| 4 | **全局桶未纳入代际构建** | 🟡 中 | 构建器只处理租户桶 |
| 5 | **存量片段无版面事实** | 🟡 低 | 显示"未采集"；回填需重跑 ingestion |
| 6 | **退役代际未清理** | 🟡 低 | 持续占用存储 |
| 7 | **#6 dry-run 预览未做** | 🟢 低 | 现有"上传后看预览"已覆盖大部分场景 |

### 特别提示：上线顺序（不可颠倒）

```
1. 执行 09_v1_0_3_index_generation_alter.sql
2. 执行 10_v1_0_3_layout_facts_alter.sql
3. 部署应用
```

应用新增了 `AND e.index_generation = (...)` 与三列写入。
**表未迁移 → 检索报错 / 入库失败**。

## 七、一句话总结

> 这轮改造把 RAG 语料管理从**"1 页 5 Tab + 后端 34 端点 + 四层重复规则"**
> 收敛成**"13 页四域 + 单分数量纲 + 单一真源"**，
> 并补齐了 6 项后端缺口。
>
> **最大的收获不是页面变多了，而是每个复杂度都有了唯一归属**：
> 归因在后端、阈值在结果里、判据在快照里、代际在表里。
>
> **最大的风险也不是功能缺失，而是两个迁移脚本还没在真实库跑过。**

### 剩余的真正风险（未变）

**三个迁移脚本（09/10/11）仍未在真实库执行过。**

功能已全部闭环，但"能不能安全上线"与"功能是否完整"是两件事。
建议下一步不要再加功能，而是：

1. 测试库执行 09/10/11，实测锁表时间与回滚；
2. 代际切换端到端演练（创建 → 构建 → 切换 → 回滚）；
3. 全局桶通道（`rag_ops`）实测——单测覆盖不到会话窗行为。

### 最大的能力缺口（未变）

**三个占位 Port 仍未接入真实实现**（解析器 / 嵌入 / 蕴含）。
预览、检索、接地判定的**效果**都取决于它们——
当前所有质量结论都不能用于生产判断（RAG-07 已 fail-closed 化，但能力本身仍是占位）。
