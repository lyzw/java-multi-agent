## 一、完整 RAG 处理路径梳理

### 1.1 端到端环节全景

当前系统是 **"写面（语料入库）＋ 读面（检索→生成）＋ 治理面（审核/抽检）"** 三面，
共 **11 个模块**（`rag-core` / `rag-ports` / `rag-application` / `rag-infrastructure` / `rag-worker` / `rag-api` / `rag-bootstrap` / `rag-management`）。

#### 写面：语料入库（异步）

```
PDF → 解析器(Docling) → 结构化块序列 → 切分+角色判定 → 知识点挂接
    → 逐片段嵌入 → chunk+embedding 同事务落库 → jieba 分词回填 → 载体状态回写
```

具体实现链路（`IngestJobOrchestrator` → `IngestionPipeline`）：

| # | 环节 | 作用 | 衔接 | 实现 |
|---|---|---|---|---|
| 1 | 载体装载 | 从对象存储取原文字节 | 输入 | `IngestSourceView.load` |
| 2 | **解析** | PDF→版面块（标题层级/题号/答案区/字符偏移） | → 步骤3 | `DocumentParserPort.parse` |
| 3 | **切分+角色判定** | 结构优先、语义兜底；角色**基于版面事实**（不基于模型） | → 步骤4 | `IngestionPipeline.ingest` / `resolveRole` |
| 4 | 知识点挂接 | 确定性别名匹配（非模型抽取） | → 步骤5 | `matchKnowledgePoints` |
| 5 | **嵌入** | 逐片段、批量接口 3 次指数退避重试 | → 步骤6 | `embedWithRetry` |
| 6 | **原子落库** | `chunk` + `embedding` 同事务（防静默漏召回） | → 步骤7 | `saveChunkAndEmbedding` |
| 7 | 词法回填 | `jieba` 分词写入 `text_jieba` | → 步骤8 | `updateJiebaTokens` |
| 8 | 状态收口 | job 成功 + 载体 `parse_status=CHUNKED/FAILED` | 输出 | `markSucceeded` / `markDocumentParseStatus` |

#### 读面：检索 → 生成（同步 RPC）

`POST /retrieval`（七步编排）→ 平台侧生成 → `POST /retrieval/generate`（依据装配）。
这是**两步式 API**，每步各有独立编排。

**检索编排（`RetrievalOrchestrator.retrieve`，文档标注"顺序不可调换"）：**

```
① 知识点解析 → ② 多路召回(稠密+词法+知识点补全) → ③ 版本硬过滤 → ④ 角色硬过滤
            → ⑤ 知识点补全(再做一次) → ⑥ 排序+版本惩罚 → ⑦ 分数门禁
```

**生成装配（`GroundedGenerationService.generate`）：**

```
① UUID形态校验 → ② 依据取回(loadByIds) → ③ 存在性校验 → ④ 角色过滤 → ⑤ 版本过滤 → ⑥ 逐字装配
```

#### 治理面：管理控制台

`RagManagementController`（**2396 行、34 个端点**）：来源登记/批量登记/校验决定/元数据确认/载体上传/载体校验/片段查看/统计/抽检/审核员名录/知识点别名/字典/摄取任务/重索引。

### 1.2 "过分复杂"的具体所在

> 本节按"复杂度是否直接转化为缺陷 / 是否产出能力收益"为标准，定位出 **7 个真实靶点**，
> 每个靶点均给出代码或文档实证，避免"凭感觉判复杂"。

| # | 过分复杂之处 | 证据 | 后果 |
|---|---|---|---|
| **A** | **写路径状态机过细**：`PARSING→CHUNKING→EMBEDDING→INDEXING→SUCCEEDED` 五阶段，每阶段 `advance`＋`updateStage`（20 片写一次进度），并与载体 `parse_status` 形成**两条状态线** | `IngestJobOrchestrator` / `IngestJobStatus`；文档实测"载体状态从不回写→管理面恒 PENDING" | 状态越多越易漏写，出现"表面上成功、实际状态失真" |
| **B** | **读路径"知识点补全"执行两次**：第②步已 `addAll(findByKnowledgePoint + findPrerequisites)`，第⑤步又 `findByKnowledgePoint` 补 siblings，靠去重保幂等 | `RetrievalOrchestrator` 第 78–88 行 vs 第 102–114 行 | 逻辑重叠，同源数据走两条路径，增加漂移面 |
| **C** | **两套分数量纲并存**：`score`（相关性分，门禁用）＋`fusionScore`（RRF 排序分），门禁与排序不是一个数 | `ScoredChunk` 双字段；`RAG-D05 §6.0` 明确记录"混用废掉门禁"两次踩坑 | 复杂度直接转化为"语料再全也召不回"的静默缺陷 |
| **D** | **同一套过滤规则在四层重复实现**：SQL 谓词(`admissiblePredicate`＋版本角色) → 端口 `search()` 内部 → 编排器 ③④ 步 → 生成服务 ④⑤ 步，靠"幂等"约定而非结构保证 | `JdbcRetrievalRepository` 注释自认 + `RetrievalOrchestrator` + `GroundedGenerationService` | 规则漂移恰是文档自述"泄题闸门失效最常见的成因" |
| **E** | **两步式 API 把编排复杂度外溢给调用方**：platform 要先存 `hitIds` 再回传，还要区分 `MissingBasisException(400)` 与 `insufficient(200)` 两种语义 | `RagRetrievalController` 两端点；`GroundedGenerationService` 注释 | 组装/校验本可服务端封装，却让每个调用方重复实现 |
| **F** | **能力"写了但不生效"**：`GroundingService.verify` 五步闸门**零调用**；三个占位 Port（解析/嵌入/蕴含）fail-closed；`agent-infra` 存在**第三套检索栈死代码** | `问题记录/09-RAG与检索质量.md` RAG-07/09/10 | 复杂度堆叠但无能力收益，还制造"看似有防护"的假象 |
| **G** | **治理面过重**：34 端点单控制器，来源/载体/片段/抽检/审核员/字典/重索引全塞一处 | `RagManagementController` 行数 | 状态机＋权限＋审计在控制器层交织，改动一处波及全局 |

> **关键判断**：当前复杂度的**本质不是"环节多"，而是"同一件事在多层重复 + 一套规则两套分数量纲 + 能力未接调用点"**。
> 教辅 RAG 的领域特殊性（版本五轴、泄题闸门、逐字引用）是**真实且必要**的复杂度，
> 问题在于实现层把必要的规则**复制**而非**收敛**。

## 二、主流 RAG 服务对比

> 说明：以下为稳定行业认知，聚焦"流程设计/能力/差异"，不引具体版本号。
> 对比的目的不是选型替换，而是找到"复杂度应该安放在哪里"的参照系。

### 2.1 选型视角：两类产品

| 类别 | 代表 | 定位 |
|---|---|---|
| **编排框架**（给开发者拼装） | LangChain、LlamaIndex、Haystack | 提供检索/向量库/重排/提示的积木，流程自己搭 |
| **产品化平台**（给业务人员配置） | Dify、RAGFlow、FastGPT | 可视化知识库＋工作流，RAG 作为内置 pipeline |

### 2.2 逐项对比

| 维度 | **RAGFlow** | **Dify** | **FastGPT** | **Haystack** | **LlamaIndex / LangChain** |
|---|---|---|---|---|---|
| 核心主张 | **DeepDoc 深文档解析**，"garbage in garbage out"，把质量压在**解析/切分**前端 | **可视化编排**，RAG 是 Agent/Workflow 的一个节点，重产品化 | **知识库＋工作流＋问答**，国内 MVP 友好，数据集管理直观 | **显式 Pipeline**：`节点(组件)→连接`，检索/重排/生成/评估组件化 | **可编程框架**，索引与查询高度可定制 |
| 文档处理流程 | 解析(Docling 强化) → 模板化切分(General/QA/Manual/Table/Book/Paper等) → 自动选模板 | 上传 → 自动/自定义分段 → 清洗 → 索引 | 上传 → 分块(固定/QA/表格) → 索引 | 自定义 Retriever 前置处理 | 自定义 Reader → NodeParser → 索引 |
| 检索流程 | 混合检索(全文+向量)默认开启 → RRF 融合 → 重排(reranker) → 引用 | 向量/全文/混合可选 → 重排可选 → 召回测试页 | 混合检索 → 引用（重排可选） | BM25+dense HybridRetriever → Ranker → Reader | 检索器→节点后处理→重排→响应合成，全部可拆 |
| 门禁/"找不到" | 有**相似度阈值**，可配但不够结构化 | 有阈值，但"拒答"体验弱 | 阈值可配，依赖提示词兜底 | 由用户自建（无内置硬门禁语义） | 无内置，需自己写 |
| 引用溯源 | chunk 级引用、支持 **RAPTOR/知识图谱**补充 | 引用回显、支持多种向量库 | chunk 引用显式 | Retriever 返回 Document 带元数据可溯源 | 元数据贯穿，可自定义 citation |
| 权限/多租户 | 用户/团队/文档访问控制 | 应用级＋workspace，多租户较成熟 | 团队＋数据集权限 | 无内置底层的多租户，需自建 | 无内置，需自建 |
| 与业务的耦合方式 | API + 知识库内置工作流 | **Agent 编排内嵌 RAG**，低代码 | 低代码知识库 App + 工作流 | **代码集成**（Python 库，DRY pipeline） | 代码集成 |
| 定位差异 | **把"语料质量"当第一性**，重文档理解 | **把"应用编排"当第一性**，RAG 是能力之一 | **把"快速上线问答"当第一性** | **把"可测可复现的检索管线"当第一性** | **把"灵活与可控"当第一性** |

### 2.3 关键差异归纳（与本项目相关的三点）

1. **复杂度的安放位置不同**：RAGFlow 把复杂度前置到**解析/切分**（DeepDoc＋模板化），换取检索侧的简单；Haystack 用**显式 pipeline**把多步检索线性化、可测试；而本项目当前的复杂度**散落在四层**（SQL/端口/编排/生成），没有收敛到单一权威层。
2. **"拒答"能力的分野**：主流产品几乎都不把"依据不足＝合法输出"做成**硬门禁**（多是阈值＋提示词兜底）；本项目把"分数门禁"列为**第一性**（`RD-11`，无语料不回答），这是教辅/防幻觉场景的**合理差异化**，但实现上被"两套分数量纲"拖累。
3. **重排(reranker)的共识**：RAGFlow/Haystack 都把 cross-encoder reranker 作为**默认/一等环节**；本项目选型已定 `bge-reranker-v2-m3` 但**尚未接入**，导致只能靠"双量纲分数＋手工阈值"硬撑，这是"过分复杂"的**根因之一**——不是设计错了，而是关键组件缺位逼出了补丁式复杂度。

## 三、重新设计的 RAG 业务流程

> 原则：**收敛单一真源、一段式管线、单分数量纲、能力不接调用点就移除**。
> 本节逐条给出"原 → 新"的对照，并标注各自消解了 §1.2 中的哪一项靶点（A–G）。

### 3.1 设计原则

| 原则 | 含义 | 对应靶点 |
|---|---|---|
| 收敛单一真源 | 过滤规则、角色规则、分数量纲各自只存在一份 | D、C |
| 一段式管线 | 单端点内封装两阶段，调用方不再接触中间态 | E |
| 单分数量纲 | 排序与门禁用同一个 `relevance` | C |
| 能力不接调用点就移除 | 未接入的校验/占位 Port 或删或显式降级 | F |

### 3.2 写路径：五阶段状态机 → 三态任务

```
原：PENDING → PARSING → CHUNKING → EMBEDDING → INDEXING → SUCCEEDED（两状态线）
新：SUBMITTED → PROCESSING → READY / FAILED（进度是日志，不是状态）
```

| 优化点 | 原 | 新 |
|---|---|---|
| 状态 | 5 阶段＋载体 2 状态并行 | **3 态**：`SUBMITTED/PROCESSING/READY\|FAILED`；内部阶段降级为 `progress 0–100%` 只写日志/进度字段 |
| 嵌入 | 逐片段调用批量接口＋3 次退避 | **真批量**：一次 128 片，块级重试而非片段级 |
| 落库 | 逐条 `saveChunkAndEmbedding` | 批量事务（`chunk`+`embedding` 仍同事务，但一个载体一个事务） |
| 状态收口 | 双状态线易漏写 | **单一任务状态**，载体 `parse_status` 由任务状态派生（不再独立手工写） |

> 本改造直接消解靶点 **A**（状态机过细）与 **G** 中"状态线交织"的部分。

### 3.3 读路径：七步＋两步式 → 四步一段式

**统一为一个端点，服务端内部封装两阶段，调用方不再接触 `hitIds`：**

```
RAG.ask(student_context + question)
  └─ 1) 解析过滤上下文  →  2) 召回(SQL内完成全部硬过滤)  →  3) 重排+门禁  →  4) 组装交付
```

| 步 | 新设计 | 消解的原靶点 |
|---|---|---|
| **1. 上下文解析** | 调用方只传 `student_context`（学段/学科/教材版本/意图 intent），服务端解析出过滤谓词 `F`（版本+角色+权威+撤回） | 原 ①② 前置步骤 |
| **2. 召回（硬过滤进 SQL）** | 稠密+词法融合，**版本/角色/权威/撤回/RESTRICTED 全部在 SQL 谓词 F 内完成**（fail-closed，非法内容不进内存）；知识点补全/先修扩展降级为**可选"召回增强器"**，只做一次 | 原 ③④⑤ 及过滤四层重复（D、B） |
| **3. 重排 + 门禁** | 引入 reranker（`bge-reranker-v2-m3`），产出**唯一** `relevance ∈ [0,1]`，**排序与门禁同源同一个数**；`relevance < threshold → 返回"依据不足"` | 原 ⑥⑦ 及双分数量纲（C） |
| **4. 组装交付** | 内部完成：依据取回 → 存在性校验 → 角色复核 → 逐字装配 → 带引用返回 | 原两步式 API（E） |

**关键简化——分数量纲合并：**

```
原：召回器给 score(相关性)  + fusionScore(RRF排序)   ← 两个数，门禁/排序各用各的
新：RRF 仅在"召回模块内部"合并候选 → 合并后立刻用 reranker 归一 → 只对外暴露 relevance
```

> 本改造直接消解靶点 **B、C、D、E**，是把读路径"变薄"的枢纽。

### 3.4 接地校验：五步闸门 → "确定性两查＋可选 NLI"

| 原 | 新 |
|---|---|
| 五步（存在性→角色→冲突→蕴含→裁决），`GroundingService.verify` **零调用** | 保留**存在性校验＋角色校验**两个确定性检查并**接入调用点**（真正有效且零模型依赖）；NLI 蕴含/冲突检测改为**显式启用的可选能力**，未选配时**不创建、不默认放行**（删除占位 `return true` 语义） |

> 本改造直接消解靶点 **F**——把"写了但不生效"的能力收敛为"要么接入、要么移除"。

### 3.5 治理面：单控制器 → 按角色分域

- 来源/载体/片段 → **"录入与校对"域**；校验/抽检 → **"审核"域**；审核员/字典 → **"规则配置"域**；任务/重索引 → **"运维"域**。
- 治理状态机收敛为**四个可观测状态**：`PENDING → VERIFIED → REVOKED`（＋`FAILED`），与读路径的口径一致（不再是"控制器 29 个状态分支＋RLS＋审计"交织）。

> 本改造直接消解靶点 **G**（治理面过重、状态分支交织）。

## 四、新流程下的业务交互设计

### 4.1 读面：与主平台（Agent）的交互

**单一工具契约（替代现有 `search_knowledge_base`＋两步 RPC）：**

```jsonc
// 调用（platform → rag）
{
  "tool": "ask_textbook",
  "student_context": {
    "grade": "七年级", "subject": "数学", "term": "上册",
    "publisher": "人教版", "revision": "2024修订",
    "intent": "EXPLAIN"        // EXPLAIN | SOLVE | VERIFY | OVERVIEW
  },
  "question": "二次函数的顶点怎么求"
}

// 返回（rag → platform，三种稳定形态）
{ "status": "GROUNDED",   "answer": "...", "citations": [ { "chunkId", "locator", "verbatimQuote" } ] }
{ "status": "INSUFFICIENT", "reason": "未在已授权语料中找到依据" }
{ "status": "SUPPRESSED", "reason": "答案类内容已按讲解策略排除" }
```

- **交互要点**：
  1. platform 传**意图**而非让 rag 猜模式；
  2. `status` 用**三态枚举**取代 `400/200＋异常` 的双语义区分（缺失/不足/被策略排除各归其位）；
  3. 引用必须带 `verbatimQuote`（逐字引文），前端可直接渲染"翻书核对"。
- **前置约束不变**：`HallucinationDetector` 判据反转（M-1）仍是接入硬条件，但新契约把"正确引用"显式化为 `citations` 字段，使检测器改为**校验引用可核验**而非**禁止引用格式**。

### 4.2 写面：语料录入交互

> 聚焦"录入 → 校对 → 审核"三个角色视图设计交互，隐藏内部五阶段。

| 角色 | 视图 | 交互 |
|---|---|---|
| **录入员** | 来源登记 + 上传 | 上传后得到**实时解析预览**（切片结果、角色着色、页码/题号），确认无误才提交 |
| **校对员** | 片段预览 + 角色纠错 | 对"疑似答案区误判"高亮一键纠正；纠正即回到队列 |
| **审核员** | 抽检队列 | 看到的是**召回解释**（"这条为什么被召回：通道＋分数＋命中原因"），而非内部管线日志 |
| **任务视图** | `SUBMITTED→PROCESSING→READY/FAILED` | 只需进度条＋失败原因，不再展示解析/切分/嵌入/索引四个中间态 |

> 交互焦点从"看懂状态机"转为"看懂内容对不对"——这是对"过分复杂"最直接的业务化解。

### 4.3 质检与运维交互

- **抽检面板**：展示"过滤前后数量"（诊断"是召回不足还是过滤过严"），阈值 `relevance` 单一值直接可读。
- **运维面板**：摄取任务三态＋失败详情；重索引（换嵌入模型）以"索引代际＋蓝绿切换"对外表达，运维不感知向量列迁移细节。

### 4.4 与主流服务的对齐结论

新流程实质是**吸收 RAGFlow 的"质量前置"＋ Haystack 的"线性可测管线"＋本项目自有的"硬门禁/逐字引用"**：

- 复杂度**前移并收敛到解析-切分**（对应 RAGFlow），读路径变薄；
- 检索管线**线性化、单一分数量纲**（对应 Haystack），消灭四层重复；
- 保住并强化了主流产品普遍缺失的**"依据不足＝合法输出"硬门禁**——这是教辅/防幻觉场景的核心竞争力，只是之前被实现复杂度拖住了。

---

## 总结

**一句话总结**：当前的"过分复杂"不是环节多，而是**同一套规则在四层复制、一套门禁顶着两种分数量纲、关键能力写了不接调用点**；简化方案的本质是**收敛单一真源 + 一段式管线 + 单分数量纲 + 不生效的能力就移除**，同时把教辅领域真正必要的复杂度（版本五轴、泄题闸门、逐字引用）保留并让它落在正确的那一层。

**后续可展开的落地项**：

1. `RetrievalOrchestrator` 的代码级重构方案（七步 → 四步，移除重复补全与双分数量纲）。
2. `ask_textbook` 单一工具契约的接口级设计与 `student_context → 过滤谓词 F` 的映射表。
3. 写路径三态状态机的迁移脚本与 `rag_ingest_job` 字段变更。
4. reranker（`bge-reranker-v2-m3`）接入的分段计划与阈值重标定（依赖 `RAG-D08` 评测集）。
