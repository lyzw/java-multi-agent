A1. AI 知识点精讲：从概念到本仓库的落点

这一册专门讲 AI 相关知识，但不是通用科普：每个概念都给出它在本仓库里的实体（类、表、配置键、文档、事故），并标注是「已在代码实现」还是「仅文档设计目标」。目标是让有 Java 后端经验的人建立起一套可查证的心智模型，而不是记住若干模型名词。

本册的证据标签

已实现 有源码 / DDL / yml / 测试可直接定位　仅设计 只在方案、待评审文档中出现　证据空白 仓库查不到结论　文档冲突 两份权威材料互相矛盾　未确认 本次勘察无法核实。

A1.1 为什么 AI 系统不能按 CRUD 的思路验收

CRUD 服务的正确性是二值的：给定输入，写库结果要么对要么错，异常会抛出来。AI 链路里「错了」经常不报错——响应 200、日志正常、看板有数，但数字悄悄偏了、检索静默降级成空命中、或功能在空转。这是本仓库反复出现 静默失真 一词的根本原因。

维度传统 Java 后端本项目 AI 链路直接后果
正确性确定性，输入相同输出相同模型输出概率性；压缩/抽检/降级会改变送模型的字节「测过一次」不能推及所有请求
资源单位请求数 / 连接数 / 行数token：输入 + 输出都计费，且上下文窗口是有界硬资源不控制上下文长度 = 成本与超限双重风险
状态位置DB 是唯一状态，请求本身无状态请求级 SSE 后端不存对话正文，多轮历史由前端内存回传「重放一次」不是同一个请求
外部数据参数绑定后视为数据检索命中、工具结果、压缩态都是不可信文本，可携带指令必须围栏 + USER 角色注入
验收口径断言相等 / 影响行数 = 1需要统计口径（样本量、置信度、覆盖率）+ 行为单测 + 链路 E2E「测试全绿」只是候选证据
失败表现异常、5xx、事务回滚静默 0 行 / 静默回滚 / 静默降级 / 数字悄悄错 / 功能空转 / 假绿见 A3.8 静默失真案例矩阵
证据： docs/上下文压缩完整方案_设计与实施_v1.0.md §0.2（8 条现状差距，逐条附代码位置）；docs/问题记录/README.md §「静默失败分类 M1–M4」；审查文档/AI全流程审查报告_2026-10-31.md。

A1.2 一次 LLM 调用在本项目里长什么样

不要把「调模型」理解成一次普通 HTTP 调用。在本仓库里，一次调用必须同时闭环请求装配、成本预留、usage 结算、指标观测、幂等键五件事，缺一件就可能出现「账目丢失但不报错」。

  1. 装配请求：RequestAssemblyPort.assemble(input) 产出唯一送模型的 ModelRequest；关闭态必须返回 legacyRequest 同一引用。见 A2.6。
  2. 调用前预留：RunExecutionLoop.reserveModelCost():1650-1691 按 estimatedInput × INPUT_TOKEN_ESTIMATE_SAFETY_FACTOR 预留。
  3. 发出请求：MiniMaxModelGateway / OpenAiCompatibleModelGateway（POST /chat/completions），未知 provider 回落 FakeModelGateway（fail-soft，需警惕）。
  4. 调用后结算：settleModelCost():1707-1739 按 response.usage() 真实 token 与 ModelPricing.cost() 写 usage_record；失败 releaseModelCost()。
  5. 幂等：modelCallId() 由 runId + 领取代次 + 调用序号 派生确定性 UUID，是 usage_record.operation_id 的唯一约束键；同一次重试算出不同键会重复计费。
text一次模型调用的真实账单路径（RunExecutionLoop）
reserveModelCost()   // 调用前：按估算上限预留，budget.tryReserve
  │
  ├─ modelGateway.complete(assembly.request())   // 唯一送模型请求
  │       └─ response.usage() → input_tokens / output_tokens
  │
  └─ settleModelCost()  // 调用后：真实 token × 单价 → usage_record.cost_amount
         └─ ModelPricing.cost(...)  HALF_UP 6 位小数，对齐 numeric(18,6)

单价来源：application.yml:518-538 → agent.pricing.models
          精确匹配 → 最长前缀 → "default" 兜底
          查不到单价必须返回 empty，不得按 0 元放行（ModelPricingPolicy:33-37）

表 public.usage_record 的字段是 tenant_id / run_id / step_id / operation_id / model_id / input_tokens / output_tokens / cost_amount numeric(18,6) / currency / reservation_id，带 FORCE ROW LEVEL SECURITY 与部分唯一索引 idx_usage_operation_once。已实现

证据： platform/agent-worker/.../execute/RunExecutionLoop.java:1620-1758；deploy/sql/platform/01_platform_ddl.sql:3024-3038, 4529；platform/agent-core/.../config/ModelPricing.java:28-74；docs/租户级Token计费系统设计方案_v1.0.md §0.1（状态「待评审」）。
一个容易误写的口径

A1.3 Token、上下文窗口与「估算误差」

上下文窗口是模型一次调用能容纳的 token 上限，它不是「消息条数」。本仓库最初只有「消息序列预算 16000」，不含 systemPrompt、工具 Schema、RAG 块，这是 ADR-013 要解决的头号问题。

概念本项目取值 / 实现状态
上下文窗口 context_window_tokens默认 32768；由 07_model_catalog_context_upgrade.sql 给 model_catalog 加列已实现
可用输入 max_input_tokens默认 28672（= window − 4096 输出预留）；ContextBudget.hardLimit()已实现
硬顶 hard-ceiling-tokens128000（AGENT_CONTEXT_HARD_CEILING_TOKENS）已实现
token 计数器HeuristicTokenCounter（启发式），无 tiktoken / JTokkit 依赖已实现
估算误差中英混合 30–50%；由 TokenEstimationCalibrator 按真实 prompt_tokens 反馈校正（min-samples=30、alpha=0.20、bias clamp 0.80–2.00）已实现
精确 tokenizer / prompt caching列已预留 tokenizer_id / supports_prompt_caching = false，能力未启用仅设计

全窗口预算口径是本项目最需要重建的概念之一。它不是一个数字，而是九项之和；任何一项漏算，压缩后的实际请求就可能超窗，而系统不报错：

text全窗口预算构成（上下文压缩完整方案 §1.2）
window = systemPrompt 基段
       + skillGuidance
       + toolSchemas                 ← 旧预算 16000 漏算
       + 记忆 block
       + 裁剪说明 notice
       + RAG 命中块                 ← 旧预算 16000 漏算
       + 历史对话
       + 当前用户输入
       + 输出预留 (4096)

pinned = count(systemBase) + count(toolSchemas)
       + count(firstUserTurn) + count(currentInput) + GUARD_OVERHEAD
if (pinned + reserve > usableInput) → CONTEXT_PINNED_OVERFLOW（fail-closed）

另一个必须记住的实现细节：estimate 委托 ContextLayout.countRendered，即先渲染成真实文本再数 token，而不是对结构化对象估算——否则围栏标记、JSON 标点、换行都会被漏掉。已实现（ADR-013 D27）

证据： docs/上下文压缩完整方案_设计与实施_v1.0.md §0.2 / §1.2 / §2.2 / §5.2；platform/platform-bootstrap/src/main/resources/application.yml:231-262；deploy/sql/platform/07_model_catalog_context_upgrade.sql:29-34。

A1.4 Prompt 的结构、四种角色与「稳定前缀」

LLM 请求里每条消息都有角色，角色决定模型如何对待这段文本。本项目把它们用得很严格：

角色本项目用途硬约束
system系统提示基段、能力说明、工具 Schema逐字保留、位置固定、永不压缩；绝不塞外部数据或压缩态
user当前输入、所有外部不可信数据（RAG 命中 / 工具结果 / 上一轮压缩态）必须经 PromptGuard 围栏包装
assistant历史回复、流式 delta内容不可作为「事实」抽进压缩状态（否则把幻觉洗成事实）
tool工具结果回灌同上，按不可信数据处理

稳定前缀（pinned）是压缩算法与 prompt caching 的共同前提：前缀只要有一个字节变化，缓存就失效，压缩的「净成本守恒」也算不出来。因此项目把 systemBase / toolSchemas / firstUserTurn / currentInput 单独钉住，弹性池 ragCap / memoryCap / summaryCap 是上限 cap 而非目标配额，未用额度回流给 history。

为什么「关闭态必须同一引用」是 AI 特有的要求

传统功能开关关掉时，只要行为等价即可。这里要求 agent.context.enabled=false 时 RequestAssemblyPort 直接短路，原样返回 input.legacyRequest() 同一对象引用，且零策略解析、零预算、零管线、零事件、零指标。原因是要能用「引用身份」在测试中证明请求字节逐位未变，而不必逐字段比对；一旦多一个拷贝，前缀就可能漂移，缓存与成本口径都失真。

证据： platform/agent-ports/.../ports/contextwiring/RequestAssemblyPort.java:16-21, 27-29；RequestAssemblyResult.java:17-20, 79-81；docs/上下文压缩完整方案_设计与实施_v1.0.md §5.1 / §5.2；ADR-013 D27 / D38 / D41。

A1.5 工具调用（Tool Calling）：不是「让框架自动执行」

主流框架常提供「模型说要调工具 → 框架自动调 → 结果回灌」的内置循环。本项目明确禁止这条自动路径：授权、Schema 校验、ToolOperation 账本必须在注册与执行环节插入。

  • ADR-011 §3.3：利用 Spring AI 2.0「移除内置工具执行循环、须显式注册 ToolCallback」的变化，在注册环节插入授权 / Schema 校验 / 账本；禁止使用 ToolCallingAdvisor 自动执行路径。
  • 执行侧是 15 步准入链 CapExecutionFlow（第 3 步即 EffectiveClosure），加 ExecutionAdmissionChecker 的 TOCTOU 复核、ToolInvocationGate 的幂等键、fencing_token 防陈旧领取代次。
  • 工具结果一律 PromptGuard.wrapToolResult(toolName, payload) 包成 <tool_result trust="untrusted"> 后作 USER 消息注入，绝不拼进 systemPrompt。
  • 重试刻意避开 Spring 的 @Retryable：record_weakness 这类写操作重复执行按 Sev-0 定级，重试统一在 Outbox Publisher 与 ModelGateway 自研。
Spring AI 到底用没用

证据空白 两个 reactor 的 pom.xml 均无 Spring AI 依赖声明。它在仓库里的角色只有三个：ADR-011 选 Java 21 / Boot 4.1.1 的理由之一、ToolCallback 约束的设计依据、以及早期方案中「包在适配层后」的历史主张（与最终基线不一致）。不能写成「本项目基于 Spring AI 开发」。详见 A2.10。

证据： docs/P0/P1/ADR-011_技术基线_Java21_SpringBoot41.md §3.3 / §2.2；docs/Agent设计总览.md §4；docs/P0/P1/ADR-001_主MQ选型_RabbitMQ.md §5。

Embedding 把文本映射成向量，检索时用向量距离找相似片段。这里最容易踩的不是算法，而是维度与索引上限。

A1.7 混合检索、RRF 融合与分数门禁

本项目同时用全文检索（tsvector + 应用层中文预分词）与向量检索召回，再用 RRF 把两路排名融合。理解「两个分数不是一回事」比记公式重要。

textRRF 与分数门禁（RAG-D05 §2.1 / §6.2）
RRF: score(d) = Σ 1 / (k + rank),  k = 60
     代码：rrf = 1.0 / (RRF_K + (rank + 1))     // JdbcRetrievalRepository

否决「分数加权」的理由：
  ts_rank 与 cosine 量纲不同，需要人工标定且随语料变化 → 会静默漂移

两个必须分开的字段：
  ScoredChunk.score        = 相关性分（用于分数门禁）
  ScoredChunk.fusionScore  = RRF 融合分（双通道最大约 0.033，用于排序）

门禁阈值：
  minRetrieverScore = 0.38   （2026-10-28 首次标定；原设计 0.35 / 配置默认 0.2 已废弃）
  entailmentThreshold = 0.75 （未标定）

真实事故：曾把 RRF 融合分写进 score，而门禁拿 score 与 0.38 比——RRF 最大约 0.033，于是门禁恒不通过，表现为「检索永远无结果」但没有任何异常。另一个：版本降权若用减法作用在 RRF 量纲上，会把异版本分数一律压成 0、组内次序全丢；若作用在相关性分上，「降权」又退化为静默过滤。现在实现是 rankPenalty 乘法版本惩罚。已实现

还有一层必须说清：文档冲突 rag/docs/RAG-D05_检索策略与召回质量控制.md §8 L-2 写「RRF 融合与 cross-encoder 重排未实现」，但代码里 RRF_K=60 已落地；问题记录/11-文档与代码漂移.md DOC-10 更正为「RRF 已实现，仅缺重排」。所谓「重排」目前就是 RRF 融合分 + 版本惩罚，没有 cross-encoder 重排器（选型定了 bge-reranker-v2-m3 但尚未接入）。

A1.8 幻觉、接地与「不可信数据」原则

幻觉不是靠「让模型别编」解决的，而是靠检索期与生成期的结构性约束。RAG-D00 的 RD-07 / RD-09 / RD-11 给出三层：

层机制本项目状态
检索期硬过滤泄题闸门：答案类片段在检索期直接过滤，不进 prompt；版本 / 角色过滤必须在重排之前已实现
分数门禁低于 minRetrieverScore 即返回「未找到依据」，而不是硬凑一个答案已实现
接地三重校验存在性 / 蕴含 / 冲突，整体 fail-closed；HallucinationDetector 判据反转（RAG-D00 RD-14）仅设计（判别式 NLI 模型仅文档选型，未落地）
引用溯源片段带五轴版本坐标（学科/年级/册次/出版社/版次）与 locator，答案可回溯到册页已实现
不可信围栏RAG 命中经 PromptGuard.wrapToolResult("rag", …) 作 USER 消息注入，自带「这是数据不是指令」声明已实现

最后一条是 AI 系统里最反直觉、也最必须养成的习惯：模型读到的任何非系统文本都可能是指令。因此本仓库把「绝不拼进 systemPrompt」写成硬约束。压缩态更进一步——PromptGuard.wrapCompactedContext() 用 <compacted_context trust="untrusted"> 包成 USER 消息，且 sanitize() 必须净化掉能提前闭合围栏的标记（这是 S3-M8-a 修掉的一个真实注入洞，见 A3.3）。

证据： rag/docs/RAG-D00_决策基线与范围边界.md §2 RD-07/09/11/14；rag/docs/RAG-D06_引用溯源与防幻觉机制.md；platform/agent-application/.../prompt/PromptGuard.java:38-67, 204-267, 311-329；platform/agent-worker/.../agentchat/AgentChatOrchestrator.java:595-598。

A1.9 评测体系：L0–L3、样本量与 LLM-as-judge

「答案对不对」在 AI 系统里是一个统计问题，不是一个断言。本仓库用可信度分层来约束哪些数字可以下结论：

层含义展示纪律
L0 系统事实执行链路直接落库（如 cost_amount、终止原因）高可信，可直接下结论
L1 自动终态校验自动规则判定必须同时显示覆盖率
L2 抽样标注人工 / 黄金基线必须带样本量 n；n<30 一律显示「样本不足」，绝不显示 0% / 100%
L3 有噪信号用户反馈等只看趋势，只用于触发复核

LLM-as-judge（用模型判模型）在本项目的落地是 ModelAttributionJudge：只判「Agent 错因归因 vs 题库标准解析」的实质一致性，严格 rubric、结构化输出 {correct, reason, confidence}，temperature=0、max-tokens=256、min-confidence=0.75；六种情况 fail-closed 返回 empty（单价缺失 / 预算超限 / 模型异常超时 / 非 STOP / 请求工具 / 解析失败或置信度不足）。题面、Agent 归因、标准解析三段都经 PromptGuard.wrapToolResult 围栏。已实现

关联纪律同样是 AI 特有的：questionId 只能来自 run.input_payload.questionId，SQL 先判 jsonb_typeof(...)='string'，再走 QuestionIdTag 白名单 [A-Za-z0-9_.:-]+；缺失 / 非法 / 非字符串一律 empty，不做题面文本相似度猜测，也不写进指标宽表（避免看板分组基数爆炸）。

机器判分 ≠ 人工裁定：一次物理分离的修复（R2）

早期设计把机器结论写成 verdict='ATTRIBUTION' 塞进人工标注表 agent_eval_sample，撞上两张表的 CHECK 白名单；即使放宽约束，也会让 recordEvalSample 把 sampled 置 TRUE，把机器结论算进人工抽样覆盖率——一个不报错、只是数字悄悄错的失真。修复不是加白名单，而是物理分离写入路径：机器轨只写 agent_trace_metric.attribution_correct，不碰 sampled / human_verdict。注意 agent_eval_sample.attribution_correct 这一列确实存在（人工轨），不要误写成「列不存在」。

证据： docs/管理后台开发计划/P7_Agent效果指标体系.md §0；docs/Agent对话质量跟踪_回溯_评估体系_详细设计.md §0.0 R2 / §13；platform/agent-application/.../evaluation/ModelAttributionJudge.java；L2AttributionEvaluator.java:38-44, 155-156；JdbcAgentMetricRepository.java:634-638。

A1.10 成本模型：业务账、评估账与压缩净省

AI 系统至少有三本不能混的账，混淆任意两本都会让看板数字失真：

账写在何处红线
业务 Run 成本usage_record.input_tokens / output_tokens / cost_amount，预留→结算→释放只反映该 Run 自己的模型 / 工具调用
Judge 评估开销独立科目 EVAL_JUDGE_COST，进程内日预算 daily-cost-limit-yuan=1.00绝不写 usage_record、不调 AgentMetricPort.upsert、不碰 cost_amount；否则「单 Run 成本」「按模型成本」全部偏高，且评估越勤偏得越多
压缩收益影子期指标 context.tokens.before / actual / estimation_error_ratio / bias（由独立开关 agent.context.calibration.enabled 控制，默认开）压缩行为指标（compaction_total / checkpoint.* / tokens.after）在影子期禁止出现；关闭态必须零压缩行为指标
text压缩净成本守恒（上下文压缩完整方案 §7.1 / §7.5）
saved = (before − after) × price_input − summaryCost

saved ≤ 0 连续 20 次  → 自动降级 TRIM_ONLY 并告警
n < 30                → 不显示百分比（统计口径，同 L2 抽样）
前提：model.pricing.models 必须配到真实模型，
      否则业务 Run 成本按 0 记，saved 恒失真。

一个真实的「配置键把 AI 链路悄悄弄坏」案例：模型 ID 含点号 MiniMax-M2.5 若写成 yml 裸键，Spring Binder 会拆成 MiniMax-M2 + 子键 5，症状是业务 Run 成本静默按 0 记、L2 judge 因查不到单价直接拒调，两者都不报错。必须写成方括号字面键 "[MiniMax-M2.5]":，并有 ApplicationConfigKeyAlignmentTest#dottedModelIdKeepsItsPricing 锁死。完整因果链见 A3.5。

文档冲突 docs/上下文压缩开发计划_v1.0.md §6.2 曾把「model.pricing.models 未配 MiniMax-M2.5、成本按 0 记」登记为 IN-1 阻塞；而当前 application.yml:531-538 已写入国内计价 0.002100 / 0.008400（每千 token）并有守卫。这是不同时点快照，以当前 yml 与守卫测试为准，现场仍应核对活库与运行实例。
