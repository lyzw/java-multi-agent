A19. 能力缺口与增强路线：从「没有」到「该怎么补」

前十八册讲的是系统现在是什么样。这一册讲它还不是什么样，以及如果要补，该从哪下手。这不是一份愿望清单——每一条都基于前十八册已核实的证据，标注了「缺口在哪、为什么缺、补的时候要注意什么」。对 Java 后端转型者来说，这一册的价值在于：看懂一个系统的能力边界，比记住它的功能列表更重要，因为你要做的就是扩展它。

本册的定位与读法

如果你刚接手这个项目，先读 A19.8 的「第一周路线」；如果你要规划迭代，读 A19.2–A19.6 的缺口分级与优先级；如果你在做架构评审，A19.7 的「可复用增强模式」给出了每一次扩展都该遵守的形态。本册不代替项目排期——它只回答「技术上该注意什么」。

A19.1 引用式提示词库：一个「已定义但被明确拒绝」的缺口

这是本册最值得细讲的一条，因为它推翻了「Prompt 完全没有设计」这个粗略结论。真实状态是：契约里已定义，运行期明确拒绝执行。

javasystemPrompt 的三种结果（AgentModelConfigAssembler.java:320-370）
/**
 * 解析系统提示：读 cap_agent_def.instructions
 *
 * ⚠️ V1 只支持 inlineInstructions
 *    （契约的 systemPromptRef 引用式提示词库在 V1 未实现）
 *    —— 出现 systemPromptRef 时【明确拒绝】（返回 null → 拒绝执行），
 *    而不是静默忽略：静默忽略会让运维以为「提示词已生效」，
 *    而运行期实际用的是另一段（甚至没有）文本。
 *
 * ⚠️ 「声明坏了」与「没声明」是两种不同的失败：
 *   · 没声明（{}）→ 系统提示词为空串，Agent 照常跑
 *     （它可能本来就不需要特殊指令）
 *   · 声明坏了（JSON 非法 / 用了未实现的引用式）→ 【拒绝执行】
 *     带着一份「读不懂的提示词」跑，等于静默丢掉了业务指令，
 *     而模型仍然按「无约束」行事 —— 这是最坏的一类假成功。
 */

三个层次的事实必须分清，混说任何一个都会写错方案：

层次事实证据
契约层 已定义systemPromptRef 是一个已定义的字段，指代「引用式提示词库」代码显式判断 root.containsKey("systemPromptRef")
实现层 零落地V1 未实现；grep prompt_template|PromptTemplate|提示词模板 全仓零命中，DDL 无提示词表全仓 grep + deploy/sql/ 无对应表
运行期 fail-closed配置里写了 systemPromptRef → 拒绝执行（fail-closed），不是静默降级systemPrompt() 返回 null → 调用侧拒绝
当前实际系统提示来自 cap_agent_def.instructions 的 inlineInstructions 内联字符串；「版本」随 CAP 发布流程走（A5.7 三步发布），不是独立的提示词版本库AgentModelConfigAssembler.java:351-365
这个 fail-closed 设计本身就是教材

面对「不支持的功能被配置了」，有三种处理方式——静默忽略（最差）、静默降级（次差）、明确拒绝（本项目选择）。理由写在注释里：静默忽略会让运维以为「提示词已生效」，而实际跑的是另一段文本。同样重要的是区分「没声明」与「声明坏了」：{} 是合法的「不需要提示词」，Agent 照常跑；解析失败或用了未实现的引用式则是「带着读不懂的指令跑」，必须拒绝。这两种情况的失败语义不同，处理方式也不该相同。

如果要补，该注意什么

  • 不要绕过 CAP 发布流程：提示词一旦可被引用，它就必须有版本、有发布、有回滚——否则「改提示词」会变成一次不可审计的热更新。参考 A5.7 的三步发布（登记 → 双人复核 → CAS 切指针）。
  • 围栏常量必须与 PromptGuard 同源：提示词正文会被拼进系统提示，若模板里允许插入变量，就重新打开了 A3.3 的注入面。模板变量必须走 PromptGuard 围栏。
  • 保留 inlineInstructions：作为「不需要版本管理的小改动」的逃生通道，强行统一到引用式会增加低价值流程成本。
  • 补测试时优先测「拒绝路径」：这套设计现在唯一被保证的行为就是「遇到 systemPromptRef 就拒绝」，实现引用式之后这条测试要保留（防止回退成静默忽略）。
证据： platform/agent-worker/.../execute/AgentModelConfigAssembler.java:320-370（systemPrompt 三种结果与注释）；全仓 grep prompt_template|PromptTemplate|提示词模板|提示词管理 = 0 命中（2026-11-12）。

A19.2 缺口全景：按「性质」而非「热度」分类

把十八册里散落的「未落地」条目汇总，按性质分成四类。分类决定处理方式——这是本册的核心方法：

性质含义处理方式条目
A. 刻意不做 有意为之做过取舍，有明确理由，现在做反而有害不要动；只在条件变化时重评模型 fallback 链、网关级重试、模型侧熔断、SSE 断线重连、模糊测试式动态发现、HNSW 索引（4096 维建不了）
B. 分期未到 已排期有设计、有分期，只是排期在后按既有分期推进，不插队记忆 P2 向量召回、P3 会话记忆、MCP stdio 传输、代际分布式分片
C. 结构缺口 该补契约已定义、实现缺失，且缺了会有真实风险优先补，补时要防回退引用式提示词库（A19.1）、Agent Chat 事件序列号与重放、MCP Server 暴露
D. 证据空白 先勘察不知道做没做、或不知道效果如何先勘察再决策，不要凭想象排期记忆召回的实际教育效果、代际清理策略、oauth 凭据完整性、流式故障矩阵覆盖度

这个分类的回答方式是「这条缺口该不该补」——A 类不该补，B 类不用现在补，C 类该补，D 类先查。能分清这四类，比列一百条 TODO 有用。

证据： 汇总自 A13.11、A14.10、A15.10、A16.10、A17.10、A18.10；总表见 §20.5。

A19.3 A 类：刻意不做的六项，及其「什么条件下该重评」

未落地 在这里不等于欠债。下面每一项的「不做的理由」都能在代码或 DDL 里找到原文，这是它与「懒得做」的唯一区别（判据见本节末尾的警示框）。

这一节是本册最容易被误读的部分——「未落地」不等于「欠债」。每一项都附了重评条件，这是判断「现在还该不该不做」的唯一依据：

缺口不做的理由重评条件
多模型 fallback 链静默换模型会同时改变单价与能力，破坏成本与质量两条口径（A14.10）需要「单一供应商不可用时的业务连续性 SLA」时——届时要做显式降级（标记模型降级 + 成本按实际价）而非静默切换
网关级自动重试与 Worker 侧重试同时生效 = 双重重试（A14.5）只有当重试职责整体迁到网关侧、Worker 侧撤除时才做（二选一，不能并存）
模型侧熔断器模型网关是一等资源、失败率靠指标告警治理；MCP 才需要熔断（A16.7）单供应商失败率波动导致成本/延迟显著恶化时——先看指标能否支撑决策
SSE 断线重连 / 事件重放聊天链路未做事件序号，重放需要后端持久化缓冲；Run 链路已有序号（A15.10）用户投诉「长回答断线后全部丢失」成为主要问题时——需先给事件加 sequenceNo
MCP 动态工具发现DDL CHECK 强制 dynamic_discovery=false：新工具必须走发布流程（A16.9）不建议重评：这是安全边界而非性能取舍
HNSW 索引4096 维 > halfvec 4000 上限，建不了；当前语料量级全表扫描更快且无召回损失（A18.2）语料达万级片段，且已选定三条路线之一（MRL 截断 / 二进制量化 / 换小维度模型）
「刻意不做」也要有证据，否则会变成「懒得做」的借口

区分标准很简单：能否指出写在代码/DDL 里的具体理由。A 类六项全部有注释或约束可查（fallback 的注释、重试的注释、DDL 的 CHECK、索引的留档注释）。如果你发现某个「未落地」找不到这类证据，它就不属于 A 类，应该归入 C 或 D。

A19.5 可复用的五种增强模式：每次扩展都该遵守的形态

前十八册里反复出现的不是具体功能，而是几种扩展形态。任何新能力都应先问「它属于哪一种」，答案会直接决定设计：

模式形态范式案例扩展时最易犯的错
① 端口 + 可空注入新能力做成 ports 接口，宿主类用可空依赖；null = 未装配，能力降级但不影响主流程McpHandlerProvider（可空 = 只有原生工具）、IndexGenerationBuilder（可空 = 静默待命）用 new 直接实例化 → 装配缺失时不会降级而是 NPE；且测试无法替换
② 增强 + 降级不穿透增强功能失败只 WARN + 本次不生效，绝不耗尽主流程记忆召回失败 → memoryBlock=null（A13.7）；播放 checkpoint 失败 → 退回 v1 字节（A15.3）把增强失败当核心失败抛出去 → 一个非关键组件拖垮整个 Run
③ fail-closed 未知拿不准就拒绝，绝不「先跑起来」配置坏了拒绝执行（A19.1）、解析不到模型抛异常（A14.3）、pgvector 缺失拒绝启动（A18.9）静默回落默认值 → 变成「配置坏了但没人知道」
④ 唯一信任边界不可信内容的可信化只在一个地方做MCP 输出在 Gate 边界可信化（A16.8）；记忆/压缩态/RAG 统一走 PromptGuard 围栏在多层各清一次 → 既多余又不足，且审计无单一锚点
⑤ 双写同一事务 + 派生列失效主数据与派生数据同事务写，且派生列在变更时显式失效text_jieba='' 与 embed_model=EXCLUDED（A18.6）只更新主数据 → 派生列陈旧，判据认为「已完成」，静默不重算
怎么用这五种模式

接手一个「加个功能」的需求时，先用这五条过一遍：它是增强还是核心（决定 ②）？依赖该可空吗（①）？未知情况该拒还是该默认（③）？哪些内容不可信、在哪统一处理（④）？有没有派生数据要失效（⑤）？五问过完，设计基本就定了——这比参考任何框架文档都更贴合这个仓库。

A19.7 不建议做的事：三类常见但错误的扩展方向

看起来该做为什么不建议正确做法
引入 Spring AI 全家桶替换自研网关两个 reactor 的 pom 均无 Spring AI 依赖；它的作用只是 ADR-011 的设计依据之一（A1.5）。引入即等于重做已经验证过的归一化/脱敏/观察者三层若确需，先做 PoC 证明「替换后仍满足六分类与脱敏契约」，再谈
给 Agent 聊天加 WebSocket 替代 SSESSE 的单向/文本/HTTP 特性正好匹配「一问一答 + 事件流」；WS 带来的双向能力当前无需求，却要重做鉴权（DispatcherType.ASYNC 那套不再适用）与双前端协议真需要双向时再评估；当前缺口是重连，不是通道能力
把提示词直接塞进数据库做热更新绕开 CAP 发布流程 = 无版本、无复核、无回滚，且会重新打开注入面（A19.1）走 A5.7 三步发布；模板变量走 PromptGuard 围栏

给转型者的心里话

这套系统里最反直觉的一条经验是：「没做什么」和「做了什么」同等重要。十八册里至少有六处「刻意不做」，每一处都有写在代码里的理由。传统后端习惯用「功能完备度」评价系统，而 AI 系统的成熟度更多体现在边界是否清晰、失败是否可解释、取舍是否留痕。你在这个项目里最该练的，不是把功能堆齐，而是在每一个「要不要做」的岔路口给出有证据的判断——这也是这个知识库反复用「证据 → 已实现 / 仅设计 / 证据空白」三档标注的原因。
