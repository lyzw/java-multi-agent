A10. 对话质量评估、判定与归因体系：从 Run 终态到可证伪的质量信号

A9 讲「怎么证明系统是对的」——那是工程正确性；本册讲「怎么证明 Agent 的答案是对的」——这是内容质量。项目在 P7 指标体系与「Agent 对话质量跟踪/回溯/评估体系」两份设计文档之上，落地了一条从 Run 终态自动采集、L1 链路判分、L2 LLM-as-judge 归因判分、确定性抽样到人工审查与告警的闭环。本册把这条链路的真实落点、隔离铁律与尚未落地的部分逐层拆开，每条都给代码或 DDL 证据。

本册与已有册的分工

A6 是事故案例集，A9 是工程质量的守卫与反证，第 11 章 是一次 Run 的执行链路。本册只回答一个问题：Run 跑完之后，系统怎么自动判断「答得好不好、错在哪」，并且不让这个判断本身把账目和指标搞脏。所有数字带出处与时点；「仅设计 / 未落地」的内容用 证据空白 或 仅设计 标注，不写成已实现。

A10.1 两套「L1/L2」语境：先分清再谈判分

A10.4 L2 归因判分：8 值 Outcome 与 fail-closed

L2AttributionEvaluator.java（行 46–185）是全链路里 fail-closed 纪律最密集的一环。它用一个 8 值 Outcome 把「判不了」的所有原因显式编码出来，任何一个环节缺失都不猜测、不降级为「算它错」。

Outcome触发条件
GRADED题库命中 + 判定器返回明确结论
SKIPPED_SAMPLING确定性抽样未命中（默认 sample-rate 0.05）
UNGRADED_DISABLED总开关 agent.quality.eval.llm-judge.enabled=false（生产默认）
UNGRADED_NO_JUDGE判定器 Bean 未注册（默认不注册，见 A10.10）

UNGRADED_NO_REFERENCE题库中无该 questionId 的标准解析
UNGRADED_JUDGE_UNSURE判定器低置信 / 解析失败 → 待人工复核

判定器 ModelAttributionJudge（行 41–231）实现 AttributionJudge，默认模型 MiniMax-M2.5，严格 rubric SYSTEM_PROMPT（行 48–62）。它有六种返回 empty 的情形：无单价、预算超限、模型异常、非 STOP、请求工具、解析失败/低置信（行 121–207）。三段 PromptGuard.wrapToolResult 围栏分别用于 question、agent-attribution、standard-analysis（行 173–183）——防止被评估的文本里藏注入指令影响判分。

迁移提示：把「LLM-as-judge」当成一个 must-fail-closed 的服务

传统后端做「对账/校验」，失败通常是重试或告警。这里的判定器把「无法判定」当成一等公民：没有单价就不调模型、预算超限就不调模型、低置信就不给结论。核心心智模型是——评估器本身也是被评估对象，它的结论只有在「能证明自己判得准」时才落库，其余一律走人工或保持空值。这与A9.4 的反证纪律是同一套哲学。

A10.5 questionId 白名单与标准答案解析

L2 的「精确关联」是整套体系的地基：只认 questionId 精确关联，绝不接题面文本、模糊匹配或猜默认题。这是为了避免「拿相似题的标准答案判这道题」，那会制造看起来很美的假正确率。

A10.6 成本隔离铁律：judge 成本绝不混 usage_record / cost_amount

这是项目反复强调的一条铁律（工作记忆铁律 8）：机器判分绝不写 agent_eval_sample，judge 成本绝不混 usage_record/cost_amount。原因很实际：如果把评估模型调用混进业务账，租户账单会突然多出一笔它没请求过的开销；如果把机器结论混进人工样本，人工覆盖率和 n 就不可信了。

A10.8 幻觉检测与编造出处：编造引用即 Sev-0

HallucinationDetector（行 27–128）在首期「不做 RAG」的语境下采取了一个非常激进但清晰的判据：输出里出现「出处断言」即视为编造（DEC-5，行 12–16）。它不是判断知识点是否存在（那是内容质量评审的事），而是只看输出文本里有没有编造的出处，且注入不得豁免（行 18–20）。

全仓 *BusinessAcceptance* 只命中一个测试类，没有独立主类 BusinessAcceptanceEval。业务验收评测集实际由该测试 + eval/cases/br01-attribution.json（caseSetId="BR-01"）+ HallucinationDetector 共同承担。写文档或做交接时不要假设存在一个叫「业务验收评估器」的运行时 Bean。

A10.9 告警与审查闭环：不猜基线，n<30 不告警

质量告警分成两类：比例类跨 Trace 统计（QualityAlertEvaluator）与单条 Trace规则（ReviewAlertService）。两者都命中后建 review_task，靠 uq_review_task_open 部分唯一索引去重。

规则判据动作
SLA-3MODEL_ERROR + TOOL_5XX 占比 > 10%HIGH / ALERT
SLA-7单工具失败率 > 20% 且调用数 ≥ 30NORMAL / ALERT
内容质量n≥30 时幻觉率 > 5%（分母是 sampledCount 不是 traceCount）HIGH / ALERT
SLA-2当前成功率 < 基线 − 3σ；σ 用二项近似 sqrt(p(1-p)/n)，历史窗 n<30 记「不判」HIGH / ALERT
BEH-4loop_suspected_count > 0（循环）HIGH / ANOMALY
COST-4coalesce(in,out) > 20000 tokenNORMAL / ANOMALY
MAX_ROUNDS / SAFETY_BLOCK触顶 / 安全拦截HIGH / ANOMALY · ALERT

关键纪律是「不猜基线」：基线从历史 7d 窗口实测算，任一窗 n<30 不告警，绝不硬编码 3σ 数字（QualityAlertEvaluator.java:24–46,158–181）。命中后 fire() 用 "ALERT:"+rule+":"+UTC日期 作 traceId、全零 UUID 作平台级 tenant_id 哨兵（行 198–225）。这保证同一天同类告警只建一条任务，重复触发是预期去重而非异常。

用户反馈走 TenantFeedbackController：POST /api/metrics/feedback，请求体刻意不含 tenantId，由已验签令牌 CurrentPrincipal.context() 派生；traceId 服务端带租户谓词解析，跨租户 404；kind ∈ THUMB_UP/THUMB_DOWN/RETRY/ABANDON；不写原文，L3 有噪信号只触发复核（行 43–44,71–116）。

最容易被误读成「已完成」的两件事

① 「骨架已落地」≠「判分已生效」：默认开关 false + 空题库 + 未注册判定器，意味着生产上 L2 现在恒为 UNGRADED_*，看板显示「未启用」。② 「EvaluationClosedLoopIT 有 9 例」≠「业务验收达标」：早期文档写「4 例」是过时口径（进度台账已记 9 例）；而「SB-01 达到 80%」需要真模型 + 人工评审，当前测试不产出该结论。把测试通过当成指标达标，正是本项目最忌讳的静默失真。

迁移提示：给「质量」建立可证伪的证据链

传统 Java 后端的质量往往止于单元测试和接口自动化。本项目要求的是：每一个质量结论都能回答「撤掉修复点会不会变红」。对应到内容质量，就是——判不了要显式编码（8 值 Outcome）、机器与人工分域存放（两张表）、成本独立科目（EVAL_JUDGE_COST）、样本不足不给百分比（n<30）、编造出处即 Sev-0。「看起来对」不算对，「能被证明对」才算对。
