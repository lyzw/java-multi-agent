1. 项目全景：业务、边界与进程拓扑

1.1 业务定位与首期场景

项目是一个面向初中生错题归因与个性化辅导场景的企业级、多租户、可审计、可恢复的 Java SaaS Agent 平台（docs/业务架构图.md / docs/系统架构图.md）。业务上分成两个平面：

租户平面（Tenant Control Plane）

学生 / 家长 / 教师提交「题目文本 + 解题过程 + 已知正确答案」，Agent 读取学习画像 → 归因分析 → 生成讲解 → 记录薄弱点 → 返回结构化结果。这是 P0-D00 定义的首个业务场景 BR-01。

首期只有两个工具：get_student_profile（只读）与 record_weakness（唯一有副作用工具，幂等键为 student_id + run_id + knowledge_point）。

平台平面（Platform Control Plane）

admin-console 是独立的控制面：独立主体、独立令牌域（aud=admin-console-api）、独立授权域与 platform schema，而不是「拥有全租户权限的超级租户控制台」。管理租户、平台用户/角色、Agent / Tool / Skill / MCP 能力目录、模型目录、审计与语料治理。

明确不做的事（避免误读需求）

docs/P0/P0/P0-D00_决策基线与业务场景定义.md 与 SRS 明确排除作业批改与自动打分（涉及评分公平性与申诉链路）与实时在线辅导；主平台 DEC-5 原本「首期不纳入 RAG」，RAG 子项目是对该决策的重审（rag/docs/RAG-D00_决策基线与范围边界.md）。库中确有名为 assignment-copilot 的 Agent，但文档并未把它定义为作业批改打分能力 未确认：其确切业务语义。

2. 技术架构：六边形、事实源与五条链路

2.1 六边形分层与依赖方向

两个 reactor 都采用端口-适配器（六边形）架构：依赖永远指向中心，agent-core 是纯领域对象、零框架依赖（不 import Spring）；agent-ports 定义接口；agent-infrastructure / agent-persistence 提供实现；platform-bootstrap 是唯一的组合根，决定容器里装哪些 Bean。

图 2-1　platform reactor 的分层与依赖方向（示意，模块清单以 §3.2 为准）
可直接复用 但边界更严

分层与 Spring 的依赖注入、接口与实现分离、配置类装配你都熟悉。这里的差别是边界由测试强制：ModuleDependencyDirectionTest 检查倒流、DatabaseBoundaryTest 检查 java.sql.* / org.springframework.jdbc.* / Hikari 只许出现在 persistence 模块、AgentCorePurityTest 检查领域层零框架依赖。写错 import 会在构建期变红，而不是 Code Review 时才被指出。

2.2 PostgreSQL 是唯一事实源：Outbox + 租约 + Worker

架构文档里写得最重的一条原则：「PostgreSQL 是任务状态的权威事实来源；MQ 只负责唤醒和分发」；「Run 与 Outbox 事件在同一数据库事务中提交」（docs/系统架构图.md / docs/P0/P2/P2-D02_Outbox发布与MQ消费.md）。

  1. API 创建 Run 时，在同一个事务里写 run 行 + outbox_event 行。若「先落库再发 MQ」，进程在两者之间崩溃会造成任务永久丢失且无任何报错。
  2. OutboxRelay 按租户驱动 OutboxPublisher，把待发消息推到消息通道；发布器在发送前还会复核消息里的 tenantId 是否与自己绑定的租户一致（第二道防线）。
  3. 消息只携带 tenant_id + run_id + message_id，不携带可信权限与任务状态；Worker 领取后必须回数据库重读。
  4. 领取靠租约 + fencing token 防脑裂；崩溃恢复由 RunRecoverySweeper 接管过期 RUNNING；UNKNOWN 状态走对账而非盲目重放。
  5. 代价是至少一次投递，因此消费端必须幂等；终态后禁止补 attempt。

消息通道有两条，默认 agent.messaging.mode=database（PG 表 agent_message_queue），可切到 RabbitMQ；agent.mq.* 定义 quorum 队列与死信。两条通道都要求按 eventType 分流（EventRoutedMessageHandler → TraceCollectMessageHandler），否则采集事件会被当成执行事件，把已终态的 Run 重跑 — 这是项目登记过的 Sev-0 级风险。

2.3 租户隔离：RLS 与正在进行的迁移

数据库侧 44 张表启用（并 FORCE）行级安全，52 条策略形如 tenant_id = current_tenant_id()，函数读取会话变量 app.tenant_id。应用侧的连接由 TenantSessionBinder 在事务内、业务 SQL 之前用 set_config(..., true) 绑定，事务结束自动失效，避免连接池串租户。

javaplatform/agent-persistence/.../persistence/TenantSessionBinder.java
/** 与 DDL 中 current_tenant_id() 读取的键名保持一致。 */
public static final String SESSION_VAR = "app.tenant_id";
private static final String SQL_SET_TENANT =
        "SELECT set_config('" + SESSION_VAR + "', ?, true)";   // is_local=true：事务局部

public static void bind(@NonNull Connection connection, @NonNull TenantContext context)
        throws SQLException {
    try (PreparedStatement ps = connection.prepareStatement(SQL_SET_TENANT)) {
        ps.setString(1, context.tenantId());
        ps.execute();
    }
}

同时项目正在把行级隔离的「唯一权威」从 RLS 谓词逐步迁移到应用层的 ScopeFilter（四种形态：TenantWithShared / TenantOnly / Unrestricted / fail-closed 的 None()），双写期纪律是「RLS 一条策略都不许动，应用层过滤全部加在 RLS 之内取交集」。

文档冲突 迁移状态要以代码为准

docs/developer-onboarding.md 写的是「用应用层 ScopeFilter 替换 PG RLS 谓词」，属于目标态描述；据项目进度台账，RLS→应用层迁移仍在进行中，尚有相当数量 Jdbc*Repository 未接入 Gate，出口条件是 rlsDependent() 归零，而不是 AUTHZ_MISMATCH=0。 未确认：当前精确剩余数量需现场核对。详见 §16.8 案例。

2.5 五条执行链路与请求级 SSE

上下文压缩方案把运行形态分成 L1 异步 Worker / L2 请求级 SSE / L3 控制台直连 / L4 子 Agent / L5 语义路由。请求级 SSE 有两条链：

  • 平台链 /api/agent/chat/stream（可下发 thinking）；租户链 /api/knowledge/agent/chat/stream（恒丢 thinking、禁带 tenantId）。
  • 不写 Outbox、不发 MQ；审计 begin() 写 RUNNING，finish() 按 fencing token 收敛，影响行数 ≠ 1 必须抛异常。
  • RAG 命中经 PromptGuard.wrapToolResult("rag", …) 作为 user 消息注入，绝不进 systemPrompt。
  • SSE v1.1 冻结 14 个事件，新增第 14 事件 context.checkpoint，线序 answer → usage → context.checkpoint? → done；done 是应用层终帧。客户端 carry-over 状态默认不落库，用独立 HMAC 校验（AGENT_CONTEXT_STATE_HMAC_KEY，绝不复用 JWT 私钥）。
交叉引用：完整 Run 生命周期见 第 11 章；SSE 与压缩链路见 第 12 章；协议事件字典出处见 第 19 章。

2.6 贯穿全项目的设计原则

原则在这项目里的具体含义违反后的典型症状
fail-closed配置缺失、策略解析不到、能力未知、凭据缺失时拒绝而非放行；ScopeFilter.None() 恒假返回 0 行「静默放行」或「静默 0 行」，功能空转却不报错
Run 创建期快照固化能力闭包、配置、上下文策略在建 Run 时钉死成 execution_snapshot；发布引用必须 id@version，禁止 latest 漂移发布后旧 Run 行为漂移、无法复现
闭包只收紧不扩张能力目录解析不到的对象抛 ClosureResolutionException；委派不授权限，每跳重新授权越权工具调用
平台级对象带外运维平台域用独立 platform_ops 通道；应用层不提供创建超级管理员端点把 BYPASSRLS 角色当业务账号用 → 租户隔离被关掉
无物理删除端点清理走保留期与状态收敛；风险事件只存 detailDigest审计链断裂
指标低基数标签用代码级白名单；run_id/user_id/student_id 等高基数标签注册即抛异常；明细走日志、聚合走指标Prometheus 基数爆炸 / 日志泄漏个人信息

三个「看起来像、其实不是」的技术选型

① 没有独立向量库 Java 依赖：pgvector 是 PG 扩展，通过 SQL 的 <=> 算子与 ?::halfvec cast 使用。② rag 侧零 MQ：入库任务靠 PG FOR UPDATE SKIP LOCKED 轮询 + @Scheduled，主平台已有 RabbitMQ，刻意不引入第二套。③ 没有 cross-encoder 重排器：代码里的「重排」是 RRF 融合分排序 + 版本惩罚；bge-reranker-v2-m3 选型已定但尚未接入 文档冲突：RAG-D05 记「RRF 未实现」，与代码不符。
