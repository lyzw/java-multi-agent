A12. 可观测性、审计链与运维 Runbook：从指标到不可抵赖的证据

A10 讲质量信号怎么产生，A11 讲成本怎么记账，本册讲系统怎么把运行状态暴露出来、把关键操作变成不可抵赖的证据、以及线上怎么安全地切换开关和轮换密钥。这里既有可直接复用的工程实践（Micrometer、MDC、Grafana、触发器），也有本项目特有的「配了等于没配」陷阱——守卫数组被注释成空、指标出口的鉴权落差、审计守卫空转。照 A9 的纪律，这些都要摊开讲，不粉饰成「已就绪」。

本册与已有册的分工

第 14 章 讲「出问题怎么排查」，A9 讲「怎么证明系统正确」，本册讲「平时靠什么看见系统、事后靠什么举证、上线靠什么不出事」。三条线互补：可观测性是眼睛，审计链是黑匣子，Runbook 是操作手册。

// 白名单净化：防 CR/LF/ANSI 日志注入；traceId 来自外部请求头，属攻击者可控输入
String sanitize(String v) {
    if (v == null || v.isEmpty()) return NONE;
    String cleaned = v.replaceAll("[^A-Za-z0-9._:@-]", "");
    return cleaned.isEmpty() ? NONE
         : cleaned.length() > MAX_VALUE_LENGTH ? cleaned.substring(0, MAX_VALUE_LENGTH) : cleaned;
}

注意 sanitize 是净化（过滤非法字符）而非对敏感值打码：它防的是日志注入（换行伪造日志行、ANSI 控制序列），MAX_VALUE_LENGTH=64 截断超长值。跨线程传递用 wrap(Runnable/Callable) 与 push(Snapshot) try-with-resources，并要求在 finally 调用 clear()。HTTP 入口在 RequestLoggingConfiguration（行 54,109–127）写 traceId、回写响应头、finally 清 MDC；MQ 侧 RabbitExecutionListener（行 100,119）从消息头取。

A12.4 审计链真相：不是哈希链，是 append-only 触发器 + 凭据隔离

先纠正三个常见误解

① 未找到 独立表 agent_chat_audit：请求级对话审计由 JdbcAgentChatAuditRepository 写 run/run_event/run_step 三张表。
② 未找到 精确表 platform_audit：实际是 platform.platform_audit_event。
③ 未找到 哈希链：全库 grep prev_hash/hash_chain/merkle/nonce 均无匹配。审计的不可抵赖靠「DB 触发器 append-only + 角色凭据隔离 + 敏感信息拒写 + fail-closed」，不靠链式哈希。

表用途 / 关键字段
public.audit_record租户侧通用行为审计（01_platform_ddl.sql:1488–1507）：audit_id/tenant_id/actor_id/action/resource_type/resource_id/detail(jsonb)/correlation_id/created_at；FORCE RLS + 策略 audit_record_tenant_isolation
platform.platform_audit_event平台域管理审计（无 tenant_id，行 1064–1078）：actor_type/action/target_type/decision/reason_code/ip/ticket_scope；ticket_scope CHECK 三值 PLATFORM/TENANT/ALL
platform.authz_decision_log授权判定流水（行 971–1002）：每次 AccessGate 判定一行（主体+动作+资源+permitted+reason_code），tenant_id text 故意 text，不挂 RLS，隔离靠授权（app_agent 仅 INSERT，读走 platform_ops）
public.cap_decision_log / rag.rag_access_auditCAP 决策审计（租户隔离）/ RAG 侧访问审计，分域存放

防篡改的实现：触发器 trg_audit_record_append_only（行 4663）对 BEFORE DELETE OR UPDATE 执行 public.forbid_audit_mutation()。加固版（04_retention_role.sql 行 176–192）规定：DELETE 仅放行具备 agent_retention 成员身份的连接（pg_has_role(current_user,'agent_retention','MEMBER')）且须声明 agent.retention.actor 留痕；UPDATE 永远拒绝。agent_retention 唯一拥有 DELETE 权，从 app_agent 撤销；重跑 03_platform_roles.sql 的 GRANT … ON ALL TABLES 会静默回授 DELETE，所以重跑 03 后必须紧接 04。

sqldeploy/sql/platform/04_retention_role.sql 行 176–192（forbid_audit_mutation，节选）
CREATE FUNCTION public.forbid_audit_mutation() RETURNS trigger AS $$
BEGIN
  IF TG_OP = 'UPDATE' THEN
    RAISE EXCEPTION 'audit_record is append-only: UPDATE denied';
  END IF;
  -- DELETE：仅 agent_retention 成员且声明了留痕 actor
  IF NOT pg_has_role(current_user, 'agent_retention', 'MEMBER')
     OR current_setting('agent.retention.actor', true) IS NULL THEN
    RAISE EXCEPTION 'audit DELETE requires isolated retention credential';
  END IF;
  RETURN OLD;
END $$ LANGUAGE plpgsql;

JdbcAuditRepository 有三条不变量（行 33–43）：敏感信息拒写（写前逐字段跑 IdentifyingPattern，命中身份证/手机/学号/邮箱即抛异常整条不写，行 227–263）；关键审计 fail-closed / 访问日志 fail-open（行 93–94 vs 106–116）；追加不可改靠 DB 触发器。按键豁免 VALUE_SCAN_EXEMPT_KEYS（runId/operationId/approvalId/resourceId/correlationId），studentId 不在豁免名单。AuditChainIT（IT_PG_URL 活库、非特权 app_agent）用反证证明：drop 掉触发器后 UPDATE/DELETE 被静默放行（T-4，行 150–179，restoreTrigger 在 finally），且跨租户隔离、敏感信息拒写、fail-closed vs fail-open 都有断言。

A12.5 禁 RETURNING 铁律：authz_decision_log 只 INSERT 无 SELECT

这条铁律针对的是 platform.authz_decision_log，不适用于 audit_record/usage_record（后两者有 SELECT + RLS，可用 RETURNING）。

环节事实
授权设计该表按设计只给应用角色 INSERT、显式 REVOKE SELECT（03_platform_roles.sql:263,273–274，DRY 断言 :291–297）
为什么禁 RETURNINGPG 的 INSERT … RETURNING <col> 需要返回列的 SELECT 权限；无 SELECT 会 permission denied，且失败被「限频告警 + 绝不外抛」吞掉 → 表现为「判定照常、审计零行、系统全绿」（13_RLS到应用层权限迁移_设计与实施计划.md:137–143）
源码守卫AuthzDecisionLogSchemaTest#insertMustNotUseReturning（行 75–90）断言 .doesNotContainIgnoringCase("RETURNING")
活库守卫AuthzDecisionLogLiveIT#insertWithReturningIsDenied（单测盲区，靠真库证明）
启动零行探测JdbcAuthzDecisionLog.probe()（行 86–91,139–159）用 INSERT … SELECT … WHERE FALSE 零行探测表/权限/列漂移；AuthzDecisionLogGuard 在装配层决定是否拒绝启动
三类审计表，三种信任模型

audit_record（租户行为审计，RLS 隔离）、platform_audit_event（平台管理审计，无租户）、authz_decision_log（授权判定流水，仅 INSERT 无 SELECT）分域存放。它们的共同点是「只增不改」，差别在于「谁能读」：租户侧靠 RLS、平台侧靠专用数据源 platform_ops、决策日志靠「应用不可读」。把三张表当一张用，会同时踩权限和隔离两个坑。

平台审计数据源 assembly：JdbcPlatformAuditRepository（注意包是 infrastructure.security）只追加写 platform.platform_audit_event，供 /api/platform/v1/audit-events；它不挂 @Repository——app_agent 对该表无授权，组件扫描会挂到主数据源导致 permission denied，必须走 platformIdentityDataSource()（platform_ops）。写字段与 ?:: 占位符按位置一一对应（行 42–66），列顺序漂移会「审计还在、证据换人」。

A12.7 告警与 fail-closed 门禁：开关怎么安全落地

告警分应用层与 Prometheus 两侧，见 A10.9 的 SLA-2/3/7 与 BEH/COST 规则。这里补一条关键取舍：monitoring/prometheus/prometheus.yml（16 行）无 rule_files、无 alerting、无 groups 未落地。原因是刻意把比例告警放应用层（QualityAlertEvaluator），因为 rule_files 告警不能建 review_task、无法复用 uq_review_task_open 去重；代价是运维接 Alertmanager 需另建规则。部分早期文档仍写「alert rules 本期补齐」，与 2026-11-09 的取舍未同步。

fail-closed 门禁汇总（缺配置或状态不对就拒绝启动，而不是带病运行）：

门禁触发条件 → 行为
JWT 私钥缺失生产 profile（非 dev/local/test）未配置私钥 → IllegalStateException 拒绝启动；禁止启动时生成新密钥（否则滚动重启全员掉线），dev 下临时生成打醒目 WARN（AuthConfiguration.java:90–134）
平台身份数据源缺失PlatformOpsUnavailableException，绝不回落应用角色（行 245–251）
CAP 开启但流程未装配CapEnforcementReadinessGuard：开启但 CapExecutionFlow 未装配 → 拒绝启动；关闭时打印显眼 SECURITY WARN
审计凭据未隔离AuditTamperProofGuard 设计上「require-isolated-credential 时应用角色仍有 DELETE → 拒绝启动」，但当前数组为空、实际不生效（见 A12.6）
决策日志不可写JdbcAuthzDecisionLog.probe() 返回 false，由装配层决定是否拒绝启动

配套配置：CONFIG_FLAG_CAP_ENFORCEMENT_REQUIRED、CONFIG_FLAG_CAP_CLOSURE_ENFORCEMENT（默认 warn）、CONFIG_FLAG_CAP_AUTHORIZATION_ENFORCED（默认 false）、CONFIG_FLAG_CAP_DUAL_WRITE（默认 true）、AGENT_RETENTION_REQUIRE_ISOLATED_CREDENTIAL（默认 false）。CapEnforcementMetrics 用 Gauge cap.enforcement_status 暴露 0/1/2 三态，放在 bootstrap 是因为 CapEnforcementSwitch 所在的 agent-application 不依赖 Micrometer。

A12.9 密钥轮换与环境治理：明文即泄露

传统运维把「加了监控 / 加了守卫 / 配了开关」当成完成。本项目的教训是：指标可能没人写（AgentMetrics 空转）、守卫可能守着空数组（AuditTamperProofGuard）、开关可能只改了配置没接执行侧（tenant_quota）、说明可能停留在旧快照（16 vs 13 面板）。可复用的是 Micrometer / MDC / Grafana / 触发器 / kid 滚动这些成熟手段；必须新建的是「的配置到底有没有生效」的证伪习惯——看真实出口抓不抓得到、看守卫数组里有没有表、看关了开关数据是不是还在、看文档数字和 JSON/DDL 对不对得上。可观测性的第一原则，是先观测「观测系统本身」。
