A14. 模型统一配置与模型网关：单一事实源、归一化与凭据边界

A2.9 讲「为什么要统一模型配置」的决策口径，A11 讲「调一次模型记多少钱」；本册讲中间那段工程实现：一次调用前，模型怎么从目录里解析出来（fail-closed、不缓存、禁用即不可用）；调用后，异常怎么归一成六类（误标 retryable = 无限重试）；密钥怎么不进日志（脱敏双正则 + 异常不挂 cause）。这一段是 Java 后端最能直接复用方法论的部分——适配器模式、错误分类、脱敏——但每一处都有 AI 特有的坑。

本册与已有册的分工

A1.2 讲一次 LLM 调用的账单路径，本册讲它的前置解析与异常面；A3.4 讲跨进程契约失配，本册 A14.8 的 MiniMax tool_call_id 事故是其代表性案例；A12.1 讲指标出口，本册 A14.4 讲网关的观察者装饰层；agent.pricing.models 单价配置见 A11.4。

A14.1 单一事实源：model_catalog 表、「密钥与目录分离」铁律与无租户无 RLS 的理由

所有「用哪个模型」的事实收敛在一张平台全局表 public.model_catalog（01_platform_ddl.sql:5926 起，21 列），三个刻意的「没有」：

设计内容理由
无租户列表上没有 tenant_id，也不挂 RLS模型目录是平台资源：哪个模型可用、什么能力，是平台决策，不是租户数据。租户配额在预算侧管（A11.8）
无密钥列API Key 绝不入 model_catalog；凭据在 model_provider_credential（encrypted_key AES-256-GCM + key_checksum 明文 SHA-256 用于篡改检测、不回显）目录数据会进管理后台列表与解析结果；密钥与目录的生命周期、可见面完全不同。DDL 注释原文：api_key 明文绝不落库
无「列不存在就回落默认」JdbcModelCatalogRepository 刻意不做缺列降级（约 :277）缺列说明 DDL 与代码漂移，静默回落会把「结构坏了」变成「能力错了」——fail-closed

窗口相关三列（context_window_tokens 默认 32768 / max_input_tokens 默认 28672 / tokenizer_id）是 A1.3 全窗口预算的数据来源；「每场景至多一个默认」由部分唯一索引 model_catalog_scenario_default_uq 在库里强制，不靠应用层自觉。

证据： deploy/sql/platform/01_platform_ddl.sql:5926-6020（model_catalog / model_provider_credential / 唯一索引）；platform/agent-persistence/.../JdbcModelCatalogRepository.java；管理入口 platform/agent-api/.../admin/AdminModelConfigController.java / AdminModelCredentialController.java / InternalModelConfigController.java。

A14.2 场景模型：ModelScenario 七个内置场景与字符串常量的取舍

ModelScenario 定义七个内置场景常量：agent-chat / console-chat / embedding / summarization / classification / moderation / default。注意它是 public static final String 而非枚举：场景是开放集合（后续加 rerank、judge 之类不该改端口层），端口方法签名收 String scenario，常量只是「平台已知的拼写」。已实现

同一物理模型可以在多个场景各占一行（场景名 + 模型名联合唯一），这让「对话用大模型、分类用小模型、嵌入用专用模型」成为配置问题而非代码问题——A10 的 judge 场景、RAG 的 embedding 场景都从这里解析。

证据： platform/agent-ports/.../modelcatalog/ModelScenario.java:21-39、ModelDefinition.java。

A14.3 解析优先级四级：显式名 → 同名 → 场景默认 → default，fail-closed 不猜模型

ModelResolver 的解析顺序（类注释 :20-34）是本册最常被引用的规则：

text解析优先级（ModelResolver.java:20-34）
同一场景内：
① 显式指定的模型名在该场景内命中「启用」模型
② 显式名退化为全目录同名「启用」模型（跨场景同名兜底）
③ 该场景的默认模型（每场景至多一个，部分唯一索引强制）
④ default 场景的默认模型
⑤ 都没有 → 返回空（fail-closed：绝不随便挑一个模型）

两条横切规则：
- 已禁用模型不参与解析：is_enabled=false 即使被显式点名、
  即使在默认位，一律跳过（:29-31）
- 不缓存：每次解析都读端口（端口实现可自带缓存）（:32-34）
  → 管理后台改完，下一次调用即刻生效；无需重启、无需清缓存

resolveRequired（:106-119）是 fail-closed 的强制形态：解析不到直接抛异常，异常文案里写明「fail-closed 拒绝猜测模型」。这里没有 fallback 链——找不到就是找不到，不会「退到一个更便宜的模型」（见 A14.10 的未落地清单与理由）。

证据： platform/agent-application/.../modelcatalog/ModelResolver.java:20-34, 52-70, 78-89, 106-119；Agent 侧装配 platform/agent-worker/.../execute/AgentModelConfigAssembler.java / RootAgentModelConfigProvider.java / WorkerChildAgentModelConfigProvider.java。

A14.4 网关抽象：AbstractModelGateway 的三层职责与观察者装饰

三个真实实现（MiniMaxModelGateway / OpenAiCompatibleModelGateway / FakeModelGateway）都继承 AbstractModelGateway，基类把三件事收口，适配器只实现 invokeGuarded：

层基类行为为什么放基类
归一化complete() 捕获适配器异常并 classify() 成 ModelErrorKind若各适配器自己实现 complete()，漏掉一个分支就会把不可重试误判为可重试（:31-35 注释）
超时callWithTimeout()（:94-136）在受控线程里执行并施加时限；已归一化的异常原样上抛（:119-127）——外层再 classify 一次会把 kind 降级成 PROVIDER_ERROR超时控制与线程上下文传递是横切关注点
观测ObservableModelGateway（ports 层装饰器）把每次调用的 before/after/exception 分发给 ModelCallObserver 链（Slf4j / Micrometer / EventPort 桥 / Noop 四个实现）指标与日志不侵入适配器；真实出口见 A12.1
证据： platform/agent-infrastructure/.../model/AbstractModelGateway.java:31-136；platform/agent-ports/.../observer/ObservableModelGateway.java；platform/agent-infrastructure/.../observer/{logging,metrics,bridge,noop}/。

A14.5 ModelErrorKind 六分类与 retryable 语义：误标 = 无限重试

javaModelErrorKind（ModelGateway.java:31-50）
enum ModelErrorKind {
    TIMEOUT(true),          // 可重试
    RATE_LIMITED(true),     // 可重试
    PROVIDER_ERROR(true),   // 可重试（供应商 5xx / 网络）
    INVALID_REQUEST(false), // 不可重试：context length exceeded 等，重试无意义
    UNAUTHORIZED(false),    // 不可重试：密钥错，重试只会再错
    CONTENT_BLOCKED(false); // 不可重试：内容拦截，重试同样内容同样被拦
    ...
    boolean retryable();
}

这张表是重试策略的单一依据：重试统一在 Worker 侧（RunExecutionLoop.java:63-65 注释：绝不引入 Spring @Retryable，两者同时生效会双重重试），判据就是 kind.retryable()。由此推出两条红线：把不可重试误标为可重试 = 无限重试烧钱；对已归一化异常二次分类 = kind 降级。写新适配器时 classify 分支必须覆盖供应商文档里的每一种 4xx/429/5xx。

未知 provider 会回落 FakeModelGateway（见 A2.9）——这在生产是一根「不报错但没调真模型」的尾巴。判断链路是否走了真模型，查 model_catalog 的 provider 拼写与网关装配（WorkerRealModelGatewayResolutionTest 断言的就是这个）。

A14.6 凭据脱敏：双正则、***REDACTED*** 与 safeMessage 不挂 cause

textCredentialRedactor（CredentialRedactor.java:21-32, 66-75）
正则一（形态匹配）：sk-xxxx… / ghp_xxxx… / AKIA… / xoxb-… / Bearer xxx
正则二（键值匹配）：authorization|api-key|secret|token|password = …
占位符：***REDACTED***

safeMessage(context, error) 刻意不把 error 设为 cause：
日志框架打印被抑制的异常时会带出原始消息——供应商异常若挂在
cause 链上，原始消息（可能含回显的密钥）会绕过脱敏层直接进日志。

这条「不挂 cause」是 AI 系统特有的纪律：传统后端的异常链是调试资产，这里它是泄露通道。供应商 401 文案常回显请求头片段，脱敏只处理字符串、不处理对象图，所以必须从源头切断。已实现

证据： platform/agent-infrastructure/.../model/CredentialRedactor.java；密钥供给 ModelCredentialProvider.java（env 解析）。

A14.7 MDC 与线程边界：模型调用为什么要 LogContext.wrap

callWithTimeout 在受控线程执行适配器调用，而 MDC（日志上下文）是 ThreadLocal 的，不跨线程。若不搬运，模型报错日志会退化成 [- - -]——没有 traceId、没有租户、没有主体，跨 A12.2 的日志上下文纪律就断了。基类用 LogContext.wrap 把上下文带进执行线程（:97-102 附近）。给 Java 后端的提示：这等价于你在异步编排里手工传播 MDC，但这里的上下文除了 traceId 还有租户与主体——少一个，多租户问题的排查就瞎一只眼。

证据： platform/agent-infrastructure/.../model/AbstractModelGateway.java:94-136；platform/agent-application/.../observability/LogContext.java。

A14.8 真实供应商的坑：MiniMax tool_call_id 成对结构事故

2026-10-28 MiniMax 真实端到端事故（MiniMaxModelGateway.java:47-50 注释存档）

旧实现按「工具名 = call id」重组多轮工具消息，且只回发 tool 消息 → 供应商报 400 invalid params, tool result's tool id(...) not found (2013)，整次请求被拒收。根因：tool_call_id 是供应商生成的成对标识（assistant 的 tool_calls 与 tool 的 tool_call_id 必须逐字配对），不是自己起的工具名。这也是 A3.4「跨进程 AI 服务契约失配」的范式案例：OpenAI 兼容不等于语义一致，每个供应商在工具协议的边角都有自己的方言，集成测试必须用真实供应商跑一轮（或用契约测试固化成对结构）。

证据： platform/agent-infrastructure/.../model/MiniMaxModelGateway.java:47-50（事故存档注释）；MiniMaxModelGatewayTest.java / OpenAiCompatibleModelGatewayTest.java。

A14.9 能力探测的诚实性：未探测前恒 false

model_catalog 的能力三列——supports_prompt_caching / supports_tokenize_api 默认 false、tokenizer_id 默认 NULL（DDL :5947-5952 的 R10 规则）。语义是「未探测 = 不支持」，不是「默认支持」。这条与 A1.3 直接挂钩：若假设供应商支持精确计数而实际不支持，token 估算会系统性偏小，压缩后的请求静默超窗。诚实的能力台账是全窗口预算能算准的前提。

证据： deploy/sql/platform/01_platform_ddl.sql:5947-5952（R10 注释）。

A14.10 未落地清单：fallback 链 / 网关重试 / 模型熔断 / Prompt Registry

能力状态说明（全仓 grep 零命中的证据口径）
多模型 fallback 链未落地Resolver 只解析一个模型，取不到即 fail-closed；不存在「主模型失败退备选」的代码路径。属有意取舍：静默换模型会破坏成本与质量口径（换模型 = 换单价 + 换能力）
网关级自动重试未落地（刻意）重试只在 Worker 侧按 retryable 分类做；网关每次调用就是一次。理由写在 RunExecutionLoop:63-65：避免双重重试
模型侧熔断器未落地全仓唯一熔断器是 MCP 侧的 McpCircuitBreaker（见 A16.7）；模型失败率治理目前靠指标观测（A12.7 告警）
Prompt 模板管理 / Registry / 版本化未落地grep prompt_template|PromptTemplate|提示词模板|提示词管理 零命中；DDL 无 prompt 表。系统提示实际来自 cap_agent_def.instructions 的 inlineInstructions 内联字符串，「版本」随 CAP 发布流程走（A5.7）。注意不是「完全没设计」：契约里已定义 systemPromptRef 引用式提示词库，但 V1 明确拒绝执行（fail-closed），详见 A19.1

把「没有」写清楚与把「有」写清楚同样重要：这四项是业界宣传画的常客，如果按「Agent 平台应该都有」的想象去写方案，就会重演 A11.1「把设计稿当实现」的错误。

A14.11 用 Fake 网关做测试：七种故障注入与「假密钥进异常消息」的证明法

FakeModelGateway 内置 FaultMode 七态：NONE / TIMEOUT / RATE_LIMITED / PROVIDER_ERROR / INVALID_REQUEST / UNAUTHORIZED / CONTENT_BLOCKED（:30-45），与 ModelErrorKind 一一对应。两个范式级的技巧：

  • 假密钥进异常消息（:84-98）：Fake 网关把 FAKE_SECRET 刻意拼进异常文案（如 "HTTP 429 rate_limit_exceeded; api-key=sk-fake…"）——若脱敏层被绕过，ModelGatewayContractTest 立刻失败。把安全属性写成可执行断言，而不是靠 code review 盯。
  • 流式路径先归一化再回放（:114-115）：故障模式在流式入口先抛归一化异常，否则回放罐头响应——保证「流式的错误分类」与「一次性调用」不分叉。

TIMEOUT 模式的实现是睡到超时+500ms、由外层 callWithTimeout 中断它——测的就是超时控制本身。这套 Fake 网关配合 A9 的两套 IT 独立库，构成「无网络、无凭据、不抖动」的 AI 测试底座。给 Java 后端的迁移提示：这等价于 WireMock 对 HTTP 的作用，但多了一层「错误分类契约」——你的 Mock 不仅要回放响应，还要回放失败形态。

证据： platform/agent-infrastructure/.../model/FakeModelGateway.java:21-115；platform/agent-infrastructure/src/test/.../model/ModelGatewayContractTest.java。
迁移提示：网关层的「三层收口 + 一条红线」

可复用：适配器模式收归一化/超时/观测三层、错误分类带 retryable、脱敏从字符串与对象图两面堵、能力台账未探测恒 false。必须新建的心智：异常链即泄露面（不挂 cause）、「OpenAI 兼容」≠ 语义一致（工具协议方言）、不缓存解析结果是特性不是缺陷（改完即生效）。
