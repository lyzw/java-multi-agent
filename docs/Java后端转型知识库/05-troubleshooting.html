14. 排查总方法论

14.1 五段式记录模板

项目 问题记录/README.md 规定每条问题固定三段（问题描述 / 产生原因 / 相关解决方案），本手册按培训需要扩展为五段式。任何一次排查都按这个结构写，避免「改好了但不知道为什么好」：

段要回答的问题反面例子合格例子
① 现象谁在什么环境、看到什么可观测结果？有没有报错？「检索不好使」「POST /api/v1/retrieval 返回 200 且 hits=[]；同 query 直连 rag 返回 2 命中」
② 可能原因列出 2–4 个可证伪的假设，按先验排序「大概是配置问题」「a) revisionCode 空串被拒 b) 嵌入维度漂移 c) 租户未绑定」
③ 定位方式用哪条命令 / 哪个日志 / 哪张表把假设逐一排除？「看了一下代码」「curl 原始字节 + 只读 SQL 查 count(*) + current_setting('app.tenant_id')」
④ 解决方案改了哪个文件、为什么这样改、有没有更根本的修法「重启就好了」「按对端真实校验把默认 revisionCode 改为『未指定』，并补契约守卫」
⑤ 验证步骤如何证明修好了、且撤掉修复会红？「测试全绿」「两真进程 369 帧 / 2 命中；9/9 反证撤点转红；skipped=0」
为什么强调「可证伪」

本项目最贵的缺陷不是抛异常的那些，而是不报错、数字悄悄错、或功能空转的那一类。如果假设无法用一条命令证伪，你就永远不知道自己修的是不是真因。项目方法论归档称之为「绿不等于对」「能力的存在 ≠ 能力的生效」。

14.2 核心概念：静默失真（Silent Distortion）

这是贯穿全项目的问题分类。它不是「报错」，而是系统继续正常运行，但结果已经错了，且没有任何信号。项目里出现过的形态：

形态例子判别口诀
静默 0 行FORCE RLS 未绑租户 → 删/查返回 0 行；平台档会话置空后应用角色读全局行恒 0「查不到」先查 current_setting 和 current_user
静默回滚事务内 SQL 失败被 fail-soft 吞掉后 COMMIT，PG 已 aborted 事务静默等价 ROLLBACK看影响行数，不看有没有抛异常
静默降级下游 500 被降级成「空命中」；解析器失败回落占位实现区分「确实没有」与「拿不到而假装没有」
数字悄悄错成本只算工具次数；JOIN 从表把他租户 attempt 计入本租户失败率；压缩 before 注水「有一行」≠「数字算对了」，要独立复算
功能空转影子能力没接线、守卫引用被测实现常量、假 Server 掩盖契约失配、Worker 未开 @EnableScheduling问「撤掉修复点会红吗」
假绿 / 假红IT 全类跳过、mvn -q 吞汇总行、陈旧报告、旧 jar 仍在运行看 XML <testcase>、skipped=0、产物 inode

14.3 三级验收

出自 docs/上下文压缩完整方案_设计与实施_v1.0.md §7.3，是项目所有功能交付的统一门槛：

级别内容合格判据（举例）
① 行为单测预算分配、水位线、增量合并、围栏注入、配置门禁、record 全参拷贝边界值、确定性、fail-closed 分支都覆盖
② 链路 E2E三条链路各跑一次真实编排（生产 Bean、真网关或可控桩）断言压缩确实发生，且事件/指标自动产出
③ 闭环真跑一次 Run 或 SSE 请求断言 usage_record 的 token 真的下降、checkpoint 真的落、下一轮真的复用、答案关键事实与未压缩版一致

配套的三条约束：守卫绝不引用被测实现自己的常量（否则实现改了守卫跟着改，等于没守）；从编排入口进，不直连端口（否则绕过接线层）；弱断言要造出挤出压力（否则永远不触发）。

14.4 反向验证（撤点 / 反证）

定义：临时撤掉刚实现的修复点，指定测试必须如期转红；复原后文件哈希一致。这是「测试是否真的有检出力」的唯一可靠证据。rag/docs/RAG-D08_评测体系与质量门禁.md 的 FR-RAG-010 更把它写成门禁条件：「每条门禁至少一条『移除该机制后转红』的用例，反证未执行视为门禁未生效」。

bashscripts/m3-context-policy-counterproof.sh（头部注释，原样节选）
# S1-M3 反证脚本：钉住 execution_snapshot.context_policy 双写入口不是假绿。
# RV-M3-01（旧直发强制写 {}）：把 JdbcAgentManageRepository 的派生值硬编码成
#   "{}"，AgentRepositoryIT#publishVersionSnapshotsContextPolicy 必须红。
#   若仍绿，说明旧直发入口其实没有写规范快照。
# … 共 RV-M3-01 .. RV-M3-06 六个独立假绿形态 …
# ⚠️ 判定：结论不变（仍全绿）或编译失败均判「无效反证」。
# ⚠️ 中断安全：SIGTERM/SIGINT 时先复原当前撤点文件再退出，
#    避免残留撤点源码造成后续静默失真。
set -u
OLD_MANAGE='        String contextPolicy = ContextPolicyReader.snapshotFromAgentConfig(definition);'
NEW_MANAGE='        String contextPolicy = "{}"; // RV-M3-01'
restore() { # 从 /tmp 备份逐个 cp 回原路径 … }

中断安全是血的教训：撤点脚本被 SIGTERM / SIGINT 打断时 finally 可能不执行，残留的撤点源码会静默失真（M10 曾残留 MAX_INJECT_HITS=16）。跑完或跑断后都要做三件套校验：old 锚点全量计数 = 1 + new 残留标记全无 + git diff --check。

未确认 仓库内没有 *-rv-*.py 文件；反向验证脚本是 scripts/*-counterproof.sh（另有 doc-c*.py 文档门禁回写脚本），RV-* 只是脚本内的锚点编号。

14.5 假绿识别清单

  • @EnabledIfEnvironmentVariable(IT_PG_URL) 有没有把整类 IT 跳过？看 skipped=0 而不是 BUILD SUCCESS。
  • 用例数是按 XML <testcase> 数出来的吗？参数化 / 嵌套下根 tests 属性会偏离。
  • 夹具是不是比被测路径更「方便」？（TST-14：手工插 execution_snapshot 导致「发布的 Agent 永远不可运行」全绿。）
  • 断言是不是同义反复？（P2：用「打算查谁」比「查到了谁」，恒不违例。）
  • 守卫是不是引用了被测实现自己的常量？
  • 单测替身是不是返回了常量 / 绕过了框架真实序列化？（TST-20：真实 HTTP 字节是 data:event: delta 二次包裹。）
  • 用的是 ai_agent(BYPASSRLS) 还是 app_agent？前者验隔离必然假绿。
  • 运行的是刚构建的 jar 吗？（inode / 构建时间线；clean 后旧进程仍在跑。）
  • AUTHZ_MISMATCH=0 是不是因为影子链根本没接线？应看 rlsDependent() 归零。
  • 「和基准库一致」是否只是「基准库本身错得很一致」？（TST-12。）
  • 假 Server 放宽了哪些对端真实校验？（跨进程契约失配。）
  • 报表数字是不是来自被 IT 污染的库？（P8：常驻实例把 IT 遗留 Run 当真活跑。）

# ⚠️ set -o pipefail 是必须的：默认 shell 是 bash -e {0}，不含 pipefail；

十条总体方法论（项目归档原文要点）

绿不等于对；能力的存在 ≠ 能力的生效；同义反复是假绿第一来源；单测替身会掩盖真问题；排除法要按读方实际查的那张表来验；基线必须绑定目标环境的实际形态且一源一份；接缝必须「插电」；跨库/跨进程契约要按对端真实校验；聚合口径污染比主表泄漏更难发现；fail-closed 贯穿三层，任何「降级即放行」都要被双层守卫堵住。出处：docs/RLS到应用层权限迁移-问题方案与方法论归档.md。

  • 两 reactor 各自 clean verify，且显式带本地 IT 环境变量
  • 运行产物 = 本轮构建；跨进程字段按对端真实校验
  • 撤点脚本跑完/跑断后做了三件套校验
