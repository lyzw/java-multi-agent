A2. 技术选型决策：备选、取舍理由、状态与未定案

这一册专门回答「为什么是这样，而不是那样」。项目里确实留下了一批有编号、有备选、有否决理由的决策记录，也留下一批被反复引用却从未真正定案的说法。把两者区分开，是接手架构评审或灰度放行的前提。

本册怎么写

每条决策按统一五段展开：要解决的问题 → 考虑过的备选 → 最终选择 → 取舍理由 / 证据 → 当前状态。状态用 已落地 / 已决策待签 / 未定案 / 已漂移 标注。凡仓库查不到结论的，全部汇总到 A2.11，不补推测。

项内容
问题v3.1 设计方案第 83 行写 Spring Boot 3.x，DEC-4 决定改用 Java 21 + Boot 4.x，偏离需留决策记录

这里有个对 Java 后端很实用的迁移提示：Boot 4 的「破坏性」主要不在 API，而在默认值与自动装配。项目因此把「配置 fail-closed」写成硬约束——缺失 / 非法配置拒绝启动，而不是给一个「能跑」的默认值。相关守卫见 §10。

A2.4 ADR-001 / DEC-12：主 MQ 为什么是 RabbitMQ 4.3.6

项内容
问题主 MQ 与投递 / 死信 / 重放策略
备选Kafka（否决）、NATS（否决）、双栈（明确禁止）
最终选择RabbitMQ 4.3.6 社区版 + Quorum Queue；Exchange agent.run.dispatch(direct,durable)、Queue agent.run.execute(quorum)、死信 agent.run.dead、x-delivery-limit=3（quorum 默认 20）
核心理由MQ 只作唤醒信号，权威事实源永远是 PostgreSQL。因此真实需求只有五项：at-least-once、幂等消费、死信、积压可观测、低资源占用——不是高吞吐日志流。Kafka 的 partition / consumer group / retention 设计、JVM+KRaft 运维负担、无内建死信，全部与「每 Run 一条唤醒消息」的量级不匹配
约束Erlang/OTP 25.0+；Khepri（Mnesia 已移除）；社区支持截至 2026-11-30；消息体仅 5 字段 runId/tenantId/attempt/fencingToken/enqueuedAt
勘误§4.1：agent.run.reconcile 队列未落地，UNKNOWN 对账走 DB 侧 ToolOperationReconciliationService，不经 MQ
残余风险P4-R022_RabbitMQ停维残余风险安全复核登记.md 评级 Accepted with conditions，其中 R-022-R2（卷丢失致已确认消息永久丢）为 Sev-0，且「无任何一项 R-022-Rx 在当前代码中被自动闭环」
一个因 yml 标量类型导致的 Sev-0

YamlPropertiesFactoryBean 会丢弃裸标量 delivery-limit: 3，队列退回 quorum 默认 20，record_weakness 最多可重复写 20 次。修复是把数值加引号并加 ApplicationConfigTest 断言。见 A3.8 案例 7。

A2.5 P4-D17：为什么又新增一条 database 消息通道

这是「决策发生演变」的最好样本：ADR-001 定下 RabbitMQ，一年内的工程实践又追加了一条等价通道，并把它设为运行期默认。

项内容
问题交换机 / quorum 队列 / 消费容器 / @RabbitListener 全部无条件装配 → CI 必须起 broker、换载体要改代码、无法按租户灰度
备选保留 rabbitmq 通道；新增 database 通道（PG 表 agent_message_queue）
语义逐条对齐至少一次；有限重试 x-delivery-limit=3 ⇄ attempts；死信 agent.run.dead ⇄ agent_message_dead_letter；背压 ready 深度 ⇄ 各租户 PENDING 行数之和
选择理由database 通道零外部依赖（PG 本就是强依赖），使 CI / 本地 / 试运营小客群无 broker 运行；切换只需改一个环境变量，可回滚
关键设计端口不变（MessageSender / MessageHandler / QueueDepthProbe）；TenantRoutingMessageSender 按 tenantId 灰度；MessagingSwitchGuard 启动期排空检查（有残留即拒绝启动）；配置一律 fail-closed
不复用 outboxoutbox_event 是发布侧事务日志（是否已交给通道），队列表是通道侧（是否已被消费）；混用会让「已发布但未消费」无法表达
运行期默认application.yml:448 → mode: "${AGENT_MESSAGING_MODE:database}"；生产跑 database 已落地
诚实边界broker 端到端 E-1/E-2/E-3 不在 CI 覆盖；DB 队列吞吐未经压测；切换不是热切；证据空白 查不到「永久以 database 取代 RabbitMQ」的决策
这条决策衍生出的 Sev-0

DB 通道按租户领取全部 PENDING 消息，而执行消息与采集消息同表。若整表交给采集处理器，已终态的 Run 会被重新执行。修复是 EventRoutedMessageHandler 按 eventType 分流（"agent.trace.collect" → TraceCollectMessageHandler），对未知类型 REJECTED 兜底，且发送侧单建独立路由键。完整链路见 A3.8 案例 4。

证据： docs/P0/P4/P4-D17_消息通道可切换.md §1–§7；application.yml:448；docs/项目进度台账.md:2302；实测「database 无 broker 时 822 项 0 跳过、0 次 broker 连接尝试」。

A2.7 ADR-013：上下文压缩统一入口与全窗口预算

这是本项目与 AI 关联最紧密、记录最完整的一份 ADR（2026-11-11，状态「已采纳」）。它同时是理解 §12 与 A3.2 的钥匙。

项内容

归因错误示范：ADR-011 到底决定了什么

错误写法：「两 reactor 两库 ⇒ 各一个 persistence 模块（ADR-011）」——v1 手册铁律表、docs/模型统一配置架构设计.md:149/262、docs/上下文压缩开发计划_v1.0.md:60/71 都这么写。
核对结果：ADR-011 全文（190 行）主题为「Java 21 + Spring Boot 4.1.1 技术基线」，不含 reactor / 两库 / persistence 字样。约束本身真实存在，但出处是：约束 C12「两 reactor 两库互不塞代码」、C1「DB 写入只在 agent-persistence」、两个 pom 各自的 <module>agent-persistence</module> / <module>rag-persistence</module>，以及模块边界守卫。
正确写法：「项目铁律 C12 / C1 + 两个 pom 的模块清单；多份文档把它归因为 ADR-011，但 ADR-011 正文无此条目」。文档冲突

同样的核对纪律适用于门禁数字：100 / 120 / 126 组反向验证是三个时点的快照；platform 3103/639 → 3110/641 → 3193/641、rag 756/65 也是不同批次。引用时带出处与日期，不要写「项目累计 126 组」而不说明口径。

证据： 本册全部结论来自 4 份 ADR、P0-D00、P4-D17、RAG-D00/D02/D05/D12、模型统一配置架构设计.md、主流Agent框架设计对比与演进建议_v3.2.md、上下文压缩G2验收签核包_v1.0.md 与两个 reactor 的 pom / yml / 源码。
