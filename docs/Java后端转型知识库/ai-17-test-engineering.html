A17. AI 测试工程与故障注入：无网络、无凭据、可证伪

A9 讲的是质量保障体系——三级验收、27 个守卫、37 个反证脚本、CI 判绿口径；本册讲更下一层、也更可复用的东西：怎么写一个 AI 系统的测试。核心矛盾是：AI 测试不能依赖真实供应商（要凭据、会抖动、行为会变），但「不依赖真实供应商」很容易滑向「测了个假的」。本册的答案是一套可执行的工程手法——故障注入式契约测试：用 Fake 网关注入七种失败形态，用假密钥把脱敏写成断言，用独立库把「隔离」变成可验证命题。

本册与 A9 的分工

A9：体系视角（有几层防线、多少个守卫、CI 怎么判绿、成熟度评估）。本册：手法视角（一个测试该怎么写、断言什么、什么该用源码扫描、什么必须上真库）。两册交叉引用不重复：A9.2 的 IT 独立库制度在这里给出工程细节，A9.4 的「守卫怎么写才不失真」在这里给出可抄的范式。

A17.1 为什么 AI 测试必须 Mock 供应商：三条硬理由与一条边界

FakeModelGateway 的类注释把「用途」写得非常克制，值得逐字读（:14-22）：

text为什么需要 Fake（FakeModelGateway.java:14-22）
用途：让契约测试能在【无网络、无真实凭据】的前提下验证
      「归一化」与「脱敏」是否正确。

若直接对接真实供应商做测试：
  · 既需要凭据（CI 无凭据环境直接跑不了）
  · 也会因供应商行为变更而使测试不稳定

边界：这是 PoC 的测试替身，【不得用于生产】。
     真实实现继承 AbstractModelGateway 并覆写 invokeGuarded。

三条理由里，第三条最容易被忽略：供应商行为变更。OpenAI 兼容不等于语义一致（A14.8 的 MiniMax tool_call_id 事故就是活例），若测试直连供应商，供应商某天改一个字段，你的测试就红了——但这不代表你的代码坏了。测试应该断言你的归一化契约，而不是供应商的当下行为。

反过来，Fake 也有一个必须守住的边界：它不能证明「真实供应商下也对」。所以本项目的分层是——Fake 测归约与脱敏（纯逻辑），真库 IT 测持久化与隔离（A17.5），真实供应商只在人工端到端走查时用一次并留下记录（A3.4 的事故就是这样发现的）。三层各证各的，谁都不冒充谁。

证据： platform/agent-infrastructure/.../model/FakeModelGateway.java:14-27。

A17.2 七态故障注入：把「供应商会怎么坏」变成枚举

FaultMode 七态与 ModelErrorKind 六分类严格对应（外加 NONE），这不是巧合而是设计要求——每一种「供应商会怎么坏」都必须有枚举值，否则那类失败就没有测试覆盖：

FaultMode模拟的真实场景对应 kindretryable实现手法
NONE正常返回——回放 cannedResponse（带 usage）
TIMEOUT上游不响应TIMEOUTtrue睡到 timeout+500ms，由外层 callWithTimeout 中断它——测的是超时控制本身，不是 sleep
RATE_LIMITED429 限流RATE_LIMITEDtrue异常消息含 api-key=<FAKE_SECRET>
PROVIDER_ERROR500 内部错误PROVIDER_ERRORtrue异常消息含 Authorization: Bearer <FAKE_SECRET>
INVALID_REQUEST上下文超限 400INVALID_REQUESTfalse「context length exceeded」——重试无意义
UNAUTHORIZED401 密钥错UNAUTHORIZEDfalse「invalid api key: <FAKE_SECRET>」
CONTENT_BLOCKED内容拦截CONTENT_BLOCKEDfalse「content blocked by safety policy」

注意三种故障（RATE_LIMITED / PROVIDER_ERROR / UNAUTHORIZED）的异常消息里刻意塞了假密钥，这是下一节要讲的证明法。已实现

证据： FakeModelGateway.java:30-45（FaultMode）、:70-105（七态实现与异常文案）。

A17.3 用假密钥证明脱敏：把安全属性写成可执行断言

这是本册最值得抄走的一个范式。传统做法是「code review 检查脱敏逻辑有没有漏」，问题是：你无法证明它覆盖了所有路径。本项目的做法是把不可证伪的「我们做了脱敏」变成可证伪的断言：

java假密钥证明法（FakeModelGateway.java:47-48 + :83-98）
// 1. 在测试替身里放一个已知的假密钥
private static final String FAKE_SECRET = "sk-fake1234567890abcdefghijklmn";

// 2. 让它在异常消息里以真实泄露形态出现
case RATE_LIMITED:
    throw new ModelGatewayException(ModelErrorKind.RATE_LIMITED,
            "HTTP 429 rate_limit_exceeded; api-key=" + FAKE_SECRET);
case UNAUTHORIZED:
    throw new ModelGatewayException(ModelErrorKind.UNAUTHORIZED,
            "invalid api key: " + FAKE_SECRET);

// 3. 契约测试断言：任何对外可见的字符串都不含 FAKE_SECRET
//    （日志、safeMessage、异常 message、审计字段…逐面检查）
//    → 若脱敏被绕过，测试立刻失败

这个范式的三个要素缺一不可：① 假密钥必须是可识别的形态（sk- 前缀，能被 A14.6 的双正则匹配）；② 必须出现在真实泄露会出现的那个位置（异常 message，而不是随便一个字段）；③ 断言必须覆盖所有对外出口（ModelGatewayContractTest 对应 AT-MODEL-002「秘密不出现在日志」）。

推广：这套手法不限于密钥

同一个思路可以证明任何「不该出现的东西不出现」：租户 A 的 tenantId 不出现在租户 B 的响应里（越权）、学生 PII 不出现在日志里（合规）、压缩态正文不出现在审计可信面（A15.3 的标量审计）。用一个哨兵值 + 全出口断言，把「应该不会」变成「证明不会」——这是 AI 系统里最划算的测试投资，因为这类泄露一旦发生不可撤销。

证据： FakeModelGateway.java:47-48, 83-98；ModelGatewayContractTest.java（AT-MODEL-002 映射，类注释 :23-35）。

A17.4 错误归一化契约矩阵：六分类 × retryable 的断言表

契约测试的组织方式本身就是知识：ModelGatewayContractTest 用 @Nested 把断言按验收项分组，每条对应 P0-D04 的一个验收 ID（AT-MODEL-001 / AT-MODEL-002）。这种「验收 ID ↔ 测试类」的映射让「哪条验收没有测试」变成可查的。

断言项验证什么为什么这条重要
normalCall正常响应带 usage，且 totalTokens() 等于 input+outputusage 是 A11.3 结算的唯一输入；丢了或算错，账目静默失真
timeoutNormalizedTIMEOUT 且 retryable()==true超时无副作用，可退避重试
rateLimitedNormalizedRATE_LIMITED 且可重试唯一「应该重试」的限流类失败
providerErrorNormalizedPROVIDER_ERROR 且可重试5xx 通常是暂时性
invalidRequestNotRetryableINVALID_REQUEST 且 retryable()==false最关键的一条：误标为可重试 = 无限重试烧钱（A14.5）
unauthorizedNotRetryableUNAUTHORIZED 且不可重试密钥错，重试只会再错
contentBlockedNotRetryableCONTENT_BLOCKED 且不可重试同样内容同样被拦

给 Java 后端的迁移提示：这个矩阵的结构比内容更值钱。任何「把外部异常翻译成本地枚举」的适配层都该有这样一张表，且每个枚举值都要有测试——覆盖率低的适配层，坏就坏在没人测的那个分支上。

证据： ModelGatewayContractTest.java:44-80+（@Nested 分组与逐条断言）；ModelGateway.java:31-50（六分类定义）。

A17.5 流式与一次性路径的语义同源：别让两条路径各坏各的

Fake 网关同时实现 ModelGateway（一次性）与 ChatStreamGateway（流式），注释点明一条纪律（:114-115）：

text流式故障语义必须同源（FakeModelGateway.java:113-116）
⚠️ 错误语义必须与 invokeGuarded 同源：
   故障模式【先归一化抛错】，否则回放罐头响应
   （作为单个增量实时回吐，再返回整包）。

反例后果：
   流式路径把 TIMEOUT 当成「正常返回了空内容」
   → 前端显示一个空答案 + done，用户以为模型没话说
   → 而一次性路径同一场景会抛 TIMEOUT
   → 两条路径对同一故障给出不同结论，排查时必然走错方向

这条纪律的一般形式：当同一能力有两条实现路径（同步/异步、一次性/流式、本地/远程），必须有一条测试锁定「失败语义一致」。不能只测成功路径的同构。

证据： FakeModelGateway.java:107-140（streamChat 的 switch 逐态归一化）；MiniMaxModelGatewayStreamTest.java。

A17.6 IT 独立库与守门写法：把「隔离」变成可验证命题

集成测试最大的假绿来源是与运行实例共用库。scripts/it-env.sh 的头注释记录了一次真实教训：

text为什么必须换库（scripts/it-env.sh:6-17）
在此之前，IT 与运行实例共用一个库（agent_dev），于是：
  · IT 往 t-a 灌 Run/快照 → 运行实例的调试数据被污染
  · 运行实例的常驻 worker 会抢 IT 造的 Run → 报「任务未被领取」
  · execution_snapshot 有 forbid_snapshot_mutation 触发器、物理删不掉
    → 所以污染【不可逆】（实测 t-a 累积 1018 Run / 139 快照）

正解不是「记得清理」，而是【换库】：IT 跑 agent_it，agent_dev 只服务运行实例。
并把最容易回归的那一步做成 fail-closed：
  ⚠️ 目标库与应用库同名时【直接拒绝】
  —— 「IT 又浇回 agent_dev」不再靠人记。

三个可迁移的设计点：① 「记得清理」不是工程方案（触发器让清理都不可能），换库才是；② 把纪律做成 fail-closed 断言（同名即拒绝），而不是写进文档靠自觉；③ 守门变量（IT_PG_URL / IT_RAG_PG_URL）缺失时整类跳过——但这正是 A17.8 要盯的假绿入口，所以 CI 必须断言「跳过数不超上限」。

RAG 侧同理且更严格（scripts/rag-it-env.sh）：本地 Docker 容器 study_rag_it 与 ragdb / study_rag 完全分开；三条专用角色——rag_it_app（NOBYPASSRLS，业务断言一律走它）/ rag_it_admin（BYPASSRLS，seed 清理）/ rag_it_ops（BYPASSRLS，运维通道）。用超级用户跑租户隔离测试会得到「隔离失效」的虚假结论——这条坑 CI 注释里也写了一遍。

证据： scripts/it-env.sh:1-40、scripts/rag-it-env.sh:1-30；.github/workflows/ci.yml:85-95（非特权角色注释）。

A17.7 源码级守卫的边界：什么能用源码扫描、什么必须上真库

ReingestDisciplineGuardTest 是一份罕见的「诚实守卫」——它在注释里主动声明自己的局限（:15-25）：

text源码扫描守卫的自我声明（ReingestDisciplineGuardTest.java:15-25）
⚠️ 为什么用源码扫描而不是行为测试：
  真正的验证需要「同一片段写两次 → 查 text_jieba 是否为空」，
  这要求一个带 pgvector 的真库 IT。

  源码级断言【无法证明运行时正确】，但能【廉价地挡住最危险的回退】——
  有人把 ON CONFLICT DO UPDATE ... text_jieba = '' 删掉或改回纯 INSERT。

  行为级 IT 在有库环境时补（见计划文档 S2-5 的验收判据）。

它守的是三个字面断言：方法内必须含 ON CONFLICT (chunk_id) DO UPDATE、必须含 text_jieba = ''、INSERT 列清单必须显式含 text_jieba,。背后的真实事故：D04 §5.4 记录「改了切分规则但检索没变」——根因是重灌不清 text_jieba，而索引判据是 text_jieba='' OR 无向量行，于是旧片段永远不被重新嵌入。

能且适合用源码扫描必须上真库
「某段 SQL 片段还在不在」（防回退）「同一片段写两次后 text_jieba 真的是空」（行为正确性）
「某个守卫数组是否被注释成空」（A12.6 的 GUARDED_TABLES）「触发器真的拦住了 UPDATE」（AuditChainIT）
「领域层有没有偷偷 import Spring」（AgentCorePurityTest）「RLS 对非特权角色真的生效」（用 app_agent 跑）
源码守卫最大的风险：它自己变成假绿

源码扫描断言的是「文本存在」，不是「逻辑正确」。若有人把 text_jieba = '' 挪到一个永不执行的分支里，守卫照样绿。所以本项目的纪律是：源码守卫只能当「防回退的锁」，不能当「功能正确性的证明」，且必须配一条真库 IT 兜底（S2-5）。这与 A9.7「11 层防线、成熟度 B-」的评估口径一致。

证据： rag/rag-persistence/src/test/.../ReingestDisciplineGuardTest.java；platform/agent-core/.../AgentCorePurityTest；docs/问题记录 D04 §5.4。

A17.8 CI 的四条反假绿纪律：pipefail、跳过数上限、job 职责分离、非特权角色

CI 文件头记录了一次「从未真实运行过」的教训（2026-10-22 实测修订），三个缺陷全是假绿形态：

yaml反假绿四件套（.github/workflows/ci.yml:10-18, 60-110）
① pipefail —— 否则 mvn | tee 吞掉退出码
   GitHub Actions 的 run: 默认 shell 是 bash -e {0}，【不含 pipefail】。
   `bash -e -c 'false | tee /tmp/x; echo $?'` → 0
   即：构建失败该步骤仍报绿。
   修复：run 开头显式 `set -o pipefail`

② 跳过数上限 —— 否则「全跳过了」也显示通过
   unit-test job 不提供 IT_PG_URL → 249 项 IT 被整体跳过，
   界面依旧显示「构建与单元测试 ✅ 通过」——绿得没有意义。
   修复A：unit-test 只跑到 package（不跑 verify），IT 交给独立 job
   修复B：断言 skipped ≤ 60（已知需库集合 25，超出即有测试被误门禁）
   修复C：断言 ran ≥ 480（低于基线说明环境退步，而非「测得少说明代码好」）

③ job 职责分离 —— 需要库的测试不能混在无库 job 里

④ 非特权角色 —— 集成测试应用连接用 app_agent，不用 superuser
   超级用户绕过 RLS，用它跑租户隔离测试会得到「隔离失效」的虚假结论

第 ② 条最有普适价值：「跳过」必须被当成一种失败来治理。JUnit 的 @EnabledIfEnvironmentVariable 守门很方便，但它让「测试没跑」和「测试通过」在界面上看起来一样。加一条上限断言，就把这个盲区堵上了。注意注释里的实测数据：无库场景锚定行尾后计数 180（未锚定时 366，因为逐类明细行也被计入）——计数脚本本身也要防止数错。

证据： .github/workflows/ci.yml:1-30（设计要点与三缺陷）、:60-110（pipefail / 上下限断言）、:200+（非特权角色创建）。

A17.10 本册的未落地与证据边界

项状态说明
真实供应商契约的自动化回归未落地真实端到端只在人工走查时跑（如 2026-10-28 MiniMax 那次）；无 CI 内 nightly 真打供应商的 job
流式路径的完整故障矩阵测试部分覆盖Fake 的 streamChat 已逐态归一化，但断言覆盖度未逐态核对
真库行为 IT 补齐源码守卫计划中ReingestDisciplineGuardTest 自称「行为级 IT 在有库环境时补（S2-5）」，该 IT 是否已存在未逐条核实
供应商行为漂移的检测未落地供应商改协议（如 tool_call_id 形态变化）只能靠线上事故或人工走查发现，无自动探针
迁移提示：AI 测试的三条可复用骨架

① 故障用枚举——每一种「外部会怎么坏」都该有一个枚举值和一条断言，缺一个就是缺一块覆盖；② 安全用哨兵——把「不该出现的东西」具化成已知值，再对全出口断言，比 code review 强得多；③ 跳过要计数——「没跑」和「通过」在 CI 界面上长得一样，必须用上限断言把它们分开。
