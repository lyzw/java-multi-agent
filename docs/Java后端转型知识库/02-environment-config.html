5.1 配置从哪里来：三层模型

图 5-1　配置的三层来源（依据 env.example、application.yml、seed_model_catalog.sql）

一个非常容易踩的点：model_catalog 不是 yml 配置项，而是库表（平台库全局表、无租户、无 RLS、不含密钥）；网关密钥只从 AGENT_MODEL_MINIMAX_API_KEY 环境变量注入。想「改配置」时先判断它属于哪一层。

5.2 env 文件的格式纪律

三份 env.example 共同声明的硬约束

只允许 KEY=VALUE 与 # 注释；不写 export / $(...) / if…fi；值不加引号——IDEA 的 EnvFile 插件不剥引号，会给值原样加上引号。典型症状：jwt.env 里公钥被带引号后，大台登录正常、调 RAG 全 401（Base64 校验失败）。

复制与生成的标准动作：

bash仓库根目录
cp platform.env.example platform.env
cp rag.env.example rag.env
scripts/gen-jwt-keys.sh           # 生成 jwt.env（0600，含两域私钥 + RAG 两个公钥）
scripts/gen-jwt-keys.sh --check   # 与运行中平台的 JWKS 比对，确认两侧配套
chmod 600 platform.env rag.env jwt.env

需调整 传统项目里常把配置写进 application-dev.yml 并用 spring.profiles.active 切换。这里 rag 侧确认没有任何 Spring profile（无 application-{profile}.yml、无 @Profile），功能开关全部是 @ConditionalOnProperty；platform 侧的 SPRING_PROFILES_ACTIVE=dev 主要用于 JWT 私钥的开发态放行，不能当环境切换机制理解。

不要再新增增量 patch 脚本——那正是 2026-11-01 收敛掉的东西。活库等价 ALTER 目前以 07_*.sql 等形式存在（如 07_execution_snapshot_context_policy.sql、07_model_catalog_context_upgrade.sql），且均声明 IF NOT EXISTS 幂等。

6.3 角色体系：谁可以做什么

角色库RLS 属性用途绝不能
app_agentagent_devNOBYPASSRLS（@Primary 数据源）所有业务 SQL，租户隔离的实际执行者用 ai_agent 代替它验隔离（会假绿）
ai_agentagent_devBYPASSRLS / ownerDDL、迁移、带外运维出现在业务 SQL / RLS 验证中
platform_opsagent_devBYPASSRLS（平台域）/api/platform/v1/** 与 PLATFORM 作用域发布填进 SPRING_DATASOURCE_USERNAME
agent_retentionagent_dev凭据隔离保留期清理任务用于业务查询
rag_appstudy_ragNOSUPERUSER + NOBYPASSRLS检索与租户档语料换成 owner 账号（启动自检拒启）
rag_opsstudy_ragLOGIN + BYPASSRLS全局语料治理通道，最小授权 13 项与主数据源同名；手工 GRANT（04 是「先 REVOKE ALL 再 GRANT」的自收敛脚本）
RLS 验证的铁律

验隔离要用 app_agent / rag_app；用 ai_agent（BYPASSRLS）会得到「隔离失效」或「隔离有效」的假结论。FORCE RLS 下未绑定租户的删/查会静默返回 0 行；FORCE RLS 表判空必须先绑租户，否则是假空。此外 ON CONFLICT DO UPDATE 需要额外 UPDATE 权限，新幂等 upsert 必须同步授权并补 SchemaDriftIT。

7. 启动步骤、验证与联调

7.1 一键方式（最快）

bashscripts/dev-env-up.sh（内部依次做：PG + RabbitMQ + 自检 + 冒烟 + 打包）
./scripts/dev-env-up.sh                  # 全量
./scripts/dev-env-up.sh --smoke-only     # 只跑纯领域冒烟（最快）

# 冒烟测试单独跑（纯领域对象、零连接，用于验证概念理解）
mvn -o -pl agent-core test -Dtest=QuickstartDemoTest

7.2 分步启动（推荐理解顺序）

  1. 准备配置：复制三份 env.example 并填值；scripts/gen-jwt-keys.sh 生成 jwt.env；chmod 600。见 §5.2。
  2. 起依赖服务：RMQ_MIRROR=docker.1ms.run ./scripts/dev-rabbitmq.sh start，然后 ./scripts/dev-postgres.sh start；用各自的 status 确认。
  3. 初始化库结构：scripts/init-db.sh platform|rag …（或本地容器脚本 dev-postgres.sh start 已幂等应用 01 快照 + 种子 + 授权）；核对 ./scripts/dev-postgres.sh verify。
  4. 本地账号（可选）：./scripts/dev-seed.sh --list 查看；租户账号与平台账号是两套，平台账号用 dev-seed-platform-users.sh --commit。口令一律通过环境变量传入。
  5. 构建：cd platform && mvn -o clean verify 与 cd rag && mvn -o clean verify；只打包用 mvn -o -pl platform-bootstrap -am package -DskipTests。
  6. 启 platform：scripts/dev-backend.sh（读 platform.env + jwt.env，跑 -exec.jar）。
  7. 启 rag：scripts/dev-rag.sh [端口]（默认 8081）；如需异步入库/索引，另起 rag-worker 进程。
  8. 启前端：cd frontend && npm run dev（:5173）与 cd admin-console && npm run dev（:5180/admin），二者按需启动。
  9. 联调验证：按 §7.4 的判据逐项确认，最后跑一次跨服务检索或 SSE 请求。

7.3 两个 jar：一个必须避开的命令陷阱

文档冲突 已由产物 MANIFEST 实证

platform-bootstrap 的 spring-boot-maven-plugin:repackage 配了 <classifier>exec</classifier>（为保证 failsafe 的 @SpringBootTest 能读到类）。因此 target 下有两个 jar：

  • platform-bootstrap-1.0.1-SNAPSHOT.jar（约 164 KB）＝ thin jar，MANIFEST 无 Main-Class，不能直接 java -jar；
  • platform-bootstrap-1.0.1-SNAPSHOT-exec.jar（约 42 MB）＝ 可执行 fat jar，Start-Class: …PlatformApplication。

而 docs/本地启动指南.md §0 / §4.1（2026-10-19 实测版）给出的启动命令用的是不带 exec 的名字；platform-bootstrap/pom.xml 的注释却写「部署时使用带 exec 后缀的包，见 docs/本地启动指南.md」。两者自相矛盾。现行正确命令以 scripts/dev-backend.sh 为准。

bash正确的手工启动方式（与 scripts/dev-backend.sh 等价）
set -a; source ./platform.env; [ -f ./jwt.env ] && source ./jwt.env; set +a
"$JAVA_HOME/bin/java" -jar \
  platform/platform-bootstrap/target/platform-bootstrap-1.0.1-SNAPSHOT-exec.jar \
  --spring.profiles.active=dev --server.port=8080

# rag 侧没有 classifier，主构件本身即 fat jar（约 28 MB，MANIFEST 有 Main-Class）
set -a; source ./rag.env; [ -f ./jwt.env ] && source ./jwt.env; set +a
"$JAVA_HOME/bin/java" -jar \
  rag/rag-bootstrap/target/rag-bootstrap-1.0.1-SNAPSHOT.jar \
  --server.port=8081

另一条相关纪律：运行中的 jar inode 必须等于磁盘上的 jar。clean 之后旧进程仍在跑旧代码，任何「我已经改了、怎么没生效」的结论都要先按构建时间线核对。这也是 dev-backend.sh 开头注释「为什么不用 IDE 启动」的原因。

7.5 前端代理顺序与同源约束

两份 vite.config.ts 都明确写了同一条纪律：/api/v1 代理必须排在 /api 之前，否则 RAG 请求被前缀匹配抢到 8080 → 404。默认值：

前缀frontend 目标admin-console 目标
/api/v1VITE_DEV_RAG_API_TARGET ?? http://127.0.0.1:8081VITE_DEV_RAG_TARGET ?? http://127.0.0.1:8081
/api、/actuatorVITE_DEV_API_TARGET ?? http://127.0.0.1:8080

后端 SecurityConfiguration 为 cors.disable()，因此前端不能独立域名直连，必须走 devServer 同源代理；绝不可为图方便给后端开 cors.allowOrigins("*")（令牌在 Authorization 头）。切换后端地址用 VITE_DEV_API_TARGET=http://… npm run dev。
