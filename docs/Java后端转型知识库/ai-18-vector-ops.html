A18. 向量库运维与索引代际：维度契约、蓝绿重建与嵌入一致性

A7 讲的是语料怎么进来（PDF → 解析 → 切分 → 入库），A1.6 讲 Embedding 与向量列的基本概念。本册讲向量怎么活下来：维度为什么是契约而不是常量、换模型怎么做到零停机、后台构建 Worker 的四条纪律、中文全文检索为什么要在应用侧预分词。这是 RAG 系统上线后运维频率最高的一块——换模型、重建索引、补向量、清残留，每次都在这个面上。

本册与 A7 / A1 的分工

A7：语料流水线（解析、切分、入库、检索准入、十条文档失真）。A1.6：Embedding 概念与「4096 维建不了索引」这个坑的一句话结论。本册：向量列与索引的工程细节——`VectorColumn` 为什么被建模成 record、代际状态机怎么转、构建 Worker 为什么没有分布式锁。

A18.1 维度是契约不是常量：从「写库时才炸」到「启动即失败」

VectorColumn 的类注释记录了一次真实的认知升级（:9-19）：

text为什么把维度显式建模（VectorColumn.java:9-19）
此前代码把 vector(1024) 当【常量】，于是「换一个大维度模型」的
表现是【写库时才炸】：
  · 索引流水线会逐条失败
  · 查询向量的维度不符也只会被 PG 拒绝
  · 错误信息离根因很远（expected N dimensions, not M）

现在：
  · 维度来自 EmbeddingPort.dimension()、类型来自配置
  · 两端（写入 SQL 的 cast、查询 SQL 的 cast）都用同一个对象
  · 并在【发请求给数据库之前】校验维度

这是传统 Java 后端最能共鸣的一类改进：把一个魔法数字提升为领域对象。收益不只是可读性——record VectorColumn(String type, int dimension) 在构造器里就做了两件事：类型白名单校验（cast 要拼进 SQL，绝不接受任意字符串）、维度必须为正。于是错误在装配期就暴露。

requireDimension(float[] vector) 的错误文案本身是运维资产，值得完整引用：

textrequireDimension 的错误文案（VectorColumn.java:65-77）
向量维度与列 halfvec(4096) 不符：实际 1024 维。
三者必须同时改：嵌入模型、rag.embedding.dimension、
rag_chunk_embedding.embedding 的列类型（并全量重建索引）。

它把「改哪里」直接写进异常。对比 PG 原生报错的 expected 4096 dimensions, not 1024——后者只告诉你结果不符，不告诉你该改三处。好的错误消息是写给凌晨三点被叫起来的人看的。已实现

证据： rag/rag-persistence/.../persistence/VectorColumn.java:9-81；VectorColumnTest.java。

A18.2 halfvec 4000 维上限与「能存不能索引」：一个必须摊开的取舍

text维度上限与索引能力（VectorColumn.java:19-36）
维度上限（pgvector 0.8.x，HNSW / IVFFlat 索引）：
  vector   → 2000 维
  halfvec  → 4000 维

超过上限仍可【存储】，但【建不了 ANN 索引】
→ 稠密检索退化为全表精确扫描 → 语料规模一大就是瓶颈

本项目实测配置：qwen3-embedding:8b / 4096 维 / halfvec
→ 4096 > 4000 → rag_chunk_embedding_hnsw_idx 【刻意不存在】

这个取舍在 DDL 里有完整记录（01_rag_ddl.sql 约 :957-966），而且是把旧定义留档注释掉而不是删除：

sql被刻意注释掉的 HNSW 索引（deploy/sql/rag/01_rag_ddl.sql:957-966）
-- ⚠️ 本索引在 halfvec(4096) 下【刻意不存在】（2026-10-28 换真实嵌入模型）：
--   pgvector 的 HNSW/IVFFlat 对 halfvec 只支持到 4000 维（vector 2000 维），
--   4096 维能存不能建 ANN 索引，稠密检索退化为全表精确扫描。
--   当前语料量级（数百片段）下精确扫描既快又无召回损失；
--   规模化后再二选一：MRL 截断到 ≤4000 维，或改用二进制量化（bit 可到 64000 维）。
--   旧定义留档：USING hnsw (embedding public.vector_cosine_ops) WITH (m='16', ef_construction='64')
-- CREATE INDEX rag_chunk_embedding_hnsw_idx ON rag.rag_chunk_embedding USING hnsw (embedding public.halfvec_cosine_ops) WITH (m='16', ef_construction='64');
「刻意不存在」与「忘了建」在执行层面完全不同

把索引定义注释掉并写下三段理由（为什么不存在 / 现在为什么可以 / 将来怎么解决），远优于删掉它。删除会让下一个人（或半年后的你）以为「性能优化没做」而盲目加上索引，然后建不出来或建了也没用。取舍必须留痕，否则取舍会重开。三条后续路线也写清了：MRL 截断到 ≤4000 维 / 二进制量化（bit 类型可到 64000 维）/ 换回小维度模型——A1.6 的「三条路都还没做」即指此。

判断是否需要索引的运维口径：先看语料规模。数百片段量级下全表精确扫描比 HNSW 更快且无召回损失（ANN 是近似算法）；到万级片段再考虑改。不要因为「向量检索就该有 HNSW 索引」而提前优化。

证据： deploy/sql/rag/01_rag_ddl.sql:955-973；VectorColumn.java:19-36, 49-56；问题记录/09-RAG与检索质量.md RAG-04。

A18.3 嵌入端口：批大小、超时与「每条向量都要校验」

OpenAiCompatibleEmbeddingPort 对接任何 OpenAI 语义的 /embeddings（BGE-M3 网关、Ollama、vLLM --task embed）。三处实现细节：

项取值 / 行为理由
批大小DEFAULT_BATCH_SIZE = 16网关普遍对请求体大小敏感；embed() 按批切分并汇总
超时DEFAULT_TIMEOUT = 120s本地大模型首 token 前排队可能很慢，给足但不无限
API Key 缺省空时填 "empty"Ollama 不校验 key，但 OpenAI 协议的 Authorization 头不能是空值
端点归一容忍有无 /v1 与尾斜杠，统一成 <base>/embeddings减少「配置写法不同就调不通」的支持成本
维度校验构造期要 expectedDimension，并对每一条返回向量校验长度一条维度不符的向量会让整个事务回滚 → 索引流水线里意味着「静默少索引一批 chunk」

为什么是「每一条」而不是「第一条」：批量接口理论上可能对个别条目返回异常长度（网关实现差异）。校验第一条只能证明网关大体正确，校验每一条才能保证没有一条脏数据进库——而脏数据进向量表的后果是索引流水线静默少一批，比直接报错更难查。

证据： rag/rag-infrastructure/.../embedding/OpenAiCompatibleEmbeddingPort.java:36-107；另有 LocalDeterministicEmbeddingPort.java（无外部依赖的确定性实现，供离线测试）。

A18.4 蓝绿代际：BUILDING / ACTIVE / RETIRED 状态机

换嵌入模型最危险的动作是「原地改列」。不同模型的向量空间不可比，旧向量不会被新查询向量正确命中——你会得到「检索恒低分且不报错」。解法是代际（generation）：新旧向量并存，新代际在后台建好再切换。

text代际状态机（IndexGeneration.java:19-24）
BUILDING ──构建完成──▶ ACTIVE ──被新代际替换──▶ RETIRED
   │                      ▲                        │
   └──── 不可直接激活 ─────┘                        └── 可回到 ACTIVE（回滚）

「回滚」= 把一个 RETIRED 代际重新置为 ACTIVE，
        同时把原 ACTIVE 置为 RETIRED。
【任何时刻每个租户至多一个 ACTIVE】——这是检索「只读一个代际」的前提。

表结构（09_v1_0_3_index_generation_alter.sql:33-60）的关键列：tenant_id / generation / embed_model / dimension / status / indexed_chunks / total_chunks / scope，主键是 (tenant_id, generation)，状态有 CHECK 约束。注意 dimension 列的存在理由写得很好：「换模型若变维度，此列让『列维度 vs 期望维度』的不符在切换前就被发现」——把 A18.1 的启动期校验延伸到了代际元数据。

为什么改主键而不是新建一张向量表

迁移注释说得直白：若拆表，「每次换模型都要新建一张『向量表』并改检索 SQL —— 那才是真正的灾难」。改主键为 (tenant_id, chunk_id, index_generation) 后，检索只需多一个 AND e.index_generation = <当前代际> 谓词。一个谓词 vs 一套动态表名，这个取舍决定了系统能不能长期维护。

证据： rag/rag-core/.../indexing/IndexGeneration.java:19-103；deploy/sql/rag/09_v1_0_3_index_generation_alter.sql:1-60。

A18.5 索引构建 Worker：四条纪律与「为什么没有分布式锁」

改造前的形态：POST /index-generations/{g}/build 在 HTTP 线程上一次性跑完全部片段——数万片段阻塞数十分钟，进程重启后进度丢失、无法续跑。现在的形态：

textWorker 轮询 + 分批推进（IndexGenerationBuildWorker.java:19-46）
HTTP 端点：只创建 BUILDING 代际，立即返回
worker  ：每 2 秒问一次「有没有待构建的代际」→ 处理一批 → 释放

⚠️ 四条关键纪律：
① fixedDelay 而非 fixedRate
   一批可能跑数秒到数分钟，fixedRate 会让下一轮追赶上一轮，堆积并发线程

② 异常绝不让线程死掉
   单批失败只记日志并跳过，下一轮重试——
   否则一次数据库抖动会永久停止所有代际构建（且表面无异常）

③ 租户清单由配置显式给出
   worker 以非特权角色连接，rag_index_generation 受 RLS FORCE 约束，
   未设会话租户【读不到任何行】。跨租户扫描会「看起来在跑、实际永远领不到」

④ 全局桶走独立通道
   清单里出现全局哨兵时调 buildGlobalBatch，其写连接是 BYPASSRLS 的
   运维角色且不设会话租户。把哨兵填进 app.tenant_id 会让 rag_current_tenant()
   直接抛错（V8 封堵「租户伪装成平台身份」）

第 ② 条是 Spring @Scheduled 的经典坑：定时任务里抛未捕获异常，调度器可能停止该任务的后续触发——一次抖动永久停摆，而且没人知道。第 ③ 条是 RLS + 定时任务的组合坑：非特权角色 + FORCE RLS + 未设会话租户 = 查询恒空，日志上「什么都没发生」。

为什么没有分布式锁

注释里的取舍很清晰：多 worker 实例可能同时捡到同一个代际，当前依赖幂等——upsertEmbeddingForGeneration 是 ON CONFLICT DO UPDATE，重复嵌入同一片段只是浪费算力，不会产生错误数据。代价是算力浪费，收益是不引入额外中间件（与 RAG-D02「零新增中间件」一致）。若后续 worker 多副本且算力敏感，应改为「按代际号取模分片」而非加锁。

这个判断值得学习：不是所有并发都需要锁。当操作天然幂等且重复代价可接受时，不做协调是更简单的正确答案；但必须把「什么条件下这个判断会失效」写清楚（多副本 + 算力敏感 → 改分片）。

证据： rag/rag-worker/.../IndexGenerationBuildWorker.java:1-120（含 @Scheduled(fixedDelayString = "${rag.generation.build.poll-interval-ms:2000}", initialDelayString = "10000") 与可空 IndexGenerationBuilder 降级）。

A18.6 重灌纪律：text_jieba 与 embed_model 两个必须同时更新的列

索引流水线的待索引判据是 text_jieba='' OR 无向量行。由此推出两个极容易踩的坑，每个都有真实事故：

坑机制后果
重灌不清 text_jieba改了切分规则但重灌时 text_jieba 保持非空 → 判据认为「已索引过」→ 旧片段永远不被重新嵌入「改了切分规则但检索没变」（D04 §5.4 记录）。ReingestDisciplineGuardTest 守的就是这条
换模型不更新 embed_modelembed_model 是「这批向量出自哪个模型」的代际标识；不同模型向量空间不可比旧向量不会被新查询命中 → 检索恒低分但不报错

正确写法（JdbcCorpusRepository 的 saveChunkAndEmbedding / upsertEmbedding）：ON CONFLICT (chunk_id) DO UPDATE 时同时写 text_jieba = '' 与 embed_model = EXCLUDED.embed_model。守卫测试断言的就是这两个字面片段（A17.7 讲了源码守卫的适用边界）。

证据： rag/rag-persistence/.../JdbcCorpusRepository.java（saveChunkAndEmbedding / upsertEmbedding）；rag/rag-persistence/src/test/.../ReingestDisciplineGuardTest.java；问题记录 D04 §5.4。

A18.7 中文全文检索：为什么必须在应用侧预分词

PG 的 to_tsvector('simple', 中文整段) 不会按词切分——它会把整段当一个 token，全文检索等于失效。本项目的解法是：应用侧先用 jieba 预分词，把结果存进 text_jieba 列，再对该列建 GIN 索引：

sql预分词的全文索引（deploy/sql/rag/01_rag_ddl.sql:973）
CREATE INDEX rag_chunk_jieba_idx
    ON rag.rag_chunk USING gin (to_tsvector('simple'::regconfig, text_jieba));

三个设计后果：① text_jieba 是派生列，分词规则一变就必须重灌（A18.6 第一个坑的由来）；② 写入路径必须保证「有向量必有分词」或反之，否则判据失效；③ 检索时查询词也要用同一套分词，天然与 A1.7 的 RRF 混合检索配合——全文通道与稠密通道的量纲不同，所以用 RRF 而不是分数加权。

证据： deploy/sql/rag/01_rag_ddl.sql:973；docs/Agent记忆机制分析与设计方案.md:857（同款说明）；A1.7 RRF 与门禁。

A18.8 换模型的完整操作顺序：一个可执行的 Runbook

把前面各节串成一次真实操作。任何一步顺序错了都会导致「检索静默退化」：

text换嵌入模型 Runbook（依据 VectorColumn / IndexGeneration / 09 alter 的纪律）
① 先确认新模型维度
   若 > 4000（halfvec）或 > 2000（vector）→ 该模型无法建 ANN 索引
   → 记下「将退化为全表扫描」，评估语料规模能否接受

② 改配置三处【必须同时】
   rag.embedding.model / rag.embedding.dimension / vector-type
   ⚠️ 只改一处 = 启动期 requireDimension 失败（这是好事，比静默错好）

③ 建新代际（BUILDING），不碰 ACTIVE
   让后台 Worker 分批构建；期间旧代际继续服务 → 零停机

④ 观察构建进度：indexed_chunks / total_chunks
   worker 崩溃会留痕（日志），但不会自动停止其它代际

⑤ 构建完成后切指针：新代际 ACTIVE、旧代际 RETIRED
   ⚠️ 每租户至多一个 ACTIVE（状态机硬约束）

⑥ 验证：抽检若干查询，确认分数分布恢复正常区间
   若恒低分 → 大概率是查询向量与索引向量不同源（配置漂移）

⑦ 保留旧代际一段时间以便回滚
   回滚 = RETIRED 重新置 ACTIVE，原 ACTIVE 置 RETIRED

⛔ 绝不做的三件事：
   · 原地 UPDATE 向量列（旧向量会被新查询命中错乱，且无法回滚）
   · 先改查询侧再改索引侧（期间全部查询恒低分）
   · 换模型后不重建索引就宣布完成
第 ⑥ 步为什么必须是「抽检」而不是「跑一轮看看」

维度不符、模型不同源、代际指针错，这三种错的共同表现都是「检索能返回结果，但分数普遍偏低」——不报错。只有把分数分布与历史基线对比（A3.6 的检索质量静默退化）才能发现。运维上这意味着：换模型必须有前后对比的分数基线，否则「切换成功」只是「切换完成」。

证据： 综合 VectorColumn.java:65-77（三处同改）、IndexGeneration.java:19-24（状态机）、09_v1_0_3_index_generation_alter.sql:1-60（改主键与上线顺序）、01_rag_ddl.sql:955-966（索引取舍）。

A18.9 与 pgvector 扩展的交互：启动自检与「官方镜像陷阱」

pgvector 是PG 扩展而非 Java 依赖（A1.6 的一句话结论在此展开）：postgres:17 官方镜像里执行 CREATE EXTENSION vector 会失败，必须用 pgvector/pgvector:pg17。启动自检直接查系统表：

sql启动自检口径（RagStartupSelfCheck）
SELECT extname FROM pg_extension WHERE extname = 'vector'
→ 查不到即 fail-closed 拒绝启动，而不是「先跑起来再说」

记忆模块的 PgVectorAvailability 采用了相反策略：探测不到就 WARN + 降级（P2 向量召回是增强功能，不是 Run 的必要条件，见 A13.9）。同一个「pgvector 不可用」，在 RAG（核心能力）是 fail-closed，在记忆（增强能力）是 fail-soft——降级策略由能力的必要性决定，不由技术栈决定。

证据： rag/rag-persistence/.../bootstrap/RagStartupSelfCheck.java:96-100；platform/agent-persistence/.../memory/persistence/PgVectorAvailability.java:115,123。

A18.10 未落地与证据边界

项状态说明
ANN 索引（HNSW / IVFFlat）刻意不存在4096 维 > halfvec 4000 上限；当前语料量级下全表扫描更快且无召回损失。规模化需三选一（MRL 截断 / 二进制量化 / 换小维度模型），均未做
cross-encoder 重排器仅选型bge-reranker-v2-m3 已选但未接入；当前「重排」= RRF 融合分 + 版本惩罚（A1.7）
分布式锁 / 按代际分片未实现（当前靠幂等）多 worker 可能重复嵌入同代际；单副本下无害，多副本 + 算力敏感时应改分片
代际清理策略未确认RETIRED 代际「可保留用于回滚，也可清理」，但自动清理的保留期与触发条件未在代码中找到明确实现
rag 侧 SSE 进度流文档冲突rag-api/pom.xml description 写「SSE 进度流」，但 rag 全树无 SseEmitter 实现——进度靠 HTTP 轮询（§20.1 第 7 行）
迁移提示：向量库运维的四条通用原则

① 维度当契约——魔法数字提升为领域对象，在发库请求前校验，错误文案直接写「改哪三处」；② 换模型走代际——旧向量原地改写等于不可回滚的赌注，双代际并存才能零停机 + 可回滚；③ 定时任务防停摆——fixedDelay + 异常不外抛 + RLS 租户显式给，三条缺一条就「看起来在跑、实际永远不动」；④ 派生列要防陈旧——text_jieba / embed_model 这类派生列，重灌时必须一并失效，否则判据会认为「已完成」。
