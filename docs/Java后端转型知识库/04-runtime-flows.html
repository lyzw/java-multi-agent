11.3 三处必须自己能说清的一致性边界

  1. Run 与 Outbox 的事务边界：为什么不能先发消息？答案见 §2.2 与 OutboxPublisher 类注释「消息发出前进程崩溃 → 任务永久丢失且无任何报错」。
  2. 消息与状态的信任边界：MQ payload 不是事实源，Worker 回库重读；同时 OutboxPublisher.publishOne 在发送前复核 tenantId，防止仓储实现出错造成跨租户发布。
  3. 终态与并发的边界：fencing token、终态不可迁出、影响行数断言、崩溃恢复扫描，四者一起防脑裂与重复执行。

// ⚠️ 租户归属复核（P4-D05 / I-D05-1）：仓储若忽略 tenantId 参数返回了别的租户的行，

11.4 端到端验证清单（不要只看「Run 建出来了」）

  • 用真实 HTTP 发布链路创建 Agent 版本，再建 Run（不要手工插 execution_snapshot 夹具 —— TST-14 的教训）。
  • Run 状态确实从 QUEUED → RUNNING → 终态，且抵达过真实模型调用或可控网关。
  • execution_snapshot 写出 agent_version / config_version / authz_version / effective_closure 四字段（DAT-01 事故的验证口径）。
  • usage_record 的 token 与 cost_amount 真的入账，且不是「工具次数 × 固定值」的代理值（P0-3b 事故）。
  • 跨租户验证：用 t-a / t-b 各造一条，确认互不可见；用 app_agent 而非 ai_agent。
  • 撤点反向验证：临时移开一个关键机制，指定用例必须转红，复原后 md5 一致。

12. 请求级 SSE 与上下文压缩链路

12.1 五条执行链路的定位

链路形态入口上下文特点
L1异步 WorkerRunExecutionLoop服务端持久化快照；全窗口预算
L2请求级 SSEAgentChatOrchestrator后端无状态 + 前端内存维护多轮 history；不存正文
L3控制台直连ConsoleChatController平台链纯 LLM 多轮
L4子 AgentWorkerChildAgentRunner不继承父 checkpoint；首轮锚独立 pinned
L5语义路由ModelAgentRouterLLM 选 Agent + 白名单校验 + fail-closed

与其混淆的还有两层「路由」：agent-routing 的 RoutingEngine 是纯函数规则转发引擎（按 ordinal 首个 TRUE 命中，只选目标不做准入）；ModelAgentRouter 才是入口级语义路由。两者不是一回事。

12.2 SSE v1.1 协议与两条链

项平台链租户链
路径/api/agent/chat/stream/api/knowledge/agent/chat/stream
消费前端admin-console（AI 实验室）frontend（辅导台 Agent 对话）
thinking 帧可下发恒丢弃
请求体 tenantId—禁止携带（白名单拒收并留痕）
Outbox / MQ都不写、都不发
审计begin() 写 RUNNING → finish() 按 fencing token 收敛，影响行数≠1 必抛

协议 v1.1 只做追加，不改任何 v1 帧的一个字节：冻结 14 个事件字典，新增第 14 事件 context.checkpoint，线序 answer → usage → context.checkpoint? → done；done 是应用层终帧。客户端 carry-over envelope 默认不落库，用独立 HMAC 校验；SEND/STOP/RETRY 必须把旧 state 展开，不能丢字段。

另有一条 Run 事件流 GET /api/runs/{runId}/events：服务端 SseEmitter + 500ms 轮询、30min 超时，前端用短连接 + 3s 轮询续传（Last-Event-ID），不用 EventSource——因为它不能带 Authorization 头，令牌放 query 会落访问日志。

12.3 上下文压缩管线与硬不变量

agent-context 是零 LLM / 零 IO 的纯算法层：CompactionPipeline 按 W1 外置 → W2 裁剪 → W3 增量摘要三段执行；四级水位线由 ContextBudget / BudgetAllocator 决策；RagHitQuota 负责 RAG 命中配额（chunkId 去重 → 确定性全序 → 动态 top-k → 单块截断 → 引用也扣预算）。

不变量含义为什么重要
稳定前缀不压缩systemPrompt 基段 + toolSchemas 逐字保留；记忆/裁剪说明/摘要块后置为带围栏的 USER 消息保证前缀缓存命中；不可信内容不进 systemPrompt
关闭态逐位等价开关 false 时返回 legacyRequest 同一引用，零策略/预算/指标/事件G1「影子对照零差异」放行条件
硬顶与引用扣预算压缩后 after ≤ budget，且 chunkId+locator 引用也计入防止「正文减了、引用又涨回来」
严格净省before 按含重复的全量命中计算，末级 tie-break 确定性防止用注水的 before 数字伪造收益
首轮锚 pinned、L4 不继承父 checkpoint任务锚独立固定；子 Agent 用自己的首轮防止多轮压缩把原始任务挤掉
净成本守恒saved = (before − after) × price_input − summaryCost；连续 N 次 ≤0 自动降为 TRIM_ONLY 并告警「token 变少」不等于「成本变低」

三级回滚路径：enabled=false → strategy=OFF → TRIM_ONLY。影子期严禁改变任何模型请求字节。

12.4 门禁、里程碑与当前状态

上下文压缩方案定义了阶段 S0–S6 / 门禁 G0–G6 / 里程碑 MS-1–MS-6，通用完成门槛 G-a～G-j（含三级验收、反向验证、fail-closed）。与本手册最相关的三道：

门禁通过条件（文档口径）禁止事项
G1影子对照零差异 + TL / QA 签核本阶段禁止改变压缩行为或请求字节
G2三级验收在 L1 闭合 + QA 签核任一真库 IT 用 ai_agent 跑过即判假绿重跑
G3SSE 100 轮压测 + 协议兼容报告 + QA / FE 签核跨进程契约失配不允许用假 Server 掩盖

未确认：当前各门禁的正式签署结论。仓库中 docs/上下文压缩G2验收签核包_v1.0.md 是 G2 证据汇总入口，rag/docs/RAG-D09_阶段门禁与主平台接入计划.md（早期版本）写「三道门禁全部未通过」；工作区进度记录则称 G1 / G2 已对话确认放行、G3 待 TL/QA/FE 落签。以签核包与实际签署记录为准，本手册不代替门禁结论。

项目里有多套 G 编号，引用必须带出处

上下文压缩 G0–G6、RAG-D09 的 G1/G2/G3（建设阶段，无连字符）、RAG-D07 的 G-1～G-5（语料准入）、RAG-D08 的 G-1～G-9（CI 门禁）、P0 的 GATE-1/2/3（模型零保留）。rag/docs/RAG-D09 §0.3 明确要求「跨文档引用必须带出处，裸写 G-1 视为引用不完整」。同理 S 编号也有上下文压缩 S0–S6 / RAG 录入 S1–S2 / RAG-D09 R1–R3 三套。

13. RAG 链路：从 PDF 到可溯源答案

13.1 两个进程、两套连接、一条共享库

项rag-bootstrap (8081)rag-worker
职责检索面 + 管理面 HTTP异步入库、切分、向量化、索引代际
驱动方式HTTP 请求@Scheduled 轮询 PG FOR UPDATE SKIP LOCKED
扫描包5 个包，刻意排除 worker仅 cn.studykid.rag.worker
共有配置同一 study_rag 库；rag.embedding.* 与 rag.ops.* 必须逐项一致

rag-worker 不提供 Web 容器，也没有 MQ 依赖；「不引入第二套 MQ」是 RAG-D02 的明确选型。若 Worker 没起来，表现是上传成功但 ingest-jobs 永远 PENDING，而 HTTP 服务健康检查正常。

13.2 入库到检索的七步

  1. 上传 / 登记来源：POST /api/v1/management/sources、/documents（multipart，256MB 上限）、/documents/preview（上传前 dry-run 解析预览）。三层去重预检：DUP_SOURCE / DUP_EDITION / DUP_CARRIER。
  2. 建 IngestJob：一次处理尝试一条事实记录，重试新建一行、旧行永久留痕；Worker 轮询领取。
  3. 版面解析：DoclingDocumentParserPort（HTTP 到 :5001）/ MinerU MiddleJson；输出是带版面结构的块序列而非纯文本；BlockRoleResolver 判定片段角色（正文/例题/习题/答案册…）。
  4. 切分：IngestionPipeline 结构优先、语义兜底；rag.premise.enabled 灰度切换到 rag-premise 的 BlockChunker SPI；chunk_policy 留痕。
  5. 向量化与索引：OpenAiCompatibleEmbeddingPort（/embeddings）→ ChunkIndexer / IndexGenerationBuilder；chunk 与 embedding 必须同事务写入；中文预分词写 text_jieba 供 tsvector 词法通道。
  6. 检索七步：RetrievalOrchestrator ①知识点解析 ②多路召回（稠密 <=> + 词法）③版本过滤 ④角色过滤 ⑤知识点补全 ⑥排序（RRF 融合分 + 版本惩罚）⑦分数门禁。过滤条件是硬过滤，不是排序偏好。
  7. 接地生成 / 引用：GroundedGenerationService 校验 hitIds → 复用检索闸门 → 逐字装配（generator=EXCERPT_ASSEMBLY）或 LLM 接地合成；引用必须指向可核验位置，依据不足输出「依据不足」，disclaimer 必须随 answer 展示。

13.3 教辅语料的四个特有约束

约束落地违反后果
版本五轴学科 × 学段/年级 × 册次 × 出版社 × 修订版次；缺一轴不可入库；EditionScope 三档 STRICT / PREFERRED_WITH_FALLBACK / CROSS_EDITION跨版本串答案
片段角色 + 泄题闸门答案类内容为独立 ChunkRole，检索期硬过滤，EXPLAIN 模式不进 prompt泄题（比答错更严重）
权威等级与准入状态机TrustTier 连续分级；VERIFIED 是入索引必要条件且只能由人工签发（自动链路终点恒为 PENDING / IN_REVIEW）伪造证据 / 自动放行
分数门禁rag.retrieval.min-score（标定值 0.38，与模型+语料绑定）；低于阈值即「未找到依据」拒答成为非法输出 → 幻觉

索引代际蓝绿：BUILDING → ACTIVE → RETIRED，换嵌入模型时构建新一代再切换，检索只读 ACTIVE；代际构建已从 HTTP 同步改为 Worker 轮询分批（RAG-D22/D23），并有 scripts/e2e-index-generation.sh 端到端演练。

13.5 跨服务契约：最容易「假绿」的地方

platform 通过 HttpRagRetrievalGateway（地址来自 agent.rag.base-url）调用 /api/v1/retrieval。已登记的真实事故：假 Server 允许空 revisionCode=""，单测全绿，而真 rag 拒空串 → 检索 500 → 降级为空命中；修复值改为 "未指定"。

跨进程契约的通用纪律

凡是跨进程 HTTP 的字段，必须按对端真实校验取值，而不是按本端 mock 的宽松程度。联调时至少做一次「两个真进程 + 真实字节」验证；空命中必须区分「确实没命中」与「下游 500 后被降级成空命中」——后者是静默失真，正是 §14.2 定义的典型形态。

RAG 命中回到 platform 后，经 PromptGuard.wrapToolResult("rag", …) 作 user 消息注入；scenario 只认 run.input_payload.scenario，不从正文派生。
