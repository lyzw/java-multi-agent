A11. 租户级成本治理与 Token 计费：已落地的金额账 vs 仅设计的 Token 配额

LLM 系统把「成本」从运维指标变成了业务账目：每一次模型调用都要在正确的租户、正确的 Run、正确的操作上记一笔，且重复消费不能重复计费。本册先讲清楚仓库里真正跑起来的金额账（预算三表 + 单价表 + 真实 token 计量），再专门用一节指出：那份看起来很完整、标题叫「租户级 Token 计费系统设计方案」的文档，其规划的三张表和全部 TokenQuota* 类在代码库里一行都没有落地。把这两件事分开，是本册最重要的纪律。

先读这条事实边界

仓库里存在两套东西：① 已落地（源码 + DDL 可证）——金额预算三表 budget_account/budget_reservation/usage_record、模型单价配置 agent.pricing.models、真实 token 计价（P0-3b 成本入账改造）。② 纯设计、零落地——docs/租户级Token计费系统设计方案_v1.0.md（状态：待评审）规划的三张新表 tenant_token_quota/tenant_token_account/token_quota_reservation、全部 TokenQuota* 类与 agent.billing.* 配置键。全库 grep 这些标识符只命中该文档自身；结构快照仍是 71 表 / 44 RLS / 52 策略，不是文档期望的 72/45/53。培训与交接时只把 ① 当现行事实。

A11.2 usage_record 事实账：字段、幂等与租户隔离

public.usage_record 是「已计量（metered）」的权威事实表。建表在 01_platform_ddl.sql:3024–3038，字段如下：

字段类型 / 默认含义
usage_iduuid PK主键
tenant_iduuid NOT NULL租户隔离键，FORCE RLS
run_iduuid NOT NULL归属 Run
step_iduuid 可空当前恒 NULL：写入 SQL 未含该列（已知缺口，见 A11.10）
operation_iduuid 可空逻辑操作幂等键，来源 modelCallId(runId,attempt,ordinal)
model_idtext NOT NULL模型 ID
input_tokens / output_tokensbigint DEFAULT 0真实 token，CHECK 非负
cost_amountnumeric(18,6) DEFAULT 0金额，币种默认 CNY
reservation_iduuid 可空关联的预留流水；无预留的「只计量」路径为 NULL

幂等靠部分唯一索引 idx_usage_operation_once UNIQUE (tenant_id, operation_id) WHERE operation_id IS NOT NULL（行 4529）。写入只用一条 SQL（JdbcBudgetRepository.insertUsageOnce，行 448–479）：

sqlplatform/agent-persistence/.../JdbcBudgetRepository.java 行 452–460（节选）
INSERT INTO usage_record
  (tenant_id, run_id, operation_id, reservation_id,
   model_id, input_tokens, output_tokens, cost_amount, currency)
VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?)
ON CONFLICT (tenant_id, operation_id) WHERE operation_id IS NOT NULL DO NOTHING
RETURNING usage_id

注意这里用了 RETURNING——因为 usage_record 对 app_agent 有 SELECT + RLS；「禁 RETURNING」铁律只针对 authz_decision_log（该表仅 INSERT、显式 REVOKE SELECT），不要张冠李戴，详见 A12.5。所有写入都经 inTenantTx() 绑定租户（行 887–892），每条 SQL 带 WHERE tenant_id = ?::uuid，符合 RLS 铁律。currency 取 BudgetPort.SETTLEMENT_CURRENCY = CNY。

「一次性写明细」而非「累加」

每次模型调用写一行明细，不在 Repository 里做 token「累计」。真实 token 由 RunExecutionLoop.settleModelCost 从 response.usage() 取出后传入；累计成本体现在 budget_account.settled_amount 的逐级累加。ModelPricing 不在这里计算，只接收上层 actualAmount 原样写入（行 473）。

A11.3 一次模型调用的成本时序：预留 → 结算 → 释放

成本链路在 RunExecutionLoop.java 里有三个明确的钩子，对应「调用前 / 调用后 / 失败」三态：

阶段方法 / 行行为
调用前预留reserveModelCost :862–873按保守上界预留：reservedInput = estimatedInput × INPUT_TOKEN_ESTIMATE_SAFETY_FACTOR（因子 2），输出按 agentConfig.maxTokens()；预留被拒 → commitFailure(...,"BUDGET_EXHAUSTED")
调用后结算settleModelCost :923,1717–1730有预留走 budget.settle(...)（预留全额扣回、只计实结额）；无预留走 budget.recordModelUsage(...)
失败释放releaseModelCost :899,911模型调用异常时释放预留；llmCalls++ 仅成功后计

operation_id 必须确定性且含 attempt：modelCallId(runId, attempt, ordinal) = UUID.nameUUIDFromBytes((runId + "|" + attempt + "|" + ordinal).getBytes(UTF_8))（行 1630–1634）。Javadoc 强调「必须确定性、必须含 attempt，否则重复计费或漏记」——attempt 每次领取 +1，使同一 Run 的重试落在不同的 operation_id 上，既避免重复扣费，又不漏记真实的多次调用。

A11.4 模型定价配置：per-1k 单价与方括号字面键

先澄清一个易混淆点：docs/模型统一配置架构设计.md 讲的是 model_catalog（模型目录 + 密钥/目录分离 + ModelResolver），该表没有定价字段。定价是另一套独立机制，落在 application.yml 的 agent.pricing.models（行 514–547），计价单位每千 token（per-1k），币种 CNY。

yamlplatform/platform-bootstrap/src/main/resources/application.yml 行 530–547（节选）
agent:
  pricing:
    models:
      fake-model: { input-per-1k-tokens: "0", output-per-1k-tokens: "0" }
      gpt-4o:     { input-per-1k-tokens: "0.018", output-per-1k-tokens: "0.072" }
      qwen-max:   { input-per-1k-tokens: "0.02",  output-per-1k-tokens: "0.06" }
      "[MiniMax-M2.5]":            # ← 点号模型名必须用方括号字面键
        input-per-1k-tokens:  "0.002100"
        output-per-1k-tokens: "0.008400"
点号模型名必须写 "[MiniMax-M2.5]"

根因：MiniMax-M2.5 含点号，裸键会被 Spring Binder 拆层成 MiniMax-M2 + 子键 5。症状极其隐蔽：业务 Run 成本静默按 0 记、L2 judge 因查不到单价而拒调，且两者都不报错。必须写成方括号字面键。守卫 ApplicationConfigKeyAlignmentTest#dottedModelIdKeepsItsPricing（行 203–228）与 L2ProductionGuardTest（行 157–165）锁死此约定。这也是工作记忆里的高频坑之一。

读价与计算：装配在 WorkerExecutionConfig.modelPricingPolicy()（行 832–858），用 Binder.get(environment).bind("agent.pricing.models", Bindable.mapOf(String.class,Object.class)) 读 raw map 再 ModelPricingPolicy.of(raw)，空表告警。匹配顺序是精确 → 最长前缀（如 gpt-4o-2024-08-06 命中 gpt-4o）→ default 兜底，查不到返回 empty 而非 0 元（ModelPricingPolicy.java:33–37,123–149）。计算在 ModelPricing.cost()（行 62–74）：in = inputPerThousandTokens × inputTokens / 1000，各自 HALF_UP, SCALE=6 后相加，与列精度 numeric(18,6) 对齐。

单价是占位价，不是报价

platform/platform-bootstrap/src/main/resources/application.yml 行 532–534 自述「以下为占位价，上线前必须按供应商最新报价替换；换模型必须同步改这里——没有第二处真相源」。培训里引用的 0.002100 / 0.008400 是冻结价示例，不是供应商当前报价，不要拿去算真实账单。

A11.5 记 0 的诚实语义：未配价与上游不回 usage

项目对「算不出成本」采取的是如实记 0，不报错也不估算，而不是拍一个估值填进去。这有两处来源：

场景行为证据
模型未配单价recordModelUsage 路径：reservation_id=NULL，成本记 0，token 如实记，只计量不扣款JdbcBudgetRepository.java:490–493,497–535
上游不回 usageusage.path("prompt_tokens").asLong(0) / completion_tokens.asLong(0) → ModelPricing.cost(0,0)=0，账上记 0OpenAiCompatibleModelGateway.java:365–366；ModelPricing.java:52–56
查不到定价ModelPricingPolicy.pricingOf 返回 Optional.empty()（非 0 元），调用侧决定记 0 行为ModelPricingPolicy.java:33–37

回归测试 RunExecutionLoopModelCostTest.unpricedModelStillRecordsTokens（行 303）断言：未配价时 token 如实记 500/100、cost=0、reserveCalls=0。这是「成本记 0」的有意设计而非 bug；但它也意味着配额若仅依赖 usage 回传会被绕过——设计文档因此规划了保底结算 usage-missing-floor-tokens，但该配置与代码均未落地（见 A11.10）。

A11.6 分账铁律：judge 成本绝不混 usage_record / cost_amount

与 A10.6 呼应，从成本账本这一侧再看一次：评估判分模型的调用必须独立科目，绝不写业务账。

科目承担者落账位置
业务 Run 成本BudgetPort / JdbcBudgetRepositoryusage_record、cost_amount、budget_account.settled_amount
L2 judge 成本EvaluationCostBudget（SUBJECT="EVAL_JUDGE_COST"）进程内预留/结算快照，不写 usage_record / cost_amount / 业务指标端口
机器判分结论L2AttributionEvaluator只写 agent_trace_metric.attribution_correct，不写 agent_eval_sample

共享的是单价（"[MiniMax-M2.5]" 的冻结价），不是账本。物理隔离由 L2ProductionGuardTest.judgeCostIsPhysicallyIsolatedFromBusinessCost 用源码断言保证（行 137–166）。宽表 agent_trace_metric 冗余的 input_tokens/output_tokens/cost_amount 是派生口径（给监控面板用），不是账本真相；真相在 usage_record。

迁移提示：从「记日志」到「记账」

传统后端把「调用外部服务的消耗」记进日志或监控，错了最多影响图表。这里它变成带幂等键、租户边界、预留—结算—释放语义的账目：重复消费不能重复扣费（operation_id 含 attempt）、跨租户读不到（FORCE RLS + 非特权验证）、算不出就如实记 0（不估算）、评估成本另立科目（EVAL_JUDGE_COST）。可复用的是事务与唯一约束；必须新建的是「每一笔钱都能对上到底是哪次模型调用」的可追溯性——这也是为什么 A10 和本册都反复强调分账。
