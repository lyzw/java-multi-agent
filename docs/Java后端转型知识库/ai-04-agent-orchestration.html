A4. 多级 Agent 编排与路由：从委派状态机到规则转发引擎

这是本项目 AI 能力里结构最复杂、文档与代码口径差最大的一块。它回答三个问题：一个 Agent 如何把任务委派给子 Agent（编排与状态机）、委派链里「选哪个子 Agent」如何变成确定性规则（RouteAgent 规则转发）、以及 Agent / Skill / Tool / MCP 四类能力如何用一套配置与权限体系统一管理。本册以代码事实为准，把「文档自称未上线、代码其实已实现」的口径差逐条摊开。

本册最重要的一条口径纠偏

docs/多级 Agent优化/10_RouteAgent规则转发设计.md 头部写「状态：设计方案候选；未上线，无兼容包袱，可重建模型」，但同一批文档的 §9 实施表 S0–S6 全部标 ✅，代码里 platform/agent-routing/ 模块（RoutingEngine + 6 个测试类）真实存在，00 号文档 :360 也写明「路由策略的内容模型…已由 10 号设计定稿并实现（第三十八批消解）」。结论：把「设计候选」误读为「未实现」会低估系统能力；把「已实现」误读为「生产可用」会踩到 P3 门禁未闭环的坑。两种误读本册都会标出来。

证据基线：docs/多级 Agent优化/00_修订说明与评审决议项.md（决议与批次状态权威表）、06_配置数据模型与生命周期设计.md、07_执行链集成设计.md、08_安全测试与验收矩阵.md、10_RouteAgent规则转发设计.md、11_RouteAgent请求示例模拟.md、docs/Agent - Skill- Tool -MCP 统一配置与权限管控体系.md、docs/P0/P1/ADR-012_委派调用状态机与取消语义.md，以及 platform/agent-routing/、platform/agent-core/、platform/agent-application/、deploy/sql/platform/ 源码。三档标注：已实现（有代码/测试/真库 IT）/ 仅设计（文档描述）/ 证据空白（查不到）。

A4.1 先分清三层概念：编排、路由、能力配置

新人最容易把这三层混成一件事。它们各自解决不同问题，落在不同模块，失败模式也不同：

层解决的问题核心代码落点失败时的典型症状状态
① 编排与委派父 Agent 把子任务交给谁、状态怎么流转、取消/超时/预算怎么算agent-application/orchestration/DelegationExecutor.java
agent-core/orchestration/AgentInvocationStatus.java		子调用卡在 UNKNOWN、跨进程崩溃后无人接管、终态被重写已实现
② 规则路由委派链内「按策略规则选哪个子 Agent」，要求确定性、可重放agent-routing/RoutingEngine.java
PredicateEvaluator.java / PublishGuards.java		同一输入路由到不同目标、谓词报错被当成「不命中」已实现
③ 能力配置与权限Agent / Skill / Tool / MCP 的定义、发布、绑定、授权agent-core/cap/EffectiveClosure.java
agent-application/cap/ConfigPublishWorkflowService.java		能力存在但不生效、发布头选错版本、越权启用工具已实现（灰度开关默认关）
还有一个容易被混进来的第四层：入口级语义路由（L5）

ModelAgentRouter.askModel()（agent-worker/.../agentchat/ModelAgentRouter.java:26，ROUTER_MAX_TOKENS=192）是入口级路由：把顶层候选 Agent 的 id / 名称 / 描述放进一次无工具的模型调用，由 LLM 选一个，再做严格白名单校验，否则 fail-closed。它和 ② 的 RoutingEngine 不是一回事：后者是委派链内部的纯函数规则引擎，模型零参与。前者消耗 token、单独计量、不进压缩预算（见 A1.2、§12.1 的 L5）。

A4.2 委派调用状态机：ADR-012 冻结的是「现状」，不是新设计

ADR-012_委派调用状态机与取消语义.md:30 原文：「本 ADR 不改任何实现：它冻结的是现状，不是新设计……逐条一致，无需改动」，决策日期 2026-10-25，状态「已决策」。这类 ADR 的读法与常规不同——它是对既有代码行为的契约化封存，所以「ADR 已决策」不等于「某天有人实现了它」，而是「代码本来就这样，以后不许偏离」。

text七态封闭集合（AgentInvocationStatus.java，MultiAgentSchemaIT 断言恰好七态）

   │                 └──timeout───▶ TIMED_OUT    （终态）

UNKNOWN ──adopt/reconcile──▶ 上述终态之一   （不是终态，是「待对账」）
语义点规则（ADR-012 定位）为什么容易错
取消 ≠ 撤销:52-62 取消是请求语义，不保证外部副作用回滚；已发生的子调用结果按对账处理调用方以为 cancel 后「什么都没发生」，实际工具可能已执行
UNKNOWN 五类触发:81-101 明确列出哪些情况只能收敛到 UNKNOWN（如响应丢失、凭证过期无法判定）把 UNKNOWN 当成 FAILED，或当成 SUCCEEDED「猜一个」
接管三步:107-117 在途委派被新 Worker 接管需满足 fencing / 租约 / 状态条件裸奔的跨进程接管会让两个 Worker 同时推进同一个子调用
预算处置矩阵:119-130 不同终态下预留额度如何释放 / 结算失败也占额度、或成功没结算，都会让成本账悄悄错
验收绑定08_安全测试与验收矩阵.md:486-494 MA-T24a～T24i 每条绑定既有用例，如 MA-T24f=DelegationExecutorTest#expiredFencingTokenMustNotAcceptResult只跑新增测试、不跑绑定的既有用例，会漏掉状态机被改坏的回归
与 ADR-012 配套的 Sev-0 铁律

终态后禁止补 attempt（写入口 fail-closed）；run_step 必填 fencing token；状态收敛用三态 CAS（AgentInvocationPort.markTerminal），影响行数不等于 1 必须抛异常，否则会静默把「别人已经收敛的终态」再改一次。这些与 §10.2 编码红线、A3.8 静默失真案例 是同一套纪律在不同层次的体现。

A4.3 RouteAgent 规则转发：纯函数引擎 + 发布期静态守卫

RouteAgent 是设计文档里的角色名，不是 Java 类名（证据空白：全仓 find platform -iname "*RouteAgent*" 无结果）。它的工程落地是独立 Maven 模块 platform/agent-routing/，pom.xml:14-17 自述「RouteAgent 的规则转发引擎（10 号设计）：封闭谓词文法 + 确定性求值 + 有界 DNF 规范化 + 发布期静态守卫 V1-V10」，且零框架依赖，决策必须是纯函数 f(策略版本, 规范化输入, 拓扑)。

引擎只选目标，不做准入

RoutingEngine.java:18-22：「本类只负责『选哪个目标』，不负责『这个目标允不允许』」——拓扑包含、固定版本、逐跳授权、深度/次数/超时/预算属于阶段⑤，由调用方 DelegationExecutor 执行。

把「选择」和「准入」分开，才可能让规则引擎保持纯函数、可重放、可单测。

四条铁律（RoutingEngine.java:31-38）

① 按 ordinal 升序，首个 TRUE 命中；② Truth.ERROR 永不等于命中（谓词求值出错≠规则匹配）；③ RULES_ONLY 模式不消费模型候选；④ 纯函数，不读时钟/环境/IO。

③ 和 ④ 是「同一策略可重放」的前提，也是 RoutingReplayIT 8 例能成立的基础。

mode语义（10 号设计 :99-111）代码
RULES_ONLY纯规则引擎决策，模型零参与RoutingMode.java
RULE_FIRST规则优先，规则不命中时才用模型候选RoutingEngine.adoptCandidate()
SEMANTIC目标由模型按 §3 契约选定RoutingMode.java:33
发布期静态守卫 V1–V10 与「有界 DNF」

规则策略在发布前会被静态展开与校验（10_…md:203-230，代码 PublishGuards.java + PublishGuardsTest.java）。关键点：DNF（析取范式）展开有界——超过 4096 个乘积项即拒发，避免组合爆炸；V10 不得跳过 V4–V6。重放不变式 :264：「(policyRef, canonicalInputSha256) → finalTarget 唯一」，由 RoutingReplayIT 8 例钉死。这套设计把「规则引擎的不确定性」在发布期就消灭掉，运行期只做确定性求值。

11 号「请求示例模拟」暴露的 6 个缺口，后来都关了

11_RouteAgent请求示例模拟.md:547-556 用一次完整请求走查，暴露 G-1 input_digest/output_digest 恒 NULL、G-2 trace_id 写成 runId、G-3 configVersion 硬编码 0、G-4 input 可缺省、G-5 additionalProperties 字符串比较、G-6 未知字段拒收未实现。10_…md:403 S0 标 ✅「§8 六个缺口 G-1~G-6…S3 的硬前置」，说明它们在进入运行期实现前被当作硬前置修掉。这是「文档走查 → 缺口登记 → 实现关单」的一条完整可追溯链。

有材料写「六张 cap_* 表」，但 06 号设计实际列 7 张（其中一张叫 execution_capability_snapshot、不带 cap_ 前缀），DDL 快照则含 16 张 cap_* 表。三处口径都不同。培训时建议直接说「V1 设计定义 7 张核心表，DDL 已扩展到 16 张 cap_* 表，以 01_platform_ddl.sql 为准」。
