A3. 特殊 AI 问题处理：现象、根因、定位、修复、验证

这一册是十六册里最贴近日常开发的一册。它讲的不是「AI 概念」，而是这个项目真实踩过、并且留下了证据的特殊问题：上下文爆窗、提示词注入、跨进程契约失配、成本账目污染、检索静默退化、假绿测试。每条都按「现象 → 可能原因 → 定位方式 → 解决方案 → 验证步骤」五段式给出，并附可回溯的文件路径。

和第五篇的分工

第五篇 §14–§17 是通用排查方法论与全类诊断表（启动、权限、DB、消息、测试…）；本册只讲 AI 链路特有的失效形态，并向第五篇反向链接。两册配合用：先用 §15 定层，再来本册找机制。

A3.1 总纲：AI 系统的主要失效形态是「不报错」

传统后端的 bug 通常会留下异常、5xx、回滚日志。AI 链路里，很多问题只表现为「数字偏了一点」「看板空了一块」「检索永远没结果」「功能看起来在跑但什么也没做」。本仓库把它们统一叫 静默失真（Silent Distortion），并归成六型：

型表现典型触发本册章节
静默 0 行SQL 执行成功、影响 0 行、无任何异常FORCE RLS 未绑租户 / LIMIT 退化A3.8 案例 1
静默回滚外层看到「成功」，写入全丢PG aborted 事务被 fail-soft 吞掉后 COMMITA3.8 案例 2
静默降级返回 200 但结果是空 / 兜底值跨服务 500 → 捕获 → 空命中；未知 provider → Fake 网关A3.4
数字悄悄错成本按 0 记、抽样覆盖率虚高、压缩净省失真点号模型 ID、机器判分混入人工表、单价缺失A3.5
功能空转服务健康、日志正常、任务永远不推进缺 @EnableScheduling；采集消息无人消费A3.8 案例 4/9
假绿 / 假红测试全绿但功能是空的；或真测试被残留数据挤出假 Server、BYPASSRLS、固定 usage、夹具残留A3.7

因此本仓库形成了一条硬纪律：「有一行」≠「数字算对了」，「测试全绿」≠「功能正确」。任何 AI 链路改动都要过三级验收（行为单测 → 链路 E2E → 真跑闭环），并进行反向验证（撤掉修复点必须转红）。见 A3.7。

证据： docs/问题记录/README.md §「静默失败分类 M1–M4」；docs/上下文压缩完整方案_设计与实施_v1.0.md §7.3；docs/Java后端转型培训手册.html §14.2（v1 归档，内容已并入第五篇）。

定位方式：不要从「模型返回了什么」倒推，要从「实际送出去的 ModelRequest 有多少 token」正推。这正是 G2-b 门禁 D43 的要求：OFF / TIERED 双臂必须在同一 Spring 上下文里，按 HeuristicTokenCounter.count(RequestContextProjection.project(request)) 对真实送出请求计费，禁止固定 usage 桩。

解决方案：把 ContextBudgetTrimmer 升级成单一内核 ContextAssembler，口径改为全窗口 + 四级水位 + 增量结构化状态 + 可逆引用。

text四级水位线 W0–W3 + HARD（上下文压缩完整方案 §2.3）
W0   usage < 0.60                      不动作
W1   usage ≥ tierSnipRatio(0.60)        TOOL 结果外置（仅当归档行 token 严格少于原文）
W2   usage ≥ triggerRatio(0.70)         整轮裁剪，目标 = targetRatio(0.40) × window
W3   usage ≥ 0.90 或 W2 后仍超预算       最多一次 LLM 摘要（TIERED 策略）
HARD usage ≥ 1.00 或 pinned 溢出        fail-closed，绝不 clamp

策略：OFF / TRIM_ONLY（只 W1+W2，零 LLM） / TIERED（默认）
失败阶梯：W3 失败 → 回落 W2 且 fallback=true → 绝不伪造摘要

L1–L5 五条链路的边界必须分清，否则会把「SSE 的压缩态」错误套到 Worker 上：

RAG 命中配额（RagHitQuota）是压缩算法里最容易被低估的一块。五个动作内聚在纯算法层：① 按 chunkId 去重保留全序最优候选 → ② 确定性二次排序 score desc → locator → chunkId → text → ③ 按 token 配额动态 top-k（非固定条数）→ ④ 单块正文截断到 maxHitTokens → ⑤ 放不下的只留 chunkId + locator 引用。三条硬不变量：硬顶 afterTokens ≤ tokenBudget（引用也扣预算）、严格净省（beforeTokens 按含重复的原始全量算）、确定性全序（末级 tie-break 到 chunkId / text）。已实现（17/17 行为测试 + 7/7 守卫 + RV-201…210 撤点反证）

文档冲突 「三条硬不变量」的第 ③ 条在 ADR-013 D37 写作「引用严格比原文便宜才保留」，实施记录 §9.2 与代码 Javadoc 写作「确定性全序」。三处都自称「三条」，引用时务必带出处，不要合并成一句。另：签核包 / 实施记录时点记为「纯算法内核、零生产接线，L2 SSE 仍用 MAX_INJECT_HITS=8 / MAX_HIT_TEXT=1200」；交付时工作区另有未提交的 D51 薄适配（RagHitQuotaPort + RagHitQuotaAdapter 已接入编排器），关闭态与失败仍回退 legacy 固定口径。未确认 是否已启用须现场核对，详见 A2.12 时点差异。

SSE v1.1 协议（第 14 事件）是压缩态跨请求传递的契约。字典顺序为 run.start / route / rag.query / rag.hits / skill / tool / handoff / thinking / delta / answer / usage / error / done / context.checkpoint，但声明顺序与发射线序刻意解耦：

fail-closed 而非静默回退 legacy

A3.3 提示词注入：压缩态围栏上的一个真实洞

现象：如果不可信文本里含有与围栏闭合标记相同的字符串，攻击者可以用一条用户消息提前闭合围栏，让后续内容被模型当成指令执行。这类问题不会报错，只表现为「模型偶尔不遵守系统约束」。

根因与定位：PromptGuard.sanitize() 原本只净化 user_input / tool_result / memory_context 三类围栏标记（第 ④⑤⑥ 条）。S3-M8-a 新增压缩态围栏 <compacted_context trust="untrusted"> 时，如果忘了补净化，压缩态由「被压缩的对话内容」派生、其中可能含用户原文 / 模型输出，就构成一条真实注入路径。

解决方案：补齐 sanitize() 第 ⑦ 条——把 <compacted_context 替换为 [compacted_context、把闭合标记替换为 [/compacted_context]，并加测试锁死「净化后仅剩一个闭合标记」（PromptGuardCompactedContextTest 5/5）。

textPromptGuard 的四类围栏（platform/agent-application/.../prompt/PromptGuard.java:38-67）
USER_INPUT_OPEN / CLOSE            用户输入
TOOL_RESULT_OPEN = <tool_result trust="untrusted"  工具结果 / RAG 命中
MEMORY_OPEN / CLOSE                记忆块
COMPACTED_OPEN  = <compacted_context trust="untrusted">
COMPACTED_CLOSE = </compacted_context>        上一轮压缩态

统一纪律：全部包成 USER 消息，绝不进 systemPrompt
wrapToolResult()     超长 → 截断并显式标注「[输出已截断：原始长度 … 字符]」
wrapCompactedContext() 超长 → 抛 PromptRejectedException(TOO_LONG)，不截断
                        （状态是确定性 JSON，截断会破坏可复现性）

验证步骤：构造一条用户消息，内容里塞入 </compacted_context> 及后续伪指令 → 走完整 applyContextState → wrapCompactedContext → messages.add(ModelMessage.user(...)) 链路 → 断言净化后围栏闭合标记只出现一次，且模型收到的整段仍在 USER 角色内。这类测试必须从编排入口进，不能只测 sanitize() 这个私有方法。

文档 审查文档 护栏设计综合评估文档1.md:139 曾记 wrapToolResult 在生产主路径「零调用方死代码」（红队 R-7）；当前 AgentChatOrchestrator.java:526, 595-598 已把它用于 RAG 命中注入。这是时点差异，不是矛盾。

A3.4 跨进程 AI 服务契约失配：revisionCode=""

这是本仓库最能说明「假 Server 会锁死契约失配」的案例。platform 与 rag 是两个独立 Maven reactor / 进程，跨进程 HTTP 字段必须按对端真实校验取值，不能按「我方觉得合理」取值。

A3.6 检索质量的静默退化：量纲、门禁与版本降权

检索类问题几乎从不抛异常，只会「一直没结果」。四个真实机制：

  1. 阈值形同虚设：配置默认 min-score=0.2 过低，几乎不过滤；2026-10-28 首次标定为 0.38（原设计 0.35 已废弃）。docs/RAG检索与端到端实测问题记录_20261028.md 是本项目最密集的问题源（836 行 / 29 条）。
  2. 量纲混用：ts_rank 与 cosine 量纲不同，ScoredChunk.score（相关性分）与 fusionScore（RRF 分，双通道最大约 0.033）必须分开；曾把 RRF 写进 score → 与 0.38 比 → 门禁恒不通过。
  3. 版本降权用减法：在 RRF 量纲下减法会把异版本分数一律压成 0、组内次序全丢；作用在相关性分上则「降权」退化为静默过滤。现实现为 rankPenalty 乘法惩罚。
  4. 文档与代码漂移：RAG-D05 §8 写「RRF 与 cross-encoder 重排未实现」，DOC-10 更正为「RRF 已实现，仅缺重排」；LocalLexicalEntailmentPort 自述「不是 NLI 蕴含模型，也不是 cross-encoder 重排器」。所谓「重排」目前就是 RRF 融合分 + 版本惩罚。

定位方式：按七步顺序逐段打点（知识点解析 → 多路召回 → 版本过滤 → 角色过滤 → 知识点补全 → 排序 → 分数门禁），确认每一段的计数而不是只看最终命中数；RAG-D17_召回漏斗计数改造说明.md 正是为此而生。重点检查：过滤是否在重排之前、分数用的是哪个字段、阈值来自哪份配置。

验证步骤：造跨版本 / 跨角色 / 低分三类夹具，断言漏斗各段计数与最终命中一致；对「分数门禁」做反向验证——把 fusionScore 撤回到 score，对应 IT 必须转红。

文档 实测条目「min-score=0.2 形同虚设、重灌 SQL 剪枝 DELETE 清零、limit 被静默忽略、缺 edition.revisionCode 返 500 被证伪为 400、平台档上传必 500」等，本次勘察只核到文档描述与派生分类文件，未逐条追到代码行或测试断言，标注为「仅文档描述」。

A3.7 「测试全绿」在 AI 系统里为什么不够：三级验收与反向验证

三级验收是本项目所有 AI 改动的准入条件，缺一级就可能出现「有一行，但数字算错了」：

级要证明什么典型手段
① 行为单测算法 / 状态机在给定输入下输出正确RagHitQuotaTest、ContextStateEnvelopeTest
② 链路 E2E请求真的流过编排入口，不是直连端口TraceCollectEndToEndIT、SSE 真联调
③ 真跑闭环按真实送出的请求计费 / 计量，指标真的前移ContextCompactionL1RealRunIT（OFF/TIERED 双臂同上下文）、acked 增量与 computed_at 前移

四个守卫设计原则（方案 §7.3 原文口径）：

  • 每个守卫必问「撤掉修复点它会红吗」；
  • 守卫绝不引用被测实现自己的常量（否则一起改一起绿）；
  • 必须从编排入口进，不直连端口；
  • 弱断言要造出挤出压力（如 5 轮大工具输出把 budget 挤爆），否则断言恒真。

反向验证（撤点 / 反证）判定三硬条件：compiled=True（撤点后编译成功，编译失败是无效反证而非假红）、目标测试真红、skipped=0；再加 finally/trap 复原 + md5 一致 + git diff --check。结论不变（仍全绿）或编译失败，一律判无效反证。累计台账随时点变化：100 组（影子报告 A.3）→ 120 组（ADR D47）→ 126 组（G2 签核包 §5.4）。

假绿的几种典型形态：

形态机制修复
跳过型假绿@EnabledIfEnvironmentVariable 因 IT_PG_URL 丢失整类跳过必须断言 skipped=0；在 bash 内 source scripts/it-env.sh 后跑 Maven（Python subprocess 传 env 易丢变量）
管道吞退出码mvn … | tee log 让 $? 变成 tee 的 0set -o pipefail

A3.9 AI 链路排查清单（与传统 Java 问题的差异对照）

排查动作传统 Java 后端本项目 AI 链路必须多做的一步
确认「请求发了什么」看 Controller 入参与日志看最终送模型的 ModelRequest（装配后，不是 legacy）；关闭态必须同一引用
确认「数据查到了吗」看返回行数先确认租户是否绑定；FORCE RLS 下未绑租户是静默 0 行 / 假空
确认「消息消费了吗」看 consumer lag看 eventType 分流与通道模式（database 默认）；看 PENDING / 死信是否归零
确认「钱算对了吗」一般不涉核对单价 pricingOf() 非空、token 来自真实 usage、judge 成本未混入业务账
确认「结果可信吗」断言相等核对样本量 n≥30、覆盖率、置信度；机器判分与人工标注是否物理分离
确认「降级了吗」看异常与 5xx看是否有 RAG_UNAVAILABLE / FakeModelGateway / EXCERPT_ASSEMBLY / fallback=true 等静默兜底
确认「测试可信吗」BUILD SUCCESS数 XML <testcase>、断言 skipped=0、set -o pipefail、撤点反证必须转红
确认「代码真的跑起来了吗」看启动日志比对运行 jar inode 与磁盘 jar；确认 @EnableScheduling / 组合根装配存在
确认「配置生效了吗」看配置中心三层来源（env / yml / DB 目录）+ 活库 07_*.sql 是否已执行 + fail-closed 是否拒绝启动
一句话方法论

AI 链路排查的起点不是「哪里报错了」，而是「哪里可能没报错但悄悄错了」。先列出所有静默兜底点（降级、回落、fail-soft、跳过、空题库、桩），逐个证明它们没有被触发，再谈结论。
