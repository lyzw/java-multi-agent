第三篇 / 第 9 章

9. 必须重新建立的八个心智模型

9.1 「数据库连接」不等于「请求上下文」

传统做法把租户 ID 放进 ThreadLocal，SQL 里拼 WHERE tenant_id = ?。这里租户身份绑定在 PG 连接的会话变量上（set_config('app.tenant_id', ?, true)），连接池复用时若上一次请求残留，下一个请求会沿用上一个租户的身份静默越权。所以：事务内绑定、业务 SQL 前绑定、Repository 不 commit、验隔离用非特权角色。详见 §2.3。

9.2 「消息发出去」不等于「任务会执行」

Outbox 把消息与业务数据放进同一事务，换取的是「不会静默丢任务」，代价是至少一次投递。MQ payload 不可信（只带 ID），Worker 必须回库重读状态；消费端按 eventType 分流、按幂等键去重；终态后禁止补 attempt。详见 §2.2 与 第 11 章。

9.3 「配置改了就生效」在这里是双刃剑

能力目录与模型目录改完即生效，但 Run 创建时把配置钉死成 execution_snapshot。发布引用必须是 id@version，禁止 latest 漂移；审批要求 approver_id <> requester_id；指针切换用 CAS + 全局单调序号。于是「我刚发布的新配置为什么这个 Run 没用上」往往是正常行为，不是 bug。

9.4 「查不到数据」要分四种情况

可能原因判别方法
确实没有数据用非特权角色 + 绑定正确租户后查 count(*)
没绑 app.tenant_id，FORCE RLS 静默 0 行SELECT current_setting('app.tenant_id', true)
连错库 / 连错实例（5432 vs 5433；本地 vs 远程 RDS）SELECT current_database(), inet_server_addr(), inet_server_port()
用了 BYPASSRLS 角色导致「假绿/假空」结论反转SELECT current_user, rolbypassrls FROM pg_roles WHERE rolname = current_user

项目里有一句很值得记住的话：FORCE RLS 表判空必须先绑租户，否则是假空。真实案例见 §16.9（平台档 500 与「全表 0 行」的区分）。

9.5 「LLM 调用」是预算问题，不只是 HTTP 调用

上下文压缩方案把请求看成全窗口预算：system + tools + memory + RAG + history + 当前输入 + 输出预留，一起受 hard-ceiling 约束。核心不变量包括：稳定前缀不压缩（systemPrompt 基段 + toolSchemas 逐字保留）、首轮任务锚 pinned、RAG/记忆等不可信内容绝不进 systemPrompt（作带围栏的 USER 消息）、RAG 命中配额硬顶且引用也扣预算、净成本守恒 saved = (before − after) × price_input − summaryCost。

关闭态必须与「没有压缩功能」逐位等价：RequestAssemblyPort 规定实现短路后直接返回 input.legacyRequest() 同一引用，调用方靠引用身份分流，绝不在 worker 里再抄一份 enabled 判定。

javaplatform/agent-ports/.../ports/contextwiring/RequestAssemblyPort.java（注释节选）
/**
 * ⚠️ 关闭等价桥是构造级保证：agent.context.enabled=false 时实现必须短路——
 * 零策略解析、零能力读取、零预算、零管线、零布局、零摘要、零指标、零事件，
 * 直接返回 input.legacyRequest() 同一引用。

 * ⚠️ fail-closed：冻结策略非法 / 预算超硬顶 / 装配链路异常时抛

 * ⛔ 绝不静默回退 legacy（那会让「配错策略」被伪装成「策略正常」）。
 */

9.6 「答案对」不等于「链路对」

项目区分 L0 系统事实 / L1 自动终态校验 / L2 抽样标注 / L3 有噪信号，并有 P7 三条铁律：指标是事实表的确定函数（幂等 ON CONFLICT (trace_id) DO UPDATE）、只算收敛 Trace、后端回填前端不推算。「未采集 ≠ 0」；只校验 3% 时写「99% 正确」是误导，必须同时给出覆盖率。L2 判分结论只写 agent_trace_metric.attribution_correct，机器判分绝不写 agent_eval_sample。

9.7 「降级」在这个项目里通常是错误答案

传统服务里「依赖不可用先降级返回缓存/默认值」是常见容错。这里的业务语义（防泄题、防幻觉、防越权）使明确失败优于看起来成功：解析器未确认时显式失败而非回落占位；策略非法抛 RequestAssemblyException；能力闭包解析不出按「未声明」处理；检索依据不足输出「依据不足」而不是用模型参数内知识补；占位端口默认由 LocalPortGate 拒绝装配。

9.8 「测试全绿」只是候选证据

项目的统一教训是「全绿不是证据，可复现的全绿才是」（问题记录/07-测试基建与验证方法论.md）。要额外确认：本轮确实执行了用例（不是被 @EnabledIfEnvironmentVariable 整类跳过）、skipped=0、断言走的是真实链路而不是夹具、撤掉修复点会转红、运行的是刚构建的产物而不是旧 jar。展开见 第 14 章。

10.3 FORCE RLS 下的领取查询范式（Sev-0 级）

已登记事故：在 FORCE RLS 表上写 IN (SELECT … LIMIT … FOR UPDATE SKIP LOCKED) 时，security-barrier 会让 IN 退化为逐行 SubPlan，LIMIT 静默失效；用 superuser 复现不出来（因为绕过 RLS），必须用非特权真库 IT。正确范式是物化候选集再 UPDATE：

sql范式（示意；项目内实现见 agent-persistence 的 PgQueueRepository / JdbcRunClaimRepository）
-- ❌ 错误范式：FORCE RLS 下 LIMIT 可能静默失效
UPDATE task SET state = 'RUNNING'
 WHERE id IN (SELECT id FROM task
                  WHERE state = 'PENDING'
                  LIMIT 10 FOR UPDATE SKIP LOCKED);

-- ✅ 正确范式：先物化候选集，再 UPDATE … FROM candidates
WITH candidates AS MATERIALIZED (
  SELECT id FROM task
   WHERE state = 'PENDING'
   LIMIT 10 FOR UPDATE SKIP LOCKED
)
UPDATE task t SET state = 'RUNNING'
  FROM candidates c WHERE t.id = c.id;

上例为教学用等价示意，实际列名、租户绑定与 fencing token 以仓储实现为准。关键点：MATERIALIZED 保证候选集先被一次性取定。

反向验证脚本长什么样

项目里没有 *-rv-*.py 文件；反向验证实际是 scripts/*-counterproof.sh（如 m3-context-policy-counterproof.sh、g2-b-counterproof.sh、m8a-context-state-counterproof.sh），RV-* 只是脚本内部的注入锚点编号。标准手法：精确计数替换注入一个缺陷 → 跑指定测试 → 期望如期转红 → 还原并校验 md5；「结论不变（仍全绿）」或「编译失败」一律判无效反证。
