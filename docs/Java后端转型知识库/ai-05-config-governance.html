A5.6 授权决策日志：为什么「禁 RETURNING」是一条铁律

authz_decision_log（01_platform_ddl.sql:971-1002，9 列，tenant_id 是 text 而非 uuid，不挂 RLS，隔离靠授权）有一组非常典型的「权限收窄改变 SQL 可用性」的证据链：

  1. 只写不读。应用角色 GRANT INSERT + 显式 REVOKE SELECT（03_platform_roles.sql:262-274，注意 :269-272 解释 ALTER DEFAULT PRIVILEGES 会让 SELECT 悄悄回潮）。
  2. 禁 RETURNING。PG 的 INSERT…RETURNING 需要返回列的 SELECT 权限。带 RETURNING 会让每次判定写失败，而失败被限频告警吞掉 → 「判定照常、审计零行、系统全绿」。
  3. 两道守卫。源码层 insertMustNotUseReturning + 活库层 insertWithReturningIsDenied（AuthzDecisionLogSchemaTest.java:74-91、AuthzDecisionLogLiveIT.java:51-54，活库 5/5）。
  4. 启动期 fail-closed。AuthzDecisionLogGuard 两道：开关开但无记录器 → 拒启；Jdbc 记录器零行写入探测（INSERT…SELECT…WHERE FALSE）失败 → 拒启。用「真走一遍 INSERT」而非 has_table_privilege（后者对列漂移无感）。
  5. 故障隔离。日志失败绝不外抛（否则 Permit 路径把放行变 5xx、Deny 路径覆盖 reasonCode），60s 限频告警（JdbcAuthzDecisionLog.java:49-58,161-176）。
这条铁律的可迁移价值

「禁 RETURNING」不是本项目的怪癖，而是把授权约束翻译成 SQL 写法约束的通用模式：只写不读不只是授权配置，还决定了你能不能用 RETURNING、能不能回读校验。任何给审计/日志表做最小权限设计的项目都会遇到。同类案例见 A6.9 的部分证据 P2（03 重跑静默覆盖 04 的 REVOKE DELETE）。未确认 日志开关 agent.authz.decision-log.enabled 默认 false，生产是否持续累积行数无证据。

A5.7 配置数据模型、生命周期与三步发布

与 A4.5 对应，这里从治理视角补充关键约束（数据模型与状态机本身见 A4.5，不重复）：

原子发布事务 + CAS

版本行 + 发布头 cap_config_release + 指针 CAS 同事务提交，失败整事务回滚无半成品（P5 交付说明:73-90，ConfigPublishIT#casFailureLeavesNoHalfPublishedState）。CAS 用 IS NOT DISTINCT FROM 而非 =（首次发布基线 NULL）。

双人复核三道防线

应用层 SelfApprovalException 409 + 存储层 FOR UPDATE 状态守卫 + DB CHECK cap_config_publish_request_two_person_ck（P6R4:186-192）。注意 未确认：该 CHECK 谓词被记录为「双 NULL 也放行」，名字比实现严格（见 A6.9 P3）。

回滚协议：切指针，不恢复已撤权

回滚 = 新建 PUBLISHED release 指向旧版本 + 原 release 标 ROLLED_BACK + CAS 切指针；不触碰 cap_authz_version / cap_approval（不恢复已撤权）（P5:99-110、06 文 :181-186）。当前生效版本只认指针指向的 PUBLISHED release，绝不以 max(seq) 或扫描历史行判断（cap_config_pointer 表注释 :1848）。

配置指纹的四类版本不可互相替代 06 文 :218-233

agentVersion / configVersion(config_publish_seq) / configFingerprint / authzVersion 四者分离——「回滚使指纹相同但发布事件不同」。指纹是闭包级而非全局聚合：「一个与某 Run 无关的 Tool/Skill/MCP 变更不应使该 Run 快照失效」（05 文 :204-210）。这是配置治理里最容易被做错的一处：图省事用全局聚合指纹，会让任何无关变更都冲掉所有在途 Run 的快照。

未闭环 回滚/生命周期迁移的成功路径未单列 IT（只测拒绝路径）；发布与申请单状态回写是两个事务（已知窗口）；前端未接入（P6R4:311-320）。

成本分解：慢的不是闭包查表，是每次全量重算指纹

:143-172 闭包查表仅占 0.6%–3.3%，其余全是每次判定全量重算闭包指纹（O(闭包规模)，分配压力致 GC 次数 6→19→74）。核心结论：p99<1ms 缺「闭包规模上界 + 并发度」前提即无意义，须写成「规模 + 并发 + p99」三元组。建议目标值（2× 安全系数）待评审签署。测试环境是开发机（JDK 21.0.13 / 10 核 / 8GiB 堆），非生产规格；生产真实闭包规模分布未统计（:82-90）。

怎么测的（:64-120，LocalDecisionBenchmark.java:260-290,514-588）：三档位 S/M/L（20/80/320 绑定）× 1/4/8 并发 × 30000 次；自适应预热到 p50 收敛（连续 3 窗偏离 ≤5%）；记录 GC；轮转目标位置（避免只测线性扫描首位）；运行期遍历对象图断言无 DataSource/Connection（assertNoDataSourceIn）——证明被测路径真的不碰数据库。:252-261 有 6 项结构断言每次构建跑，但无耗时阈值断言（避免共享构建机随机红），这是很有分寸的设计。

A5.10 V1 冻结判定：是「冻结候选」，不是「已冻结」

P6_V1冻结判定报告.md:9-18,71-73 的结论是 M6「V1 冻结候选」，带 12 项限制：三类门槛（功能/安全/工程）+ 硬约束均达成，但任一需求未达 ACCEPTED 故不宣布「已冻结」。全量 mvn -o clean verify 1200 项 0 失败/0 跳过（:203-222）。24 项中 21 项达 SECURITY_ACCEPTED / INTEGRATION_TESTED，R-15 性能止于 DESIGNED、NFR-03 依赖方向止于 UNIT_TESTED。

最关键的未闭环（E2E 后新发现）

A5.11 迁移方法论：十条总体 + 五条增量

RLS到应用层权限迁移-问题方案与方法论归档.md §4:181-194 的十条总体方法论，是本项目最值得跨项目复用的沉淀：

#方法论一句话解释
1绿 ≠ 对测试通过只是候选证据，不是结论
2能力存在 ≠ 能力生效代码在、配置有、开关没开/读侧没接，等于没有
3同义反复是假绿第一来源用「查询绑定租户」当「行租户」→ 恒不违例（见 A5.3）
4单测替身掩盖真问题常量 filter / 动态代理 JDBC / NoConnectDataSource 测不到 SQL 语法、列解析、RLS 行为、真实行归属
5区分三类「证明」可写（零行探测）/ 在写（写后由库 owner 回读整行）/ 运行期开启（时长）——缺一类就是盲区
6权限收窄会改变 SQL 可用性RETURNING 要 SELECT；DEFAULT PRIVILEGES 会悄悄回潮（见 A5.6）
7基线绑定实际形态且一源一份跨库混用基线必出假阳性（见 A5.1）
8可观测性要可复现 + 全覆盖0.1% 在确定性分桶下单组合平均 ~100 小时才采到一次，小流量租户两个月一次没被看过，读数仍是 0（归档 P9）
9隔离做成硬约束而非约定「幂等」必须由行数不增长这类真证据钉死，ON CONFLICT 不报错 ≠ 真幂等（归档 P8）
10fail-closed 贯穿三层授权/执行/配置三层都不能「出事就放过去」

另外五条是本次勘察从代码/台账中提炼的增量，归档（11-03）尚未写入：

  • M11 · 「绿」的口径本身要被版本化审计。判绿指标 2026-11-09 从 AUTHZ_MISMATCH=0 升级为 rlsDependent=0（AuthzShadowReporter:83-100；归档 11-03 无此修正）。用旧口径判绿，会在隔离没做好的情况下也全绿。
  • M12 · 灰度回滚 ≠ 删数据，口径自带诚实边界。E1 非零 → 立即从白名单移除该租户，不删除已写 cap_* 数据（关 = 停止走新判定，不是删数据）。且 cap_authz_mismatch_total 全局按 resource_type、不带租户标签，某租户 =0 必须叠加按租户扫 WARN 日志，不能只凭全局计数（运行时灰度验证方案:54-60,83-85）。
  • M13 · 机器校验把「我认为覆盖了」变成「我证明覆盖了」。Section9ScenarioCoverageTest#everyBehaviorEvidenceAssertsItsReasonCode 首跑即失败：S3f 三个终态里两个从未真验（测试树 FAILED/TOOL_EXECUTION_FAILED 零命中）（P6 冻结报告:93-139）。
  • M14 · 失败注入要在驱动层而非替身层。原 S3a/S3d 用内存夹具改值/记录不存在，证不了「版本来自权威库、存储真不可用」；回流用独立连接池与真实不可达端口——失败发生在驱动层（:143-160）。
  • M15 · 数据库约束自己抓出测试缺陷。加 uq_review_task_open 部分唯一索引后，2 个既有 IT 红了：它们为测排序/租户过滤给同 trace 建两条任务——说明约束在如实履职（项目进度台账:2619-2626）。

综合本册：① 目标态与当前态分列，不用文档的目标态描述当前态；② 判绿用 rlsDependent=0 且警惕结构性 0；③ 基线一库一份、先归因基线；④ 反证必须注入他租户行（同义反复不算）；⑤ 进真库的语句要活库解析/回读实证；⑥ 区分可写/在写/运行期开启三类证明；⑦ 静态扫描白名单制不等于全覆盖，要查未登记对象；⑧ 性能结论写成「规模+并发+p99」三元组；⑨ 回滚不恢复已撤权、灰度回滚不删数据；⑩ 开关默认 fail-closed，开启前置证据未产出前不得置 true。
