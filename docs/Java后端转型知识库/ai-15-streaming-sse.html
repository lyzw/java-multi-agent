A15. 流式输出与前端 SSE 消费：从供应商 token 流到浏览器增量渲染

第 12 章 的 SSE v1.1 讲的是上下文压缩态怎么走事件流（context.checkpoint 等）；本册讲另一条更贴近用户的流：答案本身怎么一个 token 一个 token 到达浏览器——供应商侧 SSE 怎么解析、平台怎么定义 13 类事件协议、双身份域为什么是两个端点、前端怎么用增量解析器 + 状态机做到「迟到事件不串台、截断不伪装」。

本册与已有册的分工

A14 讲一次性归一化调用（ModelGateway），本册讲它的流式兄弟端口；A3.2 讲压缩管线，本册 A15.9 讲压缩态在前端的 carry-over 消费；usage 事件与 A11.2 的账本挂钩；联调排障见 §15.4 跨服务契约诊断。

A15.1 为什么要独立 ChatStreamGateway 端口：不污染领域契约

ModelGateway.complete() 是领域层（Worker 执行 Agent Run）用的一次性归一化调用，按 ADR-002 不暴露任何流式/响应式类型。控制台对话是平台工具而非租户 Run，其流式需求单独成端口 ChatStreamGateway（MiniMaxModelGateway 同时实现两者）。端口契约里三条最重要的纪律（类注释）：

  • 每个内容增量通过 StreamDeltaConsumer.onDelta 实时回吐，不得缓冲到结束才一次性抛出——否则「流式」只是分批；
  • onDelta 回调内的异常由调用方（控制器）捕获并终止流，实现方不得吞掉或重新归一化已抛出的 ModelGatewayException；
  • 入参/出参沿用 ModelRequest/ModelResponse，不引入供应商或 Spring AI 专属类型——领域中立。

另有一个容易被忽略的默认行为：onThinking（推理草稿增量）默认空实现。注释写明：思考内容未经答案级安全审核，仅展示给平台管理员（控制台工具），不可回落到面向学生的通道——这是 A15.4 双端点设计的伏笔。

证据： platform/agent-ports/.../model/ChatStreamGateway.java（类契约与 StreamDeltaConsumer javadoc）。

A15.2 供应商侧 SSE 解析：stream=true 覆盖、逐行读取、[DONE] 与 ThinkFilter

textMiniMax streamChat 解析（MiniMaxModelGateway.java:104-267）
streamChat(request, consumer)
  ├─ 组装请求体时覆盖 stream=false → stream=true
  ├─ streamAndParse(): 逐行读 SSE
  │    ├─ 注释行（:开头）跳过
  │    ├─ data: [DONE] → 终止，整合终态 ModelResponse（含完整正文与 usage）
  │    └─ data: {json} → delta 增量
  │         └─ ThinkFilter 分流：
  │              <think>…</think> 内 → consumer.onThinking（推理草稿）
  │              外 → consumer.onDelta（答案正文）
  └─ 返回整合后的终态响应（供用量结算 / 前端兜底展示）

三个实现细节值得抄走：① 增量不保证按词/句边界切分，消费者必须能处理任意切分（前端按纯文本拼接）；② 思考与答案是两条流（onThinking/onDelta），不是靠前端猜 <think> 标签；③ 终态响应仍带完整 usage——流式不等于放弃计量（A11.3 的结算时序对流式同样成立）。

证据： platform/agent-infrastructure/.../model/MiniMaxModelGateway.java:104-267（含 ThinkFilter 内部类）；MiniMaxModelGatewayStreamTest.java。

线序（硬约束）：… → answer → usage → context.checkpoint → done

     done 仍是唯一的应用层终帧（客户端不必知道第 14 帧存在）

state 是不透明 base64：结构化状态 JSON + 元数据，经独立 HMAC 密钥
  AGENT_CONTEXT_STATE_HMAC_KEY 签名（⛔ 绝不复用 JWT 密钥）
  服务端下一轮按不可信数据处理，六项校验（D49）任一失败即丢弃退回全量历史

fail-soft（可选增强）：未装配 / 关闭态 / 无新增 / 抽取回落 / 超长 /
  密钥不可用 → 一律 null，不发事件、Done 退回 v1 字节，主流程不受影响

A15.4 双身份域双端点：平台链与租户链、thinking 草稿可见性边界

text双端点（AgentChatController.java:35-70）
POST /api/agent/chat/stream        平台链（aud=admin-console-api）
  → admin-console 使用；允许下发 event: thinking（推理草稿）

POST /api/knowledge/agent/chat/stream  租户链（aud=agent-platform）
  → frontend 使用；身份取自已验签令牌；恒丢弃思考草稿

硬规则：
- 身份不入参：tenantId/principalId/Bearer 全部由
  AgentChatIdentityResolver 从已验签属性解析
- 租户链请求体出现 tenantId → 直接 400
  「租户链不得在请求体中指定 tenantId」（:126-130，防越权）
- 平台链的 tenantId 仅作为「目标租户」，必须合法且存在

thinking 的可见性差异不是功能开关而是安全边界：推理草稿未过答案级审核，把它下发给学生会多开一个内容泄露面。两链共享同一编排器、同一份事件协议与状态机语义，「只是身份来源与草稿可见性不同」——这是把差异面压到最小的刻意设计。

证据： platform/agent-api/.../chat/AgentChatController.java:35-70, 107-130；AgentChatIdentityResolver。

A15.5 后端 SSE 实现纪律：SseEmitter、虚拟线程、反代缓冲与 ASYNC 放行

  • 帧一律用 SseEmitter.event().name().data() 构造，绝不手工拼 event:/data: 字符串（:51-53 注释）——换行转义、多行 data 的坑框架已处理；
  • 响应头带 X-Accel-Buffering: no（:192）关闭 Nginx 等反代缓冲——否则 token 会被反代攒成一坨再吐，「流式」名存实亡；
  • Security 链必须放行 DispatcherType.ASYNC（:54）：SSE 的异步终止块若被二次授权拦截，客户端会拿到「流中断但无 error」的悬空状态；
  • 每连接一个虚拟线程（:89-90），SSE 超时 SSE_TIMEOUT_MS=180_000（:72-73）。
证据： platform/agent-api/.../chat/AgentChatController.java:51-90, 192；ConsoleChatController.java（控制台直连对话同构实现）。

A15.6 超时三层对齐与失败口径分层：180s / 150s / 120s

层值来源
后端 SSE 整体超时180_000 msAgentChatController.java:72-73，注释要求「须大于两前端的 120s / 150s 请求超时，否则会先被服务端截断」
frontend 请求超时AGENT_CHAT_TIMEOUT_MS = 150_000frontend/src/api/agentChatApi.ts:36
admin-console 请求超时AGENT_LIVE_TIMEOUT_MS = 120_000admin-console/src/api/agentChatApi.ts:48

方向必须严格递增（后端 > frontend > admin-console）：若服务端先超时，客户端拿到的是「连接被服务端掐断」而非应用语义的 error/done，失败口径就乱了。失败口径本身分两层：建连前失败（身份/参数/限流）走 HTTP 4xx；编排中失败走 event: error + event: done，审计仍收敛 FAILED（:56-57）。这与 A12.4 的审计闭环对接。

证据： 三处常量如上；AgentChatController.java:56-57（失败口径分层注释）。

A15.7 前端增量解析器：IncrementalSseParser 与逐字段解析

frontend/src/features/run/sse.ts 提供两块能力：parseFrame（:30-81）按 SSE 规范逐字段解析（event:/data:/id:/retry: 与注释行）；IncrementalSseParser（:105-129）做边读边出——chunk 到达即切分完整帧、保留半截帧等下一个 chunk。为什么必须增量：后端单次响应可能连发大量事件（Run 事件接口单次上限 200 条，:103 附近注释），整段等 buffer 会造成用户可见的长白屏。注意 id 字段的注释明确「是 Last-Event-ID 的值」，但当前没有任何代码消费它做重连——这是 A15.10 未落地清单的第一条。

证据： frontend/src/features/run/sse.ts:15, 30-129；frontend/tests/sse.test.ts。

A15.8 前端状态机：useReducer 六种 Action 与乐观 UI

textagentChat 状态机（agentChatState.ts:407-580 + useAgentChat.ts）
Action 六种：SEND / STREAM / FAIL / STOP / RETRY / NEW_SESSION

乐观 UI：SEND 先插入 user + assistant 两个气泡，
         assistant 初始为 streaming 态；FAIL 转 failed

四条不串台纪律：
① controllerRef 身份比较（useAgentChat.ts:95 附近）：
   旧请求的迟到事件与失败不写进新气泡
② id 在 dispatch 之前生成（:121-122）：reducer 异步生效，
   从 state 读回刚插入的气泡会晚一帧
③ done 到达即释放「在途」锁（:86-88）：不等微任务队列
④ stop() 是正常操作，不 dispatch FAIL（:141）——
   用户主动停止 ≠ 系统失败

存储纪律：会话历史只在内存，不写 sessionStorage/localStorage（:10）

truncated 是独立状态，不是 failed 的别名：流结束但没收到 done 终帧 → 标 truncated，「已到达正文保留 + 不伪装完整也不伪装系统故障」（agentChatApi.ts:23-25）。这个三态区分（完整/截断/失败）是 AI 前端最容易偷懒做坏的地方——把截断渲染成失败会制造假报警，渲染成完整会撒谎。另两条诚实边界：live 模式收到 404/501 明示「能力未接入」，绝不退化成假流（:13-18）；sample 回放醒目标注「非真实模型输出」。

证据： frontend/src/features/agentChat/agentChatState.ts:32-630；frontend/src/features/agentChat/useAgentChat.ts；frontend/src/api/agentChatApi.ts:10-47；配套测试 frontend/tests/agentChat.{api,state}.test.ts。

A15.9 双工程同构与压缩态 carry-over：架构测试锁协议、contextState 只上送 committed

frontend（租户端）与 admin-console（平台端）各有一份 agentChatState.ts / useAgentChat.ts / agentChatApi.ts，协议与状态机语义刻意同构，由 agentChat.architecture.test.ts 逐事件名比对双工程锁定。改协议的流程因此是：改后端事件 → 同步两份前端 → 架构测试与各端单测一起转绿，少一边都不行。

压缩态 carry-over（与 §12.2 对接）：后端在 context.checkpoint 事件下发压缩状态，前端把它作为 contextState 在下一次请求回传。前端纪律：只回传已完成且未截断的 committed 状态（useAgentChat.ts:78-80），pending/截断/失败态绝不上送——半截压缩态回传会让后端把「上一轮的残缺」当成「这一轮的事实」。

证据： frontend/tests/agentChat.architecture.test.ts；admin-console/src/features/aiChat/（同构实现 + MarkdownAnswer.tsx 增量渲染）；frontend/tests/agentChat.contextState.test.tsx。

A15.10 未落地清单：断线重连、Last-Event-ID 续传、事件序列号与重放

能力状态说明
SSE 断线重连 / Last-Event-ID 续传未落地sse.ts 定义了 id 字段语义，但无任何重连消费代码；断线 = 用户重发。设计上后端也未存「按 Last-Event-ID 重放」的缓冲
Agent Chat 事件序列号 / 重放未落地AgentChatEvent 无 sequenceNo 字段——对比 Run 链路的 RunEventStreamer（有事件序号，服务端轮询推送）。聊天链路因此不可断点续传，这是与 Run 链路的关键能力差
会话历史持久化未落地（刻意）前端会话只在内存；历史靠后端 run_message（保留期见 A12.10），前端不留存是隐私取舍

给 Java 后端的迁移提示：SSE 不等于 WebSocket——它是单向、文本、基于 HTTP 的协议，天然没有 WS 的重连/续传语义；「断线怎么办」要在应用层自己设计（事件序号 + 重放缓冲），本项目聊天链路明确选择了「不做」，把复杂度留给 Run 链路。知道哪里刻意没做与知道哪里做了同样重要。

迁移提示：流式链路的「一协议两端口三层超时」

可复用：独立流式端口不污染领域契约、sealed interface 事件协议 + 架构测试锁双端、SseEmitter 三条纪律（不手拼帧 / 关反代缓冲 / 放行 ASYNC）、乐观 UI + 身份比较防串台。必须新建的心智：done 是应用层终帧（不等 EOF）、truncated 三态（完整/截断/失败不能互相伪装）、超时方向严格递增（后端 > 前端，否则口径乱）、carry-over 只上送 committed（半截状态是下一轮的毒药）。
