守门写法的差异（13 册未区分） 已实现：platform 75 个 *IT.java 用类级 @EnabledIfEnvironmentVariable(named="IT_PG_URL", matches=".+"))；rag 的 4 个 IT 类用 Assumptions.assumeTrue(System.getenv("IT_RAG_PG_URL") != null)（rag-it-env.sh 行 6）。不带环境时整类跳过：rag 基线「只有 682 单测」；配好后「10 模块 / 745 testcase（682 单测 + 63 IT）/ 0 失败 / 0 错误 / 0 跳过」。

典型假绿：缺环境变量 → 整类跳过 → 构建全绿

Python subprocess 传 env 可能丢 IT_PG_URL / IT_RAG_PG_URL → @EnabledIfEnvironmentVariable / assumeTrue 全跳过 → Maven 报 BUILD SUCCESS 而一条 IT 都没跑。CI 因此硬断言 skipped != 0 → exit 1（ci.yml 行 301–303）：「构建绿不等于验证过」。另一个实例：缺 IT_RETENTION_* → RetentionErasureIT 整类挂起，20 例一条没跑，failsafe 只显示 Skipped: 1。

四道隔离闸 + 判据反证（platform 独有） 已实现：集成测试（IT）运行指南.md 行 140–164 描述「建库 / 结构 / 导出变量 / 构建（surefire）」四层，最后一道 ItTargetDatabaseIsolationTest 放在 surefire（任何 IT 连库之前失败 → 给出「一条人话」而不是「五十条诡异断言」）。ItTargetDatabase.violation/requireIsolated 硬编码 agent_dev/study_rag 兜底 + 读 platform.env 的 SPRING_DATASOURCE_URL 交叉比对；ItTargetDatabaseTest 10 例反证。诚实边界：判据只做字符串比对、不连库（刻意如此，避免网络抖动假红）。

共库拒绝：platform it-env.sh 行 111–117 目标库 == 应用库且 IT_ALLOW_SHARED_DB != 1 → die；rag rag-it-env.sh 行 104–119 黑名单（postgres/template*/ragdb/study_rag/agent_dev/agent_it）+ 与 rag.env 的 RAG_PG_URL 交叉比对，--reset 只允许名字含 it 的库。

造数与回收：ItTenantProvisioner（test 作用域，唯一幂等供给入口）强制 it- 前缀，连 tenant/agent/agent_version/execution_snapshot 一起建（因 run.snapshot_id 复合外键）。幂等必须靠行数钉死：ON CONFLICT DO NOTHING 不报错 ≠ 真幂等——唯一约束是 (tenant_id, snapshot_id) 而 snapshot_id 每次新随机，冲突永不发生、每轮泄漏一份租户；改为 AND NOT EXISTS 且 ItTenantProvisionerIT 断言行数不增长。execution_snapshot 不可删（forbid_snapshot_mutation 触发器）→ 正解是复用种子租户 t-a/t-b，断言写增量（before/after 差值）。多个 IT 在 @BeforeAll 用管理通道 purge 上一轮遗留 Run（子表 CASCADE 删、快照不动），约 20+ 处。

rag 侧的「探针库 ≠ 生产库」边界

rag-it-env.sh 行 28–36、223–244：探针刻意用 vector(1024) + chunk_id 单列唯一约束，而活库是 halfvec(4096) + (tenant_id, chunk_id, index_generation) 复合主键 → 这轮 IT 不覆盖生产向量列形态与索引代际语义，是独立待办。另每次 source TRUNCATE 全部 rag 表、只留 4 行全局字典（杜绝跨轮夹具累积）；口令 openssl rand 缓存 /tmp/rag-it-env.password（0600），仓库零凭据。共享库假绿实例：legalTransitionChainWritesAudit 在共享库因同 ISBN 残留审计行让 auditCount >= 2 恒真；干净隔离库暴露 applyVerification 把 ADMIT 审计一并跳过（已修）。

守卫是把「架构纪律」编译成测试。Java 后端要学的不只是「有哪些守卫」，更是「守卫怎么写才不失真」（A9.4）。

A9.4 守卫怎么写才不失真：七条代码级纪律

这一段是本册对 Java 后端最有迁移价值的部分。每条都有代码注释实证，不是通用建议。

纪律出处与实证
① 不引用被测实现常量ContextCompressionM6GuardTest.java 行 52–54：「本类不引用被测实现自己的常量：线格式用字面量冻结，源码用语义锚点，避免『改常量 = 改测试』的自证循环」；M3 GuardTest 行 83「与 DDL/07 脚本逐字比对的列定义（不引用被测实现常量）」。
② Pattern.find() 取反，不用 doesNotMatchContextCompressionM6GuardTest.java 行 56–57、485–487；M8aGuardTest.java 行 34、539–541：「所有『不得出现某模式』断言均用 Pattern.find() 取反，不用 AssertJ doesNotMatch（它是全串不匹配语义，长函数里恒真，是假绿源）」。
③ stripCommentsKeepStrings 识别 char 字面量ContextCompressionS1GuardTest.java 行 561–600：「字符字面量（如 '"' / '\\' / '/'）必须先于字符串处理：否则 '"' 会被误判为字符串起点，吞掉后续注释，守卫拿到含注释的源码 → 假绿」。
④ yml 用 raw() 读原文ContextCompressionM8aGuardTest.java 行 472–475；AgentChatProductionGuardTest.java 行 34–36：「yml 含 http:// 不能用 Java 扫描器剥离，单独用原文读取」；「yml 断言用解析后的对象 → 用 raw() 读原文」。
⑤ 防空转反向断言DatabaseBoundaryTest.java 行 40–41、124–125、203–208、248–256；ScopeBypassArchitectureTest.java 行 38–40：「路径发现失败会让空集合恒绿，本项目踩过多次，故每个扫描都带『至少扫到 N 个模块/文件』的反向断言」；「每条断言都配一个反证用例：把违规代码喂给扫描器，必须变红」。
⑥ 剥注释保留字符串ApplicationConfigKeyAlignmentTest.java 行 277–287、384–428；L2ProductionGuardTest.java 行 34：「只剥注释、不剥字符串：配置键就写在字符串里」；「注释里提到某常量就会让守卫假绿」。
⑦ 不复制第二份实现DatabaseBoundaryTest.java 行 64–69：Java SQL 豁免只给 DB 模块 + agent-test-support，「刻意不复制第二份实现，避免租户回收纪律分裂成两套真相」。
zsh / shell 的同类坑

scripts/it-env.sh 行 32–42：zsh 取脚本路径时 BASH_SOURCE 恒空、funcfiletrace 因缺 zsh/parameter 模块不可用，唯有 prompt 转义 %x 稳定给出路径；scripts/export-rls-policies.sh 行 186：macOS 自带 bash 3.2 在 set -u 下 declare -A 报错，故用纯文本而非关联数组。证据空白 「zsh 无数组切片」的专门写法本轮未检索到明确条目，勿据传闻补写。

A9.5 反向验证（撤点反证）体系：37 脚本、中断安全与三件套

以 scripts/m3-context-policy-counterproof.sh（六点反证）为标准样本，反证脚本的工程结构固定为十步：

text撤点反证脚本标准结构（m3-context-policy-counterproof.sh）
1. 头部注释：声明要证伪的每个假绿形态 + 期望变红的测试
2. OLD/NEW 锚点对：逐字字面量，NEW 带 // RV-M3-01 标记
3. 备份 + trap：cp 到 /tmp；trap restore EXIT；trap 'restore; exit 130' INT TERM
4. md5 前后比对：MD5_BEFORE=$(md5_all)
5. 精确计数注入：Python s.count(old)，n != 1 → ANCHOR_MISMATCH exit 3
   （多行锚点用 Python str.count，不能用 grep -cF 按行误计）
6. clear_report：必须删旧报告，否则编译失败时读到上一次报告 → 假红/假绿
7. run_mvn 故意不返回 mvn 码：红/绿只以「报告」判定，编译失败由「无报告」拦截
8. expect_red / expect_green：严格匹配 Tests run: 1, Failures: 1, Errors: 0, Skipped: 0
9. 恢复：restore()
10. 收尾三件套：old 锚点全量计数=1 + 残留 RV 标记全无
             + md5 复原一致 + git diff --check PASS

中断安全 已实现：trap restore EXIT + trap 'restore; exit 130' INT TERM 同时出现于 m3 / m8a / m8b-l2 / m8b2-checkpoint / m10-rag-quota / g2-b 六个脚本。教训出处：M10 曾被 SIGTERM/SIGINT 打断导致 MAX_INJECT_HITS=16 残留源码；m10-rag-quota-counterproof.sh 行 93 记录「曾导致 file2.bak 从未生成、restore 静默 ENOENT、撤点残留源码而收尾误判」→ 改为 Python 文件 IO + 备份完整性检查。

判定标准：「结论不变（仍全绿）或编译失败均判无效反证」（m3-...sh 行 26；g2-b-counterproof.sh 行 20–21「编译失败不算『用例红』——它证明不了任何运行时结论」）。实例 RV-67：首版直接给 record 加组件导致测试编译失败，已改为「不破坏构造器的提前暴露 contextState() 访问器」撤点，保证编译通过、只让目标守卫红。

残留标记计数不能误伤合法字面量

m8b-l2-assembly-counterproof.sh 行 195：残留 RV 标记计数需排除守卫纪律断言里的合法字面量 .contains("RV-M8B-0X")——那是常驻代码，不是残留。另 g2-b-counterproof.sh 行 26–33 硬编码绝对路径 ROOT=/Users/zhouwei/...，可移植性注意点。

A9.6 CI 与判绿口径：三个必红/假绿缺陷

.github/workflows/ci.yml 行 10–14 首部注释如实记录三个「从未在 Runner 上真实运行过」的缺陷：

缺陷机理修复
a) mvn | tee 吞退出码默认 shell bash -e {0} 无 pipefail，退出码取自 tee（恒 0）。实测 bash -e -c 'false | tee /tmp/x; echo $?' → 0两处加 set -o pipefail（行 74、254）
b) unit job 无库必红29 项装配测试装配完整 Spring 上下文启动即查 tenant 表（空库报 relation "tenant" does not exist）4 类加 @EnabledIfEnvironmentVariable(IT_PG_URL)，只到 mvn clean package

判绿口径清单（逐条可操作）：

  • 真绿定义：Tests run: N, Failures: 0, Errors: 0, Skipped: 0，不是 BUILD SUCCESS。
  • skipped != 0 → exit 1（ci.yml 行 301–303）。
  • 执行数下限：低于实测基线 1289（单测 872 + IT 417）→ 判环境退步；下限设 1000 留余量（行 305–312）。「不是『代码变好了所以测得少』」。
  • XML <testcase> 计数，不用根 <testsuite tests=>（G2验收签核包 行 215–217）。
  • CI-4 断言失真：台账行 262–266「skipped 的 grep 未锚定行尾，把逐类明细行与模块汇总行重复计数——实测无库场景：未锚定 366 vs 真实 180（虚高一倍）」→ 修复用 grep -oE "... Skipped: [0-9]+$" 锚定行尾（行 85、292）。
  • -Dtest 纯排除陷阱：ci.yml 行 262–276「-Dtest='!MessagingCanaryWiringTest'（纯排除）会让 surefire 扫描集合从『默认 includes』退化成『全部类』→ 38 个 *IT 被拉进单元测试阶段，RealBrokerEndToEndIT 当场 3 ERROR，failsafe 根本没跑（绿但没跑）」。实测对照：纯排除扫到 38 个 *IT / 432 项 / 3 ERROR；带正向模式扫到 0 个 *IT / 141 项 / 0 ERROR。正解：-Dtest='Test*,*Test,*Tests,*TestCase,!MessagingCanaryWiringTest'。
  • 门禁 job 用 needs.<job>.result 判定，不能用 job.status（后者读本 job 自身状态，永远显示「通过」，P1-10_重估门禁结论.md 行 68 的 Sev-1 缺陷 4）。
  • 不带 -am 找不到符号（Maven 单模块从本地仓库取依赖 jar）；不带 clean 时陈旧报告假红（先清 */target/{surefire,failsafe}-reports 再跑）。

迁移提示：把「测试」升级为「证据工程」

传统 Java 后端的验收往往止于「单测覆盖率 + CI 绿」。本项目的教训是：CI 绿可能吞了退出码、IT 可能一条没跑、守卫可能在验死代码、反证可能只是注入失败或编译失败、文档数字可能是三个版本前的快照。可复用的是 JUnit / Mockito / Maven reactor；必须新建立的是「每一条结论都要有可证伪的证据链」——判绿看 XML <testcase> 且 skipped=0，架构纪律写成守卫，修复点写成撤点反证，运维开关写成 fail-closed 门禁。这不是多写代码，是让「绿」这个词重新有意义。
