A16. MCP 客户端实现与运行时防护：传输、SSRF 三件套与按 server 熔断

MCP（Model Context Protocol）是「让 Agent 摸到外部世界」的协议，也是把 SSRF、凭据泄露、不可信输出三条风险一起带进门的地方。本册以客户端运行时为主线：传输怎么建连、地址怎么校验、熔断怎么分组、输出在哪可信化。

A16.1 定位纠偏：A4 讲配置模型，本册讲客户端运行时

先纠正一处滞后的文档口径

docs/governance/01-现状分析（2026-10-22）写「Skill 与 MCP 在代码中尚不存在」，A12.10 沿用了这一结论；但 MCP 客户端已于 2026-10-23 随 W-PERM-P4（commit b770141）落地：16 个类（端口 6 + 基础设施 10）、约 1586 行基础设施代码、7 个专项测试，且在 ApplicationConfiguration 完整接线。文档冲突 已登记 §20.5。A4.4 讲的是 MCP 的配置数据模型（cap_mcp_server_def 表、依赖方向、四类能力区别）；本册讲运行时实现——两者合起来才是完整的 MCP。

A16.3 HttpMcpTransport：协议流程、「不用 HttpClient」与「不做连接池」的两条决策

text两条反直觉决策（HttpMcpTransport.java:42-57 类注释）
决策一：不用 java.net.http.HttpClient
  HttpClient 按域名发起连接 —— 「校验过的 IP」与「实际连上的 IP」
  可能是两个东西（DNS rebinding 窗口）。
  本类直接建连到已校验的 IP，原始主机名放进 Host 头；
  HTTPS 用 SSLSocketFactory.createSocket(socket, host, port, true)
  让 JDK 依旧按主机名做证书校验（SNI + endpoint identification）
  → 钉死目标 IP，又不牺牲 TLS 主机名校验。

决策二：不做连接池
  池化连接会把「建立连接时的凭据」固化在连接上，
  凭据轮换后旧连接仍在用旧凭据。
  V1 每请求一条新连接（Connection: close），凭据逐请求解析，
  轮换立即生效。性能优化留给 P5（需带凭据版本进池键）。

协议：MCP 2024-11-05（HTTP / SSE 传输）
输出：远端返回文本原样透传，由调用方在 Gate 边界可信化。

这两条决策是「安全属性优先于性能」的完整示范：每请求新建连接在传统后端是反模式（三次握手开销），在这里是凭据轮换生效性的保障。给 Java 后端的提示：当你看到的代码「违背常识」时，先找它的安全注释——本仓库把每条反直觉决策的 why 都写在 javadoc 里，这正是 A2.2「决策记录怎么判断还有效」的代码级对应物。

证据： platform/agent-infrastructure/.../mcp/HttpMcpTransport.java:42-66（682 行）。

A16.4 SSRF 三件套：解析后校验、二次解析复验、连接地址=被校验地址

textMcpEndpointGuard 防 rebinding（McpEndpointGuard.java:26-172）
① 解析后校验：对解析出的实际 IP 逐个过地址策略
② 二次解析复验：连接前再解析一次，
   两次结果不一致 = DNS 在两次解析之间换了指向
   —— 这正是 rebinding 的动作本身 → 整体拒绝
③ 连接地址 = 被校验的地址（与决策一配合：建连到 IP 而非域名）

三件套缺一不可：只做 ①，攻击者在校验与连接之间换 DNS 记录（rebinding）；只做 ②③ 而校验逻辑错，等于白测。McpEndpointGuardTest 逐条覆盖这些场景。已实现

证据： platform/agent-infrastructure/.../mcp/McpEndpointGuard.java:26-48, 144-172；McpEndpointGuardTest.java。

A16.5 fail-closed 语义：一个 IP 被禁即整体拒绝

校验不是「挑一个能用的」：域名解析出 [公网 IP, 内网 IP] 本身就是可疑信号（正常 CDN 不会把内网地址混进公网解析），任一结果被禁即整体拒绝。这与 A5.5 的「ALLOW ≠ 成功」同族：授权语义里没有「部分通过」。防御深度上，SSRF 防护共三层：地址策略（应用层）→ 端点守卫（基础设施）→ 连接钉死 IP（传输层）；单层被绕过（如策略漏了一个 CIDR）还有下一层兜底。

A16.6 地址策略：信任级别、私有 CIDR 与云元数据地址的绝对禁止

textMcpAddressPolicy（McpAddressPolicy.java:19-50）
默认禁止：回环 / 私有 CIDR / 链路本地（169.254.0.0/16）……
  设计文档 06 §5 的豁免：trustTier=internal 显式授权可放行私有地址

绝对禁止（任何信任级别都不豁免，本类的刻意收紧）：
  169.254.169.254   AWS / GCP / Azure 实例元数据
  169.254.170.2     AWS ECS 任务凭据
  fd00:ec2::254     AWS EC2 IPv6 元数据
  100.100.100.200   阿里云元数据

理由：读到元数据 = 读到实例角色的临时凭据
  = 横向移动到整个云账号。没有任何业务理由需要
  MCP 访问元数据地址 —— 所以不做豁免，直接禁止。
为什么「字面覆盖」还要刻意收紧

设计文档的「除非 trustTier=internal」在字面上也覆盖了 169.254.0.0/16；实现把它拆开：私有地址可按信任级别豁免，元数据地址不可。这是「威胁建模驱动实现」的例子——规则不是从文档抄的，是从「攻击者拿到它会发生什么」倒推的。Java 后端对接外部 HTTP 时的同款检查清单：SSRF 三件套 + 元数据黑名单 + 凭据不进池。

证据： platform/agent-application/.../cap/McpAddressPolicy.java:19-50；McpAddressPolicyTest.java / McpSecurityBehaviorTest.java。

A16.7 熔断器：按 server 维度、CLOSED/OPEN/HALF_OPEN 与快速失败

McpCircuitBreaker（装配参数：阈值 5 次失败、OPEN 持续 30s，ApplicationConfiguration:1660-1663）按 server 维度分组熔断：一个坏掉的 MCP Server 不应让其它 server 全部不可用（对比全局熔断：「一坏全坏」）。状态机 CLOSED → OPEN → HALF_OPEN：失败累计到阈值进 OPEN；OPEN 期间快速失败——每次调用都去等一次超时，是把熔断做成了限流；30s 后进 HALF_OPEN 放探测请求，成功复位 CLOSED。

注意它与 A14.10 的关系：模型侧没有熔断器（失败率治理靠指标 + 告警），MCP 侧有——因为 MCP server 是「自己登记的外部依赖」，质量不可控且数量多；模型网关是平台统一管理的一等资源，熔断的收益场景不同。同一个「要不要熔断」的问题，两处答案不同，且都有明确理由。

证据： platform/agent-infrastructure/.../mcp/McpCircuitBreaker.java:21-78；platform/platform-bootstrap/.../ApplicationConfiguration.java:1660-1663。

A16.8 输出不可信：可信化在 Gate 边界，不在传输层

HttpMcpTransport 对远端返回的文本原样透传（:56-57 注释：「本类不做任何『清洗后即安全』的假设」）。可信化统一在 Gate 边界做：MCP 工具结果经 McpUntrustedOutput / UntrustedOutputEnvelope 包装，再按 A1.8 的不可信数据原则处理（围栏 + USER 消息注入）。为什么不在传输层清洗：传输层不知道下游怎么用这段文本，任何「清洗」都可能既是多余的又是不足的；信任边界唯一且明确，审计与测试才有单一锚点（与 A13.6 记忆围栏同一设计哲学）。

证据： HttpMcpTransport.java:56-57；McpUntrustedOutput.java / UntrustedOutputEnvelope.java / McpOpAllowlistNormalizer.java；McpUntrustedOutputTest.java。

A16.9 唯一执行入口：MCP 工具与原生工具共用 ToolInvocationGate

这一条写在三处注释里（:106-113、:313-315）：MCP 工具不另开执行入口，与原生工具共用 ToolInvocationGate 这一条路径——否则八道闸门（Schema 校验、执行时授权、幂等键、账本、审批、预算、执行、账本更新）对 MCP 全部失效。配置层 cap_mcp_server_def 的 CHECK 约束（transport ∈ {http,sse,stdio}、dynamic_discovery = false 强制）与运行时这条「共用入口」配对：配置面管「能不能登记」，运行面管「能不能执行」，两面都不留旁路。A4.4 的依赖方向图（ToolDefinition / McpServerDef → SkillDefinition → AgentDefinition，唯一执行入口 ToolInvocationGate）在这里落到代码。

证据： platform/agent-worker/.../execute/ToolInvocationGate.java:106-113, 313-315；deploy/sql/platform/01_platform_ddl.sql:2033-2056（cap_mcp_server_def 及 CHECK）；McpBackedToolHandler.java。

迁移提示：把 MCP 防护翻成 Java 后端语言

MCP 客户端 ≈ 一个会执行外部指令的出站 HTTP 集成层，它的防护清单其实适用于所有「按配置调用外部端点」的场景（webhook、回调、第三方 API）：SSRF 三件套（解析后校验 / 二次解析复验 / 连接=校验值）、云元数据绝对禁止、凭据逐请求解析不进池、按依赖维度熔断快速失败、输出在唯一信任边界可信化、唯一执行入口不留旁路。AI 特有的部分只有最后一条的「八道闸门」——那是 A4 的领地。
