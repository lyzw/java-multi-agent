1目标使用场景与非目标

1.1 目标场景

优先级场景描述
P0 主场景 学生针对错题归因结果追问 学生在查看归因结果 / 讲解（/runs/:runId/result、/rag 检索页）后仍有疑问，用自然语言追问：「这道题第二步为什么用配方法？」「(2x+1)² 展开后中间项是怎么来的？」。问答页以独立对话页呈现（路由 /ask，学生侧不挂 area，任何已登录用户可见），并可从结果页 / 检索页携带上下文跳入。
P1 次场景 知识点开放式提问 不绑定某道错题，直接问概念性问题：「一元二次方程判别式小于零是什么意思？」。后端检索按当前租户语料回答，回答必须可溯源（引用片段）。
P2 延伸 教师 / 运营侧复用 同一套聊天组件后续可作为「语料问答」嵌入管理侧（admin-console 需另行适配 antd，本规划不覆盖）。

1.2 非目标（明确排除）

  • 不做多轮 Agent 编排可视化：这是「普通 AI 聊天框」，不是 Run 执行过程监视器。Run 进度已有 /runs/:runId 页与 SSE 链路，两者不混用。
  • 不做语音 / 图片 / 文件输入：P1 仅文本输入。
  • 不做流式打字机特效优先：若后端仅提供同步生成端点（当前 /api/v1/retrieval/generate 即如此），就如实整段返回 + 呼吸纸面加载态；不为特效而伪造流式（fail-closed：不假装在流式）。
  • 不做自动埋点推断：任何反馈（👍/👎）只来自用户显式点击，对齐 recordRunFeedback 的 L3 有噪信号纪律。

产品签名约束（对齐既有设计纪律）

本项目是「批改纸」视觉体系（墨色 + 纸面 + 批改红边），不引入 antd、不引入圆角卡片阴影、不引入灰色微光骨架屏。聊天气泡是本功能新增的唯一视觉概念，样式规范见 §5，必须落在 tokens.css 既有变量体系内。

2.2 异常分支一览

异常判定前端行为
输入为空 / 纯空白本地校验发送按钮保持禁用，不发起请求。
请求超时requestWithTimeout 归一为 REQUEST_TIMEOUT（对齐 RAG 20s 超时纪律）错误气泡：「等待回答超时」+ 下一步「重试 / 换个问法」；用户气泡保留、可重发。
限流（429）ApiError.normalized错误气泡明确「提问太频繁」+ 冷却提示；不做自动重试（会烧配额）。
后端能力未接入约定 501 / 配置开关整页 Unavailable（标注阻塞编号），输入框禁用——不提供「看起来能用但必然失败」的入口。
401 会话失效复用 _request 既有 401 兜底由全局 UnauthorizedBridge 清会话跳登录，聊天组件不另行处理。
组件卸载 / 路由离开AbortController.abort()中止在途请求，cancelled 守卫防 StrictMode 双挂载 setState（对齐 useRunStatus 纪律）。

2.3 对话历史与自动滚动

  • 会话内历史：单会话消息全量保存在内存 + sessionStorage（刷新恢复，关闭标签即清除——不落 localStorage，避免未成年人对话内容长期驻留浏览器）。
  • 跨会话历史：P2 提供侧栏「历史会话」列表（后端需提供会话列表端点，见 §6）；P1 仅「当前会话」+「开启新会话」按钮。
  • 自动滚动策略（关键细节，见 §4.4）：
    • 用户位于底部附近（距底 < 80px）→ 新消息 / 流式增量到来时自动跟随滚动；
    • 用户已上翻阅读历史 → 停止跟随，在输入框上方浮现「回到底部 ↓」胶囊（含未读新消息数）；
    • 用户发送消息 → 无论当前位置，强制滚到底。

│  ├─ scrollBehavior.ts      # 距底判定 / 跟随 / 强制滚动（纯函数，可单测）
│  ├─ sessionStorage.ts      # 会话持久化（sessionStorage 读写 + 版本号防脏数据）

│  ├─ MessageBubble.tsx      # 单条气泡（user / ai / error 三态 + 引用 + disclaimer）
│  ├─ TypingIndicator.tsx    # 呼吸纸面等待态（复用 .loading 视觉语言）
│  ├─ ChatInput.tsx          # textarea + 发送 + 停止 + 字数上限提示

└─ tests/ask/                 # vitest 用例，见 §7

分层原则

chatState.ts 与 scrollBehavior.ts 保持纯函数（无 React 依赖），单测不必渲染组件——对齐 features/run/runState.ts、sse.ts 的既有风格。页面组件只做装配，业务规则全部下沉 feature 层。

4关键状态管理要点

4.1 技术选型：不引入状态库

工程现状为 React hooks + 自定义 hook，零全局状态库（grep 确认无 redux/zustand/recoil）。问答状态是页面局部状态，不跨页面共享（跳入时经 URL 参数携带上下文即可），故：

决策

用 useReducer + 单一 useChatSession hook 管理全部问答状态；不引入 Redux/Zustand。若 P2 出现「多页面共享会话」的真实需求，再评估——为假设的需求引入状态库是过度设计。

4.2 消息数据模型

// chatTypes.ts —— 与后端契约对齐后微调
export type MessageRole = 'user' | 'assistant'

export type MessageStatus =
  | 'sent'        // 用户消息已入列
  | 'streaming'   // 回答接收中（若走流式端点）
  | 'done'        // 回答完整落地
  | 'failed'      // 本条回答失败（用户气泡保留，失败原因在伴随的错误气泡）

export interface Citation {          // 回答引用的语料片段（可溯源，⛔ 不凭空生成）
  hitId: string
  sourceTitle: string
  snippet: string
}

export interface ChatMessage {
  id: string                         // 前端生成（crypto.randomUUID()），重试时不复用
  role: MessageRole
  status: MessageStatus
  content: string
  citations?: Citation[]             // 仅 assistant
  disclaimer?: string                // 仅 assistant：生成方式声明（EXCERPT_ASSEMBLY 必须展示）
  createdAt: number
  error?: { code: string; message: string }   // 仅 failed 的 assistant 位
}

export interface ChatSession {
  id: string                         // 后端会话标识（P1 可本地生成）
  title: string                      // 首条用户消息截断
  messages: ChatMessage[]
  updatedAt: number
}

4.3 Reducer 动作与防竞态纪律

Action语义防坑要点
SEND_START乐观插入 user 气泡，sending=true发送期间禁用发送按钮但保留输入内容（失败可改后重发）；同时暴露 stop()。
REPLY_DELTA流式增量追加到最后一条 assistant 消息仅在流式端点下存在；批量合并增量（如 60ms 节流）避免高频 re-render。
REPLY_DONE回答落地，写入 citations / disclaimer⛔ disclaimer 必须随答案渲染——只展示 answer 等于把摘录伪装成 AI 讲解（后端既有红线）。
REPLY_FAILED置 failed + 错误信息错误码取 ApiError.normalized.code，文案归一（超时/限流/网络分口径，见 §2.2）。
RETRY移除失败气泡，以原问题重发新 AbortController；旧 controller 必先 abort。
STOP用户主动停止abort + 气泡标记「已停止」而非 failed——用户主动 ≠ 出错，混同会让用户以为系统坏了。
HYDRATE / NEW_SESSION恢复 / 新建会话hydrate 读 sessionStorage 带版本号校验，脏数据直接丢弃回空态（fail-closed）。

两条铁律（直接抄自工程既有教训）

  • effect 内 cancelled 守卫：所有异步 setState 前检查，防 StrictMode 双挂载与路由离开后的 setState（useRunStatus 同款）。
  • 在途请求单一化：同一会话同一时刻至多一个在途回答；sending 状态下不排队第二条——初中生场景追问应等回答落地，排队会造成消息序与回答序错位。

4.4 自动滚动（独立纯函数模块）

// scrollBehavior.ts —— 全部纯函数，可单测
export const STICKY_THRESHOLD_PX = 80

/** 距底 < 阈值 → 认为用户「贴底」，允许跟随 */
export function isNearBottom(el: HTMLElement): boolean

/** 新消息到来时是否应自动滚动：贴底 或 消息由本用户发出 */
export function shouldAutoScroll(
  nearBottom: boolean, byUser: boolean
): boolean
  • 滚动监听用 scroll 事件 + requestAnimationFrame 节流即可（消息量级小，不上 IntersectionObserver）。
  • 「回到底部」胶囊状态（可见性 + 未读数）由 reducer 管理，避免放在 DOM ref 里导致测试不可断言。
  • ⛔ 不用 smooth 滚动跟随流式增量（连续 smooth 会抖动）；仅用户点「回到底部」时用 smooth。

4.5 会话持久化与隐私

  • P1：sessionStorage（键 ask.session.v1），刷新恢复、关标签清除；写入前 JSON 校验 + 版本号不符即弃。
  • P2 起若后端落库会话历史，前端只做缓存不做真相源（后端为权威快照，对齐「单一数据源」纪律）。
  • 对话内容属学生个人信息：不在前端做任何导出/分享入口，P2 历史列表的删除能力以后端物理不可删（平台纪律）为准绳做「隐藏」语义。

5五态对齐与视觉规范

5.1 五态映射（工程既有 FE-D3 §4 纪律：五态不可互相混淆）

状态问答场景下的定义呈现
默认会话进行中消息列表 + 输入框常驻。
加载已发送、等待回答最后一条下挂 TypingIndicator：「正在组织讲解…」呼吸纸面动画。⛔ 不用灰色微光条。
空查了，确实没有消息（新会话）Empty + 3 条可点击示例问题（点击即填入输入框）——空态是邀请行动，不是死话「暂无数据」。
错误某条回答失败内联错误气泡（原因 + 下一步 + 重试）；不弹全局 toast、不清空对话。
未开放后端问答端点不存在整页 Unavailable（阻塞编号可追溯）+ 输入框禁用。⛔ 与「空」严格区分。

5.2 气泡样式规范

气泡实况预览

这道题第二步为什么要先移项？
先移项是为了把方程整理成 ax² + bx = c 的标准形，这样系数才好配平方……

规范要点

  • 用户气泡：右对齐、墨色底白字（--ink）、右下直角；最大宽 78%。
  • 回答气泡：左对齐、纸面底（--paper-2）+ 1px --line 边、左下直角；⛔ 不用品牌色底，回答是「纸上的批注」不是「聊天气球」。
  • 引用：气泡内低饱和胶囊（--accent-soft），点击展开片段原文；无引用的回答必须显式标注「本回答无语料依据」（fail-closed）。
  • disclaimer：虚线分隔的脚注小字，后端给了就展示，前端不吞。
  • 错误气泡：批改红边语言（对齐 .marked），含重试动作。
  • 长文本：正常换行、保留空行；P1 不做 Markdown 渲染（避免引入解析器与注入面），纯文本 + 换行保留。

5.3 可访问性

  • 消息列表 role="log" + aria-live="polite"，新回答可被读屏感知；typing 态 role="status"。
  • 输入框带 <label>（复用 .field 结构）；发送按钮有明确可访问名；错误气泡 role="alert"。

6API 依赖与后端缺口（fail-closed）

6.1 两条实现路线

路线做法流式评估
A · 最小闭环
推荐先行		 复用现有 POST /api/v1/retrieval（检索召回）+ POST /api/v1/retrieval/generate（摘录装配）。前端把「问题 → 检索 → 生成」串成一轮回答；多轮追问在前端把历史摘要拼进检索 query。 否（同步 20s 超时） 零后端改动即可上线；回答为摘录装配，必须展示 generator 与 disclaimer；引用天然可溯源。受 A-008 / G3 占位限制，讲解质量有限但诚实。
B · 专用问答端点
目标形态		 后端新增 POST /api/v1/qa/sessions + POST /api/v1/qa/sessions/{id}/messages，服务端维护会话上下文，SSE 流式返回（复用既有 SSE 帧格式与 IncrementalSseParser）。 是 前端 chatApi 预留双实现：接口层已按「同步 / 流式」抽象，切换只动 chatApi.ts 一层。

6.2 必须遵守的调用纪律（沿用既有约定）

  • X-Tenant-Id 头：走 RAG 链路（路线 A）时必须携带，缺失后端 400——此前生成端点漏传该头是已确认缺陷，此处列为验收项。
  • 限流意识：发送按钮防抖 + 失败不自动重试；若路线 B 上线，问答端点限流桶与 EVENT_QUERY（30 次/60s）的关系须由后端明示，前端轮询/重连策略不得新增未报备的请求链。
  • 错误归一化：只走 api/errors.ts 的归一化产物，组件层不直接读 HTTP 状态码。
  • 401 兜底：不新增处理，交给全局 UnauthorizedBridge。

8实施分期

阶段范围验收口径
P1 最小闭环：路线 A（检索 + 摘录生成）、单会话、五态齐全、错误/超时/停止、空态示例、sessionStorage 恢复、自动滚动 /ask 可用；mvn 之外的前端 npm run typecheck + vitest 全绿；无引用回答有显式标注；disclaimer 必现。
P2 历史会话侧栏（依赖后端会话端点）、从结果页/检索页带上下文跳入、反馈 👍/👎（显式动作，接 recordRunFeedback 或专用端点） 上下文跳入后首条消息携带题目摘要；后端未接入的部分一律 Unavailable 而非隐藏入口。
P3 路线 B 流式端点接入、REPLY_DELTA 增量渲染与节流、追问上下文由服务端维护 流式断线可续（Last-Event-ID）；切换实现仅改 chatApi.ts，组件层零改动。

风险与未决

  • 路线 A 的回答质量受 RAG G3 占位（逐字摘录而非模型生成）限制——产品话术须如实定位为「语料检索式问答」，禁止包装成「AI 智能讲解」。
  • 「多轮追问」在路线 A 下是前端拼接（检索 query 携带历史摘要），上下文窗口有限，追问超过 3 轮建议引导「开启新会话」。
  • 后端问答会话端点（路线 B）尚无排期，P1 交付不依赖它；chatApi 的接口抽象须在 P1 就位，避免 P3 返工组件层。
