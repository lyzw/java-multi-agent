**修订批次**：Agent Multi-Agent Orchestration Change Set v1.1  
**基线**：Java SaaS Agent v3.1；Agent / Skill / Tool / MCP 契约 v1.0-rc2  
**状态**：设计修订候选；待架构、安全、产品/业务、QA 联合评审。本文档包不代表运行时已经实现。

## 本次修订原则
- 保留现有架构、命名和 P0–P5 阶段，不另建并行体系。
- 统一使用 `AgentDefinition.orchestration` 表达编排，旧配置缺字段时兼容为 `LEAF`。
- 通过固定版本子 Agent 引用、递归发布闭包、`configFingerprint` 和 CAS 保证可复现。
- 每跳授权；委派关系不是授权关系。沿用 `EffectiveConfigResolver`、`ConfigTighteningPolicy`、`AuthorizationService`、`ToolInvocationGate`、`authzVersion` 和 `execution_snapshot`。
- V1 默认有界串行；动态发现、并行委派、跨租户委派、无界递归、跨 Agent 自动补偿不开放。

## 评审前置决策
1. 是否将 `SEQUENTIAL` 纳入 P2，或仅先交付 `ROUTER`，由产品/架构在 P1 决策。
2. 最大深度、子调用数、超时和预算默认值由容量与业务风险评估后确定，不把示例值视为生产默认值。
3. `agent_invocation` 的最终状态枚举、父子取消语义、重试和 UNKNOWN 条件须在 P1 状态机/ADR 冻结。
4. `cap_agent_child_ref` 为可选关系投影设计；需由 DDL/迁移评审决定是否存储，Agent release 内容仍为权威来源。
5. P3 安全和恢复验收未通过前，多级 Agent 不得标记为生产可用。

### 历批修正的设计缺陷（已改，记录在案）

| 缺陷 | 现象 | 修正 |
|---|---|---|
| 超时判定语义错误 | `DelegationGuard` 原把「根 Run 剩余时间 **>** 本级 `timeoutMs`」判为超时；而闸门拿不到 Run 真实剩余时间（只能传上界）→ **所有经闸门的委派都会被拒** | 改为「有效预算 = `min(根 Run 剩余时间, 本级 timeoutMs)`」：本级 timeout 仍封顶，根 Run 剩余更长属常态，不再误拒（`DelegationGuardTest#remainingTimeIsCappedByLevelTimeout`） |
| 原因码混淆 | 「父是 LEAF（拓扑事实）」与「目标未声明（越界尝试）」共用 `DELEGATION_TARGET_NOT_DECLARED` → 审计无法区分「配错了」与「越权了」 | `DelegationExecutor` 先判父的编排模式，LEAF → `DELEGATION_NOT_ALLOWED`（`DelegationExecutorTest#leafParentCannotDelegate`） |
| 四字段混淆 | 子执行失败被记成「授权 DENY」→ 审计把「执行失败」说成「越权被拒」 | 引入 `childStarted` 区分拒绝与执行失败（`DelegationGateBranchTest#childExecutionFailureIsNotRecordedAsAuthorizationDenial`） |
| UNKNOWN 后未停 | 委派分支遇 `UNKNOWN` 仍继续执行本轮后续工具调用 | UNKNOWN 即返回，后续调用不再启动 |
| 世代令牌写死 | `agent_invocation` 的 `fencing_token` 与终态 CAS **都写死 `1L`** → 任何世代都能提交终态，MA-T12「旧 fencing token 不能提交结果」形同虚设 | 改用命令携带的真实 `fencingToken`；终态写入结果**三态可区分**，token 过期时**不承认**本次结果（报 `UNKNOWN` 交对账） |
| 预算预留不可见 → **调用被静默丢弃** | 既有链路（`invokeAllLegacy`）在「预留已生效、但 `findByOperation` 查不到预留记录」时返回 `null`，调用方把 `null` 一律当成「已记录拒绝」直接 `continue` → 工具没执行、账本停在 `IN_FLIGHT`、**没有拒绝原因、没有拒绝记录、模型收不到反馈**，这次调用**从系统里彻底消失**（不可见、不可对账） | 与 CAP 链路对齐：`reserveBudget` 在该情形下 **fail-closed** —— 工具不执行（无 reservationId 就无法结算/释放）、账本记 `FAILED`（工具根本没发出 = 确定失败）、写入明确的拒绝原因；若预留行已落库则成为悬挂预留，由对账释放（`ToolInvocationGateBudgetGuardTest`） |
| 工具结果只写进 `result_events` | CAP 链路的工具输出**没有回传给调用方** → 模型看不到自己刚调了什么，多轮工具协作无法成立（子 Agent 调完工具即结束，等于工具调用无意义） | `CapToolDecision` 增 `output` + `CapExecutionFlow` 成功路径回填 → 闸门 `outputs` → 子执行回灌为 TOOL 消息（`CapExecutionFlowTest#successCarriesToolOutputForFeedback`） |
| 有效预算**只判定不下传** | 守卫算出「有效预算 = min(根剩余, 本级 timeout)」却只返回「允许/拒绝」，执行器于是把**本级声明值** `orchestration.timeoutMs()` 下传给子执行 → 根 Run 的剩余时间只是「参与了一次判定」，**毫无强制力**：根 Run 只剩 10 秒时子 Agent 仍会跑满 30 秒 | 守卫改为返回 `Verdict`（决策 + `effectiveTimeoutMs`），执行器按**有效预算**下传（`DelegationExecutorTest#effectiveBudgetIsPassedDownToChild`） |
| 闸门把根剩余传成上界 | 闸门委派分支传 `Long.MAX_VALUE` 当「根 Run 剩余时间」（当时 `run` 表无截止时间字段）→ 「全调用树共享超时上限」在根层**从未真正生效**：父 Agent 可无限次委派，每一跳都能跑满自己的 timeout | `run.deadline_at`（V21）+ `LeasedTask.remainingMillis` + 闸门真实剩余；剩余 ≤ 0 时**在新增子调用前**拒绝（`DelegationGateBranchTest`） |
| 预算探针只看租户级 | `BudgetBalanceProbe` 判定的是**租户级余额**（`budget_account` 只有「租户+币种」维度）→ 「这一棵调用树没超预算」**没有任何独立口径**：一个 Run 可以把租户余额烧光，而 MA-T17「不能通过嵌套重置额度」在系统里是空的 | 新增 `RunBudgetPort` + `run.budget_amount`（V22）+ `RunBudgetProbe`；探针升级为**双口径**（租户级 AND Run 级）；两条工具调用链路在预留前强制（`BudgetBalanceProbeTest` / `ToolInvocationGateRunBudgetTest` / `CapExecutionFlowTest`） |
| Run 额度校验被错误地与截止时刻绑定 | `RunLimits` 构造期写成「有 deadline **且** 额度 ≤ 0 才拒绝」→ 「只声明额度且额度为 0」的组合被**漏放**（额度为 0 = 明确禁止花钱，意图失效） | 额度校验**独立于**截止时刻（`RunLimitsTest#nonPositiveBudgetIsRejected` 钉死） |
| 根 Agent 看不到自己的工具结果 | `RunExecutionLoop` 每轮都用**同一份** `renderInput(input)` 作为模型输入 → 第 2 轮上下文与第 1 轮完全相同，模型无法基于工具结果继续推理。子 Agent 侧早已回灌（第五批），于是形成**父子两套语义** | 根循环改用消息序列回灌，并与子执行器**共用** `ToolOutcomeRenderer`（避免两份实现漂移）；反证已做：临时移除回灌后 3 条用例全部变红 |
| 接管后在途委派**永远悬着** | Worker 崩溃后新世代接管，但 `agent_invocation` 的在途记录仍带**旧世代** token：新世代 CAS 写不了终态、旧世代也写不了 → 记录永远 RUNNING；重放时幂等分支返回该 RUNNING 状态 → 父 Agent 收到「执行失败」，**真实原因（Worker 崩溃）被掩盖** | 接管时提升世代令牌（`adoptInFlight`）→ 收敛为 UNKNOWN（结果不可知，交对账）→ 重放拿到 UNKNOWN 且**不重跑**子 Agent（`InFlightDelegationAdopterTest` / `DelegationExecutorTest#takeoverThenReplayYieldsUnknown`） |
| **编排声明在闭包里零表示** | `ClosureFingerprint.canonicalJson` 只写 Agent 的 `(id, version)`，**编排声明（路由策略引用 / 输出契约引用 / 超时 / 深度 / 次数 / 失败策略）完全没有进指纹**。后果不是「漏判」而是**漏判成「没变」**：① 同一版本行的编排声明被就地改写 → 指纹不变 → 在途 Run 不失效、绑定了旧指纹的审批被**继续复用**（MA-T18）；② 子 Agent 的编排漂移 → 子闭包指纹不变 → 子工具审批绑定形同虚设。**「指纹说没变，行为却变了」** —— 这正是指纹机制要防的那类事故 | `EffectiveClosure` 增第 7 分量 `OrchestrationBinding` + `ClosureFingerprint` 增 `orchestration` 段（空值写显式 `null`）+ `PermissionResolver` 在构建期解析一次并固化；反证已做：移除编排段 → 5 条变红，不填充绑定 → 4 条变红（`ClosureFingerprintTest` / `PermissionResolverMultiLevelTest` / `DelegationApprovalScopeTest`） |
| **闭包缓存只比版本号 → 陈旧闭包藏住漂移** | `CachingClosureResolver.isFresh` 对 Agent 只比**版本号**，不比**内容指纹** → 「同一版本行被就地改写」（如编排声明被改）不被察觉，缓存继续供出陈旧闭包 —— 于是上一行的漂移在**缓存层**就被抹平，指纹永远算不出变化 | `Entry` 增记 Agent 版本行的内容指纹（覆盖编排声明），`isFresh` 比对之；读不到定义行 → 判定不新鲜（fail-closed）；反证已做：去掉该比对 → 1 条变红（`CachingClosureResolverTest#changedOrchestrationInvalidatesCache`） |
