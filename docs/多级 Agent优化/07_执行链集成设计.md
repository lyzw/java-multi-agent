# 07｜执行链集成设计

> 定位：定义新增校验组件与**现有 `ToolInvocationGate`** 的职责边界，避免重复校验与绕过路径。
> 评审依据：03 P0-2（授权校验与现有执行闸门缺少接口契约）、C4（职责未划清）、05（授权≠执行）。

---

## 1. 组件职责表（唯一真相）

| 组件 | 职责 | 输入 | 输出 | 失败语义 | 复用/新增 |
|---|---|---|---|---|---|
| **PermissionResolver** | 计算"有效能力闭包"（Agent→Skill→Tool/MCP），合并继承/覆盖/收紧 | Agent/Skill/Tool/MCP 配置 + 租户覆盖 | `EffectiveClosure`（含 `configFingerprint`） | 配置缺失/环/放宽为 CONFIG_ERROR DENY | 新增（复用 `EffectiveConfigResolver` 读取） |
| **InvocationValidator** | 调用期**能力链+配置约束**判定（不含预算/执行副作用） | `AuthContext` + `EffectiveClosure` + 本次调用目标 | `Decision(allow/deny, stage, code)` | 任一因子 false → DENY（05 公式） | 新增（实现 05 §1–§4） |
| **AuthorizationService** | 主体当前授权 + `authzVersion` 重授权 | `AuthContext`, action, resourceId | bool（实时） | 陈旧/不足 → DENY(stale_authz) | 已有（换 DB 实现，04 §1.1） |
| **ToolInvocationGate** | **唯一执行入口**：输入校验→重授权→幂等→账本→审批→预算→执行→账本更新 | `ToolHandler` + 调用参数 | 执行结果 + `executionStatus` | 各闸门独立拒绝（不混淆为授权 DENY） | 已有（ADR-011 禁绕过） |
| **ApprovalPort** | 风险驱动审批（REQUIRED/OPTIONAL），绑定操作+参数域+指纹 | 工具/风险/参数 | 审批态 | 缺失/拒/不可确认 → DENY(approval) fail-closed | 已有（`RiskBasedApprovalPolicy`） |
| **BudgetPort** | 预算预留（幂等键） | tenant/run/tool | 预留成功/失败 | 不足 → DENY(budget) | 已有 |
| **RunToolLedgerPort** | 账本登记（幂等） | invocationId/结果 | 登记 | 写入失败 → 重试/告警 | 已有 |
| **ToolHandler** | 原子执行（native 或 MCP-backed 统一接口） | 校验后参数 | 结果（含 UNKNOWN 对账） | 异常 → FAILED/UNKNOWN | 已有（MCP-backed 包装新增） |

> 组件名是**职责划分**，非认定当前已存在这些新类。`InvocationValidator` 与 `PermissionResolver` 为本次新增；其余复用既有。

## 2. 调用契约顺序（T3，无重复副作用）

```
调用进入 ToolInvocationGate.invoke(agentId, skillId, toolId|mcp, params, ctx)

[1] PermissionResolver.resolve(ctx)  → EffectiveClosure（命中缓存则校验 authzVersion/fingerprint 仍有效）
[2] InvocationValidator.validate(ctx, closure, target) → Decision
        ├ false → 写决策日志(DENY, stage, code) → 返回（不执行）
        └ true  → 继续
[3] AuthorizationService.isAuthorized(ctx, TOOL_INVOKE, toolId)  → 实时主体授权（不允许以快照代替）
[4] ToolHandler.validate(params)  → 结构校验（JSON Schema）
[5] ApprovalPort.check(tool, params, fingerprint)  → 风险审批（REQUIRED 且未满足→DENY）
[6] BudgetPort.reserve(tenant, run, tool, idempotencyKey)  → 预算（不足→DENY）
[7] RunToolLedgerPort.record(invocationId, PRE)  → 账本
[8] ToolHandler.execute(params)  → 执行；UNKNOWN → reconcile → 对账队列
[9] RunToolLedgerPort.record(invocationId, POST, executionStatus)
→ 返回 Decision(ALLOW) + executionStatus
```

**边界铁律**：
- `[2] InvocationValidator` **只做能力链+配置约束判定**，不预留预算、不写账本、不执行——避免与 `[6][7]` 重复副作用。
- `[3]` 主体授权**必须用实时 `authzVersion`**，禁止用 `[1]` 的闭包快照代替（评审 02 §3.3）。
- `[5][6][7]` 的审批/预算/账本由既有闸门 Port 负责，**不得**在 `InvocationValidator` 内重复执行。

## 3. 唯一执行入口与防绕过

- **所有** Native Tool 与 MCP-backed Tool **必须**经 `ToolInvocationGate` 单一入口；ADR-011 禁止 Spring AI 自动执行、禁止直接调用 `ToolHandler` 实现类。
- **集成验收条件**（进入 PoC 强制）：
  - 静态：扫描确认无任何 `ToolHandler.execute()` 被业务代码直接调用（仅 `ToolInvocationGate` 调用）。
  - 运行时：注入"绕过闸门直接调用工具"的测试 → 必须失败（无授权上下文即拒绝）。
  - 覆盖：每个 MCP-backed Tool 与 Native Tool 走同一 `invoke` 路径，决策日志格式一致。

---

## 4. 配置读取与缓存失效

- `PermissionResolver` 闭包结果按 `(tenantId, agentId, agentVersion, configFingerprint, authzVersion)` 缓存。
- `authzVersion` 变化 → 失效（DB 一致源，04 §1.1）。
- `configFingerprint` 变化（含 MCP 固定清单变更）→ 失效 → 新 Run 重新计算；已有 Run 快照 mismatch → `config_stale` DENY（06 §4）。
- 版本服务不可用 → fail-closed 拒绝新调用（05 §5）。

## 变更补充：AgentInvocation 运行时委派（v1.1）

### 执行链
`Run → Root Agent → AgentInvocation → Child Agent → Skill → ToolInvocationGate → Tool/MCP`。子 Agent 仍使用原 Tool 执行链，不允许绕过 `ToolInvocationGate` 或直接调用 MCP Client。

### 委派时序
1. RouterAgent 输出候选目标及结构化委派输入；模型输出仅为候选决策。
2. 服务端验证目标是否在**当前执行中的 Agent** release 的 `childAgentRefs` 中，且目标 release 与 `execution_snapshot` 一致。⚠️ **第十五批**：此处的「当前 Agent」= 嵌套委派时**发起委派的那个 Agent**（不是根 Agent），由 `DelegationContext` 逐跳传下来；根调用时仍按 Run 能力快照解析（见下「嵌套委派的执行语义」）。
3. **ROUTER 模式追加一步路由收窄（第十四批）**：按父声明的固定版本路由策略校验候选是否落在策略允许的目标集合内；策略不可用（不存在 / 未发布 / 读失败）→ fail-closed（`ROUTING_POLICY_UNAVAILABLE`），候选越出允许集 → 拒绝（`ROUTING_TARGET_NOT_ALLOWED`）。
4. 校验深度、剩余调用次数、剩余时间、预算、父调用状态及取消标志。⚠️ **第十六批**：**委派本身也必须占 Run 预算额度** —— 见下「委派的预算口径」。⚠️ **第十五批**：深度按**当前 Agent** 的声明判定；剩余时间按**根 Run 的业务截止时刻**（绝对）计算，逐跳不得重置（见下「嵌套路径的超时共享」）。
5. `AuthorizationService` 对当前主体/委托凭证、租户、目标 Agent 资源和当前 `authzVersion` 重新授权。
6. 持久化 AgentInvocation 与父子关联，再调度子 Agent；重复投递按 invocationId 幂等。⚠️ **第十五批**：invocationId 的派生材料包含**父调用标识**（嵌套路径上不再为 null）→ 不同父的同名 tool call 不再撞号。
7. 子 Agent 结果按输出契约校验，作为不可信业务数据返回父 Agent；失败按声明的 `failurePolicy` 处理。
8. 子 Agent 内 Tool 调用继续执行 T3 门禁、审批、预算、幂等、账本和 UNKNOWN 对账流程。

### 嵌套委派的执行语义（第十五批）

⚠️ **此前闸门构造委派命令时，父身份 / 深度 / 父调用标识恒为「根 Agent / 1 / null」** ——
于是子 Agent 发起的委派被按**根 Agent** 的编排声明判定。本批确立以下口径：

**「当前执行中的 Agent」由 `DelegationContext` 承载**（`core/orchestration/DelegationContext`）：
当前 Agent 标识 + 固定版本号 + 所在深度（根 = 1）+ 该 Agent 自己对应的委派调用标识（根为 null）。
它由 `WorkerChildAgentRunner` 构造并传给闸门，**沿调用链逐跳传下去**。

⚠️ **`DelegationContext` 与 `ExecutionScope` 是两件事，不可互相替代**：

| 对象 | 回答的问题 | 取错的后果 |
|---|---|---|
| `ExecutionScope` | **按哪个 release 授权**（子 Agent 不得借用父的闭包） | 权限下放（Sev-0） |
| `DelegationContext` | **当前处在调用树的哪一层、当前 Agent 是谁**（委派拓扑 / 深度 / 父子链由此推导） | 委派拓扑错判（越权路径） |

二者同时存在时，Agent 标识与版本**必须一致** —— 不一致说明上下文串了（多半是调用方拼错了），
此时**委派一律拒绝**（`ORCHESTRATION_INVALID`，fail-closed）：猜哪个是对的，等于在越权路径上替调用方做决定。

**根路径不变**：无 `DelegationContext` → 父按 Run 能力快照解析、深度 1、父调用标识为 null。

**幂等键口径**：invocationId 的派生材料是「同一 Run + **同一父调用** + 同一模型 tool call」。
父调用标识在嵌套路径上不得为 null —— 否则不同子 Agent 的**同名** tool call 派生出同一个 id，
后者被当成幂等重放，**第二次委派根本没发生**。

⚠️ **「最大委派深度」不级联**（登记为缺口，本批不修）：祖先声明的上限不自动约束后代声明的更大上限。
这是**配置一致性**问题而非模型可利用的攻击面（模型改不了配置），且级联语义本身是未闭环的设计决策
（后代声明更大值可能是刻意意图）→ 待评审决策项 2 一并闭环。

### 嵌套路径的超时共享（第十五批 · C15-2）

⚠️ **此前子执行构造闸门任务时恒传 `deadlineAt = null`（= 不限时）** → 子 Agent 再发起嵌套委派时，
闸门算出的剩余时间是 `Long.MAX_VALUE` → 嵌套预算 = min(无限, 本级声明 30s) = **30s**，
而根 Run 只剩 5s。后果：**只要多套一层，根 Run 的业务截止时间就不再有任何强制力**。

**口径**：根 Run 的业务截止时刻（`run.deadline_at`）以**绝对时刻**沿调用链逐跳下传：

```
根 Run（deadline_at = T）
  └─ 委派命令带 rootDeadlineAt = T
     └─ 子执行请求带 rootDeadlineAt = T
        └─ 子执行的闸门任务 deadlineAt = T   ← 嵌套委派据此算剩余
           └─ 孙执行请求带 rootDeadlineAt = T
```

⚠️ **必须用绝对时刻而不是「本跳剩余毫秒数」**：相对值每跳都要重新起算，
绝对值才是整棵树共享的**同一个**上界。

**子执行侧自己实施**（不由父代劳）：
- 墙钟预算 = min(父给的链路预算, 根 Run 的**真实剩余**)；
- 根截止时刻**已过** → 子执行**不启动**（明知会超时还要先花钱）；
- 注入**墙钟**（与既有的单调 `nanoTime` 分工：绝对时刻必须用墙钟比对）。

### ROUTER 模式的运行期语义（第十四批）

⚠️ **此前 ROUTER 与 LEAF / SEQUENTIAL 的运行期行为完全相同** ——
执行器与守卫只判断「是不是叶子」与「有没有子 Agent」，三种模式走同一条路径，
于是 `routingPolicyRef` 是一句纯装饰。第十四批让 ROUTER 真正走另一条路。

**判定顺序是契约（两层收窄，先拓扑后路由）**：

| 步骤 | 判定 | 未通过时的原因码 | 含义 |
|---|---|---|---|
| ① | 委派拓扑：候选在父的 `childAgentRefs` 内 | `DELEGATION_TARGET_NOT_DECLARED` | **越出委派边界**（越界试探） |
| ② | 路由策略（仅 ROUTER）：候选在策略允许的目标集合内 | `ROUTING_TARGET_NOT_ALLOWED` | 拓扑过了、**路由收窄**没过 |
| ③ | 路由策略可用性（仅 ROUTER） | `ROUTING_POLICY_UNAVAILABLE` | **路由依据不可用**（fail-closed） |

⚠️ 顺序不可颠倒：策略允许集是拓扑的**子集**（发布期强制），
若先判路由，「越出委派边界」会被报成「越出路由允许集」——
两个原因的排查方向完全不同（前者查子 Agent 声明，后者查路由策略内容）。

**fail-closed 优先**：策略取不到（不存在 / 未发布 / 读失败 / 能力未装配）一律拒绝且**不触发子执行**，
绝不降级成「按父声明的子 Agent 随便选一个」——
那等于让「路由策略写了但没生效」变成常态，而外部观察不到任何差异。

**实际生效的目标才是事实**：路由策略降级后，
委派记录（`agent_invocation.target_agent_id`）、子执行请求、闭包解析与逐跳授权
一律使用**生效目标**；调用方钉的目标版本与生效目标对不上时拒绝
（`RESOURCE_VERSION_MISMATCH`）——「钉版本」在降级路径上不得形同虚设。

### 状态与失败语义
AgentInvocation 至少区分 `QUEUED`、`RUNNING`、`SUCCEEDED`、`FAILED`、`CANCELLED`、`TIMED_OUT`、`UNKNOWN`（仅当子操作/委派结果确实不确定且无法证明未执行时使用）。不得把父 Run 失败自动解释为所有已发起副作用均已撤销。

V1 采用有界串行委派；子调用取消传播规则需明确：停止新委派、通知运行中的子调用协作式取消、等待已启动 ToolOperation 进入可解释状态。取消不能保证撤销外部副作用。

### 委派的预算口径（第十六批 · MA-T17）

⚠️ **此前委派是「免费动作」**：闸门的委派分支直接 `continue`，
**绕过**了工具路径的 ⑥ Run 级**金额**判定与 ⑥ **预算预留**。
一次委派会启动子 Agent、子 Agent 会调模型 —— 那是**真实成本**，却**不占任何额度**。

**为什么这是 Sev-0 级的缺口**：MA-T17 的承诺是「全调用树共享预算上限，不能重置额度」。
该承诺此前**只对工具调用成立** —— 所有工具调用都记在同一 `run_id` 下，
按 Run 聚合出的消耗就是整棵树的消耗；**但委派不在聚合里**。
而 `maxChildInvocations` 是**每父 Agent** 的（每层相乘：8 × 8 × 8 = 512 次子调用），
**不是 Run 级上限** → Run 额度本是唯一的 Run 级兜底，却恰好对委派不管用。

**执行链（第十六批）**：

```
委派发起
 ├─ ① Run 级**金额**判定（runBudget.check：剩余额度 ≥ 本次预留额）
 │     └─ 不足 → 拒绝（BUDGET_EXCEEDED）+ **零子执行**
 ├─ ② 权威预留（budget.reserve，幂等键 = 委派 invocationId）
 │     └─ 失败 → 拒绝 + **零子执行**
 ├─ ③ 执行委派（既有链路）
 └─ ④ 按结局处置预留：
       成功        → 结算
       执行失败     → 结算   （子执行已启动 = 子 Agent 跑过了 = 成本已发生）
       被拒         → 释放   （子执行从未启动 = 零成本 = 额度原样退回）
       UNKNOWN     → 既不结算也不释放（成本是否发生未知 → 留 RESERVED 待对账）
```

⚠️ **工具与委派共用同一份预算预留核心**（`reserveQuota`）—— 两份实现必然漂移，
而漂移就是「两个真相」本身。

⚠️ **「执行失败 → 结算」与工具路径的「确定失败 → 释放」刻意不同**：
工具的确定失败 = 工具没产生副作用；子执行的失败 = 子 Agent **已经运行过**。

⚠️ **预留额取「一次调用当量」—— 本批取舍，非评审冻结的定价模型**：
预算体系当前按「调用当量」计量，真实成本由 `usage_record` 独立记录（P3-D04 §6 L-5）。
一次委派的真实成本（子 Agent 的多轮模型调用）**高于**一次工具调用当量，
故本口径是**保守下界**，不是精确计价。
⚠️ **模型调用本身仍未计入 Run 额度**（根与子 Agent 的模型调用都是）——
彻底修需要冻结成本模型（token 计价），属**未闭环范围** → 已登记为缺口。

⚠️ **行为变更**：租户**未开通预算账户**时，委派从「能跑」变成「被拒」
（`NO_ACCOUNT`，fail-closed）—— 与工具调用**同口径**；此前委派完全不碰预算，
才造成「多级 Agent 在没开预算的租户上能用、单 Agent 工具路径不能用」的不一致。

### 工具幂等键的 Agent 维度（第十七批）

⚠️ **此前键里没有「谁在调用」**：形状是 `run_id/tool_name/call_id`。
而账本命中重复键时**复用既有 operation、不再次执行工具** —— 于是
**父 Agent 与子 Agent**（或两个**兄弟**子 Agent）调用
**同名工具 + 同名 model call id**（模型通常都叫 `call_1`）时算出同一个键 →
后者被当成前者的幂等重放 → **那次工具调用根本没发生**，
且模型拿到的还是**另一个 Agent 的结果**。

**执行链（第十七批）**：

```
工具调用（闸门）
├─ 解析「当前执行中的 Agent 引用」
│    执行作用域 → 委派上下文 → 无（单 Agent 路径）
│    引用格式 = agentId@version（唯一定义：IdempotencyKey.agentRefOf）
├─ 算幂等键
│    run_id / [agent_ref] / tool_name / call_id
│    ⚠️ agent_ref 可省略：单 Agent 路径的键与历史逐字符一致
└─ 两条链路共用同一个值
     既有链路（ToolInvocationGate.invokeAllLegacy）
     CAP 链路（CapExecutionFlow.invoke(..., scope, agentRef)）
```

⚠️ **为什么由闸门算一次再透传**：「当前 Agent 是谁」在两条链路上来源不同
（既有链路看委派上下文，CAP 链路看执行作用域），
各算各的必然漂移 —— 漂移出来的不是「两条路径各自的键」，
而是「同一次调用在两条链路上算出两个键」。

⚠️ **刻意不动 `record_weakness`**：它的键**不含** Agent 维度
（业务事实全局唯一，父子记同一条被幂等拦下是正确行为）。

### 子 Agent 路径的授权与准入口径（第十八批）

⚠️ **此前 CAP 链路的子 Agent 路径整体不可用**：子 Agent 的每一次工具调用
都在 §5.3 步骤 13 被判 `EXEC_ADMISSION_STALE`。两个独立缺陷：

① **快照复核拿错了主体** —— Run 快照存的是**根 Agent** 的闭包指纹，
子路径的 Phase A 基线是**子 Agent** 的闭包指纹，而闭包指纹**含 `agent.id`** →
两者是不同主体、必然不等 → 每次调用都被判失效。

② **闭包解析漂移到「当前已发布版本」** —— 校验器与准入各自按 `resolveCurrent`
解析，而子 Agent 的 release 在委派时**固定** → 别人给它发布新版本时，
在途委派漂移并被拒（「发布」变成了「打断在途执行」）。

**执行链（第十八批）**：

```
子 Agent 的工具调用（CAP 链路）
├─ Phase A
│   ├─ 闭包解析：按 scope 的**固定 release**（不是「当前已发布版本」）
│   ├─ 步骤 3–7 校验：校验器按**同一个固定 release** 解析
│   │   └─ 步骤 7 指纹比对：与 scope.expectedFingerprint（委派时固化的）比对
│   └─ PhaseA 携带 agentVersion（固定版本；根路径为 null）
├─ 步骤 8 幂等键：按「当前执行中的 Agent」分域（第十七批）
├─ 步骤 13 执行准入
│   ├─ 授权版本未递增？（撤权 → EXEC_ADMISSION_STALE）
│   ├─ 执行主体闭包新鲜度：按**同一个固定 release** 重算
│   └─ Run 快照复核：按「**快照自己的 Agent**」的当前闭包比对
│       ├─ 同一执行主体（根路径）→ 复用刚算出的当前指纹（不重复解析）
│       └─ 不同主体（子路径）→ 拿根的当前闭包指纹比快照
└─ 步骤 14 执行
```

⚠️ **不放宽任何既有防线**：根的闭包漂移 → 根路径在 Phase A 步骤 7 被拒
（`CONFIG_FINGERPRINT_STALE`，拦截点更早）、子路径在步骤 13 被拒
（`EXEC_ADMISSION_STALE`）；撤权两条路径都仍在准入被拒。

⚠️ **仍然待补**：子路径在 CAP 链路上的**端到端证据**
（跨 `DelegationExecutor` → scope → CAP 闸门 → 工具）与
**审批范围绑定（MA-T18）/ 输出契约（MA-T16）**的子路径端到端证据。

### 委派分支在两条执行链路上的执行位置（第十九批补充）

⚠️ **此前委派分支只存在于 CAP 链路**（`invokeAllCap` 的循环体内），
既有链路（`invokeAllLegacy`）没有对应分支 → 委派调用落到 `findHandler` → null →
「**未登记的工具**」被拒。而既有链路是**生产默认路径**
（`config.flag.cap-authorization-enforced` 默认 `false`）
→ 多级 Agent 在生产上根本不可用。

**执行链（第十九批）**：

```
一次模型返回的工具调用
├─ isDelegationCall(call)?                       ← 两条链路共用
│   ├─ 否 → 普通工具路径（各链路原有序，不变）
│   └─ 是 → handleDelegationCall（两条链路共用）
│       ├─ ① FAIL_FAST 已停？→ 记拒绝（DELEGATION_NOT_ALLOWED），不再发起
│       ├─ ② scope 与 ctx 不一致？→ fail-closed 拒绝（ORCHESTRATION_INVALID）
│       │     └─ ⚠️ 零子执行
│       └─ ③ invokeDelegation
│             ├─ 取消检查（RUN_CANCELLED）
│             ├─ 参数口径（PARAM_SCHEMA_FAIL）
│             ├─ invocationId 派生（父调用参与）
│             ├─ 根 Run 剩余时间 ≤ 0？（DELEGATION_TIMEOUT）
│             ├─ Run 级预算判定 + 预留（第十六批）
│             └─ 委派执行器 → 守卫 → 子 Agent
└─ 未装配委派执行器 → 落回「未登记的工具」（TOOL_NOT_DECLARED，两条链路同口径）
```

⚠️ **委派**不经过**普通工具**的 Schema / 授权 / 幂等 / 账本闸门**：
它的授权与边界由 `DelegationGuard` 承担（逐跳授权 + 深度/次数/超时/预算），
副作用由 `agent_invocation` 承担。**两条链路同口径** ——
否则「同一个委派在两条链路上额度不同 / 深度不同」就是可利用的差异。

⚠️ **既有链路的 `invokeAllLegacy` 签名随之调整**：
由 `(tenantId, task, calls, agentRef)` 改为 `(tenantId, task, calls, scope, delegationContext)`
—— Agent 维度（幂等键分域，第十七批）仍由 `resolveAgentRef(scope, ctx)` 解析，
**键值口径不变**。

### 委派工具在模型侧的装配位置（第二十批补充）

⚠️ **此前委派工具从未进入任何模型的工具表**：
它只出现在 `DelegationExecutor` 的常量与闸门分支里 ——
闸门是「执行期」的东西，而模型是「发起期」的：
模型<b>看不见</b>委派工具，就<b>不会发起</b>委派。
后果是守卫、预算、账本、输出契约、逐跳重新授权**全都齐备**，
多级 Agent 在生产上却**一次委派都发不出去**。

**装配链（第二十批）**：

```
模型发起前：装配模型可见的工具表
├─ 子 Agent 路径
│   └─ WorkerChildAgentModelConfigProvider.toolSchemas
│       ├─ 闭包工具（按子 Agent 自己的闭包）
│       └─ 委派工具 ← DelegationToolSchemaAssembler（按该 Agent 自己的编排声明）
└─ 根 Agent 路径
    └─ RunExecutionInputs.agentConfig(tenantId, runId)
        ├─ 根 Agent 身份 ← Run 能力快照（snapshot.agentId / agentVersion）
        └─ 委派工具 ← DelegationToolSchemaAssembler（同一份实现）
```

⚠️ **委派工具与闭包工具并列**：它不属于闭包，但同样出现在模型可见的工具表里。

⚠️ **「装配了 Schema」不等于「委派会被放行」**：
闸门的判定顺序不变（取消 → 参数口径 → 根 Run 剩余时间 → Run 级预算 →
守卫的逐跳判定 → 目标资源授权）。Schema 只解决「模型看得见」，
**不解决**「模型看得见就一定合法」。

⚠️ **根 Agent 的其余模型配置原为 L-4 占位**：模型标识（`fake-model`）、提示词、
**普通工具表**均为占位 → ✅ **已由第二十一批消解**（改为按 Run 能力快照的固定 release
读真实定义）；本批（第二十批）只补「委派工具」这一项触发点。


### 根 Agent 模型配置的装配位置（第二十一批补充）

⚠️ **本节为本批补充** —— 07 原文从未规定「根 Agent 的模型配置由谁装配」。

```
Run 能力快照(execution_capability_snapshot)
    │  agent_id + agent_version（= 这个 Run 绑定的固定 release）
    ▼
AgentModelConfigAssembler ── 读 agent_version.definition（按该固定版本）
    │    · modelRef/modelId → 模型标识
    │    · instructions.inlineInstructions / systemPrompt → 提示词
    │    · temperature / maxOutputTokens / timeoutMs → 生成参数
    │    · 该 Agent 自己闭包的 Skill→Tool → 普通工具 Schema
    ▼
RootAgentModelConfigProvider ── 并列装配委派工具（显式，不进闭包）
    │
    ▼
bootstrap: RunExecutionInputs.agentConfig(tenantId, runId)
    │  ⚠️ 返回 Optional：**读不到即空**
    ▼
RunDispatchConsumer ── 空 → 该 Run 拒绝执行（fail-closed，不回落占位模型）
```

⚠️ **为什么身份必须来自 Run 能力快照**：同一租户的不同 Run 可能由不同根 Agent 执行，
按全局装配会让 A 的 Run 拿到 B 的模型与工具。

⚠️ **为什么必须绑定固定 release**：否则别人给该 Agent 发布新版本时，
在途 Run 会静默漂移到新模型 / 新提示词（MA-T08）。

⚠️ **根与子共用同一份装配实现**（`AgentModelConfigAssembler`）：
子路径此前自己解析定义，根路径走占位 —— 两套语义必然漂移。


### 根路径的 fail-closed 处置（第二十一批补充）

⚠️ **本节为本批补充**。

根路径读不到模型配置时，**不回落任何占位值**，而是**拒绝执行该 Run**：

| 情形 | 处置 | 理由 |
|---|---|---|
| Run 能力快照缺失 | 拒绝执行该 Run | 不知道根 Agent 是谁 → 无法确定它跑在哪个模型上 |
| 快照读取异常 | 拒绝执行该 Run | 异常不得被吞成「没有配置」之外的任何结论 |
| 定义缺少模型标识 | 拒绝执行该 Run | 无法确定用哪个模型 → **不猜**（与子路径同口径） |
| 定义不是合法 JSON | 拒绝执行该 Run | 配置不可解析 → 不凭空造一份配置 |
| 闭包解析失败 | **工具表为空**，Agent 仍可用 | 「一条工具边读不出来」不该被放大成「这个 Agent 全瘫」 |
| 委派工具装配器未装配 | **不给委派工具**，其余照常 | 无从判断委派能力 → 宁可不给 |

⚠️ **与子路径的一致性**：子 Agent 取不到模型配置时，
`WorkerChildAgentRunner` 判**确定失败**（`RESOURCE_UNKNOWN`）；
根路径取不到时判**该 Run 失败**。两侧都是「确定失败」而非「UNKNOWN」——
因为配置缺失是可重试也无用的**确定性**结论。


### 委派预留的对账与处置位置（第二十二批补充）

⚠️ **本节为本批补充** —— 07 原文只规定了「委派本身要占额度」，
从未规定「这笔额度出问题时怎么找回来」。

```
闸门（ToolInvocationGate）
    │  委派前：reserve(tenantId, runId, invocationId, 当量)
    │    └─ operation_id = 委派调用标识（= agent_invocation.invocation_id）
    │  委派后：SUCCEEDED → settle / 子执行未启动 → release
    │          UNKNOWN → **既不结算也不释放**（R-007）
    ▼
预算对账（BudgetReconciliationService.reconcileAll）
    │
    ├─ 工具侧：findOrphaned / findUnknownHeld
    │     └─ INNER JOIN tool_operation → **看不见委派的预留**（修复前的漏点）
    │
    └─ 委派侧（本批新增）：DelegationBudgetReconciliationService
          ├─ scan(tenantId)
          │    └─ DelegationBudgetPort.findHeldReservations(tenantId)
          │         └─ budget_reservation LEFT JOIN agent_invocation
          │            + 排除工具侧锚点（两条通道互补，不重叠）
          ├─ settleTerminalHeld(tenantId) → 终态委派自动结算
          └─ disposeHeld(tenantId, invocationId, 收敛结论, 金额)
               └─ UNKNOWN 预留唯一的出口：**只接受对账已收敛的结论**
    ▼
统计：ReconcileStats 纳入委派侧计数
    └─ needsAttention() 覆盖「委派 UNKNOWN」与「委派无锚点」
       ⚠️ 不计入的话，运维看到的永远是「一切正常」，
          而实际上额度正被一批看不见的委派预留长期占着
```

⚠️ **与闸门不冲突**：闸门在委派返回后会自己结算同一笔预留；
两者都受「`RESERVED` → `SETTLED`」的状态前置条件保护，
先到者生效，后到者拿到 `false` —— **不会重复计费**。

⚠️ **未装配时显式告警**：委派对账通道未接入 `BudgetReconciliationService` 时，
对账会打 `WARN` 级告警并继续 —— **绝不静默跳过**：
静默跳过等于让「委派额度泄漏」这件事**永远不被发现**。

⚠️ **本批的剩余缺口（如实登记）**：对账**没有调度器**、
**没有对外处置入口**（API / 运维命令）——
与工具侧同款（只提供能力，触发时机待 D7 审计链路接入）。

### 「模型原始候选」的落库位置（第二十三批补充）

⚠️ **本节为本批补充** —— 07 原文从未规定「路由降级在运行期记到哪里」。

```
路由判定（DelegationExecutor.selectByRoutingPolicy）
    │  模型候选 = command.targetAgentId()   ← 模型给出的原始候选
    │  生效目标 = effectiveTargetId
    │    ├─ 未降级：生效目标 == 模型候选
    │    └─ 降级  ：生效目标 == policy.targets().get(0)（≠ 模型候选）
    ▼
写委派记录（第 6 步，调度子 Agent 之前）
    AgentInvocation(
        targetAgentId           = effectiveTargetId,   ← 谁真的被调用了（权威事实）
        requestedTargetAgentId  = command.targetAgentId(),  ← 模型本来想要谁（审计线索）
        ...)
    ▼
agent_invocation
    · target_agent_id              NOT NULL
    · requested_target_agent_id    NULL（存量行：当时未记录）
    ▼
读侧
    AgentInvocation.routedFallback()
      = requestedTargetAgentId != null && requestedTargetAgentId != targetAgentId
      ⚠️ NULL 时返回 false —— 那只意味着「**无从判断**」，
         不得据此断言「这次没有降级」
```

⚠️ **为什么两列都要在「调度之前」就写好**：
委派记录是在**调度子 Agent 之前**落下的（`DelegationExecutor` 第 6 步插记录、
第 7 步才调度），所以记录里的「生效目标」是**决策的事实**而不是事后追认 ——
「模型原本想选谁」也必须在同一个时点落下，否则 Worker 崩溃后就无从复原。
### 上下文与安全
子 Agent 仅收到通过输入 Schema 的最小必要上下文，不继承父 Agent 的全部 Prompt、工具集或权限。父 Agent 不得将子 Agent 输出提升为系统/开发者指令。日志仅记录摘要和关联 ID；敏感输入/输出按数据分级存储。
