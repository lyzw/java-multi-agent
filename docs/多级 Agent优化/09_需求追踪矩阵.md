⚠️ **FR-045 是「评审冻结」而非「新需求」**：它冻结的是**已经实现并被用例钉住**的
委派状态语义 —— 七态封闭集合 / 终态不可覆盖 / 协作式取消（取消 ≠ 撤销）/
墙钟超时 / 幂等重放不重复执行 / 终态写入三态可区分 / 四类 UNKNOWN /
接管三步（提升世代 + 收敛 UNKNOWN + 绝不重放）/ 预算处置矩阵。
落地物是 ADR-012 与 08 §MA-T24a～MA-T24i，**不改任何实现**。
⚠️ 决策 3 的原文要求「须在 P1 状态机/ADR 冻结」—— 本条即为该冻结的凭据；
但「多子结果聚合（FR-027）」与「平台默认值」**不在本条范围内**
（分别由评审前置决策 1、2 拍板，落地见第三十二批、第三十三批）。
⚠️ 仍缺：**跨进程的接管演练**（真实 Worker 崩溃 → 新 Worker 接管 → 在途记录收敛）
需故障注入手段，本条不声称已具备。

⚠️ **FR-033 的需求描述与验收编号均为「本批补充」**，不是评审冻结的需求项：
06/07/08 原文只规定「子 Agent 固定 release」与「运行期子 Agent 发布新版本 →
当前 Run 继续绑定原 release」，从未规定**「这个固定版本号在授权与准入链路上
如何被携带」**（本批取「由 Phase A 一路下传到校验器与准入」的最小方案）。
状态仍为 `Draft` —— **不得**因本批已有实现与自动化证据就标记为 `Approved`：
⚠️ 其中「**Run 快照对子路径意味着什么**」虽已有可工作的口径，
但「子路径的端到端证据（跨委派执行器 → CAP 闸门 → 工具）」与
「**审批范围绑定 / 输出契约在子路径上的端到端证据**」仍缺，已登记为缺口。

⚠️ **FR-034 的需求描述与验收编号均为「本批补充」**，不是评审冻结的需求项：
06/07/08 原文从未规定**「委派分支在哪几条执行链路上存在」**
（本批取「两条链路共用同一份实现、判定排在『未登记的工具』之前」的最小方案）。
⚠️ 补充的是**既有约束**（MA-T05 / MA-T11 的目标未声明拒绝、参数非法拒绝、
取消后不发起子执行）在**生产默认链路**上的落地 —— 此前那条链路根本没走到委派分支。
⚠️ **剩余缺口**：① 委派分支的**跨链路端到端证据**（跨 `DelegationExecutor`
→ scope → 闸门 → 子 Agent → 回灌）仍缺，当前是**闸门层**的链路一致性证据；
② **委派工具的 Schema 从未装配给模型**（`delegate_to_agent` 只出现在
`DelegationExecutor` 常量与闸门分支里；根 Agent 的 `AgentModelConfig` 在生产仍是
`fake-model` 占位 + 空 toolSchemas）→ 运行期模型**不可能发起委派**，
多级机制齐备但**无触发点** —— 这是比本批更大的缺口；
✅ 触发点已由**第二十批**消解（委派工具 Schema 装配），
根 Agent 的配置占位已由**第二十一批**消解；
③ CAP 链路默认关闭，子路径在 CAP 链路上的端到端证据（审批范围绑定 MA-T18 /
输出契约 MA-T16）待补。

⚠️ **FR-044 的需求描述与验收编号均为「本批补充」**，不是评审冻结的需求项：
08 原文从未规定「管理台必须提供哪几个表单」，本批取的是
「编排声明结构化表单 + 契约登记独立页 + 与后端口径对齐」这一组最小口径。
⚠️ **本批补的是「可达性」而不是「能力」**：
后端治理通道（`AgentRequest.orchestration` + `PublishRequest.resultContracts`）
第十一批就已端到端打通，本批只是把**前端**补齐 ——
此前管理台**够不着**这两样声明，全仓 grep 不到 orchestration / childAgentRefs /
resultContract / routingPolicy 任何字样，于是「治理通道存在，但没人走它」，
多级 Agent 只能靠手写 SQL 配。
⚠️ **本批刻意让前端校验与后端口径对齐**：
后端在配置期 fail-closed（非法声明绝不「降级成 LEAF 照常发布」——
那会让作者以为多级已生效，实际所有委派都被静默丢弃），
前端做同样的校验只是为了让作者**当场**看到错误；
**服务端才是权威**，前端校验不是防线。
⚠️ **本批刻意不预填默认值**：默认值口径属**评审前置决策 2**
（最大深度与预算默认值，**尚未闭环**），前端一旦预填就等于替评审先定了一套口径，
且会成为「第二个默认值来源」（前后端各一份，迟早漂移）。
⚠️ **剩余缺口**：① **路由策略登记**表单未做（后端同样已支持）；
② 契约**目录 / 查看**页尚无；③ 编排声明的**子 Agent 候选列表**未接
（需后端提供按租户的 Agent 列表接口供下拉选择，当前手填 id）。

⚠️ **FR-043 的需求描述与验收编号均为「本批补充」**，不是评审冻结的需求项：
08 原文从未规定「MQ 拓扑由谁声明」，本批取的是
「拓扑全部配置驱动 + 生产自己声明绑定 + 测试用独立拓扑」这一组最小口径。
⚠️ **本批补的是「声明」而不是「行为」**：
消息发布/消费的行为早已有测试覆盖，缺的是**声明本身的完整性** ——
生产代码从未声明绑定（没有绑定就没有路由，消息被 broker 静默丢弃），
而集成测试自己补了绑定，于是「测试替生产兜底」，缺陷只在真部署那一刻暴露。
⚠️ **本批刻意让「不可路由」变得可见**：此前 mandatory 退回的消息
**无声无息消失**，现打成显式 ERROR 日志 —— 拓扑改成配置驱动后，
失配的可能性变高，必须看得见。
⚠️ **本批刻意把隔离判定做成确定性的**：
原先用「生产队列深度不变」判定，而该判定**依赖生产队列是否存在**
（全新环境里它根本不存在）—— 已改为「发送器**实际发布目标** ≠ 生产拓扑」
这条**静态**性质（RabbitMQ 按 `(exchange, routing key)` 路由，
不同目标的消息在结构上到不了生产队列）。
⚠️ **剩余缺口**：① bootstrap 侧启动完整上下文的 E2E 测试
（`PlatformSecurityE2ETest` 等）仍会向**真实 broker** 发消息，本批只隔离了
`agent-infrastructure` 的 IT，那部分未动；② 本机 `mvn verify` 仍红，
余下的是**历史 run 累积**（既有缺陷，与多级 Agent 无关）。
