## 2. 平台级 vs 租户级引用与唯一性

- **唯一性**：`cap_tool_def` / `cap_mcp_server_def` / `cap_skill_def` 的 `id` **全局唯一**，`namespace=platform` 由平台拥有。
- **引用约束**：`cap_skill_def.declared_tools` 的每个 id 必须存在于 `cap_tool_def`；`declared_mcp[].serverId` 必须存在于 `cap_mcp_server_def`（FK 或 T1 校验）。
- **租户级**（V1 仅 platform 定义；V2 开放 `tenant:<id>` 自定义）：若开放，须加 `tenant_id` 列并受 RLS；租户定义**仅可引用** platform 级或被本租户拥有的对象，禁止跨租户引用。
- **删除被引用对象**：见 §3.5（禁止物理删除被引用，改停用/标记）。

## 3. 配置生命周期（状态机）

```
DRAFT ──(validate)──▶ VALIDATED ──(approve, 双人复核)──▶ PUBLISHED
                        │                                  │
                        │(reject)                           │(new version)
                        ▼                                  ▼
                     REJECTED                          PUBLISHED'(新版本)
                        │                                  │
                        └────(revise)──────────────────────┘
PUBLISHED ──(deactivate)──▶ DEPRECATED（不可新引用，存量 Run 按 authzVersion 过渡）
```

| 步骤 | 职责 | 校验 |
|---|---|---|
| create/edit | 配置管理 Port | schema + 引用完整性 + 收紧棘轮（放宽即拒） |
| validate | `PermissionResolver` + T1 守卫 | 闭包可达性、riskCeiling 合法、allowlist 非空语义（05 §4）、循环依赖（V2） |
| approve | `ConfigChangeController`（双人复核 `approver_id <> requester_id`） | 高危变更（trustTier=public / WRITE_EXTERNAL）强制 |
| publish | 配置发布服务 | bump `configVersion`/`config_fingerprint`；对新 Run 生效 |
| rollback | 配置发布服务 | 切回上一 PUBLISHED 版本（不可"部分回滚"能力闭包） |
| deactivate/delete | 配置管理 Port | 被引用对象禁止物理删除 → DEPRECATED；新 Run 不可引用 |

### 3.1 生效范围
- **新 Run**：创建时（T2）读取**当前** `configVersion`/`config_fingerprint` 与 `authzVersion` 生成快照。
- **已有 Run**：按 `execution_capability_snapshot` 记录的版本/指纹；若运行期检测到 `authzVersion` 或 `config_fingerprint` 失效 → 新调用 DENY（05 §5），在途按对账处理。

### 3.2 删除/停用被引用对象
- 物理删除被 Skill 引用的 Tool / 被 Agent 启用的 Skill → **拒绝**（除非先解除所有引用并 DEPRECATE）。
- 替代：对象置 DEPRECATED，禁止新引用，存量 Run 按版本过渡。

### 3.3 Schema 版本与迁移
- `cap_*` 表带 `schema_version` 列；旧版本读取时按迁移脚本向后兼容。
- **从自由 JSONB 迁移**：`agent.definition` 现有自由 JSONB → 新增 `cap_agent_def` 结构化表；迁移脚本抽取 `enabled_skills`/`roles` 等字段，旧 `definition` 保留为 `legacy_definition` 只读归档，直至双写校验通过后废弃。

## 4. 版本与失效模型（闭环 05 §5）

| 概念 | 存储 | 失效触发 |
|---|---|---|
| `agentVersion` | `cap_agent_def.version` | Agent 定义重发 |
| `configVersion` / `configFingerprint` | `cap_*_def.config_fingerprint` 聚合 | 任一 cap_* 内容变更（含 MCP 固定清单变化） |
| `authzVersion` | `cap_authz_version`（DB 单调） | 主体授权变更（撤权/角色变） |

**失效规则**（运行期 T3）：
- `ctx.authzVersion ≠ current` → DENY(stale_authz)。
- `snapshot.config_fingerprint ≠ current_cap_fingerprint` → DENY(config_stale)（V1 的"MCP 工具发生变化"判定即由此触发）。
- 两者满足且闭包内各边通过 → 进入执行闸门（预算/幂等/账本/执行）。

## 5. MCP 安全接入补充（评审 03 P1-2）

| 项 | 规则 |
|---|---|
| **SSRF 防护** | `endpoint` 须落允许范围（内网白名单/域名清单）；禁止 `127.0.0.0/8`、`169.254.0.0/16`、私有 CIDR，除非 `trustTier=internal` 显式授权。 |
| **凭据** | `credential_ref` 引用密钥管理；明文**禁止**入库；日志脱敏；支持轮换（轮换后连接级重验）。 |
| **超时/限流** | 连接超时、读超时、响应大小上限、并发上限、失败隔离（单 server 故障不拖垮全局）。 |
| **名称映射** | `McpServer.id + mcpToolName → 内部 Tool.id` 稳定映射；同名不同 server 区分，禁止冲突。 |
| **不可信输出** | MCP 返回内容视为不可信，禁止直接当可信指令。 |
| **Schema 兼容** | server Schema 变更导致不兼容 → 视为 `config_fingerprint` 变化 → DENY（需重发配置）。 |

## 变更补充：多级 Agent 数据模型与发布闭包（v1.1）

### AgentDefinition 增补
增加可选 `orchestration`：
- `mode`: `LEAF | ROUTER | SEQUENTIAL`
- `childAgentRefs[]`: 每项必须含固定 `agentId`、`releaseRef`/`version`；禁止 `latest`
- `routingPolicyRef`: ROUTER 模式引用固定版本路由策略
- `maxDelegationDepth`、`maxChildInvocations`、`timeoutMs`、`failurePolicy`
- `resultContractRef`：用于约束委派结果的结构化契约（如父子输出不直接同构，需映射策略）

缺省 `orchestration` 等价于 `LEAF`。字段仍受 `additionalProperties: false` 约束；应显式更新 JSON Schema，不得关闭额外字段校验来规避迁移。

### 编排模式语义（第三十二批补充 · 评审前置决策 1）

⚠️ **本节是「评审已决策」的口径，不是本批自定的设计**（决策人：zhouwei，2026-10-25）：
`SEQUENTIAL` **不纳入 P2** —— 多子结果聚合**不由框架代劳**。

| 模式 | 语义 |
|---|---|
| `LEAF` | 不发起任何委派（缺省语义） |
| `ROUTER` | 按固定版本的路由策略选择子 Agent（第十四批已落地） |
| `SEQUENTIAL` | 父 Agent 可在其声明的子 Agent 集合内**逐次委派**；**串行与聚合由父 Agent 自己完成，框架不代劳** |

⚠️ **一次委派 = 一个目标 = 一条 `agent_invocation` 记录 = 一次子执行**：
框架**不会**因为声明了多个子 Agent 就替父把子 Agent 全跑一遍再合成 ——
父 Agent 本身是**多轮执行体**，它可以在不同轮次依次委派给不同子 Agent
并把各轮结果合成一份输出，那是**父的模型行为**，不是框架的功能。
（`DelegationExecutorTest#multipleDeclaredChildrenStillRunOnePerDelegation` 钉住这一条）

⚠️ **`resultContractRef` 是「链接契约」**：由**调用方**声明、约束**被调方**的输出形状
（父子输出不同构时用它做映射）。**每一跳的契约都由调用方声明** ——
不是「被调方声明自己的输出契约」，也不是「父声明自己该收到什么再自己校验自己」。
⚠️ 由此推出：父 Agent 聚合后的输出，是它**被调用时**的返回值，
由**调用方声明的链接契约**校验（MA-T16），而不是由父自己声明的契约自校验。

⚠️ **「按输出契约聚合结果」不是框架的动作**：此前 `OrchestrationMode.SEQUENTIAL`
的 javadoc 承诺过它而实现没有 —— 名字许诺了做不到的事，
配置方就会按那个许诺来设计（以为「声明了多个子，框架会替我串起来」）。
这与第十四批之前 ROUTER「名不副实」同构，已于第三十二批更正。
⚠️ **P0-D02（SRS）的 FR-027 原文不改** —— 那是评审原始需求规格，
改写只记在变更包与 00（第三十二批）。


### 委派限制的声明口径：不再有平台默认值（第三十三批补充 · 评审前置决策 2）

⚠️ **本节是「评审已决策」的口径，不是本批自定的设计**（决策人：zhouwei，2026-10-25）：
**取消平台默认值** —— 非 LEAF 的 Agent 发布时**必须显式声明**
`maxDelegationDepth` / `maxChildInvocations` / `timeoutMs`，**缺失即拒绝发布**。

| 模式 | 三个限制 | 缺失时的行为 |
|---|---|---|
| `LEAF` | **不适用**（解析为 `null`） | 正常 —— LEAF 不参与委派，限制对它无意义 |
| `ROUTER` / `SEQUENTIAL` | **必填**（三者都要，缺一不可） | **拒绝发布**（`ORCHESTRATION_INVALID`） |

⚠️ **`null` 是「不适用」，不是 0、也不是默认值**：
- 用 `0` 表达「LEAF 没有限制」会制造第二种解读 ——「0 次子调用」看起来像个真实上限；
- 用某个默认值表达同样会制造「这一跳**有**上限」的错觉。

⚠️ **规范化 JSON 只写已声明的字段**（`AgentOrchestrationParser.toJson`）：
LEAF 的规范化 JSON 里**不出现**这三个字段 —— 写进去会让「LEAF 没有限制」
与「LEAF 限制为 0」在指纹口径上长得一样。

⚠️ **判据放在领域模型，不只放在解析器**：`AgentOrchestration` 的构造器
强制「非 LEAF 必须显式声明」，因此**任何**构造路径（解析 / 指纹固化 / 测试替身）
都必须过这一关；否则「从别处 new 出来的编排」就能绕过「必须显式声明」。
⚠️ **运行期同样 fail-closed**：`DelegationGuard` 读到 `null` 即判
`ORCHESTRATION_INVALID` —— 守卫是**安全边界**，读不到上限时**绝不**当成「不限制」。

⚠️ **存量配置的迁移影响**：升级前**没有显式声明**这三个字段的
ROUTER / SEQUENTIAL 配置，**升级后将无法发布**（fail-closed）。
这是决策的直接后果，不是缺陷 —— 但运维必须知道。

⚠️ **深度不级联**（决策 2b）：每一跳按**当前 Agent 自己**声明的
`maxDelegationDepth` 判定，不取父子较小值、不逐层收敛。
这与「拓扑取自当前 Agent」自洽
（`NestedDelegationGateTest#nestedDelegationRespectsCurrentAgentDepthLimit`）。

### 关系数据
新增建议关系表 `cap_agent_child_ref`：`tenant_id`、`parent_agent_id`、`parent_release_id`、`child_agent_id`、`child_release_id`、`ordinal`、`required`、`created_at`。唯一约束防止同一父 release 重复声明同一子 release；复合外键/发布校验保证租户一致和引用完整。该表为发布关系投影，权威定义仍是不可变 Agent release 中的 `childAgentRefs`。


### 关系投影的存储口径：投影必落库（第三十四批补充 · 评审前置决策 4）

⚠️ **本节是「评审已决策」的口径，不是本批自定的设计**（决策人：zhouwei，2026-10-25）：
`cap_agent_child_ref` **存储** —— 父子关系投影**必落库**，
不再是「装配了就写、不装配就静默跳过」。

⚠️ **为什么「静默跳过」是缺陷而不是「可选增强」**：
投影表回答的是「**谁依赖我**」——
影响分析、删除守卫、委派拓扑图都靠它。
表是空的就等于「**没人依赖我**」，
于是「被引用对象被抽走」的事故一路畅通，
而运维看到的是「**发布成功**」。
静默跳过把「关系真相缺失」伪装成了「发布成功」，这是最坏的失效形态。

| 场景 | 决策 4 之前 | 决策 4 之后 |
|---|---|---|
| 投影端口**已装配** | 边落库 | 边落库（**不变**） |
| 投影端口**未装配** + 本次发布**带了子引用** | **静默跳过**（发布成功、关系一条没落） | **拒绝发布**（`ORCHESTRATION_INVALID` + 「父子关系投影未装配」） |
| 投影端口**未装配** + 本次发布**没有子引用** | 发布成功 | 发布成功（**不变** —— 不做过度拦截） |

⚠️ **判据是「本次发布有没有边」，不是「仓储装没装配」**：
纯 LEAF Agent 的发布与关系投影**无关**，
让投影能力成为整个平台级发布的**隐形前置依赖**是错的。
⚠️ **实测证据**：把判据改成「仓储没装配就全拒」，
在 `agent-application` 全模块会红 **9 条** —— 说明判据选错的波及面远不止漏判的那一条。

⚠️ **投影仍然是投影，不是第二份真相**：
- 权威来源始终是**不可变 Agent release** 里的 `childAgentRefs`；
- 投影表**可重建**（重放发布即重建），**release 永不改写**；
- 投影写入**幂等**（`ON CONFLICT DO NOTHING`）—— 重放发布是常态，
  同一父 release 重复投影同一子 release **不产生第二行**；
  真正的「重复声明」在**发布期**就被编排解析层拒绝。

⚠️ **查询口径（三条，均按 Agent 维度而非版本维度）**：
| 口径 | 方法 | 语义 |
|---|---|---|
| 出向 | `listByParentAgent` | 该父 Agent 的**全部**边（**不限父 release**）—— 拓扑图要呈现全部边，否则图会随版本选择而「缺边」 |
| 入向（**反查**） | `listByChildAgent` | 声明了该子 Agent 的**全部**父（**不限子版本**）—— 被停用的是那个 Agent，不是某一版 |
| 全量 | `listByTenant` | 本租户的全部边（拓扑视图一次取全量，避免 N+1 与并发下的不一致快照） |

新增 `agent_invocation` 运行记录：`invocation_id`、`tenant_id`、`run_id`、`parent_invocation_id`（根调用为空）、`parent_agent_release_id`、`target_agent_release_id`、`status`、`depth`、`trace_id`、`input_digest`、`output_digest`、`started_at`、`finished_at`、`reason_code`、`fencing_token`。不得默认保存不必要的敏感输入/输出明文；必要内容引用受控存储并按原读取授权规则处理。

### 路由策略（第十四批补充）

> ⚠️ **本节的内容模型是「本批取舍」，不是评审冻结的模型**。
> 06 原文只规定了「ROUTER 模式按固定版本路由策略选择子 Agent」，
> 从未规定策略的**内容模型**。本批刻意选择最小可扩展的一档：
> **一个策略枚举 + 一个有序目标列表**，不引入条件表达式 DSL。
> 理由：可配置判定逻辑一旦进入配置，就同时欠下「求值确定性」「发布期校验」
> 「求值失败语义」三件事 —— 那属于评审未决范围，与其自造半成品 DSL，
> 不如先交付语义无歧义的最小模型，把扩展点留在枚举上。

新增租户级配置对象表 `cap_routing_policy`（V24）：

| 列 | 含义 |
|---|---|
| `tenant_id` | 租户标识（RLS 隔离，与 `cap_agent_def` 同口径） |
| `policy_id` | 策略标识（**可读字符串**，与 `cap_result_contract.contract_id` 同构） |
| `version` | 策略版本号（固定引用，禁止 `latest`） |
| `strategy` | 选择策略：`EXPLICIT_TARGETS` / `ORDERED_FALLBACK` |
| `targets` | 允许的目标 Agent 标识（**有序** JSONB 字符串数组） |
| `config_fingerprint` | 内容指纹（**服务端计算**，顺序参与哈希） |
| `schema_version` / `created_at` / `published_at` | 行格式版本与时间戳；`published_at IS NULL` = 草稿（不可被引用） |

**两层收窄关系（发布期强制）**：
`childAgentRefs` 声明**委派拓扑**（允许交给谁），
路由策略声明**允许的子集与选择方式**（在拓扑内还能交给谁、怎么选）。
策略的 `targets` **必须**是父声明 `childAgentRefs` 的**子集** ——
否则「拓扑」与「策略」就有两个真相，「谁说了算」说不清。
运行期判定顺序同理：**先拓扑（`DELEGATION_TARGET_NOT_DECLARED`）、后路由收窄（`ROUTING_TARGET_NOT_ALLOWED`）**，
两个原因的排查方向完全不同，不得混用。

**两种选择策略**：
- `EXPLICIT_TARGETS`：模型给出的候选必须命中 `targets`，否则**拒绝委派**（不降级）——
  候选不命中意味着「路由没能选出合法的目标」，那是一次真实的路由失败，
  静默换一个目标会让父 Agent 收到一份「不是我点的那个」的结果却毫不知情；
- `ORDERED_FALLBACK`：候选未命中时按 `targets` 的**声明顺序**取第一个目标。
  ⚠️ 降级**只作用于「选择」，不作用于「准入」**：降级选中的目标仍须通过
  「父声明包含 → 版本固定 → 逐跳授权 → 深度/次数/超时/预算」的全部判定，
  不会继续尝试下一个候选（否则「一次委派」变成「一串委派」，次数与预算上限被绕过）。

**治理路径**：路由策略随 `ConfigPublishCommand.routingPolicies` 在**同一发布事务**内登记
（与 Agent 同批次、同发布头、同指针 CAS、同审计）；版本号由服务端按「现有最大版本 + 1」分配，
内容指纹由服务端计算。发布期校验三道关：① 只有 ROUTER 模式可声明策略引用；
② 引用必须指向**已发布**的固定版本；③ 策略目标必须是父声明拓扑的子集。

⚠️ **`policy_id` 必须是 TEXT 而非 UUID**：对外 schema 契约
（`common.schema.json#/$defs/id`）把 `fixedVersionRef.id` 定义为**可读字符串**，
治理通道也按字符串接收。V23 已因「输出契约 id 声明成 UUID」付出过整笔发布事务回滚的代价，
新概念不再重复这个错误。

### 运行期量 vs 配置量（第十五批补充）

> ⚠️ **本节记录的是「哪些东西不进配置」的边界**，不是新增配置对象。

多级递归需要两类**运行期量**，它们**刻意不落在 `orchestration` 里** ——
`orchestration` 是**不可变配置**（进闭包指纹、进发布闭包），而运行期量随调用树逐跳变化：

| 运行期量 | 载体 | 为什么不能进配置 |
|---|---|---|
| **当前执行中的 Agent 身份 + 深度 + 父调用标识** | `core/orchestration/DelegationContext`（**逐跳下传**，不进指纹） | 它描述的是「这一次调用处在树的哪一层」，同一个 Agent 在不同调用里深度不同。若进配置，会被固化成「Agent 声明的深度」——那正是本批修掉的「深度恒为 1」的形态 |
| **根 Run 的业务截止时刻** | `run.deadline_at`（**已落库**，V21）+ `ChildAgentRequest.rootDeadlineAt` / `DelegationCommand.rootDeadlineAt`（逐跳下传） | 它是**根 Run 的**属性，不是任何 Agent 的属性。同一个 Agent 可以被不同 Run 调用，剩余时间不同 —— 把它写进 Agent 声明，等于让「这个 Agent 永远只有 30s」变成事实 |

⚠️ **两者的语义必须分清**：
- `ExecutionScope`（按哪个 release 授权）与 `DelegationContext`（当前在树的哪一层）
  是**两件事**，不可互相替代；二者同时存在时 Agent 标识与版本必须一致，
  不一致 → fail-closed 拒绝委派（`ORCHESTRATION_INVALID`）。
- `rootDeadlineAt = null` 的语义是「根 Run **未声明**截止时间 → 不限时」，
  与根路径下 `run.deadline_at IS NULL` **逐字对齐**，**不是**「跳过超时约束」。

### 工具幂等键的 Agent 维度（第十七批补充）

> ⚠️ **本节记录的是「键的形状」，不是新增配置对象**。幂等键不落配置、
> 不进闭包指纹 —— 它是**运行期量**（每次调用现算）。

`tool_operation.idempotency_key` 的唯一约束是 `UNIQUE (tenant_id, idempotency_key)`
（**租户级**），而账本命中重复键时**复用既有 operation、不再次执行工具** ——
于是「键的维度够不够」直接等于「会不会吞掉一次调用」。

| 工具 | 键形状 | 说明 |
|---|---|---|
| `record_weakness` | `student_id/run_id/knowledge_point` | **不含** Agent 维度、**不含** callId：它记的是「某学生的某知识点」这条**业务事实**，全局唯一 —— 父子记同一条，后写的那次被幂等拦下是**正确**的。⚠️ 代价：子 Agent 想**订正**同一知识点也会被吞（既有 ADR-003 口径，非多级引入）→ 已登记为缺口 |
| 其他工具 | `run_id/[agent_ref/]tool_name/call_id` | `agent_ref` 是**可省略**段（第十七批）：`null` = 单 Agent 路径 → 键值与历史**逐字符一致**（在途 `tool_operation` 行不受影响）；非 null → `agent_ref = agentId@version` |

⚠️ **为什么 `agent_ref` 带版本**：同一个 `agent_id` 的不同 release 是**不同的执行主体**
（闭包、工具集都可能不同）。只写 `agent_id` 会让「同一 Agent 的新 release」
继承旧 release 的幂等记录。

⚠️ **为什么是「可省略」而不是「统一带」**：单 Agent 路径若也改键形状，
按旧键写入的在途 `tool_operation` 行就再也匹配不上 → 重放会被当成新调用 →
**重复副作用**（比吞调用更糟的失效方向）。

⚠️ **Agent 标识必须可唯一分解**：`agent_id` 含分隔符 `/` 时
`(a/b, c)` 与 `(a, b/c)` 会算出同一个键 —— 那正是本次要修的缺陷换个方向复发。
故 `ExecutionScope` / `DelegationContext` 在**构造期**就拒绝这类标识。

### 固定 release 的贯穿口径（第十八批补充）

> ⚠️ **本节记录的是「同一个版本号必须在链路上保持一致」的边界**，不是新增配置对象。

子 Agent 的 release 在**委派时固定**（`childAgentRefs` 的固定版本引用；
`latest` 一律拒绝发布）。这个版本号此后会出现在**三处**，
三处必须**解析同一个闭包**，否则比的是三个不同的东西：

| 环节 | 解析口径 | 为什么 |
|---|---|---|
| 委派时 | `resolve(tenantId, targetId, targetVersion)` → 写入 `ExecutionScope`（含闭包指纹） | 把「这次委派授权到什么」**固化**下来 |
| 授权（Phase A 步骤 3–7） | `resolve(tenantId, agentId, **固定版本**)` | 授权依据必须与委派时固化的那一份一致 —— 否则「委派给 v1、执行时按 v2 授权」 |
| 执行准入（§5.3 步骤 13） | `resolve(tenantId, agentId, **固定版本**)` | 新鲜度校验必须重算**同一个**闭包，否则「指纹变了没有」这个判断本身就没有意义 |

⚠️ **固定版本必须一路带到底**：`PhaseA` 承载它，
经 `InvocationRequest.agentVersion` / `AdmissionRequest.agentVersion` 下传
（`null` = 单 Agent 路径 = 「当前已发布版本」）。

⚠️ **为什么不能用「当前已发布版本」**：那会让「别人给子 Agent 发布新版本」
变成「打断在途执行」—— 在途委派漂移到新 release，表现为「工具未声明 / Skill 未启用」
而被拒。**发布是治理动作，不该顺手改写在途执行的授权依据**（MA-T08 的原意）。

⚠️ **Run 快照复核按「快照自己的 Agent」**：快照存的是**根 Agent** 的闭包指纹
（Run 的依赖集固化证据），而子路径的执行主体是**子 Agent** ——
两者是不同主体，**不可互相比**。子路径下应拿**根**的当前闭包指纹比快照；
子 Agent 自己的新鲜性由上表第二、三行保证。

### 委派调用在两条执行链路上的身份口径（第十九批补充）

> ⚠️ **本节记录的是「同一个委派调用在两条链路上必须同身份」的边界**，
> 不是新增配置对象。

⚠️ **此前委派分支只存在于 CAP 链路**（`invokeAllCap`），既有链路
（`invokeAllLegacy`）里委派调用落到 `findHandler` → null →
被当成「**未登记的工具**」拒掉（`TOOL_NOT_DECLARED`）。

⚠️ **这不是「两条链路行为略有差异」，而是「多级 Agent 在生产上不可用」**：
`config.flag.cap-authorization-enforced` 默认 `false` → 生产走既有链路。
于是同一个委派调用在两条链路上给出**不同结论**（CAP 链路成功、既有链路被拒）。

**身份口径（第十九批）**：

| 环节 | 口径 | 为什么 |
|---|---|---|
| 委派判定 | `isDelegationCall(call)`：委派执行器**已装配** 且 工具名匹配 | 未装配时落回「未登记的工具」被拒 —— **不静默放行**（否则没有委派执行器的部署会「看起来支持委派」） |
| 判定顺序 | 必须在「未登记的工具」判定**之前** | 委派不是普通工具（不注册 `ToolHandler`），先查 handler 就必然被判成「未登记」 |
| 执行作用域 | `ExecutionScope`（按哪个 release 授权） | 与 `DelegationContext`（当前 Agent 是谁）**不可互相替代** |
| 一致性校验 | 两者同时存在时，agentId **与** agentVersion 必须一致 | 不一致 = 上下文串了 → **fail-closed 拒绝**（`ORCHESTRATION_INVALID`），不猜哪个是对的 |

⚠️ **两条链路共用同一份实现**（`handleDelegationCall`）：「共用」不是洁癖 ——
两份实现必然漂移（本地复制一份就会丢掉一致性校验），
而漂移出来的差异恰好落在**越权路径**上。

### 委派工具的 Schema 形态与装配口径（第二十批补充）

> ⚠️ **本节记录的是「委派工具在模型侧长什么样、由谁装配」的边界**，
> 不是新增配置对象。

⚠️ **委派不是普通工具**：它<b>不进</b> Skill→Tool 能力闭包
（进了闭包就等于给每个 Agent 都发一把委派枪），
因此闭包解析<b>永远给不出</b>它 —— 必须<b>显式装配</b>。

**形态（`DelegationToolSchema`）**：

| 环节 | 口径 | 为什么 |
|---|---|---|
| 工具名 | `delegate_to_agent`（**唯一定义**在 `DelegationToolSchema.TOOL_NAME`；闸门常量引用它） | 两处各写一遍必然漂移；漂移的后果是「模型看得见的委派工具」与「闸门认得的委派调用」对不上，模型发起的委派被当成「未登记的工具」拒绝 |
| 参数 | 只允许 `targetAgentId` + `input` | 必须与 `DelegationArguments.parse` **逐字对齐** —— 否则模型按 Schema 合法发出的参数被闸门拒（两套语义，模型永远学不会正确调用） |
| 多传字段 | `additionalProperties:false` | 模型必须自己看见「多传不被允许」，而不是发出后才被拒 |
| 目标范围 | `targetAgentId` 用 **enum 枚举该 Agent 自己声明的子 Agent** | 可用性（模型不必猜标识）+ 边界（不给模型试探越界目标的机会）。⚠️ **这只是提示，不是授权** |
| 版本 | **不暴露** | 目标版本由服务端按父声明解析；模型若能指定版本，就能要求漂移到别的 release（与「固定 release」直接冲突） |

⚠️ **Schema ≠ 授权**：真正的授权判定在闸门（`DelegationGuard`：
目标未声明 → `DELEGATION_TARGET_NOT_DECLARED`；深度/次数/超时/预算逐跳判定）。
Schema 只是<b>提示</b>，两者都成立才算合法 —— **委派关系 ≠ 授权关系**。

**装配口径（`DelegationToolSchemaAssembler`）**：

| 情形 | 是否装配 | 为什么 |
|---|---|---|
| 该 Agent 声明了子 Agent | ✅ 装配 | 有委派能力 |
| LEAF / 无子引用 | ❌ 不装配 | 无委派能力就别发枪 —— 否则模型反复尝试必然被拒的调用（白烧模型调用） |
| 读不到编排声明 / 声明非法 / 仓储异常 | ❌ 不装配 | **fail-closed**：不知道有没有委派能力时<b>宁可不给</b>，也不凭猜测发枪 |

⚠️ **根路径与子路径共用这一份装配器**：两处各写一份必然漂移，
而漂移的后果是「根能委派、子不能」（或反之）—— 那正是「两套语义」本身。

⚠️ **根路径按 Run 装配**：根 Agent 的身份来自 **Run 能力快照**
（`snapshot.agentId()` / `agentVersion()`）——
同一租户的不同 Run 可能由不同根 Agent 执行，
按全局装配会让 A 的 Run 拿到 B 的委派目标。


### 根 Agent 的模型配置口径（第二十一批补充）

⚠️ **本节为本批补充，非评审冻结模型** —— 06/07/08 原文从未规定
「根 Agent 的模型标识 / 提示词 / 普通工具表从哪来」。

| 项 | 口径 |
|---|---|
| 根 Agent 身份 | **Run 能力快照**（`execution_capability_snapshot.agent_id` / `agent_version`）—— 不是「当前已发布版本」 |
| 配置来源 | 该 Agent **固定 release** 的 `agent_version.definition`（JSONB）：`modelRef`/`modelId`、`instructions.inlineInstructions`/`systemPrompt`、`temperature`、`maxOutputTokens`、`timeoutMs` |
| 普通工具表 | 该 Agent **自己闭包**里的 Skill→Tool 绑定（**不放宽工具授权面**） |
| 委派工具 | 显式装配（不进闭包），与闭包工具**并列** |
| 取不到模型标识 | **拒绝执行**（不猜模型）—— 与子路径**同口径** |
| 读不到快照 / 定义 | **拒绝执行该 Run**（fail-closed）—— **不回落 `fake-model` 占位** |

⚠️ **为什么「根」与「子」必须共用同一份装配实现**：
两处各写一份必然漂移，而漂移落在「根按占位配置跑、子按真实配置跑」这类
**两套语义**上 —— 那正是本项目反复消除的问题本身。


### 根 Agent 模型配置与占位的替换（第二十一批补充）

⚠️ **本节为本批补充**。L-4 占位（`fake-model` + 写死提示词 + 空工具表）已由
→「按 Run 快照读真实定义」替换。

⚠️ **口径切换的三点边界**：
1. **只换配置侧**：Run 的**输入载荷**（`run.input_payload`）仍是占位 ——
   本批未接通输入侧，不得据此认为根 Agent 已能跑真实业务请求。
2. **fail-closed 优先**：读不到根 Agent 的模型配置 → **该 Run 不执行**。
   代价是「配置未接好时平台不可用」，收益是「配置缺失不会被伪装成配置正常」。
3. **委派目标依赖 CAP 侧投影**：根 Agent 的委派目标枚举读 `cap_agent_def.orchestration`，
   而<b>双写开关默认关闭</b> → 未走 CAP 发布通道的 Agent 仍被识别为 LEAF。
   这是<b>发布通道</b>的缺口，与本批的<b>读取口径</b>无关，两者不可混为一谈。

### 委派预算预留的对账口径（第二十二批补充）

⚠️ **本节为本批补充，非评审冻结模型** —— 06/07/08 原文从未规定
「委派的预算预留怎么被找到、怎么被处置」。

**反查口径**：`budget_reservation` **LEFT JOIN** `agent_invocation`
（`operation_id = invocation_id`），且**工具侧无锚点**（`NOT EXISTS tool_operation`）。

| 项 | 口径 |
|---|---|
| 为什么是 LEFT JOIN | 委派终态提交若报 `NOT_FOUND`（记录不存在），闸门判 `UNKNOWN` 并**持有**预留 —— 此时**连 `agent_invocation` 行都没有**。用 INNER JOIN 会把这一类**漏掉**，而它恰恰是最需要人工看一眼的那一类（额度被占、查无实据） |
| 为什么排除工具侧 | 工具侧的预留由 `findOrphaned` / `findUnknownHeld` 负责；两边靠「工具侧无锚点」**互补**划分 —— 否则同一笔预留会被两条通道**处置两遍** |
| 持有 ≠ 悬挂 | 持有可能是「子执行还在跑」「结果不确定」「闸门崩溃」—— 三者处置动作**完全不同**，判定在应用层做 |
| UNKNOWN 处置 | **不自动结算、不自动释放**（R-007 红线），只统计并转人工 |
| 人工处置的输入 | 只接受**对账已收敛**的结论（`RECONCILED_SUCCEEDED` → 结算 / `RECONCILED_ABSENT` → 释放） |

**处置矩阵**：

| 委派调用状态 | 含义 | 处置 |
|---|---|---|
| `QUEUED` / `RUNNING` | 子执行可能还在跑 | ⚠️ **不动** —— 动了就是凭空吞额度 |
| `UNKNOWN` | 结果不确定（R-007） | ⚠️ **不动**，只统计并转人工；须有明确的收敛结论才可处置 |
| `SUCCEEDED` / `FAILED` / `CANCELLED` / `TIMED_OUT` | 子执行已启动并结束 | **结算** —— 子执行跑过 → 成本可能已发生 |
| 无锚点（连 `agent_invocation` 行都没有） | 委派终态提交报 `NOT_FOUND` | ⚠️ **不动**，只统计；查无实据 → 不自动改账 |

⚠️ **为什么终态一律「结算」而不是照抄工具侧的「成功结算、其余释放」**：
闸门对委派的既有口径是「**子执行从未启动 → 释放；子执行已启动但失败 → 结算**」
（子 Agent 已经跑过，模型调用的钱已经花出去）。
而「委派调用有终态」这件事<b>本身就等价于「子执行已启动」</b> ——
`agent_invocation` 行是在**调度子 Agent 之前**落下的，
所以凡是**有记录行**的委派，子执行都已被调度过。
⚠️ 照抄工具侧的「其余释放」会把这笔钱**白送**出去。

⚠️ **`UNKNOWN` 也是终态枚举值，但它不是「已定论」**：
`UNKNOWN` 的语义是「不再变化、等对账给结论」——
判定「结果是否已定」必须用「**确定**终态」判据，不能用「是否终态」，
否则 `UNKNOWN` 会被误当成「已结束」而自动结算（R-007 被拆）。

### 委派记录的「模型原始候选」口径（第二十三批补充）

⚠️ **本节为本批补充，非评审冻结模型** —— 06/07/08 原文从未规定
「路由降级这件事要怎么被记录下来」。

`agent_invocation` 现在**并存**两列关于「目标」的字段：

| 列 | 语义 | 回答的问题 | 可空 |
|---|---|---|---|
| `target_agent_id` | **实际生效**的目标（谁真的被调用了） | 「这次到底是谁干的」 | 否 |
| `requested_target_agent_id` | **模型给出的原始候选**（路由降级<b>前</b>） | 「模型本来想选谁 / 是不是被降级了」 | 是（存量行为 NULL） |

⚠️ **为什么两列都要，不能只留一列**：
只留「生效目标」→ 降级这件事在数据上**消失**，事后无从复核；
只留「候选」→ 审计看到的是一份「**并非事实**」的委派（谁真的跑了就说不清了）。
两列**互不替代**。

⚠️ **回填口径：不回填**（本节最需要被审的一点）：

| 项 | 口径 |
|---|---|
| 为什么不能回填 | 存量行的「模型原始候选」在任何**持久化**位置都不存在 —— 当时只有应用日志留痕，而日志可能已轮转、已归档、已按租户擦除 |
| 为什么不能「据日志回填」 | 据此回填 = 用**猜测**冒充事实：猜错的行会把「没降级」记成「降级过」，比空值更有害 |
| 存量行的取值 | 一律 `NULL` |
| `NULL` 的语义 | 「**当时未记录**」—— ⚠️ **不是**「没有降级」 |
| 读侧义务 | 判定「是否降级」时必须区分「候选 ≠ 生效目标」（降级过）与「候选为 NULL」（无从判断） |

⚠️ **降级索引的谓词必须显式排除 NULL**：
`requested_target_agent_id IS DISTINCT FROM target_agent_id` 在 NULL 左侧会判为「不同」——
若不补 `IS NOT NULL`，**从未发生降级**的历史行会被算进降级集合，
恰恰制造出本列要消除的那种噪音。

⚠️ **候选的版本不记录**：候选目标在降级场景下**从未被解析出固定 release**
（生效目标的版本来自父声明对**生效目标**的引用），
把一个不存在的版本记下来反而是误导 → 本列只记 Agent 标识。

### 被引用行内容指纹的承载口径（第二十四批补充）

⚠️ **本节为本批补充，非评审冻结模型** —— 06/07/08 原文从未规定
「被引用对象（输出契约行 / 路由策略行）自己的内容要不要进闭包指纹」。

| 项 | 口径 |
|---|---|
| 编排绑定承载什么 | ① **固定版本引用**（`id@version`）——「依赖的是哪一版」；② **该行的内容指纹**——「那一版的内容是什么」 |
| 为什么两者都要 | 只承载引用 → 「同一版本行被就地改写」这一支**没有防线**（版本号没变、引用没变、编排声明没变）；只承载内容 → 丢掉了「依赖哪一版」这个事实 |
| 承载位置 | `OrchestrationBinding.routingPolicyFingerprint` / `resultContractFingerprint`（可空，紧邻对应引用之后） |
| 指纹来源 | 被引用行**自己的**服务端内容指纹（`cap_result_contract.config_fingerprint` / `cap_routing_policy.config_fingerprint`）—— 不重新计算，避免两处算法漂移 |
| 解析不出时 | **fail-closed**（拒绝构建闭包）——「引用了却解析不出」≠「没引用」 |
| 解析能力未装配时 | **fail-closed** —— 绝不「没有解析器就当没有指纹」 |

⚠️ **「没有声明引用」的闭包，指纹必须完全不变**：
它压根不依赖任何被引用行，其旧指纹**本就是完整证明**；
让它也变一变，只是无谓地让在途 Run 集体失效 ——
那不是 fail-closed，只是返工。
⚠️ **「声明了引用」的闭包，指纹必须变化**：
它此前的「内容没变」证明是**不完整**的（没覆盖被引用行的内容），
故在途 Run 必须失效（MA-T15 / MA-T18 的核心命题）。

⚠️ **内容指纹只覆盖「该行自身的内容」**，不覆盖别的依赖 ——
被引用行若再引用别的对象，那一层的覆盖要由那一层自己的绑定负责。
### 发布闭包算法
`EffectiveConfigResolver` 从根 Agent release 递归展开固定子 Agent 引用，再展开其 Skills、Tools、MCP/策略/Schema。必须：
1. 检查目标 release 已发布、租户/命名空间一致、引用固定；
2. 用 DFS 访问栈拒绝自环和间接环；限制最大静态深度；
3. 规范化排序所有节点/边与版本，计算 `configFingerprint`；
4. 任何子 Agent release 或影响行为的策略变化均形成新闭包，不改变历史 release；
5. 通过 CAS 更新发布指针；并发修改冲突返回 `RELEASE_CONFLICT`；
6. 父 Agent 发布失败时不得留下半发布的子图或部分更新的指针。

数据库迁移需支持旧 Agent 无编排字段的兼容读；回填不应把历史 release 内容原地改写。对既有 release 的默认 `LEAF` 解释应在解析层完成，并通过迁移/兼容测试证明。

### 管理台前端对平台级对象的读写面（第三十四批补充 · C34-3）

⚠️ **本节为本批补充**（C34-3）：06 §平台级对象的登记与生命周期描述的是
**后端**通道；本节补**前端**这一半 —— 管理台怎么用这条通道，
以及前端**必须**替作者挡住的几个坑。

| 项 | 口径 |
|---|---|
| 登记与修改 | **共用同一张草稿表单**（`new` 是保留路由段）。分两条路由就会有两份表单，迟早漂移 —— 而「登记」与「改版」的差别只在「标识是否已存在」 |
| 三步工作流 | 前端**不**合并三步：申请 → 审批 → 执行各有各的端点与各自的按钮。把三个动作塞进一次请求，双人复核就退化成自证 |
| 「删除」语义 | **物理删除不做**（已发布行不可变，DB 触发器）。正确语义是**停用**（`PUBLISHED → DEPRECATED`，单向终态），走 `lifecycle-requests`，CAS 前置条件携带**真实**的 `expectedFrom` |
| 停用原状态 | **不得硬编码 `PUBLISHED`** —— 对象可能早已停用（迁移是单向终态）。后端目录接口**已提供** `lifecycleState`，前端须如实读取；对 `DEPRECATED` 对象直接禁用停用入口，并说明「它早就停了」，而不是让操作者走到审批才收到一个读起来像「有人跟我抢」的「原状态不符」 |
| 闸门语义可分辨 | 400（参数非法，作者能改）/ 403（不是 `PLATFORM_ADMIN`，作者改不了，得换人）/ 409（自审批或状态冲突，流程问题）/ 503（**平台运维通道未接入 = 环境问题，不是用户的错**）—— 四者**必须分开呈现**，合并成一句「操作失败」会让操作者去改自己的填法，而真因在权限或环境 |

⚠️ **前端先拒，只是体验优化，服务端门禁才是权威**：
前端在提交前做形状与一致性检查，让作者**当场**看到错误，
而不是填完理由、走到审批才被拒。

⚠️ **闭包补齐的 fail-closed：凭据引用不得被静默丢弃**：
平台级发布必须构成**自洽闭包** —— Skill 声明的每个 Tool / MCP Server、
以及 MCP 型 Tool 绑定的 Server，都必须出现在**同一次请求**的发布集合里
（否则后端以 `TOOL_NOT_DECLARED` / `MCP_NOT_BOUND` 拒）。
前端替作者补齐闭包，而补齐时有个**必须拦住的坑**：
**目录接口从不回显凭据定位符**（只给 `hasCredentialRef` 布尔，凭据材料与定位符
永不入响应，§4.2 / P5-T3）⇒ 补齐时重发出来的 Server spec **必然没有凭据引用**
⇒ 后端为它建**新版本行**时凭据引用为 null ⇒ 指针移过去后，
该 Server 在**全平台**的生效配置里**认证失效**。
一个「改 Skill 的声明清单」的操作，静默改掉了全平台的 MCP 认证 ——
与「显式授权材料被静默清空」同级。故前端 **fail-closed 拦截并点名具体 Server**，
要求改到该 Server 自己的详情页单独改版（那里能填凭据引用）。

⚠️ **传递闭包这一跳不能省**：
「Skill 声明的 Tool / 声明的 MCP」只是**第一跳**；
若被声明的 Tool 本身是 **MCP 型**，它绑定的 Server 也必须一并发布。
省掉这一跳 ⇒ 「声明了一个 MCP 型 Tool 但没声明其 Server」必被后端
`MCP_NOT_BOUND` 拒，而**被拒的那个对象根本不在用户眼前**。

⚠️ **`null` 与 `[]` 的三态在前端也必须分得开**：
`declared_mcp[].tool_allowlist` 与 `exposed_tool_allowlist` 的三态
（未配置 `null` / 显式空 `[]` / 清单）**不可归一化** ——
把「显式空」显示成「未配置」等于**权限放宽**（未配置 = 取全集）。
故三态在 UI 上真的分得开，且**页面接线**也被用例钉住
（纯函数两端被测、中间接缝未测是本批发现并补上的最大覆盖缺口）。

### 平台级对象的登记与生命周期：PLATFORM 作用域发布通道（第三十四批补充）

⚠️ **本节为本批补充**（用户拍板于 2026-10-25 · zhouwei）：
平台级对象（Tool / Skill / MCP Server）的写入口走
**平台作用域发布端点**（`PLATFORM_ADMIN` 闸门 + 平台运维通道）。

⚠️ **为什么平台级对象此前没有写入口**：
它们**无 `tenant_id`**（V15 明写「这三张表是 platform 级，不启用 RLS」），
而平台的**发布头**（`cap_config_release`）与**当前指针**（`cap_config_pointer`）
的写策略**只放行本租户的 TENANT 行**（V15 / V17）——
平台行**只能**由平台运维角色（BYPASSRLS）写入。
于是此前只有两条路：手写 SQL，或带外运维工具。

| 项 | 口径 |
|---|---|
| 身份闸门 | `PLATFORM_ADMIN` 角色（**403 默认拒绝**）。平台身份表 `principal` 是**租户内**的，没有跨租户主体 —— 没有这道闸门，任一租户管理员自授角色即可改全平台配置 |
| 通道闸门 | 写入走**平台运维角色连接**（BYPASSRLS）。**未接入时明确失败（503）**，**绝不回落应用角色** —— 回落后 RLS 会拒写，报错点落在 RLS 策略上，离「这个环境没配运维凭据」这一真因极远 |
| 双人复核 | 平台级变更**同样走「申请 → 审批 → 执行」三步**。把申请人与审批人两个 id 放进一次请求由调用方填写，双人复核就退化成「调用方自己声明另一个人同意了」（V18 迁移注释原话） |
| 作用域闸门 | PLATFORM 作用域的发布**只带平台级对象**；TENANT 作用域**只带租户级对象**。混装被配置期门禁拒绝（`ConfigValidationGate`），且发布头的作用域会与内容自相矛盾 |
| 版本号与指纹 | **服务端决定**：版本号 = 该对象现有最大版本 + 1；内容指纹 = `CapObjectFingerprint` 按内容计算。客户端提交这两者 = 让客户端指定「内容没变」这个证明 |
| 申请单的作用域 | `cap_config_publish_request` **第三十四批起支持 PLATFORM 作用域**（V27 迁移：`tenant_id` 可空 + `scope` 列 + 一致性 CHECK）。⚠️ **RLS 读写策略一个字都不改** —— 策略是严格相等（`tenant_id = current_tenant_id()`），平台行（`tenant_id IS NULL`）对**应用角色连接天然不可见**：租户既读不到、也写不进平台的申请单 |
| 「删除」语义 | **物理删除不做** —— 已发布行不可变（DB 层触发器）。正确语义是**停用**（`PUBLISHED → DEPRECATED`，单向终态）。管理台的「删除」按钮因此映射到停用通道 |
| 停用的边界 | 停用**只挡「新引用」**；存量引用按固定版本继续过渡（同 06 §3.2 对契约 / 策略的口径） |

⚠️ **关系维护的口径（每个对象只维护自己声明的关系）**：
| 对象 | 声明的关系 | 存储落点 |
|---|---|---|
| Skill | 声明哪些 Tool（`declared_tools`）、声明哪些 MCP Server（`declared_mcp`） | `cap_skill_def` |
| Tool | 绑定在哪个 MCP Server 的哪个远端工具（`mcp_server_id` + `mcp_tool_name`） | `cap_tool_def` |
| MCP Server | 允许哪些远端工具（`exposed_tool_allowlist`） | `cap_mcp_server_def` |

⚠️ **`declared_mcp[].tool_allowlist` 的 `null` 与 `[]` 语义不同**（§4.4）：
`null` = 未配置（取 ServerAllowedOps 全集），`[]` = 显式不允许任何操作。
**不可归一化** —— 把 `null` 归一成 `[]` 会让「没配」变成「什么都不许」，
那是**可用性事故**而不是保守收紧。

⚠️ **「MCP Server 允许集」与「实际登记在该 Server 上的 Tool」是两回事**：
前者是连接级允许集，后者是 Tool 定义绑定。两者可以不一致（允许集更宽、登记更窄），
刻意**分开呈现**，避免运维把「没登记」误读成「不允许」。

⚠️ **「声明了但对象不存在」必须如实呈现**：
`declared_tools` 里可以出现尚未登记的 id（草稿态 Skill 的正常情形）。
关系查询端点把它们**显式列为 `missing`**，而不是悄悄从清单里消失 ——
悄悄消失会让运维以为「没有这个依赖」。

⚠️ **本节为本批补充，非评审冻结模型** —— 06 §3 的状态机原文只覆盖
「Tool / Skill / MCP Server / Agent」四类对象，
从未规定「输出契约行 / 路由策略行」是否也有生命周期。

| 项 | 口径 |
|---|---|
| 为何这两张表此前没有生命周期 | `cap_result_contract`（V20）与 `cap_routing_policy`（V24）建表时只继承了 V15 时代的 `published_at`（布尔式），**没有** V17 引入的 `cap_lifecycle_state` 列 → 只能表达「已发布 / 未发布」两态 |
| 为何不能靠 `published_at` 表达停用 | `published_at` 是**不可变触发器的判定依据**（非空 = 已发布 = 内容冻结）。要「停用」就得把它清空 —— 那等于把已发布行**降级回草稿**：内容重新可改、「已发布」这个事实凭空消失。故停用必须是**独立于 `published_at` 的第三个维度** |
| 数据层落点 | V26 迁移：`lifecycle_state cap_lifecycle_state NOT NULL DEFAULT 'DRAFT'`；回填「`published_at` 非空 → `PUBLISHED`」；接入 `align_cap_lifecycle_state()`（绑定两者）与 `forbid_published_def_mutation()`（**内容冻结**，并放行 `PUBLISHED → DEPRECATED` 的**纯元数据**迁移） |
| 治理通道 | 生命周期迁移端点（申请 → 审批 → 执行，三步）的类型闸门放开到 `{agent, result_contract, routing_policy}` —— 全是**租户级**对象；平台级对象（tool / skill / mcp_server）在**租户通道**里**仍然拒绝**（其发布走平台运维通道，不经租户身份暴露）。⚠️ **第三十四批更正**：平台级对象**另有**一条独立通道（`PLATFORM_ADMIN` 闸门 + 运维通道，见本文件「平台级对象的登记与生命周期」小节）——「仍然拒绝」只对**租户通道**成立，不再是「平台级对象无生命周期通道」 |
| 停用的效力 | **只挡「新引用」**：新发布不得引用已停用的契约 / 策略（`RESULT_CONTRACT_DEPRECATED` / `ROUTING_POLICY_DEPRECATED`）；**存量引用按固定版本继续过渡**（06 §3.2） |
| 为何「未发布」与「已停用」必须分列原因码 | 两者都表现为「引用不可用」，但排查方向**相反**：前者查发布流程（还没生效），后者查停用记录（曾经生效、现被显式停用）。混用会让运维去查「为什么没发布」，而真因是「上周有人把它停了」 |
| 顺带补上的一处更硬的缺口 | V20 / V24 建表时**漏挂了不可变触发器** —— §6.1「已发布版本行不可变」对这两张表**从未生效**（运维直接 UPDATE 可改写已发布契约）。V26 补上 |

⚠️ **回填期间必须临时 `NO FORCE ROW LEVEL SECURITY`**：
这两张表都是 FORCE RLS 的租户表，迁移角色若是 owner 也**同样受策略约束**；
未解除 FORCE 时 UPDATE 影响 0 行 → 回填**静默不生效**，
表现为「迁移跑成功了，但状态全是 DRAFT」—— 最难查的一类假成功。
异常路径必须把 FORCE 状态复原（否则留下「租户表不再受 RLS 保护」的残局）。

⚠️ **读不到生命周期状态时不得降级成「没有停用」**：
仓储读不出 `lifecycle_state` 时**不吞异常**，让数据层失败显式炸出来 ——
否则发布期引用校验读不到「已停用」这个事实，停用防线会**看起来在、其实不在**。

### 三张表的结构不变量与构建期门禁（第二十七批补充）

⚠️ **本节为本批补充，非评审冻结模型** —— 06 原文从未规定
「三张表的 DDL 形态由谁守护」。

⚠️ **为什么这道门禁是必需的（这是本批要补的真实缺口）**：
这三张表的结构**只由迁移脚本定义**，而迁移脚本**只在部署新环境时执行**。
于是「脚本被改坏 → **已部署环境察觉不到**（库里已经是旧结构）→
现有行为断言照样全绿（它们跑在早就建好的库上）→
直到某天**新建环境**，改坏的脚本才被执行」——
那一刻线上环境已经建起来了。

⚠️ **只加行为断言是不够的**：
行为断言（写入后能否读回、非法值是否被拒）验证的是**当前库**，不是**脚本**。
脚本退化后只有**新环境**才会中招 —— 而新环境恰恰是最不该出事的那个。

#### 门禁断言的结构不变量

| 表 | 关键不变量 |
|---|---|
| `agent_invocation` | 状态集合**恰好七态**（封闭，多一个少一个都不行）；`fencing_token > 0`（MA-T12 的地基）；根调用（`depth=1`）必须无父、非根调用必须**有**父（否则悬空根可写入，调用树无法重建）；主键恰为 `(tenant_id, invocation_id)`（MA-T10 幂等的地基）；降级索引的谓词必须排除存量行（NULL ≠「发生过降级」） |
| `cap_agent_child_ref` | 父子两侧都必须有指向 `cap_agent_def` 的**复合外键**，且复合外键第一列是 `tenant_id`（顺带保证租户一致）、`ON DELETE CASCADE`（否则删父版本后留下悬空边）；`ordinal >= 0`、两侧版本号 `> 0` |
| `cap_result_contract` | `contract_id` 必须是**可读字符串**（TEXT 而非 UUID —— 对外契约把 id 定义为可读字符串，曾声明成 UUID 导致非 UUID id 的发布事务整笔回滚、运行期恒 fail-closed，V23 已修）；内容指纹非空；`lifecycle_state` 必须存在（第二十五批 V26 补的停用维度落点） |
| 三张表共同 | 主键必须**以 `tenant_id` 打头**；必须 **RLS enabled 且 FORCE**（未 FORCE 时表 owner 仍能跨租户读，而迁移角色正是 owner）；策略必须**读写双向**收口（只写 `USING` 不写 `WITH CHECK` 等于只挡读） |

#### ⚠️ 断言的是「跨多版本迁移后的**有效结构**」，不是任何单个脚本的原文

这是必需的：`cap_result_contract.contract_id` 在 V20 建表时是 `UUID`，
V23 才改成 `TEXT`。若只看 V20 的原文，会把「已被修复的缺陷」当成「要防的东西」，
而真正要防的是「**它被改回 UUID**」。

⚠️ 由此还带出一条**工程约束**：迁移脚本必须按**版本数值**排序生效 ——
字典序会把 `V10` 排到 `V9` 之前，于是「谁最后改了这张表」会判错
（契约 id 的类型就断在这里）。

#### 两层门禁（缺一不可）

| 层 | 手段 | 抓什么 |
|---|---|---|
| **构建期（脚本层）** | `MultiAgentSchemaStructureTest` —— 解析迁移脚本 | 「脚本被改坏但已部署环境察觉不到」 |
| **库层** | `MultiAgentSchemaIT` —— 真实 PG 查 `pg_catalog` | 「脚本写了但迁移没跑到那一步」 |

⚠️ 后者不是前者多余的重复：V26 的回填在 FORCE RLS 下会**静默影响 0 行**，
表现为「迁移报成功，状态全是 DRAFT」—— 最难查的一类假成功。
只有真的查一遍库里的实际结构才抓得住。

⚠️ **库层还验证迁移脚本可重复执行**（在事务内重放后回滚）：
PostgreSQL 的 DDL 是事务性的，所以重放既验证了「能执行」，
又不会把共享的 IT 库留在被改动的状态。

⚠️ **剩余缺口**：① `cap_routing_policy` 与 `cap_agent_def.orchestration` 列
**尚未纳入**该门禁；② 结构断言是**文本解析**，
改写方式超出解析器能力时可能漏判 —— 故库层那一层不可省。
