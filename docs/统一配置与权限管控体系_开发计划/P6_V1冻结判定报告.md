## 2. P6-T1 · 全量 §9 套件与机器校验（本阶段的核心交付）

### 2.1 为什么不能只写一张 Markdown 表

P6 §6 风险登记把「追踪矩阵虚标」列为已知风险，缓解决策是「§10 强制证据路径；CI 报告可关联，**禁止手工勾选代替**」。
而「手工勾选」的反面正是**把矩阵写成散文** —— 一张写着「S3f ✅」的表格无法回答：
「那条用例现在还在吗？」「它真的断言了那个原因码吗？」

故本阶段把矩阵做成**四重机器校验**（`Section9ScenarioCoverageTest`，8 项）：

| # | 校验 | 挡住的是什么 |
|---|---|---|
| 1 | §9.1 行为场景集合与设计文档**完全一致** | 文档改了、矩阵没改（两份真相） |
| 2 | §9.2 不变量/故障场景集合与设计文档**完全一致** | 同上 |
| 3 | 每个场景的**四字段期望**与文档表格**逐字一致** | 改了文档的期望而没同步实现 |
| 4 | 每个场景的**证据方法在源码中确实存在** | 用例被改名/删除，矩阵指向空气 |
| 5 | 每个行为场景的证据方法**确实断言了那个原因码** | 方法还在但断言被删（最隐蔽的虚标） |
| 6 | 注册表自检（无重复键、每条有如实备注、行为/不变量字段互斥） | 备注空白 → 读者默认它是完整覆盖 |

冻结门槛侧另有 `FreezeGateEvidenceTest`（3 项）：三类门槛 + 硬约束的**每一项证据**回源码核对存在性，
并断言「防绕过 0」的三层证据（静态扫描 / 架构边界 / 运行时注入）**齐备** ——
少一层就不成立（07 §3：「静态扫描无法单独证明闭环」）。

### 2.2 设计文档是唯一真相来源

`Section9ScenarioSpec` 直接解析
`docs/Agent - Skill- Tool -MCP 统一配置与权限管控体系.md` 的 §9.1 / §9.2 表格：

- **期望四字段不写死在代码里** —— 否则注册表与文档之间会有两份真相；
- 复合取值按文档语义配对（§9.1 的 S3f「SUCCEEDED/FAILED/UNKNOWN」与「SUCCESS / 稳定失败码 / EXEC_UNKNOWN」
  **按位置一一对应**，而 S5c 的「NOT_STARTED × 两个码」是笛卡尔积）；
- 文档里的散文占位（「稳定失败码」）由**显式映射表**指向平台码，不靠推断 ——
  推断出来的映射会让「文档与实现一致」变成一句无法证伪的话。

### 2.3 机器校验当场抓出的真实缺口

`everyBehaviorEvidenceAssertsItsReasonCode` 首次运行即失败：

```
S3f → TOOL_EXECUTION_FAILED（证据：[CapExecutionFlowTest#inFlightCallIsNotCancelled]）
S3f → EXEC_UNKNOWN（证据：[CapExecutionFlowTest#inFlightCallIsNotCancelled]）
```

即：**§9.1 的 S3f 三个终态里，有两个从未被真正验过** —— 代码路径存在
（`CapExecutionFlow.java:595` / `IdempotencyGuard.java:187,200`），
但全仓测试树里 `Status.FAILED` 与 `TOOL_EXECUTION_FAILED` **零命中**。
本阶段已补齐（见 §3）。

> 这正是「机器校验」的价值：**它把「我认为覆盖了」变成了「我证明覆盖了」**。
