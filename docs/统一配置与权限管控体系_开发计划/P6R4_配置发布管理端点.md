## 0. 一句话结论

限制 7 与限制 8 的**真实缺口不是「校验没写」，而是「没有可达的写入口」**。
本轮交付了**租户级的三步发布管理端点**（申请 → 审批 → 执行），
并给出一个此前没有被说清的结论：

> **平台没有跨租户身份 —— `principal` 表是租户内的（`tenant_id UUID NOT NULL REFERENCES tenant`）。**
> 因此**平台级（PLATFORM 作用域）发布不能经租户身份暴露**，否则任一租户管理员自授角色即可改全平台配置。
> 本轮把 PLATFORM 作用域**显式拒绝**（403），平台级发布继续走 P6R1 的运维通道（带外运维工具 + BYPASSRLS 凭据）。

配套结论：

> **`dynamicDiscovery` / `stdio` 的三层防护本来就已完备**（DB CHECK + 发布门禁 + 采集兜底），
> 缺的只是一个能让运维**触发**「写一条非法配置看它被拒」的入口 —— 本轮补的正是这个入口。

## 2. 三条关键勘察结论（本轮最有价值的产出）

### 2.1 结论一：`principal` 是租户内的 → **平台没有跨租户身份**

`principal` 表结构（勘察所得）：

```
principal.tenant_id UUID NOT NULL REFERENCES tenant
principal.login_name ... (全局唯一)
```

即**任何登录主体都属于且仅属于一个租户**。角色经 `PrincipalRepository` → JWT claims 发放，
**不存在**可以代表「整个平台」的主体。

**推论**：若把 PLATFORM 作用域的发布暴露在租户身份的 HTTP 端点上，
则**任一租户管理员只要给自己加上 `config:publish` 角色，就能改全平台配置** ——
这是直接的权限提升，不是「便利性」问题。

**处置**：PLATFORM 作用域在租户通道**显式拒绝**（403），平台级发布继续走 P6R1 的运维通道。

### 2.2 结论二：作用域决定对象集合 → **TENANT 作用域发布的对象是 Agent 定义**

| 表 | 有无 `tenant_id` | 归属 |
|---|---|---|
| `cap_tool_def` | ❌ 无 | 平台级 |
| `cap_skill_def` | ❌ 无 | 平台级 |
| `cap_mcp_server_def` | ❌ 无 | 平台级 |
| `cap_agent_def` | ✅ 有（PK = `(tenant_id, agent_id, version)`，FK → `agent`） | 租户级 |

**推论**：租户管理员能发布的对象集合**只有 Agent 定义**。
这与既有 `ConfigPublishCommand` 的约束完全一致（PLATFORM 只能带 tool+skill+mcpServer，TENANT 只能带 agent）。

### 2.3 结论三：`dynamicDiscovery` 三层防护**本来就已完备**，缺的是入口

| 层 | 落点 | 作用 |
|---|---|---|
| 1. 数据层 | DB CHECK `cap_mcp_server_def_no_dynamic_ck` | 非法值**写不进库** |
| 2. 发布门禁 | `ConfigValidationGate.validateMcpServers` → `McpServerConfigValidator` | 配置期拒 |
| 3. 采集兜底 | `TransportMcpManifestPort.collect` | 运行期拒 |

P6R1 的平台运维通道**同样**过 `ConfigPublishService` 的门禁 —— 即平台级发布也享受第 2 层防护。

**推论**：限制 8 的实质缺口**只是「没有 HTTP 入口」**，
而不是「校验没实现」。本轮补的端点因此**天然继承**了第 2 层防护，
无需另写一份 `dynamicDiscovery` 校验逻辑（**避免两处规则分叉**）。

## 4. 三步流程与双人复核

### 4.1 为什么需要一张「申请单」表

§6.3 的发布是「版本行 + 发布头 + 指针 CAS」三件事的**原子事务**，天然不可拆成两次调用；
而双人复核又要求**申请人与审批人是两个不同的主体**。

> 若把两个 id 直接放在一次请求里由调用方填写，
> 双人复核就退化成「调用方自己声明另一个人同意了」—— **那不是复核，是自证。**

故新建 `cap_config_publish_request` 表承载「待审批的变更方案」，
让申请与审批成为**两次独立的、带身份的调用**。

### 4.2 状态机

```
                  ┌──────────────► REJECTED (终态)
                  │
  PENDING ──审批──┤
    │             └──────────────► APPROVED ──执行──► APPLIED (终态)
    │                                     │
    │                                     └──执行失败──► FAILED (终态，不可重试)
    │
    └──(未审批直接执行)──► 拒绝，零副作用
```

⚠️ **本表的 `state` 与配置对象的生命周期状态刻意分开**：

| | 取值 | 落点 |
|---|---|---|
| **审批流程状态** | `PENDING` / `APPROVED` / `REJECTED` / `APPLIED` / `FAILED` | `cap_config_publish_request.state`（V18） |
| **对象生命周期** | `DRAFT` / `VALIDATED` / `PUBLISHED` / `DEPRECATED` | `cap_*_def.lifecycle_state`（V17） |

混用会让「审批通过了但还没生效」的对象被误当成「已发布」。

⚠️ **`FAILED` 是终态、不可自动重试**：重试等于让审批人批过的东西在无人参与下变形。
由人判断「改参数重来」还是「重新申请」。

### 4.3 三步

| 步 | 端点 | 写入 | 关键行为 |
|---|---|---|---|
| ① 申请 | `POST /api/cap/config/publishes` | **仅申请单** | 跑门禁**预检**（`validateForReview`）；作用域闸门；对象类型闸门；版本号 = 现有最大版本 + 1；**内容指纹由服务端算** |
| ② 审批 | `POST /api/cap/config/publishes/{id}/decision` | **仅申请单状态** | 双人复核：`approver_id <> requester_id`；只允许 `APPROVE` / `REJECT` |
| ③ 执行 | `POST /api/cap/config/publishes/{id}/apply` | **配置表** | 跑权威门禁 + CAS 基线比对；成功后指针切换；失败落 `FAILED` |

### 4.4 三条关键设计决策

1. **版本号与内容指纹由服务端决定** ——
   客户端若能指定 `configFingerprint`，「内容没变」这个证明就是客户端自己说的。
   `CapObjectFingerprint` 是 §6.1「内容指纹」概念的直接实现：
   覆盖 agent / tool / skill / mcp_server 四类，**不含时间戳、不含自身、不含 `credentialRef`**。
   聚合指纹同理：命令不携带 `aggregateFingerprint` 时，由
   `ConfigObjectVersionCodec.aggregateFingerprint`（`cfg_agg_v1:` + SHA-256）在发布事务内计算。

2. **申请阶段跑门禁预检**（`validateForReview`），执行阶段仍跑权威门禁 ——
   两次之间配置可能已变，**预检不能替代权威门禁**。

3. **申请单 payload 存 JSON 原文** ——
   审批人批的是**这份**方案，执行时执行的必须是**这份**方案。

### 4.5 双人复核的三道防线

| 层 | 落点 | 作用 |
|---|---|---|
| 应用层 | `ConfigPublishWorkflowService.decide` | `approver_id == requester_id` → `SelfApprovalException` → 409 |
| 存储层 | `JdbcConfigPublishRequestRepository.decide` | 状态迁移守卫（`FOR UPDATE`，只允许 `PENDING → APPROVED/REJECTED`） |
| DB 层 | CHECK `cap_config_publish_request_two_person_ck` | `approver_id IS NULL OR approver_id <> requester_id` |

## 5. 作用域边界与平台级发布处置

### 5.1 闸门只有一处实现

作用域闸门**下沉到应用层**（`ConfigPublishWorkflowService.request*`），
API 层也保留一道 —— **双保险**，避免「API 层拒了、应用层放行」的分裂。

| 请求作用域 | 处置 | 落点 |
|---|---|---|
| `TENANT` | ✅ 允许（对象类型必须是 `agent`） | 应用层放行 → 门禁 → CAS 发布 |
| `PLATFORM` | ⛔ **403**，且**不留申请单** | 应用层抛 `ConfigPublishScopeNotAllowedException` |

> ⚠️ **拒绝必须发生在落单之前** —— 否则「先落一条申请单再说」会留下垃圾数据，
> 且会让「平台级发布未经租户身份暴露」这条边界变得可被绕过。

### 5.2 平台级发布的处置

| 通道 | 用途 | 身份 |
|---|---|---|
| **租户管理端点**（本轮） | 租户级 Agent 定义发布 | 租户管理员（`TENANT_ADMIN`） |
| **P6R1 运维通道** | 平台级 Tool / Skill / MCP Server 发布 | 平台运维身份（BYPASSRLS 凭据，带外运维工具） |

**平台级发布在本轮不做 HTTP 入口** —— 因为那需要平台级身份，而平台级身份**目前不存在**（§2.1）。
造一个「平台级 HTTP 身份」是**设计决策范围**，不在本轮消解的两项限制内。

## 6. 端点清单

Base path：`/api/cap/config`

| 方法 | 路径 | 鉴权动作 | 限流 | 说明 |
|---|---|---|---|---|
| `POST` | `/publishes` | `CONFIG_PUBLISH` | `GOVERNANCE_QUERY` | 提交变更申请（**不写配置表**） |
| `POST` | `/publishes/{requestId}/decision` | `CONFIG_PUBLISH` | `GOVERNANCE_QUERY` | 审批：批准 / 拒绝 |
| `POST` | `/publishes/{requestId}/apply` | `CONFIG_PUBLISH` | `GOVERNANCE_QUERY` | 执行已批准的变更 |
| `GET` | `/publishes` | `CONFIG_PUBLISH` | `GOVERNANCE_QUERY` | 分页列出本租户申请单 |
| `GET` | `/pointer` | `CONFIG_PUBLISH` | `GOVERNANCE_QUERY` | 读取当前生效指针 |

请求体（`PublishRequest`）：

```jsonc
{
  "operation": "PUBLISH" | "ROLLBACK" | "LIFECYCLE_TRANSITION",
  "scope": "TENANT" | "PLATFORM",     // PLATFORM → 403
  "reason": "变更理由（必填，空串拒绝）",
  "agents": [ /* AgentSpec[]：仅 PUBLISH 用 */ ],
  "expectedPublishSeq": 123,          // CAS 基线；给了就必须与当前一致
  "targetReleaseId": 45,              // 仅 ROLLBACK 用
  "lifecycle": { /* LifecycleSpec */ } // 仅 LIFECYCLE_TRANSITION 用
}
```

**状态码语义**：

| 码 | 含义 |
|---|---|
| `400` | 参数非法（理由为空、decision 非法、门禁预检未过） |
| `403` | 作用域不允许（PLATFORM）/ 越权 |
| `404` | 申请单不存在 |
| `409` | 自审批 / 状态冲突 / CAS 基线过期 |
| `429` | 限流 |

> ⚠️ 端点默认受 `anyRequest().authenticated()` 保护（见 `SecurityConfiguration`）：
> **漏配 `PUBLIC_ENDPOINTS` 时是拒绝而非放行**。
