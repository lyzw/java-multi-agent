## 2. §5.3 顺序落地

### 2.1 实际顺序

```
[Phase A — 授权]  1 构建可信上下文 → 2 PrincipalAuthorized → 3 闭包解析
                  → 4 声明关系/风险上限 → 5 MCP 绑定 → 6 参数策略 → 7 指纹
[Phase B — 准入]  8 幂等键校验 → 9 SchemaValid
                 → 10 账本登记（PRE）
                 → 11 Approval → 12 BudgetOk
                 → 13 ExecutionAdmissionCheck（TOCTOU）
                 → 13a 持久化执行意图 → 13b 审批 INTENT_SUBMITTED
                 → 14 ToolHandler.execute → 14a 结果落盘 → 15 账本 POST
```

### 2.2 与 §5.3 字面顺序的一处偏离（**账本登记前移**）—— 有外键强制依据

§5.3 把「账本 PRE」列在**步骤 12**（审批、预算之后）。但既有表结构不允许：

| 约束 | 定义 | 后果 |
|---|---|---|
| `approval_operation_fk` | `FOREIGN KEY (tenant_id, operation_id) REFERENCES tool_operation (tenant_id, operation_id)` | 审批记录必须引用一个**已存在**的逻辑操作 |
| `part_uniq_reservation_operation` | `UNIQUE (tenant_id, operation_id) WHERE operation_id IS NOT NULL`（`budget_reservation`） | 预算预留按 `operation_id` 唯一；悬挂预留扫描靠它与 `tool_operation` JOIN |

审批消费（`ApprovalPort.consume(tenantId, operationId, …)`）与预算预留（`budget.reserve(…, operationId, …)`）**都必须拿到 `operationId`**，而 `operationId` 由账本登记产生 → **账本登记必然先于审批与预算**。

**处理方式**：把「账本登记」定为步骤 10，**保持「审批 → 预算」的相对顺序不变**（§5.3 的补偿链依赖它），其余全部语义不变：

- ✅ 「Schema 失败不预占审批 / 不预留预算 / **不写 PRE**」—— 步骤 9 仍在步骤 10 之前，**完全保持**；
- ✅ 「准入失败 → 释放预算 + PRE 标失败」—— 完全保持（§5.3 步骤 13 的补偿清单中「cancel 审批」在 P2 不可实现，见 §3.5）；
- ✅ 「禁止绕过账本发请求」—— 账本登记失败即 fail-closed 拒绝。

### 2.3 为什么 `invocationId` = 账本 `operationId`

§5.3 步骤 8「已完成 → 返回首次结果（含首次 reasonCode）」要求能按**幂等键**找到首次结果。首次结果存在**结果事件表**，其唯一键是 `(tenant_id, invocation_id)`。若 `invocationId` 每次调用都新生成，则按幂等键重试时**取不到首次结果**，只能重新执行 —— 与「禁止重复副作用」直接冲突。

故本阶段令 `invocationId ≡ 账本 operationId`：幂等键 → `operationId` → 首次结果事件，三者一条链打通。

## 3. 关键设计决策（需 P3/P4/P5 复核）

### 3.1 CAP 链路置于开关之后，且**默认关闭**

P1 交接结论：P5 的发布指针读落地前，`PublishedVersionPort` 的对象级解析与 §6.3 存在已知偏差（回滚场景下两者指向不同对象）。因此：

- `CapEnforcementSwitch`（`config.flag.cap-authorization-enforced`）**默认 `false`**；
- 开关位于**编排器内部** → 不存在「以为走了新链路、其实没走」的静默降级；
- 既有链路（`invokeAllLegacy`）**逐字保留**，行为零变化；开关关闭时既有闸门（Schema / 执行时重授权 / 账本 / 审批 / 预算）一个不少。

**P5 前不得在生产开启**（前置条件见 §7）。

### 3.2 主体授权在闸门与校验器各做一次（有意冗余）

`CapExecutionFlow.phaseA` 自己做一次主体授权（读权威 `authzVersion` + 角色判定），`InvocationValidator` 内部**又**做一次。二者读的是同一个 `AuthzVersionPort`（DB 强一致），结论必然一致；冗余的理由是：

- 闸门必须**在解析闭包之前**就拒绝无权主体（§5.3 步骤 2/3 的顺序），
  而 `InvocationValidator` 是整体单元，闭包解析在它内部 —— 不在闸门侧先挡一道，
  无权主体仍会触发一次闭包解析（泄露能力面 + 无用功）；
- 闸门侧这次检查产出的**版本值**是准入比对（步骤 13）的基线，必须由闸门自己持有。

### 3.3 多个 Skill 声明同一工具 → **全部通过**才算通过

闭包允许同一工具被多个 Skill 声明。校验器要求 `skillId` 显式传入，故闸门对**每个候选 Skill** 各跑一次 Phase A，**任一拒绝即拒绝**。理由：风险上限取**最严者**（§4.4「Skill 只能收紧」），只取一个 Skill 会让宽松上限的 Skill 成为绕过口。

### 3.4 幂等「进行中」返回而非阻塞（**P3 必接**）

§5.3 步骤 8 允许「阻塞或返回进行中」。P2 选择**返回进行中**（`IDEMPOTENCY_IN_PROGRESS`）：

- Worker 是批处理进程，阻塞会占住租约并拖垮整个批次；
- 代价：上一次尝试若崩溃留下悬挂 `IN_FLIGHT` 行，重试会被挡住。

P2 刻意选择「**宁可挡住也不重复执行**」。悬挂 `IN_FLIGHT` 的崩溃恢复属 **P3 的 COMP-\*** 范围（§5.3.5 跨系统恢复表）。

### 3.5 审批在 P2 是过渡语义（**P3 必须替换**）

§5.3.3 的 `PENDING → RESERVED → INTENT_SUBMITTED → CONSUMED` 状态机与 §5.3.1 的双哈希属 **P3**。P2 复用既有 `ApprovalPort.consume`（一次性消费），带来两个**已知差距**：

1. **准入失败时审批已被消费、无法 cancel**（§5.3 步骤 13 补偿清单要求「cancel 审批」）—— P3 的 `RESERVED → CANCELLED` 补齐；
2. 审批原因码按 P2 过渡映射（见 §4），未精确到 §9.1 S6a–e 的五个码。

步骤 13b 的调用点**已在 P2 落地**（`ApprovalPort.markIntentSubmitted`），P3 只需覆写端口实现，**调用点无需改动**。

### 3.6 缓存命中条件 = **依赖版本集合一致**（可证）

`CachingClosureResolver` 的命中条件不是「缓存里有」，而是「**逐个依赖对象重新读权威版本，与缓存条目记录完全一致**」。由于 `cap_*_def` 版本行**不可变**（§6.1）：

> 依赖版本集合一致 ⟹ 重新解析会得到逐字段相同的闭包 ⟹ 指纹必然相同。

校验步骤与 `PermissionResolver` 的解析步骤**逐一对应**（Agent 版本 / SKILL 版本 / TOOL 版本 / MCP_SERVER 版本；MCP 工具按 `(serverId, op)` 定位，因其不经发布指针），故这是**解析过程的镜像**，不是启发式判断。

⚠️ **依赖集合里没有全局发布序号**（§7.3）：无关对象发布新版本 → 依赖版本不变 → 命中 → 闭包未变 → 指纹未变 → **不产生 `CONFIG_FINGERPRINT_STALE`**。

⚠️ **MCP 清单漂移不在本装饰器的检测范围**：MCP 固定清单是实时源（`McpManifestPort`），不经发布指针。该项由 §5.8 步骤 3 的操作级复核兜底（P4 落地 MCP 传输后生效）。

### 3.7 账本登记失败复用 `IDEMPOTENCY_UNAVAILABLE`

账本同时是幂等存储（`UNIQUE (tenant_id, idempotency_key)`），「账本不可用」与「幂等存储不可用」是同一件事，故共用一码，不另造码。

## 4. §5.7 原因码缺口补齐清单（**需设计文档回填**）

§5.7 是对外稳定码权威源。P2 落地 §5.3 时发现**原表未覆盖**下列情形，而 §5.3/§9.1 又明确要求这些情形的可判定结论。按 §5.7「变更须版本化并保持兼容策略」，采取**只追加、不改写**的方式补齐：

| 新增码 | 阶段 | 触发的契约条款 | 若不复用会怎样 |
|---|---|---|---|
| `IDEMPOTENCY_UNAVAILABLE` | B | §5.3 步骤 8「幂等存储不可用 → fail-closed」 | 复用 `IDEMPOTENCY_CONFLICT` 会把「存储挂了」误报成「参数被篡改」，运维排查方向完全错误 |
| `IDEMPOTENCY_IN_PROGRESS` | B | §5.3 步骤 8「进行中 → 按契约阻塞或返回进行中」 | 同上：「重复投递」与「参数被改」是两件事 |
| `RUN_CANCELLED` | B | §5.3 步骤 1 的取消前置 + `ApprovalOutcome.RUN_CANCELLED` | 与「审批被拒绝」混为一谈（前者主动中止、后者策略结论） |
| `EXECUTION_PERSISTENCE_FAILED` | B | §5.3 步骤 13a「执行意图必须先于外部调用持久化」 | 与「幂等存储不可用」分属不同存储、不同后果（一个影响重复副作用，一个影响恢复能力） |
| `TOOL_EXECUTION_FAILED` | 执行后 | §9.1 S3f「确定失败 → 稳定失败码」 | 复用 `SUCCESS` 会把失败说成成功；复用 `EXEC_UNKNOWN` 会把「确定失败」误报成「结果不确定」，凭空造出待对账的幽灵操作（§5.1 明令禁止） |

> ⚠️ **这是对权威表的补充，不是改写**。建议设计文档 §5.7 表补入这 5 行；若评审否决，需回到 §5.3 逐条复核「无码可用」时的表达方式。
