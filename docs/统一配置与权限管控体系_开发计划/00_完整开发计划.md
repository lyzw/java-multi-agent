## 1. 定位：为什么是「单独阶段」

| 维度 | 说明 |
|---|---|
| 独立版本线 | 设计契约以 `docs/Agent - Skill- Tool -MCP 统一配置与权限管控体系.md` 为唯一事实源；本计划只消费它，不反向改写其规则（§5 安全决策 / §8 冻结门槛 / §9 验收矩阵为权威）。 |
| 独立依赖门 | 仅依赖平台 **P2 核心闭环 MVP**（已有 `ToolInvocationGate` / `AuthorizationService` / RLS / 审批·预算·账本 Port）与 **P3 可靠性基座**（UNKNOWN·幂等·对账语义）。不阻塞平台其它工作流。 |
| 独立验收门槛 | 以设计文档 §8.3 三类门槛 + §9 行为/不变量/故障注入 + 附录 A 检查清单为冻结依据；Demo 永不等于平台验收（§9 / §13）。 |
| 独立追踪 | 状态枚举 `DESIGNED → DEMO_IMPLEMENTED → PLATFORM_IMPLEMENTED → UNIT_TESTED → INTEGRATION_TESTED → SECURITY_ACCEPTED → ACCEPTED`（§10）；每个 P0 保证至少 1 个实现落点 + 1 个测试 ID。 |

**与整体平台计划的关系**：整体平台计划（Java SaaS Agent 平台 v3.1 软件开发阶段实施计划）使用 P0–P5 描述平台大闭环。本 W-PERM 是其「安全治理 / 权限管控」切片的独立细化：内部细化为 **W-PERM-P0 ~ W-PERM-P6** 七个阶段，各自带独立门禁、责任分工与测试证据。

### 3.1 依赖图

```text
平台 P2（ToolInvocationGate / AuthorizationService / RLS / 审批·预算·账本 Port）
        │
        ├──▶ W-PERM-P0 地基（cap_* 表 + authzVersion DB + 结果事件 + 执行意图）
```

## 4. 逐阶段开发计划

### W-PERM-P0 · 地基

> **阶段目标**：建立统一配置与权限管控的持久化地基——不可变版本对象表、`cap_authz_version` DB 强一致版本、迁移双写可回退、结果事件表与执行意图记录。这是后续所有阶段（P1–P5）的硬依赖。
> **设计文档落点**：§6.1 核心表、§6.2 引用与快照职责、§6.4 闭包指纹（结构就绪，算法在 P1 实现）、§5.4 四类版本、§8.4 迁移。

#### 目标与范围

| 范围 | 内容 |
|---|---|
| 入库 | `cap_tool_def` / `cap_skill_def` / `cap_mcp_server_def` / `cap_agent_def`（不可变版本行 + RLS）、`cap_authz_version`、`execution_capability_snapshot`、`cap_config_release`、结果事件表、执行意图记录 |
| 版本服务 | `cap_authz_version` 原子自增仓库；初始值 1；读写权威主库/线性一致源 |
| 迁移 | 现有 `agent`/`agent_version`/`execution_snapshot` 双写接入；可回退到旧读路径 |
| 不在此阶段 | 任何 Phase A 校验逻辑、Gate 改造、审批/预算/账本改造（留 P1–P3） |

#### 前置条件

- 平台 **P2 核心闭环 MVP** 已交付：`ToolInvocationGate`、`AuthorizationService` 接口、RLS 框架、审批/预算/账本 Port 可用。

- RLS 17 表已具备租户上下文注入机制。

| 风险 | 缓解 / 回滚 |

| 迁移脚本在目标库失败 | 前向修复脚本 + 回滚脚本随迁移同版本提交 |

#### 退出门禁

- [ ] 所有核心表 DDL 在目标 PostgreSQL 版本应用成功，含不可变版本行与 RLS。
- [ ] `cap_authz_version` 原子自增 IT 通过（并发自增单调无丢失，初始值 1）。
- [ ] RLS 租户隔离 IT 通过（tenant A 不可见 tenant B 的 agent/快照/审批/账本）。
- [ ] 迁移双写可回退：开关切 false 后旧路径完全接管，无数据丢失。
- [ ] 双写一致性比对在抽样数据上差异为 0（或已登记并获批的差异清单）。
- [ ] 事务契约测试通过（版本行插入 + authzVersion 自增 + RLS 同事务）。

**出口**：M0 数据地基就绪。**工作量**：1.5 人周。

### W-PERM-P1 · 解析校验

> **阶段目标**：实现无副作用的能力闭包计算（`PermissionResolver`）与 Phase A 全因子授权校验（`InvocationValidator`），覆盖 §5.2 授权公式与 §5.8 MCP 新鲜度判定顺序。这是「运行期纵深防御」的第一道闸门（授权层）。
> **设计文档落点**：§5.1 决策状态模型、§5.2 授权公式、§5.3 Phase A（步骤 1–7）、§5.7 原因码、§5.8 MCP 顺序、§6.4 闭包指纹算法、§7.1 组件职责。

#### 目标与范围

| 范围 | 内容 |
|---|---|
| 闭包计算 | `PermissionResolver`：Agent→Skill→{Tool,MCP} 沿链取交集闭包；仅逻辑 id 引用；版本由当前 PUBLISHED release 解析（P5 提供，本阶段用测试桩） |
| Phase A 校验 | `InvocationValidator`：PrincipalAuthorized → AgentSkillAllowed → SkillToolAllowed → RiskWithinCeiling → MCPBindingAllowed → ParamPolicyPassed → ConfigFingerprintValid |
| 决策状态 | 产出 `authorizationDecision` / `executionDecision` / `executionStatus` / `reasonCode` 四字段（§5.1）；授权失败 = DENY + NOT_EVALUATED + NOT_STARTED + 对应码 |
| 指纹算法 | 实现 §6.4 闭包指纹（SHA-256，含本 Run 依赖对象 `(id,version)`/riskCeiling/allowlist/paramPolicies/MCP 固定清单/ForcedSafety 摘要；凭据永不入指纹） |
| 参数策略 | `in_allowlist` / `lte` 合并（§4.3，仅收紧）；null vs [] 语义（§4.3/§4.4） |
| 未知风险 | `RISK_LEVEL_UNKNOWN`：配置期拒发布（P5 校验）、运行期 `authorizationDecision=DENY`（本阶段） |

> 不在本阶段：Phase B 执行准入（P2）、审批/预算/账本（P3）、MCP 传输适配（P4，本阶段仅校验逻辑）。

### 5.2 关键前置修正：DB 化 authzVersion 前移至 V1

评审指出「分布式授权版本若是多实例安全正确性的必要条件，应前移 V1」。本平台为**多租户 SaaS、多实例部署**，单实例内存版 `RoleBasedAuthorizationService` 无法满足「撤权即时全实例失效」。

**V1 强制要求**：`authzVersion` 必须为 **DB 支撑、单调递增、全局一致** 的版本号（或等价逻辑时钟），且**经强一致读取（或具强一致保证的授权服务）**判定失效——**不依赖普通异步缓存刷新**来承诺即时撤权。撤权 → 同一事务内 bump 版本 → 所有实例下一次调用读取到新版本即失效旧授权。V1 **不要求**完整的策略即代码，但**必须**提供该版本的存储、并发自增、读取与失效判定契约。

> **可验证的撤权 SLA**：撤权事务成功提交后，任意实例发起的新工具调用，只要其授权判定发生在提交之后，必须读取到不早于该提交版本的 `authzVersion`；若无法确认版本新鲜度（版本服务不可用/读取超时），fail-closed 拒绝该调用。该 SLA 以 DB 强一致读取或强一致授权服务为技术契约，而非「异步缓存最终一致」。

### 5.3 V1 明确不做（Explicit Non-Goals）

| 编号 | 能力 | 归属 | 不做的原因 |
|---|---|---|---|
| **N1** | 嵌套 Skill / `Skill.inherits` | V2 | 传递闭包易抬权（P3）；V1 只显式 ID 引用，写 `inherits` 即拒 |
| **N2** | Capability Tag / Skill Bundle / Agent Profile | V2 | 缓解组合爆炸用（M1），但标签过宽有越界风险；V1 仅显式 ID，避免歧义 |
| **N3** | 通用参数策略引擎 | V2 | V1 仅在验收场景必需处做**手写参数约束**（`in_allowlist` / `lte` 两点判定），不形成可组合策略引擎 |
| **N4** | 动态 MCP 工具发现 | V2 | V1 用固定工具清单 + 配置版本/指纹校验；运行期实时列举属 V2 |
| **N5** | 策略即代码（OPA/Rego） | V3 | 本期声明式规则 + 闭包计算已够 |
| **N6** | 跨 Agent 委托（A2A 授权） | V3 | 本期单 Agent 内能力闭包 |
| **N7** | 共享参数策略库 / 标签化权限市场 | V2 | 依赖 N2/N3 |

### 5.4 V1 预留接口（Reserved, stubbed）

| 字段 | V1 行为 | 理由 |
|---|---|---|
| `Skill.inherits` | 写入即**拒绝**（校验失败），不允许误用 | 防 P3 抬权 |
| `Agent.skillBundles` / `capabilityTags` / `Skill.requiredCaps` | 接受写入但**忽略语义**（等价于空），不用于任何启用判定 | 防 M1 标签越界；为 V2 留字段 |
| `Skill.paramPolicies` / `Tool.paramPolicies` | 仅支持 `in_allowlist` / `lte` 两点手写判定；其他 op 写入即拒 | 防 G2 参数越权 |
| `McpServer.dynamicDiscovery` | 固定为 `false`；写入 `true` 即拒绝 | V1 不动态发现 |
| `Tool.namespace = tenant:<id>` | V1 仅 `platform` 级定义；租户级自定义 Tool 留 V2 | 单一事实源治理 |

## 6. 通用执行原则与 DoD

### 6.1 执行原则

1. 每阶段必须有可运行软件、测试结果、文档、明确退出门禁。
2. 先验证高风险协议：authzVersion 强一致、CAS 发布、执行意图先于副作用、COMP-6 崩溃恢复。
3. 数据库为执行事实源；MQ 仅通知/唤醒。
4. 副作用先记账、后调用、可对账；UNKNOWN 不得盲目重放。
5. 安全不是后置阶段；越权拒绝测试与正向授权测试成对出现。
6. 文档与实现同版本：DDL/迁移、状态机、原因码表、ADR、测试用例随代码变更更新。

### 6.2 单项 DoD（Definition of Done）

- [ ] 验收标准满足，未完成项已登记并获批。
- [ ] 代码合并并通过非作者 Review；权限/状态机/迁移/安全改动有领域负责人 Review。
- [ ] 单元/集成/契约/E2E 测试通过，证据可追溯（关联 §9 测试 ID）。
- [ ] 涉及 API/DDL/状态机/配置/权限的文档同步更新。
- [ ] 关键路径具备日志/指标/Trace/审计；不记录密钥或多余敏感内容。
- [ ] 涉及副作用时，幂等/超时/重试/UNKNOWN/对账语义明确且有测试。
- [ ] 涉及权限时，正向授权 + 越权拒绝测试成对。
- [ ] 涉及迁移时，迁移/失败/回滚（或前向修复）路径已在目标版本验证。

## 7. 风险登记

| 风险 | 影响 | 缓解（落点） |
|---|---|---|
| authzVersion 强一致读延迟/抖动 | 撤权阻断不及时（§5.5） | 读权威主库/线性一致源；缺失 fail-closed（`AUTHZ_UNAVAILABLE`） |
| 发布 CAS 并发回滚半成品 | 当前指针错乱（§6.3） | 同事务版本+release+CAS；失败整事务回滚；PUB-1/PUB-2 注入 |
| 执行意图未先于副作用写入 | 崩溃窗口重复/丢失副作用（§5.3.4） | 13a 强制先于 execute；COMP-6 硬门槛 |
| 审批参数替换重放 | 越权执行（§5.3.1） | approvalScopeHash + effectiveArgsHash；消费时范围重验 |
| MCP SSRF / DNS rebinding / 重定向 | 内网/元数据泄露（§6.5） | endpoint 防 SSRF、DNS 后 IP 校验、禁重定向至内网、凭据仅 `credential_ref` |
| 嵌套 Skill / 动态发现提前引入 | V1 非目标越权面（§3.2 N1/N4） | 代码层显式拒绝 `inherits`、关闭 `dynamicDiscovery` |
