## 2. §5.8 四步顺序与「同一类变化不得两种码」

| 步骤 | 判定 | 原因码 |
|---|---|---|
| 1 | 闭包指纹新鲜度 | `CONFIG_FINGERPRINT_STALE` |
| 2 | 请求 op ∈ 快照 AllowedOps / ClosureOps | `MCP_OP_NOT_ALLOWED` |
| 3 | 请求 op 仍 ∈ 当前 ManifestOps | `MCP_TOOL_DRIFTED` |
| 4 | 逻辑 id 映射到未绑定新版本 | `RESOURCE_VERSION_MISMATCH` |

### 2.1 原因码的收敛（退出门禁 3）

| 变化类别 | 原因码 | 为什么唯一 |
|---|---|---|
| 清单**内容变了**（op 下线 / 清单缩小） | `CONFIG_FINGERPRINT_STALE` | 清单在闭包指纹内（§6.4）→ 闭包无法按当前清单复现 → 指纹失效 |
| 清单**读不到**（server 宕机 / SSRF 拦截 / 熔断） | `CONFIG_FINGERPRINT_STALE` | 同上：闭包同样无法复现 |
| 清单在**本次校验过程中**变化（指纹重算与步骤 3 之间） | `MCP_TOOL_DRIFTED` | 指纹检查已通过，但实时复核发现 op 已不在清单内 |
| 端点**静态形态**不安全 | `MCP_OP_NOT_ALLOWED` | ForcedSafety 把该 server 的全部操作剔除 → op 不在允许集 |

> ⚠️ **「清单不可用」与「清单变了」必须收敛到同一码**，这是本阶段修掉的一个真实缺陷：
> 若缓存保留（不可用时沿用旧 `manifestOps`），则**有缓存**路径给 `MCP_TOOL_DRIFTED`、
> **无缓存**路径给 `CONFIG_FINGERPRINT_STALE` —— 同一类故障因缓存状态不同给出两个码。
> 故 `CachingClosureResolver` 在**清单不可用时同样作废缓存条目**，两条路径一致。

### 2.2 与 P1 已建立契约的关系

P1 已把 §5.8 的四步顺序与两个漂移场景的原因码**固定下来**（`InvocationValidatorTest` 有专门用例）。
P4 **未改动**这两条契约，只补齐了：
① 清单「不可用」这一新增状态的收敛；② 缓存按 07 §4 纳入清单变更检测；③ ForcedSafety 的端点谓词。

## 3. SSRF 防御（06 §5 逐条落地）

| 06 §5 要求 | 实现 |
|---|---|
| `endpoint` 须落允许范围；禁止 `127.0.0.0/8`、`169.254.0.0/16`、私有 CIDR，除非 `trustTier=internal` 显式授权 | `McpAddressPolicy` + `McpEndpointGuard`；**云元数据地址任何级别都绝对禁止**（刻意收紧，见 §6 决策 2） |
| DNS 解析后对**实际 IP** 校验 | `McpEndpointGuard`：解析全部候选 → 逐个判定 → **任一被禁即整体拒绝**（fail-closed） |
| 防 DNS rebinding（解析与连接用同一结果、连接前复验） | **二次解析**：两次结果不一致即拒（rebinding 的动作本身）；返回**被校验的 IP 集合**，传输层据此连到该 IP |
| 禁止未经授权的 HTTP 重定向跳内网/云元数据 | `HttpMcpTransport` **不自动跟随**重定向；每个 `Location` 重新走完整校验 |
| 每次连接与重定向**重新校验**目标地址 | 每次发请求前都重新 `guard.validate(...)` |
| 凭据仅 `credential_ref`；明文禁入库；日志脱敏；支持轮换（轮换后连接级重验） | `RefMcpCredentialPort`（不缓存 → 轮换即生效）；`CapMcpServerDef.toString()` 脱敏；`McpCredential.toString()` 脱敏；闭包指纹不含凭据 |

### 3.1 为什么不用 `java.net.http.HttpClient`

它按**域名**发起连接 —— 「校验过的 IP」与「实际连上的 IP」可能是两个东西，
而 06 §5 要求「**解析与连接用同一结果**」。

本实现直接建连到**已校验的 IP**，并把原始主机名放进 `Host` 头；
HTTPS 场景用 `SSLSocketFactory.createSocket(socket, host, port, true)`，
让 JDK 依旧按**主机名**做证书校验（SNI + endpoint identification）——
**既钉死了目标 IP，又没有牺牲 TLS 的主机名校验**。

### 3.2 连接级凭据重验与「不做连接池」

连接池会把「建立连接时的凭据」固化在连接上，凭据轮换后旧连接仍在用旧凭据 ——
这正是 06 §5「轮换后连接级重验」要防的事。V1 选择**每请求一条新连接**
（`Connection: close`），凭据**逐请求解析**，轮换立即生效。性能优化留给后续（P5 立项，需把凭据版本进池键）。

## 5. 关键设计决策（需 P5 复核）

### 5.1 清单「不可用」与「为空」必须区分

`ManifestSnapshot.available()` 是本阶段新增的语义。
「这个 server 确实没有工具」（配置事实）与「读不到这个 server」（运行故障）
在授权语义上都是「无法确认 op 仍在清单内」，但运维处置方式完全不同。
区分靠**日志**，不靠**原因码** —— 原因码是对外稳定契约，不能随意分化。

### 5.2 云元数据地址在任何信任级别下都绝对禁止

06 §5 的「除非 `trustTier=internal` 显式授权」在字面上也覆盖了 `169.254.0.0/16`。
本实现**刻意收紧**：元数据地址（`169.254.169.254` / `169.254.170.2` /
`fd00:ec2::254` / `100.100.100.200`）**任何信任级别都不放行** ——
没有任何业务理由需要 MCP 去访问元数据服务，而它是 SSRF 的最高价值目标。

### 5.3 清单不可用时缓存必须作废

见 §2.1。这是本阶段修掉的一个**真实缺陷**：不修则同一类故障按缓存状态给出两个原因码。

### 5.4 Phase A 只做端点**静态**判定，DNS 判定在传输层

Phase A 是授权路径，不应引入 DNS 解析（延迟 + 可被用作放大器）。
静态判定能拦住：非 http/sse、URL 带凭据、endpoint 直接写成内网/元数据 IP 字面量。
「域名解析到哪里」由传输层在**每次连接前**判定，那里才是最终拦截点。

### 5.5 失败语义：请求没发出 = 确定失败；已发出但响应不可信 = 结果未知

`McpBackedToolHandler.translate(...)`：
`SSRF_BLOCKED` / `CIRCUIT_OPEN` / `RATE_LIMITED` / `CREDENTIAL_UNAVAILABLE` / `CONNECT_FAILED`
→ **确定失败**（可重试）；
`TIMEOUT` / `PROTOCOL_ERROR` → **结果未知**（副作用可能已发生，必须进 UNKNOWN 对账，禁止盲目重试，P0-D03 §4 红线 7）。

### 5.6 输出不可信：只加边界 + 限体积，不做「清洗」

本类不删除、不改写内容里的任何字符 —— 删字符会改变语义，且攻击者总能绕过。
它只保证「**边界可见 + 体积有界**」：输出被包进显式数据信封，
并按**字节预算 + 字符边界**截断（直接砍字节数组会把多字节字符砍成半个 → 解码出替换字符）。

### 5.7 MCP 工具不另开执行入口

`ToolInvocationGate` 只在静态注册表未命中时**解析**一个 MCP 处理器，
后续八道闸门（Schema / 重授权 / 审批 / 预算 / 账本 / 准入 / 意图 / 落盘）与原生工具完全一致。
防绕过架构测试（`ToolBypassArchitectureTest`）的白名单已按新持有者更新并说明理由。
