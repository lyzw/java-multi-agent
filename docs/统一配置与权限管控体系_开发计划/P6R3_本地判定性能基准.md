## 0. 一句话结论

P6 登记的限制 1 是「**R-15 性能目标无任何压测/基准测试**」。
本轮交付了**可复现的基准 harness + 实测数据 + 建议目标值**，并给出一个此前没有被说清的结论：

> **08 §7 登记的 `p99 < 1ms` 在没有「闭包规模上界 + 并发度」两个前提时是不可用的目标。**

### 2.1 「不含 DB 读取」是**可执行**核实，不是文档声称

`InvocationValidator` 的五个端口（`AuthzVersionPort` / `RolePermissionPort` / `ClosureResolver` /
`CapabilitySnapshotPort` / `McpManifestPort`）在基准里全部换成**内存实现**（复用既有 `CapFixture`）。
此外，`LocalDecisionBenchmark.assertNoDataSourceIn` 在运行期把判定器持有的**对象图逐层走一遍**，
确认其中**不存在**任何 `javax.sql.DataSource` / `java.sql.Connection`，
并核对遍历到的类名里没有 JDBC 驱动或连接池实现。

> 这条「实测路径无数据库访问」的断言由 `LocalDecisionBenchmarkTest#measuredPathTouchesNoDatabase` 把守，
> **每次全量构建都会跑**。P6R2 的 `ModuleDependencyDirectionTest` 从模块依赖方向上提供了第二重保证
> （`agent-application` 不依赖基础设施层）。

## 4. 测量方法学（决定了数据可不可信）

基准测试最容易骗人的地方是「测了一个看起来像基线、其实与生产无关的数」。本 harness 在方法上做了三件事：

1. **自适应预热（跑到 p50 收敛为止）**
   JIT 编译是渐进的。固定次数预热常常在 C2 编译完成前就结束，
   测量窗口里混着解释执行与 C1 代码 —— 得到的 p99 比稳态高一个数量级，
   那个数**与生产无关**却会被误当成基线。
   本 harness 以窗口为单位采样 p50，连续 3 个窗口的 p50 互相偏离 ≤ 5% 才判定收敛。
   *（实测：档位 S 用了 10 400 次、档位 M 4 000 次、档位 L 3 200 次才收敛。）*

2. **记录 GC 影响**
   闭包指纹每次判定都要全量序列化 + 哈希，分配量很大。尾延迟里有多少是 GC 造成的，
   必须随数据一起报出来，否则 p99 无法解读。报告里每档带 `gcCount` / `gcMillis`。

3. **轮转目标位置**
   `EffectiveClosure.skill()/tool()` 是**线性扫描**，命中首位的耗时与命中尾部差一个数量级。
   只测首位会得出「查表几乎不要钱」的测量假象。故测量与分解均按请求序列轮转取样。

### 4.1 为什么**没有**耗时阈值断言

- 把 p99 写成断言，会把「共享构建机繁忙」误判为「代码退化」，让全量构建**随机变红**，
  久而久之所有人都会无视红灯；
- 更根本的是：§8.2 明文「目标由压测标定」，**在标定完成前写死阈值等于把一个还没有依据的数字升级成门禁**。

因此机器把守的是**结构不变量**（不会随机器负载漂移）：
判定结论全部 ALLOW、样本量达标、分位单调、实测路径无数据库访问、报告口径完整。

## 6. 关键发现

### 6.1 单跳成本几乎全部来自**闭包指纹的每次全量重算**

`InvocationValidator` 步骤 7 每次判定都调用 `ClosureFingerprint.of(closure)` ——
把整个闭包**规范化（排序 + JSON 序列化）后 SHA-256**。这是 `O(闭包规模)` 的。

分解数据显示：闭包查表只占 **0.6% ~ 3.3%**，其余全部是指纹重算。
p50 随闭包规模**近似线性**增长（20 → 80 → 320 绑定：15.71 → 74.17 → 557.04 µs），与该结构一致。

### 6.2 并发扩展性差

| 档位 | 单线程吞吐 | 8 并发吞吐 | 8 并发 p99 劣化倍数 |
|---|---|---|---|
| S | 58 242 | 108 229 | 4.0×（p99 36.88 → 146.46 µs） |
| M | 12 691 | 25 172 | **5.5×**（p99 181.46 → 988.96 µs） |
| L | 1 730 | 3 891 | **5.6×**（p99 974.75 → 5 489.17 µs） |

吞吐只涨了约 2×，而尾延迟劣化 5～6 倍。根因指向**分配压力**：
每次判定都新建一棵 JSON 树 + 一段规范化 JSON 字符串（GC 次数随规模线性上升：6 → 19 → 74）。

### 6.3 由此得到的核心结论

> **「p99 < 1ms」这个目标，在缺少「闭包规模上界」与「并发度」两个前提时是无意义的。**
>
> | 前提 | 实测 p99 | 与 1ms 目标的关系 |
> |---|---|---|
> | ≤ 80 绑定 · 单线程 | 0.18 ms | 成立，裕度 5.4× |
> | ≤ 320 绑定 · 单线程 | 0.97 ms | 勉强成立，**裕度 1.03×（等于没有裕度）** |
> | ≤ 80 绑定 · 8 并发 | 0.99 ms | 勉强成立，**裕度 1.01×** |
> | ≤ 320 绑定 · 8 并发 | 5.49 ms | **不成立，超出 5.5 倍** |
>
> 因此下一版性能目标必须写成 **「规模 + 并发 + p99」三元组**，不能只写一个数。

### 6.4 后续项（登记，不在本轮实施）

## 7. 建议目标值（**待评审签署**，非既成事实）

标定方法：以本次实测 p99 为基线，取 **2× 安全系数**，并**与闭包规模上界、并发度联合声明**。

| 闭包绑定上界 | 并发度 | 实测 p99 | **建议目标 p99** |
|---|---|---|---|
| ≤ 20 | 1 | 0.037 ms | **≤ 0.1 ms** |
| ≤ 20 | 8 | 0.146 ms | **≤ 0.3 ms** |
| ≤ 80 | 1 | 0.181 ms | **≤ 0.4 ms** |
| ≤ 80 | 8 | 0.989 ms | **≤ 2.0 ms** |
| ≤ 320 | 1 | 0.975 ms | **≤ 2.0 ms** |
| ≤ 320 | 8 | 5.489 ms | **≤ 11.0 ms** |

⚠️ **本表是「建议值」，不是「已达成的标准」**：
- 需**评审签署**后才具备约束力；
- 需在**目标生产规格环境**重新标定后确认安全系数是否仍成立；
- 在此之前，**不得**把这些数字写成任何构建门禁。

### 为什么不给「性能达标」结论

P6 限制 1 明文要求「结论不得声称『性能达标』」。本次**遵守**该约束，具体理由：

1. **目标生产规格环境未标定** —— 本次是开发机（10 核 arm64 / JDK 21 / 8 GiB 堆）的单机结果，
   目标生产环境的核数、堆、容器限额、网络栈均未知；
2. **目标值尚未经评审签署** —— §7 表格是建议，不是已批准的门禁；
3. **生产真实闭包规模分布未统计** —— 档位 S/M/L 是人为梯度，不能代表真实负载分布；
4. **未做长稳 / 混合负载 / 压测集群** —— 本次只测了单一合成数据集。

本轮**只**做到两件事：① 消解「无任何压测/基准测试」（产出可复现的基准与数据）；
② 给出可评审的**建议目标值**。

## 10. 复现命令

```bash
cd platform

# 默认（全量构建）：档位 S/M，小样本量，结构自检 + 冒烟数据（约 2.4 秒）
export JAVA_HOME=/opt/homebrew/opt/openjdk@21
mvn -o -pl agent-application -am test -Dtest='LocalDecisionBenchmarkTest' \
    -Dsurefire.failIfNoSpecifiedTests=false

# 标定：全档位 S/M/L，大样本量，产出归档报告（约 55 秒）
mvn -o -pl agent-application -am test -Dtest='LocalDecisionBenchmarkTest' \
    -Dsurefire.failIfNoSpecifiedTests=false \
    -Dcap.benchmark.mode=calibration \
    -Dcap.benchmark.samples=30000 \
    -Dcap.benchmark.maxWarmup=60000 \
    -Dcap.benchmark.concurrencyWarmup=1000 \
    -Dcap.benchmark.report=../../docs/统一配置与权限管控体系_开发计划/P6R3_本地判定性能基准_标定报告.json
```
