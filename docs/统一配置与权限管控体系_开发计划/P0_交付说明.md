## 2. 数据模型

| 表 | 作用域 | RLS | 要点 |
|---|---|---|---|
| `cap_tool_def` | platform | ❌ 不启用 | `(id, version)` 不可变版本行；`kind`/`risk_level` 枚举化；`kind=mcp` 必须带 `mcp_server_id`+`mcp_tool_name` |
| `cap_skill_def` | platform | ❌ 不启用 | `inherits` **写入即拒**（N1）CHECK 兜底；`risk_ceiling` 枚举化 |
| `cap_mcp_server_def` | platform | ❌ 不启用 | `dynamic_discovery` **恒为 false**（N4）CHECK 兜底；`exposed_tool_allowlist` 可空且 `null ≠ []`；仅存 `credential_ref` |
| `cap_agent_def` | tenant | ✅ FORCE | `(tenant_id, agent_id, version)`；复合 FK 防跨租户引用；`inherits` 写入即拒 |
| `cap_authz_version` | tenant | ✅ FORCE | PK `(tenant_id, principal_id)`；`authz_version` 单调；**原子自增**由 `ON CONFLICT DO UPDATE` 保证 |
| `execution_capability_snapshot` | tenant | ✅ FORCE | `config_version`（序号）与 `config_fingerprint`（内容）**并存不合并**；复合 FK → `run` |
| `cap_config_release` | 平台 + 租户 | ✅ FORCE（读写分离） | 序号由序列分配；`status` 枚举；双人复核 CHECK；写策略只放行本租户行 |
| `cap_result_event` | tenant | ✅ FORCE | **UNIQUE `(tenant_id, invocation_id)`** = 「只落账不重执行」的存储层保障 |
| `cap_execution_intent` | tenant | ✅ FORCE | **UNIQUE `(tenant_id, invocation_id)`**；状态 CAS 式迁移；`BEFORE UPDATE` 不可改写 |

**已发布行不可改写**：`forbid_published_def_mutation()` 触发器封禁**已发布**行（`published_at IS NOT NULL`）的 UPDATE。草稿行可编辑（06 §3「草稿编辑不修改已发布版本行」）。

> ⚠️ **DELETE 不受此约束**：删除/保留期链路（V8 erasure）必须能物理删除，否则「被遗忘权」会被一条技术不变式挡住。引用完整性（06 §3.4「被引用对象不得物理删除 → DEPRECATED」）由应用层保证，属 P5 范围。

## 3. 关键设计决策（需 P5 复核的 3 项）

### 3.1 `cap_config_release` 的作用域与 RLS（P0 落地偏离 §6.1 的字面表述）

§6.1 的租户 RLS 清单未含发布头，但 §6.3 允许「租户级（若有）按 tenant」。V1 的 `cap_agent_def` 是**租户级**，若发布头为 platform 级且**不带 RLS**，其 `object_versions` 会把**各租户的 Agent 结构**写进一张任何租户都能 SELECT 的表 —— 跨租户结构泄漏（与 R-004 同类，Sev-0 级）。

**处置**：本表用 `scope`（`PLATFORM`/`TENANT`）+ `tenant_id` 区分，RLS **读写分离**：
- SELECT：PLATFORM 行对所有租户只读可见；TENANT 行仅本租户可见。
- INSERT/UPDATE：**只允许写本租户的 TENANT 行**。若写策略也放行 `tenant_id IS NULL`，任一租户都能发布**全局**配置 —— 那是直接越权。PLATFORM 行的写入只能由平台运维角色（BYPASSRLS / 迁移角色）执行。

> **P5 待复核**：P5 实现 CAS 发布时，需确认 PLATFORM 作用域发布的执行路径与角色。

### 3.2 闭包指纹在 P0 是「临时占位」

`config_fingerprint` 列非空，但 §6.4 的真实闭包指纹算法属 **P1**（依赖 P0 还不存在的 Tool/Skill/MCP 定义与发布头）。P0 写入**带 `pending_v1:` 前缀**的确定性摘要：

- 前缀与 P1 真实算法输出**物理隔离** —— 数据里一眼可辨，不会被误当成可用���失效判定的真实指纹。
- 确定性（同输入同输出）是双写比对工具能判定一致性的前提。

> **P1 必办**：实现 §6.4 真实算法后，**重算并迁移**存量 `pending_v1:` 值。

### 3.3 `execution_capability_snapshot` 的内容属 P1

该表的 `effective_closure` / `config_fingerprint` / `authz_version` 全部依赖 P1 尚未实现的计算（`PermissionResolver` 闭包、§6.4 指纹、DB 化版本源的运行期读取）。P0 阶段 `cap_skill_def` / `cap_tool_def` **无任何数据**，闭包在数学上就不可计算。

**处置**：P0 只提供**存储 + 仓储 + 端口**；双写挂起点已就位（`CapDualWriteService.onExecutionSnapshotCreated`），P1 补上闭包计算即可启用。**P0 不写占位闭包** —— 往授权决策的输入表里塞假数据，若被读成「权威闭包」即为越权面。

> **P1 必办**：接入 `PermissionResolver` 后启用该双写分支，并回填存量快照。

### 4.1 存量欠账清单（门禁 5 的「已登记差异」）

开发库 `agent_dev` 实测（双写开关默认关，灰度未开）：

| 租户 | 旧模型已发布版本 | 未双写（存量欠账） |
|---|---:|---:|
| t-a | 105 | **105** |
| t-b | 0 | 0 |

**性质**：属**存量欠账**（开关未开时的正常状态），非本次双写缺陷。**处置**：灰度开启双写后由 `CapDualWriteComparator` 逐 Agent 比对收敛，或在 P5 迁移流程（06 §3.3 第 3 步「幂等迁移」）中批量回填。

> ⚠️ 比对工具**必须按 Agent 限定**才能回答「本次双写做对了吗」——整租户比对会把这类存量欠账混进来，让报告淹没在噪声里。故 `compare(tenantId, agentId)` 与 `compare(tenantId)` 两个口径并存。

### 4.2 验收复现：如何确认「绿」不等于「跑过」

本仓库的 IT 一律用 `@EnabledIfEnvironmentVariable(named = "IT_PG_URL", matches = ".+")` 守门。**该变量缺失时全部 IT 被静默跳过，而构建仍报 BUILD SUCCESS** —— 与 F-14/CP-1/CP-2 同形态。复盘 P0 验收时实测踩中过一次：

```bash
# ❌ 错误写法：IT_PG_URL 只是 shell 变量，**没有 export**
export JAVA_HOME=/opt/homebrew/opt/openjdk@21 && IT_PG_URL="jdbc:..." IT_PG_USER=app_agent && mvn -o clean verify
# → 输出「Tests run: 37, Skipped: 37」，BUILD SUCCESS，绿色但一条 IT 都没跑

# ✅ 正确写法：export 一次带上全部变量
export JAVA_HOME=/opt/homebrew/opt/openjdk@21 IT_PG_URL="jdbc:..." IT_PG_USER=app_agent IT_PG_PASSWORD=""
# → 输出「Tests run: 37, Skipped: 0」
```

**判读纪律**：任何 IT 结果都要先看 **Skipped 数**，再用 CI 同款口径统计汇总行（逐类明细行带 `, Time elapsed: ... -- in ...`，锚定行尾才能取到模块汇总行，否则计数翻倍）：

```bash
summary() { grep -oE "Tests run: [0-9]+, Failures: [0-9]+, Errors: [0-9]+, Skipped: [0-9]+$" build.log; }
```

> ✅ **CI 侧已有防线**：`.github/workflows/ci.yml` 的 integration-test job **断言跳过数必须为 0**，且执行数低于 700 即失败。单元测试 job 只跑到 `package`（不提供库），由 IT job 跑全 reactor —— 职责分离，绿得诚实。**本节记录的是本地复现时的同类陷阱**，不影响流水线结论。

## 5. 顺带修复的既有缺陷（与 P0 无关，但不修则构建不可信）

### 5.1 `RealBrokerEndToEndIT` 队列残留

原实现只在收尾时收走**最多 5 条**消息，而队列跨轮次累积（本机实测 76+ 条）。残留的历史消息会被本片「接收」先取到，断言「回环载荷的 runId 必须与发出的一致」失败 —— 症状指向本片载荷，真因是**上一轮**残留。

**修复**：开测前先排空（`drainQueue()`），收尾同样排空；上限 1000 条防跑飞。

### 5.2 既有 IT 的连接池泄漏

8 个既有 IT 类各建一个 `appPool` 且**从不关闭**（AgentRepositoryIT / ConfigChangeRepositoryIT / ConfigOverrideRepositoryIT / GovernanceQueryIT / RunClaimFencingIT / RunCreationAtomicityIT / RunEventAppendIT / TransactionBoundaryIT）。

### 5.3 测试环境连接池默认值

Hikari 默认 `minimumIdle = maximumPoolSize = 10`，即每个 Spring 上下文**常驻 10 条连接**；上下文缓存最多留 32 个 → 320 条 ≫ `max_connections = 100`。后果是**后续模块**以 `FATAL: sorry, too many clients already` 失败，报错点离真因隔一个模块。

**修复**：新增 `platform-bootstrap/src/test/resources/application-test.yml`，测试环境池收窄为 `maximum-pool-size: 4` / `minimum-idle: 1`。

> ⚠️ **上述三项均为既有缺陷**：以 pristine `HEAD`（`git worktree` 独立检出）复跑基线，`platform-bootstrap` 同样以 `too many clients` 失败（计数 13），与本次 P0 改动无关。
