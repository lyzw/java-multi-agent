## 2. 原子发布与 CAS（§6.3）

### 2.1 三者同事务

```
发布事务（ConfigPublishTransaction）
  ├─ 插入版本行（cap_tool_def / cap_skill_def / cap_mcp_server_def，published_at = now()）
  ├─ 插入发布头（cap_config_release，status = PUBLISHED，object_versions = 本次完整集合）
  ├─ CAS 切换当前指针（cap_config_pointer）
  └─ 写发布审计（cap_decision_log，decision_kind = PUBLISH）
```

成功条件唯一：**版本行 + 发布头 + 指针 CAS 同事务提交**；任一失败整事务回滚，**无半成品当前发布**。

### 2.2 CAS 的两个关键 SQL 形态

| 形态 | 为什么不能换 |
|---|---|
| `WHERE current_publish_seq IS NOT DISTINCT FROM ?` | 首次发布时基线是 `NULL`，而 SQL 里 `NULL = NULL` 恒为 UNKNOWN —— 用 `=` 则首次发布**静默失败**，且失败现场指向「CAS 没生效」而非「首次发布语义」 |
| 「先 UPDATE，0 行且指针确实不存在且 expected 为 null → 再 `INSERT … ON CONFLICT DO NOTHING`」 | 用 `INSERT … ON CONFLICT DO UPDATE … WHERE` 时，指针不存在会走 INSERT 分支，条件不满足则既不更新也不报错 —— 调用方**分不清**「CAS 失败」与「指针不存在」 |

### 2.3 变基重试只用于发布，不用于回滚

| 场景 | 变基重试 | 理由 |
|---|---|---|
| 发布 | ✅（上限 `DEFAULT_MAX_ATTEMPTS = 3`） | §6.3 第 4 条**明文要求**：同基线并发仅一次成功，失败方读新基线再试 |
| 回滚 | ❌（冲突即失败） | 回滚要切到的是**指定的那份配置**。若指针在此期间被别人推进，重试等于「回滚了另一份配置」—— 比失败更糟 |

### 2.4 回滚协议（§6.3 / 06 §3.2）

```
1. 新建一条 PUBLISHED 的「回滚发布」（object_versions = 目标发布的集合）
2. 原（当前）release 标 ROLLED_BACK —— 保留，不删除
3. CAS 把当前指针切到回滚发布
4. ⛔ 绝不触碰 cap_authz_version 与 cap_approval
```

> ⚠️ **回滚不恢复撤权**：撤权由 `cap_authz_version` 自增表达，与配置发布是**两条独立的状态机**。
> 回滚一份旧配置**不能**把已撤销的授权恢复回来 —— 否则「停用某工具」会被一次配置回滚悄悄推翻。
> 该性质由 `ConfigPublishIT#rollbackDoesNotRestoreRevokedAuthorization` 独立验证。

## 3. 生命周期（§6.6 / 06 §3）

### 3.1 状态与 `published_at` 并存，语义不同

| | 作用 | 由谁保证 |
|---|---|---|
| `published_at` | **不可变触发器的依据**（已发布行不可改写内容） | V15 `forbid_published_def_mutation` |
| `lifecycle_state` | **流程状态**（能表达 VALIDATED / DEPRECATED） | V17 `align_cap_lifecycle_state` 对齐触发器 |

对齐触发器把两者绑定：`published_at` 非空 ⇒ 状态 `PUBLISHED`（`DEPRECATED` 除外，它是显式停用终态）；
`published_at` 为空却声称 `PUBLISHED` ⇒ **显式报错，不静默降级** —— 悄悄改回 DRAFT 会让「发布」看起来成功而对象其实仍是草稿。

> ⚠️ **这一条是 P5 实测补正的**：首版实现的列 DEFAULT 是 `'DRAFT'`，
> 于是「INSERT 一行 `published_at = now()`」会得到 `lifecycle_state = 'DRAFT'` —— 一个自相矛盾的状态。
> 后果是 `PUBLISHED → DEPRECATED` 的停用迁移被不可变触发器拒绝（old_state='DRAFT'），
> 即「停用一个已发布对象」在数据层**无法表达**（06 §3.4 被架空）。

### 3.2 状态机接进了服务层（不是摆件）

`ConfigLifecyclePort` 只提供 **CAS 迁移**，**不判断迁移本身是否合法** —— 那是状态机的职责。
本阶段新增 `ConfigLifecycleService` 把两者合体，区分两类失败：

| 失败类型 | 表现 | 处置 |
|---|---|---|
| **非法迁移**（`DEPRECATED → PUBLISHED`、`DRAFT → PUBLISHED`） | 抛 `ConfigPublishRejectedException`（带原因码与对象定位） | 配置/操作错误，**重试没有意义**，必须改操作方式 |
| **CAS 前置条件不符**（原状态已被别人改动） | 返回 `false` | 并发竞争，调用方应重新读状态再决定 |

> ⚠️ 若没有这一层，非法迁移会一路落到 DB，被不可变触发器 / 对齐触发器以**裸 SQL 错误**炸出来 ——
> 报错点离真因（「这条迁移根本不合法」）很远，且错误文案取决于 DB 而非领域语义。

### 3.3 「发布」不是状态迁移

概念图上 `VALIDATED → PUBLISHED` 是合法边，但它**不能**通过改状态列实现 ——
到达 `PUBLISHED` 的唯一途径是**发布新版本行**（`published_at` 非空 → 对齐触发器置 PUBLISHED）+ 切换当前指针（§6.3）。
若允许改状态列，一个从未发布过的草稿就能自称已发布，而它**不在任何发布头的 `object_versions` 里** ——
授权路径读指针时根本找不到它，「未发布不可启用」反而被绕过。

### 3.4 「未发布不可被 Agent 启用」靠机制，不靠约定

未发布的对象不在**当前发布头**的 `object_versions` 里 → 闭包解析根本找不到它 → 启用链路上它压根不会出现。
该性质由 `ConfigLifecycleIT#unpublishedObjectCannotBeEnabled` 端到端验证（Agent 启用该 Skill → 闭包解析失败）。

## 4. 审计日志（§5.1 / §7.4 / 08 §7）

### 4.1 为什么不用 V1 的 `audit_record`

`audit_record` 的列是 `(action, resource_type, resource_id, detail JSONB)`，是**通用行为审计**；
08 §7 要求的是「runId / invocationId / authzDecision / execDecision / execStatus / reasonCode / fingerprint」
**四字段 + ledger**，且要求「四字段完整率 100%」「非笼统 DENY 占比 100%」。
用通用审计表承载四字段，只能靠 `detail` 里的约定 key 表达 —— 「完整率 100%」就变成了一条**无法用 SQL 断言**的约定。

故另立专表 `cap_decision_log`，用 **NOT NULL 从存储层强制完整率**。

### 4.2 天然脱敏（NFR-06）

`cap_decision_log` **只有** id、决策字段与上下文 id，**没有任何承载业务参数的列**。
「日志不含明文凭据与不必要的敏感参数」因此**不需要额外的过滤逻辑** —— 没有可泄漏的字段。
凭据材料更是在任何阶段都不入库（06 §5）。

### 4.3 审计写入点在 `CapExecutionFlow.invoke` 包装层

不改 7 处内部 `return`，而是在最外层包一层：invocationId ≡ 账本 operationId；
无 operationId 的拒绝用 `pending:<runId>:<toolName>` 稳定替代。

### 4.4 分级失败处置

| 情形 | 处置 | 理由 |
|---|---|---|
| 执行**未开始** | **fail-closed**，抛异常 | 审计写不进去就等于这次调用没有依据，不能放行 |
| 执行**已完成** | 只 ERROR 日志 + 计数，**不抛** | 把「已完成」变成「失败」会造成**重复副作用**（重试会再执行一次） |

## 6. 关键设计决策

### 6.1 当前指针用独立表，不编码进发布头

指针是**可变**的（每次发布改一行），发布头是**不可变**的历史。
把「当前」编码成发布头上的一列，就退化成可变标志（06 §3.2 明令禁止）。
`pointer_key` 用**单列主键**（`'PLATFORM'` / `'TENANT:<uuid>'`）而不是复合主键 ——
避免「按 `(scope, tenant_id)` 定位」在 `tenant_id` 为 NULL 时语义含糊（SQL 里 NULL 比较恒为 UNKNOWN）。

### 6.2 事务边界由端口持有，而不是应用层

应用层 `ConfigPublishService` 只**编排**（版本行 → 发布头 → CAS → 审计），
事务边界由 `ConfigPublishTransaction` 端口持有，基础设施实现用 `TransactionalConnectionHolder.inTransaction`。
这样保留「发布头插入与 CAS 之间」的**可测缝隙** —— PUB-2 用阻塞式 `ConfigPointerPort` 装饰器
**确定性地**制造「seq 分配序 ≠ 提交序」，而不是靠 sleep 碰运气。

### 6.3 「绝不以 max(seq) 选择当前版本」

`config_publish_seq` 的分配序 ≠ 提交序（PUB-2），且回滚发布保留原 release ——
按 seq 取最大可能选中**已回滚的**发布。`JdbcPublishedVersionPort` 只读指针，读不到就是读不到（fail-closed）。
P1 的过渡实现（取对象最新已发布版本行）**整体作废**。

### 6.4 发布命令携带**完整生效集合**

各类型的对象定义都随命令下发，`insert` 幂等；发布头的 `object_versions` 必须构成**自洽闭包**
（§6.4「缺失对象 → 发布校验失败」）。跨作用域引用不在同一集合内，不做同集合校验。

### 6.5 风险上限的覆盖关系**不在配置期拒**

「Skill 的 riskCeiling 低于其声明工具的风险」是**合法的收紧配置**（§5.6 运行期给 `RISK_EXCEEDS_CEILING`），
不是配置错误。若在配置期就拒，会把「声明得宽、限得严」这种常见且安全的写法堵死。
配置期只拒**未知 / 非法**的风险取值。

### 6.6 `PUBLISHED → DEPRECATED` 的放行范围被严格限定

必须「除 `lifecycle_state` / `updated_at` 外**内容一字未改**」才放行。
用 `to_jsonb` 差分实现，保证四张结构不同的表共用同一函数时依然精确
（直接比较业务列会导致 `cap_agent_def`（无 `id` 列）报错）。

### 6.7 审计写入点的选择

写在 `CapExecutionFlow.invoke` 包装层而不是 7 处内部 `return`：
改 7 处意味着漏一处就少一条审计，而**审计覆盖率 100% 是硬指标**。
包装层保证「每一次调用**恰好一条**审计」，invocationId ≡ 账本 operationId。
