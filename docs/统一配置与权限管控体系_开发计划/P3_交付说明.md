## 4. 关键设计决策（需 P4/P5 复核）

### 4.1 P3 另起 `cap_approval` 表，而非改既有 `approval` 表

既有 `approval` 表是「一次性消费」模型（消费即失效）；§5.3.3 的状态机是「PENDING → RESERVED → INTENT_SUBMITTED → CONSUMED」多阶段模型。两者的 PENDING 语义不同（P3 的 PENDING 是「已批准待预占」，旧表无对应态）、终态幂等语义相反（旧表重复消费报错，§5.3.3 要求幂等）。塞进一张表必然要在两套语义间做妥协，**改表比加表风险更高**。

### 4.2 审批查找键 = `(tenant_id, tool_id)`，逐候选校验绑定

工具的审批可能不止一条（不同有效期 / 不同范围）。流程按 `(tenant_id, tool_id)` 取候选集，**逐条校验绑定**：

1. **绑定校验先于状态校验** —— 绑定不符的候选根本不是「这条审批」，先看状态会把「绑定不符」误报成「已过期」；
2. **回落顺序：绑定不符 → 已过期 → 不存在**；
3. **非本主体的审批按「不存在」处理**（不算绑定不符）—— 主体不符时暴露「存在但不是你」等于泄露审批存在性。

### 4.3 `ArgsNormalizer` 取代 `InvocationDigest`

P2 的 `InvocationDigest` 与 §5.3.2 的 `args_norm_v1` 规则不等价（缺 NFC 规范化、缺十进制规范形式、缺 Schema default 展开、缺集合语义）。若审批绑定用一套算法、账本摘要用另一套，**「审批绑定的参数」与「实际执行的参数」会算出两个值，防重放就是摆设**。故合并为单一实现，三处同源同值。

### 4.4 范围定义采用可解析的 JSON 规范形式 + 带类型标签的值编码

- 行式文本在值含空格 / 换行时往返有歧义 → 改用 JSON；
- 裸数字会让 `1` / `1.0` / `1.00` 哈希不同 → 数值统一规范化；
- 但**统一写文本又丢失类型**：与 `Double` 实参比较会误判不等 → 因此值编码带类型标签（`{"t":"num","v":"1"}` / `{"t":"str","v":"x"}`）。

### 4.5 `ApprovalScope` 携带 effectfulParams + schemaDefaults + setValuedParams

授予侧（算 `effectiveArgsHash`）与消费侧（重验）必须用**同一份**规范化选项，否则两侧算出两个值 —— 这正是 §5.3.1「禁止因参数未出现在某条 paramPolicy 而默认允许其在复用时变化」要防的。

### 4.6 `CapExecutionFlow` 的 CAP 链移除 `ApprovalSource`

`cap_approval` 记录本身就是权威决定。若同时接受 `ApprovalSource`（外部传入的审批凭证），就出现**两个权威来源**，二者可能互相矛盾 —— 那是两个真相来源，不是冗余。移除后：**无记录即 fail-closed 拒绝**（等价或更强）。

### 4.7 14a 失败则**不落账**

§5.3 步骤 14a 明确「结果事件必须先落盘」。若结果未落盘却把账本记成 SUCCEEDED，运维看到 SUCCEEDED 便不会再去查 —— **账本撒谎比账本缺一条更危险**。故：

| 情形 | 账本 | 结局留存 | ledger |
|---|---|---|---|
| 结果事件已写 | POST 成功 | 结果事件 | `RECORDED` |
| 结果事件已写 | POST 失败 | 结果事件 | `RETRYING`（只重试落账） |
| 结果事件写失败 | — | 补偿任务已入队 | `RETRYING` |
| 结果事件写失败 | — | **补偿任务也落不下去** | 账本记 UNKNOWN 进对账 → `NEEDS_MANUAL` |

### 4.8 `ledgerStatus` 三分支

`posted` → `RECORDED`；`!posted` 但结局仍被持久化（事件已存在 **或** 补偿任务已入队）→ `RETRYING`；结局彻底丢失 → `NEEDS_MANUAL`。

### 4.9 14a 失败分支下预算按「结算」而非「释放」

工具确实成功，成本已发生 → 释放额度等于白送预算。（普通失败分支才释放，见步骤 14 的 `releaseQuietly`。）

### 4.10 审批消费失败不阻断落账

账本才是事实源。审批停在 `INTENT_SUBMITTED` 交由对账处置 —— 审批的终态不影响「副作用是否已发生」这一事实。

### 4.11 审批的 `authzVersion` 采用**精确匹配**

版本变化即视为绑定不符 → `APPROVAL_SCOPE_MISMATCH`（fail-closed 方向）。授权版本变了却仍按旧审批执行 = 撤权被绕过。
