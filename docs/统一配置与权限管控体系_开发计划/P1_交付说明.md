## 2. Phase A 判定链（§5.3 顺序）

```
步骤 2  PrincipalAuthorized   ── 版本（DB 强一致）→ 角色
步骤 3  PermissionResolver    ── 仅在步骤 2 通过后执行
步骤 4  AgentSkillAllowed → SkillToolAllowed → RiskWithinCeiling
步骤 5  MCPBindingAllowed     ── §5.8 四步顺序（仅 MCP）
步骤 6  ParamPolicyPassed     ── 强制安全 ∧ Tool 策略 ∧ Skill 策略
步骤 7  ConfigFingerprintValid
```

**顺序是契约，不是实现细节**（§5.3「本小节为全文档唯一顺序与语义」）。三条关键性质已被测试锁死：

1. **主体授权最先**：主体无权时**不解析闭包**（`InvocationValidatorTest.principalCheckHappensBeforeClosureResolution` 用计数型解析器断言解析次数为 0）—— 既不向无权主体暴露能力面，也避免为无权调用做无用功。
2. **主体授权内部，版本先于角色**：上下文版本落后于权威源时先报 `AUTHZ_STALE` 而非 `AUTHZ_ROLE_MISSING` —— 后者会把「撤权」误报成「角色不足」，让运维排查指向错误的配置。
3. **风险先于 MCP、参数策略先于指纹**：§4b/S4c 的原因码不会被指纹变化覆盖（§9.1 的场景逐条锁定）。

### 2.1 主体授权为什么不用 `AuthorizationService.isAuthorized`

既有 `RoleBasedAuthorizationService.isAuthorized` 把「版本陈旧」与「角色不足」压成同一个 `false`，无法映射 §5.7 的两个不同码；更严重的是它的版本判定读**进程内内存 Map**（缺省 `0L`），在「DB 已撤权、内存未同步」的实例上会**静默忽略撤权**。

故 P1 新增窄端口 `RolePermissionPort`（只回答角色问题），版本维度由 `InvocationValidator` 直接读 `AuthzVersionPort`（DB 强一致，§5.5）。角色矩阵本身**不重复定义**，直接复用 `RoleBasedAuthorizationService.permissionsOf`，避免两套矩阵各说各话。

## 3. 关键设计决策（需 P2/P4/P5 复核的 4 项）

### 3.1 原因码枚举一次性落地 §5.7 全表

计划写的是「Phase A 子集」，但 §5.7 标注「本表为对外稳定码权威源」且要求「变更须版本化并保持兼容策略」。**一次落地完整表**比 P2/P3 落地时再补枚举更符合该要求：码一旦对外出现即为契约，分批追加等于让已发布的行为码漂移。本枚举**不含任何判定逻辑**，多出来的常量不产生行为。

### 3.2 `PublishedVersionPort` 是 P1 过渡实现，P5 必须替换（**重要**）

§6.2 要求「当前 PUBLISHED release → `object_versions` → 解析 id→精确版本」，§6.3 要求「**当前版本不以 max(seq) 选择**」「只认**指针指向的** PUBLISHED release」。但 P0 建立的 `cap_config_release` 只有发布头与 `object_versions`，**没有「当前指针」这一实体**（指针的写侧 CAS 属 P5）。

P1 的 `JdbcPublishedVersionPort` 因此退化为**对象级解析**（取该对象最新已发布版本行），并加**回滚守卫**：一旦存在 `ROLLED_BACK` 的发布，一律解析失败（返回空）→ 上层 fail-closed。宁可「无人能授权」，也不可「解析到已回滚的版本」。

> ⚠️ **P5 上线前的强制约束**：在 P5 的指针读落地前，**CAP 授权链路不得在生产开启**。
> P2 接线时必须置于开关之后（与 P0 的双写开关同一治理思路）。

### 3.3 MCP 清单漂移的原因码归属（§5.8 的括号说明）

§5.8 步骤 3 给了 `MCP_TOOL_DRIFTED`，并注明「**若清单变更已纳入指纹导致步骤 1 失败，则统一为 `CONFIG_FINGERPRINT_STALE`；同一类变化不得两种码**」。

由于 §6.4 明确把「MCP 固定清单」纳入闭包指纹，P1 的实现是：**清单漂移先被步骤 1 的指纹校验捕获 → 统一报 `CONFIG_FINGERPRINT_STALE`**（`InvocationValidatorTest.mcpManifestDriftIsCaughtByFingerprint`）。

`MCP_TOOL_DRIFTED` 仍被实现为 §5.8 步骤 3 的**兜底防线**，覆盖「清单在指纹重算与操作级复核之间发生变化」的 TOCTOU 窗口（`InvocationValidatorTest.mcpManifestToctouDriftIsDenied` 用会变化的清单替身复现该窗口）。

> 📌 **待 P4 复核**：P4 落地 MCP 适配器后，若出现「清单变化不体现在指纹」的场景，步骤 3 即成为唯一出口。

### 3.4 `CapabilityRiskLevel` 与既有 `ToolRiskLevel` 并存

既有 `core.config.ToolRiskLevel` 是**旧平台**的工具风险登记取值域，其 `resolve()` 对未登记工具**降级为最严格的 `WRITE_EXTERNAL`**（服务于旧审批策略的「宁可多审批」）。而 §5.7 为「风险未知」单列了 `RISK_LEVEL_UNKNOWN`，P1 的退出门禁又明确要求「未知风险拒绝且**不降级**为 WRITE_EXTERNAL」。

若沿用旧枚举，「未知」就无法与「超限」区分——处置不同（前者是**配置缺陷**须修配置，后者是**策略边界**属正常拒绝）。故新建独立枚举，`UNKNOWN` 是**不可判定**而非「最严格」，并**不修改**既有枚举，避免波及旧审批链路。

## 4. 技术说明：两个值得记住的坑

### 4.1 JSpecify 的 `@NonNull` 不能用在限定名类型上

Java 规定：限定名 `Outer.Inner` 中的注解作用于**外层** `Outer`，而非 `Inner`。于是 `@NonNull Outer.Inner x` 编译失败（`无法使用 type-use 批注来批注确定作用域结构`），正确写法是 `Outer.@NonNull Inner x`。

本仓库既有写法即此模式（如 `ExecutionIntent.@NonNull IntentState`）。P1 沿用之，并把**跨类共享**的枚举（`CapToolKind`、`McpTrustTier`）提升为顶层类型 —— 否则 `EffectiveClosure` 里 `@NonNull CapToolDef.Kind kind` 无法编译。

### 4.2 Jackson 3 用 `properties()`，没有 `propertyNames()`

`ClosureFingerprint` 的规范化需要按键排序；Jackson 3 的 `JsonNode` 提供 `properties()`（`Map.Entry` 集合），`propertyNames()` 已移除。

## 6. 顺带修复的既有缺陷

| 缺陷 | 性质 | 处置 |
|---|---|---|
| `CapabilityRiskLevel.stricter` 取了**更宽松**的上限（`a.rank >= b.rank`） | **P1 自身缺陷**，开发期被 `CapabilityRiskLevelTest` 捕获 | 已修正为 `a.rank <= b.rank`（上限约束的是「允许的最大风险」，故**等级更低者更严格**）。测试同时断言「覆盖只能收紧、不能放宽」 |
| `ParamPolicyEngine` 对 `in_allowlist` 的非数组 value / `lte` 的非数值 value **在求值期才报错** | **P1 自身缺陷** | 已前移到**解析期**（配置期拒，§4.3）。否则「本次调用恰好不涉及该参数」的路径会绕过校验，让非法配置长期潜伏 |
| `InvocationValidator` 依赖 `AuthorizationService.isAuthorized` 的版本判定 | **P1 设计缺陷**（会导致撤权被静默忽略） | 改为独立读 `AuthzVersionPort`（DB 强一致）+ 窄端口 `RolePermissionPort` 只答角色 |

> 以上三项均为 P1 开发过程中自测捕获，**不涉及既有生产代码的回归**。

## 7. P2 交接清单

1. **接线位置**：`InvocationValidator` 目前**未接入任何执行路径**（Bean 已就绪）。P2 按 §5.3 步骤 2–7 把它接进 `ToolInvocationGate`，且**必须置于开关之后**（决策 3.2 的强制约束）。
2. **发布指针读**：`PublishedVersionPort` 的指针读实现属 P5。P2 若要开闸，需先确认 P5 的发布流程已落地。
3. **决策日志**：§5.3 步骤 7 要求「失败 → 写决策日志」。P1 只产出决策值对象，**不写日志**（审计 100% 属 P5 的账本/审计链路）。
4. **MCP 适配器**：`McpManifestPort` 当前是 fail-closed 占位（空集 → MCP 一律不可调用）。真实采集属 P4。
5. **审批/预算/账本**：Phase B（步骤 8–15）属 P3，P1 未触及。
6. **快照双写已启用**：`CapDualWriteService.onExecutionSnapshotCreated` 现在会真实写 `execution_capability_snapshot`（含真实 §6.4 指纹与 `authz_version`）。但生产库中 `cap_skill_def` / `cap_tool_def` **尚无数据**（P5 的发布流程才写入），故闭包不可解析时会**跳过并计数**（`deferredSnapshotCount`），**不写占位闭包**（沿用 P0 决策 3.3）。
7. **存量回填**：`cap_agent_def.config_fingerprint` 仍是 P0 的 `pending_v1:` 占位值。**它不是 §6.4 的闭包指纹**（那是按对象的内容摘要，§6.4 未定义该口径），且已发布行被 `forbid_published_def_mutation()` 触发器封禁 UPDATE —— 故其重算属 **P5 发布流程**的职责（P5 发新版本行时写入真实指纹），不是 P1 能就地完成的。
