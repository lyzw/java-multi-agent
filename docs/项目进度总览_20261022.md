### 3.3 🔴 IT 工具链只能在「本地 trust 认证库」上跑（全仓 14 处，已修）

`FaultInjectionSupport.adminPool()` 等**管理员池**只设用户名、**从不设口令**——
因为本机 Docker PG 是 trust 免密，换到任何口令认证的库（RDS / 任何 CI）就必然连不上：

```

```

实测后果：`ConfigChangeRepositoryIT` 等 **18 个 IT 类全部无法启动**（不只是 D16 的用例）。
项目自带的 `V__manage_app_role.sql` 文档里写了角色规范，**但没有任何一处代码读 `IT_PG_ADMIN_PASSWORD`**。

**处置**：14 处管理员连接统一补 `IT_PG_ADMIN_PASSWORD`（有则用、无则保持 trust 行为，本地开发不受影响）。

### 3.4 🔴 `RetentionErasureIT` 依赖别的 IT 留下的夹具（换新库必失败）

它直接向 `t-b` 取快照，而 `V1_seed.sql` **只为 t-a 建了快照**；
旧实现靠「前面某个 IT 跑过并留下数据」——而那些 IT 按纪律在 `@AfterAll` 自清理，
于是：**干净库上必红，脏库上靠执行顺序侥幸绿**（假绿）。
**处置**：本类 `setUp` 自己调 `ensureTenantSnapshot`（幂等）补齐两个租户。修复后 N-1~N-7 共 20 项全绿。

### 3.5 🟠 `RateLimitIT` 双抖动：窗口边界（本轮实测复现 2 次，已修）

`JdbcRateLimiter` 的 `window_start = floor(epoch/W)*W`，**每 W 秒一个硬边界**：

| 用例 | 原配置 | 失败实测 |
|---|---|---|
| T-3 并发不超发 | W=60s | `expected: 24 but was: 0`（跨边界后 `currentCount` 去看下一个窗口） |
| T-9 新窗口重置 | W=1s | `expected: REJECTED but was: ALLOWED`（两次 check 跨秒，落进不同窗口） |

> 原注释「窗口取 60 秒：足够长，测试不会因跨窗口而抖动」是**错的推理**：
> 跨边界概率 = 用例时长 / W，**W 越大越稳**。

**处置**：W=60s→3600s；T-9 改为**锚定到整秒边界后 100ms** 再发请求。
**复验**：连跑 4 轮 `RateLimitIT` 均 **9/9 全绿**（修复前约每 2 轮抖 1 次）。

### 3.6 🔴 配置写入：`agent.approval.ttl` **没有基线，收紧判定形同虚设**（真产品缺陷）

实测：`PUT agent.approval.ttl = 10m` 成功后，再写 `30m`（放宽）返回 **200 OK**——预期 409。

| 环节 | 事实 |
|---|---|
| yml | `agent.approval.ttl: 15m` **确实有声明** |
| `ConfigReadService.Spec` | 该键 `effective=false`，自注「⛔ 实测：无任何读取点」 |
| `declaredValues()` | **只收 `effective=true` 的键** |
| `EffectiveConfigResolver` | **只遍历 `declaredValues()`** → 该键无基线、无生效值 |
| 收紧校验 | `currentValue == null` → **方向无从判定 → 放行** |
| 表现 | GET 返回 `effectiveValue: null`；写了等于没写（正是 D15-B3「看起来生效了其实没生效」的形态） |

**更深一层的设计缺口**：`ConfigOverridePort.TIERS` 里**所有带数值基线的键（max-steps / max-cost /
rate-limit / retention…）全部是 `L3_HIGH`**，直写会先被审批门禁拦下，**根本走不到收紧校验**；
仅有的两个 L2 可直写键（`approval.ttl`、`approval.required-by-risk`）中，前者未接线、无基线。
即：**「只能收紧」这条契约目前只能通过审批矩阵棘轮被真正验证**。

**处置**：
- `writeThenRead` 改用**已接线 + L2 + 有基线**的 `agent.approval.required-by-risk`（并加反向断言：`effectiveValue` 不得回落到 yml 基线）；
- 原「放宽上限 → 409」用例改为断言**真实存在**的那条保证：`agent.run.max-steps`（L3）直写 → **409 `CONFIG_APPROVAL_REQUIRED`**，且**不得落库**；
- ⏔ **待你决策的产品问题**：`approval.ttl` 目前「可写但无效果」。二选一：
  **(a)** 从 `WRITABLE` 中移除（fail-closed，不给无效旋钮）；**(b)** 把它接入运行时（审批过期判定）。
  我没有替你改产品行为。

> 这三处缺陷**全都藏在专门为拆穿假绿而写的脚本里**。

（实测无库场景：未锚定 **366** vs 真实 **180**）。`ran` 是锚定的（正确）——
一段脚本里两种口径混用，报出来的数是假的。

**处置与复验**（全部以实跑日志为据）：
- 两处构建步骤加 `set -o pipefail`；
- 4 个需库的装配测试类按项目既有约定加 `@EnabledIfEnvironmentVariable(IT_PG_URL)`
  → 无库**跳过**、integration job（有库）**真跑**并纳入 skipped==0 断言；
- integration job 命令加 `-Dit.test='*IT,!RealBrokerEndToEndIT'`（**CI 未覆盖 broker IT**，写进注释与台账，不假装覆盖）；
- `skipped` 与 `ran` 统一锚定口径；
- unit job 增设断言（失败/错误为 0、执行数 ≥ 480、跳过 ≤ 60）。

> **验证方式不是「我读了一遍 YAML」**：用 YAML 解析器**把 ci.yml 里的步骤脚本抽出来原样执行**，
> 避免「我抄的脚本 ≠ 文件里的脚本」这一新失效形态。
> - unit job 等价执行 → `执行 507 项 / 失败 0 / 错误 0 / 跳过 21` ✅
> - integration job 等价执行 → `执行 781 项 / 失败 0 / 错误 0 / 跳过 0` ✅
> - **反证 3/3 全部按预期报警**：① 构建失败 → 退出码 1；② 无库日志 → 断言失败退出 1；③ 截断日志 → 低于基线退出 1。

**CI 的建库/迁移/种子/授权步骤：本地逐字复刻通过**
用 `docker exec` 在容器内逐字执行 ci.yml 的 psql 命令（含 `sort -t_ -k1.2 -n` 数值序迁移循环）：
V1→V12 按序 ✅ → 种子 ✅ → 建 `app_agent`（NOSUPERUSER/NOBYPASSRLS）✅ → 授权 ✅ →

### 7.1 本轮新增：本地复现「CI 两个 job」的等价命令（2026-10-22 实测跑通）

```bash
# ── 0. 恢复 Docker（守护进程无响应时：Docker 进程在 ≠ 守护进程活着）──
#    症状：docker ps 报 500 / 无输出；5433 端口能连但 PG 握手挂起

cd platform && mvn -B clean package

# ── 2. integration-test job 等价（有库）→ 应 BUILD SUCCESS，断言 781 项 / 0 跳过 ──
export IT_PG_URL='jdbc:postgresql://127.0.0.1:5433/agent_ci'
export IT_PG_USER=app_agent IT_PG_PASSWORD=ci_app_not_a_secret
export IT_PG_ADMIN_USER=postgres IT_PG_ADMIN_PASSWORD=ci_only_not_a_secret
mvn -B clean verify -Dit.test='*IT,!RealBrokerEndToEndIT' -Dfailsafe.failIfNoSpecifiedTests=false

# ── 3. broker IT（需真实 RabbitMQ，CI 目前不覆盖）→ 3/3 绿 ──
export RABBITMQ_HOST=127.0.0.1 RABBITMQ_PORT=5672 \
       RABBITMQ_USER=agent RABBITMQ_PASSWORD=agent_dev_pw RABBITMQ_VHOST=agent
mvn -B verify -pl agent-infrastructure -Dtest='NoSuchUnitTest' \
    -Dsurefire.failIfNoSpecifiedTests=false \
    -Dit.test='RealBrokerEndToEndIT' -Dfailsafe.failIfNoSpecifiedTests=false

# ── 4. 断言脚本必须从 ci.yml 里「抽出来跑」，不要手抄 ──
python3 - <<'PY'
import yaml, pathlib
d = yaml.safe_load(open(".github/workflows/ci.yml"))
want = {"断言单元测试真实执行": "unit-assert",
        "断言集成测试确实执行（跳过数必须为 0）": "it-assert"}
for job in d["jobs"].values():
    for s in job.get("steps", []):
        if s.get("name") in want:
            pathlib.Path(f"/tmp/{want[s['name']]}.sh").write_text(s["run"])
PY
bash /tmp/unit-assert.sh && bash /tmp/it-assert.sh
```

> ⚠️ **不要用 `-q`**：`mvn -q` 会吞掉 `Tests run` 汇总行，grep 永不匹配 ——
> 这正是本项目记为 F-14 的失效形态（实测复现了一次）。
> ⚠️ **不要用超级用户跑 IT**：超级用户与 `BYPASSRLS` 角色会绕过全部 RLS 策略，
> `FORCE ROW LEVEL SECURITY` 也拦不住，会得到「隔离失效/隔离生效」的**反向**虚假结论。
> ⚠️ **`V1_seed.sql` 必须由管理角色执行**：以非特权角色跑会被 RLS 拒绝
> （`new row violates row-level security policy`）——种子层与测试层必须分层。
> ⚠️ **CI 的 `mvn | tee` 步骤必须带 `set -o pipefail`**：默认 shell 无 pipefail 时，
> `tee` 会把构建失败的退出码吞成 0 → **失败报绿**（本轮实测，见 §3.9）。
