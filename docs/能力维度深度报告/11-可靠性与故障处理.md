## 一、维度定义与评估坐标系

### 1.1 这个维度到底解决什么问题

一句话：**失败是常态，问题不是「如何不失败」，而是「失败之后系统是否还在说真话」。**

绝大多数工程团队把「可靠性」理解为可用性（多副本、多活、重试）。但对一个 agent 平台而言，最难的不是让 Run 跑完，而是**在跑不完的时候，让所有相关方对「发生了什么」达成一致**：

- 调用方要知道：**该重试还是该放弃**。重试一个 403 打到天亮也不会有不同结果；不重试一个 503 则白白丢一次本可成功的请求。
- 运维要知道：**这次的故障会不会自己结束**。一个「重试窗口 < 故障持续时长」的设计，会让故障从局部过载升级为 metastable state（见 T3），此时系统**不会自愈**，只能靠外部强推。
- 账务要知道：**钱到底花了没有**。UNKNOWN 的语义是「可能花了」，把它当「没花」释放额度，账就再也对不上。
- 合规要知道：**记录是否就是事实**。一条「执行中」的日志掩盖了一个早已死掉的事务，比没有日志更危险——因为它让排查方向从「查哪里坏了」变成「查为什么没坏」。

因此本维度的核心命题可以拆成三个子命题，后一个比前一个更难：

1. **分类**：失败能否被归入「可重试 / 不可重试 / 不知道」三类，且分类**不依赖调用点的临场判断**。
2. **收敛**：每一次失败都必须在有限时间内到达一个**终态**（成功、失败、取消、挂起、待对账），不允许停留在「看起来还在跑」。
3. **保真**：终态的**名称**必须等于事实。不允许「事务回滚了但接口返回 201」「超时了但库里写着 FAILED 而事件写着 TIMED_OUT」「被拒了但日志写着已被接管」。

本项目在这三件事上的形态非常鲜明，也用一句话概括：**分类弱、收敛强、保真极强**。

- **分类弱**：错误分类只存在于模型调用一侧（`ModelErrorKind` 六值，`ModelGateway.java:29-52`），工具侧、RAG 侧、DB 侧没有同等粒度的分类；也没有任何跨依赖的熔断/舱壁。
- **收敛强**：DB 状态机 + 租约 + fencing + 崩溃恢复扫描器 + 有限重试 + 死信，五道机制保证「不会有 Run 永远 RUNNING」（`RunRecoverySweeper.java:19-50`）。
- **保真极强**：POISONED 事务把「静默回滚 + 假 201」这类最危险的失真按死在提交点（`TransactionalConnectionHolder.java:170-186`）；UNKNOWN 处置端点**明文禁止提供重试**（`UnknownOperationController.java:26-32`）；前端把「HTTP 错误 → 是否给重试按钮」收敛到单一函数（`errorGuidance.ts:37-95`）。

### 1.2 能力分层的四档模型

本维度不适合用「有没有重试」分层——所有框架都有重试。更有区分度的分层轴是：**失败是否被分类 → 重试是否有界且退避 → 失败是否必然收敛 → 语义是否被结构强制保真**。

| 档位 | 名称 | 判定特征 | 典型表现 |
|---|---|---|---|
| **L0 无** | 异常冒泡 / 静默吞异常 | 无分类、无重试、无终态；异常决定命运 | 脚本式 agent demo；`except: pass` |
| **L1 应用层重试** | try/catch + 固定次数重试 | 有重试但**不区分错误类型**；无退避或固定 sleep；重试是否安全靠人记得 | 大量业务代码里的 `for i in range(3): try: ...` |
| **L2 分类 + 退避 + 有界 + 死信** | 错误分类学 + 指数退避 + 上限 + DLQ | 重试有界；坏消息能落地；但**终态语义靠约定**，应用层写错就失真 | 竞品主流档位（LangGraph `RetryPolicy`、OpenAI `ModelRetrySettings`、ADK `HttpRetryOptions`） |
| **L3 结构强制保真** | DB 状态机 / 事务毒化 / 幂等记录 / 终态不可伪装 | 应用崩了不变量仍在；「假装成功」在结构上不可能 | 本项目：触发器 + POISONED + fencing + UNKNOWN 禁重放 |
| **L4 引擎原生一等公民** | 失败预算 + 熔断 + 舱壁 + 常驻混沌实验 + 错误契约机器可校验 | 重试被当作**全局资源**分配；错误码是**契约**而非字符串；故障注入是 CI 常规项 | 目前**无一家 agent 框架完整达到**；AWS/Google 的成熟服务在「重试预算 + 熔断」上接近，但错误契约与 chaos 常驻仍未普及 |

**本项目必须分项判定，不给总分**：

| 子能力 | 档位 | 依据 |
|---|---|---|
| 终态收敛 | **L3** | 状态机触发器（`01_platform_ddl.sql:453-475`）+ 租约 + fencing + 恢复扫描器（`RunRecoverySweeper.java:172`，30s） |
| 语义保真（事务侧） | **L3+** | POISONED 标记在顶层提交前拒绝提交（`TransactionalConnectionHolder.java:170-179`） |
| 语义保真（API/前端侧） | **L2.5** | `errorGuidance` 已是单一真相源，但 **SSE 轮询器未接入**（`eventStream.ts:205-223` 只认 401） |
| 错误分类 | **L2** | 仅模型侧有 `ModelErrorKind`；工具/RAG/DB 侧靠异常类型与字符串 |
| 重试治理 | **L1.5** | 有指数退避与上限（`PgQueueListener.java:317-322`），**无抖动、无全局重试预算**；Rabbit 通道 `nack(requeue=true)` 无退避 |
| 熔断 / 舱壁 | **L0** | 全仓无 resilience4j / spring-retry / circuitbreaker 依赖（§4.3 证据 E-21） |
| 死信可运维性 | **L1** | 表存在且写入同事务（`PgQueueRepository.java:270-285`），但**只进不出、无 API、无告警**（DDL 注释 `:1399`「只进不出，须人工介入」） |
| 故障注入可验证性 | **L1** | 有反向守卫单测（如 `TransactionBoundaryIT.java:238`），但无系统化故障注入清单 |

| 轴 | 观测什么 | 怎么观测（本项目可采集的信号） |
|---|---|---|

**上游**：维度 3（租约/fencing/幂等是重试安全性的前提）、维度 5（`tool_operation` 三态是「副作用是否发生」的唯一事实）、维度 9（预算预留失败是重要的失败源）、维度 7（权限失败是最容易被伪装成临时故障的一类）、维度 8（跨进程调用的超时与降级）。
**下游**：维度 10（所有失败必须变成可告警信号，否则等于没有）、维度 4（客户端收到什么错误决定它是否继续轮询）、维度 13（挂起与失败的边界）、维度 12（重试与并发度共同决定部署容量）。

**一句话**：本维度不生产业务价值，它是其他维度的**减震器**——减震器失效时，最先坏的不是功能，而是**对故障的解释**。

## 二、理论体系（必须引用真实出处）

> 以下理论均给出真实出处。论文给会议/年份/DOI；规范给 URL；书籍给出版社与年份。凡本环境抓取失败者，**显式降级标注**，不臆测原文。

### 2.1 核心理论 / 概念框架（9 个）

**T1 · 失败分类学：transient / permanent / unknown**

- 出处：Marc Brooker，**"Timeouts, Retries, and Backoff with Jitter"**，Amazon Builders' Library（<https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/>）。原文要点（本环境抓取成功）：瞬时失败不可避免；超时保证系统不会无限悬挂；**重试只应在观察到依赖健康时进行**，「当重试不能提高可用性时就停止重试」。
- 核心命题：三类失败的**正确动作完全不同**——transient 值得退避重试；permanent（参数错、鉴权错、内容被拦）重试是纯浪费且会放大负载；unknown（请求已发出、响应丢失）**既不能重试也不能当失败**，只能对账。第三类最容易被工程实践忽略，因为它既不像「成功」也不像「失败」。
- **对本项目的映射**：本项目的 `ModelErrorKind` 恰好实现了前两类（`TIMEOUT/RATE_LIMITED/PROVIDER_ERROR` = transient，`INVALID_REQUEST/UNAUTHORIZED/CONTENT_BLOCKED` = permanent，`ModelGateway.java:31-41`）；第三类被提升到了**数据模型层**：`tool_operation.state=UNKNOWN`（DDL `:2990`）+ 专表 `agent_message_dead_letter`。这是本报告认为本项目最值得肯定的一处理论落地——**把 unknown 从「异常的一种」提升为「状态的一种」**。

**T2 · 指数退避 + 抖动（Exponential Backoff and Jitter）**

- 出处：Marc Brooker，**"Exponential Backoff And Jitter"**，AWS Architecture Blog，2015-03-04（<https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/>）。该文以 OCC 争用模拟证明：**无抖动的指数退避是明确的输家**——不仅工作量更大，耗时也更长；并给出三种抖动算法：**Full Jitter** `sleep = random(0, min(cap, base·2^n))`、**Equal Jitter** `temp/2 + random(0, temp/2)`、**Decorrelated Jitter** `min(cap, random(base, prev·3))`。文中结论：抖动方案相对无抖动方案，**工作量减半以上**，而实现复杂度回报极高，「应被视为远程客户端的标准做法」。
- **对本项目的映射**：本项目实现了 `base × 2^(n-1)` 并以 `max` 封顶（`PgQueueListener.java:318-322`），**但没有抖动**。这不是「没想到」，而是配置注释里明确写了「指数退避：base × 2^(n-1)」（yml `:485`）——说明作者知道指数退避、但跳过了抖动这一步。见改进点 1。

**T3 · Metastable failure 与 retry amplification**

- 出处：Nathan Bronson, Abutalib Aghayev, Aleksey Charapko, Timothy Zhu，**"Metastable Failures in Distributed Systems"**，HotOS '21（ACM Workshop on Hot Topics in Operating Systems），2021，第 221-227 页，DOI `10.1145/3458336.3465286`，PDF：<https://sigops.org/s/conferences/hotos/2021/papers/hotos21-s11-bronson.pdf>。
- 核心命题（已核对摘要原文）：metastable failure 是「**触发器移除后系统仍停留在坏状态**」的失败模式；坏状态中 goodput 异常低，且存在**sustaining effect（维持效应）**——通常是 **work amplification（工作放大）** 或整体效率下降；离开该状态需要「强纠正推力」（重启、大幅降载）。论文明确指出这类故障的根因**常常是提升效率或可靠性的特性本身**（典型：重试、缓存、自动扩缩）。
- 与重试的关系：重试是最经典的 work amplification。1 次逻辑请求失败 → N 次物理请求；当依赖已在过载边缘，重试把「局部慢」变成「全局塌」，而**触发器（最初的那次抖动）早就消失了**——这就是为什么「等一会儿自己就好了」不成立。
- **对本项目的映射（本报告最重要的判断之一）**：本项目**没有全局重试预算**，也没有熔断，因此具备 metastable failure 的**两个必要成分**：work amplification（重试）× 无抑制机制（无 breaker、无 budget）。唯一的部分抑制是背压控制器（`BackpressureController.java:13-33`，滞回 + 探测失败按超限处理），但它作用于 **outbox 发布侧**（队列深度），不作用于**消费侧的重试速率**。因此结论是：**本项目的重试有界（次数），但无速率上限（rate）**，在有界次数内仍可形成同步重试波。见改进点 1、2。

**T4 · 熔断器 / 舱壁 / 超时**

- 出处：Michael T. Nygard，**《Release It! Design and Deploy Production-Ready Software》**，2nd Edition，Pragmatic Bookshelf，2018（ISBN 978-1-68050-239-8）。Circuit Breaker / Bulkhead / Timeout / Steady State / Handshaking 等稳定性模式均出自此书（第 5 章 "Stability Patterns"）。补充公开参考：Azure Architecture Center 的 Circuit Breaker 与 Bulkhead 模式页（<https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker>、<https://learn.microsoft.com/en-us/azure/architecture/patterns/bulkhead>）。
- 三个模式的分工（本报告归纳，非原文引用）：**超时**回答「等多久算失败」；**熔断**回答「已知对方坏了，还要不要发」——它把「重试的决策权」从调用点收回到一个共享状态机；**舱壁**回答「一个依赖坏了，会不会拖垮其他依赖」——按依赖/租户划分资源池，使故障域有界。
- **对本项目的映射**：本项目**只有超时，没有熔断与舱壁**。超时做得相当细致（见 D-7：抢占式 `Future.get(剩余时间)`，`:1511-1557`），但缺少「已知模型供应商挂了，还要不要继续发」的判断——一旦供应商全面 5xx，现有设计会让每个 Run 都走完 `RETRYABLE_FAILURE` 的完整重试链，这正是 T3 描述的放大路径。

**T5 · 死信队列 / poison message**

- 出处：AWS 官方文档 **Amazon SQS Dead-Letter Queues**（<https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html>）；RabbitMQ 官方 **Dead Lettering**（<https://www.rabbitmq.com/docs/dlx>，其中 `x-delivery-limit` 用于 quorum queue 的投递次数上限）。
- 核心命题：DLQ 的价值不在「存起来」，而在**切断「坏消息无限重投」这个循环**——poison message 的判别特征就是「重投 N 次结果相同」。DLQ 的语义必须是「已停止自动处理，等待人」。
- **对本项目的映射**：两条通道都落地了投递上限（Rabbit `delivery-limit=3`，yml `:414`；DB 队列 `max-attempts=3`，yml `:479`），且**解析失败/载荷不安全的消息直接进死信而不消耗重试次数**（`PgQueueListener.java:249-258`、`RabbitExecutionListener.java:109-115`）——这一条与本理论的建议完全一致（坏消息重投多少次都一样）。但 DLQ 的「等人工」这半句没有落地：无查询 API、无重放端点、无告警（§4.5-b）。

**T6 · Fail-closed vs fail-open**

- 出处：OWASP Cheat Sheet Series，**Error Handling Cheat Sheet**（<https://cheatsheetseries.owasp.org/cheatsheets/Error_Handling_Cheat_Sheet.html>）。已核对原文要点：应用应「尽量穷举所有失败模式」，5xx **只用于表示无法完成的请求**，且**不得在响应体中泄露实现细节**；应使用 4xx 表示客户端侧错误、5xx 表示服务端非预期错误；**5xx 必须被监控**，因为它是「对某类输入持续失败」的良好指标。
- 补充原则：fail-closed（拒绝优先）与 fail-open（放行优先）的选择本质是**安全性与可用性的不对称定价**——鉴权、预算、内容安全应 fail-closed（错误代价 > 不可用代价）；只读查询、缓存、推荐位可以 fail-open。
- **对本项目的映射**：本项目把 fail-closed 写成了**项目铁律第 8 条**，并在五处落地：授权读不到=拒绝、审批源未接入=一律拒（`ToolInvocationGate.java:202-209`）、预算预留失败=拒绝（`:40-48`）、输出命中毒性=阻断、背压探测失败=停发（`BackpressureController.java:25-27`）。这是理论—纪律—代码三层一致的少见案例。

**T7 · 混沌工程**

- 出处：**Principles of Chaos Engineering**（<https://principlesofchaos.org/>，最后更新 2019-03）。已核对原文：定义「稳态」（steady state）→ 假设对照组与实验组稳态相同 → **引入真实世界变量**（服务器宕机、硬盘故障、网络断开）→ **试图证伪假设**。五条进阶原则中与本维度最相关的是 **Minimize Blast Radius**（最小化爆炸半径）与 **Run Experiments in Production**（在生产上实验，因为环境的流量模式无法在预发复现）。文中明确提到要寻找的系统性弱点包括「服务不可用时的错误 fallback 设置」「**不当超时配置引发的重试风暴**」「单点故障引发的级联失败」——三条里两条属于本维度。
- **对本项目的映射**：本项目**没有混沌工程实践**，但有它的「穷亲戚」：反向守卫单测（撤掉修复点必红的用例，如 `TransactionBoundaryIT.java:238-239`）与项目铁律 6「守卫必问『撤掉修复点会红吗』」。这是同一思想在单测粒度的落地——**用「证伪」而不是「验证」来获得信心**。改进点 5、7 是把这条思路从单测提升到系统级。

**T8 · 错误语义保真：HTTP 语义与机器可读错误**

- 出处：**RFC 9110 — HTTP Semantics**（IETF，2022-06，<https://www.rfc-editor.org/rfc/rfc9110>）：§9.2.2 定义幂等方法，§10.2.3 定义 `Retry-After`，§15 定义状态码语义。**RFC 9457 — Problem Details for HTTP APIs**（IETF，2023-07，<https://www.rfc-editor.org/rfc/rfc9457>）：定义 `type/title/status/detail/instance` 的机器可读错误体。**RFC 6585**（<https://www.rfc-editor.org/rfc/rfc6585>）§4 定义 429。
- 核心命题：HTTP 状态码是**契约**而非标签。把 403 报成 5xx，等于告诉客户端「稍后可能成功」——而这句谎言的代价是**无限重试**；把 404 报成 500，等于让客户端永远不知道「这个东西根本不存在」。OWASP 的同一段（T6）从安全侧给出了对称理由：4xx/5xx 的区分是**语义正确性**问题，不只是分类学问题。
- **对本项目的映射**：本项目在「反探测」与「语义终态」之间做了一个很讲究的取舍：**对「不存在」与「无权访问」统一返回 404**（`RunEventController.java:215-229`、`ResultController.java:82-96`，注释明写「区分即提供存在性探测通道」），然后在前端把 404/403/401 一律定为**终态、不给重试**（`errorGuidance.ts:44-75`）。这是一个正确的组合——**用 404 承担 403 的信息隐藏职能，再用客户端的「404 是终态」规则保证不无限重试**。代价是运维侧无法从状态码区分「越权探测」与「真的没有」，只能靠 `authz_decision_log`（维度 7/10）。

**T9 · 幂等与 at-least-once 的交互**

- 出处：Pat Helland，**"Idempotence Is Not a Medical Condition"**，ACM Queue，2012（<https://queue.acm.org/detail.cfm?id=2187821>）；工程侧权威表述见 AWS Builders' Library 的 T1 一文（同源：重试必须与幂等一起讨论）。
- 核心命题：at-least-once 投递 + 非幂等副作用 = 重复副作用；**重试的安全性不是重试机制自身的属性，而是下游幂等性的属性**。因此「能不能重试」这个问题的正确答案永远是「取决于这个动作是否幂等」，而不是「取决于这次错误是否 5xx」。
- **对本项目的映射**：这是本项目与其他框架最根本的分歧点（§5.4 分歧 3）。本项目把「是否幂等」前移到了**工具定义**（`cap_tool_def.risk_level NOT NULL`）与**操作账本**（`tool_operation.idempotency_key`），因此可以在 `UNKNOWN` 时**一律禁止重放**，而不需要判断具体工具——因为「可能已发生」这个事实与工具是什么无关。竞品则普遍把这件事交给使用者的 `retry_on` 谓词或文档警告。

### 2.2 理论给出的「设计张力」清单

| # | 张力 | A 方案 | B 方案 | 本项目的选择与代价 |
|---|---|---|---|---|
| K-1 | **重试 vs 放大** | 多试几次提高单请求成功率 | 少试以免拖垮依赖 | 选 B 的中庸版：次数有界（3），但**无速率上限、无抖动**，放大风险仍在 |
| K-2 | **快速失败 vs 完成优先** | 一遇错就终态，用户立刻得到确定答案 | 尽量重试，用户多等但可能成功 | 按错误类型分流（`ModelErrorKind.retryable()`），但**分流粒度只到「模型侧」** |
| K-3 | **语义精确 vs 信息隐藏** | 403/404 分开报，便于排障 | 统一 404 防探测 | 选 B（统一 404）+ 前端把 404 定义为终态；**代价是运维可观测性下降** |
| K-4 | **终态严格 vs 可恢复** | 终态不可迁出，保证账实一致 | 允许重开，提高最终成功率 | 选 A（触发器强制），代价是「错了就只能新建 Run」 |
| K-5 | **UNKNOWN 保守 vs 激进** | 不重放、转人工（保证不重复副作用） | 重放一次（保证吞吐） | 选 A，且用 DB 触发器堵死（`forbid_attempt_after_terminal` `:531-536`）；**代价是人工队列会积压** |
| K-6 | **分类集中 vs 就地判断** | 一处定义错误枚举，全局复用 | 每个调用点自行判断 | 现状是「半个 A」：模型侧集中，其余就地；这是语义失真的结构性土壤 |
| K-7 | **重试在哪一层** | 只在最外层（业务层）重试，内层不重试 | 每层都重试（各层自保） | 选 B 的隐式版本：MQ 层 + Worker 层都会「重试」，需要靠语义对齐才不冲突（见 §4.2 D-4 与 §5.3 劣势 2） |
| K-8 | **失败是否要「有主」** | 失败必须指派到人/角色（DLQ 有 owner） | 失败只记录，不指派 | 现状是 B：死信无 owner、无 SLA、无告警 |

### 2.3 业界公认的反模式清单及判别方式

| # | 反模式 | 为什么错 | 判别方式（本项目可用的检查） |
|---|---|---|---|
| A-1 | **catch-all 后 fail-soft 继续执行**（吞异常当降级） | 在事务内等于制造「静默回滚」；在事务外等于制造「假成功」 | 搜 `catch (SQLException` 后不 rethrow 的分支；本项目用 POISONED 反向堵死（`:152-162`） |
| A-2 | **无抖动的同步重试** | 所有客户端在同一时刻重试，形成尖峰（T2、T3） | 检查退避函数是否含随机项：`backoffFor`（`PgQueueListener.java:317-322`）**无随机项** → 命中 |
| A-3 | **重试不可重试的错误**（401/403/400/422） | 结果不会变，纯放大负载；且掩盖真实问题 | 检查错误分类是否覆盖 permanent 类；本项目模型侧覆盖，**MQ 层不覆盖**（`Outcome.RETRYABLE_FAILURE` 由 Worker 判定，故间接覆盖） |
| A-4 | **把 unknown 当失败重试** | 重复副作用（Sev-0） | 检查是否存在「UNKNOWN → 重投」路径；本项目 `toConsumeResult` 把 UNKNOWN 映射为 CLAIMED（`:108-109`）→ 未命中 |
| A-5 | **无限重投**（无 delivery-limit） | poison message 会永久占用消费者 | 检查队列 `delivery-limit` / `max-attempts`；本项目 3 → 未命中 |
| A-6 | **错误码是自由文本** | 客户端无法据此决策，只能猜；语义漂移无法检测 | 检查 `error_code` 列是否被枚举约束；**本项目是 `text`，无 CHECK** → 命中（改进点 3） |
| A-7 | **按原因告警而非按症状告警** | 告警风暴且不指向用户影响 | 检查告警规则来源；本项目应用内 4 条规则基于终态（症状）→ 未命中 |
| A-8 | **日志里有 = 被看见了** | 重复 2880 次/天的同文案 WARN 会被规则滤掉，等于静默 | `RunRecoverySweeper.java:79-83` **明确写了这条反思**（「有日志不等于可被察觉」）→ 作者已知，但 `healthy()` 无消费者（§4.5-e） |
| A-9 | **「稍后再试」掩盖终态** | 用户对着永不出现的结果死等；烧配额 | 检查前端错误文案与是否给重试按钮；本项目 `errorGuidance` 已修（`:9-15`），**SSE 轮询器未修**（`eventStream.ts:205-223`） |
| A-10 | **退避窗口 < 故障恢复时间** | 重试窗口全部落在故障期内，等于没重试 | 本项目 3 次 × (1s,2s) ≈ 3s 总窗口；对比模型供应商典型故障（分钟级）→ 命中（见 §5.3 劣势 3） |

## 三、竞品实现全景

> 说明：以下每条均给出官方 URL。**本环境对 `docs.anthropic.com` / `platform.claude.com` 的抓取被地域拦截**（跳转到 app-unavailable-in-region），Anthropic 部分的事实以公开 API 错误码约定与既有竞品报告为准，并显式标注未逐字核对。

### 3.1 OpenAI Agents SDK（Python / JS）

- **定位**：极简原语库（Agent / Runner / Handoffs / Guardrails / Sessions / Tracing），无显式图。
- **失败处理机制**：
  - **重试是 opt-in**：`ModelSettings.retry: ModelRetrySettings`，字段只有三个——`max_retries`、`backoff`、`policy`；`backoff` 是嵌套的 `ModelRetryBackoffSettings`（`initial_delay` / `max_delay` / `multiplier` / **`jitter: bool`**）。默认全部 `None`，即**默认不重试**。（<https://openai.github.io/openai-agents-python/ref/model_settings/>、<https://openai.github.io/openai-agents-python/ref/retry/>）
  - **重试判定走策略回调**：`RetryPolicyContext` 暴露 `normalized`（含 `status_code` / `error_code` / `retry_after` / `is_timeout` / `is_network_error`）、`provider_advice`、`attempt`、`stream`；策略返回 `RetryDecision(retry, delay, reason, approve_unsafe_replay)`。
  - **重放安全是独立防线（本报告认为这是它最聪明的设计）**：`RetryPolicyContext.replay_safety ∈ {"safe","unsafe","unknown"}`，`response_started` 表示提供商是否**已开始输出**。普通的 `RetryDecision(retry=True)` **永远不能绕过重放保护**；必须显式 `approve_unsafe_replay=True` 才能重试「可能已有副作用」的请求。文档原文强调这一字段「deliberately separate from `retry`」。
  - **异常分类**：`AgentsException` 为基类，含 `MaxTurnsExceeded`、`ModelBehaviorError`、`ModelRefusalError`、`ModelTimeoutError`、`ToolTimeoutError`、`UserError`、`MCPToolCancellationError` 及四个 guardrail tripwire。（<https://openai.github.io/openai-agents-python/ref/exceptions/>）
  - **轮次上限**：`max_turns` 属 `RunOptions`（**不在 `RunConfig` 中**，本报告核实后更正了常见误传），`None` 表示不限制。
  - **工具错误的两条路**：`RunConfig.tool_not_found_behavior` 可取 `raise_error`（默认，抛 `ModelBehaviorError`）或 `return_error_to_model`（把错误作为 `function_call_output` 回灌，让模型自行改道）；`tool_error_formatter` 可定制回灌文案。
- **优点**：① **重放安全是一个一等公民概念**，且默认拒绝——这与本项目「UNKNOWN 禁重放」的精神一致，但实现层级不同（SDK 层 vs DB 层）；② 归一化错误对象（`ModelRetryNormalizedError`）字段齐全，含 `retry_after`、`request_id`，便于排障；③ 错误分类与「回灌给模型」解耦，支持 agent 自愈。
- **局限**：① 默认**不重试**——生产必须显式开启，忘配就等于零容错（对新手是陷阱，对专家是好默认）；② **无跨调用重试预算**，也无熔断；③ `approve_unsafe_replay` 是一个「能力极强的开关」，一旦被无差别打开，等于放弃了它最核心的保护。
- **适用场景**：已自建重试/限流基础设施、只需要 SDK 层「可观测 + 可分类」的团队。

### 3.2 Anthropic Claude Agent SDK

- **定位**：把 Claude Code 当库用（工具 / 权限 / sessions / hooks / MCP）。
- **失败处理机制（未逐字核对，见本节说明）**：官方 API 错误码页（<https://docs.anthropic.com/en/api/errors>，现跳转 `platform.claude.com/docs/en/api/errors`）给出 400/401/403/404/413/429/500/529 等状态码语义与「哪些应重试」的建议；SDK 侧以 `max_turns` 与 `max_budget_usd` 作为**失控保护**（防无限循环 / 无限花钱），而不是作为重试策略。既有竞品报告维度 11 记录：Anthropic 侧「`max_turns` 防失控」，未提节点级重试原语。
- **优点**：① 失控保护与预算熔断同源，配置面极小；② 错误码语义清晰（529 = overloaded 是可重试的明确信号）。
- **局限**：① 重试策略不在框架内，node 级容错需自建；② 地域/网络限制使文档可达性成为问题（本报告即受此影响）——这不是技术缺陷，但**对一个要长期运维的系统，「依赖文档可达性」本身就是风险**。
- **适用场景**：以 Claude Code 工作流为原型、需要「快」而不是「可控」的场景。
- **诚实标注**：本条的重试细节**未能从官方页逐字核实**（抓取被地域拦截），仅采用公开的错误码语义与既有报告结论，未做推断。

### 3.3 LangGraph

- **定位**：低层图式编排运行时（State / Node / Edge + checkpointer），持久执行。
- **失败处理机制**（官方博客 <https://www.langchain.com/blog/fault-tolerance-in-langgraph>，2026-06-04，已抓取全文）：
  - **三个原语，按节点挂载**：`RetryPolicy` / `TimeoutPolicy` / `error_handler`，均通过 `add_node(...)` 或 `set_node_defaults(...)` 声明。
  - `RetryPolicy(initial_interval, backoff_factor, max_interval, max_attempts, jitter, retry_on)`：默认 `retry_on` **刻意保守**——只重试 `ConnectionError`、`httpx`/`requests` 的 5xx 与少数通用瞬时类别，**不重试 `ValueError` / `TypeError` / `RuntimeError`**（「几乎总是编程错误」）。`retry_on` 可传类型集合或**运行期谓词**。
  - `TimeoutPolicy(run_timeout, idle_timeout, refresh_on)`：`run_timeout` 是单次尝试的墙钟硬顶；`idle_timeout` 在每次「进展信号」（channel 写、流式 chunk、子任务事件、回调）时重置——**长但活跃的任务不会被误杀，真挂死的会被杀**。这个区分是本报告认为竞品里最精细的一处超时设计。
  - `error_handler`：**只在重试耗尽后**触发，注入 `NodeError(node, error)`；且「handler 上不能再挂 handler」，因此无递归爆炸。文档强调其状态转换是**原子的**（原节点写 `ERROR` 与调度 handler 在同一个 superstep），崩溃恢复后恢复的是 handler 而不是失败节点。
  - **与 SAGA 的组合**：官方示例把「订座 → 支付 → 出票」逐步重试，重试耗尽后 `Command(goto="compensate")`，补偿只回滚**确实执行过**的步骤——这与本项目的「UNKNOWN → 对账而非重放」是同一问题的两种答案（LangGraph 用补偿，本项目用对账 + 人工处置）。
- **优点**：**声明式、按节点、可组合**，容错配置与业务逻辑同址；超时的 idle/run 二分很实用；error_handler 的「耗尽才触发」语义干净。
- **局限**：① **无跨节点重试预算**——N 个节点各 3 次重试，仍是相乘；② 无熔断/舱壁；③ 中断后「节点从头重跑」，**要求节点幂等**（官方明说），这个要求在工具型节点上很难满足；④ 补偿逻辑需自建，框架只提供 goto。
- **适用场景**：需要精细控制「哪一步可以重试几次」的工作流型 agent。

### 3.4 Google ADK

- **定位**：code-first Agent + 图工作流，自带部署（Cloud Run / Agent Runtime）。
- **失败处理机制**：`HttpRetryOptions`（`google.genai.types`）挂在模型适配器或 `generate_content_config.http_options` 上，字段为 `attempts` / `initial_delay` / `max_delay` / `exp_base` / `jitter` / `http_status_codes`。官方文档（<https://adk.dev/agents/models/google-gemini/>，已抓取）在「429 RESOURCE_EXHAUSTED 排障」一节给出两种配置位置（Agent 级 `generate_content_config`、模型适配器级 `Gemini(retry_options=...)`）。
- **值得单独指出的风险（来自第三方深入分析，非官方页）**：ADK 的重试是**分层叠加**的——底层 `google-genai` SDK 的 `RetryInterceptor` 默认 5 次（含首次）、initial 1s、max 60s、exp_base 2、jitter 1.0，重试 408/429/500/502/503/504 与 IOException；上层若再加装饰器与调用方重试，则总请求数为 `C × D × S`。该分析给出的建议是「**只在一层重试，其余关掉**」（<http://www.aicassindra.com/blogs/adk_java/adk_java_llm_layer_retries.html>）。**本报告标注：该来源为个人技术博客，不是官方文档，仅作风险提示，不作为事实依据。**
- **优点**：错误分类用 `http_status_codes` 白名单表达，简单直观；与 Google 生态（Cloud Trace）天然衔接；官方明确「404/400 不重试」的实践建议（社区文章一致）。
- **局限**：① 分层重试相乘是最容易踩的坑，且**默认值是「已重试 5 次」而非「不重试」**——对新手是隐藏放大；② 无节点级 error_handler 的等价原语（官方 error-handling 语义未完整明示，本报告不臆测）；③ 429 的两种形态（尖峰 vs 配额耗尽）框架不区分，只能靠 `attempts` 折中。
- **适用场景**：Gemini/Vertex 生态、希望「开箱有重试」的团队。

### 3.5 Microsoft AutoGen（已归档，仅作参照）

- **定位**：分层事件驱动多智能体（Core / AgentChat / Extensions）。官方已于 2025-10 并入 Microsoft Agent Framework，2026-10 起归档停维护——**不应作为新项目选型依据**。
- **失败处理机制**：**当前 AgentChat API 用 `TerminationCondition` 取代了单 agent 的连续回复限制**。官方 termination 文档（<https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/termination.html>，已抓取）列出 11 种内置条件：`MaxMessageTermination` / `TextMentionTermination` / `TokenUsageTermination` / `TimeoutTermination` / `HandoffTermination` / `SourceMatchTermination` / `ExternalTermination` / `StopMessageTermination` / `TextMessageTermination` / `FunctionCallTermination` / `FunctionalTermination`，并支持 `&`/`|` 组合。
- **重要更正**：`max_consecutive_auto_reply` **是 AutoGen 0.2 的 `ConversableAgent` 属性，当前 AgentChat API 中不存在**（官方页明确把 0.2 Docs 单列）。本报告据此更正了「AutoGen 的失败保护靠 `max_consecutive_auto_reply`」这一常见说法。
- **优点**：终止条件**可组合**，是「什么算结束」这件事上表达力最强的设计；`TokenUsageTermination` / `TimeoutTermination` 把成本与时延纳入终止语义。
- **局限**：终止条件解决「循环何时停」，**不解决「单次调用失败怎么办」**——模型调用重试仍靠 client 层（host 责任）。框架已归档，且实现不统一（0.2 与 0.4 语义断裂）。
- **适用场景**：仅历史项目维护参照。

### 3.6 CrewAI

- **定位**：角色扮演式 Crew（Agents + Tasks + Process）+ Flows。
- **失败处理机制**（<https://docs.crewai.com/en/concepts/agents>，已抓取）：Agent 级 `max_retry_limit`（**默认 2**）、`max_iter`（默认 20）、`max_rpm`（限速）、`max_execution_time`（秒）；`cache=True` 默认开（缓存工具结果）。**本报告注意到一条很特别的机制**：同一 agent 用**相同参数**调用同一工具、得到**相同结果**累计 5 次，任务直接以 `ToolExecutionFailedError` 终止——且「`max_retry_limit` 不会重试它」，阈值 5 不可配置。
- **优点**：① **内置了 poison loop 检测**（同参同结果 5 次即熔断），这是竞品中唯一显式处理「模型陷入重复调用」的；② `max_rpm` 在框架层提供速率上限，是最接近「重试预算」的原语；③ 默认值保守（2 次重试）。
- **局限**：① `max_retry_limit` 是**粗粒度**的——不区分错误类型，「所有错误都重试 2 次」，对 4xx 是浪费，对 UNKNOWN 是危险；② `cache=True` 默认开启，在副作用工具上是隐患（缓存命中会让模型以为「又成功了一次」）；③ 无节点级超时/退避配置，也无抖动。
- **适用场景**：快速搭建、失败主要来自模型抖动的场景。

### 3.7 Agno

- **定位**：Agent / Team / Workflow + 自托管 AgentOS。
- **失败处理机制**（<https://docs.agno.com/reference/agents/agent>，已抓取）：Agent 构造参数含 `retries: int = 0`、`delay_between_retries: int = 1`（秒）、`exponential_backoff: bool = False`。此外 AgentOS 的 Durable Queue 提供心跳租约 + `max_attempts` + Idempotency-Key（<https://docs.agno.com/agent-os/background-execution/durable-queue>，既有竞品报告已引）。
- **优点**：三个参数覆盖了「次数 / 基数 / 是否指数」，心智负担最低；Durable Queue 的「心跳租约 + 幂等键」与本项目的「租约 + fencing + 幂等记录」是同构的，且已产品化。
- **局限**：① **默认 `retries=0`**（不重试）且 `exponential_backoff=False`（默认线性），生产必须显式调；② 无抖动参数——即使开了指数退避也是同步的；③ 重试仍是「Agent 整体重跑」粒度，副作用安全依赖调用方自己保证。
- **适用场景**：需要自托管、并接受「自己配重试」的团队。

### 4.1 架构与数据流：一次失败的完整旅程

### 4.2 关键设计决策逐条剖析

#### D-1 · POISONED 事务：把「静默回滚」变成显式 5xx

- **决策**：用 `ThreadLocal<Boolean> POISONED` 记录「本事务内曾发生 SQL 失败」；嵌套事务捕获 `SQLException` 时 `markPoisoned()` 并转成运行时异常；**顶层提交前**检查 `isPoisoned()`，命中则抛异常、**绝不 commit**。
- **为什么**（源码注释已给出实测结论，`:52-57`）：PostgreSQL 语句一旦报错，事务立即进入 aborted 态；**此时 COMMIT 不抛错，而是静默等价 ROLLBACK**。若嵌套层把 `SQLException` 包成运行时异常、上层又按 fail-soft 语义吞掉（例如双写挂起），顶层会带着「看起来成功」的结果走到 commit——结果是「四条 INSERT 全回滚，接口却返回 201 + 一个从未落库的 runId」。
- **代价**：① 任何「业务上算不出来的降级」与「SQL 真的失败」必须被严格区分——前者不得打标，否则会把正常的 fail-soft 降级变成 5xx；源码把这条写进了注释（`:59-62`）。② `bind()` 时必须清标记（`:100-102`），否则上一事务的毒化会污染下一事务（「fail-closed 但方向错误」）。③ ThreadLocal 若不清理会跨请求泄漏，`clear()` 必须无条件调用（`:114-119`）。
- **证据锚点**：`agent-persistence/.../persistence/TransactionalConnectionHolder.java:64`（标记定义）、`:100-102`（bind 清理）、`:114-119`（clear 双清理）、`:152-162`（嵌套打标）、`:170-186`（顶层拒提交 + finally 清理）、`:187-192`（异常归一）。
- **反向守卫**：`agent-persistence/src/test/.../TransactionBoundaryIT.java:238-239` 写明「撤掉 `markPoisoned()` 或顶层的 `isPoisoned()` 检查，本用例**必然变红**」——这是项目铁律 6 的教科书式执行。

#### D-2 · 终态不伪装：四层防线，各管一段

本项目的「不伪装」不是一处设计，而是四层各解决一类失真：

| 层 | 防的是哪种失真 | 机制 | 证据 |
|---|---|---|---|
| **DB 层** | 「终态被改写回非终态」 | `enforce_run_state_transition` 只允许 7 条合法跃迁，其余 `RAISE EXCEPTION ... ERRCODE='restrict_violation'` | `01_platform_ddl.sql:453-475` |
| **DB 层** | 「终态后补 attempt」 | `forbid_attempt_after_terminal`：终态或 UNKNOWN 下插入 `tool_operation_attempt` 直接拒 | `:516-539` |
| **DB 层** | 「终态缺完成时间 / SUCCEEDED 无结果」 | `run_completed_at_consistent`、`run_result_consistent` 两条 CHECK | `:2748`、`:2750` |
| **应用层** | 「事务回滚了但返回成功」 | POISONED（D-1） | `TransactionalConnectionHolder.java:170-179` |
| **传输层** | 「UNKNOWN 被重投」 | `toConsumeResult` 把 UNKNOWN 映射为 `CLAIMED`（ack 丢弃），并注明「这是全项目最危险的一行映射」 | `RunDispatchConsumer.java:99-112` |
| **客户端** | 「403/404 被当成网络抖动」 | `errorGuidance`：先判 403/404/401 为终态（`retryable=false`），再判 5xx/超时为可重试 | `errorGuidance.ts:44-95` |
| **治理端点** | 「UNKNOWN 提供一键重试」 | 处置端点只有三个终态归档动作，**不存在 retry 路径**（注释写明「反证 A-5 锁定」） | `UnknownOperationController.java:26-32` |

- **为什么分层而不集中**：每层的失败模式不同——DB 层能防住「应用代码写错」，但防不住「应用代码撒了谎」；应用层能防住事务静默回滚，但防不住「客户端解读错」；客户端规则能防住「无限重试」，但防不住「服务端给了错的码」。**只有分层才能覆盖整条链路上的失真面**。
- **代价**：四层之间没有共享的错误词汇表（这是 §5.3 劣势 1 与改进点 3 的由来）。例如 `run.state` 的 `TIMED_OUT` 与事件 payload 的 `TIMED_OUT` 与 `error_code` 的 `TIMEOUT` 是三个不同来源的字符串，而 DB 里没有一条约束保证它们一致。

#### D-3 · 三类结局而非两类：`Outcome` 六值 + `ExecutionOutcome` 九值

- **决策**：MQ 处置层定义 `Outcome{SUCCEEDED, FAILED, CANCELLED, RETRYABLE_FAILURE, UNKNOWN_RESULT, STALE_GENERATION}`（`RunDispatchConsumer.java:61-74`），执行层定义 `ExecutionOutcome.Kind{SUCCEEDED, FAILED, RETRYABLE_FAILURE, UNKNOWN_RESULT, SKIPPED_STALE_GENERATION, CANCELLED, TENANT_BLOCKED, PARKED}`（`RunExecutionLoop.java:2152-2176`），二者在装配层**穷尽映射**（`WorkerExecutionConfig.java:930-946`）。
- **为什么必须多于两类**：如果只有 success/failure，那么 UNKNOWN 会被迫选一边——选 success 则丢账，选 failure 则重试（重复副作用）。六值/九值的本质是**为「不确定」和「不归我管」留出位置**。
- **代价**：① 两个枚举 + 一个映射 switch，新增值时必须三处同步（`default` 分支刻意按「丢弃」兜底，`:165-167`、`:288-295`）；② `TENANT_BLOCKED` 与 `PARKED` 在 `RunDispatchConsumer.Outcome` 中**没有对应值**，被折叠进 `FAILED` 与 `SUCCEEDED`（`:940`、`:945`）——这在 MQ 处置上正确（都不重投），但让「租户被暂停」在消费层指标上与「真失败」不可区分。
- **证据锚点**：见上；另 `:2222-2225` 的 `retryable()` 只认 `RETRYABLE_FAILURE`，注释写明「UNKNOWN / 世代失效 / PARKED 均不允许」。

#### D-4 · 重试分两层：MQ 层管「投递」，Worker 层管「分类」

- **决策**：Worker 不自己 sleep 重试，而是把「可重试」这个判断**编码成返回值**交给 MQ 层；MQ 层负责延迟与次数上限。DB 通道由 `PgQueueListener.retryOrDead` 实现（`:306-315`），Rabbit 通道由 `basicNack(tag, false, true)` 实现（`RabbitExecutionListener.java:139-143`）。
- **为什么**：① Worker 是同步阻塞的，自己 sleep 会长期占用执行线程；② 重试次数必须与「消息投递次数」同源，否则两套计数会打架（项目铁律：绝不引入 `@Retryable`，`RunExecutionLoop.java:63-66`）。
- **代价（本报告认为这是本项目最需要正视的架构缝隙）**：**两条通道的重试语义并不等价**：
  - DB 通道：`next_attempt_at = now + backoffFor(n)`，退避 1s/2s，且有 `visibility-timeout=300s`（yml `:484`）；
  - Rabbit 通道：`nack(requeue=true)` **立即重投**，无退避，只有 `x-delivery-limit=3` 兜底（yml `:414`）。
  - 而 `application.yml:443-447` 声称两条通道「**语义等价**（at-least-once + 有限重试 + 死信 + 背压）」。**「有限重试」等价，「退避」不等价**。后果：Rabbit 模式下 3 次投递在毫秒级内烧完，等于「没有退避的重试」，正是 T2/T3 描述的放大形态。
- **证据锚点**：`PgQueueListener.java:306-322`、`RabbitExecutionListener.java:139-143`、`application.yml:414、443-447、479-488`。

#### D-5 · 死信：两条通道、一张表、零出口

- **决策**：Rabbit 侧 `agent.run.execute` 挂 `x-delivery-limit=3` + DLX `agent.run.dlx` → `agent.run.dead`（该队列**自身不挂 DLX**，避免死信循环，yml `:426-428`）；DB 侧 `max-attempts=3`，耗尽后**同事务**「删队列行 + 插死信行」（`PgQueueRepository.java:270-285`，注释写明「两步必须同一事务」）。
- **为什么**：坏消息必须**离开热路径**，否则会持续占用消费者与重试预算；而同事务保证不会出现「消息凭空消失」或「已进死信但队列还在」。
- **代价**：DDL 注释直接承认了现状——`agent_message_dead_letter` 是「**只进不出，须人工介入**」（`:1399`）。而「人工介入」所需的三件东西（查询、重放、告警）**一件都没有**：`agent-api` 中无任何 `dead` 相关端点（本报告实测 grep 无命中），无 Gauge，无告警规则。**这是一个「设计上正确、运维上悬空」的机制**。
- **证据锚点**：DDL `:1379-1399`；`PgQueueRepository.java:273-286`；`PgQueueListener.java:324-330`；yml `:406-436`。

#### D-6 · 崩溃恢复：租约 + fencing + 30s 扫描器

- **决策**：`RunRecoverySweeper` 每 30s 枚举活跃租户，调 `claimTasks` 接管**租约已过期**的 RUNNING；领到后用与 MQ 主路径**完全相同**的 `RunExecutor` 执行。
- **为什么**：`claimTasks` 的 SQL 早已就绪，但长期**无生产调用方**——worker 崩溃后其持有的 RUNNING 租约过期却无人认领，Run 永久卡死（类注释 `:22-26` 记录了这件事）。
- **代价与已有的补救**：① 恢复粒度 = 30s + 租约 30s（yml `:219`），即最坏约 60s 的「假死」窗口；② 租户枚举依赖平台运维通道，端口不可用时**只 WARN 并跳过**（`:30-33`）——作者把这件事升级成了健康事实 `healthy()`/`unhealthyReason()`（`:139-157`），并写下了本报告最欣赏的一句工程反思：「**重复 2880 次/天的同文案 WARN 会被日志告警规则当噪音滤掉——等同于静默。『有日志』不等于『可被察觉』，更不等于『可被告警』**」（`:79-83`）。
- **残留缺口**：`healthy()` **没有任何 HealthIndicator 消费它**（全仓 grep 仅见类内引用与测试），所以这句反思目前仍停在注释层。见 §4.5-e 与改进点 4。
- **证据锚点**：`RunRecoverySweeper.java:19-50、74、84、139-157、172`；`JdbcRunClaimRepository.java:216-260`（领取条件含 `lease_expires_at < now()`）。

#### D-7 · 抢占式单步超时：把「每轮检查 deadline」升级为「每次调用受限」

- **决策**：把每次模型/工具调用提交到 `preemptionExecutor`，用 `Future.get(剩余时间, MILLISECONDS)` 包裹，到期 `cancel(true)` 并抛 `StepDeadlineExceededException` → Run 收敛为 TIMEOUT。
- **为什么**（`:211-225`）：`task.deadlineAt()` 原先只在**每轮迭代开头**检查，一次模型调用卡 10 分钟就整段跳过检查——FR-024「整树共享超时上限」在单步粒度上形同虚设。
- **代价**：① 需要额外线程池（配置缺失时**退回旧行为并 WARN**，不假装已受保护，`:221-224`）；② `cancel(true)` 是协作式中断，若底层 HTTP 客户端不响应中断，线程仍会被占住直到 socket 超时——**这只能限制「Run 的推进」，不能立刻释放线程**；③ `deadline == null` 时**不中断**（「创建时声明不限时」是既定语义，`:1536-1538`），而 `run.require-timeout` **默认 false**（yml `:503`）——意味着默认配置下这条防线对「不限时的 Run」完全不生效。
- **证据锚点**：`RunExecutionLoop.java:211-225、1511-1557、755-763、898-906、1019-1023`。

#### D-8 · 预算与故障的交叉规则：预留失败记 FAILED 而非 UNKNOWN

- **决策**：`ToolInvocationGate` 三条铁律——预留失败即拒绝（fail-closed）；预留失败记 `FAILED` 而非 `UNKNOWN`（工具根本没发出）；`UNKNOWN` 绝不释放预留。
- **为什么**：把「确定没执行」记成 UNKNOWN 会凭空造出待对账的幽灵操作（`ToolInvocationGate.java:44-45`）；把 UNKNOWN 当失败释放额度则等于「成本可能已发生却退回额度」（`:46-47`，R-007）。
- **代价**：UNKNOWN 越多，`budget_account.reserved_amount` 越会「虚高」，租户额度被不确定占用——这是**用可用性换账实相符**的自觉取舍。
- **证据锚点**：`ToolInvocationGate.java:40-48`；DDL `tool_operation.budget_reservation_id` 注释（`:3001`）；`forbid_attempt_after_terminal`（`:531-536`）。

#### D-9 · 配置 fail-closed：缺失即拒启，不退回默认值

- **决策**：`WorkerPolicy` 对继电器间隔（<10ms 拒）、并发度（>64 拒）、预取（>100 拒）、租户清单（空/重复/超上限拒）一律 `IllegalStateException`。
- **为什么**：`WorkerPolicy.java:12-16` 写明「退回默认值等于『悄悄用了一个没人审过的并发度』；容器化环境下默认并发可能直接打垮下游模型服务与 MQ」。
- **代价**：部署成本上升（少一个 key 就起不来）；但对「静默用错配置」这类故障，这是唯一有效的防线。
- **证据锚点**：`WorkerPolicy.java:12-16、59-93、95-124`；消费侧 `PgQueueListener.java:160-161`。

#### D-10 · 错误码白名单：失败载荷只放 state，不放原文

- **决策**：`commitFailure` 写入 `result_payload={"reason":...}`（内部），但**事件载荷只放 `{"state":"FAILED"}`**，`error_code` 只放码。
- **为什么**（`:1841-1846`）：reason 是内部细节（如「模型调用失败：TIMEOUT」），白名单要求 `errorCode` 是**码**而非原文；同时 `error_code` 真实写入 `run` 表，供指标做终止原因归因。
- **代价**：排障需要把「事件里的 state」+「run 表里的 error_code」+「日志」三者拼起来；这也是 §4.5-c 语义漂移的土壤。
- **证据锚点**：`RunExecutionLoop.java:1836-1853`；`failurePayload`（`:2134-2138`）。

#### D-11 · 前端错误语义：单一真相源，但只覆盖「非流式」路径

- **决策**：把「HTTP 错误 → 是否给重试按钮 + 说什么话」收敛到 `errorGuidance()`；把「Run 失败码 → 用户可读原因 + 是否可重新发起」收敛到 `runFailureGuidance()`，并**禁止把内部 errorCode 原样透出**。
- **为什么**（`errorGuidance.ts:4-15`）：F8 只修了进度页的 404，画像页仍把 403 说成「可能是网络问题」并给重试按钮——「同类问题散落四处，修一处漏一处」，故收敛到一个函数。
- **代价 / 残留**：SSE 轮询器 `eventStream.ts` **没有接入 `errorGuidance`**，它只对 401 做特殊处理（`:212-216`），403/404 落入通用 `catch` → `schedule(ERROR_BACKOFF_MS=10_000)` → **每 10 秒永久重连**（`:205-223`）。这与铁律 15「404/403/401 须显式终态 + 停轮询」的后半段**尚未闭合**（详见 §5.3 劣势 4 与改进点 6）。
- **证据锚点**：`frontend/src/api/errorGuidance.ts:1-16、37-95、99-191`；`frontend/src/features/run/eventStream.ts:20-22、205-223`；`frontend/src/features/run/useRunStatus.ts:35-47、108-119`（这个 Hook 是**已修**的正面样本）。

#### D-12 · 背压：滞回 + 探测失败按超限

- **决策**：`BackpressureController` 在高水位停发、低水位才恢复、之间维持；**探测异常 = 按超限处理**（fail-closed）；降级后拉长轮询间隔。
- **为什么**（`:20-29`）：无滞回会在阈值处抖动（发布—停止—发布—停止），比恒定停发更难排障；「探测失败放行」等于「背压在最需要它的时候失效」。
- **代价**：`throttledRounds` 与 `lastDepth` 只在内存里，**未注册任何 Meter**（维度 10 已记该缺口），所以「正在被背压」这件事对运维不可见。
- **证据锚点**：`BackpressureController.java:13-33、45-48`；`OutboxRelay.java:242-245`。

### 4.4 我们独有的设计（差异化）

**U-1 · 把「事务毒化」写成显式状态，而不是靠约定**
在主流框架与多数业务系统里，「事务内异常被吞掉」只能靠 code review 或数据库的 `in_failed_sql_transaction` 报错被动发现。本项目用 ThreadLocal 标记把「这件事发生过」变成一个**可在提交点查询的事实**，并选择「宁可 5xx 也不要假 201」。本报告未见任何竞品或主流框架有等价机制——它们不管理事务，所以无从谈起；但即便在 Java 业务系统里，这也属于少数派做法。

**U-2 · UNKNOWN 是「状态」而不是「异常」，且处置端点物理上不存在重试**
`tool_operation.state` 有 8 个值，其中 4 个（`SUCCEEDED/RECONCILED_SUCCEEDED/RECONCILED_ABSENT/MANUAL_DISPOSED`）是终态，`UNKNOWN` 是「不能自动前进」的中间态，且 **DB 触发器禁止在 UNKNOWN 下新增 attempt**（E-26）。治理端点用**三个终态归档动作**替代了「重试」，并在类注释里把「不提供一键重试」标为反证 A-5 的锁定项。OpenAI 的 `approve_unsafe_replay` 是最接近的设计，但它是**调用方可选的开关**；本项目是**没有那个开关**——差别在于「可能被误用」与「不可能被误用」。

**U-3 · 错误语义的「生成端白名单 + 消费端单一函数」**
服务端只允许 `error_code` 是码（D-10），客户端把所有 status/code 的处置收敛到 `errorGuidance`（E-35）。这是「错误契约」的雏形，虽然两侧尚未共享同一份定义（改进点 3），但**结构方向是对的**：一句话定义，全局复用。

**U-4 · 用「谁能接手」而不是「谁没失败」来定义可靠性**
恢复路径不是「重试直到成功」，而是「租约过期 → 有人能合法接手（fencing 保证旧世代写不进去）」。这使「Worker 崩溃」从「需要人工重启」降级为「60s 内自动恢复」，且不会产生双写（`enforce_fencing_on_write`，DDL `:410-421`）。

**U-5 · 把「日志不等于告警」写进代码注释**
`RunRecoverySweeper.java:79-83` 的反思在本报告看来比很多监控系统的实现更有价值：它明确区分了「有日志」「可被察觉」「可被告警」三级，并把状态落到 `healthy()` 而不是日志。虽然消费端还没接（§4.5-e），但**问题被正确定义了**。

### 4.5 源码复核不一致声明（对照《能力维度实现方式梳理报告》第 11 章）

> 本节是本报告的**强制诚实项**。以下 7 条均为到源码/DDL 复核后发现的「梳理报告未提及、或表述不够精确」之处。凡属「读代码推断、未运行时验证」的，已单独标注。

**（a）`run_attempt` 不是表，`forbid_attempt_after_terminal` 也不作用于 run**
现状：`01_platform_ddl.sql` 中**不存在** `run_attempt` 表；`run_attempt` 只是 `run.attempt` 列上的一条 CHECK 约束名（`:2747` `run_attempt_non_negative`）。`forbid_attempt_after_terminal` 的触发器只挂在 `tool_operation_attempt` 上（`:4818-4821`），**与 `run.attempt` 无关**。
影响：不能把「终态后禁补 attempt」理解为对 Run 重试次数的保护；Run 的重复领取保护来自 `claimSpecificRun` 的 WHERE 条件（`JdbcRunClaimRepository.java:232-236`）与 fencing，不是这条触发器。

**（b）「重试只在 Worker 侧实现」的说法只覆盖了一半**
梳理报告第 11 章写「重试只在 `RunExecutionLoop` Worker 侧，禁止 `@Retryable`」。源码复核：Worker 侧**不做 sleep 重试**，它只做**分类**并返回 `RETRYABLE_FAILURE`；真正的重试在 **MQ 层**（`PgQueueListener.retryOrDead` / `RabbitExecutionListener.basicNack`）。完整表述应为：「**分类在 Worker，投递在 MQ，两层分工，禁止第三层（`@Retryable`）**」。
另：`RunExecutionLoop.java:63-66` 的注释确实只说了「不引入 `@Retryable`」，没说「Worker 自己重试」——是梳理报告的转述产生了偏差。

**（c）`run.state = 'TIMED_OUT'` 没有任何写入方（本报告最重要的不一致发现）**
源码：所有超时路径都调 `commitFailure(...)`，而它固定写 `"FAILED"`（`RunExecutionLoop.java:1838`），错误码写 `"TIMEOUT"`；事件载荷里写 `state: "TIMED_OUT"`（`:760、:902、`:1022`）。全仓 grep `"TIMED_OUT"` 在 main 侧仅出现在**读取方**（`AgentMetricCollector.java:297`、`TraceFactPort.java:171`、`RunListController.java:46`、`JdbcStatisticsRepository.java:247` 等），**无一处写入 `run.state='TIMED_OUT'`**。
后果：① 数据库层面的超时事实是 `FAILED + error_code='TIMEOUT'`，而 `run_state` 枚举里的 `TIMED_OUT` 是**死枚举值**；② 任何按 `terminal_state='TIMED_OUT'` 聚合的指标/看板**恒为 0**，真实超时被计入 `FAILED`（与维度 10 的「termination_reason 归因」口径不一致）；③ 事件流与 DB 行对同一件事用了两个词。这与项目铁律 16「`run_step.state` 恒 `'RUNNING'`＝步骤已发生」属于**同一族问题**：枚举值存在但语义悬空。

**（d）`ToolOperationReconciliationService` 在生产中无调用方（自动对账未接线）**
梳理报告写「`tool_operation.state=UNKNOWN` … 转 `ToolOperationReconciliationService` 对账」。源码复核：该类存在且实现完整（`ToolOperationReconciliationService.java:14-34`，含「查下游事实，不猜」「读己之写延迟下『没查到』≠『没发生』」的宽限期设计），但**main 侧无任何调用方**——grep 结果只有该类自身、测试与注释；没有 `@Scheduled`，没有 Controller 引用。
现状准确表述：**UNKNOWN 的人工处置通道存在**（`UnknownOperationController`，list + 三态归档），**自动对账调度不存在**。因此 UNKNOWN 操作在无人干预时会长期停留（这正是 `forbid_attempt_after_terminal` 生效的状态）。

**（e）`RunRecoverySweeper.healthy()` 无消费者**
类注释说「装配侧的 `HealthIndicator` 读本方法即可」（`:152-153`），但全仓无任何 `HealthIndicator` 引用它；`/actuator/health` 只挂了消息通道的 `rabbitHealthIndicator`（`MessagingHealthConfig.java:33-37`）。结论：**「崩溃恢复已死」这件事目前仍然不可被告警**——这正是该类自己批判过的那种失败形态。

**（f）`commitFailure` 被连续调用两次，第二次把结局标成「世代失效」（推断，未运行时验证）**
`:761-763`（业务超时）与 `:1182-1184`（步数超限）两处写法相同：
```java
notifyLoopComplete(tenantId, runId, commitFailure(...), steps);  // 第一次：成功写 FAILED
return commitFailure(...);                                        // 第二次：!ok → SKIPPED_STALE_GENERATION
```
第二次 `commitResult` 因状态已是终态而影响 0 行 → `commitFailure` 返回 `skippedStaleGeneration()`（`:1851-1852`）。**MQ 处置仍然正确**（两者都 ack、不重投），但 `ExecutionObserver.LoopOutcome` 会记成「被接管」，日志语义与事实相反，且会让「stale_generation」计数虚高、「failed」计数偏低。同一文件里 `:1146-1149`（3 次被拒）与 `:1218-1221`（装配被拒）用的是先存变量再返回的写法——**说明作者知道正确写法，这 2 处是笔误**。

**（g）「两条消息通道语义等价」的声明与退避实现不符**
见 D-4：DB 通道有指数退避，Rabbit 通道是立即 requeue。yml `:443-447` 的「语义等价」在「有限重试 + 死信 + 背压」三件事上成立，在**退避**上不成立。

### 5.2 优势详解（讲机制，不讲结论）

**优-1 · 语义保真做在「提交点」，而不是做在「返回值」**
多数系统的「不返回假成功」靠的是「记得在 catch 里 throw」。本项目的做法是把判断放到**唯一能提交事务的地方**（`inTransaction` 的顶层分支）：只要事务内发生过 SQL 失败，无论中间被谁吞掉、包了几层、有没有转成业务异常，**提交这一步都会被拦下**。这个设计的价值在于它**不依赖调用链上任何一个人的自觉**——防线的强度等于最弱一环的强度，而 POISONED 把最弱一环变成了最强一环。
代价是它只覆盖「事务内 SQL 失败」这一种失真，覆盖不了「代码逻辑撒谎」（例如把 403 写成 500）。

**优-2 · 用「物理上不存在」代替「约定上不要」**
「不要盲目重放 UNKNOWN」在绝大多数系统里是一条文档纪律。本项目把它做成了三个物理事实：① `tool_operation.state=UNKNOWN` 时触发器拒绝新增 attempt；② 治理端点没有 retry 动作；③ `toConsumeResult` 把 `UNKNOWN_RESULT` 映射为 ack。任何一条被绕过，另外两条还在。这解释了为什么本报告判定本项目在「防重复副作用」上领先：**它不依赖任何人记住规则**。

**优-3 · 恢复靠「合法接手」而非「重试」**
`claimSpecificRun` 的 WHERE 条件同时要求 `fencing_token` 相等与租约过期（`JdbcRunClaimRepository.java:232-236`），`enforce_fencing_on_write` 拒绝旧世代写新世代（DDL `:410-421`）。这使「重试」这件事从「同一个执行者再试一次」变成「任意合格执行者接手一次」，且**旧执行者即使还活着也写不进去**。相比「重试 N 次」的模型，这个模型对「脑裂」「长 GC」「网络分区」都是安全的。

**优-4 · 配置 fail-closed 把「静默用错」变成「立刻起不来」**
`concurrency>64` 拒、`prefetch>100` 拒、租户清单空/重复/超上限拒（E-17）。这类校验的成本几乎为零，收益是「不会有人用 256 并发把供应商打挂之后才发现配置写错了」。多数框架把并发度当普通参数，本项目把它当**承诺**。

### 5.3 劣势与盲区详解（含根因）

**劣-1 · 没有熔断器：已知依赖全挂时，系统仍会「礼貌地」把每次调用走完重试链**
- **现象**：模型供应商整体 5xx 时，每个 Run 依次经历 `MODEL_CALL` → `PROVIDER_ERROR` → `RETRYABLE_FAILURE` → 3 次投递 → 死信。并发 4 的 Worker 会把「等待重试」的时间全部用来做无用的调用。
- **根因**：**能力缺失，不是设计取舍**。全仓无 resilience4j / spring-retry（E-21），说明这条能力从未被规划。作者对「重试必须有界」有清晰认识（`max-attempts=3`），但没有把「有界」升级为「有界 + 有速率」。
- **为什么危险**：这正是 T3 的 metastable 形态——触发器（最初的抖动）早已消失，但重试维持着高负载，系统**不会自愈**。

**劣-2 · 重试放大系数未被建模，且两条通道不一致**
- **现象**：一次逻辑失败最多可产生 `3（MQ 重投）× 1（Worker 不重试）= 3` 次物理尝试；但若叠加「租约过期 → 恢复扫描器重新执行」，同一 Run 的**执行次数**可达 `3（MQ）× 2（sweeper 接手）` 而无统一上限——`run.attempt` 会累加，但**没有任何逻辑读它做上限判断**（`run_attempt_non_negative` 只校验 ≥0）。
- **根因**：`attempt` 是**观测列**而非**控制列**。这在多数系统里也如此，但它使「总尝试次数」成为一个无法被约束的量。
- **附加风险（本报告推断，未实测）**：`RETRYABLE_FAILURE` 返回后**没有释放租约**（`:1186-1194` 只 return，未 `releaseLease`），而重投的消息立刻会遇到「租约仍有效」→ `claimSpecificRun` 影响 0 行 → `DUPLICATE_DISCARDED` → ack。因此**实际的重试恢复时延 ≈ 租约 30s + 扫描间隔 30s**，而不是退避的 1s/2s。这意味着：3 次投递会在秒级内被「空转」消耗掉（进入死信），真正的恢复由 sweeper 完成——**死信里会出现「后来其实恢复成功」的假死信**。这条需要一次真实注入验证（改进点 5 的用例 C1）。

**劣-3 · 退避窗口远小于典型故障时长**
3 次投递、退避 1s/2s，总窗口约 3 秒（DB 通道），Rabbit 通道约 0 秒。而模型供应商的典型故障是**分钟级**。按 A-10 的判别标准，本项目命中：**重试窗口全部落在故障期内，等于没有重试**，只是把「一次失败」变成「四次失败」（含首次）。

**劣-4 · 客户端侧语义保真只覆盖一半路径**
`useRunStatus`（轮询状态）已按 `errorGuidance` 停轮询（`:108-119`），但 `createRunEventPoller`（事件流）只处理 401（`eventStream.ts:212-216`）。**403/404 会以 10s 间隔永久重连**——这正好是铁律 15 描述的那个坑，只是从「3 秒」变成了「10 秒」。后果：烧 `EVENT_QUERY` 配额（30 次/60 秒），用户对着「正在处理」死等一个不存在的 Run。
- **根因**：**修一处漏一处**的典型。`errorGuidance` 的类注释自己写了这个病因（`:4-7`），但收敛动作没做完——`eventStream.ts` 没有 import 它。

**劣-5 · 死信与自动对账都是「只写不读」**
- 死信：表 + DLX 都在，但无查询 API、无 Gauge、无告警、无重放（E-27 + `agent-api` 无 `dead` 端点）。
- 对账：`ToolOperationReconciliationService` 实现完整但**无生产调用方**（§4.5-d）。
- **根因**：这两处都属于「机制先于运维」——先把不变量正确性做对（值得肯定），把「谁来处理」留给了未来。代价是：**在有人值守之前，UNKNOWN 与死信都是只增不减的债**。

**劣-6 · 错误词汇表有四处来源，无一致性约束**
`run.state`（7 值）、`run.error_code`（text，无 CHECK）、`run_event.payload.state`（字符串，无 CHECK）、`ExecutionOutcome.Kind`（9 值）。四者靠人工保持一致，已经产生了 §4.5-c 的 `TIMED_OUT` 悬空。**这是「语义失真」在 schema 层的结构性土壤**，也是改进点 3 的直接动因。

### 5.4 关键分歧点（最本质的架构分歧）

**分歧 1 · 「错误语义」由谁定义：框架 / 供应商 / 数据模型**
- 竞品：错误语义由**框架的异常类**或**供应商的 HTTP 状态码**定义（`ModelErrorKind` 在 OpenAI 是 `normalized` 对象，在 ADK 是 `http_status_codes`）。
- 本项目：错误语义由**数据模型**定义（`run_state` / `tool_operation_state` / `error_code`），应用层只是填充者。
- 后果：本项目能保证「终态不可迁出」这种框架做不到的事；但代价是**词表变更需要 DDL 迁移**，且 schema 中的每个值都必须有写入方（否则就是 `TIMED_OUT` 那种悬空）。这个分歧没有绝对优劣，但**选数据模型就必须承担「枚举值必须有写入方」的纪律**——本项目目前没有这条门禁。

**分歧 2 · 重试是「调用点行为」还是「消息系统行为」**
- 竞品：重试是调用点行为（`@retry` 装饰器 / `RetryPolicy` 挂在 node 上 / `HttpRetryOptions` 挂在 client 上）。
- 本项目：重试是**消息系统的行为**（Worker 只返回一个「可重试」信号，由 MQ 层执行延迟与次数）。
- 后果：本项目的重试天然带「跨进程、可持久、可观测」的属性（`attempts`/`next_attempt_at` 落库），比内存重试强；但也因此**退避策略被绑在通道实现上**，出现 D-4 的两通道不一致。若重做，应当把「退避策略」抽成通道无关的策略对象（改进点 1 的一部分）。

**分歧 3 · 失败之后的两种哲学：「重试到成功」vs「确认事实再决定」**
- 竞品（LangGraph 的 SAGA 示例最典型）：失败 → 重试 → 耗尽 → 补偿（用反向操作撤销）。哲学是**向前推进**。
- 本项目：失败 → 分类 → 若 unknown 则**停止并查证下游事实**（`ToolOperationReconciliationService` 的「查下游事实，不猜」）。哲学是**先确认真相**。
- 后果：本项目在「不可逆副作用」（写学生数据、扣费）上更安全；在「可逆操作」上效率更低（补偿比重试慢）。教育场景下数据写入的不可逆性高于性能诉求，因此这个取舍在本项目语境下是**正确的**；但若要支持交易类 agent（可退款、可撤销），需要补上补偿原语。

## 六、优缺点总评

### 6.1 我们的优点

**结构性优势（靠架构而非纪律保证）**
1. **终态不可伪装在 DB 层闭环**：状态机触发器 + 三条一致性 CHECK + attempt 禁令（E-24..E-26）。应用代码写错也破不了不变量。
2. **事务失真被显式标记**：POISONED（E-01..E-04）+ 反向守卫（E-05）。这是本项目最不可替代的一处设计。
3. **UNKNOWN 是状态而非异常**，且三条独立防线禁止重放（E-26、E-32、E-07）。
4. **恢复依靠合法接手，fencing 拒绝旧世代写**（E-30 + DDL `:410-421`）。

**工程性优势（靠纪律与配置保证）**
5. **配置 fail-closed**（E-17）：缺失即拒启，不退回默认。
6. **错误语义在客户端收敛为单一函数**（E-35），并禁止透出内部 errorCode。
7. **超时做到单步粒度**（E-11），补齐了「每轮才查 deadline」的洞。
8. **两条消息通道都有死信上限**，且坏消息直接进死信不耗重试次数（E-18、E-22）。

**领域性优势（教育多租户语境下的正确取舍）**
9. **UNKNOWN 不释放预算**（D-8）：账实相符优先于额度可用性。
10. **租户生命周期阻断执行**（`TENANT_BLOCKED`，`:1295-1314`）：暂停/退役租户不会被在跑任务继续消耗。

### 6.2 我们的缺点

**设计取舍导致的代价（可接受，但要知道）**
1. 恢复窗口 30-60s（租约 30s + 扫描 30s），对交互式场景偏慢。取舍：换来了「不会双写」。
2. 统一 404 反探测 → 运维侧无法从状态码区分越权与不存在，必须查 `authz_decision_log`。
3. UNKNOWN 不释放额度 → 租户额度会被不确定占用，需要人工对账释放。

**能力缺口（应补）**
4. **无熔断、无舱壁**（按依赖隔离）——行业普遍空白，但对本项目这种「单模型供应商 + 单 RAG 服务」的架构，风险集中度更高。
5. **无重试预算 / 无抖动**——T2/T3 的标准防线缺失。
6. **无自动对账调度**（§4.5-d）：UNKNOWN 只能靠人。
7. **死信无出口**：无查询、无重放、无告警（§4.5）。
8. **无错误码枚举**：`error_code` 是 text，四套词表靠人工一致（§4.5-c 已产生实际漂移）。
9. **无系统化故障注入**：现有的只有单测级反向守卫。

**运维负担**
10. `healthy()` 无消费者 → 「恢复链路已死」不可告警（§4.5-e）。
11. `throttledRounds`/`lastDepth` 无 Meter → 「正在被背压」不可见（D-12）。
12. `commitFailure` 双调用导致归因偏差（§4.5-f），会让「stale_generation」虚高。

## 七、可优化与改进点

> 每条均写明：问题 → 方案（文件/DDL/配置级）→ 收益（指标口径）→ 成本与风险 → 优先级 → **验收门禁**。
> 门禁一律遵循项目铁律 6：必须包含「撤掉修复点会红」的反向验证。

### 改进点 1 · 退避抖动 + 全局重试预算（P0）

**问题陈述**
- `PgQueueListener.backoffFor()` 是 `min(max, base × 2^(n-1))`，**无随机项**（`:317-322`）；Rabbit 通道更糟——`basicNack(requeue=true)` 立即重投（`RabbitExecutionListener.java:139-143`）。多个 Worker 同时失败会在同一时刻重试（T2 的同步波）。
- 无任何全局「重试次数 / 成功请求数」比例约束，缺乏对 work amplification 的抑制（T3）。

**方案设计**
1. **加抖动（改 1 个方法）**：`agent-persistence/.../messaging/PgQueueListener.java`
```java
/** 指数退避 + Full Jitter（Brookers 2015）：sleep = random(0, min(cap, base·2^(n-1))) */
private Duration backoffFor(int attempts) {
    long base = retryBackoffBase.toMillis();
    long ceiling = Math.min(retryBackoffMax.toMillis(), base * (1L << Math.max(0, attempts - 1)));
    long jittered = ceiling <= 1 ? ceiling
            : ThreadLocalRandom.current().nextLong(ceiling / 2, ceiling + 1); // equal-jitter 下限 50%
    return Duration.ofMillis(jittered);
}
```
配置新增 `agent.messaging.retry-jitter-ratio`（默认 `0.5`，允许 0 = 关闭，便于灰度对比），在 `MessagingPolicy` 校验 `0 ≤ ratio ≤ 1`。
2. **Rabbit 通道补退避**：不要再用 `requeue=true`。改为「延迟重投」——把消息 `basicNack(requeue=false)` 进 `agent.run.dlx.retry`（TTL 队列 + DLX 回原队列），TTL 取 `backoffFor(n)`。配置：`agent.mq.queues.execute.retry-ttl-ms` 与 `agent.mq.queues.execute.retry-backoff-max-ms`。**注意**：Rabbit 的 per-message TTL 在队列头阻塞时会失效，必须用「固定 TTL 队列 + 多档 TTL」（如 1s/2s/4s/8s 四个队列），档位由消息头 `x-retry-tier` 决定。
3. **重试预算（retry budget）**：在 `agent-application/.../resilience/RetryBudget.java` 新增：
```java
/** 令牌桶式重试预算：重试次数 ≤ ratio × 成功请求数，窗口 10s。 */
public final class RetryBudget {
    private final double ratio;          // 默认 0.2（AWS SDK adaptive 默认量级）
    private final int minRetriesPerSec;  // 默认 10，避免低流量时完全禁重试
    public boolean tryAcquire();         // 超预算返回 false → 消息直接进死信（标记 RETRY_BUDGET_EXCEEDED）
    public BudgetSnapshot snapshot();    // 供 Gauge 暴露
}
```
落点：`PgQueueListener.retryOrDead()` 在 `nextAttempts < maxAttempts` 之后再问一次预算；`RabbitExecutionListener` 同理。**超预算的处置**必须是「进死信 + 明确错误码 `RETRY_BUDGET_EXCEEDED`」，不是「丢弃」也不是「无限等」。
4. **配置**：`agent.messaging.retry-budget.ratio: "0.2"`、`agent.messaging.retry-budget.min-per-second: "10"`，`WorkerPolicy` 风格 fail-closed 校验（缺失拒启）。

**预期收益**
- 同步重试尖峰下降：以「同一秒内重试请求数 / 总请求数」为口径，目标从当前（无抖动，理论上接近 1.0 同步率）降至 < 0.3。
- 依赖过载期间的总请求量：目标 ≤ 1.2 × 正常量（当前理论峰值可达 3 ×）。
- 新增可观测：`messaging.retry.budget_exhausted.total`（计数器）、`messaging.retry.delay_ms`（直方图，观察抖动分布）。

**实施成本与风险**
- 抖动：1 个方法 + 1 个配置，**风险极低**，可灰度（ratio=0 即旧行为）。
- Rabbit 延迟队列：需新增 4 个 TTL 队列 + 路由，**队列类型一经声明不可改**（yml `:405` 已警示），需在空窗期重建。
- 重试预算：会让「本来第 3 次能成功」的消息提前进死信，**需接受少量成功率下降换取系统不塌**；必须配死信告警（改进点 4）才能上线。

**优先级**：P0（抖动部分）、P0（Rabbit 退避）、P1（重试预算）
**排期**：抖动随下一个 P4 补丁；延迟队列与重试预算进 P5「生产就绪」阶段。

**验收门禁**
1. **单测（确定性）**：注入固定 `Random` 种子，断言 `backoffFor(3)` 输出落在 `[0.5·4s, 4s]` 区间；断言 `ratio=0` 时输出恒等于旧实现（**兼容性反证**）。
2. **统计断言**：1000 次 `backoffFor(3)` 的样本标准差 > 0；且 `ratio=0` 时标准差 == 0（**撤掉抖动必红**）。
3. **MQ 集成测**：`PgQueueIT` 新增用例——同一租户注入 50 条必失败消息，断言「首次重试时刻的方差 > 0」（抖动生效）且「总投递数 ≤ 3 × 50」。
4. **预算门禁**：`RetryBudgetTest` 断言「成功 10 次 + 重试 5 次（ratio=0.2）→ 第 3 次重试被拒」；撤掉 `tryAcquire()` 调用 → 用例变红。
5. **配置门禁**：缺失 `retry-budget.ratio` 时启动失败（与 `WorkerPolicy` 同风格的 `IllegalStateException`），并有单测锁定。

### 改进点 2 · 熔断器与舱壁隔离（P1）

**问题陈述**
全仓无熔断实现（E-21）。模型供应商、工具 HTTP 通道、RAG 服务是三个**独立故障域**，但共享同一个 Worker 线程池与同一套重试路径。任一依赖全挂，Worker 会把全部并发用来做无用调用 + 等待重试，**其他依赖正常的 Run 被饿死**（无舱壁）。

**方案设计**
1. **引入 Resilience4j（不引入 Spring Retry，避免与 MQ 层重试叠加）**：`platform/platform-bootstrap/pom.xml` 增加 `io.github.resilience4j:resilience4j-circuitbreaker`、`resilience4j-bulkhead`（**不要** `spring-boot-starter-aop` 自动织入，改为手动包装，避免注解不可控）。
2. **三个独立熔断器实例**（按故障域，不按租户——租户级熔断会让单租户故障影响他人）：
```java
// agent-application/.../resilience/DependencyBreakers.java
public enum Dependency { MODEL_PROVIDER, TOOL_HTTP, RAG }

// 配置（application.yml）
agent:
  resilience:
    breakers:
      model-provider:
        failure-rate-threshold: "50"
        slow-call-duration-threshold: "10s"
        slow-call-rate-threshold: "80"
        sliding-window-type: "TIME_BASED"
        sliding-window-size: "60"          # 60s 窗口
        minimum-number-of-calls: "20"       # 小样本不触发（与 min-samples=30 同纪律）
        wait-duration-in-open-state: "30s"
        permitted-number-of-calls-in-half-open-state: "5"
      tool-http: { ... }
      rag:       { ... }
    bulkheads:
      model-provider: { max-concurrent-calls: "16", max-wait-duration: "0" }
      tool-http:      { max-concurrent-calls: "8",  max-wait-duration: "0" }
      rag:            { max-concurrent-calls: "4",  max-wait-duration: "0" }
```
3. **包装点**（三处，且**只在最内层**，避免嵌套放大）：
   - `MiniMaxModelGateway.invokeGuarded()` / 流式入口：`MODEL_PROVIDER` 熔断 + 舱壁；
   - `HttpToolExecutor`（或 `kind=http` 的执行入口）：`TOOL_HTTP`；
   - `HttpRagRetrievalGateway.retrieve()`：`RAG`。
4. **熔断打开时的语义（关键，不能含糊）**：
   - 模型：**不是** `RETRYABLE_FAILURE`，而是 `commitFailure(reason, "MODEL_CIRCUIT_OPEN")` —— 因为熔断打开意味着「重试没有意义」（T1：仅在观察到依赖健康时才重试）。这会把 Run 快速失败，**把资源让给其他租户**。
   - 工具：`FAILED`（工具未发出，无副作用），错误码 `TOOL_CIRCUIT_OPEN`；
   - RAG：保持现有 `RagUnavailableException` 语义（组件级 error + 空命中），**不升级为 Run 失败**（检索是增强而非必需）。
5. **舱壁与现有并发度的关系**：`agent.worker.concurrency`（≤64）是**总闸**，舱壁是**分闸**；分闸之和应 ≤ 总闸，`WorkerPolicy` 增加交叉校验（`Σ max-concurrent-calls ≤ concurrency`，否则拒启）。

**预期收益**
- 依赖全挂时的「无效调用数 / 总调用数」：目标从接近 1.0 降到 < 0.1（熔断打开后不再调用）。
- 单依赖故障对**其他依赖**的 Run 成功率影响：目标 < 5 个百分点（舱壁隔离生效）。
- 新增可观测：`resilience4j.circuitbreaker.state`（按 name）、`...calls.not_permitted`。

**实施成本与风险**
- 改动面：3 个包装点 + 1 个配置类 + 1 个门禁；**不改 DDL**。
- 风险 1：熔断打开会把「本可恢复」的 Run 判成终态（`FAILED`），**语义上是正确的但用户感知是失败**。缓解：`wait-duration-in-open-state=30s` 后 half-open 试探；且错误码 `MODEL_CIRCUIT_OPEN` 在前端归为 `transient`（`errorGuidance.ts:131-144` 的 `TRANSIENT_CODES` 已含 `PROVIDER_ERROR` 类，需新增此码）——**注意：这与「不给重试」矛盾，需明确「新 Run 可重试，同一 Run 不可重试」**。
- 风险 2：舱壁 `max-wait-duration=0` 意味着立即拒绝，会放大「启动瞬间尖峰」的失败率。缓解：先灰度一个租户，观察 `not_permitted` 比例 < 5% 再全量。

**优先级**：P1
**排期**：P5「生产就绪」阶段，与改进点 1 的重试预算同批（两者互补：预算管速率，熔断管可用性）。

**验收门禁**
1. **单测（状态机）**：`DependencyBreakersTest` —— 注入 20 次失败 → 断言 OPEN；注入 5 次成功 → 断言 CLOSED。撤掉 `failure-rate-threshold` 配置 → 用例变红。
2. **语义门禁（最重要）**：`CircuitOpenSemanticsIT` —— 熔断打开时触发一次 Run，断言：① `run.state='FAILED'`；② `run.error_code='MODEL_CIRCUIT_OPEN'`；③ **MQ 消息被 ack 而非重投**（查询 `agent_message_queue` 无 RETRY 行）。**撤掉「熔断→FAILED（非 RETRYABLE）」的映射 → 该用例必然变红**（会观察到重投）。
3. **舱壁门禁**：`BulkheadIsolationIT` —— 用固定延迟的假模型（占用全部 MODEL_PROVIDER 并发）同时发起 RAG 调用，断言 RAG 调用**不被阻塞**（P95 延迟与无故障时差异 < 20%）。撤掉舱壁 → 变红。
4. **配置门禁**：`Σ bulkhead.max-concurrent-calls > agent.worker.concurrency` 时启动失败，单测锁定。

### 改进点 3 · 错误分类的机器可读契约（P0）

**问题陈述**
- 四套词表并存（`run.state` 7 值、`ExecutionOutcome.Kind` 9 值、`run.error_code` text 无约束、事件 payload state 字符串无约束），已产生 `TIMED_OUT` 悬空（§4.5-c）。
- 前端 `errorGuidance` 与后端错误码靠人手对齐（`SERVICE_CONFIG_CODES` / `TRANSIENT_CODES` 两个硬编码数组，`errorGuidance.ts:121-144`）。
- 任何新增错误码都可能漏配 → 前端落入「未知错误→不给重试」（安全）或「未知→给重试」（危险，取决于分支）。

**方案设计**
1. **新增单一枚举**：`platform/agent-core/src/main/java/cn/studykid/multiagent/core/error/ErrorCode.java`
```java
public enum ErrorCode {

    MODEL_TIMEOUT(Class.TRANSIENT, HttpStatus.SERVICE_UNAVAILABLE, "模型调用超时"),
    MODEL_RATE_LIMITED(Class.TRANSIENT, HttpStatus.TOO_MANY_REQUESTS, "模型限流"),
    MODEL_PROVIDER_ERROR(Class.TRANSIENT, HttpStatus.BAD_GATEWAY, "供应商内部错误"),
    RAG_UNAVAILABLE(Class.DEGRADED, HttpStatus.OK, "检索不可用，已降级"),

    // ── 不可重试（permanent）──────────────────────────
    MODEL_UNAUTHORIZED(Class.PERMANENT, HttpStatus.BAD_GATEWAY, "模型凭证失效"),

2. **DDL 加约束**（`deploy/sql/platform/02_platform_seed.sql` + 活库 ALTER，遵循项目结构变更纪律）：

ALTER TABLE public.run ADD CONSTRAINT run_error_code_known
  CHECK (error_code IS NULL OR error_code IN (
    'MODEL_TIMEOUT','MODEL_RATE_LIMITED','MODEL_PROVIDER_ERROR','MODEL_UNAUTHORIZED',

    'INTERNAL_ERROR','TENANT_BLOCKED','SAFETY_BLOCK'));
```
3. **修复 `TIMED_OUT` 悬空（二选一，本报告建议 B）**：
   - A：把超时路径改成 `commitResult(..., "TIMED_OUT", ...)`（需扩展 `commitResult` 的状态参数校验，且触发器已允许 `RUNNING→TIMED_OUT`）。
   - **B（推荐）**：**从 `run_state` 枚举中废弃 `TIMED_OUT`**（保留列值兼容，不再写入，读取方统一改用 `FAILED + error_code='TIMEOUT'`），并同步修正 `AgentMetricCollector.java:297`、`TraceFactPort.java:171`、`JdbcStatisticsRepository.java:247`、`RunListController.java:46` 四处读取方。
   - 理由：`FAILED + reason` 的表达力严格强于单独的 `TIMED_OUT`（可以区分模型超时/工具超时/根 deadline），且改动只在读取侧，无写入语义风险。**选 A 会让「超时」与「失败」在 state 上分叉，反而增加词表规模。**

**预期收益**
- 消除「错误码漏配」这一类故障：新增码若未在两处定义，CI 直接失败。
- 消除 `TIMED_OUT` 零值面板：看板「超时率」从恒 0 变为真实值（口径：`error_code='TIMEOUT'`）。
- 用户侧：所有失败都能落到「可重试 / 找管理员 / 找客服」三类之一，无「未知」。

**实施成本与风险**
- 改动面：新增 1 个枚举 + 1 个生成器 + 1 条 DDL 约束 + 4 处读取方 + 前端 2 个数组。**无数据迁移**（约束只对新写入生效，存量需先 SQL 普查）。
- 风险 1：`run_error_code_known` 上线前必须普查存量值，否则 ALTER 失败。普查 SQL：
```sql
SELECT error_code, count(*) FROM public.run WHERE error_code IS NOT NULL GROUP BY 1 ORDER BY 2 DESC;
```
- 风险 2：新增码需要 DDL 迁移，**每个新错误都要动 schema** —— 这是「错误码进 DB 约束」的固有代价。缓解：把约束改为「必须匹配 `^[A-Z][A-Z0-9_]{2,39}$`」的**形状约束** + 应用侧枚举校验，而不是白名单值约束。**本报告推荐这个折中**（既有形状保护，又不阻碍演进）。

**优先级**：P0（`TIMED_OUT` 修复 + 前端生成物 CI 校验）、P1（DDL 形状约束）
**排期**：P0 部分随下一补丁；P1 进 P5。

**验收门禁**
1. **一致性单测**：`ErrorCodeContractTest` —— 断言 `ErrorCode` 中每个值都在前端生成物中出现，且 `clientMayRetryNewRun()` 与 `errorGuidance` 的 `retryable` 判定**逐值相等**。撤掉生成器 → 用例红（生成物缺失）。
2. **CI 门禁**：`mvn verify` 后执行 `git diff --exit-code frontend/src/api/generated/`，有差异即 fail（**防止手改生成物**）。
3. **`TIMED_OUT` 反证**：`TimeoutTerminalStateIT` —— 触发一次单步超时，断言 `run.state='FAILED'`、`error_code='TIMEOUT'`、事件 payload 的 `state` 与 `run.state` **取值一致**（当前会红，因为事件写 `TIMED_OUT`）。**这条用例本身就是「语义失真」的回归守卫**。
4. **DDL 门禁**：`SchemaDriftIT`（项目已有）断言新约束存在于活库；`CheckConstraintIT` 断言写入 `error_code='not-a-code'` 被拒（形状约束生效）。
5. **存量普查门禁**：迁移脚本前置一段 `DO $$ ... RAISE EXCEPTION IF EXISTS(非法值) $$`，非法存量存在时迁移失败而非静默跳过。

### 改进点 4 · 死信队列的运维化（P1）

**问题陈述**
`agent_message_dead_letter` 注释明确「只进不出，须人工介入」（DDL `:1399`），但三件必需的事都没做：无查询 API、无重放、无告警。运维只能连库 SQL，且 `agent-api` 无任何 `dead` 端点（实测 grep 无命中）。后果：死信是一个**只增不减、不可见、不可处理**的债。

**方案设计**
1. **DDL 增补**（`02_platform_seed.sql` + 活库 ALTER）：
```sql
ALTER TABLE public.agent_message_dead_letter
  ADD COLUMN IF NOT EXISTS replayed_at    timestamptz,
  ADD COLUMN IF NOT EXISTS replayed_by    text,
  ADD COLUMN IF NOT EXISTS replay_run_id  uuid,          -- 重放后新产生的 queue 行
  ADD COLUMN IF NOT EXISTS disposition    text NOT NULL DEFAULT 'PENDING'
    CHECK (disposition IN ('PENDING','REPLAYED','DISCARDED','ESCALATED')),
  ADD COLUMN IF NOT EXISTS disposition_note text;

-- 重放门禁：同一条死信只允许重放一次（防人工连点造成重复副作用）
CREATE UNIQUE INDEX IF NOT EXISTS dead_letter_single_replay
  ON public.agent_message_dead_letter (tenant_id, dead_id)
  WHERE disposition = 'REPLAYED';
```
2. **端点**（新文件 `agent-api/.../governance/DeadLetterController.java`），三个动作，**全部需要 `AuthorizationService.Actions.UNKNOWN_DISPOSE` 级别的权限**（复用现有动作，不新增）：
```java
GET  /api/dead-letters?state=PENDING&limit=50          // 列表（按 failed_at 倒序，游标分页）
POST /api/dead-letters/{deadId}:replay                 // 重放
POST /api/dead-letters/{deadId}:discard                // 归档
```
3. **重放的安全门禁（四条，缺一不可）**：
   - ① 权限：`UNKNOWN_DISPOSE`；
   - ② **目标 Run 必须仍是可执行状态**：`SELECT state FROM run WHERE run_id=?` 必须是 `QUEUED`（终态 Run 重放 = 重跑已完成的 Run = Sev-0，呼应铁律 5）；
   - ③ **同一 `dead_id` 只能重放一次**（上面那个部分唯一索引 + `ON CONFLICT DO NOTHING`）；
   - ④ **载荷必须重新校验**（`OutboxMessage.assertPayloadSafe`），防止「重放时才发现消息本身有毒」。
   - 违反任一条 → `409 Conflict` + 明确错误码，**不做「尽力重放」**。
4. **告警（Gauge + 规则）**：
   - `Micrometer` 注册 `agent.dead_letter.pending`（按 tenant + event_type 打标签，每 30s 刷新一次，不要每次查询都打）；
   - Prometheus 规则：`agent_dead_letter_pending > 0` 持续 5 分钟 → 告警；`increase(...[1h]) > 10` → 升级告警。
   - **必须同时暴露 `agent.dead_letter.oldest_age_seconds`** —— 「有多少」不如「积压多久」，后者才说明是否有人在处理。

**预期收益**
- 死信从「不可处理」变为「可处理」；运维 MTTR 从「需要 DBA 介入」降到「控制台操作」。
- 可观测：`agent_dead_letter_pending`、`agent_dead_letter_oldest_age_seconds` 两个指标，使「死信积压」成为可告警的症状（T6：按症状告警）。
- 假死信（§5.3 劣-2 描述的「后来其实成功」）可通过「重放前置校验 ②」在重放时被发现并 `discard`。

**实施成本与风险**
- 改动面：1 条 DDL 迁移 + 1 个 Controller + 1 个 Service + 1 个 Gauge + 2 条告警规则。
- **最大风险：重放端点本身成为 Sev-0 的源头**。缓解：四条门禁 + 强制「终态 Run 不可重放」+ 重放动作写 `audit_record`（`AuditPort.Actions.UNKNOWN_DISPOSE` 同款做法，`JdbcUnknownOperationRepository.java:200`）。
- 次风险：`agent_message_dead_letter` 已有 FORCE RLS（`:1392`），新端点必须**在事务内绑定租户**（铁律 1），否则查询恒 0 行。

**优先级**：P1
**排期**：P5。

**验收门禁**
1. **门禁②的反证（最重要）**：`DeadLetterReplayIT` —— 构造一条死信，其 Run 已是 `SUCCEEDED`，调用 `:replay` → 断言 **409 + 无新 queue 行 + 无重放记录**。**撤掉「终态 Run 不可重放」校验 → 该用例必然变红**（会出现重跑已终态 Run 的记录）。
2. **门禁③的反证**：连续两次调用同一 `dead_id:replay` → 第二次 409；断言 `agent_message_queue` 只新增 1 行。撤掉部分唯一索引 → 变红（2 行）。
3. **RLS 门禁**：用租户 A 的 token 查租户 B 的死信 → 返回空列表（不是 403，沿用反探测 404 语义）；用 `app_agent`（NOBYPASSRLS）连接验证（铁律 1）。
4. **告警门禁**：`promtool check rules` 通过；且在 `agent_dead_letter_pending=1` 的撮合测（可用 `micrometer-test` 的 `SimpleMeterRegistry`）中断言 Gauge 值正确。
5. **审计门禁**：重放后 `audit_record` 必有一条 `UNKNOWN_DISPOSE` 动作记录（断言存在，且 payload 不含消息体原文——呼应「只存摘要」纪律）。

### 改进点 5 · 故障注入测试体系（P1）

**问题陈述**
现有验证是「单点反向守卫」（如 `TransactionBoundaryIT`），但**没有系统化的「依赖故障 → 预期行为」清单**。这意味着：新增一条依赖（比如换 RAG 实现）时，没人知道「它挂了会怎样」。

**方案设计**
新建 `platform/platform-bootstrap/src/test/java/.../chaos/FaultInjectionIT.java`（复用现有 IT 基座与假实现），**六条实验，每条一个断言组**：

| # | 注入 | 手法 | 预期行为（断言） |
|---|---|---|---|
| C1 | **DB 断连**（事务内） | 用 `DataSource` 代理，在第 2 条 SQL 抛 `SQLException` | ① 接口返回 5xx（**不是 201**）；② `run` 表**无**该 runId；③ 日志含「事务已被毒化」 |
| C2 | **MQ 不可用** | `MessageHandler` 抛 `RuntimeException` × 3 | ① 消息进死信（`agent_message_dead_letter` 1 行）；② `run.state='FAILED'`（孤儿兜底收敛）；③ **不重投第 4 次** |
| C3 | **模型超时** | 假网关 sleep > 剩余 deadline | ① `run.state='FAILED'`、`error_code='TIMEOUT'`；② **事件 payload 的 state 与 run.state 一致**（改进点 3 的回归守卫）；③ 预算预留已释放 |
| C4 | **工具 500** | 假工具抛 `ProviderStatusException(500)` | ① 工具层记 `FAILED`（**不是 UNKNOWN**）；② `tool_operation_attempt` **无新增**（终态后禁补）；③ 预算预留已释放 |
| C5 | **预算拒绝** | `budget_account` 预置 `reserved+settled = total_limit` | ① Run 终态 `FAILED`、`error_code='BUDGET_EXHAUSTED'`；② 工具**未执行**（无 `tool_operation` 行）；③ 前端指引落 `service-config` 类（`errorGuidance` 单测校验） |
| C6 | **RAG 不可用** | 假 RAG 返回 503 | ① 组件级 error + 空命中；② **Run 不失败**（可继续）；③ 上下文里**无伪造命中**（断言消息体不含任何 chunkId） |

另加两条「**语义不变量**」实验（不属于依赖故障，但同属本维度）：
| C7 | **重复投递** | 同一消息投两次 | ① 第二次 `DUPLICATE_DISCARDED`；② `run.fencing_token` 只 +1；③ 工具副作用只发生 1 次 |
| C8 | **UNKNOWN 后强行补 attempt** | 直接 INSERT `tool_operation_attempt` | ① DB 抛 `restrict_violation`；② 错误消息含「等同盲目重试」 |

**预期收益**
- 把「我们知道它应该怎样」变成「CI 证明它确实这样」，覆盖 6 个依赖 + 2 条不变量。
- 新人接手时，`FaultInjectionIT` 就是**故障行为的规格说明书**。

**实施成本与风险**
- 改动面：1 个测试类（8 个用例）+ 假实现（多数已存在：`FakeModelGateway` 已支持注入 TIMEOUT/RATE_LIMITED/PROVIDER_ERROR 等，`FakeModelGateway.java:77-101`）。
- 风险：C1/C2 需要操纵 DB/MQ，可能拖慢 CI。缓解：标记 `@Tag("chaos")`，在 `mvn verify` 中独立 profile 执行（约 +60s），PR 流水线全跑、本地默认跳过。

**优先级**：P1（C1/C3/C7 为 P0，因为它们覆盖最高危的三条失真）
**排期**：P4 末启动，P5 完成。

**验收门禁**
1. **每条用例自身必须能红**：对 C1..C8 逐条做「撤点验证」——例如 C3 撤掉 `commitFailure` 的 `TIMEOUT` 码 → 红；C8 撤掉触发器 → 红。**把逐条撤点记录写进用例的 Javadoc**（沿用 `TransactionBoundaryIT.java:238-239` 的写法）。
2. **覆盖率门禁**：断言 `ExecutionOutcome.Kind` 的 **9 个值**在 `FaultInjectionIT` 中每个至少被触发 1 次（用 `AtomicInteger` 计数器或观测者收集），缺失即 fail。这条门禁的意义是防止「新增一种结局但没人验证」。
3. **C3 的语义一致性断言必须写成双向**：断言 `event.payload.state == run.state`（不只是「都是终态」）。这是当前会红的用例（§4.5-c）。

### 改进点 6 · 降级路径的显式定义（P1，需先解决治理冲突）

**问题陈述**
当前「降级」是零散的、隐式的：RAG 挂了转空命中（好），上下文摘要失败回落 W2（好），但**模型不可用时没有任何降级**（直接失败），**预算耗尽时是拒绝**（正确但未在契约里声明为一种「降级」）。缺一份「哪种依赖挂了，系统退到什么形态」的显式定义。

**方案设计（含一个必须先解决的治理冲突）**
1. **冲突先讲清**：本项目有一条明确纪律——「`cap_agent_def.model_ref` 为 NULL 时**绝不回落默认模型**」（梳理报告维度 13，DDL `:1664-1667`）。因此「模型不可用 → 降级到备用模型」**不能**实现为「运行期自动挑一个能用的」，那会绕过治理发布。正确做法是**把降级链写进治理发布物**：
```sql
-- 03_platform_roles.sql 之后新增（02_platform_seed.sql 结构变更）
ALTER TABLE public.cap_agent_def
  ADD COLUMN IF NOT EXISTS fallback_model_refs jsonb NOT NULL DEFAULT '[]'::jsonb;
-- 约束：必须是数组、长度 ≤ 3、元素形如 {"modelRef": "...", "maxAttempts": 1}
ALTER TABLE public.cap_agent_def ADD CONSTRAINT fallback_model_refs_shape
  CHECK (jsonb_typeof(fallback_model_refs) = 'array'
         AND jsonb_array_length(fallback_model_refs) <= 3);
```
该列随 Agent 定义进入 `execution_snapshot`（不可变），**运行期只读**——符合「治理期发布、运行期钉死」。
2. **降级矩阵（写成文档 + 代码常量，两处一致）**：

| 依赖 | 降级形态 | 是否影响 Run 终态 | 用户可见文案 | 关联铁律 |
|---|---|---|---|---|
| RAG 不可用 | 空命中 + 组件级 error | **否**（继续） | 无（静默降级，但事件留痕） | 铁律 14 |
| 上下文摘要失败 | 回落 W2 裁剪 + `fallback=true` | 否 | 无 | 维度 6 |
| 模型主引用不可用 | 依次尝试 `fallback_model_refs`（每个 1 次） | 全部失败才 FAILED | 「本次分析未能完成」+ 可重试 | 铁律：不得运行期自选模型 |
| 预算耗尽 | **明确拒绝**（不降级） | 是（`BUDGET_EXHAUSTED`） | 「额度不足，请联系管理员」 | 铁律 8 |
| 审批源不可用 | **fail-closed 拒绝**（不降级） | 是 | 「需要审批但审批服务不可用」 | 铁律 8 |
| MQ 不可用 | outbox 重试 + 背压停发 | 最终是（`max-publish-attempts`） | 「服务繁忙」 | 维度 12 |

3. **代码落点**：`agent-worker/.../execute/FallbackModelResolver.java`（新类），在 `RunExecutionLoop` 取 `AgentModelConfig` 之后、第一次模型调用之前解析出「候选模型序列」；**每次切换必须写 `run_event`**（`eventType=RUN_MODEL_FALLBACK`，payload 只放 `fromRefKind/toRefKind` 与 `reason`，绝不落模型名与 key）。

**预期收益**
- 单供应商故障时的 Run 成功率：目标从 ~0% 提升到 > 80%（假设 fallback 链中有一个健康模型）。
- 用户侧：不再是「系统坏了」，而是「慢一点但完成了」。
- 可观测：`agent.model.fallback.total{from,to}` 计数 → 直接反映主引用健康度（补充改进点 2 的熔断信号）。

**实施成本与风险**
- 改动面：1 条 DDL + 1 个新类 + `RunExecutionLoop` 1 处注入 + 1 个事件类型 + 前端 `errorGuidance` 增补。
- 风险 1：**成本与计费口径变化**（换模型后单价不同）——`usage_record.model_id` 已按次记录（DDL `:3041`），但「单 Run 跨模型」会让成本报表需要按 model_id 分组才能算准。需在 `ModelPricingPolicy` 确认支持多模型（现状 `application.yml:529-533` 已有按模型定价表，满足）。
- 风险 2：**降级可能掩盖主引用长期故障** —— 必须配 `agent.model.fallback.total` 的告警（连续 > 10 次/小时即告警），否则「一直在降级跑」会变成新的静默失效。
- 风险 3：治理侧需要 UI 支持（填 fallback 链），否则该列永远为空 = 无降级。**因此本项排在改进点 3 之后**。

**优先级**：P1（RAG/摘要类降级已具备，仅需文档化，P2；模型降级 P1）
**排期**：P6。

**验收门禁**
1. **治理门禁**：`fallback_model_refs` 未发布时，运行期**不得**尝试任何其他模型——`NoImplicitFallbackIT`：构造一个只有主引用且主引用不可用的场景，断言 `MODEL_PROVIDER_ERROR` 终态且**无第二次模型调用**（用假网关计数器）。撤掉「只读发布物」约束 → 变红。
2. **降级链门禁**：`FallbackChainIT` —— 主引用 500，fallback 成功，断言 ① `run.state='SUCCEEDED'`；② `run_event` 有且仅有 1 条 `RUN_MODEL_FALLBACK`；③ `usage_record` 两行、`model_id` 不同。
3. **静默失效门禁**：`FallbackAlarmIT` —— 连续 11 次降级后，告警计数器 > 阈值（用 `SimpleMeterRegistry` 断言）。
4. **RAG 降级门禁**：C6（改进点 5）已覆盖，此处只需断言「无伪造命中」与「Run 不失败」两条同时成立。

## 八、其他有价值的横向对比

### 8.1 与本项目其他维度的耦合与相互约束

**耦合 1 · 与维度 3（状态持久化）：重试安全完全依赖幂等与 fencing**
本维度所有「可重试」的判断，其安全性都来自维度 3 的三件东西：`idempotency_record`（同请求不重复建 Run）、`run_message.idem_key`（冲突覆盖而非追加）、`fencing_token`（旧世代写不进）。
**约束**：若维度 3 的幂等键设计改变（例如把 key 从 `(tenant, key_namespace, key)` 改为业务键），本维度的「可重试」范围必须同步收缩——**这是改维度 3 时必须回归维度 11 的原因**。反向亦然：把 `max-attempts` 从 3 提到 5，会让「幂等冲突」路径被触发得更多，可能暴露幂等实现的边界。

**耦合 2 · 与维度 9（成本预算）：UNKNOWN 不释放额度与降级换模型相互拉扯**
UNKNOWN 越多，`budget_account.reserved_amount` 越虚高；而改进点 6 的「降级换模型」会让单 Run 成本波动变大。
**约束**：不能为了「让额度看起来健康」而在 UNKNOWN 时释放预留（那是 Sev-0 级的账实不符）；正确做法是**加快对账**（改进点 4 的自动对账 + 人工处置效率）。另外，降级链的每个 fallback 都必须有单价（`application.yml:529-533` 的定价表），否则成本会按 0 记并打 WARN——「空表 ≠ 按 0 元计费」这条注释（`:519-524`）在此处同样适用。

**耦合 3 · 与维度 4（流式）与维度 10（可观测）：故障的「最后一公里」在两个下游**
`errorGuidance`（维度 4 的客户端侧）决定用户是否被告知「别再等了」；`RunRecoverySweeper.healthy()` 与死信 Gauge（维度 10）决定运维是否被告知「恢复链路已死」。
**约束**：本维度可以做到「终态正确」，但只要这两处下游没接完，**故障就只对数据库正确，对人不正确**。这正是本报告把改进点 4 与「eventStream 接入 errorGuidance」列为高优先级的原因。

### 8.2 与非 agent 领域成熟做法的对照

| 领域 | 成熟范式 | 与本项目的对照 | 可借鉴点 |
|---|---|---|---|
| **支付/清算** | 幂等键 + 差错处理（exception queue）+ 日终对账 | 本项目已有 `idempotency_key` 与 UNKNOWN 对账，但**缺「日终自动对账」**（人工触发） | 引入定时对账任务 + 差异报表；对账结果必须是「三态」（已确认/已否定/仍未知），不允许二元化 |
| **电信/骨干网** | 熔断 + 限流 + 过载保护（load shedding）三级 | 本项目有背压（shedding 雏形）与并发度上限，缺熔断 | 分级降载：先拒绝低优先级（如 `trace.collect`），再拒绝新 Run，最后才降级已跑 Run |
| **航空/核电** | Checklist + 冗余 + 「异常即停」（fail-safe） | 本项目的 fail-closed 与 checklist 精神一致（铁律 27 条） | 「异常即停」的边界要写清：本项目对「工具 UNKNOWN」停，对「RAG 失败」不停 —— 这个分级已存在但未文档化 |
| **数据库** | WAL + checkpoint + 崩溃恢复（ARIES） | 本项目用 outbox + 租约 + fencing 实现了「等价的重做日志」 | ARIES 的「分析-重做-撤销」三阶段可直接映射为「sweeper-重放-补偿」；当前只有前两阶段 |
| **SRE 实践** | error budget + burn-rate 告警 | 本项目无 SLO/error budget（维度 10 已记） | 若定义 SLO = 「Run 终态成功率」，则本维度的 `RETRY_BUDGET_EXHAUSTED` 与死信数量可直接作为 burn-rate 的输入 |

### 8.3 反向思考：若从头重做本维度，我们会怎么设计？

**会保留的（判断正确的部分）**
1. **UNKNOWN 作为一等状态**，且 DB 层禁止重放。这是本项目最正确的决定，任何重做都应保留。
2. **POISONED 事务标记**。成本极低（一个 ThreadLocal + 两处检查），收益是消灭一整类静默失真。
3. **恢复靠合法接手 + fencing**，而不是「重试到成功」。
4. **配置 fail-closed**。

**会改的（顺序与边界）**
1. **先定义错误契约，再写错误处理**。现状是「先有各种 `error_code` 字符串，后想办法统一」。重做时会先写 `ErrorCode` 枚举（含 `Class` 与 HTTP 映射），再让所有失败路径**只能**从枚举取码——这样 §4.5-c 的 `TIMED_OUT` 悬空在编译期就不可能发生。
2. **重试策略与通道解耦**。现状是「退避写在 `PgQueueListener` 里、立即重投写在 `RabbitExecutionListener` 里」，导致两通道语义漂移（D-4）。重做时会把 `RetryPolicy(backoff, jitter, budget)` 抽成通道无关的对象，两条通道只是执行器。
3. **把「失败」当成有主人的工单**。现状死信与 UNKNOWN 都无 owner（§4.5-d、改进点 4）。重做时会从第一天就让每条死信带 `owner_role` 与 `sla_deadline`，超时升级——这是把「可靠性」从技术问题变成组织问题的唯一办法。
4. **不引入 `run.state` 的细粒度终态**。重做时终态只用 `SUCCEEDED / FAILED / CANCELLED / WAITING_APPROVAL`，其余全部用 `error_code` 表达。理由：`TIMED_OUT` 这类细粒度终态的**收益是语义清晰，代价是每个新终态都要改状态机、改所有读取方、改前端映射**——而 `error_code` 已经在做同样的事，两者重复。**现状的 `TIMED_OUT` 悬空正是这个重复的代价。**
5. **混沌实验从第一天进 CI**，而不是事后补（改进点 5）。

**取舍的诚实说明**：以上第 1、2、4 条都需要在项目早期确定，现在改的迁移成本明显更高（第 4 条甚至会触及状态机触发器与所有读取方）。因此本报告在改进点里**没有建议废除细粒度终态**，而是建议「修复 `TIMED_OUT` 的写入方」或「废弃它」二选一（改进点 3 选 B）。这是**承认历史成本的现实选择**，不是认为现状更优。

## 九、对产品演进的启发

### 9.1 本维度支撑的产品能力（用户能感知什么）

| 产品能力 | 用户感知 | 背后依赖 |
|---|---|---|
| **「失败会明确告诉你，而且不会再骗你」** | 失败的 Run 显示「本次分析未完成」+ 一个可报障的标识，而不是永远转圈 | POISONED + 终态不可伪装 + `errorGuidance` |
| **「不会重复扣费、不会重复改数据」** | 同一次分析重发，不产生第二次写学生数据 | 幂等记录 + UNKNOWN 禁重放 + fencing |
| **「系统抖动后能自己回来」** | 服务端抖动后 1 分钟内 Run 继续跑完，用户只需等待 | 租约 + sweeper + `RETRYABLE_FAILURE` |

### 9.3 风险清单（做这一步可能踩的坑，关联已知铁律）

| # | 风险 | 触发条件 | 缓解 | 关联铁律 |
|---|---|---|---|---|
| R-1 | **重放端点成为 Sev-0 源头** | 允许重放终态 Run / 未做单次去重 | 四条门禁 + 部分唯一索引 + 审计 | 铁律 5（终态重跑） |
| R-2 | **熔断把可恢复故障判成终态** | `wait-duration` 过长 / 阈值过松 | half-open 试探；错误码归 `transient` 供**新 Run** 重试；灰度单租户 | 铁律 15（新 Run 重试 ≠ 同 Run 重试） |
| R-3 | **抖动掩盖了真实的同步问题** | 抖动过大导致重试时刻不可复现 | `ratio` 可配为 0；日志必须记录**实际延迟**而非计算延迟 | 铁律 6（可复现性） |
| R-4 | **错误码 DDL 约束挡住热修** | 白名单值约束 + 紧急新增错误码 | 用**形状约束**而非值白名单（改进点 3 的推荐折中） | 铁律 2（枚举/约束） |
| R-5 | **降级链绕过治理发布** | 运行期「找不到主模型就随便挑一个」 | 只读 `execution_snapshot`；无发布物则必须失败 | 铁律 8（fail-closed）+ 维度 13 |
| R-6 | **自动对账把「读己之写延迟」误判为不存在** | 未设宽限期 | 沿用 `gracePeriod`（`ToolOperationReconciliationService.java:22-26`）；宽限期内保持 UNKNOWN | 铁律 14（按对端真实行为取值） |
| R-7 | **死信查询走错角色** | 用 `app_agent` 查无权限 / 忘绑租户 | 事务内绑定 GUC + 用 `app_agent` 验证（NOBYPASSRLS） | 铁律 1、铁律 7 |
| R-8 | **新增保护反而引入新静默** | 熔断打开后无人告警 | 每个新机制必须自带一个 Gauge（不可观测 = 不可运维） | 维度 10 的「有日志≠可察觉」 |

### 9.4 一句话结论

**本项目在「失败之后是否说真话」这件事上做到了行业内少见的严谨（POISONED、UNKNOWN 禁重放、DB 终态强制），但在「失败之前如何不死」这件事上还停留在最朴素的有界重试（无抖动、无预算、无熔断），且三处已经正确设计的机制（死信、自动对账、恢复健康事实）因为「没有出口」而处于悬空状态——把出口接上，比再加一道防线更重要。**

| 世代令牌 | fencing token | 单调递增的写权限凭证，拒绝旧世代写入 |
| 租约 | lease | 有时限的执行所有权 |
| 结果未知 | UNKNOWN | 请求已发出、响应丢失，副作用可能已发生 |
| 对账 | reconciliation | 通过查询下游事实来判定 UNKNOWN 的真实结果 |
| 崩溃恢复扫描 | recovery sweep | 周期性接管租约已过期的 RUNNING |
| 幂等键 | idempotency key | 使重复请求产生同一结果的标识 |
