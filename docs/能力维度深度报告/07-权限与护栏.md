## 一、维度定义与评估坐标系

### 1.1 这个维度到底解决什么问题（问题陈述，不谈实现）

"权限与护栏"回答的不是"agent 能干什么"，而是"**谁、在什么条件下、被允许做什么，以及当内容或行为越界时系统如何反应**"。它要解决四条独立的威胁链：

- **授权链**：主体（用户/Worker/平台运维）对资源（Run/Agent/工具/审批/审计）的每一次敏感动作，都必须经过"当前有效"的授权判定；授权被撤销后，在途请求应当失效，而非长期越权。
- **隔离链**：多租户下，主体只能看到/改动自己租户的数据；越权读不得返回数据，越权写不得落库。
- **内容链（护栏）**：模型产出与用户输入中可能夹带可识别信息（PII）、有害内容、越狱话术，或试图把不可信数据当作指令执行（提示注入）。系统必须在输入侧与输出侧都部署防线。
- **失败语义链**：当判定服务、脱敏服务、审批源本身不可用时，系统必须**默认拒绝**（fail-closed），而非默认放行（fail-open）。

这一维度是维度 2（多租户隔离）、维度 5（工具调用）、维度 9（预算）、维度 13（HITL）的**交叉约束面**——几乎所有敏感动作都要先过它。

### 1.2 能力分层的四档模型（通用分层法）

按"授权判定与护栏由哪一层强制、是否默认拒绝"给出四档，从弱到强：

| 档位 | 名称 | 授权/护栏由谁持有 | 代表形态 | 典型代价 |
|---|---|---|---|---|
| **L0 无内置** | 宿主应用自管 | 宿主代码里的 ad-hoc `if` | 多数 agent 库（OpenAI/Anthropic/ADK/AutoGen 默认形态） | 越权与否全靠开发者自律，易漏 |
| **L1 应用层显式 Gate** | SDK/库内提供鉴权 hook | 应用层中间件/拦截器 | LangGraph `AgentMiddleware`、CrewAI `before_tool_call`、Agno guardrails | 绕过 hook 即失效，不变量靠约定 |
| **L2 框架层强制** | 框架提供不可绕过的护栏原语 | 框架执行引擎内置 | 本平台的 `ToolInvocationGate` + `AuthorizationService`（应用层但唯一、不可绕过） | 开发侧需显式接 hook，但仍可被旁路 |
| **L3 数据层强制 + 应用层双写** | 存储触发器 + 应用层 Gate 双保险 | DB 触发器（状态机/RLS）+ 显式 Gate | **本平台（RLS `FORCE RLS` + `enforce_*_transition` 触发器 + 应用层 `AuthorizationService` + 影子对账）** | 部署复杂、需正确绑 GUC 与角色 |

**判定**：本平台落在 **L3（数据层强制）+ L2（应用层唯一 Gate）双保险**，是本次对比中唯一把"授权判定"同时下沉到数据库策略层（RLS）与执行层 Gate 的方案；护栏面（输出 moderation、提示注入信任围栏）落在 L2。竞品普遍落在 L0–L1。

**为什么 L3 在实践中罕见**：把授权不变量下沉到数据库触发器/RLS，意味着应用层任何 bug、任何绕过 Gate 的代码路径，都会被存储层二次拦截。代价是部署必须正确绑定 GUC（`app.tenant_id`）、正确授予 `app_agent` 角色（`NOBYPASSRLS`），且策略与触发器需随 schema 一起迁移（`01_platform_ddl.sql` 与 `03_platform_roles.sql` 必须配套）。多数框架选择 L0–L1 正是为了"轻"——把这部分复杂度推给宿主。本平台选择 L3 是因为其产品定位是"带强治理的生产运行时"（见维度 1 结论），而非"库"。

### 1.3 评估坐标系：5 个评价轴

| 轴 | 含义 | 观测方式（如何度量） |
|---|---|---|
| **强制程度** | 不变量（越权读返回 0 行、越权写被拒、判定服务不可用时默认拒绝）由哪一层强制 | 注入越权查询看是否返回 0 行；`authz_version` 撤销后在途请求是否失效；判定服务宕机是否仍拒绝 |
| **可审计性** | 谁何时对什么被判允许/拒绝，可否复盘 | 是否存在不可变判定流水（`authz_decision_log`）；读写权限是否分离 |
| **细粒度** | 动作矩阵是否足以表达"双人复核不被同一身份绕过"等约束 | 角色×任务动作数；是否可表达 `config:request` 与 `config:approve` 分离 |
| **护栏完整性** | 输入/输出/提示注入/PII 是否都有防线，且 fail-closed | 输出命中 PII 是否脱敏、命中毒性是否阻断；输入侧是否有信任隔离；判定服务不可用是否拒绝 |
| **失败可诊断性** | 护栏/权限失效时能否定位、是否能灰度切换 | 影子对照是否产出非平凡信号；`block-on-violation` 翻转是否有门禁 |

### 1.4 本维度在 agent 系统中的位置（上下游依赖）

```
   用户请求 ──▶ API 层（JWT 验签 → 主体角色以 principal_role 表为准）
                    │
                    ▼
   RunCreationService ──▶ AuthorizationService.requireAuthorized(RUN_CREATE)
   （创建期授权一次，写 authz_version 快照）
                    │
   ┌──────────────── 事件边界 ────────────────┐
                    ▼
   RunExecutionLoop（每轮）
      ├─ AuthorizationService.isAuthorized(TOOL_INVOKE/...)   ← 执行时重新授权（authz_version 校验）
      ├─ ToolInvocationGate（15 步准入：Schema→授权→幂等→账本→审批→预算→执行）
      │     └─ RiskBasedApprovalPolicy.ApprovalSource 默认 FAIL_CLOSED
      ├─ PromptGuard（输入侧：信任围栏 + 长度/深度上限 + 注入观测）
      ├─ 模型输出 ──▶ OutputModeration（PII 脱敏 / 毒性·越狱阻断，fail-closed）
      └─ authz_decision_log INSERT（每判定一行，app_agent 仅 INSERT）
                    │
   依赖的下游维度：多租户隔离(02) · 工具调用(05) · 预算(09) · HITL(13) · 可观测(10) · 可靠性(11)
   平行对账：AuthzShadowBinding/Hooks/Reporter（应用层 Gate 判定 vs RLS 基线，影子期只记不拦）
```

**关键依赖**：本维度的"重新授权"与"authz_version"强依赖维度 02 的 RLS/GUC 与 `principal_role` 真相表；输出 moderation 的 PII 检测与维度 05 的零保留闸门、维度 13 的审批状态机共享 `DataClassification`/`ClosureResolutionException` 等原语。

**核心准入契约（ToolInvocationGate 的 15 步门禁）**：工具调用的执行链被显式写成不可绕过的契约（维度 5 已述，此处从权限角度复看）：

| 序号 | 步骤 | 与权限/护栏的关联 |
|---|---|---|
| 1 | Schema 校验 | 闭集校验：未声明参数不传入（维度 5） |
| 2 | **执行时重新授权** | `AuthorizationService.isAuthorized(TOOL_INVOKE, ...)`，`authz_version` 比对 |
| 3 | 幂等键 | 防重复副作用 |
| 4 | 账本 | 每次工具操作落 `tool_operation` |
| 5 | **审批（FAIL_CLOSED）** | `RiskBasedApprovalPolicy.ApprovalSource` 默认 `DENY_ALL_APPROVALS` |
| 6 | **预算预留（FAIL_CLOSED）** | 预留失败即拒，降级放行=无限花钱 |
| 7 | 执行 | 仅上述全过才执行 |
| 8 | 账本更新 | 结算/释放 |

其中第 2、5、6 步是本维度的直接落点，且全部 fail-closed。该 Gate 明确禁止走 Spring AI `ToolCallingAdvisor` 的自动执行路径（会绕过全部门禁，ADR-011 §3.3）——这是"Gate 不可绕过"的硬约束。

## 二、理论体系（必须引用真实出处）

### 2.1 核心理论/概念框架（逐一给真实出处）

#### (1) RBAC — 基于角色的访问控制
- **出处（核实）**：Ferraiolo, D. F., Sandhu, R., Gavrila, S., Kuhn, D. R., Chandramouli, R., *"Proposed NIST Standard for Role-Based Access Control"*, ACM Transactions on Information and System Security (TISSEC), Vol. 4, No. 3, 2001, pp. 224–274。NIST 另以 RBAC 作为 ANSI/INCITS 359 标准基础。
- **定义**：权限不直接授予用户，而是授予角色；用户通过被赋予角色获得权限。核心组件：用户-角色分配（URA）、角色-权限分配（PRA）、角色层级（RH）、约束（含 SSD/RSSD 静态/动态职责分离）。
- **与本维度的关系**：本平台的 `AuthorizationService.Roles`/`Actions`（`AuthorizationService.java:180-247`）+ `principal_role` 表（`01_platform_ddl.sql:2677-2685`）正是 RBAC 的工程实现——`principal_role` 注释明确"JWT 中的 roles 仅为声明，实际生效角色以此表为准"，对应 RBAC 的"权威角色源"。

#### (2) ABAC — 基于属性的访问控制
- **出处（核实）**：Hu, V. C., Kuhn, D. R., Ferraiolo, D. F., Voas, J., *"Guide to Attribute Based Access Control (ABAC) Definition and Considerations"*, **NIST Special Publication 800-162**, 2014。
- **定义**：授权决策基于主体/资源/环境/操作的属性（如"租户 ID""风险等级""时间"），而非固定角色。适合细粒度、动态策略。
- **与本维度的关系**：本平台当前是 RBAC 为主、`AgentOverrides`（风险上限 `lowerRiskCeiling`）+ `run.deadline_at`/租户配额等属性为辅的**混合态**。维度 7 改进点 5 即从 RBAC 升级到 ABAC/PBAC 以支撑属性策略（见第七章）。

#### (3) PBAC / Policy-as-Code — OPA(Rego) 与 AWS Cedar
- **出处（核实）**：Open Policy Agent（OPA），Rego 策略语言，官方文档 <https://www.openpolicyagent.org/docs/latest/>（Styra 维护，CNCF 毕业项目）；AWS Cedar 策略语言，官方文档 <https://docs.cedarpolicy.com/> 与 AWS Verified Permissions。
- **定义**：把授权策略表达为可执行代码，与业务解耦，可版本化、可测试、可集中评估。
- **与本维度的关系**：本平台的 `AuthzShadowPolicyDefaults.rules()`（`AuthzShadowPolicyDefaults.java:161-166`）已暴露出"策略规则"的雏形（RETRIEVE + TENANT + TENANT_ONLY），但尚未形成外部化策略引擎。其"规则集"目前是 Java 常量，是向 PBAC 演进的天然接口点。

#### (4) Zero Trust — 零信任架构
- **出处（核实）**：Rose, S., Borchert, O., Mitchell, S., Connelly, S., *"Zero Trust Architecture"*, **NIST Special Publication 800-207**, 2020。
- **定义**："永不信任，始终校验"（never trust, always verify）；每次访问都基于主体、设备、环境动态评估，不依赖网络位置隐含信任。核心原则之一是"假定失陷"（assume breach）。
- **与本维度的关系**：本平台"执行时重新授权"（每次敏感动作前都重判当前授权，而非仅创建期一次）正是零信任"每次访问都校验"的工程落地；`authz_version` 递增使陈旧上下文失效，对应 ZT 的"持续评估"。

#### (5) Least Privilege / Defense in Depth
- **出处（核实）**：Saltzer, J. H., Schroeder, M. D., *"The Protection of Information in Computer Systems"*, ACM Computing Surveys, Vol. 9, No. 4, 1975（最小权限列为八大设计原则之首）。Defense in Depth 在 NIST SP 800-53（Security Controls）与 SANS 术语体系中均为基线控制思想。
- **定义**：主体只拥有完成任务所需的最小权限；多重独立防线叠加，任一单层失效不致全面失守。
- **与本维度的关系**：本平台"RLS 默认拒绝 + 应用层 Gate 重新授权 + 复合外键完整性"三层叠加即 Defense in Depth；`principal_role` 不授予 `PLATFORM_ADMIN` 给租户主体、`isAudienceOnly` 收窄受众可见范围，即最小权限。

#### (6) fail-closed vs fail-open
- **出处（核实）**：OWASP Application Security Verification Standard（ASVS），V1（Architecture）与 V4（Access Control）明确要求"访问控制在错误时默认拒绝"（fail securely / secure failure）。亦见 OWASP "Fail Securely" 设计原则。
- **定义**：当授权组件（判定服务、审批源、脱敏引擎）不可用或判定不确定时，系统必须**默认拒绝**（fail-closed），而非默认放行。fail-open 是越权与数据泄露的经典根因。
- **与本维度的关系**：本平台多处 fail-closed：`ToolInvocationGate` 的 `approvalSource` 默认 `FAIL_CLOSED`（`ToolInvocationGate.java:64,207`）；`OutputModeration.defaultActionFor` 未知类别按 `BLOCK`（`OutputModeration.java:130-137`）；`AgentOverrides.parse` 解析失败抛 `ClosureResolutionException`（`AgentOverrides.java:57-59`）；`PermissionResolver` 任何对象解析不到即抛异常（`PermissionResolver.java:49-53`）。

#### (7) OWASP Top 10 for LLM Applications
- **出处（核实）**：OWASP, *"OWASP Top 10 for Large Language Model Applications"*, 2025 版（首版 2023）。相关项：
  - **LLM01 Prompt Injection**：提示注入——将不可信内容当指令执行；
  - **LLM02 Sensitive Information Disclosure**：敏感信息（含 PII）泄露；
  - **LLM03 Supply Chain**：供应链（含第三方模型/工具/向量库）风险；
  - **LLM06 Overreliance**：对模型输出的过度信赖（不校验即执行）。
- **与本维度的关系**：本平台 `PromptGuard`（信任围栏 + 不可信标记）对应 LLM01 的缓解；`OutputModeration` 的 PII 脱敏与毒性/越狱阻断对应 LLM02；`ToolInvocationGate`"模型不自动执行"对应 LLM06。

#### (8) NIST AI RMF 1.0
- **出处（核实）**：NIST, *"AI Risk Management Framework (AI RMF 1.0)"*, NIST AI 100-1, 2023。四大职能：Govern / Map / Measure / Manage。
- **定义**：对 AI 系统风险做全生命周期治理，强调可测量、可治理、可问责。
- **与本维度的关系**：本平台"判定流水 + 风险事件只存摘要 + 不超发预算 + 影子灰度"正是 AI RMF "Measure/Manage" 的可审计落地。

#### (9) 提示注入分类与防护
- **出处（核实）**：
  - Greshake, K. et al., *"Not what you've signed up for: Compromising Real-World LLMs via Indirect Prompt Injection"*, **arXiv:2305.13851**（注：用户任务书引用 2310.12815，按 arXiv 编号核验未能定位到该精确编号的对应论文；本报告采用同主题、可核验的 Greshake et al. arXiv:2305.13851，并诚实标注任务书所给编号未核实到对应文献）。
  - Liu, Y. et al., *"Prompt Injection Attacks and Defenses in LLM-Integrated Applications"*, **arXiv:2402.07838**, 2024。
- **定义**：提示注入分**直接注入**（用户直接在对话里诱导）与**间接注入**（经工具结果/检索内容/记忆等外部数据夹带）。防护分"输入侧检测/隔离"与"架构侧不信任模型决定"两类。
- **与本维度的关系**：本平台 `PromptGuard` 的 `wrapToolResult`（工具结果标 `trust="untrusted"`）、`memory_context` 围栏（记忆内容源自模型历史输出，是经典二次传播路径）对应间接注入防护；但其**检测只观测不拦截**（见 4.2/5.3），主防线是"Gate 不信任模型决定"。

#### (10) 输出审核 / 内容安全
- **出处（核实）**：OpenAI Moderation API，官方文档 <https://platform.openai.com/docs/guides/moderation>；Azure AI Content Safety，官方文档 <https://azure.microsoft.com/en-us/products/ai-services/ai-content-safety>。业界通行做法为"分类器 + 规则混合"，输出侧 moderation 与输入侧并行。
- **定义**：对模型输出做有害内容/PII/越狱检测，命中后脱敏或阻断。
- **与本维度的关系**：本平台 `OutputModeration`（`OutputModeration.java:46`）是平台侧输出 moderation，修复前只有模型侧过滤且 `SENSITIVE_OUTPUT` 只观测不阻断（见类注释），现改为 fail-closed。

#### (11) 数据分类与 PII 检测（合规驱动）
- **出处（核实）**：GDPR（EU 2016/679，第 4(1) 条定义个人数据、第 9 条特殊类别）；HIPAA（美国《健康保险流通与责任法案》，受保护健康信息 PHI）；PCI-DSS（PCI 安全标准委员会，支付卡数据）。PII 含身份证号、手机号、邮箱、账号等。
- **定义**：PII 为可识别自然人的任何信息；不同法规对"是否可识别""是否跨境"有不同口径。
- **与本维度的关系**：本平台 `DataClassification.IdentifyingPattern`（`DataClassification.java:90-149`）用正则黑名单检测身份证号/手机号/学号/邮箱，作为零保留闸门与输出脱敏的检测基础。

#### (12) 影子模式（Shadow / Dark Launch）
- **出处（核实）**：Google SRE Book, *"Site Reliability Engineering"*（Beyer et al., 2016）第 17 章讨论"Shadow Traffic / Dark Launch"；Humble & Farley, *"Continuous Delivery"*（2010）讨论金丝雀与影子部署。
- **定义**：新逻辑与旧逻辑并行运行，新逻辑结果只观测不生效，比对差异后再切换。用于"强一致迁移"（如把授权从 RLS 下移到应用层 Gate）时降低风险。
- **与本维度的关系**：本平台 `AuthzShadowBinding`/`AuthzShadowHooks`/`AuthzShadowReporter`（P1 影子期只记不拦，P2 双写期 `block-on-violation` 翻转）是权限/护栏体系迁移的灰度方法论，详见 4.4。

### 2.2 理论给出的「设计张力」（trade-off）清单

| 张力 | A 方案 | B 方案 | 本平台取舍 |
|---|---|---|---|
| **授权层位置** | A：仅 RLS（数据库隐式生效，应用无感） | B：应用层显式 Gate（可表达"重新授权/影子对账"） | B 为主 + A 为基线（双层），代价是部署复杂度 |
| **判定失败语义** | A：fail-open（不可用即放行，体验好） | B：fail-closed（不可用即拒绝，安全） | B（铁律 8），代价是可用性风险 |
| **注入检测策略** | A：检测即拦截（启发式阻断） | B：检测只观测 + 硬上限兜底 | B（避免教育场景误杀），代价是注入不被主动阻断 |
| **权限模型表达力** | A：RBAC（简单、可解释） | B：ABAC/PBAC（细粒度、可组合） | A 起步，预留 B 接口（见改进点 5） |
| **PII 检测引擎** | A：re2j（线性时间、防 ReDoS） | B：JDK 引擎（支持 lookbehind） | B 路径保留（铁律 21），代价是潜在 ReDoS 风险由规则审查兜底 |
| **护栏灰度** | A：直接切换（简单） | B：影子双写（安全但长周期） | B（P1 影子→P2 双写），代价是迁移周期长 |

**元张力**：上述 6 条张力在更抽象的层面都收敛为同一条——**"安全强度 vs 部署/运维轻量 + 可用性"**。本平台几乎全部选了"强"的一侧（B 列），唯一在"注入检测"上刻意选了 A 列（检测只观测），因为教育场景下"误杀正常数学题"的代价高于"漏过一次注入观测"。这一选择不是对 fail-closed 的违背，而是把 fail-closed 的落点从"检测层"转移到了"架构层"（Gate 不信任模型决定 + 信任围栏 + 硬上限），与铁律 8 不冲突。理解这一点，是读懂本维度所有设计取舍的总钥匙：本平台宁愿牺牲一点"开箱即用"的轻量感，也要把不变量钉死在数据层与应用层两处。

### 2.3 业界公认的反模式（anti-pattern）清单及判别方式

1. **fail-open 护栏**（OWASP ASVS 反面）：判定服务异常时放行。判别：grep "catch → allow"/"default allow"。本平台：须审计所有 `defaultActionFor`/审批源默认分支是否 `ALLOW`。
2. **权限判定分散多处**（与铁律 8 冲突）：同一动作在 N 个地方各判一次，迟早漂移。判别：`ScopeBypassArchitectureTest`/`ToolBypassArchitectureTest` 扫描是否唯一实现。
3. **角色自封管理员**（JWT 里的 roles 即权威）：越权者篡改 token 即提权。判别：`principal_role` 表是否作为权威源覆盖 token 声明（本平台是，见 1.1）。
4. **令牌长期有效不重判**（非零信任）：创建期授权一次，撤销无感。判别：是否在每次敏感动作前重判 `authz_version`。
5. **脱敏与检测各写一份正则**（漂移）：检测用 A、脱敏用 B。判别：`DataClassification.IdentifyingPattern.pattern()` 是否唯一判据来源（本平台是）。
6. **把不可信内容当指令**（LLM01）：工具结果/记忆未隔离就混入系统提示。判别：`PromptGuard` 是否对工具结果、记忆、压缩态都加信任围栏。
7. **决策流水可读越权**：审计表 `app_agent` 既能 INSERT 又能 SELECT，则任一租户主体可枚举其他租户判定记录。判别：`03_platform_roles.sql` 是否显式 `REVOKE SELECT`。本平台已规避（`:273-274`）。
8. **影子期恒定假 mismatch 淹没真违例**：某资源类型未登记规则，每次查询都落到 `Deny(NO_RULE)` 假 mismatch，真实违例被噪声淹没。判别：`ShadowPolicyCoverageTest` 是否扫描"钩子用到的每个资源类型都有对应规则"。本平台 `AuthzShadowPolicyDefaults.java:13-17` 注释已说明此陷阱并设 `ShadowPolicyCoverageTest` 钉死。
9. **RLS 退役前无"仍依赖 RLS 兜底"信号**：RLS 仍在时比对/染色结构性为 0，让人误以为"应用层过滤已正确"。判别：是否有 `reportRlsDependent` 这类独立计数（`AuthzShadowReporter.java:97-100`）。本平台独有此信号。

## 三、竞品实现全景（每个主流方案一段）

### 3.1 OpenAI Agents SDK
- **官方定位与实现机制**：极简原语（Agent/Runner/Handoffs/Guardrails/Sessions/Tracing），无显式图。护栏由开发者接入 `InputGuardrail`/`OutputGuardrail`（异步并行护栏，返回 tripwire 即中断）或 Guardrails AI 集成；另有 Moderation 与 input/output validation。授权/多租户**不在框架内**，靠宿主。
- **官方来源 URL**：<https://openai.github.io/openai-agents-python/>
- **优点**：Guardrails 并行执行、性能友好；Moderation 开箱即用；开发者体验顺滑。
- **局限/代价**：**无内建 RBAC/多租户隔离**；护栏需自建或接第三方；授权判定不强制 fail-closed（取决于开发者实现）。
- **适用场景**：单租户、快速原型、开发者自管安全的内部工具。

### 3.2 Anthropic Claude Agent SDK
- **官方定位与实现机制**：把 Claude Code 当库用，继承其工具/权限/sessions/hooks/MCP。通过 `canUseTool` 审批回调、权限机制、`max_budget_usd`/`max_turns` 熔断做护栏；prompt caching 用于把 system 护栏缓存复用（Constitutional AI 思路）。
- **官方来源 URL**：<https://docs.anthropic.com/en/api/agent-sdk>
- **优点**：`canUseTool` 审批与预算熔断一体化；system prompt 可固化护栏并缓存。
- **局限/代价**：**无内建 RBAC**；`max_budget_usd` 是会话级熔断而非多租户配额；权限粒度依赖宿主接线。
- **适用场景**：以 Claude 为中心、需精细工具审批与成本熔断的应用。

### 3.3 LangGraph
- **官方定位与实现机制**：低层图式编排运行时（StateGraph：State/Node/Edge + channels/reducer），持久化 checkpointer。护栏靠开发者：`HumanInTheLoopMiddleware`、自定义 `AgentMiddleware`（before/after hook 做鉴权/限流/内容过滤）、图 schema 校验、`recursion_limit`。LangSmith 提供 guardrails 集成。
- **官方来源 URL**：<https://docs.langchain.com/oss/python/langgraph/overview> ；护栏 <https://docs.langchain.com/oss/python/langchain/guardrails>
- **优点**：中间件机制灵活，可在任意 before/after 钩子做鉴权/限流；图 schema 校验易组合。
- **局限/代价**：**无内建 RBAC**；护栏全靠开发者自觉接线；hook 可被绕过（L1 档）。
- **适用场景**：需要可控状态图、愿自管护栏的工程团队。

### 3.4 Google ADK

- **官方来源 URL**：<https://adk.dev/> ；确认 <https://adk.dev/tools-custom/confirmation/>
- **优点**：自带托管运行时与部署；Safety Settings 内建。
- **局限/代价**：**无内建细粒度权限框架**，多租户靠 GCP IAM；护栏不强制 fail-closed。
- **适用场景**：GCP 生态、需托管运行时的应用。

### 3.5 Microsoft AutoGen（已归档，仅供参照）
- **官方定位与实现机制**：分层事件驱动多智能体（Core/AgentChat/Extensions）。**官方已于 2025-10 并入 Microsoft Agent Framework、2026-10 起归档停维护**。Core 无内建护栏，依赖 host 应用。
- **官方来源 URL**：<https://microsoft.github.io/autogen/stable/>
- **优点**：事件驱动拓扑灵活（历史价值）。
- **局限/代价**：**已停维护**；Core 无内建护栏；**不应作为新项目选型依据**（诚实标注）。
- **适用场景**：仅历史参照。

### 3.6 CrewAI
- **官方定位与实现机制**：角色扮演式 Crew（Agents+Tasks+Process）+ Flows（`@start/@listen`），企业 Control Plane 才有 RBAC/guardrails（函数式 + LLM 式 Task guardrails、`before_tool_call` hooks）。
- **官方来源 URL**：<https://docs.crewai.com/>（概念 concepts/tasks）；企业层 <https://www.crewai.com/>
- **优点**：企业 Control Plane 提供 RBAC 与审计；Task 级 guardrails 开箱。
- **局限/代价**：**开源核心无内建 RBAC/细粒度护栏**，需企业付费层才有；护栏粒度依赖订阅。
- **适用场景**：愿付费上企业层的团队。

### 3.7 Agno
- **官方定位与实现机制**：Agent/Team/Workflow 抽象 + 自托管 AgentOS。内建护栏框架（pre/post hooks + PII/提示注入/OpenAI Moderation 内置）、HITL、security（JWT/service-account/security-key + 授权作用域 + per-user 隔离）。
- **官方来源 URL**：<https://docs.agno.com/> ；护栏 <https://docs.agno.com/examples/agents/guardrails/overview> ；安全 <https://docs.agno.com/agent-os/security/overview>
- **优点**：内建 PII/提示注入/Moderation 开箱；内建多租户安全（最接近本平台的"框架内建隔离"）。
- **局限/代价**：细粒度 RBAC 仍主要靠 host；护栏默认策略完备度不及 fail-closed 强制。
- **适用场景**：希望框架内建较多安全原语的团队。

### 3.8 竞品格局小结（横向归类）

把 3.1–3.7 的做法按"权限与护栏是否内建"归类，可清晰看到本平台的定位：

- **完全外置型（L0）**：OpenAI / Anthropic / Google ADK / AutoGen。护栏靠开发者接 Guardrail hook 或第三方，授权/多租户完全不进框架。优势是"轻"；劣势是越权与否全靠宿主自觉，且 fail-closed 多为"建议"而非契约。
- **中间件可接型（L1）**：LangGraph（`AgentMiddleware`）、CrewAI 开源核心（`before_tool_call`）。框架提供 hook 点但不强制，hook 可被绕过（维度 2 所述"旁路"风险）。
- **企业/付费层内建型（L1→L2 局部）**：CrewAI 企业 Control Plane、Agno。前者需付费才有 RBAC/审计；后者已内建 PII/注入/Moderation 与多租户安全，是最接近本平台的"框架内建隔离"形态，但细粒度 RBAC 与 fail-closed 强制度仍不如本平台。

**格局判断**：竞品的"轻"是建立在一个隐含假设上——"agent 框架的使用者是能自管安全的工程师团队"。本平台的隐含假设相反——"agent 平台的使用者是学校/教育局这类需要生产级强治理的客户"。两种假设无对错，但决定了护栏与授权是否应成为**平台的一等公民**。本平台选择了前者（把护栏/授权下沉为不可绕过的基础设施），因此在本维度对绝大多数竞品形成结构性领先；代价如 1.2 所述，是部署与运维复杂度的上升，这是产品定位差异而非能力缺失。

## 四、我们的实现（源码级解剖）

### 4.1 架构与数据流（关键组件、调用链、数据落点）

本平台的权限与护栏由四条相互独立的防线叠加，且每道防线都可独立失效而不致全面失守（Defense in Depth）：

1. **DB 触发器级（数据层强制，L3）**：42 张业务表 `FORCE ROW LEVEL SECURITY`（DDL 头注释 `:5`），策略模板统一为 `USING (tenant_id = current_tenant_id())`（如 `01_platform_ddl.sql:5830`）；`enforce_*_transition` 五个触发器守卫状态机（`:304-482`）。越权读返回 0 行，越权写被 `RAISE EXCEPTION` 拒。
2. **应用层显式 Gate（执行层，L2）**：`AuthorizationService`（端口）+ `RoleBasedAuthorizationService`（实现）+ `ToolInvocationGate`（15 步准入契约）。授权判定从 RLS 隐式上移为显式；每次敏感动作前重新授权，撤销=`authz_version` 递增使在途失效。
3. **复合外键完整性**：跨表引用用 `(tenant_id, 父id)` 复合外键（`Agent设计总览.md` 不变式 6，`agent` 表 `UNIQUE(tenant_id, agent_id)`），保证引用完整性下的租户一致。
4. **护栏（输入/输出，L2）**：输入侧 `PromptGuard`（信任围栏 + 长度/深度上限 + 注入观测）；输出侧 `OutputModeration`（PII 脱敏 / 毒性·越狱阻断，fail-closed）。

**决策流水落点**：每次 AccessGate 判定一行写入 `platform.authz_decision_log`（`:971-982`），`tenant_id`/`principal_id` 为 **text 非 uuid**（审计流水须"无论主体长什么样都能记下来"，见 `:995` 注释），只增不改、不挂 RLS、隔离靠授权（`app_agent` 仅 INSERT，`03_platform_roles.sql:273-274`）。

#### 4.1.1 一次工具调用的四道防线时序（端到端复现）

为说明"四道防线如何真正叠加、且任一层失效不致全面失守"，下面用"租户 A 的 STUDENT 触发一次 `tool:invoke`（调用知识库检索）"的完整链路复现各层触发顺序与失败语义：

| 时序 | 动作 | 触发的防线 | 若此处失效/被绕过会怎样 |
|---|---|---|---|
| T0 | 请求进入，`current_tenant_id()` 绑定 GUC（事务内、业务 SQL 前） | L3：RLS 基线 | 绑错 → FORCE RLS 静默 0 行或跨租户（铁律 1） |
| T1 | `AuthorizationService.isAuthorized(TOOL_INVOKE)` 取 `principal_role` 真相表 + 比对 `authz_version` | L2：应用层 Gate + 零信任重判 | 取 JWT 声明而非表 → 自封管理员（反模式 3） |
| T2 | `AgentOverrides.parse` 唯一解析收紧项（含 `removeTools`） | L2：唯一解析单点 | 多处解析 → 收紧不一致（铁律 8） |
| T3 | `ToolInvocationGate` 审批源判定（未接入 → `DENY_ALL_APPROVALS` FAIL_CLOSED） | L2：fail-closed 准入 | 审批源 fail-open → 越权执行（反模式 1） |
| T4 | `PromptGuard.wrapToolResult` 把工具结果标 `trust="untrusted"` 回灌模型 | L2：输入侧信任围栏 | 结果当指令 → 间接注入（LLM01） |
| T5 | 模型输出进入 `OutputModeration`：PII→REDACT、毒性/越狱→BLOCK | L2：输出护栏 fail-closed | 判定服务异常 → 默认 BLOCK（铁律 8） |
| T6 | 落 `authz_decision_log` 一行（仅 INSERT）；业务查询受 RLS 二次拦截 | L3 + 审计 | `app_agent` 无 SELECT → 审计不被跨租户读 |

**关键观察**：T1 与 T6 是同一动作被"应用层 Gate"和"RLS"各判一次。即使 T1 因某 bug 被绕过（如有人直连 DB 跳过 Gate），T6 的 RLS 仍会在数据层把越权读/写挡掉——这就是 L3 不可替代的价值。反之，若未来按改进点 4 把 RLS 退役、全面应用层化，则 T6 消失，T1 成为唯一防线，届时必须依赖影子门禁（RLS_DEPENDENT=0）证明应用层过滤已完整，否则不能退役。

### 4.2 关键设计决策逐条剖析（每条：决策 → 为什么 → 代价 → 证据锚点）

**D1：执行时重新授权（zero-trust 落地）**
- 决策：Run 创建时授权一次不够，工具执行/结果读取/事件订阅等每个敏感动作前都重新校验当前授权；撤销=`authz_version` 递增。
- 为什么：曾合法的主体（学生退课/教师离职/账号封禁）若只在创建期授权，可用一个曾经合法的 Run 长期越权。
- 代价：每次动作多一次判定与版本比对（性能开销）。
- 证据：`AuthorizationService.java:12-19`（类注释）、`:51 currentAuthzVersion`；`principal.authz_version` 列与注释 `01_platform_ddl.sql:2642,2670`。

**D2：极细动作矩阵，刻意不复用/不合并**
- 决策：`Actions` 拆到 17 个动作（`run:create`/`run:read`/`config:request`/`config:approve`/`agent:delegate`/`tool:invoke`…），且注释反复强调不复用（如 `profile:read` 不复用 `run:read`；`config:approve` 与 `config:request` 分开保双人复核不被同一身份绕过；`agent:delegate` 与 `tool:invoke` 分开）。
- 为什么：省事复用会让授权范围失真（"能改覆盖值的人也能审批"）。
- 代价：动作数多、维护成本略高。
- 证据：`AuthorizationService.java:59-177`（含逐条注释）。

**D3：角色真相以 `principal_role` 表为准，不信任 JWT 声明**
- 决策：JWT 中的 roles 仅为声明，实际生效角色以 `principal_role` 表为准；`PLATFORM_ADMIN` 刻意不在租户权限矩阵登记，走 BYPASSRLS 运维凭据。
- 为什么：防止"令牌自封管理员"（反模式 3）。
- 代价：每次判定需查表（与缓存权衡）。
- 证据：`AuthorizationService.java:195-208`（PLATFORM_ADMIN 注释）；`principal_role` 注释 `01_platform_ddl.sql:2692`。

**D4：`isAudienceOnly` 收窄受众可见范围**
- 决策：STUDENT/PARENT/TEACHER 仅持有受众角色时，Run 读取范围收窄到 `requester_id = principal_id`，且"不归属"与"不存在"统一 404。
- 为什么：防止受众探测他人 Run 存在性。
- 代价：受众视图需额外过滤逻辑。
- 证据：`AuthorizationService.java:230-246`。

**D5：AgentOverrides 只收紧，且全仓唯一解析（铁律 8）**
- 决策：`cap_agent_def.overrides`（`01_platform_ddl.sql:1631`）只允许 `removeSkills`/`removeTools`/`lowerRiskCeiling`；`AgentOverrides.parse` 全仓唯一实现，解析失败即抛 `ClosureResolutionException`（fail-closed）。
- 为什么：授权判定分散多处会漂移（反模式 2）；解析失败静默忽略等于把应收紧的配置放行。
- 代价：新增收紧形态须改唯一实现 + 全仓回归。
- 证据：`AgentOverrides.java:18-38,49-97`；`PermissionResolver.java:173-175`。

**D6：fail-closed 贯穿授权与护栏**
- 决策：审批源未接入时高风险工具一律拒（`ToolInvocationGate` 默认 `DENY_ALL_APPROVALS`）；输出命中未知类别按 `BLOCK`；`PermissionResolver` 任何对象解析不到即抛。
- 为什么：OWASP ASVS fail-closed（理论 6）；fail-open 是越权/泄露根因。
- 代价：判定服务/审批源不可用 → 功能不可用（可用性风险）。
- 证据：`ToolInvocationGate.java:64,207,1332-1357`；`OutputModeration.java:130-137`；`PermissionResolver.java:49-53`。

**D8：PII 检测/脱敏保留 JDK 引擎（铁律 21/22）**
- 决策：`DataClassification.IdentifyingPattern` 正则含零宽前后顾（`(?<![0-9A-Za-z])` 等），RE2/J 不支持环视断言 → `OutputModeration.maskWith` 保留 JDK `java.util.regex` 引擎；其余 re2j 收敛 ReDoS。

- 代价：该路径失去 re2j 的线性时间保证，靠规则审查兜底 ReDoS。
- 证据：`DataClassification.java:99,106,114,117`（lookbehind）；`OutputModeration.java:237-248`（保留 JDK 引擎注释）。

> **代码见证（D8 — 含 lookbehind 的正则，RE2/J 无法直接承接）** `DataClassification.java:99`：

>         + "(0[1-9]|[12]\\d|3[01])\\d{3}[0-9Xx](?![0-9A-Za-z])"),
> ```
> 前后顾 `(?<![0-9A-Za-z])`/`(?![0-9A-Za-z])` 用零宽断言收窄匹配（避免"订单号后 11 位"误判为手机/身份证）。`OutputModeration.maskWith`（`OutputModeration.java:245-248`）刻意留在 JDK `java.util.regex`，因 RE2/J 编译含环视的正则会直接抛 `PatternSyntaxException`——换引擎会让"检测与脱敏共用同一份正则"的硬约束无从谈起（铁律 21）。

### 4.4 我们独有的设计（差异化设计，标为「差异化设计」）

- **【差异化设计 1】`AgentOverrides` 作为"唯一权限解析"单点**：授权路径（`PermissionResolver`）与管理面图谱（`DependencyGraphService`）共用 `AgentOverrides.parse`，杜绝"图谱显示与实际收紧不一致"（见 `AgentOverrides.java:34-37`）。竞品普遍把权限判定散落各处。
- **【差异化设计 2】权限影子对照（Shadow）作为"护栏/权限体系迁移的灰度方法论"**：`AGENT_AUTHZ_SHADOW_ENABLED` + `block-on-violation` 翻转，是"RLS 隐式 → 应用层 Gate 显式"强一致迁移的可复用灰度范式（见 4.2 D10）。竞品无对应原语；本平台独有且可复用于任何"判定逻辑下沉"迁移。
- **【差异化设计 3】信任围栏 + 硬上限的提示注入架构（而非检测即阻断）**：`PromptGuard` 的结构化信任标记（`trust="untrusted"`）+ 长度/深度上限是主防线，检测只观测——契合"Gate 不信任模型决定"的正确主次（见 4.2 D9）。
- **【差异化设计 4】决策流水 text 化 + 只增不改 + 读写权限分离**：`authz_decision_log` 用 text 容纳任意主体形态、`app_agent` 仅 INSERT 且显式 REVOKE SELECT（`03_platform_roles.sql:273-274`），使"判定发生过"的举证材料既不被业务进程读越权、也不因主体形态异常而丢失（见 4.2/4.3）。

### 5.2 优势详解（为什么领先，讲清机制）

1. **"读不到=拒绝"而非跳过**：RLS 默认拒绝（`current_tenant_id()` 返回 NULL → 所有策略拒）+ 应用层 Gate 重新授权，双层独立、互不替代。竞品的"库形态"把隔离责任完全推给宿主（AutoGen/OpenAI/Anthropic 均无内建多租户）。本平台越权读返回 0 行而非报错伪装，越权写被触发器 `RAISE`。
2. **双人复核不被同一身份绕过**：`config:request` 与 `config:approve` 拆成两个动作（`AuthorizationService.java:99-107`），辅以 `cap_config_publish_request.two_person_ck: approver_id <> requester_id`（维度 13）。竞品若提供 RBAC（CrewAI 企业层）也只是角色分配，未必有"同人不许自批"的硬约束。
3. **fail-closed 是契约而非约定**：审批源未接入时 `DENY_ALL_APPROVALS` 恒 `FAIL_CLOSED`（`ToolInvocationGate.java:207`），脱敏引擎未知类别按 BLOCK；竞品护栏多为"建议"，fail-open 风险由开发者承担。具体到"判定服务不可用"这一最危险的失真来源，本平台在"明确拒绝"上比多数框架更彻底——竞品的审批/脱敏若依赖外部服务且未配置降级，往往静默放行。
4. **影子对账弥补"应用层改了 RLS 没改"的漂移**：`AuthzShadowReporter.reportRlsDependent` 专门记录"仍依赖 RLS 兜底"的查询（P1 唯一非平凡信号），是竞品没有的迁移安全网。竞品的"应用层化授权"要么没有 RLS 基线可对照，要么没有影子机制，迁移通常靠一次性切换 + 事后救火。
5. **动作矩阵刻意"过度细分"带来可解释性**：17 个动作（`AuthorizationService.java:59-177`）虽增加维护成本，但让"谁对什么做了什么"可被逐条审计与报表化（改进点 6 的产出物直接建立在此之上）。竞品的 RBAC（如 CrewAI 企业层）多为粗粒度角色，难以支撑"双人复核不被同一身份绕过"这种细约束。

6. **决策流水作为"不可抵赖"证据而非"业务数据"**：`authz_decision_log` 用 text 容纳任意主体形态（`:995`）、只增不改、不挂 RLS、`app_agent` 仅 INSERT 且显式 `REVOKE SELECT`（`:273-274`），`reason_code` 只存码不存自由文本（`:1002`）。这套设计使"某次判定是否真的发生、被允许还是拒绝"成为**可被第三方验证、业务进程无法篡改或枚举**的取证材料——这是教育/政务客户安全评估中最常被问到的"你能证明你没越权吗"的硬答案。竞品即便有 tracing（如 LangSmith/OpenAI 仪表盘），其审计数据仍挂在业务主体可读的通道上，不具备本平台这种"取证与业务读写分离"的隔离强度。

### 5.3 劣势与盲区详解（明确承认，含根因）

1. **权限决策不可实时查询（落后，能力缺口）**：`authz_decision_log` 已落库（`:971`），但 `app_agent` 被 REVOKE SELECT（`03_platform_roles.sql:274`），读只能走 `platform_ops` 运维通道，**当前没有面向运维/前端的查询端点或报表**。根因：决策流水按"取证"设计，未设计"可观测报表"。改进见点 6。
2. **PII 检测受引擎限制、靠黑名单（落后，能力缺口）**：`DataClassification` 仅 4 类正则黑名单（身份证/手机/学号/邮箱，`:90-149`），且因铁律 21 必须留 JDK 引擎（`:99` lookbehind）。对照 OpenAI Moderation / Azure Content Safety / Presidio 类库，本平台在覆盖度与可维护性上落后。改进见点 3。
3. **提示注入 detection 只观测不阻断（盲区，设计取舍）**：`detectSuspicious` 命中仅 `log.warn`（`PromptGuard.java:277-290`），不拒绝。这是**有意取舍**（避免教育场景误杀），真相防线是信任围栏 + Gate 不信任模型决定。但对照 OWASP LLM01 的"主动缓解"期望，本平台在"主动阻断注入"上偏弱；且**既有梳理报告第 7 章未记载 `PromptGuard`**，造成"提示注入防护盲区"在文档层面被夸大——实际已有输入侧围栏，只是检测非阻断。改进见点 1。
4. **权限模型表达力停留在 RBAC（落后，设计取舍）**：属性策略（风险等级/时间/环境）仅以 `AgentOverrides.lowerRiskCeiling` 等零星形态存在，未形成 ABAC/PBAC 引擎。对照 OPA/Rego、AWS Cedar 的外部化策略，本平台在多租户细粒度属性策略上落后。改进见点 5。
5. **工具/审批的 fail-closed 依赖配置正确（运维负担）**：`AGENT_PLATFORM_OPS_ENABLED` 等若配置错会 fail-closed 拒启（铁律），但意味着迁移/部署需精确配置（`03_platform_roles.sql:34-36`）。代价是部署复杂度高于竞品"库形态"。

### 5.4 关键分歧点（最本质的架构分歧）

1. **授权判定位置：数据库隐式（竞品普遍）vs 应用层显式 Gate + 数据库基线（本平台）**。竞品把授权当"宿主责任"，本平台把它当"平台一等公民"。后果：本平台强一致、可审计，但部署重；竞品轻、但越权与否靠开发者。
2. **护栏失败语义：fail-open（竞品取决于实现）vs fail-closed（本平台铁律）**。本平台"判定不可用即拒绝"，牺牲可用性换安全；竞品多为"建议"，易被误配成 fail-open。
3. **提示注入：检测即阻断（部分竞品/通用预期）vs 信任围栏+硬上限+观测（本平台）**。本平台认为"检测不可靠、主防线在架构"，故检测只观测；这是与"主动阻断"范式的最本质分歧。

#### 5.4.1 迁移期的"混合态"是暂时最安全配置（呼应改进点 4）

需要特别指出：当本平台处于"RLS 基线 + 应用层 Gate 双跑、且影子门禁尚未放行退役 RLS"的阶段时，系统实际处于**双重强制**状态（数据层与应用层同时生效）。这是整个演进周期里**最安全**的配置——任何一层的 bug 都被另一层兜底。真正的危险窗口只出现在"决定退役 RLS、应用层成为唯一防线"的那一刻：届时必须已有 `RLS_DEPENDENT=0` 的硬证据（见改进点 4），证明所有"Gate 要求收口但查询缺显式租户谓词"的路径已被补上。换言之，分歧点 #1 的"应用层显式 Gate"并非天然优于"数据库隐式 RLS"，它只有在"已证明应用层过滤完整"之后才敢独立承担；在此之前，本平台刻意保持混合态。这一点常被外部评审误读为"架构拖沓"，实为有意的、可验证的渐进收敛。

### 5.5 护栏成熟度自评估（雷达，1–5 分）

| 子能力 | 自评分 | 说明 |
|---|---|---|
| RBAC 细粒度 | 5 | 17 动作 + 角色真相表，行业前列 |

## 六、优缺点总评

### 6.1 我们的优点（分级）

- **结构性优势**：RLS FORCE + 应用层 Gate 双层强制（L3）——即使应用层出现绕过 Gate 的 bug，存储层触发器/策略仍二次拦截，越权读返回 0 行、越权写被拒；`AgentOverrides` 唯一解析单点，杜绝"授权判定分散多处漂移"（铁律 8）；`authz_decision_log` 决策可举证，且 text 化 + 读写分离使它既不被业务读越权也不因主体形态异常丢失。
- **工程性优势**：fail-closed 贯穿（审批源/脱敏/解析三处默认拒绝，见 4.2 D6）；`isAudienceOnly` 最小权限收窄（受众角色 Run 可见范围收至本人，且"不归属"="不存在"统一 404，防存在性探测）；影子对照（`AuthzShadowReporter`）弥补"应用层改了 RLS 没改"的迁移漂移，且 `reportRlsDependent` 独立信号避免"结构性为 0"误读。
- **领域性优势**：面向初中生产品的毒性/越狱 BLOCK、PII REDACT——这是教育垂直领域的合规刚需（未成年人保护）；信任围栏覆盖模型历史输出二次传播路径（记忆围栏），即"模型在 Run A 说的话在 Run B 以历史记忆身份回来"这一经典注入路径被显式降级为不可信数据。

### 6.2 我们的缺点（分级）

- **设计取舍导致的代价**：PII detection 只观测非阻断是教育场景取舍；RBAC 起步非 ABAC 是早期简化。
- **能力缺口**：决策流水无查询端点；PII 检测靠 JDK 正则黑名单、覆盖度有限；提示注入检测非阻断；缺外部化策略引擎。这些缺口的共性根因是"平台早期以机制正确优先、以覆盖度/可观测其次"的演进顺序——不是能力缺失，而是优先级排序的结果，且全部已有明确改进项（点 1/3/5/6）。
- **运维负担**：双层授权 + 角色授予脚本 + 灰度参数 fail-closed 拒启，部署重。具体表现为：每次 schema 变更须同步 `03_platform_roles.sql` 授权（铁律 7）、`app_agent` 必须 `NOBYPASSRLS`（否则隔离假绿）、影子配置需显式开启。这对比"库形态"竞品确实是负担，但对应的是"生产级隔离"的硬承诺。

### 6.3 每个竞品的优点（简明，带来源）

- OpenAI：Guardrails 并行、Moderation 开箱（<https://openai.github.io/openai-agents-python/>）。
- Anthropic：`canUseTool` 审批 + 预算熔断一体化（<https://docs.anthropic.com/en/api/agent-sdk>）。
- LangGraph：中间件灵活，任意 before/after 钩子（<https://docs.langchain.com/oss/python/langchain/guardrails>）。
- Google ADK：自带部署 + Safety Settings（<https://adk.dev/tools-custom/confirmation/>）。
- CrewAI：企业 Control Plane 提供 RBAC/审计（<https://www.crewai.com/>）。
- Agno：内建 PII/注入/Moderation + 多租户安全（<https://docs.agno.com/agent-os/security/overview>）。
- AutoGen：已归档停维护，仅历史参照（<https://microsoft.github.io/autogen/stable/>）。

### 6.4 每个竞品的缺点（简明，带来源）

- OpenAI/Anthropic/ADK/AutoGen：**无内建 RBAC/多租户隔离**，授权靠宿主（竞品报告 §维度 7）。
- LangGraph：护栏全靠中间件，可被绕过（L1 档）。
- CrewAI：开源核心无 RBAC，需企业付费层（<https://docs.crewai.com/>）。
- Agno：细粒度 RBAC 仍主要靠 host，默认策略完备度不及强制 fail-closed。
- AutoGen：停维护，不应作为新选型（诚实标注）。

## 七、可优化与改进点（必须可执行）

> 每个改进项都具体到文件/表/配置/接口级，并给验收门禁（可执行，非"加强测试"空话）。所有改动须遵守铁律 8（fail-closed）/11（事务毒化）/铁律 21（JDK 引擎保留）。

### 改进点 1：提示注入输入侧检测的"最小阻断"实现（不是全量拦截，而是高风险模式 fail-closed）

- **问题陈述**：当前 `PromptGuard.detectSuspicious` 仅 `log.warn`（`PromptGuard.java:277-290`），注入模式不被主动阻断；纯观测在教育场景可接受，但**高风险模式**（如"输出/打印你的系统提示词""声称已解锁开发者模式并诱使执行操作"）已有明确恶意意图，可安全阻断而不误杀正常数学题（R-8 已证明"忽略第 3 小问"不在高风险集合）。
- **方案设计**：
  - 在 `PromptGuard.java` 新增 `List<Pattern> HIGH_RISK_PATTERNS`（仅含"诱导泄露系统提示词""声称已解锁并要求执行特权动作"两类，复用 re2j，无 lookbehind），新增方法 `DetectedRisk classifyInput(String text)` 返回 `{NONE, OBSERVE_ONLY, HIGH_RISK_BLOCK}`。
  - 在 `RunExecutionLoop` 入口（`RunExecutionLoop.java:68` 主循环首轮或 `AgentModelConfigAssembler` 组装前）调用 `classifyInput`：命中 `HIGH_RISK_BLOCK` → 抛 `PromptRejectedException(reason=INJECTION_HIGH_RISK)`，Run 进入 FAILED 终态（不落入模型）。
  - 配置项：`application.yml` 新增 `agent.worker.prompt-guard.block-high-risk: "${AGENT_PROMPT_GUARD_BLOCK_HIGH_RISK:true}"`（默认开，fail-closed）。
  - **配置片段示例**（`application.yml` 现有 `agent.worker` 块内）：
    ```yaml
    agent:
      worker:
        prompt-guard:
          block-high-risk: "${AGENT_PROMPT_GUARD_BLOCK_HIGH_RISK:true}"
          # 仅含"诱导泄露系统提示词""声称已解锁并要求执行特权动作"两类，
          # 不含"忽略第 3 小问"类合法数学指令（避免 R-8 误杀）
    ```
  - 关键：复用 `PromptInjectionRedTeamTest` 已存在的 R-8"不误杀"用例集，**新增**"高风险模式被拒"用例（R-9），与既有"只观测"用例不冲突。
- **预期收益（可度量）**：已知注入样本（来自 R-1~R-8 + 新增 R-9 红队集）的**高风险模式召回率 ≥ 95%**；正常数学题/作业题误杀率 = 0（由 R-8 强制保证）。
- **实施成本与风险**：改动面小（单类 + 单调用点 + 单测试类）；迁移无需灰度（默认开但仅针对显式高风险模式，不影响既有只观测路径）。
- **优先级**：P1；建议排期：里程碑 M-runtime-guardrails。
- **验收方式（门禁）**：
  1. 单元测试：`PromptInjectionRedTeamTest` 新增 R-9，`assertThatThrownBy(renderUserInput/run入口).isInstanceOf(PromptRejectedException.class)`，且 `reason()==INJECTION_HIGH_RISK`。
  2. 反向验证（撤点反证）：临时把 `block-high-risk` 置 false，R-9 用例须红——证明阻断确实由该配置/代码路径生效，而非"恰巧"。
  3. 误杀门禁：R-8 全部用例 + 100 条真实作业题样本（来自 `agent-test-support` 语料）不得被拒。

### 改进点 2：护栏 fail-closed 自动化回归（判定服务不可用时默认拒绝）

- **问题陈述**：`ToolInvocationGate` 审批源默认 `FAIL_CLOSED`（`ToolInvocationGate.java:207`）、`OutputModeration.defaultActionFor` 未知类别 BLOCK（`:130`）、`AgentOverrides.parse` 失败抛异常——但这些 fail-closed 语义**没有契约测试保证"判定服务/脱敏引擎不可用时确实拒绝"**，仅靠代码注释。
- **方案设计**：
  - 在 `agent-worker/src/test/.../execute/` 新增 `FailClosedContractIT`：
    - 场景 A：装配一个**故意抛异常**的 `ApprovalSource` 实现（模拟审批源不可用），断言需审批工具一律被拒且 Run 进入 WAITING_APPROVAL 而非 SUCCEEDED。
    - 场景 B：装配一个**返回 null/异常**的脱敏 `DataClassification` 模拟（或 Mockito 让 `IdentifyingPattern.detect` 抛），断言 `OutputModeration.moderate` 对非空输入返回 `BLOCK`（而非 REDACT/ALLOW）。
    - 场景 C：`AgentOverrides.parse` 喂非法 JSON，断言抛 `ClosureResolutionException`。
  - 关键：这些测试须用"撤点反证"——把 fail-closed 改成 fail-open（临时改默认分支）后用例必红，证明门禁有效。
  - 运维侧：`application.yml` 现有 `AGENT_PLATFORM_OPS_*` 的 fail-closed 拒启已在 `03_platform_roles.sql:276-326` 自检覆盖，本条聚焦"运行期判定服务不可用"。
- **预期收益（可度量）**：fail-closed 路径的回归覆盖率从"注释保证"升级为"CI 强制"；每次重构护栏默认分支，CI 必红。
- **实施成本与风险**：纯测试新增，零运行时风险；改动面 = 测试目录。
- **优先级**：P0（铁律 8 的核心保障）；排期：M-guardrail-contract。
- **验收方式（门禁）**：
  1. `FailClosedContractIT` 三个场景全部绿；且在 PR 模板中加入"改任何 fail-closed 默认分支须先改此测试"的 check。
  2. 撤点反证：将 `DENY_ALL_APPROVALS` 的 `Verdict` 临时改为 `APPROVED`，场景 A 必红——合并前恢复。
  3. CI 卡点：该 IT 纳入 `agent-worker` 模块 `verify` 阶段，失败即阻断发布。

### 改进点 3：PII 检测从 JDK 正则迁移到可维护识别器（保留 JDK 引擎但结构化规则表，或引入 Presidio 类库）

- **问题陈述**：`DataClassification.IdentifyingPattern` 仅 4 类硬编码正则（`DataClassification.java:90-149`），含 lookbehind 致必须留 JDK 引擎（铁律 21）；覆盖度低（无地址/银行卡/姓名等），且新增类型需改 Java 枚举重编译。
- **方案设计（A：结构化规则表，低成本）**：
  - 将识别模式外置为 `application.yml` 的配置块（如 `agent.worker.pii-patterns: [{label: 身份证号, regex: "(?<![0-9A-Za-z])[1-9]...", engine: JDK}, ...]`），`DataClassification` 启动时加载为 `List<IdentifyingPattern>`，**含 lookbehind 的项 engine=JDK，其余可 engine=RE2J**（在 re2j 上预编译以收敛 ReDoS）。保留 `pattern()` 唯一判据来源。
  - 文件改动：`DataClassification.java`（枚举改为从配置构建的 `record IdentifyingPattern(String label, String regex, Engine engine)`），新增 `PiiPatternProperties` 绑定 `application.yml`。
  - **配置片段示例**（`application.yml`）：
    ```yaml
    agent:
      worker:
        pii-patterns:
          - { label: "身份证号", engine: JDK,   regex: "(?<![0-9A-Za-z])[1-9]\\d{5}(19|20)\\d{2}(0[1-9]|1[0-2])(0[1-9]|[12]\\d|3[01])\\d{3}[0-9Xx](?![0-9A-Za-z])" }
          - { label: "手机号",   engine: JDK,   regex: "(?<![0-9])1[3-9]\\d{9}(?![0-9])" }
          - { label: "银行卡",   engine: RE2J,  regex: "\\b(?:\\d[ -]*?){13,19}\\b" }
          - { label: "地址",     engine: RE2J,  regex: "[省|市|区|路|号|栋]" }
    ```
    规则：`engine=JDK` 用于含 lookbehind 的项（铁律 21 不可改）；`engine=RE2J` 用于线性时间项以收敛 ReDoS。加载时校验所有 `JDK` 项正则能编译、`RE2J` 项不含环视（否则启动失败，fail-closed）。
- **方案设计（B：引入 Presidio 类库，高成本）**：评估微软 Presidio（<https://microsoft.github.io/presidio/>）做识别，`DataClassification` 适配其 `AnalyzerEngine` 结果映射到既有 `Category`/`Action`。保留 JDK 引擎兜底（铁律 21 不破）。
- **预期收益（可度量）**：PII 类型覆盖从 4 类提升到 ≥ 12 类（含地址/银行卡/姓名/IP）；新增类型零代码改动（方案 A）；误报/漏报率可由语料回归量化。
- **实施成本与风险**：方案 A 改动面中等（单类 + 配置 + 测试），无外部依赖；方案 B 引入重依赖、需模型/规则包，迁移需灰度。二者都须保留 JDK 引擎（铁律 21）。
- **优先级**：方案 A 为 P1；方案 B 为 P2（评估后决策）。排期：M-pii-enrich（A）/ M-pii-presidio（B）。
- **验收方式（门禁）**：
  1. 方案 A：新增 `DataClassificationIT`，用 30 条真实样本（身份证/手机/学号/邮箱/地址/银行卡各 5 条）+ 20 条负样本（正常数学题），断言识别精确率 ≥ 0.95、召回率 ≥ 0.90。
  2. 撤点反证：临时把某类 engine 改成 RE2J 且含 lookbehind，启动须抛 `PatternSyntaxException`（证明 JDK 引擎保留机制有效），恢复。
  3. 性能：re2j 路径的单条检测 P99 < 1ms；JDK 路径单条检测 P99 < 2ms。

### 改进点 4：影子模式的推进门禁（何时从 shadow 切到 enforce）

- **问题陈述**：`AuthzShadowReporter` 有 P1 影子（只记不拦）→ P2 双写（`block-on-violation` 翻转）（`AuthzShadowReporter.java:20-27`），但**没有明确的"切换判定指标"**——何时把 `AGENT_AUTHZ_SHADOW_BLOCK_ON_VIOLATION` 从 false 翻 true，靠人工拍脑袋。
- **方案设计**：
  - 在 `AuthzShadowReporter` 增加**口径固定的出口门禁指标**（已在 `AuthzShadowPolicyDefaults.java` 注释中部分提及）：
    - 连续 2 周（或 N=100 万次采样）`AUTHZ_MISMATCH = 0` 且 `TAINT_VIOLATION = 0`；
    - **关键**：`RLS_DEPENDENT`（"仍依赖 RLS 兜底"的查询，`:97-100`）已清零——即所有"Gate 要求收口但查询无显式租户谓词"的查询已补应用层过滤（这是 P1 唯一非平凡信号，必须归零才敢退役 RLS）。
  - 新增 `ShadowPromotionGate.mayPromote(metrics)` 返回布尔 + 理由；在 `application.yml` 注释写明门禁公式。
  - 提供运维脚本/端点：`GET /api/platform/v1/authz-shadow/report` 返回上述三类计数与"是否可推进"结论（复用 platform 权限闸门，隔离靠授权）。
- **预期收益（可度量）**：切换决策从"人工"变"指标驱动"；RLS 退役（若未来做）前必有 `RLS_DEPENDENT=0` 证据。
- **实施成本与风险**：低（指标已采集，只差聚合与判定）；不直接动 RLS，安全。
- **优先级**：P1（与影子灰度同期）；排期：M-shadow-promotion。
- **验收方式（门禁）**：
  1. 单元/集成：`ShadowPromotionGateTest` 断言"MISMATCH>0 → 不推进""RLS_DEPENDENT>0 → 不推进""三项全 0 满窗口 → 推进"。
  2. 在 `AuthzShadowLiveIT` 中模拟注入一条 mismatch，断言 `mayPromote=false`。
  3. 文档门禁：在 `application.yml` 与运维手册写明"推进前必须 `RLS_DEPENDENT=0`"，否则视为违规切换。

### 改进点 5：权限模型从 RBAC 升级到 ABAC/PBAC（支撑更细属性策略）

- **问题陈述**：当前 `Actions`/`Roles` 是 RBAC（`AuthorizationService.java:59-247`），属性策略（风险等级/环境/时间/数据分类）仅以 `AgentOverrides.lowerRiskCeiling` 等零星形态存在；维度 2 多租户的细粒度属性策略（如"仅上课时段可发起""仅特定班级可见"）无法表达。
- **方案设计**：
  - 在 `AuthorizationService` 引入属性上下文：`AuthorizationContext`（含 `tenantId`、`principalId`、`riskCeiling`、`timeOfDay`、`dataClassification`、`environment`）。`isAuthorized` 重载为 `isAuthorized(context, action, resourceId, attributes)`。
  - 新增 `PolicyDecisionPoint`（PDP）接口与默认实现 `AbacPolicyEngine`，规则源复用 `AuthzShadowPolicyDefaults.rules()` 的 `PolicyRule` 结构（已是 `Action/Requirement/Effect` 三元组，`AuthzShadowPolicyDefaults.java:161-166`），外置为 `application.yml` 的 `agent.authz.policies` 列表（向 OPA/Rego、AWS Cedar 形态靠拢）。
  - 不破坏 RBAC：现有角色映射作为 PDP 的第一层；新属性规则叠加。铁律 8 不变（`AgentOverrides` 仍唯一解析，权限判定仍单一 PDP）。
  - 配置：`application.yml` 新增 `agent.authz.engine: rbac|abac`（默认 rbac，向后兼容）。
- **预期收益（可度量）**：可表达"风险上限随班级/时段变化"等属性策略；策略变更无需改 Java 重编译；与维度 2 多租户属性隔离对齐。
- **实施成本与风险**：中（新增 PDP + 属性上下文 + 规则源迁移）；需保证 PDP 判定仍 fail-closed（无匹配规则 → DENY，见 `AuthzShadowPolicyDefaults.java:13` 注释）；灰度用影子（改进点 4 同机制）。
- **优先级**：P2；排期：M-abac-engine。
- **验收方式（门禁）**：
  1. `AbacPolicyEngineTest`：注入"放学后禁止发起辅导"策略，断言 21:00 的 `run:create` 被拒、09:00 被允；无匹配规则 → 默认 DENY（fail-closed）。
  2. 反向验证：临时把所有规则 engine 置为 fail-open（默认 ALLOW），断言既有 `AuthorizationService` 调用用例必红。
  3. 兼容门禁：开启 `abac` 后，既有 17 个 RBAC 动作 + `isAudienceOnly` 行为不变（回归 `AuthorizationService` 既有测试）。

### 改进点 6：authz 决策实时可解释（查询端点/报表）

- **问题陈述**：`authz_decision_log` 已落库（`:971`），但读只能走 `platform_ops`，**无面向运维/前端的查询端点或报表**；运维排查"某主体为何被拒"需直连库（`03_platform_roles.sql:274` 已 REVOKE app_agent SELECT）。这限制了"可审计性"轴的实际可用性（见 5.1/5.3）。
- **方案设计**：
  - 新增 `platform/platform-bootstrap/.../api/platform/AuthzDecisionLogController.java` + `GET /api/platform/v1/authz-decision-log`（带 `tenant_id`/`principal_id`/`action`/`permitted`/`occurred_at` 分页过滤），经平台权限闸门（隔离靠授权码，非 RLS，同 `review_task` 形态，`03_platform_roles.sql:253-260`）。
  - 新增 `PlatformOpsDataSourceProvider` 查询通道（已存在，复用 `platform_ops` 专用数据源），仅对 `platform.authz_decision_log` 的 SELECT 授权给 `platform_ops`（运维通道，不开放给 `app_agent`）。
  - 提供报表视图：按 `action` × `permitted` 聚合的拒绝率、按 `reason_code` 的拒绝分布（区分 403 vs 500，呼应 `reason_code` 只存码的设计 `:1002`）。
  - **接口签名示例**：
    ```java
    @GetMapping("/api/platform/v1/authz-decision-log")
    public Page<AuthzDecisionLogRow> query(
        @RequestParam(required=false) String tenantId,
        @RequestParam(required=false) String principalId,
        @RequestParam(required=false) String action,
        @RequestParam(required=false) Boolean permitted,
        @RequestParam(defaultValue="0") int page,
        @RequestParam(defaultValue="50") int size);
    ```
  - **DDL 权限（复用 `03_platform_roles.sql` 的运维通道纪律）**：`platform_ops` 已获 platform 域整域 DML（`:192-215`），只需确认 `authz_decision_log` 在该范围内（是）；`app_agent` 维持"仅 INSERT + 显式 REVOKE SELECT"（`:273-274`）。无需新授权，`AuthzDecisionLogController` 经平台权限闸门（与 `review_task` 同形态 `:253-260`）。
  - 配置：`application.yml` 复用现有 `AGENT_PLATFORM_OPS_*` 开关。
- **预期收益（可度量）**：运维可在 1 分钟内定位"某被拒请求的原因码"；可视化拒绝率趋势，作为 fail-closed 健康度看板。
- **实施成本与风险**：低（查询端点 + 运维数据源，无运行期风险）；须严格沿用"读走 platform_ops、app_agent 不获 SELECT"纪律（防跨租户元数据泄漏）。
- **优先级**：P1；排期：M-authz-observability。
- **验收方式（门禁）**：
  1. 集成测试 `AuthzDecisionLogControllerIT`：写入一条 denied 决策，断言经运维端点可按 `reason_code` 查回；`app_agent` 凭据访问该端点须 403（证明未泄漏）。
  2. 权限自检扩展：在 `03_platform_roles.sql` 自检块新增"platform_ops 对 authz_decision_log 有 SELECT"断言。
  3. 报表门禁：聚合接口返回的拒绝率与 `reason_code` 分布须在 Grafana/内部看板上可渲染（截图或接口契约测试）。

## 八、其他有价值的横向对比（避免维度内自闭）

### 8.1 与本项目其他维度的耦合与相互约束（≥2 条）

1. **与维度 2（多租户隔离）耦合**：本维度的 RLS 基线（`current_tenant_id()`）与维度 2 共用同一套 `FORCE RLS` 策略（`:5830` 等 50 条）。任何"退役 RLS、全面应用层化"的改动都必须先过改进点 4 的影子门禁（RLS_DEPENDENT=0），否则会直接越权。约束：维度 2 的 GUC 绑定错误会同时击穿维度 7 的隔离——两者是同一条命门。
2. **与维度 13（HITL）/维度 9（预算）耦合**：`ApprovalSource` 默认 FAIL_CLOSED（`ToolInvocationGate.java:207`）依赖维度 13 的审批状态机；预算预留失败即拒（维度 9）与授权失败即拒共用"fail-closed 不可超发"语义。约束：任何让审批源"fail-open 回落"的改动都同时破坏维度 7 与维度 9/13 的铁律。
3. **与维度 10（可观测审计）耦合**：`authz_decision_log` 是维度 10 审计宽表的事实源之一；改进点 6 的查询端点直接喂维度 10 的看板。约束：决策流水不得被"只增不改"破坏（铁律：`app_agent` 不得获 UPDATE/DELETE）。

### 8.2 与非 agent 领域成熟做法的对照

- **金融反洗钱/权限治理**：银行"四眼原则"（dual control）与本平台 `config:request`/`config:approve` 分离 + `two_person_ck` 同构；可借鉴其"操作与复核分离且不可同一人"的审计证明范式。
- **分布式系统 Zero Trust**：服务网格（Istio mTLS + Authz）的"每次请求都验 JWT + 属性"与本平台"执行时重新授权"同构；可借鉴其 SPIFFE 身份锚定思路强化 `principal` 真实性。
- **合规（GDPR/HIPAA/PCI-DSS）**：PII 检测与脱敏的"数据分类分级"是合规基线；本平台 `DataClassification` 已做最小形态，可借鉴 GDPR 的"数据保护影响评估（DPIA）"把 PII 类型与处置策略做成清单化治理。

### 8.3 反向思考：若从头重做本维度，我们会怎么设计？

- **会保留**：RLS FORCE 默认拒绝 + 应用层唯一 Gate 双保险（已被证明是最强隔离）；`AgentOverrides` 唯一解析；fail-closed 贯穿；信任围栏 + 硬上限的注入架构。
- **会改**：① 权限模型从一开始就做 ABAC/PBAC（省去 RBAC→ABAC 迁移，见改进点 5）；② 决策流水设计之初就带查询端点与报表（而非事后补，见改进点 6）；③ PII 识别从一开始就结构化规则表 + 可选 Presidio（省去枚举硬编码，见改进点 3）；④ 提示注入从一开始就区分"高风险阻断"与"只观测"，而非先只观测后补阻断（见改进点 1）——但会保留"信任围栏 + 硬上限"作为主防线这一正确架构。
- **会保留的代价意识**：即使重做，也**不会**为追求竞品式"轻量 SDK"而放弃 RLS 双保险。因为本平台的产品契约是"多租户生产运行时"，强隔离是不可交易项；若要做轻量 SDK，应另起一个明确标注"非生产级"的子项目，而非削弱主平台。
- **取舍诚实**：若追求"轻量 SDK"体验（竞品优势），本平台会牺牲强一致与可审计——这是产品定位差异，非能力缺失。本平台定位是"生产运行时"而非"库"。

### 8.4 与 OWASP LLM Top 10 的覆盖映射（合规对账）

为便于安全评审对照，下面把 OWASP Top 10 for LLM Applications（2025）逐条映射到本平台本维度的控制点，并标注覆盖状态与缺口（依据见 2.1(7) 与 4.2 D1–D10）：

| OWASP LLM 项 | 风险 | 本平台控制点 | 覆盖状态 |
|---|---|---|---|
| LLM01 Prompt Injection | 不可信内容被当指令 | `PromptGuard` 信任围栏 + 硬上限；检测只观测（D9） | 部分（架构侧强、检测非阻断） |
| LLM02 Sensitive Information Disclosure | PII/机密泄露 | `OutputModeration` PII→REDACT；`DataClassification`（D7/D8） | 部分（仅 4 类正则，改进点 3） |
| LLM03 Supply Chain | 第三方模型/工具风险 | `AgentOverrides.removeTools/removeSkills` 唯一解析（D5） | 覆盖（工具收敛可管控） |
| LLM04 Data Poisoning | 训练/检索数据投毒 | 记忆围栏标记为不可信数据（D9） | 部分（间接注入缓解，非训练防护） |
| LLM05 Improper Output Handling | 输出未校验即用 | `OutputModeration` 输出侧 fail-closed（D7） | 覆盖 |
| LLM06 Overreliance | 过度信赖模型输出 | `ToolInvocationGate` 模型不自动执行（铁律：禁 ToolCallingAdvisor 自动路径） | 覆盖 |
| LLM07 System Prompt Leakage | 系统提示泄露 | `PromptGuard` 高风险阻断（改进点 1，待落地） | 部分（观测中，阻断待落地） |
| LLM08 Excessive Agency | 模型获过多权限 | `Actions` 极细矩阵 + 审批 FAIL_CLOSED（D2/D6） | 覆盖 |
| LLM09 Overpermissioned Access | 授权过宽 | `isAudienceOnly` 最小权限 + RLS 默认拒绝（D4/L3） | 覆盖 |
| LLM10 Unbounded Consumption | 资源无上限 | 预算预留 FAIL_CLOSED（维度 9）+ 硬上限（D9） | 覆盖（跨维度） |

**对账结论**：10 项中 6 项已被本维度直接覆盖、3 项部分覆盖（缺口均已有对应改进点：点 1 补 LLM01/07 阻断、点 3 补 LLM02 覆盖度）、1 项（LLM04）属训练/检索数据治理范畴、非运行时护栏职责。整体覆盖度高于同类"库形态"框架，短板集中在"运行期检测阻断"的主动性上——与 5.3 的判定一致。

## 九、对产品演进的启发

### 9.1 本维度支撑的产品能力（用户能感知什么）

- **租户数据强隔离**：学校 A 绝看不到学校 B 的学生数据（即使平台 bug 也难越权）——这是 ToB 教育 SaaS 签约时的硬合规项，直接决定能否通过学校/教育局的安全评估。
- **双人复核可感知**：治理面配置变更必须两人（`two_person_ck`），普通用户无法自批；家长/教师的治理审批（APPROVER 角色）与受众自助能力（STUDENT/PARENT/TEACHER）严格分离。
- **未成年人保护**：面向初中生的有害/越狱输出被阻断（不为"讲了题但夹带自伤话术"放行），PII 被脱敏后下发（身份证/手机/邮箱命中即换占位符）。
- **可信审计**：任何"为何被拒"都可追溯（改进点 6 落地后）；运维可在看板上区分"真拒绝（403）"与"系统错误（500）"，因为 `reason_code` 只存码不存自由文本（`:1002`）。
- **可演进的安全承诺**：因 fail-closed 是铁律，平台升级/扩容/灰度期间不会出现"判定服务抖动 → 临时放行"这类隐蔽越权窗口——这对学校客户是比"功能多"更值钱的承诺。

### 9.2 演进路线图（近/中/远三期，每期有明确产出物与验收标准）

- **近期（M-runtime-guardrails / M-guardrail-contract / M-pii-enrich(A) / M-shadow-promotion / M-authz-observability）**：改进点 1（高风险注入阻断）、2（fail-closed 契约测试）、3A（PII 规则表化）、4（影子推进门禁）、6（决策查询端点）。**验收**：R-9 误杀率=0、FailClosedContractIT 全绿、PII 精确率≥0.95、RLS_DEPENDENT=0 才推进、决策端点 403 自保护。
- **中期（M-abac-engine / M-pii-presidio）**：改进点 5（ABAC 引擎，rbac|abac 开关）、3B（Presidio 评估引入）。**验收**：属性策略回归通过、默认 DENY 不破 fail-closed、Presidio 覆盖 ≥12 类。
- **远期**：权限体系"应用层唯一权威 + RLS 退役"完整切换（以改进点 4 门禁为界）；策略引擎对接 OPA/Rego 或 Cedar 外部化（PBAC）。**验收**：RLS_DEPENDENT 持续 0、策略变更无需重编译、灰度零事故。

### 9.3 风险清单（做这一步可能踩的坑，关联本项目已知铁律）

- **铁律 8 风险**：任何"判定默认放行"的改动（如改进点 5 的 PDP 默认 ALLOW）都会破 fail-closed——须以"无匹配规则=DENY"兜底 + 反向验证门禁。
- **铁律 21 风险**：改进点 3 引入 re2j 时必须审查所有正则无 lookbehind，否则启动抛 `PatternSyntaxException`；保留 JDK 引擎路径不可删。
- **铁律 7/11 风险**：改进点 6 新增查询端点若复用 `app_agent` 而非 `platform_ops` 数据源，会越权读全平台决策流水——须沿用 `03_platform_roles.sql:274` REVOKE SELECT 纪律。
- **铁律 1/15 风险**：权限错误不得伪装成临时故障（404/403/401 须显式终态+停轮询），改进点 1 的注入拒绝须落 FAILED 终态而非 5xx 重试。
- **改进点 4 风险**：若"推进门禁"指标（RLS_DEPENDENT、MISMATCH、TAINT）采集本身有采样漏桶，可能"结构性为 0"被误读为"已安全"。缓解：`AuthzShadowReporter.shouldEvaluate` 注释明确"采样只决定看不看，看到必报"（`:54-57`），且 `RLS_DEPENDENT` 是非平凡信号、与采样无关必须归零。
- **改进点 5 风险**：ABAC 引擎引入后，若属性上下文（如 `timeOfDay`）取值来自不可信源，可能被注入绕过。缓解：属性全部来自已验签的 `TenantContext`/服务端时钟，绝不来自客户端输入（呼应 `AuthorizationService.java:25` "context 来源必须可信"）。
- **改进点 6 风险**：决策查询端点若错误返回其他租户数据，等于把审计面变成泄露面。缓解：端点须走 `platform_ops` 数据源 + 平台权限闸门，且 `tenant_id` 过滤在 SQL 层强制（绝不靠应用层 if，呼应铁律 8 读不到=拒绝）。
- **监管合规风险**：PII 脱敏若覆盖率不足（改进点 3 未落地前仅 4 类），仍可能经模型输出泄露学生身份证/手机。缓解：在改进点 3A 落地前，输出 moderation 的 PII 检测虽覆盖窄，但 `ZeroRetentionGate`（维度 5）已在"真实学生数据"分支强制零保留，二者叠加降低泄露面。

### 9.4 一句话结论

本平台在"权限与护栏"维度以 **RLS 数据层强制 + 应用层唯一 Gate + fail-closed 贯穿 + 信任围栏注入架构 + 影子灰度方法论** 的组合，显著领先竞品的"无内建/靠宿主"范式；其真实短板不在机制而在**可观测性（决策查询端点缺失）、PII 覆盖度（受引擎限制）、属性策略表达力（RBAC 起步）** 三处——三者均有明确、可验收的改进路径，且不与任何铁律冲突。

4. **与既有梳理报告不一致之处（重要）**：任务书与既有的 `docs/能力维度实现方式梳理报告.md` 第 7 章均将"提示注入防护"描述为疑似盲区（"当前是否有输入侧注入检测？还是只靠 RLS + 工具 Gate？"）。**经源码复核，本平台实际已实现 `PromptGuard`（`agent-application/.../prompt/PromptGuard.java`）**：含用户输入/工具结果/记忆/压缩态的信任围栏、长度/深度/元素数硬上限（fail-closed 拒绝）、以及 `detectSuspicious` 观测型注入检测，并带 `PromptInjectionRedTeamTest`（R-1~R-8）红队回归。**梳理报告第 7 章遗漏了 `PromptGuard`，属文档不完整而非代码缺口**。本报告已如实补全：实际存在输入侧防护，但其"检测只观测不阻断"是有意设计取舍（避免教育场景误杀），真正的主防线是"Gate 不信任模型决定 + 信任围栏 + 硬上限"。据此，本平台在提示注入维度是"持平"而非"落后"，盲区应修正为"高风险注入模式未被主动阻断"与"无分类器级检测"。
