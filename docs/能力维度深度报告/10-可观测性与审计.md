## 一、维度定义与评估坐标系

### 1.1 这个维度到底解决什么问题

一个 agent 平台出问题时，工程师要连续回答三个问题，而这三个问题的难度是递增的：

1. **「怎么知道出问题了？」** —— 这是**检测**。传统服务的检测对象是 HTTP 状态码与延迟；agent 的检测对象多了一层：**模型答完了但答错了**（链路 `SUCCEEDED`，任务却是失败的）。本仓库把这件事写进了 schema 注释：「链路终态 **≠ 任务成功**。`SUCCEEDED` 只说明框架没崩、走完了终止逻辑」（`01_platform_ddl.sql:823`）。
2. **「怎么定位到是哪一步出的？」** —— 这是**归因**。agent 的一次运行横跨 HTTP 入口、数据库事务、消息队列、另一个进程的 Worker、外部模型供应商、外部工具与 RAG 服务。归因的前提是**这些边界上有一个共同的标识能把它们串起来**。这是本维度真正的工程难点，也是本报告的核心结论所在。
3. **「怎么证明当时确实发生了什么？」** —— 这是**举证**。对教育场景（未成年人数据、PIPL）与多租户 SaaS（SOC 2 / 等保），"我们记录过"必须能变成"任何人（包括我们自己）都改不掉、删不掉的记录"。这要求审计不是"一张写了就完事的表"，而是**追加写 + 不可改 + 可验证**。

它**不解决**「模型质量本身」（维度 6/8）与「权限判定正确性」（维度 7），但与它们强耦合：**没有可观测性，维度 6/8/9/11 的所有机制都无法被证明在工作**——这正是本维度在 13 个维度里的特殊地位：它是其他维度的**证据层**。

本项目在这个维度上有一个非常鲜明的形态，可以一句话概括：**审计优先、指标滞后、追踪半程**。

- **审计优先**：`audit_record` 有 DB 触发器拒绝一切 UPDATE（`01_platform_ddl.sql:546-560`、触发器 `:4683`），DELETE 只走"声明了 `agent.retention.actor` 的受控清理通道"；`authz_decision_log` 不挂 RLS、只增不改、`reason_code` 只存码（`:971-1002`）；审计写入前跑 PII 正则，命中即**拒绝整条写入**（`JdbcAuditRepository.java:34-56`）。这套东西的完成度在本次对比的框架里是罕见的。
- **指标滞后**：指标宽表 `agent_trace_metric` 有 40 列（`01_platform_ddl.sql:761-809`），设计得相当讲究（幂等覆盖写、`trace_id_source` 降级留痕、9 值终止原因、`metric_version`），但**其中 7 列至今没有任何写入方**（§4.2 D-9），看板上因此有恒为"未采集"的面板。
- **追踪半程**：`traceId` 在 HTTP 入口、MDC、`correlation_id`、MQ 消息头、Worker 消费端**全部打通**，但它**不跨 outbox**——中继线程为每一轮发布**新生成**一个 traceId（`OutboxRelay.java:123-132`），于是"用户报障时提供的那个 traceId"只能查到 HTTP + DB 段，查不到 Worker 的执行日志。这不是遗漏，是**写进了注释的有意取舍**（"一轮中继 = 一条系统链路"），但它的代价被严重低估了（§5.3 劣势 1）。

### 1.2 能力分层的四档模型

本维度不适合用"有没有监控"来分层，因为几乎所有系统都有日志。更有区分度的分层轴是：**记录是否结构化 → 记录之间是否可关联 → 关联是否跨进程 → 事实是否不可篡改且可验证**。

| 档位 | 名称 | 判定特征 | 典型表现 |
|---|---|---|---|
| **L0 黑盒** | 只有 stdout | 无 traceId、无指标、无审计；排障靠 `grep` 时间窗 + 猜 | 早期 Demo、`print` 驱动开发 |
| **L1 进程内可观测** | 日志带 traceId + 散点指标 | 单进程内能定位；跨进程即断链；指标是"打点"而非"事实派生" | 多数 Spring Boot 服务的默认形态；OpenAI Agents SDK 关闭外发后的形态 |
| **L2 三支柱成型** | 结构化日志 + 指标 + 持久化 trace/事件表 | 有 `run_event`/trace 表可回放；有 Prometheus 抓取；审计表 append-only（应用层约定） | 本项目的**指标与审计**已在此档，**追踪**在此档下沿 |
| **L3 事实派生 + 跨边界 + DB 强制** | 指标是事实表的确定函数；traceId 跨 HTTP/MQ/DB；审计不可改由数据库强制；有 SLO 告警规则 | 竞品的 SaaS 形态（LangSmith）在"追踪 + 看板"上到此档，但不做 DB 强制审计 |
| **L4 语义约定一等公民** | OTel GenAI SemConv span 树 + tail sampling + evals 进 CI + 可验证审计链（Merkle/WORM）+ 单位经济学 | 目前**没有任何一家**完全达到；OpenAI/LangSmith 在 span 语义与评估上最接近，WORM/哈希链在通用合规领域成熟但 agent 框架普遍没有 |

**本项目的位置需要分项判定，不能给一个总分**：

| 子能力 | 档位 | 依据 |
|---|---|---|
| 审计不可变性 | **L3+**（接近 L4 的"凭据分离"） | DB 触发器 + 角色隔离脚本 + 启动守卫（**守卫当前空转**，见 §4.2 D-5） |
| 指标事实派生 | **L3** | `agent_trace_metric` 由 `run`/`run_step`/`tool_operation`/`usage_record` 派生并幂等覆盖写（`AgentMetricCollector.java:104-211`） |
| 指标业务语义 | **L2** | 有 token/成本/轮次，**无** cost per successful task、无 RAG 命中率 |
| 分布式追踪 | **L1.5** | traceId 跨 MQ 打通，但无 span、无父子层级、**不跨 outbox**、无 OTel |
| 告警闭环 | **L1** | 应用内 4 条规则落 `review_task`；比例类规则**已写但无调用方**；Prometheus **无任何告警规则** |
| 审计可验证性 | **L2** | append-only（可信）但**无哈希链**，无法自证"没有被有权限的人改过" |

| 轴 | 观测什么 | 怎么观测（本项目可采集的信号） |

### 1.4 本维度在 agent 系统中的位置

```
  维度 7 权限（authz 判定举证） ──► authz_decision_log（只增不改，不挂 RLS）
  维度 5 工具（副作用事实）     ──► tool_operation / attempt ──┐
  维度 9 成本（计量事实）       ──► usage_record ──────────────┤
  维度 3 事件溯源（既成事实）    ──► run + run_step + run_event ─┴─► AgentMetricCollector
                                   （终态触发 → outbox → 专用队列 → 指标宽表）
                                     └─► agent_trace_metric（40 列，幂等）+ tool_call 明细
                                          └─► mv_agent_metric_hourly ──► Grafana
  维度 4 流式（事件流）         ──► run_event（SSE 游标 + 回放 /transcript）
  维度 11 故障（异常信号）       ──► ReviewAlertService（4 条）──► review_task
                                    QualityAlertEvaluator（比例类，⛔ 无调用方）
  维度 8 RAG（检索质量）        ──► agent_risk_event（只存摘要）+ agent_eval_sample（n<30）
                                    + agent_task_outcome（外部校验回执）

  反哺：告警 → 维度 11 故障收敛 ｜ 成本看板 → 维度 9 定价与配额
        质量抽样 → 维度 6/8 效果回归 ｜ 审计 → 维度 2/7 合规举证
```

**上游**：维度 3（`run_event`/`run_step` 是唯一可信事实源）、维度 5（`tool_operation`）、维度 9（`usage_record`）、维度 7（`authz_decision_log`）、维度 11（错误码与终态）。
**下游**：维度 9 的成本治理决策、维度 11 的故障响应、维度 6/8 的质量回归、对外合规与 SLA 承诺。

**一句话**：本维度不生产事实，它**把其他维度生产的事实变成可读、可查、可举证的证据**。因此它的质量上限被事实层的质量决定，而它的下限决定其他维度是否能被验证。

### 2.1 核心理论 / 概念框架（9 个）

**T1 · 可观测性三支柱与「监控 ≠ 可观测」**

- 出处：Charity Majors、Liz Fong-Jones、George Miranda《**Observability Engineering**》，O'Reilly，2022（ISBN 978-1-4920-7644-5）。另见 Google SRE Book 第 6 章 "Monitoring Distributed Systems"（<https://sre.google/sre-book/monitoring-distributed-systems/>，**本环境抓取该域名失败，引用依据为该书公开出版的章节标题与业界通用表述，未逐字核对原文**）。
- 核心命题：**监控（monitoring）回答"系统是否在工作"，可观测性（observability）回答"为什么它不工作"**。前者面向已知故障模式（预定义指标 + 阈值），后者面向**未知的未知**——要求系统输出足够丰富的结构化事件，使工程师能在事后提出**任意**新问题而不必先改代码埋点。
- 三支柱的分工（本书与 SRE 系列的共识）：**metrics 便宜、聚合、适合告警**；**logs 昂贵、明细、适合取证**；**traces 结构化、适合跨服务归因**。三者不是替代关系：用 metrics 做告警、用 trace 定位到段、用 log 看到具体值。
- **对本项目的映射**：`LogContext` 的类注释把这个分工写死了一次——"指标里没有、日志里必须有，两边不冲突"（`LogContext.java:21-24`）；`AgentMetrics` 的类注释同样写了"明细 → 日志；聚合 → 指标"（`AgentMetrics.java:32-36`）。这是**理论被落进代码注释**的少见案例，值得肯定。

**T2 · SLI / SLO / SLA 与 error budget**

- 出处：Google SRE Workbook，"Implementing SLOs" 与 "Alerting on SLOs"（<https://sre.google/workbook/implementing-slos/>、<https://sre.google/workbook/alerting-on-slos/>，**本环境同样抓取失败，降级标注：引用依据为该系列公开的章节结构与业界通用定义**）。
- 核心定义：**SLI**（service level indicator）= 一个可测量的服务质量比值（好事件 / 有效事件）；**SLO** = SLI 的目标值 + 时间窗；**SLA** = 带违约后果的 SLO。**error budget = 1 − SLO**，是"允许失败多少"的预算。
- 告警推论（该章最有操作性的部分）：**不要按原始指标阈值告警，要按 error budget 的燃烧速率（burn rate）告警**，并采用多窗口（如 1h 短窗 + 6h 长窗）多燃烧率（14.4x / 6x / 1x）以减少误报与漏报；而且**只在症状（用户可感知的失败）上告警，不在原因（CPU 高）上告警**。
- **对本项目的映射**：本项目有 SLI 的**原料**（`terminal_state`、`auto_verified`、`duration_ms`），但**没有一个被声明为 SLI，没有 SLO，没有 error budget，也没有任何基于燃烧率的告警**。`QualityAlertEvaluator` 用了"当前窗 vs 7 天基线 + n≥30"（`:44-68`），这是**统计异常检测**而非 SLO 告警——两者解决不同问题：前者发现"和过去不一样"，后者回答"我们是否正在违约"。见改进点 2。

**T3 · USE 与 RED 两套资源/服务观测方法**

- 出处：Brendan Gregg，**The USE Method**（<https://www.brendangregg.com/usemethod.html>）；Tom Wilkie，**The RED Method**（<https://grafana.com/blog/2018/08/02/the-red-method-how-to-instrument-your-services/>）。
- **USE**（面向资源）：对每个资源看 **U**tilization（使用率）、**S**aturation（饱和度，排队长度）、**E**rrors（错误数）。判定口径是"资源"，如 CPU、连接池、队列。
- **RED**（面向服务）：对每个服务看 **R**ate（请求速率）、**E**rrors（错误率）、**D**uration（时延分布）。
- **对本项目的映射**：
  - 本项目**部分覆盖 RED**：`ai.model.calls.total`（rate）+ `error` 标签（errors）+ `ai.model.calls.latency`（duration，带 0.5/0.95/0.99 分位）（`MicrometerModelCallObserver.java:39-49`、`:69-129`）。
  - 本项目**几乎没有 USE**：`outbox_event` 积压（饱和度）**无任何指标**；`BackpressureController` 内存里算了 `lastDepth`/`throttledRounds`/`probeFailures`（`:44-54`）但**没有注册任何 Meter**；DB 连接池、RabbitMQ 队列深度都只能靠外部 exporter。
  - 这个缺口直接导致改进点 2 的 outbox 积压告警**无法只靠现有指标实现**，必须先加 Gauge。

**T4 · 分布式追踪上下文传播：W3C Trace Context**

- 出处：W3C Recommendation，**Trace Context**，2021-11-23（<https://www.w3.org/TR/trace-context/>）。已核对原文：`traceparent` = `version "-" trace-id "-" parent-id "-" trace-flags`；`trace-id` 为 **32 位小写十六进制（16 字节）**，全零无效；`parent-id` 为 **16 位小写十六进制（8 字节，即 span-id）**，全零无效；`trace-flags` 当前仅最低位 `sampled` 有效；`tracestate` 承载厂商扩展，最多 32 个 list-member，合并头至少应传播 512 字符。
- **对本项目的关键映射（本报告最重要的技术观察之一）**：本项目 `LogContext.newTraceId()` 生成的是 **32 位小写十六进制、无连字符**（`LogContext.java:75-87`），其**形状与 W3C `trace-id` 完全一致**。也就是说，**我们已经有了 trace-id，缺的是 `parent-id`（span-id）、`traceparent` 头，以及 span 这一层结构**。这使改进点 1 的迁移成本远低于从零引入追踪——不需要把已有 id 体系推倒重来，只需要"给每个 trace-id 挂上 span-id"。

**T5 · OpenTelemetry 与 GenAI 语义约定（状态：演进中，未 stable）**

- 出处：OpenTelemetry 官方语义约定页（<https://opentelemetry.io/docs/specs/semconv/gen-ai/>）**现在只返回一条迁移公告**：GenAI 语义约定已迁出主仓库，迁至 <https://github.com/open-telemetry/semantic-conventions-genai>，原页面"no longer maintained in this repository"。新仓库 README（核对日 2026-11-05）说明它"extends the OpenTelemetry Semantic Conventions with GenAI-specific conventions"，覆盖 **spans / metrics / events，面向 GenAI clients、MCP 与厂商专有约定（OpenAI 等）**，且 **Schema URL 一节仍写着 "TODO"**。
- **诚实结论**：截至 2026-11，GenAI SemConv **仍处于演进状态，未进入 stable**（主仓库把整块内容迁出、schema URL 未定，是最直接的证据）。因此本报告在改进点 1 中采用"**属性名可对齐、但不要把内部数据模型绑死在 SemConv 上**"的保守策略。
- 常被引用的属性族（各家实现普遍已支持，具体拼写以 semconv 仓库为准）：`gen_ai.operation.name`、`gen_ai.provider.name`、`gen_ai.request.model`、`gen_ai.response.model`、`gen_ai.usage.input_tokens` / `gen_ai.usage.output_tokens`、`gen_ai.response.finish_reasons`、`gen_ai.tool.name`、`gen_ai.conversation.id`。**这些是 span 属性（允许高基数），不是 metric 标签**——这个区分是本项目 `AgentMetrics` 白名单与 Micrometer 观察者之间冲突的根源（§4.2 D-7）。
- 另需注意：规范里 token 计量有"是否记录 prompt/completion 内容"的开关语义；本项目因合规红线（未成年人原文）**必须永久关闭内容记录**，这与 OpenAI Agents SDK 默认 `trace_include_sensitive_data=True` 的取向**正好相反**（§3.1）。

**T6 · LLM/Agent 的 trace 语义：run / span / generation / retrieval**

- 出处（框架级，均已核对官方页）：
  - OpenAI Agents SDK：**Trace** = "a single end-to-end operation of a 'workflow'"，由 **Span** 组成（"operations that have a start and end time"）；内置 span 类型含 `agent_span`、`generation_span`、`function_span`、`guardrail_span`、`handoff_span`、`turn_span`、`task_span`（<https://openai.github.io/openai-agents-python/tracing/>）。
  - LangSmith：**run** ≈ OTel span（"you can think of a run as a span"），**trace** = 一次操作的 run 集合，**thread** = 多轮会话的 trace 序列，**trajectory** = 把会话压平成有序消息列表（<https://docs.langchain.com/langsmith/observability-concepts>）。单 trace 上限 **25,000 runs**，SaaS 保留 **180 天**。
  - Agno：span 覆盖 agent/team/workflow run、model call、tool call、team coordination、workflow step；**每个 span 最多保留 1024 个属性**（<https://docs.agno.com/agent-os/tracing/overview>）。
- **共同抽象（可视为该领域的事实标准）**：一次任务 = 一棵树，根是"任务"，叶是"模型调用 / 工具调用 / 检索调用"，每层都有开始/结束/状态/属性。**本项目只有"根"（`run`）与"扁平事件序列"（`run_event`），没有中间层**——`agent_trace_metric` 是**一条 Trace 一行**的宽表（DDL `:816`），`agent_trace_tool_call` 是**按工具名聚合**（DDL `:862`），两者都不是"树"。

**T7 · 审计的不可否认性：append-only、WORM、Merkle 哈希链、合规基线**

- 出处：
  - **RFC 6962**《Certificate Transparency》，Ben Laurie / Adam Langley / Emilia Kasper，2013-06（<https://www.rfc-editor.org/rfc/rfc6962>）——**可验证追加日志（verifiable append-only log）**的工程标准形态：Merkle 树 + 包含证明（inclusion proof）+ 一致性证明（consistency proof）。这是"日志可自证未被篡改"的经典构造。
  - **SEC Rule 17a-4(f)**（<https://www.sec.gov/rules/final/34-47806.htm>）——金融业电子记录留存规则，其技术附件确立了 **WORM（Write Once Read Many）**存储的合规地位：记录写入后不可改、不可删，直至保留期结束。
  - **GDPR Art. 30**（处理活动记录）与 **Art. 32**（处理安全，含"确保秘密性、完整性、可用性与韧性"）（<https://gdpr-info.eu/art-30-gdpr/>、<https://gdpr-info.eu/art-32-gdpr/>）。Art. 5(1)(f) 的完整性/秘密性原则要求"防止未经授权或非法的处理，以及意外丢失、毁损"。
  - **SOC 2 Trust Services Criteria**（AICPA，<https://www.aicpa-cima.com/topic/audit-assurance/audit-and-assurance-greater-than-soc-2>）——CC7 系列（系统运营）要求对安全事件的检测与评估，审计日志的完整性与保留期是常见审计证据项。
- **三层不可变性（本报告的归纳，用于评价本项目）**：
  1. **L-a 应用层约定**：代码里不提供 update/delete（最弱，直连 SQL 即绕过）。
  2. **L-b 数据库强制**：触发器拒绝 UPDATE/DELETE + 角色权限回收（强，但**持有超级用户/表主仍可绕过**；且"声明式 `set_config` 即放行"本质是**意图声明而非访问控制**——本项目的 DDL 注释自己承认了这点，见 `01_platform_ddl.sql:567`）。
  3. **L-c 可验证**：哈希链 + 周期锚定 + 第三方/离线副本（最强，能证明"连有权限的人也没改"）。
- **本项目的落点**：**L-b**（触发器 + 凭据分离脚本 + 启动守卫），**没有 L-c**（全仓无 `prev_hash`/`chain_hash`，见 §4.2 D-4）。对现阶段的合规诉求（PIPL 未成年人数据、教育行业审计）L-b 可能够用；但一旦客户要求 SOC 2 或等保三级以上的"日志完整性"证据，L-b 是**结构上无法回答**的——这是改进点 4 的动机。

**T8 · 采样的两种时机与成本结构**

- 出处：OpenTelemetry 官方 Sampling 文档（<https://opentelemetry.io/docs/concepts/sampling/>，核对原文）：**head sampling** 在 trace 早期决策，最常见形态是 **Consistent Probability Sampling**（按 trace-id 哈希 + 目标比例，所以整条 trace 要么全采要么全不采，不会缺 span）；**tail sampling** 在 trace 完成后按全链路属性决策（"always sampling traces that contain an error"、"based on overall latency"）。文档明确 head 的**主要缺点是"无法基于整条 trace 的数据决策"**（"you cannot ensure that all traces with an error within them are sampled with head sampling alone"），tail 的**三个主要缺点是难实现、难运维（有状态、吃资源）、常被厂商锁定**。
- **对本项目的映射（一个反直觉的正面结论）**：本项目**事实层根本不采样**（所有 Run 都落 `run_event` + `agent_trace_metric`），采样只发生在**评估抽样**（`agent.quality.eval.sample-rate=0.05`，yml `:81`）与**人工复核抽样**（`ReviewSampler`，yml `:119-146`）。这是一种**"事实层全量 + 派生层聚集 + 评估层抽样"的三层结构**，天然规避了 head sampling 的"错误 trace 被漏采"问题——因为事实从不丢。代价是存储随 Run 数线性增长（且**指标宽表没有保留期配置**，见 §5.3 劣势 6）。改进点 7 讨论的是**导出层**采样（span/trace 外发），与事实层无关。

**T9 · 评估驱动的可观测（evals as tests）**

- 出处：Hamel Husain《**Your AI Product Needs Evals**》（2024，<https://hamel.dev/blog/posts/evals/>，**博客级来源，未逐字引用**）；工程化载体见 LangSmith 的 Evaluation 体系（<https://docs.langchain.com/langsmith/evaluation-concepts>）与 OpenAI Evals 的公开接口。业界共识表述：**把评估集当单元测试跑在 CI 里**，让"模型/提示/检索改动导致的质量回退"在合并前被发现，而不是上线后靠用户投诉发现。
- **与本项目的映射**：本项目已有评估的**骨架**（`agent_eval_sample` 人工打标 `n<30 不显示百分比`、`agent_task_outcome` 外部校验回执并"必须并排显示覆盖率"、`L2AttributionEvaluator` + `ModelAttributionJudge` 独立科目），但**没有把它接成 CI 门禁**——评估是"线上抽样 → 人工看板"，不是"改动前必须通过的测试"。
- **一个尖锐的对照**：`PublishGuards` 是发布守卫（会读 `sampled` 相关状态），但**它守卫的是"有没有抽样"，不是"抽样结果是否达标"**。也就是说，当前的门禁是"流程合规"，不是"质量达标"。改进点 5 要解决的就是这一字之差。

### 2.3 业界公认的反模式（anti-pattern）清单及判别方式

1. **「指标标签放 run_id / trace_id」**：每个 Run 一条时间序列，时序库被打爆，且零业务价值。判别：Prometheus 里 `count by (__name__)` 是否随流量线性增长。本项目`AgentMetrics` 在**运行期**抛异常拒绝（`:80-110`），是正确做法；**但 Micrometer 观察者绕过了这套约束**（§4.2 D-7）。
2. **「只有成功率，没有分母口径」**：把"链路 SUCCEEDED"当成功率。判别：分母是 `terminal_state='SUCCEEDED'` 还是 `human_verdict='SUCCESS'`。本项目 schema 注释明确区分（DDL `:823`），看板统计用的是 `terminal_state`（`agent-quality.json` 成功率面板），**属"技术成功率"，不是"任务成功率"**——诚实但需要标注。
3. **「用 max 冒充 P95」**：分位数不可从计数与求和还原。判别：看板上 P95 是否由 `percentile_cont` / histogram bucket 算得。本项目在 `agent_trace_tool_call` 上**主动放弃 P95**（DDL `:862`："不存 P95 …… 强行用 max 冒充 P95 会让尾部延迟被高估"），这个自我约束是**正面案例**。
4. **「审计只写不校验」**：有表、有数据、无完整性校验。判别：是否存在一条能回答"第 N 行之后有没有被删/改"的命令。本项目**没有**（劣势 4）。
5. **「守卫写了但没跑」**：守卫逻辑存在、单测全绿、运行时因配置为空/未装配而空转。判别：**把守卫的输入改成空集合，测试还绿吗？** 本项目 `AuditTamperProofGuard.GUARDED_TABLES` 是**被注释掉的空数组**（`:35-37`），单测测的是纯函数 `assess()`，因此"守卫在跑"这个事实**不成立而无人发现**（§4.2 D-5）。
6. **「列存在 ≠ 有人写」**：宽表加了列、文档写了指标名、看板画了面板，但生产者传 `null`。判别：对每一列做"全仓写入方检索"，找不到非测试写入方即为死列。本项目 7 列中招（§4.2 D-9）。
7. **「告警出口是人工队列」**：把异常变成 `review_task` 而没有通知通道，等于"异常在等一个有缘人打开看板"。判别：告警产生到人收到通知的 P50 时延。本项目**全部告警都落 `review_task`**，`RetentionJob` 甚至自陈"这是它唯一的告警出口"是一行 WARN（`RetentionJob.java:34-37`）。
8. **「日志里打请求/响应原文」**：agent 场景下原文即用户隐私（未成年人原话）。判别：`grep` 日志模板里是否出现 `prompt|content|answer|payload` 变量。本项目在**审计与指标层**做得很严（`AgentChatAuditPort` 明确"不存正文"、`agent_risk_event` 只存摘要），但**日志层没有编译期/扫描期约束**（劣势 5）。
9. **「共享可变状态做计时」**：把 `Timer.Sample` 存在单例字段上，并发下互相覆盖。判别：观察者类是否有非 final 的 `Timer.Sample` 字段。本项目 `MicrometerExecutionObserver.loopTimer`（`:48`）与 `MicrometerTraceObserver.sample`（`:38`）**都是实例字段**，而 Worker 并发度为 4（yml `:193`）——A 的耗时会被算到 B 头上（劣势 3）。
10. **「静默降级冒充成功」**：采集失败只 WARN、指标缺失显示 0、traceId 缺失就用 runId 顶替。判别：缺失路径是否有稳定原因码。本项目做对了两件：采集失败**不阻断终态**但由"补算"兜底（`RunExecutionLoop.java:1329-1353`）；`trace_id` 降级**必须留痕** `trace_id_source`（`JdbcTraceFactRepository.java:130-148`）。这是**正面案例**。

## 三、竞品实现全景（每个主流方案一段）

> **总体判断（先行给出）**：本次对比的 7 个方案里，**追踪的"语义与易用性"普遍强于本项目**（开箱 span 树 + 可视化 + 与评估打通），而**审计的"不可变性"与"多租户隔离"普遍弱于本项目**（多数框架没有审计表，更没有 DB 强制 append-only）。两边的强项几乎不重叠——这决定了本项目的改进方向应当是"补追踪与告警"，而不是"补审计"。

### 3.1 OpenAI Agents SDK（内建 tracing + Traces 仪表盘）

**官方定位与实现机制**（<https://openai.github.io/openai-agents-python/tracing/>，已核对原文）：
- **内建 tracing 且默认开启**："The Agents SDK includes built-in tracing, collecting a comprehensive record of events during an agent run: LLM generations, tool calls, handoffs, guardrails, and even custom events that occur."
- **两级原语**：Trace（"a single end-to-end operation of a 'workflow'"）与 Span（"operations that have a start and end time"）。默认 span 覆盖 `agent_span` / `generation_span` / `function_span` / `guardrail_span` / `handoff_span` / `turn_span` / `task_span` / 语音相关 span。
- **导出机制**：默认 `BatchTraceProcessor` 后台批量导出；`flush_traces()` 可在 trace 关闭后阻塞式刷出；三种关闭方式（环境变量 / `set_tracing_disabled` / `RunConfig.tracing_disabled`）。
- **隐私取向**：`RunConfig.trace_include_sensitive_data` **默认 True**（即默认把 LLM 输入输出与工具输入输出一起上传）；官方同时写明"Tracing is unavailable for organizations that use OpenAI's APIs under a Zero Data Retention (ZDR) policy"。
- **扩展性**：`add_trace_processor()`（追加处理器）/ `set_trace_processors()`（替换，不再发 OpenAI 后端）；官方列了 **31 个**第三方集成（Arize Phoenix、Langfuse、LangSmith、Datadog、Pydantic Logfire 等）。**重要警告**（原文）："A redaction processor registered before an exporter therefore does not prevent that exporter from receiving data if redaction fails." —— 即"脱敏处理器 + 导出器"不是原子组合，脱敏失败仍可能外发。官方建议把脱敏与投递放进同一个 exporter。

**优点**：零配置即有 span 树与仪表盘；语义完备（handoff/guardrail 这些 agent 特有动作都有 span）；批量导出与 `flush_traces` 兼顾吞吐与确定性；对"脱敏与导出必须原子"的**诚实警告**在同类文档中少见。
**局限/代价**：**默认上传敏感内容**，与本项目合规红线直接冲突（要额外实现 redaction exporter 并替换默认处理器）；ZDR 客户**完全不可用**；trace 结构是 OpenAI 后端的私有格式而非 OTel 标准（集成方做转换）；**无审计不可变性概念**（trace 可删、可改、有保留期）。
**适用场景**：以 OpenAI 为主模型、对数据出境无硬约束、需要最快拿到调试体验的团队。

### 3.2 Anthropic Claude Agent SDK（无内建 tracing）

**官方定位与实现机制**（<https://code.claude.com/docs/en/agent-sdk/overview>，已核对）：SDK 是"a library that runs the Claude Code binary"在你自己的进程内。官方概览页的 **Capabilities 表**列出 Built-in tools、**Hooks**、Subagents、MCP、Permissions、Sessions、Skills/commands/memory、Plugins——**没有** telemetry / tracing / observability 任何一项；页面全文**不出现** OpenTelemetry、trace、telemetry、observability、logging、monitoring 这些词，也**不出现** usage/cost 上报。
**唯一相关扩展点**：Hooks——"Run custom code at key points in the agent lifecycle"。这是事实上的埋点入口（可在 tool 调用前后、会话边界插入自己的日志/span），但**官方未把它描述为监控机制**。
**优点**：不自造半成品观测层（与它在预算上的取向一致）；Hooks 是通用扩展点，宿主可接任意后端；`--output-format json` 的 headless 模式可作为结构化结果通道。
**局限/代价**：**可观测性完全外包给宿主**——没有 trace 数据模型、没有 span 约定、没有内置看板；多进程/子 Agent 场景下**跨进程关联要靠宿主自己设计**；成本与用量要到 API Console 侧看，与运行期事件不同源。
**适用场景**：已有成熟可观测栈（OTel + 自建 trace 库）且希望完全掌控数据边界的团队；本项目在"审计与指标自持"的取向上与它更接近，但本项目**做了它没做的持久化事实层**。

### 3.3 LangGraph / LangSmith（一等公民 trace + 评估 + 监控）

**官方定位与实现机制**（<https://docs.langchain.com/langsmith/observability-concepts>，已核对原文）：
- **四级数据模型**：**run**（单个工作单元，"you can think of a run as a span"）→ **trace**（一次操作的 run 集合）→ **thread**（多轮会话的 trace 序列，靠 `thread_id` metadata 关联）→ **trajectory**（把 thread 压平成有序消息列表）。这是本次对比里**唯一把"多轮会话"做成一等公民**的方案。
- **接入方式**：集成（LangChain/LangGraph/OpenAI/Anthropic/CrewAI 等自动埋点，等价于 auto-instrumentation）+ 手工（`@traceable` 装饰器 / `trace` 上下文管理器 / `RunTree` 低层 API）。
- **限额与保留**：单 trace **最多 25,000 runs**，超过即拒绝后续 run；SaaS **保留 180 天**，之后永久删除（保留有限元数据做用量统计）；想长期保留必须把数据放进 dataset（dataset 永久保存）。
**优点**：**trace 数据模型最完整**（run/thread/trajectory 三层，直接对齐"调试一次 / 看多轮 / 读对话"三种诉求）；评估（dataset + evaluator）与 trace 同源，`evals as tests` 落地最顺；自动埋点覆盖面广。
**局限/代价**：**25,000 runs 硬上限 + 180 天硬保留**——超过上限的 run 被**拒绝**（"LangSmith will reject any additional runs"），这在长任务/高并发下是**数据缺口而非降级**；**无审计不可变性**（trace 可 `delete`）；租户/权限模型是 workspace 级，**不是数据库强制的多租户隔离**；SaaS 形态意味着**数据出境**。
**适用场景**：以"可观测性驱动优化"为主线的团队；需要 trajectory 视角做对话级分析的场景。

### 3.4 Google ADK（OTel 原生 + Cloud Trace/Logging/Monitoring）

**官方定位与实现机制**（<https://adk.dev/observability/>，已核对原文）：官方明确"ADK provides built-in observability through **logging, metrics, and traces**"。JVM（Kotlin/Java）路径的官方 Quick Start 直接给出 **OpenTelemetry `GlobalOpenTelemetry` + `OtlpGrpcSpanExporter` + `SdkTracerProvider` + `BatchSpanProcessor`** 的装配代码，即**ADK 走标准 OTel，不自定义导出体系**。另有 `TelemetryConfig.captureMessageContent` 开关（官方标注"use with caution in production"），以及 `LoggingPlugin` 做控制台输出。更高级能力指向 "observability ADK Integrations"（ADK 集成页的 observability 分类）。
**优点**：**与标准栈零摩擦**——只要 OTel Collector 能收，任何后端都能接（Cloud Trace、Jaeger、Langfuse、Phoenix、Datadog）；内容捕获有显式开关且默认谨慎；Java/Kotlin SDK 与 Spring 生态同源（对本项目最有参考价值的一家用例）。
**局限/代价**：**观测能力与 GCP 托管栈耦合更深的部分（Agent Engine 的观测/指标）不在开源 SDK 里**；开箱"仪表盘"仍需自己搭（ADK 给的是 instrumentation，不是 dashboard 产品）；**无审计/不可变性**；内容捕获开关是"全局静态字段"（`TelemetryConfig.captureMessageContent`），在多租户进程里**无法按租户差异化**。
**适用场景**：已用 GCP 或已有 OTel 体系的团队；希望"框架只负责埋点，后端自己选"的组织——这是本项目改进点 1 最直接的技术参照。

### 3.5 Microsoft AutoGen（原生 OTel + GenAI SemConv；已归档）

**官方定位与实现机制**（<https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tracing.html>，已核对原文）：
- "AutoGen has **built-in support for tracing** and observability … This capability is powered by the **OpenTelemetry** library, which means you can use any OpenTelemetry-compatible backend"。
- **遵循语义约定**："AutoGen follows the **OpenTelemetry Semantic Conventions** for tracing, for agents and tools"，并"It also follows the **Semantic Conventions for GenAI Systems** currently under development"——**注意"under development"是官方原话**，与 T5 的结论一致。
- **Runtime 自动埋点**："The AutoGen runtime already supports open telemetry (automatically logging message metadata)"；LLM 侧靠 `OpenAIInstrumentor` 自动插桩；可用 `NoOpTracerProvider` 或 `AUTOGEN_DISABLE_RUNTIME_TRACING=true` 关闭。
- **后端**：Jaeger / Zipkin（示例给的是 OTLP gRPC `:4317`）。
**优点**：**"框架只埋点、后端随便选"的最干净范例**；明确区分 agents/tools 语义约定与（开发中的）GenAI 语义约定，这种"标注成熟度"的做法值得学习；关闭开关有两级（构造参数 + 环境变量），便于排障期临时关。
**局限/代价**：**官方已于 2025-10 并入 Microsoft Agent Framework、2026-10 起归档停维护**，其结论只代表末代状态，**不应作为新项目选型依据**；文档**未列 span 的精确字段清单**（只说"遵循约定"），落地时仍需自行核对；**无审计、无多租户、无内置看板**。
**适用场景**：仅作历史参考与"OTel 接入方式"的对照样本。

### 3.6 CrewAI（观测由第三方平台生态承担）

**官方定位与实现机制**（<https://docs.crewai.com/en/observability/overview>，已核对）：官方 observability 概览页的组织方式是"**Available Observability Tools**"（监控与追踪平台、评估与质量保障两类），并给出指标清单分类：性能（执行时间、token 用量、API 时延、成功率）、质量（输出准确率、一致性、相关性、安全性）、成本（API 成本、资源利用率、**Cost per Task**、预算跟踪）。落地方式是接入第三方平台（页面所在版本为 v1.15.x；历史版本页面可见 Portkey 等集成）。
**优点**：**指标分类直接对齐业务语言**（尤其 "Cost per Task" 被列为标准成本指标，比多数框架更接近单位经济学）；"先选工具 → 埋点 → 看板 → **定义告警** → 建基线"的六步落地路径，是本次对比里最像"运维手册"的一份文档。
**局限/代价**：**框架本身不持有 trace 数据**（无内建 trace 存储、无审计表），观测能力随所选第三方平台而变；"Cost per Task" 的分母是"任务"而非"成功任务"，与 T2/T9 的口径要求仍有差距；**离线/自托管场景需要自己拼装**。
**适用场景**：愿意为观测付费买平台、且团队里没有专职 SRE 的组织。

### 3.7 Agno（`tracing=True` + OTel instrumentation + 落库 + Control Plane）

**官方定位与实现机制**（<https://docs.agno.com/agent-os/tracing/overview>，已核对原文）：
- **一行开关**：`AgentOS(agents=[...], db=db, tracing=True)` 即把 span 落到 Agno 数据库；也可 `setup_tracing(db=..., batch_processing=True, max_queue_size=2048, max_export_batch_size=512, schedule_delay_millis=3000)` 精细控制。
- **实现**："AgentOS uses **OpenTelemetry instrumentation** and stores the resulting traces in an Agno database." —— 即**用 OTel 采集、用自己的库存储**，这一点与本项目"事实落自己的 PG"取向最接近。
- **捕获范围**：agent/team/workflow run、model calls、tool calls、team coordination、workflow steps。
- **工程细节**：**每 span 最多 1024 个属性**（可调）；"Tracing is **process-wide**"——若已存在真实 `TracerProvider`，`setup_tracing()` **直接返回**、不安装新 exporter（避免与宿主冲突，但也会让"以为开了其实没开"发生）。
- **查看**：AgentOS Control Plane 或 AgentOS API；支持 trace 过滤。
**优点**：**"OTel 采集 + 自持存储 + 自带控制台"三者齐备**，是本次对比中与本项目架构取向最接近的方案；显式给出 span 属性上限（防属性爆炸）；"process-wide、已有 provider 则不覆盖"是负责任的默认值。
**局限/代价**：**无审计不可变性**（trace 存在自己的库里，可删可改）；Control Plane 是商业产品形态；`setup_tracing` 的"静默返回"是一个**需要被检测的静默降级**（与本项目"fail-closed"取向相反）；多租户隔离依赖 AgentOS 自己的认证模型，不是 DB 级 RLS。
**适用场景**：自托管 AgentOS、希望 trace 数据不出自己库的团队。

## 四、我们的实现（源码级解剖）

### 4.1 架构与数据流

#### 4.1.1 四层结构

本项目的可观测性**不是一套东西**，而是**四套独立演化、通过 `run_id`/`trace_id`/`tenant_id` 三个键松耦合的系统**：

| 层 | 载体 | 写入时机 | 读出口 | 关键性质 |
|---|---|---|---|---|
| **L1 日志** | stdout（`logback-spring.xml`，仅 CONSOLE） | 全过程 | 容器日志采集（**未配置任何采集器**） | MDC 三键恒有值，缺省 `-` |
| **L2 进程指标** | Micrometer `MeterRegistry` | 模型调用 / 执行循环 / 授权影子 | `/actuator/prometheus`（yml `:821-842`） | 仅 `metrics,provider,finish,error,tenant,outcome,retryable` 标签 |
| **L3 事实与派生指标** | PG：`run`/`run_step`/`run_event`/`tool_operation`/`usage_record` → `platform.agent_trace_metric` + `agent_trace_tool_call` → `mv_agent_metric_hourly` | Run 终态触发（异步采集） | Grafana（Platform-PG 数据源）+ `/api/platform/v1/metrics/agent/*` | 幂等 upsert、`trace_id` 唯一、`metric_version` |
| **L4 审计** | PG：`public.audit_record`、`platform.authz_decision_log`、`platform.platform_audit_event`，以及复用 `run`/`run_event`/`run_step` 的 `AgentChatAuditPort` | 治理动作 / 每次授权判定 / 会话审计 | `/api/audit` | append-only、PII 拒写、`erasure_certificate` |

#### 4.1.2 采集链路（Run 终态 → 宽表）

```
RunExecutionLoop（Worker）
  ├─ 终态提交 → appendEvent → run_event（失败只 WARN，不影响终态）   RunExecutionLoop.java:1316-1327
  ├─ appendStep → run_step（幂等，按 (tenant,run,step) 覆盖）
  ├─ emitRiskEvent → platform.agent_risk_event（只存摘要）           :1482-1489
  └─ publishTraceCollect → traceSender.send("TRACE_COLLECT", …)      :1341-1353
        ⚠️ 专用队列 agent.trace.collect；绝不复用 agent.run.execute（铁律 5）
        ▼
TraceCollectMessageHandler（按 eventType 分流，三态：REJECTED / RETRY / CLAIMED）
        ▼
AgentMetricCollector.collect(tenantId, runId)
  ├─ TraceFactPort.load() ← 只读已收敛 Run（在途返回空，采集器二次判 converged）
  ├─ 派生：termination_reason（9 值）、loop_suspected（同工具同参数摘要 ≥3 次）、
  │        invalid = unknown_tool + invalid_arg + duplicate（三类不重叠）
  ├─ upsert → INSERT … ON CONFLICT (trace_id) DO UPDATE；replaceToolCalls 先删后插
  ├─ ReviewAlertService.evaluate() → 命中建 review_task
  └─ raiseEvaluation() → L1 自动校验 / 抽样打标（questionId 只走内部链）
```

**三个值得单独指出的设计点**：
1. **采集走异步、专用队列，失败不影响终态**——"可观测性不能反向伤害业务"的正确取舍。代价是需要"补算"兜底（`PlatformAgentMetricsController` 有重算入口），而**"补算"是否真被使用没有指标能回答**。
2. **`knownTools` = 能力目录 ∪ 代码注册表**（`AgentMetricCollector.java:119-126`）。只用目录会把 native 工具判成"模型幻觉工具"，导致无效调用率虚高——源码注释原文："不报错，只让看板数字悄悄变错"。**指标口径陷阱的典型样本**。
3. **`usage_record` 聚合排除 `tool:` 前缀行**（`JdbcTraceFactRepository.java:287-300`），否则工具名混进"按模型分组"。与维度 9 的 D-15/D-17 同源。

#### 4.1.3 三个 id 空间（本维度的核心缺陷，必须先讲清）

```
【ID-1 HTTP 链路号】32 hex
  X-Trace-Id 请求头（净化后沿用）或 LogContext.newTraceId()
    → MDC traceId                          RequestLoggingConfiguration.java:109-113
    → 响应头 X-Trace-Id（报障时可直接复制）
    → run.correlation_id                   ApplicationConfiguration.java:775-791
    → agent_trace_metric.trace_id（作为 CORRELATION_FALLBACK）
  传播到：HTTP 线程 + 本进程日志 + 落库 correlation_id ✔   不传播到：outbox / MQ / Worker ✘

【ID-2 中继轮次号】32 hex（每轮新生成）
  OutboxRelay 每轮 relayOnce() 生成一次              OutboxRelay.java:119-132
    → MDC traceId（本轮所有租户的发布日志共用）
    → MQ 消息头 x-trace-id                          RabbitMessageSender.java:126-137
    → Worker 消费端 MDC                             RabbitExecutionListener.java:100
  与 ID-1 的关系：无。同一 Run 的两侧是两个不同的随机值 ✘

【ID-3 调用级串链号】模型给的 callId 或 invocationId
  ToolInvocationGate 构造 DelegationCommand 时传入   ToolInvocationGate.java:895-925
    → agent_invocation.trace_id（每次委派一行）
  用途：把"一次委派"归因到"某次模型 tool call"（多跳 Run 区分是第几跳）
```

**这张图解释了一个具体的排障困境**：用户报障给出 `X-Trace-Id` → 你能在网关日志找到请求、在 `run.correlation_id` 找到 Run、回放 `run_event` → 但**无法用这个 id 在 Worker 日志里检索到任何执行细节**，因为 Worker 的 MDC 里装的是 ID-2；反过来，拿 Worker 日志里的 traceId 去查 `run.correlation_id` 也**查不到**。

**交叉点只有一处**：`agent_trace_metric.trace_id` 依次取 `run.trace_id`（**该列无写入方**，D-10）→ `agent_invocation` depth=1 的 `trace_id`（ID-3）→ `correlation_id`（ID-1），并把来源记进 `trace_id_source`（`JdbcTraceFactRepository.java:106-168`）。即：**指标表的 trace_id 大多等于 ID-1，日志的 traceId 大多是 ID-2**——三支柱之间**恰好没有共享键**。

### 4.2 关键设计决策逐条剖析

> 格式：**决策 → 为什么 → 代价 → 证据**。D-5、D-7、D-8、D-9、D-12、D-14 是本次源码复核**新发现**的问题，既有梳理报告未覆盖。

**D-1 · 日志三要素收口到 `LogContext`，键永不为空、值一律净化**
`LogContext` 是 `traceId/tenantId/principalId` 的**唯一写入点**：未知写 `NONE`（`-`）而非留空；所有值经白名单 `[A-Za-z0-9._:@-]` + 64 截断（`:206-219`）；系统作业写 `system` 以区分"设计如此"与"上下文丢了"。类注释把三种失败形态写透：键名拼错（编译器不管）、忘记 `clear()`（线程池复用后**串号**）、异步边界静默丢失。净化的目标是**日志注入**（CR/LF 伪造行、ANSI 污染终端），而 `traceId` 来自请求头，属攻击者可控输入。
**代价**：长 id 被截（见 D-12 冲突）；白名单会丢掉含 `|` 等字符的 OIDC `sub`（静默信息损失，方向安全）。**证据**：`LogContext.java:34-148`、`:206-219`；`logback-spring.xml:19-32`（`%X{traceId:--}` 三键默认值，注释解释"不写默认值会渲染成空方括号，grep 永远匹配不到"）。

**D-2 · HTTP 入口用最外层过滤器，traceId 走"请求属性 > 请求头 > 新生成"**
`RequestLoggingFilter` 注册在 `Ordered.HIGHEST_PRECEDENCE`（早于安全链），最终 traceId 存 request attribute（`:74-84`、`:109-113`）。两条理由都很关键：① 早于安全链——"traceId 的价值在于任何一段日志都能定位到同一条链路，包括**还没认证就失败**的请求（401、限流、框架异常）"；② 存 attribute——ERROR/ASYNC 派发会**再次进入**过滤器链，只认请求头会导致"同一次请求两个 traceId"。
**代价**：无（纯收益）。唯一可挑：访问日志不打 `run_id`（此刻还没有），"从访问日志跳到 Run"要靠 `correlation_id`，而这条链在 Worker 侧断掉（D-3）。**证据**：`:22-48`、`:101-143`；访问日志格式见 yml `:845-855`。

**D-3 · MQ 的 traceId 走消息头（正确），但中继按轮生成、不继承上游（断链）**
`RabbitMessageSender` 把 `ensureTraceId()` 写进 AMQP header `x-trace-id`——`LogContext.java:57-65` 解释"刻意放消息头而非消息体：`OutboxMessage.ALLOWED_KEYS` 白名单约束的是业务载荷，载荷最小化不应因一个链路标识被放宽"。消费端读头 → setTraceId → 写身份（tenant 来自消息体、主体固定 `system`）→ `finally clear()`。**但** `OutboxRelay.relayOnce()` 用 `push(new Snapshot(newTraceId(), null, SYSTEM))` 为**每一轮**生成新 id，注释自陈"一轮中继 = 一条系统链路"。
**为什么**：中继是批处理（`outbox-batch=50`，跨多租户多 Run），按 Run 生成则"这一轮发了多少条/哪个租户失败"读不出来；按轮生成则"这一轮"体验最好。**代价（被低估）**：同一 Run 的 HTTP 侧与执行侧没有共同 id；且 `ensureTraceId()` 语义是"当前有效则保留"，**同一轮内所有消息共享一个 traceId** → N 条消息在 Worker 侧**无法区分是哪条消息**。这不是"少一个字段"，是**"一条消息"这个粒度在追踪上不存在**。**证据**：`RabbitMessageSender.java:120-140`、`RabbitExecutionListener.java:95-167`、`OutboxRelay.java:115-135`。

**D-4 · 审计不可变 = DB 触发器 + 凭据分离 + PII 拒写；没有哈希链**
① **触发器**：`forbid_audit_mutation()` 中 UPDATE 永远 `RAISE EXCEPTION`，DELETE 仅当 `current_setting('agent.retention.actor', TRUE)` 非空时放行（DDL `:546-560`），挂 `BEFORE DELETE OR UPDATE … FOR EACH ROW`（`:4683`）。② **凭据分离**：`04_retention_role.sql` 撤销应用角色 DELETE；`RetentionDataSourceConfiguration` 支持独立清理数据源（yml `:380-396`，`require-isolated-credential` 默认 **false**）。③ **PII 拒写**：`JdbcAuditRepository.insert` 前逐字段跑 `IdentifyingPattern`，命中即**抛异常拒绝整条写入**（`:34-46`）；`recordRequired` 上抛（关键审计失败让主流程中止），`recordAccess` 只 WARN。④ **无哈希链**：全仓 `prev_hash`/`chain_hash`/`prevHash` **零命中**。
**为什么**：DDL 注释诚实得罕见——"这是意图声明而非访问控制……真正的防线在 **DB 凭据分离**"（`:567`）。
**代价**：L-b 的固有上限——持超级用户凭据者可 `DISABLE TRIGGER` 后改数；"不可篡改"当前是"**对应用凭据**不可篡改"。**无 L-c 就无法自证**：**删除中间若干行不会被发现**，对 SOC 2 / 等保的"日志完整性"是**结构性缺口**（改进点 4）。PII 拒写是双刃：写入因含 PII 失败时该条审计就不存在，`recordRequired` 会中止业务（fail-closed 正确），但**只有异常栈、没有稳定原因码**。**证据**：DDL `:546-560`、`:4683`、`:1488-1507`；`JdbcAuditRepository.java:34-140`；`JdbcErasureRepository.java:368`、`:533`。

**D-5 · ⛔ 防篡改漂移守卫已写、已装配、但空转（新发现）**
`AuditTamperProofGuard` 是 `ApplicationRunner`，用 `has_table_privilege(current_user, ?, 'DELETE')` **只读地**检查（`:70-80`，注释："拿删除动作去验证删除权限是不可接受的"），三态判定：无 DELETE → 通过；有 DELETE 且 `isolationRequired` → **拒绝启动**；有 DELETE 未要求隔离 → **SECURITY 告警**（`:100-118`）。它**确实被装配**（`ApplicationConfiguration.java:1981-1987`）。**但受检表清单是空的**——`GUARDED_TABLES = { // "audit_record", "erasure_certificate", }`（`:34-37`，两行被注释掉）。
**后果**：`run()` 的 for 循环**一次都不执行**，启动日志既无"✅ 通过"也无"⚠️ SECURITY"，**什么都不会发生**；而单测 `AuditTamperProofGuardTest` 只测纯函数 `assess()`（`:59-65`），**全绿**。这是本维度最严重的一处：它精确命中铁律 6/17——失败形态是**最坏的一种：守卫存在、测试通过、日志沉默、保护为零**，而它守护的正是"审计不可篡改"这条对外承诺。
**根因（推断）**：大概率是"隔离脚本未执行的环境里应用角色本就有 DELETE，硬失败会让实例起不来"——但代码**已经**为此设计了三态（`isolationRequired=false` 只告警），所以注释掉表清单在逻辑上**多余且有害**。**证据**：`:30-37`、`:48-68`、`:100-118`；`ApplicationConfiguration.java:1981-1987`；`AuditTamperProofGuardTest.java:55-70`。

**D-6 · 授权判定流水：不挂 RLS、`tenant_id text`、只存原因码、禁 RETURNING**
`platform.authz_decision_log` 每次 `AccessGate` 判定一行，**不挂 RLS**（`app_agent` 仅 INSERT，读走 `platform_ops`），`tenant_id` 是 **text 而非 uuid**，`reason_code` 只存码。三条注释本身就是论证：text 因为"审计流水必须『无论主体长什么样都能记下来』，写成 uuid 后非 UUID 形态的主体（测试夹具/历史遗留/非 PG 后端）会让写入抛类型错误，而那一刻正是最需要留下痕迹的时刻"（`:995`）；只存码因为"塞进不可枚举的文本会让它失去判别力"（`:1002`）；禁 RETURNING 避免"写审计反而需要 SELECT 权限"。
**代价**：不挂 RLS ⇒ 跨租户读权限收敛到 DB 授权，`platform_ops` 凭据泄露即全量可读（可接受，运营本就要跨租户）；无保留期；它是**判定流水**而非业务审计——用户看不到"我被拒绝了"。**证据**：DDL `:971-1002`；`JdbcAuthzDecisionLog.java:25-95`。

**D-7 · 三套指标基数政策并存且相互矛盾（新发现）**
- **政策 A（严格）**：`AgentMetrics` 运行期校验标签键必须在 `ALLOWED_LABEL_KEYS`（`run_state/tool_name/risk_level/outcome/error_kind/provider/reason/bucket`，**不含 tenant**），否则抛异常，并单列 `FORBIDDEN_LABEL_KEYS`（`run_id/user_id/trace_id/principal_id/agent_id/snapshot_id/email`）（`AgentMetrics.java:46-110`）。注释："刻意不引 Micrometer：引入后标签约束会退化为文档约定"。
- **政策 B（宽松）**：`MicrometerModelCallObserver` 与 `MicrometerExecutionObserver` 都用 `tenant` 作标签；`MicrometerTraceObserver` 甚至用**从 traceId `split(":")` 得到的字符串**当 tenant（`:104-107`），并以自由文本 `error` 作标签。
- **政策 C（空转）**：`AgentMetrics.increment(...)` 在全仓 main **零调用** ⇒ `/metrics`（`MetricsController.java:38-44`）**永远返回只有注释头的空文本**——"运行期强制低基数"这套机制**没有任何数据流过**。
**为什么是问题**：`tenant` 本身不是坏事（租户数有限），但它**不在政策 A 白名单里**，说明两套设计意图不一致；真正危险的是**B 绕过了 A**——将来有人在 Micrometer 侧加 `trace_id` 标签，**没有任何运行期检查会拦**；而 `/metrics` **比不存在更糟**（运维会以为指标没产出是采集问题）。**证据**：`AgentMetrics.java:15-37`、`:46-110`、`:141-170`；`MicrometerModelCallObserver.java:44-99`；`MicrometerExecutionObserver.java:44-134`；`MicrometerTraceObserver.java:34-107`。

**D-8 · 追踪观察者链死接线：`ai.trace.*` 永不产出（新发现）**
`ObserverConfiguration` 装了三类链：`ModelCallObserverChain` 被 `ObservableModelGateway` 消费（`:141-147`）**活**；`ExecutionObserverChain` 被 `WorkerExecutionConfig:672` → `RunExecutionLoop`（`:720-722`）消费**活**；`TraceObserverChain` **bean 存在（`:236-247`）但全仓无注入点**。后果：`Slf4jTraceObserver`/`MicrometerTraceObserver` **永不执行**，看板没有端到端 trace 指标；顺带掩盖了两个缺陷——`extractTenant` 把整个 traceId 当 tenant 标签（**基数爆炸**）、`private Timer.Sample sample` 是**实例字段**（并发互覆）。另有 `Slf4jTraceObserver.generateTraceId` 产出 `tenantId:runId:8hex`（**82 字符**，超 `MAX_VALUE_LENGTH=64`）且**零调用方**——两套生成器，一套死、一套会截断。

**D-9 · 指标宽表 7 列无写入方（新发现）**
`AgentMetricCollector.collect` 构造 `TraceMetric` 时效果/反馈/风险类参数**全部传 `null`**：`null, null, null, null, null, null, / null, null, null, null, / null, null, null,`（`:199-202`）。逐列核对（全仓 main 检索）——`safety_blocked_count`、`unauthorized_attempt_count`、`sensitive_output_hits`、`instruction_followed`、`feedback_up`、`feedback_down`、`retry_count`、`abandoned` **全部无生产点**（`JdbcAgentMetricRepository` 只做 SQL 绑定；feedback/risk 是**另外两张表**，`:670`/`:714`）。

**D-10 · `trace_id` 三级降级且降级留痕（正确），但第一级永不命中**
`readRun` 顺序为 `run.trace_id` → `agent_invocation(depth=1).trace_id` → `correlation_id`，来源写入 `trace_id_source`；**三者都空则不采集**（"宁可不采集也不用假值"，`:145-148`）。"降级必须留痕，不能冒充同源"是**可观测性系统自身的诚实性**，竞品少见。

**D-11 · 审计读取：查询本身也留痕（fail-open），且不返回 tenantId**
`/api/audit` 先 `requireAuthorized(context, AUDIT_READ, null)`，再过治理桶限流，查询完成后 `recordAccess(...)` 记"查过审计"（**fail-open**，避免查询变写入风暴）；响应 DTO **不含 `tenantId`**（`AuditQueryController.java:25-88`）。理由：① "查询审计这件事本身也留痕"是审计系统的元要求（否则内部人可静默翻看）；② fail-open 因为"『查不了审计』本身就是事件"；③ 不返回 tenantId 防"通过响应探测租户存在性"。
**代价**：DB 故障时"查询留痕"可能丢失（合理取舍），但**当前无"审计查询失败"计数**。**证据**：`AuditQueryController.java:24-88`；`JdbcAuditRepository.java:84-115`。

**D-12 · 指标"未采集 = NULL"，绝不等于 0（贯穿全链路的头号纪律）**

**D-16 · 审计与会话审计复用 run/run_event/run_step，不新建"对话审计表"**

**代价**：① **对话审计与业务 Run 混表** ⇒ "Run 总数/成功率"会被 L3 ConsoleChat 污染——**当前是否排除取决于采集 SQL 是否过滤 `SSE_DIRECT_LEASE_OWNER`（未见过滤）**，需在指标层确认；② 会话事件保留期与执行事件同为 30 天（合规可能要求更短）；③ `agent_message_queue`/`run_message` 的 `message-days=30` 是**独立键**（yml `:363-372` 明确"不跟随 trace-days"）——这点做得对。**证据**：`AgentChatAuditPort.java:12-52`；`JdbcAgentChatAuditRepository.java:97-103`；yml `:355-378`。

### 5.2 优势详解（为什么领先，要讲清机制）

**优势 A · 审计的"三保险"是数据层不变量，不是应用层纪律**

```
第 1 层：DB 触发器（forbid_audit_mutation）→ UPDATE 一律 restrict_violation；
        DELETE 仅在 current_setting('agent.retention.actor') 非空时放行
第 2 层：凭据分离（04_retention_role.sql 撤 DELETE + 可选独立数据源）
        → 即便有人拿到应用凭据，也没有删除权限
第 3 层：写入前 PII 拒写 → 敏感信息根本不会进入审计表
        （拒绝整条，而不是"打码后入库"）
```

**为什么竞品做不到**：7 个框架**没有一个有审计表**——它们的"记录"是 trace/日志，而 trace 天然可删（LangSmith 有 `manage-trace#delete-a-trace`，Agno 存在自己库里随 DBA 处理）。**"可删"与"可举证"是互斥的**：一个能被运营一键删掉的记录，在合规审查里不能作为"当时确实发生"的证据。本项目在这个点上选择了**与框架生态相反的方向**，且落到了 DB 层——这是本维度最实质的领先。

**优势 B · 指标是"事实的确定函数"，因此可以补算、可以对账**

`agent_trace_metric` 的写入是 `INSERT ... ON CONFLICT (trace_id) DO UPDATE`（`JdbcAgentMetricRepository.java:111`），工具维度是"先 DELETE WHERE trace_id 再插"（`:193-205`）。这意味着：**同一份事实重算 N 次，结果逐字节相同**。带来的三个能力：
1. **采集失败可补算**（专用队列 + 失败不影响终态 + 手动重算入口）；
2. **口径升级可回刷**（`metric_version` 列为此预留）；
3. **指标可被质疑并重新验证**（"这个 87% 是怎么算的" → 重跑采集器即可复现）。

对照：竞品的指标多是**打点累加**（Counter/Timer 在内存里累加后导出），**过程不可复现**——你把代码改了、把采样率调了，历史数字就无法重算。这不是"实现差异"，是**认识论差异**：本项目的指标是"事实的投影"，竞品的指标是"事件的计数"。

**优势 C · 降级必须留痕（`trace_id_source` / `termination_reason=OTHER` / `NULL=未采集`）**

三处一致的纪律：
- `trace_id` 用 `correlation_id` 兜底时，**必须**标 `CORRELATION_FALLBACK`（`JdbcTraceFactRepository.java:139-143`："降级必须留痕：用 correlation_id 冒充 trace_id 而不标记，下游会误以为两个 ID 体系同源"）；
- 未识别的终止原因**必须**归 `OTHER` 而非丢弃（DDL `:830`："丢弃未识别原因会让『终止原因分布』的合计小于总数，看板上出现『不知道哪去了』的黑洞"）；
- 未采集**必须**是 `NULL` 而非 0（D-12）。

**为什么这构成优势**：可观测性系统最常见的失效不是"没数据"，而是**"数据看起来是对的"**。这三条纪律共同保证"不知道"永远有一个显式表达。

**优势 D · 采集链路的隔离纪律（专用队列 + 不复用执行队列 + 失败不伤主流程）**

`publishTraceCollect` 走 `agent.trace.collect` 专用队列，注释写明了为什么："**绝不是** `agent.run.execute`，否则会被 `RunDispatchConsumer` 当成『唤醒执行』再次跑这个已终态的 Run（重复执行 = Sev-0）"（`RunExecutionLoop.java:1333-1335`）。而 `TraceCollectMessageHandler` 又反向防御："只处理采集事件；其它事件走到这里说明分流配错了，按不可恢复处理（进死信）"（`:57-62`）。

**这是一个"双向防御"的罕见样本**：发送侧保证不误发，消费侧保证不误收。竞品里常见的是"采集与执行共用一个队列 + 靠 type 字段区分"，一旦分流写错就是重复执行。

**优势 E · 看板口径的双数据源分工（技术指标 Prometheus / 业务口径 PG）**

`datasources.yml` 把两件事分开：JVM/HTTP/`ai_model_calls_*` 走 Prometheus（高基数、短保留、适合 rate）；成功率/成本/评估覆盖走 PG（可跨表 join、可算分位、可保证"n<30 不显示"）。并且明确注释了为什么必须用 `platform_ops`（BYPASSRLS）："app_agent（NOBYPASSRLS）会被 RLS 收窄到单租户，看板数字失真"。

**这个坑很多团队踩过而不自知**：看板上"全平台成功率 92%"其实只是"某个租户的 92%"。本项目显式识别并规避了它。

### 5.3 劣势与盲区详解（明确承认，含根因分析）

**劣势 1 · 追踪在 outbox 处断链：三个 id 空间互不相通**

- **现状**：HTTP 链路号（ID-1）→ `correlation_id` → 落库；中继轮次号（ID-2）→ MQ 头 → Worker 日志；调用串链号（ID-3）→ `agent_invocation`。**三者无一处汇合**（§4.1.3）。
- **后果**：① **用户报障的 id 查不到执行细节**——这是最伤的（用户能提供的只有响应头里的那个 id）；② "Worker 侧看到的异常"无法反查是哪个 HTTP 请求触发的；③ `agent_trace_metric.trace_id` 在同一列混了 ID-1 与 ID-3 两种语义，按 trace 聚合时不可比。
- **根因分析**：**设计取舍 + 一个被低估的代价**。`OutboxRelay` 的注释说明"一轮中继 = 一条系统链路"是为了让批处理排障更容易。这个收益是真实的，但代价被低估了：它牺牲的是**"一个用户请求的端到端可追踪性"**，而后者才是可观测性的核心诉求（T1/T4）。正确的形态不是二选一，而是**两者都要**：消息头带 `traceparent`（继承 ID-1），同时用一个 span/attr 记录"本轮中继 id"以便按批排障。改进点 1 给的正是这个方案。

**劣势 2 · 没有 span 层级：能看"发生了什么"，不能看"哪一步导致了下一步"**

- **现状**：`run_event` 是**扁平**的 `(sequence_no, event_type, payload)` 序列（DDL `:2788-2797`）；`agent_trace_metric` 是**一条 Trace 一行**的宽表；`agent_trace_tool_call` 是**按工具名聚合**。没有任何结构表达"第 3 轮模型调用 → 第 2 次工具调用 → 第 5 轮模型调用"的父子关系。
- **后果**：① 无法回答"这次 Run 的 40 秒里，哪 25 秒花在第 4 轮的某个工具上"（只有 `tool_ms_total` 总和与 `max_duration_ms`）；② 无法做"漏斗式"耗时归因（排队 / 模型 / 工具 / 重试各占多少）；③ 无法算"单步成本"（`usage_record.step_id` 是死列，维度 9 已记录）。
- **根因分析**：**能力缺口（数据模型缺一层）**。补这一层不是"加个 UI"，需要：span 表（或 OTel span 导出）+ `run_step` 与 `tool_operation` 的父子关联 + 采样策略。这也是改进点 1 的实质工作量所在（不是装个 agent 就完事）。
- **代价量化**：以本项目当前形态，"P95 延迟高"这类问题只能定位到"某个 Run 慢"，**无法定位到"慢在哪一段"**——这就是 `ai.execution.latency.total` 与 `ai.model.calls.latency` 之间那段"不知道去哪了"的时间。

**劣势 3 · 观察者用实例字段做计时，并发下互相覆盖**

- **现状**：`MicrometerExecutionObserver.loopTimer`（`:48`）与 `MicrometerTraceObserver.sample`（`:38`）都是**非 final 实例字段**；而这两个观察者都是单例 Bean，Worker 并发度 `concurrency: 4`（yml `:193`），消费线程池并发执行多个 Run。
- **后果**：A 的 `onLoopStart` 写入 `loopTimer`，B 的 `onLoopStart` 覆盖它，A 的 `onLoopComplete` 停掉的是 **B 的 sample** → 延迟被记到错误的 Run/租户标签上；同时 A 的那个 sample 永不 stop（Timer 少记一次）。表现是"`ai.execution.latency.total` 的分位数漂移 + count 小于 loops.total"。
- **根因分析**：**实现缺陷**（典型"单例 + 可变状态"）。修法很轻：`Timer.record(...)` 包裹整个 loop，或把 `Timer.Sample` 放进 run 上下文的局部变量（通过观察者方法参数传递）。
- **对比**：这是本项目特有的问题（竞品用 span 的 `start/end` 时间戳而非共享 sample 对象）。

**劣势 4 · 审计无哈希链：能防"应用改"，不能证明"没人改过"**

- **现状**：`audit_record` 无 `prev_hash`/`row_hash`；`audit_id` 是随机 UUID（无序），无单调序号；无周期锚定。
- **后果**：① **删除中间行不可发现**（触发器只管"通过 SQL 删"，不管"删了再插一条伪造的"）；② 无法向审计方提供"日志完整性"证明（SOC 2 CC7 / 等保"审计记录保护"）；③ 一旦发生内部人篡改，**举证责任落回"信任我们"**。
- **根因分析**：**设计取舍（当时合理的取舍）**。哈希链的代价是：写放大（每行多一次前序读取 + 一次 SHA-256）、**串行化**（同租户必须按序追加）、以及"链断即全断"的运维脆弱性。在"审计写入量低（治理动作级）+ 单租户试点"的阶段，L-b 足够。但它是**只能向前补、不能追溯补**的能力——越晚做，历史段越无法纳入链（改进点 4 给出"只从启用日建链 + 锚定"的务实方案）。

**劣势 5 · 日志层没有 PII 门禁，也没有结构化**

- **现状**：`logback-spring.xml` 只有一个 `ConsoleAppender`，纯文本 pattern（`:19-32`），无 JSON encoder、无异步 appender、无文件 appender、无采样、无脱敏。
- **后果**：① 日志无法被 Loki/ELK 直接按字段检索（只能正则）；② **无法在日志层强制"不打原文"**——`RunExecutionLoop` 在输出审核失败时会 `log.error("... labels={}", decision.labels())`（`:1778-1780`，打的是标签不是原文，**这一处是对的**），但这个纪律**靠人守**，没有编译期/扫描期约束；③ 审计与指标层都做了 PII 防护，**唯独日志层没有**，而日志恰恰是最容易被 `grep` 出来、最容易被贴进工单的载体。
- **根因分析**：**能力缺口（未做，不是难做）**。JSON encoder + 字段白名单 + 一个 `MaskingJsonGenerator` 是半天到一天的工作量；难点在"如何证明它有效"（改进点 6 给出门禁）。

**劣势 6 · 指标表无保留期，`authz_decision_log` 无保留期**

- **现状**：`agent.retention.*` 覆盖 profile/memory/prompt/audit/trace/message/withdrawal 七类（yml `:346-378`），**不含** `platform.agent_trace_metric`（一条 Trace 一行，40 列）、`platform.agent_trace_tool_call`、`platform.authz_decision_log`（每次判定一行）、`platform.agent_risk_event`、`platform.platform_audit_event`。
- **后果**：① 宽表随 Run 数**永久增长**（10k Run/日 × 365 天 ≈ 365 万行 + 工具明细数倍）；② `authz_decision_log` 每次授权判定一行，QPS 与业务请求同阶，**增长最快**；③ 与"最小化保留"的合规原则冲突（dimension 7 的 PIPL 语境）。
- **根因分析**：**能力缺口**（保留期治理只覆盖了"业务事实"，漏了"观测事实"）。补法不难（加键 + 加清理分支），但要先回答"指标表保留多久"——这个决策不宜由工程单方面拍（审计要求 vs 存储成本）。

**劣势 7 · 看板数据源明文连库、且租户无自助视图**

- **现状**：`datasources.yml` 的 `sslmode: disable`，注释自陈"2026-11-08 实测：当前 RDS 实例未启用 TLS"。数据源用户 `platform_ops` 是 **BYPASSRLS**。看板无 `templating` 变量，租户维度只能在明细表里 `left(tenant_id::text, 8)` 显示前 8 位。
- **后果**：① 看板流量走**明文**（含审计/指标/成本数据）；② 平台运营能看到**全部租户**的指标（设计如此），但**租户自己看不到自己的**（无租户侧指标端点；`PlatformAgentMetricsController` 是平台链 `/api/platform/v1/metrics/agent`）；③ 租户无法自查"我们的成功率/成本"，只能提工单。
- **根因分析**：**前两项是取舍（可接受但要登记风险），第三项是能力缺口**。"平台看板用 BYPASSRLS"是正确的（否则数字失真），但"租户无自助视图"不是必然——需要一套租户域端点 + 按租户聚合的视图（改进点 3 的一部分）。

**劣势 8 · 告警"有规则、有实现、无出口、无调度"**

- **现状**：① `ReviewAlertService` 4 条规则 → `review_task`（**无通知**）；② `QualityAlertEvaluator` 比例类规则 → **零调用方**；③ `prometheus.yml` **无 `rule_files`/`alerting`**；④ `RetentionJob` 的失败可见性 = 一行 WARN（`:34-37` 自陈）。
- **后果**：从"异常发生"到"人知道"的时延 = **人下次打开看板的间隔**（不可控）。对 Sev-0 类（重复副作用、预算被击穿、审计写入失败）而言，这个时延不可接受。
- **根因分析**：**能力缺口 + 一次未完成的接线**（D-14）。这不是"不知道怎么告警"——`QualityAlertEvaluator` 的阈值与基线设计相当专业——而是"**没有把判定结果送到能叫醒人的地方**"。改进点 2 给的是"Prometheus 规则 + Alertmanager/Webhook"这条最短路径；同时必须先给 outbox/UNKNOWN 等补 Gauge（因为它们的"原因指标"当前不存在）。

### 5.4 关键分歧点（最本质的架构分歧）

#### 分歧点 1 · 追踪的"连续性"与"批处理效率"能否两全？

- **我们的选择**：**牺牲连续性**——中继按轮生成 traceId（D-3），换取"这一轮发布了多少条/哪个租户失败"的批处理排障体验。
- **竞品的选择**：**连续性优先**——ADK/AutoGen 用 OTel 上下文自动传播（一条 trace 贯穿）；OpenAI 用私有 trace 贯穿 SDK 内部；LangSmith 用 `trace_id` + `run_id` 贯穿。
- **后果**：我们获得"发布轮次"这个运维视角，失去"用户请求端到端"这个产品/支持视角。**而后者才是可观测性的主诉求**。正确形态是"两个 id 都留"：`traceparent` 继承上游 + 一个 batch span 记录本轮（改进点 1）。这不是"要不要 OTel"的问题，是**"要不要让用户报的 id 有用"**的问题。

#### 分歧点 2 · 审计的强度应该由谁定义：工程约定还是客户合规？

- **我们的选择**：**工程约定 + DB 强制**（L-b），并把"是否硬失败"做成配置（`require-isolated-credential` 默认 false）。
- **竞品的选择**：**不做审计**（7 家全无），把这件事完全留给宿主/客户。
- **后果**：我们在"审计存在性"上远超竞品，在"审计可验证性"上落后于合规要求。分歧的实质是：**审计强度不是技术选择，是商业承诺的选择**。如果目标客户是公立学校/教育主管部门，"能证明没被改"是投标门槛；如果是内部工具，L-b 足够。**因此改进点 4 不应该是无条件 P0，而应该由"是否有 SOC 2 / 等保三级客户"触发**——这是本报告与"越多越安全"直觉的一次有意识的偏离。

#### 分歧点 3 · 指标口径的"事实派生" vs "事件计数"

- **我们的选择**：**事实派生**（PG 宽表、幂等覆盖、可补算、可回刷）。
- **竞品的选择**：**事件计数**（内存 Counter/Timer 累加后导出，进程重启即从 0 开始，历史不可复算）。
- **后果**：我们获得可复现性与"补算"能力，代价是**采集延迟**（走 outbox + MQ + 采集器，端到端从"秒级"变成"取决于 relay-interval + 消费延迟"）与**两套指标并存**（Micrometer 实时 + PG 准实时，口径可能不一致——例如 `ai.execution.loops.total` 与 `trace_count` 的差值就是"采集失败/在途"的量，**而没有任何面板展示这个差值**）。
- **一个诚实的提醒**：这个分歧让我们**必须**回答"实时性要求多高"。当前答案是"看板分钟级可接受"，所以选对了。但**告警不能建立在 PG 宽表上**（延迟 + 采集失败会让告警滞后/漏报）——这正是改进点 2 要用 Prometheus 而不是 PG 做告警的原因。

## 六、优缺点总评

### 6.1 我们的优点（分级）

**结构性优势（架构层面带来的、竞品难以快速复制的）**
1. **审计不可改由 DB 触发器 + 凭据分离双保险**（D-4）——7 家竞品全无审计表。
2. **指标是事实的确定函数 + 幂等覆盖写 + 可补算**（D-9 的正向面 / `JdbcAgentMetricRepository.java:86-205`）。
3. **授权判定流水独立成表、只增不改、不挂 RLS、只存原因码**（D-6）。
4. **采集链路双向防御**（专用队列 + 消费侧按 eventType 分流拒绝），封堵"采集触发重跑"这一 Sev-0（优势 D）。
5. **降级必须留痕的三条纪律**（`trace_id_source` / `OTHER` / `NULL`）（优势 C）。

**工程性优势（工程打磨带来的）**
6. **日志三要素收口 + 净化防注入**（D-1）。
7. **HTTP traceId 的派发鲁棒性**（请求属性 > 头 > 新生成；ERROR/ASYNC 派发复用）（D-2）。
8. **MQ traceId 走消息头而非消息体**，与载荷最小化白名单不冲突（D-3 前半）。
9. **审计 PII 拒写 + 关键/非关键分级（fail-closed / fail-open）**（D-4）。
10. **看板双数据源分工**（Prom 技术 / PG 业务），并识别"RLS 会收窄看板"的坑（优势 E）。

**领域性优势（教育/多租户场景带来的）**
11. **审计 180 天 / 原文 30 天 / trace 30 天分层保留，且 `message-days` 独立于 `trace-days`**（yml `:355-372`，注释："共用一个键意味着为多看几天指标，被迫把学生原话也留更久——这类耦合在合规审查里无法解释"）。
12. **`agent_risk_event` 只存摘要**（合规红线）。

### 6.2 我们的缺点（分级）

**设计取舍导致的代价（值得付，但要知道账单）**
1. **traceId 跨 outbox 断链**（三个 id 空间）：换来批处理排障体验，代价是端到端不可追踪（劣势 1）。
2. **无 span 层级**：换来 schema 简单（两张表 vs 一棵树），代价是无法做耗时归因与单步成本（劣势 2）。
3. **审计只到 L-b**：换来低成本与低运维脆弱性，代价是无法自证完整性（劣势 4）。
4. **告警只落人工队列**：换来"不制造噪声告警"（有一致的设计理由），代价是 MTTR 不可控（劣势 8）。
5. **指标准实时而非实时**：换来可复算，代价是两套指标并存且差值无人监控（分歧点 3）。

**能力缺口（纯粹的"没做"）**
6. **7 列指标无写入方**（D-9）。
7. **`QualityAlertEvaluator` 零调用方**（D-14）。
8. **`AuditTamperProofGuard` 空转**（D-5）——**这是最严重的一个**。
9. **无 Prometheus 告警规则、无 Alertmanager、无通知通道**（D-15）。
10. **无 OTel / 无 W3C traceparent / 无 span**。
11. **`agent_trace_metric` / `authz_decision_log` / `agent_risk_event` 无保留期**（劣势 6）。

**运维负担**
12. **观察者计时字段并发不安全**（劣势 3），会造成"分位数漂移 + count 缺失"这类**需要专业经验才能识别**的假象。
13. **看板数据源明文连库**（`sslmode: disable`），依赖内网与 RDS 侧加固。
14. **保留期需人工决策**（指标表保留多久没有安全默认值，与 `RetentionPolicy` fail-closed 的取向冲突）。

### 6.3 每个竞品的优点（简明，带来源）

- **OpenAI Agents SDK**：**零配置 span 树 + 仪表盘**，span 类型覆盖 agent/generation/function/guardrail/handoff/turn/task（含语音）；对"脱敏与导出非原子"的**诚实警告**（"A redaction processor registered before an exporter therefore does not prevent that exporter from receiving data if redaction fails"）；31 家集成生态。（<https://openai.github.io/openai-agents-python/tracing/>）
- **Anthropic Claude Agent SDK**：**不自造半成品观测层**；Hooks 提供通用生命周期扩展点；`--output-format json` 提供结构化结果通道；数据边界完全由宿主掌控。（<https://code.claude.com/docs/en/agent-sdk/overview>）
- **LangSmith**：**run/trace/thread/trajectory 四级模型**，是本次对比里唯一把"多轮会话"做成一等公民的方案；评估（dataset + evaluator）与 trace 同源，`evals as tests` 落地最顺；自动埋点覆盖广。（<https://docs.langchain.com/langsmith/observability-concepts>）
- **Google ADK**：**原生 OTel**，JVM 路径直接给 `GlobalOpenTelemetry` + OTLP exporter 装配代码；内容捕获有显式开关且默认谨慎；后端完全可选（Cloud Trace / Jaeger / Langfuse / Phoenix / Datadog）。（<https://adk.dev/observability/>）
- **Microsoft AutoGen（归档）**：明确"follows OTel Semantic Conventions for agents and tools"且"also follows the Semantic Conventions for GenAI Systems **currently under development**"——**主动标注成熟度**的做法值得学习**；两级关闭开关（构造参数 + 环境变量）便于临时排障。（<https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tracing.html>）
- **CrewAI**：指标分类**直接用业务语言**（含 "Cost per Task"、"Budget Tracking"）；给出"选工具→埋点→看板→**定义告警**→建基线→迭代"的六步落地路径，最像运维手册。（<https://docs.crewai.com/en/observability/overview>）
- **Agno**：**"OTel 采集 + 自持存储 + 自带 Control Plane"三者齐备**，与本项目架构取向最接近；显式给 span 属性上限（1024，可调）防属性爆炸；`setup_tracing` 在已有 `TracerProvider` 时不覆盖（负责任的默认值）。（<https://docs.agno.com/agent-os/tracing/overview>）

### 6.4 每个竞品的缺点（简明，带来源）

- **OpenAI Agents SDK**：**默认上传敏感内容**（`trace_include_sensitive_data` 默认 True），与未成年人数据合规直接冲突；ZDR 客户**完全不可用**；trace 是私有格式非 OTel；**无审计不可变性**（可删）。（同上）
- **Anthropic Claude Agent SDK**：**完全没有可观测性原语**——无 trace 数据模型、无 span 约定、无看板；跨进程/子 Agent 关联要宿主自建；成本与用量要到 API Console 看（不同源）。（同上）
- **LangSmith**：**25,000 runs 硬上限**（超过即"reject any additional runs"）+ **180 天硬保留** ⇒ 长任务/高并发下是**数据缺口**而非降级；trace 可删（无不可变）；workspace 级权限非 DB 强制多租户；SaaS ⇒ 数据出境。（同上）
- **Google ADK**：开源 SDK 只给 instrumentation，**仪表盘要自己搭**；部分观测能力绑定 Agent Engine（非开源）；`TelemetryConfig.captureMessageContent` 是**全局静态**，多租户进程内无法按租户差异化；无审计。（同上）
- **AutoGen（归档）**：**官方已归档停维护**（2025-10 并入 Microsoft Agent Framework），不应作为选型依据；文档未列 span 精确字段；无审计/多租户/看板。（同上）
- **CrewAI**：**框架不持有 trace 数据**（无内建 trace 存储、无审计表），观测能力随所选第三方而变；"Cost per Task" 的分母是"任务"而非"成功任务"；离线/自托管需自行拼装。（同上）
- **Agno**：trace 存在自己库里，**可删可改**（无不可变）；Control Plane 是商业产品；`setup_tracing` 的"已存在 provider 就静默返回"是**静默降级**（与本项目 fail-closed 取向相反）；多租户靠 AgentOS 认证非 DB 级 RLS。（同上）

### 改进点 8 · 让已写好的观测件真正在链路上（P0 · 最高性价比）

### 改进点 2 · Prometheus 告警规则落地（P0）

**问题陈述**：`prometheus.yml` 仅 16 行 `scrape_configs`，**无 `rule_files`、无 `alerting`**；应用内告警全落 `review_task`（无通知通道），`QualityAlertEvaluator` 零调用方。结果："异常发生 → 人知道"的时延 = 人下次打开看板的间隔。**更根本的问题**：**若只加规则，一半规则写不出来**——`BackpressureController` 算了 `lastDepth`/`throttledRounds`/`probeFailures`（`:44-54`）但**未注册 Meter**；`ReserveOutcome` 六值枚举只在日志里、**无 Counter**；`tool_operation.state='UNKNOWN'` 只在表里、**无 Gauge**；**无"最后采集成功时间"**。

**2-A 先补 4 个 Meter**

**2-B 规则文件**（新增 `monitoring/prometheus/rules/agent-slo.rules.yml`，以下为骨架，其余 3 条同构）
```yaml
groups:
  - name: agent-slo
    interval: 30s
    rules:
      # ── SLO 类（症状告警）──
      - alert: AgentRunFailureRateHigh                    # 5m 窗口 >5%，持续 10m
        expr: |
          sum(rate(ai_execution_loops_total{outcome!="SUCCEEDED"}[5m]))
            / clamp_min(sum(rate(ai_execution_loops_total[5m])), 1e-9) > 0.05
        for: 10m
        labels: { severity: critical, slo: run_success }
        annotations: { summary: "Run 失败率 {{ $value | humanizePercentage }}（阈值 5%）",
                       runbook_url: "docs/runbook/obs-run-failure.md" }
      - alert: AgentModelCallErrorRateHigh                # 5m 窗口 >2%，持续 10m
        expr: |
          sum(rate(ai_model_calls_total{error!=""}[5m]))
            / clamp_min(sum(rate(ai_model_calls_total[5m])), 1e-9) > 0.02
        for: 10m
        labels: { severity: critical, slo: model_availability }
      # ── 饱和类（原因告警，用于定位而非叫醒）──
      - alert: AgentOutboxBacklog
        expr: agent_outbox_depth > 1000
        for: 10m
        labels: { severity: warning, kind: saturation }
      # ── 正确性类（Sev-0 邻接）──
      - alert: AgentBudgetRejectRatioHigh
        expr: |
          sum(rate(agent_budget_reserve_total{outcome=~"INSUFFICIENT|RUN_BUDGET_EXHAUSTED|NO_ACCOUNT|FAIL_CLOSED"}[10m]))
            / clamp_min(sum(rate(agent_budget_reserve_total[10m])), 1e-9) > 0.10
        for: 15m
        labels: { severity: critical, kind: correctness }
        annotations: { description: "NO_ACCOUNT=未开通 / INSUFFICIENT=加额度 / RUN_BUDGET_EXHAUSTED=调小额度 / FAIL_CLOSED=查预算服务" }
      # 另有 AgentUnknownOperationsStuck（agent_tool_operation_unknown > 20 持续 1h）
      # 与 AgentTraceCollectStale（time() - 采集时间 > 1800 持续 5m）两条，写法同上
```
> 另 3 条同构规则：`AgentRunP95LatencyHigh`（直接用已导出的 `quantile="0.95"`，避免桶边界误差）、`AgentOutboxThrottledPersistent`（`increase(...[15m]) > 0`）、`AgentNodeDown`。

**2-C 打通出口**：`prometheus.yml` 加 `rule_files: [/etc/prometheus/rules/*.rules.yml]` 与 `alerting.alertmanagers.targets: ['alertmanager:9093']`。先接 **webhook**（企业微信/钉钉机器人）即可，不必上 Alertmanager 集群；关键是**让告警离开"人工队列"**。

**成本与风险**：4 个 Java 小类（≈120 行）、1 个规则文件、`prometheus.yml` 3 行、可选 Alertmanager。风险：① **阈值是拍的**（5%/2%/60s/1000 条），必须在试点流量下校准，否则重复 `ReviewAlertService` 批判过的"噪声告警训练人忽略队列"；② `outcome!="SUCCEEDED"` 依赖 `LoopOutcome.kind().name()` 的枚举稳定性（改枚举名会**静默**让告警失效），需给枚举加稳定性测试；③ Micrometer 会做 base unit 转换（`_total`/`_seconds`），**必须用 `promtool` 对真实抓取值校验**，否则规则永不触发（最常见的低级错误）。

### 改进点 1 · OpenTelemetry + GenAI SemConv 接入与 trace 跨 outbox 传播（P0）

**问题陈述**：① 全仓无 OTel 依赖，无 span、无 W3C `traceparent`、无 `span-id`；② traceId 在 outbox 处断链（D-3），用户报障的 id 查不到执行细节；③ `agent_trace_metric` 是"一条 Trace 一行"，**无法做耗时归因**；④ `ToolInvocationGate` 的逐调用 trace_id（ID-3）只能用于委派归因，不能用于耗时。

**1-A 依赖**（版本由 Spring Boot 4 BOM 管理）：`io.micrometer:micrometer-tracing-bridge-otel` + `io.opentelemetry:opentelemetry-exporter-otlp`（均置于 `agent-infrastructure`）。

**1-B 保留 MDC，但让值来自 OTel 上下文（不引入第二套 id）**
```java
public static String currentOrNewTraceId() {
    String fromMdc = MDC.get(TRACE_ID);
    if (fromMdc != null && !NONE.equals(fromMdc)) return fromMdc;
    String fromSpan = Span.current().getSpanContext().isValid()
            ? Span.current().getSpanContext().getTraceId() : null;   // 已是 32 hex
    setTraceId(fromSpan);            // 内部仍走 sanitize + 兜底生成
    return MDC.get(TRACE_ID);
}
```
> W3C `trace-id` 就是 **32 位小写 hex**，与 `LogContext.newTraceId()` **同形**（T4），因此**不需要迁移历史 id**，`run.correlation_id` 与 `agent_trace_metric.trace_id` 都能与 OTel traceId 直接对齐。

**1-C span 模型（四层，与 T6 对齐）**

| span | 位置 | 关键属性 | 说明 |
|---|---|---|---|
| `http.server` | `RequestLoggingFilter`（或 `ServerHttpObservationFilter`） | `http.request.method`、`url.path`、`http.response.status_code` | 根 span；**不记 query** |
| `agent.run` | `RunDispatchConsumer`/`RunExecutor` 起点 | `app.run.id`、`app.tenant.id`、`app.run.attempt`、`app.run.fencing_token` | MQ 侧**新 trace** + **Link** 上游 |
| `gen_ai.chat` | `ObservableModelGateway` | `gen_ai.operation.name=chat`、`gen_ai.provider.name`、`gen_ai.request.model`、`gen_ai.usage.input_tokens`/`output_tokens`、`gen_ai.response.finish_reasons` | **绝不记 prompt/completion 内容** |
| `execute_tool` | `ToolInvocationGate` | `gen_ai.tool.name`、`app.tool.risk_level`、`app.tool.outcome`、`app.tool.operation_id` | 与 `tool_operation` 对齐 |

> **属性 vs 标签的红线**：以上属性**只进 span**，不进 metric 标签（span 后端可承受高基数，metric 不行）。必须写进代码评审清单。

**1-D 跨 outbox 的传播方案（本改进点核心）**
```
问题：relay 是批处理（一轮 50 条），无法用"父子 span"表达（父只有一个）
方案：消息级 traceparent 继承 + 批次 Link（OTel Links：因果相关但非父子）

① 生产侧（Run 创建）：ALTER TABLE public.outbox_event ADD COLUMN trace_parent text;
   值形如 00-<32hex trace-id>-<16hex span-id>-01，插入时从当前 span 取
   ⚠️ 存量行为 NULL（消费端按"无父"处理并打 app.trace.parent=missing）
② relay 侧：为本轮起短 span `outbox.publish.batch`（attr：messages 计数、租户数）；
   每条消息读 outbox 行 trace_parent → 写 AMQP header（不改 payload 白名单）；
   为空则用本轮 traceparent（保留"轮次可追踪"能力）
③ 消费侧：读 header → `agent.run` span 的 remote parent（extract），
   同时 Link 到 `outbox.publish.batch`（若 header 带批次上下文）
   ⇒ 一条 trace 从 HTTP 贯穿到 Worker；批次视角仍可 Link 反查
```
**为什么用 Link**：OTel 的 Link 正是为"批处理/扇入"设计的——一批消息在批次 span 下是**兄弟**，不是父子。既不破坏"一请求一链路"，又保留"这一轮发了什么"的视图。**这是本报告对该问题的核心技术建议**。

**1-E 明确不做**：**不生成 JDBC span**（SQL 文本可能含 PII，且 DB 段已有 `pg_stat_statements`）；**不记 prompt/response 内容**（与 OpenAI 默认相反）；**不做 tail sampling**（见改进点 7），Run 级 span 全量（每 Run 约 6–10 个）。

**成本与风险**：改动面**最大的一项**——`pom`（2 依赖）、`LogContext`（1 方法）、`RequestLoggingConfiguration`、`RunDispatchConsumer`/`RunExecutionLoop`、`ObservableModelGateway`、`ToolInvocationGate`、`OutboxRelay`、`RabbitMessageSender`/`Listener`、DDL（`outbox_event` +1 列）、yml（OTLP endpoint + 采样率）。`outbox_event` 是热点表，PG 11+ 加可空列仅改元数据（不重写表），低峰执行即可。风险：① **OTLP 导出失败可能阻塞业务**——必须 `BatchSpanProcessor`（异步）+ 队列满时**丢 span 不阻塞**，并计 `agent.span.dropped_total`；② span 属性含 `tenant_id`/`run_id` 会让后端变大（可接受），需设 TTL；③ **与 `TraceCollect` 双写**：`agent_trace_metric` 仍是权威业务指标，span 只做诊断，**两者不可互相替代**（必须写死，否则有人会提议"用 span 替代宽表"）。灰度：`agent.telemetry.otlp.enabled`（默认 false），先只导 `agent.run` + `gen_ai.chat`，观察 3 天 exporter 错误率再开 `execute_tool`。

**验收门禁**：① `OtelTracePropagationIT` 用 `InMemorySpanExporter` 驱动一次 `POST /api/runs`，断言响应头 `X-Trace-Id` == 某 `agent.run` span 的 traceId，且该 trace 下同时存在 `http.server`/`outbox.publish.batch`（或 Link 指向）/`agent.run`/`gen_ai.chat`/`execute_tool`；② 反向验证——注释掉 `trace_parent` 读取（回落本轮 trace），断言 ① 变红（证明该列 load-bearing）；③ `OtelNoContentAttributeTest` 扫描 span 构造点，断言无 `gen_ai.prompt`/`gen_ai.completion`/`content`/`messages` 键，并跑一次含身份证号的输入，断言 exporter 收到的**所有属性值**不含该号；④ exporter 指向黑洞端口，断言 Run 仍成功且 `agent_span_dropped_total` 递增（"可观测性不得伤害业务"）；⑤ 断言 Prometheus 输出**不因新增 span 出现新标签**；⑥ 断言 `gen_ai.operation.name` ∈ `{chat, execute_tool}` 且与 SemConv 拼写一致（防 `genai.` 手误），并固定"属性名快照"强制 SemConv 升级时人工确认；⑦ `SchemaDriftIT` 断言 `outbox_event.trace_parent` 与 DDL 一致，且存量 NULL 行消费不抛异常。

**3-A 漏斗视图**

```sql
CREATE MATERIALIZED VIEW platform.mv_run_funnel_hourly AS
SELECT date_trunc('hour', r.created_at) AS bucket_start, r.tenant_id,
       (r.input_payload->>'scenario')   AS scenario,
       count(*)                                                        AS created,
       count(*) FILTER (WHERE r.lease_owner IS NOT NULL)                AS claimed,
       count(*) FILTER (WHERE r.state = 'RUNNING')                      AS running_now,
       count(*) FILTER (WHERE r.state IN ('SUCCEEDED','FAILED','CANCELLED','TIMED_OUT')) AS converged,
       count(*) FILTER (WHERE r.state = 'SUCCEEDED')                    AS succeeded_tech,
       count(*) FILTER (WHERE t.auto_verified IS TRUE)                  AS succeeded_verified
FROM public.run r
LEFT JOIN platform.agent_trace_metric t ON t.run_id = r.run_id AND t.tenant_id = r.tenant_id
GROUP BY 1, 2, 3 WITH NO DATA;
```

**3-B cost per successful task**（复用维度 9 改进点 3 的口径，避免两套定义）

```sql
CREATE VIEW platform.v_cost_per_successful_task AS
SELECT f.bucket_start, f.tenant_id, f.scenario,
       sum(m.cost_amount) AS total_cost, sum(f.succeeded_verified) AS successes,
       CASE WHEN sum(f.succeeded_verified) >= 30
            THEN sum(m.cost_amount) / NULLIF(sum(f.succeeded_verified), 0) END AS cost_per_success
FROM platform.mv_run_funnel_hourly f
JOIN platform.mv_agent_metric_hourly m USING (bucket_start, tenant_id, scenario)
GROUP BY 1, 2, 3;
```

### 改进点 6 · 日志规范化与 PII 脱敏（P1）

**问题陈述**：`logback-spring.xml` 只有 `ConsoleAppender` + 纯文本 pattern（`:19-32`），无 JSON、无异步、无文件、无采样、无脱敏。后果：日志无法按字段检索；**日志层没有"不打原文"的技术约束**（只有代码纪律）；工单里贴日志时 PII 无法自动拦截。

**6-A JSON 结构化（保留人读 profile）**：`LoggingEventCompositeJsonEncoder` + 白名单 `mdc`（`traceId`/`tenantId`/`principalId`/`runId`）+ `loggerName/threadName/level/message/stackTrace`；`message` 经 6-B 的 masker。人读 profile 保留现有 `LOG_CONTEXT_PATTERN`。

**6-B 出口脱敏（复用 `DataClassification.IdentifyingPattern`，与维度 7 同一份正则）**
```java
// agent-infrastructure/.../logging/PiiMasking.java（新增）
public static String mask(String text) {
    if (text == null || text.isEmpty()) return text;
    String out = text;
    for (IdentifyingPattern p : IdentifyingPattern.values())        // 与 OutputModeration 同一枚举
        out = p.pattern().matcher(out).replaceAll(p.placeholder());  // 如 <MASKED:MOBILE>
    return out;
}
```
> **铁律 21 提醒**：`IdentifyingPattern` 含 lookbehind（`(?<![0-9A-Za-z])`），**只能用 JDK 引擎**，不得替换为 RE2/J。

**6-C 写入侧纪律**：日志参数**只允许**标量事实（id/枚举/计数/时长/状态码），**禁止**传 `prompt`/`content`/`answer`/`messages`/`detail` 等正文变量；用 `StructuredArguments.kv("runId", id)` 而非字符串拼接。

**6-D 采集与保留**：容器 stdout → 采集器（Loki/Filebeat）→ 后端，**保留期与 `trace-days=30` 对齐**（日志不应比事实活得久）；不做 app 侧文件轮转（交给运行平台），避免两个真相源。

**成本与风险**：`logback-spring.xml`、`PiiMasking` + encoder 装饰器、`pom`（logstash-logback-encoder）、源码扫描守卫。风险：① **正则性能**——每条日志跑 N 个正则，高 QPS 下是真实开销，必须在 `AsyncAppender` 消费线程或 `MaskingJsonGenerator` 里做（**不在业务线程**）；② **过度脱敏**——UUID 被当学号误掩码（铁律 17 已警告），需 mask 前后各保留 4 字符便于排障；③ JSON 体积膨胀 2–3 倍，需同步调采集器批大小。

**验收门禁**：① IT 触发一条业务日志，断言可被 `ObjectMapper` 解析为 JSON 且含 `traceId/tenantId/principalId` 三键（可为 `-`）；② 构造含 `13800138000`/18 位身份证/学号的日志，断言输出出现 `<MASKED:*>` 且**原串不出现**；③ 反向验证——注释掉 `mask`，断言 ② 变红；④ 断言纯 UUID（`run_id`）**不被掩码**（防"结构性标识被当 PII"）；⑤ `LogPiiSourceScanTest` 扫描 `platform/*/src/main` 的 `log.*` 参数，出现 `prompt|content|answer|messages|body|detail` 变量名且不在白名单 → 红；⑥ 基准断言 `mask()` 对 200 字符文本 P99 < 50µs。

**成本与风险**：新 eval 模块（数据集 + IT）、`QualityAlertJob`、`PublishGuards`（+1 规则）、yml（2 开关）、题库文件；**无 schema 变更**。风险：① **评估成本**——CI 用 FakeModelGateway 回放（零成本），真实 judge 只夜间跑；② **数据集污染**——题库（judge 参考答案）与被测数据集必须用独立键，否则"见过答案"；③ **门禁过严会阻塞发布**——阈值必须留 −3~−5pp 抖动，否则团队会关掉门禁，反而更糟。

**验收门禁**：① 断言 CI 配置含 `evals` job 且路径过滤命中 `agent-context/**`；② 把数据集中 10 条期望归因改错，断言 `OfflineEvalIT` **失败**（反向验证）；③ 阈值边界——`attributionCorrectRate=0.89` → 红、`0.91` → 绿；④ 扫描 eval 模块源码不含 `usage_record`/`cost_amount`，断言不消耗 judge 日预算（复用维度 9 的 `L2ProductionGuardTest` 手法）；⑤ 发布门禁——n<30 不阻断但带 `QUALITY_GATE_INSUFFICIENT_SAMPLE`，n≥30 且低于阈值返回 409；⑥ 断言 `QualityAlertJob` 存在且被 `@Scheduled` 标记——**专防"实现了没接线"这一高频故障形态**（D-5/D-8/D-14 已三次）。

### 改进点 4 · 审计防篡改升级：哈希链 + 每日锚定（P2）

**问题陈述**：`audit_record` 无 `prev_hash`/`row_hash`，`audit_id` 是随机 UUID 无顺序，无周期锚定。后果：删除中间行不可发现；无法向审计方提供"日志完整性"证明（SOC 2 CC7 / 等保"审计记录保护"）；内部人篡改的举证责任落回"信任我们"。

**4-A 只从启用日建链 + 独立链表**（不改 `audit_record` 写入路径）
```sql
CREATE TABLE public.audit_record_chain (
    audit_id    uuid PRIMARY KEY REFERENCES public.audit_record(audit_id),
    tenant_id   uuid NOT NULL,
    chain_seq   bigint NOT NULL,          -- 同租户内单调，由 advisory lock 保护
    prev_hash   text,                     -- 首行为 NULL（创世）
    row_hash    text NOT NULL,            -- sha256(prev_hash || canonical_json)
    anchored_at timestamp with time zone,
    created_at  timestamp with time zone DEFAULT now() NOT NULL,
    UNIQUE (tenant_id, chain_seq));
ALTER TABLE public.audit_record_chain FORCE ROW LEVEL SECURITY;
CREATE POLICY audit_chain_tenant_isolation ON public.audit_record_chain
    USING ((tenant_id = public.current_tenant_id()))
    WITH CHECK ((tenant_id = public.current_tenant_id()));
-- 04_retention_role.sql 中显式 REVOKE UPDATE/DELETE
```
```sql
CREATE FUNCTION public.append_audit_chain(p_audit_id uuid, p_tenant_id uuid) RETURNS void
LANGUAGE plpgsql AS $$
DECLARE v_prev text; v_seq bigint; v_row text;
BEGIN
    PERFORM pg_advisory_xact_lock(hashtext(p_tenant_id::text));       -- 同租户串行
    SELECT row_hash, chain_seq INTO v_prev, v_seq FROM public.audit_record_chain
     WHERE tenant_id = p_tenant_id ORDER BY chain_seq DESC LIMIT 1;
    v_seq := COALESCE(v_seq, 0) + 1;
    SELECT encode(digest(COALESCE(v_prev,'') || (to_jsonb(a)::text), 'sha256'), 'hex')
      INTO v_row FROM public.audit_record a WHERE a.audit_id = p_audit_id;
    INSERT INTO public.audit_record_chain(audit_id, tenant_id, chain_seq, prev_hash, row_hash)
    VALUES (p_audit_id, p_tenant_id, v_seq, v_prev, v_row);
END $$;
```
> **关键取舍**：**不同租户各自一条链**，而非全平台单链——全平台单链会把所有租户的审计写入串行化成单点瓶颈；按租户分链既保证"单租户内不可篡改"，又保留并发。

**4-B 每日锚定**：新表 `platform.audit_anchor_daily(anchor_date, tenant_id, head_seq, head_hash, row_count, anchored_at, signature)`，PK `(anchor_date, tenant_id)`。每日 02:00 由 `AuditAnchorJob` 写一行，并把摘要写进 `platform.platform_audit_event`（跨租户可见）。**锚定行的价值**：即使有人删了一段链并重算后续哈希，**另一张表里的锚定行**仍指向旧 `head_hash`，比对即暴露。

**4-C 校验器**：`AuditChainVerifier` 每日 03:00 + 手动端点触发，逐租户重算 `row_hash` 并校验 `prev_hash` 连续性；断链 → 写 `platform_audit_event(severity=CRITICAL)` + 触发改进点 2 的告警。

**为什么降为 P2**：触发条件应是"**有 SOC 2 / 等保三级客户要求日志完整性证据**"，而非工程直觉。单租户试点阶段做它，会引入 2–3× 审计写延迟 + 一条新的高危告警路径，收益为 0（没人验收）。

**成本与风险**：1 张链表 + 1 张锚定表 + 1 函数 + 1 Job + 1 校验器 + `04_retention_role.sql`（REVOKE）+ `03_platform_roles.sql`（GRANT INSERT/SELECT）；`audit_record` 插入路径需**同事务**调用 `append_audit_chain`（否则链与记录不一致）。风险：① **锁序**——必须"先插 `audit_record` → 再取锁 append"，且锁内不做其他 DML，防死锁；② **canonical_json 稳定性**——`to_jsonb` 键序在 PG 中稳定，但 `jsonb` 规范化行为需实测（不同小版本可能差异），**必须先 PoC**；③ 误报会消耗信任，需影子期（只算不报）≥2 周。

**验收门禁**：① `AuditChainIntegrityIT` 写 100 条审计，断言 100 条链行、`prev_hash` 逐条相等、`chain_seq` 连续；② `DISABLE TRIGGER` 后直连 `UPDATE audit_record SET detail=...`，断言校验器**报红并定位到该 audit_id**；③ 删中间 5 条，断言校验器报"链断在第 N 条"；④ 反向验证——`row_hash` 去掉 `prev_hash`（只哈希本行），断言 ③ 变红；⑤ 单租户 50 并发写审计，P95 写延迟 < 50ms，超标则改为"批量追加 + 链段"；⑥ 断言 `app_agent` 对 `audit_record_chain` 无 UPDATE/DELETE 权限（复用 `AuditTamperProofGuard` 的 `has_table_privilege` 逻辑，**并把两张链表加进 `GUARDED_TABLES`**）。

### 改进点 7 · 导出层采样策略：head + tail 组合（P2）

**问题陈述**：事实层不采样（正确），但引入 span 导出（改进点 1）后**全量导出**会让后端成本随 Run 数线性增长；而 head sampling 会漏掉"错误 trace"（T8 的核心缺陷）。当前**没有任何采样配置**。

**7-A 三层采样**：**事实层**（`run_event`/`agent_trace_metric`）**100%**（权威源，采样即失真）；**Run 级 span**（`agent.run`）**100%**（每 Run 仅 1 个，量 = Run 数）；**子 span**（`gen_ai.chat`/`execute_tool`）**head 10% + 错误 100%**（量最大，错误必须全采——head 做不到，故用 tail）。

**7-B head 侧（SDK）**：`management.tracing.sampling.probability: 1.0`——根 span 全采、子 span 由父决定（**parentbased_always_on**），保证"整条 trace 要么全采要么全不采"（T8：head 最大风险是"缺 span"）；比例控制**放到 Collector 的 tail sampling**，不在 SDK 里各打各的比例（否则拼出不完整的树）。

**7-C tail 侧（OTel Collector）**
```yaml
processors:
  tail_sampling:
    decision_wait: 10s
    policies:
      - { name: errors-always,  type: status_code,   status_code: { status_codes: [ERROR] } }
      - { name: slow-runs,      type: latency,       latency: { threshold_ms: 30000 } }
      - { name: baseline-10pct, type: probabilistic, probabilistic: { sampling_percentage: 10 } }
```
> 顺序即优先级：**错误全采 → 慢链路全采 → 其余 10%**。

**7-D 采样决策的可见性**（否则变成"静默丢数据"）：trace 上打 `sampling.policy` 属性（`errors-always`/`slow`/`baseline`），让"这条为什么被采"可回答；指标 `agent.span.dropped_total{reason}`、`agent.trace.sampled_total{policy}`。

**收益量化**：全量导出 ≈ 80 MB/日（10k Run × 8 span × ~1KB）、head 10% ≈ 8 MB/日但错误 trace 只覆盖 10%，**head + tail ≈ 12 MB/日且错误/慢链路 100% 覆盖**；实现复杂度从"0 / 低"升到"中（Collector 有状态）"。

**成本与风险**：`application.yml`（1 键）、Collector 配置（1 文件）、2 个新指标。风险：① **tail sampling 有状态**（缓存整条 trace 等 10s），需要足够内存与副本一致性（同一 trace 的 span 必须落同一实例，按 `trace_id` 做负载均衡）——T8 明确列出的"难运维"；② 采样率变更会让"span 数趋势"出现台阶，看板需标注；③ **绝不能让采样影响 `agent_trace_metric`**（事实层不采样是红线）。灰度：先 100% 导出 1 周建基线，再开 10%，并验证"采样前后错误率与 P95 一致"。

**验收门禁**：① 断言导出数据中不存在"只有子 span 没有根 span"的 trace（parentbased 生效）；② 构造 100 条含错误子 span 的 trace，断言导出 100 条；③ 构造 1000 条正常 trace，断言导出 100 ± 15 条；④ 断言 `agent_trace_metric.trace_count` 与"导出 span 的 trace 数"**不相等**（证明采样只作用于导出层）；⑤ 断言每条被采 trace 带 `sampling.policy` 且取值 ∈ 三项枚举。

## 八、其他有价值的横向对比（避免维度内自闭）

### 8.1 与本项目其他维度的耦合与相互约束（≥2 条，本报告给 5 条）

**耦合 1 · 维度 3（状态持久化/事件溯源）→ `run_event` 既是流式事实源，也是审计线索**

- **耦合形态**：`run_event` 同时服务三个消费者：SSE 流（维度 4，靠 `sequence_no` 游标续传）、指标采集（`AgentMetricCollector` 从 `run`/`run_step`/`tool_operation` 派生）、以及"事后复盘"（`TraceReplayService`/`/transcript`）。它**没有独立审计表**，因此"对话审计"的完整性完全依赖 `run_event` 的保留期与不可变性。
- **具体证据**：`run_event` 定义（DDL `:2788-2797`，**无 trace_id 列**）；SSE 白名单（`RunEventStreamer.filterPayload`）；保留期 `trace-days=30`（yml `:361-362`）。

**耦合 2 · 维度 9（成本）→ 成本指标的口径与"单任务成本"的分母**

- **耦合形态**：`agent_trace_metric.cost_amount` 来自 `usage_record` 聚合（`JdbcTraceFactRepository.readUsage`，`:287-324`），而 `usage_record` 的工具行是**固定 ¥0.50 代理值**（维度 9 的 D-15）。因此本维度的"成本"指标**混合了实测与代理两种精度**，而看板不标注。
- **相互约束**：① 维度 9 若加 `cost_kind`（`MEASURED`/`PROXY`）列，本维度的看板必须同步分组，否则"总成本"仍是混合数；② 本维度若先做 `cost per successful task`（改进点 3），会**放大**这个口径问题（分母是成功数，分子含代理值）；③ 维度 9 的"重置/回刷"（改价后重算）会**打破"指标是事实确定函数"**这一原则——若 `cost_amount` 可被重算，`agent_trace_metric` 的幂等覆盖写就会在"重算后与历史不同"上产生歧义，**必须引入 `metric_version`/`priced_at` 才能解释**。
- **具体证据**：`JdbcTraceFactRepository.java:287-300`（`min(model_id) FILTER (WHERE model_id NOT LIKE 'tool:%')`）；DDL `:776`（`cost_amount`）、`:803`（`metric_version`）。

**耦合 3 · 维度 11（可靠性）→ 告警是故障收敛的输入，但当前"信号在、出口无"**

- **耦合形态**：维度 11 的所有可靠性机制（UNKNOWN 转对账、POISONED 事务、状态机守卫、fencing）都产出"可观测信号"（错误码、`tool_operation.state`、`run.error_code`），但**只有 4 条单 Trace 规则**把它们转成 `review_task`；UNKNOWN 堆积、预算拒绝、outbox 积压**没有任何告警**（改进点 2）。
- **相互约束**：① 维度 11 若新增错误码（如 `MODEL_DEGRADED`），`agent_trace_metric.termination_reason` 的 9 值枚举必须同步（否则归 `OTHER`，告警无法按原因分流）；② 本维度若加"UNKNOWN 超时告警"（改进点 2 的 `AgentUnknownOperationsStuck`），会**给维度 11 带来新的运维动作**（必须有人处置），因此阈值不能拍太紧（否则天天误报 → 人去关告警）；③ 反之，维度 11 若引入熔断/降级，会改变 `outcome` 分布，**P95/失败率告警的基线必须重算**。
- **具体证据**：DDL `:805`（9 值终止原因 + `OTHER` 兜底）、`:830`（兜底理由）；`QualityAlertEvaluator.java:62-68`（阈值常量）；改进点 2 的规则集。

**耦合 4 · 维度 7（权限）→ `authz_decision_log` 是"判定举证"，但其保留期与读取权限都在平台域**

- **耦合形态**：每次 `AccessGate` 判定一行（`JdbcAuthzDecisionLog`），**不挂 RLS**（隔离靠授权：`app_agent` 仅 INSERT，读走 `platform_ops`）。这使"授权是否按预期发生"可举证，但也意味着**租户无法自查"我被拒绝了几次"**。
- **相互约束**：① 维度 7 若增加新的 `Action`（如 `audit:read`），本维度的 `AuditQueryController` 与 `authz_decision_log` 的 `action` 取值集合必须同步（否则报表里出现未登记动作）；② 本维度若给 `authz_decision_log` 加保留期（改进点 8 的邻接项），**必须先确认维度 7 的"举证窗口"要求**（合规通常 ≥ 6 个月，与 180 天审计同级）；③ 若维度 7 打开 SHAODW 模式（`AGENT_AUTHZ_SHADOW_ENABLED=true`），`MicrometerAuthzMismatchMetrics` 的计数会激增，**需要新的告警阈值**（否则永远红）。
- **具体证据**：DDL `:971-1002`；`JdbcAuthzDecisionLog.java:25-95`；`MicrometerAuthzMismatchMetrics.java`；yml `:154`（shadow 开关默认 false）。

**耦合 5 · 维度 4（流式）→ SSE 与指标采集共享 `run_event`，但一个是"读"一个是"派生"**

- **耦合形态**：SSE 从 `run_event` 按 `sequence_no` 增量读（`RunEventStreamer.java:182`），指标采集从 `run`/`run_step`/`tool_operation` 派生。二者都依赖"事件已落库"这一事实，但**SSE 对延迟敏感（200ms 轮询）、采集对完整性敏感**。
- **相互约束**：① 维度 4 若改用 `LISTEN/NOTIFY`（P4 计划）减少轮询，`run_event` 的写入路径要加 `NOTIFY`，**采集链路不受影响**（它读表不读通知）——但**若 NOTIFY 在事务提交前发，会出现"通知到了、数据没提交"**（现有 `JdbcRunCreationRepository` 已在同事务内发 NOTIFY，`:335-337` 注释说明"事务回滚则通知不发出"）；② 本维度若给 `run_event` 加列（`trace_id`/`span_id`），必须确认 SSE 的 `filterPayload` 白名单不会把它透给前端（**前端不需要 span 信息**，且多一个字段就是多一个泄露面）。
- **具体证据**：`run_event` 唯一约束（DDL `:3835-3846`，注释"SSE 续传依据"）；`JdbcRunCreationRepository.java:326-337`；`RunEventStreamer.filterPayload`（`:233-246`）。

### 8.2 与非 agent 领域成熟做法的对照

**对照 1 · 金融交易的"双录 + 不可变账本"（对审计）**
- **出处**：SEC Rule 17a-4(f) 的 WORM 要求（<https://www.sec.gov/rules/final/34-47806.htm>）；支付域的"授权-捕获-结算"与对账（见 09 报告 T3）。
- **可借鉴**：① **WORM 的核心不是"不能删"，而是"删了能被发现"**——这正是哈希链 + 锚定要解决的；② 金融业把"审计轨迹"与"业务账"**分开存储、分开权限**（本项目已做到：`audit_record` 用独立清理凭据）；③ 对账是**双向的**（我方记录 vs 对方回执），本项目对应 `agent_task_outcome`（外部终态校验回执）——这个设计在 agent 框架里很罕见，值得保留并强化。
- **本项目的差距**：缺 WORM/哈希链（改进点 4）；缺"审计轨迹的外发副本"（金融业会把审计同步到独立系统，本项目只有单库）。

**对照 2 · 分布式系统的"结构化日志 + 事件溯源"（对日志与事实层）**
- **出处**：Kleppmann《Designing Data-Intensive Applications》O'Reilly 2017（事件溯源与日志作为"系统真相"的论述）；Kubernetes 的 Events 与 `kubectl describe` 模式。
- **可借鉴**：① **事件溯源系统天然有"可重放"能力**——本项目的 `run_event` + 幂等采集正是这个模式，因此"指标可补算"是**结构赐予的**，不是额外努力；② K8s 的做法是"**resource 状态 + 事件流**"两层：状态给机器读，事件给人读。本项目 `run.state`（状态）+ `run_event`（事件）是同构的，**但没有 `kubectl describe` 那样的"一屏看懂"入口**（`/transcript` 接近，但只覆盖会话）。
- **本项目的差距**：缺一个"单 Run 全景视图"（把 state/step/tool/usage/risk/eval 拼成一屏），这是**看板与 API 之间缺失的一层**。

**对照 3 · 数据库的 WAL/CDC 与"变更数据捕获"（对指标派生）**
- **出处**：PostgreSQL 逻辑复制与 `pg_stat_statements` 的官方文档（<https://www.postgresql.org/docs/current/logical-replication.html>、<https://www.postgresql.org/docs/current/pgstatstatements.html>）。
- **可借鉴**：① **CDC 是"事实 → 派生"的标准管道**，本项目用"终态触发 + 专用队列 + 幂等 upsert"实现了同一效果，但**依赖应用显式发事件**（`publishTraceCollect`），一旦漏发就永远不采（只能靠补算）；CDC 则**不会漏**（只要写库就有变更）。② `pg_stat_statements` 提供的"按 SQL 归一化的耗时/次数"是 USE 方法在 DB 层的落地——本项目**完全没开**，等于放弃了最便宜的 DB 段可观测性。
- **本项目的差距**：① 采集的"完备性"依赖应用发事件（可在改进点 8 里加"未采集 Run 扫描"作为兜底）；② 未启用 `pg_stat_statements`（一条 `shared_preload_libraries` 配置的事）。

**对照 4 · 航空"黑匣子"（对不可变与独立供电）**
- **出处**：ICAO Annex 6 对飞行记录器（FDR/CVR）的要求（**未逐字核对原文，属公开常识级引用**）。
- **可借鉴**：黑匣子的两条设计原则对本维度极有启发：① **记录与业务系统物理独立**（坏了也不影响飞行、且能独立取出）；② **循环覆盖但保留最后一段**（不是无限增长）。
- **本项目的对照**：① 审计与业务**同库**（一台 PG 挂了，审计也没了）——这是真实风险，金融业会用独立审计库；② 指标表**无限增长**（劣势 6），而黑匣子是"固定窗口 + 覆盖"——本项目应给指标表定保留期（例如 180 天明细 + 永久小时桶），而不是"永久明细"。

### 8.3 反向思考：若从头重做本维度，我们会怎么设计？

**设计 1 · 第一天就引入"一个 trace-id + 一棵 span 树"，而不是"三个 id + 扁平事件"**
- **动机**：T4 指出本项目已有 32-hex trace-id（与 W3C 同形），**只差 span-id**。若第一天就用 OTel，`traceparent` 会自然贯穿 HTTP/outbox/MQ/worker，`run_event` 只需带 `span_id` 就能定位到具体步骤。
- **会怎么做**：`LogContext` 只保留 MDC 映射（不作为 id 源头）；`outbox_event` 建表时就带 `trace_parent`；`run_step` 建表时就带 `span_id`/`parent_span_id`。
- **与现状的取舍**：现状的"扁平事件 + 宽表"更简单（两张表 vs 一棵树），且**查询性能更好**（`sequence_no` 顺序扫）。**从零设计我会选 OTel，但会保留宽表作为"业务指标权威"**——即"span 做诊断、宽表做报表"，这正是改进点 1 + 3 的组合。

**设计 2 · 审计表从第一天就是"链"而非"表"**
- **动机**：改进点 4 的核心难题是"历史无法回填"。若第一天就设计成 `prev_hash` + `chain_seq`，零迁移成本。
- **与现状的取舍**：**这是本报告最强烈的一条"如果重来"建议**（与 09 报告"定价应该从第一天版本化"同级）。但要注意：它会让"审计写入"从"一次 INSERT"变成"取锁 + 读上一行 + 算哈希 + INSERT"，**在单租户试点阶段纯属过度设计**。正确的做法是**先设计好 schema（留 `prev_hash` 列）但不启用链**，等合规要求出现时再打开计算逻辑——**schema 预留的成本近零，补 schema 的成本是"无法回填"**。

**设计 3 · 指标"一列一写入方"的强制约束（编译期或扫描期）**
- **动机**：D-9 的 7 个死列不是"忘了写"，而是"**加了列但没人负责**"。若第一天就有"新列必须登记写入方"的机制（例如在 `AgentMetricPort` 的 record 定义里，每个字段必须有非空的构造点，且有测试断言），就不会出现。
- **会怎么做**：用 `TraceMetric` 的**全参构造 + 无 null 默认值**（现在已经是 record，但允许 null）；改为"显式 `NotCollected` 包装类型"（`Collected<T>` / `NotCollected(reason)`），**让"未采集"成为类型系统的一部分**而不是 null。
- **与现状的取舍**：这会显著增加代码量（每个字段都要包装），**对 40 列宽表不划算**。**更好的折中**：保留 null，但加"死列守卫测试"（改进点 8 的门禁 5）——**用测试而不是类型来保证**。

**设计 4 · 告警从第一天就"规则即代码 + 单元测试"**
- **动机**：本项目三次出现"实现了没接线"（D-5/D-8/D-14），根因是"接线"这一步**没有测试覆盖**。若告警规则是"Prometheus YAML + `promtool test rules`"，则"规则存在但没生效"会在 CI 就被发现（`promtool` 会校验表达式引用的指标名）。
- **与现状的取舍**：现状的"应用内规则 → `review_task`"有好处（能携带业务上下文、能自动去重），坏处是**不可被 `promtool` 验证**。**从零设计我会两者都做**：应用内规则负责"业务语义判定"（如"循环调用"），Prometheus 规则负责"SLO/饱和"（能用标准指标表达的），并用一个 IT 断言"应用内规则产出的计数被 Micrometer 暴露"（把两者接起来）。

**如果重来，我最遗憾的三件事**：① **`outbox_event` 没有 `trace_parent` 列**（唯一"只能向前补、无法回填历史"的追踪缺口）；② **`audit_record` 没有 `prev_hash` 列**（schema 预留成本近零，补的成本是"历史不可入链"）；③ **`AgentMetrics` 与 Micrometer 两套指标并存**（一套空转、一套无约束，本可以只有一套）。

**如果重来，我会庆幸的三件事**：① **把"指标 = 事实的确定函数"作为第一原则**（它让补算、回刷、对账全部成为可能，这是竞品普遍缺失的能力）；② **`trace_id_source` 降级留痕**（一次性解决了"id 从哪来"的可解释性问题）；③ **审计 PII 拒写而非脱敏**（"不存"比"存了再打码"更彻底，且与 `OutputModeration` 复用同一份正则，少一套规则）。

## 九、对产品演进的启发

### 9.1 本维度支撑的产品能力（用户能感知什么）

**对终端用户（学生/家长/教师）**
- **「我反馈的问题，客服能查到」** —— 当前**不能**（响应头 `X-Trace-Id` 在 Worker 侧断链，D-3）。改进点 1 落地后，"复制响应头 → 客服一次查询看到全链路"才成立。这是**最直接的用户可感知价值**。

**对租户管理员（TENANT_ADMIN）**
- **「我们这周跑了多少、成功多少、花了多少、每个成功任务多少钱」** —— 当前**看不到**（无租户侧指标端点、无 cost per successful task）。改进点 3 是这条产品线的全部。
- **「我们的 Agent 最近是不是变差了」** —— 需要 `QualityAlertEvaluator` 接线（D-14）+ 租户视图。

**对平台运营（PLATFORM_ADMIN）**
- **「现在有没有事？」** —— 当前只能靠"打开 Grafana 看一眼"；改进点 2 之后是"告警会来找你"。
- **「出事时先看哪」** —— 当前没有 runbook（改进点 2 的 `runbook_url` 门禁强制补齐）。
- **「这个租户的审计能导出给监管吗」** —— `/api/audit` 有，但**无导出格式（CSV/PDF）**、无"完整性证明"（改进点 4）。

**对合规/法务**
- **「日志留多久、删的时候有没有凭证」** —— ✅ 已实现（`audit-days=180`、`erasure_certificate`、`actor` 声明）。
- **「能不能证明没人改过审计」** —— ❌ 当前不能（劣势 4）；且**启动守卫空转**（D-5）使"连'有没有撤权'都没在检查"——这一条在合规访谈里会被直接问出来。
- **「未成年人原文存在哪、留多久」** —— ✅ 有明确答案（不存正文 + `message-days=30` + 独立于 trace 的配置键）。

### 9.2 演进路线图（近/中/远三期，每期有明确产出物与验收标准）

#### 近端（P4 实测调优批 · 1 个迭代内）

**目标**：把"已写好但没生效"的东西接上，把"能叫醒人"的最小告警建立起来。**不加新架构**。

|---|---|---|
| `AuditTamperProofGuard` 恢复受检表 + 空清单拒启 | 8 | 启动日志出现"受检 2 张表"；改回空数组则启动失败 |
| `/metrics` 二选一（下线或接线） | 8 | 架构测试断言"端点存在 ⇒ 有 increment 调用点" |
| `TraceObserverChain` 删除或接线（推荐删除） | 8 | 上下文中不存在无消费者的 observer bean |
| 7 个死列回填（除 `instruction_followed`） | 8 | `safety_blocked_count == count(risk_event)` 对同一 trace 成立 |
| 4 个新 Gauge（outbox 深度/预算拒绝/UNKNOWN/采集新鲜度） | 2 | `/actuator/prometheus` 中四个名字全部存在 |

**近端明确不做**（避免范围蔓延）：OTel 全量 span（跨迭代）、哈希链（等合规触发）、日志 JSON 化（中期）、看板改造（中期）。

#### 中期（平台化批 · 2 个迭代）

**目标**：端到端可追踪 + 业务看板 + 日志合规。

| 产出物 | 对应改进点 | 验收标准 |
|---|---|---|
| OTel 接入（`agent.run` + `gen_ai.chat` + `execute_tool` 三类 span） | 1 | `OtelTracePropagationIT` 断言响应头 traceId == `agent.run` span traceId；五类 span 同 trace |
| trace 跨 outbox 贯通（`trace_parent` 读写 + 批次 Link） | 1 | 反向验证：注释读取列 → 贯通断言变红 |

#### 远期（生态批 · 3 个迭代以上）

**目标**：可验证审计 + 导出成本可控 + 单位经济学闭环。

| 产出物 | 对应改进点 | 验收标准 |
|---|---|---|
| 审计哈希链（按租户分链）+ 每日锚定 + 校验器 | 4 | 直连删中间行 → 校验器定位到第 N 条；反向验证去 prev_hash 变红 |
| tail sampling（Collector）+ 采样决策属性 | 7 | 错误 100% 采、基线 10% ± 15、事实层不受影响 |
| 指标表保留期（明细 180 天 + 小时桶永久） | 8 邻接 | 到期清理可查；`agent_trace_metric` 行数进入稳态 |
| 单 Run 全景视图（state + step + tool + usage + risk + eval 一屏） | 8.2 对照 2 | 一个 API 返回六类事实；P95 < 300ms |
| 租户数据访问报告（合规产品化） | 9.1 | 可按时间窗导出该租户的全部审计/访问记录 |

**远期的最大不确定性**：**哈希链是否值得做**。它取决于"是否有要求 SOC 2 / 等保三级的客户"——这是商业决策而非工程决策。本报告的建议是：**先把 schema 预留（`prev_hash` 列），但不启用计算**，等客户要求出现时再打开。

### 9.3 风险清单（做这一步可能踩的坑，关联本项目已知铁律）

| # | 风险 | 触发场景 | 后果 | 缓解 |
|---|---|---|---|---|
| R1 | **恢复 `AuditTamperProofGuard` 后开发环境起不来** | 改 8-A 后本地未执行 `04_retention_role.sql` | 开发阻塞、被回滚 | 默认 `require-isolated-credential=false`（只告警），并在 `platform.env.example` 写明；IT 用独立 profile |
| R2 | **告警阈值拍错 → 噪声训练人忽略** | 改进点 2 上线 | 告警疲劳，比没有告警更糟 | 先在影子期只记录不通知（`alert: ... for: 9999h` 或 recording rule），校准后再开；每条规则必须配"负向用例" |
| R3 | **OTel exporter 阻塞业务** | 后端不可达 / 队列满 | Run 变慢甚至超时（比没有追踪更糟） | `BatchSpanProcessor` + 队列满丢弃 + `agent.span.dropped_total`；IT 用黑洞端口验证不阻塞 |
| R4 | **span 里写入 prompt/response 原文** | 有人为了"方便调试"加 `gen_ai.prompt` | 违反未成年人数据红线（不可接受） | 源码扫描门禁 + 运行时"含身份证的输入不进 span"IT（改进点 1 门禁 3） |
| R5 | **`traceparent` 列加在热点表上导致锁表** | `ALTER TABLE outbox_event ADD COLUMN` | 发布暂停、消息积压 | PG 11+ 可空列加列是元数据操作；仍在低峰执行 + 先在预发验证 |
| R6 | **哈希链的 advisory lock 与业务锁序冲突** | 改进点 4 | 死锁（`deadlock detected`），审计写入失败 → fail-closed → 业务中止 | 固定锁序（先 `audit_record` INSERT，后取链锁）；锁内不做其他 DML；并发 IT 验证 |
| R7 | **`to_jsonb` 规范化不稳定导致链校验误报** | 不同 PG 小版本 / 含 `jsonb` 字段 | 校验器天天报"链断"→ 失去信任 | 先做 PoC（同一行多次 `to_jsonb` 是否逐字节相同）；只对**关键列**哈希，不哈希 `jsonb` 全量 |
| R8 | **日志 JSON 化导致采集器 OOM** | 日志体积 2–3× | 采集链路崩 | 同步调批大小 + 采样（只采 INFO 以上 + 全量 ERROR） |
| R9 | **PII 正则性能拖慢业务** | 每条日志跑 N 个正则 | 请求延迟上升 | 在 `AsyncAppender` 的消费线程做，不在业务线程；基准门禁（P99 < 50µs） |
| R10 | **看板/告警把 sse-direct Run 算进成功率** | 改进点 3 未排除 | 成功率虚低 → 误告警 | `RunFunnelIT` 显式断言排除；在视图注释里写明理由 |
| R11 | **新视图未同步 `03_platform_roles.sql`** | 加 `mv_run_funnel_hourly` | 生产查询权限不足（Grafana 报错） | **铁律 7**：新表/新视图同步授权 + `SchemaDriftIT` |
| R12 | **"实现了没接线"再次发生** | 改进点 5 的 `QualityAlertJob`、改进点 2 的 Gauge | 又一次"代码在、运行无" | 每个新组件必须有"上下文存在性 + `@Scheduled` 注解 + 一次真实调用"三重断言（改进点 5 门禁 6 的模式） |
| R13 | **用 span 替代宽表** | 改进点 1 落地后有人提议 | 指标变成"非确定函数"，失去补算能力 | 文档写死"span 只做诊断"；架构测试断言 `AgentMetricCollector` 不依赖任何 OTel API |
| R14 | **审计链让"删除中间行"从"不可能"变成"可能且需检测"** | 引入链后有人误以为"有链就可以删" | 反而降低实际保护 | 链是**检测**手段，不是**允许**手段；`audit_record` 的触发器与凭据隔离**必须同时保留** |

### 9.4 一句话结论

**本平台在本维度上做出了一个罕见的组合——"DB 强制不可改的审计 + 事实派生的可补算指标 + 降级必须留痕的三条纪律"，这三条在本次对比的 7 个框架里没有一家同时具备；但也正因为工程力量集中投在"事实与审计"上，追踪与告警停在了半成品：traceId 在 outbox 处断成三套 id、`ai.trace.*` 与 `/metrics` 是两个永不产出数据的端点、7 列指标无人写入、比例类告警写好了却没被调用、防篡改启动守卫的受检表被注释成了空数组——所以下一步的正确顺序不是继续加机制，而是先把这些"已写好但没生效"的接上（改进点 8），再用 Prometheus 规则让异常能叫醒人（改进点 2），最后才谈 span 树与哈希链。**
