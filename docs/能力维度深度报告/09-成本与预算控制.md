## 一、维度定义与评估坐标系

### 1.1 这个维度到底解决什么问题

LLM agent 系统的成本结构与传统软件有本质区别：**传统软件的成本在部署时基本确定，而 agent 的成本在运行时按 token 线性增长，且增长曲线由模型自主行为决定**。一个 agent 任务可能调 1 次模型，也可能因为工具失败重试、循环检测失败、上下文膨胀而调 20 次——**成本方差比传统服务高一个数量级**。

这个维度要回答五个连续的问题：**计量**（一次运行消耗了什么：token / 模型调用 / 工具调用 / 步骤）、**定价**（这些消耗值多少钱，谁给 token 定价，单价从哪来，价格变了历史账怎么办）、**准入**（允不允许这次消耗发生，能不能超，超了怎么办）、**分摊**（这笔钱算在谁头上：租户 / Agent / 任务 / 步骤 / 模型 / 工具 / 场景）、**治理**（怎么持续控制而不损害质量）。

它**不解决**「模型答得好不好」（维度 6/10）与「权限够不够」（维度 7），但与它们强耦合：**权限决定谁能花（维度 7 的 `tool:invoke` 是花钱的前置）、上下文决定花多少（维度 6 的压缩直接降本）、可靠性决定花几次（维度 11 的重试直接放大成本）**。

本项目在这个维度上有一个特殊的历史包袱：早期 `usage_record.cost_amount` 只记「工具调用次数 × ¥0.50」的**固定代理值**，`input_tokens` / `output_tokens` 两列**无任何写入方**——「一个 Run 花了多少 token」这件事**在账上曾经根本不存在**。P0-3b 批次补上真实计量通道，但成本治理的整体形态（预留 → 结算 → 对账）比计量通道更早成型——这个**倒序**是理解现状的关键：**账本先有骨架，度量后补齐**。

### 1.2 能力分层的四档模型

| 档位 | 名称 | 含义 | 典型表现 |
|---|---|---|---|
| **L0 无计量** | 黑盒烧钱 | 跑完才知道花了多少，靠供应商账单反查 | 早期 Demo、内部 PoC |
| **L1 观测计量** | 只看不说 | 有 usage dashboard / trace 级 token 计数，但**不影响执行** | LangSmith、OpenAI Usage Dashboard、Agno `Metrics` |
| **L2 执行侧闸门** | 预留-结算 | 执行前占用额度、执行后按实际结算，重复结算幂等 | 本项目 `budget_reservation` + `BudgetPort`；支付域「授权-捕获-结算」三段式 |
| **L3 数据层强不变量** | DB 强制不超发 | 「不能超」由数据库约束/触发器保证，应用层写错也失守不了 | 本项目 `budget_no_overspend` CHECK + `enforce_reservation_state_transition` 触发器（本项目独有能力） |

**关键区分（L1 与 L2 的本质差别）**：L1 的限流/预算**是软告警或请求级拒绝**，L2 的预算**参与执行链**：它在工具执行**之前**占额度，占不到就不许执行。因此 L1 的超支是「事后发现」，L2 的超支是「结构上不可能」。

**关键区分（L2 与 L3 的本质差别）**：L2 的「不超发」由应用层 SQL 保证，**并发窗口靠应用层写对**；L3 由 DB CHECK 保证，**应用层写错也只是报错而不是超发**。多数竞品停留在 L1。

### 1.3 评估坐标系：5 个评价轴

| 轴 | 观测什么 | 怎么观测（本项目可采集的信号） |
|---|---|---|
| **A. 计量保真度** | token 是真实 tokenizer 还是估算；成本是真实价格还是代理值 | `usage_record.input_tokens/output_tokens` 的写入方；`ModelPricingPolicy.pricingOf` 是否命中；`usage_record.model_id` 的 `tool:` 前缀占比 |
| **B. 强制程度** | 「不能超」靠什么保证：应用层 if / 软告警 / DB 约束 | `budget_no_overspend` CHECK；`tryAtomicReserve` 的单条条件 UPDATE；`enforce_reservation_state_transition` 触发器 |
| **C. 会计正确性** | 预留-结算是否账实相符；重复结算是否重复计费；异常状态如何处置 | `usage_record` 幂等唯一索引 `idx_usage_operation_once`；`isConsistent` 的账实比对；UNKNOWN 预留处置矩阵 |

### 2.1 核心理论 / 概念框架（8 个）

**T1 · FinOps 学科与「加性成本单位」（additive cost unit）**
- 出处：FinOps Foundation《FinOps Framework 2025》<https://www.finops.org/?p=20636>；同基金会《The State of FinOps Report 2025》<https://data.finops.org/2025-report>。
- 定义：FinOps = 「在技术投入上组织性地实现最大价值」的实践纪律，由**原则/域/能力/角色/度量**构成。2025 版新增 **Scopes**（一段技术支出，FinOps 概念可应用其上），因实践已从公有云扩展到 SaaS、Licensing、**AI 成本**与私有云。
- **对本平台最关键的一条**：报告把「**Managing AI/ML spend**」列为优先级上升最快方向之一（+4 位），「**Getting to unit economics**」上升 5 位；**63%** 受访者已管理 AI 支出（2024 年 31%）。行业共识已把 **AI/ML 支出当成独立 Scope**，而非「云支出的子项」。
- **加性成本单位**：把异构消耗归一到可加总的抽象单位，典型实现是 LangSmith 的 **LSU（LangChain Standard Units）**——trace、Agent Server 运行时、sandbox 统一折算为 `$1.00 / LSU`（<https://www.langchain.com/pricing>，取数日 2026-11-15）。
- **对本项目的含义**：本项目当前是**「元」+「token 数」两个并列口径**（`budget_account.total_limit` 是元，`usage_record.input_tokens` 是 token），尚未归一到一个加性单位。这不是缺陷——平台内成本全部由平台自己定价、以元计价——但意味着**「token 数」与「元」两套报表可能因估算误差而不自洽**（详见 4.2 D-7 与改进点 1、2）。

**T2 · Unit Economics 与「每次成功任务的成本」（cost per successful task）**
- 出处：State of FinOps Report 2025（同上）将 "Getting to unit economics" 列为优先级上升 5 位的方向；SaaS 领域标准定义见 <https://www.saas-capital.com/blog-posts/what-is-unit-economics/>（取数日 2026-11-15）。
- 定义：**Unit economics** 追问「每一单位产出的边际成本与边际收益之比」，而非绝对成本。对 agent 平台，正确的分母**不是「调用次数」而是「成功完成的任务数」**。
- **关键分母选择**：`total_cost / trace_count` 与 `total_cost / succeeded_task_count` 可相差一个数量级——agent 的链路终态 ≠ 任务成功（本项目 `agent_trace_metric.terminal_state` 列注释明确「链路终态 ≠ 任务成功」，由 `human_verdict` / `auto_verified` 回答是否达成目标，DDL `:758`、`:812-814`）。
- **对本项目的含义**：`mv_agent_metric_hourly` 已同时提供 `trace_count`、`succeeded_count` 与 `sum(cost_amount)`（DDL `:1009-1055`），**数据基础完全具备**，但**无一处计算 cost per successful task**（见改进点 3）——本维度最清晰、最高性价比的缺口。

**T3 · 预算治理的「预留-结算」三段式（pre-authorization / reserve-then-settle）**
- 出处：支付域成熟范式。Stripe 的授权-捕获（authorization / capture）是业界标准参照——授权时**冻结**额度，捕获时才真正扣减，授权可撤销、可部分捕获：<https://docs.stripe.com/payments/place-a-hold-on-a-payment-method>（取数日 2026-11-15）。数据库侧等价物是「单条原子条件更新 + 不可变预占行」：PostgreSQL `SELECT ... FOR UPDATE` 与原子 DML 语义 <https://www.postgresql.org/docs/current/explicit-locking.html>（取数日 2026-11-15）。
- 三段式：**预留（reserve）→ 执行 → 结算（settle）或释放（release）**。
- **本项目是这套范式的完整实现**：`budget_reservation` 预留行（`state ∈ {RESERVED, SETTLED, RELEASED}`）+ `budget_account` 三段金额 + 幂等结算（`ON CONFLICT DO NOTHING`）+ 终态不可回退（`enforce_reservation_state_transition` 触发器）。
- **与支付域的关键差异**：支付域的「预留过期」是**正常业务流**（授权到期自动释放）；本项目的 UNKNOWN 预留**刻意不释放**（见 T5），因成本可能已发生。这是**有意识的、偏离支付域惯例的取舍**。

**T4 · 精确一次计费 vs at-least-once 副作用的成本放大**
- 出处：Kleppmann《Designing Data-Intensive Applications》O'Reilly 2017（幂等与去重讨论）；Microservices.io Idempotent Consumer 模式 <https://microservices.io/patterns/communication-style/idempotent-consumer.html>（取数日 2026-11-15）。
- 核心：**at-least-once 交付 + 无幂等 = 副作用重复执行**。对 agent 而言，重复副作用不只是数据问题，还是**钱的问题**——每次重复调用都会再次产生 token 消耗。
- 本项目处置链条：`usage_record` 以 `(tenant_id, operation_id)` 唯一索引保证「同一逻辑操作只结算一次」（DDL `:4549`）；`modelCallId` 必须含**领取代次 attempt**（`RunExecutionLoop.modelCallId`，`runId|attempt|ordinal` 的确定性 UUID），否则「Run 被重投时第二次尝试命中第一次幂等键 → 第二次真实消耗不被记账」（`RunExecutionLoop.java:1620-1636` 注释）。
- **但成本放大本身未被度量**：**没有**「重试导致成本放大倍数」指标（`retry_count` 存在于 `agent_trace_metric`，但与 `cost_amount` 之间无比值口径）。见改进点 5。

**T5 · UNKNOWN 状态：不确定副作用下的账务保守原则**
- 出处：Two Generals Problem（分布式共识的经典困境）通常归到 Jim Gray 的工作；工程侧的标准表述见 Kleppmann,《DDIA》2017 关于「无法判定操作是否已执行」的讨论；本项目自身的铁律 R-007 / P3-D04 §2.4 记录于 `01_platform_ddl.sql:1569-1572`（`budget_reservation.state` 列注释）。
- **本项目规则**：UNKNOWN 预留**保持 RESERVED，绝不自动释放**——「成本可能已发生」；只有对账收敛（`RECONCILED_SUCCEEDED` → 结算 / `RECONCILED_ABSENT` → 释放）或确定失败（`FAILED` → 释放）才可离开 RESERVED。
- **会计学论证**：预留是「已承诺但未结算」的额度。UNKNOWN 状态下，操作既不能被判为「已发生」（不能结算，因为可能是幽灵操作）也不能被判为「未发生」（不能释放，因为成本可能已付）。因此**唯一正确的姿态是挂账待对账**——这与会计上的「未决科目」（ suspense account）是同一个模式。
- **代价**：若对账链路不运转，UNKNOWN 预留会**长期占用额度**，最终导致「明明没花多少钱却预留失败」。本项目为此专门建了两条反查通道：`findUnknownHeld`（工具侧）与 `DelegationBudgetReconciliationService`（委派侧），并且在未装配时**显式告警而非静默跳过**（`BudgetReconciliationService.java:153-159`）。这是本项目在「UNKNOWN 语义」与「成本治理」之间的**闭环设计**，是本维度最有价值的耦合点之一。

**T6 · 配额、限流与准入控制（token bucket / leaky bucket / admission control）**
- 出处：**RFC 2697**《A Single Rate Three Color Marker》（单速率三色标记，srTCM）<https://www.rfc-editor.org/rfc/rfc2697>；**RFC 2698**《A Two Rate Three Color Marker》（双速率三色标记，trTCM）<https://www.rfc-editor.org/rfc/rfc2698>（取数日 2026-11-15）。二者都是令牌桶在 DiffServ 流量整形语境下的标准化形态。
- **令牌桶**：`tokens(t) = min(b, tokens(t−1) + r·Δt)`——桶容量 `b` 决定**允许的突发**，补充速率 `r` 决定**长期平均**。其可证明性质（网络演算中的 (σ, ρ) 约束）：任意长度 T 的区间内，通过量不超过 `b + r·T`。
- **漏桶**：以恒定速率 λ 输出，**平滑**突发。区别：令牌桶容忍突发，漏桶消除突发。
- **与本项目的关系**：本项目的 `agent.rate-limit.limit-per-window` / `window-seconds`（application.yml:130-134）实现的是**固定窗口计数**，配置注释明确承认「窗口边界处实际放行量可达 2×limit」，并提供 `sliding-window` 开关切换为「上一窗口按剩余时间衰减加权」的滑动窗口近似。**这是 RFC 2697/2698 意义上的降级实现**：既非严格令牌桶（无桶容量与补充率语义），也非严格漏桶（不保证输出平滑）。同时，`JdbcRateLimiter` 是**按租户的 API 请求限流**（治理台查询/决策桶），**与并发 Run 数无关**——见 4.2 D-11 与第七章改进点 6。
- **准入控制（admission control）**：在系统过载时**拒绝或降级新请求**而非让系统崩溃。Google SRE 书籍中的 "Handling Overload" 一章是标准参照 <https://sre.google/sre-book/handling-overload/>（取数日 2026-11-15）。

**T7 · 成本-延迟-质量三难与 LLM 路由**
- 出处：Ong et al.《RouteLLM: Learning to Route LLMs with Preference Data》arXiv:2406.18665（UC Berkeley / Anyscale / Canva，2024-06 首版，2025-02 v4）<https://arxiv.org/abs/2406.18665>；早期工作 Chen, Zaharia, Zou《FrugalGPT》arXiv:2305.05176（2023-05）<https://arxiv.org/abs/2305.05176>。
- **三难**：给定质量下限，成本与延迟往往同向——想更准就得用更贵的模型（更慢更贵）；想更便宜就得降级（更不准）。
- **RouteLLM 量化结论**（论文摘要与正文）：路由器在特定基准上**在不牺牲响应质量前提下把成本降低超过 2 倍**（另给出 MT-Bench 降 85%+、MMLU 45%、GSM8K 35% 的对比 GPT-4 口径，保持约 95% 的 GPT-4 质量水平）；且具备**迁移能力**——强弱模型在测试时被换掉仍保持表现。
- **对本项目的含义**：`cap_agent_def.model_ref`（维度 13）在治理期发布时**钉死模型**，运行期只读快照（`forbid_published_def_mutation`）。这意味着**本项目当前在架构上排除了「按请求动态选模型」**，成本优化只能来自上下文压缩（维度 6）、缓存命中、减少调用次数（`max-llm-calls`）与**降级失败**。改进点 7 讨论的「成本超阈值降级模型路由」需与维度 13 的发布期固化语义做取舍。

**T8 · 成本可归因性（cost attribution）与「计量账 ≠ 业务账」的科目分离**
- 出处：FinOps Framework 2025 的 Scopes 概念（同 T1）提供「不同支出段用不同科目管理」的框架依据；shared-cost allocation 与 showback 见 Allocation 能力域 <https://www.finops.org/framework/capabilities/allocation/>（取数日 2026-11-15）。
- **核心命题**：把**平台自身为评估/治理付出的成本**（judge、LLM-as-judge、离线评测、抽样打分）与**业务运行成本**混在一个账上，会让「单 Run 成本」随评估频率漂移——评估越勤，业务成本看起来越高，而这个虚高会被误读为「业务本身变贵了」。
- **本项目实现**：`EvaluationCostBudget` 用独立科目名 `EVAL_JUDGE_COST` 在**进程内**单独记账，**不写 `usage_record`、不调 `AgentMetricPort.upsert`、不碰 `cost_amount`**（`EvaluationCostBudget.java:15-40` + `ModelAttributionJudge.java:36-39`）。且有**守卫测试**钉死：`L2ProductionGuardTest.judgeCostIsPhysicallyIsolatedFromBusinessCost`（`platform-bootstrap/src/test/.../L2ProductionGuardTest.java:138-160`）断言 judge 源码中不出现 `cost_amount` / `usage_record`。
- **这是相对竞品的真实领先**：业界通用做法（LangSmith、Agno、OTel 生态）普遍把评测调用与业务调用混在同一 trace/span 树里靠 tag 区分；**账本层面物理隔离**更严格。

### 2.2 理论给出的「设计张力」（trade-off）清单

| 张力 | A 方案 | B 方案 | 本项目取舍 |
|---|---|---|---|
| 硬不超发 vs 随机拒绝 | 只有 DB CHECK（最后防线） | 只有应用层原子 UPDATE | **二者缺一不可**：DDL `:1562-1572` 明写「仅有 CHECK 会出现『随机预算不足』，仅有应用层会在 SQL 写错时失守」 |
| 精确计量 vs 实现成本 | 真实 tokenizer（精确但需依赖、随模型变） | 启发式估算（CJK 1 / 非CJK 3，零依赖） | 上下文侧**启发式**（`HeuristicTokenCounter`），但**结算侧用模型回传的真实 token**——不确定性只封装在可自动回退的一侧 |
| 预留保守 vs 额度占用 | 按估算×安全系数预留（防结算超预留） | 按真实值预留（省额度） | 预留取 **估算输入 × 2 + maxTokens 输出**上界（`INPUT_TOKEN_ESTIMATE_SAFETY_FACTOR=2`），多预留部分结算时自动退回 |
| UNKNOWN 释放 vs 保留 | 释放（额度不浪费） | 保留（防白送额度） | **保留**（R-007），代价是需对账链路兜底 |
| 成本口径纯净 vs 可比 | judge 成本物理隔离到独立科目 | 与业务成本同账打 tag | **物理隔离**（`EVAL_JUDGE_COST`），代价是跨科目总成本需要显式相加 |
| 单价配置 vs 价格漂移 | 配置文件里改单价（简单） | 单价表版本化 + 生效日期 + 历史回溯 | **当前是配置改单价**（无版本化、无生效日期）→ 价格调整后历史成本口径会漂移，见改进点 2 |
| 精确计量 vs 实现成本 | 真实 tokenizer（精确、需依赖、随模型变） | 启发式估算（CJK 1 / 非CJK 3，零依赖） | **启发式**（`HeuristicTokenCounter`），且该估算只用于**预留上界**；**结算用模型回传的真实 token**——这是本项目一个容易被误解但实际正确的设计 |
| 硬失败 vs 降级 | 成本超限直接失败 Run | 降级到更便宜模型继续 | **当前是硬失败**（`MAX_COST` → Run 收敛 FAILED），与维度 13 的「发布期固化模型」一致，见改进点 7 |
| 单层限额 vs 分级限额 | 一个总额硬封顶 | 按场景/Agent 分级封顶 | **当前是租户总额 + Run 级两个口径**，`platform.tenant_quota.budget_limit` **存在但未接入闸门**，见 4.2 D-10 |
| 固定窗口 vs 令牌桶 | 固定窗口（简单，边界 2× 突发） | 滑动窗口 / 令牌桶（平滑） | **固定窗口默认 + `sliding-window` 可选**，注释明写边界放大 |

### 2.3 业界公认的反模式（anti-pattern）清单及判别方式

1. **「成本 = 调用次数 × 固定单价」**：把 agent 的成本当成 RPC 成本。判别：`usage_record.input_tokens` / `output_tokens` 是否真的有非零写入方，且 `cost_amount` 是否随 token 变化。本项目**历史上正是这个反模式**（`ModelPricingPolicy` 类注释自陈：「`usage_record.cost_amount` 此前记的是『工具调用次数 × ¥0.50』的固定代理值」），P0-3b 已修，但**工具调用路径至今仍按「调用当量」计费**（`settleQuietly` 传 `reserveAmountPerToolCall`，`ToolInvocationGate.java:1643-1644`）——半修状态。
2. **「没有单价就按 0 元放行」**：把「不知道价格」静默变成「这次调用免费」。判别：查不到价时是否**显式可见**（WARN + token 如实记录 + 成本按 0 记）。本项目做到了（`ModelPricingPolicy.java:33-37`、`RunExecutionLoop.java:1661-1663`），这是**正确做法**。
3. **「用估算 token 直接当成本」**：把预估值当事实值入账。判别：结算路径用的是模型回传的真实 token 还是估算值。本项目**结算用真实 token**（`settleModelCost` 读 `response.usage().inputTokens()`），估算只用于**预留上界**——这一点做对了，但**报表侧仍混用**（见反模式 5）。
4. **「评测成本混进业务成本」**：见 T8。判别：judge 调用是否写 `usage_record`。本项目物理隔离，有守卫测试。
5. **「成本报表的分子分母都取自同一估算」**：`cost_amount` 由估算 token 算出，又除以估算的成功数——误差会被放大且无法察觉。判别：成本与 token 两条指标是否来自**同一个数据源**。本项目**存在此风险**：`agent_trace_metric.cost_amount` 来自 `usage_record` 的聚合（`JdbcTraceFactRepository.readUsage`），而 `usage_record.cost_amount` 在模型路径是真实 token × 配置单价（好），在工具路径是固定 ¥0.50（代理值，坏）——**同一列混了两种精度**。
6. **「预算只有一个总额，没有归属」**：只知道花了 10 万，不知道哪个租户/场景花的。判别：`usage_record` 是否有 tenant/run/model/reservation 四维可追；`budget_account` 是否只有租户+币种一个维度。本项目计量明细有四维，但**账户维度只有 (tenant_id, currency)**（`budget_account_unique UNIQUE (tenant_id, currency)`，DDL `:3523-3527`）——**无法按 Agent / 场景分账**。
7. **「限流只限请求数，不限并发」**：QPS 相同不代表系统压力相同。判别：是否同时有速率维度与并发维度。本项目**只有速率维度**（`agent.rate-limit`），且**并发 Run 上限未生效**（`agent.tenant.max-concurrent-runs` 引用数为 0，见 4.2 D-11）。
8. **「预算耗尽时静默降级」**：悄悄换便宜模型而不告警。判别：是否有明确的终止原因码。本项目用 `BUDGET_EXHAUSTED` / `MAX_COST` 显式收敛 Run 并写事件——做对了。
9. **「静态源码守卫 ≠ 运行时成立」**：铁律 17。判别：预算上限是否真的在执行链上生效。本项目 `max-cost-per-run` 曾是「只用于配置展示」的纸面承诺（`RunExecutionLoop.java:619` 注释自陈），P4-D11 才接入运行时（`ConfigReadService.java:128-133` 记录了这次修复）。
10. **「预留过期自动释放」在不确定副作用场景下的滥用**：见 T5。判别：释放路径是否检查了操作状态是否为 UNKNOWN。本项目 `ToolInvocationGate` 在 UNKNOWN 分支**不调用 `releaseQuietly`**（直接 `return result`），且 `BudgetPort.release` 的契约注释明确写「调用方责任：UNKNOWN 状态下禁止调用本方法」。

## 三、竞品实现全景（每个主流方案一段）

> **总体判断（先行给出，避免读者被「都有成本相关字样」误导）**：在本次对比的全部方案中，**没有任何一个在执行侧实现了「预留-结算」语义**。OpenAI / Anthropic / LangSmith / Vertex AI / CrewAI / Agno 的成本与配额能力全部属于 L1（观测计量 + 请求级限流/告警）或 L2 弱形态（会话级熔断）。**「DB 层强不超发 + 执行前预留 + 结算幂等 + UNKNOWN 不释放」这条完整链路，是本项目独有的。**

### 3.1 OpenAI（API Platform：Usage Dashboard + Rate Limits + Spend Limits）

**官方定位与实现机制**：成本治理拆成三个互相独立的机制——① **Rate limits**（速率）：按组织与项目两级生效（官方明确「not user level」），指标含 RPM / RPD / **TPM** / TPD / IPM，命中任一即拒绝；响应头回传 `x-ratelimit-limit-requests`、`x-ratelimit-limit-tokens`、`x-ratelimit-remaining-*`、`Retry-After`。**按 token 维度（TPM）限流**，语义上比纯请求数更接近「花多少钱」。② **Spend limits**（支出）：组织级与项目级均可设月度支出上限，官方明确二分——**Spend alert**「sends a notification; API traffic continues」（告警不中断流量）与 **Hard spend limit**「affected API requests return a 429 error」（超限返回 429）。③ **Usage Dashboard**（观测）：按项目拆解用量，可查当前与历史计费周期的 token 使用。
**官方来源**：<https://developers.openai.com/api/docs/guides/rate-limits>｜<https://help.openai.com/en/articles/9186755-managing-projects-in-the-api-platform>｜<https://openai.com/api/pricing>
**优点**：硬上限的失败语义与本项目一致（超限被拒 429，而非仅告警）；速率限制覆盖 token 维度；计费维度与组织/项目两级 RBAC 对齐，天然支持多租户分账。
**局限/代价**：**官方文档自陈「Enforcement isn't instantaneous, so recorded spending can slightly exceed the configured amount.」**——这正是本项目 DB CHECK 试图消灭的那类窗口，OpenAI 接受它，因为计量是异步的；**无预留-结算语义**（请求发出后才知道花了多少，并发场景必然小幅超支，官方自认）；支出上限是月度、聚合、事后计量，无法表达「这一棵调用树最多花多少」；Agents SDK 本身**不提供预算原语**。
**适用场景**：面向「谁调用 API 就谁付钱」的公有 API 消费方，解决**供应商侧的成本保护**，不是**平台侧的多租户成本分摊**。

### 3.2 Anthropic（Console Usage/Cost + 速率限制 + Prompt Caching 降本）

**官方定位与实现机制**：① **速率限制**：按组织与工作区两级的 RPM / ITPM（input tokens per minute）/ OTPM（output tokens per minute）——**ITPM 与 OTPM 分开计量**，因输出 token 单价远高于输入，分开限流更精确。② **Console Usage/Cost**：组织与工作区两级的用量与成本视图。③ **Prompt Caching 降本**（Anthropic 最有价值的一课）：官方定价（取数日 2026-11-15）显示缓存写入有溢价（5 分钟 TTL = 基础输入价 **1.25×**，1 小时 TTL = **2×**），而**缓存命中只收基础输入价的 0.1×**（部分新模型 0.025× / 0.05×）。官方特别提醒：**「input_tokens does NOT represent all input tokens, only the portion after your last cache breakpoint」**——命中缓存后 `input_tokens` 显著小于真实总输入。
**官方来源**：<https://platform.claude.com/docs/en/build-with-claude/prompt-caching>｜<https://www.anthropic.com/pricing>｜<https://docs.anthropic.com/en/api/agent-sdk>
**优点**：**缓存命中折价 0.1× 是量级级降本手段**，远大于任何工程优化——这是「成本治理」的上游杠杆；ITPM/OTPM 分开限流粒度细；API 响应返回 `cache_creation_input_tokens` / `cache_read_input_tokens`，让缓存效果**可被计量**（「降本手段本身必须可观测」）。
**局限/代价**：**`max_budget_usd` 是 SDK 级会话熔断**——单值、进程内、无多租户口径、无跨实例聚合（与本项目 `EvaluationCostBudget` 是**同一类局限**）；缓存计价使 token 口径**非线性**，任何跨供应商成本对比都必须先归一化到「等价未缓存 token」；官方明确「There's no way to manually clear the cache」。
**适用场景**：Anthropic 生态内、以 prompt 前缀稳定为特征的高频 agent（长 system prompt + 稳定工具定义 + 变化的用户输入），缓存收益最大。

### 3.3 LangGraph / LangSmith（trace 级 token/成本追踪 + workspace 支出上限）

**官方定位与实现机制**：① **Trace 级计量**：每条 trace 记录 token 与成本，单位是 **LSU（LangChain Standard Units）**，$1.00 / LSU（取数日 2026-11-15）——把 trace 存储、Agent Server 运行时、sandbox 资源统一折算到一个加性单位（T1 的实例）。② **Workspace 级支出上限**：在 Settings → Billing and Usage → Usage limits 设 workspace 的 spend limit，LangSmith 据此推算 base / extended trace 限额；**官方明确承认精度边界**：「although workspace-level spend limits are approximate for multi-workspace organizations, the **organization-level spend limit is absolute**」。③ **命中后的行为**：开发者计划用户达到 trace limit 后「will receive tracing errors and will not be able to create new traces」——**拒绝新 trace，而非拒绝业务请求**。④ **LLM Gateway 成本控制**：提供「Cost controls / Rate limiting controls / Model fallbacks」三项——**这是本次对比中唯一接近「成本超限 → 模型降级」的机制**，但属网关层能力。
**官方来源**：<https://docs.langchain.com/langsmith/billing>｜<https://www.langchain.com/pricing>｜<https://support.langchain.com/articles/1066772484-how-do-i-set-trace-limits-in-my-langsmith-workspace>
**优点**：**加性成本单位（LSU）**是本维度最值得借鉴的抽象；**Trace 级成本归因**天然对齐「一次任务」这一业务单位，`cost per successful task` 在其数据模型里是现成的；官方对多 workspace 精度边界的诚实标注值得学习（与本项目「小样本不显示百分比」同源）。
**局限/代价**：**支出上限是事后计量，不是执行前预留**——trace limit 命中后**已发出的 LLM 调用照常计费**，上限是「观测预算」而非「执行预算」；**LangGraph 编排核心无预算原语**（reducer / Checkpointer / Store / `trim_messages` 都与成本无关），成本完全靠旁路观测；**「拒绝新 trace」不是「拒绝新请求」**——业务请求照跑，只是没了可观测性，**对成本控制几乎无效**（钱照花，只是不记账）。
**适用场景**：以「可观测性驱动优化」为主线的团队；先有 trace 数据再谈成本治理的组织。

### 3.4 Google ADK / Vertex AI Agent Engine（Cloud Billing + 配额体系）

**官方定位与实现机制**：把 agent 成本**完全交给 Google Cloud 的既有基础设施**——① **Cloud Billing**：Agent Engine 按**计算资源**计费（官方定价 `ReasoningEngine vCPU $0.0994/vCPU-Hr`、`ReasoningEngine Memory $0.0105/GiB-Hr`，取数日 2026-11-15）。② **配额体系**：官方提供**峰荷估算方法**——定义 U（峰值并发用户数，如 250）、X（每用户每分钟请求数，如 2）、Y（每请求会话事件数，如 12），算 QPM = U×X，再按 50% 缓冲申请提额；具体配额项含 `reasoning_engine_service_query_requests`、`session_event_append_requests`、`session_write_requests`、`reasoning_engine_service_concurrent_query_requests`（并发双向连接）等。③ **模型成本另计**：走 Vertex AI 自己的配额与计费。
**官方来源**：<https://cloud.google.com/gemini-enterprise-agent-platform/resources/agent-quotas>｜<https://cloud.google.com/vertex-ai/generative-ai/docs/rag-engine/rag-quotas>｜<https://adk.dev/deploy/agent-runtime/>
**优点**：**配额维度贴近真实成本结构**——`session_event_append_requests` 直接对应「一次请求产生多少步」，这正是 agent 成本的主要驱动因子；**峰荷估算公式**（U×X×Y + 50% 缓冲）是可操作的容量规划方法；与 Cloud Billing 天然打通，成本直接进企业账单与 showback 流程。
**局限/代价**：**配额是「速率/并发」维度，不是「金额」维度**，没有「这一棵树最多花多少钱」的语义；**超限返回 429 Resource Exhausted** 需人工提额，运营负担在客户侧；**强绑定 GCP**（无法自托管或多云）；**完全无预留-结算**（Cloud Billing 是后置计量，Agent Runtime 不知道「这次调用会不会超预算」）。
**适用场景**：已全面上云、接受 GCP 计费与配额体系、需要与既有 Cloud Billing/预算告警打通的团队。

### 3.5 Microsoft AutoGen（依赖 Azure OpenAI 计费；已归档）

**官方定位与实现机制**：AutoGen Core / AgentChat 的运行时**不含任何成本或预算原语**——`Memory` 协议、`save_state/load_state`、`BaseGroupChat.run_stream` 都与成本无关；成本完全来自所选模型服务（通常是 Azure OpenAI），因而适用 Azure OpenAI 的配额与计费。
**官方来源**：<https://microsoft.github.io/autogen/stable/>｜<https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/memory.html>
**优点**：架构简单，不自造成本抽象——避免「半成品计费系统」这一常见坑。
**局限/代价**：**完全无成本治理能力**，成本 = 所选 LLM 服务商的账单，与编排框架无关；**官方已于 2025-10 并入 Microsoft Agent Framework、2026-10 起归档停维护**，其结论仅代表末代状态，**不应作为新项目选型依据**。
**适用场景**：历史项目参考；不建议作为新项目的成本治理参考系。

### 3.6 CrewAI（Control Plane 的 usage tracking + `max_rpm` / `max_iter`）

**官方定位与实现机制**：① 编排层限额：`max_rpm`（速率上限）与 `max_iter`（迭代上限）——注意 `max_iter` 是**次数**维度而非金额维度；工具侧支持 `cache=True`（缓存命中直接省下真实调用与真实成本）。② **企业 Control Plane**：提供 usage tracking 与成本可见性，以及完整的「full cost accounting」。
**官方来源**：<https://docs.crewai.com/en/concepts/crews>｜<https://www.crewai.com/>｜<https://docs.crewai.com/v1.15.6/en/observability/portkey>
**优点**：**工具缓存是直接的降本原语**（与 Anthropic prompt caching 同构）；`max_iter` 防止 agent 循环烧钱——「次数型防失控」的实用护栏；企业层提供完整成本记账。
**局限/代价**：**编排层两个限额都不是金额**，没有「这个任务最多花多少钱」的语义，金额上限需在企业层解决；企业层是**商业产品**，开源版不含。
**适用场景**：角色扮演型 Crew 编排 + 已购买企业版的团队。

### 3.7 Agno（`Metrics` 三级层次：Message → Run → Session）

**官方定位与实现机制**：Agno v2 的 `Metrics` 类是本次对比中**成本计量粒度最细**的——① **三级层次**：Message 级（单次 LLM turn 或工具执行的耗时与 token）→ Run 级（`agent.run()` 总量）→ Session 级（`AgentSession.metrics`，DB 持久化的会话累计）。② **Token 字段**：`input_tokens` / `output_tokens` / `total_tokens` / **`reasoning_tokens`**（o1/o3 思维链）/ **`cache_read_tokens`** / **`cache_write_tokens`**（Anthropic 缓存）/ 音频 token。③ **成本字段** `cost`（provider 支持时的估算成本）。④ **多模型细分**：`metrics.details` 按 `model` / `memory_model` / `session_summary_model` / `culture_model` 分别归集——**这正是「每租户每场景每模型成本」所需的粒度**，且把「记忆管理器」「会话摘要管理器」这类**辅助模型消耗与主模型分开**。⑤ Workflow 层还有 `WorkflowMetrics.steps` 与 `workflow.get_session_metrics()`。
**官方来源**：<https://docs.agno.com/sessions/metrics/workflow>｜<https://deepwiki.com/agno-agi/agno-docs/9.5-metrics-reference>
**优点**：**计量层次与业务层次天然对齐**，`cost per session` / `cost per run` 是现成查询；**辅助模型单独归集**——**与本项目「judge 成本物理隔离」同源**（把非主链路消耗分开记），但 Agno 按**模型**归集、本项目按**科目**归集；**缓存 token 单独成列**，为缓存效果分析留了位置。
**局限/代价**：**纯观测，无执行侧控制**（无预留、无结算、无金额闸门）；`cost` 是 provider 支持时的**估算**，Agno 不维护自己的价格表版本化；多模型细分是 `details` 字典（弱类型），不像本项目 `usage_record.model_id` 那样有唯一索引与幂等约束。
**适用场景**：需要细粒度 token 成本可见性的自托管 AgentOS 用户。

### 4.1 架构与数据流

#### 4.1.1 三张账与两个口径

本项目的成本治理由**三张账 + 两个独立限额口径**构成：

**三张账**

| 账 | 表 | 性质 | 幂等键 | 谁写 |
|---|---|---|---|---|
| **总账** | `public.budget_account` | 租户级余额（三段金额） | `UNIQUE (tenant_id, currency)`（DDL `:3523-3527`） | `JdbcBudgetRepository.reserve/settle/release` |
| **预留明细账** | `public.budget_reservation` | 每笔预留的状态机 | `UNIQUE (tenant_id, operation_id) WHERE operation_id IS NOT NULL`（部分唯一索引，DDL `:4627`） | 同上 |
| **计量明细账** | `public.usage_record` | 每次消耗的事实（token + 金额） | `UNIQUE (tenant_id, operation_id) WHERE operation_id IS NOT NULL`（DDL `:4549`） | 同上 + `recordModelUsage` |

**两个独立限额口径**（DDL `:2764-2767` 明写「与租户级 `budget_account` 是两个独立口径：前者约束单棵调用树，后者约束租户总量」）：

1. **租户级**：`budget_account.total_limit`，`numeric(18,6)`，`CHECK (reserved_amount + settled_amount) <= total_limit`（`budget_no_overspend`，DDL `:1524`），注释「数据库层最后防线：即使应用层并发检查有漏，DB 约束也拒绝超发（R-007）」。
2. **Run 级**：`run.budget_amount`（DDL `:2745`），`NULL = 不额外限制；非空时按 budget_reservation.run_id 聚合判定`。**所有深度的工具调用都记在同一个 `run_id` 下**——这就是「全调用树共享上限」的实现基础（`RunBudgetProbe.java:21-24`）。

**第三道口径（新增，梳理报告未提）**：`agent.run.max-cost-per-run`（application.yml:493，初值 2.00）——**单 Run 的模型成本累计上限**，在 `RunExecutionLoop` 里用 `accumulatedCost` 变量逐次累加并在超限时收敛 Run（`RunExecutionLoop.java:922-937`）。注意它与 `run.budget_amount` 的区别：前者只统计**模型调用成本**（`settleModelCost` 返回值），后者统计**全部预留额**（含工具调用当量与委派当量）。**两个口径独立生效，取更严者**（`RunExecutionLoop.java:927-928` 注释）。

#### 4.1.2 三条预留路径

预算闸门在执行链上有**三个插入点**，每个都有独立的预留语义：

```
路径 A：工具调用（ToolInvocationGate）
  ⑥ Run 级量级判定 (RunBudgetProbe.check)      ← 快检，可拒绝
  ⑥ 权威预留 (reserveQuota → BudgetPort.reserve)
  ⑦ 执行
  ⑧ 账本记结果 → settleQuietly / releaseQuietly

路径 B：模型调用（RunExecutionLoop）
  reserveModelCost（估算输入×2 + maxTokens 上界）
  → modelGateway.complete
  → settleModelCost（按模型回传的真实 token × 配置单价）
  失败/超时 → releaseModelCost

路径 C：委派（ToolInvocationGate.reserveDelegationQuota）
  ① Run 级量级判定 → ② 权威预留（与工具调用同一份核心）
  子 Agent 执行 → settleQuietly / releaseQuietly
```

**调用链总览**：

```
RunController.createRun
  └─ JdbcRunCreationRepository（run + run_event + idempotency_record + outbox_event 同事务）
       └─ RunDispatchConsumer → RunExecutor → RunExecutionLoop
            ├─ 上下文装配（维度 6）→ estimatedInput（afterTokens）
            ├─ 路径 B：reserveModelCost → 模型调用 → settleModelCost → accumulatedCost 检查
            └─ 路径 A/C：ToolInvocationGate.invoke
                 Schema 校验 → 重新授权 → 幂等键 → 账本 → 审批 → ⑥ Run 级判定 → ⑥ 预留 → ⑦ 执行 → ⑧ 结算/释放
```

### 4.2 关键设计决策逐条剖析

> 每条格式：**决策 → 为什么 → 代价 → 证据锚点**。合并了机制上同源的决策项（合并关系在标题中标注）。

#### D-1 · 预留是单条原子条件 UPDATE，绝不「先 SELECT 检查再 UPDATE」

**决策**：`JdbcBudgetRepository.tryAtomicReserve`（`:258-275`）用单条语句完成判定与扣减：
```sql
UPDATE budget_account
SET reserved_amount = reserved_amount + ?, updated_at = now()
WHERE tenant_id = ?::uuid AND currency = ?
  AND reserved_amount + settled_amount + ? <= total_limit
```
**为什么**：检查与扣减之间存在 check-then-act 窗口，N 个并发可同时读到余额充足而全部通过判定 → 直接超发。DDL `:1562-1572` 的表注释把这个论证写进了 schema：「（1）应用层单条原子条件 UPDATE（WHERE reserved+settled+? <= total_limit）；（2）budget_no_overspend CHECK 作为最后防线。**二者缺一不可：仅有 CHECK 会出现「随机预算不足」，仅有应用层会在 SQL 写错时失守**」。
**代价**：并发超限时**失败方不等待**（PG 行级 MVCC 下条件更新天然原子），无需排队——类注释明确「加锁只是把『并发拒绝』换成『并发排队』，在 DoS 场景下更糟」。 **证据锚点**：`JdbcBudgetRepository.java:258-275`、`BudgetPort.java:66-92`、DDL `:1524`、`:1562-1572`。
#### D-2 · Run 级上限必须加行锁，租户级不加——两者不矛盾

**决策**：`JdbcBudgetRepository.lockRunBudgetCap`（`:206-217`）对 `run` 行加 `SELECT ... FOR UPDATE`，在锁内重读 `budget_amount`，再在同一事务内聚合 `budget_reservation`、判定、扣减。
**为什么**：租户级上限是**单行**条件更新，判定与扣减天然在同一原子操作内；而 Run 级上限的判定口径是**多行聚合**（`budget_reservation` 按 `run_id` 汇总），多行聚合**没有单条条件 UPDATE 可写**——聚合读到的永远是已提交快照，并发预留会同时读到同一份旧聚合而全部通过判定 → 突破 Run 上限。
**代价**：同一 Run 的预留被**串行化**。类注释给出缓解：「未声明额度 → 不加锁」（`run.budget_amount IS NULL` 表示不额外限制，没有上限就没有可突破的东西），这条快路径避免了「没配预算的 Run 也被行锁串行」的无谓竞争。锁序固定「run 行 → 账户行」，与预留写入的 FK 键共享锁不冲突（无死锁环）。 **证据锚点**：`JdbcBudgetRepository.java:53-61`、`:129-146`、`:182-248`、`RunBudgetAggregate.occupied`。
#### D-3 · 预算账户不存在 ≠ 额度不足（枚举而非 boolean）

**决策**：`BudgetPort.ReserveOutcome` 是六值枚举（`RESERVED` / `REPLAYED` / `INSUFFICIENT` / `RUN_BUDGET_EXHAUSTED` / `NO_ACCOUNT` / `FAIL_CLOSED`），而非 boolean。
**为什么**：`UPDATE` 在「账户不存在」与「额度不足」两种情况下都返回 0 行。若都报 false，运维看到「预算不足」会去加额度，而真实原因是**该租户根本没有开通预算账户**——排查方向完全错误。`RUN_BUDGET_EXHAUSTED` 与 `INSUFFICIENT` 同样必须可区分：前者是「这一棵调用树自己的上限不够」，处置方向是「调小该 Run 的额度声明」；后者是「给租户加额度」。混报会让运维往错误方向排查（给租户加钱后问题依旧）。
**代价**：调用方需穷举枚举值，分支增多。 **证据锚点**：`BudgetPort.java:207-247`、`JdbcBudgetRepository.java:148-159`。
#### D-4 · 预留三律：失败即拒 / 记 FAILED 非 UNKNOWN / UNKNOWN 绝不释放

**决策**：`ToolInvocationGate` 类头的「预算环节的三条规则」（`:40-48`）：
1. **预留失败即拒绝**（fail-closed）。降级放行等于「预算系统故障时无限花钱」——P1-10 记录的 Sev-0 类。
2. **预留失败记 FAILED 而非 UNKNOWN**：工具根本没发出，结果确定是「未执行」。记 UNKNOWN 会凭空造出待对账的幽灵操作。
3. **UNKNOWN 绝不释放预留**：成本可能已发生，只有确定失败（FAILED）才退回额度。

**为什么**：这是本维度「会计学正确性」的核心。三条规则分别对应：*不应发生的必须被阻断*、*账本状态必须反映真实执行状态*、*不确定时必须保守挂账*。
**代价**：第 3 条会让 UNKNOWN 预留长期占用额度，需要对账链路兜底（见 D-8）。 **证据锚点**：`ToolInvocationGate.java:40-48`、`:1399-1420`（预留异常 fail-closed）、`:1447-1462`（UNKNOWN 分支直接 `return result`，**不调用 `releaseQuietly`**）、DDL `:1569-1572`、`:3011-3014`。
#### D-5 · 结算与释放都必须幂等：同事务 + `ON CONFLICT DO NOTHING` + 重复不改账户

**决策**：
- **结算**：`JdbcBudgetRepository.settleInternal`（`:364-419`）在一个事务内做四步：① 锁行读预留（`FOR UPDATE`）② 计量 `INSERT ... ON CONFLICT DO NOTHING RETURNING` ③ 账户 `reserved → settled` 迁移 ④ 预留状态推进 `SETTLED`。
- **释放**：`JdbcBudgetRepository.release`（`:578-627`）先锁行读预留，若已非 `RESERVED` 则**直接返回 false，不改账户**。

**为什么**：
- **幂等（结算侧）**：用 `ON CONFLICT DO NOTHING` 而非「先查后插」（后者是 check-then-act，并发下可插入两行）；命中冲突时**不得**再次累加 `settled_amount`。
- **同事务**：计量插入与账户更新必须同事务，任一失败整体回滚——**半边落地会造成永久账实不符**（预留已扣但计量没写，或计量写了但账户没扣），且重复结算会凭空多计费。
- **锁行读**：只有 `RESERVED` 状态可离开，锁保证并发重复结算/释放被串行化。
- **幂等（释放侧）**：若在已终态时仍退回额度，**额度会被凭空放大**——那比超发更隐蔽，因为它让后续所有预留都能通过（CHECK 依然成立）。

**代价**：结算与释放路径各持有一把 `budget_reservation` 行锁 + 一把 `budget_account` 行锁，高并发下会成为热点。 **证据锚点**：`JdbcBudgetRepository.java:364-419`、`:429-479`、`:538-561`、`:578-593`｜`BudgetPort.java:94-140`、`:168-182`。
#### D-6 · 对账三态处置：终态结算 / 终态释放 / UNKNOWN 只统计

**决策**：`BudgetReconciliationService.reconcileAll`（`:104-176`）的三类处置矩阵：

| 差异 | 处置 |
|---|---|
| 悬挂预留（RESERVED 但操作已终态且成功） | 结算 |
| 悬挂预留（操作已终态且未成功） | 释放 |
| UNKNOWN 预留 | **不处置**，只统计并转人工 |
| 账实不符 | **只报不改** |

**为什么**：
- **UNKNOWN 不处置**：成本可能已发生（R-007）。自动释放 = 白送额度；自动结算 = 凭空多计费。
- **账实不符不自动修正**：自动「修正」账户余额 = 把「钱账不符」变成「看起来钱账相符」，差异被**永久掩盖**，且掩盖的正是「有人手工改过数据」这类线索。正确做法是告警 + 人工介入。
- **`MANUAL_DISPOSED` 按「未确认成功」处理 = 释放额度**（`:111-116` 注释明写「人工处置的结论不一定是副作用已发生」），且「真实成本是否发生由 `usage_record` 独立记录，不依赖预留」——这是**计量账与预留账解耦**的又一个体现。

**代价**：UNKNOWN 与账实不符需要**人工介入**，运维负担真实存在。 **证据锚点**：`BudgetReconciliationService.java:15-38`、`:104-176`、`:187-213`。
#### D-7 · 委派侧的独立对账通道（否则额度泄漏永不可见）

**决策**：`BudgetReconciliationService` 持有可选的 `DelegationBudgetReconciliationService`；未装配时**显式告警**而非静默跳过。
**为什么**：委派的预留记在 `agent_invocation` 里，**没有对应的 `tool_operation` 行**，而工具侧的两条查询（`findOrphaned` / `findUnknownHeld`）用 **INNER JOIN `tool_operation`**，因此**看不见委派侧的预留**。若这里也不计，运维看到的永远是「一切正常」，而实际上额度正被一批看不见的委派预留长期占着。 **证据锚点**：`BudgetReconciliationService.java:50-56`、`:82-95`、`:139-159`、`JdbcBudgetRepository.java:637-679`、`:681-716`。
#### D-8 · 结算用**模型回传的真实 token**，估算只用于**预留上界**

**决策**：预留侧 `estimatedInput × INPUT_TOKEN_ESTIMATE_SAFETY_FACTOR(2)` + `maxTokens` 输出上界（`RunExecutionLoop.java:1604`、`:1667-1668`）；结算侧用 `response.usage().inputTokens()` / `outputTokens()` × `ModelPricing` 的真实单价（`RunExecutionLoop.java:1707-1745`）。
**为什么**：
- **预留必须 ≥ 真实成本**，否则结算会被 DB 的 `CHECK (settled <= reserved)` 拒绝，账就断了。
- **结算必须用真实 token**，因为「预留是上界，结算才是事实」。多预留的部分在结算时自动退回（`moveReservedToSettled` 把 `reserved_amount` 全额扣回、只把 `actual` 计入 `settled_amount`）。
- 输入侧取 2 倍上界的理由被明确记录：「`ContextBudgetTrimmer` 的 token 估算是**粗估**（非真 tokenizer），且**系统提示与工具 Schema 不在消息序列的估算里**」。

**代价**：预留额是真实成本的**上界（可能 2 倍以上）**，在并发密集时**额度被虚占**——账面上「快没钱了」但实际没花那么多。这是保守性与额度效率的取舍。 **证据锚点**：`RunExecutionLoop.java:1594-1604`、`:1650-1704`、`:1707-1745`、`JdbcBudgetRepository.java:537-561`。
#### D-9 · Run 级预算快检是「快检」，权威判定在 reserve 事务内

**决策**：`RunBudgetProbe` 明确声明自己**不是权威**：「本探针是**快检**（读一次聚合），**不是**权威：它与扣减之间存在 check-then-act 窗口，权威判定在 `BudgetPort.reserve` 的同一事务里」。
**为什么**：双重判定（快检 + 权威）能在**不持有 DB 锁**的前提下提前拒绝明显超限的请求（省掉锁等待），同时权威性由原子操作保证。**快检拒绝时不动额度**（`JdbcBudgetRepository.java:140-141`：「Run 级与租户级是两道独立闸门，这里过不去就不该动租户额度（否则会出现『钱被占了但没干活』）」）。
**关键设计**：`RunBudgetProbe.check` 的三态语义——**未声明额度 → 放行**（不是「额度为 0」！）；**剩余额度 ≥ 本次预留额 → 放行**；**剩余额度 < 本次预留额 → 拒绝**；**读不到 → fail-closed**（`Denial.READ_FAILED`）。**必须按「量」判**：只判「还有没有余额」时，剩余 10 元的 Run 仍能预留 50 元——单次调用即突破上限，共享上限名存实亡。 **证据锚点**：`RunBudgetProbe.java:25-41`、`:102-133`、`BudgetPort.java:71-84`、`JdbcBudgetRepository.java:129-146`。
#### D-10 · `budget_account` 的维度只有 (tenant_id, currency)——**无法按 Agent/场景分账**

**决策**：`budget_account` 的唯一约束是 `UNIQUE (tenant_id, currency)`（DDL `:3523-3527`），即**一个租户只有一个币种账户**。
**为什么（设计意图）**：预留-结算的原子性依赖**单行条件 UPDATE**（D-1）。若账户按 Agent 拆分，同一次 Run 的工具调用可能落在不同 Agent 的账户上，「单 Run 上限」的原子判定就失去了单行基础。
**代价（本项目最真实的成本归属缺口）**：
- **无法回答「每租户每场景成本」**——场景维度在 `agent_trace_metric` 与 `mv_agent_metric_hourly` 里有，但那是**事后指标**；`budget_account` 里没有场景维度，**无法为某个场景单独设预算、无法按场景分账**。
- 计量明细 `usage_record` 有 `tenant_id / run_id / step_id / operation_id / model_id / reservation_id`，可**事后**按模型/工具聚合，但**无法事前按场景封顶**。 **证据锚点**：DDL `:3515-3527`、`JdbcBudgetRepository.java:260-267`（`WHERE tenant_id = ? AND currency = ?`）。
#### D-11 · 限流只有速率维度；**并发 Run 上限与 `tenant_quota.budget_limit` 均未接入执行链**

**现状（三件事，都已复核）**：
1. `agent.rate-limit.limit-per-window`（30）+ `window-seconds`（60）+ `sliding-window` 开关（默认 false），由 `RateLimitPolicy` / `JdbcRateLimiter` 实现，**按租户的 API 请求限流**；治理台另有独立的 query / decide 两桶限额（`RateLimitPolicy.governanceLimitFor`，默认 120 / 30，与全局桶**刻意分开**——全局桶服务「单个学生的个人动作」，治理桶服务「一个租户的多个运维共享」，用同一阈值会让运维之间互相限流）。
2. `agent.tenant.max-concurrent-runs`（初值 5）**在运行期没有任何引用**。项目自己的 `ConfigReadService` 已诚实标注：「**⛔ 实测：常量 KEY_MAX_CONCURRENT_RUNS 定义外引用数 0 → 租户并发**无限制**」」（`ConfigReadService.java:138-139`）。
3. `platform.tenant_quota` 表有 `agent_limit / run_concurrency_limit / budget_limit`（DDL `:1280-1286`），`JdbcPlatformTenantRepository` 提供读写（`:104-114`、`:238-257`），`PlatformTenantController` 暴露 `QuotaSummary`（`:107`、`:223`）；但全仓检索 `budget_limit` / `budgetLimit` 的引用**只出现在 platform 域的 CRUD 与 API 展示层**，`agent-worker`、`agent-application`、`JdbcBudgetRepository` 中**均无引用**——**没有任何执行路径读取它**。

**为什么重要**：并发 Run 数直接决定**同时占用的额度**与**同时消耗的 token**。没有并发上限，一个租户可并发开 100 个 Run，每个 Run 各自判定「剩余额度充足」，在预留原子性之外**放大总额外暴露**——这正是 T6 中「速率维度 ≠ 并发维度」的现实案例。同理，管理员在控制台设置「该租户预算上限 ¥100」会以为生效，实际**完全不生效**——真正生效的是 `budget_account.total_limit`。
**根因**：第 2、3 点是**能力缺口**而非设计取舍——表结构与 API 都做了，接线没做完。`ConfigReadService` 对 `max-concurrent-runs` 有诚实标注，说明项目**知道**这件事（至少对并发上限知道），但对 `budget_limit` 的未接线**没有**同等标注。 **证据锚点**：`application.yml:130-152`、`:506-508`、`RateLimitPolicy.java:14-104`、`JdbcRateLimiter.java`、`ConfigReadService.java:138-139`、DDL `:1280-1286`、`JdbcPlatformTenantRepository.java:104-114`、`:238-257`。
#### D-12 · 「查不到单价」≠「免费」：token 如实记、成本按 0 记、并 WARN

**决策**：`ModelPricingPolicy.pricingOf` 查不到时返回 `Optional.empty()`（**不返回 0 元**）；`RunExecutionLoop.reserveModelCost` 在查不到价时**不预留**（金额 0 的预留会被 DB 拒绝）但**继续执行**并 WARN；结算时走 `recordModelUsage` 路径——**只计量不扣款**（token 是事实必须记，金额按 0 记）。
**为什么**：否则「漏配单价」会静默变成「这次调用不存在」，账实从此对不上且无人察觉。`BudgetPort.recordModelUsage` 的契约注释把这套逻辑写得很清楚。
**代价**：**成本报表会低估**（漏配的模型成本记 0），且低估**不体现在任何数字上**——只能靠 WARN 日志发现。`WorkerExecutionConfig.modelPricingPolicy`（`:832-864`）只 WARN 不拒绝启动（刻意取舍：「单价表缺失只是『成本不可计量』，不是『安全门禁缺失』……让平台因为『没配价』而拒绝启动，是拿可用性换一个可观测性缺口，不划算」）。 **证据锚点**：`ModelPricingPolicy.java:33-37`、`RunExecutionLoop.java:1659-1663`、`BudgetPort.java:142-166`、`WorkerExecutionConfig.java:825-864`。
#### D-13 · 单价表：精确匹配 → 最长前缀匹配 → 显式 default 兜底；但无版本化

**决策**：`ModelPricingPolicy.pricingOf`（`:123-149`）三级匹配：精确 → **最长前缀匹配** → `default` 兜底键。`default` **只在运维明确配置后生效**，缺省即「查不到单价」。
**为什么**：模型标识常带日期/版本后缀（`gpt-4o-2024-08-06`），只做精确匹配会让「配了价却用不上」——**配了却用不上比没配更危险**（运维以为配好了，实际在按 0 记账）。
**代价与缺口**：**没有生效日期、没有版本、没有历史回溯**。配置里 6 个条目（`gpt-4o` / `gpt-4o-mini` / `qwen-max` / `qwen-plus` / `deepseek-chat` / `MiniMax-M2.5`）是**占位价**，注释明确标注「上线前必须按供应商最新报价替换：错价会让成本报表失真（比『不记成本』更危险，因为它看起来是真的）」。价格一旦调整，**历史 `usage_record.cost_amount` 不会重算** → 趋势图失真。见改进点 2。 **证据锚点**：`ModelPricingPolicy.java:42-166`、`application.yml:515-548`。
#### D-14 · judge 成本物理隔离到独立科目（铁律 8）

**决策**：`EvaluationCostBudget` 用科目名 `EVAL_JUDGE_COST` 在**进程内**独立记账，**不写 `usage_record`、不调 `AgentMetricPort.upsert`、不碰 `cost_amount`**。
**为什么（业界对照）**：judge 是平台评估开销，不是业务开销。混进去会让「单 Run 成本」「按模型成本」全部偏高，**且评估越勤偏得越多**——偏差与评估频率正相关，是个系统性偏差而非噪声。
**证据链**：
- `EvaluationCostBudget.java:15-40`（类注释「⚠️⚠️ **绝不混入业务成本**」）
- `ModelAttributionJudge.java:36-39`（「成本物理隔离……**不**写 `usage_record` / `cost_amount` / 业务指标端口」）｜`AttributionJudge.java:14`（接口级声明）
- **守卫测试**：`L2ProductionGuardTest.judgeCostIsPhysicallyIsolatedFromBusinessCost`（`platform-bootstrap/src/test/.../L2ProductionGuardTest.java:138-160`）断言 judge 源码中不出现 `cost_amount` / `usage_record`
- **IT 级断言**：`L2AttributionClosedLoopIT.java:209`（断言「judge 成本走独立评估科目，绝不写业务 usage_record」）

**judge 自身的会计纪律**（与业务侧同源）：① **无单价即拒绝调用**（`ModelAttributionJudge.java:121-127`，「不是『免费』，而是『不许花不知道多少钱的钱』」）；② **按最坏上限预留**（`:130-139`，保守按「system + user 每字符 1 token」估输入上界 + `maxTokens` 输出上界，「预留偏大只会保守拒绝，不会低估成本」）；③ **按真实 token 结算**（`:146-149`，即使 JSON 解析失败也**如实记账**）；④ **失败释放预留**（`:162-169`，异常时降级为「待人工」而非把异常当成 false）。
**已知边界**：`EvaluationCostBudget` 是**单进程预算**，多实例部署时总量上限 = 实例数 × `dailyLimit`（类注释自陈）。这与 Anthropic SDK `max_budget_usd` 是同类局限。

#### D-15 · 工具调用按「调用当量」计费 —— 半修状态

**决策**：`ToolInvocationGate.settleQuietly`（`:1633-1653`）按 `reserveAmountPerToolCall`（配置 `agent.budget.reserve-per-tool-call`，初值 ¥0.50）**全额结算**，并把 `model_id` 写成 `"tool:" + 工具名`。
**为什么加前缀**：`usage_record` 里现在有两类行——工具调用行与模型调用行。两类的 `model_id` 语义完全不同：模型行是真实模型标识，工具行**本来就没有模型**。此前工具行直接把工具名写进 `model_id`，于是「按模型聚合成本」会把工具名当成模型名——报表失真（`BudgetPort.java:43-53`）。
**为什么用固定当量**：工具调用没有 token 概念，且**不采信工具自报预留额**——「工具自报预留额等于『让被约束方申报约束额度』，一个有 bug 或恶意的工具可以声明『我只要 0.01 元』，而它实际触发的是按 token 计费的模型调用」（`BudgetPolicy.java:15-20`）。
**遗留缺口**：① **委派按「一次调用当量」计费，但其真实成本（子 Agent 的多轮模型调用）更高**——`ToolInvocationGate.reserveDelegationQuota` 注释明说：「本口径是**保守下界**，不是精确计价。⚠️ **模型调用本身仍未计入 Run 额度** —— 那需要冻结成本模型（token 计价），属未闭环范围 → 已登记为缺口」；② 工具调用**不产生 token**，因此「工具成本」永远无法与「工具引发的模型成本」区分——**若一个工具内部会调 LLM，这部分成本当前完全不可见**。

#### D-16 · 「预算预留额」是保守常量而非按实际预估

**决策**：`BudgetPolicy.requireReserveAmount`（`:51-71`）解析配置，缺失/非数值/非正数一律 `IllegalArgumentException`，**禁止退回默认值放行**。`DEFAULT_RESERVE_AMOUNT = 0.50` 仅用于生成配置模板与文档标注，**不参与运行时兜底**。`ToolInvocationGate` 构造期也校验（`:524-529`）：「缺失/非法配置在装配时就失败，而不是等到某个工具调用时才被拒——后者会让『预算闸门形同虚设』在测试中不易察觉」。
**为什么**：与 `WorkerPolicy` / `RateLimitPolicy` 同一取舍——「退回默认值等于『悄悄用了一个没人审过的限额』」。
**代价**：所有工具一视同仁 ¥0.50，与真实成本无关。昂贵工具与廉价工具的额度占用相同。

#### D-17 · 成本指标是「事实表的确定函数」，写 `agent_trace_metric` 用幂等 upsert

**决策**：`AgentMetricCollector` 把 `usage_record` 的聚合（`JdbcTraceFactRepository.readUsage`）写进 `platform.agent_trace_metric`，写入用 `INSERT ... ON CONFLICT (trace_id) DO UPDATE`（`JdbcAgentMetricRepository.java:91-125`）。
**为什么**：指标可重算、幂等；小时桶 `mv_agent_metric_hourly` 供 Grafana 直读，刷新期间响应体必须带 `refreshed_at`（**不假装实时**）。
**已解决的一个真实 bug**：`readUsage` 聚合时用 `min(model_id) FILTER (WHERE model_id NOT LIKE 'tool:%')` 排除工具行——「直接用 `min(model_id)` 会把工具名混进『按模型分组』，报表失真」。
**遗留缺口**：① **`usage_record.step_id` 列存在但无写入方**——「步骤」级成本归属不可用；② **`mv_agent_metric_hourly` 的 GROUP BY 是 (hour, tenant_id, agent_id, agent_version, scenario)**——**没有 model_id 维度**，按模型拆成本只能查明细表；③ **没有「cost per successful task」的任何计算**（见改进点 3）。

#### D-18 · 单 Run 成本上限：`max-cost-per-run` 触顶即失败（硬失败，不降级）

**决策**：`RunExecutionLoop.java:922-937`：模型调用结算后累加 `accumulatedCost`，超过 `snapshot.maxCostPerRun()` 即写 `RUN_FAILED` 事件 + `errorCode=MAX_COST` + 收敛 Run 为 FAILED。
**为什么不是降级**：与维度 13 的「治理期发布、运行期钉死」语义一致——`cap_agent_def.model_ref` 在发布期固化，运行期只读快照（`forbid_published_def_mutation` 禁止改写），**架构上排除了「按成本动态换模型」**。
**历史诚实标注**：`RunExecutionLoop.java:619` 注释自陈「`maxCostPerRun`（DEC-9，默认 ¥2.00）此前只进快照、只用于配置展示」，`ConfigReadService.java:126-133` 记录了 P4-D11 修复前「生产快照是硬编码的（成本上限 10.00 / 步数 20 / 调用 8），yml 的 `max-cost-per-run=2.00` **无任何生产读取点**——声明比真实敞口紧 5 倍，运维读到的数字是假的」。
**代价**：**硬失败直接终止用户任务**，质量与成本之间没有缓冲带。

### 4.4 我们独有的设计（差异化设计）

| # | 差异化设计 | 对比中不常见的原因 | 价值 |
|---|---|---|---|
| **1** | **DB CHECK 作为「最后防线」的显式双保险设计** | 竞品的硬上限（OpenAI）自己承认会小幅超支；没有任何竞品在**自己的账本表**上放一个「应用层写错也失守不了」的 CHECK | 把「不超发」从应用层纪律变成**数据层不变量** |
| **2** | **UNKNOWN 预留永不自动释放 + 双向反查对账通道** | 支付域的授权会过期释放；多数 agent 框架没有 UNKNOWN 概念，因此也不存在这个问题 | 账实相符可对账；避免「白送额度」与「凭空多计费」两个方向的错 |
| **3** | **判定原因用六值枚举而非 boolean** | 多数实现只有「够/不够」 | 运维排查方向不跑偏（加额度 vs 调小 Run 额度 vs 开账户） |
| **4** | **结算用真实 token、估算只用于预留上界** | 常见错误是「估算值直接入账」 | 报表数字有事实基础；估算误差被限制在**预留侧**（可自动退回） |
| **5** | **judge 成本物理隔离到独立科目 + 守卫测试** | 主流做法是同账打 tag | 「单 Run 成本」不被评估频率污染；偏差方向单一可解释 |
| **6** | **账本 ↔ 预留双向可追溯**（`usage_record.reservation_id`） | 竞品通常只有单向的 usage 日志 | 可回答「这笔成本对应哪次预留、这次预留最终结算了多少」 |
| **7** | **工具行 `tool:` 前缀** | 竞品要么只有模型 token，要么只有工具计数 | 「按模型聚合成本」不会被工具名污染 |
| **8** | **三层独立限额**（租户总额 / Run 级调用树 / 单 Run 模型成本） | 竞品通常只有会话级单值熔断 | 覆盖「一个租户总共能花多少」「这一棵树最多花多少」「这次任务最多花多少」三种不同粒度的诉求 |
| **9** | **查不到单价时「不预留但如实计量 + WARN」** | 常见做法是静默按 0 或直接失败 | 「不知道价格」与「这次免费」在账上可区分 |
| **10** | **预留异常 / 预算系统故障一律 fail-closed 拒绝执行** | 多数实现会降级放行 | 「预算系统故障时无限花钱」被封堵 |

### 5.2 优势详解（为什么领先，要讲清机制）

**优势 A · 「硬不超发」是数据层不变量，不是应用层纪律**

这是本维度最实质的领先，三层机制缺一不可：

```
第 1 层：应用层单条原子条件 UPDATE（D-1）→ 并发下判定与扣减不分离，check-then-act 窗口消失
第 2 层：DB CHECK budget_no_overspend（D-1 最后防线）→ 应用层 SQL 写错时「报错」而非「超发」
第 3 层：Run 行锁 + 同事务聚合判定（D-2）→ 多行聚合口径下的 Run 级上限不被并发穿透
```

**为什么竞品做不到第 2 层**：OpenAI 的 hard spend limit 是**供应商侧**的——它维护自己的计量管道，计量是异步的，官方文档明确「recorded spending can slightly exceed the configured amount」。我们把「不超发」放在**自己账本的表上**，是同步的、原子的、数据库拒绝的。

**为什么第 3 层关键且不平凡**：Run 级上限的判定口径是**多行聚合**，而多行聚合**在 PG 的 MVCC 下没有单条条件 UPDATE 可写**——聚合读到的永远是已提交快照。实现者必须显式加锁，否则并发预留会同时读到同一份旧聚合而全部通过判定。这不是「加个 if」能解决的。

**优势 B · UNKNOWN 的会计学正确性是完整的、闭环的**

不是一句「UNKNOWN 不释放」的规则，而是一条**从产生到收敛的完整链路**：

```
产生：工具超时/未预期异常 → 保守记 UNKNOWN → 预留保持 RESERVED（D-4）
  ↓ 识别：findUnknownHeld（工具侧 INNER JOIN tool_operation 找 state='UNKNOWN'）
  ↓      DelegationBudgetReconciliationService（委派侧，无 tool_operation 行）
  ↓ 收敛：ToolOperationReconciliationService → RECONCILED_SUCCEEDED / RECONCILED_ABSENT
  ↓ 处置：BudgetReconciliationService.disposeAfterReconciliation
  ↓      ├─ RECONCILED_SUCCEEDED → settle（结算）  └─ RECONCILED_ABSENT → release（释放）
  ↓ 兜底：对账通道未装配 → 显式告警（D-9），绝不静默跳过
```

**两条反查通道的必要性**：委派的预留记在 `agent_invocation` 而非 `tool_operation`，工具侧的 INNER JOIN 查询**看不见它们**。若只做工具侧，运维看到的是「一切正常」而额度正被一批不可见的委派预留长期占着。这个「不可见额度」的洞察是本项目独有的。

**优势 C · 判定原因的六值枚举让运维排查不跑偏**

`ReserveOutcome` 的六值划分（`BudgetPort.java:207-247`）对应**三种完全不同的处置方向**：`NO_ACCOUNT`（未开通账户 → **开通账户**，不是加额度）、`INSUFFICIENT`（余额不足 → **给租户加额度**）、`RUN_BUDGET_EXHAUSTED`（调用树上限不够 → **调小该 Run 的额度声明**）、`FAIL_CLOSED`（金额非法 → 修调用方/配置）、`READ_FAILED`（预算系统故障 → **查预算服务**，不是加额度）。若合并为 boolean，「给租户加钱后问题依旧」会成为常态。

**优势 D · 结算用真实 token、估算只用于预留上界——本项目最易被误解但实际最正确的一处设计**

直觉上「用估算值统一处理」更简单，但那样**成本报表的每个数字都是估算值**，误差不可知、不可控。本项目的做法：
- **预留侧**用估算（估错了最多导致预留不足 → 被 DB CHECK 拒绝 → fail-closed 拒绝执行，**不会产生错账**）；
- **结算侧**用模型回传的真实 token（报表数字有事实基础）。

这是**把不确定性封装在「可自动回退」的一侧**的经典工程手法。

**优势 E · judge 成本物理隔离 + 守卫测试**

这不是「设计得好」，是**有测试钉死的**：`L2ProductionGuardTest.judgeCostIsPhysicallyIsolatedFromBusinessCost` 直接读源码断言 judge 类里不出现 `cost_amount` / `usage_record`，**后人无法轻易破坏这条边界**（会红）。按铁律 6 的「守卫必问『撤掉修复点会红吗』」——撤掉这个守卫类，测试会红。✓

### 5.3 劣势与盲区详解（明确承认，含根因分析）

**劣势 1 · 成本归属粒度不够——无法回答「每租户每场景成本」**

- **现状**：`usage_record` 有 `tenant_id / run_id / step_id / operation_id / model_id / reservation_id`，其中 `step_id` **无写入方**（死列）；账户 `budget_account` 维度只有 `(tenant_id, currency)`。
- **后果**：① **无法事前按场景封顶**——场景只存在于 `agent_trace_metric`（事后指标），预算侧完全没有；② **无法为某场景单独设预算**——`tenant_quota.budget_limit` 有列但**未接入闸门**（D-11）；③ 「每租户每场景成本」只能事后从 `mv_agent_metric_hourly` 按 `(tenant_id, scenario)` 聚合，且因该视图 GROUP BY **不含 model_id**，按模型拆成本必须查明细表。
- **根因分析**：**这是设计取舍导致的代价，不是能力缺失**。预留-结算的原子性依赖「单行条件 UPDATE」，账户按场景/Agent 拆分会让一次 Run 的多步调用落在不同账户上，破坏 D-2 的锁序与原子性。正确路径不是「给账户加维度」，而是**引入「预算池（budget pool）」抽象**：账户仍是单行原子对象，多维度共享同一个池，池分配是另一套机制。

**劣势 2 · 单价表无版本化、无生效日期、无历史回溯**

- **现状**：`agent.pricing.models` 是纯配置映射（`application.yml:515-548`），`ModelPricingPolicy` **不可变**（装配期构造，运行期只读）。
- **后果**：① 价格调整后**历史 `usage_record.cost_amount` 不重算** → 历史与当前口径不一致 → 同比/环比失真；② `usage_record` **不记录当时用的哪个价**（只有 `model_id`，无 `pricing_version`）；③ 配置里 6 个条目是**占位价**，注释自陈「错价会让成本报表失真（比『不记成本』更危险，因为它看起来是真的）」。
- **根因分析**：**能力缺失**。价格是**有生效日期的一等数据**，不是配置项。当作配置项处理改起来简单，但代价是历史不可回溯。

**劣势 3 · 并发 Run 上限未生效 + 限流只按请求数（无 token 维度）**

- **现状**：`agent.tenant.max-concurrent-runs` 定义在 `PlatformConfig.KEY_MAX_CONCURRENT_RUNS`（`:48`）但**定义外引用数为 0**，`ConfigReadService.java:138-139` 已诚实标注「租户并发**无限制**」；限流只有 `limit-per-window` / `window-seconds`（请求数），**无 TPM/并发维度**。
- **后果**：① 单租户可并发开无限 Run → **额度被大量预留同时占满**（总额不超，但可用额度被瞬间吃光，其他 Run 全部 `INSUFFICIENT`）；② 「这一秒烧了多少 token」无法被限流直接约束——一个 Run 可单次调用 16000 token（`agent.worker.context-token-budget`），30 次/分钟的请求限流**完全拦不住**。
- **根因分析**：**能力缺失 + 已知未做**。项目对缺口是知情的（`ConfigReadService` 有标注），只是没排期。

**劣势 4 · 成本异常检测只有「单条 Trace 超大 token」一条规则**

- **现状**：`ReviewAlertService` 规则集为 BEH-4（循环）/ COST-4（超大 token > 20000）/ MAX_ROUNDS / SAFETY_BLOCK 共 4 条，**全部是「单条 Trace 自身可确定判定」**的。类注释明确：「比例类（错误率 > 10%、单工具失败率 > 20%）需要**分母**，而单条 Trace 的样本量不足以下结论——留给 §7.2 的分层抽样」。
- **缺失**：① **单任务成本突增**（与历史基线比）——无；② **重试风暴导致的成本放大**——`retry_count` 存在，但与 `cost_amount` 之间**无比值口径**（T4 明确要求的能力）；③ **告警出口**——`ReviewAlertService` 产出的是**人工审查任务**不是告警（无 Prometheus alert rules，项目记忆已记为缺口）。
- **根因分析**：**能力缺失**，但方向正确（坚持「不猜基线」）。缺口在「分层抽样 + 基线」那一侧尚未接线。

**劣势 5 · 成本超限只能硬失败，没有降级路径**

- **现状**：`max-cost-per-run` 触顶 → Run 收敛为 FAILED（`RunExecutionLoop.java:922-937`）。
- **根因分析**：**这是与维度 13 的架构一致性带来的取舍**，不是疏忽。`cap_agent_def.model_ref` 在治理期发布时固化，运行期只读快照（`forbid_published_def_mutation`），架构上排除了运行期动态换模型。若要加降级，需引入「模型候选集 + 成本感知的路由策略」，并处理「降级后的质量是否可接受」——这是维度 7（护栏）与维度 10（评测）的联合问题，不能只改预算模块。
- **代价量化**：一个本来能靠便宜模型完成的任务被硬失败直接终止——**平台省钱、用户受苦，没有中间带**。

**劣势 6 · 工具调用成本仍是固定当量，且「工具引发的模型成本」完全不可见**

- **现状**：工具结算按 ¥0.50 固定当量（`settleQuietly`）；委派按「一次调用当量」计费，而其真实成本（子 Agent 多轮模型调用）**更高**——代码注释自陈是「保守下界，不是精确计价」。
- **后果**：① 工具密集型 Run 成本被**低估**；② 若工具内部调用 LLM，这部分成本**完全不进账**。
- **根因分析**：**未闭环的既有缺口**（注释明确写「属未闭环范围 → 已登记为缺口」）。修法涉及「工具侧成本归集协议」（工具需回报其引发的下游消耗），是维度 5 与维度 9 的联合设计。

**劣势 7 · `cost per successful task` 这个最重要的单位经济学指标没有被计算**

- **现状**：`mv_agent_metric_hourly` 同时提供 `trace_count`、`succeeded_count`、`sum(cost_amount)`，**数据基础完全具备**，但全仓**没有任何一处计算 cost per successful task**。
- **后果**：FinOps 视角下最核心的数字——「我们每成功完成一个任务花多少钱」——**不存在**；「成本优化」因此没有可对比的目标值（不知道从 0.80 元/任务优化到 0.65 元算不算有进展）。
- **根因分析**：**能力缺失**，且是最容易补的一个（数据都在）。

**劣势 8 · judge 预算是单进程的，多实例部署下总量 = 实例数 × 日限额**

- **现状**：`EvaluationCostBudget` 用 `ConcurrentHashMap<LocalDate, Day>` 进程内记账，类注释自陈「当前是单进程预算……骨架阶段如实标注这个边界，不假装『全局封顶』」。
- **对比**：Anthropic SDK 的 `max_budget_usd` 是**同一类局限**（会话级、进程内）。
- **根因分析**：**设计取舍**（骨架阶段不引入 Redis 依赖）。诚实标注是加分项。

### 5.4 关键分歧点（最本质的架构分歧）

#### 分歧点 1 · 「不超发」应该是数据库不变量，还是应用层策略？
- **我们的选择**：**数据库不变量**——`budget_no_overspend` CHECK + `enforce_reservation_state_transition` 触发器是不可绕过的边界。
- **竞品的选择**：**供应商侧/平台侧的软硬混合**——OpenAI 的 hard spend limit 是异步计量 + 请求级 429（官方承认会小幅超支）；LangSmith 限的是 trace 数不是金额；Vertex AI 限的是速率与并发配额。
- **后果**：我们获得**「结构上不可能超发」**的强保证，代价是**必须在写入方严格设计数据模型**（单行账户、锁序、幂等键），且**跨维度预算分摊无法通过加列实现**（必须走「预算池」抽象）。竞品更灵活，但**留了一个「可能超支」的口子**，且口子大小不可控。

#### 分歧点 2 · 不确定状态的账务处置：释放（回血）还是挂账（保守）？
- **我们的选择**：**挂账**——UNKNOWN 预留保持 RESERVED，等对账收敛。
- **竞品的选择**：**不存在这个问题**——多数框架没有「操作已发出但结果未知」的持久化语义（AutoGen/CrewAI/OpenAI Agents SDK 都是内存态或简单重试）。
- **后果**：我们获得**账实相符**，代价是**额度可能被长期占用**且需人工对账。这条取舍与维度 3 的 UNKNOWN 语义**完全同源**，但暴露一个必须补的缺口：**对账链路必须真的在跑**（否则挂账变成额度泄漏）。当前对账有实现（`BudgetReconciliationService`）但**没有定时调度证据**——需在改进点 4/5 中一并处理。

#### 分歧点 3 · 成本的计量与治理应该在哪一层？
- **我们的选择**：**执行链内部**（闸门里预留、执行后结算），而非「旁路观测 + 事后分析」。
- **竞品的选择**：**全部旁路**——LangSmith / Agno / Vertex AI / OpenAI 的成本能力都在**观测侧或供应商侧**，不参与执行决策；唯一接近执行侧的是 Anthropic SDK 的 `max_budget_usd`（会话级进程内熔断）与 LangSmith Gateway（网关层）。
- **后果**：我们获得**「不能超」的结构性保证**，代价是**执行路径变长**（每次工具调用多一次预留 + 一次结算的 DB 往返）、**额度效率下降**（预留是上界，可能 2 倍虚占）、**故障模式增加**（预算服务故障 = 全部工具调用被拒，这正是 fail-closed 的代价）。竞品旁路方案零侵入零故障耦合，但**对成本失控无能为力**。

## 六、优缺点总评

### 6.1 我们的优点（分级）

> 本节是对第五章的**分级归纳**，不重复论证（机制见 §5.2，根因见 §5.3）。

**结构性优势（架构层面带来的、竞品难以快速复制的）**
1. **DB 层强不超发**：CHECK + 原子条件 UPDATE + Run 行锁三层，数据层不变量（D-1 / D-2）。
2. **UNKNOWN 不释放 + 双向对账闭环**：账实相符的完整会计学处置（D-4 / D-8 / D-9）。
3. **三层独立限额**（租户总额 / 调用树 / 单任务模型成本）（D-10 / D-20）。
4. **预留-结算范式完整**：三段式、幂等、终态不可回退（D-3 / D-5）。
5. **judge 成本物理隔离 + 守卫测试**：科目分离有测试钉死（D-15）。

**工程性优势（工程打磨带来的）**
6. **判定原因六值枚举**，运维排查不跑偏（D-3）。
7. **结算用真实 token、估算只用于预留上界**，不确定性封装在可回退的一侧（D-7）。
8. **`tool:` 前缀 + 聚合 FILTER**，按模型聚合成本不被污染（D-16 / D-19）。
9. **fail-closed 贯穿**：预留异常、预算读不到、金额非法一律拒绝执行（D-4 / D-18）。
10. **配置 fail-closed 纪律**：`BudgetPolicy` / `RateLimitPolicy` / `WorkerPolicy` 缺失即拒启（D-17）。
11. **账实一致性自检** `isConsistent`，且**只报不改**（D-8）。

**领域性优势（教育/多租户场景带来的）**
12. **场景维度的成本归属基础**：`agent_trace_metric.scenario` 由 `input_payload.scenario` 规范化而来（铁律 9），是「每租户每场景成本」的唯一可信分组键。
13. **费用口径适配国内供应商**：`per-1k` 计价 + MiniMax 等国产模型定价 + CNY 单一结算币种（`application.yml:515-548`）。
14. **L3 ConsoleChat 独立预算协议**：`ConsoleBudgetAdapter` 是 L3 预算保护唯一组合根，关闭态构造级 passthrough、开启态 fail-closed——两套预算语义各自清晰不互相污染（`ConsoleBudgetAdapter.java:30-60`）。

### 6.2 我们的缺点（分级）

**设计取舍导致的代价（值得付的代价，但要知道它的账单）**
1. **预留是上界 → 额度效率损失**（输入侧 2 倍安全系数 + 输出侧 maxTokens 上界）：并发密集时账面余额虚高，出现「看起来没钱其实有钱」。
2. **单行账户 → 无法按场景/Agent 分账**（破坏原子性是硬约束）：代价比想象的大。
3. **UNKNOWN 挂账 → 需要持续的对账运维**：对账不跑就变成额度泄漏。
4. **闸门内预留 → 执行路径变长 + 新故障模式**：预算服务故障 = 工具全拒。
5. **硬失败而非降级 → 用户体验受损**（与维度 13 的模型固化语义绑定）：用户任务被直接终结。

**能力缺口（纯粹的「没做」）**
6. **真实 tokenizer 未接入**：上下文侧仍是 CJK1/非CJK3 启发式（自陈误差 30-50%）。
7. **单价表无版本化/生效日期/历史回溯**：价格调整后历史成本漂移。
8. **并发 Run 上限未生效**（`ConfigReadService.java:138-139` 已诚实标注）。
9. **限流无 token 维度（TPM）**：只有请求数限流，烧 token 拦不住。
10. **`tenant_quota.budget_limit` 未接线**：管理台设了不生效。
11. **成本异常检测只有 1 条规则**：无成本突增、无重试风暴放大、无 Prometheus 告警。
12. **`cost per successful task` 未计算**：数据具备但无口径。
13. **`usage_record.step_id` 是死列**：步骤级成本归属不可用。
14. **`mv_agent_metric_hourly` 无 model_id 分组**：按模型拆成本需查明细表。
15. **对账无定时调度证据**：UNKNOWN 挂账可能长期不收敛。

**运维负担**
16. **对账 + 人工处置流程**：UNKNOWN / MANUAL_DISPOSED 需要人介入。
17. **价格维护是手工的**：注释明说「上线前必须按供应商最新报价替换……**没有第二处真相源**」——没有第二处真相源本身就是风险。
18. **限流的固定窗口边界**：窗口边界处实际放行量可达 2×limit（注释自陈）。

### 6.3 每个竞品的优点（简明，带来源）

- **OpenAI**：速率限制覆盖 **TPM/token 维度**且响应头回传剩余量；spend limit 明确区分「软告警」与「硬 429」两档语义；官方**诚实披露**执行非瞬时、可能小幅超支；按组织/项目两级分账。（<https://developers.openai.com/api/docs/guides/rate-limits>、<https://help.openai.com/en/articles/9186755-managing-projects-in-the-api-platform>）
- **Anthropic**：速率限制把 **ITPM / OTPM 分开**（输出更贵，分开限流更精确）；**prompt caching 命中价 0.1×** 是量级级降本杠杆；`cache_creation_input_tokens` / `cache_read_input_tokens` 让降本手段**本身可观测**；SDK `max_budget_usd` / `max_turns` 提供简单直接的会话熔断。（<https://platform.claude.com/docs/en/build-with-claude/prompt-caching>、<https://docs.anthropic.com/en/api/agent-sdk>）
- **LangSmith**：**LSU 加性成本单位**把异构消耗统一到一个可配额可分账的单位；trace 级成本归因天然对齐「一次任务」；**官方诚实标注**多 workspace 下 spend limit 是近似、org 级才绝对；LLM Gateway 提供成本控制 + 限流 + 模型降级三件套。（<https://docs.langchain.com/langsmith/billing>、<https://www.langchain.com/pricing>）
- **Vertex AI Agent Engine**：配额维度**贴近真实成本结构**（`session_event_append_requests`、`reasoning_engine_service_concurrent_query_requests`）；提供**峰荷估算公式**（U×X×Y + 50% 缓冲）可操作；与 Cloud Billing 天然打通。（<https://cloud.google.com/gemini-enterprise-agent-platform/resources/agent-quotas>）
- **AutoGen（归档）**：架构简单不自造计费半成品。（<https://microsoft.github.io/autogen/stable/>）
- **CrewAI**：`max_rpm` + `max_iter` 双限额简单有效；工具 `cache=True` 直接省真实调用与真实成本；企业层 full cost accounting。（<https://docs.crewai.com/en/concepts/crews>）
- **Agno**：**Message → Run → Session 三级计量层次**与业务层次天然对齐；**辅助模型单独归集**（`memory_model` / `session_summary_model` / `culture_model`）——与本项目「judge 成本分离」同源但按模型而非按科目；缓存 token 单独成列。（<https://docs.agno.com/sessions/metrics/workflow>）

### 6.4 每个竞品的缺点（简明，带来源）

- **OpenAI**：**无预留-结算**，执行后才知道花多少；官方承认硬上限也会超支；支出上限是月度聚合事后口径，无调用树级约束；Agents SDK 无预算原语。（同上门户）
- **Anthropic**：`max_budget_usd` 是**进程内会话级**，无多租户无跨实例；缓存计价使 `input_tokens` 语义**非线性**（命中后只算断点后部分），跨供应商成本对比必须先归一化；缓存无法手动清除。（同上）
- **LangSmith**：支出上限**限的是 trace 数不是金额**；命中后「不能创建新 trace」而**业务请求照跑、钱照花**——对成本控制几乎无效；LangGraph 编排核心无任何预算原语。（同上）
- **Vertex AI**：配额是速率/并发维度，**无金额语义**；超限 429 需人工提额，运营负担在客户侧；强绑定 GCP 不可移植；纯后置计量。（同上）
- **AutoGen（归档）**：**完全无成本治理能力**，成本=服务商账单；官方已归档停维护，不应作为选型依据。（同上）
- **CrewAI**：编排层的 `max_rpm` / `max_iter` **都不是金额**；金额上限需购买企业版；工具缓存无成本效果指标。（同上）
- **Agno**：**纯观测无执行侧控制**（无预留/结算/金额闸门）；`cost` 是 provider 估算、无自维护的价格版本化；多模型细分是弱类型 `details` 字典，无幂等约束。（同上）

### 改进点 1 · 接入真实 tokenizer 计量（替换启发式估算）

**问题陈述** — 上下文侧 token 计数是**启发式估算**：`HeuristicTokenCounter` 用「汉字 1 字 ≈ 1 token、非汉字 3 字符 ≈ 1 token」（`HeuristicTokenCounter.java:30-33`），类注释自陈「粗估中英混合误差可达 **30–50%**」；`ContextBudgetTrimmer.estimateTokens`（`:171`）同口径但只统计消息序列（**漏算 system prompt 与 tool schema**）。传导路径：`估算误差(±30~50%) → estimatedInput → ×2 安全系数 → 预留额`——误差偏大则额度虚占、并发下 `INSUFFICIENT` 误拒；误差偏小时 ×2 系数通常兜住，但 tool schema 漏算时兜不住 → 结算被 DB CHECK 拒绝。

**⚠️ 一个重要的正面事实**：**结算侧不受影响**——`settleModelCost` 用 `response.usage()` 的真实 token（`RunExecutionLoop.java:1722-1724`）。故本缺口影响的是**预留准确度与额度效率**，不是**成本报表的准确性**。不能夸大成「成本算不准」。

**方案设计** — 1. **新增真实实现**。端口已存在（`agent-ports/.../ports/context/TokenCounter.java`，22 行），现实现为 `HeuristicTokenCounter`。新增 `RealTokenizerCounter`：经 `ModelCatalogPort` 按模型选 tokenizer 规格（`ModelCapabilities` 抽象可挂 tokenizer 标识）；**供应商返回的真实 usage 才是权威**，tokenizer 只用于调用前预估（业界共识：调用前无法知道真实 token）；降级链为 真实 tokenizer → 按供应商公开 token/字符比校准的启发式 → 现状启发式，降级必须**可观测**（WARN + 「估算降级次数」指标）。
2. **口径统一到一处**。当前两套并存（`ContextBudgetTrimmer.estimateTokens` 消息序列 / `HeuristicTokenCounter.count` 六块全窗口），`RunExecutionLoop.java:862-869` 已用 `assembly.assembled()` 分流，「两处各算一份必然漂移」（`:1645` 注释自陈）。应收敛到**同一个 `TokenCounter` 实现**，`ContextBudgetTrimmer` 保留为兼容路径并标 `@Deprecated`。
3. **补上 tool schema 与 system prompt 的漏算**。`HeuristicTokenCounter` 已计 toolSchemas（`:41-42`，有反向验证点 RV-1），但 `ContextBudgetTrimmer.estimateTokens` **不计**——legacy 路径的工具 schema 从未进入预留。

**接口片段**

**实施成本与风险** — - **改动面 / 迁移影响**：`agent-context`（新增实现）、`agent-ports`（端口加默认方法）、`platform-bootstrap`（装配）、`agent-worker`（`RunExecutionLoop` 改注入）。 ｜ **迁移影响**：**无数据迁移**（token 是计量值，不改历史账）。

**优先级**：**P0**（预留效率直接决定额度吞吐）· **排期**：近端（P4 实测调优批）

**验收方式（可执行门禁）** — 1. **误差门禁**：新增 IT `RealTokenizerAccuracyIT`，取 ≥ 200 条真实 `ModelResponse`，断言 `|estimated - actual| / actual ≤ 0.10`；不达标则红。

3. **口径收敛门禁**：新增架构测试 `SingleTokenCounterArchitectureTest`，断言生产装配路径中**只有一个** `TokenCounter` Bean 注入 `RunExecutionLoop`。
4. **保留项门禁**：断言 `RunExecutionLoop.settleModelCost` 仍使用 `response.usage()`，**不接受**任何形式的估算值入账（源码级断言）。
5. **预算门禁**：跑 `BudgetReservationIT` 全量，证明换计数器后「预留-结算-释放」链路仍全绿（无结算被 DB CHECK 拒绝）。

### 改进点 2 · 模型定价表的版本化维护（生效日期 + 历史回溯定价）

**问题陈述** — `agent.pricing.models` 是纯配置映射，`ModelPricingPolicy` 装配期构造、运行期只读（`:52-64`），**没有生效日期、没有版本号、没有历史回溯**。后果：① 价格调整后**历史 `usage_record.cost_amount` 不重算** → 历史与当前成本口径不一致 → 趋势图失真；② `usage_record` **不记录当时用的哪个价**（只有 `model_id`，无 `pricing_version`）；③ 配置里 6 个条目是**占位价**，注释自陈「上线前必须按供应商最新报价替换……**没有第二处真相源**」。

**方案设计** — 1. **新增 `model_price_book` 表**（`public` 域，RLS 按 `tenant_id`；同步 `deploy/sql/platform/03_platform_roles.sql` 授权，按铁律 7）：
```sql
CREATE TABLE public.model_price_book (
    price_version uuid DEFAULT gen_random_uuid() NOT NULL,
    tenant_id uuid NOT NULL,
    model_pattern text NOT NULL,              -- 模型标识或前缀模式
    input_per_1k_tokens numeric(18,8) NOT NULL,
    output_per_1k_tokens numeric(18,8) NOT NULL,
    currency text DEFAULT 'CNY'::text NOT NULL,
    effective_from timestamp with time zone NOT NULL,
    effective_to timestamp with time zone,     -- NULL = 当前生效
    source_ref text,                           -- 供应商报价页 URL + 取数日
    created_at timestamp with time zone DEFAULT now() NOT NULL,
    CONSTRAINT model_price_amount_ck CHECK (
        input_per_1k_tokens >= 0 AND output_per_1k_tokens >= 0),
    CONSTRAINT model_price_window_ck CHECK (
        effective_to IS NULL OR effective_to > effective_from)
);
CREATE UNIQUE INDEX uq_price_version ON public.model_price_book
    (tenant_id, model_pattern, effective_from);
CREATE INDEX idx_price_lookup ON public.model_price_book
    (tenant_id, model_pattern, effective_from DESC);
ALTER TABLE public.model_price_book FORCE ROW LEVEL SECURITY;
CREATE POLICY model_price_book_tenant_isolation ON public.model_price_book
    USING ((tenant_id = public.current_tenant_id()))
    WITH CHECK ((tenant_id = public.current_tenant_id()));
```
2. **`usage_record` 增加 `price_version` 列**（可空，向后兼容——存量行无版本，如实为 NULL）：`ALTER TABLE public.usage_record ADD COLUMN price_version uuid;`
3. **`ModelPricingPolicy` 改为「按时间点查价」**：新增 `pricingOf(modelId, atInstant)`，返回含 `priceVersion` 的结果。**结算时按调用发生时刻查价**（非当前价），从而历史成本**自动可回溯**、价格调整**不影响已发生的账**。
4. **配置降级为启动种子而非运行时真相源**：`application.yml` 的 `agent.pricing.models` 仅在首次启动时导入 `model_price_book`（写入 `effective_from = 导入时刻`、`source_ref = 'application.yml (seed)'`）。运维日常改价走 DB / 管理台，不改 yml。
5. **版本化查询口径**：`pricingOf` 的三级匹配（精确 → 最长前缀 → default）不变，但**加时间窗口筛选**：`WHERE effective_from <= at AND (effective_to IS NULL OR effective_to > at)`。

**预期收益（可度量口径）**
| 指标 | 现状 | 目标 |
|---|---|---|
| 价格调整导致的历史成本漂移 | 不可测（无版本概念） | 可测：改价后重跑历史对账，历史行成本**逐位不变** |
| 「哪些模型没配价」的可见性 | 启动日志一行 WARN | 可查询，且**每行带 source_ref 与取数日** |
| 单位经济学指标的稳定性 | 改价即失真 | 改价只影响新发生的调用 |

**实施成本与风险** — - **改动面 / 迁移影响**：`agent-persistence`（新表 + 新仓储 + `usage_record` 加列）、`agent-application`（`ModelPricingPolicy` 改签名）、`agent-worker`（结算路径传时间点）。 ｜ **迁移影响**：**需数据迁移**（存量 `usage_record.price_version` 为 NULL，如实标注「未记录价格版本」；可选回填脚本按当前配置回填并打标记）。
- **风险 / 灰度**：① 引入「查价失败」的新失败模式——必须保留配置兜底（查不到 DB 版本时回退 yml 并 WARN）；② 多一处真相源——必须明确 yml 只是**种子**，启动时校验二者一致，不一致则**拒绝启动**（沿用本项目「权威在代码/DB，yml 是镜像」的既有模式）。 ｜ **灰度**：先双写（同时记 `price_version` 与按当前价的 `cost_amount`），比对一致后切换。

**优先级**：**P0**（历史成本不可回溯是数据正确性问题，不是体验问题）· **排期**：近端

**验收方式（可执行门禁）** — 1. **回溯门禁**：新增 IT `PriceVersionRetroactiveIT`——建两个版本（v1 生效 2026-01-01，v2 生效 2026-06-01），两个时间点各做一次模型调用，断言两条 `usage_record.cost_amount` **分别按 v1 / v2 计算**且 `price_version` 正确；改 v2 的价后重跑断言 v1 那条**逐位不变**。
2. **反向验证门禁**：去掉 `pricingOf(modelId, atInstant)` 的时间筛选（改为恒取最新版本），断言上述 IT **变红**。
3. **回填诚实性门禁**：断言存量行 `price_version IS NULL` 时任何成本报表**必须**显示「未记录价格版本」，而非按 0 或按当前价填补。
4. **一致性守卫**：启动守卫断言「`application.yml` 的 `agent.pricing.models` 与 `model_price_book` 当前生效版本逐条一致」，不一致 → 拒绝启动（fail-closed）。
5. **权限门禁**：新增 SchemaDriftIT 断言 `model_price_book` 在 `03_platform_roles.sql` 中有对应授权；业务 SQL 用 `app_agent` 绝不 `agent_retention`（铁律 7）。

### 改进点 3 · 成本报表与看板：cost per successful task（多维归因）

**问题陈述** — `mv_agent_metric_hourly` 已提供 `trace_count` / `succeeded_count` / `sum(cost_amount)` / `sum(input_tokens)` / `sum(output_tokens)`，数据**完全具备**，但全仓**没有任何一处计算 cost per successful task**。其余缺口：① 物化视图 GROUP BY `(hour, tenant_id, agent_id, agent_version, scenario)` **不含 model_id** → 按模型拆成本需查明细表；② `usage_record.step_id` 是**死列**（无写入方）→ 步骤级成本不可归属；③ 成本报表**没有工具维度**（`tool:` 前缀可区分，但无现成聚合）。

**方案设计** — 1. **新增视图 `platform.mv_cost_attribution_hourly`**（按需刷新，`CONCURRENTLY`）：
```sql
CREATE MATERIALIZED VIEW platform.mv_cost_attribution_hourly AS
SELECT date_trunc('hour', u.created_at)                AS bucket_start,
       u.tenant_id,
       r.agent_id,
       (r.input_payload->>'scenario')                   AS scenario,
       CASE WHEN u.model_id LIKE 'tool:%' THEN NULL
            ELSE u.model_id END                        AS model_id,
       CASE WHEN u.model_id LIKE 'tool:%'
            THEN substring(u.model_id from 6) END      AS tool_name,
       count(*)                                        AS usage_count,
       sum(u.input_tokens)                             AS input_tokens,
       sum(u.output_tokens)                            AS output_tokens,
       sum(u.cost_amount)                              AS cost_amount,
       count(DISTINCT u.run_id)                        AS run_count
FROM public.usage_record u
JOIN public.run r
  ON r.tenant_id = u.tenant_id AND r.run_id = u.run_id
GROUP BY 1,2,3,4,5,6;
```
2. **新增视图 `platform.mv_cost_per_successful_task`**——把「链路成功」与「任务成功」**分开**：
```sql
CREATE MATERIALIZED VIEW platform.mv_cost_per_successful_task AS
SELECT date_trunc('hour', started_at) AS bucket_start,
       tenant_id, agent_id, scenario,
       count(*)                                          AS trace_count,
       count(*) FILTER (WHERE terminal_state='SUCCEEDED') AS link_success_count,
       count(*) FILTER (WHERE human_verdict='SUCCESS')   AS task_success_count,
       count(*) FILTER (WHERE auto_verified)              AS auto_verified_count,
       sum(cost_amount)                                  AS total_cost,
       -- ⚠️ 分母口径三选一，绝不混用；样本不足时必须为 NULL 而非 0
       CASE WHEN count(*) FILTER (WHERE human_verdict='SUCCESS') > 0
            THEN sum(cost_amount)
                 / count(*) FILTER (WHERE human_verdict='SUCCESS')
            ELSE NULL END                                AS cost_per_successful_task,
       CASE WHEN count(*) FILTER (WHERE terminal_state='SUCCEEDED') > 0
            THEN sum(cost_amount)
                 / count(*) FILTER (WHERE terminal_state='SUCCEEDED')
            ELSE NULL END                                AS cost_per_link_success
FROM platform.agent_trace_metric
GROUP BY 1,2,3,4;
```
⚠️ **样本量纪律**：沿用本项目「小样本不展示百分比」的既有铁律——**分母 < 30 时该列必须为 NULL**（不是 0、不是按 1 算），与 `agent_eval_sample` 的 n<30 规则同源。
3. **补齐 `usage_record.step_id` 写入方**：在 `JdbcBudgetRepository.insertUsageOnce` 调用侧传入 `run_step.step_id`（模型调用在 `RunExecutionLoop` 的 THINK 步骤落库后可回填）。⚠️ 需「步骤落库 → 计量写入」的顺序保证；若步骤 ID 在计量写入时尚未生成，则**如实留 NULL**（不为了填满而编造）。
4. **API 暴露**：`agent-api` 新增 `GET /api/agent/costs?dimension=tenant|agent|scenario|model|tool&from=&to=`，返回带 `refreshed_at` 的聚合结果（呼应 `mv_agent_metric_hourly` 注释「刷新期间响应体必须带上 refreshed_at，不能假装是实时的」）。

**预期收益（可度量口径）**
| 指标 | 现状 | 目标 |
|---|---|---|
| cost per successful task | **不存在** | 可查，可按租户/Agent/场景/模型/工具五维拆分 |
| 按模型拆成本 | 需查明细表 | 小时桶直读 |
| 步骤级成本归属 | `step_id` 是死列 | 非 NULL（能回填的部分） |
| 样本不足时的展示 | —— | 分母 < 30 → NULL，绝不显示 0 |

**实施成本与风险** — - **改动面 / 迁移影响**：`deploy/sql/platform/01_platform_ddl.sql`（新视图）、`agent-persistence`（视图查询仓储）、`agent-api`（新端点）、`agent-worker`（step_id 回填）。 ｜ **迁移影响**：**无表结构变更**（视图 + 可空列回填）。

**优先级**：**P0**（FinOps 最核心的一个数字，且数据已具备）· **排期**：近端

### 改进点 4 · 预算策略可配置化（硬/软/分级封顶 + 按场景预算 + 预留过期策略）

**问题陈述** — 当前预算策略是**硬编码的三层固定口径**：租户级 `budget_account.total_limit`（**只有硬封顶**，CHECK 强制，无软告警档）、Run 级 `run.budget_amount`（只有硬封顶）、单任务 `max-cost-per-run`（硬失败）。

**缺失**：① **软预算/告警档**——运维想「花到 80% 告警但不中断」当前无此能力（OpenAI 的 spend alert / hard limit 二分法）；② **按场景/按 Agent 分级封顶**——`tenant_quota.budget_limit` 存在但**未接线**（D-11），场景维度只在事后指标里；③ **预留挂账兜底**——UNKNOWN 预留刻意不释放（T5），但**缺少「预留最长挂账时长」兜底**，对账长期不收敛则额度被永久占死；④ **过期与 UNKNOWN 的边界**——普通工具预留（工具没发出 → FAILED → 已释放）无过期问题，但**委派预留**与**模型调用预留**在异常路径上可能长期 RESERVED。

**方案设计** — 1. **新增「预算策略」配置层**（`agent.budget.policy`），三档模式：
```yaml
agent:
  budget:
    reserve-per-tool-call: "0.50"
    policy:
      mode: HARD          # HARD | SOFT | GRADED
      # HARD：超额即拒（现状，默认）；SOFT：超额只告警；GRADED：按阶梯封顶
      soft-thresholds: ["0.80", "0.95"]   # GRADED 模式下的分级封顶点
      on-exhausted: REJECT               # REJECT | DEGRADE（DEGRADE 见改进点 7）
      reservation-hold-max-hours: "72"   # 超过则转「人工处置队列」而非静默占用
      release-policy:
        unknown: HOLD                    # 硬规则，不可配置（见下方 ⚠️）
        failed: RELEASE                   # 确定失败即释放
        expired: MANUAL                  # 超时未收敛 → 转人工，不自动释放
```
⚠️ **`release-policy.unknown` 必须恒为 HOLD 且不可配置**——这是 T5 的核心，不得变成配置项（可配置就会被误改成 RELEASE）。实现上**不把它做成配置项**，而在配置校验里硬编码：若配置出现该键且值 ≠ `HOLD` → **拒绝启动**。
2. **按场景预算：引入「预算池（budget pool）」抽象**（解决 D-10 的归属粒度缺口而不破坏原子性）：
```sql
-- 账户仍是唯一的原子扣减对象；池是账户下的一个「子额度」视图
CREATE TABLE public.budget_pool (
    pool_id uuid DEFAULT gen_random_uuid() NOT NULL,
    tenant_id uuid NOT NULL,
    account_id uuid NOT NULL,
    pool_kind text NOT NULL,          -- 'SCENARIO' | 'AGENT' | 'TENANT_DEFAULT'
    pool_key text NOT NULL,           -- scenario 值 / agent_id / ''（默认池）
    limit_amount numeric(18,6) NOT NULL,
    reserved_amount numeric(18,6) DEFAULT 0 NOT NULL,
    settled_amount numeric(18,6) DEFAULT 0 NOT NULL,
    created_at timestamp with time zone DEFAULT now() NOT NULL,
    CONSTRAINT budget_pool_amounts_ck CHECK (
        total_limit >= 0 AND reserved_amount >= 0 AND settled_amount >= 0),
    CONSTRAINT budget_pool_no_overspend CHECK (
        (reserved_amount + settled_amount) <= limit_amount),
    CONSTRAINT budget_pool_kind_ck CHECK (
        pool_kind IN ('SCENARIO','AGENT','TENANT_DEFAULT'))
);
```
**关键设计**：**账户仍是唯一的原子扣减对象**（保住 D-1 的单行条件 UPDATE），池是**账户之上的第二道原子条件 UPDATE**（同样用 `WHERE reserved+settled+? <= limit_amount`）。两层原子条件在同一事务内依次执行，**任一层拒绝则整体回滚**。这让「按场景封顶」在**不破坏单行原子性**的前提下成为可能。
3. **软预算的实现**：在 `JdbcBudgetRepository.reserve` 的原子 UPDATE 中把「硬拒绝」与「软放行」分开——硬拒绝：`reserved + settled + ? > total_limit` → 0 行 → `INSUFFICIENT`；软放行：处于软阈值内（如 80%–100%）→ **允许**并发出 `budget_soft_threshold_crossed` 事件（写 `run_event`，供维度 10 看板消费）。⚠️ 软阈值**不改变 DB 约束**，只改变**应用层的接受/拒绝判定**——故 `SOFT` 模式下账户余额**可以超过** `total_limit`。**推荐做法**：软模式用**独立列 `soft_limit`**，硬约束仍作用在 `total_limit`，软模式判定在应用层比较 `soft_limit`；**绝不**通过放宽 `budget_no_overspend` 实现软模式（那会破坏 D-1 的最后防线）。
4. **预留挂账兜底**：新增 `ReservationHoldMonitor`（定时任务）扫描 `state='RESERVED' AND created_at < now() - reservation_hold_max_hours` 的预留，**不自动释放**（绝不在不确定时释放），而是写入 `platform.review_task`（复用维度 10/11 审查队列机制，`review_task` 已有生成列 + 部分唯一索引做并发去重），并关联对应的 `tool_operation` / `agent_invocation` 供人工处置。

**预期收益（可度量口径）**
| 指标 | 现状 | 目标 |
|---|---|---|
| 可配置的预算封顶层级 | 1 层（租户总额，硬） | 4 层（租户/池-场景/池-Agent/Run），硬软可切 |
| 软预算可用性 | 无 | 试点期可切 SOFT 观察，**不影响硬约束** |
| 「配置了但不生效」的配置项数 | ≥ 2（`tenant_quota.budget_limit`、`tenant.max-concurrent-runs`） | **0**（全部接线或明确标注不生效） |
| 预留长期挂账的可见性 | 靠人工跑对账 | 自动进审查队列，超 72h 未收敛必被发现 |

**实施成本与风险** — - **改动面 / 迁移影响**：`deploy/sql/platform/01_platform_ddl.sql`（新表 `budget_pool` + 授权同步到 `03_platform_roles.sql`）、`agent-persistence`（新仓储 + 两层原子预留）、`agent-worker`（预留路径加池判定）、`platform-bootstrap`（配置绑定）、新增 `ReservationHoldMonitor` 调度。 ｜ **迁移影响**：需为现有租户**创建默认池**（`TENANT_DEFAULT`，额度 = 账户总额），否则池判定会因「无池记录」而 fail-closed 拒绝所有调用——**迁移脚本必须与代码同批上线**。
- **风险 / 灰度**：① **两层原子扣减引入新的死锁可能性**——必须固定锁序（「账户行 → 池行」）并写进文档；② 软模式让余额可能超 `total_limit`——**必须用独立列 `soft_limit` 而非放宽 CHECK**；③ 池引入了「这笔钱算在哪个池」的新归属问题——需在 `budget_reservation` 加 `pool_id` 列以便追溯。 ｜ **灰度**：池抽象建议**先只读影子**（计算池占用但不参与判定，对比两套口径），确认一致后再切为参与判定。

**优先级**：**P1**（软预算与池的收益依赖真实流量；「配置不生效」的清理可先做）· **排期**：中期

**验收方式（可执行门禁）** — 1. **配置生效门禁**：新增 IT `BudgetPolicyConfigIT`——`mode=SOFT` 下把账户花到 95%，断言**预留被允许**且产生 `budget_soft_threshold_crossed` 事件；`mode=HARD` 时同场景断言**被拒**且 `ReserveOutcome.INSUFFICIENT`。
2. **不可配置项门禁**：配置里写 `release-policy.unknown=RELEASE`，断言应用**拒绝启动**并给出明确错误（铁律 8 的红线守卫）。
3. **池原子性门禁**：并发发起 N 次预留超过池限额，断言 ① 池的 `reserved+settled <= limit_amount` CHECK 成立；② 账户的 CHECK 成立；③ **失败的预留没有在账户上留下扣减**（同事务回滚）。
4. **迁移门禁**：迁移脚本未执行时（无默认池），断言预留被**明确拒绝**（fail-closed）而非静默放行或静默拒绝（消息须指明「缺默认池」）。
5. **死锁门禁**：并发跑「多池 + 多账户」混合预留 10 万次，断言无 `deadlock_detected`。
6. **挂账兜底门禁**：构造一条 100 小时的 RESERVED 预留，断言 `ReservationHoldMonitor` 把它写进 `review_task`，且**额度未被自动释放**（`reserved_amount` 未变）。
7. **反向验证门禁**：把「池判定」从预留路径移除，断言第 3 条门禁变红。

### 改进点 5 · 成本异常检测（单任务成本突增 / token 暴涨 / 重试风暴放大）

**问题陈述** — `ReviewAlertService` 当前只有 4 条规则（BEH-4 循环 / COST-4 超大 token > 20000 / MAX_ROUNDS / SAFETY_BLOCK），**全部是「单条 Trace 自身可确定判定」**的。类注释明确拒绝比例类判断（「需要分母，而单条 Trace 的样本量不足以下结论」）。缺失三类成本异常：① **单任务成本突增**（与历史基线比）——无；② **重试风暴导致的成本放大**——`retry_count` 存在，但与 `cost_amount` 之间**无比值口径**（T4 明确要求的能力）；③ **告警出口**——`ReviewAlertService` 产出的是**人工审查任务**不是告警（无 Prometheus alert rules，项目记忆已记为缺口）。

**方案设计** — 1. **新增「成本基线」物化视图**：
```sql
CREATE MATERIALIZED VIEW platform.mv_cost_baseline AS
SELECT tenant_id, agent_id, scenario,
       count(*)                                             AS sample_count,
       avg(cost_amount)                                     AS avg_cost,
       percentile_cont(0.5) WITHIN GROUP (ORDER BY cost_amount) AS p50_cost,
       percentile_cont(0.95) WITHIN GROUP (ORDER BY cost_amount) AS p95_cost,
       avg(retry_count)                                      AS avg_retry,
       max(retry_count)                                      AS max_retry
FROM platform.agent_trace_metric
WHERE cost_amount IS NOT NULL
GROUP BY tenant_id, agent_id, scenario;
```
2. **新增告警规则到 `ReviewAlertService`**（作为**分层抽样规则**的一部分，因为它们需要分母与基线）：

| 规则 | 判据 | 严重度 | 前置条件 |
|---|---|---|---|
| **COST-5 单任务成本突增** | `cost_amount > p95_cost × 3`（同租户+Agent+场景桶） | HIGH / ANOMALY | 桶 `sample_count ≥ 30` |
| **COST-6 token 相对突增** | `total_tokens > p95_tokens × 3` | NORMAL / ANOMALY | 同上 |
| **COST-7 重试风暴成本放大** | `retry_count ≥ 3` 且 `cost_amount / 基线 avg_cost ≥ 3` | HIGH / ALERT | 同上 |
| **COST-8 成本-失败背离** | `cost_amount > p95_cost` 且 `terminal_state <> 'SUCCEEDED'` | HIGH / ANOMALY | 同上 |

⚠️ **样本量纪律**：桶 `sample_count < 30` 时**一律不判定**（不告警、不进队列），并记录「基线不足」计数——沿用本项目「小样本不展示百分比」的铁律。
3. **重试放大倍数显式化**（可先在视图里算；列方案）：`ALTER TABLE platform.agent_trace_metric ADD COLUMN retry_cost_multiplier numeric(10,4);` —— 注释写明「= 本 Trace 成本 / 同桶基线中位数。⚠️ 基线样本 < 30 时为 NULL（不猜基线）」。
4. **告警双出口**：人工通道进 `review_task`（复用既有并发去重机制）；机器通道用 Micrometer 计数器（`agent.cost.anomaly.total{type=COST-5|...}`）+ Prometheus alert rules（补上项目记忆中「Prometheus alert rules 未落地」的缺口）。

**预期收益（可度量口径）**
| 指标 | 现状 | 目标 |
|---|---|---|
| 成本异常检测规则数 | 1 条（超大 token） | 4 条（COST-5/6/7/8） |
| 误报率 | —— | 抽样复核 50 条告警，误报率 ≤ 20% |
| 重试风暴可见性 | **无** | `retry_cost_multiplier` 可查；放大 ≥ 3× 的 Trace 必被标出 |
| 告警出口 | 1 个（人工队列） | 2 个（人工队列 + Prometheus） |

**实施成本与风险** — - **改动面 / 迁移影响**：`agent-application/.../review/ReviewAlertService.java`（新规则）、`deploy/sql/platform/01_platform_ddl.sql`（新基线视图 + 可选新列）、`agent-persistence`（基线查询）、`agent-application/.../metrics/`（Micrometer 计数器）。 ｜ **迁移影响**：新视图需首次刷新；新列可空回填。
- **风险 / 灰度**：① **基线漂移**——业务形态变化会让基线失真；缓解：按 `(tenant, agent, scenario)` 分桶且样本 < 30 不判定；② **告警风暴**——上线初期可能大量触发；缓解：**先影子运行 2 周只计数不告警**，再切为告警；③ 基线视图刷新延迟——必须带 `refreshed_at`。 ｜ **灰度**：影子期 → 部分租户 → 全量。

**优先级**：**P1**（与维度 11 强耦合，重试风暴检测尤其重要）· **排期**：中期

**验收方式（可执行门禁）** — 1. **规则门禁**：新增 IT `CostAnomalyRulesIT`——构造「同桶 30 条正常 Trace + 1 条成本 10× 的 Trace」，断言 COST-5 命中并生成 `review_task`（含摘要，**不含原文**）。
2. **小样本门禁**：桶样本 29 条时构造一条高成本 Trace，断言**不告警**且「基线不足」计数 +1。
3. **重试放大门禁**：构造 `retry_count=3` 且成本为基线 3.2× 的 Trace，断言 COST-7 命中且 `retry_cost_multiplier` 正确（容差 1%）。
4. **反向验证门禁**：把 `sample_count >= 30` 改成 `>= 1`，断言第 2 条门禁**变红**。
5. **告警出口门禁**：断言 Micrometer 计数器在触发时 +1，且 Prometheus 规则文件中存在对应告警项。
6. **不猜基线门禁**：断言基线为 NULL 时**任何**成本类规则都不触发（而非当作 0 触发）。

### 改进点 6 · 限流与准入控制（并发 Run 上限 + 租户级 token 维度限流）

**问题陈述** — `agent.tenant.max-concurrent-runs`（初值 5）**定义外引用数为 0** → 租户并发**无限制**（项目自己的 `ConfigReadService.java:138-139` 已诚实标注）。`agent.rate-limit.limit-per-window`（30/60s）**只按请求数**，**无 token 维度**——一个 Run 单次模型调用可达 16000 token（`agent.worker.context-token-budget`），**30 次/分钟的请求限流完全拦不住烧 token**。固定窗口实现有边界放大（注释自陈「false = 固定窗口（窗口边界处实际放行量可达 2×limit）」）。`platform.tenant_quota.run_concurrency_limit` 同样未接线（D-11）。

**方案设计** — 1. **接入租户级并发 Run 上限**（把已有配置真正用起来）：
```java
// 新增：agent-ports/.../ports/persistence/RunAdmissionPort.java
public interface RunAdmissionPort {
    /** @return 该租户当前在执行的 Run 数（含本进程持有的租约） */
    int activeRunCount(@NonNull String tenantId);
    /** @return 准入判定；读不到 → fail-closed（与预算系统故障同源：宁可少接单，不可无上限） */
    @NonNull AdmissionDecision admit(@NonNull String tenantId, int limit);
}
```
**实现要点**：① 活跃 Run 数的权威口径 = `public.run` 中 `state IN ('QUEUED','RUNNING')` 的计数 + 本 Worker 在手租约（避免「DB 计数有延迟但本地已领」导致超发）；② 判定点在 `RunDispatchConsumer` 领取租约**之前**（准入）与 `RunController.createRun` 受理**之前**（快速拒绝，避免用户等半天）；③ 超限返回 **429 + `Retry-After`**（对齐 OpenAI 响应头语义），并**明确告知是并发上限而非速率上限**（避免运维查错方向）；④ 计数实现为避免每次领取都全表 count，应维护增量计数表或用「带索引的 count + 短 TTL 缓存」。
2. **引入 token 维度限流桶**（对齐 OpenAI TPM / Anthropic ITPM·OTPM）：
```yaml
agent:
  rate-limit:
    limit-per-window: "30"
    window-seconds: "60"
    sliding-window: "${AGENT_RATE_LIMIT_SLIDING_WINDOW:false}"
    token-limit-per-window: "${AGENT_RATE_LIMIT_TOKEN_LIMIT:200000}"        # 每租户每窗口 token 预算
    output-token-limit-per-window: "${AGENT_RATE_LIMIT_OUTPUT_TOKEN_LIMIT:20000}"  # 输出单独限（单价更高）
    max-concurrent-runs: "${AGENT_TENANT_MAX_CONCURRENT_RUNS:5}"
```
- **token 限流的计量点**：在 `RunExecutionLoop` 的**模型调用结算处**（`settleModelCost` 之后）用 `response.usage().inputTokens()/outputTokens()` 扣减租户 token 桶——**事后扣减**（真实 token 只有调用后才知道），因此 token 限流是**滞后的**（可被单次大调用击穿），属于**兜底而非闸门**。这是诚实的设计取舍，必须在注释中写明。**事前保护**由 `context-token-budget` + `max-cost-per-run` + 预算预留共同承担。
3. **令牌桶替换固定窗口**（RFC 2697 语义）：桶参数 = 容量 `b`（= `limit-per-window`）+ 补充速率 `r`（= `limit-per-window / window-seconds` tokens/sec）；实现用 `INSERT ... ON CONFLICT (tenant_id, bucket_key) DO UPDATE SET tokens = LEAST(b, tokens + r * elapsed) ...`（原子，无需外部依赖）。**保留固定窗口开关**，但默认改 `true` 并在文档说明两者的边界差异。
4. **准入控制（过载保护）**：活跃 Run 数 > 阈值或队列积压 > 阈值时**快速拒绝新 Run**（429），但**不拒绝已受理 Run 的续跑**（避免把已花钱的工作杀掉——既浪费钱又伤体验），并触发指标 `agent.admission.rejected`。

**预期收益（可度量口径）**
| 指标 | 现状 | 目标 |
|---|---|---|
| 租户并发 Run 上限 | **无限制**（配置引用数 0） | 生效且可配置；超限返回 429 |
| 「配置了但不生效」的配置项 | ≥ 2（`max-concurrent-runs`、`run_concurrency_limit`） | **0** |
| token 维度限流 | 无 | 每租户每窗口 token 上限可配并生效 |
| 单租户最大额度瞬时占用 | 无界 | 受并发上限 × 单 Run 上限双重约束 |
| 限流窗口边界放行量 | 可达 2× limit | ≤ 1.2× limit（令牌桶） |

**实施成本与风险** — - **改动面 / 迁移影响**：`agent-ports`（新端口）、`agent-persistence`（计数与桶实现）、`agent-worker`（`RunDispatchConsumer` 准入点 + `RunExecutionLoop` token 扣减）、`agent-api`（429 响应 + `Retry-After` 头）、`platform-bootstrap`（配置绑定 + 启动守卫）。 ｜ **迁移影响**：无表结构变更（若用 `run` 表计数查询）。
- **风险 / 灰度**：① **准入判定本身的 check-then-act 窗口**——与预算的 D-1 同源问题；缓解：并发计数的判定与「领取租约」应尽量在同一事务（`run` 行的条件 UPDATE 可实现「`WHERE (SELECT count(*) FROM run WHERE ...) < limit`」这类原子写法，但 PG 中带子查询的 UPDATE 会有性能问题，需实测）；② **token 限流滞后**——必须诚实标注，不能宣称是硬闸门；③ 429 会改变现有 API 行为——需**灰度**（先只记录不拒绝，观察一周）。 ｜ **灰度**：`max-concurrent-runs` 先以「只告警不拒绝」模式跑一周（对照 `AuthzShadowBinding` 的影子对照思路），再切为拒绝。

**优先级**：**P0**（并发上限未生效是**已知的敞开敞口**，且 `ConfigReadService` 已标注）· **排期**：近端

**验收方式（可执行门禁）** — 1. **并发上限门禁**：新增 IT `TenantConcurrencyLimitIT`——并发发起 10 个 Run（限 5），断言**恰好 5 个进入 RUNNING**、其余 5 个收到 429 且响应含 `Retry-After`；断言错误信息明确指向「并发上限」而非「速率上限」。
2. **反向验证门禁**：把准入判定短路（直接返回允许），断言 IT **变红**。
3. **令牌桶边界门禁**：以 `limit=30, window=60` 的桶，在窗口边界前后 1 秒内打 61 次请求，断言**实际放行 ≤ 36 次**（≤ 1.2× limit）——对比固定窗口实现会放行 60 次，该断言必须能在切换实现后变红。
4. **token 限流门禁**：构造一个 Run 的模型调用返回 `output_tokens=5000`，断言租户输出 token 桶被扣减 5000，且超出 `output-token-limit-per-window` 后的调用被拒绝。
5. **失败语义门禁**：断言超限返回 **429**（不是 500、不是 200 里的业务错误码），且**不产生任何 DB 写入**（Run 未被创建）——避免「拒绝了但留了半条记录」。
6. **已受理 Run 不被误杀门禁**：断言达到并发上限后**已在执行的 Run 仍能正常跑完**（不被取消、不被 FAILED）。
7. **配置生效门禁**：新增架构测试断言 `KEY_MAX_CONCURRENT_RUNS` 的**定义外引用数 ≥ 1**（把当前那个「引用数 0」的自检守卫反转成一条正向守卫）。

### 改进点 7 · 成本与质量的联合门禁（超阈值时降级模型路由，而非直接失败）

**问题陈述** — `max-cost-per-run` 触顶 → Run **硬失败**（`RunExecutionLoop.java:922-937`，`errorCode=MAX_COST`）；`INSUFFICIENT` 预留失败 → 工具调用被拒（`BUDGET_EXCEEDED`）。二者都是「直接失败」。**架构障碍（如实说明）**：本项目 `cap_agent_def.model_ref` 在治理期发布时固化，运行期只读快照（`forbid_published_def_mutation` 禁止改写已发布定义行）——**架构上排除了运行期动态换模型**。因此「降级模型路由」不是改一个 if，而是要引入一个新的治理概念。

**方案设计** — 1. **在治理期引入「模型候选集 + 降级序」**（与现有发布流程同源，不破坏运行期只读快照）：
```sql
-- 模型降级序：随 Agent 定义一起发布，运行期只读
CREATE TABLE public.cap_agent_model_fallback (
    tenant_id uuid NOT NULL,
    agent_release_id uuid NOT NULL,
    ordinal integer NOT NULL,
    model_ref text NOT NULL,
    max_cost_ratio numeric(6,4) NOT NULL,   -- 相对主模型的成本上限比（如 0.25 = 主模型价的 25%）
    CONSTRAINT cap_fallback_ordinal_ck CHECK (ordinal >= 0),
    CONSTRAINT cap_fallback_ratio_ck CHECK (max_cost_ratio > 0 AND max_cost_ratio <= 1),
    CONSTRAINT cap_fallback_unique_ck UNIQUE (tenant_id, agent_release_id, ordinal)
);
```
降级序随 `cap_agent_def` 的 release **一起发布**（不可变），运行期只读——**与维度 13 的「治理期发布、运行期钉死」完全一致**，不需要在运行期引入可变配置。`max_cost_ratio` 的语义：**降级模型的单位成本不得高于主模型的该比例**（价格由 `model_price_book` 查得，比的是**单价**而非绝对值——让降级决策与具体价格表解耦）。
2. **运行期的降级判定点**：在 `RunExecutionLoop` 中，当 `accumulatedCost` 超过 `maxCostPerRun` 的**软阈值**（如 80%）时：① **不立即失败**；② 切换到下一档降级模型（按 ordinal 顺序），并**重新装配请求**（用新模型的 tokenizer 重新估算预留额）；③ 记录 `run_event`（`MODEL_DEGRADED`，含从哪个模型降到哪个模型、当时累计成本），供维度 10 看板与维度 7 护栏消费；④ 若降级序耗尽 → 才硬失败（`MAX_COST`）；⑤ **降级次数上限**（如最多 1 级），防无限降级导致质量崩塌。
3. **质量护栏**：降级不是无条件的。降级时必须 ① 记录 `degradation_reason` 与降级前后模型标识；② **在 Trace 指标上打标**（`agent_trace_metric` 增列 `degraded` / `degraded_from_model`），使「成本降低」与「质量下降」在同一张表上可对照——这是 T7（三难）的落地要求；③ **被降级的 Trace 必须进入评测抽样队列**（复用维度 10 的 `agent_eval_sample`），否则「成本降了但质量崩了」不会被发现。
4. **联合判定（更完整形态）**：若某次 Run 的自动判定质量分（`auto_verified`）显著低于降级前，则该 (agent, 降级档) 组合应被**自动摘除降级序**（熔断）——需评估反馈闭环，属更长线演进（近期不实现，只在设计中预留数据）。

**预期收益（可度量口径）**
| 指标 | 现状 | 目标 |
|---|---|---|
| 因成本上限导致的 Run 失败率 | 未知（未采集） | 下降 ≥ 50%（有降级路径后） |
| 降级 Run 的质量保持率 | —— | 被降级 Trace 的 `auto_verified` 率与未降级 Trace 差值 ≤ 5 个百分点 |
| 成本降幅 | —— | 降级 Run 的平均成本下降 ≥ 30% |
| 降级可观测性 | 无 | 100% 的降级 Run 在 Trace 指标上可查（`degraded=true` + 原模型） |

**实施成本与风险** — - **改动面 / 迁移影响**：`deploy/sql/platform/01_platform_ddl.sql`（新表 + 授权同步）、`agent-application/.../cap/`（降级序随 release 发布）、`agent-worker/.../RunExecutionLoop.java`（降级判定 + 重新装配）、`agent-persistence`（指标打标）。 ｜ **迁移影响**：新表无历史数据；存量 Agent release 无降级序 → **行为不变**（不降级，直接失败），灰度友好。
- **风险 / 灰度**：① **降级可能引入质量回归**——必须由第 3 点的抽样评测兜底，否则「省钱」变成「效果打折且没人知道」；② 降级切换需**重新装配上下文**（不同模型的 tokenizer 与工具能力不同），这是本改进最大的工程复杂度；③ 与维度 13 的发布流程耦合——降级序是**治理期产物**，须走双人复核（`cap_config_publish_request.two_person_ck`）；④ **若目标模型未配价，降级会落入「成本按 0 记」的路径（D-12）**——降级前必须校验目标模型有价，否则等于免费无限用。 ｜ **灰度**：先只记录「如果降级会发生会降到什么」（影子），验证 2 周后再切为真实降级。

**优先级**：**P2**（收益依赖真实流量与质量基线；架构耦合较深）· **排期**：远期

**验收方式（可执行门禁）** — 1. **降级序发布门禁**：断言降级序**只存在于已发布的 release 行**上，且 `forbid_published_def_mutation` 触发器**拒绝**对已发布 release 的降级序做 UPDATE（新增 attempt + 验收契约反证，铁律 23）。
2. **降级触发门禁**：新增 IT `ModelDegradationIT`——把 `maxCostPerRun` 设为极小值，断言 Run **不是**直接 FAILED，而是先用主模型、再用降级模型（断言 `run_event` 出现 `MODEL_DEGRADED` 且记录了原模型与目标模型）。
3. **降级次数上限门禁**：构造只有 1 档降级序的场景，断言降级 1 次后仍超限 → Run 以 `MAX_COST` 失败，且**降级次数恰为 1**。
4. **无价不降级门禁**：把降级目标模型的单价从 `model_price_book` 移除，断言**不发生降级**（降级后成本不可计量 = 无限花），且 Run 按原路径失败并 WARN。
5. **质量可观测门禁**：断言被降级 Trace 在 `agent_trace_metric` 上 `degraded=true` 且 `degraded_from_model` 非空；断言降级 Trace **100% 进入**评测抽样队列。
6. **反向验证门禁**：把降级判定短路（直接失败），断言门禁 2 变红。
7. **多人复核门禁**：断言降级序的变更走 `cap_config_publish_request` 双人复核路径（`approver_id <> requester_id` CHECK 生效）。

## 八、其他有价值的横向对比（避免维度内自闭）

### 8.1 与本项目其他维度的耦合与相互约束（≥2 条）

**耦合 1 · 维度 3（状态持久化）与 UNKNOWN → 预算预留的永久挂账**
- **耦合形态**：维度 3 的 `tool_operation.state=UNKNOWN` 与维度 9 的 `budget_reservation.state=RESERVED` 是**同一件事的两个投影**。UNKNOWN 产生时，预留同步保持 RESERVED；只有对账收敛（`RECONCILED_SUCCEEDED` / `RECONCILED_ABSENT`）才允许离开。
- **相互约束**：**改维度 3 会改维度 9**。若维度 3 引入新的终态（例如新增 `TIMED_OUT` 并认为「未产生副作用」），维度 9 的 `findOrphaned` 的操作状态白名单（`'SUCCEEDED','FAILED','RECONCILED_SUCCEEDED','RECONCILED_ABSENT','MANUAL_DISPOSED'`）必须同步——否则新增终态的预留**永远不会被对账扫到**，额度静默泄漏。反之，若维度 9 引入新的预留状态，维度 3 的 `forbid_attempt_after_terminal` 与维度 9 的 `enforce_reservation_state_transition` 必须保持一致。
- **具体证据**：`JdbcBudgetRepository.findOrphaned`（`:653-655`）的 `o.state IN (...)` 白名单，与 `enforce_reservation_state_transition`（DDL `:428-437`）的终态集合，是**两处必须手工对齐的白名单**——这是典型的漂移风险点，建议加一条架构守卫测试断言两者一致。

**耦合 2 · 维度 5（工具调用）→ 工具成本仍是固定当量，「工具引发的模型成本」不可见**
- **耦合形态**：维度 5 的 `ToolInvocationGate` 是预算环节的**唯一插入点**（工具、原生工具、MCP 工具、HTTP 工具共用这一条路径——这保证了「预算闸门不可绕过」）。但正因如此，**工具本身的真实成本（尤其是工具内部调用 LLM 的成本）没有任何回传通道**。
- **相互约束**：维度 5 若要支持「工具声明自己的成本构成」（如「本工具会调 3 次 gpt-4o-mini」），必须引入**工具成本归集协议**——工具执行后回报其引发的下游消耗（token 或金额），由维度 9 汇总。这需要：
  - 维度 5 侧：`ToolHandler.ToolResult` 扩展一个可选的 `incurredCost` 字段（**注意铁律 10**：record 兼容构造器静默清空后加字段 ⇒ 转换全参构造逐字段带过）；
  - 维度 9 侧：`usage_record` 的 `operation_id` 幂等键必须能容纳「一次工具调用引发的多次下游计量」——当前 `(tenant_id, operation_id)` 唯一索引**不允许同一 operation 有多行计量**！这是一个**硬约束**：要支持工具引发的下游计量，必须改为 `usage_record` 引入一个 `parent_usage_id` 或把幂等键改为 `(tenant_id, operation_id, seq)`。**这是改进点 4/5 之外的一个未登记缺口**，值得单列。

**耦合 3 · 维度 6（上下文管理）→ token 估算口径直接决定预留准确度**
- **耦合形态**：维度 6 的两个 token 计数器（`HeuristicTokenCounter` 六块全窗口 vs `ContextBudgetTrimmer.estimateTokens` 消息序列）**同时是维度 9 的输入**。`RunExecutionLoop.java:862-869` 的分流逻辑（开启态用 `afterTokens`、关闭态用 `trimmed.estimatedTokens() + systemPrompt`）说明**两套口径在维度 9 的预留路径上并存**。
- **相互约束**：维度 6 切换压缩策略（`context.enabled` 翻转、`TRIM_ONLY` → `TIERED`）会**改变预留额**，进而改变「额度被占用多少」与「预算耗尽的时机」。反之，维度 9 若提高预留精度（改进点 1），会让维度 6 的 `context-token-budget=16000` 这个参数的实际含义发生变化（它现在约等于「预留用的估算 token 上限」）。
- **具体证据**：`RunExecutionLoop.java:1645` 的注释「⛔ 不在这里重算口径 —— 两处各算一份必然漂移」已经点出这个耦合。

**耦合 4 · 维度 10（可观测）→ 成本指标的口径与看板**
- **耦合形态**：`agent_trace_metric.cost_amount` 来自 `usage_record` 聚合；`mv_agent_metric_hourly` 的 GROUP BY **不含 model_id**；`ReviewAlertService` 的 COST-4 只看 token 不看金额。
- **相互约束**：维度 10 的「指标是事实表的确定函数」原则要求成本指标也必须可重算——但**工具调用行的 `cost_amount` 是固定 ¥0.50 的代理值**，它**不是事实表的确定函数**（真实工具成本可能不同）。这意味着**成本指标的可重算性目前是打折的**。改进点 3 必须同时把「代理值 vs 事实值」标注清楚（例如 `cost_amount` 增加 `cost_kind` 列：`MEASURED` / `PROXY`），否则看板上的「总成本」是**混合精度**的数。

**耦合 5 · 维度 11（可靠性）→ 重试风暴的成本放大**
- **耦合形态**：`RunExecutionLoop` 的重试只在 Worker 侧（禁止 `@Retryable`），但**重试本身意味着重复的模型调用与重复的 token 消耗**。`modelCallId` 含 `attempt` 保证重试的成本**被如实记账**（而不是被幂等吞掉）——这是正确设计，但**没有「放大倍数」的可见性**。
- **相互约束**：维度 11 若引入「自适应退避」或「熔断」，会改变重试次数分布 → 直接改变成本分布。反之，维度 9 的成本异常检测（改进点 5 的 COST-7）实际上是一个**可靠性信号**：成本放大倍数异常高 = 重试风暴正在发生。**这两个维度应该共用同一个信号，而不是各自造。**

### 8.2 与非 agent 领域成熟做法的对照

**对照 1 · 支付域的「授权-捕获-结算」三段式**
- **出处**：Stripe PaymentIntents 的 authorization / capture 语义，<https://docs.stripe.com/payments/place-a-hold-on-a-payment-method>（取数日 2026-11-15）。
- **可借鉴的三点**：① **授权与结算分离**，让「钱」在业务完成前处于「已承诺未动用」状态——本项目的 `reserved_amount` 正是这个概念；② **部分捕获**（capture 小于授权额），对应本项目「实际 < 预留 → 退款」（`moveReservedToSettled` 把预留全额扣回、只计实结额）；③ **授权可撤销**，对应本项目的 `release`。
- **本项目超出支付域的一点**：支付域的授权会**过期自动释放**（这是支付行业的标准做法，因为授权本身不产生成本）；而本项目**刻意不释放 UNKNOWN 预留**。这个偏离是**正确的**——因为 agent 调用的成本在请求发出时就可能已经发生，不能套用支付域的「授权未捕获 = 未扣款」假设。**这是一次有意识的范式迁移，而非照搬。**

**对照 2 · 数据库的「预留模式（reservation）」与两阶段提交**
- **出处**：PostgreSQL 的 `SELECT ... FOR UPDATE` 与 MVCC 隔离级别语义，<https://www.postgresql.org/docs/current/explicit-locking.html>（取数日 2026-11-15）。
- **可借鉴**：本项目的 D-2（Run 行锁把多行聚合判定串行化）与「锁序固定为 run 行 → 账户行」正是教科书级的做法。教科书同时指出「**多版本并发控制下 `SELECT FOR UPDATE` 可能阻塞**」——本项目在 `lockRunBudgetCap` 的**快路径**（未声明额度 → 不加锁）正是对此的优化。
- **本项目的取舍**：租户级用**条件 UPDATE** 而非行锁，避免「并发拒绝」变成「并发排队」（DoS 场景下更糟）。这与教科书推荐的 `FOR UPDATE` 不同，但是一个**在预算场景下更优**的选择——预算拒绝是正常的业务结果，不是异常。

**对照 3 · 云计算的「配额（Quota）与承诺用量折扣」**
- **出处**：Google Cloud 的配额与配额调整流程（见 3.4 的官方配额页）；AWS 的 Service Quotas。
- **可借鉴**：配额是**速率/并发**维度，账单是**金额**维度，两者**分开管理**。本项目当前把两者混在「预算」一个词下，导致 `tenant_quota`（配额语义，未接线）与 `budget_account`（金额语义，已接线）并存却互不连通。**改进点 4 + 6 的本质就是把这两个语义显式分开**：配额管并发与速率（准入控制），预算管金额（预留-结算）。
- **另一处借鉴**：Vertex AI 的**峰荷估算公式**（U×X×Y + 50% 缓冲）是本项目改进点 6 定并发上限时可直接借用的方法论。

**对照 4 · 会计的「未决科目（suspense account）」与「预付账款」**
- **出处**：财务会计基本原理（未决科目用于记录已收付但尚未确定归属的款项；预付账款用于记录已支付但尚未收到商品/服务的款项）。
- **可借鉴**：本项目的 UNKNOWN 预留**本质上是一笔未决科目**。会计原则是：未决科目**必须尽快清理**，否则会让资产负债表失真。本项目的对应义务是**对账必须真的在跑**——当前 `BudgetReconciliationService` 有实现但**没有定时调度证据**，这是一个**运维义务被欠下**的缺口。改进点 4 的「预留挂账兜底（`reservation-hold-max-hours` → 转人工）」正是把会计原则落成代码。
- **另一处借鉴**：预付账款在**折旧的记账方法**上要区分「总额法 vs 净额法」——本项目正好用「预留额全额扣回、只计实结额」（净额法），避免了「先按预留额入账再冲回」的总额法在报表上产生虚假的期间波动。

**对照 5 · 电信的「承诺信息速率（CIR）+ 峰值信息速率（PIR）」双档模型**
- **出处**：RFC 2698（trTCM），<https://www.rfc-editor.org/rfc/rfc2698>（取数日 2026-11-15）。
- **可借鉴**：CIR 是「保证能过的」，PIR 是「超过也能过但要标记为超额」。这正是本项目改进点 4 的**软/硬双档**的标准化表达：软阈值 = CIR，硬上限 = PIR，超出硬上限 = 拒绝。当前 `tenant_quota` 的 `agent_limit` / `run_concurrency_limit` / `budget_limit` 三列正是这个「多档配额」模型，但**未接线**。

### 8.3 反向思考：若从头重做本维度，我们会怎么设计？

**设计 1 · 引入「成本单位」抽象（Cost Unit），而不是直接用「元」**
- **动机**：FinOps 的加性成本单位（T1）表明异构消耗应归一到**一个可加总的抽象单位**再管理。本项目当前有三个并行量纲：元（`budget_account`）、token（`usage_record`）、调用当量（工具预留），换算关系是**估算的**。
- **会怎么做**：定义 `CostUnit`（如「1 CU = 1 元」）为唯一内部量纲，`usage_record` 同时记 `cost_amount` 与 `cost_unit`，换算规则版本化。
- **与现状的取舍**：现状的「元」已是唯一内部量纲（token 只是**计量输入**），够用；引入 CU 会**增加一层抽象**而收益有限。**保留三量纲并存，但必须显式标注每个数字的精度等级**（改进点 3 的 `cost_kind` 列）——比引入新抽象更划算。

**设计 2 · 「预算账户」不是一个单行对象，而是「账户 + 池」两层**
- **动机**：D-10 揭示了单行账户与多维归属的冲突。正确设计是**两层原子**：账户（唯一的余额真相）与池（维度的子额度），各自用单条条件 UPDATE、同事务执行。
- **与现状的取舍**：这正是改进点 4 的方案，**从零设计我一开始就会这么做**——但两层的锁序、迁移（默认池）、与 Run 级上限的三方交互都增加复杂度。现有的「单层 + Run 级行锁」是能正确工作的更简单方案。**结论：改进点 4 应该做，但要在有第二个场景预算需求时才做**。

**设计 3 · 预留与结算应由同一个「成本账本服务」统一管理**
- **动机**：模型调用成本在 `RunExecutionLoop` 算（需要 `ModelResponse`），工具调用成本在 `ToolInvocationGate` 算（需要工具上下文），两处各自实现「预留-结算」，逻辑相似但语义不同。
- **会怎么做**：抽出 `CostLedger` 服务，统一提供 `reserve/settle/release`，两个调用点都用它。
- **与现状的取舍**：两处实现**语义确实不同**（模型有 token，工具无），强行统一会引入「什么都能算但什么都不精确」的中间层。**更好的做法不是统一实现而是统一契约**——`BudgetPort` 已是这个契约，六值枚举与幂等语义都设计得很好。**现状优于我设想的统一服务**。

**设计 4 · 定价应该是带生效日期的领域对象，从第一天就版本化**
- **动机**：改进点 2 的全部内容。若从零设计，`model_price_book` 应是**第一张表**，而不是有 6 个月历史账之后才补。
- **与现状的取舍**：这是现状最应该改的地方，且**越早改代价越小**。现在补要处理 `price_version` 为 NULL 的存量行（诚实标注「未记录价格版本」），从零设计则零迁移成本。**这是本报告最强烈的一条「如果重来」建议**：价格是有生效日期的业务数据，不是配置项。

**设计 5 · 预算闸门应是「策略链」而不是分散的 if**
- **动机**：成本相关判定散在至少 6 处（`ToolInvocationGate` / `RunExecutionLoop` / `RunBudgetProbe` / `JdbcBudgetRepository` / `EvaluationCostBudget` / `ConsoleBudgetAdapter`）。每处判定语义不同，但**「什么情况下拒绝、拒绝时留下什么痕迹」的语义应当统一**。
- **会怎么做**：定义 `CostGate` 策略接口与统一的 `CostDecision`（携带原因码 + 后续动作：拒绝/降级/告警）。
- **与现状的取舍**：现状的分散有一面好处——**每处判定紧贴上下文**（闸门知道工具语义，执行循环知道模型语义），强行抽象会丢上下文。**但「拒绝原因码」的统一值得做**——当前 `BUDGET_EXCEEDED`（工具侧）、`BUDGET_EXHAUSTED`（模型侧）、`MAX_COST`（单 Run 侧）三个码语义相近却不统一，维度 10 的看板无法按统一口径统计「因成本被拒的 Run 占比」。**这是一条低成本改进，应加进改进点 3 或 4 的实施范围**。

**设计 6 · 从第一天就把「成本」与「质量」放在同一张表上**
- **动机**：T7 的三难要求成本优化必须伴随质量验证。当前成本在 `usage_record`、质量在 `agent_trace_metric`，能通过 `run_id` 关联，但**没有联合口径**。
- **会怎么做**：在 `agent_trace_metric` 上直接提供 `cost_per_successful_task` 与降级标记（改进点 3 + 7 的方向）。
- **与现状的取舍**：差距不大——`agent_trace_metric` 已有 `cost_amount`、`human_verdict`、`auto_verified`、`retry_count`、`scenario` 五列，**联合口径所需的原料几乎全在**。**这是本项目最有希望「低成本达成高价值」的维度**。

**如果重来，我最遗憾的三件事**：① **定价没有版本化**（唯一需要「追溯性补救」的，其余都能向前修）；② **单价表是配置项而非领域对象**（「没有第二处真相源」这句话本身就是风险）；③ **上下文 token 估算没有从第一天就用真 tokenizer**（它同时影响成本预留与上下文压缩两个维度，误差在两处叠加）。

**如果重来，我会庆幸的三件事**：① **把「不超发」放在 DB CHECK**（第 0 天就做对了，随后的池/场景预算扩展都是在它之上叠加）；② **UNKNOWN 不释放 + 双向对账**（与维度 3 的 UNKNOWN 语义同源，一次决策解决两个维度的难题）；③ **judge 成本物理隔离 + 守卫测试**（同时是「成本治理」和「评测体系」的正确做法，且有测试钉死）。

## 九、对产品演进的启发

### 9.1 本维度支撑的产品能力（用户能感知什么）

**对租户管理员（TENANT_ADMIN）**
- **「这个月我花了多少？花在哪？」** —— 成本看板按场景/Agent/模型/工具拆分（改进点 3）。当前只有 `mv_agent_metric_hourly` 的粗粒度聚合，**没有任何面向用户的成本报表端点**。
- **「我快要超预算了，能提前知道吗？」** —— 软预算/分级阈值 + 告警（改进点 4、5）。当前超限是**硬失败**（Run 直接 FAILED），用户只在失败后才知道。
- **「我能给自己设一个月度预算吗？」** —— `budget_account.total_limit` 需通过平台侧路径维护，`tenant_quota.budget_limit` 存在但**未接线**；租户自助设置**当前不可用**。
- **「超预算了会怎样？」** —— 当前答案是「Run 失败」（硬失败）。降级路径（改进点 7）会把它变成「先降级保任务，实在不行才失败」。

**对终端用户（学生/家长/教师）**
- **「我的问题不会被平台中途掐掉」** —— 硬失败直接终结任务是最差的产品体验；降级路径（改进点 7）+ 软预算（改进点 4）是这条体验线的关键。
- **「我不会因为别人把我的额度用光而无法提问」** —— 并发 Run 上限（改进点 6）+ 预算池（改进点 4）让额度占用更均衡。

**对平台运营（PLATFORM_ADMIN）**
- **「哪个租户在烧钱？」** —— `budget_account` 视图 + 成本归因视图。
- **「哪些成本是评估开销而不是业务开销？」** —— judge 独立科目（已实现），但**目前只进日志与进程内账，没有看板**——运营看不到 `EVAL_JUDGE_COST` 的历史曲线（进程内账随重启归零）。
- **「我们的成本结构健康吗？」** —— cost per successful task（改进点 3）。

**对财务/合规**
- **「成本口径可审计吗？」** —— `usage_record` 的幂等键、`budget_reservation` 的状态机、`agent_trace_metric` 的确定性聚合，构成可审计链。**但定价版本化缺失（改进点 2）使「历史成本」在价格变更后不可复现**——这是一个**审计缺口**。

### 9.2 演进路线图（近/中/远三期，每期有明确产出物与验收标准）

#### 近端（P4 实测调优批 · 1 个迭代内）

**目标**：把「已存在但未生效/未接线」的东西接上线，把「数字变真」的基础打好。

| 产出物 | 对应改进点 | 验收标准 |
|---|---|---|
| 租户并发 Run 上限真正生效（429 + `Retry-After`） | 6 | 10 并发 → 恰好 5 个 RUNNING；反向验证门禁变红 |
| token 维度限流桶（租户级 TPM/输出 TPM） | 6 | 超限请求被拒；桶扣减可查 |
| `cost per successful task` 视图 + 租户成本报表 API | 3 | 分母用 `human_verdict='SUCCESS'`；n<30 → NULL；`refreshed_at` 存在 |
| 统一成本拒绝原因码（`BUDGET_EXCEEDED` / `BUDGET_EXHAUSTED` / `MAX_COST` 归一） | 8.3 设计 5 | 看板可按统一码统计「因成本被拒的 Run 占比」 |
| `model_price_book` 建表 + 迁移 + `usage_record.price_version` 列 | 2 | 存量行 `price_version IS NULL` 且报表如实标注「未记录价格版本」 |
| 预留挂账定时监控（`ReservationHoldMonitor`）先只**计数+告警**不建任务 | 4（部分） | 超 72h 的 RESERVED 预留被计数并在日志中可查；额度**未被自动释放** |
| `cost_kind` 列（`MEASURED` / `PROXY`）标注成本精度 | 3（部分） | 看板能区分「实测成本」与「代理成本」；总成本旁标注混合精度 |

**近端明确不做**（避免范围蔓延）：真实 tokenizer（依赖需评估，先做影子比对）、预算池（新表 + 迁移，收益依赖第二场景）、降级路由（架构耦合深）。

#### 中期（平台化批 · 2 个迭代）

**目标**：预算策略可配置化 + 成本异常检测闭环 + 定价表真正生效。

| 产出物 | 对应改进点 | 验收标准 |
|---|---|---|
| 预算策略配置层（`mode: HARD/SOFT/GRADED` + `on-exhausted`） | 4 | SOFT 模式放行且产生软阈值事件；`unknown: RELEASE` 配置导致**拒绝启动** |
| 定价表 DB 化（`model_price_book` 接管运行时查价，yml 降级为种子） | 2 | 改价后重跑历史对账，历史行成本逐位不变；yml 与 DB 不一致 → 拒绝启动 |
| 成本异常检测四规则（COST-5/6/7/8）+ Prometheus 告警 | 5 | 30 条基线 + 1 条异常 → 命中并建 `review_task`；n<30 → 不判定 |
| 真实 tokenizer 影子比对（与估算并行跑，只报差异不切换） | 1 | 200 条真实响应，相对误差 ≤ 10%（真实 tokenizer 路径）；影子期不改变现有行为 |
| 令牌桶替换固定窗口（保留开关） | 6 | 窗口边界放行 ≤ 1.2× limit；对比固定窗口会变红 |
| 成本拒绝统一码进维度 10 看板 | 10 | 看板有「因成本被拒」的趋势线 |

**中期的关键风险**：定价表 DB 化引入「两处真相源」——必须严格「DB 为权威、yml 为种子、不一致即拒启」，否则违反本项目既有模式。

#### 远期（生态批 · 3 个迭代以上）

**目标**：成本-质量联合治理 + 多维预算分账 + 完整单位经济学。

| 产出物 | 对应改进点 | 验收标准 |
|---|---|---|
| 模型降级序（治理期发布）+ 运行期降级路由 | 7 | 降级被触发并记录 `MODEL_DEGRADED`；降级 Trace 的 `auto_verified` 率与未降级差 ≤ 5pp；降级 Trace 100% 进评测抽样 |
| 预算池（场景/Agent 维度）+ 双层原子预留 | 4 | 并发下池与账户两个 CHECK 均成立；失败预留不留扣减；无死锁 |
| `usage_record.step_id` 写入方（步骤级成本归属） | 3 | 步骤级成本可查；无法回填的如实留 NULL |
| 工具成本归集协议（工具回报其引发的下游消耗） | 8.1 耦合 2 | 工具引发的下游计量可查；**需要先解决 `usage_record` 幂等键不允许同 operation 多行的问题** |
| 降级熔断（质量持续退化 → 自动摘除降级序） | 7（远期部分） | 质量显著退化的 (agent, 降级档) 组合自动摘除并告警 |
| 单位经济学报表（cost per successful task × 场景 × 客户） | 3 | 可按客户/场景出账单级报表 |

**远期的最大不确定性**：降级路由与维度 13 的「治理期固化」如何长期共存——如果治理要求「发布后行为绝对不变」，则运行期降级会与之冲突。**这是一个需要产品层面拍板的架构决策，不是工程问题。**

### 9.3 风险清单（做这一步可能踩的坑，关联本项目已知铁律）

| # | 风险 | 触发场景 | 后果 | 缓解 |
|---|---|---|---|---|
| R1 | **把「不超发」从 DB CHECK 迁回应用层 if** | 引入预算池/多级限额时的重构 | 应用层并发窗口失守 → 超发（Sev-0 级） | CHECK **永远保留**为最后防线；新增的池也必须有 CHECK；架构测试断言 CHECK 存在 |
| R2 | **judge 成本被合并进 `usage_record`** | 「统一成本看板」的需求诱惑 | 违反**铁律 8**；业务成本口径被评估频率污染 | 守卫测试 `L2ProductionGuardTest` 已钉死；**任何统一看板需求都必须走「科目相加」而非「合并记账」** |
| R3 | **UNKNOWN 预留被自动释放** | 「额度被占死了，运维要手工解」的抱怨压力 | 白送额度、账实不符；或自动结算 → 凭空多计费 | 释放路径**必须**检查操作状态；`release-policy.unknown` **不做成配置项**；配置里出现该键且值≠HOLD → 拒绝启动 |
| R4 | **`usage_record` 幂等键改造引入重复计费** | 支持「工具引发的下游多行计量」时 | 重复计费（铁律 8 邻接风险） | 改造必须**向后兼容**（存量行按 `(tenant_id, operation_id)` 仍唯一）；新语义用**新列 + 新部分唯一索引**，不改旧索引；必须有「重复结算不重复计费」的 IT（`AT-BUDGET-002` 已有） |
| R5 | **新表未同步 `03_platform_roles.sql` / 枚举未用 `?::enum`** | 加 `model_price_book` / `budget_pool`、新增枚举 | 权限缺失 → 生产查询失败；权限过宽 → 越权；枚举类型不稳定 | 按**铁律 7** 新表同步授权 + `SchemaDriftIT`；业务 SQL 用 `app_agent` 绝不 `agent_retention`；按**铁律 2** 新枚举一律 PG enum + `?::enum` |
| R7 | **成本口径变更引发「历史不可比」** | 改进点 1/2/3 同时落地 | 老数据与新数据口径不同，趋势图失真 | 每次口径变更必须：① 记 `cost_kind`；② 记 `price_version`；③ 视图带 `refreshed_at`；④ 报表标注口径版本 |
| R8 | **并发准入判定引入 check-then-act** | 改进点 6 | 并发超限（限流形同虚设） | 优先「条件 UPDATE」而非「先 count 后 update」；否则用与预算同源的锁序；必须有并发 IT（10 并发恰好 5 通过） |
| R9 | **限流/预算造成「预算系统故障 → 全站不可用」** | 预算表锁竞争、DB 慢 | fail-closed 的代价被放大 | fail-closed 是既定铁律，但**必须有降级预案**：预算服务不可用时的**明确错误语义**（503 而非 500），以及独立监控该路径的失败率 |
| R10 | **降级路由绕过治理期固化** | 改进点 7 | 违反维度 13 的不变式；发布后行为不可预测 | 降级序**随 release 一起发布**（不可变）；`forbid_published_def_mutation` 触发器必须同时保护降级序表；新增 attempt + 验收契约反证（铁律 23） |
| R11 | **静态守卫通过但运行时不成立** | 所有新增门禁 | 「有一行」≠「数字算对了」（铁律 6） | 每个门禁必须有**反向验证**：撤掉修复点必须变红（已在各改进点的验收中逐条列出） |
| R12 | **文档/配置注释与实际行为漂移** | 改进点陆续落地 | 运维读到假数字（历史上 `max-cost-per-run` 曾出现「声明比真实敞口紧 5 倍」的假承诺） | 每次上线同步更新 `ConfigReadService` 的 `Spec` 标注；**把「未接线的配置项」显式标注为不生效**，而不是沉默 |
| R13 | **「成本优化」悄悄牺牲质量** | 改进点 7 降级 | 省钱但效果打折，无人察觉 | 降级 Trace **强制进评测抽样**；质量差异指标与成本指标同表；质量退化 → 熔断摘除降级序 |

### 9.4 一句话结论

**本平台在本维度上做出了本次对比中独一无二的「会计学正确性」——DB 层强不超发 + 执行前预留 + 结算幂等 + UNKNOWN 不释放的双向对账闭环——但同时在「成本治理的运营面」上留有明确缺口：定价无版本、并发未限、报表无单位经济学、异常只有一条规则；下一步的正确顺序不是继续加机制，而是先把「已存在但未生效/未接线」的东西接上线、把定价与 token 计量这两个「数字变真」的基础补掉，再用软预算、降级路由与异常检测把「治理」从「拦截」升级为「调度」。**
