## 一、维度定义与评估坐标系

### 1.1 这个维度到底解决什么问题（问题陈述，不谈实现）

"部署与伸缩"回答的不是"agent 能跑多快"，而是**"当负载变成一个变量时，系统凭什么还成立"**这一组元问题：

- **启动形态**：交付物是什么？一个进程、一组进程、还是一个由平台托管的运行时？运维要手工装多少东西、配多少个环境变量、起几类进程，才能从"代码"走到"能接流量"？
- **状态归属**：进程被杀、被重建、被调度到另一台机器时，**权威状态**在哪里？如果状态在进程内存里，扩容就是复制不确定性；如果状态在外部存储，扩容就是加无状态副本。
- **并发配比**：一次 Run 从"排队"到"执行"要穿过几层并发闸门？每层各允许多少个在途？三层配错时，是"吞吐上不去"、"消息重复处理"还是"数据库被打爆"？
- **故障域**：一个租户的长任务 / 高并发 / 坏消息，会不会拖垮其他租户？一个大池子挂了，是全部停摆还是只损失 1/N？
- **容量与过载**：QPS 翻倍时，先扩容谁、扩到几个、上限由什么决定？当"生产快于消费"时，是排队、降级、还是拒绝？拐点在哪里、怎么测出来？
- **变更与停机**：发版时如何不丢在途任务？Pod 被 SIGTERM 时，未完成的 Run 是"体面收尾"、"租约自然过期被接管"，还是"永久卡在 RUNNING 且无报错"？

这一维度是**所有其他维度的物理承载层**：维度 02 的 RLS GUC 绑定依赖"每个连接都正确绑定租户上下文"；维度 03 的租约 / fencing 依赖"多实例共享同一 DB 且时钟可比"；维度 09 的预算原子预留依赖"连接池不被打满导致事务排队"；维度 11 的 UNKNOWN 对账依赖"崩溃恢复扫描器真的在跑"。部署层选错，上面所有严谨设计都可能在生产里**一次都不执行**（本项目源码里已反复记录这类"断链"事故，见 `WorkerLoopConfig.java:62-68`、`RunRecoverySweeper.java:22-25`）。

### 1.2 能力分层的四档模型（通用分层法）

按"伸缩由谁驱动、故障域由谁切分、多租户由谁隔离"给出四档，从弱到强：

| 档位 | 名称 | 伸缩触发 | 状态/故障域 | 代表形态 | 典型代价 |
|---|---|---|---|---|---|
| **L0 单点手工** | 单机单进程 | 人工换更大机器（垂直） | 进程内存持有状态，单故障域 | 开发期单 jar、Notebook | 崩了全丢；扩容=停机迁移；无灰度 |
| **L1 手工多实例** | 无状态进程 + 外部化配置 | 人工起 N 个副本 | 状态外置到 DB，但副本数靠人拍 | **本平台（现状）**、库形态 SDK 自建服务 | 扩缩容慢；并发参数靠人配；无队列深度驱动；多租户共享池 |
| **L2 编排平台驱动** | HPA / KEDA / 队列深度伸缩 | 指标或队列深度自动触发 | 无状态容器 + preStop 优雅停机 + 配额隔离 | K8s + KEDA、自托管 LangGraph Agent Server（split API/queue）、Agno AgentOS 多副本 | 需自己维护控制面、指标口径、优雅停机契约 |
| **L3 托管运行时** | Serverless 式弹性 | 平台自动伸缩（含 scale-to-zero） | 平台切分故障域 / cell / 沙箱 | Vertex AI Agent Engine、LangSmith Cloud、Claude Managed Agents、CrewAI AMP Cloud | 供应商锁定；数据驻留 / 合规边界；黑盒容量模型 |

**判定**：本平台落在 **L1 上沿**——它已经把「状态外置到 DB」「配置外部化」「部署参数 fail-closed」「进程内优雅停机」「代码级灰度上限」这些 L1/L2 的地基打得很扎实，但**伸缩触发仍是人工**（`scripts/dev-backend.sh` 起一个 fat jar，多副本靠人配 `AGENT_TENANT_SLUGS` 与 `agent.worker.id`），**没有 HPA/KEDA**、**没有 preStop 编排**、**没有租户级并发准入**、**没有容量基线**。与 L3 托管竞品的差距不是"功能少"，而是**运维责任主体不同**：他们的运行时替用户承担了伸缩、故障域切分与过载防护，我们把它留给了运维手册与环境变量。

### 1.3 评估坐标系：5 个评价轴

| 轴 | 含义 | 观测方式（如何度量） |
|---|---|---|
| **伸缩触发自动化程度** | 副本数由人、由指标、还是由队列深度决定 | 注入 N 倍积压（`outbox_event` / `agent_message_queue` PENDING 行数），观察 60s 内副本数是否变化；无变化即人工档 |
| **状态无状态化程度** | 进程内是否持有不可重建的权威状态 | 杀掉任一 Worker 实例 → 观察在途 Run 是否由其他实例凭 DB 租约接管、副作用是否恰好一次（12-Factor VI 的 sticky-session 反例检测） |
| **单点与故障域隔离** | 是否存在「挂一个全停」的组件；故障是否按租户 / cell 收敛 | 列出所有常驻线程与单例（relay / sweeper / listener / 调度器），逐一问「多实例是否安全、靠什么互斥」；注入单租户毒消息观察其他租户是否继续被消费 |
| **多租户隔离强度** | 一个租户的长任务/高并发能否饿死他人 | 同池注入「租户 A 持续投递 1000 条长任务 + 租户 B 1 条短任务」，量 B 的排队时长；检查是否有按租户的并发准入、独立池或公平调度 |
| **容量可预测性与过载防护** | 有无容量基线、拐点、背压、连接数上限公式 | 压测出单实例吞吐 / P95 拐点；核对 `实例数 × 每实例连接数 ≤ PG max_connections − 预留`；检查高水位背压是否真能停发 |

## 二、理论体系（必须引用真实出处）

### 2.1 核心理论 / 概念框架（8 个，逐一给真实出处）

#### (1) 12-Factor App：VI. Processes（无状态）与 VIII. Concurrency（进程模型）

- **出处**：Adam Wiggins（Heroku 联合创始人），*The Twelve-Factor App*，2011。官方页：https://12factor.net/processes 、https://12factor.net/concurrency 。
- **定义（已逐字核对）**：
  - VI：「**Twelve-factor processes are stateless and share-nothing**. Any data that needs to persist must be stored in a stateful backing service, typically a database.」并明确「**Sticky sessions are a violation of twelve-factor and should never be used or relied upon**」——进程内存 / 本地磁盘只能当单事务内的短暂缓存，不能假设下次请求还落在同一进程。
  - VIII：「**Scale out via the process model**」——把不同类型的工作分配给不同 *process type*（web / worker），「**the share-nothing, horizontally partitionable nature ... means that adding more concurrency is a simple and reliable operation**」；「进程构成（process formation）= 每种 process type 各跑几个」；进程「should never daemonize or write PID files」，交给 OS / 平台的进程管理器处理崩溃重启与停机。
- **与本维度的关系**：本平台的「无状态 worker + DB 事实源」正是 VI 的教科书实现——`RunDispatchConsumer` 不信任 MQ payload 的任务状态，领取后重读 DB（`docs/系统架构图.md:349`），权威状态全在 PG。VIII 则指出我们的**准确短板**：我们只有一个 fat jar 的 process type（`agent.worker.enabled` 只切「要不要在本进程里跑 worker」，不是两个独立构建产物），且**没有进程管理器**——`OutboxRelay` / `PgQueueListener` 自己在 `start()` 里 `new Thread(...).setDaemon(true)`（`OutboxRelay.java:170-193`、`PgQueueListener.java:333-371`），这正是 12-Factor 明确反对的「进程自己 daemonize」。

#### (2) 云原生伸缩：Kubernetes HPA / VPA / KEDA（含队列深度驱动）

- **出处（官方文档）**：
  - Kubernetes *Horizontal Pod Autoscaling*：https://kubernetes.io/docs/tasks/run-application/horizontal-pod-autoscale/
  - Kubernetes *Vertical Pod Autoscaler*（kubernetes/autoscaler 子项目）：https://github.com/kubernetes/autoscaler/tree/master/vertical-pod-autoscaler
  - KEDA *PostgreSQL scaler*：https://keda.sh/docs/latest/scalers/postgresql/ ；*RabbitMQ Queue scaler*：https://keda.sh/docs/latest/scalers/rabbitmq-queue/
- **定义（已核对）**：
  - HPA 是控制面里的一个控制回路，默认 `--horizontal-pod-autoscaler-sync-period=15s`，核心算式 `desiredReplicas = ceil(currentReplicas × currentMetricValue / desiredMetricValue)`；多指标取各指标算出的最大副本数；缩容有默认 5 分钟的 `--horizontal-pod-autoscaler-downscale-stabilization` 平滑窗口。HPA 只作用于有 `scale` 子资源的负载（Deployment / StatefulSet），**不能用于 DaemonSet**。
  - VPA 自动设置容器 CPU / 内存 requests 与 limits（recommender / updater / admission-controller 三组件），是**垂直**伸缩，与 HPA 的水平伸缩互补；官方 README 明确 VPA 与「pod-level resources stanza」当前不兼容。
  - KEDA 用 `ScaledObject` CRD 把任意指标源接成 HPA 的 external metric，并支持 **scale-to-zero**。`postgresql` trigger 的 `query` 必须返回单个数值，配 `targetQueryValue` / `activationTargetQueryValue`（官方示例：`SELECT ceil(COUNT(*)::decimal / 16) FROM task_instance WHERE state='running' OR state='queued'`，并提醒用 `COALESCE` 处理 NULL）。`rabbitmq` trigger 的 `mode: QueueLength` + `value`（旧的 `queueLength` 已 DEPRECATED）按队列深度伸缩，官方原文：「if one pod can handle 10 messages ... If the actual number of messages in the queue is 30, the scaler will scale up to 3 pods」。
- **与本维度的关系**：这是改进点 1 的直接理论依据。**队列深度才是 worker 型负载的正确伸缩信号**——CPU 是滞后且会被 IO 等待污染的信号；LangGraph Agent Server 官方也明确「queue workers scale on pending run count」（见 §3.3）。

#### (3) Cell-Based Architecture 与 Bulkhead（舱壁 / 故障爆炸半径）

- **出处（官方）**：
  - AWS Well-Architected Framework，*REL10-BP04 Use bulkhead architectures to limit scope of impact*：https://docs.aws.amazon.com/wellarchitected/2023-04-10/framework/rel_fault_isolation_use_bulkhead.html
  - AWS 白皮书 *Reducing the Scope of Impact with Cell-Based Architecture*，发布日 2023-09-20：https://docs.aws.amazon.com/wellarchitected/latest/reducing-scope-of-impact-with-cell-based-architecture/reducing-scope-of-impact-with-cell-based-architecture.html
  - AWS *Guidance for Cell-Based Architecture on AWS*：https://aws.amazon.com/solutions/guidance/cell-based-architecture-on-aws/
  - Bulkhead 模式命名来自 Michael T. Nygard，*Release It! Design and Deploy Production-Ready Software*（Pragmatic Bookshelf，2007；2nd ed. 2018）；Azure 架构中心条目：https://learn.microsoft.com/en-us/azure/architecture/patterns/bulkhead
- **定义（已核对）**：REL10-BP04 原文：「cell 是工作负载的多个**独立实例**，每个 cell 独立、不与其他 cell 分享状态（路由器层除外），只处理请求的一个子集。**如果 10 个 cell 服务 100 个请求，故障时 90% 的请求不受影响**」。分区键（partition key）示例：客户 ID / 资源 ID；cell 路由层按分区键把请求分发到单个 cell 并对客户端提供单一端点。官方列的反模式：「让 cell 无限制地发展」「**同时把代码更新或部署应用到所有 cell**」「在不同 cell 之间分享状态或组件」「**向路由器层添加复杂的业务或路由逻辑**」。AWS Guidance 的 Step 6 明确「Updates are first deployed to a **canary cell**」——cell 与金丝雀是组合技。
- **与本维度的关系**：改进点 6 的直接依据，也是「吵闹邻居」在**故障域**层面的答案：按租户分组到不同 cell，把「一个租户的毒请求 / 一次坏发布」的爆炸半径从 100% 降到 1/N。

#### (4) 部署策略：蓝绿 / 金丝雀 / 滚动更新

- **出处（官方）**：
  - Martin Fowler，*BlueGreenDeployment*，2010-03-01：https://martinfowler.com/bliki/BlueGreenDeployment.html
  - Danilo Sato（署名于 martinfowler.com），*CanaryRelease*，2014-06-25：https://martinfowler.com/bliki/CanaryRelease.html
  - Kubernetes Rolling Update：https://kubernetes.io/docs/concepts/workloads/controllers/deployment/#rolling-update-deployment
- **定义（已核对）**：蓝绿 = 两套「尽可能一致」的生产环境，任一时刻一套 live，切换靠改路由器；**回滚 = 把路由器切回去**；Fowler 特别指出「数据库往往是这个技术的难点」，解法是**把 schema 变更与应用升级分离**（先做兼容新旧两版的 DB 重构，再切应用）。金丝雀 = 先把新版本部署到一小部分基础设施且**不路由用户**，再按随机抽样 / 内部员工 / 用户画像逐步放量；「A canary release ... rollback strategy is simply to reroute users back to the old version」；其额外收益是「capacity testing of the new version in a production environment with a safe rollback」；代价是「**you have to manage multiple versions of your software at once**」。滚动更新是 K8s Deployment 的默认策略，逐批替换 Pod。
- **与本维度的关系**：本平台当前的「灰度」是**产品级租户准入灰度**（`pilot.max-tenants` + `AGENT_TENANT_SLUGS`），不是**版本发布灰度**——这两件事常被混为一谈。改进点 5 要把「单租户试点 → 多租户」做成 DB 配置 + 灰度百分比 + 自动回滚，就必须补上 Fowler 强调的「多版本并存」与「schema 变更先行」纪律。

#### (5) 容量规划与排队论：Little's Law、利用率—延迟非线性、Google SRE Handling Overload

- **出处（已核对）**：
  - John D. C. Little，*"A Proof for the Queuing Formula: L = λW"*，*Operations Research* 9(3): 383–387，1961（DOI 10.1287/opre.9.3.383）。
  - Betsy Beyer / Chris Jones / Jennifer Petoff / Niall Richard Murphy（编），*Site Reliability Engineering: How Google Runs Production Systems*，O'Reilly，2016，Chapter 21 *Handling Overload*、Chapter 22 *Addressing Cascading Failures*：https://sre.google/sre-book/handling-overload/
  - HikariCP Wiki，*About Pool Sizing*：https://github.com/brettwooldridge/HikariCP/wiki/About-Pool-Sizing
- **定义（已核对）**：Little's Law `L = λW`（系统中的平均请求数 = 平均到达率 × 平均驻留时间），1961 年的原始证明不要求泊松到达 / 指数服务时间 / 特定排队纪律，只要求稳态与均值存在。它给出**容量 sizing 的恒等式**：要撑 1000 QPS、P95 50ms，就必须容纳 `1000 × 0.05 = 50` 个并发在途。而利用率—延迟的非线性来自排队模型：M/M/1 的驻留时间 `W = 1/(μ − λ)`，当利用率 `ρ = λ/μ → 1` 时分母趋零、延迟发散；这不是「慢一点」，是**拐点后崩塌**。
  - SRE Ch.21 的实践结论：①「**The Pitfalls of "Queries per Second"**」——不同请求资源消耗差异极大，应以可用资源（CPU 核 / 内存）或归一化 CPU time 建模容量，而非 QPS；② **Per-Customer Limits**——全局过载时「只给行为不端的客户返回错误，其他客户不受影响」，按协商用量定义 per-customer quota；③ 客户端自适应节流（2 分钟窗口内 requests vs accepts，`requests > K × accepts` 时按概率本地拒绝，K 默认 2）；④ Criticality 四级（CRITICAL_PLUS / CRITICAL / SHEDDABLE_PLUS / SHEDDABLE），过载时先丢最低关键性；⑤ 降级响应（stale cache / 缩小候选集）。Ch.22 补充：级联失败的症状是「in-flight 请求数上升 + 队列变长 + 线程饥饿」，稳态系统应「keep your request queue length small」（经验值 > 线程池大小 50% 即拒），并「Always use randomized exponential backoff」+ 全局重试预算。
  - HikariCP：经验公式 `connections = ((core_count × 2) + effective_spindle_count)`；「**You want a small pool, saturated with threads waiting for connections**」；PG 基准里 TPS 约在 50 连接后走平；防 pool-locking 的最小池 `pool size = Tn × (Cm − 1) + 1`。
- **与本维度的关系**：改进点 4（连接池 / PG 容量公式）、改进点 7（容量基线与压测）、改进点 2（per-customer 配额即 SRE 的 Per-Customer Limits）三条共同的数学底座。

#### (6) 吵闹邻居与资源隔离：cgroups v2、Kubernetes QoS、ResourceQuota

- **出处（官方）**：
  - Linux Kernel，*Control Group v2*（自称 "the authoritative documentation"）：https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html
  - Kubernetes，*Configure Quality of Service for Pods*：https://kubernetes.io/docs/tasks/configure-pod-container/quality-service-pod/ ；*Resource Quotas*：https://kubernetes.io/docs/concepts/policy/resource-quotas/
- **定义（已核对）**：cgroup v2 是「organize processes hierarchically and **distribute system resources** along the hierarchy in a controlled and configurable manner」，单一层级树，子层只能**进一步收紧**不能覆盖父级限制；`cpu` controller 有 `cpu.weight`(默认 100，范围 1–10000) 与 `cpu.max`（`$MAX $PERIOD` 绝对带宽上限）、`memory` 有 `memory.high`（throttle，不触发 OOM）与 `memory.max`（硬限，触发 OOM）、`io` 有 `io.weight` / `io.max`；资源模型分 Weights / Limits / Protections / Allocations 四类。K8s 依 requests/limits 把 Pod 分三档 QoS：**Guaranteed**（每个容器 CPU/内存 limit == request）、**Burstable**（不满足 Guaranteed 但至少一个 request/limit）、**BestEffort**（全无），节点资源超限时按 QoS 决定驱逐顺序。
- **与本维度的关系**：`cgroups` 解决的是「同一台机器上进程之间」的隔离，K8s QoS / ResourceQuota 解决「同一集群里 Pod 之间」的隔离；但**都解决不了「同一进程内同一线程池里，租户 A 的 1000 条长任务排在租户 B 前面」**——那是应用层调度问题（见 §4.2 D-8 与改进点 2）。

#### (7) Graceful Shutdown 与 Pod 终止生命周期

- **出处（官方）**：
  - Kubernetes，*Pod Lifecycle — Termination of Pods*：https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#pod-termination
  - Kubernetes，*Container Lifecycle Hooks*：https://kubernetes.io/docs/concepts/containers/container-lifecycle-hooks/
- **定义（已核对）**：Pod 默认 `terminationGracePeriodSeconds = 30`。`PreStop` hook「**is called immediately before a container is terminated ... and the hook must complete before the TERM signal to stop the container can be sent**」，且「**PreStop hooks are not executed asynchronously from the signal**」——hook 挂住则 Pod 一直 `Terminating`，直到宽限期耗尽被杀；宽限期倒计时**在 preStop 执行前就开始**，覆盖「hook 执行 + 容器正常停止」的总时长（官方举例：宽限 60s，hook 55s + 进程 10s ⇒ 进程来不及体面停止即被杀）。hook 交付语义是 **at-least-once**，可能重复投递，实现必须幂等。Endpoint 摘除与 SIGTERM 是并发发生的，因此常见做法是 preStop 里先短暂 sleep 让 endpoint 传播，再进入 drain。
- **与本维度的关系**：改进点 3 的规范依据。本平台**已有进程内停机编排**（§4.2 D-9），但缺 K8s 生命周期契约与「等待在途完成 / 主动释放租约」两件事。

#### (8) 数据库连接池与 PG max_connections 的容量约束、PgBouncer

- **出处（官方）**：
  - PostgreSQL 18 文档，*19.3.1 Connection Settings*：https://www.postgresql.org/docs/current/runtime-config-connection.html
  - PgBouncer，*Features*：https://www.pgbouncer.org/features.html ；配置：https://www.pgbouncer.org/config.html
  - HikariCP Wiki（同 (5)）：https://github.com/brettwooldridge/HikariCP/wiki/About-Pool-Sizing
- **定义（已核对）**：`max_connections`「The default is typically **100** connections ... **PostgreSQL sizes certain resources based directly on the value of max_connections. Increasing its value leads to higher allocation of those resources, including shared memory**」；另有 `superuser_reserved_connections`（默认 3）与 `reserved_connections`。PgBouncer 三种池化模式：**session**（连接整个会话期绑定，支持全部 PG 特性）、**transaction**（仅事务期绑定 server 连接，吞吐最高）、**statement**（禁止多语句事务）；官方 SQL feature map 明确 **`SET` / `RESET` 在 transaction pooling 下是 "Never"**，`LISTEN` 也是 Never，`session-level advisory locks` 是 Never。
- **与本维度的关系**：改进点 4 的硬约束。**重要兼容性告警**：本平台 `application.yml:29` 的 `spring.datasource.hikari.connection-init-sql: SET search_path TO public` 是**会话级 SET**，若改用 PgBouncer transaction pooling 将不生效（官方标 Never），必须改成事务内 `set_config` 或采用 session pooling；而 RLS 的 GUC 绑定按铁律 1 是「事务内、业务 SQL 前」的 `set_config('app.tenant_id', ..., true)`，属事务局部，反而与 transaction pooling 相容。这是评估 PgBouncer 时**必须写进方案的源码级细节**。

### 2.2 理论给出的「设计张力」清单（A vs B）

| # | 张力 | A 方案 | B 方案 | 本平台选择 / 后果 |
|---|---|---|---|---|
| T1 | 状态放哪 | 进程内存（快、低延迟） | 外部 DB（可重建、可扩容） | 选 B（VI）。代价：每次领取重读 DB、RLS GUC 每次事务绑定，DB 成为唯一瓶颈 |
| T2 | 伸缩信号 | CPU / 内存（通用、易得） | 队列深度 / 积压数（对 worker 精准） | 现状两者皆无（人工）；改进点 1 选 B |
| T3 | 副本数 | 固定 N（可预测、容量好算） | 自动弹性（省成本、抗突发） | 选 A。代价：峰值靠超配、低谷白付；但 PG 连接数上限反而好算 |
| T4 | 消息通道 | 外部 broker（解耦、吞吐高） | DB 表即队列（少一个依赖、同事务边界） | **默认选 B**（`mode=database`），Rabbit 可选。B 让「MQ 伸缩」这一层整个消失，也把队列压力搬进 PG |
| T5 | 并发闸门 | 单层大池（简单） | 三层分级（prefetch / 线程池 / 行锁） | 选 B。代价：**三层配比极易错配**，默认部署下 ①② 实际未生效（§4.5） |
| T6 | 多租户 | 共享 worker 池（利用率高） | 按租户独立池 / cell（隔离强） | 选 A。代价：吵闹邻居无防护（§4.2 D-8） |
| T7 | 灰度控制 | 文档约定 / 人工审批 | 代码强制 + fail-closed | 选 B（`WorkerPolicy`）。代价：白名单硬编码、扩租户要改 yml 重打包 |

| T9 | 过载 | 无限排队（不拒请求） | 背压 + 降级 + per-customer 拒绝 | 部分：全局高水位背压（`high-watermark=1000`），**无 per-customer 限流** |
| T10 | 连接池 | 每实例大池（少等待） | 小池 + PgBouncer（保护 PG） | 现状：主池 10 + 运维池 2 + 清理池 2，未评估 PgBouncer；实例数受 `max_connections` 硬约束 |
| T11 | 版本发布 | 一刀切全量 | 蓝绿 / 金丝雀 / 滚动 | 现状无版本发布策略；产品级灰度是「租户准入」而非「版本比例」 |
| T12 | 故障域 | 大池共享（成本低） | Cell 化（爆炸半径 1/N） | 选 A。代价：一次坏发布 / 一次 DB 抖动影响全部租户 |

### 2.3 业界公认的反模式清单及判别方式

| # | 反模式 | 判别方式（可执行） |
|---|---|---|
| AP1 | **Sticky session / 进程内会话状态**（违反 12-Factor VI） | 杀掉任一实例，观察该实例「专属」的在途请求是否永久丢或 500；查代码是否有 `static Map<sessionId, state>` 且无外部持久化 |
| AP2 | **Vertical-only scaling**（VIII 反例） | 负载翻倍时唯一手段是加 CPU/内存；`replicas` 字段常年为 1 且无 HPA 对象 |
| AP3 | **CPU 驱动 worker 伸缩** | HPA 目标为 CPU 但队列持续积压——LLM 调用是 IO 等待型，CPU 低而 backlog 高，HPA 不扩容 |
| AP4 | **three-layer 并发配比失配** | `prefetch × concurrency ≫ DB 有效并发`，或 `线程池 ≫ 连接池`；表现为大量消息被 prefetch 到内存却等人、或连接池排队打满、或 `SKIP LOCKED` 空转 |
| AP5 | **无互斥的多实例轮询发布** | 对 `outbox` 类表用裸 `SELECT ... LIMIT` 领任务（无 `FOR UPDATE SKIP LOCKED`、无 CAS 状态更新）；N 个实例同时领到同一批 → 重复发布 |
| AP6 | **共享池 + 无配额（吵闹邻居）** | 注入单租户洪泛，量其他租户排队时长；若 > 基线 10× 且无按租户准入/公平调度，即命中 |
| AP7 | **无限队列 / 无背压** | 队列深度单调递增且无高水位停发、无告警、无死信；SRE Ch.22 的级联失败前兆 |
| AP8 | **优雅停机假象** | 只看「进程退出了」不看「在途任务收敛」；判别：SIGTERM 期间查询 `run.state='RUNNING' AND lease_expires_at < now()` 是否出现孤儿，以及是否有 `preStop` / `terminationGracePeriodSeconds` 配置 |
| AP9 | **连接池随实例数线性膨胀** | 算 `实例数 × 每实例池大小 > max_connections − 预留`；判别：扩容到 N 后 PG 报 `sorry, too many clients` |
| AP10 | **配置漂移 / 死键** | 同一个语义有两个配置键、其中一个无读取点；判别：全仓 grep 键名，`effectiveFlags` 是否标 false（本项目 `ConfigReadService` 已内建此检测） |
| AP11 | **硬编码白名单当灰度** | 扩量需改源码/打包/重启；判别：灰度上限是否可在不发版的情况下变更、是否有审计与回滚 |
| AP12 | **同时向所有 cell / 所有副本推发布**（AWS 明列反模式） | 部署流水线是否只有「全量」一个按钮、有无 canary cell / 分批 |
| AP13 | **QPS 当容量指标**（SRE Ch.21） | 容量文档只写「支持 X QPS」，不区分 Run 步数 / 工具数 / 模型耗时；压测用同一种请求 |
| AP14 | **测试替生产兜底拓扑** | 集成测试里 `declareBinding`、生产代码里没声明；判别：换一个全新环境是否仍能跑通（`WorkerLoopConfig:162-166` 记录了本项目真实踩过的这一形态） |

### 3.1 OpenAI Agents SDK —— 库形态，宿主自建服务

- **官方定位与实现机制**：极简 Python/JS 包（`pip install openai-agents`），核心原语 `Agent`（LLM + instructions + tools）、`Runner`（`run_sync` / 流式）、Handoffs、Guardrails、Sessions、内建 Tracing。官方文档原文把它描述为「a lightweight, easy-to-use package with very few abstractions」，并用「higher-level runtime」指 **SDK 进程内部**管理 turns / tool execution / guardrails 的循环，**不是托管运行时**。
- **官方来源**：https://openai.github.io/openai-agents-python/ （中文 https://openai.github.io/openai-agents-python/zh/ ，仓库 https://github.com/openai/openai-agents-python ）
- **优点**：零运维依赖、启动即一个进程、部署完全自由（可塞进任何已有服务 / FaaS）；对「给现有产品加一个 agent 能力」最轻。
- **局限/代价**：**部署、伸缩、隔离、优雅停机、连接池全部由宿主自己负责**；SDK 不提供队列、不提供任务持久化、不提供多租户原语（隔离靠 `thread_id` 等作用域交宿主）。**诚实标注**：官方首页**未逐字写**「no hosted runtime / 部署在你自己的基础设施」，只从「pip 安装 + `Runner` 在应用进程内执行」可判定为库形态——本报告按「官方未明示、但工程上可判定」表述，不臆造引文。
- **适用场景**：原型、单体应用内嵌、已有成熟运维体系的产品加 agent 功能。

### 3.2 Anthropic Claude Agent SDK + Claude Managed Agents —— 库 + 托管的双形态

- **官方定位与实现机制**：官方 overview 明确用「**who runs the agent**」区分四种工具：
  - **Agent SDK**：「Embed Claude Code's agent in your own Python or TypeScript application, **in a process you operate**」；「A library that runs the Claude Code binary」，提供 built-in tools / permissions / sessions / hooks / subagents / MCP / Skills。即**库形态**。
  - **Managed Agents**：「**Have Anthropic host the agent**, configured through the Claude API」；官方定义为「A hosted agent harness that runs the agent loop, with sessions in an **Anthropic-managed cloud sandbox** or a **self-hosted sandbox** on your own infrastructure」，可通过语言 SDK、`ant` CLI、REST API 使用；支持 stateful sessions、持久事件历史、Cron 调度、自托管 sandbox 的 Kubernetes 部署。
- **官方来源**：Agent SDK https://code.claude.com/docs/en/agent-sdk/overview （原 `https://docs.anthropic.com/en/api/agent-sdk/overview` → `https://platform.claude.com/docs/en/api/agent-sdk/overview` → 现域名，三级重定向已核实）；Managed Agents https://platform.claude.com/docs/en/managed-agents/quickstart 、https://platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes 。（竞品报告登记的 https://docs.anthropic.com/en/api/agent-sdk 已迁移。）
- **优点**：**同一厂商同时给「自己跑」与「托管跑」两条路**，且托管侧提供 sandbox 隔离、session 持久化、调度，等于把 §1.2 的 L1 与 L3 一次性覆盖；self-hosted sandbox 兼顾数据驻留。
- **局限/代价**：托管是云 sandbox，模型与平台强绑定；官方页明确第三方产品不得提供 claude.ai login / rate limits、须遵守 Commercial Terms、产品不得看起来像 Claude Code。托管侧按 session 运行时长计费（官方 FAQ 提到 token 费 + 每小时 session 费）。

### 3.3 LangGraph / LangSmith Agent Server —— 自带运行时、队列 worker 分离、按 pending run 数伸缩

- **官方定位与实现机制**（官方页逐字核对，是本维度最贴近的竞品）：
  - Agent Server 是「a workflow orchestration runtime for agent workloads」，一次部署 = 若干 graphs + **PostgreSQL 持久化** + **task queue**。API server 收到 run 创建请求后「enqueues it and a **queue worker** picks it up」；**Redis 只做 signaling / cancellation / streaming pub-sub，不存用户或 run 数据**，run 数据恒读写 PostgreSQL。
  - 三种 deployment mode：**Single host**（默认，无独立 worker）、**Split API and queue**（`queue.enabled: true`，「Each tier scales independently — **API servers scale on request volume, queue workers scale on pending run count**」）、**Distributed runtime**（orchestration 与 execution 再拆）。
  - 容器「**stateless but persistent**」，API server 与 queue worker 是**两个独立容器池**且「scale independently」；「At least 1 queue worker must listen ... to ensure no runs are orphaned」；每个 worker 「executes up to `N_JOBS_PER_WORKER` runs concurrently (default: 10)」；队列强制「at most 1 run can be executed for a given thread at one time」，worker「acquires a **lease** on it」。
  - 内建 cron jobs、checkpointer（Postgres 默认，可换 Mongo）、Store（长期记忆）。
- **官方来源**：https://docs.langchain.com/langsmith/agent-server （应用结构 https://docs.langchain.com/langsmith/application-structure 、伸缩调优 https://docs.langchain.com/langsmith/agent-server-scale 、数据面自动伸缩 https://docs.langchain.com/langsmith/data-plane#autoscaling ）
- **优点**：**与本平台架构同构度最高**——「DB 事实源 + 队列 worker + 租约 + 无状态容器」，但人家把它**产品化**了：queue worker 按 pending run count 独立伸缩（正是本报告改进点 1 想做的事）、`N_JOBS_PER_WORKER` 把「进程内并发」变成一等配置、split 模式把控制面与执行面拆成两个独立伸缩池。
- **局限/代价**：自托管要自己搭 PG + Redis + 多类容器；`N_JOBS_PER_WORKER` 是**每 worker 固定值**而非队列驱动，仍需上层 HPA/KEDA 才能自动扩副本；控制面（LangSmith）与云版有商业绑定；多租户隔离仍主要靠 `thread_id` / assistant 作用域，不是 DB 强制 RLS。
- **适用场景**：需要 durable execution + 自主可控部署 + 已有 K8s 运维能力的团队。

### 3.4 Google ADK / Vertex AI Agent Engine（Agent Runtime）—— 端到端托管、自动伸缩含 scale-to-zero

- **官方定位与实现机制**：`adk deploy agent_engine` 一条命令「packages your code, **builds it into a container**, and deploys it to the **managed Agent Runtime** service」；Agent Engine 是「fully managed runtime」，官方 startup guide 明确「**Automated scalability: Automatically handles scaling to meet varying user loads**」，并「optimized to be a cost-effective, **auto-scaling** solution」，抽象掉底层基础设施；另有「session persistence, **auto-scaling (including scale-to-zero during idle time)**, and Cloud Trace integration out of the box」。支持 sessions / Memory Bank / Example Store，模型与部署无关（也可部署 LangGraph、CrewAI 写的 agent）。
- **官方来源**：https://adk.dev/deploy/agent-engine/deploy 、https://adk.dev/deploy/agent-runtime/ 、https://cloud.google.com/blog/products/ai-machine-learning/more-ways-to-build-and-scale-ai-agents-with-vertex-ai-agent-builder/
- **优点**：**运维负担最低**——伸缩、会话持久化、监控、评估全托管，含 scale-to-zero；对「不想养运维团队」的团队是 L3 的标杆。
- **局限/代价**：GCP 强绑定、黑盒容量模型（无法按自己的 `max_connections` 公式推容量）、数据驻留与合规边界由平台决定；托管运行时不暴露 MQ prefetch / 线程池 / 行锁这类可调层，调优手段是平台参数而非源码。
- **适用场景**：GCP 上从原型直上生产、愿意以供应商锁定换零运维。

### 3.5 Microsoft AutoGen —— 库形态（已归档停维护，仅作参照）

- **官方定位与实现机制**：Core（事件驱动运行时）+ AgentChat（对话 API）+ Extensions；**AutoGen Studio 是开发/原型工具，不是生产运行时**。2025-10-01/02 官方公告 AutoGen 与 Semantic Kernel 合并为 **Microsoft Agent Framework**，AutoGen 进入 maintenance mode（「will not be adding significant new features」）；2026-10 起官方 README 标注 **archived / no longer maintained**。
- **官方来源**：https://microsoft.github.io/autogen/stable/ 、https://devblogs.microsoft.com/foundry/introducing-microsoft-agent-framework-the-open-source-engine-for-agentic-ai-apps/ 、https://learn.microsoft.com/en-us/agent-framework/overview
- **优点**：历史贡献是多智能体编排范式（GroupChat / GraphFlow）；作为库，部署自由度高。
- **局限/代价**：**不应作为新项目选型依据**（官方已归档）；无生产级托管运行时、无内建多租户隔离、无队列/伸缩产品化。对本维度的意义是「反面参照」：库形态的尽头就是把所有部署责任推给宿主。
- **适用场景**：仅作历史对比 / 已有存量迁移评估。

### 3.6 CrewAI —— 库 + 企业版 Control Plane / AMP（云 / 自托管 / 混合）

- **官方定位与实现机制**：开源是 `Crew = Agents + Tasks + Process` + `Flows` 的 Python 库；企业侧 `crewai deploy --prepare` / `crewai deploy` 把 crew/flow 部署到 **CrewAI AMP（Agent Management Platform）**，部署后得到 REST endpoint（`POST /api/v1/crews/<id>/kickoff`）。三种部署形态：**Cloud**（app.crewai.com 托管）、**Factory（Self-Hosted，跑在自己基础设施，带数据驻留/合规控制）**、**Hybrid**；AMP 提供 traces / logs / 性能观测、Crew Studio（低代码）、SSO/RBAC、工具仓库、Agent Control Plane（运行时策略：PII 检测、允许模型与工具、执行时间窗、成本上限）。
- **官方来源**：https://docs.crewai.com/ 、https://www.crewai.com/ 、https://docs-platform.crewai.com/platform/guides/deploy-to-amp
- **优点**：从 `crewai create crew` 到生产 endpoint 的链路最短之一；企业侧把「运行时治理」与「部署」合在一个控制面；自托管形态兼顾合规。
- **局限/代价**：伸缩细节（副本、队列、自动扩缩）官方部署文档未逐字明示，属控制面黑盒；RBAC / 审计 / 成本记账只在企业层；多租户隔离是组织级而非 DB 强制行级。
- **适用场景**：业务团队快速把流程自动化上线、且愿意用企业控制面换运维简化。

### 3.7 Agno —— AgentOS 自带 FastAPI 运行时 + 容器化 / 多副本

- **官方定位与实现机制**：AgentOS「serves agents, teams, and workflows through a **FastAPI application you own and host**」；`AgentOS(...).get_app()` 组装路由，`serve()` 用 Uvicorn 起服务（`AGENT_OS_HOST` / `AGENT_OS_PORT` 默认 localhost:7777）。可选能力一览：`authorization=True`（JWT）、`tracing=True`、`mcp=True`（MCP server）、`queue=QueueConfig(durable=True)`（**Durable Queue**）、`scheduler=True`（**Cron 调度**）、`interfaces`、`base_app`（嵌入已有 FastAPI）。官方明确「shutdown exits those managed lifespans and releases their resources」，并专门有 **multiple replicas** 文档处理共享取消与事件投递。
- **官方来源**：https://docs.agno.com/agent-os/overview 、https://docs.agno.com/agent-os/background-execution/durable-queue 、https://docs.agno.com/agent-os/background-execution/multi-replica 、https://docs.agno.com/agent-os/scheduler/overview
- **优点**：**自带运行时但完全自托管**，FastAPI 可嵌入既有服务；Durable Queue（`SELECT ... FOR UPDATE SKIP LOCKED` + 心跳租约 + 幂等键）与本平台思路高度同构且已产品化；有明确的多副本与 lifespan 停机语义。
- **局限/代价**：FastAPI 进程仍要自己容器化、配 HPA、配连接池；官方未给「按队列深度自动伸缩」的开箱实现；多租户安全虽内建（JWT/service-account/每用户隔离），但不是 DB 触发器级强制。
- **适用场景**：Python 栈、要自托管运行时又不想引入 LangGraph 全套控制面的团队。

### 3.8 竞品横向小结（本报告归纳）

| 竞品 | 形态分档 | 伸缩驱动 | 队列 / 运行时 | 多租户隔离 | 优雅停机 | 与本平台关系 |
|---|---|---|---|---|---|---|
| OpenAI Agents SDK | L1（库） | 宿主自建 | 无 | 无（thread 作用域） | 宿主自建 | 同「无运行时」，我们多了 DB 事实源与代码级灰度 |
| Claude Agent SDK | L1（库） | 宿主自建 | 无 | 无 | 宿主自建 | 同上 |
| Claude Managed Agents | L3（托管） | 平台自动 | 托管 session + sandbox | 平台 sandbox | 平台负责 | 我们无对应能力 |
| LangGraph Agent Server | L2/L3 | **pending run count** | task queue + PG + Redis | 作用域级 | 容器 stateless | **架构最同构、产品化最值得对标** |
| ADK Agent Engine | L3（托管） | 自动（含 scale-to-zero） | 托管 | 平台 | 平台负责 | 差距最大的一维 |
| AutoGen（归档） | L1（库） | 宿主自建 | 无 | 无 | 宿主自建 | 反面参照 |
| CrewAI AMP | L2/L3 | 控制面（细节未明示） | 企业控制面 | 组织级 RBAC | 平台 | 企业治理对标 |
| Agno AgentOS | L2（自托管运行时） | 宿主配 HPA | Durable Queue + Cron | 内建 JWT/每用户 | lifespan 释放 | **Durable Queue 同构** |
| **本平台** | **L1 上沿** | **人工** | **PG 表队列（默认）/ 可选 Rabbit** | **DB 强制 RLS（领先）** | **进程内部分实现** | — |

**结论**：在「隔离强度」与「配置安全取向」上本平台不输甚至领先；在「伸缩自动化」「托管运行时」「故障域切分」「租户级配额」上落后——且**落后不是能力缺失，而是「把运维责任留在自己这边」这一设计取舍的必然结果**（§5.3 详述根因）。

#### 4.1.1 交付物与启动形态：一个 fat jar 的模块化单体

`scripts/dev-backend.sh:19-26` 是全仓唯一的「生产启动」入口：


即**全部 13 个 Maven 模块打进一个可执行 jar，一个 JVM 进程同时跑控制面 API、OutboxRelay、PgQueueListener / Rabbit 消费容器、RunRecoverySweeper、上下文压缩、SSE 推送、指标采集**。`docs/系统架构图.md:351` 的「控制面和 Worker 可独立部署，但首期不拆成过多微服务」是**设计原则**，实际落地为「同一 jar + `agent.worker.enabled` 开关」的**进程级切分**：`WorkerLoopConfig` 由 `@ConditionalOnProperty(name = "agent.worker.enabled", havingValue = "true")`（`WorkerLoopConfig.java:90-93`）决定是否装配 worker 相关 Bean，`application.yml:188` 声明 `enabled: "true"`，`application.yml:50` 用 `AGENT_WORKER_ENABLED` 占位符同步控制 `spring.rabbitmq.listener.simple.auto-startup`。因此可跑「API-only 实例（`AGENT_WORKER_ENABLED=false`）+ N 个 worker 实例」，但**没有独立的 worker 构建产物、没有 Dockerfile、没有 k8s/helm manifest**（见 §4.5 不一致 8）。

配置全部来自 `platform.env` + `application.yml` 的 `${ENV:default}` 引用（`AGENT_TENANT_SLUGS`、`RAG_BASE_URL`、`AGENT_MESSAGING_MODE`、`SPRING_DATASOURCE_*` 等），符合 12-Factor III Config。`scripts/init-db.sh` 按依赖序灌 `deploy/sql/platform/01_platform_ddl.sql` → seed → roles → retention role；`scripts/dev-env-up.sh` 编排「PG + Rabbit + 冒烟 + 打包」。`monitoring/docker-compose.yml` 只有 Prometheus / Grafana，`deploy/docling/docker-compose.yml` 是文档解析服务——**都不是平台自身的部署清单**。

### 4.2 关键设计决策逐条剖析（决策 → 为什么 → 代价 → 证据锚点）

**D-1｜PostgreSQL 为唯一权威事实源，进程不持有权威状态（12-Factor VI）**
- 决策：`RunDispatchConsumer`「只负责把消息变成一次租约领取」，明确「不把 MQ payload 当作可信任务状态；必须重新读取数据库」（`docs/系统架构图.md:349`）；消费端 `handle()` 只用消息里的 `tenantId/runId/messageId` 绑定 RLS 与领取（`RunDispatchConsumer.java:199-203`）。
- 为什么：进程崩溃 / 重投 / 扩容后，能从任意租约点凭 DB 恢复；`UNKNOWN_RESULT` ack 丢弃不重投（`:70-71, :106-112`），重复副作用 = Sev-0。
- 代价：**数据库成为唯一且不可绕过的伸缩瓶颈**——RLS 每次事务 `set_config`、outbox/queue 两张热表轮询、`SKIP LOCKED` 高并发下的锁竞争，全部压在一个 PG 实例上（§5.3 劣-1）。
- 锚点：`RunDispatchConsumer.java:16-27, 179-237`、`docs/系统架构图.md:349, 401`、`PgQueueRepository.java:33-39`。

**D-2｜Outbox 用轮询中继而非「落库后直发 MQ」**
- 决策：`OutboxRelay` 每 200ms 轮询，`OutboxPublisher.publishOnce()` 先发消息（等 publisher confirms）再 `markOutboxPublished`。
- 为什么：Run 与消息同事务落库，「DB 提交失败但消息已发 → 幽灵任务」被根除；代价是 ≤200ms 发布延迟，「教育场景完全可接受」（`OutboxRelay.java:34-39`）。
- 代价：**中继是每实例一个 daemon 线程、没有 leader election、发布侧没有 `FOR UPDATE SKIP LOCKED`**（§4.5 不一致 4）；发布延迟与 DB 轮询压力随实例数线性增长。
- 锚点：`OutboxRelay.java:46-99, 113-162, 170-193, 202-222`、`OutboxPublisher.java:73-130`、`JdbcRunCreationRepository.java:442-496`。

**D-3｜双通道消息 + 按租户通道灰度（差异化）**
- 决策：`messageSender` 是 `TenantRoutingMessageSender(defaultSender, overrides)`，`MessagingChannels.resolve()` 在启动期把 slug → tenantId + 全局模式 + 租户覆盖解析成路由表（`WorkerLoopConfig.java:403-414, 455-493`）。
- 为什么：试运营小客群「无 broker 也能跑」，切回 Rabbit 只改一个键；通道切换不触碰业务语义（两条通道共用 `MessageSender` / `QueueDepthProbe` / `MessageHandler` 端口）。
- 代价：同一份语义要维护两套实现；`agent.worker.concurrency/prefetch` 只在 Rabbit 通道生效（§4.5 不一致 1/2）；切换必须排空旧通道否则 Run 永远 QUEUED 且无报错。
- 锚点：`application.yml:438-479`、`WorkerLoopConfig.java:75-84, 339-369, 403-414, 684-699`。

**D-4｜部署参数全部 fail-closed，不退回默认值**
- 决策：`WorkerPolicy` 对 `relay-interval-ms`（下限 10ms）、`concurrency`（上限 64）、`prefetch`（上限 100）、`outbox-batch`、`max-publish-attempts`、`tenant-slugs` 一律「缺失/非法即 `IllegalStateException` 拒绝启动」；`BackpressurePolicy` 三项水位同样 fail-closed，且 `low < high` 强校验、cooldown ≤ 20。
- 为什么：类注释直言「退回默认值等于**悄悄用了一个没人审过的并发度**，容器化环境下可能直接打垮下游模型服务与 MQ」（`WorkerPolicy.java:12-17`）；水位「过高 = 护栏形同虚设、过低 = 正常流量被误判为过载」，不存在保守兜底值（`BackpressurePolicy.java:8-15`）。
- 代价：所有参数必须显式配置；运维改一个数字就要重启；**配置项存在但无消费方时，fail-closed 守卫也救不了**（`max-concurrent-runs` 即此形态，§4.5 不一致 6）。
- 锚点：`WorkerPolicy.java:18-152`、`BackpressurePolicy.java:20-96`、`application.yml:180-199, 303-317`。

**D-5｜三层并发控制：MQ prefetch / worker 线程池 / DB 行锁**
- 决策与配比（**本维度重点**）：

| 层 | 位置 | 默认 | 作用 | 配错的后果 |
|---|---|---|---|---|
| ① 消费者级 | `spring.rabbitmq.listener.simple.prefetch=10`（`yml:54`）+ `agent.worker.prefetch=10`（`yml:195`）→ `factory.setPrefetchCount(...)`（`WorkerLoopConfig.java:363`） | 10 / 消费者 | 单消费者未 ack 前最多预取 10 条 | 过大 ⇒ 重投时重复处理窗口放大（`WorkerPolicy.java:26, 120-121`）；过小 ⇒ 吞吐上不去、消费者空转 |
| ② 进程级 | `agent.worker.concurrency=4`（`yml:193`）→ `factory.setConcurrentConsumers(...)`（`WorkerLoopConfig.java:362`） | 4 | 每实例 4 个并发消费者 | 过大 ⇒ 打垮下游模型服务（`WorkerPolicy.java:110-111` 上限 64）；与 ① 相乘 = 40 在途/实例 |
| ②' DB 通道进程级 | `agent.messaging.batch-size=50`（`yml:475`）+ `PgQueueListener.pollOnce()` 单线程顺序 `handleOne`（`PgQueueListener.java:188-219`） | 1 有效并发 | 单轮领 50 条但逐条执行 | **默认部署下 ①② 全不生效**（Rabbit 容器 `setAutoStartup(autoStartup && channels.rabbitActive())` = false），单实例一次只跑 1 个 Run |
| ③ 数据级 | `PgQueueRepository.claim` 与 `JdbcRunClaimRepository.claimTasks` 的 `WITH candidates AS MATERIALIZED (... FOR UPDATE SKIP LOCKED)` | — | 多实例并发领取互不阻塞、`fencing_token` 递增防双写 | 缺失 ⇒ 争抢同一行、高并发退化为串行（`JdbcRunClaimRepository.java:36-38`）；`IN (SELECT … LIMIT … FOR UPDATE SKIP LOCKED)` 在 FORCE RLS 下 LIMIT 静默失效 ⇒ 必须 MATERIALIZED（铁律 13，`:133-140`） |

- 为什么分三层：让「谁在排队、谁在跑、谁持锁」各自可控，且 ③ 是最后的安全网（应用崩了 DB 仍守住不变量）。
- 代价：**三层配比目前是失配的**——默认 database 模式下 ①② 是死配置，③ 承担了全部并发语义；`concurrency=4` 与 `prefetch=10` 给运维的「4×10=40 并发」印象与真实的「单实例顺序 1」相差 40 倍。这正是 2.3 的 AP4。
- 锚点：`application.yml:43-59, 191-199, 471-479`、`WorkerLoopConfig.java:339-369, 634-676`、`PgQueueListener.java:188-219, 333-371`、`PgQueueRepository.java:53-56, 114-148`、`JdbcRunClaimRepository.java:34-38, 128-155`。

**D-6｜灰度上限 `deployment.pilot.max-tenants` + 显式 `AGENT_TENANT_SLUGS`（本维度独有的产品级容量治理）**
- 决策：`application.yml:654-658` `deployment.pilot.max-tenants: "1"`（**字面量硬编码，非 env**）；`application.yml:216` `agent.worker.tenant-slugs: "${AGENT_TENANT_SLUGS:t-a}"`；`platform.env` 实际配 `AGENT_TENANT_SLUGS=t-e2e-fe`。`WorkerPolicy.requireTenantSlugs(raw, maxTenants)`（`WorkerPolicy.java:59-93`）校验：缺失 → 拒启、空清单 → 拒启（「空清单即消息永不发布、而系统表面完全正常」）、重复 → 拒启、**数量 > maxTenants → `IllegalStateException("灰度控制不得被配置绕过")`**。装配期由 `WorkerLoopConfig.messagingChannels()`（`WorkerLoopConfig.java:403-414`）把 `pilotMaxTenants` 与 `tenantSlugs` 一起解析并传给 `MessagingChannels.resolve`。
- 为什么（类注释 `:44-52` 的两段，是本项目最有价值的部署设计文档）：
  1. **「显式清单」而非「扫全表」**：扫全表要求连接具备跨租户读权限，「一旦配置或实现出错就是**跨租户发布**（越权，且静默）」；显式清单最坏是**漏发或拒启**——「失败形态从『越权』降级为『不可用』」。`OutboxPublisher.publishOne` 还有第二道防线：发送前复核 `tenantId.equals(message.tenantId())`，不匹配即拒发并标 FAILED（`OutboxPublisher.java:95-108`）。
  2. **灰度上限是「承诺」不是「建议」**：「试点期上限是灰度承诺的一部分，允许配置悄悄超过上限等于『灰度控制形同虚设』」，且必须用代码强制而非文档约定。
- 代价 / 局限（重点提炼）：
  - **白名单硬编码风险**：`max-tenants` 写死在 yml 里、不是 `${PILOT_MAX_TENANTS:...}`，扩量必须**改文件 → 重新打包 fat jar → 重启**；`AGENT_TENANT_SLUGS` 是 env 白名单，两处真相源（yml 上限 + env 清单）靠人工保持一致，`platform.env` 注释已警告「漏配/清单外 ⇒ worker 不消费该租户 outbox、Run 永远 QUEUED 且无任何报错」。
  - 这是**「单租户试点 → 多租户」的准入开关**，不是版本发布灰度（无百分比放量、无自动回滚、无按租户健康度回退）；与 Fowler 的 CanaryRelease 是两种东西。
  - 与 `RunRecoverySweeper` 的租户来源存在张力：sweeper 经 `PlatformTenantPort.listTenants("ACTIVE", tenantLimit=200)`（`RunRecoverySweeper.java:113, 229`）枚举**所有 ACTIVE 租户**做崩溃恢复，并不按本实例 slug 清单收窄（默认 `require-tenant-port=false` 且平台运维通道常不可用 → 整轮跳过，属潜在而非当前故障）。
- 锚点：`application.yml:209-216, 654-658`、`WorkerPolicy.java:35-36, 41-58, 59-93`、`WorkerLoopConfig.java:403-414, 541-572`、`OutboxPublisher.java:24-32, 88-108`、`platform.env`、`ConfigReadService.java:138-139`。

**D-7｜单租户故障隔离贯穿发布与消费**
- 决策：`OutboxRelay.relayOnce()` 对每个租户的 `publishOnce()` 单独 try/catch，「单租户失败**不得**终止本轮其他租户，也不得终止循环」（`OutboxRelay.java:145-150`）；`PgQueueListener.pollOnce()` 同样「单租户领取失败继续下一个租户」（`PgQueueListener.java:203-207`）；`RunRecoverySweeper` 单租户异常只 WARN 跳过（`:285-288`）。
- 为什么：「一个租户的数据问题会让所有租户停摆」是隔离的反面；与维度 02 的 RLS 是同一取向在部署层的延伸。
- 代价：**只隔离了「异常」，没隔离「资源」**——同一 `pollOnce()` 里租户按固定顺序遍历，租户 A 的 50 条消息会在 A 的循环里**顺序执行完**才轮到租户 B（Head-of-Line blocking）。长任务 / 高并发的租户仍能饿死他人（D-8）。
- 锚点：`OutboxRelay.java:24-32, 128-153`、`PgQueueListener.java:193-214`、`RunRecoverySweeper.java:255-289`。

**D-8｜多租户共享 worker 池，无租户级并发准入（吵闹邻居现状）**
- 决策：一个 `PgQueueListener` 服务 `channels.databaseTenantIds()` 下**全部**租户，`claim(tenantId, batchSize=50, ...)` 对每个租户各领 50 条；无按租户的并发计数、无限流、无优先级、无独立池。
- 为什么：利用率优先、实现简单；试运营单租户阶段（`max-tenants=1`）没有暴露问题。
- 代价：**吵闹邻居完全无防护**。更关键的是——项目自己已经把这件事记在案：`ConfigReadService.java:138-139` 把 `agent.tenant.max-concurrent-runs` 标为 `effective=false`，备注「⛔ 实测：常量 `KEY_MAX_CONCURRENT_RUNS` 定义外引用数 0 → **租户并发无限制**」；`ConfigReadServiceTest.java:158` 断言该 flag 为 false。`platform.tenant_quota.run_concurrency_limit`（`01_platform_ddl.sql:1280-1285`）只被 `JdbcPlatformTenantRepository` 在**开通租户时写入/读取默认值**（`:104-113, 163-164, 238-256`），不在 Run 创建或消费的准入路径上。即：**yml 里写了 5、DDL 里建了列、但没有任何一处拿它做闸门**。
- 锚点：`ConfigReadService.java:125-139`、`ConfigReadServiceTest.java:115-116, 158`、`PlatformConfig.java:48, 72`、`application.yml:504-506`、`01_platform_ddl.sql:1280-1285`、`JdbcPlatformTenantRepository.java:104-113`、`PgQueueListener.java:193-214`。

**D-9｜优雅停机：进程内已实现，K8s 层与在途等待缺失**
- 决策：`WorkerShutdownCoordinator implements AutoCloseable`（`WorkerLoopConfig.java:701-740`）在 Spring 上下文关闭时按序 `relay.stop()` → `pgListener.stop()`；`OutboxRelay.stop()` 先置 `stopped` 再中断、并 `t.join(STOP_TIMEOUT_MS=30_000)` 等线程真正退出（「否则守护线程会在 DataSource 关闭后仍在跑」，`OutboxRelay.java:202-222`）；`PgQueueListener.stop()` 同构（`:374-395`）；停机窗口内 DB 异常降级为 DEBUG，不污染告警（`OutboxRelay.java:138-150`、`PgQueueListener.java:348-356`）。
- 为什么：**顺序很重要**——「先停中继（不再领取新任务），再等在途完成。顺序反了会在停机窗口内不断产生新工作」（`WorkerLoopConfig.java:702-705`）。
- 代价 / 边界（必须诚实）：
  - 注释明确「**不强制中断在途执行**：Run 的租约会自然过期被其他实例接管，强制中断只会浪费一个租约周期」（`:706-708`）——即**不等待在途 Run 完成、不主动释放租约**，而是把恢复责任交给 30s 租约过期 + `RunRecoverySweeper`（每 30s 扫一次）。
  - `join` 等的是**轮询线程**，不是 `RunExecutionLoop` 在途任务；停机时若有长任务在跑，进程退出后该 Run 停在 `RUNNING` 直到租约过期被接管（维度 11 的孤儿 Run 收敛路径）。
  - **无 `preStop`、无 `terminationGracePeriodSeconds`、无 drain HTTP 端点、无 SIGTERM 显式处理**；`terminationGracePeriodSeconds` 默认 30s 与 `STOP_TIMEOUT_MS=30_000` + 租约 30s 恰好撞车，K8s 很可能在中继还没 join 完就 SIGKILL（§2.1(7) 的官方宽限期算式）。
- 锚点：`WorkerLoopConfig.java:701-740`、`OutboxRelay.java:59-77, 195-222`、`PgQueueListener.java:333-395`、`application.yml:219`（`lease-seconds: "30"`）、`RunRecoverySweeper.java:172`。

**D-10｜全局背压（高/低水位 + 滞回 + 冷却倍数）**
- 决策：`BackpressureController` 每轮 `relayOnce()` 前先 `allowPublish()`，队列深度 ≥ 1000 即**整轮跳过一条不发**，`≤200` 才恢复，`cooldown-multiplier=4` 拉长轮询间隔；探测失败按「超限」处理（fail-closed）。`QueueDepthProbe` 是 `CompositeQueueDepthProbe`，**只纳入活动通道**（DB 部署不探测 Rabbit，避免 broker 不存在导致恒超限 → 消息永不发布）。
- 为什么：「半开半续（只发部分租户）会让『谁被牺牲』变得不确定，排障时无法解释」（`OutboxRelay.java:107-109`）；`isThrottled()` 长期为 true 即「生产快于消费、需要扩容或排查」的信号（`OutboxRelay.java:234-240`）。
- 代价：这是**全局**背压，不是 per-tenant；一个租户灌爆队列时，**所有租户一起停发**（与 D-7 的单租户异常隔离形成有趣反差）。也正是改进点 1/2 要解决的指标口径来源。
- 锚点：`application.yml:303-317`、`BackpressurePolicy.java:20-96`、`WorkerLoopConfig.java:495-539`、`OutboxRelay.java:30-32, 107-121, 163-193, 234-245`。

### 4.4 我们独有的设计（差异化设计）

1. **「灰度上限用代码强制」而非文档约定（D-6）**：`WorkerPolicy.requireTenantSlugs` 把「试点最多 N 个租户」写进**启动期不可绕过的校验**，让「配置想偷偷扩量」直接变成 `IllegalStateException`。竞品里没有见到把「租户准入数量」作为**代码级容量治理开关**的做法——LangGraph/ADK/AgentOS 的多租户是「作用域」，CrewAI 是「组织 RBAC」，都没有「单租户试点 → 多租户」这一产品化阶段机。这是本平台独有的、面向**教育 SaaS 试运营**的领域性设计。
2. **「越权降级为不可用」的失败形态设计（D-6）**：显式 slug 清单而不是扫全表，把「配置错了会跨租户发布」这一最危险的失败，换成「漏发/拒启」这一最可见的失败。`OutboxPublisher` 再加一道 `tenantId` 二次复核，形成双保险。这与维度 02「fail-closed 默认拒绝」是同一哲学在部署层的投影。
3. **两条消息通道语义等价 + 按租户通道灰度（D-3）**：`AGENT_MESSAGING_MODE` 全局 + `AGENT_MESSAGING_TENANT_MODES` 按租户，配合 `MessagingSwitchGuard` 的启动期残留拒启，是一种「无 broker 也能跑、切换不丢消息」的部署级灰度。竞品大多是「要么库+broker 托管，要么纯库」，没有把「通道选择」本身做成租户级灰度维度。
4. **部署参数全量 fail-closed（D-4）**：把并发度、预取数、租户集、水位线全部纳入「缺失即拒启」，且数值加引号防 `YamlPropertiesFactoryBean` 丢裸标量。这种「宁可起不来、不可悄悄用没审过的参数」的取向，在竞品里罕见（多数给默认值）。
5. **「数据库即队列」与 DB 事实源共用同一事务边界（D-1/D-3）**：默认 `database` 模式让 outbox、queue、run、预算、审计全在一个 PG 事务边界内，`FOR UPDATE SKIP LOCKED` 天然支撑多实例互斥。LangGraph Agent Server 需要 PG + Redis 两类存储，我们少一个分布式组件——代价是 PG 成为单点与瓶颈（诚实承认）。
6. **进程内优雅停机 + 停机窗口异常降级（D-9）**：`shuttingDown` 标志把「DataSource 正在关闭」的预期异常降级为 DEBUG，避免污染告警；`stop()` 先置 stopped 再中断再 join，防止守护线程在池关闭后仍 `getConnection`。这类「停机语义的可观测性」细节在库形态竞品里通常交宿主，少有内建。
7. **崩溃恢复与执行主路径共用同一执行器（D-1/E-34）**：`RunRecoverySweeper` 接管过期 RUNNING 后驱动的是**与 MQ 主路径完全相同**的 `RunDispatchConsumer.RunExecutor`，避免恢复链路走出一套分叉语义；靠 `claimTasks` 的 SKIP LOCKED + fencing 保证多实例扫描不双写。

**（a）默认消息通道是 `database`（PG 表队列），不是 RabbitMQ；梳理报告 §1/§12 的「投递到 MQ」在默认部署下不准确**
`application.yml:457` `mode: "${AGENT_MESSAGING_MODE:database}"`，注释直言「暂时以异步（数据库队列）替代 RabbitMQ」。默认部署**无外部 broker**：队列是 `agent_message_queue` 表，`PgQueueListener` 轮询它。`spring.rabbitmq.*` 与 `agent.worker.*` 的 Rabbit 相关参数仅在显式切到 `rabbitmq` 或某租户 `tenant-modes=rabbitmq` 时才生效。竞品报告 §维度 12「伸缩靠手动起多 Worker 实例」方向正确，但未点明「默认连 MQ 都没有」——这直接改变了扩容分析：**扩的是 PG 轮询者，不是 broker 消费者**。

**（b）`agent.worker.concurrency=4` / `prefetch=10` 在默认部署下不生效；有效并发是「单实例 1」**
`WorkerLoopConfig.java:359` `factory.setAutoStartup(autoStartup && channels.rabbitActive())`——纯 DB 部署 `rabbitActive()=false`，Rabbit 消费容器**根本不启动**，`:362-363` 的 `setConcurrentConsumers(4)` / `setPrefetchCount(10)` 设了也无从生效。DB 侧 `PgQueueListener.pollOnce()`（`:188-219`）是**单 daemon 线程逐租户、逐条顺序 `handleOne`**，`batch-size=50` 只是「一次领 50 条」，不是「并发 50」。故默认部署单实例有效并发 = **1**（长任务期间整条轮询循环被占住），与梳理报告 §12 把这些称作「Worker 弹性参数」给人的「4×10=40」印象相差约 40 倍。这是 D-5 三层配比失配的根源。

**（c）`spring.rabbitmq.listener.simple.prefetch`（`yml:54`）疑似死键（读代码推断，未运行时验证）**
`WorkerLoopConfig` 自建名为 `rabbitListenerContainerFactory` 的 Bean，其注释 `:351-353` 明确「本类自建工厂 → Boot 的 `SimpleRabbitListenerContainerFactoryConfigurer` **不会**自动应用，故 autoStartup 等属性必须自己读」。据此，`spring.rabbitmq.listener.simple.*` 下的 `prefetch: "10"` 不会被 Boot 配置器应用；实际 prefetch 来自 `agent.worker.prefetch`（`yml:195`）经 `:363` 设置。两处恰好都写 10，掩盖了重复。**判别方式**：把 `yml:54` 改成 99 而 `:195` 保持 10，运行期看消费者实际预取数。

**（d）OutboxRelay 发布侧没有多实例互斥（最重要的单点发现）**
`JdbcRunCreationRepository.loadPendingOutbox`（`:442-449`）是**裸 `SELECT … WHERE state='PENDING' ORDER BY created_at LIMIT ?`**，无 `FOR UPDATE SKIP LOCKED`；`markOutboxPublished`（`:479-483`）是无条件 `UPDATE ... SET state='PUBLISHED'`，**没有 `WHERE state='PENDING'` 的 CAS**。而消费/领取侧 `PgQueueRepository.claim`（`:128-140`）与 `JdbcRunClaimRepository.claimTasks`（`:141-155`）都有 SKIP LOCKED + fencing。结论：**「多实例可水平扩展」只在消费/领取侧成立**；N 个 Worker 实例 = N 个 `OutboxRelay` daemon 线程同时轮询，可读到同一批 PENDING 并各自发布 → **重复发布窗口**。正确性由下游 `RunDispatchConsumer.DUPLICATE_DISCARDED` + 租约/fencing 兜住（`E-33`），不至于重复副作用，但 MQ/PG 写入压力与重复消息率随实例数**线性增长**。梳理报告与竞品报告都未提这个单点是否可多实例、靠什么互斥。

**（e）`agent.worker.id` 默认是静态字面量，水平扩容必须人工注入唯一值**
`application.yml:221` `id: "worker-local"`（**不是** `${AGENT_WORKER_ID:...}` 占位），`WorkerLoopConfig.java:617, 651` 与 `RunRecoverySweeper.java:109` 均用 `${agent.worker.id:worker-local}`。`:627-632` 记录过同源真实事故：监听器曾自造 `pg-worker-<pid>`、执行循环用 `worker-local`，身份不一致导致「每个带工具调用的 Run 在第一个工具执行成功后被误判『已被接管』、永久卡在 RUNNING」。多实例若都带默认 `worker-local`，会共用同一 `lease_owner`，`renewLease` 按身份精确匹配（维度 03）→ 互相误判接管。Spring Boot 的 relaxed binding 允许用 `AGENT_WORKER_ID` 环境变量覆盖，但**yml 无显式占位、deploy/ 无 k8s manifest 用 `fieldRef: metadata.name` 注入**，属「靠运维知识而非靠结构保证」。

**（f）租户级并发配额「声明了但没接线」，吵闹邻居当前无隔离（项目自证）**
`agent.tenant.max-concurrent-runs: "5"`（`yml:506`）与 `platform.tenant_quota.run_concurrency_limit`（`01_platform_ddl.sql:1283`）**没有任何生产读取点用于准入**。`ConfigReadService.java:138-139` 已把前者标 `effective=false` 并注明「⛔ 实测：常量 `KEY_MAX_CONCURRENT_RUNS` 定义外引用数 0 → 租户并发**无限制**」，`ConfigReadServiceTest.java:158` 锁定该结论；后者只被 `JdbcPlatformTenantRepository` 在开通租户时写入/读取默认值（`E-38`）。梳理报告 §9 把它列为「租户额度配置」容易被读成已生效。**这是改进点 2 的硬证据，不是推测。**

**（g）灰度机制比梳理报告描述的更丰富，也更不一致**
除 `pilot.max-tenants` + `AGENT_TENANT_SLUGS` 外，还有第二套按租户的**消息通道灰度** `agent.messaging.tenant-modes`（`yml:470`）与 `MessagingCanaryWiringTest`；`max-tenants` 是**字面量**而非 env（扩量要重新打包）；`RunRecoverySweeper` 的 `listTenants("ACTIVE", 200)` 在平台运维通道接入时会枚举全部 ACTIVE 租户、不与本实例 slug 清单严格对齐（默认 `require-tenant-port=false` + 端口常不可用 → 跳过，属**潜在张力，未运行时验证**）。三者构成「三套租户来源」，与 `platform.env` 注释自承的「同为保留期清理的租户来源：两套来源迟早不一致」（`yml:215`）是同族问题。

**（h）deploy/ 下没有生产部署清单；启动脚本在 scripts/，且是单 fat jar**
用户要求核查的 `deploy/` 目录里只有 `docling/docker-compose.yml`（文档解析服务）与 `sql/`（DDL）；`init-db.sh`、`dev-backend.sh`、`dev-env-up.sh` 全在 `scripts/`；`monitoring/docker-compose.yml` 只有 Prometheus/Grafana。全仓**无 Dockerfile、无 k8s/helm manifest、无 HPA/KEDA/ScaledObject、无 preStop/terminationGracePeriodSeconds 配置**（`find` 全仓核对）。`docs/系统架构图.md:351`「控制面/Worker 可独立部署」因此应精确表述为「**同一 jar + `agent.worker.enabled` 开关的进程级切分**」，而非独立构建产物或已落地的部署编排。竞品报告 §维度 12「配置全外部化」成立，但「部署为手工配置」应补一句「手工到连容器清单都没有」。

**（i）优雅停机已有进程内实现，梳理报告 §12 完全未提；但也不完整**
`WorkerShutdownCoordinator`（`WorkerLoopConfig.java:701-740`）+ `OutboxRelay.stop()` + `PgQueueListener.stop()` 已实现「停中继 → 停监听 → join 轮询线程」，且 `shuttingDown` 降级停机窗口 DB 异常。**但**：`:706-708` 明确「不强制中断在途执行，租约自然过期由其他实例接管」→ **不等在途 Run 完成、不主动释放租约、无 k8s preStop / 宽限期配置**。所以改进点 3 不是「从零实现停机」，而是「补 K8s 生命周期契约 + 在途等待 + 主动释放租约」。

**（j）竞品信息需要按 2026 现状更新**
竞品报告 §维度 12 把 Anthropic 归为「库形态，无自带编排 server」——**已不准确**：Claude Managed Agents 现为官方托管 harness（云 sandbox 或自托管 sandbox，可 K8s 部署、支持 Cron），官方 overview 明确用「who runs the agent」并列 Agent SDK 与 Managed Agents（`§3.2`）。AutoGen 的「已归档」需补时间线：2025-10 并入 Microsoft Agent Framework 进入 maintenance、2026-10 README 标 archived（`§3.5`）。OpenAI Agents SDK 的「无运行时」官方页**未逐字明示**（`§3.1` 已诚实标注）。LangGraph Agent Server 的「queue workers scale on pending run count」「`N_JOBS_PER_WORKER`」「split API/queue」是本维度最有价值的对标细节，竞品报告未展开。

### 5.2 优势详解（讲机制，不讲结论）

1. **「DB 事实源 + 租约 + fencing」让扩容在语义上是安全的**：新增一个 Worker 实例不需要迁移状态、不需要 sticky session、不需要数据分片——它只需要连到同一个 PG，`claimSpecificRun` 的 `FOR UPDATE SKIP LOCKED` + `fencing_token` 递增（`JdbcRunClaimRepository.java:128-155`）就保证「同一 Run 不会被两个实例写」。对照 12-Factor VI，这是「进程可随时被杀、被换、被加」的最强形式；对照竞品，LangGraph 用「at most 1 run per thread + lease」，Agno 用「SKIP LOCKED + 心跳租约」，三者机制同构，但我们的隔离是 **DB 触发器级**（`enforce_fencing_on_write`），比应用层 lease 更抗应用 bug。
2. **「越权降级为不可用」的失败形态工程**：显式 slug 清单 + 每租户独立 `OutboxPublisher` + 发送前 `tenantId` 二次复核（`OutboxPublisher.java:95-108`），构成三道防线。这个设计的价值不在「功能多」，而在**把最危险的静默越权变成了最吵闹的拒启**——与本项目反复记录的「断链」「假 201」失败族正好相反。
3. **灰度上限是「代码承诺」而非「运维约定」**：`WorkerPolicy.requireTenantSlugs` 在启动期把 `deployment.pilot.max-tenants` 与清单长度绑定校验，任何「偷偷多配一个租户」的尝试都会 `IllegalStateException`。在竞品普遍把多租户交给作用域或组织 RBAC 的背景下，这是面向「单租户试点 → 多租户」这一**具体商业阶段**的产品级容量治理。
4. **fail-closed 部署参数 + 配置键对齐守卫**：并发度、预取数、水位线、租户集一律「缺失/非法拒启」，且 `ApplicationConfigKeyAlignmentTest` 防止「env 定义了但 yml 写字面量」这类静默漂移（`yml:227-228, 640-642`）。运维看到的数字就是生效的数字——除了 (f) 那一个被项目自己标红的例外。
5. **单租户异常隔离 + 全局背压的组合**：`OutboxRelay` / `PgQueueListener` / `RunRecoverySweeper` 三处都做了「单租户失败不影响其他租户」，同时 `BackpressureController` 在队列达 1000 时整轮停发、探测失败按超限处理。这套「隔离 + 背压」在库形态 SDK（OpenAI / Claude Agent SDK / AutoGen）里是完全没有的。

### 5.3 劣势与盲区详解（明确承认，含根因）

**劣-1｜无托管运行时，运维全靠手工（根因：设计取舍）**
竞品报告 §维度 12 已点明，本报告补充程度：不仅「无 Agent Runtime / Agent Server 式托管」，而是**连 Dockerfile、k8s manifest、HPA、preStop 都没有**（§4.5(h)）。启动靠 `scripts/dev-backend.sh` 的 `java -jar`，扩容靠人配 `AGENT_TENANT_SLUGS` 与 `agent.worker.id` 再起一个进程。根因不是「没想到」，是 `docs/系统架构图.md:351`「首期不拆成过多微服务」+「DB/治理中心化」的自觉取舍：把一个 fat jar 的确定性、单事务边界、强一致放在了「运维弹性」之前。代价是**所有 L2/L3 能力都要自己补**，且每补一个都会碰到 PG 这个共享瓶颈。

**劣-2｜伸缩触发是人工、且三层并发配比失配（根因：能力缺口 + 配置漂移）**
没有 KEDA/HPA 是能力缺口；`concurrency/prefetch` 在默认 `database` 模式下不生效（§4.5(b)）则是**配置漂移**——梳理报告与 yml 注释都把它们当全局并发参数，实际只作用于 Rabbit 容器。二者叠加的后果是：即使运维「按 4×10=40 并发」规划容量，真实单实例只跑 1 个 Run；队列积压时 `BackpressureController` 会停发，但**没有任何机制自动加副本**。这是本维度最影响生产容量的一项。

**劣-3｜OutboxRelay 是未加互斥的单点（根因：能力缺失）**
发布侧裸 SELECT + 无条件 UPDATE（§4.5(d)）意味着「多实例」在**发布**这一环不是靠租约/fencing 保证的，而是靠下游消费端幂等容忍重复。正确性没破，但「发布压力 ∝ 实例数」会让 §7 改进点 1 的「按队列深度扩容」在一个未被治理的链路上放大写放大。这不是设计取舍，是漏了一层 `SKIP LOCKED` / CAS。

**劣-4｜多租户共享池且无并发准入，吵闹邻居无防护（根因：能力缺口，项目已自知）**
`ConfigReadService.java:138-139` 的 `effective=false` 是项目自己给的证据。机制层面有两处具体放大：① `PgQueueListener.pollOnce()` 按固定租户顺序、把某租户一批 50 条**顺序执行完**才轮到下一个（Head-of-Line blocking）；② `BackpressureController` 是**全局**停发，一个租户灌爆队列会让所有租户一起停。cgroups / K8s QoS 管不了这个（§2.1(6)），必须应用层做按租户准入/公平调度/独立池。这是 D-7「只隔离异常、没隔离资源」的直接后果。

**劣-5｜数据库是真正的伸缩瓶颈（根因：架构取舍的结构性代价）**
D-1 把状态全压给 PG，换来强一致与可恢复；代价是四个叠加压力：① `max_connections` 默认 100，`实例数 × (10 主 + 2 运维 + 2 清理) ≤ 100 − 3(superuser) − 其他` ⇒ **N ≈ 6~7 就是硬上限**（改进点 4 给公式）；② 42 张表 FORCE RLS、每次事务 `set_config` 绑定 GUC，查询带 security-barrier 开销，且铁律 13 的 MATERIALIZED CTE 就是 RLS 下 LIMIT 失效的实证；③ `outbox_event` 200ms 轮询 + `agent_message_queue` 200ms 轮询，N 个实例 = 2N 个常数级打库流；④ `SKIP LOCKED` + 热表 UPDATE 在高并发下的锁/ vacuums 压力。**托管竞品把这一层抽象掉了，我们必须自己算清楚。**

**劣-6｜优雅停机不完整（根因：取舍 + K8s 契约缺失）**
`WorkerLoopConfig:706-708` 主动选择「不强等在途、靠租约过期接管」，这在**有健康的其他实例 + 30s 租约 + 30s sweeper** 时是可接受的取舍；但在「缩容到 0」「整组滚动重启」「无其他实例」时，在途 Run 会停在 RUNNING 直到接管，且 `terminationGracePeriodSeconds=30` 与 `STOP_TIMEOUT_MS=30_000` + 租约 30s 撞车，K8s 可能在中继 join 完成前 SIGKILL。缺的是 preStop + 宽限期 + drain 端点 + 主动释放租约（改进点 3）。

**劣-7｜容量基线与压测是空白（根因：能力缺口）**
`application.yml` 多处写「调优时点：P4 压测实测消费速率后」（`:311, 492-506`），但仓库里没有压测方案、没有单 worker 吞吐基线、没有 P95 拐点数据、没有「实例数 ↔ 连接数」的容量表。`high-watermark=1000`、`max-concurrent-runs=5`、`batch-size=50` 全是保守初值而非实测值。SRE Ch.21/22 要求「add load until the system breaks / know the breaking point」，我们目前连「拐点在哪」都不知道（改进点 7）。

**劣-8｜灰度产品化程度低且三套租户来源不一致（根因：演进阶段 + 硬编码）**
`max-tenants` 字面量、`AGENT_TENANT_SLUGS` env 白名单、`tenant-modes` 通道灰度、`RunRecoverySweeper.listTenants` 全量枚举、`agent.retention` 又一套租户来源（`yml:215` 自承），共 4~5 处。无百分比放量、无按租户健康度自动回滚、无审计。改一个租户要改 env 并重启（若同时要调 max-tenants 还得重新打包）。Fowler 的 CanaryRelease「slowly roll out + reroute to rollback」在我们这里是「二分开关 + 人工改配置」。

### 5.4 关键分歧点（3 个最本质的架构分歧）

**分歧 1｜「状态放哪」：DB 中心化 vs 运行时/托管状态**
- 我们：PG 是唯一权威源，MQ 只唤醒（D-1）。→ 扩容语义最安全，但 PG 是单点与容量天花板。
- LangGraph：PG 存 checkpoints + Redis 存 signaling；ADK / Managed Agents：平台托管 session/sandbox。→ 把状态与伸缩交给运行时，运维轻，但一致性与可审计性依赖平台。
- 后果：我们的 `max_connections` 公式、RLS 开销、outbox 轮询压力是**自己要背的债**；他们的是**平台账单**。

**分歧 2｜「伸缩由谁驱动」：人工 process formation vs 队列深度自动伸缩**
- 我们：12-Factor VIII 只做到「可以加进程」，没做到「自动加进程」；并发参数还是 fail-closed 的人工契约。
- LangGraph Agent Server / KEDA：「queue workers scale on pending run count」是内建一等能力。
- 后果：同样的架构同构度，人家是 L2/L3，我们是 L1 上沿；峰值靠超配、低谷白付，且积压时只能靠背压停发而不是扩容消费。

**分歧 3｜「多租户是作用域还是准入」：作用域隔离 vs 产品级容量治理**
- 竞品：多租户是 `thread_id` / `assistant` / 组织 RBAC / 每用户数据隔离——本质是**数据可见性**问题。
- 我们：RLS 是**默认拒绝的硬边界**（领先），且额外把「试点能放几个租户」做成代码级上限（独有）；但**恰恰没做「一个租户能占多少并发」**（`effective=false`）。
- 后果：我们在「谁能看什么」上最严，在「谁能用多少」上最松——吵闹邻居是这个不对称的直接产物。改进点 2 不是补一个限流器，而是把「容量」也纳入我们已有的「准入治理」体系。

## 六、优缺点总评

### 6.1 我们的优点

**结构性优势**
- DB 事实源 + 租约 + fencing ⇒ 无状态进程可安全水平扩展，崩溃恢复不重复副作用（D-1）。
- 领取侧 `FOR UPDATE SKIP LOCKED` + MATERIALIZED CTE（铁律 13）⇒ 多实例并发领取天然互斥，且已在 `app_agent(NOBYPASSRLS)` 下实测过 RLS 陷阱。
- 双通道语义等价 + 启动期残留守卫 ⇒ 切换通道不产生「静默滞留」（D-3）。

**工程性优势**
- 部署参数全量 fail-closed + 配置键对齐守卫（D-4）：「起不来」优于「悄悄用没审过的并发度」。
- 优雅停机已内建 stop/join + 停机窗口异常降级（D-9）：避免了 `HikariDataSource has been closed` 污染告警。
- 单租户异常隔离贯穿 relay / listener / sweeper 三处，全局背压带滞回与冷却（D-7/D-10）。

**领域性优势**
- `pilot.max-tenants` + 显式 slug（D-6）：面向教育 SaaS「单租户试点 → 多租户」阶段的产品级容量治理，把越权降级为不可用，竞品无对应物。
- 配置全外部化 + `scripts/init-db.sh` 依赖序初始化，换环境不改代码。

### 6.2 我们的缺点

**设计取舍导致的代价**
- 单 fat jar 模块化单体、无独立 worker 产物、无容器清单 ⇒ 运维弹性差（劣-1）。
- DB 中心化 ⇒ PG 连接数 / RLS / 轮询 / 热表四重瓶颈，实例数有硬上限（劣-5）。
- 停机「不强等在途、靠租约接管」⇒ 缩容到 0 / 整组重启时体验差（劣-6）。

**能力缺口**
- 无 HPA/KEDA、无队列深度伸缩（劣-2）；`concurrency/prefetch` 默认不生效（§4.5(b)）。
- OutboxRelay 发布侧无互斥（劣-3）。
- 租户级并发准入缺失、吵闹邻居无防护（劣-4）。
- 无容量基线与压测（劣-7）；无 cell 化故障域切分、无版本发布灰度、无自动回滚（劣-8）。

**运维负担**
- 手工配 `AGENT_TENANT_SLUGS` / `agent.worker.id` / `max-tenants` 三处且要保持一致；扩租户可能要重新打包；无 preStop / 宽限期 / drain 端点；无 PgBouncer 评估；`dr.rpo=24h / rto=4h` 仅是声明（`yml:714-717`），无演练证据。

## 七、可优化与改进点

> 每条均写明：问题 → 方案（**文件 / 表 / 配置 / 接口级**，含 DDL / YAML / Java 片段）→ 收益（**指标口径**）→ 成本与风险 → 优先级 + 排期 → **验收门禁**。
> 门禁一律遵循项目铁律 6：必须包含「**撤掉修复点会红**」的反向验证；并遵循铁律 1（RLS GUC 事务内绑定）、铁律 12（SSE 双链不写 outbox）、铁律 13（FORCE RLS 下 MATERIALIZED CTE）、铁律 17（静态守卫 ≠ 运行时成立，必须真实交互驱动）。

### 改进点 1 · KEDA / 队列深度驱动的 HPA（P0）

**问题陈述**
- 无 HPA/KEDA/ScaledObject（`find` 全仓核对，§4.5(h)）；副本数靠人工。
- 积压时 `BackpressureController` 只会**停发**（`high-watermark=1000`），不会**扩消费**；`OutboxRelay.isThrottled()` 长期 true 只是日志信号（`OutboxRelay.java:234-240`），无任何自动化动作。
- 更根本的：`agent.worker.concurrency/prefetch` 在默认 `database` 模式不生效（§4.5(b)），单实例有效并发 = 1 —— **先修这个，扩容才有意义**（否则加副本只是加更多「单线程」实例，收益仍在，但每实例吞吐基线要先测准，见改进点 7）。

**方案设计**
1. **先修 DB 通道进程内并发**（否则 KEDA 扩出来的副本都是单线程）：在 `agent-persistence/.../messaging/PgQueueListener.java` 把 `pollOnce()` 的顺序 `handleOne` 改为**有界线程池 + 按租户公平分发**：
```java
// PgQueueListener.java —— 新增构造参数 workerThreads（默认 4，经 MessagingPolicy 校验 ≤ 64）
private final ExecutorService pool = Executors.newFixedThreadPool(workerThreads, ...);
// pollOnce(): 领取后按 tenantId 轮询（round-robin）提交，而非 A 租户 50 条跑完再 B
for (QueuedMessage m : fairInterleave(batchByTenant)) {
    pool.submit(() -> handleOne(m.tenantId(), m));   // 在途计数 inFlight.incrementAndGet()
}
```
   配置新增 `agent.messaging.worker-threads: "${AGENT_MESSAGING_WORKER_THREADS:4}"`，在 `MessagingPolicy` 用 `requireBoundedInt(..., 64)` fail-closed 校验（与 `WorkerPolicy.requireConcurrency` 同风格）。
   ⚠️ 并发提升后必须同步复核改进点 4 的连接池公式：`workerThreads × 实例数` 不能把主池 10 打满（HikariCP pool-locking 公式 `pool size = Tn × (Cm − 1) + 1`）。
2. **指标口径（两条 trigger 取最大）**：新增只读视图 `platform.v_scaling_backlog`（`deploy/sql/platform/` 下新迁移 `18_platform_scaling_backlog.sql`）：
```sql
-- ⚠️ KEDA 的 postgresql trigger 用专用角色连接，若走 app_agent(NOBYPASSRLS) 且不绑 GUC，
--    FORCE RLS 会让它看到 0 行 → 恒不扩容（铁律 1）。故用专用只读角色 + 平台域视图。
CREATE OR REPLACE VIEW platform.v_scaling_backlog AS
SELECT
  GREATEST(
    (SELECT COUNT(*) FROM public.outbox_event      WHERE state = 'PENDING'),
    (SELECT COUNT(*) FROM public.agent_message_queue WHERE state = 'PENDING'),
    (SELECT COUNT(*) FROM public.run              WHERE state = 'QUEUED')
  )::bigint AS backlog;
GRANT SELECT ON platform.v_scaling_backlog TO keda_probe;
REVOKE ALL ON platform.v_scaling_backlog FROM app_agent;   -- 绝不复用业务角色
```
   KEDA `query` 用 `SELECT COALESCE((SELECT backlog FROM platform.v_scaling_backlog), 0);`（官方要求 `COALESCE` 防 NULL）。
3. **ScaledObject**（新文件 `deploy/k8s/scaledobject-agent-worker.yaml`）：
```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: agent-worker
  namespace: agent-platform
spec:
  scaleTargetRef:
    name: agent-worker                 # Deployment 名
  pollingInterval: 15                  # 与 HPA sync-period 对齐
  cooldownPeriod: 300                  # 与 HPA downscale-stabilization 5min 对齐
  minReplicaCount: 1                  # ⚠️ LangGraph 官方「At least 1 queue worker ... no runs orphaned」
  maxReplicaCount: 6                  # ⚠️ 由改进点 4 的 max_connections 公式推导，不是拍脑袋
  advanced:
    horizontalPodAutoscalerConfig:
      behavior:                        # 防抖动
        scaleDown:
          stabilizationWindowSeconds: 300
  triggers:
    - type: postgresql
      name: pg-backlog
      authenticationRef: { name: keda-pg-auth }
      metadata:
        host: postgres.agent-platform.svc.cluster.local
        port: "5432"
        dbName: agent_prod
        userName: keda_probe
        sslmode: require
        query: "SELECT COALESCE((SELECT backlog FROM platform.v_scaling_backlog), 0);"
        targetQueryValue: "20"         # 每副本目标积压 20 条（口径：单副本 20 条 = 触发扩容）
        activationTargetQueryValue: "5"# <5 条可缩到 minReplicaCount
    - type: rabbitmq                   # 仅当 AGENT_MESSAGING_MODE=rabbitmq 或 tenant-modes 含 rabbitmq 时启用
      name: rabbit-queue-depth
      authenticationRef: { name: keda-rabbit-auth }
      metadata:
        protocol: http
        queueName: agent.run.execute
        mode: QueueLength
        value: "20"                    # 官方：1 pod 处理 10 条、队列 30 条 → 3 pods
        activationValue: "5"
```
   `TriggerAuthentication` 用 K8s Secret 注入 PG/Rabbit 凭据，**绝不写进 yml**（配置外部化纪律）。
4. **Deployment 配套**：`agent-worker` Deployment 的 `replicas` 交给 HPA 管理，`AGENT_WORKER_ID` 用 `fieldRef: metadata.name` 注入（顺带修 §4.5(e)）：
```yaml
env:
  - name: AGENT_WORKER_ID
    valueFrom: { fieldRef: { fieldPath: metadata.name } }
  - name: AGENT_TENANT_SLUGS
    valueFrom: { configMapKeyRef: { name: agent-pilot, key: tenant-slugs } }
```
5. **护栏联动**：`maxReplicaCount` 必须由改进点 4 的公式计算并写成常量注释；KEDA 扩容不得突破 PG 连接数上限，否则「自动扩容」会变成「自动把 DB 打爆」（AP9）。

**预期收益（指标口径）**
- 扩容时延：注入 `backlog=200`（目标 20/副本）→ 60s 内副本数从 1 → 6（`maxReplicaCount`），`outbox_event(PENDING)` 单调下降。
- 积压消化：恒定 λ=50 run/s 注入下，`P95(run QUEUED→RUNNING)` 从当前「受单线程限制」降至 < 5s（口径：改进点 7 的基线对比）。
- 缩容：backlog 归零后 5 分钟回到 `minReplicaCount=1`，无 Run 孤儿（`run.state='RUNNING' AND lease_expires_at < now()` 计数 = 0）。
- 新增可观测：`keda_scaler_backlog`、`agent_worker_replicas`、`scaling_events_total`。

**实施成本与风险**
- 改 1 个 Java 类（PgQueueListener 并发模型）+ 1 个策略类 + 1 个 SQL 迁移 + 2 个 k8s YAML + 2 个 Secret；**并发模型改动面较大**，必须先有改进点 7 的压测基线再灰度。
- **RLS 风险最高**：KEDA 查询角色必须用平台域视图 / 专用角色，若图省事给 `keda_probe` 加 BYPASSRLS 或复用 `app_agent`，会直接违反铁律 1 且可能读到跨租户数据（只 COUNT 不读明细，但仍属越权通道）。
- **扩容上限风险**：`maxReplicaCount` 与 `max_connections` 耦合，改进点 4 未落地前先设保守值 3。
- 需灰度：`agent.messaging.worker-threads=1` 即旧行为（顺序消费），可对比。

**优先级**：P0（视图 + ScaledObject + worker 身份注入）、P1（DB 通道进程内并发）
**排期**：随 P5「生产就绪」阶段；DB 并发改动排在改进点 7 压测基线之后。

**验收门禁**
1. **指标门禁（真实交互，铁律 17）**：用 `scripts/` 新增 `scale-backlog-inject.sh` 真实插入 200 条 PENDING outbox（`app_agent` 绑定 GUC），断言 `platform.v_scaling_backlog.backlog = 200`；**撤掉视图里的 `outbox_event` 分支 → 断言变红**。
2. **RLS 反证**：以 `app_agent`（NOBYPASSRLS）**不绑 GUC** 查 `v_scaling_backlog` → 必须 0 行 / 拒绝（`REVOKE` 生效）；**撤掉 `REVOKE ... FROM app_agent` → 用例变红**（铁律 1）。
3. **扩容门禁（k8s 集成测）**：`kubectl apply` ScaledObject 后注入积压，断言 `kubectl get hpa` 的 `REPLICAS` 在 60s 内 ≥ 6；**把 `targetQueryValue` 改成 9999 → 不扩容，用例变红**。
4. **并发门禁**：`PgQueueListenerConcurrencyIT` 注入 2 租户各 10 条、单条 sleep 200ms，断言 `worker-threads=4` 时总耗时 < 1.2s 且租户 B 首条在 300ms 内开始；**`worker-threads=1` 时耗时 > 3.5s 且 B 首条 > 2s（撤掉线程池必红）**。
5. **worker 身份门禁**：起 3 个副本，断言 `SELECT DISTINCT lease_owner FROM run WHERE ...` = 3 个不同值；**去掉 `fieldRef` 注入 → 全为 `worker-local`，用例变红**（§4.5(e) 反证）。
6. **上限门禁**：断言 `maxReplicaCount × 每实例连接数 ≤ max_connections − 预留`，写进 `ApplicationConfigTest`，改大 `maxReplicaCount` 即红。

### 改进点 2 · 租户级并发配额与隔离（noisy neighbor 防护）（P0）

**问题陈述**
- `ConfigReadService.java:138-139` 项目自证「租户并发无限制」；`platform.tenant_quota.run_concurrency_limit` 无准入消费方（§4.5(f)）。
- `PgQueueListener.pollOnce()` 按固定租户顺序、整批顺序执行 ⇒ Head-of-Line blocking；全局背压让一个租户灌爆队列时**所有租户一起停发**（D-7/D-10）。
- cgroups / K8s QoS 管不了进程内共享线程池的排队顺序（§2.1(6)）。

**方案设计**
1. **把已有 quota 列接线（不新造概念）**：新增 `platform.tenant_concurrency`（`deploy/sql/platform/19_platform_tenant_concurrency.sql`）：
```sql
CREATE TABLE platform.tenant_concurrency (
    tenant_id       uuid PRIMARY KEY REFERENCES platform.tenant(id),
    max_in_flight   integer NOT NULL CHECK (max_in_flight > 0),
    in_flight       integer NOT NULL DEFAULT 0 CHECK (in_flight >= 0),
    priority        smallint NOT NULL DEFAULT 0,   -- 优先级队列用
    updated_at      timestamptz NOT NULL DEFAULT now()
);
-- 原子占额：条件 UPDATE + RETURNING，拿不到额度即拒绝（fail-closed）
-- UPDATE platform.tenant_concurrency
--    SET in_flight = in_flight + 1, updated_at = now()
--  WHERE tenant_id = $1 AND in_flight < max_in_flight
--  RETURNING in_flight;
```
   与维度 09 的预算原子条件 UPDATE 同构（「应用层原子 UPDATE + DB CHECK 双保险」），**不用 `SELECT count(*) FOR UPDATE`**（会把并发准入串行化，见 `JdbcBudgetRepository.java:49-51` 的同类论证）。
2. **准入点（两处，缺一不可）**：
   - `RunCreationService`（创建期）：`TenantConcurrencyGuard.tryAcquire(tenantId)`，失败即 `429 / TENANT_CONCURRENCY_EXCEEDED` + `Retry-After`（SRE Ch.21 明确拒绝也要给客户端节流信号），**不写 outbox**、不创建 Run。
   - `PgQueueListener.doHandle` / `RabbitExecutionListener`（消费期）：领取前再问一次 guard（防「创建时没超额、排队期间超额」）；释放放在 `finally`（含 UNKNOWN / 异常路径）。
   - 新增接口 `TenantConcurrencyPort`（`agent-ports`），实现在 `agent-persistence`，遵循铁律 4（main 侧 JDBC import 只许 persistence）。
3. **公平调度 / 独立池（二选一，按阶段）**：
   - 近期：`pollOnce()` 把 `for (tenantId : tenantIds)` 改为**按租户 round-robin interleave + 每租户单轮上限 `perTenantBatch = ceil(batchSize / tenantCount)`**，杜绝 A 租户 50 条跑完才轮到 B。
   - 中期：**按租户独立 worker 池 / 优先级队列**——`agent.messaging.tenant-pools: "t-a:4,t-b:2"`（复用 `tenant-modes` 的解析风格，`MessagingPolicy` 校验 slug 必须在清单内否则拒启），每租户独立 `Semaphore(max_in_flight)`；高优先级租户独立 `ThreadPoolExecutor`。
4. **per-tenant 背压**：把 `BackpressureController.allowPublish()` 从全局单水位改为**按租户水位**（`platform.tenant_concurrency` 加 `high_watermark/low_watermark`），一个租户超限只停该租户的 `OutboxPublisher`，其余租户继续发——与 `OutboxRelay` 已有的「单租户失败不终止本轮」语义对齐。
5. **配置接线修正**：`agent.tenant.max-concurrent-runs`（`yml:506`）改为**从 `platform.tenant_concurrency.max_in_flight` 读取并作为全局兜底上限**，同时把 `ConfigReadService.java:138-139` 的 `effective` 从 `false` 改为 `true` 并更新说明；`ConfigReadServiceTest` 相应解锁。⚠️ 这一步是**把死键变活**，必须走维度 13 的治理发布（配置变更双人复核），不得直接改 yml 生效。

**预期收益（指标口径）**
- 隔离：注入「租户 A 1000 条长任务（每条 2s）+ 租户 B 1 条短任务」→ 租户 B 的 `QUEUED→RUNNING` P95 < 2 × 基线（当前会被 A 饿死，预期 > 50×）。
- 配额：租户 A `max_in_flight=5` 时，并发在途恒 ≤ 5（`SELECT in_flight` 采样）；超限请求返回 429 且**不产生 outbox 行**。
- 背压：A 队列超其水位时，B 的 `outbox_event` 发布速率不下降（口径：`published_per_tenant` 分租户计数器）。

**实施成本与风险**
- 新增 1 张表 + 1 个端口/实现 + 改 3 处（创建、DB 消费、Rabbit 消费）+ 改 `pollOnce` 调度 + 1 个 ConfigReadService 条目；DDL 需同步 `03_platform_roles.sql`（铁律 7：新表同步角色授权）。
- **风险**：`in_flight` 泄漏（进程崩溃未 finally 释放）⇒ 租户被永久限流。必须配 `lease`/TTL 回收：新增 `RunRecoverySweeper` 一轮里按 `run.state IN (RUNNING,QUEUED) AND lease_expires_at < now()` 对账重置 `in_flight`（与已有崩溃恢复同轮）。

- 与维度 09 预算预留共享「原子条件 UPDATE」写法，避免引入第二套并发语义。

**优先级**：P0（配额接线 + 公平调度）、P1（独立池 + per-tenant 背压）
**排期**：P5 生产就绪；独立池进 P6 多租户扩量阶段（与改进点 5 灰度扩量同步）。

**验收门禁**

### 改进点 3 · Graceful Shutdown：preStop + 停止领取 + 等待在途完成 + 释放租约（P0）

**问题陈述**
- 已有 `WorkerShutdownCoordinator`（`WorkerLoopConfig.java:701-740`）+ `OutboxRelay.stop()` / `PgQueueListener.stop()` 的 join 语义（D-9），但 `:706-708` 明确**不等待在途 Run 完成、不主动释放租约**，靠 30s 租约过期 + 30s sweeper 接管。
- **无 k8s 生命周期契约**：全仓无 `preStop` / `terminationGracePeriodSeconds` / drain 端点（§4.5(h)）；默认 30s 宽限期与 `STOP_TIMEOUT_MS=30_000` + `lease-seconds=30`（`yml:219`）撞车，K8s 可能在中继 join 完成前 SIGKILL（§2.1(7) 官方宽限期算式）。
- 缩容到 0 / 整组滚动重启时，在途 Run 会停在 `RUNNING` 直到被接管。

**方案设计**
1. **新增 `WorkerDrainService`**（`platform/agent-application/.../lifecycle/WorkerDrainService.java`），幂等（preStop 是 at-least-once，§2.1(7)）：
```java
public final class WorkerDrainService {
    private final AtomicBoolean draining = new AtomicBoolean(false);
    private final AtomicInteger inFlight = new AtomicInteger(0);   // RunExecutionLoop 进入/退出时增减
    private final OutboxRelay relay;
    private final PgQueueListener pgListener;
    private final RunClaimPort claimPort;
    private final Duration drainTimeout;   // 必须 < terminationGracePeriodSeconds

    /** @return 是否已排空；preStop 会轮询本方法对应端点直到 true */
    public DrainSnapshot drain() {
        if (draining.compareAndSet(false, true)) {
            relay.stop();        // ① 停止发布新任务
            pgListener.stop();   // ② 停止领取新消息（已存在，复用）
        }
        return new DrainSnapshot(draining.get(), inFlight.get(), /* 已释放租约数 */ released.get());
    }
    /** ③ 在途完成后主动释放租约，让其他实例立即接管而非等 30s 过期 */
    private void onRunFinished(String tenantId, String runId, String fencingToken, String workerId) {
        inFlight.decrementAndGet();
        claimPort.releaseLease(tenantId, runId, fencingToken, workerId);
    }
}
```
2. **新增 `RunClaimPort.releaseLease(...)`**（`agent-ports/.../RunClaimPort.java` + `JdbcRunClaimRepository` 实现）：条件更新 `SET lease_owner=NULL, lease_expires_at=NULL WHERE run_id=? AND lease_owner=? AND fencing_token=?`，**按 workerId + fencing 双条件**，绝不误放他人租约（与 `renewLease` 同源纪律）。
3. **在途计数挂钩**：`RunDispatchConsumer.consume()` 在 `executor.execute` 前 `inFlight.incrementAndGet()`，`finally` 里 `decrement + releaseLease`（覆盖 SUCCEEDED/FAILED/UNKNOWN/异常全路径，与 `tryFailRunAsOrphan` 兜底并存）。
4. **drain 端点**（`agent-api`）：`POST /actuator/worker/drain` 返回 `{draining, inFlight, released}`；readiness probe 在 `draining=true` 时置 `false`（**先从 Endpoint 摘流量**，这是 preStop sleep 要达到的效果）。
5. **k8s 配置**（`deploy/k8s/deployment-agent-worker.yaml`）：
```yaml
spec:
  template:
    spec:
      terminationGracePeriodSeconds: 180      # > drainTimeout(120) + join(30) + 余量
      containers:
        - name: agent-worker
          lifecycle:
            preStop:
              exec:
                # ① 先 sleep 让 Endpoint 摘除传播；② 触发 drain 并轮询至在途归零
                command: ["sh","-c",
                  "sleep 5; until curl -sf -XPOST http://127.0.0.1:8080/actuator/worker/drain | grep -q '\"inFlight\":0'; do sleep 2; done"]
          readinessProbe:
            httpGet: { path: /actuator/health/readiness, port: 8080 }
            periodSeconds: 2
          env:
            - name: AGENT_WORKER_DRAIN_TIMEOUT_MS
              value: "120000"
```
   ⚠️ preStop 必须**在 SIGTERM 之前完成**（官方：`hook must complete before the TERM signal`），且 `terminationGracePeriodSeconds` 覆盖「preStop + 容器停止」总和；`drainTimeout < 宽限期`，超时则放行让租约机制兜底（不无限挂住）。
6. **把 `WorkerShutdownCoordinator.close()` 改为委托 `WorkerDrainService.drain()`**，保留「停中继 → 停监听」顺序（`WorkerLoopConfig.java:702-705` 的纪律不能破）。

**预期收益（指标口径）**
- 滚动重启期间 `run.state='RUNNING' AND lease_expires_at < now()` 的孤儿 Run 数 = **0**（当前靠 30s 过期会短暂 > 0）。
- 在途 Run 完成率：SIGTERM 时点有 N 个在途，宽限期内收敛到终态的比例 = 100%；或被主动释放租约后由其他实例在 < 5s 内接管（当前需等到租约过期 + sweeper 30s）。
- 缩容到 0 无 Run 卡死；`preStop` 重复投递 2 次时 `drain()` 幂等，不产生二次释放。

**实施成本与风险**
- 改 3 处 Java（新增 service、端口/实现、consumer 挂钩）+ 1 个端点 + 1 个 k8s YAML + 改 `WorkerShutdownCoordinator`；`releaseLease` 是新 DB 写路径，需同步 `03_platform_roles.sql` 的 UPDATE 授权（铁律 7）。
- **风险最高**：`releaseLease` 条件写错会误放他人租约 → 双 Worker 写同一 Run（fencing 会拒旧世代，但仍属 Sev-0 边缘）；必须 `WHERE lease_owner = workerId AND fencing_token = ?` 双条件 + 单测反证。
- **风险**：preStop 轮询若 `inFlight` 永不归零（长任务 > drainTimeout）会挂到宽限期被 SIGKILL；必须有超时放行 + 日志告警，不能 `until` 无限等待。
- 需灰度：先只在 worker Deployment 启用，控制面实例不启用。

**验收门禁**
1. **释放租约单测**：两个 `workerId` 领取同一 Run（模拟接管），`releaseLease(w1, ...)` 必须影响 0 行、`releaseLease(w2, ...)` 影响 1 行；**去掉 `lease_owner=?` 条件 → 误放，用例变红**。
2. **在途集成测（真实 SIGTERM，铁律 17）**：起 1 个实例跑 10s 长任务，中途 `kubectl delete pod` → 断言该 Run 在宽限期内收敛为 SUCCEEDED 或被立即接管（< 5s），且 `run` 表无 `RUNNING` 残留；**撤掉 `releaseLease` 挂钩 → 出现 30s 孤儿窗口，用例变红**。
3. **drain 幂等门禁**：连续调用 `drain()` 3 次，断言 `relay.stop()` 只执行 1 次（`AtomicBoolean`）、`released` 不重复；**去掉 CAS → 计数异常，用例变红**。
4. **preStop 顺序门禁**：k8s 集成测断言 `readiness=false` **先于** 首个新任务被拒绝；**去掉 sleep/readiness 联动 → 仍有新流量进入，用例变红**。
5. **宽限期算式门禁（静态守卫）**：`DeploymentLintTest` 断言 `terminationGracePeriodSeconds > AGENT_WORKER_DRAIN_TIMEOUT_MS/1000 + 30`；改小宽限期即红（§2.1(7) 官方算式）。
6. **超时放行门禁**：注入一个永不结束的在途任务，断言 preStop 在 `drainTimeout` 后放行、Pod 最终终止（不 `Terminating` 到天荒地老）；**去掉超时 → 用例超时变红**。

### 改进点 4 · 连接池与 PG 容量规划（HikariCP + PgBouncer 评估 + max_connections 公式）（P0）

**问题陈述**
- `application.yml:30` 主池 `maximum-pool-size: 10`、`:651` 运维池 2、`:392` 清理池 2；**没有任何「实例数上限」的推导或守卫**（§4.5(h) 无容量文档）。
- PG `max_connections` 默认 100、`superuser_reserved_connections=3`（官方文档 §2.1(8)）；扩容到 N 个实例时连接数线性膨胀，AP9「sorry, too many clients」是迟早的事。
- `connection-init-sql: SET search_path TO public`（`yml:29`）是**会话级 SET**；PgBouncer transaction pooling 官方 feature map 明确 `SET/RESET: Never`（§2.1(8)）——若将来直接上 transaction pooling，这条初始化会静默失效，可能把表建到错误 schema（yml:14-20 注释正是防这个）。
- 未评估 PgBouncer；`dr.rpo/rto` 只是声明。

**方案设计**
1. **写出并守卫容量公式**（新增 `docs/容量规划基线.md` 由改进点 7 产出，此处先把约束编码进 `ApplicationConfigTest`）：
```
设：C_pg      = max_connections（默认 100）
    R_super   = superuser_reserved_connections（默认 3）
    R_other   = 迁移/运维/监控/Grafana 等常驻连接（实测，建议预留 ≥ 10）
    P_main    = spring.datasource.hikari.maximum-pool-size        (= 10)
    P_ops     = agent.platform-ops.datasource.max-pool-size        (= 2)
    P_ret     = agent.retention.datasource.max-pool-size           (= 2)
    N         = Worker/API 实例总数（含 KEDA 扩到的 maxReplicaCount）

硬约束：N × (P_main + P_ops + P_ret) ≤ C_pg − R_super − R_other
默认：  N × 14 ≤ 100 − 3 − 10 = 87  ⇒  N ≤ 6
⇒ KEDA 的 maxReplicaCount 必须 ≤ 6（改进点 1 直接引用本式）。
若需 N > 6：① 降 P_main（HikariCP 公式，见下）或 ② 引入 PgBouncer 或 ③ 调 C_pg（但官方警告共享内存随之增长，需实测）。
```
   HikariCP 经验起点：`P_main ≈ (core_count × 2) + effective_spindle_count`（SSD/全缓存下趋近 `core_count × 2`）；本项目 4C 实例 ⇒ 8~10 是合理量级，**不要盲目调大**。pool-locking 下限 `pool size = Tn × (Cm − 1) + 1`（`Tn` = 改进点 1 的 `worker-threads`，`Cm` = 单 Run 同时持有的连接数，实测）。
2. **连接池参数补全**（`application.yml:28-31`）：
```yaml
spring:
  datasource:
    hikari:
      connection-init-sql: SET search_path TO public
      maximum-pool-size: "${AGENT_HIKARI_MAX_POOL_SIZE:10}"   # 改 env 可覆盖，容量公式同步
      minimum-idle: "${AGENT_HIKARI_MIN_IDLE:1}"
      connection-timeout: "${AGENT_HIKARI_CONNECTION_TIMEOUT_MS:5000}"   # 池满快速失败，别无限等
      leak-detection-threshold: "${AGENT_HIKARI_LEAK_DETECTION_MS:30000}" # 在途任务持连接过久可见
      max-lifetime: "${AGENT_HIKARI_MAX_LIFETIME_MS:1740000}"             # < PG/网络层 idle 超时
```
   在 `PrimaryDataSourceConfiguration` 增加启动期守卫：`N × pools ≤ 预算`（N 由部署侧 `AGENT_EXPECTED_INSTANCES` 注入，缺失即拒启，fail-closed 与 D-4 同纪律）。
3. **PgBouncer 评估（结论先行：先不上 transaction pooling）**：
   - 若只需解决「连接数」，`session pooling` 与本平台**完全兼容**（官方：支持全部 PG 特性，`SET` 可用），但连接复用收益有限；
   - `transaction pooling` 收益最大，但**与本平台两处冲突**：① `connection-init-sql` 的会话级 `SET search_path` 失效；② RLS GUC 若被改成会话级 `SET app.tenant_id` 会失效（**但按铁律 1，本项目是事务内 `set_config('app.tenant_id', ..., true)`，属事务局部，反而相容**）。
   - 改造方案：把 `connection-init-sql` 从会话级 `SET` 改为每条业务事务开头由 `TenantSessionBinder` 一并 `set_config('search_path', 'public', true)`；**上线前必须用 `app_agent(NOBYPASSRLS)` 真实跑一遍 RLS 验收**（铁律 1/17），确认 `search_path` 与 `app.tenant_id` 在事务内均生效。
   - 折中建议：**先用「降 P_main + 限 N」满足试点期（N≤6），把 PgBouncer 列为 N>6 时的备选**，并明确 KEDA 文档 (Remarks) 也提示 KEDA 自身应走 PG 默认端口而非 PgBouncer 端口（§2.1(2) 已核实）。
4. **监控**：Grafana 增加 `hikaricp_connections_active / pending / timeout`、`pg_stat_activity.count by usename`，告警阈值 `active / max_pool > 0.8` 持续 5min（口径来自改进点 7 的基线）。

**预期收益（指标口径）**
- 容量可知：`N ≤ 6` 成为**可执行守卫**而非口头约定；KEDA `maxReplicaCount` 与之绑定，扩容不会打爆 PG。
- 连接故障：`pg` 报 `too many clients` 次数 = 0；`hikaricp_connections_pending` P95 < 10（池未成为瓶颈）。
- 池满诊断：`connection-timeout` 5s + `leak-detection-threshold` 30s ⇒ 长事务持连接可被定位，而非「全员变慢且无因」。

**实施成本与风险**
- 改 1 个 yml 段 + 1 个配置类守卫 + 1 个测试 + 1 份容量文档；PgBouncer 属**评估结论**不在本期落地（避免过度工程）。
- **风险**：把 `connection-init-sql` 改成事务内 `set_config` 会触碰所有业务事务入口，属高风险改动，必须走维度 13 治理发布 + 全量 RLS 反向验证（撤掉绑定即 0 行）。
- **风险**：调小 `P_main` 可能与改进点 1 的 `worker-threads` 冲突（pool-locking），两改进点必须联调，用压测验证 TPS 不降。

**优先级**：P0（公式 + 守卫 + 参数）、P2（PgBouncer 落地评估）
**排期**：公式与守卫随 P5；PgBouncer 进「N>6 扩容」里程碑触发时再评估。

**验收门禁**
1. **公式门禁**：`CapacityFormulaTest` 参数化 `C_pg=100, R=13, pools=14 → N=6`；**改 `maxReplicaCount=7` → 断言失败（红）**。
2. **启动守卫门禁**：`AGENT_EXPECTED_INSTANCES=7` 且未调池大小 → 启动抛 `IllegalStateException`（fail-closed）；**撤掉守卫 → 启动成功，用例变红**。
3. **连接数实测门禁（真实交互，铁律 17）**：起 6 个实例，查 `SELECT count(*) FROM pg_stat_activity WHERE usename='app_agent'` ≤ 87；**起第 7 个 → 应被守卫拒绝而非连上**。
4. **PgBouncer 兼容性门禁（若启用）**：transaction pooling 下以 `app_agent` 真实执行一条带 RLS 的查询，断言返回本租户行且 `search_path=public`；**把 `set_config` 改回会话级 `SET` → 查询 0 行 / 建表到错 schema，用例变红**（铁律 1）。
5. **pool-locking 门禁**：`worker-threads=4`、单 Run 持 2 连接时断言 `P_main ≥ 4×(2−1)+1 = 5`；调小到 4 → 压测出现获取连接超时，用例变红。
6. **告警门禁**：注入池打满场景，断言 `hikaricp_connections_pending > 0` 且 5min 内触发告警；**撤掉 Micrometer 绑定 → 无指标，用例变红**。

### 改进点 5 · 灰度机制产品化：从 env 白名单到 DB 配置 + 灰度百分比 + 自动回滚（P1）

**问题陈述**
- `deployment.pilot.max-tenants: "1"` 是 **yml 字面量**（`yml:654-658`），扩量要改文件 → 重新打包 fat jar → 重启；`AGENT_TENANT_SLUGS` 是 env 白名单（`platform.env`）；两处真相源靠人工一致（D-6/§4.5(g)）。
- 无百分比放量、无自动回滚、无审计；与 Fowler CanaryRelease「slowly roll out + reroute to rollback」不符（§2.1(4)）。
- 三~五套租户来源并存（`tenant-slugs` / `tenant-modes` / retention / `RunRecoverySweeper.listTenants`），`yml:215` 自承「两套来源迟早不一致」。

**方案设计**
1. **DDL**（`deploy/sql/platform/20_platform_pilot_config.sql`，同步 `03_platform_roles.sql` 授权，铁律 7）：
```sql
CREATE TABLE platform.pilot_config (
    id                  smallint PRIMARY KEY DEFAULT 1 CHECK (id = 1),  -- 单行配置
    phase               text NOT NULL CHECK (phase IN ('SINGLE','CANARY','RAMP','GA')),
    max_tenants         integer NOT NULL CHECK (max_tenants > 0),
    rollout_percent     integer NOT NULL CHECK (rollout_percent BETWEEN 0 AND 100),
    allowlist           jsonb NOT NULL DEFAULT '[]'::jsonb, -- 显式 slug 白名单（保留「越权降级为不可用」语义）
    error_rate_threshold numeric(5,4) NOT NULL DEFAULT 0.05,  -- 自动回滚阈值
    version             bigint NOT NULL,                      -- CAS 切指针，绝不 max(version)
    updated_by          text NOT NULL,
    updated_at          timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE platform.tenant_pilot_state (
    tenant_id     uuid PRIMARY KEY REFERENCES platform.tenant(id),
    slug          text NOT NULL UNIQUE,
    enrolled_at   timestamptz NOT NULL DEFAULT now(),
    cell_id       text,                    -- 预留给改进点 6
    state         text NOT NULL CHECK (state IN ('ELIGIBLE','ENROLLED','ROLLED_BACK'))
);
```
   ⚠️ 复用维度 13 的治理纪律：**双人复核 + CAS 切版本 + 不可变发布**，绝不「直接 UPDATE 生效」；`version` 只由 `ConfigPublishService` 的指针切换递增（与 `cap_config_pointer` 同源）。
2. **解析替换**：新增 `PilotGovernanceService`（`agent-application`），`resolveTenantSlugs()` 读 `platform.pilot_config` + `tenant_pilot_state`，逻辑：
```
有效租户 = allowlist ∪ { hash(tenant_id) % 100 < rollout_percent 的 ELIGIBLE 租户 }
最终清单长度 ≤ max_tenants（保留 WorkerPolicy 的硬上限，代码强制不撤）
```
   `WorkerLoopConfig.messagingChannels()`（`WorkerLoopConfig.java:403-414`）改为注入 `PilotGovernanceService`；**`WorkerPolicy.requireTenantSlugs` 的 fail-closed 校验全部保留**（D-6 的安全取向不能丢），只是 `raw` 从 env 换成 DB 解析结果。
3. **统一租户来源**：`agent.messaging.tenant-modes`（`yml:470`）、`agent.retention` 租户来源、`RunRecoverySweeper.listTenants("ACTIVE", 200)` 全部改为经 `PilotGovernanceService.activeTenantIds()` 收窄 —— 消除 §4.5(g) 的「sweeper 枚举全量租户」张力。
4. **自动回滚**：新增 `PilotHealthGuard`（`agent-application` + `@Scheduled`），每 60s 按 `platform.agent_trace_metric`（维度 10 已有事实表）算「新纳入租户的 Run 失败率 / UNKNOWN 率」；超 `error_rate_threshold` 即触发**治理期回滚工单**（写 `cap_config_publish_request`，走双人复核，不自动直接改配置——铁律 8 fail-closed、避免自动改治理态），标记 `tenant_pilot_state.state='ROLLED_BACK'` 并把该租户从有效清单移除。
5. **兼容与迁移**：`deployment.pilot.max-tenants` 改为 `"${PILOT_MAX_TENANTS:${...}}"` 并**降级为兜底读 DB 失败时的拒启依据**；`AGENT_TENANT_SLUGS` 保留为「DB 不可用时的 fail-closed 兜底」，但启动日志必须打「来源=DB / 兜底=env」可见（避免「以为在灰度、实际没灰度」，`WorkerLoopConfig:399-402` 同款纪律）。

**预期收益（指标口径）**
- 扩租户时延：从「改 yml + 打包 + 重启（数十分钟、需发版）」→「DB 治理发布 + 实例热重载（< 1 个中继轮询周期 200ms + 配置刷新）」，且**零重启**。
- 可回滚：注入 `error_rate=10%` → 60s 内生成回滚工单且该租户从有效清单移除；口径 `pilot_rollback_latency_seconds < 120`。
- 一致性：`tenant-slugs / tenant-modes / retention / sweeper` 四套来源收敛为 1 个 `activeTenantIds()`，配置漂移缺陷数归零。

**实施成本与风险**
- 新增 2 张表 + 1 个 service + 1 个 guard + 改 4 处租户来源 + 1 个治理端点；**触碰维度 13 治理发布链路**，改动面大。
- **风险最高**：DB 配置读取失败时若回落到「空清单」或「全量租户」都会出问题——必须 fail-closed 拒启（沿用 D-6 哲学），不能「读不到就先放行」。
- **风险**：自动回滚若直接改治理态会破坏「双人复核 / 状态只能前进」铁律，故设计为**生成工单**而非直接生效（诚实取舍：牺牲回滚速度换治理完整性）。
- 需灰度：先 `phase=SINGLE, rollout_percent=0, allowlist=[t-e2e-fe]` 与现状逐位等价（`enabled` 影子对照），再逐步放量。

**优先级**：P1
**排期**：P5 末 / P6「多租户扩量」阶段（与改进点 2 独立池、改进点 6 cell 化同步设计）。

**验收门禁**
1. **等价门禁（影子对照）**：`phase=SINGLE, rollout_percent=0, allowlist=[t-e2e-fe]` 时，断言 `resolveTenantSlugs()` 与旧 `AGENT_TENANT_SLUGS` 输出**逐位相同**；**改一个字符 → 用例变红**（对标维度 06 的 G1 影子零差异纪律）。
2. **上限仍代码强制**：把 `allowlist` 塞 3 个租户而 `max_tenants=1` → 断言抛 `IllegalStateException("灰度控制不得被配置绕过")`；**撤掉 `WorkerPolicy.requireTenantSlugs` 调用 → 3 个全放行，用例变红**（D-6 不可退化）。
3. **百分比门禁**：`rollout_percent=10`、100 个 ELIGIBLE 租户，断言纳入数落在 [5, 15] 且 `hash` 稳定（同输入恒等输出）；**改成随机数 → 重复运行不一致，用例变红**。
4. **fail-closed 门禁**：模拟 `platform.pilot_config` 不可读 → 断言**拒绝启动**而非回落全量；**改成 catch 后返回 `List.of()`（空清单）→ 启动成功但消息永不发布，用例变红**。
5. **自动回滚门禁**：注入 `error_rate=0.10` → 断言 60s 内 `cap_config_publish_request` 新增一行且 `tenant_pilot_state.state='ROLLED_BACK'`；**撤掉 `PilotHealthGuard` 调度 → 无工单，用例变红**。
6. **来源统一门禁**：`RunRecoverySweeper` 一轮的 `listTenants` 结果集合 ⊆ `activeTenantIds()`；**改回 `listTenants("ACTIVE",200)` → 出现清单外租户，用例变红**（§4.5(g) 反证）。
7. **治理门禁（铁律 13/维度 13）**：断言 `pilot_config.version` 只能经 `ConfigPublishService` CAS 递增、直接 UPDATE 被触发器拒；`two_person_ck` 生效。

### 改进点 6 · Cell-Based 隔离（按租户分组到不同 cell，限制爆炸半径）（P2）

**问题陈述**
- 当前所有租户共享一个 worker 池、一个 PG 实例、一次全量发布 ⇒ 一次坏发布 / 一次 DB 抖动 / 一个毒请求影响 100%（D-8/劣-5）。
- AWS REL10-BP04 与 cell-based 白皮书（§2.1(3)）明确：cell 独立、不分享状态、按分区键路由，10 cell 时故障只影响 10% 请求；**且「同时把部署应用到所有 cell」是官方反模式**。
- 本平台 `dr.rpo=24h/rto=4h`（`yml:714-717`）与「单池共享」不相称。

**方案设计**
1. **分区键 = `tenant_id`**（AWS 官方示例即 customer ID），cell 路由层只做「tenant → cell」映射，**不承载业务逻辑**（官方反模式：向路由器层加复杂逻辑）。DDL（`21_platform_cell.sql`）：
```sql
CREATE TABLE platform.cell_assignment (
    tenant_id   uuid PRIMARY KEY REFERENCES platform.tenant(id),
    cell_id     text NOT NULL,
    version     bigint NOT NULL,
    migrated_at timestamptz
);
CREATE TABLE platform.cell_registry (
    cell_id     text PRIMARY KEY,
    phase       text NOT NULL CHECK (phase IN ('ACTIVE','CANARY','DRAINING','OFFLINE')),
    db_dsn_key  text NOT NULL,     -- 指向该 cell 的 PG 连接配置键（真隔离的关键）
    slug_set    jsonb NOT NULL     -- 该 cell 服务的 AGENT_TENANT_SLUGS
);
```
2. **cell 拓扑**：每个 cell = 一套独立 `agent-worker` Deployment + 独立 `AGENT_TENANT_SLUGS`（取自 `cell_registry.slug_set`）+ 独立 KEDA ScaledObject（`maxReplicaCount` 按该 cell 的 PG 连接预算单独算）+ **独立 PG 实例/独立 schema**（否则 DB 仍是共享故障域，cell 化只是假隔离）。
   - 控制面可按 cell 拆或保持共享（读多写少、无状态），但 `outbox_event` / `agent_message_queue` / `run` 必须随 cell 走。
   - **canary cell**：新版本先只发到 `phase='CANARY'` 的 cell（AWS Guidance Step 6），观察 1 个完整压测周期后再逐 cell 滚动，**绝不一次推全量**。
3. **路由层**：新增 `CellRouter`（`agent-api` 前置或独立轻量网关），按已验签 JWT 的 `tenant_id claim` 查 `cell_assignment` 转发；**找不到映射即 403/503 显式终态**（铁律 15：终态/权限错误不得伪装成临时故障、不给重试）。迁移期间旧 cell 留 marker 重定向（AWS Guidance Step 8 的 rebalancer 思路）。
4. **与灰度联动**：改进点 5 的 `tenant_pilot_state.cell_id` 就是 cell 落点；`rollout_percent` 先只作用于 CANARY cell 的租户，形成「灰度 → cell」二级漏斗。
5. **诚实标注取舍**：**真 cell 隔离要求按 cell 拆 DB**，这与本项目「PG 单一权威事实源」「治理发布单指针（`cap_config_pointer`）」存在根本张力——跨 cell 的治理发布、全局审计（`platform.authz_decision_log`）、跨租户指标汇聚都要重新设计。因此本改进点定位为 **P2 / 远期**，且明确「**共享 PG 的伪 cell 只隔离计算不隔离存储**」，不得对外宣称已实现故障域隔离。

**预期收益（指标口径）**
- 爆炸半径：单 cell 故障 / 坏发布时受影响租户比例 = `1 / cell_count`；目标 4 cell 时 ≤ 25%（口径：`affected_tenants / total_tenants`）。
- 发布：CANARY cell 观察期 ≥ 1 个压测周期，全量发布前 `error_rate` 无回归；「同时部署到所有 cell」的流水线调用次数 = 0。
- 隔离：cell A 的 PG 连接池耗尽时，cell B 的 `P95(QUEUED→RUNNING)` 不劣化 > 5%。

**实施成本与风险**
- **成本最高**：拆 DB 意味着 DDL、Flyway 迁移、治理发布、审计汇聚、备份/恢复、跨 cell 报表全部改造；多个 `max_connections` 预算；运维复杂度 ×N。
- **风险**：cell 间数据不一致（同一租户被路由到两个 cell）⇒ 需 `cell_assignment.version` CAS + 迁移期双写/只读窗口（Fowler 蓝绿的 DB 纪律，§2.1(4)）。
- **风险**：路由层成为新单点且若塞业务逻辑即命中 AWS 反模式；必须保持无状态、可多副本、只做映射。
- 需灰度：先 1 个 cell（等价现状）+ 1 个 CANARY cell 只放内部测试租户。

**优先级**：P2
**排期**：远期（多租户规模 > 试点期、且改进点 5/7 落地后）；本期只产出「cell 路由设计 + 伪 cell 演练」，不拆 DB。

**验收门禁**
1. **路由门禁（真实交互，铁律 17）**：租户 `t-a` 的请求恒落到 `cell-1`、`t-b` 恒落 `cell-2`；**撤掉 `cell_assignment` 查询改回固定路由 → 用例变红**。
2. **分区键门禁**：`CellRouter` 不得读取 `run.input_payload.scenario` 或任何业务字段（铁律 9 同源纪律）；静态扫描 + 单测断言只用 `tenant_id`。
3. **爆炸半径集成测**：对 `cell-1` 注入 PG 连接池耗尽，断言 `cell-2` 的 Run 仍正常收敛且 P95 劣化 < 5%；**若两 cell 共用一个 DSN → 隔离失败，用例变红**（这正好验证「伪 cell 不算数」）。
4. **发布纪律门禁**：部署流水线断言「同一次发布目标 cell 数 = 1」且首目标 `phase='CANARY'`；**改成全量 → 用例变红**（AWS 反模式 AP12）。
5. **终态门禁**：无映射租户返回 403/503 且不重试（铁律 15）；**改成 5xx + 客户端重试 → 用例变红**。
6. **一致性门禁**：同一 `tenant_id` 并发迁移断言只有 1 个 `cell_assignment` 版本胜出（CAS）；去掉 version 条件即红。

### 改进点 7 · 容量基线与压测（单 worker 吞吐 / DB 瓶颈点 / P95 拐点）（P0）

**问题陈述**
- `application.yml` 至少 4 处写「调优时点：P4 压测实测消费速率后」（`:311, 492-497, 505`），但仓库**无压测方案、无基线数据、无拐点结论**。
- 改进点 1/2/4 的三层配比、`maxReplicaCount`、连接池公式、KEDA `targetQueryValue=20` 全部依赖「单副本能处理多少」——没有这个数，所有扩容参数都是猜的。
- SRE Ch.22 明确要求「add load until the system breaks / know the breaking point」（§2.1(5)）；我们目前连拐点在哪都不知道。

**方案设计**
1. **压测工具与脚本**：新增 `scripts/bench/`（`k6` 或 Gatling，`Makefile` 编排），三类场景：
   - **S1 单 worker 吞吐**：固定 1 实例、关闭背压影响（或记录背压触发点），逐步提升 λ，测 `runs_completed/s`、`QUEUED→RUNNING`、P50/P95/P99、`outbox_event` 发布延迟。
   - **S2 DB 瓶颈定位**：分别打 `outbox_event` 轮询、`agent_message_queue` claim（SKIP LOCKED）、RLS 绑定（`set_config` 开销）、`run_step` INSERT；采集 `pg_stat_activity` / `pg_locks` / `pg_stat_user_tables`、Hikari `active/pending`、CPU / IO。
   - **S3 P95 拐点 / 破坏性测试**：按 Little's Law `L = λW` 持续加 λ 直到 P95 非线性上翘，记录 `λ_knee`、`utilization_knee`、此时 `backlog` 与 `max_connections` 余量；再验证过载后撤压能否恢复（SRE Ch.22「Can the system recover gracefully」）。
2. **基线表**（产出 `docs/容量规划基线.md`，被改进点 1/4 引用）：
```
| 指标 | 口径 | 目标/实测 | 用途 |
| 单实例吞吐 R1 | 1 worker、标准 Run(≤3 步/1 工具) | ___ runs/s | KEDA targetQueryValue = R1 × 目标排队时长 |
| DB 每 Run 连接占用 | pg_stat_activity 采样 | ___ | 改进点 4 的 Cm / pool-locking |
| P95 拐点 λ_knee | QUEUED→RUNNING P95 上翘点 | ___ runs/s | maxReplicaCount 与背压 high-watermark |
| RLS 开销 | 同 SQL 绑/不绑 GUC 对比 | ___ ms | 容量模型修正项 |
| outbox 轮询压力 | N 实例 × 200ms 轮询的 QPS | ___ | DB 规格 |
```
3. **把基线编码进配置**：`high-watermark`（`yml:311`）、`targetQueryValue`（改进点 1）、`maxReplicaCount`(改进点 1/4)、`worker-threads`(改进点 1)、`max_in_flight`(改进点 2) 全部**由基线推导并在注释里写明来源**，禁止再出现「保守初值」无出处。
4. **CI 回归门禁**：把 S1 的「单实例吞吐不低于基线 90%」做成 nightly 或发版前门禁，防止某次改动悄悄把吞吐打回单线程（§4.5(b) 这类漂移的防复发）。

**预期收益（指标口径）**
- 所有扩容参数有实测出处；`targetQueryValue` 从「拍的 20」变成 `R1 × 目标排队秒数`。
- 得到 `λ_knee` 后可定义 SLO：`稳态利用率 ≤ 0.7 × λ_knee`（SRE 利用率—延迟非线性）；背压 `high-watermark` 设为「`λ_knee` 对应 backlog × 0.8」。
- 破坏性测试给出「过载后恢复时间」与「是否级联」，补齐 `dr.rto=4h` 的演练证据。

**实施成本与风险**
- 主要是脚本 + 文档 + CI 作业；需一个与生产同构的隔离压测库（`scripts/init-it-db.sh` 已有 IT 库基础），**绝不压生产/共享 dev 库**（`platform.env` 指向 RDS 实例）。
- **风险**：压测会真实调用模型 / 产生 `usage_record` 成本，必须用 `fake` 模型（`yml:530` 已内置单价 0 的假模型）与独立租户，且 judge 成本绝不混 `usage_record`（铁律 8）。
- **风险**：压测数据污染指标宽表 `platform.agent_trace_metric`；需独立库或事后按租户清理（受控通道，铁律 8 无物理删除端点）。

**优先级**：P0（必须先于改进点 1/4 的参数定稿）
**排期**：P5 首个里程碑；改进点 1/2/4 的配置定稿以本报告产出为前置。

**验收门禁**
1. **基线可复现门禁**：`make bench-s1` 连续 3 次 `R1` 变异系数 < 10%；**把 `worker-threads` 改回 1 → R1 显著下降，用例变红**（§4.5(b) 的运行时反证，铁律 17）。
2. **拐点门禁**：S3 报告必须给出 `λ_knee` 且 P95 在拐点后 ≥ 3 × 基线；**若压测脚本没打到拐点就结束 → 报告生成失败（红）**。
3. **参数溯源门禁**：静态检查 `application.yml` 与 `scaledobject-*.yaml` 中每个容量参数注释含「来源=S1/S2/S3」；**删掉出处注释 → lint 红**。
4. **DB 瓶颈门禁**：S2 必须定位到**具体**瓶颈表/锁（不能只写「DB 慢」）；采样 `pg_locks` 与 `hikaricp_connections_pending`；**撤掉采样 → 报告缺项，用例变红**。
5. **恢复门禁（SRE Ch.22）**：撤压后 5 分钟内 P95 回到基线 ±10% 且无孤儿 Run；**若出现级联不恢复 → 用例变红**。
6. **成本隔离门禁**：压测全程 `usage_record` 中真实模型 cost = 0（只用 `fake`）、独立租户；**误用真实模型 → 断言红**（铁律 8）。
7. **CI 回归门禁**：吞吐低于基线 90% 即阻断发版；**把 PgQueueListener 并发改回单线程 → nightly 红**。

## 八、其他有价值的横向对比

### 8.1 与本项目其他维度的耦合与相互约束（≥2 条）

1. **↔ 维度 02 多租户隔离（最强耦合）**：部署层每加一个实例 / 一个连接，都要重新证明「RLS 的 GUC 在事务内、业务 SQL 前绑定」（铁律 1）。改进点 4 的 PgBouncer transaction pooling 评估之所以高风险，正因为 `SET/RESET` 在 transaction pooling 下是 Never——**部署形态的选择会直接改变 RLS 是否成立**。改进点 1 的 KEDA 查询视图也必须避开 `app_agent` + 未绑 GUC 的 0 行陷阱。反之，维度 02 的 FORCE RLS 是改进点 6「cell 拆 DB」的最大约束：拆库后 `current_tenant_id()` / 42 张表策略 / 复合外键要按 cell 各复制一套。
2. **↔ 维度 03 状态持久化与可恢复性**：改进点 3 的 `releaseLease` 直接触碰 `run.lease_owner/lease_expires_at` 与 `fencing_token`（`enforce_fencing_on_write` 触发器）；改错会让旧世代写新世代状态（Sev-0）。同时「无状态 worker + DB 事实源」（D-1）是 12-Factor VI 与本维度全部伸缩论证的前提——若将来把状态挪进 Redis/内存，本报告所有扩容结论作废。
3. **↔ 维度 09 成本与预算控制**：改进点 2 的 `tenant_concurrency` 原子条件 UPDATE 与预算 `budget_no_overspend` CHECK + 原子预留是**同一套「应用层原子 UPDATE + DB CHECK 双保险」**；两处应共用写法，避免第二套并发语义。扩容会增加并发预留次数，压测（改进点 7）必须覆盖预算竞争。
4. **↔ 维度 10 可观测性与审计**：改进点 1/2/5/7 全部依赖 `platform.agent_trace_metric` 与队列深度指标；`BackpressureController.isThrottled()` 已是可用的扩容信号但没有 Grafana 面板（竞品报告 §维度 10 也点明「Prometheus alert rules 未落地」）。改进点 5 的自动回滚按 `agent_trace_metric` 算失败率，必须与「终态 ≠ 成功」口径对齐（维度 10 的硬规则）。
5. **↔ 维度 11 可靠性与故障处理**：改进点 3 的「在途等待 + 主动释放租约」是维度 11「孤儿 Run 兜底收敛」（`RunDispatchConsumer.tryFailRunAsOrphan`、sweeper）的**前置收敛**——把「等 30s 租约过期再接管」提前到「停机即接管」，会减少 UNKNOWN / 孤儿窗口。反向：sweeper 每 30s 扫描是改进点 2 `in_flight` 泄漏回收的挂载点。
6. **↔ 维度 13 人机协同 / 治理发布**：改进点 5 的 `pilot_config`、改进点 6 的 `cell_assignment` 都必须走「双人复核 + CAS 切指针 + 不可变发布」；`cap_config_pointer` 当前是**单指针**，cell 化后跨 cell 发布一致性是未解问题（已在 §7 改进点 6 诚实标注）。

### 8.2 与非 agent 领域成熟做法的对照

| 领域 | 成熟做法 | 可借鉴到本维度 |
|---|---|---|
| **金融核心系统「单元化 / 异地多活」** | 按客户号分单元（shard），单元内自包含应用 + 数据，单元间无同步调用；灰度按单元切流；RPO/RTO 按单元定义 | 改进点 6 的 cell 设计几乎同构；金融界强调「单元内闭环、跨单元只走异步对账」可指导我们别在 cell 路由层塞业务逻辑 |
| **数据库中间件 / 分库分表（ShardingSphere、Vitess）** | 连接池治理、读写分离、连接数预算、慢查询熔断 | 改进点 4：把 `N × pools ≤ max_connections` 做成中间件级硬约束而非文档 |
| **电信信令网过载控制** | 按用户等级 / 业务关键性的分级拒绝、令牌桶、过载时按百分比丢弃（类似 SRE Criticality） | 改进点 2 的 per-tenant 配额 + 优先级队列；「拒绝也要给明确码 + Retry-After」 |
| **消息队列中间件（Kafka / RocketMQ）** | 分区（partition） = 并行度单位、消费者组 rebalance、按分区限流、积压 lag 作为伸缩信号 | 改进点 1 的「队列深度即伸缩信号」、改进点 2 的「按租户 = 按分区做公平调度」 |
| **传统应用服务器（WebLogic / WebSphere）** | 工作管理器（Work Manager）、线程池隔离、连接池 + 过载拒绝、优雅停机 `drain` | 本平台的 `WorkerPolicy` / `BackpressurePolicy` 就是轻量版 Work Manager；缺的是「按租户的工作管理器」 |
| **SRE 容量管理（Google / AWS）** | load test to breaking point、per-customer quota、client-side throttling、error budget 驱动发布 | 改进点 7（破坏性测试）与改进点 5（按 error rate 自动回滚）的直接来源 |

### 8.3 反向思考：若从头重做本维度，我们会怎么设计？（并诚实指出与现状的取舍）

若 2026 年重新设计，我会做四件与现状不同的事：

1. **从第一天就把「控制面」与「执行面」做成两个独立构建产物**（而不是一个 fat jar + 开关）：`agent-api` 与 `agent-worker` 各自 Dockerfile、各自 Deployment、各自 HPA。这直接对齐 12-Factor VIII 的 process type 与 LangGraph 的 split API/queue，也让 KEDA 只扩 worker 不扩 API。**取舍**：会失去「一个事务里同时写 run + outbox + budget」的极简一致性与本地 `java -jar` 的开发体验——这正是现状选择单体的理由，我不建议现在拆。
2. **把消息通道收敛为一条**：默认就用外部 broker 或默认就用 PG 队列，别同时维护两条等价通道 + 按租户切换。双通道是 P4-D17 为「无 broker 试运营」做的过渡，代价是 `concurrency/prefetch` 一半时间在默认部署下是死配置（§4.5(b)）。**取舍**：现状的「灰度切通道」能力确实帮试运营省了部署成本，是多付复杂度换的灵活性。
3. **把「租户并发配额」与「灰度上限」放进同一个准入治理体系**（改进点 2 + 5 合并设计）：既然已经有 `pilot.max-tenants` 这种代码级容量承诺，就该同时有 `max_in_flight`，而不是等到项目自己用 `ConfigReadService` 标红「无限制」才补。**取舍**：这属于事后视角，试运营单租户阶段确实不需要。
4. **先定容量基线再定配置**（改进点 7 前置）：所有 `concurrency/prefetch/high-watermark/batch-size/max-concurrent-runs` 都应有「来源=压测 S1/S3」的注释，而不是「保守初值、调优时点：P4 压测」。**取舍**：早期快速迭代时，先给保守值跑起来比先搭压测环境更现实；代价是这些数字后来没人回头改，其中 `max-concurrent-runs` 甚至一直没接上线。

**明确不建议现在改的**：不拆单体、不引入 Redis、不上 PgBouncer transaction pooling、不拆 DB 做真 cell。理由统一——它们都会破坏「PG 单一权威事实源 + 单事务边界」这一本项目最硬的结构性优势，而当前规模（试点 1 租户、`max-tenants=1`）远未到需要它们的临界点。**先做 7/4/3/2/1，把 L1 上沿补成扎实的 L2，再谈 L3。**

### 9.3 风险清单（做这一步可能踩的坑，关联本项目已知铁律）

|---|---|---|---|

### 9.4 一句话结论

**本平台用「无状态 worker + PostgreSQL 唯一事实源 + 租约/fencing」把 12-Factor VI 的「可安全扩容」做到了竞品里最硬的一档，还独有「代码强制的租户准入灰度」；但它停在了 12-Factor VIII 的前半句——「可以加进程」而非「自动加进程」：无托管运行时、无队列深度伸缩、无租户级并发准入、无 K8s 停机契约、无容量基线，且默认 database 模式下三层并发配比实际失配（有效并发 1）、OutboxRelay 发布侧未加互斥。近期的正确动作不是追 L3 托管，而是先用压测基线（7）→ 连接上限（4）→ 优雅停机（3）→ 租户隔离（2）→ 队列驱动 HPA（1）把 L1 上沿补成扎实的 L2，再谈灰度产品化（5）与 Cell 化（6）。**
