## 一、维度定义与评估坐标系

### 1.1 这个维度到底解决什么问题（问题陈述，不谈实现）

"流式输出"回答的不是"agent 能输出什么"，而是**一组关于「用户何时、以何种保真度看到 agent 中间过程」的元问题**：

- 一次 agent run 从创建到终态可能持续数十秒甚至数分钟，用户是**等终态一次性拿到全部结果**，还是**边执行边看到步骤（路由、RAG、工具调用、token 增量）**？
- 当网络抖动、浏览器标签页切走、代理超时导致连接断开，**用户能否从断点续看、不重不漏**？
- 当用户在 run 中途点"取消"，**是切断了 SSE 连接，还是真的取消了后台 Run**？两者语义是否被正确区分？
- 当模型吐 token 的速度**快过前端渲染/网络下发**时，服务端如何不把内存/连接撑爆（背压）？
- 当 agent 在**语音/视频**通道里说话，用户能否**中途打断**（双向流）？

这一维度是"用户体验可见性"与"系统资源边界"的交汇点——它直接决定产品观感（"卡不卡、连不连得上"），又深度耦合维度 03（事件持久化是续传底座）、07（订阅须重新授权）、10（流式可观测）、11（连接泄漏=故障）。

### 1.2 能力分层的四档模型（通用分层法）

按"事件从哪来、连接模型、续传由谁保证"给出四档，从弱到强：

| 档位 | 名称 | 事件来源 / 连接模型 | 代表形态 | 典型代价 |
|---|---|---|---|---|
| **L0 无流式** | 请求/响应一次性 | 无；终态后才返回 | 同步 `chat/completions` 单次 | 长 run 期间用户零可见性；无中途取消 |
| **L1 应用层轮询** | 客户端定时拉 | 客户端每 N 秒 `GET /events`；事件存内存 | 自建前端定时器轮询 | 延迟由轮询周期决定；连接频繁重建；断点需自管 |
| **L2 框架长连接流** | 库/SDK 内 SSE/WS | 框架内建 SSE/WebSocket；事件多在内存或框架专用持久层 | OpenAI Agents SDK、Anthropic Agent SDK、LangGraph、ADK（SSE/live）、CrewAI、Agno、AutoGen | 续传/幂等靠框架；与业务库分离；多租户隔离交宿主 |
| **L3 持久事实表驱动流** | 事件即 DB 事实 + SSE 下发 | `run_event`（PG 权威事实表）单调递增 `sequence_no`；读表经 SSE 下发；续传游标=序列号 | **本平台（两条流：chat SSE + run-event 流）** | 延迟由服务端轮询/下发决定；"真零轮询"归 P4；解析器与协议强耦合需治理 |

**判定**：本平台落在 **L3（持久事实表驱动）**，与 L0–L2 的本质区别是——**流不是"凭空推送的临时数据"，而是"对一张不可变事实表的可重放读取"**。这带来"续传天然幂等、断点不丢、可审计"的优势，代价是延迟由服务端轮询配置决定（见第七章 I-1 的 LISTEN/NOTIFY 混合方案）。

### 1.3 评估坐标系：5 个评价轴

| 轴 | 含义 | 观测方式（如何度量） |
|---|---|---|
| **可见性及时性** | 用户多快看到首事件 / 每步增量 | 注入一个多步 run，度量 `run_created → 首事件到达`、`step 完成 → 前端显示` 的 P95 延迟 |
| **续传正确性** | 断线重连后不重不漏 | 切断连接再重连（带 Last-Event-ID），断言收到的事件集合恰好是 `[cursor+1, N]`，且无重复 |
| **终止信号可靠性** | 前端能否确切知道"结束了" | 断言终态 run 的响应一定含 `: run-terminal` 注释行；断言缺失该信号时前端轮询是否永不停止 |
| **资源边界（背压）** | 慢消费者不撑爆服务端 | 构造"前端消费极慢"场景，度量服务端连接内存/线程是否受限；断言有缓冲上限或丢弃策略 |
| **隔离与授权** | 流式通道不越权、不泄露 | 断言租户 A 的令牌不能订阅租户 B 的 run 事件；断言平台令牌不能穿过租户链（反之亦然） |

## 二、理论体系（必须引用真实出处）

### 2.1 核心理论/概念框架（≥3 个，逐一给真实出处）

#### (1) Server-Sent Events（SSE）/ `EventSource` 规范
- **出处**：WHATWG HTML 规范 §9.2 *"Server-sent events"*（https://html.spec.whatwg.org/multipage/server-sent-events.html ，权威镜像 https://whatwg.org/C/server-sent-events.html ；另见 https://www.w3.org/TR/eventsource/ W3C 版本）。
- **核心语义（逐条对照本项目）**：
  - **`text/event-stream` 线格式**：事件块由若干行组成，空行（`\n\n`）为分发边界；字段名 `data`/`event`/`id`/`retry`/`:`(注释)，冒号后可选一个空格被剥离。
  - **`id` 字段 = Last-Event-ID**："if the connection died between this block and the next, the server would be sent a `Last-Event-ID` header with the value…"，即客户端重连时自动把最后见到的 `id` 作为 `Last-Event-ID` 请求头回传——这是**标准断线续传机制**的规范根。
  - **`retry` 字段**：设置重连延迟（毫秒），解析到即生效，不需空行。
  - **注释行（以 `:` 开头）**：被解析器忽略，规范明确建议"include a comment line every 15 seconds"以对抗代理超时——即**心跳/保活**的规范用法。
  - **重连**：`EventSource` 在连接断开后自动重连；多数非 2xx / 网络错误被视为可重试。
- **与本维度的关系**：本项目两条流（chat SSE、run-event 流）的 wire 格式完全是 WHATWG SSE；`RunEventStreamer.FrameSender.sendComment`（`: run-terminal`）正是规范里的"注释行作为控制/终止信号"的标准用法。**关键契约**：前端 `sse.ts` 仅认 `: run-terminal` 注释行作终止信号（见 4.2 D-TERM 与诚实边界）。

#### (2) SSE vs WebSocket vs 长轮询 vs gRPC streaming vs HTTP/2 选型矩阵
- **出处**：属分布式系统/Web 传输工程共识，可由 WHATWG SSE 规范 + IETF RFC 6455（*The WebSocket Protocol*，Fette & Melnikov, 2011）+ IETF RFC 7540（*HTTP/2*，Belshe et al., 2015）+ gRPC 官方文档（https://grpc.io/docs/what-is-grpc/ ）共同支撑；浏览器侧约束见 WHATWG SSE §9.2.6 "Clients … may run into trouble … HTTP's per-server connection limitation"（**浏览器对每个域的并发连接数限制，通常 6 个**）。
- **选型矩阵**：

| 维度 | SSE | WebSocket | 长轮询 | gRPC streaming | HTTP/2 多路复用 |
|---|---|---|---|---|---|
| 方向 | 单向（服务器→客户端） | 全双工 | 单向（拉） | 双向（stream） | 多路复用单向/双向 |
| 协议升级 | 否（普通 HTTP） | 是（Upgrade: websocket） | 否 | 是（HTTP/2） | 否（原生） |
| 代理/防火墙兼容 | 好（普通 HTTP） | 部分代理剥离 Upgrade | 好 | 需 HTTP/2 端到端 | 好（但常被降级） |
| 自动重连/续传 | **内建（Last-Event-ID）** | 需自写 | 自写 | 需自写 | 自写 |
| 浏览器连接上限 | 受 6 连接限制（同域） | 同 | 同（且更碎） | 通常经网关 | 单连接多路 |
| 文本增量（token） | 天然 | 可 | 差 | 可 | 可 |
| 语音/视频双向打断 | 否 | 可 | 否 | 可（ADK live 即用） | 可 |

- **与本维度的关系**：本项目选 SSE 而非 WebSocket，正是看中"单向 + 普通 HTTP + 内建 Last-Event-ID 续传 + 代理友好"四点的组合（维度 4 是 server→client 单向广播，不需要双向帧）。竞品中 Google ADK 的 `run_live()` 选 WebSocket 双向流（见 3.4），是因为它要支持语音/视频**中途打断**——这是 SSE 的能力盲区，也是本平台的明确短板。

#### (3) Backpressure 与流控（Reactive Streams 规范 + Reactor 模型）
- **出处**：**Reactive Streams 规范**（http://www.reactive-streams.org/ ，Bonn, Kuhn, et al., 2013–2015，定义了 `Publisher/Subscriber/Subscription/Processor` 与"请求式拉取 `request(n)`"契约）；**Project Reactor 3 参考指南**（https://projectreactor.io/docs/core/release/reference/ ，背压策略：`BUFFER` 默认/`ERROR`/`DROP`/`LATEST`/`IGNORE`）。
- **核心模型**：Reactor 是"混合 push/pull"——消费者先 `request(n)`，源头在请求额度内 push；溢出时按 `OverflowStrategy` 处理：
  - `BUFFER`（默认，**无界缓冲，可能 OOM**）；
  - `ERROR`（队列满抛 `IllegalStateException`）；
  - `DROP`（下游未就绪则丢弃新信号）；
  - `LATEST`（只保留最新信号，丢弃旧的）；
  - `DROP_OLDEST`（丢最老以容纳新）。
- **与本维度的关系**：本平台的"服务端轮询 PG + 下发"在概念上等价于一个**生产者（DB 新事件）远快于消费者（前端/网络）**的流。虽未直接用 Reactor，但其背压四象限（缓冲/丢弃/最新/错误）正是本项目"慢消费者治理"的设计空间（见第七章 I-3）。token 级流中，背压直接压低模型吐字速率——"生产者=模型、消费者=网络/SSE 写入"，二者速率不匹配时必须显式决策策略。

#### (4) 幂等续传（Last-Event-ID / cursor 语义）
- **出处**：WHATWG SSE §9.2（Last-Event-ID 头回传）；分布式系统幂等性经典论述 Pat Helland *"Idempotence Keys"*（2023，原则：接收方须记住已处理过什么、对重复返回同一答案）。
- **核心语义**：续传的正确性判据是"**游标单调、读取 `[cursor+1, ∞)`、按序、可重复执行且结果一致**"。本平台用 `run_event.sequence_no`（bigint 单调，`CHECK (sequence_no > 0)`）作游标，`findAfter(tenantId, runId, cursor, 200)` 取 `sequence_no > cursor ORDER BY sequence_no ASC LIMIT 200`——天然幂等。
- **与本维度的关系**：这是"流只读持久化事实表"带来的**结构性优势**（见 4.4 D-REPLAY）：续传不需要服务端记"谁看到哪"，只需客户端回传一个数字游标。

#### (5) 事件溯源（Event Sourcing）vs 状态快照：CQRS
- **出处**：Martin Fowler *"Event Sourcing"*（https://martinfowler.com/eaaDev/EventSourcing.html ，2005）；Greg Young *"CQRS"*（https://cqrs.files.wordpress.com/2010/11/cqrs_documents.pdf ）。
- **定义**：Event Sourcing 把状态变化记录为**不可变事件序列**，当前状态 = 事件重放；CQRS 把"写模型（事件追加）"与"读模型（状态投影）"分离。
- **与本维度的关系**：本项目 `run_event` 就是一张**事实表（event log）**，而 `run` 表的 `state` 是其投影（CQRS 读模型）。流的"实时性"本质是"读模型投影 + 增量读取"。这解释了为何"流只读事实表"优于"直接流式生成"：前者可重放、可审计、可多客户端并发读同一游标，后者一旦断连就丢失中间态。

#### (6) 增量式 LLM 输出（token streaming、delta 合并）
- **出处**：OpenAI/Anthropic/Google 等 LLM API 的 streaming 约定（`stream: true` 返回 `delta` 块）；SSE 是"大多数 LLM token streaming 的传输层"（见 https://openllm.wavise.com/blog/server-sent-events-protocol-reference 的实证说明）。
- **定义**：模型以 token/字符块增量返回，客户端把 `delta` 累积合并成完整文本；多个 `data:` 行以 `\n` 连接（WHATWG 规范）。
- **与本维度的关系**：本平台 `AgentChatEvent.Delta`（`delta` 事件，data=裸文本）正是 token 增量；`Answer`（`answer` 事件）作为"终答兜底，**绝不回撤已到达的 delta**"——这是有意的设计：前端拿到 delta 即渲染，最终 answer 是幂等兜底而非覆盖。

#### (7) PostgreSQL `LISTEN/NOTIFY`（官方文档）
- **出处**：PostgreSQL 官方文档 *"NOTIFY"*（https://www.postgresql.org/docs/current/sql-notify.html ；`LISTEN` https://www.postgresql.org/docs/current/sql-listen.html ）。
- **核心语义（逐条，对本项目 P4 方案至关重要）**：
  1. **事务提交才发通知**："If NOTIFY is executed inside a transaction, the notifications are not delivered until the transaction commits."——未提交/回滚的事务不产生通知。
  2. **不持久、断连丢失**："If no one is listening — your listener crashed, was restarting, or lost its connection — the message is simply gone. There's no replay."（PG 官方 + 社区共识一致）。通知队列默认 8GB，但**仅对"在线的监听者"投递**。
  3. **载荷上限 8KB**，超长应只发 ID 让监听者回表取。
  4. **PgBouncer 陷阱**：事务池化模式下 `LISTEN` 注册在"不会保留的连接"上——监听者必须直连 PG（或 session 模式池）。
  5. **同事务同 payload 去重**：同一事务内相同 channel+payload 只投递一次。
- **与本维度的关系**：这是本项目"真零轮询"的候选底层（把"服务端轮询 PG"升级为"NOTIFY 唤醒 + 表兜底"），但**第 2 条的"不持久、断连丢失"决定了它必须配 `run_event` 事实表兜底**——见第七章 I-1 的"混合方案"。

#### (8) SSE 连接数与代理超时（nginx `proxy_read_timeout` / `X-Accel-Buffering`）
- **出处**：nginx 官方文档 `proxy_read_timeout`（http://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_read_timeout ）、`X-Accel-Buffering`（http://nginx.org/en/docs/http/ngx_http_proxy_module.html#x_accel_buffering ）；WHATWG SSE §9.2.6 代理超时建议。
- **核心语义**：① nginx 默认 `proxy_read_timeout=60s`，SSE 长连接会被**静默切断**——须调大或心跳保活；② nginx 默认**缓冲**上游响应，导致事件"攒批后才下发"，必须 `X-Accel-Buffering: no` 关闭。
- **与本维度的关系**：本项目 `RunEventController` 已显式下发 `X-Accel-Buffering: no` + `Cache-Control: no-cache, no-store`（RunEventController.java:257-260），这正是针对 nginx 缓冲的防御；`RunEventStreamer` 的 `maxLifetimeMillis` 则是防"代理/连接永久悬挂"的兜底。

### 2.2 理论给出的「设计张力」（trade-off）清单

| # | 张力 | A 方案 | B 方案 | 本平台选择 |
|---|---|---|---|---|
| T1 | 流来源 | 内存态实时推送（低延迟、易丢） | DB 事实表驱动（可重放、延迟由轮询定） | **DB 事实表驱动（L3）** |
| T2 | 连接模型 | 长连接 SseEmitter（实时、占资源） | 短连接 + Last-Event-ID 续传（省资源、略增往返） | **run-event 用短连接续传；chat 用长连接 SseEmitter** |
| T3 | 终止信号表达 | 业务事件帧（`event: run-terminal`） | SSE 注释行（`: run-terminal` 控制帧） | **注释行（控制帧）** |
| T4 | 续传游标 | 服务端记忆（会话态） | 客户端回传游标（Last-Event-ID / sequence_no） | **客户端回传（幂等游标）** |
| T5 | 背压 | 无限缓冲（简单、OOM 风险） | 有界缓冲/丢弃/最新（可控、可能丢） | **当前无显式背压（缺口，I-3 补）** |
| T6 | 推送机制 | 真零轮询（LISTEN/NOTIFY） | 服务端轮询 PG | **当前服务端轮询（P4 升级 I-1）** |
| T7 | 事件契约 | 竞品"任意事件流" | 固定事件集 + 版本化 | **固定 13+1 事件集 + v1.1 版本化** |

### 2.3 业界公认的反模式（anti-pattern）清单及判别方式

1. **业务事件流混入假事件（终止帧当事件发）**：终止信号作为带 `id` 的事件帧下发，前端事件分支要求 `id` 否则丢弃→终止信号丢失→轮询永不停止。判别：看终止信号是否走注释行而非事件帧（本项目曾犯此错，见 4.2 D-TERM）。
2. **代理缓冲导致"不推送"**：nginx 未关 `X-Accel-Buffering`，事件攒批。判别：查响应头是否含 `X-Accel-Buffering: no`。
3. **续传非幂等（游标语义漂移）**：游标用"时间戳/页码"而非单调序列号，重连后重复或漏事件。判别：断线重连断言事件集恰好 `[cursor+1, N]`。
4. **无限缓冲撑爆连接**：慢消费者下无缓冲上限。判别：压测"极慢前端"看连接内存。
5. **把 SSE 断开当 Run 取消**：连接断开即停后台执行。判别：断开连接后查 run 是否仍跑到终态（本平台明确区分，见 4.2 D-CANCEL）。
6. **轮询把延迟写死在客户端**：客户端每 3 秒拉一次，延迟由客户端定。判别：延迟能否由服务端配置决定（本平台服务端轮询即为此）。

#### 2.3.1 反模式 → 本平台规避手段映射

| 反模式（2.3） | 本平台规避手段 | 证据锚点 |
|---|---|---|
| 终止帧当事件发 | `sendComment("run-terminal")` 注释行 + 前端只认注释 | `RunEventStreamer.java:199,71-82`；`sse.ts:42-46` |
| 代理缓冲 | `X-Accel-Buffering: no` + `Cache-Control` | `RunEventController.java:257-260` |
| 续传非幂等 | `sequence_no` 单调 + `findAfter(... > cursor)` | `JdbcRunEventQueryRepository.java:68-76` |
| 无限缓冲 | `maxLifetimeMillis` 兜底强关 + `LIMIT 200` 分批 | `RunEventStreamer.java:220-229`；`JdbcRunEventQueryRepository.java:85` |
| SSE 断开=取消 | 断开只停轮询，run 取消走 `cancel_requested_at` | `RunEventStreamer.java:151-166`；维度 03 `ToolInvocationGate.CancelGuard` |
| 客户端定延迟 | 服务端 `pollIntervalMillis` 配置化 | `RunEventStreamer.java:49-57`（注：当前硬编码 500ms，见诚实边界） |

### 2.4 端到端时序示例（标准机制如何落地）

#### 示例 A：原生 `EventSource` 断线重连续传（标准 Last-Event-ID 流）

```
  浏览器 EventSource              网关/nginx             本平台端点
       │                            │                        │
       │ GET /api/runs/{runId}/events                       │
       │  (无 Last-Event-ID)        │                        │
       ├───────────────────────────►│───────────────────────►│ 读 run_event
       │                            │                        │ 取 seq(1..200)
       │◄── id:1\ndata:...          │◄───────────────────────│
       │◄── id:2\ndata:...          │                        │
       │   ...                      │                        │
       │◄── : run-terminal          │◄──(终态)───────────────│ 追加注释行终止帧
       │  (解析器 terminal=true)    │                        │
       │  [连接关闭]                │                        │
       │                                                     
   ~~~~ 网络抖动，EventSource 自动重连 ~~~~                       
       │                                                     
       │ GET .../events            │                        │
       │  Last-Event-ID: 2         │                        │
       ├───────────────────────────►│───────────────────────►│ findAfter(...,cursor=2)
       │                            │                        │ 取 seq(3..N) 不重不漏
       │◄── id:3\ndata:...          │◄───────────────────────│
```

要点：① 续传游标由浏览器**自动回传**（`Last-Event-ID`），客户端零代码；② 服务端用 `findAfter(tenantId, runId, cursor=2, 200)` 取 `sequence_no > 2`，天然幂等、结果可重复；③ 若 run 已终态，重连仍会在末帧追加 `: run-terminal`，前端才真正停——即"重连安全，不存在重复或遗漏"。

#### 示例 B：SSE 连接断开 ≠ Run 取消（本平台 D-CANCEL 语义）

```
  用户浏览器        SSE 连接          后台 Worker(维度03)       run 表
       │               │                     │                 │
       │ 订阅 run#R     │                     │                 │
       ├──────────────►│ 读 run_event 下发     │                 │
       │◄── delta 帧... │────────────────────►│ 执行 step1,2...  │ state=RUNNING
       │               │                     │                 │
   │ 用户关标签页/断网  │                     │                 │
   │ (SSE 连接断开)    │ 连接关闭,轮询停      │                 │
       │               │ 但 run#R 继续跑 ────►│ step3 完成        │ state=SUCCEEDED
       │               │                     │                 │
   │ 稍后重连          │                     │                 │
       │ GET ../events  │                     │                 │
       │  Last-Event-ID:k├──────────────────►│ (已终态)          │
       │◄── : run-terminal│◄── 追发末态+终帧  │                 │
```

要点：连接断开**只停了"下发管道"**，Worker 不受任何影响；真取消必须走 `cancel_requested_at` + `ToolInvocationGate.CancelGuard`（维度 03），与 SSE 生命周期完全解耦。误把"断连=取消"会让用户关标签页就杀掉后台 run——本平台明确规避（4.2 D-CANCEL）。

## 三、竞品实现全景（每个主流方案一段，≥4 个）

### 3.1 OpenAI Agents SDK（streaming events）
- **官方定位与机制**：极简原语 `Agent / Runner / Handoffs / Guardrails / Sessions / Tracing`，流式通过 SDK 的 `RunResultStreaming` 逐 token / 逐 run-event 吐出（`stream_events()` 产出 `RawResponsesStreamEvent` 与 `RunItemStreamEvent`）。
- **官方来源**：https://openai.github.io/openai-agents-python/ （streaming 章节）
- **优点**：开箱即用的流式 + 内建 Tracing；与 Sessions 一体化。
- **局限/代价**：**无内建多租户隔离**（交宿主）；流式与运行时一体，无"持久事实表续传"语义；取消由调用方控制。
- **适用场景**：单租户、开发者体验优先。

### 3.2 Anthropic Claude Agent SDK（stream events / partial messages）
- **官方定位与机制**：把 Claude Code 当库用，流式由 SDK 的 `query()` / `stream` 产出**partial messages**（增量文本 + 工具调用片段）；agent loop 内 `max_turns` 熔断。
- **官方来源**：https://docs.anthropic.com/en/api/agent-sdk ；"Building Effective Agents" https://www.anthropic.com/research/building-effective-agents
- **优点**：与 Claude 工具/权限体系一体；`canUseTool` 审批 + `max_budget_usd`/`max_turns` 熔断。
- **局限/代价**：状态在进程内存；流式续传靠上层；多租户无内建。
- **适用场景**：以 Claude 为中心的产品。

### 3.3 LangGraph（stream_mode 多模）
- **官方定位与机制**：`graph.stream()` 支持多种 `stream_mode`：`values`（每步完整状态）、`updates`（每步增量）、`messages`（仅 LLM token）、`custom`（节点自定义）、`checkpoints`（检查点事件）、`tasks`、`debug`。即"同一张图可切换观察粒度"。
- **官方来源**：https://docs.langchain.com/oss/python/langgraph/streaming
- **优点**：观察粒度可组合、可调试；配合 PostgresSaver/Checkpointer 可断点续跑。
- **局限/代价**：Checkpointer 是**专用持久层**（与业务库分离）；多租户隔离无内建；流式与图强绑定。
- **适用场景**：需可组合状态图、可调试长流程。

### 3.4 Google ADK（SSE 逐字 + 双向 live `run_live()`）
- **官方定位与机制**：ADK 明确区分三种"流式"（https://goo.gle/4fH2Aa9 ）：① 服务端流式（单向 feed）；② **逐字流式（SSE，`StreamingMode.SSE`）**；③ **双向流式（`runner.run_live()`，WebSocket + Gemini Live API，支持语音/视频、用户可中途打断、`interrupted: true`）**。live 会话下，连接（WebSocket）与会话（持久上下文）分离，支持 session resumption 跨网络抖动恢复。
- **官方来源**：https://adk.dev/live/ ；live sessions https://adk.dev/live/sessions/ ；ADK 总览 https://adk.dev/
- **优点**：**双向 live + 可打断**是业界最丰富的交互形态；SSE 逐字与 live 并存；托管运行时。
- **局限/代价**：强一致/硬不超发非内建；双向流依赖 Gemini Live API（模型绑定）；多租户隔离交会话作用域。
- **适用场景**：语音/视频实时助手、低延迟交互。

### 3.5 Microsoft AutoGen（**已归档停维护，仅供参照**）
- **官方定位与机制**：分层事件驱动多智能体（Core/AgentChat），`BaseGroupChat.run_stream` 产出流式消息。
- **官方来源**：https://microsoft.github.io/autogen/stable/ （`user-guide/agentchat-user-guide/index.html`）
- **优点（历史）**：对话驱动协作灵活。
- **局限/代价**：**官方已于 2025-10 并入 Microsoft Agent Framework、2026-10 起归档停维护**；流式与状态机靠应用层；多租户无内建。**不应作为新项目选型依据**。
- **适用场景**：仅参照。

### 3.6 CrewAI（`stream=True` → `CrewStreamingOutput`）
- **官方定位与机制**：`Crew(stream=True)` 返回 `CrewStreamingOutput`，可逐块（`yield`/迭代）消费 crew 执行过程的事件/日志。
- **官方来源**：https://docs.crewai.com/en/concepts/crews （"Streaming" 章节）；企业层 https://www.crewai.com/
- **优点**：角色/任务直观；流式输出开箱即用；企业层补 RBAC/审计。
- **局限/代价**：社区版多租户强隔离无内建；背压/取消语义未明示。
- **适用场景**：角色化协作任务。

### 3.7 Agno（`stream=True`）
- **官方定位与机制**：`agent.run(stream=True)` 产出事件流（`yield` 事件），内建 per-user 数据隔离与 AgentOS 自托管。
- **官方来源**：https://docs.agno.com/hitl/overview （stream 章节）；安全总览 https://docs.agno.com/agent-os/security/overview
- **优点**：**唯一内建多租户安全**（JWT/服务账号 + per-user 隔离）的竞品；流式开箱即用；Team 协作拓扑灵活。
- **局限/代价**：隔离裁决仍在应用/SDK 层（未下沉 RLS）；AgentOS 自有运维复杂度。
- **适用场景**：自托管、开箱多租户安全。

### 3.8 竞品流式范式综合归类

| 形态 | 代表 | 流模型 | 续传/重放 | 多租户 |
|---|---|---|---|---|
| 内存态 SDK 流 | OpenAI/Anthropic/AutoGen | SDK 流式事件 | 靠上层 | 无 |
| 图持久化流 | LangGraph | stream_mode 多模 | Checkpointer 重放 | 无 |
| 双向 live | ADK（`run_live()`） | WebSocket 双向 + 可打断 | session resumption | 会话作用域 |
| 库流式 | CrewAI/Agno | `stream=True` 迭代 | 未明示 | Agno 内建 |
| **事实表驱动流** | **本平台** | **SSE + `run_event` 事实表** | **sequence_no 游标幂等续传** | **RLS 强制（L3）** |

**关键结论**：除 Agno 内建多租户外，竞品的流式多"与运行时一体、从内存/框架专用层取"，**没有一家把"事件流"做成"对一张业务事实表的可重放读取"**。本平台这一点的差异化最彻底，但也因此在"双向语音/视频打断"上最弱（SSE 单向的固有限制）。

### 3.9 选型决策树（何时选 SSE / WebSocket / gRPC）

```
  需要双向(语音/视频中途打断)? ──是──► WebSocket / gRPC (如 ADK run_live)
            │否
            ▼
  只要 server→client 单向广播? ──是──► SSE (本平台选择)
            │否
            ▼
  需要浏览器原生 + 代理友好 + 自动续传? ──是──► SSE
            │否
            ▼
  后端是 gRPC 服务且客户端也是 gRPC? ──是──► gRPC streaming
            │否
            ▼
  老旧环境不支持 SSE/WS? ──是──► 长轮询(兜底)
```

结论：本平台"维度 4 是 server→client 单向、要代理友好、要自动续传、浏览器原生"——四条件全部命中 SSE，故不选 WebSocket（双向能力用不上、且代理/防火墙更挑剔）或 gRPC（浏览器端需 grpc-web 网关）。若未来产品需要"用户打断 agent 说话"的语音交互，应**另立独立 WebSocket 通道**（8.3 已声明），而非改造 SSE。

## 四、我们的实现（源码级解剖）

### 4.1 架构与数据流（关键组件、调用链、数据落点）

本平台有**两条独立的流式通道**与**一个可选的轮询器组件**，需先厘清边界（实测，非既有报告描述的单一路径）：

#### 4.1.1 通道①：对话流式（chat SSE）—— `AgentChatController`
- **端点（铁律 12）**：`POST /api/agent/chat/stream`（平台链，aud=admin-console-api）、`POST /api/knowledge/agent/chat/stream`（租户链，aud=agent-platform），见 `AgentChatController.java:37,40,68,70`。
- **连接模型**：`SseEmitter` 长连接（`emitterFactory` 默认 `new SseEmitter(SSE_TIMEOUT_MS)`，`AgentChatController.java:79,90,163`）。
- **事件集**：`AgentChatEvent` sealed 接口（**13 个事件 + 第 14 个 `context.checkpoint`**，协议 v1.1，`AgentChatEvent.java:29-43`）。每帧经 `SseEmitter.event().name(eventName()).data(safe)` 发送（`sendFrame`，`AgentChatController.java:198-206`）——**绝不手工拼 `event:/data:`**（Spring Framework 7 覆写 `SseEmitter#send` 的硬性要求，`AgentChatController.java:343-357` 注释明示）。
- **身份域隔离**：`RequestAgentChatIdentityResolver` 从已验签令牌推导租户，**平台令牌不得穿过租户链、租户令牌不得穿过平台链**（`SecurityConfiguration.java:102-110`；E2E 测试 `AgentChatEndpointIT:130-140` 锁死）。`thinking`（推理草稿）仅在平台链可见，租户链不暴露（多租户/合规考量）。

#### 4.1.2 通道②：Run 事件流（run-event SSE）—— `RunEventController`
- **端点**：`GET /api/runs/{runId}/events`（`produces=text/event-stream`，`RunEventController.java:188-189`）。
- **连接模型**：**短连接 + Last-Event-ID 续传**（P2-D05 §3.3，注释明言"保持长连接会造成连接池耗尽"）。`streamEvents` 同步构建 `ResponseEntity<String>` 返回，**不持有长连接**（`RunEventController.java:237-261`）。
- **事件来源**：`run_event` 事实表，经 `JdbcRunEventQueryRepository.findAfter(tenantId, runId, cursor, 200)` 取 `sequence_no > cursor ORDER BY sequence_no ASC LIMIT 200`（`JdbcRunEventQueryRepository.java:68-76,85`）。
- **终止信号**：`if (TERMINAL_STATES.contains(state) && events.size() < MAX_EVENTS)` 时追加 `: run-terminal` 注释行（`RunEventController.java:246-248,323-325`）。
- **头部治理**：`X-Accel-Buffering: no` + `Cache-Control: no-cache, no-store`（`RunEventController.java:257-260`）。
- **授权**：每层 `EVENT_SUBSCRIBE` + 受众隔离（`isAudienceOnly` 只订阅本人 run），且"不存在"与"他人租户"**同返 404** 防存在性探测（`RunEventController.java:197-231`）。

#### 4.1.3 可选组件：长连接轮询器 `RunEventStreamer`
- **机制**：`RunEventStreamer.stream(SseEmitter, query, tenantId, runId, cursor, stateSupplier, terminalStates, payloadFilter, sender)` 用 `scheduleAtFixedRate` 每 `pollIntervalMillis` 轮询 `query.findAfter(...)` 下发，命中终态发 `: run-terminal` 并 `complete()`，`maxLifetimeMillis` 兜底强关（`RunEventStreamer.java:133-229`）。
- **关键事实（源码复核发现）**：`RunEventController` 持有一个 `RunEventStreamer streamer` 字段（由便捷构造器 `new RunEventStreamer(500L, 30*60*1000L)` 注入，`RunEventController.java:151,176`），但 `streamEvents` 方法**并未调用 `streamer.stream()`**——生产 run-event 端点实际走 4.1.2 的短连接模型。`RunEventStreamer.stream()` 目前**仅被 `SseStreamingTest` 单测覆盖**（见诚实边界）。该组件是"长连接 SSE"的工程化封装，可作为未来切换或 chat 流的底层，但**当前并非任一生产端点的实际执行路径**。

#### 4.1.4 数据落点
- `run_event`（`01_platform_ddl.sql:2788`）：`event_id/tenant_id/run_id/sequence_no bigint NOT NULL/event_type/text/payload jsonb`，`CHECK (sequence_no > 0)`，`FORCE ROW LEVEL SECURITY`（:2799）。`sequence_no` 单调，是续传游标。
- 写入方：`JdbcRunCreationRepository`（RUN_CREATED，`sequence_no=1`，`JdbcRunCreationRepository.java:326-327`）、`JdbcAgentChatAuditRepository`（对话审计事件，`JdbcAgentChatAuditRepository.java:76`）。`run_event` 表**只有 `RUN_CREATED` 直接由 Run 创建事务写**，其余由审计仓库写（`RunQueryController.java:24` 注释；维度 03 指出 Worker 不直接写该表）。
- `run` 表的 `state` 是终止信号的最终真相源（终态集 `SUCCEEDED/FAILED/CANCELLED/TIMED_OUT`，`RunEventController.java:61-65`）。

#### 4.1.5 写入→下发链路（一个事件如何变成 wire 帧）

以"工具调用完成"为例，追踪 `run_event` 行从产生到前端收到帧的全链路：

```
[写入侧] 审计仓库 (应用事务内)
  JdbcAgentChatAuditRepository.audit(runId, TOOL, payload)
        │ INSERT INTO run_event(event_id,tenant_id,run_id,sequence_no,event_type,payload)
        │   VALUES (..., @tenant, runId, nextval('run_event_seq'), 'tool', {...})
        │   -- sequence_no 由 run 级序列单调分配 (CHECK>0)
        ▼
  public.run_event  (FORCE RLS; 租户只能读自己的行)
        ▲
        │ (查询侧, 每次请求重校验 EVENT_SUBSCRIBE + 受众隔离)
  JdbcRunEventQueryRepository.findAfter(tenantId, runId, cursor, 200)
        │ WHERE tenant_id=? AND run_id=? AND sequence_no>? ORDER BY sequence_no ASC LIMIT 200
        │ ① 应用层 tenant_id=?  (来自令牌, 非入参)
        │ ② FORCE RLS 二次兜底 (即便误改①仍挡住跨租户)
        ▼
  RunEventController.streamEvents / RunEventStreamer.stream
        │ 逐行映射为 SSE 帧:
        │   id: <sequence_no>
        │   event: tool
        │   data: <payload 经 ALLOWED_PAYLOAD_FIELDS 白名单过滤>
        ▼
  前端 sse.ts parseFrame → 分发到 onTool(...)
```

关键不变量：① `sequence_no` 单调且唯一，是续传游标；② 租户隔离有"应用层 `tenant_id=?` + FORCE RLS"双层，任一层被破坏另一层仍生效（影子对照可验证）；③ 载荷在发出前经白名单收敛，新增字段默认不透出（D-WHITE）；④ **写入与下发解耦**——写入方宕机不影响已落表事件的续传。

#### 4.2.x 协议帧真实线格式样本（13+1 事件 → wire）

前端 `sse.ts` 实际解析的字节（每行以 `\n` 终止，空行 `\n\n` 为帧边界）。下列为真实形态（非示意占位）：

```
id: 1
event: run.start
data: {"runId":"r-9f2","agent":"kbase-qa"}

id: 3
event: rag.query
data: {"question":"退款政策?"}

id: 7
event: tool
data: {"name":"sql-lookup","args":{"table":"orders"}}

id: 12
event: delta
data: 根据退款政策，您可在

id: 18
event: answer
data: 根据退款政策，您可在 7 天内无理由退款。

id: 19
event: done
data: {"usage":{"promptTokens":120,"completionTokens":38}}

id: 20
event: context.checkpoint      ← 第 14 个事件(协议 v1.1 新增)
data: {"checkpointId":"cp-3","tokens":158}

: run-terminal                 ← 终止控制帧(注释行, 非 event)
```

契约要点：① 每帧带 `id=sequence_no`，断线重连即 `Last-Event-ID`；② `delta` 是裸文本增量（`data:` 后直接是正文，非 JSON），多个 `delta` 在前端累积合并成完整答案；③ `answer` 是终答兜底，**绝不回撤已到达的 delta**；④ `context.checkpoint` 是 v1.1 新增，老客户端（无对应 `case`）走 `default: ignore` 忽略、不中断；⑤ **终止信号永远是 `: run-terminal` 注释行**——若后端误发 `event: run-terminal`（无 `id`），前端事件分支会因缺 `id` 直接丢弃该帧 → 永收不到终止 → 轮询永不停止（D-TERM 事故根因）。

### 4.4 我们独有的设计（差异化设计）

1. **"流 = 对事实表的可重放读取"（L3，D-REPLAY）**：竞品的流多从内存/框架层取；本平台把 `run_event` 当不可变事实表，SSE 只是"按游标读取 + 下发"。这带来**结构性幂等续传**——任何客户端断线重连同游标即可，服务端无会话态。这是与维度 03（事件溯源）同源的差异化。
2. **终止信号用控制帧（注释行）而非业务事件（D-TERM）**：这是"协议语义 × 客户端解析器"强耦合的可迁移经验（详见 5.4 分歧 1）。我们用 SSE 规范原生的注释行作控制信道，隔离了"业务事件流"与"连接生命周期信号"。
3. **固定 + 版本化事件集（D-FIXED）**：`AgentChatEvent` 是 sealed 接口，13 事件 + 第 14 checkpoint 全部冻结；协议 v1.1 明确"旧 13 事件 data 字节逐字冻结、新增字段/事件向后兼容"（AgentChatEvent.java:19-28）。对照竞品"任意事件流"，我们以"契约稳定性"换"灵活性"。
4. **多租户流式隔离走"身份域分离 + RLS 双保险"（D-RLS）**：平台链/租户链在 SecurityConfiguration 层**精确不匹配**（防令牌串链），run_event 再叠加 `FORCE RLS`——两层独立、互不替代。
5. **载荷白名单 fail-closed（D-WHITE）**：以"默认拒绝"的白名单替代"默认放行"的黑名单，把"新增字段即潜在泄露"风险降到最低。

### 5.2 优势详解（为什么领先，讲清机制）

- **为什么"流=事实表读取"领先**：竞品的 `stream_events()` 多从进程内存/框架层取，断线后若上层没做重放状态就丢中间态。本平台把 `run_event`（`FORCE RLS` 事实表）当事件 log，SSE 仅是"按 `sequence_no` 游标读取 + 下发"——**续传不需要服务端记会话**，客户端回传游标即可（幂等，4.1.2）。这与 CQRS/事件溯源（2.1 理论 5）同源：读模型投影 + 增量读取，可多客户端并发读同一游标而不互相干扰。
- **为什么"终止信号用注释行"领先且可迁移**：前端 `sse.ts` 的 `parseFrame` 明确"注释行 `: run-terminal` → `terminal=true`"（sse.ts:42-46），而事件分支要求有 `id`。若后端发事件帧（`event: run-terminal` 无 `id`），前端会**直接丢弃**该帧 → 永远收不到终止信号 → 轮询每 3 秒重连**永不停止**。我们改用 SSE 规范原生的注释行作控制信道，使"连接生命周期信号"与"业务事件流"解耦（RunEventStreamer.java:71-82）。这是"协议语义 × 客户端解析器"契约耦合的标准范式，可迁移到任何 SSE 项目。
- **为什么"固定+版本化事件集"领先**：`AgentChatEvent` 是 sealed 接口，13 事件 + 第 14 `context.checkpoint` 全部冻结；v1.1 明确"旧 13 事件 data 字节逐字冻结、新增字段/事件向后兼容"（AgentChatEvent.java:19-28）。老客户端 `default: return null` 忽略未知事件，不会因协议演进崩溃。竞品的"任意事件流"灵活但易漂移、难审计。

### 5.3 劣势与盲区详解（根因分析）

- **落后 1：实时性受服务端轮询制约（根因=设计取舍 + 当前配置缺口）**。当前 run-event 流是"服务端轮询 PG"（D-POLL），且 `pollIntervalMillis` 硬编码 500ms（`RunEventController.java:151`），并非竞品 SDK 的"模型吐字即推"。更关键：**`application.yml` 的 `poll-interval-ms: "200"`（:473）属于消息队列消费，根本不是 SSE 间隔**——SSE 间隔目前无外部化配置（见诚实边界 I-2 改进）。真零轮询（LISTEN/NOTIFY）归 P4，见 I-1。
- **落后 2：无双向语音/视频打断（根因=传输选型）**。SSE 是单向协议，无法支持 ADK `run_live()` 式的"用户中途打断 agent 说话"。这是 SSE 选型的固有能力边界，非配置可补。
- **落后 3：无显式背压/慢消费者治理（根因=能力缺口）**。当前 `RunEventStreamer` 只靠 `maxLifetimeMillis` 兜底强关 + `LIMIT 200` 分批，没有"缓冲上限/丢弃策略/最新策略"的显式决策（对照 2.1 理论 3 的 Reactor 四象限）。慢消费者下连接内事件会无限堆积直到超时。见 I-3。
- **落后 4：`RunEventStreamer` 与生产的"双模型并存"认知负担（根因=历史演进）**。既有梳理报告把 `RunEventStreamer.stream()` 描述为 run-event 流式机制，但生产端点是短连接模型（4.1.3）。两套心智模型并存，新成员易误读。须靠 I-6 契约测试 + 文档澄清。

### 5.4 关键分歧点（最本质的架构分歧）

**分歧 1：终止信号该走"控制帧"还是"业务事件帧"？**
- 竞品：多在事件流里塞终止/完成事件（如 `event: done`/SDK 回调）。
- 本平台：**走 SSE 注释行控制帧**（`: run-terminal`）。
- 后果：我们用"协议原生控制信道"隔离了连接生命周期与业务事件，换来"前端解析器零歧义 + 终止信号绝不丢失"。代价是终止信号不能携带业务数据（控制帧语义）。这是"协议语义 × 客户端解析器"契约耦合的教科书级样例——**任何 SSE 项目若把终止信号塞进业务事件帧，且前端事件分支要求 `id`，就会重蹈我们 P4-D12 M-1 的坑**。

**分歧 2：流来源——"内存实时"还是"事实表重放"？**
- 竞品：流式多从内存/框架层取，低延迟但断线易丢中间态。
- 本平台：流 = 对 `run_event` 事实表的可重放读取。
- 后果：我们牺牲一点首响延迟，换"续传幂等、可审计、多客户端并发读同一游标不干扰"。适合"生产 SaaS 要可追责"的定位，不适合"极致低延迟聊天玩具"。

**分歧 3：事件契约——"固定集+版本化"还是"任意事件流"？**
- 竞品：事件类型开放、随 SDK 演进。
- 本平台：13+1 固定 + 协议版本化。
- 后果：我们换来了"前后端契约稳定、老客户端不崩"，代价是新增事件受版本治理约束（见 I-4）。这是"可维护的生产系统"对"灵活的实验框架"的典型取舍。

## 六、优缺点总评

### 6.1 我们的优点

**结构性优势（架构层，竞品普遍不具备）**
- S1：流 = 对事实表的可重放读取（L3），续传天然幂等、可审计。
- S2：终止信号走 SSE 注释行控制帧，与业务事件流解耦、绝不丢失。
- S3：固定 13+1 事件集 + 协议版本化，前后端契约稳定、老客户端不崩。
- S4：多租户流式隔离 = 身份域分离（铁律 12）+ `FORCE RLS` 双保险。

**工程性优势（实现层）**
- E1：`X-Accel-Buffering: no` 防 nginx 缓冲"假不推送"。
- E2：`maxLifetimeMillis` 兜底强关，防连接/代理永久悬挂。
- E3：载荷白名单 fail-closed，新增字段默认不泄露。
- E4：`Last-Event-ID` / `sequence_no` 游标续传，断线不重不漏。

**领域性优势（业务层）**
- D1：受众角色只订阅本人 run（`isAudienceOnly`），且"不存在/无权限"同返 404 防探测。
- D2：run-event 短连接模型省连接池、天然适配续传。

### 6.2 我们的缺点

**设计取舍导致的代价**
- C1：实时性受服务端轮询制约（SSE 间隔硬编码 500ms，无外部化配置）。
- C2：无双向语音/视频打断（SSE 单向固有限制）。
- C3：协议固定集不如"任意事件流"灵活（需版本治理，见 I-4）。

**能力缺口**
- G1：**无显式背压/慢消费者治理**（无缓冲上限/丢弃策略），I-3 补。
- G2：真零轮询（LISTEN/NOTIFY）未落地，延迟由轮询定。
- G3：`RunEventStreamer` 双模型并存（长连接轮询器 vs 生产短连接端点）带来认知与维护负担（诚实边界）。
- G4：`poll-interval-ms` 配置名被消息队列占用，SSE 间隔无独立外部化配置（诚实边界 I-2）。

**运维负担**
- O1：SSE 长连接需正确配置代理超时与 `X-Accel-Buffering`（已做，但部署须持续校验）。
- O2：前端解析器与后端协议强耦合，任何一端改协议都需同步（I-6 治理）。

- ADK：**SSE 逐字 + 双向 live `run_live()` 可打断**（adk.dev/live/）。
- AutoGen：**已归档停维护**，仅参照（microsoft.github.io/autogen）。
- CrewAI：`stream=True` → `CrewStreamingOutput`（docs.crewai.com）。
- Agno：内建 JWT/per-user 隔离的流式（docs.agno.com）。

### 6.4 每个竞品的缺点（简明，带来源）
- OpenAI/Anthropic/LangGraph/AutoGen/CrewAI：无内建多租户隔离（各自官方文档）。
- ADK：双向流绑定 Gemini Live API；强一致/硬不超发非内建。
- Agno：隔离裁决仍在应用/SDK 层，未下沉 RLS。
- AutoGen：停维护，不推荐新项目（microsoft.github.io/autogen）。

## 七、可优化与改进点（必须可执行）

> 准则：每条均写到文件/表/配置/接口级别，并给可执行的验收门禁（不写"加强测试"空话）。所有改动遵守项目铁律（尤铁律 12：SSE 不写 outbox/不发 MQ；铁律 2/7/16）。

### I-1：LISTEN/NOTIFY 混合推送（真零轮询加速）

- **问题陈述**：当前 run-event 流是"服务端轮询 PG"（`pollIntervalMillis` 硬编码 500ms，RunEventStreamer.java:49），对延迟敏感的首响偏保守；纯轮询不是真零延迟（维度 4 梳理报告已标注真零轮询归 P4）。
- **方案设计**：
  - **监听者**：新增 `PgNotifyDispatchListener`（置于 `agent-infrastructure` 或 `agent-application` 的 messaging 包），在专属直连 PG 连接（**非 PgBouncer 事务池**，避免 LISTEN 注册丢失，2.1 理论 7）上 `LISTEN run_event_channel`。
  - **通知载荷**：Run 创建/审计写 `run_event` 的**同一事务**内 `SELECT pg_notify('run_event_channel', run_id::text)`（事务提交才发，2.1 理论 7 第 1 条）。**只发 run_id，不塞全量 payload**（8KB 上限 + 回表取更稳）。
  - **丢事件兜底（核心）**：因 NOTIFY "不持久、断连丢失"（2.1 理论 7 第 2 条），保留 `run_event` 事实表作为**权威兜底**——监听者收到 notify 仅"唤醒"对应 run 的增量扫描；若 notify 丢失/监听器重启，仍由**轮询兜底**按 `sequence_no` 补齐（与维度 03 的 outbox 双通道同源）。
  - **连接重建**：监听器须处理 PG 连接断开→重连→`LISTEN`（重新注册），重连后第一件事先全量扫描未消费游标（防重连期间丢失的通知）。
  - **指标**：新增 `sse_notify_wakeups`（NOTIFY 命中）、`sse_poll_fallbacks`（轮询补齐）、`sse_notify_lost`（推断丢失，= 期望-实际）三个 Counter。
  - **配置**（`application.yml` 加，fail-closed 默认关）：
    ```
    agent.api.streaming.notify-enabled: "false"   # P4 灰度开启
    agent.api.streaming.notify-channel: "run_event_channel"
    ```
- **预期收益**：开启后 run-event 首响延迟从 ≤500ms 降到 ≤50ms（P99）。可度量：基准测试对比 `notify-enabled=true/false` 的 `run_created → 首事件到达` P95/P99。
- **实施成本与风险**：新增监听者 + 配置；风险：NOTIFY 在连接池/事务边界下可能丢失或乱序——故**轮询兜底必须保留**，NOTIFY 仅加速不替代（铁律类比：维度 01 的 I-5 同思路）。须验证 NOTIFY 与 RLS（`app.tenant_id`）绑定上下文不冲突（通知不携带租户，监听器用 run_id 回表取，天然 RLS 安全）。
- **优先级**：P3（P4 期，对应"真零轮询"）。
- **验收门禁**：① `NotifyDispatchIT`：开启 NOTIFY，断言 `run_created → 首事件到达` P99 < 50ms；② 关闭 NOTIFY（仅轮询）→ 断言延迟回落 ≤500ms 且功能不退化；③ 注入"NOTIFY 丢弃"→ 断言轮询兜底仍能补齐、无永久卡死、无重复事件；④ 断言监听器重启后先全量扫描再 LISTEN（防重连丢事件）。

### I-2：`Last-Event-ID` 标准断线重连续传（游标映射 + SSE 间隔外部化）

- **问题陈述**：短连接端点已用 `Last-Event-ID` 头 → `parseCursor`（RunEventController.java:192,274-292），但**长连接 `RunEventStreamer.stream()` 用的是 Java `cursor` 局部变量，并未在 SSE 层声明标准 `id`/消费 `Last-Event-ID`**（仅测试用）。且 SSE 轮询间隔/存活时长**硬编码**（`RunEventController.java:151` `new RunEventStreamer(500L, 30*60*1000L)`、`ApplicationConfiguration.java:324-325`），而 `application.yml:473` 的 `poll-interval-ms` 属消息队列消费——**SSE 无独立外部化配置**。
- **方案设计**：
  1. **游标→标准头映射**：让 `RunEventStreamer` 产出的每帧都带 `id: <sequenceNo>`（已通过 `emitter.send(SseEmitter.event().id(sequenceNo)…)` 实现，RunEventStreamer.java:94-97），并在长连接路径的 `onCompletion` 钩子里显式支持浏览器 `EventSource` 自动回传的 `Last-Event-ID`——即把自定义 `sequence_no` 映射到 SSE 标准 `Last-Event-ID` 头，使"重连用标准 header、续传用 sequence_no"统一。
  2. **SSE 间隔外部化**：把 `RunEventStreamer` 的 `pollIntervalMillis` / `maxLifetimeMillis` 改为从配置读取（替代硬编码 500/30min）：
     ```
     agent.api.streaming.poll-interval-ms: "${AGENT_SSE_POLL_INTERVAL_MS:500}"
     agent.api.streaming.max-lifetime-ms: "${AGENT_SSE_MAX_LIFETIME_MS:1800000}"
     ```
     并**重命名/澄清** `application.yml:473` 的 `poll-interval-ms` 为 `messaging.poll-interval-ms`（或加注释归属），消除"SSE 间隔"误读（诚实边界 G4）。
  3. 非法 `Last-Event-ID` 仍 400 拒绝（`parseCursor` 已做，RunEventController.java:288-291），不静默归零。
- **预期收益**：长/短连接续传语义统一到 SSE 标准；SSE 延迟可由运维调优而不改代码；消除配置名歧义。可度量：单测断言 `RunEventStreamer` 帧带 `id=sequenceNo`；配置改为 100ms 后实测首响 P95 下降。
- **实施成本与风险**：改动面小（构造器 + 配置 + 注释）。风险：误改消息队列 `poll-interval-ms` 影响消费延迟——故采用**独立命名**的 `agent.api.streaming.*` 而非复用。
- **优先级**：P2。
- **验收门禁**：① 单测断言 `RunEventStreamer.sseSender` 每帧 `id` == `sequenceNo`；② `LastEventIdResumeIT`：长连接中途断开（带 `Last-Event-ID`）重连，断言收到 `[cursor+1, N]` 且无重复；③ 配置 `poll-interval-ms=100` 生效（`application.yml:473` 仍=200 表示消息队列不受影响）；④ 非法 `Last-Event-ID` 断言 400。

### I-3：背压与慢消费者治理（缓冲上限/丢弃策略/nginx）

- **问题陈述**：当前无显式背压（G1）。`RunEventStreamer` 每轮 `findAfter(...,200)` 取 200 条后全量下发，慢消费者下这些帧在连接缓冲区堆积；`maxLifetimeMillis` 只是最后兜底，期间内存可能膨胀。
- **方案设计**（对齐 2.1 理论 3 的 Reactor 四象限）：
  1. **有界缓冲 + 溢出策略**：在 `FrameSender` 之外引入发送侧背压——若待发帧队列超过 `streaming.backpressure.buffer-cap`（默认 200，对应单次 `LIMIT`），采用 `DROP_OLDEST` 或 `LATEST` 策略（对 token 增量流，`LATEST`/丢弃最老更合理；对 run-event 关键帧不可丢，须 `ERROR` 或阻塞）。在 `RunEventStreamer.stream()` 的 `pollTask` 内加：
     ```java
     if (pendingQueue.size() > bufferCap) {
         metrics.dropSlowConsumer(runId);   // 计数
         // run-event 关键帧：抛/阻塞；chat delta：丢弃最老
     }
     ```
  2. **nginx 配置落地**：部署文档/Helm 模板显式：
     ```
     proxy_read_timeout 3600s;      # SSE 长连接不被 60s 切断
     proxy_buffering off;            # 等价 X-Accel-Buffering: no（双保险）
     chunked_transfer_encoding on;
     ```
     并补充 `X-Accel-Buffering: no` 已由后端下发（RunEventController.java:259），nginx 侧再锁死。
  3. **慢消费者指标**：新增 `sse_pending_queue_size`（Gauge）、`sse_backpressure_drops`（Counter），Grafana 面板 + 告警（队列持续 > 阈值即 P2）。
- **预期收益**：慢消费者不再无界堆积，连接内存可控；代理超时不再"假不推送"。可度量：混沌测试"前端消费速率=1 帧/秒、生产=100 帧/秒"下，断言服务端连接内存有界、不 OOM、`sse_backpressure_drops` 计数可见。
- **实施成本与风险**：改动面中等（发送侧队列 + nginx 模板）。风险：丢弃策略选错会丢关键帧——故 run-event 关键帧（run.start/tool/error/done）**不可丢**，仅 chat `delta` 可丢弃最老；策略按事件重要性分级。
- **优先级**：P2。
- **验收门禁**：① `BackpressureIT`：构造慢消费者，断言 `pending_queue_size` 不超过 `buffer-cap` 且 `sse_backpressure_drops>0`（delta 流）；② 断言 run-event 关键帧在背压下仍 100% 到达（不丢）；③ nginx 模板含 `proxy_read_timeout 3600s` + `proxy_buffering off`（`grep` 校验）；④ 慢消费者断开后连接被 `maxLifetimeMillis` 兜底关闭（无泄漏）。

### I-4：事件协议版本化（新增类型不破坏老客户端）

- **问题陈述**：`AgentChatEvent` 是 sealed 13+1 接口（AgentChatEvent.java:29-43），新增事件类型需改接口——若前端未同步升级，老客户端遇未知事件须 `default: return null` 忽略（已实现，但**无机制保证**新老客户端行为一致，且无协议版本协商）。
- **方案设计**：
  1. **协议版本头**：SSE 响应新增 `X-Agent-Stream-Version: 1.1` 头（`AgentChatController` / `RunEventController` 下发）；前端 `sse.ts` 读取并据版本决定是否消费 `context.checkpoint` 等新类型。
  2. **新增事件的"可降级"约束**：新增 `AgentChatEvent` permit 时，必须在 `decodeAgentFrame`（前端）保留 `default: ignore`，并在 `AgentChatEvent.java:19-28` 的协议注释里登记"新增类型向后兼容规则"。
  3. **契约测试门禁**：新增 `StreamProtocolVersionIT`，断言"v1.0 客户端（不识 `context.checkpoint`）收到 v1.1 流"时只忽略未知事件、不抛、不中断既有 13 事件的解析字节与 v1 逐字一致。
  4. **新增字段兼容**：`Done` 已示范"加字段收敛到全参构造 + 空串视作未提供"（AgentChatEvent.java:287-305，铁律 10），新事件须沿用同构。
- **预期收益**：协议演进可灰度、老客户端零中断。可度量：协议版本头存在且新老客户端 E2E 均通过。
- **实施成本与风险**：改动面小（响应头 + 前端读取 + IT）。风险：版本头遗漏导致老客户端误解析——故 IT 门禁强制。
- **优先级**：P2。
- **验收门禁**：① 断言 SSE 响应含 `X-Agent-Stream-Version`；② `StreamProtocolVersionIT`：v1.0 客户端收 v1.1 流，断言忽略 `context.checkpoint`、13 事件 data 字节与 v1 逐字一致、连接不中断；③ 新增 permit 后断言前端 `default: ignore` 分支存在（静态/契约测试）。

### I-5：多租户流式隔离的 SSRF/越权校验（租户链禁带 tenantId）

- **问题陈述**：铁律 12 要求租户链 `/api/knowledge/agent/chat/stream` **禁止在请求体/参数带 `tenantId`**（租户来自已验签令牌）。若误把客户端 `tenantId` 当查询依据，等于"客户端自证身份"——越权（维度 02 反模式 3）。同时 run-event 端点的"不存在/无权限同返 404"须持续锁死，防存在性探测。
- **方案设计**：
  1. **租户源断言**：`RequestAgentChatIdentityResolver` 已只从令牌推导（:27-30 文档）；新增静态守卫 `StreamTenantSourceGuard`：在 `AgentChatController` / `RunEventController` 入口断言**入参/请求体不含 `tenantId` 字段**（若含则 400 拒绝，fail-closed），从代码层杜绝"客户端 tenantId 当授权依据"。
  2. **身份域不匹配拒绝**：`SecurityConfiguration.java:102-110` 已让平台链前缀不匹配租户链；扩充集成测试 `PlatformSecurityE2ETest` 风格用例，断言"平台令牌穿租户链 403 / 租户令牌穿平台链 403"。
  3. **SSRF 防线（chat 上游）**：`ConsoleChatController` / `AgentChatController` 调用模型/rag 网关须走已验签内部通道，禁止把用户可控 URL 当上游（参照维度 08 的 RagUnavailableException + 连接/读超时 3s/20s + 响应体封顶 512KB + 禁重定向）。
  4. **续传游标越权**：`findAfter` 的 `tenant_id=?` 必须由服务端从令牌填（JdbcRunEventQueryRepository.java:68-76 双保险①），`Last-Event-ID` 只含 `sequence_no`，绝不携带租户——防"用他人 run_id + 自己游标"越权读。
- **预期收益**：流式通道与维度 02 同等强度的"默认拒绝 + 身份域分离"。可度量：渗透用例"带 `tenantId` 参数请求租户链"断言 400；"平台令牌穿租户链"断言 403。
- **实施成本与风险**：改动面小（守卫 + 测试）。风险：误拒合法请求——故仅拒绝"显式 tenantId 字段"，不拒正常业务字段。
- **优先级**：P1（安全红线）。
- **验收门禁**：① `StreamTenantSourceIT`：租户链请求体含 `tenantId` → 断言 400；② `PlatformSecurityE2ETest` 扩展：平台令牌穿租户链/租户令牌穿平台链 → 断言 403；③ `RunEventControllerTest` 既有"租户 B 订阅租户 A run"→ 404 用例保留并通过（RunEventControllerTest:101）；④ `findAfter` 单测断言 `tenant_id` 来自服务端令牌而非入参。

### I-6：前端 SSE 解析器的契约测试（防"解析器与后端协议漂移"）

- **问题陈述**：D-TERM 的根因是"后端协议语义 × 前端解析器"强耦合——一旦两端漂移（如后端改发事件帧、前端仍只认注释行），终止信号静默丢失、轮询永不停止。当前 `sse.ts` 与 `AgentChatEvent` 各自演进，无自动门禁锁定二者契约。
- **方案设计**：
  1. **双向契约测试**：新增 `sse-contract.test.ts`（前端）与 `SseContractIT`（后端），共享一份"golden 帧样本"：
     - 后端用 `AgentChatEvent` 全量序列化 → 产出帧文本 → 喂给前端 `parseStream`/`IncrementalSseParser` → 断言解析结果与预期结构一致（含 `terminal` 仅由 `: run-terminal` 触发）。
     - 前端构造"后端可能发出的帧"（含注释行终止、含未知事件 `context.checkpoint`、含多 `data:` 行合并）→ 喂给后端 `parseFrame` 等价逻辑（或经真实 HTTP）断言行为。
  2. **漂移门禁**：CI 中任一方改动触发对方契约测试；断言"后端 13+1 事件名集合 == 前端 `switch` 已知集合 ∪ {ignore}"；新增事件名若前端无 `case` 且无 `default: ignore` 即红。
  3. **终止信号铁律**：契约测试**必须**包含"后端发 `event: run-terminal`（无 id）→ 前端 `terminal=false`"的反例，以及"后端发 `: run-terminal` → `terminal=true`"的正例，防重蹈 P4-D12 M-1。
- **预期收益**：协议演进不再依赖人工同步，漂移在 CI 阻断。可度量：CI 门禁存在且"后端增事件/前端漏 case"即红。
- **实施成本与风险**：新增测试，无运行时代码改动。风险：golden 样本过时——故样本由 `AgentChatEvent` 实序列化生成（非手敲），随接口演进自动刷新。
- **优先级**：P1。
- **验收门禁**：① `sse-contract.test.ts` + `SseContractIT` 存在并绿色；② 注入"后端 `event: run-terminal` 无 id"→ 断言前端 `terminal=false`（反例红）；③ 注入"后端 `: run-terminal`"→ 断言 `terminal=true`；④ 后端新增 permit 而前端无 case/无 default → CI 红。

## 八、其他有价值的横向对比（避免维度内自闭）

### 8.1 与本项目其他维度的耦合与相互约束（≥2 条）

1. **↔ 维度 03 状态持久化与可恢复性**：本维度的 `run_event` 事实表 + `sequence_no` 游标**直接就是**维度 03 的承载体。改本维度（如把流来源从"事实表读取"改成"内存实时生成"）会直接摧毁维度 03 的"可重放/可审计"优势。**约束**：任何流式改动不得削弱 `run_event` 的不可变事实表语义（铁律 2/16）。
2. **↔ 维度 07 权限与护栏**：`RunEventController` 每次订阅都重校验 `EVENT_SUBSCRIBE` + 受众隔离（`RunEventController.java:197-231`），与维度 07 的"执行时重新授权"同源——订阅者权限在连接期间被撤销必须即时失效。**约束**：流式授权不得退化为"仅建连时校验一次"（铁律：SSE 断开重连必重过闸门）。
3. **↔ 维度 10 可观测性/审计**：流的"终止信号可靠性""续传正确性"本身是维度 10 的可观测对象。I-1/I-3 的 `sse_notify_*`/`sse_backpressure_*` 指标喂给维度 10 的 Grafana。
4. **↔ 维度 11 可靠性**：`RunEventStreamer` 的 `maxLifetimeMillis` 兜底强关、`onError/onTimeout` 清理（RunEventStreamer.java:151-166,220-229）防连接泄漏——连接泄漏即资源耗尽型故障。SSE 断开 ≠ Run 取消（D-CANCEL）也与维度 11 的"取消语义"一致。

### 8.2 与非 agent 领域成熟做法的对照

- **金融/行情实时推送（feed）**：证券交易所行情推送普遍用"持久订单簿/成交事实表 + 增量快照下发"，与本平台"事实表 + 游标续传"同构；其背压用"丢弃最老 tick、保留最新"（Reactor `DROP_OLDEST`/`LATEST`，2.1 理论 3）正是 I-3 对 chat `delta` 流的建议策略。
- **分布式日志/CDC（Debezium 等）**：将 DB 变更流作为事件源对外推送，与本平台"run_event 事实表驱动流"同源（2.1 理论 5 事件溯源）。可借鉴其"offset/游标管理 + 至少一次投递 + 消费侧幂等"范式强化 I-2。
- **Web 推送工程（SSE 代理部署）**：nginx `proxy_read_timeout`/`X-Accel-Buffering` 是 SSE 上线的标准 checklist（2.1 理论 8），本平台已落地后端头，但**部署侧 nginx 模板须同步锁死**（I-3 第 2 点）——这是"代码正确 ≠ 部署正确"的典型。
- **消息队列的"真推送 vs 轮询"权衡**：维度 01 的 I-5（LISTEN/NOTIFY 双通道）与本维度 I-1 同构——都是"事件总线唤醒 + 事实表兜底"的混合范式，可共用一套"通知仅加速、表兜底不退化"的工程纪律。

### 8.3 反向思考：若从头重做本维度，我们会怎么设计？（诚实取舍）

- **仍保留**：① 流 = 对 `run_event` 事实表的可重放读取（L3）；② 终止信号用 SSE 注释行控制帧；③ 固定 + 版本化事件集；④ 多租户 RLS + 身份域分离；⑤ `X-Accel-Buffering: no` + `maxLifetimeMillis` 兜底。这五点是相对竞品**唯一且正确**的差异化，重做不会丢。
- **会改变**：① 从第一天就把 SSE 间隔/存活**外部化配置**（而非硬编码 500ms，消除诚实边界 G4）；② 一开始就把 `RunEventStreamer`（长连接轮询器）与短连接端点**统一为一条路径**（消除 G3 双模型认知负担），或明确文档化"两条路径各自的适用边界"；③ 一开始就把 LISTEN/NOTIFY 混合推送（I-1）做进架构，而非事后补；④ 一开始就建"前端解析器 ↔ 后端协议"契约测试（I-6），而非靠 P4-D12 M-1 的事故倒逼；⑤ 背压策略（I-3）作为一等设计，而非缺失。
- **诚实取舍**：即便重做，仍会牺牲"双向语音/视频打断"（SSE 单向固有限制）与"极致低首响延迟"（事实表读取的固有代价）——这是本平台"生产 SaaS 要可追责、可续传、强隔离"定位决定的，不可妥协；双向实时交互若未来需要，应走**独立 WebSocket 通道**（如 ADK `run_live()` 式），而非改造 SSE。

## 九、对产品演进的启发

### 9.1 本维度支撑的产品能力（用户能感知什么）

- 用户能感知：**run 执行过程实时可见**（路由/RAG/工具/思考/正文增量）、**断网重连不丢进度**（游标续传）、**结束确切可知**（`: run-terminal`）、**自己的 run 不被他人看到**（租户隔离 + 受众隔离）。
- 用户不能感知（当前短板）：**首响延迟受 500ms 轮询制约**（I-1/I-2 补）、**语音/视频中途打断**（SSE 单向限制）、**慢网络下的背压兜底体验**（I-3 补）。

### 9.2 演进路线图（近/中/远三期，每期明确产出物与验收标准）

- **近期（P1–P2）**：交付 I-5（租户链禁带 tenantId 守卫 + 安全测试）、I-6（前后端 SSE 契约测试）。**验收**："租户链带 tenantId→400"+"跨链令牌→403"；"后端增事件/前端漏 case→CI 红"；终止信号正/反例锁定。
- **中期（P2）**：交付 I-2（Last-Event-ID 标准续传 + SSE 间隔外部化）、I-3（背压治理 + nginx 模板）、I-4（协议版本化）。**验收**："帧带 id=seqNo、长连接续传无重复"；"慢消费者队列有界、关键帧不丢、nginx 含超时/缓冲关闭"；"v1.0 客户端收 v1.1 流不中断"。
- **远期（P3/P4）**：交付 I-1（LISTEN/NOTIFY 混合推送，真零轮询加速）。**验收**："开启 NOTIFY P99<50ms；关闭/丢失时轮询兜底不退化、无重复事件"；若需双向实时交互，另行立项独立 WebSocket 通道（不在本维度 scope）。

### 9.3 风险清单（做这一步可能踩的坑，关联本项目已知铁律）

1. **I-1 NOTIFY 丢失导致永久卡死** → 必须保留 `run_event` 轮询兜底（NOTIFY 不持久、断连丢失，2.1 理论 7）；监听器重启先全量扫描再 LISTEN。
2. **I-2 误改消息队列 `poll-interval-ms`** → 采用独立命名 `agent.api.streaming.*`，不复用 `application.yml:473`（诚实边界 G4）。
3. **I-3 丢弃策略误伤关键帧** → run-event 关键帧（run.start/tool/error/done）**不可丢**，仅 chat `delta` 可 `DROP_OLDEST`/`LATEST`。
4. **I-4 版本头遗漏致老客户端误解析** → `StreamProtocolVersionIT` 门禁强制；新增 permit 须带 `default: ignore`。
5. **I-5 误拒合法请求** → 仅拒绝"显式 tenantId 字段"，不拒正常业务字段；游标（`Last-Event-ID`）只含 sequence_no，绝不携带租户（铁律 12）。
6. **I-6 golden 样本手敲过时** → 样本须由 `AgentChatEvent` 实序列化生成，随接口演进自动刷新。

### 9.4 一句话结论

**本平台在"流式输出"维度以"DB 事实表驱动（L3）+ SSE 注释行控制帧终止信号 + 固定 13+1 版本化事件集 + 多租户 RLS/身份域双隔离 + 载荷白名单 fail-closed"的组合，换来了竞品普遍缺失的续传幂等、可审计、强隔离、前后端契约稳定，代价是首响延迟受服务端轮询制约、无双向语音/视频打断、缺显式背压治理——前两者是 SSE 选型与"生产 SaaS 要可追责"定位的自觉取舍，后者可由 I-1/I-3 工程化补齐，且须以"NOTIFY 仅加速、表兜底不退化"与"关键帧不丢"为不可逾越的红线。**

- **差异 1（双流式路径 vs 单一 `RunEventStreamer.stream`）**：既有 `docs/能力维度实现方式梳理报告.md`（第 4 章）与 `docs/Agent平台竞品对比报告_2026-11-15.md`（维度 4）将 `RunEventStreamer.stream()`（长连接 SseEmitter 轮询，`RunEventStreamer.java:182` 读 `findAfter`、`:196-200` done 终帧）描述为 run-event 流的**实际流式机制**。本次逐行复核发现：**生产 `GET /api/runs/{runId}/events` 端点（`RunEventController.streamEvents`）走的是短连接 + `Last-Event-ID` 续传模型（返回 `ResponseEntity<String>`），并未调用 `RunEventStreamer.stream()`**；`RunEventStreamer.stream()` 当前**仅被 `SseStreamingTest` 单测覆盖**（`SseStreamingTest.java:125-287`）。即既有报告把"一个工程化封装类"当成了"生产端点的执行路径"，与代码现实不一致。本报告以实测代码为准，并在 4.1.3 / 6.2-G3 / 8.3 中如实呈现"双模型并存"的现状与改进方向。
