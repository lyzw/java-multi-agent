## 一、维度定义与评估坐标系

### 1.1 这个维度到底解决什么问题

LLM 的上下文窗口是一个**有限、昂贵、且随长度增长而质量衰减**的注意力预算（这一论断由 Anthropic 在 2025 年的 "Effective context engineering for AI agents" 中正式命名为 *attention budget* 与 *context rot*，见第二章）。一个 agent 在长程任务（多轮对话、多步工具链、跨会话持续辅导）中，必须把「系统提示 + 工具定义 + 检索结果 + 历史消息 + 当前输入」塞进这个窗口。上下文管理（Context Management）要解决的就是：**在每一步推理前，如何决定「哪些 token 进入窗口、以什么形式进入、旧的如何裁剪/压缩/归档、跨会话的记忆如何召回」**，使「进入窗口的高信号 token 集合」最大化任务成功率，同时控制成本与延迟。

它不解决「模型会不会推理」，而是解决「模型**看到的东西**是否足够且不被噪声淹没」。在 agent 系统里，它是连接「持久化状态（维度 3）」「工具调用（维度 5）」「RAG 检索（维度 8）」「成本（维度 9）」「可观测（维度 10）」的中枢——几乎所有其它维度的产物最终都要被装配进上下文窗口。

### 1.2 能力分层的四档模型

对这个维度，业界通用分层（L0–L3）如下：

| 档位 | 名称 | 含义 | 典型表现 |
|---|---|---|---|
| **L0 无管理** | 朴素拼接 | 把全部历史无脑塞进窗口，超窗即报错/截断 | 早期 demo、「上下文溢出导致模型只看到噪声」 |
| **L1 应用层手工裁剪** | 启发式截断 | 开发者用「轮次/字符数/估算 token」做简单截断或滑动窗口 | 本项目生产态 `ContextBudgetTrimmer`；多数自研 agent |
| **L2 框架层自动压缩** | 分级压缩 + 摘要 | 框架内建 W1 外置 / W2 裁剪 / W3 增量摘要，配置化水位线 | 本项目已建成但**默认关闭**的 `agent-context`/`CompactionPipeline`；Google ADK 自动 history compaction；LangGraph `trim_messages` |
| **L3 引擎/数据原生一等公民** | 记忆 + 缓存 + 压缩闭环 | 上下文压缩、长期记忆、KV/Prefix 缓存、质量评测形成可观测闭环，且默认开启 | Anthropic Claude Agent SDK（prompt caching 原生 + sub-agent 分工）；Agno（Memory 一等公民）；理想态 |

> **关键提醒（诚实校准）**：本项目在「代码资产」层面已达到 **L2**（有完整的分级压缩纯算法模块与记忆层），但在「生产默认态」层面目前是 **L1**——因为 `context.enabled=false`（application.yml:232），真实生产链路走的是 legacy `ContextBudgetTrimmer`。本报告第四章给出逐行证据。这与《能力维度实现方式梳理报告》第 6 章的呈现（把 L2 模块直接当作「实现方式」描述）存在口径差异，详见第四章「源码复核不一致声明」。

### 1.3 评估坐标系：5 个评价轴

| 轴 | 观测什么 | 怎么观测（本项目可采集的信号） |
|---|---|---|
| **A. 自动压缩能力** | 是否能在超阈值时自动压缩（外置/裁剪/摘要），而非只截断 | 是否存在 `CompactionPipeline` 此类管线；`context.enabled` 是否默认开启；压缩触发计数 |

## 二、理论体系（必须引用真实出处）

> 硬性要求：以下理论均给出真实出处。论文给标题/作者/年份/arXiv 号；框架能力给官方文档 URL。无法核实的已显式降级标注。

### 2.1 核心理论 / 概念框架（7 个）

**T1 · Context Engineering（上下文工程，2024–2025 业界共识）**
- 出处：Anthropic Applied AI 团队，《Effective context engineering for AI agents》，2025-09，<https://anthropic.com/engineering/effective-context-engineering-for-ai-agents>。
- 定义：Context Engineering 是「在 LLM 推理期间，策划并维护最优 token 集合（进入窗口的全部信息）的策略集合」，是 prompt engineering 的自然演进——prompt 写一次，context 每轮都要管。
- 该文提出两个核心概念：**Context Rot**（随着上下文 token 数上升，模型准确回忆信息的能力衰减）与 **Attention Budget**（注意力是有限预算，每个无关 token 都有成本）。并给出长程任务三技术：**compaction**（摘要历史后重初始化）、**structured note-taking / agentic memory**（把笔记持久化到窗口外、按需读回）、**sub-agent architectures**（子 agent 在干净上下文里干活、只回传 1k–2k token 蒸馏摘要）。

**T2 · Lost in the Middle（中间丢失，Liu et al. 2023）**
- 出处：Nelson F. Liu, Kevin Lin, John Hewitt, Ashwin Paranjape, Michele Bevilacqua, Fabio Petroni, Percy Liang，《Lost in the Middle: How Language Models Use Long Contexts》，Stanford / TACL 2023，arXiv:2307.03172，<https://arxiv.org/abs/2307.03172>。
- 核心结论：模型在「相关信息位于上下文**开头或结尾**时表现最好，**位于中间**时显著退化」，即便标注为 long-context 的模型也是如此。这对上下文管理意味着：**首轮锚（first user turn / system）与最近轮次必须保留在窗口两端，早期中间轮次可安全裁剪**——本项目 `ContextBudgetTrimmer` 与 `CompactionPipeline` 的「首条原始输入永不裁 + 保留最近轮」设计正是对此的响应。

**T3 · Context Rot / 长上下文真实有效长度（RULER）**
- 出处：Cheng-Ping Hsieh, Simeng Sun et al. (NVIDIA)，《RULER: What's the Real Context Size of Your Long-Context Language Models?》，2024，arXiv:2404.06654，<https://arxiv.org/abs/2404.06654>。
- 核心结论：用 needle-in-a-haystack 之外的多类任务（多跳追踪、聚合、QA）评测，**几乎所有标称 32K+ 的模型在真实长任务上都远低于标称长度的有效表现**；上下文越长、任务越复杂，退化越大。另有 "Goldfish Memory" 类工作（如 arXiv:2411.03688，未能 100% 确认作者与期刊，本报告标注为「业界已知现象，单篇未逐一核实」）描述模型对长上下文中早期信息的「金鱼记忆」式遗忘。
- 对实践的约束：不能因为「模型说支持 200K」就放任上下文膨胀；**有效窗口 << 标称窗口**，预算/压缩必须按有效窗口设。

**T4 · KV Cache / Prefix Caching（对成本与延迟的影响）**
- 出处：Anthropic Prompt Caching 官方文档，<https://platform.claude.com/docs/en/build-with-claude/prompt-caching>（同 docs.anthropic.com/en/docs/build-with-claude/prompt-caching）；vLLM Automatic Prefix Caching，<https://docs.vllm.ai/en/latest/usage/compatibility.html>。
- 机制：模型在处理 prompt 时会把前缀的 KV 状态缓存；当后续请求**字节精确**共享同一前缀时，直接复用缓存，prefill 成本按 0.1× 计费、延迟大幅下降。约束：缓存**按模型固定、要求前缀字节精确、有 TTL（通常 5 分钟）**；system prompt / 工具定义这类「稳定前缀」应放在最前，动态内容追加在末尾；compaction 会重写对话前缀、正是切换模型的时机。
- 对上下文管理的意义：**稳定前缀 + 动态历史后置**是降低长程多轮成本的关键工程手段（本项目 `RunExecutionLoop:1241` 注释已点出「systemPrompt 用稳定前缀」）。

**T5 · Memory 分类（short/working vs long-term；结构化 vs 非结构化；向量 vs 摘要）**
- 出处：Anthropic "Building Effective Agents"，<https://www.anthropic.com/research/building-effective-agents>；Generative Agents（Park et al. 2023，Stanford，arXiv:2304.03442）提出「记忆流 / 检索 / 反思」三段式记忆架构，是 agent 记忆研究的奠基性工作。
- 分类框架：
  - **Short-term / working memory**：单 Run 内的消息历史（本项目 `run_message`）。
  - **Long-term memory**：跨 Run 持久化的、可召回的语义（本项目 `student_memory`，但为领域聚合而非通用）。
  - **结构化记忆 vs 非结构化**：`student_memory` 是结构化（studentId+knowledgePoint+strength）；笔记/摘要式是非结构化。
  - **向量召回 vs 摘要**：向量召回（本项目 `student_memory` 预留 `agent.memory.vector.enabled=false`，DDL:3125）vs 强度阈值筛选（当前默认路径）。

**T6 · Prompt Compression / LLMLingua / RECOMP（压缩方法）**
- 出处：Huiqiang Jiang et al. (Microsoft)，《LLMLingua: Compressing Prompts for Accelerated Inference of Large Language Models》，EMNLP 2023，arXiv:2310.05736，<https://arxiv.org/abs/2310.05736>；同作者《LongLLMLingua》arXiv:2310.06839；《RECOMP: Improving Retrieval-Augmented LMs with Compression and Selective Augmentation》，Xu et al. 2023，arXiv:2311.07919，<https://arxiv.org/abs/2311.07919>。
- 定义：在 token 进入模型前，用一个小模型/规则**有选择地删除低信息量 token**（LLMLingua，可达 20× 压缩、质量损失小）或**用检索到的证据做抽象压缩再注入**（RECOMP）。与「截断」的本质区别：压缩是**全局选择性保留语义骨架**，截断是** contiguous 丢弃**，常丢后期关键信息。

**T7 · Sliding Window / Truncation（基础策略与局限）**
- 出处：属工程常识，无单一权威论文；作为 baseline 对照 T6。经典做法：保留最近 K 轮、丢最早轮（sliding window）。局限：① 早期关键信息被永久丢弃（除非有记忆层兜底）；② 若关键事实恰在早期，任务直接失败；③ 与 lost-in-the-middle 叠加，丢中间信息风险高。本项目 `ContextBudgetTrimmer` 即此策略（轮次截断）。

### 2.2 理论给出的「设计张力」（trade-off）清单

| 张力 | A 方案 | B 方案 | 本项目取舍 |
|---|---|---|---|
| 压缩保真 vs 成本 | W3 增量摘要（高质量，但有 1 次 LLM 调用成本 + 延迟） | W1/W2 纯算法外置/裁剪（零 LLM，但可能丢细粒度上下文） | 默认 `TRIM_ONLY` 仅 W1/W2；`TIERED` 才上 W3（CompactionPipeline:127） |
| 估算精度 vs 实现复杂度 | 真实 tokenizer（tiktoken/cl100k，精确但需随模型变、增依赖） | 启发式（CJK 1/非CJK 3，偏保守，零依赖） | **两个路径都是启发式**，无真实 tokenizer（见第四章） |
| 记忆召回 vs 噪声/隐私 | 召回更多长期记忆（提升连贯性） | 少召回（避免稀释注意力 + 隐私面） | `MemoryPolicy` 上限 20 条 / 4000 token / 强度门槛（MemoryPolicy.java:86-101） |
| 缓存命中 vs 动态性 | 稳定前缀固定（高缓存命中、低成本） | 每轮重排上下文（灵活但每次重算前缀） | system/tool 稳定前缀置前（RunExecutionLoop:1241） |
| 压缩失败 | 回落（fallback）保任务 | 硬失败（fail-closed） | **摘要失败回落 W2 + 稳定原因码，绝不伪造**（CompactionPipeline:139-143） |

### 2.3 业界公认的反模式（anti-pattern）清单及判别方式

1. **「加更多上下文 = 更好」**：违反 context rot（T1/T3）。判别：有效窗口 << 标称窗口，长任务质量随轮次单调下降。
2. **把模型原始输出直接当可信记忆注入**：记忆若来自模型历史输出且不过围栏/校验，等于「历史幻觉被固化成事实」。判别：记忆来源是否经 `PromptGuard.sanitize` 与围栏（本项目 MemoryRecallService:118 有此约束）。
3. **裁剪不留痕**：丢历史却不告诉模型「前面调过哪些工具」→ 模型重复调用 → 重复副作用（Sev-0）。判别：裁剪说明是否进 system 提示并列出已调用工具（ContextBudgetTrimmer:287-311）。
4. **W1 外置净增 token**：把短 tool 结果替换为更长的归档行 = 触发了却变增 token。判别：外置前是否用 counter 比较原文/归档行长度（CompactionPipeline:219-224）。
5. **压缩失败塞编造摘要**：看似「保任务」，实则注入幻觉上下文。判别：是否有 `fallback=true` + 稳定原因码而非编造文本（CompactionPipeline:139）。
6. **记忆预算扣到 0**：记忆占满预算 → `trim(0)` 直接抛异常 → 每次 Run 首步崩。判别：是否有 `MIN_TRIM_BUDGET` 夹紧（MemoryPolicy.java:48）。
7. **静态源码守卫 ≠ 运行时成立**：编译期「有压缩类」不代表运行时触发。判别：是否真实交互驱动 + 撤点反证（铁律 17；本报告第四章强调 `context.enabled=false` 时类存在但不生效）。

### 2.4 补充理论：压缩策略的工程谱系、KV 机制与记忆架构

**2.4.1 压缩策略的连续谱（从截断到语义压缩）**
把业界做法按「信息保真度」从低到高排成谱，便于定位本项目坐标：
1. 不压缩（L0）：全量拼接，超窗即错。
2. 滑动窗口 / 轮次截断（L1）：保留最近 K 轮、丢最早轮——本项目 `ContextBudgetTrimmer` 在此档。
3. 可逆外置（W1）：老工具结果替换为「归档引用 + 一行结论」，保留配对——本项目 `CompactionPipeline` W1 已建。
4. 语义摘要压缩（W3 / LLMLingua）：用小模型选择性删低信息 token，或 LLM 摘要历史——本项目 W3 已建未启。
5. 结构化笔记 / agentic memory（note-taking）：把进度/结论持久化到窗口外、按需读回——本项目 `student_memory` 近似此档（领域特定）。
6. sub-agent 蒸馏：子 agent 在干净上下文干活、只回传 1k–2k token 蒸馏摘要——本项目靠 `WorkerChildAgentRunner`（维度 1）部分覆盖，但非为压缩设计。

**2.4.2 KV Cache / Prefix Caching 机制深述（对成本延迟的工程含义）**
Transformer 每处理一个 token 都会产出该 token 的 Key/Value 向量并缓存（KV cache）。当后续请求**前缀字节精确相同**时，可直接复用该前缀的 KV，跳过昂贵的 prefill。关键工程事实（来自 Anthropic Prompt Caching 文档 T4 与 vLLM Automatic Prefix Caching）：
- **缓存按模型固定**：换模型 = 缓存全失效。
- **字节精确要求**：前缀中任一字节变化，其后的全部 KV 都要重算——因此 system prompt / 工具定义这类稳定内容必须放在最前，动态内容（当前输入、时间戳、RunId）追加在末尾。
- **TTL**：通常 5 分钟（可付费延长到 1 小时）；若 agent 阻塞在长工具调用超过 TTL，下一轮需重写缓存，按 1.25× 写价计费。
- **成本结构**：cache write ≈ 1.25× 基础输入价（5 分钟 TTL），cache read ≈ 0.1× 基础输入价。对多轮长程 agent，稳定前缀命中可把重复 prefill 成本压到约 1/10。
- 对本项目的启示：本项目 `RunExecutionLoop:1241` 已点出「systemPrompt 用稳定前缀」，但**尚未在请求构造处声明 `cache_control` 断点、也无命中比例可观测**（见 7.4/7.5）。

**2.4.3 Anthropic 三技术取舍再述（compaction / note-taking / sub-agent）**
Anthropic "Effective context engineering"（T1）明确三种长程技术各有适用面：
- **Compaction**（摘要历史后重初始化）：适合「需要大量来回对话」的任务——本项目教育辅导多轮对话正属此类。
- **Structured note-taking / agentic memory**：适合「有清晰里程碑的迭代开发」——本项目 `student_memory` 本质是 note-taking 的领域变体（把「学生总错在哪」记成外部笔记、下次读回）。
- **Sub-agent architectures**：适合「可并行的复杂研究/分析」——子 agent 返回 1k–2k token 蒸馏摘要给协调者。
本项目目前在这三类的「资产」分别处于：compaction（L2 已建未启）、note-taking（领域版已启）、sub-agent（编排层部分覆盖）。

**2.4.4 Generative Agents 记忆架构（记忆研究的奠基范式）**
出处：Joon Sung Park et al. (Stanford/Microsoft)，《Generative Agents: Interactive Simulacra of Human Behavior》，UIST 2023，arXiv:2304.03442，<https://arxiv.org/abs/2304.03442>。其记忆由三层构成：
- **Memory Stream**：原始观察的时序日志（对应本项目 `run_message` + `weakness_record` 事件日志）。
- **Retrieval**：按「近因（recency）+ 重要性（importance）+ 相关性（relevance）」三者加权召回（对应本项目 `MemoryEntry.liveStrength` 的衰减 ≈ 近因/重要性，但**缺相关性语义打分**）。
- **Reflection**：把多次观察提炼成高层洞察（如「这个学生不擅长代数」）——**本项目缺这一层**：`student_memory` 只聚合「薄弱点+强度」，未把多次薄弱点反思成「学生画像」摘要。
启示：7.3 的通用长期记忆层可顺带补「reflection」型 `FACT` 记忆（周期性把会话摘要提炼为高层事实），缩小与 Generative Agents 的差距。

## 三、竞品实现全景（每个主流方案一段；≥4 个，官方 URL）

### 3.1 OpenAI Agents SDK
- **官方定位与机制**：极简原语（Agent/Runner/Handoffs/Guardrails/Sessions/Tracing），**无原生自动上下文压缩**；上下文即开发者自己维护的 `messages` 列表，超窗由开发者负责截断或摘要。成本优化靠 **prompt caching**（稳定前缀自动缓存）。
- URL：<https://openai.github.io/openai-agents-python/>
- **优点**：简单、可预测；prompt caching 原生降低重复 prefill 成本。
- **局限/代价**：自动压缩完全交给开发者；长程任务的 context rot 由开发者自行治理。
- **适用场景**：短中程、开发者愿意自己管 messages 的应用。

### 3.2 Anthropic Claude Agent SDK
- **官方定位与机制**：把 Claude Code 当库用，继承其工具/权限/sessions/hooks/MCP。上下文管理靠 **prompt caching 原生**（见 T4）+ **sub-agent 分工**（每个 sub-agent 在干净上下文干活、只回传蒸馏摘要，对应 T1 的 sub-agent 架构）。`/compact` 是会话级摘要重初始化。
- URL：<https://docs.anthropic.com/en/api/agent-sdk>；prompt caching <https://platform.claude.com/docs/en/build-with-claude/prompt-caching>
- **优点**：prompt caching 降低长多轮成本；sub-agent 天然隔离上下文；`/compact` 提供会话级压缩。
- **局限/代价**：压缩/摘要由 Claude Code 运行时内部处理，平台侧可控粒度有限；依赖 Anthropic 生态。
- **适用场景**：长程 coding/研究 agent、需要跨会话连贯性的任务。

### 3.3 LangGraph
- **官方定位与机制**：低层图式编排（State/Node/Edge），**无内建自动压缩**；消息裁剪靠 LangChain `trim_messages`（按 token/轮次保留最近、可选保留系统消息），消息 reducer（`add_messages`）支持按 ID 更新/追加。记忆层：`MemoryStore`（跨线程长期）+ `Checkpointer`（线程级短期，支持 PostgresSaver，time-travel、断点续跑）。

## 四、我们的实现（源码级解剖）

> 本章所有结论均经源码复核。核心结论先行：**本项目存在两套上下文路径——(A) 生产默认运行的 legacy 路径（L1），(B) 已建成但默认关闭的富管线路径（L2）。两者并存，且都没有真实 tokenizer。**

### 4.1 架构与数据流

```
[RunExecutionLoop.java]
   │ 每轮：读取 run_message 历史 + 工具结果
   ▼
[MemoryRecallService.recall] ──► student_memory 表（跨 Run 长期记忆块，注入 system 提示）
   ▼
[ContextBudgetTrimmer.trim]  ◄── 生产默认路径（L1）：粗估 token + 整轮截断
   │   生成 notice（裁剪说明 + 已调用工具列表）→ 拼进 legacySystemPrompt
   ▼
[RequestAssemblyPort.assemble]  ◄── M7-b 接线入口
   │   if (global.enabled()==false) → 直接 passthrough 返回 legacy 同一引用（零改动）
   │   if (enabled) → ContextAssembler → CompactionPipeline(W1/W2/W3) → 重渲染
   ▼
构造 ModelRequest → 调 LLM
```

- **生产实际跑的是哪条？** `RunExecutionLoop.java:777-778` 无条件调用 `ContextBudgetTrimmer.trim(messages, trimBudget)` 构造 **legacy 基线请求**；随后 `requestAssemblyPort.assemble(...)`（注入点 `RunExecutionLoop.java:274`）。而 `ContextRequestAssemblyAdapter.java:86` 在 `!global.enabled()` 时**第一行就返回 passthrough（同一引用）**。`global.enabled()` 来自 `application.yml:232` `context.enabled: "${AGENT_CONTEXT_ENABLED:false}"`——**默认 false**。
- 结论：**默认生产态 = legacy `ContextBudgetTrimmer`（L1）。`CompactionPipeline` 富管线（L2）因 `context.enabled=false` 处于影子期（S1），由里程碑守卫（M5/M6/M7/S1/G2/M9 guard 测试）控制启用节奏，当前不进入生产字节。**

### 4.2 关键设计决策逐条剖析

**决策 D1：生产用 `ContextBudgetTrimmer` 做「按 token 预算的整轮截断」**
- 决策：`RunExecutionLoop.java:777` 始终 trim。
- 为什么：根循环消息序列随轮次线性增长，`maxSteps` 可达 20、单条工具输出封顶 8000 字符，多轮会顶爆窗口。
- 代价：① **只截断不摘要**（早期决策/事实被永久丢失，除非记忆层兜）；② token 是**粗估**（CJK 1 字=1 token、非 CJK 3 字符=1 token，ContextBudgetTrimmer.java:23-31, :62, :70）；③ 保留「最近轮」、丢「最早轮」——若关键事实在早期，直接失败（不抗 lost-in-the-middle 的中间段，只保两端）。
- 证据：`ContextBudgetTrimmer.java:50` 类注释、`:127-163` trim 主逻辑、`:269-285` splitRounds。

**决策 D2：`context.enabled=false` 的影子期设计（S1）**
- 决策：富管线先建后开，默认关闭（application.yml:231-232 注释「影子期默认关闭……不得改变任何模型请求字节」）。
- 为什么：避免在未充分验证压缩质量前就把线上请求字节改掉；「关闭态与没有压缩功能逐位一致」是硬约束（ContextAssembler.java:27-33 关闭等价桥 [D11]）。
- 代价：**L2 能力（自动压缩/摘要）当前不生效**，对外呈现为 L1；易被误读为「已有自动压缩」（见第四章不一致声明）。
- 证据：`application.yml:223-232`；`ContextAssembler.java:100-103`；`ContextRequestAssemblyAdapter.java:85-88`。

**决策 D3：压缩是「确定性纯函数、零 LLM/零 IO」**
- 决策：`CompactionPipeline` W1/W2 零 LLM；W3 摘要经注入 `Summarizer` 由外部 `ModelGateway` 产出，本类绝不自己调模型（CompactionPipeline.java:22-25, :99-144）。
- 为什么：与模型调用解耦避免 ReDoS/循环依赖；相同输入恒等输出，可重放可测。
- 代价：W3 依赖外部 summarizer；若未接入则回落 W2（`fallback=true` + `SUMMARIZER_FAILED` 原因码，CompactionPipeline:139-143）——**当前 `context.enabled=false`，W3 根本不触发**。
- 证据：CompactionPipeline.java:37, :125-144；ContextAssembler.java:41-45。

**决策 D4：首轮锚（first user turn / USER）永不丢，工具配对保护**
- 决策：W1 只替换 TOOL 的 content、不动 assistant 的 tool_calls 配对（CompactionPipeline.java:27-28, :212-218）；W2 裁剪只丢「可丢轮」(`droppable`)，ANCHOR 保留（RoundSplitter）。
- 为什么：① 首轮用户意图是任务的「宪法」，丢了模型不知道在干嘛；② 孤立 TOOL 消息会让部分供应商报错（工具结果无对应 tool_call），且是无意义噪声（ContextBudgetTrimmer.java:37-48）。
- 代价：首轮锚固定占用窗口，极端长任务下可压缩空间受限。
- 证据：CompactionPipeline.java:204, :266；ContextBudgetTrimmer.java:139。

**决策 D5：裁剪必须留痕（注入 system 提示，列出已调用工具）**
- 决策：trim 生成 notice，告知「前 N 轮已移除 + 期间调用过哪些工具」，走 system 提示而非混入消息序列（ContextBudgetTrimmer.java:42-49, :287-311）。
- 为什么：不告诉模型「前面调过哪些工具」→ 模型以为没调过 → 重复调用 → 重复副作用（Sev-0）。
- 代价：notice 本身占真实窗口（受 `MIN_TRIM_BUDGET` 与工具名限长 5 个约束，MemoryPolicy.java:48, ContextBudgetTrimmer.java:296-307）。
- 证据：ContextBudgetTrimmer.java:287-311；RunExecutionLoop.java:783-787。

**决策 D6：跨 Run 长期记忆 = 领域聚合 `student_memory`，非通用对话记忆**
- 决策：`MemoryRecallService` 从 `student_memory` 召回「学生薄弱知识点」块注入 system 提示；`MemoryConsolidator` 在 SUCCEEDED 后把 `weakness_record` 聚合进 `student_memory`（RunExecutionLoop.java:1003-1004）。
- 为什么：教育场景需要「记住这个学生总在哪儿错」；用聚合态（一学生一知识点一条）而非事件日志（每次 Run 一条），避免每次读都 GROUP BY（MemoryEntry.java:13-24）。
- 代价：① **是领域特定的薄弱点记忆，不是通用多轮会话记忆**——与 RAG（维 8）边界清晰但覆盖面窄；② 强度随时间衰减（`liveStrength` 读时计算，MemoryEntry.java:107-109）；③ 召回失败降级为空（绝不抛异常，MemoryRecallService.java:23-33, :84-89）。
- 证据：student_memory 表 DDL:3107-3155；MemoryEntry.java；MemoryPolicy.java。

**决策 D7：记忆占用从裁剪预算中扣减，并夹紧下限**
- 决策：`RunExecutionLoop.computeTrimBudget(memoryTokens)`（:1932-1946）用 `contextTokenBudget - memoryTokens`，若剩余 `< MIN_TRIM_BUDGET(2048)` 则夹紧并返回告警。
- 为什么：防止记忆占满预算 → `trim(0)` 抛异常 → 每次 Run 首步崩（MemoryPolicy.java:39-48）。
- 代价：记忆大时当次对话推理空间被挤压（设计上有意取舍，MemoryPolicy.java:98-101）。
- 证据：RunExecutionLoop.java:701-707, :1932-1946；MemoryPolicy.java:48。

### 4.4 我们独有的设计（差异化设计）

1. **「关闭等价桥 [D11]」构造级保证**：`context.enabled=false` 时 `ContextAssembler` 返回 legacy **同一引用**，逐位一致，杜绝「关了功能却悄悄改了字节」（ContextAssembler.java:100-103）。这是多数框架不具备的严谨度。
2. **裁剪留痕 + 工具名单防重复调用**：把「已调用工具」显式告知模型，规避重复副作用 Sev-0（ContextBudgetTrimmer.java:287-311）。这是从真实事故中长出的安全设计。
3. **记忆「聚合态 vs 事件态」拆分 + 强度衰减读时算**：`student_memory` 与 `weakness_record` 职责分离、衰减在读取路径而非夜批（MemoryEntry.java:13-24, :107-109）。领域适配但有普适价值。
4. **压缩失败「回落不伪造」**：W3 摘要失败标记 `fallback=true` + 稳定原因码，绝不塞编造摘要（CompactionPipeline.java:139-143）——诚实降级优于幻觉注入。
5. **W1 外置「净省才做」**：逐条用 counter 比较原文/归档行，避免外置反而增 token（CompactionPipeline.java:219-224）。

### 4.6 端到端示例：一次 8 轮辅导对话的「裁剪前后」与「若启用压缩会怎样」

> 目的：把上文的抽象机制落到具体数字，便于读者直观判断「当前生产态」与「启用富管线后」的差异。以下数字为基于 `ContextBudgetTrimmer` 启发式口径（CJK 1/非 CJK 3）的**示意估算**，非真实运行采样。

**场景**：学生做一道多步数学题，连续 8 轮（首轮=题目，第 2~8 轮为「ASSISTANT 意图 + TOOL 结果」交替）。设：
- 首轮题目（ANCHOR）：~600 token（中文为主）。
- 每轮 ASSISTANT 意图：~300 token；每轮 TOOL 结果：短则 ~40 token（如「正确」），长则 ~2000 token（如完整解题步骤）。
- 上下文预算 `context-token-budget = 16000`（yml:208），记忆块占用 ~500 token（已从预算扣减，见 RunExecutionLoop:701）。

**A. 当前生产态（`context.enabled=false`，legacy `ContextBudgetTrimmer`）**
- 第 8 轮时累计消息 ≈ 600 + 7×(300+平摊 800) ≈ **6500 token**，未超 16000 → **不触发裁剪**，全量发送（含第 2 轮那个 2000 token 的早期解题步骤）。
- 若任务延长到第 18 轮，累计 ≈ 600 + 17×1100 ≈ **19300 token > 16000** → 触发 `trim`：从最早轮丢起，直到保留最近若干轮落入预算。结果：**第 2~5 轮的对话（含早期关键约束）被整轮删除**，仅在 system 提示追加一条 notice：「（上下文预算裁剪：前 4 轮工具交互已被移除…期间已调用过：GetStudentProfile、RecordWeakness。请勿重复调用上述工具。移除是系统侧行为，任务本身未变。）」。
- **隐患（lost-in-the-middle 叠加）**：若第 3 轮曾确立「本题用二次函数」这一关键约束、且第 18 轮才被问到，裁剪后模型**看不到该约束**，可能用错方法——而 notice 只说「调过哪些工具」，未保留约束本身。这是当前 L1 生产的真实盲区。

**B. 若启用富管线（`context.enabled=true` + `TIERED`，当前未启）**
- **W1 可逆外置**：第 2~5 轮那些 2000 token 的 TOOL 结果，被替换为「`[tool:xxx] 结果已归档（refId=run_message:seq=N），结论：…（一行）`」。单条若原文仅 40 token 则**不做外置**（净省才做，CompactionPipeline:219）。
- **W2 整轮裁剪**：若仍超窗，丢最早可丢轮（ANCHOR 与最近轮保留）。
- **W3 增量摘要**：若触发 `tier=W3`，调用 `Summarizer` 把「第 2~5 轮增量」压成一段摘要（如「学生在二次函数符号判断上连续错 2 次，已用配方法求解」），注入上下文；若 summarizer 失败 → **回落 W2 + `fallback=true` + `SUMMARIZER_FAILED`，绝不编造**。
- **关键差异**：W3 把「早期约束/决策」提炼成摘要保留，而非像 A 那样整轮物理删除 → 显著缓解 lost-in-the-middle。这正是 7.1 要落地的收益，且须由 7.6 反向验证证明「B 的成功率 ≥ A−2%」。

**C. 长期记忆视角（`student_memory`，当前已启用）**
- 该学生若在第 2、5、8 轮都错在「二次函数符号」，SUCCEEDED 后 `MemoryConsolidator` 把 `weakness_record` 聚合进 `student_memory`（一学生一知识点一条，`evidence_count` 累加、强度按 `MemoryStrength` 衰减）。下次新 Run 开始时，`MemoryRecallService.recall` 召回该薄弱点块（带围栏 + `PromptGuard.sanitize`）注入 system 提示——**等价于 Anthropic 的 note-taking**：模型「记得」这个学生总错在哪，无需重读历史。注意：这是**跨 Run** 的，与本次对话内的 A/B 压缩正交。

### 5.2 优势详解（为什么领先，讲清机制）

1. **裁剪留痕防重复副作用**：`ContextBudgetTrimmer` 把「已丢弃轮次 + 调用过的工具名单」写进 system 提示（:287-311），模型因此不会误以为工具没调过而重复调用。这是从「重复写库/扣款 Sev-0」事故中长出的设计，多数框架不内置此安全网。
2. **压缩失败「回落不伪造」**：`CompactionPipeline:139-143` 在 W3 摘要失败时不塞编造摘要，而是回落 W2 + `fallback=true` + 稳定原因码（SUMMARIZER_FAILED/HARD_TRIM）。这优于「为保任务注入幻觉上下文」，与本项目「fail-closed/诚实优先」铁律一致。
3. **关闭态逐位等价（[D11]）**：`context.enabled=false` 时返回 legacy **同一引用**，零预算/零管线/零字节变更（ContextAssembler.java:100-103）。这保证「功能未启用 = 与没有该功能完全一致」，避免「关了压缩却悄悄改了请求字节」这类静默失真——是生产灰度严谨性的体现。
4. **记忆「聚合态/事件态」分离 + 读时衰减**：`student_memory` 一学生一知识点一条，与每次 Run 的 `weakness_record` 事件日志分离；强度衰减在**读取路径**实时计算（MemoryEntry.java:107-109），而非夜批刷新，避免白天读到过期强度。
5. **记忆预算夹紧防全局崩**：`computeTrimBudget` 把记忆占用从 trim 预算扣减并夹紧到 `MIN_TRIM_BUDGET`（MemoryPolicy.java:48），杜绝「记忆占满→trim(0) 抛异常→每次 Run 首步崩」。

### 5.3 劣势与盲区详解（根因分析）

1. **自动压缩未启用（L1 生产）**：根因是 `context.enabled=false` 的影子期设计（S1，yml:232）。这是**有意的设计取舍**（先建后开、避免未验证就改线上字节），不是能力缺失——但对外呈现为「缺自动压缩」。代价：长程任务目前只能靠「整轮截断」，早期关键事实一旦被裁即永久丢失（不抗 lost-in-the-middle 中间段）。
2. **无真实 tokenizer（全粗估）**：两条路径都用 CJK 1 字=1 token、非 CJK 3 字符=1 token 的启发式（ContextBudgetTrimmer.java:23-31；HeuristicTokenCounter.java:23-26）。根因是「本仓没有供应商 tokenizer 可用（D-002）」（ContextBudgetTrimmer.java:30），且要随模型变。代价：① 估算误差 30–50%（HeuristicTokenCounter.java:14 自承）；② 偏保守侧（早裁）保住不超窗，但可能**过早裁掉有用上下文**；③ 无法精确对齐供应商计费与窗口硬限。
3. **长期记忆是领域特定的，非通用**：`student_memory` 只记「学生薄弱知识点」（knowledgePoint/errorType），不是通用多轮会话/事实记忆。根因是项目定位（教育辅导）。代价：通用「用户偏好/会话摘要/事实记忆」缺失，跨场景复用差；且与 RAG（维 8）职责边界虽清晰，但覆盖面窄。
4. **Prefix caching 未真正利用**：虽有「稳定前缀置前」的意识（RunExecutionLoop:1241），但**未使用 `cache_control`/prefix caching 命中比例可观测**（维度 10 亦缺）。根因：平台抽象层尚未在请求构造处声明缓存断点。代价：多轮重复 prefill 成本未优化，长程任务成本高。
5. **压缩质量无反向验证闭环**：维度 3 的反向方法论（撤掉修复点是否回退）尚未用于「压缩」。根因：压缩未启用 + 缺长程评测 harness。代价：启用压缩时无法量化「质量是否不降、成本降多少」。

### 5.4 关键分歧点（最本质的架构分歧）

1. **「先建后开 + 关闭逐位等价」vs「框架默认即开」**：本项目选择 L2 资产先建成、默认关闭、灰度启用（S1 影子期）；ADK/Agno 默认即开自动压缩/记忆。分歧后果：本项目换来了「零失真灰度」，代价是「当下不享受自动压缩红利」。
2. **「裁剪留痕 + 工具名单」vs「静默丢弃」**：本项目把安全（防重复副作用）内建进裁剪；多数框架把「是否告诉模型」留给开发者。分歧后果：本项目更安全，代价是 system 提示被 notice 占用少量窗口。
3. **「领域聚合记忆」vs「通用记忆/Memory 一等公民」**：本项目记忆=教育薄弱点；Agno/ADK 记忆=通用。分歧后果：本项目记忆与场景强绑、召回精准，代价是通用性弱、与 RAG 边界需额外厘清。

### 5.5 压缩与 lost-in-the-middle / context rot 的定量关系（为什么必须做 7.1）

把 2.1 的两条理论（T2 lost-in-the-middle、T3 context rot）与本项目的 `context-token-budget=16000`（yml:208）做定量勾连，说明「不做自动压缩」的代价可被估算：

- **有效窗口假设**：依 RULER（T3）结论，标称 32K+ 的模型在真实长任务上的「有效窗口」通常只有标称的 1/2~1/4。即使接 200K 模型，对「聚合/多跳」类任务有效窗口可能仅 ~32K~64K；而本项目预算仅 16K，落在「有效」区间，但**容错余量小**。
- **lost-in-the-middle 风险面**：legacy `ContextBudgetTrimmer` 保留「首轮锚 + 最近轮」、丢「最早中间轮」。若关键约束恰落在被裁的中间轮（4.6 示例第 3 轮），且任务在更晚轮次才用到，则命中 T2 的「中间丢失」最坏情况——而模型对中间段本来就最弱（T2），双重叠加。
- **context rot 风险面**：随轮次增长，即便不裁，有效信号密度下降（T1/T3）。W3 摘要把「早期决策」提炼进稳定摘要块，等于把「中间信息」搬到「模型最强位置（开头/结尾）」，是对抗 lost-in-the-middle 的直接工程手段。
- **结论**：7.1 启用 W3 后，预期能把「被裁中间轮中的关键约束」回收进摘要，使长程（≥15 轮）任务成功率相对 legacy 截断有可测提升——这正是 7.6 反向验证要证明的命题。若 7.6 证明「启用后并未提升」，则说明本项目任务分布尚未触及有效窗口边界，7.1 可降级为「按需开启」而非默认开启——这也是诚实验收的一部分。

## 六、优缺点总评

### 6.1 我们的优点（分级）

- **结构性优势**：关闭态逐位等价（[D11]，构造级 passthrough）；压缩失败回落不伪造；裁剪留痕防重复副作用。这三点构成「安全优先」的结构性底座，多数框架不内置。
- **工程性优势**：记忆「聚合态/事件态」分离 + 读时衰减；记忆预算夹紧防全局崩；W1 外置净省才做；里程碑守卫测试门控启用。
- **领域性优势**：`student_memory` 针对教育薄弱点的精准召回；与 RAG（维 8）边界清晰（记忆=聚合薄弱点，RAG=外部知识检索）。

### 6.2 我们的缺点（分级）

- **设计取舍导致的代价**：`context.enabled=false` → 自动压缩红利当下未享（有意取舍，可启用）；启发式 token 计量（受 D-002 约束，取舍）。
- **能力缺口**：无真实 tokenizer；无通用长期记忆（仅领域）；prefix caching 未利用；压缩质量无反向验证闭环；W3 摘要未接入。
- **运维负担**：两套上下文路径并存（legacy + 富），需保证「关闭态逐位一致」不漂移（依赖 `ContextCompression*GuardTest` 守卫）；记忆表（`student_memory`）需随保留期/撤回策略维护。

### 6.3 各竞品优点（简明，带来源）

- OpenAI SDK：prompt caching 原生降成本（openai.github.io/openai-agents-python）。
- Anthropic SDK：prompt caching + sub-agent 上下文隔离 + /compact（docs.anthropic.com/en/api/agent-sdk）。
- LangGraph：`trim_messages` + reducer + MemoryStore/Checkpointer 灵活可组合（docs.langchain.com/oss/python/langgraph）。
- Google ADK：**自动 history compaction** + Memory Service + Artifacts 延迟加载（adk.dev/sessions）。
- CrewAI：short/long/entity memory + Knowledge 一体（docs.crewai.com/en/concepts/memory）。
- Agno：**Memory 一等公民**（session/agent/user + 向量）（docs.agno.com/memory/overview）。

### 6.4 各竞品缺点（简明，带来源）

- OpenAI SDK：无原生自动压缩，全靠开发者（官方文档未内建）。
- Anthropic SDK：压缩由运行时内部处理，平台侧可控粒度有限（依赖生态）。
- LangGraph：自动语义压缩非框架内建，需自接 LLM 摘要（官方图 API 文档）。
- Google ADK：强绑 GCP/Vertex，自托管运维重（adk.dev）。
- Microsoft AutoGen：**已归档停维护**，不宜新选型（microsoft.github.io/autogen）。
- CrewAI：记忆与 RAG 边界模糊、深度压缩非重点（官方 concepts）。
- Agno：框架较重、需接受其抽象与自运维（docs.agno.com）。

### 7.1 自动上下文压缩的最小生产化启用（触发器 → 摘要 → 落库 → 验收）

- **问题陈述**：当前 `context.enabled=false`（yml:232），生产只有 legacy 轮截断，早期关键信息被裁即永久丢失，不抗 lost-in-the-middle。富管线 `CompactionPipeline` 已建成但未接线生效。
- **方案设计**：

### 7.2 真实 tokenizer 计费引入（替换粗估）

- **问题陈述**：`ContextBudgetTrimmer.estimateTokens`（:171-189）与 `HeuristicTokenCounter.count`（HeuristicTokenCounter.java:49-63）均为 CJK1/非CJK3 启发式，误差 30–50%（HeuristicTokenCounter.java:14 自承），无法精确对齐供应商窗口硬限与 `usage.prompt_tokens` 计费。
- **方案设计**：
  - 新增 `agent-context` 内 `TiktokenTokenCounter implements TokenCounter`（复用现有 `TokenCounter` 接口，CompactionPipeline.java:13 已依赖），内嵌 **cl100k_base / o200k_base** 等价 BPE（用 `com.knuddels:jtiktoken` 或等价纯 Java 实现，避免 JNI/原生依赖）。模型→编码映射来自 `cap_agent_def.model_ref`（DDL:1664）经 `ModelCatalogPort` 解析（ContextRequestAssemblyAdapter.java:47-61）。
  - 接线：`ContextAssembler` 构造注入 `TiktokenTokenCounter` 替换 `HeuristicTokenCounter`（platform-bootstrap 组合根）；legacy `ContextBudgetTrimmer` 亦新增 `estimateTokens(text, TokenCounter)` 重载，生产默认切换到真实计数（保留启发式作为「模型未探测能力」时的 fallback，GlobalContextPolicy.java `unknown-capability-reserve-ratio` 上调 reserve 兜底，yml:242）。
  - 校准：`TokenEstimationCalibrator`（已存在）用 `usage.prompt_tokens` 真值做 EWMA 偏差校准（yml:254-260），`min-samples=30` 前不启用校准（防小样本噪声）。
  - **代码骨架（新增 `TiktokenTokenCounter implements TokenCounter`）**：
    ```java
    public final class TiktokenTokenCounter implements TokenCounter {
      // 模型名 → 编码（cl100k_base / o200k_base），来自 ModelCatalogPort 解析 model_ref
      private final Map<String, Encoding> encodings; // 如 com.knuddels:jtiktoken 纯 Java 实现
      @Override public int count(ContextBlocks blocks) {
        int total = 0;
        // system/tool/memory/rag/history/current 六块分别 encode 求和（对齐 HeuristicTokenCounter 口径）
        total += encode(spec.modelName(), blocks.systemPrompt());
        total += encode(spec.modelName(), blocks.toolSchemas()); // RV-1：工具定义必计入
        // ... 其余块同构
        return total;
      }
      private int encode(String model, String text) {
        Encoding enc = encodings.getOrDefault(model, encodings.get("default"));
        return enc.encode(text).size(); // 真实 BPE 计数，误差 <1 token
      }
    }
    // legacy ContextBudgetTrimmer 同步新增 estimateTokens(text, TokenCounter) 重载，
    // 未知模型时回落 HeuristicTokenCounter（GlobalContextPolicy.unknown-capability-reserve-ratio 上调 reserve 兜底）
    ```
- **预期收益**：① 预算估算误差从 30–50% 降至 <5%；② 因「估算偏小导致超窗」的事故归零（当前偏保守侧早裁，改用真实计数后可**减少过早裁剪**、提升长程质量）；③ 成本计量与供应商账单对齐，维度 9 对账更准。
- **实施成本与风险**：新增依赖（tokenizer 库）须过供应链安全评审；cl100k/o200k 词典体积（~1–2MB）需确认 Worker 启动开销；多模型映射维护成本。风险：tokenizer 版本与供应商不一致 → 仍偏差 → 用 `usage.prompt_tokens` 校准闭环兜底。
- **优先级**：**P1**。排期：S2（接入）→ S3（校准生效）。
- **验收方式**：
  1. **单元**：`TiktokenTokenCounterTest` 对已知英文/中文样本，断言与参考 tiktoken 输出一致（误差 0 token 于边界内）。
  2. **对账门禁**：连续 N≥30 次真实 Run，记录 `estimated_prompt_tokens`（装配内核 afterTokens）与 `usage.prompt_tokens`，偏差中位数 **<5%** 且 **永不低估 >2%**（防超窗）。
  3. **回归**：`ContextBudgetTrimmerTest` / `HeuristicTokenCounterTest` 保留，断言「启发式 ≠ 真实计数」路径在 unknown 模型时仍兜底不崩。

### 7.5 Prefix Caching 利用（稳定前缀 + cache_control，降延迟与成本）

- **问题陈述**：`RunExecutionLoop:1241` 已有「systemPrompt 用稳定前缀」意识，但**未在请求构造处声明 `cache_control` 断点**，也无命中比例可观测（维度 10 缺）。多轮重复 prefill 成本未优化。
- **方案设计**：
  - 在组合根构造 `ModelRequest` 时（ContextAssembler.java:124-132 已区分稳定 system/tool 与动态 messages），**把 system 提示 + 工具定义作为稳定前缀块并打 `cache_control` 断点**（Anthropic 机制 T4：<https://platform.claude.com/docs/en/build-with-claude/prompt-caching>；vLLM 等价 APC）。动态历史/当前输入追加在断点之后。
  - 约束（来自 T4）：① 稳定前缀**字节精确**——`ContextLayout.render`（CompactionPipeline 的布局）须保证 system/tool 块在多次调用间**不变**（memory/rag 块若每轮变，须放在断点之后或单独断点）；② 避免把动态时间戳/RunId 塞进前缀（否则破缓存）；③ 压缩触发（compaction）重写对话前缀时，正是切换模型的时机（T4 同述）。
  - 接线：在 `ModelGateway` 适配层（agent-infrastructure）把 `cache_control` 透传给支持前缀缓存的供应商；不支持的供应商静默忽略（fail-closed 不报错）。
  - **代码骨架（稳定前缀 + 断点）**：
    ```java
    // 在 ContextAssembler 构造 ModelRequest 处（ContextAssembler.java:124-132 已区分稳定/动态）
    // 把 system + tool 作为稳定前缀块并打 cache_control 断点，动态历史/输入置其后
    List<ContentBlock> prefix = List.of(
        systemBlock.withCacheControl(Ephemeral),   // 稳定：缓存命中关键
        toolSchemaBlock.withCacheControl(Ephemeral) // 稳定：工具定义
    );
    List<ContentBlock> dynamic = rendered.messages(); // 变化：历史 + 当前输入
    request = request.withBlocks(concat(prefix, dynamic));
    // 约束（T4）：memory/rag 块若每轮变，必须置于断点之后或单独断点，否则破缓存；
    //          动态时间戳/RunId 严禁进入前缀；compaction 重写对话前缀时恰为切换模型时机。
    ```
- **预期收益**：① 多轮长程任务**重复 prefill 成本降 ~90%**（缓存读 0.1×）；② 首字延迟下降（免重算稳定前缀）；③ 与 7.4 的命中率门禁形成闭环。
- **实施成本与风险**：需确认所接模型供应商支持 prefix caching（Anthropic/vLLM 支持，部分开源不支持）；稳定前缀「字节精确」要求高——若 memory/rag 块每轮变且误置前缀，缓存必失效。风险：误放易变内容进前缀 → 命中率 0 → 反而每次都全价。
- **优先级**：**P2**（依赖 7.1 启用后多轮才显著收益）。排期：S3。
- **验收方式**：
  1. **命中门禁**：同会话连续 ≥5 轮 Run，断言供应商 `usage.cache_read_tokens` 占 `prompt_tokens` **>60%**（与 7.4 共用）。
  2. **结构门禁**：单测断言 `ContextLayout.render` 的 system+tool 块在「仅变化当前输入」时**字节一致**（哈希稳定），动态块在断点之后。
  3. **失效诊断**：若命中率 <30%，断言 `ContextCalibrationObserver` 能报出「前缀在 step N 发生变更」（定位破缓存根因），不静默。

### 7.6 压缩质量评测（用维度 3 反向验证方法论）

- **问题陈述**：压缩未启用 + 缺长程评测 harness，无法回答「启用压缩后质量是否不降、成本降多少」（5.3 劣势第 5 点）。
- **方案设计**：
  - 建立**长程任务评测集**（≥20 条跨 ≥15 轮、含早期关键事实的多步任务），落 `agent_eval_sample`（DDL 维度 10 已存在）标记 `scenario=long_context`。
  - 反向验证协议（复用维度 3 反向方法论 + 铁律 6「撤掉修复点会红吗」）：
    - **实验 A**：`context.enabled=true`（压缩开）。
    - **实验 B**：`context.enabled=false`（legacy 截断，即「撤掉压缩」）。
    - 对比 `human_verdict`/`auto_verified`（DDL:758 注释：终态≠成功）与 `agent_task_outcome`。
  - 评测门禁：**压缩开启组在长程任务上的成功率 ≥ 关闭组（legacy 截断）成功率 − 2%**，且**输入 token 中位数下降 ≥20%**。若开启组反而更差 → 压缩实现有 bug，须回退（证明「撤掉修复点会红」成立，反向验证有效）。
  - 持续化：把该评测接进 `review_task`（DDL:936 人工审查队列）定期跑，产出「压缩质量不退化」的长期证据。
- **预期收益**：① 给 7.1 启用提供量化决策依据；② 形成「压缩质量不退化」的可重复证据链；③ 反向验证本身即验收（铁律 6/17）。
- **实施成本与风险**：评测集建设成本（领域专家标注）；长程 Run 成本高（但可用小模型压缩器降本）；需防止评测集泄漏进训练（本项目无训练，风险低）。
- **优先级**：**P1**（与 7.1 验收直接绑定）。排期：S2（建集）→ S3（持续化）。
- **验收方式**：
  1. **反向门禁**：同集跑 A/B，断言「B（撤压缩）组的早期关键事实召回率显著低于 A」或「A 成功率 ≥ B−2% 且 A 输入 token ≤ B×0.8」——**二者至少满足其一且 B 不能全面优于 A**（否则压缩无意义）。
  2. **抗 lost-in-the-middle 门禁**：评测集含「关键事实置于第 3 轮、任务在第 15 轮才用」的样本，断言启用压缩后该类样本成功率 ≥ 关闭组（证明压缩缓解了中间丢失）。
  3. **不退化承诺**：连续 3 个版本跑同一集，成功率标准差 <3%（防回归静默）。

## 八、其他有价值的横向对比（避免维度内自闭）

### 8.1 与本项目其他维度的耦合与相互约束（≥2 条）

1. **与维度 3（状态持久化/可恢复）**：`execution_snapshot.context_policy`（DDL:2525，jsonb 默认 `{}`）承载 Agent 级上下文压缩策略的**发布期不可变快照**，供回放/审计。耦合点：压缩策略必须「冻结于发布版本」而非读当前版本（ContextRequestAssemblyAdapter.java:40-45 [D4]），否则在途 Run 中途换策略。约束：压缩落库的新表（`run_context_compaction`）须与 `execution_snapshot` 同受 RLS、同不可变语义（铁律：快照不可变、新表同步角色，铁律 7）。
2. **与维度 8（RAG）**：RAG 召回块（`ragBlocks`）与长期记忆块（`memoryBlock`）在 `ContextBlocks` 中**分列**（ContextAssembler.java:109-112），在上下文里分围栏。边界：RAG=外部知识检索（只读/时效/向量），记忆=本 agent 沉淀语义（可写/衰减）。改进 7.3 显式化该边界。约束：两者都不能未经 `PromptGuard.sanitize` 进可信通道（MemoryRecallService.java:118）。
3. **与维度 9（成本/预算）**：`context-token-budget`（yml:208，16000）是压缩的「窗口上限」输入；压缩降输入 token → 直接降 `usage_record.input_tokens` 成本（7.1/7.2 收益）。约束：压缩器（W3）本身是额外 LLM 调用成本，须计入 `usage_record` 且**绝不混入 judge 成本**（铁律 8）。
4. **与维度 10（可观测）**：7.4 的 `agent_trace_context_metric` 是维度 10 指标体系的子集；压缩触发次数/档位是维度 10 尚未覆盖的信号。约束：指标是事实的确定函数（维度 10 原则），压缩指标须可重算。

### 8.2 与非 agent 领域成熟做法的对照

- **数据库查询优化器的「代价估算」**：真实 tokenizer 类比于「基于真实统计信息的基数估算」vs 启发式估算。本项目当前是「基于规则的粗估」（类比于未收集统计信息的优化器），7.2 类比于「开启 auto-analyze + 真实直方图」——精度提升直接减少「估算偏差导致的错误计划（超窗/过早裁）」。
- **操作系统虚拟内存的「工作集 / 页回收」**：上下文窗口类比于物理内存，历史消息类比于页；`ContextBudgetTrimmer` 的「保留最近轮、丢最早轮」类比于 LRU 页回收；W3 摘要类比于「working set 的压缩页」。启示：可借鉴「工作集」概念——不只按 token 数，而按「最近被模型引用的语义」决定保留，比纯轮次截断更抗 lost-in-the-middle。
- **合规领域的「数据最小化原则」（GDPR 数据最小化）**：上下文只装「高信号 token」与数据最小化同构；裁剪留痕（防重复调用）类比于「操作审计日志」——删除动作必须可解释，不能静默。

### 8.3 反向思考：若从头重做本维度，我们会怎么设计？

- **会直接默认开启分级压缩 + 真实 tokenizer**：不在「先建后开」上这么保守——但保留 [D11] 关闭逐位等价作为**回滚安全网**（这是本项目做对的部分，必保留）。
- **会把「记忆」作为一等公民通用层**：从第一天就把 `USER_PREFERENCE/SESSION_SUMMARY/FACT` 与领域 `student_memory` 并列，避免后期补通用记忆的迁移成本（7.3）。
- **会把 prefix caching 作为请求构造的一等原语**：稳定前缀 + cache_control 从架构第一天内建，而非事后补（7.5）。
- **会与维度 10 同生共长可观测**：压缩触发/档位/命中率从第一行就进指标，而非事后补（7.4）。
- **诚实取舍**：本项目的「先建后开 + 关闭逐位等价 + 失败回落不伪造 + 裁剪留痕」是**值得保留的严谨底座**；若重做，会保留这些，只把「默认关闭」改为「默认开启但带可观测熔断」。

### 8.4 与维度 10（可观测）的协同缺口（专项）

本维度当前几乎**没有任何专属可观测信号**落入维度 10 的指标体系：`agent_trace_metric`（DDL:758）记录终态/工具轮次/安全计数，但**不含**「本次调用的 prompt token 数、压缩触发档位、prefix cache 命中比例」。这意味着：① 7.1 启用压缩后，无法在 Grafana 上直接看到「压缩降了多少 token / 成本」；② 7.5 的 prefix caching 收益无法量化（命中率未知）；③ 7.6 的反向验证缺乏现成指标底座，需临时埋点。因此 7.4 不是「锦上添花」，而是 7.1/7.2/7.5 验收的**前置依赖**——必须先有 `agent_trace_context_metric`（7.4）这张事实表，其余改进的可度量收益才可被观测与回归。这一「可观测先于优化」的顺序约束，是本报告对实施排期（9.2）的重要建议。

## 九、对产品演进的启发

### 9.1 本维度支撑的产品能力（用户能感知什么）

- **长程辅导不「断片」**：启用压缩（7.1）后，学生做 20 步解题，模型仍能记住第 3 步的关键约束（抗 lost-in-the-middle），而非越聊越傻。
- **跨会话连贯**：`student_memory` + 7.3 通用记忆，让学生下次来，模型已知「他总在二次函数符号上错」，无需重新诊断。
- **更便宜的长对话**：7.1/7.2/7.5 合计把长程多轮成本显著压低，使「无限对话」在商业上可行。
- **可控可观测**：7.4 让用户/运营看到「这次对话花了多少 token、压缩了几次、缓存命中多少」，支撑按量计费与 SLA。

### 9.2 演进路线图（近/中/远三期，每期明确产出物与验收标准）

- **近期（S1→S2，灰度前）**
  - 产出：`TiktokenTokenCounter`（7.2）+ `agent_trace_context_metric`（7.4）+ 长程评测集（7.6）。
  - 验收：真实计数误差 <5%（7.2 门禁 2）；指标表有行且可对齐 `usage`（7.4 门禁 1）；评测集 ≥20 条标注完成（7.6）。
- **中期（S2→S3，单租户启用）**
  - 产出：`context.enabled=true` 灰度（7.1）+ `run_context_compaction` 落库（7.1）+ 通用长期记忆层（7.3）+ prefix caching（7.5）。
  - 验收：反向验证 A≥B−2% 且输入 token 降 ≥20%（7.1/7.6 门禁）；`agent_longterm_memory` 与 RAG 隔离（7.3 门禁 1）；cache 命中 >60%（7.5 门禁 1）。
- **远期（S3→S4，全量 + 持续化）**
  - 产出：压缩质量持续评测接 `review_task`（7.6）、记忆沉淀全类型、缓存命中率告警。
  - 验收：连续 3 版本成功率标准差 <3%（7.6 门禁 3）；命中率 <30% 自动诊断告警（7.5 门禁 3）。

### 9.3 风险清单（做这一步可能踩的坑，关联已知铁律）

1. **启用压缩改线上字节**：若未保留 [D11] 关闭等价桥，回滚会失真 → 靠 `ContextCompression*GuardTest` + 单租户灰度（铁律 17：静态守卫 ≠ 运行时成立）。
2. **记忆写入历史幻觉**：通用记忆（7.3）若写模型自由文本未 sanitize → 历史幻觉固化 → 复用 `PromptGuard.sanitize`（MemoryRecallService.java:118）。
3. **新表权限遗漏**：`run_context_compaction`/`agent_longterm_memory` 须同步 `03_platform_roles.sql`（铁律 7：新表同步角色授权；FORCE RLS）。
4. **撤回删除破记忆**：记忆表删除须走受控通道 + `erasure_certificate`（铁律 8：无物理删除端点）。
5. **压缩器成本混入 judge**：W3 摘要 LLM 调用成本须独立记账，绝不混 `usage_record` 的 judge 列（铁律 8）。
6. **prefix 破缓存**：稳定前缀字节不精确 → 命中率 0 → 反而更贵（7.5 风险）→ 靠 7.5 结构门禁（哈希稳定）兜。

### 9.4 一句话结论

> 本平台在上下文管理上「**资产已达 L2、生产仍是 L1**」：自动分级压缩与真实 tokenizer 已建成或易建但默认未启用，长期记忆是领域特定的、与 RAG 边界清晰但非通用；最该先做的三件事是**默认启用压缩（7.1）+ 引入真实 tokenizer（7.2）+ 把压缩质量用反向验证钉死（7.6）**，并借 prefix caching（7.5）与可观测（7.4）把长程成本与质量变成可量化、可回滚的工程闭环——而「关闭逐位等价、失败回落不伪造、裁剪留痕」这三项独有严谨设计，是任何时候都不应丢弃的底座。
