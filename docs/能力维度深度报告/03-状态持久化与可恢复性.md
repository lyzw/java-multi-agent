## 一、维度定义与评估坐标系

### 1.1 这个维度到底解决什么问题（问题陈述，不谈实现）

"状态持久化与可恢复性"回答的不是"agent 能跑多久"，而是**一组关于「执行事实的去向」的元问题**：

- **运行状态存在哪**：是落在进程内存（崩溃即丢）、落在框架专用持久层（与业务库分离）、还是落在业务数据库（权威源唯一）？
- **崩了怎么恢复**：Worker 进程被 SIGKILL、租约过期、消息重投时，**不变量（终态不可迁出、唯一执行者、不重复副作用）由谁、在哪一层保证**？
- **重跑会不会产生重复副作用**：恢复后，一个有真实副作用的工具调用（写数据库、记薄弱点、扣预算）会不会被执行两次？这决定了"恢复"是"续跑"还是"重复犯罪"。
- **副作用不可幂等时怎么办**：当工具调用**结果未知（UNKNOWN）**——既没确认成功也没确认失败——系统该重放、该丢弃、还是该转人工对账？

这一维度是维度 01（编排骨架）的**承载体**，也是维度 05（工具调用）、07（权限护栏）、09（预算不超发）、11（可靠性）、13（HITL）的**事实底座**——骨架、闸门、预算、对账全都要依赖"状态可靠地落在某处、崩溃后仍能恢复且不重复伤害"。

### 1.2 能力分层的四档模型（通用分层法）

按"状态权威源在哪、恢复语义由谁保证、是否能避免重复副作用"给出四档，从弱到强：

| 档位 | 名称 | 状态权威源 / 恢复保证 | 代表形态 | 典型代价 |
|---|---|---|---|---|
| **L0 无持久化** | 进程内存 | 内存，崩了即丢；恢复=从头重跑 | 裸 `chat/completions` 多轮、无状态 SDK 调用 | 崩溃丢失全部进度；重跑重复副作用 |
| **L1 应用层自管持久化** | 应用自己写表 | 应用进程内的"我记下来了"，恢复靠开发者自律 | 自写 `run_status` 表 + 手写续跑逻辑 | 不变量靠自觉；多进程/多实例下易竞态 |
| **L2 框架专用持久层** | 框架 Checkpointer/Store | 框架提供的专用持久层（PostgresSaver 等），可重放/续跑，但与业务库分离 | LangGraph、Google ADK（Session/Memory）、Agno（AgentOS DB） | 跨库一致性需自管；状态机守卫在应用/SDK 层 |
| **L3 数据层强制 + 触发器 + 租约 + fencing** | 业务数据库 + DB 触发器硬守卫 | 业务 PostgreSQL 是唯一权威源；不变量由触发器拒绝写入；租约+fencing 防脑裂 | **本平台（DB 驱动 + 事件唤醒 + 快照定上限 + 触发器状态机 + fencing）** | 开发侧不轻、缺可视化 DSL；运维需正确绑 GUC |

**判定**：本平台落在 **L3**，是本次对比的全部竞品里唯一把"状态机守卫 + 租约 + fencing + 不可变快照"一起下沉到数据库触发器层强制的方案。L0–L2 的恢复保证本质上是"建议"（应用 bug 可绕过），L3 的恢复保证是"存储层拒绝写入"（应用崩了也不破不变量）。

### 1.3 评估坐标系：5 个评价轴

| 轴 | 含义 | 观测方式（如何度量） |
|---|---|---|
| **权威源单一性** | 状态是否存在唯一真相源，避免内存/缓存/DB 多副本分叉 | 注入"内存态更新但 DB 未更新"，看恢复入口是否以 DB 为准 |
| **可恢复性** | 进程崩后能否从任意点续跑、不重复副作用 | 杀 Worker 进程 → 观察 run 是否收敛到终态、副作用是否恰好一次 |
| **脑裂防护** | 双 Worker 同时写同一 Run 是否被阻止 | 制造租约过期+旧 Worker 复活，看旧写入是否被拒绝 |
| **未知结果处置** | UNKNOWN 时是重放、丢弃还是对账 | 注入工具调用超时，看是否产生重复副作用或账实不符 |
| **可审计性** | 谁在何时改变了状态、可否复盘 | 是否存在不可变执行事实表（run_step/run_event/tool_operation） |

## 二、理论体系（必须引用真实出处）

### 2.1 核心理论/概念框架（≥3 个，逐一给真实出处）

#### (1) Transactional Outbox Pattern（事务性发件箱）与 Dual-Write Problem

- **出处**：Chris Richardson 在 *Microservices Patterns*（Manning, 2018，ISBN 9781617294549）中正式命名并归类此模式；官方站点 microservices.io 的 "Transactional Outbox" 条目（https://microservices.io/patterns/data/transactional-outbox.html ）给出权威定义。AWS Prescriptive Guidance、Microsoft Cloud Architecture 指南亦以 "dual-write problem" 描述其对立面。
- **定义**：当一个服务既要更新自己的数据库、又要向消息代理发布事件时，二者**没有共享事务**，无法原子提交。经典写路径「BEGIN → 写业务 → COMMIT → 发消息」在 COMMIT 与发消息之间会崩溃（进程被杀、broker 丢 ack、网络分区），导致"库里有了、消息没发"或反之。Outbox 的解法是：**把事件作为一行写入与业务更新同一个本地事务的 outbox 表**，再由一个**独立的 relay** 读取并发布，发布成功后标记。数据库是真相源，消息是下游投影。
- **两种 relay 取舍（理论张力的核心）**：
  - **Polling（轮询）**：周期 `SELECT ... WHERE published_at IS NULL ORDER BY created_at LIMIT N`，简单、可移植、与任何 SQL 库兼容；代价是引入轮询延迟、需清理增长表。
  - **CDC（Change Data Capture，如 Debezium 读 WAL/binlog）**：延迟低、按提交顺序流、吞吐高；代价是引入 CDC 管道运维复杂度（Kafka Connect + Debezium + schema 演进）。
  - 二者**都不承诺 exactly-once 投递**，只承诺"no lost intent"——消息可能投两次（relay 在 publish 后、标 pending 前崩溃），故**消费端必须幂等**（microservices.io 与 Richardson 均明确此点）。这正是本平台 `outbox_event`（DDL:2597）与 Run 创建**同事务**（DDL:2623）的理论根。
- **与本维度的关系**：本平台的 `outbox_event` 是教科书式 Outbox；relay 当前采用 **polling**（`application.yml:191` `relay-interval-ms=200`）；第七章改进点 2 评估 **CDC 化**（Debezium/logical decoding）的收益与代价。

#### (2) Exactly-Once 的不可能性（at-least-once + 幂等 = effectively-once）

- **出处**：Martin Kleppmann, *Designing Data-Intensive Applications*（O'Reilly, 2017），第 12 章"Stream Processing"系统论证：在跨进程、无全局事务的分布式系统中，**无法同时保证"不漏投递"与"不重复投递"**——只能做到 at-least-once 投递 + 消费端幂等 = **effectively-once（实际一次）**。Confluent 工程博客《Exactly-once semantics》明确：Kafka 的 exactly-once 只覆盖 Kafka **自身处理内部**（事务性 producer/consumer），**不包含对外部存储的更新**——即"向远端系统写一次的精确一次"在通用意义下不可达。
- **定义**："恰好一次"是一个被滥用的词。严格讲，分布式系统只能在**单个被协调的边界内**做到 exactly-once（如 Kafka 内部）；一旦动作跨越进程边界落到外部（数据库行、第三方 API），你只能选 at-least-once 执行，再靠幂等/去重把"效果"收敛到恰好一次。
- **与本维度的关系**：本平台从不声称"恰好一次投递"，而是 at-least-once 投递（Outbox relay）+ **DB 层多道去重**（idempotency_record、run_message.idem_key 唯一约束、claimSpecificRun 条件更新、fencing_token 拒绝旧世代）+ UNKNOWN 转对账（见 2.1(8)）。这正是对 "exactly-once 不可能三角" 的诚实工程应答。

#### (3) Fencing Token（围栏令牌）理论

- **出处**：Martin Kleppmann, *Designing Data-Intensive Applications*（2017）第 8 章，以及 Kleppmann 博客 *"How to do distributed locking"*（2016-02-08，https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html ）。底层思想（单调 sequencer）最早见于 Google Chubby 论文（Burrows, 2006, *"The Chubby lock service for loosely-coupled distributed systems"*, OSDI 2006）。
- **定义**：租约（lease）有 TTL，持有者可能因 GC 暂停 / 网络延迟 / SIGSTOP 而**在租约过期后仍相信自己持有**。普通锁无法防御这种"僵尸写"。Fix 是给每次租约授予一个**单调递增 token**，每次写入都携带该 token，**受保护的资源（存储层）拒绝任何 token 比已见过的最高值更低的写入**。这要求资源本身参与校验（纯文件/无状态 API 做不到，数据库行 + 条件 UPDATE 可以）。Kleppmann 原文："a fencing token is simply a number that increases every time a client acquires the lock... the storage server remembers the highest token number it has seen, and rejects any writes with a lower token"。
- **与本维度的关系**：本平台的 `enforce_fencing_on_write()`（DDL:410-421）正是此范式在 PostgreSQL 触发器内的实现：`NEW.fencing_token < OLD.fencing_token → RAISE`。`run.fencing_token`（:2730）、`run_step.fencing_token`（:2816）在领取/续租时递增，旧世代（崩溃复活的 Worker）的任何 UPDATE 被 DB 直接拒绝。**这是"防脑裂"比单纯租约更硬的根**——普通租约锁（含 `FOR UPDATE SKIP LOCKED`）只防"同时持有"，不防"过期后仍写"。

#### (4) Durable Execution / Workflow 引擎确定性重放模型（Temporal / Cadence）

- **出处**：Temporal 官方文档 *"Durable Execution"*（https://temporal.io/ ）、*Temporal Workflow*（https://docs.temporal.io/workflows ，"How Workflow replay works"）、*Learn > Durable Execution*（https://learn.temporal.io/tutorials/typescript/background-check/durable-execution/ ）。Cadence 为 Uber 开源的前身。
- **定义**：durable execution 指函数在所在机器崩溃后仍能从"已到达的那一行"继续。平台记录每一步 **Event History**（完整有序日志），Worker 崩溃后**不恢复内存快照，而是从代码开头重跑、用 Event History 引导回崩溃前状态**（deterministic replay）。模型调用、工具调用作为 **Activity** 执行——Activity 可重试、可重放、可见；重放时"已完成的 Activity 直接返回记录结果，不再发新请求"。关键纪律：**Activity 必须幂等**（重试会重发）；Workflow 主体必须确定性（无 wall-clock/随机）。
- **与本维度的关系**：本平台的"PostgreSQL 权威源 + 重读 DB + 租约 + fencing"是 durable execution 思想的**数据库内重实现**，区别在于：① 我们用 DB 行（run/run_step/tool_operation）代替 Event History，天然与业务数据同库；② 我们没有"从代码开头重放"的确定性重放引擎，而是"重读 DB 状态 + 从快照上限继续"——这是改进点 1（真续跑）要补的差距；③ 我们显式引入 fencing_token 与 UNKNOWN 对账，比 Temporal"Activity 重试"更严格地防重复副作用（见 5.4 分歧 2）。

#### (5) 幂等键与去重（Stripe Idempotency Keys + HTTP Idempotency-Key 草案 + RFC 9110）

- **出处**：
  - Stripe, *"Idempotent requests"*（https://stripe.com/docs/idempotency ）：客户端生成唯一 key，服务端对同 key 的首次请求落库（status+bod），重试返回首次结果（含 500）；key 至少 24h 后自动清理；**比对请求参数指纹，参数不同则报错**。
  - IETF **Internet-Draft** *"The Idempotency-Key HTTP Header Field"*（draft-ietf-httpapi-idempotency-key-header，作者 J. Jena & S. Dalal；截至本报告撰写时为**草稿（非 RFC）**，datatracker 标注已过期，须引用为 work-in-progress，见诚实边界）。其定义客户端生成 key、服务端按 (account, key) 存指纹与响应、重复返回存储结果、并发冲突返回 409、参数不同返回 422（draft 建议）。
  - RFC 9110 *"HTTP Semantics"* §9.2.2：幂等定义是"多次相同请求的预期**效果**相同"，PUT/DELETE 天然幂等，POST 不是；**幂等只覆盖资源状态，不覆盖它触发的业务副作用**。
- **定义**：幂等键标识"一个逻辑操作"而非"一次请求尝试"；客户端在首次尝试前生成并持久化 key，崩溃重启仍复用同一 key。服务端用唯一约束做原子"首次插入即执行、冲突即回放"，且**参数指纹比对**防止"同 key 不同参数"的静默误用。
- **诚实标注**：`Idempotency-Key` **至今只是 IETF Internet-Draft，不是 RFC**；它被广泛实践（Stripe 为最知名实现），但引用时应明确"草案、细节未冻结"。这与"不可信为 RFC 标准"的工程纪律一致。
- **与本维度的关系**：本平台 `idempotency_record`（DDL:2549，同键同摘要返回原 resource_id、同键异摘要返回冲突）、`run_message.idem_key`（:2886 唯一约束，冲突覆盖而非追加）、`tool_operation.idempotency_key`（:2991）正是此理论的落地。差异：我们的幂等域是**租户内 (tenant_id, key_namespace, idempotency_key)**，且 idem_key 必须含 tenant_id+run_id（DDL 注释 :2885）防跨租户/跨 Run 串扰。

#### (6) Saga 模式与补偿事务（Garcia-Molina & Salem 1987）

- **出处**：Hector Garcia-Molina & Kenneth Salem, *"Sagas"*, **ACM SIGMOD 1987**, pp. 249–259（DOI 10.1145/38713.38742）。原始论文针对"长事务（LLT）持锁过久阻塞短事务"，提出把长事务拆成 T1..Tn 序列，每 Ti 配补偿 Ci，系统保证"全成功 或 前缀 + 反向补偿"。
- **定义**：Saga 放弃外层原子性，换得"锁不在全网持有"的廉价——代价是**丢失隔离性（ACID 的 I）**，中间态对外可见，需开发者自加 countermeasure。补偿是**语义撤销**（semantic undo）而非物理回滚（Ci 不保证把 DB 还原到 Ti 前，只还原到"可接受的近似态"）。
- **与本维度的关系**：本平台的 `tool_operation` UNKNOWN 三态 + `ToolOperationReconciliationService`（维度 11/13 提及）+ `RECONCILED_SUCCEEDED/RECONCILED_ABSENT/MANUAL_DISPOSED` 状态，是 Saga 补偿思想在"单工具操作"粒度的体现——UNKNOWN 不盲目重试（避免重复副作用），而是"挂账→可证明成功则 RECONCILED_SUCCEEDED、可证明未发生则 RECONCILED_ABSENT、不可证明则 MANUAL_DISPOSED"。这与 Saga 的"补偿而非重跑"同构，但用 DB 状态机强制而非应用层约定。

#### (7) 快照隔离 vs 悲观锁 vs 乐观锁（冲突检测）

- **出处**：Kleppmann, *DDIA*（2017）第 7 章"Transactions"，系统比较 **snapshot isolation（SI，MVCC）**、**pessimistic（两阶段锁/SELECT FOR UPDATE）**、**optimistic（version/条件 UPDATE）** 三种冲突检测。
  - **悲观锁**：先锁后改，冲突被挡在门外，但持锁降低并发、易死锁。
  - **乐观锁**：读出版本、提交时 `WHERE version = 读出版本` 条件更新，冲突时失败重试，并发高但不防"读后决策"类的写偏斜（write skew）。
  - **快照隔离**：MVCC 下事务见一致快照，提交时检测写-写冲突；但**不防 write skew**（两个事务读同快照、各自改不同行、都提交）。
- **与本维度的关系**：本平台**不依赖任一通用隔离级别做恢复正确性的主锚**，而是用 **fencing_token（单调递增的乐观条件 UPDATE 特例）** + **DB 触发器硬拒绝** 这组合。值得强调：fencing_token 本质是"带单调代次的乐观锁"——`NEW.fencing_token < OLD.fencing_token` 拒绝，等价于"版本号只能增"。这与 铁律 13 涉及的 `SELECT ... FOR UPDATE SKIP LOCKED` 形成对照（见 5.4 分歧 3）。

#### (8) 「副作用不可幂等时的三难」（at-least-once + 不可幂等副作用 ⇒ 必须 UNKNOWN + 人工对账）

- **出处**：本结论是上述 (2)(3)(4)(6) 的工程推导，非单一论文。可佐证的工程论述：Temporal 明确要求"Activities should be idempotent"（https://docs.temporal.io/ ；其博客指出"tool calls should be idempotent, a retry that recharges a card is a bug"）；Confluent exactly-once 文档指出跨外部系统无法保证一次；Kleppmann DDIA 论证无全局事务下 at-least-once 不可避免。
- **定义（三难）**：在一个「at-least-once 投递（无法避免）+ 副作用不可幂等（真实工具如写库/扣款/发消息，重放即重复伤害）+ 无跨进程全局事务（agent 调外部系统）」的系统中，你**无法同时保证**：① 不漏执行、② 不重复执行、③ 结果确定。三者必失其一。
- **本平台的取舍**：牺牲③（结果确定）——遇到 UNKNOWN 宁可**停止执行、不重放、不释放预算预留、转对账**（enforce 在 DDL:516-539 与 `ToolInvocationGate` 预算三律之三）。这是"副作用不可幂等时三难"下的显式选择：用"对账人力/延迟"换"不重复伤害"。**理论必然性**：只要存在不可幂等副作用且无全局事务，UNKNOWN→重放必然制造重复伤害，故"不重放"不是保守，而是唯一正确解（见 5.4 分歧 2）。

### 2.1.9 理论 → 本平台代码锚点映射表

| 理论 | 核心主张 | 本平台对应实现（锚点） | 继承 / 背离 |
|---|---|---|---|
| Transactional Outbox | 事件与业务同事务，relay 异步发 | `outbox_event`（:2597）与 Run 创建同事务（:2623）；polling relay | **继承**（relay 为 polling 非 CDC，见 I-2） |
| Exactly-once 不可能 | at-least-once + 幂等 = effectively-once | 多道 DB 去重 + UNKNOWN 转对账 | **继承**（诚实接受 at-least-once） |

| Durable Execution | 崩溃续跑、确定性重放 | DB 权威源 + 重读 + 租约（无重放引擎） | **部分**（缺真·续跑，见 I-1） |

### 2.3 业界公认的反模式（anti-pattern）清单及判别方式

1. **把内存态当权威源（split-brain on restart）**：进程重启后从内存而非 DB 续跑。判别：恢复入口是否先 `SELECT` DB。本平台 `claimSpecificRun` 必重读 DB（RunDispatchConsumer.java:199-203）。
2. **Outbox 与业务不同事务（lost wakeup）**：run 已建但唤醒事件未提交 → 永久卡死。判别：run 创建与 outbox 是否同一事务。本平台四者同事务（红线 3，DDL:2623）。
3. **用普通锁替代 fencing token**：崩溃 Worker 仍相信自己持有锁并写入。判别：锁是否带单调代次且由存储层校验。本平台 `enforce_fencing_on_write`（:410-421）。
4. **把队列消息当可信状态（trust-the-payload）**：Worker 直接信 MQ 里的 tenant_id/权限。判别：Worker 是否重读 DB 并绑 RLS。本平台 MQ 仅携带 `tenant_id+run_id+message_id`，状态重读 DB（架构图 :245）。
5. **UNKNOWN 盲目重放**：超时即重试，对不可幂等副作用 = 重复伤害。判别：UNKNOWN 是否被禁止新增 attempt。本平台 `forbid_attempt_after_terminal`（:516-539）。
6. **运行期改写已发布定义**：跑着的 Run 引用被改的 Agent 定义 → 行为漂移。判别：已发布版本行是否可写。本平台 `forbid_published_def_mutation`（:574-609）+ `execution_snapshot` 不可变（:616-623）。
7. **静默回滚假成功（POISONED）**：事务进入 aborted 态被 fail-soft 吞掉，顶层 COMMIT 静默回滚却返回 201。判别：是否有事务毒化标记。本平台 `TransactionalConnectionHolder.POISONED`（:64,160,172-179）。

#### 2.3.1 反模式 → 本平台规避手段映射

| 反模式（2.3） | 本平台规避手段 | 证据锚点 |
|---|---|---|
| 把内存态当权威源 | 恢复入口必重读 DB | `RunDispatchConsumer.java:199-203` |
| Outbox 与业务不同事务 | 四者同事务提交 | `01_platform_ddl.sql:2623` |
| 普通锁替代 fencing | fencing_token 单调代次拒绝旧世代 | `01_platform_ddl.sql:410-421` |
| 队列消息当可信状态 | 仅用消息 tenant_id 绑 RLS，状态重读 DB | `RunDispatchConsumer.java:199-210` |
| UNKNOWN 盲目重放 | `forbid_attempt_after_terminal` 拒绝新增 attempt | `01_platform_ddl.sql:516-539` |
| 运行期改写已发布定义 | `forbid_published_def_mutation` + `forbid_snapshot_mutation` | `01_platform_ddl.sql:574-623` |
| 静默回滚假成功 | `TransactionalConnectionHolder.POISONED` | `TransactionalConnectionHolder.java:64,160,172-179` |

## 三、竞品实现全景（每个主流方案一段，≥4 个）

### 3.1 LangGraph（Checkpointer + Store + time-travel）

- **官方定位与机制**：低层图式编排运行时。`StateGraph` 由 `State`（channels/reducer）、`Node`、`Edge` 组成；持久执行靠 **Checkpointer**（PostgresSaver/SqliteSaver，线程级）+ **Store**（跨线程长期）。支持 time-travel（回到某状态、改状态、再跑）、断点续跑、`interrupt()`/`Command(resume)` 做 HITL。
- **官方来源**：Overview https://docs.langchain.com/oss/python/langgraph/overview ；持久化 https://docs.langchain.com/oss/python/langgraph/persistence ；Graph API https://docs.langchain.com/oss/python/langgraph/graph-api ；断点 https://docs.langchain.com/oss/python/langgraph/persistence#checkpoints ；interrupts https://docs.langchain.com/oss/python/langgraph/interrupts
- **优点**：**time-travel / 断点续跑是业界标杆**；StateGraph 可组合、可调试；LangSmith 提供零配置可视化追踪；Checkpointer 与业务库可同 PostgreSQL（降低跨库一致负担）。
- **局限/代价**：① Checkpointer 是**专用持久层**（与业务库分离，跨库一致需自管）；② 状态机守卫在应用/SDK 层（终态/唯一执行者不变量靠代码，非 DB 触发器）；③ **重放依赖 checkpointer 完整 + 代码确定性**——若节点有非确定性副作用（调外部不可幂等 API），重放会重复伤害；④ 多租户隔离无内建（thread_id 作用域）。
- **适用场景**：需可组合状态图、可调试、长流程、需 time-travel 的研发型应用。

### 3.2 Google ADK（SessionService / MemoryService / session resumption）

- **官方定位与机制**：code-first `Agent`（LlmAgent）+ `Workflow` 图；持久化靠 `SessionService`（会话状态）+ `MemoryService`（跨会话长期记忆）。`Session` 含 events 列表；Agent Runtime 下支持 **session resumption**（从保存的 session 恢复）。
- **官方来源**：https://adk.dev/ ；会话 https://adk.dev/sessions/ ；记忆 https://adk.dev/sessions/memory/ ；运行时 https://adk.dev/deploy/agent-runtime/
- **优点**：声明式图与工作流多种形态灵活；内建 RAG（VertexAiRagMemoryService）；可托管运行时（Cloud Run / Agent Engine）；OTel/Cloud Trace 可观测。
- **局限/代价**：① 强一致/不超发预算**非内建**（用量仅观测）；② 状态机硬守卫未明示（诚实标注）；③ 多租户隔离交给 session 作用域/宿主；④ session resumption 的"恰好一次副作用"语义未明示——依赖开发者保证工具幂等。
- **适用场景**：Google 云生态、需托管部署、多形态编排的产品。

### 3.3 Agno（Durable Queue + 内建多租户）

- **官方定位与机制**：`Agent`/`Team`/`Workflow` 抽象 + **AgentOS 自托管**。其 **Durable Queue**（后台执行）实现为 Postgres/Redis 队列，使用 `SELECT ... FOR UPDATE SKIP LOCKED` 领取、心跳租约（heartbeat lease）、`Idempotency-Key`、与 `max_attempts` 重试。
- **官方来源**：AgentOS https://docs.agno.com/agent-os/overview ；Durable Queue https://docs.agno.com/agent-os/background-execution/durable-queue ；多租户安全 https://docs.agno.com/agent-os/security/overview
- **优点**：Durable Queue（`FOR UPDATE SKIP LOCKED` + 心跳租约 + 幂等键）**与本平台 durable execution 思路高度相似且已产品化**；**唯一内建多租户安全**的竞品（JWT/服务账号/security-key + per-user 隔离）。
- **局限/代价**：① 状态机硬守卫仍主要靠应用/SDK 层（未下沉 DB 触发器）；② `FOR UPDATE SKIP LOCKED` 在 RLS 强制场景下存在 LIMIT 静默失效陷阱（见 5.4 分歧 3 与 铁律 13）；③ AgentOS 自有运维复杂度。
- **适用场景**：需自托管、多租户安全开箱即用的产品。

### 3.4 Microsoft AutoGen（Memory + save/load_state，**已归档停维护**）

- **官方定位与机制**：分层事件驱动多智能体（Core 事件驱动 + AgentChat 对话 API）。Memory 协议 + `save_state`/`load_state` 做状态持久化与恢复。
- **官方来源**：https://microsoft.github.io/autogen/stable/ ；Memory https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/memory.html
- **优点（历史）**：对话驱动协作灵活；内存/状态可 save/load。
- **局限/代价（关键）**：**官方已于 2025-10 并入 Microsoft Agent Framework、2026-10 起归档停维护**；状态机/不变量靠应用层；多租户无内建。**不应作为新项目选型依据**。
- **适用场景**：仅作参照。

### 3.5 CrewAI（`@persist` / checkpoint / Flow state）

- **官方定位与机制**：角色扮演式 `Crew=Agents+Tasks+Process` + `Flows`（`@start/@listen` 事件驱动状态流）。持久化：`Flows` 的 `@persist` 装饰器（SQLite 后端）持久化流状态；`Crew` 的 `checkpoint=True` 做检查点续跑。
- **官方来源**：https://docs.crewai.com/ （concepts/flows、concepts/crews）；企业 https://www.crewai.com/
- **优点**：角色/任务直观；Flows `@persist` 让状态流可控；企业层（Control Plane/AMP）补齐 RBAC/审计。
- **局限/代价**：社区版多租户强隔离无内建（企业层才有）；状态机硬守卫未明示；预算仅 `max_rpm`/`max_iter` 限流，无硬不超发；`@persist` 基于 SQLite，企业级多租户一致性弱。
- **适用场景**：角色化协作型任务、可接受企业层付费治理。

### 3.6 OpenAI Agents SDK / Anthropic Claude Agent SDK（session 持久化）

- **官方定位与机制**：
  - **OpenAI Agents SDK**：极简原语 `Agent/Runner/Handoffs/Guardrails/Sessions/Tracing`，**无显式图**；Sessions 做会话级持久化。来源 https://openai.github.io/openai-agents-python/
  - **Anthropic Claude Agent SDK**：把 Claude Code 当库用，继承其 tools/permissions/sessions/hooks/MCP；`max_turns` 熔断。来源 https://docs.anthropic.com/en/api/agent-sdk
  - **OpenAI/Anthropic 的 Sessions**：OpenAI 的 Sessions 文档明确"用 SQLAlchemy 做存储后端、加密存储"（https://openai.github.io/openai-agents-python/ 的 Sessions 条目提及存储与加密），Anthropic 的 session 由其 Claude Code 二进制维护。二者均为**进程/SDK 层会话态**，非 DB 触发器强制。
- **优点**：极简、开发者体验好；OpenAI Tracing 仪表盘开箱即用；Anthropic 与 Claude 权限/工具一体。
- **局限/代价**：状态主要在进程内存/SDK 层；**无内建状态机硬守卫、无内建多租户隔离**；崩溃恢复弱、多租户隔离交宿主；不变量守卫在 SDK 层。
- **适用场景**：轻量、单租户、开发者体验优先的实验/产品。

### 3.7 竞品持久化范式综合归类

| 形态 | 代表 | 权威源 | 恢复模型 | 内建多租户 | 状态机硬守卫 |
|---|---|---|---|---|---|
| L0 内存 | OpenAI/Anthropic SDK、AutoGen | 进程内存 | 弱（内存丢） | 无 | 无 |
| L2 专用持久层 | LangGraph（Checkpointer）、ADK（Session）、Agno（AgentOS DB）、CrewAI（`@persist`/SQLite） | 框架自带持久层 | 重放/续跑（依赖幂等） | Agno 内建；其余无 | 应用/SDK 层 |
| L3 数据层强制 | **本平台** | 业务 PostgreSQL + 触发器 | 重读 DB + 租约 + fencing | RLS 默认拒绝 | **DB 触发器** |

**关键结论**：除本平台外，**没有任何一个竞品把"状态机守卫 + fencing"下沉到存储触发器层**。Agno 的 Durable Queue（`FOR UPDATE SKIP LOCKED` + 心跳租约）与本平台的 durable execution 思路最接近，但其正确性锚在应用层心跳+行锁，未做"触发器级状态机"这一层（详见 5.4 分歧 3）。LangGraph 的 time-travel 在"可调试性"上领先，但"重放"与"不可幂等副作用"存在本质张力（见 5.4 分歧 2）。

## 四、我们的实现（源码级解剖）

### 4.1 架构与数据流（关键组件、调用链、数据落点）

**控制流（同步侧）**：`RunCreationService` 将 `run + run_event + idempotency_record + outbox_event` **四者同事务**提交（`docs/系统架构图.md:199`），提交后返回 HTTP 202。

**唤醒流（异步边界）**：`OutboxRelay` 轮询 `outbox_event`（`application.yml:191` `relay-interval-ms=200`，索引 `idx_outbox_pending` 在 :4399 仅扫 `state='PENDING'`），投递到 MQ。MQ 消息**只携带 `tenant_id + run_id + message_id`**，**不携带可信权限、不携带状态**（架构图 :245）。

**执行流（Worker 侧）**：`RunDispatchConsumer` **只负责把消息变成一次租约领取**（`RunDispatchConsumer.java:27-57`），业务执行抽成 `RunExecutor`。领取后调 `RunExecutionLoop` 真正执行。领取用 `claimSpecificRun`（:201-203）条件 UPDATE `lease_owner/lease_expires_at` 并递增 `fencing_token`；执行中每步 `renewLease` 按 `lease_owner` **精确匹配**（:1170-1171，`RunExecutionLoop.java:129-132` 注释明确"身份不一致会导致续租永远失败，多步 Run 在第二步被误判为已被接管"）。

**数据落点**：权威事实源全部在 PostgreSQL——`run`（状态机主体）、`run_step`（每轮既成事实）、`run_event`（事件流）、`tool_operation`/`tool_operation_attempt`（副作用三态记账）、`execution_snapshot`（运行期只读快照）、`outbox_event`（唤醒）。MQ 仅为"唤醒/分发"管道（架构图 :401）。

#### 4.1.1 状态机与不可变约束全景（来自 DDL 触发器与表定义）

```
┌─────────────┐         ┌──────────────────────────────────────────────┐
│  创建事务    │ 同事务  │ run(QUEUED) + run_event + idempotency_record + │
│  COMMIT     │────────▶│ outbox_event(PENDING)                         │
└─────────────┘         └──────────────────────────────────────────────┘
                                 │ OutboxRelay 轮询(200ms) → MQ 仅携带(tenant,run,msg)
                                 ▼
┌──────────────────────────────────────────────────────────────────────┐
│ RunDispatchConsumer.claimSpecificRun                                   │
│   UPDATE run SET lease_owner=?, lease_expires_at=now()+?,              │
│                fencing_token = fencing_token + 1                       │
│   WHERE run_id=? AND lease_expires_at < now()   ── 条件 UPDATE 幂等   │
│   旧世代/已被领 → 返回空 → DUPLICATE_DISCARDED（丢弃不重试）           │
└──────────────────────────────────────────────────────────────────────┘
                                 │
                                 ▼
┌──────────────────────────────────────────────────────────────────────┐
│ RunExecutionLoop（快照定上限 while steps<maxSteps）                    │
│   每步: modelGateway.call → ToolInvocationGate(15步) →                 │
│        INSERT run_step(state=RUNNING, fencing_token)                  │
│        INSERT tool_operation(PENDING→IN_FLIGHT→...8态)                │
│        renewLease(lease_owner 精确匹配)                                │
│   终态: commitResult（enforce_run_state_transition 拒绝非法跃迁）      │
└──────────────────────────────────────────────────────────────────────┘
```

**不可变约束三道闸（DDL 触发器）**：
- `enforce_run_state_transition`（:453-475）：终态 `SUCCEEDED/FAILED/CANCELLED/TIMED_OUT` 不可迁出。
- `enforce_fencing_on_write`（:410-421）：`NEW.fencing_token < OLD.fencing_token` 拒绝（旧世代写新世代）。

#### 4.1.2 tool_operation 的 8 态语义（UNKNOWN 三态语义核心）

`tool_operation_state` 枚举（DDL:239-248）共 8 态，是本平台"副作用不可幂等时三难"的工程化载体：

```
        ┌─────────┐  执行开始   ┌──────────┐
        │ PENDING │────────────▶│ IN_FLIGHT│
        └─────────┘             └────┬─────┘
                                     │ 结果到达
                       ┌─────────────┼─────────────────────┬──────────────┐
                       ▼             ▼                     ▼              ▼
                 ┌──────────┐  ┌──────────┐         ┌──────────┐   ┌──────────────┐
                 │ SUCCEEDED│  │  FAILED  │         │ UNKNOWN  │   │ (超时/断连)   │
                 └──────────┘  └──────────┘         └────┬─────┘   └──────┬───────┘
                                                          │ 对账（不重放）   │ 等同 UNKNOWN
                                                          ▼                │
                                          ┌─────────────────────────────┴──────────┐
                                          ▼              ▼                       ▼
                                  ┌────────────────┐ ┌────────────────┐  ┌──────────────────┐
                                  │RECONCILED_     │ │RECONCILED_     │  │  MANUAL_DISPOSED │
                                  │ SUCCEEDED      │ │  ABSENT        │  │(人工处置,需      │
                                  │(可证明成功)   │ │(可证明未发生) │  │ actor+时间)       │
                                  └────────────────┘ └────────────────┘  └──────────────────┘
```

关键不变量（由 DDL CHECK + 触发器强制）：
- `forbid_attempt_after_terminal`（:516-539）：`SUCCEEDED/RECONCILED_*/MANUAL_DISPOSED` 终态后**禁止新增 attempt**；**`UNKNOWN` 状态下新增 attempt = 盲目重试 = Sev-0，直接 `RAISE`**（:532-536）。
- `tool_operation_unknown_needs_disposition`（:3004）：`RECONCILED_SUCCEEDED` 必须带 `reconciled_at`。
- `tool_operation_manual_needs_actor`（:3003）：`MANUAL_DISPOSED` 必须带 `manual_disposed_by + manual_disposed_at`。
- **预算纪律（铁律/预算三律之三）**：`tool_operation.budget_reservation_id` 注释（:3014）明确"UNKNOWN 状态下不得自动释放预留——成本可能已发生（R-007）"。即 UNKNOWN **不释放预算预留、转对账而非盲目重放**。

### 4.4 我们独有的设计（差异化设计）

1. **DB 权威源 + 触发器级状态机 + fencing（L3）**：这是与所有竞品（L0–L2）的本质差异——不变量（终态不可迁出、唯一执行者、旧世代拒绝写入）在 DB 层拒绝，应用崩了也不破坏。
2. **fencing_token 而非裸锁/SELECT FOR UPDATE SKIP LOCKED**：`enforce_fencing_on_write` 用单调代次拒绝旧世代，规避"持有过期锁的进程仍相信自己持有"的 split-brain（Kleppmann 明确区分 fencing token 与 plain lock）。
3. **UNKNOWN 不重放、转对账**：对结果未知的步骤，宁可停执行转人工/自动对账，也绝不盲目重投——这是"副作用不可幂等时三难"下的理论必然选择（见 5.4）。
4. **运行期只读快照（execution_snapshot 不可变 + 已发布 def 不可改写）**：`maxSteps/maxLlmCalls/timeout/agent_config/prompt_config/tool_contracts` 在 Run 创建时冻结，**运行期不可改写**——杜绝"配置漂移"（见 5.4 分歧 4）。
5. **POISONED 事务**：把"SQL 失败"与"业务降级"区分开，事务进入 aborted 态被 fail-soft 吞掉时打标，提交前 `if (isPoisoned()) throw`——明确 5xx 优于假 201（见维度 11）。

## 五、正面对比分析

### 5.0 两条持久化范式的本质差异（任务书重点）

本平台与 LangGraph 代表了 agent 持久化的两种底层范式。最本质的分歧不是"语法糖"，而是**谁持有状态、状态以什么形态存在、恢复时做什么**这三个元问题：

| 元问题 | LangGraph（Checkpointer + 重放） | 本平台（DB 权威源 + 事件唤醒 + 租约 + fencing） |
|---|---|---|
| **状态以什么形态存在** | Checkpointer 存**图状态快照**（channels/reducer 的序列化），是"框架专用持久层" | PostgreSQL 业务库中的**事实表**（run/run_step/tool_operation），与业务数据同库 |
| **恢复时做什么** | 从 Checkpointer **重放 graph state**（time-travel），代码从记录点续跑 | **重读 DB + 领取租约 + fencing**，从快照上限继续（当前非"从崩溃点精确续跑"，见 I-1） |
| **不变量由谁强制** | 应用/SDK 层（建议性） | **DB 触发器**（强制性） |
| **能否被应用 bug 绕过** | 可能 | **不可能**（写入即被 DB 拒绝） |
| **不可幂等副作用下重放** | 若节点有非确定副作用，重放=重复伤害（需开发者自保幂等） | **UNKNOWN 不重放、转对账**（DB 状态机强制） |
| **多租户隔离** | 无内建（thread 作用域） | **内建 RLS 默认拒绝**（维度 02） |

**谁更适合"有副作用的工具调用 + 不可幂等"？**——这是本维度最关键的判准：

- **LangGraph 的优势**在于"可调试性"（time-travel 回到某状态改状态再跑）与"与业务库同 PostgreSQL 可降低跨库一致负担"。但它把"重放"当作恢复主路径，而**重放对不可幂等副作用是危险的**——除非每个节点都严格幂等。对于"写数据库、记薄弱点、扣预算"这类真实副作用，LangGraph 的默认重放模型需要开发者自己保证幂等，否则崩溃恢复即重复伤害。
- **本平台的优势**在于"DB 是权威源 + MQ 只唤醒 + 租约+fencing + UNKNOWN 转对账"的组合，从架构上**消除了重复伤害的可能性**：消息不携带状态（无陈旧状态类别错误）、旧世代写入被 DB 拒绝（无脑裂）、UNKNOWN 不重放（无盲目重试）。代价是失去 time-travel 式交互调试（改进点可部分补，但生产优先强一致）。

**结论**：在"有副作用且不可幂等的工具调用"这一前提下，**本平台的范式更安全、更正确**；LangGraph 的范式在"可调试、研发型、副作用可控/可幂等"场景更顺手。这是定位差异，不是优劣排名。

### 5.2 优势详解（为什么领先，讲清机制）

- **为什么"DB 权威源 + MQ 只唤醒"领先**：竞品的 Checkpointer/Session 是"专用持久层"，与生产业务库分离，跨库一致需自管；且消息/内存态可能携带"陈旧状态"（如过期的权限、过期的配置）。本平台让 **MQ 只携带 `tenant_id+run_id+message_id`**（架构图 :245），Worker 领取后**永远重读 DB**——这消除了分布式系统中一个经典类别错误：**"用消息体里携带的状态替代权威源"**。消息不是状态载体，只是"该醒了"的信号。机制上，这是把"状态一致性"完全收敛到 DB 一层。
- **为什么"fencing_token"领先**：竞品的并发占有控制多为租约/行锁（Agno 用 `FOR UPDATE SKIP LOCKED`）。但普通锁只防"同时持有"，不防"过期后仍写"——崩溃的 Worker 持有过期租约仍可能写入。本平台 `enforce_fencing_on_write` 要求 `NEW.fencing_token >= OLD.fencing_token`，旧世代（代次更低）的任何 UPDATE 被 DB 拒绝——等价于 Temporal/Restate 的 fencing token 范式，**在数据库内零额外组件**实现。
- **为什么"UNKNOWN 转对账"是结构性优势**：在真实副作用（写库、记薄弱点、扣预算）存在的场景，盲目重放=重复写入=Sev-0。本平台用 `Outcome.UNKNOWN_RESULT → ack 丢弃` + `forbid_attempt_after_terminal` 切断重放，代价只是"需要对账通道"，换来的是**账实相符、可对账、不重复副作用**的硬保证。这正是 "exactly-once 不可能三角" 下"牺牲结果确定、保不重复执行"的显式正确解。

### 5.3 劣势与盲区详解（根因分析）

- **落后 1：缺 time-travel 调试（根因=取舍）**。LangGraph 的 time-travel/断点续跑是标杆。本平台有不可变 `run_step/run_event/tool_operation`（已具备重放数据基础），但**未提供"回到某步、改状态、再跑"的交互**，属取舍——生产运行时优先强一致而非交互式调试。
- **落后 2：当前是"崩溃后重读 DB"，非"从崩溃点精确续跑"（根因=能力缺口 + 取舍）**。本平台恢复时从 Run 快照上限（`while steps<maxSteps`）重新驱动，而非"精确从崩溃的那一步的 cursor 续跑"——中间已完成的步骤会被重读但工具调用本身不会"断点续传"（模型调用/HTTP 调用若在中途崩溃仍可能重发）。这是改进点 1（真续跑）要补的差距。属**能力缺口**，非取舍（见 I-1）。
- **落后 3：UNKNOWN 偏人工/规则（根因=运维缺口）**。`tool_operation.state=UNKNOWN` 目前依赖 `ToolOperationReconciliationService` + 人工/规则，缺乏自动化 SLA 与可视化工作台（改进点 3 补）。
- **落后 4：开发者体验重（根因=定位差异）**。本平台是"生产运行时"而非"库"，写 agent 需走治理发布。与 OpenAI/Anthropic "几行搭好"相比确实重。
- **落后 5：Outbox relay 为 polling（根因=取舍）**。200ms 轮询引入固定唤醒延迟；CDC 化可降延迟但增运维（改进点 2 评估）。

### 5.4 关键分歧点（最本质的架构分歧）

**分歧 1：状态以什么形态存在、恢复做什么？**
- LangGraph：状态 = 图状态快照（Checkpointer），恢复 = 重放 graph state（time-travel）。
- 本平台：状态 = 业务库事实表，恢复 = 重读 DB + 租约 + fencing，从快照上限继续。
- 后果：LangGraph 可"time-travel 调试"但重放对不可幂等副作用危险；本平台杜绝重复伤害但缺交互式调试。

**分歧 2：UNKNOWN（结果未知）怎么办？——不可幂等副作用时的三难**
- Reflexion/Temporal 式：重放 + 重试（Activity 幂等假设）。
- 本平台：转对账、绝不重放、不释放预算。
- 后果：本平台在"有真实副作用"场景下避免了重复写入 Sev-0，但放弃了"从失败中自动学习"的能力——**UNKNOWN 的自动学习需由对账通道 + 人工/规则补**，而非运行期重放。这对应 **exactly-once 的不可能三角**：在一个"at-least-once 投递 + 副作用不可幂等 + 无全局事务跨进程"的系统中，你无法同时保证"不漏执行、不重复执行、结果确定"。本平台选择**牺牲"结果确定（UNKNOWN 时停）"来保"不重复执行"**——这是"副作用不可幂等时的三难"下的显式取舍（第三难：若副作用可幂等，则可重放；不可幂等则只能停+对账）。

**分歧 3：并发占有控制——fencing_token vs 乐观锁 vs 悲观锁 vs SELECT FOR UPDATE SKIP LOCKED**
- **悲观锁（`SELECT ... FOR UPDATE`）**：先锁后改，冲突挡门外，但持锁降低并发、易死锁；且锁随事务结束释放，无法跨"长事务/跨请求"保护（崩溃即丢锁）。
- **乐观锁（version 条件 UPDATE）**：读版本、提交 `WHERE version=读出版本`，冲突失败重试；并发高。fencing_token **本质是带单调代次的乐观锁特例**（`NEW.fencing_token < OLD.fencing_token` 拒绝），区别在于代次由"领取/续租"单调推进、且由 DB 触发器在**任何** UPDATE 上强制（不止提交时）。
- **`SELECT ... FOR UPDATE SKIP LOCKED`**（Agno 采用）：从队列表原子领取一行、跳过被锁行，适合高并发队列。但存在**铁律 13 的陷阱**：在 `FORCE ROW LEVEL SECURITY` 下，`IN (SELECT ... LIMIT ... FOR UPDATE SKIP LOCKED)` 子查询里的 `LIMIT` 会**静默失效**（RLS 重写使 LIMIT 不再按预期裁剪），导致"本该只领 N 条却领了一堆"或"跳过逻辑错乱"。正确写法须用 `WITH candidates AS MATERIALIZED (SELECT ... LIMIT N FOR UPDATE SKIP LOCKED)` 固化子查询结果。
- **本平台的选择与根由**：我们**没有采用 `FOR UPDATE SKIP LOCKED` 做主占有控制**，而是用 `UPDATE run SET lease_owner=?, fencing_token=fencing_token+1 WHERE run_id=? AND lease_expires_at<now()` 的**条件 UPDATE + 单调 fencing**。原因有二：① fencing 比行锁更硬（防过期后写，行锁做不到）；② 规避铁律 13 的 LIMIT 静默失效陷阱——我们的领取是单 run 精确条件 UPDATE，不依赖"LIMIT + SKIP LOCKED"的队列扫描；租约过期扫描（孤儿/接管）走 `idx_run_lease`（:4455，`WHERE state='RUNNING'` 部分索引），同样用精确 WHERE，不踩 SKIP LOCKED 的 LIMIT 坑。这是"在 FORCE RLS 下做并发占有"时比 Agno 更稳妥的选型。

**分歧 4：配置/定义可否运行期改写？——运行期只读快照的理论价值**
- LangGraph/ADK/Agno/CrewAI：运行期 Agent/图定义通常可变（改配置即时生效，或 session 内可变）。
- 本平台：**`execution_snapshot` 整体不可变**（`forbid_snapshot_mutation` :616-623）+ **已发布 `cap_*_def` 行不可改写**（`forbid_published_def_mutation` :574-609）+ 快照定上限（`maxSteps/maxLlmCalls/timeout` 创建时冻结）。
- **理论价值（配置漂移防护）**：在长生命周期、强治理的生产 SaaS 里，"跑着的 Run 引用的定义被改"会导致**不可复现、责任不清、审计失效**。运行期只读快照把"创建时刻的 Agent 契约"钉死，使其与"当前最新定义"解耦——旧 Run 不受新配置影响，审计时可精确回溯"这次执行当时依据的是哪份配置"。这是"治理期发布、运行期钉死"范式的承载体，也是与所有竞品"可变定义"的本质差异。

### 5.5 补齐差距所需的最小改动集（落后项 → 对应改进）

| 落后项（5.3） | 根因分类 | 最小改动 | 对应改进项 |
|---|---|---|---|
| 缺 time-travel | 设计取舍 | 已有不可变事实表，补"回到某步再跑"交互（非必须，生产优先强一致） | —（暂不立项） |
| 非"精确续跑" | 能力缺口 | snapshot/cursor 对齐 execution_snapshot，断点续跑 | I-1 |
| UNKNOWN 偏人工 | 运维缺口 | 自动化对账工作台（可幂等自动、不可幂等人工） | I-3 |
| polling 唤醒延迟 | 性能取舍 | NOTIFY 双通道 + CDC 评估 | I-2（CDC 评估） |
| 对账无可视化 | 运维缺口 | 对账工作台端点/UI/报表 | I-3 |

### 6.1 我们的优点

**结构性优势（架构层，竞品普遍不具备）**

## 七、可优化与改进点（必须可执行）

> 准则：每条写到文件/表/配置/接口级别，给可执行的验收门禁（不写"加强测试"类空话）。所有改动须遵守项目铁律（尤铁律 2/5/8/11/13/16）。

### I-1：真正的「续跑」能力——从崩溃点精确续跑（snapshot/cursor 对齐）

- **问题陈述**：当前恢复入口从 Run 快照上限（`while steps < snapshot.maxSteps()`）重新驱动，**非"从崩溃点精确续跑"**。若一个 Run 已在第 5 步完成、在第 6 步的模型调用中途崩溃，重启后会**重读 DB 重跑第 6 步**——模型调用本身若非幂等（如再次向外部 API 发起请求）仍可能重复发起；更隐蔽的是，若崩溃发生在 `commitResult` 之前、租约已过期被接管，接管 Worker 也会从第 6 步重跑。这与 durable execution 的"从已到达的那一行继续"仍有差距（维度 01 已指出"缺 time-travel"，此处聚焦"精确续跑"）。
- **方案设计**：引入**执行游标（execution cursor）**，使恢复能精确对齐到"下一个未完成的步骤"，而非从 `step=1` 的语义上限重驱。
  1. **`run_step` 增加 `step_status` 细化列**（或复用现有 `completed_at` + 新增 `cursor_checkpoint jsonb`）：当前 `run_step.state` 恒 `RUNNING` 且 `completed_at` 判定完成（DDL:2833）。新增列：
     ```sql
     -- V40__run_step_cursor.sql
     ALTER TABLE public.run_step
         ADD COLUMN cursor_state text NOT NULL DEFAULT 'PENDING'
             CHECK (cursor_state IN ('PENDING','MODEL_CALLING','TOOL_CALLING','COMMITTING','DONE'));
     ALTER TABLE public.run_step
         ADD COLUMN cursor_offset jsonb;  -- 步骤内进度（如已完成的子调用序号、已流式到的 token 偏移）
     COMMENT ON COLUMN public.run_step.cursor_state IS '执行游标：标记该步骤进行到哪一步内阶段，崩溃恢复据此精确续跑而非整步重跑';
     ```
  2. **`RunExecutionLoop` 在每步内按 cursor_state 推进**：进入模型调用前置 `cursor_state='MODEL_CALLING'`；模型返回后置 `'TOOL_CALLING'`（若有工具）；工具完成置 `'COMMITTING'`；`completed_at` 写入后置 `'DONE'`。重启后 `claimSpecificRun` 成功即读 `MAX(step_number)` 且 `cursor_state<>'DONE'` 的步骤作为续跑起点，跳过其已完成阶段。
  3. **与 `execution_snapshot` 对齐**：cursor 的"上限"仍由 `execution_snapshot.run_config`（maxSteps 等）约束，不突破快照；snapshot 不可变（D8）不变。
  4. **工具调用级续跑**：`tool_operation_attempt` 已有 `attempt_number` 与 `result_unknown`（DDL:3032），续跑时对 `state='UNKNOWN'` 的 attempt 走对账而非重发（铁律 2：UNKNOWN 禁 attempt）。
- **预期收益**：崩溃恢复从"可能重发整步"降级为"从断点阶段续跑"，重复副作用面显著收窄；可度量：Chaos 测试"在 step=6 的 MODEL_CALLING 阶段 kill Worker"，重启后断言该步**不重新进入已完成的子阶段**、且 `tool_operation` 无重复 `SUCCEEDED` 行。
- **实施成本与风险**：改动面中等（加列 + 执行循环写 cursor + 恢复入口读 cursor）。风险：cursor 写入须与步骤主写入**同事务**（铁律 11：事务内 SQL 失败禁 fail-soft 后 COMMIT）；cursor 不可绕过 `enforce_fencing_on_write`（写 `run_step` 必带 `fencing_token`）。
- **优先级**：P1（可恢复性的核心补全）。
- **验收门禁**：① 新增 `ResumeCursorIT`：构造 ≥6 步 run，在第 6 步 `cursor_state='MODEL_CALLING'` 时 kill 模拟（或注入异常），重启后断言 `run_step WHERE step_number=6` 的 `cursor_state` 从 `MODEL_CALLING` 续进、且未产生重复 `tool_operation`（同 `idempotency_key` 唯一）；② 断言续跑后 `run_step` 总数 == 预期步数（无步骤重复插入）；③ `V40` 迁移在真实 PostgreSQL 跑（非 H2），防 `CHECK`/`jsonb` 语义漂移；④ 断言 `cursor_state` 写入与 `completed_at` 同事务（撤掉 cursor 写入点会让"步骤完成"判定失准——反向验证）。

### I-2：Outbox relay 的 CDC 化评估（Debezium / logical decoding）

- **问题陈述**：`OutboxRelay` 轮询 `outbox_event`（索引 `idx_outbox_pending` :4399，`WHERE state='PENDING'`），`relay-interval-ms=200`（`application.yml:191`）带来固定唤醒延迟，且轮询对大表有持续读压力。CDC（Change Data Capture，读 PostgreSQL WAL via logical decoding，Debezium）可把延迟降到秒级内、按提交顺序流、降低应用读压力。
- **方案设计（评估 + 可选落地）**：
  1. **评估口径（先决，不落地）**：产出一份《CDC 化收益/成本评估表》，量化：① 延迟（polling 200ms → CDC <50ms 的 P99 收益）；② 运维成本（新增 Debezium + Kafka Connect + schema 演进 + WAL 保留策略，SRE 负担）；③ 正确性（CDC 仍 at-least-once，消费端幂等不变；崩溃在"publish 后/标 PUBLISHED 前"仍重复投递，须保留消费端去重）；④ 与现有 `idx_outbox_pending` 部分索引的冗余关系。
  2. **若评估通过，落地形态**（默认关、灰度）：
     ```yaml
     agent:
       worker:
         outbox:
           relay-mode: "POLLING"          # 默认；可选 CDC
           cdc:
             enabled: "false"
             publication-name: "outbox_pub"
             slot-name: "outbox_slot"
     ```
     新增 `V41__outbox_cdc_publication.sql`：`CREATE PUBLICATION outbox_pub FOR TABLE public.outbox_event;` 并在 relay 侧保留 polling 作为**兜底**（防 CDC 管道故障导致永久卡死，呼应铁律 5"双通道、采集不复用"的精神）。
  3. **绝不削弱消费端幂等**：无论 polling 还是 CDC，下游 `RunDispatchConsumer` 的"重复消息丢弃 + claimSpecificRun 条件更新"不变（I-1/D4）。
- **预期收益**：唤醒延迟 P99 从 ≤200ms 降到 ≤50ms（评估口径）；降低对 `outbox_event` 的轮询读压力。可度量：基准测试对比 `relay-mode=POLLING vs CDC` 的 `run_created → worker_picked` 延迟 P99 与 relay 侧 DB 读 QPS。
- **实施成本与风险**：CDC **运维成本高**（Kafka Connect/Debezium + 监控 + WAL 保留），对小部署是负担；风险：CDC 管道故障须有 polling 兜底，否则退化成"建了不唤醒"。**结论倾向**：当前规模下 polling 足够，CDC 作为"规模/延迟驱动的可选项"而非必做项——本报告将其定位为**评估 + 可选灰度**，非强制。
- **优先级**：P3（评估）/ P2（若落地）。
- **验收门禁**（若立项）：① `OutboxCdcEvalIT`：开启 CDC 后断言延迟 P99 < 50ms 且 polling 兜底在 CDC 停摆时仍能唤醒（注入 CDC 丢消息 → run 最终被 polling 消费，无永久卡死）；② 断言 CDC 重复投递下 `claimSpecificRun` 仍幂等（同 run 不双执行）；③ 评估文档须含"运维成本清单 + 回滚方案（DROP SUBSCRIPTION/PUBLICATION）"，CI 不强制但作为发布评审材料。

### I-3：对账（reconciliation）工具化——「对账工作台」最小实现

- **问题陈述**：`tool_operation.state='UNKNOWN'` 当前依赖 `ToolOperationReconciliationService` + 人工/规则（维度 11/13 提及），**缺乏可视化与 SLA**。UNKNOWN 是"三难"下的必然产物（见 2.1(8)），体量会随规模增长——必须工具化而非靠人肉捞库。
- **方案设计**（三件套：表/端点/UI/报表）：
  1. **对账工作台表**（新增，不改动既有 `tool_operation`）：
     ```sql
     -- V42__reconciliation_workbench.sql
     CREATE TABLE public.reconciliation_case (
         case_id uuid DEFAULT gen_random_uuid() NOT NULL,
         tenant_id uuid NOT NULL,
         operation_id uuid NOT NULL,
         detected_at timestamptz NOT NULL DEFAULT now(),
         disposition text NOT NULL
             CHECK (disposition IN ('PENDING','AUTO_RECONCILED','MANUAL_RECONCILED','WAIVED')),
         evidence jsonb,                       -- 查到的外部状态/日志指纹
         decided_by text,
         decided_at timestamptz,
         sla_due_at timestamptz,              -- SLA 到期，超期告警
         created_at timestamptz NOT NULL DEFAULT now()
     );
     ALTER TABLE ONLY public.reconciliation_case FORCE ROW LEVEL SECURITY;
     CREATE INDEX idx_recon_pending ON public.reconciliation_case (tenant_id, disposition)
         WHERE disposition = 'PENDING';
     ```
     触发器或调度：每次扫描 `tool_operation WHERE state='UNKNOWN'`（已有 `idx_tool_operation_unknown` :4542）且未建 case 的，自动建 `PENDING` case 并算 `sla_due_at = now() + 间隔`。
  2. **只读端点**（运维/租户管理员）：`GET /api/platform/reconciliation/cases?disposition=PENDING` 返回待办；`POST /api/platform/reconciliation/cases/{id}/decide` 落 `AUTO_RECONCILED/MANUAL_RECONCILED/WAIVED`（受 `unknown:dispose` 动作管控，铁律：MANUAL_DISPOSED 须 actor+时间）。决策写回 `tool_operation`（置 `RECONCILED_*/MANUAL_DISPOSED`）。
  3. **UI/报表**：对账工作台页面（待办列表 + 证据展示 + 批量决策 + SLA 倒计时）；报表：待办数、超期数、各 disposition 占比、按租户/工具分布。
  4. **自动化半闭环**（复用维度 01 I-3）：可幂等键/业务唯一键命中的 UNKNOWN 自动 `RECONCILED_SUCCEEDED/ABSENT`；**未命中的仍 `MANUAL_DISPOSED` 待人工，绝不自动释放 `budget_reservation`**（铁律 8 / 预算三律之三）。
- **预期收益**：UNKNOWN 从"人肉捞库"变为"有 SLA、有证据、可批量决策"的工程闭环；可度量：IT 模拟"UNKNOWN + 幂等键命中"→ 自动 RECONCILED 比例；"UNKNOWN + 无幂等键"→ 进 `PENDING` case 且 `budget_reservation` 仍 `RESERVED` 比例 = 100%。
- **实施成本与风险**：新增表 + 端点 + UI + 调度；风险：自动对账误判副作用已发生会错账——故**只有命中幂等/业务唯一键才自动**，否则人工（铁律 2：终态后禁补 attempt；铁律 8：UNKNOWN 绝不释放预算）。
- **优先级**：P2。
- **验收门禁**：① `ReconciliationWorkbenchIT`：构造 `tool_operation` UNKNOWN + 同幂等键已有 SUCCEEDED → 跑调度 → 断言自动建 `AUTO_RECONCILED` case 且 `budget_reservation` 仍 `RESERVED`；② 构造 UNKNOWN + 无幂等键 → 断言进 `PENDING` case、预算仍 RESERVED、UI 待办可见；③ 断言 `decide` 端点对 `MANUAL_RECONCILED` 要求 `decided_by` 非空（映射 `manual_disposed_by`）；④ 断言 SLA 超期报表能统计出该 case。

### I-4：幂等键作用域与 TTL 清理策略（`idempotency_record` 保留期 + 清理作业）

- **问题陈述**：`idempotency_record`（DDL:2549）有 `expires_at`（必填，非空约束），但**当前未见系统化清理作业**（维度 02 I-2 提及 `rate_limit_bucket` 同样"刻意不提供自动清理调度器"——说明本项目对"清理调度"持审慎态度）。无清理则 `idempotency_record` 随 Run 量线性增长，且过期的幂等键失去"防重放"意义却仍占空间。
- **方案设计**：
  1. **明确作用域语义**：`(tenant_id, key_namespace, idempotency_key)` 三元组（DDL:2549 注释"同键同摘要返回原 resource_id；同键异摘要返回冲突"）。`key_namespace` 区分"Run 创建幂等"与"工具调用幂等"等域，避免跨域撞键。
  2. **TTL 清理作业**（新增调度，参考既有 `rate_limit_bucket` 的 `index idx_rate_limit_cleanup` 思路，但本项**显式提供清理**）：
     ```sql
     -- V43__idempotency_cleanup.sql（清理函数 + 调度挂接点）
     CREATE OR REPLACE FUNCTION public.prune_expired_idempotency(p_batch int DEFAULT 1000)
     RETURNS int LANGUAGE plpgsql AS $$
     DECLARE n int;
     BEGIN
       DELETE FROM public.idempotency_record
       WHERE expires_at < now()
       ORDER BY expires_at
       LIMIT p_batch;
       GET DIAGNOSTICS n = ROW_COUNT;
       RETURN n;
     END; $$;
     ```
     调度层（现有 cron/调度口）按 `application.yml` 配置周期调用，如：
     ```
     agent.worker.idempotency.prune-cron: "0 0 3 * * *"   # 每日 03:00
     agent.worker.idempotency.prune-batch: "2000"
     agent.worker.idempotency.retention-days: "30"        # expires_at 据此生成
     ```
  3. **保留期口径**：`expires_at` 生成处统一用 `now() + retention_days`；保留期建议 ≥ 业务最大重试窗口（Stripe 为 24h，本项目按租户/场景可配，默认 30 天覆盖长链路重试）。
- **预期收益**：`idempotency_record` 体积可控、查询（按 tenant+key 查重）不随历史无限变慢；可度量：清理作业跑后断言 `count(*) FROM idempotency_record WHERE expires_at < now() = 0`。
- **实施成本与风险**：改动面小（函数 + 配置 + 调度挂接）。风险：清理必须与"在途 Run 仍需幂等"对齐——保留期须 > 最长在途 Run 生命周期，否则在途 Run 重试时幂等键已清会"防重放失效"（虽仍有 `run_message.idem_key` 与 fencing 兜底）。须反向验证：缩短 retention 不破坏在途 Run 重试。
- **优先级**：P2。
- **验收门禁**：① `IdempotencyPruneIT`：插入 `expires_at=now()-1d` 的过期行 + `expires_at=now()+1d` 的有效行，跑 `prune_expired_idempotency` → 断言过期行被删、有效行保留；② 断言清理后同 key 重试在"保留期内"仍命中首次结果（插入有效行 → 模拟重试 → 返回首次 `resource_id`）；③ 调度配置缺失/非法时 fail-closed（不退回默认、不静默禁用，呼应铁律）。

### I-5：分区/归档治理——`run_event` / `outbox_event` / `audit_record` 的增长治理

- **问题陈述**：`run_event`（:2788）、`outbox_event`（:2597）、`audit_record`（:1488，不可变）三者随 Run 量**单调增长**。`outbox_event` 终态后理论可删（但当前仅标 `PUBLISHED` 不删，见 microservices.io 指出"outbox 行增长需归档/删除作业"）；`run_event`/`audit_record` 为审计事实，不可物理删（铁律 8"无物理删除端点"），只能归档。**无分区/归档则查询随历史无限变慢、存储无界**。
- **方案设计**（分区 + 保留策略，严守铁律 8）：
  1. **`outbox_event` 清理**（可物理删，非审计）：终态（`PUBLISHED`/`FAILED` 且已超过宽限）行由清理作业删（参照 I-4 的 `prune` 函数范式）。保留近期用于"重投去重窗口"。
     ```sql
     -- V44__outbox_prune.sql
     CREATE OR REPLACE FUNCTION public.prune_published_outbox(p_older_than timestamptz, p_batch int DEFAULT 5000)
     RETURNS int LANGUAGE plpgsql AS $$
     DECLARE n int;
     BEGIN
       DELETE FROM public.outbox_event
       WHERE state <> 'PENDING' AND published_at < p_older_than
       ORDER BY published_at LIMIT p_batch;
       GET DIAGNOSTICS n = ROW_COUNT; RETURN n;
     END; $$;
     ```
  2. **`run_event` / `audit_record` 分区 + 归档（不物理删）**：采用**按时间范围分区**（如月度 `PARTITION BY RANGE (created_at)`）。归档走"逻辑迁移到冷存/聚合表 + 原表按保留期截断旧分区"，**不使用物理 DELETE**（铁律 8：审计/事件只增不改、无物理删除端点；受控清理仅 `audit_record` 经 `erasure_certificate` 通道）。归档目标表 `run_event_archive` / `audit_record_archive` 同结构、同 RLS。
  3. **保留策略配置**：
     ```
     agent.worker.retention.run-event-days: "400"
     agent.worker.retention.audit-record-days: "1800"   # 合规审计更长
     agent.worker.retention.outbox-published-days: "7"
     ```
  4. **分区维护作业**：月度建新分区 + 旧分区归档/截断（归档表保留），由现有调度口周期执行。
- **预期收益**：查询延迟稳定（分区裁剪）、存储有界、合规审计仍可回溯；可度量：注入 >保留期的 `run_event` → 断言其已归档到 `run_event_archive` 且主表不可见（RLS 下）、`audit_record` 同理不丢。
- **实施成本与风险**：分区改造对既有表结构改动较大（需 `pg_partman` 或手工分区）；风险：归档不得破坏"不可变审计"语义（铁律 8）——故归档是**复制+标记**，非 DELETE；`erasure_certificate` 通道的受控清理独立于本项。
- **优先级**：P2/P3（治理，非阻塞）。
- **验收门禁**：① `OutboxPruneIT`：插入 `PUBLISHED` 且 `published_at < 宽限` 的行 → 跑 `prune_published_outbox` → 断言被删；`PENDING` 行不被删；② `RetentionArchiveIT`：构造超保留期 `run_event` → 跑归档作业 → 断言主表按 RLS 查不到、归档表可查（ tenant 内）；③ 断言 `audit_record` 归档**不丢失行数**（归档前后 `count` 一致，仅位置变化）；④ 反向验证：缩短保留期不误删在途 Run 的 `run_event`（在途 Run 的 event `created_at` 近，不受影响）。

### 7.6 改进项总览矩阵

| 编号 | 改进项 | 优先级 | 改动面 | 落地期 | 核心验收门禁（一句话） |
|---|---|---|---|---|---|
| I-1 | 真续跑（cursor 对齐 execution_snapshot） | P1 | run_step 加列 + 执行循环 + 恢复入口 | 近期 | kill 在 MODEL_CALLING 阶段 → 续跑不重发已完成子阶段、无重复 tool_operation |

| I-3 | 对账工作台（表/端点/UI/报表） | P2 | 新表 + 端点 + UI + 调度 | 中期 | UNKNOWN 自动 RECONCILED 比例；无幂等键进 PENDING 且预算仍 RESERVED=100% |

## 八、其他有价值的横向对比（避免维度内自闭）

### 8.1 与本项目其他维度的耦合与相互约束（≥2 条）

1. **↔ 维度 01 架构与编排**：本维度的"DB 权威源 + fencing + 不可变快照"**直接就是**维度 01 的承载体。改本维度（如把权威源从 DB 移到内存、把 fencing 换成裸锁）会直接破坏维度 01 的"崩了也不破不变量"优势。**约束**：任何本维度改动不得削弱 fencing/不可变快照保证（铁律 16：`run_step.state` 恒 RUNNING 语义不变）。
2. **↔ 维度 09 成本与预算控制**：`tool_operation.budget_reservation_id` 的"UNKNOWN 不释放预算"是账实相符的硬规则（D5/预算三律之三）。本维度若改 UNKNOWN 处置（如允许重放/自动释放），会直接破坏维度 09 的"不超发"优势。**约束**：UNKNOWN 处置必须与维度 09 预算闸门一致（铁律 8）。
3. **↔ 维度 11 可靠性**：`Outcome.UNKNOWN_RESULT → 丢弃` 与维度 11 的"UNKNOWN 转对账、绝不重放"同源。本维度的 UNKNOWN 对账逻辑若改，会直接破坏维度 11 的"防静默失真"优势。**约束**：UNKNOWN 处置必须与维度 11 对账通道一致（铁律 2/8）。
4. **↔ 维度 02 多租户隔离**：本维度所有事实表均挂 RLS（44 表 FORCE，维度 02 已证实）。引入 I-5 分区/归档时，分区表与归档表的 RLS 策略须同步挂（否则跨租户可见）。**约束**：任何新表/归档表须同步 `03_platform_roles.sql` 与 RLS（铁律 7）。

### 8.2 与非 agent 领域成熟做法的对照

- **金融/支付系统的 fencing token 与对账**：银行核心系统的"记账幂等 + 流水号单调递增拒绝旧批次 + 对账文件 + 差错处理"与本平台 `enforce_fencing_on_write` + `ToolOperationReconciliationService` 同构。可借鉴：支付系统的"挂账/冲正/转人工"范式，本平台 I-3 的对账工作台即落地此范式（差错交易挂账、可幂等交易自动冲正、不可幂等转人工）。
- **分布式系统的 durable execution（Temporal/AWS SWF/Azure Durable Functions）**：本平台的"DB 权威源 + 重读 + 租约 + fencing"正是 durable execution 思想的数据库内重实现，区别是本平台未提供 Temporal 式"Event History 全量重放 + 中途改状态续跑"——I-1（真续跑）即补此差距。可借鉴 Temporal 的"Activity 必须幂等"纪律（本平台 `ToolInvocationGate` 预算三律 + 幂等键已等价）。
- **消息中间件的 exactly-once 边界（Confluent/Kafka）**：Kafka 的 exactly-once 只覆盖自身处理内部，不含外部存储更新——这佐证本平台"at-least-once 投递 + DB 去重 + UNKNOWN 对账"的组合是跨进程副作用场景的**唯一可行**形态，而非保守。
- **合规领域的工作流引擎三要素（控制流/持久化/可观测）**：本平台对齐，但"控制流"表达弱（无可视化）。可借鉴 BPMN/Step Functions 的"可视化状态机 + ASL 声明"提升维度 6.2-C2 的调试体验（与维度 01 I-6 同源）。

### 8.3 反向思考：若从头重做本维度，我们会怎么设计？（诚实取舍）

- **仍保留**：DB 权威源 + 触发器状态机 + fencing + 不可变快照 + Outbox 同事务 + POISONED 事务——这六点是本平台相对竞品**唯一且正确**的差异化，重做不会丢。
- **会改变**：① 从第一天就提供"执行游标 cursor"（I-1），而非事后补"精确续跑"；② 一开始就把 `tool_operation` UNKNOWN 对账做成平台内建的自动差错处理服务 + 可视化工作台（I-3），而非依赖外部脚本；③ Outbox relay 一开始就设计成"polling + CDC 双通道可切换"（I-2），而非先 polling 后评估；④ 一开始就把 `idempotency_record` / `outbox_event` 的清理与分区纳入 schema（I-4/I-5），而非增长后治理。
- **诚实取舍**：即便重做，仍会牺牲"可视化 DSL 的轻开发体验 / time-travel 的交互调试"来换"强一致、强治理、防重复伤害"——这是本平台定位（生产多租户 SaaS 运行时）决定的，不是可妥协项。会保留"UNKNOWN 不重放"作为铁律（三难下的唯一正确解）。

## 九、对产品演进的启发

### 9.1 本维度支撑的产品能力（用户能感知什么）

- 用户能感知：**run 不会因平台崩溃而卡死或重复执行**（强可恢复性）；**多租户数据绝不串**（RLS 默认拒绝，维度 02）；**预算绝不超发、UNKNOWN 不偷偷释放**（账实相符）；**每次辅导的执行过程可复盘**（不可变 run_step/run_event/tool_operation）。
- 用户不能感知（当前短板）：time-travel 式交互调试；低延迟首响（受 200ms 轮询，I-2 缓解）；UNKNOWN 对账的可视化 SLA（I-3 补）；"精确续跑"的透明性（I-1 补）。

### 9.2 演进路线图（近/中/远三期，每期明确产出物与验收标准）

- **近期（P1–P2）**：交付 I-1（真续跑 cursor）、I-4（幂等键 TTL 清理）。**验收**："kill 在 MODEL_CALLING 阶段 → 续跑不重发已完成子阶段、无重复 tool_operation"；"过期幂等键被删、保留期内重试仍命中首次"。
- **中期（P2–P3）**：交付 I-3（对账工作台）、I-5（分区/归档）、I-2 CDC 评估/可选。**验收**："UNKNOWN 自动 RECONCILED 比例达标、无幂等键进 PENDING 且预算仍 RESERVED=100%"；"超期 run_event 归档不丢、outbox 终态清理、audit 不物理删"；"CDC P99<50ms 且 polling 兜底不退化"。
- **远期（P4，研究）**：I-2 CDC 全量落地（若评估通过）、time-travel 式调试预研（生产优先强一致，非必做）。**验收**：CDC 在生产稳定；调试预研产出设计文档 + 反向验证方案。

### 9.3 风险清单（做这一步可能踩的坑，关联本项目已知铁律）

1. **I-1 cursor 写入与步骤主写入不同事务** → 须同事务（铁律 11：事务内 SQL 失败禁 fail-soft 后 COMMIT）；否则 cursor 与实际完成态分叉。
2. **I-1 cursor 绕过 fencing** → 写 `run_step` 必带 `fencing_token`（铁律 2）；否则旧世代可改新世代 cursor。
3. **I-2 CDC 管道故障导致永久卡死** → 必须保留 polling 兜底（铁律 5 精神：双通道、采集不复用）；CDC 仅加速不替代。
4. **I-3 自动对账误判副作用已发生** → 仅命中幂等/业务唯一键才自动，否则人工（铁律 2：终态后禁补 attempt；铁律 8：UNKNOWN 绝不释放预算）。
5. **I-4 缩短保留期破坏在途 Run 重试** → 保留期须 > 最长在途 Run 生命周期；反向验证。
6. **I-5 归档物理删除 audit_record** → 严禁（铁律 8：无物理删除端点）；归档是复制+标记，受控清理仅走 `erasure_certificate`。
7. **任何新表/归档表漏挂 RLS** → 同步 `03_platform_roles.sql` 与 RLS 策略（铁律 7），否则跨租户可见。

### 9.4 一句话结论

**本平台在"状态持久化与可恢复性"维度以"DB 权威源 + 事件只唤醒 + 触发器级状态机 + fencing 防脑裂 + 不可变运行期快照 + UNKNOWN 转对账"的组合，换来了竞品普遍缺失的强一致、崩溃免疫、防重复伤害的生产级底座——代价是牺牲了 time-travel 的轻调试体验与精确续跑的当前缺口，这恰是多租户 SaaS 生产运行时"宁可重、不可乱、不可重复伤害"的自觉取舍，且两项缺口均有清晰可执行补强路径（I-1/I-3）。**

**理论出处的诚实标注**：
- Transactional Outbox 权威出处为 Chris Richardson *Microservices Patterns*（2018）与 microservices.io；"dual-write problem" 亦见于 AWS/Microsoft 云架构指南——均经 WebSearch 核实。
- Exactly-once 不可能性出自 Kleppmann *Designing Data-Intensive Applications*（O'Reilly, 2017）第 12 章；Confluent 工程博客明确"Kafka exactly-once 不含外部存储更新"——经核实。
- Fencing Token 出自 Kleppmann *DDIA* 第 8 章及博客 *"How to do distributed locking"*（2016）；底层 sequencer 思想源自 Chubby（Burrows 2006）——经核实。
- Durable Execution 取自 Temporal 官方文档（https://temporal.io/ 、docs.temporal.io/workflows）；"Activity 必须幂等"为 Temporal 明确要求——经核实。
- **未能核实/须降级标注**：`Idempotency-Key` **至今只是 IETF Internet-Draft（draft-ietf-httpapi-idempotency-key-header），不是 RFC**（datatracker 标注已过期）；本报告将其明确引用为 work-in-progress，未将其当作已冻结标准。Stripe 为最知名实现，但其实践不等同于标准。
- Saga 出自 Garcia-Molina & Salem *"Sagas"* SIGMOD 1987（pp.249–259，DOI 10.1145/38713.38742）——经核实。
- 「副作用不可幂等时的三难」为本报告基于上述 (2)(3)(4)(6) 的工程推导，非单一论文；其结论（UNKNOWN 必须不重放）由 Temporal/Confluent/Kleppmann 的"无全局事务下 at-least-once 不可避免 + Activity 须幂等"共同支撑。
