## 三、四项被推翻的结论（文档纠偏，逐条附证据）

### 3.1 RAG「配置漂移导致 ANN 退化」不是缺陷

报告 08 建议「把 `application.yml` 与 DDL 对齐到 ≤4000 维 + 建 HNSW 索引」。源码与配置显示这是**已知且刻意**的取舍：

- `deploy/sql/rag/01_rag_ddl.sql:960-966`：
  > ⚠️ 本索引在 halfvec(4096) 下**刻意不存在**（2026-10-28 换真实嵌入模型）……当前语料量级（数百片段）下精确扫描既快又无召回损失；规模化后再二选一：MRL 截断到 ≤4000 维，或改用二进制量化。
- `rag.env:42-46`：注释「维度与向量列类型必须与库里实际形态一致（现为 halfvec(4096)）」+ 显式 4096 / halfvec。
- `VectorColumnTest` 断言 `new VectorColumn("halfvec", 4096).indexable()` 为 `false`。

**结论**：真正的待办不是「降维」，而是「规模化后按 DDL 注释二选一」。若按报告硬改，会与真实嵌入模型 `qwen3-embedding:8b` 输出维度冲突、并使已入库向量失效。

### 3.2 9 张无 RLS 表是影子期基线，不是漏洞

`AuthzShadowPolicyDefaults.java:23-30`：

> `platform.agent_trace_metric` …… 基线是 `NONE`（该表带 `tenant_id` 但**没有 RLS 策略**，属 D1 记的 9 张缺口之一）。缺口表的隔离**本来就只靠应用层 WHERE**，故期望值仍是 `TENANT_ONLY` —— 影子期正好用它来证明「应用层谓词确实在」。

同文件 `:108-124` 还为 `outbox_event` / `run_event` / `rate_limit_bucket` / `consent_withdrawal` / `erasure_certificate` 逐表登记了「SQL 全显式 tenant_id 谓词」的理由。既有 `ShadowPolicyCoverageTest`（新增资源类型不登记即红）与 `ScopeBypassArchitectureTest`（平台级豁免台账）是真正的门禁。

**结论**：直接补 RLS 会让「FORCE RLS 不绑租户删/查静默 0 行」（项目铁律 1）与影子期的应用层谓词验证同时失效。正确出口仍是 `rlsDependent=0` + 观察期达标（M4）。

### 3.3 `agent_trace_metric` 有完整运行期采集链

报告 10 称「7 列无写入方」。实际链路：

```
WorkerLoopConfig:288  traceCollectMessageHandler(AgentMetricCollector)
WorkerLoopConfig:311  traceMetricCollectorListener(AgentMetricCollector, ObjectMapper)
        ↓
AgentMetricCollector（agent-application）
        ↓
JdbcAgentMetricRepository.upsert()  :88  INSERT INTO platform.agent_trace_metric (...) ON CONFLICT (trace_id) DO UPDATE
```

`platform/platform-bootstrap/src/test/.../TraceCollectMessageHandlerTest`、`TraceMetricCollectorListenerTest`、`TraceCollectEndToEndIT`、`TraceMetricContentAccuracyIT` 均有覆盖。

**结论**：「无写入方」不成立。可能成立的是「个别派生列（如 `scenario`）在特定链路恒 NULL」——`CreateRunRequest.java:83` 确实记录了 `scenario` 恒 NULL 导致看板面板 13 只有「未标注」组，这是**字段填充缺口**，不是「表无写入方」。两者不可混为一谈。

### 3.4 Outbox 重复投递由消费端幂等真实承接

`RunDispatchConsumer.java:201-210`：

```java
Optional<RunClaimPort.LeasedTask> claimed =
        claimPort.claimSpecificRun(message.tenantId(), message.runId(), workerId, leaseDuration);
if (claimed.isEmpty()) {
    log.debug("消息重复（任务已被领取），丢弃: runId={}", message.runId());
    return ConsumeResult.DUPLICATE_DISCARDED;   // 丢弃而非重试
}
```

`deploy/sql/platform/01_platform_ddl.sql` 的 `outbox_event` 注释亦明写「重复投递由消费端幂等处理」。因此**无锁 SELECT 不是安全缺陷**，`FOR UPDATE SKIP LOCKED` 只是减少无谓重复投递的优化（且 `loadPendingOutbox` 以 `rollbackQuietly()` 结束，单纯 `FOR UPDATE` 锁窗口根本覆盖不到 `sender.send` 之后，加了也不解决问题）。

**真实存在的问题是账目失真**：两个发布实例各自 `send` 后都执行无条件的 `UPDATE ... SET state='PUBLISHED'`，都认为自己成功，`publishOnce()` 把重复发布也计为成功数。本次用**条件状态转换**修掉这一点，且不改 DDL/枚举/状态机：

```sql
UPDATE outbox_event
SET state = 'PUBLISHED', published_at = ?
WHERE tenant_id = ?::uuid AND outbox_id = ?::uuid
  AND state = 'PENDING'      -- 只有这次真正影响 1 行
```

`markOutboxPublished` 由 `void` 改为 `boolean`；`OutboxPublisher` 仅在 `true` 时计入成功数，`false` 时记 WARN 并 `return false`。**绝不走 `handleFailure`**——消息已成功发出，标 FAILED 会造成状态倒退与误告警。

> 诚实边界：本修复**不阻止重复投递**，只让「重复」可见且计数准确；去重仍由下游 `DUPLICATE_DISCARDED` 承接。
