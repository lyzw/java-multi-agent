admin-console 登录免租户（固定平台身份）规划

对齐《多级 Agent 优化》重规划 · 关于管理台如何认证、前后端接口与交互逻辑 · 草案 2026-10-25

结论先行： 推荐落地 方案 A（免租户登录）——前端不再要求输入租户 ID，后端按全局唯一的 loginName 反查并派生出权威 tenantId。该方案不触碰 TenantContext.tenantId 的 @NonNull 铁律，反而强化了「tenantId 只能从可信认证上下文推导」的红线（此前客户端还能自己传 tenantId）。
若确实需要「一个固定系统身份、不绑定任何业务租户」，再考虑 方案 B（哨兵租户 -1），但需额外处理 RLS 可见性。

1. 现状基线（必须尊重的硬约束）

约束来源对本次规划的含义
TenantContext.tenantId 为 @NonNull，构造时空值直接抛异常 core/tenant/TenantContext.java:33 「不传租户」≠「上下文无租户」。必须仍能解析出一个非空的、可信的 tenantId。
loginName 全局唯一（文档明文：登录名全局唯一） AuthController 注释（§3.2） 仅凭 loginName 即可唯一确定主体，tenantId 可被派生。
AuthenticationService.authenticate(tenantId, loginName, password) 按 (tenantId, loginName) 查 principal AuthenticationService.java:78 当前校验链路依赖 tenantId；免租户需新增按 loginName 全局查的路径。
PLATFORM_ADMIN 走带外 SQL 授予，且绑定到某个真实 tenant_id deploy/sql/platform/04_platform_admin_grant.sql 平台管理员本来就有一个 home tenantId（来自授予脚本的 -v tenant_id）。
前端 LoginRequest.tenantId 当前为必填（类型 + 表单） src/api/types.ts:5 / LoginPage.tsx:64 改为可选 / 删除即可，session 与 client.ts 已兼容「派生 tenantId」。
登录不区分失败原因、恒定耗时、无注册端点 AuthController 三条约束 免租户路径必须继承同样的枚举防护与恒定耗时。

2. 两条路线对比

维度方案 A · 免租户登录（推荐）方案 B · 固定哨兵租户 -1
登录时用户填什么只填 loginName + password只填 loginName + password（后端再绑定 -1）
tenantId 从哪来由后端从 principal 记录派生（其 home tenant）写死为哨兵常量 PLATFORM_TENANT_ID = "-1"
是否改动 TenantContext不改动（tenantId 仍非空）不改动，但要求 -1 在 tenant 表存在或仅用于平台端点
RLS / 自服务端点正常：自服务读「自己的租户」数据无误自服务读会落在 tenant_id='-1'，需隐藏自服务页或建伪租户
平台级端点（跨租户）经 PLATFORM_ADMIN 闸门，正常跨租户同左，但需保证平台端点不依赖 RLS 行级过滤
风险 / 工作量低 ~1 人日中 ~1.5–2 人日（含伪租户 + 导航收敛）
语义「我是某租户的成员，恰好也是平台管理员」「我就是这个平台的系统 Agent」

说明：方案 B 的「-1」本质上就是给平台操作员一个固定、不指向任何业务租户的身份。若贵方只有单一平台账号、且永远不需要自服务视图，B 可成立；否则 A 更稳。

3. 方案 A 详细设计（推荐落地）

3.1 后端接口变更

(1) AuthController.LoginRequest —— tenantId 改为可空，校验只要求 loginName+password：

// AuthController.java
public record LoginRequest(String tenantId, String loginName, String password) {
    boolean isComplete() {
        // ⚠️ tenantId 不再参与完整性判定（向后兼容：旧客户端仍可不传）
        return loginName != null && !loginName.isBlank()
            && password != null && !password.isEmpty();
    }
}

(2) AuthController.issueToken —— 按是否带 tenantId 分流：

// 带 tenantId → 旧路径；不带 → 全局按 loginName 派生
AuthResult result;
if (request.tenantId() != null && !request.tenantId().isBlank()) {
    result = authentication.authenticate(request.tenantId(), request.loginName(), request.password(), now);
} else {
    result = authentication.authenticateByLoginName(request.loginName(), request.password(), now);
}
if (!result.success()) return unauthorized();
// TokenResponse 结构不变：tenantId 来自派生结果，仍非空
return ResponseEntity.ok(new TokenResponse(
    result.token(), "Bearer", tokenTtlSeconds(),
    result.tenantId(), result.principalId(), result.roles()));

(3) AuthenticationService —— 新增按 loginName 全局反查的方法，复用既有常量耗时校验：

// AuthenticationService.java
public AuthResult authenticateByLoginName(String loginName, String rawPassword, Instant now) {
    Optional<PrincipalRepository.PrincipalRecord> found = principals.findByLoginNameGlobally(loginName);
    PrincipalRepository.PrincipalRecord record = found.orElse(null);
    // ⚠️ 无条件校验：record 为 null 走 dummy 哈希，耗时与命中路径一致（防枚举）
    boolean passwordOk = principals.verifyPassword(record, rawPassword, now);
    if (record == null || !passwordOk) {
        if (record != null) principals.recordFailure(record, now, maxFailedAttempts, lockDuration);
        return AuthResult.failure();
    }
    if (!"ACTIVE".equals(record.status()) && !"LOCKED".equals(record.status())) return AuthResult.failure();
    principals.recordSuccess(record, now);
    Set<String> roles = rolesOf(record);
    // ⚠️ tenantId 从记录派生（record.tenantId()），绝不取客户端值
    TenantContext context = new TenantContext(record.tenantId(), record.principalId(), roles, record.authzVersion());
    String token = tokens.issue(context, now);
    return AuthResult.success(token, record.principalId(), record.tenantId(), roles);
}

(4) PrincipalRepository —— 新增全局查：

// 仅按 login_name 唯一确定；依赖 DB 对 login_name 的全局唯一约束
Optional<PrincipalRecord> findByLoginNameGlobally(String loginName);

若 principal.login_name 当前仅在租户内唯一、未全局唯一，需补一个迁移：ADD CONSTRAINT uq_principal_login_name UNIQUE (login_name)（与 AuthController 的全局唯一前提对齐）。

3.2 前端接口变更

文件改动
src/api/types.tsLoginRequest.tenantId 改为可选：tenantId?: string（保留字段以兼容遗留）
src/pages/LoginPage.tsx删除 tenantId 的 Form.Item 与校验规则；onFinish 仅发送 { loginName, password }
src/api/adminApi.ts无需改（login() 直接 JSON.stringify(payload)，缺字段即不传）

要点：登录响应里的 tenantId 仍会被写入 StoredSession，自服务页（/admin/tenants/self）照常工作；平台页靠 roles 导航显隐。

3.3 交互逻辑（时序）

  1. 打开登录页：仅 loginName 与 password 两个输入。
  2. 提交：POST /api/auth/token，body 不含 tenantId。
  3. 后端：按全局唯一 loginName 查 principal（命中则取其 home tenantId），恒定耗时校验口令，签发 JWT。
  4. 前端：signIn 把回带的 tenantId/principalId/roles 写入 session。
  5. 导航：RequireRole 按 roles 显隐；自服务页用派生 tenantId 走 RLS；平台页经 PLATFORM_ADMIN 闸门跨租户。
  6. 401 兜底：client.ts 收到 401 即清 session 并跳登录（已有逻辑，零改动）。

4. 方案 B 详细设计（固定哨兵租户 -1，可选）

适用前提：管理台只做平台级运维、永远不需要「我的租户」自服务视图；且接受平台管理员是一个不指向任何业务租户的固定身份。

  1. 引入常量 PLATFORM_TENANT_ID = "-1"，并在 tenant 表插入一条 tenant_id='-1' 的伪租户（或约定平台端点不依赖 RLS）。
  2. 新增登录模式：POST /api/auth/token 支持 { "scope": "platform", "loginName", "password" }（或独立端点 /api/auth/token/platform）。
  3. 后端将该主体的 tenantId 强制绑定为 -1，并断言其含 PLATFORM_ADMIN；否则 403。
  4. 前端 navConfig.tsx 对平台身份收敛导航：隐藏「我的租户」「租户内主体」等自服务页，仅保留平台级页（租户注册表、平台能力发布、监控、审计）。
  5. RLS 注意：任何落到 tenant_id='-1' 的行级查询都会空结果。平台端点必须是 tenant 全局表或无 RLS 路径（现有 AdminTenantController 的 tenant 表已是全局表，可复用此范式）。

风险：若将来要给平台管理员一个「以某租户身份查看」的能力（如替某租户排查），B 反而要多做一套租户切换；A 天然支持。

6. 安全边界（不可妥协）

  • 保留 角色以库为准：JWT 声明里的角色只在 principal_role 登记后才生效（JwtTokenService.verify 取交集）。免租户不改这条。
  • 强化 tenantId 由后端派生后，客户端再也无法自填 tenantId——比现状更安全（现状允许客户端传任意 tenantId，虽不作为授权依据，但语义更脏）。
  • 保留 枚举防护与恒定耗时：authenticateByLoginName 必须走与现有路径一致的 dummy 哈希分支。
  • 保留 失败统一 401、不区分原因；审计留痕仍以 (tenantId, principalId) 记录（派生值同样可记）。
  • 保留 红线 9：执行时仍按后端重授权，前端 roles 仅用于导航显隐。

7. 对《多级 Agent 重规划》缺口的影响

重规划文档里的缺口 G-3（编排声明的子 Agent 候选列表未接，当前手填 id） 需要后端提供「按租户的 Agent 列表接口」。免租户登录后：

调用方身份候选列表接口应返回
平台管理员（方案 A，派生 home tenantId）建议支持 ?scope=platform 返回跨租户 Agent 列表；或按显式 tenantId 参数过滤
租户级用户返回该租户 Agent（走 RLS / 参数 tenantId）

即：子 Agent 候选列表端点要同时支持「租户作用域」与「平台作用域」，不能只返回调用方派生租户的数据，否则平台管理员在编排时看不到其他租户的候选 Agent。

9. 迁移与回滚

  • 向后兼容：tenantId 在请求侧改为可选，旧客户端/脚本继续传也不会坏。
  • DB 迁移：全局唯一约束为「收紧」型，需在迁移前确认无重复 login_name；若有，先以带外脚本归并。
  • 回滚：前端仅删一个表单字段 + 类型放宽，回退即恢复；后端新增方法不影响旧路径，可单独回滚。
