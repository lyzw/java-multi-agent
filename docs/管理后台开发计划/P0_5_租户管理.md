# W-ADMIN-P0.5 · 租户管理（M0）：生命周期、配置覆盖、主体角色与 RLS 隔离校验

> **阶段目标**：在 RLS 多租户地基上，为**平台运营者**提供跨租户的租户治理能力（M0）。注意平台没有跨租户身份（`principal` 为租户内），租户管理属 **PLATFORM 作用域**，必须经超级管理员 / 带外运维（BYPASSRLS）通道，与 `TENANT_ADMIN` 管理自身 Agent 的视角严格区分。  
> **设计文档落点**：§2.0 M0 租户管理、§5.4 租户生命周期、§5.5 租户隔离校验（RLS）、§6 `/api/admin/tenants/*` 端点、§9 租户管理作用域红线与 RLS 铁律。

---

## 0. 落地记录（2026-10-24）

> **状态**：✅ 后端 + 前端已落地并通过验证（编译 / 8 项后端单测 / 前端构建+单测）。
> **关键架构决定**：工程当前**无应用层超级管理员 / PLATFORM 作用域角色**（仅有租户内 `TENANT_ADMIN` 等）。
> `tenant` 表为**全局表、不启用 RLS**，故平台级租户读写在数据库层无需 BYPASSRLS——
> 安全性完全由**应用层 `PLATFORM_ADMIN` 作用域闸门**保证（默认拒绝 403）。
> 因此本阶段把平台级端点全部**就绪但锁定**：逻辑/数据访问已实现，仅当 `PLATFORM_ADMIN` 经平台运维通道授予后才解锁；
> 同时提供**租户内「我的租户」自服务视图**，当前即可用（任意已认证租户主体）。

### 0.1 后端（`platform/agent-api` 内扩展，不新建工程）

## 1. 目标与范围

| 范围 | 内容 |
|---|---|
| 后端 | 在共享后端 `platform/agent-api` 内扩展（**不新建独立后端工程**）：`AdminTenantController`（GET 列表/详情/覆盖/主体；PUT 覆盖与主体角色需超级管理员作用域）、`AdminTenantService`（只读聚合 + 编排）；`/tenants/:id/rls-verify`（POST，非特权 `app_agent` 账号执行隔离校验） |
| 复用 | 直接读 `tenant` / `principal` / `tenant_config_override` / `cap_authz_version`；配置覆盖语义复用 `EffectiveConfigResolver` 的收紧棘轮；主体角色变更与 authz 自增须在**同一事务** |
| 前端（独立工程） | `/tenants` 路由：列表、开通、详情（概览/覆盖/主体/资源/发布）、编辑启停、配置覆盖对比、主体与角色、RLS 隔离校验 |
| 作用域红线 | 写操作仅由超级管理员经运维通道访问；普通 `TENANT_ADMIN` 不可见跨租户写入口（前端依据后端返回的角色/作用域条件渲染，后端显式 403——安全判定一律在后端） |
| 不在此阶段 | 真实实体 CRUD、发布工作流 UI（留 P1/P2） |

## 6. 风险与回滚

| 风险 | 缓解 / 回滚 |
|---|---|
| 租户管理写入口经普通租户身份暴露 | 后端写端点强制超级管理员作用域 403；前端按角色/作用域条件渲染（双重闸门，P0.5-T5） |
| 配置覆盖放宽绕过棘轮 | 复用 `EffectiveConfigResolver` + 前端实时校验，放宽即拒 |
| RLS 校验用特权账号致结论不可信 | 强制非特权 `app_agent` + `set_config` 事务内（P0.5-T4） |
| 角色变更与 authz 自增跨事务竞态 | 同事务提交；IT 注入并发角色变更验证单调 |
