admin-console 独立后台用户体系重规划（v2）

把管理后台的运维身份与「租户用户体系」彻底解耦 —— 引入独立的 platform_operator 身份域

文档版本 v2 · 2026-10-25 · 取代《admin-console-登录免租户规划.html》（v1）
前置依据：00_修订说明与评审决议项.md · 已读码确认的架构（见 §1 约束清单）

与 v1 的关系： v1 提出「免租户登录 / 固定哨兵租户 -1」，本质仍是复用租户用户体系（从 loginName 反查 tenantId 再派生上下文）。 本版（v2）按用户最新要求转向：后台用一套完全不同的用户系统维护，与租户主体表 principal 物理隔离、互不信任、互不越界。 v1 的派生 tenantId 思路作废；本文给出 v2 的完整接口与交互逻辑。

1. 已读码确认的五条硬约束

以下结论来自实际源码，决定了方案走向，非假设：

#事实（源文件）对方案的含义
C1 TenantContext.tenantId 为 @NonNull，空值直接抛异常（core/tenant/TenantContext.java:34）。每个主体都是 (tenantId, principalId)。 「无租户」不能是「上下文无租户」。平台操作员也须解析出可信的 tenantId，但可用哨兵值表示「非租户主体」。
C2 JWT 当前声明仅 iss/sub/aud/iat/exp/jti/tenant_id/roles/authz_version，无身份域字段（JwtTokenService.issue/verify）。 需新增 domain 声明（TENANT / PLATFORM）来区分两套身份体系。
C3 已存在 BYPASSRLS 平台运维数据源 PlatformOpsDataSourceProvider + GuardedPlatformOpsDataSource + PlatformOpsSessionGuard，仅限 PLATFORM 作用域发布事务内交出连接。 平台级写入已有现成越权通道；后台操作员身份可复用其「平台身份」语义，但读路径仍需按目标租户绑定（见 C5）。
C4 租户主体表 principal(principal_id, tenant_id NOT NULL, ...) 与 principal_role 均 FORCE ROW LEVEL SECURITY（01_platform_ddl.sql:1641/1677）。全局表 tenant 无 RLS（AdminTenantRepository 注释）。 新后台身份表应仿照 tenant：全局、不挂 RLS，从而无需在每次登录读时绑定租户上下文。
C5 后台跨租户读（如 listPrincipals(id)）通过 openTenant(目标租户id) 把连接绑定到目标租户的 RLS 上下文，而非操作员的自身租户（AdminTenantRepository:288）。 数据访问层几乎无需改动：操作员自身的 tenantId 哨兵值不参与跨租户读取，读取仍以路径参数里的目标租户为准。

2. 架构总览：两套用户体系

两套体系共享同一后端与同一套 JWT 验签基础设施，靠 domain 声明在「可信上下文」层分流；数据库层靠 物理分表（principal vs platform_operator）与 RLS 策略双重隔离。

3. 身份域模型对比

维度域 T · 租户用户（既有）域 P · 后台操作员（新增）
登录端点POST /api/auth/tokenPOST /api/console/auth/login
存储表principal + principal_role（RLS 强制）platform_operator（全局、无 RLS）
是否含 tenant_id必填、NOT NULL无（平台级身份，不属于任何租户）
JWT domain 声明TENANTPLATFORM
上下文 tenantId真实租户 UUID哨兵 __platform__（永不匹配真实租户）
数据访问连接绑定自身租户 RLS跨租户读 openTenant(目标租户)；平台写经 PlatformOpsSessionGuard
授权闸门租户内角色 + 红线9 重授权requirePlatformScope()：domain==PLATFORM 且含 PLATFORM_ADMIN
使用的前端面向师生的主应用（非 admin-console）admin-console（/admin）专用
关键边界：admin-console 自 v2 起只接受域 P 令牌。即使某租户主体持有 PLATFORM_ADMIN，其域 T 令牌也无法进入后台（守卫要求 domain==PLATFORM）。租户用户体系与后台运维体系在登录入口即分叉，互不越界。

4. 后端设计

4.1 数据库：新增 platform_operator 表（DDL 增量）

CREATE TABLE public.platform_operator (
    operator_id   uuid DEFAULT gen_random_uuid() NOT NULL,
    login_name    text NOT NULL,
    password_hash text NOT NULL,
    display_name  text,
    status        text DEFAULT 'ACTIVE' NOT NULL,
    failed_attempts integer DEFAULT 0 NOT NULL,
    locked_until  timestamp with time zone,
    authz_version bigint DEFAULT 1 NOT NULL,
    created_at    timestamp with time zone DEFAULT now() NOT NULL,
    updated_at    timestamp with time zone DEFAULT now() NOT NULL,
    CONSTRAINT platform_operator_pk PRIMARY KEY (operator_id),
    CONSTRAINT platform_operator_login_unique UNIQUE (login_name),
    CONSTRAINT platform_operator_login_format
        CHECK (login_name ~ '^[a-z0-9][a-z0-9._-]{2,63}$'),
    CONSTRAINT platform_operator_hash_present
        CHECK (password_hash ~~ '$pbkdf2-sha256$i=%$%'),
    CONSTRAINT platform_operator_status_enum
        CHECK (status = ANY (ARRAY['ACTIVE','DISABLED','LOCKED'])),
    CONSTRAINT platform_operator_authz_positive CHECK (authz_version >= 1)
);
-- 刻意不 FORCE ROW LEVEL SECURITY：该表是平台级身份，无租户维度；
-- 仿 tenant 表，登录读路径用系统身份(openSystem)而非租户绑定。

CREATE TABLE public.platform_operator_role (
    operator_id uuid NOT NULL REFERENCES platform_operator(operator_id),
    role        text NOT NULL,
    granted_at  timestamp with time zone DEFAULT now() NOT NULL,
    CONSTRAINT platform_operator_role_role_fmt CHECK (role ~ '^PLATFORM_[A-Z_]{1,28}$')
);

角色名强制 PLATFORM_* 前缀，从源头杜绝把租户角色错挂到平台身份上。

4.2 新增 PlatformOperatorRepository

复用既有 PasswordHasher（PBKDF2 600k 迭代，常量耗时、防枚举、防爆破、rehash-on-success）。 与 PrincipalRepository 唯一区别：登录读走 TenantSessionBinder.clear(conn)（系统身份，不绑定任何租户），因 platform_operator 无 RLS。提供：findByLoginName / verifyPassword / findRoles / recordFailure / recordSuccess / revokeAuthorization（与现有接口同构，照搬安全注释与 dummy-hash 逻辑）。

4.3 新增 PlatformOperatorAuthenticationService

与 AuthenticationService 同构，但使用 PlatformOperatorRepository，并签发带 domain=PLATFORM 的令牌。保持三条铁律：不区分失败原因、恒定耗时、失败计数持久化。

4.4 改造 TenantContext 与 JwtTokenService（最小侵入）

TenantContext 增加字段 IDENTITY_DOMAIN domain（枚举 TENANT / PLATFORM，缺省 TENANT），并新增工厂：

public static TenantContext platformOperator(String operatorId,
        Set<String> roles, long authzVersion) {
    return new TenantContext("__platform__", operatorId, roles, authzVersion,
            IDENTITY_DOMAIN.PLATFORM);
}

JwtTokenService.issue() 在 payload 增加 "domain":"<domain>"；verify() 读取 domain 声明并据此构造 TenantContext（缺省 TENANT 以向后兼容既有租户令牌）。既有租户令牌无需重签。

4.5 新登录端点 /api/console/auth/login

POST /api/console/auth/login
{ "loginName": "ops-zhang", "password": "***" }   // 无 tenantId
→ 200 { accessToken, tokenType:"Bearer", expiresIn:900,
        operatorId, roles:[ "PLATFORM_ADMIN" ], domain:"PLATFORM" }
→ 401 { "error":"unauthorized" }   // 统一，不区分原因

加入 SecurityConfiguration.PUBLIC_ENDPOINTS。响应不返回 tenantId（哨兵值无业务意义），不返回任何凭据字段。

4.6 控制器守卫改造 requirePlatformScope()

所有后台平台级端点（AdminTenantController 的 /、/{id}、/{id}/principals、rls-verify，以及 P0–P5 的管理端点）统一改为：

private void requirePlatformScope() {
    TenantContext ctx = currentPrincipal.context();
    if (ctx.domain() != IDENTITY_DOMAIN.PLATFORM
            || !ctx.hasRole("PLATFORM_ADMIN")) {
        throw new ResponseStatusException(FORBIDDEN,
            "后台运维仅限 PLATFORM 域操作员");
    }
}

跨租户读取逻辑（openTenant(目标租户id)）保持不变 —— 操作员自身哨兵 tenantId 不参与读取，读取仍以路径里的目标租户为准（满足约束 C5）。

4.7 RLS 与数据访问影响评估

访问类型是否需要改说明
操作员登录读 platform_operator新增走 openSystem（clear 上下文），表无 RLS，正常读
后台列租户 tenant 表不改全局表无 RLS，域 P 与域 T 同路径
后台跨租户读 principal/agent不改仍 openTenant(目标租户)，与操作员自身租户无关
PLATFORM 作用域配置发布写不改仍经 PlatformOpsSessionGuard
/self 租户内自服务前端隐藏仅域 T 有意义，后台操作员不应见（见 §5.3）

5. 前端 admin-console 设计

5.1 登录页（仅操作员）

移除「租户 ID」输入框与 tenantId 字段，仅保留 loginName + password，POST 到 /api/console/auth/login。session.tsx 把响应里的 domain 一并持久化（localStorage / 内存）。

5.2 类型与请求层

// src/api/types.ts
export interface LoginRequest { loginName: string; password: string }   // 去掉 tenantId
export interface TokenResponse {
  accessToken: string; tokenType: string; expiresIn: number;
  operatorId?: string; roles: string[]; domain: "TENANT" | "PLATFORM";
}
// src/api/adminApi.ts / client.ts
const resp = await client.post("/api/console/auth/login", { loginName, password });

5.3 路由与导航按 domain 分流

  • RequireAuth：仅校验 token 存在 → 零改动。
  • RequireRole：校验 roles → 零改动（域 P 角色是 PLATFORM_*）。
  • 新增 useDomain()：从 session 取 domain。
  • 导航显隐：domain==="PLATFORM" 时隐藏租户自服务页（/tenants/self、/agents/self 等），展示平台级导航（租户注册表、跨租户主体、配置发布、监控）。
  • 401（token 失效/域不符）→ 自动跳登录页。守卫在后端硬拒绝域 T 令牌，前端无需额外判断。
为何前端无需感知租户选择：后台操作员经 openTenant(目标租户) 显式指定目标租户，所有跨租户操作都在请求路径/参数里带目标租户 id（与现在一致），前端不必维护「当前租户」概念。

7. 向后兼容与迁移

  • 既有租户令牌零失效：JwtTokenService.verify 对缺省 domain 声明按 TENANT 处理，旧令牌继续可用。
  • 旧 PLATFORM_ADMIN 越权授权路径：当前 04_platform_admin_grant.sql 把 PLATFORM_ADMIN 授予某租户主体（域 T）。迁移期：requirePlatformScope() 同时接受 domain==PLATFORM 或 domain==TENANT 且 hasRole(PLATFORM_ADMIN)；待 platform_operator 账户建好后，删除该 SQL、显式撤销租户主体上的 PLATFORM_ADMIN，关闭域 T 进入后台的口子。
  • 操作员开通：新增 05_platform_operator_seed.sql（带外运维通道），插入首名 platform_operator + PLATFORM_ADMIN 角色，口令走受控发号（同租户主体，无自助注册）。
  • admin-console 部署：已是独立 SPA（/admin 同源反向代理），无需新建工程；仅改登录入口与路由显隐。

8. 安全边界与风险登记

风险等级处置
操作员账户被爆破（高价值目标）高 复用 PBKDF2 600k + 持久化失败计数 + 锁定；口令经受控发号；后续可加 MFA（platform_operator.mfa_secret 预留列）。
域 P 令牌误用于租户业务接口中 业务接口按 tenantId RLS 访问，哨兵 __platform__ 不匹配任何租户 → 0 行；且租户接口无 PLATFORM_ADMIN 语义。纵深防御成立。
误把平台身份接上租户 RLS 读路径中 platform_operator 表不挂 RLS，登录读走 openSystem；且 requirePlatformScope 强制 domain==PLATFORM。
迁移期双路径（域T持PLATFORM_ADMIN）残留中 设明确关闭清单：删 04 SQL + 撤销租户主体角色 + 守卫移除兼容分支；纳入退出门禁。
JWT domain 声明被伪造低 RS256 验签 + iss/aud 校验；domain 与 roles 同属签名载荷，伪造即验签失败。

9. 验收矩阵

项验收标准
隔离性域 T 令牌（含旧 PLATFORM_ADMIN）调用 POST /api/console/auth/login 失败；域 P 令牌访问租户业务接口返回 0 行或 403。
操作员登录/api/console/auth/login 成功返回 domain=PLATFORM；失败统一 401 不区分原因；错误口令不计入不存在账号。
跨租户读操作员列任意租户主体/agent 成功；verifyIsolation 对目标租户仍可判定隔离。
守卫域 P 但缺 PLATFORM_ADMIN → 403；域 T → 403。
前端登录页无租户字段；domain==PLATFORM 时自服务页隐藏；401 跳登录。
回归既有租户令牌登录主应用、RLS 读本租户数据全部不变；单测/IT 零回归。
