## 2. 缺陷①：未映射路径 500 → 404

### 2.1 现象与根因

Spring 6+ 起，请求路径未映射到任何 `@RequestMapping`（且不匹配静态资源）时抛
`org.springframework.web.servlet.resource.NoResourceFoundException`，Spring 默认映射为 **404**。

但 `ApiExceptionHandler` 的兜底 `@ExceptionHandler(Exception.class)`
**优先于** Spring 内置的 `DefaultHandlerExceptionResolver`，
于是未映射路径被**吞成 500**。

这与 P4-D09 已修的 `ResponseStatusException` 属**同族缺陷**（本类 Javadoc 中已记录该族的三重危害）：
状态码语义反转（客户端无法区分「路径写错」与「服务端故障」，会做出**完全相反**的重试决策）、
破坏存在性探测纪律、监控污染（用户笔误被计入服务端错误率）。

### 2.2 修复

`platform/agent-api/src/main/java/cn/studykid/multiagent/api/error/ApiExceptionHandler.java`
新增专用处理器（比兜底处理器更具体，Spring 按最具体匹配优先）：

```java
@ExceptionHandler(org.springframework.web.servlet.resource.NoResourceFoundException.class)
public ResponseEntity<ErrorResponse> handleNoResourceFound(
        org.springframework.web.servlet.resource.NoResourceFoundException e) {
    // ⚠️ 不回显 e.getMessage()：它含请求路径原文（可能含客户端数据）
    log.info("请求路径未映射到任何端点: path={}", e.getResourcePath());
    return ResponseEntity.status(HttpStatus.NOT_FOUND)
            .body(new ErrorResponse(codeOf(HttpStatus.NOT_FOUND), messageOf(HttpStatus.NOT_FOUND)));
}
```

归一化口径：`code=NOT_FOUND` / `message=资源不存在` —— 与「已映射但资源不存在」的
`ResponseStatusException` 分支**同码同文案**，两类「不存在」在客户端侧不再分叉。

### 2.3 证伪矩阵（回归测试在**修复前**必须红）

| 测试 | 位置 | 修复前 | 修复后 |
|---|---|---|---|
| `NotFoundMappingIT.unmappedPathReturns404` | `platform/platform-bootstrap/src/test/.../NotFoundMappingIT.java` | ❌ `expected:<404> but was:<500>` | ✅ |
| `NotFoundMappingIT.unmappedActuatorPathReturns404` | 同上 | ❌ 500 | ✅ |
| `NotFoundMappingIT.unmappedPathReturnsNormalizedJsonBody` | 同上 | ❌ 500 | ✅ |
| `NotFoundMappingIT.unmappedPathAndMissingResourceShareSameCode` | 同上 | ❌ 500 | ✅ |
| `ApiExceptionHandlerTest`（5 项） | `platform/agent-api/src/test/.../error/ApiExceptionHandlerTest.java` | ⚠️ 编译不过（方法尚不存在） | ✅ |

> ⚠️ **为什么必须有真实 HTTP 的 IT**：`*@ExceptionHandler` 的**选路优先级**（最具体匹配优先于 `Exception.class`）属 Spring 框架行为，处理器自身的单元测试证明不了。
> 同时安全链是 `anyRequest().authenticated()`，**无令牌的请求在到达 DispatcherServlet 之前就被 401 拦下**，根本走不到路径映射逻辑 —— 故 IT 必须带有效令牌，否则测到的是认证链。

## 3. 缺陷②：经 API 发布的 Agent 永远不可运行

### 3.1 根因

`JdbcExecutionSnapshotResolver` 的解析 SQL 是三表**内连接**：

```sql
SELECT es.snapshot_id::text
FROM agent a
JOIN agent_version v  ON v.agent_id = a.agent_id AND v.tenant_id = a.tenant_id
JOIN execution_snapshot es ON es.version_id = v.version_id AND es.tenant_id = v.tenant_id
WHERE a.tenant_id = ?::uuid AND a.agent_id = ?::uuid
  AND v.published_at IS NOT NULL
ORDER BY v.version_number DESC LIMIT 1
```

**没有快照 = 内连接查不到 = 该 Agent 永远不可运行**（`POST /api/runs` → 404 `AGENT_SNAPSHOT_UNAVAILABLE`）。

而勘察发现：**此前没有任何生产代码路径创建 `execution_snapshot`** —— 只有种子脚本 `V1_seed.sql` 会建。
即：经 API 发布的 Agent 一律不可运行。

⚠️ **症状离真因极远**：报错点在「创建 Run」处，真因在「发布 Agent」处；
且既有测试**全绿** —— 因为所有 IT 的夹具都是**手工插** `execution_snapshot`，
「发布 → 运行」这条真实链路从未被任何 IT 覆盖过。

### 3.2 修复

`platform/agent-infrastructure/src/main/java/cn/studykid/multiagent/infrastructure/persistence/JdbcAgentManageRepository.java`
的 `publishVersion` 在**版本行插入之后、`conn.commit()` 之前**调用新增私有方法 `createExecutionSnapshot(...)`。

⚠️ **必须与版本行同事务**：快照与版本是同一个发布事实的两面；
分开提交会出现「版本已发布但无快照」的中间态 —— 那正是本缺陷本身。

内容口径：

| 列 | 取值 | 理由 |
|---|---|---|
| `agent_config` | 该版本的 `definition`（PG 规范化后的原文） | 快照自解释；为后续「读路径切到 `cap_agent_def`」保留对照基准 |
| `prompt_config` | `{}` | 尚无权威模型，**不自创契约** |
| `tool_contracts` | `{}` | 同上 |
| `run_config` | `{"maxCostPerRun":"2.00","maxLlmCalls":12,"maxSteps":20,"approvalRequired":"OPTIONAL"}` | DEC-9 运行期容量配置档，取值与 `application.yml` 的 `agent.run.*` 默认值一致，与种子脚本形态一致 |

⚠️ `run_config` 取的是**平台默认档**，不是「该租户当时的生效值」——运行期当前不消费该列（读路径未接线）；
待「Run 创建时固化生效配置」落地后，须改为读取该租户当时的实际生效值。

## 4. ⛔ 未解决：CAP 新模型链的读路径切换（阶段级任务，如实登记）

本轮修复的是**旧模型链的自洽性**。CAP 新模型链**仍未打通**：

| 项 | 现状 |
|---|---|
| `execution_capability_snapshot` | **0 行**（生产环境从不写入；只有种子脚本造） |
| 唯一写者 `CapDualWriteService.onExecutionSnapshotCreated` | **无任何生产调用方** |
| `cap_authz_version` | 本地库**无 `worker` 行**（准入比对用 worker 主体的 authz_version） |
| 开关 `config.flag.cap-authorization-enforced` | 默认 false；一旦置 true → **100% fail-closed 拒绝**（准入比对必然失配） |

**开启 CAP 授权链所需的前置条件**（属阶段级任务，不在本轮范围）：
1. worker 主体的 `cap_authz_version` 初始化；
2. Run 维度 `execution_capability_snapshot` 的写入；
3. P0 §3.3 第 5 步的**读路径切换**（`cap_agent_def` → `agent_version` 的反向投影 / 新→旧双写）。

⚠️ **不做「假装修好」**：本轮不新增未经真实数据验证的双写开关默认值，也不把「旧链能跑」写成「CAP 链已通」。

## 5. 缺陷③：platform-bootstrap IT 管理员连接池永久泄漏

### 5.1 现象

本轮修复后的**第一次全量构建**在 `ConfigEndpointIT` 处整体失败（4 项 ERROR）：

```
Caused by: ... Error creating bean with name 'retentionJob' ...
  解析租户 slug 失败（fail-closed）: slug=t-a →
  SQL 异常 [53300] FATAL: remaining connection slots are reserved for roles with the SUPERUSER attribute
```

### 5.2 根因（两层叠加）

1. **JUnit 默认每个测试方法新建一个测试类实例** → `private HikariDataSource adminPool` 是**实例字段**，
   「每个方法都是 null」→ **每个测试方法都新建一个连接池**；
2. Hikari 的 `minimumIdle` **默认等于** `maximumPoolSize`（此处 2）→ 每个池常驻 2 条连接；
   而池**从不关闭** → 连接**永不归还**。

实测：platform-bootstrap 的 failsafe 阶段在 2 秒内创建了 **54 个池**、只关闭了 5 个；
PG 侧 `pg_stat_activity` 达 **99 条**（全部为超管 `agent` 身份）→ 打满 `max_connections=100`
→ **普通角色 `app_agent` 无连接可用** → 后续 IT 类的 Spring 上下文启动失败。

⚠️ **报错点与真因相隔一个类**（真因在 `GovernanceEndpointIT` 等类的池泄漏，报错在 `ConfigEndpointIT` 的上下文启动），
且 PostgreSQL 把**连接槽位优先留给超管** —— 泄漏者正是超管，被拒者却是普通角色，故障现场极具误导性。

### 5.3 修复

对 platform-bootstrap 的 5 个 IT 类统一收口（`AgentEndpointIT` / `ConfigOverrideEndpointIT` /
`GovernanceEndpointIT` / `RunCreationEndpointIT` / `PlatformSecurityE2ETest`），
外加本轮新增的 `NotFoundMappingIT`：

1. 管理员池改为 **`private static`**（生命周期跨测试方法）；
2. 新增 **`@AfterAll` 关闭池**（static 只把泄漏从「每方法一个」降到「每类一个」，**不关闭则泄漏依旧**）。

> ⚠️ 只做其中一项都无效：两个动作缺一不可。
> 该模式与 `agent-infrastructure` 侧既有做法一致（其 IT 类本就使用 `private static HikariDataSource` + `@AfterAll` 关闭）。

### 5.4 效果

| 指标 | 修复前 | 修复后 |
|---|---|---|
| PG `pg_stat_activity` 连接峰值 | **99** | **10** |
| `ConfigEndpointIT` | ❌ 4 项 ERROR（上下文启动失败） | ✅ 4 项通过 |
