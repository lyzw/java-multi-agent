## 2. 已修复项

### 2.1 分数门禁标定：`0.2 → 0.38`

**现象**：换上真实嵌入模型后，一组完全无关的查询（`李白 静夜思`、`篮球 NBA 总决赛`）
照样能召回 top1，分数 0.31–0.41；而相关查询的正例中位是 0.50。
门禁设在 0.2，等于**没有任何门禁**——「找不到依据」这条合法输出永远不会触发，
RAG 会拿着一堆不相干的片段继续生成（RAG-D05 §⑦ 想防的正是这个）。

**标定方法**（`/tmp/calib.py`，可重跑）：16 条正例（答案确在两册里，逐条对过页码）
+ 8 条**近邻负例**（同是英语、同类教材体裁，但两册里没有：`photosynthesis chloroplast`、
`past continuous tense`…）+ 10 条**远域负例**（数学/语文/历史/体育），
`topK=10` 全量跑一遍，记录每条命中的相关性分。

**分布**：

| 档位 | 命中数 | min | p25 | 中位 | p75 | max |
|---|---|---|---|---|---|---|
| 正例 | 66 | 0.390 | 0.465 | **0.504** | 0.534 | 0.689 |
| 近邻负例 | 32 | 0.387 | 0.399 | 0.413 | 0.473 | **0.525** |
| 远域负例 | 27 | 0.306 | 0.327 | 0.339 | 0.366 | 0.411 |

**阈值扫描**（保留多少正例命中 / 放过多少负例命中）：

```
min-score  正例保留   近邻漏过   远域漏过
  0.20      66/66     32/32     27/27      ← 现状：门禁完全不做事
  0.38      66/66      32/32      3/27     ← 选它：正例零损失
  0.42      60/66      14/32      0/27
  0.45      53/66       8/32      0/27
  0.48      42/66       5/32      0/27
```

**结论与取值**：默认值改为 **0.38**（`application.yml:63` 与 `RagInfrastructureConfig:56`
与 `RagInfrastructureConfig` 的 `@Value` 兜底同源）。理由：它是「远域噪声基本消失
（27 条里只剩 3 条）而正例一条没丢」的第一个阈值；再往上是**拿正例换负例**，
换不动——近邻负例的 max（0.525）已经高于正例的 p25（0.465），
分数门禁在原理上就分不开这一类（见 §4.1 与 §4.3）。

**⚠️ 推翻旧结论**：本轮之前我给过一个「经验可用区间约 0.45–0.48」的说法，
那是**4 条查询**的样本外推，错了 0.07 左右——按它设阈值会白白砍掉约 20% 的真召回
（0.48 时正例只剩 42/66）。以 §2.1 的 34 条为准。

**复现**：
```bash
/tmp/tok.sh && python3 /tmp/calib.py     # 需 8081 在线、两册已 VERIFIED
```

### 2.2 附录词表按单元重切片

**现象**：学生问「六年级上册第五单元的单词」。Unit 5 的词表实际印在**附录**，
而附录是按页切片的：p.134 那一片 1649 字里同时含 Unit 1/2/3 的词，
p.137 一片里混着 Unit 4/5/6，`section_path` 只能标成一个笼统的「附录」，
`kp_ids='{}'`。这一片的向量被几个单元的词共同拉扯，
「Unit 5」这个信号在 1900 字里被稀释到召不出来（实测：两种 topK 均 0 命中）。

**根因**：切分粒度按**印刷页**，而词表的逻辑单位是**单元**——两者不同构。
换更强的嵌入模型**不能**替代重切片：模型再准，也只是把「混了四个单元的一整页」
表征得更准一点而已，它仍然是那一页的表征。

**处置**（`scripts/rag_import_pdf.py`）：
1. 附录区新增 `appendix_pieces()` 状态机：进入
   `Words and expressions in each unit` 后按 `Unit N` / `Starter` 边界切；
   **续页不重复单元标题**，所以当前单元跨页携带（记在 `state` 里），
   整页归给上一页留下的那个单元；遇到字母序词表或其它栏目标题即退出。
2. 每个片段开头补一行**中英双形**标题：`Unit 5（第五单元）单词表：…`。
   这是「第五单元」这种中文问法目前唯一的桥梁——不需要额外别名表。
3. `section_path` 从「附录」细化为 `Unit 5 Animals and us 词表` / `附录 · 语法` /
   `附录 · 注释`（栏目名按特异性排序匹配，否则「Notes: …」会把拼写规则页错标成注释）。
4. 封底/版权页（`定价：18.90元`、`本套教材根据…编写`）不再入语料：
   整页只有一句出版信息，**却能在检索里拿到 top1**（本轮实测的直接起因）。
5. 片段 INSERT 从 `ON CONFLICT DO NOTHING` 改为 `DO UPDATE`，
   并把 `text_jieba` 清成 `''`——这是**功能性**的：
   `ChunkIndexer.PENDING_SQL` 的待索引判据是 `text_jieba='' OR 无向量行`，
   不清它，改了正文的片段永远不会重新嵌入，表现为「改了脚本但检索没变」的假象。

**结果**：两册 287 片段，词表切出 22 片（每册 11 片，覆盖 Starter + Unit 1~6），
附录整页碎片从 45/43 片变为 48/46 片，正文内容零丢失
（附录区字符量 45023→44263、43608→42750，差额就是被丢弃的封底页与新增的标题行）。

**复测**（重索引完成后）：见 §6。

### 2.3 `reindex` 的 `limit` 查询参数

**现象**：`POST /api/v1/management/reindex?limit=4` 返回 200，
但实际按默认上限 500 跑——调用方以为「只跑了 4 条」，响应里也没有回显生效的 limit。

**根因**：`limit` 只声明在请求体 `ManagementDtos.ReindexRequest` 里（`@RequestBody(required=false)`），
查询参数从未参与绑定，于是被**静默忽略**。前端两个调用点都正确地发 body，
所以这个坑只咬手工 curl 的运维路径——而恰恰是这条路径最需要小步试跑。

**处置**（`RagManagementController.reindex` + `resolveReindexLimit`）：
`?limit=` 现在生效；请求体与查询参数同时给以**请求体为准**（它是带 Bean Validation 的正式契约）；
非整数与越界都显式 400，不放进端口层变 500。
新增 4 个单测，并在真实服务上验证：`?limit=3` → `{"indexedChunks":3,"scannedChunks":3}`
（修复前同样请求跑掉的是 500 条的批次）。

## 3. 已证伪 / 非缺陷（但要留痕，否则会重查一遍）

### 3.1 ⚠️ 我自己的脚本把两册片段**全删了**

重灌 SQL 里那条「剪掉本次不再产出的旧片段」的 `DELETE`，
判据写成了 `WHERE document_id = <本文档>`——同一事务里它同样匹配刚 INSERT 进去的 287 条，
于是执行完是 `chunks=0`。**两册被清零**。

- **为什么能恢复**：片段完全由 `PDF + 脚本` 决定（UUID 是 `uuid5(isbn|page#part)` 派生），
  重跑一次生成 SQL 就原样回来，**没有任何人工录入数据丢失**；
  向量本来就要重灌（正文变了），所以损失的是几分钟机时。
- **教训**（已写进脚本注释）：这类「同步剪枝」的判据必须是
  **`chunk_id <> ALL(本次产出的 ID 集合)`**，不能是「属于本文档」；
  并且这类脚本**必须先在事务里带一条 `SELECT count(*)` 自检**再 COMMIT——
  我把 PgRun 加了 in-tx check 通道，正是这次补上的。
- **顺带确认的两条 RLS 事实**：`rag_chunk` 上是 `FORCE ROW LEVEL SECURITY`，
  删片段必须带租户上下文（`rag_current_tenant()`），否则**静默删 0 行**；
  `rag_answer_citation` / `rag_chunk_embedding` 都是 `ON DELETE CASCADE`，
  所以剪枝语句加了「没被引用过」的护栏——删掉被引用片段会连带抹掉历史答案的证据链
  （本轮实测库内 `rag_answer_citation` 为 0 行，护栏是给以后准备的）。

### 3.2 「缺 `edition.revisionCode` 返回 500」——我误报

实测：`POST /api/v1/retrieval` 省略 `revisionCode` → **HTTP 400**。
`RetrievalRequestDto` 上有 `@Valid @RequestBody`，`EditionDto.revisionCode` 是 `@NotBlank`，一直生效。

我当时看到的 500 是**另一件事**：那条请求同时命中了 §3.3 的嵌入维度不匹配 fail-fast，
错误体被 Spring 的兜底页吃掉，我只看了状态码就归因给了参数校验。
**教训**：状态码相同不代表根因相同，先看错误体里的消息再登记缺陷。

### 3.3 嵌入维度不一致 → 500，是设计内的 fail-fast

`RAG_EMBEDDING_DIMENSION` 漏配（默认 1024）而模型返回 4096 时，
重索引直接失败并打印「Embedding 维度不匹配：模型 X 返回 4096 维，配置与向量列期望 1024 维，
三者必须同时改…」。这条把「新旧向量混在同一 `<=>` 空间里静默错乱」的整类事故
关在了启动/索引期，**是本轮最值钱的报错**。它是运行期请求的失败，返 500 合理。

### 3.4 Ollama / 代理端口的两个环境事实

- Ollama v0.40.6 **移除了** `--embeddings` 启动标志（`Error: unknown flag`），
  `/v1/embeddings` 现在原生可用，不需要额外开关。
- `127.0.0.1:8317` 是个 chat-only 的 OpenAI 兼容代理，`/v1/embeddings` 返回 404；
  嵌入必须直连 `11434`。**误判代价**：会以为「本地模型不支持嵌入」而放弃整条路线。

### 3.5 租户令牌 TTL 15 分钟

长跑测试中途所有请求一律 `401 {"message":"令牌无效、过期或受众不符"}`。
这不是鉴权缺陷（`RagJwtAuthFilter` 的行为完全正确）。已补 `/tmp/tok.sh` 每轮刷新。
**注意**：`X-Tenant-Id` 必须与令牌 `tenant_id` claim 一致，否则 403——这是设计内的归属绑定。

## 4. 如实登记的未解决项

### 4.1 词法通道与稠密通道**量纲不同**，纯词法命中被门禁恒过滤 ⛔

`JdbcRetrievalRepository.lexicalSearch` 的 `ts_rank` 与稠密通道的 cosine
不是同一个量纲，而编排层的 `relevance` 取「各通道原始分的最大值」，再统一比 `min-score`。
`ts_rank` 实测只有 **0.068** 量级，而门禁现在是 **0.38**——
**词法通道只能影响 RRF 排序，不能让它独立入选**。

后果：一个只被词法命中的精确查词（例如某个只在某页出现过一次的词），
必须**碰巧**也挤进稠密候选池才答得出。这正是 §2.1 里「近邻负例拦不住」的另一面：
门禁对两个通道的意义完全不同。

**修法**（与用户对齐过的三层路线里的第 1 层，一天内可做完、可证伪）：
门禁**按通道归一化**，或对纯词法命中单独设阈值/豁免。
本轮没做——它需要动 `RetrievalOrchestrator` 的相关性定义，
而那个定义同时是 RAG-D07 G-6 门禁的口径，不该在没有评测集护栏时顺手改。

### 4.2 4096 维无法建 ANN 索引，稠密检索是**全量精确扫描** ⛔

pgvector 的 HNSW/IVFFlat 维度上限是 `vector 2000 / halfvec 4000`，
而 `qwen3-embedding:8b` 是 4096 维 → **建不了索引**（存储本身支持到 16000）。
本轮因此主动删掉了 `rag_chunk_embedding_hnsw_idx`。

现在 287 片段扫得动（单次查询 <2s，主要耗时在嵌入模型而不是扫描）。
**规模阈值**：万级片段以后精确扫描会先崩。可选路（都还没做）：
MRL 截断到 ≤4000 维再建索引 / 二值量化 / 换 1024 维模型并接受召回质量变化。

### 4.3 分数门禁分不开「同体裁的无关内容」⛔

§2.1 的阈值扫描说明了这是**方法层面的局限**，不是参数没调好：
近邻负例 `past continuous tense` 在语料里能拿到 0.525，比正例 p25 还高。
要真正解决需要 **rerank（cross-encoder）** 或知识点结构化过滤，
而 `kp_ids` 现在两册全是 `{}`——填它需要先把知识点字典和教材映射建出来（RAG-D10 的活）。

### 4.4 平台 dev 启动生成密钥 → RAG 的验签公钥每次平台重启都作废 ⛔

`AuthConfiguration.resolveKeyPair()` 在 dev profile 下允许 `JWT_PRIVATE_KEY` 留空、
**启动时生成新密钥**。本机平台一直是这个状态，所以 RAG 侧无论配哪把公钥，
平台一重启就验不过——表现为「登录正常、调 RAG 全部 401」，
而 401 看着像 RAG 的缺陷，实际是两侧密钥漂移。

本轮处置：`scripts/gen-jwt-keys.sh` 生成两对 RSA-2048（租户域 / 平台域），
一把私钥同时产出「平台签发用 `私钥.公钥`」与「RAG 验签用公钥」，
**同源写入同一个 `jwt.env`**（0600，被 `.gitignore` 的 `*.env` 忽略），
两侧各自 source，杜绝手工搬运公钥。`--check` 会拉运行中平台的 JWKS 比对指纹。

⚠️ 换密钥后必须**两侧同步重启**，只重启一边就是上面那个故障。
本机生效顺序：平台先重启（`platform.env` 已 source `jwt.env`）→ 再起 RAG。

## 7. 本地开发环境配置（IDEA / EnvFile 插件）

### 7.1 报错指向占位实现，根因是嵌入地址没配 ✅

IDEA 起 `rag-bootstrap` 报：

```
Failed to instantiate EmbeddingPort: [RAG fail-closed] 本地占位端口未获显式启用，拒绝装配：
EmbeddingPort → LocalDeterministicEmbeddingPort
```

看文案像是「忘了设 `RAG_LOCAL_PORTS_ENABLED`」，实际不是。
`EmbeddingPorts.create()` 的分支是：**`rag.embedding.base-url` 为空**才走本地占位。
所以真实原因是 IDEA 挂的那两个 env 文件里**没有嵌入配置**——它们此前只写在仓库外的
启动脚本 `/tmp/rag-run.sh` 里，EnvFile 插件读不到仓库外的东西。

按提示去设 `RAG_LOCAL_PORTS_ENABLED=true` 会把问题**藏起来而不是解决**：
占位向量是确定性的假语义，且维度（1024）与库里的 `halfvec(4096)` 不符，
下一步就在装配期被 `VectorColumn` 的维度校验拒掉，错误还更费解。

### 7.2 env 文件必须是「纯 KEY=VALUE」，否则插件解析出的是脏值 ⚠️

IDEA 的 EnvFile 插件只做 dotenv 式逐行解析，**不认 shell**：

- `scripts/gen-jwt-keys.sh` 产出的 `jwt.env` 值**不再加单引号**

## 8. admin-console AI 实验室的 401（2026-10-28 22:3x 续，一条 curl 引出三件事）

用户贴的复现：`POST http://localhost:5185/api/runs`（平台控制台页面发起）带一枚平台令牌 → **401**。

### 8.1 401 本身不是缺陷：域隔离在令牌层就成立（核到代码行）

那枚令牌解码后是 `aud=admin-console-api`、`principal_type=PLATFORM_USER`、`roles=[PLATFORM_SUPER_ADMIN]`，
未过期。而 `/api/runs` 属**租户域**：

| 事实 | 证据 |
|---|---|
| 租户侧验签把 `aud` 与自身配置的 `agent-platform` 硬比对，不等即拒 | `JwtTokenService.java:208` |
| 租户**只能**取自已验签令牌，请求体里没有也不该有 `tenantId` | `RunController.java:137-139`（注释原文「绝不从请求参数或请求体取租户」，取值行是 `currentPrincipal.context()`） |
| 平台链反之拒租户令牌，两向都堵 | `SecurityConfiguration.java:112-113` / `:309` |
| 前端**已预期**这一条并照实提示，没有伪装成成功 | `admin-console/src/pages/agentlab/AgentLabPage.tsx:278` |

所以「按 curl 的 401 去放宽租户链、或给请求体塞 tenantId」都是错的方向：**这条边界是防平台令牌越进租户域的设计**。
真正待决策的是「平台控制台要怎么拿到租户上下文」，三个取向各有代价：

### 8.5 已落地：跨域执行票证通道（§8.1 那个「待决策」的口子按「生产默认开」定案）

**决策**：用户明确要 **生产默认开**（覆盖我建议的默认关）。默认开的前提是风险全部收敛在
「签发」这一个动作上，所以配套控制**必须先存在再打开**，而不是留一个开着的开关配一句警告。

**四道签发闸门 + 一次留痕**（`PlatformExecutionTicketService`，闸门顺序即代码顺序）：

| 顺序 | 闸门 | 不过时 | 为什么在这个位置 |
|---|---|---|---|
| 1 | 平台权限 `platform.tenant.execution_ticket`（只绑 `PLATFORM_SUPER_ADMIN`） | 403，**不写审计** | 未授权的探测不该污染审计流；只有过了授权才说明「有人试图扮演租户」 |
| 2 | 开关 `…execution-ticket.enabled` | 503 + `DENY/CHANNEL_DISABLED` 审计 | 关掉的通道被人敲要留痕，否则「有没有人在试」不可知 |
| 3 | 按**目标租户**限流（桶 `PLATFORM_EXECUTION_TICKET`，继承全局 30 次/60 秒） | 429；限流器不可用也 **429**（fail-closed，不放行） | 桶键是**被扮演的租户**而不是平台用户：防的是「单个租户身份被刷」 |
| 4 | 租户存在且非 SUSPENDED/DECOMMISSIONED、成员 ACTIVE、角色交集非空 | 404/409 + 对应 `DENY` 原因码 | 票证的 `principalId` 必须是真实存在的租户成员 |

原因码实测齐备：`CHANNEL_DISABLED` / `RATE_LIMITED` / `RATE_LIMIT_UNAVAILABLE` /
`TENANT_NOT_FOUND` / `TENANT_NOT_ACTIVE` / `PRINCIPAL_NOT_FOUND` / `PRINCIPAL_NOT_ACTIVE` /
`TICKET_ROLE_NOT_HELD`。审计字段映射（`platform_audit_event` 的列类型是硬约束，非 UUID 会被 `?::uuid` 打成 500）：
`actor_id`=发起人、`target_id`=租户、`correlation_id`=被扮演成员、`reason_code`=票证 `jti`。

**一处比设计更紧**：设计要求「角色固定 `[AGENT_AUTHOR]`」，实现是
**与库中该成员已登记角色取交集，交集为空即拒**。否则任何一次取票都会凭空给主体注入一个它没有的角色，
`authz_version` 与撤权传播也就失去意义。

**TTL 由调用方逐次指定**：`JwtTokenService` 原来只有构造期的 15 分钟 TTL。
新增 `issueDetailed(context, now, ttl)` 返回 `(token, jti, expiresAt)`，`issue()` 保持原语义委派过去
—— 而不是再造一个 60 秒的第二签发器：那会出现两个 bean 共用 `aud`/`iss`/密钥配置，
「哪把钥匙签的」变成隐性事实。构造期下限校验 `ttl-seconds >= 60`，防把票证配成 1 秒的抖动源。

React state 里存的是**不含 accessToken 的快照**，否则令牌会出现在 React DevTools 的渲染树里。
发租户域请求必须 `auth=false` + 第 4 个 `extraHeaders` 参数：`client.ts::_request` 在合并完
extraHeaders **之后**才用平台会话覆盖 Authorization，用 `auth=true` 等于把票证扔掉 —— 那正是原始 401 的成因。

**仍不假装做到的事**：票证解决「能不能拿到租户身份」，**不解决**「凭据不落 URL」。
`EventSource` 依旧带不了 Authorization 头，所以 Lab 仍然轮询，SSE 没有被声称支持。
续取节奏实测：轮询 2 秒一次、TTL 60 秒、提前 15 秒续 → **约每 45 秒一次签发**（不是每 tick 一次），
一次 300 秒的观察上限约 7 条审计。这条断言写在测试里，因为「每 tick 取票」会把审计流刷成噪音。

## 9. 执行票证 404：一个绕过 provisioning 的种子夹具（附一条我被自己收回的判断）

**现场**：`POST /api/platform/v1/tenants/2187ffed-3e2e-4fd0-b4a7-54dcc0a483e2/execution-ticket` → **404**，
响应体只有 `{"code":"NOT_FOUND","message":"资源不存在"}`。

### 9.1 已定性：不是路由/部署问题，是数据问题 + 一个真实的可诊断性缺陷

先排除「端点没起来」这条最便宜的解释，留证：类文件 mtime `23:59:21` < 进程启动 `23:59:22`，
classpath 指向 `target/classes` —— 8080 上跑的**就是**新代码。真正的证据在审计表里：

```
platform_audit_event:  DENY | reason_code=TENANT_NOT_FOUND | target_id=2187ffed…  ×4
                       （最新一条 2026-10-29 00:01:41，即我自己复现的那次 curl）
```

闸门在转、审计在写、票证没签 —— 404 是**第二道 404**（不是 Spring 的「无此路由」）。

### 9.2 根因：种子夹具绕过 `provisionTenant`，造出「业务侧有、平台侧无」的畸形租户

实测（远程 `agent_dev`，2026-10-29 00:2x）：

| 表 | 行 |
|---|---|
| `platform.tenant` | **只有** `5222d5e7… \| e2e-console \| PENDING_SETUP \| plan=null` |
| `public.tenant` | `2187ffed… \| t-a \| 某某教育科技 \| ACTIVE`、`5222d5e7… \| e2e-console \| PENDING_SETUP` |
| `public.principal` | `e2eminimax`（ACTIVE）归 `2187ffed…` |
| `public.agent` | 4 个 Agent 全部归 `2187ffed…` |

于是今天这台库上**两个租户都取不到票证**，且各卡在不同闸门：

- `2187ffed…`（有 Agent、有成员）→ 平台侧无登记 → `TENANT_NOT_FOUND`；
- `5222d5e7…`（平台侧登记了）→ `PENDING_SETUP` → `TENANT_NOT_ACTIVE`。

**两处读两张表，但设计是自洽的 —— 我一度判错，读完全文后收回**：
worker 执行前读 `public.tenant.status`（`JdbcTenantLifecycleProbe:42`），
票证闸门读 `platform.tenant.lifecycle_state`。看起来像口径分裂，
实际上 `platform.tenant` 才是权威、`public.tenant.status` 是**同事务镜像**：

| 写路径 | 代码位置 | 写哪几处 |
|---|---|---|
| 开通租户 | `JdbcPlatformTenantRepository.provisionTenant:127-167` | `platform.tenant` + `INSERT INTO tenant (...)`（业务行，供 RLS/执行基础设施识别）+ `platform.tenant_quota(50/10)`，**一个事务，失败全回滚** |
| 生命周期迁移 | 同文件 `transitionLifecycle:180-215` | CAS 更新 `platform.tenant.lifecycle_state`，随后 `UPDATE tenant SET status=?` 镜像 |

所以**走 `provisionTenant` 开通的租户，两张表恒等**（e2e-console 就是两条都有），
「停用租户」也确实会停掉执行 —— 不存在治理开关空转的问题。

真正的破口只有一处，而且比「设计分裂」小得多也坏得多：**种子绕过 `provisionTenant`**。
`public.tenant` 里那行 `2187ffed…` 来自 `deploy/sql/platform/02_platform_seed.sql:231` 的
裸 `INSERT INTO public.tenant`，没有对应的 `platform.tenant` 行 —— 镜像反过来缺了权威，
于是 worker 认它、票证闸门不认它。**这是夹具缺陷，不是判断口径缺陷**，
修法也因此在夹具侧（补 seed / 让 seed 走同一条 provisioning 形状），而不是改哪一处读哪张表。

> 顺带记下我这次是怎么读错的：只看了 `provisionTenant` 里 `INSERT INTO platform.tenant` 那一段
> （128-130 行）就下了「只灌平台侧」的结论；`INSERT INTO tenant` 在 152 行，
> 中间隔着 20 行的 `PreparedStatement` 样板。**grep `UPDATE public.tenant` 也漏了** ——
> SQL 写的是 `UPDATE tenant SET status`（schema 由连接 search_path 决定），
> 不带 `public.` 前缀，按限定名搜必然搜不到。

### 9.3 已修：原因码必须出现在响应里（这是缺陷，不只是「文案不好」）

`ApiExceptionHandler` 对 `ResponseStatusException` **刻意不回显 `getReason()`**（按状态码归一，防止把内部原因泄露成枚举），
所以 8 个闸门原因码在 HTTP 侧全部塌缩成「资源不存在」，而库里写着 `TENANT_NOT_FOUND` ——
两份记录对不上号，运维只能进库查审计。按项目既有先例（`ConfigOverrideController.ApprovalRequiredException`）
改为专用异常 + 专属 handler：

- `PlatformExecutionTicketService.TicketRejectedException(status, reasonCode, message)`，
  所有闸门经 `denyAndReject(...)` **一处写审计、一处出响应**，保证两侧原因码同源；
- `ApiExceptionHandler.handleTicketRejected` 返回 `ErrorResponse(reasonCode, message)`，
  即 `code` 直接就是审计表的 `reason_code`，可 grep、可对照；
- 文案补上可行动信息（租户 UUID、登录名、当前状态），不再出现「失败了但没说为什么」。

**这条是被测试钉住的，不是靠 review 看出来的**：新增 `responseCodeAndAuditReasonCodeAreTheSameValue`
把 6 个闸门逐个走一遍，断言 `响应 code == 审计 reason_code` 且文案含标识符。
写完第一条就抓到一处真缺陷 —— `TENANT_NOT_ACTIVE` 的文案只说「当前状态不允许」而不说**是哪个租户**，
断言直接失败（`没给出任何可行动信息`）。另加 `unregisteredTenantIsNotFoundWithItsOwnCode`
（就是今天的现场：应用侧有租户、平台侧没有）与「登记校验排在限流之后，令牌该消耗」的次序断言。

服务层 **13/13**、`mvn -o test` 全绿；前端 Lab 界面把原因码显示出来（`describeRejection`）：
`取票证失败：TENANT_NOT_FOUND：租户未在 platform.tenant 登记，无法签发执行票证：2187ffed…`。

### 9.4 三件事的分工：夹具已根治、巡检已挂上、补登记已提交

**我一度据此判「权威源分裂」，读完全文后收回**（见 §9.2 末）：`provisionTenant` 与
`transitionLifecycle` 都在同一事务里写两张表，`public.tenant.status` 是权威平台行的**镜像**。
剩下的问题比「设计分裂」小得多，也更好修：

| | 动作 | 影响面 | 状态 |
|---|---|---|---|
| b | **seed 根治**：`02_platform_seed.sql` 补 `platform.tenant` + `tenant_quota` 两段（`plan` 留 NULL、顺序在 `public.tenant` 之前以满足 FK，形状与 `provisionTenant` 一致） | 仅仓库文件 | ✅ 已做。dry-run 实测：同事务内先执行这两行，`①剩余漂移行数` 由 **1 → 0**，随后 `ROLLED BACK` |
| c | **巡检守卫**：`scripts/check-tenant-registry.sh` + `scripts/tools/CheckTenantRegistry.java`（只读、`setReadOnly` + `ROLLBACK`，退出码 0 一致 / 1 漂移 / 2 连不上） | 仅仓库文件 | ✅ 已做。对本机库实测**准确抓到当前这一条漂移**并退出 1：`① 业务侧有、平台侧无登记（1 行）→ 2187ffed… \| t-a \| ACTIVE`，②③④ 各 0 行 |
| a | **补登记当前这行**：`patch_platform_tenant_registration.sql`（幂等、NOT EXISTS、只补已登记行的缺半，不覆盖已有 `lifecycle_state`） | 写共享远程 RDS | ✅ **已提交执行**（2026-10-29，用户确认后）。执行前再跑一次 dry-run：`drift=0 tenants=2 quotas=2` → `ROLLED BACK`；随后 `commit`：`tenants=2 quotas=2 ticket_gate=ACTIVE` → `COMMITTED`。之后 `./scripts/check-tenant-registry.sh` 四项全 0 违规、退出码 **0**（此前报 ① 1 行、退出 1） |

巡检查的四条不变式（前三条破坏即退出 1，第四条也计入）：
①业务侧有 → 平台侧必须有；②平台侧有 → 业务侧必须有（否则 worker 探针读空、Agent 无处挂载）；
③三列状态相等 `public.status = platform.lifecycle_state = platform.status`
（**「停用租户」是否真生效，看的就是这一条**）；④平台侧登记了却没配额行（说明不是走 `provisionTenant` 开通的）。
连接身份必须是库 owner：`public.tenant` 开了 RLS，用 `app_agent` 连只看得到自己一个租户，巡检结论会失真。

**仍然没修的一条**：两张表之间**无外键、无触发器**，恒等只靠「大家都走 `provisionTenant`」的约定
（`transitionLifecycle` 的镜像那一步还是 best-effort，业务行不存在时 `UPDATE` 影响 0 行、静默通过）。
加 FK 属于全库 DDL、还要先清历史脏行，本轮不动；c 是当前能做到的最低成本兜底 ——
它不阻止人写裸 INSERT，但会让漂移**当天**被发现，而不是在下一次「404 到底谁的错」时被发现。

`2187ffed…` 的数据侧条件已具备（平台侧登记 ACTIVE + 配额行齐）。真跑端到端还差一步不在仓库里的动作：
**用户用带新 handler 的构建重启 8080**，再走「取票 → `POST /api/runs` → worker 真跑」。
