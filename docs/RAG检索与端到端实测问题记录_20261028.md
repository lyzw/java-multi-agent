## 2. 已修复项

### 2.1 分数门禁标定：`0.2 → 0.38`

**现象**：换上真实嵌入模型后，一组完全无关的查询（`李白 静夜思`、`篮球 NBA 总决赛`）
照样能召回 top1，分数 0.31–0.41；而相关查询的正例中位是 0.50。
门禁设在 0.2，等于**没有任何门禁**——「找不到依据」这条合法输出永远不会触发，
RAG 会拿着一堆不相干的片段继续生成（RAG-D05 §⑦ 想防的正是这个）。

**标定方法**（`/tmp/calib.py`，可重跑）：16 条正例（答案确在两册里，逐条对过页码）
+ 8 条**近邻负例**（同是英语、同类教材体裁，但两册里没有：`photosynthesis chloroplast`、
`past continuous tense`…）+ 10 条**远域负例**（数学/语文/历史/体育），
`topK=10` 全量跑一遍，记录每条命中的相关性分。

**分布**：

| 档位 | 命中数 | min | p25 | 中位 | p75 | max |
|---|---|---|---|---|---|---|
| 正例 | 66 | 0.390 | 0.465 | **0.504** | 0.534 | 0.689 |
| 近邻负例 | 32 | 0.387 | 0.399 | 0.413 | 0.473 | **0.525** |
| 远域负例 | 27 | 0.306 | 0.327 | 0.339 | 0.366 | 0.411 |

**阈值扫描**（保留多少正例命中 / 放过多少负例命中）：

```
min-score  正例保留   近邻漏过   远域漏过
  0.20      66/66     32/32     27/27      ← 现状：门禁完全不做事
  0.38      66/66      32/32      3/27     ← 选它：正例零损失
  0.42      60/66      14/32      0/27
  0.45      53/66       8/32      0/27
  0.48      42/66       5/32      0/27
```

**结论与取值**：默认值改为 **0.38**（`application.yml:63` 与 `RagInfrastructureConfig:56`
与 `RagInfrastructureConfig` 的 `@Value` 兜底同源）。理由：它是「远域噪声基本消失
（27 条里只剩 3 条）而正例一条没丢」的第一个阈值；再往上是**拿正例换负例**，
换不动——近邻负例的 max（0.525）已经高于正例的 p25（0.465），
分数门禁在原理上就分不开这一类（见 §4.1 与 §4.3）。

**⚠️ 推翻旧结论**：本轮之前我给过一个「经验可用区间约 0.45–0.48」的说法，
那是**4 条查询**的样本外推，错了 0.07 左右——按它设阈值会白白砍掉约 20% 的真召回
（0.48 时正例只剩 42/66）。以 §2.1 的 34 条为准。

**复现**：
```bash
/tmp/tok.sh && python3 /tmp/calib.py     # 需 8081 在线、两册已 VERIFIED
```

### 2.2 附录词表按单元重切片

**现象**：学生问「六年级上册第五单元的单词」。Unit 5 的词表实际印在**附录**，
而附录是按页切片的：p.134 那一片 1649 字里同时含 Unit 1/2/3 的词，
p.137 一片里混着 Unit 4/5/6，`section_path` 只能标成一个笼统的「附录」，
`kp_ids='{}'`。这一片的向量被几个单元的词共同拉扯，
「Unit 5」这个信号在 1900 字里被稀释到召不出来（实测：两种 topK 均 0 命中）。

**根因**：切分粒度按**印刷页**，而词表的逻辑单位是**单元**——两者不同构。
换更强的嵌入模型**不能**替代重切片：模型再准，也只是把「混了四个单元的一整页」
表征得更准一点而已，它仍然是那一页的表征。

**处置**（`scripts/rag_import_pdf.py`）：
1. 附录区新增 `appendix_pieces()` 状态机：进入
   `Words and expressions in each unit` 后按 `Unit N` / `Starter` 边界切；
   **续页不重复单元标题**，所以当前单元跨页携带（记在 `state` 里），
   整页归给上一页留下的那个单元；遇到字母序词表或其它栏目标题即退出。
2. 每个片段开头补一行**中英双形**标题：`Unit 5（第五单元）单词表：…`。
   这是「第五单元」这种中文问法目前唯一的桥梁——不需要额外别名表。
3. `section_path` 从「附录」细化为 `Unit 5 Animals and us 词表` / `附录 · 语法` /
   `附录 · 注释`（栏目名按特异性排序匹配，否则「Notes: …」会把拼写规则页错标成注释）。
4. 封底/版权页（`定价：18.90元`、`本套教材根据…编写`）不再入语料：
   整页只有一句出版信息，**却能在检索里拿到 top1**（本轮实测的直接起因）。
5. 片段 INSERT 从 `ON CONFLICT DO NOTHING` 改为 `DO UPDATE`，
   并把 `text_jieba` 清成 `''`——这是**功能性**的：
   `ChunkIndexer.PENDING_SQL` 的待索引判据是 `text_jieba='' OR 无向量行`，
   不清它，改了正文的片段永远不会重新嵌入，表现为「改了脚本但检索没变」的假象。

**结果**：两册 287 片段，词表切出 22 片（每册 11 片，覆盖 Starter + Unit 1~6），
附录整页碎片从 45/43 片变为 48/46 片，正文内容零丢失
（附录区字符量 45023→44263、43608→42750，差额就是被丢弃的封底页与新增的标题行）。

**复测**（重索引完成后）：见 §6。

### 2.3 `reindex` 的 `limit` 查询参数

**现象**：`POST /api/v1/management/reindex?limit=4` 返回 200，
但实际按默认上限 500 跑——调用方以为「只跑了 4 条」，响应里也没有回显生效的 limit。

**根因**：`limit` 只声明在请求体 `ManagementDtos.ReindexRequest` 里（`@RequestBody(required=false)`），
查询参数从未参与绑定，于是被**静默忽略**。前端两个调用点都正确地发 body，
所以这个坑只咬手工 curl 的运维路径——而恰恰是这条路径最需要小步试跑。

**处置**（`RagManagementController.reindex` + `resolveReindexLimit`）：
`?limit=` 现在生效；请求体与查询参数同时给以**请求体为准**（它是带 Bean Validation 的正式契约）；
非整数与越界都显式 400，不放进端口层变 500。
新增 4 个单测，并在真实服务上验证：`?limit=3` → `{"indexedChunks":3,"scannedChunks":3}`
（修复前同样请求跑掉的是 500 条的批次）。

## 3. 已证伪 / 非缺陷（但要留痕，否则会重查一遍）

### 3.1 ⚠️ 我自己的脚本把两册片段**全删了**

重灌 SQL 里那条「剪掉本次不再产出的旧片段」的 `DELETE`，
判据写成了 `WHERE document_id = <本文档>`——同一事务里它同样匹配刚 INSERT 进去的 287 条，
于是执行完是 `chunks=0`。**两册被清零**。

- **为什么能恢复**：片段完全由 `PDF + 脚本` 决定（UUID 是 `uuid5(isbn|page#part)` 派生），
  重跑一次生成 SQL 就原样回来，**没有任何人工录入数据丢失**；
  向量本来就要重灌（正文变了），所以损失的是几分钟机时。
- **教训**（已写进脚本注释）：这类「同步剪枝」的判据必须是
  **`chunk_id <> ALL(本次产出的 ID 集合)`**，不能是「属于本文档」；
  并且这类脚本**必须先在事务里带一条 `SELECT count(*)` 自检**再 COMMIT——
  我把 PgRun 加了 in-tx check 通道，正是这次补上的。
- **顺带确认的两条 RLS 事实**：`rag_chunk` 上是 `FORCE ROW LEVEL SECURITY`，
  删片段必须带租户上下文（`rag_current_tenant()`），否则**静默删 0 行**；
  `rag_answer_citation` / `rag_chunk_embedding` 都是 `ON DELETE CASCADE`，
  所以剪枝语句加了「没被引用过」的护栏——删掉被引用片段会连带抹掉历史答案的证据链
  （本轮实测库内 `rag_answer_citation` 为 0 行，护栏是给以后准备的）。

### 3.2 「缺 `edition.revisionCode` 返回 500」——我误报

实测：`POST /api/v1/retrieval` 省略 `revisionCode` → **HTTP 400**。
`RetrievalRequestDto` 上有 `@Valid @RequestBody`，`EditionDto.revisionCode` 是 `@NotBlank`，一直生效。

我当时看到的 500 是**另一件事**：那条请求同时命中了 §3.3 的嵌入维度不匹配 fail-fast，
错误体被 Spring 的兜底页吃掉，我只看了状态码就归因给了参数校验。
**教训**：状态码相同不代表根因相同，先看错误体里的消息再登记缺陷。

### 3.3 嵌入维度不一致 → 500，是设计内的 fail-fast

`RAG_EMBEDDING_DIMENSION` 漏配（默认 1024）而模型返回 4096 时，
重索引直接失败并打印「Embedding 维度不匹配：模型 X 返回 4096 维，配置与向量列期望 1024 维，
三者必须同时改…」。这条把「新旧向量混在同一 `<=>` 空间里静默错乱」的整类事故
关在了启动/索引期，**是本轮最值钱的报错**。它是运行期请求的失败，返 500 合理。

### 3.4 Ollama / 代理端口的两个环境事实

- Ollama v0.40.6 **移除了** `--embeddings` 启动标志（`Error: unknown flag`），
  `/v1/embeddings` 现在原生可用，不需要额外开关。
- `127.0.0.1:8317` 是个 chat-only 的 OpenAI 兼容代理，`/v1/embeddings` 返回 404；
  嵌入必须直连 `11434`。**误判代价**：会以为「本地模型不支持嵌入」而放弃整条路线。

### 3.5 租户令牌 TTL 15 分钟

长跑测试中途所有请求一律 `401 {"message":"令牌无效、过期或受众不符"}`。
这不是鉴权缺陷（`RagJwtAuthFilter` 的行为完全正确）。已补 `/tmp/tok.sh` 每轮刷新。
**注意**：`X-Tenant-Id` 必须与令牌 `tenant_id` claim 一致，否则 403——这是设计内的归属绑定。

## 4. 如实登记的未解决项

### 4.1 词法通道与稠密通道**量纲不同**，纯词法命中被门禁恒过滤 ⛔

`JdbcRetrievalRepository.lexicalSearch` 的 `ts_rank` 与稠密通道的 cosine
不是同一个量纲，而编排层的 `relevance` 取「各通道原始分的最大值」，再统一比 `min-score`。
`ts_rank` 实测只有 **0.068** 量级，而门禁现在是 **0.38**——
**词法通道只能影响 RRF 排序，不能让它独立入选**。

后果：一个只被词法命中的精确查词（例如某个只在某页出现过一次的词），
必须**碰巧**也挤进稠密候选池才答得出。这正是 §2.1 里「近邻负例拦不住」的另一面：
门禁对两个通道的意义完全不同。

**修法**（与用户对齐过的三层路线里的第 1 层，一天内可做完、可证伪）：
门禁**按通道归一化**，或对纯词法命中单独设阈值/豁免。
本轮没做——它需要动 `RetrievalOrchestrator` 的相关性定义，
而那个定义同时是 RAG-D07 G-6 门禁的口径，不该在没有评测集护栏时顺手改。

### 4.2 4096 维无法建 ANN 索引，稠密检索是**全量精确扫描** ⛔

pgvector 的 HNSW/IVFFlat 维度上限是 `vector 2000 / halfvec 4000`，
而 `qwen3-embedding:8b` 是 4096 维 → **建不了索引**（存储本身支持到 16000）。
本轮因此主动删掉了 `rag_chunk_embedding_hnsw_idx`。

现在 287 片段扫得动（单次查询 <2s，主要耗时在嵌入模型而不是扫描）。
**规模阈值**：万级片段以后精确扫描会先崩。可选路（都还没做）：
MRL 截断到 ≤4000 维再建索引 / 二值量化 / 换 1024 维模型并接受召回质量变化。

### 4.3 分数门禁分不开「同体裁的无关内容」⛔

§2.1 的阈值扫描说明了这是**方法层面的局限**，不是参数没调好：
近邻负例 `past continuous tense` 在语料里能拿到 0.525，比正例 p25 还高。
要真正解决需要 **rerank（cross-encoder）** 或知识点结构化过滤，
而 `kp_ids` 现在两册全是 `{}`——填它需要先把知识点字典和教材映射建出来（RAG-D10 的活）。

### 4.4 平台 dev 启动生成密钥 → RAG 的验签公钥每次平台重启都作废 ⛔

`AuthConfiguration.resolveKeyPair()` 在 dev profile 下允许 `JWT_PRIVATE_KEY` 留空、
**启动时生成新密钥**。本机平台一直是这个状态，所以 RAG 侧无论配哪把公钥，
平台一重启就验不过——表现为「登录正常、调 RAG 全部 401」，
而 401 看着像 RAG 的缺陷，实际是两侧密钥漂移。

本轮处置：`scripts/gen-jwt-keys.sh` 生成两对 RSA-2048（租户域 / 平台域），
一把私钥同时产出「平台签发用 `私钥.公钥`」与「RAG 验签用公钥」，
**同源写入同一个 `jwt-keys.env`**（0600，被 `.gitignore` 的 `*.env` 忽略），
两侧各自 source，杜绝手工搬运公钥。`--check` 会拉运行中平台的 JWKS 比对指纹。

⚠️ 换密钥后必须**两侧同步重启**，只重启一边就是上面那个故障。
本机生效顺序：平台先重启（`config.env` 已 source `jwt-keys.env`）→ 再起 RAG。

## 7. 本地开发环境配置（IDEA / EnvFile 插件）

### 7.1 报错指向占位实现，根因是嵌入地址没配 ✅

IDEA 起 `rag-bootstrap` 报：

```
Failed to instantiate EmbeddingPort: [RAG fail-closed] 本地占位端口未获显式启用，拒绝装配：
EmbeddingPort → LocalDeterministicEmbeddingPort
```

看文案像是「忘了设 `RAG_LOCAL_PORTS_ENABLED`」，实际不是。
`EmbeddingPorts.create()` 的分支是：**`rag.embedding.base-url` 为空**才走本地占位。
所以真实原因是 IDEA 挂的那两个 env 文件里**没有嵌入配置**——它们此前只写在仓库外的
启动脚本 `/tmp/rag-run.sh` 里，EnvFile 插件读不到仓库外的东西。

按提示去设 `RAG_LOCAL_PORTS_ENABLED=true` 会把问题**藏起来而不是解决**：
占位向量是确定性的假语义，且维度（1024）与库里的 `halfvec(4096)` 不符，
下一步就在装配期被 `VectorColumn` 的维度校验拒掉，错误还更费解。

**处置**：新增 `rag-local.env`（嵌入模型、批次、维度、向量列类型、占位闸门），
IDEA 与 shell 启动脚本读同一份，杜绝两处漂移；模板提交为 `.env.example`。

### 7.2 env 文件必须是「纯 KEY=VALUE」，否则插件解析出的是脏值 ⚠️

IDEA 的 EnvFile 插件只做 dotenv 式逐行解析，**不认 shell**：
`export ` 前缀、`$(...)`、`if [ -f ... ]; then ... fi` 会被整行当成变量值塞进环境；
值两端的引号也不保证被剥掉。本轮为此改了两处：

- `config.env` 里原先加的 `if … source jwt-keys.env; fi` 撤掉，改由
  `scripts/dev-backend.sh` 负责加载（shell 通道），`config.env` 恢复成插件可解析的纯键值。
- `scripts/gen-jwt-keys.sh` 产出的 `jwt-keys.env` 值**不再加单引号**
  （base64url 字母表本身不含空格，无需引用）。

### 7.3 rag-bootstrap 需要的三个 env 文件

| 文件 | 内容 | 是否提交 |
|---|---|---|
| `rag-online.env` / `.env.rag-online` | PG 连接（`rag_app` 非特权角色）、端口 | 前者已被跟踪（含生产口令，既存隐患）、后者忽略 |
| `rag-local.env` | 嵌入模型 / 维度 / 向量列类型 / 占位闸门 | ❌ `*.env` 忽略；模板 `.env.example` 提交 |
| `jwt-keys.env` | RAG 只需其中两个**公钥**（平台另用同文件的私钥签发） | ❌ 含私钥 |

三处齐备后本机实测（模拟插件语义起临时实例）：装配通过 →
`POST /api/v1/retrieval` 用真实 Ollama 嵌入返回 `Unit 5（第五单元）单词表…` top1。
