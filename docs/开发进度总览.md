### 3.1 本轮抓到的真实缺陷（实测，非推断）

| # | 位置 | 缺陷 | 危害形态 |
|---|---|---|---|
| **1** | `JdbcRunEventQueryRepository.parsePayload` | `body.split(",")` 不识别字符串内逗号 | `errorCode="E1,E2"` 被读成 `{errorCode=E1, E2=null}` → **错误码被静默改写** |
| **2** | 同上 | `unquote` 只处理 `\"` 与 `\\` | 含换行的值回读为**字面量两字符 `\n`** |
| **3** | 同上 | 手写 `coerce` 把整数全当 `Long` | 写入 `Integer` / 读取 `Long` 不对称，下游 `==` 静默失败 |
| **4** | `JdbcRateLimiter` | 全局单一限额，无桶级覆盖 | 治理桶与学生桶互相蚕食；按**租户**限流 → 多个运维互相限流 |
| **5** | `ApprovalQueryPort` | 「拒绝未填理由」抛 409 类异常 | 前端提示「已被别人处理」，真相是「少填一个字段」→ 改 400 |

> 三条 1～3 的共同形态：**不抛异常、不断言报错，只是值悄悄变了**。
> 与 P4-D08 R-1（工具未注册为 Bean → 表永远为空）同源——
> **静默失效靠「逐行看断言」抓不到，只能靠「针对可疑行为的专项用例」抓。**

## 八、⛔ 本轮新发现（10:50 · 实测，非推断）

### ⛔ F-1：`RealBrokerEndToEndIT` 默认连**生产 vhost**，与运行实例互相消费

| 项 | 内容 |
|---|---|
| **现象** | `messageSentAndReceivedWithIntegrity` 断言「发一条后深度 +1」得到 **0**（`expected: 1 but was: 0`）|
| **根因** | 该 IT 用 `env("RABBITMQ_VHOST", "agent")`取 vhost——**默认值就是生产 vhost**；而 `set -a; . config.env` 会把 `RABBITMQ_VHOST=agent` 导入，**覆盖掉隔离意图**。8080 上的运行实例正在消费同一队列 `agent.run.execute`，消息**瞬间被取走** → 深度不增 |
| **性质** | **测试隔离缺陷**，不是产品缺陷。队列深度探测本身是对的——它**如实反映了「消息被消费了」** |
| **验证** | 显式 `export RABBITMQ_VHOST=agent-test` 后，`agent-infrastructure` **全部通过**（176 项）|
| **与既有教训的关系** | 与 `scripts/dev-it-db.sh` 头部记载的**同形态**：「IT 与运行实例共用一套基建 → 双方互相污染」。**该脚本只解决了数据库侧，没解决 MQ 侧** |
| **建议修法** | ① IT 默认 vhost 改为 `agent-test`；② 在 `dev-it-db.sh` / `dev-rabbitmq.sh` 里显式导出 `RABBITMQ_VHOST=agent-test`；③ 深度断言前先确认无外部消费者 |

### ⛔ F-2：全量 `mvn clean verify` 在**运行实例占用连接**时不可复现

| 项 | 内容 |
|---|---|
| **现象** | `platform-bootstrap` 4 项错误（`ConfigEndpointIT` 全类），根因链末端 `PSQLException: FATAL: sorry, too many clients already` |
| **根因** | **三层叠加突破 `max_connections=100`**：<br>① Hikari 默认 `maximumPoolSize=10` 且 **`minimumIdle` 默认等于 `maximumPoolSize` → 每个池「急切占满」10 条**；<br>② 各 IT 的 `@TestPropertySource` **互不相同** → Spring 上下文缓存里存在**多份上下文**，**每份各持一个独立 DataSource 池**，且上下文**直到 JVM 退出才关闭**；<br>③ 本机同时有运行实例（`PostgreSQL JDBC Driver` **10 条**）+ Navicat 4 条 + 保留 3 条 |
| **为什么测试自建池没事** | IT 里用 `HikariConfig` 手工建的池**都限了大小**（1/2/4/8），例如 `FaultInjectionSupport.appPool(1)`；**唯独 Spring 上下文注入的那个 `spring.datasource.*` 池没限** —— 这正是漏掉的那一个 |
| **性质** | **测试基建配置缺陷**（非产品缺陷）：不报「功能错」，只让**基线不可复现** |
| **危害形态** | ⛔ **本项目第四次同形态**：F-14（测试没跑起来）、CP-1/CP-2（反证假阴性）、A-2（断言无判别力）、**本次（绿灯的条件不可复现）**。<br>**共同点：都不是「红」，而是「在别人复现时未必还绿」** |
| **建议修法** | ① 在 IT 的 `@TestPropertySource` 统一加 `spring.datasource.hikari.maximum-pool-size=2` + `minimum-idle=0`；② 或提高容器 `max_connections`；③ 长期：把 IT 的公共属性抽成基类/共享配置，避免每个 IT 各写一份（当前 25 个 IT 类各带一份 `@TestPropertySource`） |

> 📌 **这两个发现的共同教训**：
> 「全量构建通过」这句话**本身携带一个没说出来的前提**——「当前没有运行实例占用 MQ 与 DB」。
> 前提不写出来，下一个人（或下一轮的我）就会在**条件不同**时得出「怎么红了」的错误结论，
> 甚至反过来怀疑代码。**基线必须连同其成立条件一起记录**，否则它就不是基线，是运气。
