前端结构评审与重设计方案

错题归因辅导平台 · 多租户 SaaS Agent · 评审对象：frontend/（React 18 + react-router 7 + TS strict）· 2026-10-23

本报告基于源码逐页审查，先给出「布局 / 交互流程 / 功能组织」三类评估与问题清单，再提出以「角色分面（perspective）」为核心的重设计方案，最后梳理需要后端配合调整的字段、数据结构与业务逻辑，形成可落地的协作清单。

0 · 评审范围与方法

逐文件审查了路由表、应用外壳、设计 token、14 个页面组件、API 客户端与类型契约。重点不在视觉美化（现有「批改纸」设计语言已高度自洽、克制、且合规意识强），而在信息架构、导航逻辑、跨页操作路径，以及与后端的契约边界。

结论先行：视觉与状态纪律是资产，信息架构是短板。 最大根因不在前端代码，而在后端契约缺口（尤其登录响应不含 roles、租户上下文不随会话透传），它们让前端被迫把「所有管理功能无差别地暴露给每个登录者」。

2 · 评审发现与问题清单

2.1 信息架构与导航 P0

  • 导航不区分角色（根因：后端 G1）。 侧栏把学生功能与管理/运维功能平铺给每一个登录者。学生也能看到「审批台 / 语料管理 / 系统健康」。RequireRole 当前是空操作（void area），仅做登录校验。这是最影响专业度的问题。
  • 受众混排，缺少「分面」。 同一侧栏里既有「发起辅导 / 知识检索」又有「Agent 配置 / 系统健康」，没有把"终端用户面"和"治理运营面"分开。
  • RAG 子系统被拆到两个分组。 "知识检索"在"辅导"组，"语料管理"在"治理"组——两者同属知识库，却被导航语义割裂，用户难以建立"检索/管理是一件事"的认知。
  • 两套审计入口语义重叠。 /audit（运维）与 /config/audit（配置）查的是同一张审计表，后者只是 resourceType=config 的过滤视图，却占用两条独立导航，且文案"配置变更审计"会误导（实际是"配置查看"留痕，无变更）。
  • 死链：工作台"学习画像"指向 /profile/current。 路由是 /profile/:studentId，字面量 current 会被后端当作学号返回 notFound，最终显示"找不到这个匿名编号"——一个看起来像 bug 的入口。
  • 配置组过度细分。 6 个配置子页（总览/运行容量/工具审批/合规/审计/Agent），其中"合规与零保留""配置变更审计"长期只读或空态，对管理员也是认知负担。
关键判断

导航问题的"解药"不在前端多写几行 ROLE_PERMISSIONS 副本（现有副本已与后端静默漂移），而在后端把 roles 放回登录响应。在此之前，任何"按角色隐藏菜单"都是猜——而猜错会让无权用户点进去被 403，体验比"看不到入口"更糟。重设计方案据此分两阶段（见 §3.6）。

2.2 布局与视觉 P1

  • strengths（应保留）： "批改纸"隐喻统一、克制；批改红只用于错误/阻止态（R1 纪律）；状态色低饱和；题目区用宋体、界面区用黑体，字体即层级；五态（默认/加载/空/错误/未开放）纪律严格；焦点环、reduced-motion、sr-only 等可达性基线到位。这是成熟且独特的设计语言，不应被推倒。
  • 缺少面包屑。 深层页（进度/结果/详情）没有返回上级的路径指示，用户从结果页回不到列表。
  • 顶栏身份区是"负信息"。 显示"身份未由服务端提供"——真实但伤专业度；会话建立后应展示租户/角色（待 G1）。
  • 中屏导航折叠粗糙。 ≤1023px 时侧栏收成图标条、仅显示首字，信息损失大；移动端转顶部横滑标签，但分组标题丢失。
  • 无跨页上下文/全局检索。 发起辅导后进入进度页，没有"本次辅导"的常驻上下文；学生无法从任意页快速跳回自己的记录。

2.3 交互流程 P1

  • 知识检索 / 语料管理均需手填租户 UUID。 因 RAG 库不存租户副本、读会话变量，跨进程调用必须显式带 X-Tenant-Id。填错不会报错，只会"查不到数据"，是高频迷惑源。这是后端契约问题在前端的暴露。
  • "发起辅导"无 Agent 选择。 agentId 写死为环境变量（G2）。多 Agent 切换只能改配置，用户无感知。
  • 工作台"本设备发起的辅导"用 sessionStorage 假列表。 因为后端没有"我的/近期辅导"列表接口，前端用本地存储冒充，并已在文案里诚实标注范围——但终归是权宜。
  • 生成回答调用漏传租户头（潜在 bug）。 generateRagAnswer 未接收 tenantId 参数（检索路径 retrieveChunks 有），一旦生成端点上线即会因缺头 400。

2.4 功能组织 P2

  • 治理页长期空态风险。 审批台/处置台依赖 Worker 真实创建 approval / UNKNOWN operation，而当前 run_event 仅 RUN_CREATED 由生产写入，相关治理数据几乎不出现，页面长期空白（虽已诚实标注）。
  • 结果页"解题步骤/错因归类"结构恒空。 steps/weaknesses 无写入方，页面稳定显示"没有步骤记录"——这是真实空态，但对学生而言像"功能没做完"。
  • 学科/年级词表两份口径。 发起辅导用 ['数学'…6 科 / 初一~初三]，RAG 用 RAG_SUBJECTS（9 科 / 一年级~高三）且前端硬编码。口径不一致且易漂移。

2.5 数据诚实性 P2

现有五态纪律与"不编造"红线（C5/C6/C7、合规白名单、PIPL 纵深防御）是行业少见的严谨实现，应作为基线固化。唯一隐患：当某区块"结构恒空"时，学生侧体验接近"半成品"。解决方案不是编造，而是把"未产出"明确归因于后端能力进度（已在多数页面做到，可统一话术）。

3 · 重设计方案

3.1 设计原则（沿用 + 收敛）

  • 保留批改纸隐喻、批改红仅用于错误、宋体分隔题目区、五态纪律、合规白名单。
  • 新增：以"角色分面（perspective）"重组导航；补面包屑与顶栏身份；用"工作台聚合"替代假列表；把知识库检索与管理合并为一组。
  • 收敛：配置组精简（合并只读/空态页），审计入口合并为一条（配置查看留痕作为过滤而非独立页）。

3.2 新版信息架构：按"分面"而非"功能域"

把现有 17 条路由重排为 3 个分面 + 1 个运维子集。分面决定侧栏可见性（角色到位后由后端 roles 控制），而非把所有入口摊给所有人。

3.3 导航结构（角色到位前的过渡态）

在后端 G1 补齐前，侧栏先按"分面"分组展示但全部可见（与现状一致，不引入假判定），仅做视觉分组；G1 到位后，RequireRole 依据后端 roles 隐藏无权分面。过渡期即在每个分面标题下加一行小字说明"该分面通常需要 X 角色"。

3.5 视觉优化建议

必做

  • 顶栏加身份条：登录后显示租户 + 角色 chip（替代"身份未由服务端提供"），G1 前显示"身份待后端补充"。
  • 所有详情页加面包屑：如 检索记录 / run-123 / 归因结果。
  • RAG 两页自动带租户（G1 后从会话取），移除手填框，仅保留"高级覆盖"。

建议

  • 中屏折叠改为"分组图标 + 悬浮 tooltip 全名"，而非仅首字。
  • 发起辅导页增加 Agent 选择（多 Agent 时），默认用后端首个可用 Agent。
  • 统一"未产出/待后端能力"话术模板，避免每个页面各写一套。
  • 列表页（检索记录/审批/处置/审计）统一"筛选条 + 加载更多"为共享组件，减少重复实现。

5 · 前后端协作需求清单

按优先级排列。每项给出现状、问题、建议与前端收益。前端已用"诚实边界"缓解的部分，标注"前端已缓解"，但仍建议后端闭环以消除体验折损。

编号优先级需求现状 / 问题后端建议前端收益
B1P0 登录响应返回 roles 当前 LoginResponse 不含 roles（G1），RequireRole 空操作，所有管理功能无差别暴露。前端已缓解：不伪造角色。但导航不分层。 POST /api/auth/token 返回 roles: string[]（与后端 ROLE_PERMISSIONS 同源，删前端副本）。 角色分面导航、顶栏身份、菜单按权隐藏，专业度质变。
B2P0 统一租户上下文透传 RAG 端点要求 X-Tenant-Id，因 RAG 库不存租户副本、读会话变量。前端被迫手填 UUID，填错静默空结果。 RAG 模块信任平台会话中的租户声明（两系统共用 JWT/principal），或提供 GET /api/me 返回当前租户；前端不再手填。 移除两个 RAG 页的租户输入框与 localStorage 记忆，消除高频迷惑。
B3P1 提供 canonical 学科/年级/册次/出版社词表 前端硬编码 RAG_SUBJECTS 等常量；与"发起辅导"口径不一致，且后端枚举改名即漏召回/400。 GET /api/v1/editions（或复用配置）返回受控枚举展示名；前端下拉全部由后端驱动。 消除版本漂移、漏召回；统一两处学科/年级口径。
B4P1 Worker 真正写入执行事件 + steps/weaknesses run_event 仅 RUN_CREATED 由生产写入；结果页 steps/weaknesses 恒空，进度页时间线降级。 Worker 在每个执行阶段写 run_event；归因结果写 steps/weaknesses（或明确哪些由模型调用记录工具产生）。 进度时间线、结果步骤/错因从"结构空态"变为真实内容。
B5P1 实现 /api/v1/retrieval/generate 前端已按"未接入"诚实呈现，但生成区长期空白；且 generateRagAnswer 漏传租户头（潜在 bug）。 实现端点（grounding on hitIds）；或返回结构化 501 + {code:"NOT_IMPLEMENTED"}；并统一补 X-Tenant-Id。 知识检索回答区点亮；修复潜在 400。
B6P1 提供"我的/近期辅导"列表 + 当前学生上下文 前端用 sessionStorage 假列表（已标注范围）；/profile/current 为死链。 GET /api/runs?scope=mine（游标分页）或最近 N 条；提供"当前学生"解析（或无此概念则前端移除该入口）。 工作台"近期辅导"真实化；修复死链；支撑"待核对"聚合。
B7P2 修复健康检查探针 /actuator/health 返回 500 + 业务错误体，前端只能改判结构（G14 未暴露组件级）。 返回真实 {status:"UP/DOWN", components:{...}}；暴露 DB/队列/磁盘等组件明细。 系统健康页从"绕行"变为真实可用 + 组件明细。
B8P2 token 有效期可配置 + 续期 expiresIn 硬编码 900，无 refresh（G13），到期硬跳登录。 读配置 auth.jwt.token-ttl-seconds；提供续期端点或 silent refresh。 减少"会话即将到期"打断；提升体验。
B9P2 配置键真正接线或明确标注 多个键 effective=false（声明但未接线），前端只能标"仅声明未接入"。 推进接线，或在 note 字段给出"预计何时接线"而非永久摆设。 配置页从"看得到改不了"的无力感中解脱。
B10P2 风险动作确实创建 approval / UNKNOWN 审批台/处置台依赖 Worker 在风险动作时创建记录；当前几乎不出现，页面长期空。 Worker 在需要人工确认/结果未知时落库；缺失则治理页形同虚设。 治理分面从"几乎总是空"变为有真实职责。
B11P3 发起辅导支持 Agent 选择 /api/agents 已可用但发起页写死 agentId（G2）。 保持现状或当存在多个 Agent 时由前端拉取并选择。 多 Agent 场景下用户可感知并选择。

前端侧可独立推进项（不依赖后端）

  • F2：修复 /profile/current 死链——改为"输入匿名编号"或移除该入口。
  • F3：全站补面包屑（进度/结果/详情页）。
  • F4：合并"配置变更审计"为审计查询过滤视图，删冗余导航。
  • F5：顶栏身份条占位（G1 前显示"身份待后端补充"，G1 后显示租户/角色）。
  • F6：列表页（检索记录/审批/处置/审计）抽取共享"筛选条 + 加载更多"组件，减少重复与配额风险。
  • F7：统一"未产出/待后端能力"话术模板。

6 · 实施建议（里程碑）

阶段 A · 前端可独立（1–2 天）

  • F1 分面导航重排 + F2 死链修复 + F3 面包屑 + F4 审计合并 + F5 身份占位。
  • 不引入假角色判定，仅做视觉分组与文案。

阶段 B · 后端契约闭环（依赖 B1/B2/B3）

  • 登录返回 roles、租户透传、词表端点上线后，F5/F6 接真实数据，RequireRole 启用真判定。

阶段 C · 数据真实化（依赖 B4/B5/B6/B10）

  • Worker 写事件/steps/weaknesses、生成端点、近期列表、治理数据落地后，进度/结果/治理页从空态转为真实内容。

阶段 D · 打磨（B7/B8/B9，并行）

  • 健康探针修复、token 续期、配置接线，消除"声明≠生效"与硬跳登录。
评审结论

视觉与状态纪律是成熟资产，不要重做主题；真正的杠杆在两层：① 后端补齐 roles 与租户透传（B1/B2），让导航从"全摊给所有人"变为"按分面分层"；② 把 RAG 词表、近期列表、"我的辅导"等从前端硬编码/假列表，转为后端契约驱动。完成阶段 A+B 即可让产品从"工程师视角的中后台"升级为"分角色、有路径、无死链"的可交付应用。

评审基于 frontend/src 全量源码（路由、外壳、14 个页面、API 客户端、类型契约、设计 token）。标注"已缓解"项指前端已用诚实边界规避，但仍建议后端闭环。本报告为规划文档，不直接修改代码；落地项见 §6 里程碑。
