## 0. 先把两件事分清楚

提问里的「平台级目录的健康度」很容易和两件**已经存在**的事混淆。本方案要补的是它们**都没覆盖**的第三块：

| # | 已有的东西 | 抓什么 | 抓不到什么 |
|---|---|---|---|
| ① | `ConfigValidationGate`（`agent-application/.../cap/ConfigValidationGate.java:38`） | **单次发布命令内部**的自洽闭包：Skill 声明的 Tool / MCP 必须在**这次请求**的发布集合里 | **跨已发布目录**的状态：指针指向的行自洽吗？A 版本改了，引用它的 B 版本还用旧假设吗？ |
| ② | `MultiAgentSchemaStructureTest` + `MultiAgentSchemaIT` | **三张多级 Agent 表**（`agent_invocation` / `cap_agent_child_ref` / `cap_result_contract`）的 DDL 结构不变量 | **平台级目录三张表**恰好**不在**覆盖范围（06 §剩余缺口原话）；且它断言的是 **DDL 形态**，不是**数据自身的一致性** |
| ③ | `TaintVerifier` / `AuthzShadowHooks.shadowTaint`（逐行染色） | **读出来的每一行**归属是否越界 | 目录本身**长得对不对**：一行一行的「合法」可以拼出一个**系统性错误**的目录 |

> **一句话**：① 管「这次发布带的东西齐不齐」，② 管「表建得对不对」，③ 管「这行是谁的」。
> 本方案补的是 **「当前生效的这一版平台级目录，作为一个整体，是不是一个自洽、可用、可解释的状态」**。

## 1. 与逐行 taint 的区别与适用场景

### 1.1 本质区别（四条轴）

| 轴 | 逐行 taint（行级染色） | 目录结构完整性（整体性 Gate） |
|---|---|---|
| **判定对象** | 单行（`RowAttribution`） | **整个目录的拓扑**（节点 + 边 + 当前指针 + 生命周期状态） |
| **判定时机** | **运行期**，每次读后 | **配置期**（发布/迁移被接受之前）+ **巡检期**（周期性对活库跑） |
| **判据性质** | 谓词式：「这一行的 `tenant_id` 是否落在主体的 `ScopeFilter` 内」 | **不变量式**：「全目录必须满足 N 条结构性命题」，任一不成立即违规 |
| **失败语义** | 单点：抓一行、抛一次、计一次 `AUTHZ_MISMATCH` | **全局**：一个坏节点可以「传染」整份快照（见 §1.3） |
| **对「合法但错误」的检出** | **零**。每一行都合法 ⇒ taint 全绿 | **主战场**。指向一个 DEPRECATED 对象、allowlist 三态被归一化、语义等价但 id 不同 —— 行行合法，目录已病 |

### 1.2 为什么 taint 在本项目里**天然**管不到平台级目录

这是本方案最重要的一个观察，不是理论推演：

平台级三张表是 **`namespace='platform'`、无 `tenant_id`、无 RLS**（`deploy/sql/platform/01_platform_ddl.sql`；见 [数据库用户与权限梳理](../数据库用户与权限梳理_2026-11-01.md) §「4 张无 RLS 表」）。而 `TaintVerifier` 的核心参数就是 `rowTenantId`（`shadowTaint(type, subjectTenantId, rowTenantId)`）。

**平台级行根本没有「行租户」可染。**

这直接命中 12 文已经踩过的那个坑：*「聚合查询（`terminationDistribution`）移除该类调用 —— 聚合结果无行租户，强比即同义反复」*。给平台级目录套 taint，只有两种结果：

1. 找不到 `tenant_id` 列 ⇒ 跳过 / 恒通过 ⇒ **虚假覆盖感**（比不做更危险，12 文的原话）；
2. 硬塞一个 `tenant_id` ⇒ 污染租户语义、RLS 策略被迫改动 ⇒ 打开 C34-2 / V27 刚刚关上的后门。

> 所以「把平台级目录纳入 Gate」**必然只能走结构完整性路线** —— 这不是和 taint 二选一，而是 taint 在这里**物理上不适用**。这反过来也解释了为什么本方案必须**独立成项**，而不能「顺便加进染色」。

### 1.3 适用场景划分（什么时候用哪个）

| 场景 | 用 taint | 用结构 Gate | 理由 |
|---|---|---|---|
| 租户读 `cap_agent_def` / 运行记录 | ✅ | — | 有 `tenant_id`，行级隔离是核心命题 |
| 平台级目录的**读** | ❌ 不适用 | ✅ 巡检 | 平台行对所有租户**本就全局可读**，染不出东西来 |
| 平台级目录的**写发布** | ❌ | ✅ **阻断** | 写是全平台生效的，错一次伤全部租户 |
| 生命周期迁移（停用） | ❌ | ✅ **阻断** | 停用是单向终态，按错一次不可逆 |
| Skill 改了 `declared_tools` | ❌ | ✅ **阻断（传染检测）** | 影响面可能是**全平台所有 Agent**，见下 |
| 单次请求的越权访问 | ✅ | — | 行级、实时 |
| 租户 A 读到了租户 B 的行 | ✅ | ❌ | 结构 Gate 不看租户维度 |

### 1.4 「传染」—— 为什么整体性必须单独立项

06 §管理台那节记录过一个已修的真实缺陷：前端补闭包时重发的 MCP Server spec **必然没有凭据引用**（目录接口从不回显定位符），后端为它建新版本行 ⇒ 指针移过去 ⇒ **该 Server 在全平台范围内认证失效**。

> 「一个『改 Skill 的声明清单』的操作，静默改掉了全平台的 MCP 认证。」

这类缺陷的形态是：**局部操作、全局后果、每一行都合法**。逐行染色对它的检出能力是**结构性的零**——没有任何一行的归属有问题，问题在于**行与行之间的关系**。这正是结构 Gate 的定位。

## 2. 纳入方式

### 2.1 总原则：**并列的第三道 Gate，不是 taint 的子项**

```
                        ┌─ G-CAP-0  配置期闭包（已有：ConfigValidationGate）
   一次平台级发布/迁移 ──┼─ G-CAP-1  目录结构完整性（本方案·阻断）
                        └─ DDL 结构不可变 ─ MultiAgentSchemaStructureTest（已有，扩展覆盖三张 cap_* 表）

   运行期逐行读 ────────── R 逐行染色 TaintVerifier（已有；平台级目录不适用）

   定期巡检活库 ────────── H 目录健康度（本方案·只报告，不阻断）
```

**关键设计取舍：分「阻断」与「报告」两档，不把健康度全做成硬门禁。**

硬阻断的判据必须是 **「确定性、二值、违反即真实缺陷」** 的结构不变量（孤儿引用、状态自相矛盾、三态归一化）。
凡是**度量型**的（覆盖率、孤儿比例、新鲜度、危险组合计数）一律**只报告 + 定阈值告警**，不阻断发布 —— 否则会把「目录有 2 个历史孤儿」这种存量事实变成谁也发不了版的瘫痪，最后一定是加白名单绕过。

### 2.2 判定标准：结构不变量清单（Health Invariants）

平台级目录的健康度，本方案定义为 **8 条不变量**（HI = Health Invariant）。每条都标了**是否阻断**、**依据**、**反证方式**。

| ID | 不变量 | 级别 | 依据 | 反证（改坏哪一处必须变红） |
|---|---|---|---|---|
| **HI-1** | **指针完整性**：`cap_config_pointer` 的平台槽位必须指向**存在且已发布**的版本行；指针不得悬空 | 🔴 阻断 | 06 §3.1 生效范围 | 删掉指针指向的版本行 ⇒ 红 |
| **HI-2** | **引用可达性**：`cap_skill_def.declared_tools[]` 中每个 id 必须存在于 `cap_tool_def`；`declared_mcp[].serverId` 必须存在于 `cap_mcp_server_def`。**按「生效版本」判定，不是「任意版本存在过」** | 🔴 阻断 | 06 §2 引用约束 | 把 Skill 的 `declared_tools` 改成不存在的 id ⇒ 红 |
| **HI-3** | **传递闭包**：MCP 型 Tool 绑定的 Server 必须在 `declared_mcp` 中出现（**第二跳**）。省掉这一跳 ⇒ 运行期 `MCP_NOT_BOUND`，且被拒对象不在用户视野内 | 🔴 阻断 | 06 §「传递闭包这一跳不能省」 | 让一个 MCP 型 Tool 的 Server 不在 Skill 声明里 ⇒ 红 |
| **HI-4** | **无悬空引用**：**已发布**版本不得引用 `DEPRECATED` 对象。DEPRECATED 为单向终态、不可新引用 | 🔴 阻断 | 06 §3.2 | 停用被引用的 Tool 后，仍让含它的 Skill 版本成为生效版本 ⇒ 红 |
| **HI-5** | **三态不被归一化**：`declared_mcp[].tool_allowlist` / `exposed_tool_allowlist` 的 `null`（未配置 = 全集）/ `[]`（显式空）/ 清单 **三态必须可区分**；任何替换/补齐路径不得把 `[]` 写成 `null`（= 权限放宽） | 🔴 阻断 | 06 §「`null` 与 `[]` 的三态」 | 把某 Skill 的 `[]` 改成 `null` ⇒ 红 |
| **HI-6** | **凭据引用不被静默清空**：MCP Server 新版本行的 `credential_ref` 若**由非该 Server 的详情页**触发产生，而上一版本有引用、新版本为 null ⇒ 阻断（这是 §1.4 传染缺陷的**通用化**，不只在 UI 层拦） | 🔴 阻断 | 06 §「闭包补齐的 fail-closed」 | 让补齐路径重发一份无凭据的 Server spec ⇒ 红 |
| **HI-7** | **生命周期状态与发布状态不矛盾**：`published_at` 非空但 `lifecycle_state=DEPRECATED` 是**合法**的（停用是终态、`published` 仍为 true）；但 `lifecycle_state=PUBLISHED` 而 `published_at` 为空 是**矛盾**，必须阻断 | 🔴 阻断 | 06 §「状态列把『已停用』显示成『已发布』」 | 造一个 `PUBLISHED` 但 `published_at IS NULL` 的行 ⇒ 红 |
| **HI-8** | **孤儿节点**：已发布但**无任何引用方**、且非活跃入口的对象 | 🟡 **仅报告** | 卫生度，非正确性 | — （度量，不反证） |

补充的热度指标（**全部仅报告**，进台账与看板，不进阻断判据）：

- 覆盖率：有多少 Agent/Skill 引用了平台级对象；
- 新鲜度：每个对象的「距上次发布天数」；
- **危险组合计数**：`WRITE_EXTERNAL` 风险 × `trustTier=public` × 无审批 的对象数 —— 单独成一项看板数字；
- 停用残留：仍被存量 Run 快照引用的 DEPRECATED 对象数。

> ⚠️ **HI-2 的「生效版本」口径是这套里最容易写错的一处**，与「结构断言的是跨多版本迁移后的有效结构，不是任何单个脚本的原文」是同一类错误：如果按「任意版本存在过」判定，那么「v1 引用的 Tool 被删了、v2 已改好」会被误报；反之按「生效版本」判定时，**不许用 `max(version)` 近似**（06 §：当前版本**不以 max(seq) 选择**，要看指针）。

### 2.3 落点：三个执行位置

| 位置 | 组件 | 触发时机 | 失败语义 |
|---|---|---|---|
| **A. 配置期（主阻断面）** | 扩展 `ConfigValidationGate`：新增 `validateCatalogIntegrity(command, catalogSnapshot)` | 平台级发布 / 回滚 / 生命周期迁移，在**申请被接受之前** | 抛 `ConfigPublishRejectedException` + **稳定原因码**（见 §2.4）；申请单标 `FAILED` 并带原因 |
| **B. 架构期（防退化）** | 扩展 `MultiAgentSchemaStructureTest` 的 `GUARDED_TABLES`，纳入三张 `cap_*` 表 | CI 构建期 | 测试红 |
| **C. 巡检期（看存量）** | 新增只读脚本 `scripts/catalog-health-check.sh`（对齐既有 `platform-audit-ticket-scope-retrofit-check.sh` 形态） | 按需 / 定时；**只读、不入库、不阻断** | `exit 1` 并输出违规清单 |

⚠️ **为什么 A 之外还必须有 C**：A 只能保证「**新增的**发布是健康的」，管不住**存量** ——
这正是 `MultiAgentSchemaStructureTest`（脚本层）与 `MultiAgentSchemaIT`（库层）**两层缺一不可**的同一个理由：**脏数据不是经当前这道门进来的，它是历史遗留**。
而 C 只**报告**存量、不阻断发布（见 §2.1 取舍），避免存量问题瘫痪发布通道。

### 2.4 原因码：可分辨，不合并

沿用既有纪律（「闸门语义可分辨」，400/403/409/503 必须分开）。结构 Gate 的拒绝必须**逐条可分辨**，否则运维看到「发布失败」会去改自己的填法，而真因是目录里有个历史孤儿。

| 原因码（建议） | 对应 | 谁该处理 |
|---|---|---|
| `CATALOG_POINTER_DANGLING` | HI-1 | 平台运维（指针/版本行） |
| `CATALOG_REF_UNREACHABLE` | HI-2 | 作者（声明写错） |
| `CATALOG_MCP_NOT_BOUND_TRANSITIVE` | HI-3 | 作者 |
| `CATALOG_DEPRECATED_REFERENCED` | HI-4 | 作者（先换版本）或运维（复核停用） |
| `CATALOG_ALLOWLIST_TRI_STATE_COLLAPSED` | HI-5 | 实现方（补齐逻辑 bug） |
| `CATALOG_CREDENTIAL_REF_DROPPED` | HI-6 | 实现方（**必是代码缺陷**，不是作者错误） |
| `CATALOG_LIFECYCLE_CONTRADICTION` | HI-7 | 数据修复 |

> 区分 `TOOL_NOT_DECLARED` / `MCP_NOT_BOUND`（运行期、申请人）与 `CATALOG_*`（配置期、目录自身）是刻意的：**运行期码是「这次调用不被允许」，配置期码是「这份目录本身有病」**。把两者混用会让人在调用失败时去查权限，实际该查目录。

### 2.5 通过 / 阻断条件（判定表）

| 条件 | 判定 |
|---|---|
| 本次发布命令**未触及**任何 HI-2/3/4 相关对象 | **放行**（不因全局存量问题阻断无关发布 —— 见下） |
| 本次发布命令触及的对象，**发布后**的目录状态满足 HI-1…HI-7 | **放行** |
| 任一 HI-1…HI-7 在新状态下不成立 | **阻断**，带 §2.4 原因码，申请单记 `FAILED` |
| 存在**历史存量**违规（非本次引入） | **放行 + 告警 + 记入台账**（不阻断，但必须在证据包里可见） |
| 巡检（C）发现任一 HI-1…HI-7 违规 | `exit 1`，输出对象级清单；**不阻断发布** |

⚠️ **「只判定本次触及对象」这条边界必须显式写死**：
否则一旦目录里有 1 个历史孤儿，**全平台的发布通道就永久瘫痪**，而这不是安全要求，是可用性事故。
这也是 `ConfigValidationGate` 现有设计已经承认的边界 ——「门禁的判定边界是**发布集合内部**」，本方案只是把它从「单次请求」扩展到「单次请求 + 其引用到的生效版本」。

## 3. 风险与局限

### 3.1 结构性风险（方案本身的形态带来的）

| # | 风险 | 为什么会发生 | 缓解 |
|---|---|---|---|
| **R1** | **「只判定触及对象」留下逃生通道** | 作者可以不碰有问题的对象就把别的东西发出去 | 巡检 + 台账把存量摆到台面上；存量清理单独立项、有 deadline，不因放行而隐身 |
| **R2** | **快照读的时序窗口** | Gate 读目录快照判定 → 判定通过 → 真正的写入之间，目录可能被另一笔发布改掉 | 判定与写入**同一事务**，或在写入前对指针做 **CAS**（与既有 `expectedFrom` / CAS 基线同口径） |
| **R3** | **健康度被当成安全证明** | 结构全绿 ≠ 安全。HI 只证明「目录自洽」，不证明「授权正确」 | 文档与证据包里明写：结构 Gate **不**替代 05 的授权判定，也**不**替代 taint 的行级隔离 |
| **R4** | **阻断点选错 = 瘫痪或失效** | 阻断太早（申请时）→ 申请单留不下来、无法留痕；阻断太晚（执行时）→ 已通过双人复核才失败，浪费审批 | 阻断在「执行」前、**申请可先落库**，失败时把申请单标 `FAILED` 并带原因（对齐既有 MA-T27f「失败留痕」） |

### 3.2 判定质量风险（可能误报 / 漏报）

| # | 风险 | 说明 | 缓解 |
|---|---|---|---|
| **R5** | **误报：合法的收紧写法被拒** | 「Skill 的 `riskCeiling` 低于其声明工具的风险」是**合法的**收紧配置，不是错误（`ConfigValidationGate` 原注释已明确） | 结构 Gate **不**碰风险覆盖关系；只判定引用与状态，不判定宽严 |
| **R6** | **漏报：语义等价但 id 不同** | `auth_skill` 与 `auth_skill_v2` 是两个合法 id，结构上毫无关联，但**语义上是同一族的演进** | 结构 Gate **认不出**；需另建「对象族」元数据（同类不同名），属独立需求 |
| **R7** | **漏报：方向性的危险组合** | HI 全部满足，但「一个 `WRITE_EXTERNAL` Tool 被 `trustTier=public` 的 Skill 广泛引用」是危险的 | 只作为**度量项**进看板（§2.2 危险组合计数），不作为阻断 —— 因为它不是「错误」，是**风险偏好**，得由人做决定 |
| **R8** | **断言实现本身的脆性** | 若像 `MultiAgentSchemaStructureTest` 那样做**文本解析**，改写方式超出解析器能力时会漏判（06 §剩余缺口已如实登记） | 巡检走**真实库查询**（对齐 `MultiAgentSchemaIT` 的「库层不可省」），不解析脚本 |

### 3.3 运维与演进风险

| # | 风险 | 缓解 |
|---|---|---|
| **R9** | **存量孤儿一次性集中暴露**，可能量级很大，团队会本能地加白名单 | 首次巡检**只出清单不出结论**，先分级（真缺陷 / 历史遗留 / 无害孤儿），再决定哪些升为阻断 |
| **R10** | **不变量清单会腐化** —— 新增字段/新对象类型（如未来开放租户私有 Tool）后 HI 覆盖不到 | 把 HI 清单挂进 [09 需求追踪矩阵](../多级%20Agent优化/09_需求追踪矩阵.md)，每条一个 AC；新增平台级对象类型时**强制**新增对应 HI |
| **R11** | **双写期误判** | 12 文 P2 双写期有 `DualWriteAgentManagePort` 最终一致衔接；结构 Gate 若在双写窗口内判定，会把**写入延迟**误判为**孤儿** | Gate 判定走**权威源**（发布头 + 指针），不走投影；投影差异另设对账，不进 Gate |
| **R12** | **巡检与 Gate 口径漂移** | 两处各写一套判定，迟早不一致（项目里已多次出现过这类「两处各推导一次」的问题） | 判定逻辑**收敛为一个共享实现**（建议 `CatalogIntegrityChecker`），Gate 与脚本都调用它；仅取数方式不同（内存快照 vs 活库查询） |

### 3.4 明确**不**解决的事（写下来避免过度期待）

- ❌ 不解决跨租户行级泄漏（那是 taint 的地盘）；
- ❌ 不解决「谁有权调这个 Tool」（那是 05 分层授权的地盘）；
- ❌ 不解决 DDL 结构漂移（那是 `MultiAgentSchemaStructureTest` / `MultiAgentSchemaIT` 的地盘）；
- ❌ 不解决语义层面的「该不该存在这个对象」（那是治理/评审的地盘）。

## 4. 落地顺序建议（最小、可验证、可回退）

| 步 | 内容 | 产出 | 阻断? |
|---|---|---|---|
| **S1** | 抽 `CatalogIntegrityChecker`（纯函数：目录快照 → 违规清单），先实现 HI-2 / HI-4 / HI-5 | 单测 + 每条 HI 的**单点反证** | 否 |
| **S2** | 巡检脚本接上 checker，对活库跑一次，出**存量清单** | `scripts/catalog-health-check.sh` + 台账 | 否（只报告） |
| **S3** | 接进 `ConfigValidationGate`（仅 HI-2/4/5，只判定触及对象） | `CONFIG_PUBLISH` 用例 + 反证 | **是** |
| **S4** | 补 HI-1 / HI-3 / HI-6 / HI-7 | 同上 | **是** |
| **S5** | `MultiAgentSchemaStructureTest` 覆盖三张 `cap_*` 表（补 06 登记的缺口） | 构建期红 | **是**（CI） |
| **S6** | HI-8 与危险组合计数进看板 | 指标 | 否 |

**建议前两步（S1/S2）不要阻断** —— 先用它的输出回答一个问题：**存量里到底有多少是真缺陷？**
这个数字决定了 §3.1 R1 / 3.3 R9 的严重程度，也决定了后面要不要把某条 HI 降级为仅报告。

## 5. 与既有体系的接口一致性检查

| 既有纪律 | 本方案怎么遵守 |
|---|---|
| 作用域不混装（`ConfigValidationGate.validateScopeConsistency`） | 结构 Gate 只在 **PLATFORM 作用域**发布上做全目录判定；TENANT 发布不触发全局判定 |
| 双人复核不因「平台级」退化 | Gate 排在审批**之前/之后均可**，但**不得**因为结构 Gate 存在就跳过申请单 |
| 失败留痕（MA-T27f） | 结构 Gate 拒绝时申请单标 `FAILED` + 原因码 |
| 闸门语义可分辨（400/403/409/503） | 新增 `CATALOG_*` 原因码，**不**与运行期码复用 |
| 每条断言必须能单独证伪（`MultiAgentSchemaStructureTest` 的反证纪律） | §2.2 每条 HI 都有「改坏哪一处必须变红、其余保持绿」 |
| 结构权威源 | 判定基于**生效目录**（发布头 + 指针），不基于迁移脚本原文 |
| 两层门禁缺一不可 | 配置期 Gate + 库层巡检，两者都保留 |
