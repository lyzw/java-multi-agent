# 阶段 2：分层授权设计的合理性评估与改进建议

> 命题：「**Agent 限定可用 Skill，Skill 声明可用 Tool 与 MCP**」
> （下文称 **Agent → Skill → (Tool, MCP) 分层授权 / 组合式能力声明**）。

## 0. 结论先行

| 维度 | 结论 |
|---|---|
| 是否合理 | ✅ **方向正确，建议采纳**。符合本平台「模型只建议、平台执行」哲学，且与已成熟的 `AuthorizationService` / `ToolRiskLevel` / `EffectiveConfigResolver` / `RunConfigSnapshot` 同构。 |
| 是否「直接照搬」 | ⚠️ **需修正一处根本问题**：若字面理解为「Agent 只能经 Skill 使用 Tool、Skill 必须独占声明全部 Tool/MCP」，则会把**已有、成熟、独立的 Tool 授权**错误地收拢进 Skill，**缩小而非扩大**授权面、制造**配置冗余**与**组合爆炸**。 |
| 改进方向 | 采用「 **Skill 是 Tool/MCP 的可选能力包 + Agent 可旁路直连原子 Tool（经统一校验）**」的**非排他、双层**模型；授权以**授权快照 + 最严合并**落地，并纳入**单调收紧 + 审计**。 |

---

## 1. 为什么方向正确（优势）

1. **与既有架构同构、零冲突**
   Platform 已有：`Agent(版本快照)` / `Tool(RiskLevel+Gate)` / `AuthorizationService(role→action)` /
   `EffectiveConfigResolver(default⊕override)` / `RunConfigSnapshot(创建时固化)`。
   分层授权只是在 Agent 与 Tool 之间**补一个 Skill 抽象 + 显式绑定**，
   全部复用现有 fail-closed / 快照 / 审计机制，边际成本低。

2. **提升可复用性与可解释性**
   - 一个 `finance_audit` Skill 可被多个 Agent 复用；
   - 审计时可回答「这个 Run 用了哪些 Skill、每个 Skill 调了哪些 Tool」，
     比「Agent 直接调一堆散落 Tool」更易合规复核。

3. **为 MCP 留好接入位而不越权**
   设计文档已定性「MCP 是 Tool 的一种来源协议，不替代平台授权」。
   把 MCP 作为 Skill 可声明的**一类 Tool 来源**纳入，
   既符合标准化接入趋势，又守住「平台决定谁能用、用哪个资源」的边界。

4. **支持最小权限与按域收敛**
   通过 Skill 把「教育-学情」域的工具聚合成最小能力包，
   Agent 只需授权整包，减少逐工具声明，也更接近最小权限原则。

## 2. 潜在问题（必须正视）

### 2.1 权限越界（最关键，分四类）

| 类型 | 说明 | 对策 |
|---|---|---|
| **(a) 声明期越权** | Agent 授权了一个其角色本不应使用的 Skill（如把 `WRITE_EXTERNAL` Skill 授给只读 Agent） | **校验时机**：Agent 发布时、Run 创建时、执行时三处校验；Skill 内任一高风险 Tool 触发审批即整包审批要求 `maxWith` 抬升。 |
| **(b) 传递性放大** | Agent→Skill A、Agent→Skill B，A、B 各部分授权，**并集**可能远超 Agent 本应权限 | **授权面 = Σ(已授予 Skill 的授予集) ∩ Agent 声明**，且 Agent 可设 `maxRiskCeiling` 上限；任何 Skill 抬高 Agent 的审批/风险上限即记审计。 |
| **(c) 跨租户越权** | Skill/Tool/MCP 是**跨租户共享**还是**租户内私有**？ | **租户隔离原则**：共享能力默认 `READ` 风险、无副作用；Skill 可声明 `data_scope`（如 `tenant_local` / `cross_tenant`），跨租户声明**强制审批 + 强制最严**。 |
| **(d) 资源级越权** | Skill 声明了「能调 `get_student_profile`」，但未限制**哪些学生/哪些 MCP 资源** | **资源级授权不可绕过**：Skill/Tool 声明只决定「能否进入该能力」，**具体资源仍由 `AuthorizationService.isAuthorized(ctx, action, resourceId)` 在执行时逐资源判定**（沿用 P0-D03 红线 9）。本设计**不**试图用 Skill 声明替代资源级授权。 |

> **关键取舍 1**：Skill 层授权是**「能力可达性 + 审批/风险上限 + 数据域」**，
> **不是**资源级授权。资源级授权永远在 `ToolInvocationGate` 的执行时校验层完成。
> 这样既拿到「组合复用」的好处，又**不削弱**已有资源级边界。

### 2.2 组合爆炸

- 字面理解下若「每个 Agent 每个 Skill 都显式声明全部 Tool/MCP + 各风险级审批要求」，
  授权边 = O(Agents × Skills × Tools)。
- **对策**：
  1. **声明即白名单子集**：Skill 只能授权父 Agent「已声明可达」的原子，**不可新增父 Agent 没有的原子**（fail-closed 默认拒绝新增）；
  2. **审批要求/风险上限以 `maxWith` 合并**，不是逐层重写，减少冗余；
  3. **MCP 按「MCP Server + 白名单 tool-name 子集」声明**，而非「全部工具」，把组合维度压到可枚举。

### 2.3 配置冗余

- **双层（Agent 直连 Tool + Skill 包 Tool）会导致同一工具授权写在两处**，易漂移。
- **对策**：引入**「授权来源溯源 + 去重合并」**：
  - 授权解析结果 = `union(Agent.directTools, Σ Skill.tools) ∪ ...`，并标注 `source ∈ {agent, skill:<name>}`；
  - 解析后得到**唯一**「本 Run 可用能力图」，执行时**查图而非查声明**；
  - 写入时若两条路径声明同一原子且**要求不一致**，**取最严 + 报错拒绝**（沿用 `ConfigTighteningPolicy`「误导性文案比缺失更有害」）。

### 2.4 粒度控制

- 字面设计粒度是「包 (Skill)」级，无法表达「Agent 可复用 Skill 但禁掉其中某个高风险 Tool」。
- **对策**：**Skill 暴露 `toolGrants` / `mcpGrants` 为可被子集化的集合**：
  Agent 可对单个 Skill 的 grant 做 `deny`（黑名单）子集，但 **deny 只能收紧不能放松**（单调）。
  粒度模型：`Agent ──(allow/deny)── Skill ──(allow/deny)── (Tool | MCP-tool)`，
  三级都遵守单调收紧。

### 2.5 其他风险

| 风险 | 对策 |
|---|---|
| **循环引用**（Skill A 引用 B，B 引用 A） | 声明期静态检测，DAG 校验，违规发布即拒。 |
| **Skill 自身即风险放大器**（Skill 调 Tool + 调 MCP，组合后风险高于各自之和） | Skill 发布时计算**有效风险天花板 = max(子风险)**，并写入 Skill 元数据；Agent 授权时按此天花板判定审批。 |
| **不可变 version 漂移**（Skill 发布 v2 后 Agent 仍绑 v1 但语义变了） | Agent 绑定**必须带版本号**（`skill:edu-analysis@3`），版本变更需重新发布 Agent 版本 + 走配置变更流。 |
| **MCP 服务端不可控**（外部 MCP 可能暴露新工具） | **MCP 工具名白名单固化进 Skill 版本快照**（`mcpAllowList`）；MCP Server 侧新增工具不自动可达，必须 Skill 发版。 |
| **审批粒度失配**（Skill 审批一次后，内部多个 Tool 都放行） | Skill 授权是**「能力可达性」**，**不**代表审批。每个高风险 Tool 仍各自按 `ToolRiskLevel` 触发审批（沿用 `RiskBasedApprovalPolicy`），Skill 不合并审批次数。 |

## 3. 改进建议（落到配置模型）

### 3.1 非排他双层：Agent 既能「经 Skill」、也能「直连原子 Tool」

```
Agent ──┬──(direct)──> Tool   （原子直连，沿用现有 ToolInvocationGate 路径）
        └──(use)───> Skill ──┬──(declare)──> Tool
                             └──(declare)──> MCP Server (+ tool-name allowList)
```

- **Skill 对 Tool/MCP 是「可选能力包」**，不是「唯一通道」；
- **Agent 直连 Tool 仍被统一校验**：`Agent.directTools` 与 `Σ Skill.tools`
  在解析时合并为「本 Run 可用能力图」，执行时**查图**，路径无关。
- 这样**不缩小**现有 Tool 授权面（向后兼容），又能引入 Skill 复用。

### 3.2 单调收紧 + 最严合并

定义 `Grant = { subject, capability, riskCeiling, approvalRequirement, dataScope, source }`。
合并规则：
- **集合层（可达性）**：`⊆` 关系只能从父向子**收窄**（`deny` 白名单）。
- **强度层（审批/风险）**：`maxWith` 取**最严者**（沿用 `ApprovalRequirement.maxWith`）。
- **数据域**：`cross_tenant` 出现即强制 `approvalRequirement = REQUIRED` + `riskCeiling = WRITE_EXTERNAL`。

### 3.3 校验时机（三道闸门，fail-closed）

| 时机 | 校验内容 | 失败语义 |
|---|---|---|
| **Agent/Skill 发布期**（构建快照时） | 引用存在性、DAG/循环、白名单越界、`maxRiskCeiling` 计算、版本号一致 | 发布拒绝（4xx/5xx 区分） |
| **Run 创建期** | 用 Agent 版本快照 + Skill 注册表解析「本 Run 可用能力图」，固化进 `RunConfigSnapshot` | Run 创建 fail-closed |
| **执行期**（`ToolInvocationGate` 内） | **执行时重新授权**：资源级 + 风险级 + 审批 + 预算，**查能力图**而非查声明 | 拒绝 / 进入 UNKNOWN 对账 |

三道闸门**共享同一份授权判定器**（`CapabilityResolver`），但**输入不同**：
发布期用「声明源」、Run 期用「快照」、执行期用「快照 + 当前授权」。
这正是 `EffectiveConfigResolver + RunConfigSnapshot + AuthorizationService` 三件套的复用。

### 3.4 可观测性

- 每次能力解析结果落 `capability_graph` 表（租户隔离），随 Run 快照一起持久化；
- 审计字段补：`skill_used / mcp_server / tool_name / risk_ceiling / approval_required / source`；
- 拒绝事件写 `run_event` 并暴露原因码（`CAPABILITY_DENIED` / `CROSS_TENANT` / `CYCLE` / `STALE_GRANT` 等），
  便于事后复核「为何被拒」。

## 5. 阶段 2 结论（一句话）

**方向采纳，落点修正为「Skill 为可选能力包 + Agent 可直连原子 Tool」的非排他双层；
授权以「授权快照 + 最严合并 + 单调收紧 + 三道 fail-closed 校验」落地；
Skill 层只决定「能力可达性/数据域/风险天花板」，不替代 `AuthorizationService` 的资源级执行时判定；
MCP 作为 Tool 的一种来源协议纳入 Tool allowList，不单独建授权体系。**
