- **日期**：2026-11-04
- **范围**：《阶段一》任务 I2-2 · `CapEnforcementSwitch` 门禁「P5 发布指针读落地前不得在生产全局开启」
- **结论**：**P5 指针读路径已在代码库中完整实现并通过测试覆盖；「P5 未落地」这一当初的门禁理由已不成立。** 全量开启的唯一剩余前置是**运行时灰度验证**（连续阶段 AUTHZ_MISMATCH=0 + 工具可用率无退化）——这是必须 put 开关在低风险租户上跑出来的，静态代码层面无法替代。

## 1. 门禁文本回顾（为什么当初无法开启）

`CapEnforcementSwitch` / `CapEnforcementReadinessGuard` 明示：

> P1 的发布版本解析是**过渡实现**（对象级解析 + 回滚守卫），P5 必须替换为「当前指针 + CAS」的正式读路径；
> 在指针读路径落地前开启 CAP 授权链路，等于让授权判定依赖一个**已知不完整**的发布语义（取「最新已发布版本行」而非「指针指向的版本」）——回滚场景下两者会指向不同对象。

即：**能否全量开启 = P5 是否真正落地**。本文档逐条核实 P5 是否已落地。

---

## 2. P5 指针读路径 —— 四个构件核实（全部为既成事实）

| P5 要求（§6.3） | 实现构件 | 核实结论 |
|------|------|------|
| 当前指针实体 + 读路径：「指针 → 指针指向的 PUBLISHED release → object_versions → id→精确版本」 | `JdbcPublishedVersionPort.resolveFromPointer`（读 `ConfigPointerPort.current` → `findByReleaseId` → 校验 PUBLISHED → 解析 object_versions） | ✅ 已实现，fail-closed，绝不以 `max(seq)` 选当前版本 |
| CAS 当前指针（基于 expected 基线更新；失败→整事务回滚，无半成品） | `JdbcConfigPointerRepository.compareAndSet`（UPDATE...WHERE current_publish_seq IS NOT DISTINCT FROM ?；区分「指针不存在」与「基线已变」） | ✅ 已实现，含首次发布补插 + 并发防覆盖 |
| 版本行插入 + release 记录 + 指针 CAS 同事务原子提交 | `JdbcConfigPublishTransaction`（`TransactionalConnectionHolder` 包裹） | ✅ 已实现（这正是 PUB-1 要防的半成品形态已闭合） |
| 平台/租户作用域隔离，回滚切换指针且不恢复已撤权 | `PlatformOpsConfigPublishTransaction`（BYPASSRLS 平台通道）；rollback 用「新建 ROLLED_BACK 发布 + CAS 切指针」 | ✅ 已实现 |

**git 佐证**：`17d50f1feat(platform): W-PERM-P5 发布审计与生命周期` —— 指针/CAS 为已提交的正式实现，非占位。

## 3. 准入路径核实：真实走指针，而非过渡实现

- `ToolInvocationGate`（agent-worker，准入执行点）：**main 源树零 `findLatestPublished` 调用**；唯一能力链路是 `CapExecutionFlow`。
- `CapExecutionFlow` → `ClosureResolver`（装配为 `CachingClosureResolver`）→ 其内部用 `PublishedVersionPort.currentVersion / currentTenantVersion`（指针管道），并在 `isFresh` 二次校验时仍走 `publishedVersions` 计算当前版本（当 `findLatestPublished` 返回被回滚版本时，能识别陈旧闭包）。
- 发布流程通过 `CachingClosureResolver.invalidate(...)` 显式失效缓存（P5 配置发布后立即失效）。
- `findLatestPublished` 仅保留在**读/列表端点**（`CapabilityCatalogController` / `CapAgentDefinitionController` / `PlatformCapabilityConsoleController`）与测试夹具 —— 那是对外展示「最新已发布定义」的查询面，**不参与授权判定**。

**结论**：门禁最担心的「授权判定依赖取最近发布行的过渡语义」**在准入路径上不成立**。

## 6. 评估意见

1. **代码前置已闭合**：P5 指针读路径正式落地 —— 这是当初唯一写死「不得开启」的代码理由，现已不成立。
2. **仍不擅自翻转**：全量开启还差「运行时灰度证据」。开关默认值保持 `false`，由具备灰度租户的运行时验证驱动，方符合《阶段一》「不静默放行、以数据为凭」的纪律。
3. **可选的配套微调**（供后续开启时一并考虑，非阻塞）：
   - `CapEnforcementSwitch` / `CapEnforcementReadinessGuard` 门禁注释已过期（仍写「P5 落地前不得开启」），可在运行时验证通过后、开启那一刻随开启 PR 一并更新，避免留下误导性文本。
   - 新增一条**「读路径语义校验」防空回归测试**（可选）：「准入解析永远走指针且从未 fallback 到 findLatestPublished」的架构断言，防止未来有人把过渡实现挪回准入路径。

**最终一句话**：P5 不是「还没做」——它已经做完并在准入与 CAS 发布双侧被测试钉死；P0-1d 全量开启此刻的阻塞点已从「代码缺指针读」切换为「等待灰度阶段运行时数据」，那个数据只能靠低风险租户把开关打开跑出来。
