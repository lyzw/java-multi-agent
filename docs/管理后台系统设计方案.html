Agent / Tool / Skill / MCP 统一管理后台系统设计方案

在既有「统一配置与权限管控体系」领域模型之上，构建集中式管理控制台，覆盖四类实体的列表 / 详情 / 创建 / 编辑 / 删除 / 配置管理与运行监控。

单一事实源 · cap_*_def 平台级 / 租户级分层 双人复核 · fail-closed 复用 RLS 多租户 租户生命周期 / 配置覆盖 / 隔离校验 复用 ConfigPublish 工作流

0定位、目标与复用边界

本方案不是重新设计领域模型，而是在已落地的 cap_* 配置域、发布审批工作流、authzVersion 强一致授权与 RLS 多租户之上，补齐「管理控制台」这一层（前端 + 管理 API），让管理员能够高效地集中维护与监控四类资源。

0.1 设计原则

  • 单一事实源：所有实体以 cap_tool_def / cap_skill_def / cap_mcp_server_def / cap_agent_def 为权威；当前生效版本由 cap_config_release.object_versions 解析，绝不在前端维护「当前版本」副本。
  • 作用域分层：Tool / Skill / MCP 为平台级（无 tenant_id）；Agent 为租户级。平台级写操作不可经租户身份暴露（PLATFORM 作用域显式 403），由带外运维通道（BYPASSRLS）处理；控制台对平台级资源提供「申请 → 运维受理」或只读视图。
  • 审批双复核：高危变更（trustTier=public / WRITE_EXTERNAL 等）强制双人复核，approver_id <> requester_id。
  • 收紧棘轮：overrides / paramPolicies 只能收紧不能放宽；放宽即拒。前端需实时提示。
  • fail-closed：依赖解析失败 / 版本服务不可用 → 拒绝，并产出可监控告警信号；前端必须给出明确错误状态。

0.2 直接复用的既有能力（避免重复造轮子）

1总体架构

三层结构：管理前端（React/TS 控制台）→ 管理 API 层（在 agent-api 新增 admin 包）→ 复用既有领域 / 应用 / 基础设施。两条作用域通道决定哪些写操作走 HTTP、哪些走运维通道。

作用域通道关键约束（来自 P6R4 勘察）：平台没有跨租户身份——principal 表是租户内的。因此 Tool/Skill/MCP（平台级）的写发布不能经租户 HTTP 端点暴露，否则任一租户管理员自授 config:publish 即可改全平台配置。控制台对平台级资源：表单提交 → 生成「平台运维受理申请」→ 由带外运维通道（BYPASSRLS 凭据）执行；控制台本身对平台级仅做只读 + 申请。Agent（租户级）的发布则经 CapConfigPublishController 正常放开。

2核心功能模块

十一个模块，覆盖「租户管理 → 配置管理 → 运行监控」三条主线。租户管理为平台/运营级基础模块，前五个实体管理与后五个横切能力建立在其之上。

2.0 租户管理模块（新增 · 平台/运营级）

在 RLS 多租户地基上，为平台运营者提供跨租户的租户治理能力。注意：平台没有跨租户身份（principal 表为租户内），因此租户管理属于 PLATFORM 作用域，必须经带外运维通道 / 超级管理员角色，与租户内 TENANT_ADMIN 管理自身 Agent 的视角严格区分。

  • 租户生命周期：列表 / 详情 / 创建（开通租户 + 默认 principal + RLS 策略生效）/ 编辑 / 启停（active / suspended / decommissioned）。
  • 租户配置覆盖：查看与编辑 tenant_config_override（沿用 EffectiveConfigResolver 的收紧棘轮语义），提供「平台默认 vs 租户覆盖」对比视图。
  • 主体与角色：列出租户内 principal、分配 / 回收角色（TENANT_ADMIN 等）、查看 authz_version；角色变更与 authz 版本自增同事务。
  • 租户作用域资源视图：该租户下的 Agent 定义、运行实例、资源用量（配额/计量，V2）。
  • 隔离校验（RLS）：提供「以租户身份运行校验查询」确认 RLS 隔离正确（须用非特权 app_agent 账号验证，呼应既有 RLS 铁律）。
  • 租户级发布受理：TENANT 作用域发布（仅 Agent 定义）的状态与受理视图（复用 CapConfigPublishController）。
作用域红线：租户管理写操作不可经普通租户 HTTP 端点暴露（否则任一租户管理员自授权限即可改全平台）。本模块在控制台中仅由超级管理员经运维/BYPASSRLS 通道访问，普通 TENANT_ADMIN 仅能看到并管理自身租户内的 Agent 与主体。

3.2 关系与依赖方向

3.3 关系规则要点

  • 单向能力禁闭：Agent 只能启用已声明的 Skill；Skill 只能声明存在的 Tool / MCP；有效权限 = 沿链逐层取交集闭包（V1 禁止 inherits 嵌套抬权）。
  • 引用完整性：declared_tools 的每个 id 必须存在于 cap_tool_def；declared_mcp[].serverId 必须存在于 cap_mcp_server_def（T1 校验）。
  • 版本化：所有 cap_*_def 采用 (id, version) 复合主键不可变版本行；当前版本由 cap_config_release.object_versions 解析。
  • 删除守卫：被引用对象禁止物理删除 → 置 DEPRECATED（不可新引用），控制台删除操作前必须跑影响分析。
  • null vs [] 语义：exposedToolAllowlist / toolAllowlist 的 null≠[]，前端须区分「未配置」与「显式空」，禁止对未规范化 null 直接做集合运算。
  • 平台级 / 租户级：Tool/Skill/MCP 无 tenant_id（平台级）；Agent 带 tenant_id（租户级，受 RLS）。
  • 租户是隔离根与资源容器：tenant 派生 principal（租户内，无跨租户身份）、tenant_config_override（仅收紧的平台配置覆盖）、cap_authz_version（按 (tenant_id, principal_id) 作用域）。所有租户级读写必须带 tenant_id 并经 RLS。
  • 租户管理作用域：开通 / 启停 / 配置覆盖 / 主体与角色属 PLATFORM 作用域（平台运营），与 TENANT_ADMIN 的「租户内管理」视角分离；控制台对前者仅由超级管理员经运维通道访问。

5关键交互流程

以下流程全部复用既有后端服务，控制台负责编排与呈现。重点给出高价值流程的时序与步骤。

5.1 创建并发布一个 Agent（租户级）

1填写基本信息name / description / roles（调用资格）
2选择 enabledSkills多选平台 Skill；仅启用，非授权授予
3配置 overrides仅收紧：removeSkills/removeTools/lowerRiskCeiling
4校验闭包PermissionResolver 算有效闭包 + T1 守卫
5提交发布申请生成 cap_config_publish_request
6双复核 + 执行approver≠requester；写 release 指针
7新 Run 生效创建 Run 时读当前 config_publish_seq

5.2 发布审批时序（三步工作流）

高危强制审批：当发布对象含 trustTier=public 或 risk_level=WRITE_EXTERNAL 时，ConfigPublishWorkflowService 强制双人复核；前端在提交前即给出「需审批」提示与审批人选择。

5.3 其余关键流程（要点）

  • 绑定 / 解绑 Skill 与 Tool：表单多选 → 实时计算闭包 → 校验 riskCeiling 不越权、paramPolicies 只收紧 → 落草稿 → 走发布。
  • 新建 MCP 服务并采集工具清单：填写 endpoint（SSRF 白名单校验）→ 连接测试 → TransportMcpManifestPort.collect 采集 manifest → 生成 exposedToolAllowlist 候选 → 保存草稿。
  • 回滚发布：选择历史 release → 创建新 release 指向旧 version（新当前指针），不覆盖历史；回滚不恢复已撤销的主体授权。
  • 删除守卫：触发删除 → DependencyGraphService 跑影响分析（哪些 Skill/Agent 引用）→ 若有引用 → 置 DEPRECATED 并提示，禁止物理删除；无引用且 DRAFT → 允许删除。
  • 依赖影响分析：改/删某 Tool → 反向查 declared_tools 命中 Skill → 再查 enabled_skills 命中 Agent，输出影响链路图。
  • 运行监控：authzVersion bump：角色变化/禁用/撤销 → authzVersion 单调自增（同事务）→ 在途 Run 检测到失效 → 新调用 DENY → 监控面板告警 + ledger 留痕。

5.4 租户生命周期与配置覆盖管理（平台/运营级）

1开通租户创建 tenant + 默认 principal + RLS 策略生效
2配置覆盖tenant_config_override（仅收紧，棘轮）
3分配主体角色TENANT_ADMIN 等；同事务 bump authz_version
4资源与发布视图租户内 Agent / 运行 / TENANT 发布受理
5启停 / 注销active / suspended / decommissioned
6隔离校验以租户身份跑 RLS 校验查询

5.5 租户隔离校验（RLS）

  • 提供「以租户身份运行校验查询」入口：用非特权 app_agent 账号（设置 app.tenant_id）执行跨租户读取尝试，断言被 RLS 拦截。
  • 校验项：① 租户 A 的主体无法读取租户 B 的 cap_agent_def / principal / cap_authz_version；② set_config('app.tenant_id',?,true) 必须在事务内（既有 RLS 铁律）；③ 配置覆盖仅影响本租户。
  • 校验结果以报表呈现（通过/失败 + 失败样例），失败时阻断该租户的配置发布（fail-closed）。

  • 后端：Spring Boot 4.1.1（与平台一致）；在 agent-api 新增 admin 包；管理查询服务复用既有的 cap 配置服务、发布工作流、审计与 RLS，不新增领域规则。
  • 数据：PostgreSQL 18（平台库），复用 cap_* 表与 cap_config_release；监控视图以只读聚合为主，不新增写表（除非 M10 凭据登记需要）。
  • 鉴权：复用 JWT + Roles.TENANT_ADMIN；平台级写发布保持带外运维通道，控制台不暴露 PLATFORM 作用域写入口。

9风险与注意（来自既有设计约束）

  • 平台级作用域不可经租户身份暴露：Tool/Skill/MCP 写发布走运维通道，控制台仅对这些提供「申请（运维受理）」或只读；PLATFORM 作用域 HTTP 写入口显式 403。
  • 收紧棘轮：overrides / paramPolicies 只能收紧不能放宽，前端须实时校验并提示，放宽即拒。
  • null vs []：allowlist 字段的「未配置(null)」与「显式空([])」语义不同，前端须显式区分，禁止对未规范化 null 直接做集合运算。
  • fail-closed：依赖解析失败 / authzVersion 服务不可用 → 拒绝并告警；前端须给出明确错误态，不可静默降级放行。
  • 凭据安全：credential_ref 仅存引用，永不入前端明文 / 日志 / 指纹。
  • V1 边界：禁止 inherits 嵌套抬权、dynamicDiscovery 固定 false、仅 http/sse 传输——这些约束在表单层即禁用对应选项。
  • 租户管理作用域红线：平台没有跨租户身份，租户管理（含开通、配置覆盖、主体/角色、启停）属 PLATFORM 作用域，必须经超级管理员 / 带外运维（BYPASSRLS）通道；普通 TENANT_ADMIN 仅能管理自身租户内的 Agent 与主体，控制台不得向其暴露跨租户写入口。
  • 租户配置覆盖仅收紧：tenant_config_override 继承平台配置并仅可进一步收紧（棘轮），放宽即拒；主体角色变更须与 authz_version 自增在同一事务提交，否则出现撤权竞态。
  • RLS 隔离校验必须用非特权账号：验证隔离时须用 app_agent 而非特权账号，且 set_config('app.tenant_id',?,true) 必须在事务内，否则校验结论不可信。
