**⚠️ 实测踩坑（已修，记入教训）**：
1. **列限定符**：JOIN 的 4 张表都有 `tenant_id` 列，裸列名报
   `column reference "tenant_id" is ambiguous`（IT 14 个 error 全是这个）。
   ⇒ 谓词形态由翻译器单点产出，**列限定符**由调用方给出（JOIN 场景必须带别名）；
   已加守卫 `everyRenderMustCarryColumnQualifier` 钉死。
2. **参数顺序**：dense/lexical 通道的 `?` 分布在 SELECT / WHERE / ORDER BY 三处，
   作用域参数夹在中间 ⇒ 顺序错了**不会报错**，只会让相似度算错（静默失真）。
   ⇒ 统一走 `concat(scopeParams, head, rest)` 单点拼接，并写明各通道顺序。
3. **uuid 列 String 绑定必须 `?::uuid` 转换**：`tenant_id` / `document_id` / `chunk_id` 均为 uuid 列，
   用 `String` 参数绑定 `?` 时 JDBC 会把占位符推断成 `character varying`，
   PG 找不到 `uuid = character varying` 操作符 ⇒ `BadSqlGrammarException:
   operator does not exist: uuid = character varying`。首轮 IT 出现 14 个 error 全是这个。
   ⇒ 翻译器渲染 tenant 谓词统一输出 `?::uuid`（`IN (?::uuid, ?::uuid)` / `= ?::uuid`）；
   同查询里其他 uuid 列比较（`c.document_id = ?::uuid`、`c.chunk_id <> ?::uuid`、
   `c.chunk_id = ANY(?::uuid[])`）也已显式转换；IT 辅助查询 `countChunksAs` 的
   谓词同样补 `::uuid`。**反向验证**：撤掉 `::uuid` 即 `RetrievalRepositoryIT` 全红（符合铁律 6）。

**⚠️ `set_config` 兼容层仍保留（刻意）**：FORCE RLS 策略仍读 GUC，
此刻移除会让**全部**租户行被静默过滤（检索恒空且不报错）——正是风险登记册 R1（Sev-0）。
检索面仅保留白名单内的两种形态（`set_config('app.tenant_id', ?, true)` /
`set_config('app.tenant_id', '', true)`），随 **M4-R1** 批次退役。
守卫 `onlyWhitelistedGucBindingsRemain` 钉死白名单，新增形态必须先在计划里登记理由。

**三重反证（均已实测转红 → 修复 → 转绿）**：
1. **源码守卫** `RagRetrievalScopeGuardTest`（5 用例）：可执行代码中
   `rag_current_tenant()` / `rag_global_tenant_id()` 必须为零；`set_config` 形态在白名单内；
   每处 render 必须带列限定符。**实测**：注入 `rag_current_tenant()` 后 2 条断言同时转红。
2. **等价性 IT** `RetrievalRepositoryIT.explicitPredicateIsEquivalentToGucPredicate`：
