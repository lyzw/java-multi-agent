**代表性策略谓词**
```sql
-- platform 简单等值隔离
CREATE POLICY agent_tenant_isolation ON public.agent
  USING ((tenant_id = public.current_tenant_id()))
  WITH CHECK ((tenant_id = public.current_tenant_id()));
-- platform 读写拆分（PLATFORM 行 tenant_id IS NULL）
CREATE POLICY cap_config_pointer_read ON public.cap_config_pointer FOR SELECT
  USING (((tenant_id IS NULL) OR (tenant_id = public.current_tenant_id())));
CREATE POLICY cap_config_pointer_write ON public.cap_config_pointer FOR INSERT
  WITH CHECK ((tenant_id = public.current_tenant_id()));
-- rag 读=本租户∪哨兵、写=仅本租户且 scope='TENANT'
CREATE POLICY rag_chunk_read ON rag.rag_chunk FOR SELECT
  USING ((tenant_id = ANY (ARRAY[rag.rag_current_tenant(), rag.rag_global_tenant_id()])));
CREATE POLICY rag_chunk_write ON rag.rag_chunk FOR INSERT
  WITH CHECK (((tenant_id = rag.rag_current_tenant()) AND (scope = 'TENANT'::text)));
```

### 1.4 RLS 在权限校验中的使用

当前是**双层取交集**：应用层 `ScopeFilter`（已在 34 仓生效）+ RLS（兜底）。**鉴权入口已就位**：
- `ScopeFilter`（sealed，`TenantWithShared`/`TenantOnly`/`Unrestricted`/`None`）、`SubjectContext`（`tenantId/principalId/roles/scope/authzVersion`，`isPlatformOps()` 才产出 `Unrestricted`）；
- `AccessGate.authorize/authorizeCollection` → `RuleBasedPolicyEngine`（按 `resourceType+action` 匹配，`Unrestricted` 仅 `isPlatformOps()` 产出，否则 fail-closed）→ `Decision`；
- `AuthzShadowHooks`（统一静态入口：`compare` 影子比对 + `taint` 逐行染色）、`AuthzShadowReporter`（`rlsDependent`/`mismatch`/`taint` 指标）、`AuthzMismatchMetrics`、`RowAttribution`/`TaintVerifier`/`TaintReport`、`ScopedDataAccess`；
- 决策日志 `platform.authz_decision_log`（表已落库，`app_agent` 仅 INSERT 且 `REVOKE SELECT`），`AuthzDecisionLogGuard` 两道启动 fail-closed 守卫；
- 架构守卫 `ScopeBypassArchitectureTest`（防绕过）、`JoinTenantPredicateArchitectureTest`（JOIN 从表补 `tenant_id`）、`ShadowPolicyCoverageTest`（资源类型登记）、`AuthzShadowWiringTest`（装配钉死）。

**关键信号 `rlsDependent`**：`AuthzShadowReporter#reportRlsDependent` 统计「被观测查询是否自带显式 `tenant_id` 谓词」。它比 `AUTHZ_MISMATCH=0` 更严格——RLS 仍在时染色结构性为 0，不能证明退役后不漏；`rlsDependent=0` 才是「退役 RLS 后是否还会漏」的直接对应量。

### 1.7 当前鉴权、权限控制与数据访问流程

```
请求到达 → 认证入口写入 SubjectContext(tenantId/principalId/roles/scope/authzVersion)
        → Repository 查询：
            (1) 应用层：AccessGate.authorizeCollection → ScopeFilter
                → SqlScopeTranslator.render → 显式 WHERE tenant_id=? 注入 SQL
                → AuthzShadowHooks.taint 逐行染色（高敏 100% / 采样 1%）
            (2) RLS（兜底，当前同时存在）：连接经 TenantSessionBinder.set_config('app.tenant_id',?)
                → PG 对每张表自动应用策略谓词（含 JOIN 从表）
        → 返回前：染色校验（行 tenant_id ∈ filter 允许集）；违例打 AUTHZ_MISMATCH + 告警
        → 决策日志（platform.authz_decision_log，仅 INSERT）
运维/平台全域路径：GuardedPlatformOpsDataSource（BYPASSRLS 连接）
        → SubjectContext.scope=PLATFORM + isPlatformOps() → 产出 Unrestricted（等价于原 BYPASSRLS 视图）
```

**结论**：应用层权威已搭好并部分生效，但 RLS 仍是「第二道防线 + JOIN 自动覆盖 + GUC 隐式绑定」的来源。彻底清理 = 让 (1) 成为唯一权威，退役 (2)，并把 RLS 提供的三项隐性收益（JOIN 从表覆盖、空上下文 0 行 fail-closed、运维通道绕过）在应用层显式补偿。

## 3. 清理与改造方案

### 3.1 替代权限控制方案（应用层唯一权威）

沿用已落地的 `ScopeFilter`（4 形态）+ `AccessGate` + `RuleBasedPolicyEngine` + `SqlScopeTranslator`：
- **数据层**：每个 Repository 查询携带 `ScopeFilter`；`None` 渲染恒假（fail-closed），`Unrestricted` 仅 `isPlatformOps()` 产出，哨兵值从 PG 函数改为**配置项**。
- **纵深补偿（替代 RLS 的三项隐性收益）**：
  1. **JOIN 从表覆盖**：`JoinTenantPredicateArchitectureTest` 已穷举 platform 15 / rag 24 / sql 5 处 JOIN，强制从表补 `tenant_id`，并做 JOIN 从表二次染色。
  2. **空上下文 fail-closed**：`AccessGate` 无 subject 即抛异常，`ScopeFilter.None` 渲染恒假，染色违例即告警——三重重建。
  3. **运维通道绕过**：`SubjectContext.scope=PLATFORM` + `Unrestricted` 取代 `BYPASSRLS` 连接语义；`GuardedPlatformOpsDataSource` 形态保留、语义切换为「携带 Unrestricted 的专用客户端」，未配置即 503 绝不回落。
- **可观测性**：决策日志 + `AUTHZ_MISMATCH`/`rlsDependent` 指标 + 结果集染色（高敏 100% / 采样 1% 确定性分桶）。
- **混合终态（合法护栏）**：`principal`、审计表、`cap_decision_log` 等高敏表**默认保留 RLS** 作第二道防线，P3 白名单跳过其 `DROP POLICY`。

### 3.2 各层同步调整

- **数据库层**：退役策略与 GUC 函数；保留 `scope↔哨兵` CHECK（改读配置）；角色 `BYPASSRLS` 保留为运维通道纵深。
- **应用层**：补齐 ~14 个 Repository 的 Gate 接线；RAG 全模块 GUC 谓词改为 `ScopeFilter` 注入；删除 `TenantSessionBinder`/`set_config` 调用（P5）。
- **接口层**：`SubjectContext.scope` 推导点反证钉死。
- **测试层**：删 RLS 专属断言，反证对象由「DB 结构」换「应用层装配」；约 60 个 IT 夹具迁移。

### 3.3 风险分析

| 维度 | 分析 |
|---|---|
| 数据安全 | 退役后唯一防线是应用层：靠「无 Gate 无 Repository 实例」+ 染色 + 反证三层补偿；RAG 模块工程面最大（44 文件），须先接 Gate 再退役 rag 策略 |
| 越权风险 | 最大风险点是 **JOIN 从表漏谓词**（已抓到 1 处真实缺口 `JdbcTraceFactRepository` 的 `tool_operation ⋈ tool_operation_attempt`，指标口径污染）与 **RAG 检索谓词静默失效**（`rag_current_tenant()` 未绑定返回 NULL → 0 行，不报错）；须靠染色 + `rlsDependent` 信号暴露 |
| 兼容性 | 数据库无关性提升（新增存储 = 1 个 `ScopeTranslator`）；PG 优化器层面谓词等价仅在单表等值成立，JOIN/分区处须 `EXPLAIN` 对比（设计稿 §7.2 P6） |
| 回归风险 | `TenantSessionBinder` 删除须独立 PR + 全量回归；应用层 bug 致漏过滤不被 DDL 回滚覆盖，须代码回退开关 |

## 4. 实施步骤

### 4.1 改造顺序（基于 P0–P5，细化到本项目实际改动）

1. **P2 收尾（先让应用层全量接管）**：补齐 3 纯 RLS + 4 双绑 + 11 未挂号仓库的 Gate 接线 → 开启 `agent.authz.shadow.enabled` 跑满 ≥2 周，`rlsDependent=0` 且 `AUTHZ_MISMATCH=0`；开启决策日志生产开关并观察行数增长。
2. **RAG 侧 P2（最大面）**：RAG 全模块 GUC 谓词→`ScopeFilter`；先影子比对再双写；`rag_corpus_scope` 反证脚本改造。
3. **P3 逐表退役（分批，D8 脚本）**：B1 只增日志类 → B2 platform 业务表 → B3 rag 语料表（含哨兵）→ B4 平台目录/运维通道。每批：`DROP POLICY` → 观察 1 周 → `DISABLE RLS` → 跨租户用例仍红 + 回滚演练。
4. **P4 收口**：策略规则进配置中心 + 双人复核；新增表纪律反转（默认无 RLS，评审检查注册 + scoped）。
5. **P5 清理**：删 `TenantSessionBinder`/`set_config`/GUC 函数/增量 DDL 策略定义（独立 PR + 全量回归）；退役 `export-rls-policies.sh`。

### 4.2 关键注意事项

- **双写期 RLS 一条策略都不许动**（安全语义只会变紧不会变松）。
- **`rlsDependent=0` 是真正出口**，比 `AUTHZ_MISMATCH=0` 更诚实（RLS 在时后者结构性为 0）。
- **整库隔离优先**：IT 须指向 `agent_it`/`study_rag_it` 独立库，避免运行实例改写基线（§8.1 第三种表现）。
- **漂移先修**：`init-db.sh:194` rag 期望 35→实测 37；platform 策略 50→实测 52。
- **GUC 函数退役前**先确认所有 `rag_current_tenant()`/`current_tenant_id()` 引用（含 8 处 CHECK、增量脚本、rag_import_pdf.py）已替换，否则静默 0 行。
- **染色同义反复三连坑**（已实证）：①用绑定租户当行租户；②聚合查询不可染色；③主体取自行租户。须用「注入他租户行必须违例」的反证钉死。

### 4.3 验证方法

- **功能正确性**：全量 IT 绿（双 reactor `clean verify`，platform + rag 独立库）。
- **权限控制**：跨租户用例在 RLS 退役后**仍红**（现在靠应用层拦）；`ScopeBypassArchitectureTest`/`JoinTenantPredicateArchitectureTest`/`ShadowPolicyCoverageTest` 全绿；`AuthzShadowLiveIT` 跨租户主体 ⇒ `mismatch=1` 且逐行违例数=行数。
- **数据安全**：`rlsDependent=0` + 高敏接口 100% 染色无违例 + 决策日志行数随采样增长。
- **JOIN 不泄漏**：`authz-join-fk-counterproof.sh` 从表租户全等 + 二次染色。
- **性能**：Top-20 慢查询 + JOIN 重查询 `EXPLAIN` 对比无回归。
- **回滚演练**：每批出口含 DDL 重放 + 应用层回退开关双路就绪。

### 4.4 回滚方案

| 阶段 | 回滚方式 | 数据风险 |
|---|---|---|
| P0–P2 | 关影子/双写开关，RLS 原样兜底 | 零 |
| P3 每批 | **策略 DDL 全程保留**（只加 `DROP`，不删定义），回滚=重放该表策略 DDL + 应用层回退开关切回 | 零（不动数据） |
| 应用层 bug | DDL 回滚不覆盖 → 旧版 Repository 并行保留一个迭代 / 代码回退开关 | 须每批出口演练 |
| P5 | `TenantSessionBinder` 删除独立 PR，失败即 revert | 回归绿即安全 |
