## 1. 架构与编排模型

**实现方式**

- **Run / run_step 两段式执行模型**：一个 Run（`public.run`）是一个执行实例，由 `run_step`（`public.run_step`）记录每一轮「既成事实」。`run_step.state` 恒为 `RUNNING`（`01_platform_ddl.sql:2832-2834` 注释明确：「单条 INSERT 写入，state 恒为 RUNNING 表示『该步骤已发生』而非进行中，完成以 completed_at 判定」），`run_step_number_positive` CHECK 保证步骤号单调递增。
- **事件/队列驱动**：写入端 `RunCreationService` 把 `run` + 初始 `run_event` + `idempotency_record` + `outbox_event` **四者同事务**提交（`docs/系统架构图.md:199`、`docs/Agent设计总览.md:131`）。`outbox_event`（`01_platform_ddl.sql:2597`）`state ∈ {PENDING,PUBLISHED,FAILED}`，由 `RunDispatchConsumer` / `OutboxRelay` 从库轮询投递到 MQ（`application.yml:191` `relay-interval-ms=200`），MQ 消息只携带 `tenant_id + run_id + message_id`，**不携带可信权限**（`docs/系统架构图.md:245`）。
- **Worker 消费模式**：`RunDispatchConsumer` 只负责「把消息变成一次租约领取」，业务执行抽成 `RunExecutor`（`RunDispatchConsumer.java:27-57`）。核心规则：**重复消息必须丢弃而非重试**（Outbox at-least-once 的正常形态）；`Outcome` 区分 `SUCCEEDED/FAILED/CANCELLED/RETRYABLE_FAILURE/UNKNOWN_RESULT/STALE_GENERATION`，其中 `UNKNOWN_RESULT` **ack 丢弃、绝不重投**（重投=重复副作用=Sev-0），`STALE_GENERATION`（被接管）也 ack 丢弃。
- **编排引擎 `RunExecutionLoop`**：`agent-worker/.../RunExecutionLoop.java:68` 类头声明「**只做编排**：串联模型调用、工具调用闸门、状态提交，不关心工具做什么」；主循环 `while (steps < snapshot.maxSteps())` 取运行上限来自 **Run 快照**而非动态配置。
- **状态机由 DB 触发器守卫**：`enforce_run_state_transition()`（`01_platform_ddl.sql:453-475`）只允许 `QUEUED→{RUNNING,CANCELLED}`、`RUNNING→{SUCCEEDED,FAILED,CANCELLED,TIMED_OUT,WAITING_APPROVAL}`、`WAITING_APPROVAL→{RUNNING,CANCELLED,TIMED_OUT,FAILED}`，其余一律 `RAISE EXCEPTION 'restrict_violation'`。
- **多级编排**：`cap_agent_def.orchestration` jsonb 声明 `LEAF/ROUTER/SEQUENTIAL`（`docs/Agent设计总览.md:60-69`），`agent_invocation` 记录委派调用树（`depth=1 ⇔ parent_invocation_id IS NULL`），子 Agent 经 `WorkerChildAgentRunner` 自己起多轮小循环（默认 `DEFAULT_MAX_CHILD_STEPS=4`）。

**关键设计取舍**：PostgreSQL 是权威事实源，MQ 只负责唤醒/分发（`docs/系统架构图.md:401`）；「重试只在 Worker 侧实现，绝不引入 `@Retryable`」，否则对 `record_weakness` 这类有副作用工具会重复写入 Sev-0（`RunExecutionLoop.java:63-66`）。

## 2. 多租户隔离

**实现方式**

- **RLS + GUC 函数 `current_tenant_id()`**：DDL 定义 `public.current_tenant_id()`（`01_platform_ddl.sql:289-293`），实现为 `SELECT NULLIF(current_setting('app.tenant_id', TRUE), '')::UUID`。注释明确：「未设置 app.tenant_id 时返回 NULL，所有 RLS 策略将拒绝访问——默认拒绝，符合 fail-closed」。每个会话执行时由 `TenantContext` + `TenantSessionBinder` 调用 `set_config('app.tenant_id', ...)` 绑定。
- **策略模板一致**：`agent`/`run`/`run_step`/`run_event`/`tool_operation`/`usage_record`/`budget_account`/`execution_snapshot`/`approval`/`cap_*` 等全部表 `FORCE ROW LEVEL SECURITY`，CREATE POLICY 形如 `USING ((tenant_id = public.current_tenant_id())) WITH CHECK ((tenant_id = public.current_tenant_id()))`（如 `01_platform_ddl.sql:5830` `run_tenant_isolation`、`:5278` `agent_message_queue_tenant_isolation`）。共 **42 张表挂 RLS、50 条策略**（DDL 头注释 :5）。
- **双保险**：除 RLS 外，所有跨表引用用 `(tenant_id, 父id)` 复合外键（`docs/Agent设计总览.md:253` 不变式 6：`agent` 表 `UNIQUE(tenant_id, agent_id)` 专为此存在）。
- **租户表本身不挂 RLS**：`public.tenant` 注释「本表为全局表，不启用 RLS（租户自身即隔离单元）」（`01_platform_ddl.sql:2949`）。
- **平台域表不挂 RLS，靠授权隔离**：`platform.authz_decision_log`、`platform.review_task` 等（`01_platform_ddl.sql:2971` 注释：「跨租户隔离靠授权而非行策略；app_agent 只有 INSERT，读走 platform_ops」）。
- **复合外键级联约束**：`agent_invocation` 的 `agent_invocation_parent_ck`、`cap_agent_child_ref` 的复合外键顺带保证租户一致（`docs/Agent设计总览.md:65`）。

**关键设计取舍**：RLS 是「默认拒绝」的硬边界；应用层另有 `RoleBasedAuthorizationService` 做「执行时重新授权」（见维度 7），两层独立、互不替代。

## 3. 状态持久化与可恢复性

**实现方式**

- **PG 为权威源**：所有运行事实落库；`outbox_event` 与 Run 创建**同一事务写入**（红线 3，`01_platform_ddl.sql:2623` 注释：「与 Run 创建在同一事务写入；发布失败可重试；重复投递由消费端幂等处理」）。
- **Outbox 模式**：`outbox_event`（`:2597`）`aggregate_type/aggregate_id/event_type/payload jsonb`，`state` 三态；`RunDispatchConsumer` 从库拉取后通过 MQ 唤醒 Worker。
- **断点续跑 = 重读 DB + 租约 + fencing**：Worker 领取时条件更新 `run` 的 `lease_owner/lease_expires_at`，并获得 `fencing_token`（`01_platform_ddl.sql:2730-2732`）。`enforce_fencing_on_write()`（`:410-421`）触发器：`NEW.fencing_token < OLD.fencing_token` 直接拒绝——旧世代不能更新新世代状态。`run_step.fencing_token`（`:2816`）同样受此保护。
- **幂等/去重**：`idempotency_record`（`:2549`）按 `(tenant_id, key_namespace, idempotency_key)` 三态判定（首次/重复同请求返回首次/键同请求异拒绝）；`run_message.idem_key` 唯一约束（`:2886-2887`），冲突覆盖而非追加，防止重放重复对话。
- **不可变快照**：`execution_snapshot`（`:2517`，agent_config/prompt_config/tool_contracts/run_config/context_policy）`forbid_snapshot_mutation()`（`:616-623`）禁止修改；`cap_*_def` 已发布版本行 `forbid_published_def_mutation()`（`:574-609`）除 `PUBLISHED→DEPRECATED` 纯元数据停用外一律拒绝改写。
- **租约续期与取消**：`RunExecutionLoop.renewLease` 按 `lease_owner` 精确匹配（workerId 必须与领取时一致）；取消由 `cancel_requested_at` + `ToolInvocationGate.CancelGuard` 双重检查（`ToolInvocationGate.java:80-86`）。

**关键设计取舍**：「MQ 只唤醒、DB 重读」使 Worker 崩溃后可从任意租约点恢复；fencing token 防脑裂/双 Worker 写同一 Run；UNKNOWN 状态**不释放预算预留、转对账**而非盲目重放（`:532-536` `forbid_attempt_after_terminal`）。

## 4. 流式输出

**实现方式**

- **SSE 端点**：`agent-api/.../api/run/RunEventStreamer.java:32` 提供长连接推送。明确说明这是**服务端轮询**而非真推送（把轮询从客户端搬到服务端，延迟由服务端配置决定；真零轮询 PG `LISTEN/NOTIFY` 归 P4）。
- **事件来源即持久化 `run_event`**：`stream()` 内 `query.findAfter(tenantId, runId, cursor, 200)`（`RunEventStreamer.java:182`）轮询读取 `public.run_event`（`01_platform_ddl.sql:2788`，`sequence_no bigint NOT NULL` 单调），把每行作为 SSE event 帧发出（`eventType` + `sequence_no` 作为 `id` + `payload`）。
- **done 终帧 = 注释帧 `:run-terminal`**：`RunEventStreamer.java:196-200` 在 `stateSupplier` 取到终态时发送 `sender.sendComment("run-terminal")` 然后 `complete()`。注释（`:73-82`）解释为何必须是 **SSE 注释行而非事件帧**：前端 `sse.ts` 解析器只认 `: run-terminal`，若发事件帧（缺 `id`）会被丢弃→前端永收不到终止信号→轮询每 3 秒重连永不停止。
- **连接生命周期**：`poll-interval-ms=200`、`max-lifetime` 兜底强制关闭（`:220-229`），`onCompletion/onTimeout/onError` 都停止轮询清理，防连接泄漏。
- **payload 白名单**：`filterPayload`（`:233-246`）按 `payloadFilter` 过滤事件载荷，复用 P2-D05 白名单语义。
- **是否写 outbox**：SSE **不写 outbox**，它只读 `run_event`（即「运行事件流」本身已是持久化事实表）；Outbox 仅在 Run 创建时用于唤醒 Worker。

**关键设计取舍**：终态立即 `complete()` 释放连接；终止信号用控制帧表达，避免「业务事件流里混入假事件」；轮询间隔/存活时长全配置化、可预期。

## 5. 工具 / 函数调用

**实现方式**

- **统一闸门 `ToolInvocationGate`**：`agent-worker/.../ToolInvocationGate.java:53` 是「**不可绕过的安全边界**」，类头把执行链写成契约：`Schema 校验 → 执行时重新授权 → 幂等键 → 账本 → 审批 → 预算 → 执行 → 账本更新`。**明确禁止使用 Spring AI `ToolCallingAdvisor` 的自动执行路径**（会绕过全部闸门，ADR-011 §3.3）。
- **工具定义来源**：工具声明在 `cap_tool_def`（`01_platform_ddl.sql` 中 `risk_level NOT NULL + CHECK` 强制显式声明副作用等级，`kind ∈ {native,mcp,http}`）；模型只「提出工具调用建议」，平台负责授权/调度/执行/持久化。
- **tool schema 校验（闭集）**：`agent-infrastructure/.../tool/ToolInputSchemaValidator.java:27` 按 `cap_tool_def.input_schema` 做**闭集校验**：「必填的在、没声明的不在」；注释强调若 `additionalProperties:false` 被某处漏掉，未声明参数会被放行——故抽成公共实现供 MCP 与 HTTP 两类工具共用；**Schema 本身非法直接拒绝**（解析不了约束若当「无约束」等于关掉校验）。
- **三层逻辑操作模型**：`tool_operation`（`01_platform_ddl.sql:2983`）`state ∈ {PENDING,IN_FLIGHT,SUCCEEDED,FAILED,UNKNOWN,RECONCILED_SUCCEEDED,RECONCILED_ABSENT,MANUAL_DISPOSED}`；`tool_operation_attempt` 记录每层重试（`01_platform_ddl.sql:3018`）；`forbid_attempt_after_terminal()`（`:516-539`）在终态后禁止新增 attempt，UNKNOWN 状态禁止新增 attempt（等同盲目重试 Sev-0）。
- **内置工具**：`GetStudentProfileTool`、`RecordWeaknessTool` 两个 native 工具 + `kind=mcp`/`kind=http` 动态通道（`docs/Agent设计总览.md:274`）。
- **参数策略**：`cap_tool_def.param_policies` V1 仅支持 `in_allowlist` / `lte` 两种判定，其他 op 写入即拒（`docs/Agent设计总览.md:46`）。

**关键设计取舍**：模型永远不自动执行；工具调用必须穿过唯一闸门并经过 15 步准入（见维度 7）；Schema 校验「错误即拒、不尽力解析」。

## 6. 上下文管理

**实现方式**

- **独立算法模块 `agent-context`**：纯算法层（只依赖 `agent-ports`），位于 ports 之上、application 之下（ADR-013）。
- **管线 `CompactionPipeline`**：`agent-context/.../context/CompactionPipeline.java:37` 分级压缩 **W1 可逆外置 → W2 整轮裁剪 → W3 增量摘要**（对应《方案》§5.3/§6.4）。设计硬约束：**零 LLM / 零 IO / 零请求字节变更**（`:22-25`），W3 摘要通过注入的 `Summarizer`（外部走 `ModelGateway`）产出；**首轮锚（USER）永不丢**，W1 只替换 TOOL 的 content、不动 assistant 的 tool_calls 配对。
- **水位/预算**：`WaterLevel`（W0 不压 / W1 外置 / W2 裁剪 / HARD 硬截断）、`ContextBudget`、`BudgetAllocator`；`GlobalContextPolicy` 提供全局兜底（含 `hard-ceiling-tokens`、`unknown-capability-reserve-ratio`）。
- **策略配置**：`ContextPolicy`（strategy 含 `TIERED`/`TRIM_ONLY`）、`ContextPolicyParser`、`ContextPolicyResolver`、`ContextPolicyValidator`；Agent 级发布期规范快照落在 `execution_snapshot.context_policy`（`01_platform_ddl.sql:2539-2542`）。
- **运行时参数（application.yml）**：`agent.worker.context-token-budget=16000`（`:208`）、`default-max-input-tokens=16000`、`trigger-ratio=0.70`、`target-ratio=0.40`、`reserve-ratio=0.10`、`recent-turns=6`、`tier-snip-ratio=0.60`、`tier-summary-ratio=0.90`、`summary-timeout-ms=8000`、校准 `min-samples=30`（`:255-258`）。
- **开关与降级**：`context.enabled` 默认 `false`（`:232`）；L3 ConsoleChat 经 `ConsoleBudgetAdapter` 独立投影（只跑 W1/W2、零 LLM）。摘要失败**绝不伪造**（回落 W2、`fallback=true` + 稳定原因码 `SUMMARIZER_FAILED`/`HARD_TRIM`）。

**关键设计取舍**：压缩是确定性纯函数（相同输入恒等输出），与模型调用解耦避免 ReDoS/循环依赖；「摘要失败不伪造」优于塞一段编造摘要；小计/校准（`min-samples=30`）防止小样本噪声被当指标。

## 7. 权限与护栏

**实现方式**

- **执行时重新授权**：`agent-ports/.../security/AuthorizationService.java:20` 文档说明 Run 创建时授权一次不够，工具执行/结果读取/事件订阅等每个敏感动作前都必须重新校验**当前**授权；撤销= `authz_version` 递增，在途请求携带陈旧版本会被识别（`currentAuthzVersion`、`:51`）。
- **角色 × 任务（动作矩阵）**：`AuthorizationService.Actions`（`:59-177`）把动作拆到极细：`run:create/run:read/run:cancel/event:subscribe/result:read/tool:invoke/approval:consume/unknown:dispose/audit:read/agent:manage/profile:read/config:request/config:approve/config:publish/config:rollback/agent:delegate/agent:list`。注释反复强调**刻意不复用/不合并**（如 `profile:read` 不复用 `run:read`；`config:approve` 与 `config:request` 分开以保双人复核不被同一身份绕过；`agent:delegate` 与 `tool:invoke` 分开）。
- **角色体系**：`AuthorizationService.Roles`（`:180-247`）含 `TENANT_ADMIN/AGENT_AUTHOR/APPROVER/VIEWER/WORKER/PLATFORM_ADMIN/SUPER_ADMIN/STUDENT/PARENT/TEACHER`；`isAudienceOnly` 把受众角色（STUDENT/PARENT/TEACHER）的 Run 可见范围收窄到 `requester_id = principal_id`。
- **AgentOverrides（只收紧）**：`cap_agent_def.overrides`（`01_platform_ddl.sql:1631`）只允许 `removeSkills/removeTools/lowerRiskCeiling`；`cap_agent_def.roles` 「只声明适用主体范围，不是授权授予」（`:49`）。
- **fail-closed**：`RoleBasedAuthorizationService.isAuthorized` 异常与拒绝可区分；`ToolInvocationGate.approvalSource` 默认 `FAIL_CLOSED`（未装配真实审批源时，需审批工具一律拒）；`ConsoleBudgetAdapter` 兜底异常一律 `CONSOLE_BUDGET_FAILED`，**绝不 catch 后返回 legacy**。
- **输出审核 OutputModeration**：`agent-core/.../compliance/OutputModeration.java:46` 是平台侧输出内容安全层（修复前只有模型侧过滤且 `SENSITIVE_OUTPUT` 只观测不阻断）。判定 **fail-closed**：`PII_LEAK → REDACT`（命中片段换占位符再下发）、`TOXICITY/JAILBREAK_INSTRUCTION → BLOCK`（命中即失败该 Run）；复用 `DataClassification.IdentifyingPattern` 同一份正则做检测与脱敏；未知类别按 `BLOCK`（`:131-137`）。
- **权限影子对照（Shadow）**：`application.yml:154` `AGENT_AUTHZ_SHADOW_ENABLED:false` 默认关，开启后 `AuthzShadowBinding` 双跑比对，落 `AuthzShadowHooks` 把应用层判定与 RLS 基线对账（见 `agent-persistence/.../security/AuthzShadow*`，`AGENT_AUTHZ_SHADOW_BLOCK_ON_VIOLATION` 默认 false）。

**关键设计取舍**：权限判定从 RLS 隐式上移到应用层显式 Gate 后，用 `platform.authz_decision_log`（只增不改、text 类型）记录每次判定举证；「读不到=拒绝」而非跳过（不变式 4）；平台管理员走 BYPASSRLS 运维凭据，不经租户身份暴露。

## 8. 知识检索 RAG

**实现方式**

- **独立 RAG 服务 + 服务端到服务端网关**：platform 与 rag 是两个独立 Maven reactor / 进程。`agent-infrastructure/.../rag/HttpRagRetrievalGateway.java:57` 是第一个 platform→rag 的真实服务端通道，`POST /api/v1/retrieval`（修正了先前误用的 `/retrieval/retrieve` 404）。
- **认证与租户**：透传已验签 Bearer JWT（租户链=`tenant_id claim == X-Tenant-Id`，平台链可跨租户）+ `X-Tenant-Id`；rag 的 `RagJwtAuthFilter` 校验租户域 `tenant_id claim == X-Tenant-Id`（403 防越权）。
- **fail-closed 检索**：非 2xx / 超时 / 非法 JSON / 缺 `hits` 一律抛 `RagUnavailableException`，由编排器转成组件级 error + 空命中，**绝不伪造命中或静默当零命中**（`HttpRagRetrievalGateway.java:53-56`）；连接/读超时 3s/20s，响应体封顶 512KB，禁止重定向（SSRF 防线）。
- **响应白名单**：只取 7 字段（chunkId/text/score/locator/edition/role/reason），不把 rag 的 channel/funnel/prompt 透给前端（`parseResult` `:175-221`）；chunkId/text 空白即丢弃该条（防畸形空命中混进不可信上下文）。
- **检索引擎 Authority Triple Gate**：`agent-infra/.../retrieval/engine/RetrievalService.java:15` 实现 `RLS 租户隔离 + TTL 时效（90 天）+ 语义分阈值(0.75)` 三门任一不过即拒；混合分 = `vector*0.5 + tfidf*0.5`。
- **摄取管线**：rag 模块 `rag-application/.../ingest/IngestionPipeline.java` + `GlobalIngestJobOrchestrator` + `rag-worker/.../IngestJobConsumer`（含 `HeadingHierarchyChunker` 切块、Docling 解析、`ChunkPolicy` 切块策略、五轴 `EditionCoordinate` 版本坐标）。
- **影子模式（治理对照）**：`rag/rag-persistence/.../infrastructure/shadow/RagShadow*.java`（`RagShadowConfiguration`、`RagShadowSamplingPolicy`、`RagShadowReporter`、`RagShadowViolationException`、`RagShadowCollector` 等）——对语料治理/索引构建做抽样影子校验，违反即 `RagShadowViolationException`，不阻断主链路但留证（类似 `RagShadowLiveIT` 验收）。

**关键设计取舍**：RAG 是独立进程，平台侧只做「受控通道 + 白名单 + fail-closed」，不信任远端返回；语义分阈值与 TTL 在 `RetrievalService` 内作为门控常量，可测但向量库集成未闭环（占位打分）。

## 9. 成本与预算控制

**实现方式**

- **预算账户与预留账**：`budget_account`（`01_platform_ddl.sql:1514`，`total_limit/reserved_amount/settled_amount`，CHECK `budget_no_overspend: (reserved+settled)<=total_limit`，注释「数据库层最后防线」）；`budget_reservation`（`:1541`，`reserved_amount/settled_amount/state∈{RESERVED,SETTLED,RELEASED}`）。
- **预留闸门规则（三律）**：`ToolInvocationGate.java:40-48` 写明——① 预留失败即拒绝（fail-closed，降级放行=无限花钱 Sev-0）；② 预留失败记 `FAILED` 而非 `UNKNOWN`（工具没发出，记 UNKNOWN 会造幽灵待对账操作）；③ `UNKNOWN` 绝不释放预留（成本可能已发生，只有确定失败才退额度）。
- **不超发的双保险**：`budget_reservation` 注释（`:1562-1572`）说明来自「应用层单条原子条件 UPDATE（`WHERE reserved+settled+? <= total_limit`）+ DB CHECK `budget_no_overspend`」，二者缺一不可；`enforce_reservation_state_transition()`（`:428-439`）保证终态 `SETTLED/RELEASED` 不可回退（防二次占用）。
- **计量账 `usage_record`**：`01_platform_ddl.sql:3041`，`model_id/input_tokens/output_tokens/cost_amount`，以 `(tenant_id, operation_id)` 防重复结算同一逻辑操作。
- **Run 级预算**：`run.budget_amount`（`:2767`，单棵调用树上限）与租户级 `budget_account` 两口径独立；委派 `DelegationGuard.BudgetProbe` 整棵调用树共享根 Run 预算（`docs/Agent设计总览.md:226`）。
- **L3 ConsoleChat 预算**：`ConsoleBudgetAdapter`（bootstrap）是 L3 预算保护唯一组合根，关闭态构造级 passthrough、零策略解析，开启态 fail-closed（`:54-56`）。
- **租户额度配置**：`tenant_quota`（`01_platform_ddl.sql:1280`，`agent_limit/run_concurrency_limit/budget_limit`）、`tenant_config_override`（`:2956`，仅存覆盖值、缺省回落 yml）。

**关键设计取舍**：预算服务端强制执行（调用前预留、调用后结算、重复结算幂等）；DB CHECK 作为「应用层并发检查有漏」时的最后防线；UNKNOWN 不释放预留是「账实相符、可对账」的硬规则。

## 10. 可观测性 / 追踪 / 审计

**实现方式**

## 11. 可靠性与故障处理

**实现方式**

- **fail-closed 贯穿**：授权读不到=拒绝（`authz_version` 读失败→`AUTHZ_UNAVAILABLE`）；权限解析不到=抛 `ClosureResolutionException` 而非跳过（不变式 4）；预算预留失败=拒；输出命中毒性=阻断；上下文策略配置错=报错而非悄悄超窗。
- **终态错误不伪装（POISONED 事务）**：`agent-persistence/.../persistence/TransactionalConnectionHolder.java:64` 用 ThreadLocal `POISONED`。PG 事务进入 aborted 态后若异常被上层 fail-soft 吞掉，顶层 COMMIT 会**静默回滚**却让 `POST /api/runs` 返回 201 + 从未落库的 runId。`markPoisoned()` 在嵌套事务捕获 `SQLException` 时打标（`:160`），`inTransaction` 提交前 `if (isPoisoned()) throw ...`（`:172-179`）——**明确失败优于幽灵成功**。同时 `clear()` 无条件清理，防租户事务泄漏到下一个请求（跨租户泄露）。
- **状态机硬守卫**：`enforce_run_state_transition`/`enforce_approval_state_transition`/`enforce_cap_approval_state_transition`/`enforce_config_change_transition`/`enforce_tenant_lifecycle_transition` 全部 `RAISE EXCEPTION 'restrict_violation'`，终态不可迁出。
- **UNKNOWN 不伪装**：`tool_operation.state=UNKNOWN` 禁止新增 attempt（`forbid_attempt_after_terminal` `:532-536`，等同盲目重试 Sev-0）；`ToolOperationReconciliationService` 按稳定幂等键/业务唯一键查询、人工对账、受控补偿；`cap_compensation_task` 补偿失败落库由独立调度重放。
- **审计防篡改**：`forbid_audit_mutation`（`:546-560`）UPDATE 永远拒绝，DELETE 仅当会话声明 `agent.retention.actor` 且落 `erasure_certificate`。
- **重试纪律**：重试只在 `RunExecutionLoop` Worker 侧，禁止 `@Retryable`（双重重试=重复副作用）。

**关键设计取舍**：「明确 5xx 优于假 201」是事务毒化的核心取舍；UNKNOWN 停止执行转对账、绝不重放也不释放预算；状态机兜底在 DB 触发器层，应用崩了也不破坏不变量。

## 12. 部署与伸缩

**实现方式**

- **灰度上限 `pilot.max-tenants`**：`application.yml:656-658` `deployment.pilot.max-tenants: "1"`（试点期上限，是灰度承诺的一部分）。`WorkerPolicy.requireTenantSlugs(raw, maxTenants)`（`agent-application/.../config/WorkerPolicy.java:59-93`）校验租户 slug 清单**长度受 maxTenants 约束**：超过即 `IllegalStateException`（「灰度控制不得被配置绕过」）；缺失/空/重复也一律拒绝启动（fail-closed）。
- **显式租户绑定 `AGENT_TENANT_SLUGS`**：`application.yml:216` `agent.worker.tenant-slugs: "${AGENT_TENANT_SLUGS:t-a}"`。`WorkerPolicy.KEY_TENANT_SLUGS="agent.worker.tenant-slugs"`（`:36`）。注释（`:44-49`）解释为何用「显式清单」而非「扫全表」：扫全表需跨租户读权限，配置出错即静默跨租户发布；显式清单最坏是漏发/拒启（失败形态从越权降级为不可用）。
- **Worker 弹性参数**：`relay-interval-ms=200`（`:191`）、`concurrency=4`（`:193`，`>64` 拒）、`prefetch=10`（`:195`，`>100` 拒）、`outbox-batch=50`（`:197`）、`max-publish-attempts`；`lease` 续期参数。全部 fail-closed：缺失/非法一律拒绝启动，禁止退回默认值。
- **控制面/Worker 可独立部署**：`docs/系统架构图.md:351`「控制面和 Worker 可独立部署，但首期不拆成过多微服务」。
- **配置外部化**：`application.yml` 全键引用环境变量（`AGENT_TENANT_SLUGS`、`RAG_BASE_URL`、`AGENT_CONTEXT_*`、`PLATFORM_RAG_GOVERNANCE_TICKET_*` 等），避免 env 与 yml 漂移。
- **RAG 治理票据灰度**：`application.yml:756` `rag-governance-ticket.enabled`（`PLATFORM_RAG_GOVERNANCE_TICKET_ENABLED:true`），带 `rag_scope` claim，RAG 管理面只认「域=平台 + 票据声明=PLATFORM」。

**关键设计取舍**：部署参数 fail-closed（不退回默认值，避免悄悄用没人审过的并发度/租户集）；灰度上限用代码强制而非文档约定；租户清单显式化把「越权」风险降级为「不可用」风险。

## 13. 人机协同（Human-in-the-loop）

**实现方式**

- **审批状态机（运行期）**：`public.approval`（`01_platform_ddl.sql:1456`，`state∈{PENDING,APPROVED,REJECTED,EXPIRED,CONSUMED}`）；`enforce_approval_state_transition()`（`:307-331`）：PENDING 只能→APPROVED/REJECTED/EXPIRED；APPROVED 只能→CONSUMED/EXPIRED/REJECTED；终态（CONSUMED/REJECTED/EXPIRED）不可迁出。`approval` 绑定具体 `operation_id + 参数摘要 + 目标资源 + 有效期`（`approval` 注释：消费审批前必须检查 Run 是否已取消）。
- **CAP 审批（治理期，更强）**：`public.cap_approval`（`01_platform_ddl.sql:1695`）状态机 `PENDING→RESERVED→INTENT_SUBMITTED→CONSUMED`，旁路 `EXPIRED/CANCELLED/AWAITING_HUMAN`（`enforce_cap_approval_state_transition` `:338-366`，状态只能前进）；支持**预占 + 双哈希**（`approval_scope_hash`/`effective_args_hash`/`closure_fingerprint`），消费时重新验证参数是否仍落在范围内，防「参数替换重放」；`authz_version` 绑定，当前版本>生成时版本→审批失效。
- **审批消费端口**：`ToolInvocationGate` 经 `ApprovalPort` 消费，`RiskBasedApprovalPolicy.ApprovalSource` 默认 `FAIL_CLOSED`（真实审批台未接入前需审批工具一律拒）。`ApprovalController`（agent-api）提供审批决策端点。
- **治理发布（双人复核 + 不可变发布）**：`cap_config_publish_request`（`:1852`，`two_person_ck: approver_id <> requester_id`，scope∈{TENANT,PLATFORM}）、`cap_config_release`（`:1920`，`config_publish_seq` 单调，`cap_config_pointer` 当前版本只由指针指向的 PUBLISHED release 决定，**绝不以 max(seq) 选择**）；发布经 `ConfigPublishService` 双人复核 + CAS 切指针，`authz_version`/`config_publish_seq` 单调递增。
- **modelRef 治理发布绑定**：`cap_agent_def.model_ref`（`01_platform_ddl.sql:1664-1667`）Agent 绑定的模型引用，NULL=未绑定→运行期取不到模型即拒绝执行（**绝不回落默认模型**）；`model_ref` 随 Agent 定义经治理发布固化，已发布版本行 `forbid_published_def_mutation` 不可改写——即「治理期发布、运行期钉死」。
- **UNKNOWN 人工处置**：`tool_operation.state=MANUAL_DISPOSED` 需 `manual_disposed_by/manual_disposed_at`（`:3003`），`unknown:dispose` 动作受 `AuthorizationService.Actions.UNKNOWN_DISPOSE` 管控。

**关键设计取舍**：审批与发布的「状态只能前进、终态不可迁出」由 DB 触发器强制；参数替换重放靠双哈希在消费时重验；双人复核用应用层 + DB CHECK 双保险；治理期模型/配置绑定后运行期只读快照，杜绝「运行期临时改边」。
