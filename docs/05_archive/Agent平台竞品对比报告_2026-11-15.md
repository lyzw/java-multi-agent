# 自研 Java 多租户 SaaS Agent 平台 vs 前沿 Agent 框架 — 完整对比报告

> 生成日期：2026-11-15
> 范围：本项目（Java 多租户 SaaS Agent，包名 `cn.studykid.multiagent`，Spring Boot 4.1.1 / Java 21 / PostgreSQL 17 / RabbitMQ）与 7 个前沿 Agent 框架/SDK 的逐项能力对比。
> 证据原则：**本项目实现全部取自 `platform/` 源码与 `deploy/sql` 的 DDL（见 `docs/能力维度实现方式梳理报告.md`）；竞品实现全部取自各框架官方文档**，逐条标注来源 URL，未做臆测。

---

## 0. 执行摘要

- **本项目最突出的差异化**：在「多租户隔离」「预算/不超发控制」「fail-closed 故障语义」「DB 触发器级状态机」「不可变审计」这五项上，是本次对比的全部框架里**内建程度最高**的——绝大多数前沿框架把这些交给宿主应用或不提供。
- **前沿框架最突出的优势**：开发者体验（code-first、几行搭好）、内建可观测仪表盘（LangSmith / OpenAI Tracing）、内建 RAG 生态（ADK Vertex RAG、CrewAI Knowledge、LangChain vectorstore）、托管部署运行时（ADK Agent Runtime、LangGraph Agent Server、CrewAI AMP）、丰富工具生态（MCP / OpenAPI / 厂商预置工具）。
- **诚实短板**：本项目偏「数据库/治理中心化」，缺轻量 SDK；RAG 向量打分仍占位未闭环；部署为手工配置（无托管运行时）；上下文压缩 W3 摘要依赖外部 summarizer；多租户灰度仍硬编码上限、缺自动化。
- **关键结论**：两者范式不同——前沿框架是「库/编排 SDK」，本项目是「带强治理与强隔离的生产运行时」。直接可比的是能力覆盖，而非抽象层级。

## 2. 逐能力维度对比

> 每个维度按四块组织：**①我们的实现**（证据锚点）、**②竞品实现**（按框架，附来源）、**③竞品优点**、**④我们的优点**，最后给**差异与诚实短板**。

### 维度 1 · 架构与编排模型

**① 我们的实现**
- **Run / run_step 两段式执行模型**：一个 `run` 是执行实例，`run_step` 记录每轮「既成事实」；`run_step.state` 恒为 `RUNNING`（DDL 注释明确定义为「步骤已发生」而非进行中，完成看 `completed_at`）。证据：`01_platform_ddl.sql:2832-2834`。
- **编排引擎 `RunExecutionLoop`** 只做编排（串联模型调用→工具闸门→状态提交），主循环步数上限取自 **Run 快照**而非动态配置。证据：`agent-worker/.../RunExecutionLoop.java:68`。
- **状态机由 DB 触发器守卫**：`enforce_run_state_transition()` 只允许有限跃迁，其余 `RAISE EXCEPTION 'restrict_violation'`。证据：`01_platform_ddl.sql:453-475`。
- **事件/队列驱动 + Outbox**：Run 创建与 `outbox_event` 同事务提交，由 Relay 轮询投 MQ 唤醒 Worker。证据：`docs/系统架构图.md:199`、`application.yml:191`。
- **多级编排**：`cap_agent_def.orchestration` 声明 `LEAF/ROUTER/SEQUENTIAL`，子 Agent 经 `WorkerChildAgentRunner` 起小循环。证据：`docs/Agent设计总览.md:60-69`。

**② 竞品实现**
- **OpenAI Agents SDK**：无显式图，编排靠代码（asyncio）或 LLM（Handoffs）。来源：https://openai.github.io/openai-agents-python/
- **Anthropic Agent SDK**：agent loop 由 Claude Code 二进制驱动，编排在 SDK 层封装。来源：https://docs.anthropic.com/en/api/agent-sdk
- **LangGraph**：显式 `StateGraph`（State/Node/Edge + channels/reducer）。来源：https://docs.langchain.com/oss/python/langgraph/graph-api
- **Google ADK**：`Agent`（LlmAgent）+ `Workflow` 图（Nodes/Edges，支持 graph/dynamic/collaborative/template）。来源：https://adk.dev/graphs/ 、https://adk.dev/workflows/
- **AutoGen**：Core 事件驱动运行时 + AgentChat 对话 API。来源：https://microsoft.github.io/autogen/stable/
- **CrewAI**：`Crew = Agents + Tasks + Process`（sequential/hierarchical）+ `Flows`（`@start/@listen`）。来源：https://docs.crewai.com/en/concepts/flows
- **Agno**：`Agent`/`Team`/`Workflow` 抽象，Team 支持 coordinate/route/broadcast。来源：https://docs.agno.com/teams/overview

**③ 竞品优点**
- 开发者可「几行代码」搭好编排，迭代快、心智负担低（OpenAI/ADK/CrewAI/Agno 共同点）。
- LangGraph 的显式状态图让确定性步骤与 LLM 步骤可混排、流程可精确控制。
- ADK 同时提供声明式图与工作流多种形态，灵活度高。

**④ 我们的优点**
- **权威事实源在数据库、MQ 只负责唤醒**：崩溃后可从任意租约点重读 DB 恢复，不依赖内存状态。
- **状态跃迁在 DB 触发器层硬守卫**：应用即使崩溃也不破坏不变量（终态不可迁出）。
- **重试纪律严格**：只在 Worker 侧实现，禁止 `@Retryable`，避免对有副作用工具重复写入（Sev-0）。

**差异与诚实短板**：本项目编排是「数据库/快照驱动」，对开发者不够「轻」；缺少 LangGraph 那种可视化、可组合的状态图 DSL。但换来的是强一致与可恢复性。

### 维度 2 · 多租户隔离

**① 我们的实现**
- **RLS + GUC 函数 `current_tenant_id()`**：`SELECT NULLIF(current_setting('app.tenant_id', TRUE), '')::UUID`，未设置即返回 NULL、所有 RLS 策略拒绝——**默认拒绝**（fail-closed）。证据：`01_platform_ddl.sql:289-293`。
- **42 张表挂 RLS、50 条策略**，`FORCE ROW LEVEL SECURITY`，策略形如 `USING (tenant_id = current_tenant_id())`。证据：DDL 头注释 `:5`、`01_platform_ddl.sql:5830`。
- **双保险**：跨表引用用 `(tenant_id, 父id)` 复合外键；`agent` 表 `UNIQUE(tenant_id, agent_id)` 专为保证租户一致。证据：`docs/Agent设计总览.md:253`。
- 应用层另有 `RoleBasedAuthorizationService` 做「执行时重新授权」，与 RLS 两层独立。证据：`agent-ports/.../security/AuthorizationService.java:20`。

**② 竞品实现**
- **OpenAI / Anthropic / LangGraph / ADK / AutoGen / CrewAI**：**均无内建多租户隔离原语**。隔离以 `thread_id` / `user_id` / `session_id` 为作用域，交由宿主应用或托管运行时负责。来源：LangGraph https://docs.langchain.com/oss/python/langgraph/persistence ；ADK https://adk.dev/sessions/
- **Agno 是唯一内建多租户安全的框架**：JWT/service-account/security-key 认证 + 授权作用域 + per-user 数据隔离。来源：https://docs.agno.com/agent-os/security/overview
- **CrewAI 企业层**（Control Plane/Enterprise）才提供 RBAC、审计、IAM。来源：https://www.crewai.com/

**③ 竞品优点**
- Agno 内建认证+授权+每用户隔离，开箱即有租户安全边界。
- 其余框架虽不内建，但因其「库」形态，宿主应用可按自身模型灵活隔离，无框架约束。

**④ 我们的优点**
- **数据库级强制隔离（RLS）+ 默认拒绝**，即使应用层 bug 也很难越权（越权读返回 0 行而非报错伪装）。
- RLS 与应用层授权**双层独立、互不替代**，纵深防御。
- 复合外键级联保证引用完整性下的租户一致。

**差异与诚实短板**：Agno 在「框架内建」上略胜；但本项目 RLS 是**强制且默认拒绝**的硬边界，强于仅依赖应用层或 session 作用域的方案。代价是部署必须正确绑定 GUC，配置错误会「假绿/假失败」（见铁律 1）。

### 维度 3 · 状态持久化与可恢复性

**① 我们的实现**
- **PG 为权威源**：Run 创建与 `outbox_event` 同事务写入。证据：`01_platform_ddl.sql:2623`。
- **断点续跑 = 重读 DB + 租约 + fencing_token**：`enforce_fencing_on_write()` 触发器拒绝旧世代写新世代（`NEW.fencing_token < OLD.fencing_token` 直接拒）。证据：`01_platform_ddl.sql:410-421`、`2730-2732`。
- **幂等/去重**：`idempotency_record` 三态判定；`run_message.idem_key` 唯一约束冲突覆盖而非追加。证据：`:2549`、`:2886`。
- **不可变快照**：`execution_snapshot` 禁止修改；已发布 `cap_*_def` 行除停用外拒绝改写。证据：`:616-623`、`:574-609`。

**② 竞品实现**
- **LangGraph**：Checkpointer（线程级短期）+ Store（跨线程长期），支持 PostgresSaver/SqliteSaver、time-travel、断点续跑。来源：https://docs.langchain.com/oss/python/langgraph/persistence
- **Google ADK**：SessionService + MemoryService，云/DB 后端；Agent Runtime 下支持 session resumption。来源：https://adk.dev/sessions/
- **Agno**：db 持久化 + `continue_run` 续跑 + **Durable Queue**（Postgres/Redis，`SELECT ... FOR UPDATE SKIP LOCKED`，心跳租约、幂等键）。来源：https://docs.agno.com/agent-os/background-execution/durable-queue
- **AutoGen**：Memory 协议 + `save_state/load_state`。来源：https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/memory.html
- **CrewAI**：Flows `@persist`（SQLite）、Crew `checkpoint=True`。来源：https://docs.crewai.com/en/concepts/flows

**③ 竞品优点**
- LangGraph 的 time-travel / 断点续跑是业界标杆，调试与可恢复性极强。
- Agno 的 Durable Queue（`FOR UPDATE SKIP LOCKED` + 心跳租约）与本项目思路高度相似，且已产品化。
- ADK 的 Session/Memory 分层清晰，天然支持跨会话长期记忆。

**④ 我们的优点**
- **fencing_token 防脑裂/双 Worker 写同一 Run**，比单纯租约更硬（旧世代写被 DB 拒绝）。
- **UNKNOWN 状态绝不释放预算预留、转对账而非盲目重放**，账实相符。
- 不可变快照 + 已发布定义不可改写，杜绝运行期「临时改边」。

**差异与诚实短板**：本项目具备与 Agno Durable Queue 对等的 durable execution 能力，但**未封装为可独立复用的「队列 SDK」**；time-travel 这类调试能力弱于 LangGraph。

### 维度 4 · 流式输出

**① 我们的实现**
- **SSE 端点 `RunEventStreamer`**：服务端轮询 `run_event`（`sequence_no` 单调）后逐行发 SSE 帧，`eventType + sequence_no` 作 `id`。证据：`agent-api/.../api/run/RunEventStreamer.java:32,182`。
- **done 终帧 = SSE 注释帧 `:run-terminal`**：取终态时 `sendComment("run-terminal")` 后 `complete()`——必须用注释行（前端解析器只认注释），发事件帧会被丢弃导致永不终止。证据：`:196-200,73-82`。
- SSE **只读 `run_event`、不写 outbox**；轮询间隔/存活时长全配置化。证据：`:220-229`。

**② 竞品实现**
- **OpenAI Agents SDK**：streaming events（逐 token / run events）。来源：https://openai.github.io/openai-agents-python/
- **LangGraph**：`stream_mode` 含 `values/updates/messages/custom/checkpoints/tasks/debug`。来源：https://docs.langchain.com/oss/python/langgraph/streaming
- **Google ADK**：SSE 逐字 + 双向 live（`run_live()` 语音/视频可打断）+ `async_stream_query`。来源：https://adk.dev/live/
- **Agno**：`agent.run(stream=True)` 事件流。来源：https://docs.agno.com/hitl/overview
- **CrewAI**：`stream=True` 返回 `CrewStreamingOutput` 逐块迭代。来源：https://docs.crewai.com/en/concepts/crews
- **AutoGen**：`BaseGroupChat.run_stream`。来源：https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/index.html

**③ 竞品优点**
- ADK 的双向 live streaming（语音/视频可打断）与 LangGraph 的多模式 stream 在「交互形态丰富度」上领先。
- 多数框架流式与运行时一体，开箱即用、无需自建轮询。

**④ 我们的优点**
- **终止信号用控制帧表达**，避免业务事件流混入假事件；终态立即 `complete()` 释放连接。
- 流直接读持久化事实表，天然幂等、可重连续读（cursor 基于 `sequence_no`）。
- 连接生命周期有 `max-lifetime` 兜底强制关闭，防泄漏。

**差异与诚实短板**：我们是「服务端轮询 + SSE」（真零轮询 `LISTEN/NOTIFY` 归 P4），延迟由配置决定；交互形态（语音/视频打断）不如 ADK 丰富。

### 维度 5 · 工具 / 函数调用

**① 我们的实现**
- **统一闸门 `ToolInvocationGate`**：执行链契约「Schema 校验→重新授权→幂等键→账本→审批→预算→执行→账本更新」，**明确禁止 Spring AI `ToolCallingAdvisor` 自动执行路径**（会绕过闸门）。证据：`agent-worker/.../ToolInvocationGate.java:53`、ADR-011 §3.3。
- **闭集 Schema 校验 `ToolInputSchemaValidator`**：「必填的在、没声明的不在」，Schema 非法直接拒绝（不当「无约束」）。证据：`agent-infrastructure/.../tool/ToolInputSchemaValidator.java:27`。
- **工具定义来源 `cap_tool_def`**：`risk_level NOT NULL + CHECK` 强制显式副作用等级，`kind ∈ {native,mcp,http}`；模型只「提建议」，平台负责授权/调度/执行/持久化。证据：`01_platform_ddl.sql`。
- **三层逻辑操作模型 `tool_operation`** 记录每次重试与终态，UNKNOWN 禁止新增 attempt。证据：`:2983,3018,516-539`。

**② 竞品实现**
- **OpenAI/Anthropic**：基于模型 function calling，工具由 SDK 调度执行（自动路径）。来源：https://openai.github.io/openai-agents-python/
- **LangGraph**：`@tool` 装饰器（类型注解=输入 schema），可混用任意函数节点。来源：https://docs.langchain.com/oss/python/langchain/tools
- **Google ADK**：`FunctionTool` + 预置 Google Search/Code Exec/MCP/OpenAPI。来源：https://adk.dev/tools-custom/ 、https://adk.dev/integrations/
- **AutoGen**：McpWorkbench（MCP）、DockerCommandLineCodeExecutor（Docker 沙箱）。来源：https://microsoft.github.io/autogen/stable/
- **CrewAI**：`tools` 列表 + `function_calling_llm`；`before_tool_call` hooks 拦截。来源：https://docs.crewai.com/en/concepts/crews
- **Agno**：`tools`/integrations/MCP；callable factories 动态解析。来源：https://docs.agno.com/agents/overview

**③ 竞品优点**
- 生态丰富：MCP、OpenAPI、厂商预置工具（Google Search/Code Exec）开箱即接。
- 开发体验顺滑：装饰器即工具，模型自动调度。

**④ 我们的优点**
- **模型永远不自动执行**，所有工具调用必须穿过唯一闸门并经过多步准入——安全边界不可绕过。
- **闭集 Schema 校验「错误即拒、不尽力解析」**，避免漏掉 `additionalProperties:false` 导致未声明参数被放行。
- 工具副作用等级（`risk_level`）强制显式声明，配合审批/预算闸门分级管控。

**差异与诚实短板**：缺少 MCP/OpenAPI 等开箱生态的广度（仅有 `kind=mcp/http` 动态通道，未像 ADK/CrewAI 那样预置大量工具）；开发侧「写工具」不如装饰器式顺手。

### 维度 6 · 上下文管理

**① 我们的实现**
- **独立算法模块 `agent-context`** + `CompactionPipeline`：分级压缩 **W1 可逆外置 → W2 整轮裁剪 → W3 增量摘要**。硬约束：**零 LLM / 零 IO / 零请求字节变更**（W3 摘要经注入 `Summarizer` 产出）。证据：`agent-context/.../context/CompactionPipeline.java:22-25,37`。
- **首轮锚（USER）永不丢**；W1 只替换 TOOL content、不动 assistant tool_calls 配对。证据：同上。
- **水位/预算**：`WaterLevel`（W0/W1/W2/HARD）、`ContextBudget`、`GlobalContextPolicy`（`hard-ceiling-tokens` 等）。运行时参数 `context-token-budget=16000` 等。证据：`application.yml:208,255-258`。
- **摘要失败绝不伪造**（回落 W2，`fallback=true` + 稳定原因码）。证据：`agent-context` 模块。

**② 竞品实现**
- **LangGraph**：`add_messages` reducer 追加/按 ID 更新；**无内建自动压缩**，裁剪靠 LangChain `trim_messages`。来源：https://docs.langchain.com/oss/python/langgraph/graph-api
- **Google ADK**：自动过滤无关事件、总结较早轮次、延迟加载 Artifacts、跟踪 token（「上下文即源代码」式管理）。来源：https://adk.dev/
- **Agno**：Memory/Chat history/Session state 三层分离。来源：https://docs.agno.com/memory/overview
- **AutoGen/CrewAI**：统一 Memory 类（含 RAG 注入上下文）。来源：CrewAI https://docs.crewai.com/en/concepts/memory

**③ 竞品优点**
- ADK 的上下文组装/总结/延迟加载在工程化上较完整。
- LangGraph 的 `trim_messages` 与消息 reducer 灵活，可组合。

**④ 我们的优点**
- **压缩是确定性纯函数（同输入恒等输出）**，与模型调用解耦，避免 ReDoS/循环依赖。

### 维度 11 · 可靠性与故障处理

**① 我们的实现**
- **fail-closed 贯穿**：授权读不到=拒绝、预算预留失败=拒、输出命中毒性=阻断、上下文配置错=报错而非超窗。
- **POISONED 事务**（`TransactionalConnectionHolder`）：PG 事务进入 aborted 态若被 fail-soft 吞掉，顶层 COMMIT 会静默回滚却返回 201 假成功；`markPoisoned()` 在嵌套事务捕获 SQLException 打标，提交前 `if (isPoisoned()) throw`——**明确 5xx 优于假 201**；`clear()` 无条件清理防租户事务泄漏。证据：`agent-persistence/.../persistence/TransactionalConnectionHolder.java:64,160,172-179`。
- **状态机硬守卫**：5 个 `enforce_*_state_transition` 全部 `RAISE EXCEPTION 'restrict_violation'`。证据：`01_platform_ddl.sql`。
- **UNKNOWN 不伪装**：`tool_operation.state=UNKNOWN` 禁止新增 attempt，转 `ToolOperationReconciliationService` 对账。证据：`:532-536`。
- **审计防篡改**：`forbid_audit_mutation` UPDATE 永远拒。证据：`:546-560`。

**② 竞品实现**
- **LangGraph**：节点级 `RetryPolicy`（指数退避/抖动）+ `TimeoutPolicy` + `error_handler`，仅重试瞬时错误；中断后节点从头重跑（副作用需幂等）。来源：https://www.langchain.com/blog/fault-tolerance-in-langgraph
- **Agno**：Durable Queue 心跳租约 + `max_attempts` 重试 + Idempotency-Key。来源：https://docs.agno.com/agent-os/background-execution/durable-queue
- **Google ADK**：workflow retry + Reflect&Retry/Restate 等集成（节点级 error-handling 语义官方页未完全明示，保持诚实不臆测）。来源：https://adk.dev/integrations/reflect-and-retry/
- **CrewAI**：checkpoint + 工具缓存 + `max_rpm` + guardrail 重试。来源：https://docs.crewai.com/en/concepts/crews
- **Anthropic**：`max_turns` 防失控。来源：https://docs.anthropic.com/en/api/agent-sdk

**③ 竞品优点**
- LangGraph 节点级 RetryPolicy/TimeoutPolicy/error_handler 是成熟的容错原语，配置粒度细。
- Agno 的 Durable Queue 提供生产级弹性执行。

**④ 我们的优点**
- **「明确 5xx 优于假 201」的 POISONED 机制**直接封堵「静默回滚却返回成功」这一最危险的失真来源。
- **DB 触发器级状态机**兜底，应用崩了也不破坏不变量（终态不可迁出）。
- **UNKNOWN 停止执行转对账、绝不重放也不释放预算**，避免重复副作用与账实不符。

**差异与诚实短板**：缺少 LangGraph 那样声明式、可组合的节点级容错策略；重试仅 Worker 侧、粒度较粗。但「事务毒化防护 + 状态机兜底 + UNKNOWN 对账」在**防止静默失真**上比多数框架更彻底。

**② 竞品实现**
- **LangGraph**：`interrupt()` + `Command(resume=...)`，可在任意点暂停/编辑状态/批准，恢复须同 thread_id。来源：https://docs.langchain.com/oss/python/langgraph/interrupts
- **Google ADK**：Tool Confirmation（执行前暂停征询 yes/no 或结构化输入，支持远程 REST 审批）+ human input 节点。来源：https://adk.dev/tools-custom/confirmation/
- **Anthropic**：`canUseTool` 审批回调。来源：https://docs.anthropic.com/en/api/agent-sdk
- **OpenAI**：Guardrails 内嵌审批。来源：https://openai.github.io/openai-agents-python/
- **CrewAI**：Flows `@human_feedback`（暂停收集反馈并路由 approved/rejected）。来源：https://docs.crewai.com/en/concepts/flows
- **Agno**：完整 HITL 框架（User Confirmation/Input/External Execution/Approval & Audit），`pause`→`continue_run`。来源：https://docs.agno.com/hitl/overview
- **AutoGen**：`UserProxyAgent` 在决策点审批。来源：https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/selector-group-chat.html

**③ 竞品优点**
- LangGraph `interrupt()` + `Command(resume)` 可在**任意点**暂停并编辑状态，细粒度与灵活性最佳。
- ADK Tool Confirmation 支持远程 REST 审批，工程化完整。
- Agno 的 HITL 覆盖确认/输入/外部执行/审批审计全谱。

**④ 我们的优点**
- **审批/发布「状态只能前进、终态不可迁出」由 DB 触发器强制**，比应用层 if 判断更可靠。
- **双哈希参数重验**防「参数替换重放」（审批 A 工具却执行 B 参数）。
- **双人复核用应用层 + DB CHECK 双保险**，`authz_version` 绑定使审批随授权撤销即时失效。
- **治理期模型/配置绑定后运行期只读快照**，杜绝「运行期临时改边」。

**差异与诚实短板**：缺少 LangGraph 那种「任意点中断 + 状态编辑」的灵活交互；HITL 目前以「工具执行前审批 + 治理发布审批」为主，运行期对话中动态中断编辑能力弱于 LangGraph。

## 3. 综合对比矩阵（总表）

| 维度 | 我们 | 竞品普遍做法 | 我们相对优势 | 我们相对短板 |
|---|---|---|---|---|
| 1 编排模型 | Run/run_step + DB 状态机 + 队列驱动 | 图/Handoffs/代码编排（库形态） | 强一致、可恢复、状态机硬守卫 | 开发侧不够轻、无可视化 DSL |
| 2 多租户隔离 | RLS + GUC + 默认拒绝 + 复合外键 | 多数无内建（Agno 有内建） | **DB 强制隔离、纵深防御** | 配置错误会假绿/假失败 |
| 3 持久化/恢复 | PG 权威源 + fencing + 不可变快照 | Checkpointer/Store/Durable Queue | fencing 防脑裂、UNKNOWN 转对账 | 未封装为可复用队列 SDK；无 time-travel |
| 4 流式 | SSE + 持久化事件 + 控制帧终态 | 多模式 stream / 双向 live | 幂等续读、终态释放连接 | 服务端轮询、无语音/视频打断 |
| 5 工具调用 | 统一闸门 + 闭集 Schema + 模型不自动执行 | function calling + 自动执行 + 丰富生态 | 安全边界不可绕过、错误即拒 | MCP/OpenAPI 预置工具广度不足 |
| 6 上下文 | 确定性纯函数分级压缩、摘要不伪造 | trim_messages / 自动总结 | 确定性、诚实降级 | W3 摘要依赖外部、无 trim 生态 |
| 7 权限护栏 | 显式 Gate + 极细动作矩阵 + fail-closed + 影子对账 | Guardrails/中间件/内建 PII 检测 | 读不到=拒绝、双人复核不被绕过 | 缺开箱 PII/注入检测库 |
| 8 RAG | 独立服务 + fail-closed 网关 + 三重门 + 影子 | 内建 RAG + 多向量库生态 | 不信任远端、治理对照强 | 向量打分占位未闭环 |
| 9 成本预算 | **DB 强制不超发 + 预留/结算/幂等** | 多数无内建（Anthropic 会话熔断） | **全链路最强不超发** | 缺轻量一行配置熔断 |
| 10 可观测审计 | 指标确定函数 + 审计不可改 + 风险只存摘要 | LangSmith/OpenAI Dashboard/OTel | 审计硬约束、终态≠成功 | 缺零配置可视化仪表盘 |
| 11 可靠性 | POISONED 事务 + 状态机兜底 + UNKNOWN 对账 | 节点重试/超时/幂等键 | 防静默失真最彻底 | 缺声明式节点容错策略 |
| 12 部署伸缩 | 灰度上限代码强制 + 显式 slug + 参数 fail-closed | 托管/自托管运行时 | 部署参数安全取向明确 | 无托管运行时、手工运维 |
| 13 人机协同 | DB 触发器状态机 + 双哈希防重放 + 双人复核 | interrupt/resume、Tool Confirmation | 参数替换重放防护、不可变发布 | 缺任意点中断+状态编辑 |

## 4. 我们的差异化优势与待补强项

### 4.1 我们明显领先的能力（建议作为对外卖点）
1. **多租户强隔离**（RLS 默认拒绝 + 应用层显式 Gate 双层）。
2. **成本/预算硬不超发**（DB CHECK + 执行前预留 + UNKNOWN 不释放，全链路）。
3. **fail-closed 故障语义**（POISONED 事务封堵假 201、状态机终态不可迁出、UNKNOWN 转对账）。
4. **不可变审计与合规红线**（审计只增不改、risk_event 只存摘要）。
5. **强一致可恢复执行**（PG 权威源 + fencing 防脑裂 + 不可变快照）。

### 4.2 待补强项（诚实清单，对应项目记忆缺口）
1. **开发者体验**：缺轻量 SDK/DSL；写工具不如装饰器式顺手；缺可视化编排。
2. **RAG 闭环**：向量打分占位未闭环；缺内建多向量库生态（对标 ADK/CrewAI/Agno）。
3. **可观测仪表盘**：缺 LangSmith/OpenAI 式零配置可视化；Prometheus alert rules 未落地。
4. **托管/弹性运行时**：无 Agent Runtime/Agent Server 式托管，伸缩靠手动起 Worker。
5. **开箱护栏库**：缺 OpenAI/Agno 式 PII/提示注入检测库（自研正则受引擎限制）。
6. **运行期 HITL 灵活性**：缺 LangGraph `interrupt()`+`Command(resume)` 式任意点中断编辑。
