# 模型统一配置架构设计（管理后台集中维护）

> 适用范围：平台（platform reactor）与检索（rag reactor）中所有 LLM / Embedding 模型。
> 目标：**所有模型的定义与选择集中到管理后台维护，运行时统一从配置源读取，禁止硬编码或分散定义。**

## 1. 总体架构

```
┌─────────────────────────┐         CRUD          ┌──────────────────────────┐
│   管理后台 (admin-console) │ ───────────────────▶ │  AdminModelConfigController│
│   超级管理员维护模型目录    │                      │  (PLATFORM_ADMIN 鉴权)     │
└─────────────────────────┘                      └───────────┬──────────────┘

                                                              │ 读
                              ┌───────────────────────────────┼───────────────────────────────┐

                     ┌────────────────┐            ┌────────────────────┐          ┌──────────────────────┐
                     │  ModelResolver  │            │  ModelCredential    │          │ InternalModelConfig  │

              ┌──────────────┼──────────────┐                │                               │
```

> **本轮补齐（2026-11-07 续）**：① Agent 的 `modelRef` 经 `AgentModelConfigAssembler` → `ModelResolver`（scenario=agent-chat，命中取目录模型名，否则回落字面名 fail-soft），闭环「所有模型从此配置取」；② RAG embedding 端口在 bootstrap 与 worker 两条路径均采用目录解析（模型名+维度恒取目录，仅 baseUrl 缺失时回落 yml），消除入库/检索侧嵌入模型不一致隐患；③ `model_catalog` 已种子 4 行默认模型（agent-chat / console-chat / embedding / default），避免链路 fail-closed。种子写入 `deploy/sql/platform/01_platform_ddl.sql` 与幂等 `deploy/sql/platform/seed_model_catalog.sql`。

**核心原则**
- **单一事实来源**：模型定义只存在于 `model_catalog` 表 + 管理后台，不在 yml / 代码里散落。
- **密钥与目录分离**：目录表**不含 API Key**；密钥按 `provider` 从环境变量解析（`ModelCredentialProvider`），遵守项目铁律「api-key 仅环境变量注入，不得入库」。
- **fail-closed**：解析不到可用模型时**拒绝猜测**，由调用方按确定失败处理。
- **改完即生效**：`ModelResolver` 每次读端口、端口实现不缓存（RAG 客户端侧加 TTL 缓存以省调用），无需重启。

## 2. 数据结构：`ModelDefinition`

位置：`platform/agent-ports/.../ports/modelcatalog/ModelDefinition.java`（不可变值对象，无 DB/JDBC 类型）

| 字段 | 类型 | 说明 | 约束 |
|------|------|------|------|
| `id` | String(uuid) | 主键 | 新增时由仓储生成 |
| `provider` | String | 提供商（minimax / openai / deepseek / ollama / bge / workbuddy …） | **非空** |
| `scenario` | String | 使用场景 code（见 §4） | **非空** |
| `modelName` | String | 发给供应商的真实模型标识（如 `MiniMax-M2.5`、`bge-m3`） | **非空** |
| `displayName` | String? | 展示名 | 可空，空则回退 `modelName` |
| `baseUrl` | String? | 供应商基础地址 | 可空，缺省由凭据解析器给默认值 |
| `isDefault` | boolean | 该场景默认模型 | 每场景至多一个（部分唯一索引强制） |
| `supportsTools` / `supportsStreaming` / `supportsVision` | boolean | 能力声明 | 运行时裁剪请求 |
| `dimension` | Integer? | 向量维度（仅嵌入模型） | 须与向量列维度一致 |
| `isEnabled` | boolean | 软开关 | 禁用即不参与解析 |
| `sortOrder` | int | 同场景排序 | 列表展示 |
| `description` | String? | 备注 | |
| `createdAt` / `updatedAt` | Instant? | 时间戳 | 仓储回填 |

**建表（DDL，`deploy/sql/platform/01_platform_ddl.sql`）**

```sql
CREATE TABLE public.model_catalog (
    id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    provider text NOT NULL,
    scenario text NOT NULL,
    model_name text NOT NULL,
    display_name text,
    base_url text,
    is_default boolean NOT NULL DEFAULT false,
    supports_tools boolean NOT NULL DEFAULT true,
    supports_streaming boolean NOT NULL DEFAULT true,
    supports_vision boolean NOT NULL DEFAULT false,
    dimension integer,
    is_enabled boolean NOT NULL DEFAULT true,
    sort_order integer NOT NULL DEFAULT 0,
    description text,
    created_at timestamptz NOT NULL DEFAULT now(),
    updated_at timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX model_catalog_scenario_name_uq ON model_catalog (scenario, model_name);
CREATE UNIQUE INDEX model_catalog_scenario_default_uq ON model_catalog (scenario) WHERE is_default;
```

> **无 RLS、无 tenant_id**：模型是平台级资源，由超级管理员统一维护、所有租户共用，与「管理后台集中管理」语义一致。新增表后快照计数已从 67 同步为 **68**（`scripts/init-db.sh`、`scripts/it-env.sh --probe`）。

## 3. 获取方式：`ModelResolver`

位置：`platform/agent-application/.../application/modelcatalog/ModelResolver.java`

解析优先级（同场景内）：

1. **显式 `modelName`** → 优先在**该场景**内匹配启用中的同名模型；场景内无则退化为「全目录同名启用模型」；
2. 未给显式名 / 未命中 → 取**该场景的默认模型**；
3. 该场景无默认 → 回落到 `default` 场景的默认模型；
4. 都没有 → **返回空（fail-closed，绝不随便挑一个模型）**。

- 已禁用（`isEnabled=false`）模型**一律跳过**，即便在默认位或被显式点名。
- `resolveRequired(scenario, model)` 在「没有模型就绝不能继续」的语境下使用，取不到即抛。
- **不缓存**：每次解析都读 `ModelCatalogPort`，管理后台改完下一次调用即生效。

各模块调用示例：
- LLM 网关工厂：`resolver.defaultForScenario("agent-chat")` → 取 provider / baseUrl / modelName 构建网关；密钥 `credentialProvider.apiKeyFor(provider)`。
- RAG 嵌入：`ModelCatalogClient.resolveEmbeddingModel()`（见 §5）→ provider / baseUrl / modelName / dimension。

## 4. 场景定义与默认模型

场景为**字符串 code**（非枚举），由管理后台自由定义；平台强依赖的内置场景固化在 `ModelScenario` 作为约定值：

| code | 含义 |
|------|------|
| `agent-chat` | 主 Agent 对话（Worker 执行链路核心调用） |
| `console-chat` | 管理后台「直接对话」流式调试 |
| `embedding` | 向量化（RAG 索引与查询共用） |
| `summarization` | 摘要 / 归纳 |
| `classification` | 分类 / 意图识别 |
| `moderation` | 内容安全审核（输出护栏） |
| `default` | **兜底场景**：其它场景无命中时回落到此处的默认模型 |

**默认模型规则**：每个场景（含 `default`）至多一个 `isDefault=true`（`model_catalog_scenario_default_uq` 部分唯一索引强制）。解析器保证「任何场景都至少能回落到一个默认模型（若管理员配了）」；若某场景及其回落链都无默认，则 fail-closed。

> ⚠️ **必做**：管理员需在后台为每个使用的场景配置一个默认模型（例如 `agent-chat` 默认 MiniMax-M2.5、`embedding` 默认 bge-m3），否则对应链路会因「无可用模型」而 fail-closed。

## 5. 项目对统一配置源的依赖关系

### 5.1 平台（platform reactor）
- **依赖**：`agent-ports`(ModelDefinition/Port/Scenario) → `agent-application`(ModelResolver) → `agent-persistence`(JdbcModelCatalogRepository，全局表直连) / `agent-infrastructure`(ModelCredentialProvider) → `agent-api`(Admin + Internal 控制器) → `platform-bootstrap`(网关工厂接线)。
- **接线点**：`WorkerExecutionConfig.modelGateway()` 优先从 `ModelResolver` 取 `agent-chat` 默认模型构建网关；无目录配置 / 无密钥时回落 yml、再回落 Fake（保持 `ChatStreamGatewayWiringTest` 通过）。
- **密钥来源**：`agent.model.<provider>.api-key` / `.base-url`（环境变量），不入库。

### 5.2 RAG（rag reactor，独立库）
- **不直连平台库**（ADR-011：两 reactor 两库互不塞代码）。
- **依赖**：`ModelCatalogClient`（rag-infrastructure）经 **内部 HTTP API** `GET /api/internal/models/resolve?scenario=embedding` 解析嵌入模型；响应**不含密钥**，RAG 侧用自身 `rag.embedding.api-key` 作为密钥。
- **安全回落**：未配置 `rag.model-catalog.platform-base-url` 时完全沿用历史 yml 行为；解析失败 / 不可达时回落 yml 嵌入配置（fail-soft，不影响启动）。
- **缓存**：解析结果 TTL 缓存（默认 5 分钟），避免每条索引批都打平台。

### 5.3 依赖边界总结
| 消费者 | 配置源 | 密钥来源 | 回落 |
|--------|--------|----------|------|
| LLM 网关（platform） | `ModelResolver` → `model_catalog` | 环境变量 `agent.model.<p>.api-key` | yml → Fake |
| RAG 嵌入（rag） | `ModelCatalogClient` → 平台内部 API | `rag.embedding.api-key`（env） | yml |
| 管理后台 UI | `AdminModelConfigController` CRUD | — | — |

**平台 Worker 真实调用（已接通，本轮补「配置可见性 + 解析验证」）**

- 执行链路早已具备真实模型路径（见 §5.1）：`WorkerExecutionConfig.modelGateway()` ① 优先从统一目录取 `agent-chat` 默认模型（`ModelResolver.defaultForScenario("agent-chat")`），密钥由 `ModelCredentialProvider.apiKeyFor(provider)` 解析（DB 带外密钥优先、env `agent.model.<provider>.api-key` 回落）；② 目录空 / 无密钥时回落 yml `agent.model.minimax.api-key`；③ 仍无则 `FakeModelGateway` 占位（**明确非真实调用**）。
- **怎么配置才能走真实模型**：种子已默认 `agent-chat → MiniMax-M2.5`（`deploy/sql/platform/seed_model_catalog.sql`，幂等）。要让 Worker 真正打真实接口，二者满足其一即可：
  - 经管理后台 `PUT /api/admin/model-credentials`（带外加密存储，§7.2 ③）；或
  - 注入环境变量 `agent.model.minimax.api-key`（本地 / 历史部署兼容）。
  - 二者皆缺 → 默认回落 `FakeModelGateway` 占位；**绝不把占位伪装成「已接通」**。
- **解析验证（断言级）**：新增 `platform-bootstrap/.../config/WorkerRealModelGatewayResolutionTest`（6 例）锁死五条不变式：① 目录 minimax 默认 + 密钥可解析 → `MiniMaxModelGateway`；② 目录 openai 默认 + 密钥可解析 → `OpenAiCompatibleModelGateway`；③ 目录空 + yml 有 key → 回落真实 `MiniMaxModelGateway`；④ 目录空 + 无 key → `FakeModelGateway`；⑤ 目录给未知 provider → 回落 `FakeModelGateway`（fail-soft）。全部通过。

**RAG 生成侧真实调用（本轮新建，保持接地底线）**

- 新增 `rag-ports/.../ports/GenerationModelPort`：只有「基于给定依据片段合成讲解」一个职责，禁止检索/校验/幻觉——依据的四道闸门（租户 / 存在性 / 角色 / 版本）由 `GroundedGenerationService` 在调用前完成，模型永远拿不到未过闸门的片段。失败统一抛 `GenerationModelException`（不携带密钥/响应体），供调用方回落逐字摘录。
- 新增 `rag-infrastructure/.../infrastructure/generation/OpenAiCompatibleGenerationAdapter`：实现 `GenerationModelPort`，按 OpenAI Chat Completions 协议（`POST /chat/completions`，JDK `HttpClient` + Jackson 3）调用。系统提示**写死**「只能使用【依据原文】中的逐字片段作答，禁止引入原文之外的事实」；密钥仅走 `Authorization: Bearer` 头，绝不进日志/异常消息；非 2xx / 超时 / 空内容 / 非法 JSON 统一归一为 `GenerationModelException`。
- 修改 `rag-application/.../application/generation/GroundedGenerationService`：Step ⑥ 路由——`modelPort != null` 时优先「合成 + **强制引用块**」（合成正文后追加逐字引用块，保证学生可对照原书核对）；端口抛错 / 返回空 → **fail-soft 回落逐字摘录**（学生至少能看到可核对原文，而非无出处的话）。`generator` 字段如实标注：`LLM_GROUNDED_SYNTHESIS`（合成+引用，正文为模型转述、不保证逐字）vs `EXCERPT_ASSEMBLY`（逐字，每个字来自依据）。
- 接线 `rag-persistence/.../bootstrap/RagInfrastructureConfig`：`generationModelPort()` Bean 读 `rag.generation.model.{enabled,base-url,api-key,model,temperature,max-tokens,timeout-seconds}`（对应 `RAG_GENERATION_MODEL_*` 环境变量），**默认关闭（fail-closed）**；四项不全 → 返回 `null` → 恒走逐字摘录。`groundedGenerationService` 通过 `ObjectProvider<GenerationModelPort>` 注入（缺失即 null）。yml 段落在 `rag-bootstrap/src/main/resources/application.yml` 的 `rag.generation.model` 下。
- ⚠️ **RAG 自带配置（按用户定案）**：RAG 是独立 reactor、独立库（ADR-011），不跨进程依赖平台统一目录；base-url/api-key/model 由 RAG 自己的 yml/env 自包含，与 §5.2 的「RAG 嵌入走平台内部 API」互不冲突（嵌入仍走目录解析，生成走 RAG 自带）。
