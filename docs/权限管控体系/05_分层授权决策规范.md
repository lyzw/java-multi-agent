> 定位：**全套文档的唯一安全决策规范**，优先级最高。03 PRD 引用本规范、06/07/08 不得各自重定义规则，只能引用本规范。

## 0. 统一决策状态模型（所有文档必须采用同一语义）

一次工具/MCP 调用的最终结果由**四个互不混淆的字段**承载。任何文档、组件、审计日志、测试用例都不得把"授权失败"与"执行准入失败"混为一个笼统 `DENY`。

| 阶段 | 结果字段 | 取值 | 含义 |
|---|---|---|---|
| 授权（Phase A） | `authorizationDecision` | ALLOW / DENY | 能力闭包 + 主体授权是否通过 |
| 执行准入（Phase B） | `executionDecision` | ALLOW / DENY | 审批/预算/幂等/账本等执行前置条件是否通过 |
| 执行状态 | `executionStatus` | NOT_STARTED / RUNNING / SUCCEEDED / FAILED / UNKNOWN | 工具实际执行结果（含外部副作用未知） |
| 原因 | `reasonCode` | 见 §4 错误码表 | 首个拒绝原因或执行结果原因 |

**`ALLOW` 不等于"外部操作成功"**：`authorizationDecision=ALLOW` 仅表示授权通过；`executionStatus=SUCCEEDED` 才表示副作用成功；`UNKNOWN` 表示副作用可能已发生、响应丢失，须进对账队列，**绝不视为成功**。

| 场景 | authorizationDecision | executionDecision | executionStatus | reasonCode |
|---|---|---|---|---|
| 主体无权 / 角色不足 | DENY | DENY | NOT_STARTED | AUTHZ_STALE / AUTHZ_ROLE_MISSING |
| Agent 未启用 Skill / Skill 未声明 Tool | DENY | DENY | NOT_STARTED | SKILL_NOT_ENABLED / TOOL_NOT_DECLARED |
| 风险超限 / 风险未知·非法 / 参数越权 / MCP 操作级越界 / 配置指纹失效 | DENY | DENY | NOT_STARTED | 对应 §4 码 |
| 审批未通过/缺失 | ALLOW | DENY | NOT_STARTED | APPROVAL_REQUIRED / APPROVAL_DENIED |
| 预算不足 | ALLOW | DENY | NOT_STARTED | BUDGET_EXCEEDED |
| 全部前置通过，执行成功 | ALLOW | ALLOW | SUCCEEDED | — |
| 外部副作用已发生、响应丢失 | ALLOW | ALLOW | UNKNOWN | EXEC_UNKNOWN（进对账） |

> **铁律（评审 G-02）**：审批/预算失败**不是**授权失败。它们统一记为 `authorizationDecision=ALLOW, executionDecision=DENY`，并以独立的 `reasonCode` 区分，便于根因分析与 SLA。若实现选择保留单一 `decision` 字段，也必须在该字段文档化"代表完整调用准入"，并用 `stage` + `executionStatus` 区分拒绝阶段与执行结果——但本体系**推荐采用上述三字段模型**，实现与测试以 `src/runtime.py` 为准。

## 1. 授权决策公式（Phase A，概念定义，非执行流程）

**授权（Phase A）**由以下合取式定义（不含执行前置条件）：

$$
\begin{aligned}
Allow_{auth} ={}& PrincipalAuthorized\\
              &\land AgentSkillAllowed\\
              &\land SkillToolAllowed\\
              &\land RiskWithinCeiling\\
              &\land MCPBindingAllowed\\
              &\land ParamPolicyPassed
\end{aligned}
$$

| 因子 | 含义 | 数据来源 | 不适用时的处理（不可静默跳过） |
|---|---|---|---|
| `PrincipalAuthorized` | 当前请求主体此刻是否有权 | `AuthorizationService.isAuthorized` + `authzVersion` | 缺/过期 → `authorizationDecision=DENY` |
| `AgentSkillAllowed` | Agent 有效 Skill 集含该 Skill | `PermissionResolver`（闭包） | 不含 → DENY |
| `SkillToolAllowed` | Skill 有效 Tool 集含该 Tool | `PermissionResolver`（闭包） | 不含 → DENY |
| `RiskWithinCeiling` | `Tool.riskLevel ≤ Skill.riskCeiling` | 配置 | 超 → DENY |
| `MCPBindingAllowed` | 仅 MCP 调用：连接级+操作级 allowlist 交集通过 | Skill `declaredMcp` + server 当前清单/指纹 | 不适用（native）→ 显式跳过该因子；适用且不符 → DENY |
| `ParamPolicyPassed` | 输入满足参数策略（业务权限，非结构校验） | `paramPolicies` | 缺策略≠放行；高危建议默认强策略 |

**执行准入（Phase B）**由以下前置条件定义（授权通过后执行）：

$$
\begin{aligned}
Allow_{exec} ={}& SchemaValid\\
              &\land ApprovalSatisfied \quad\text{(若风险策略要求)}\\
              &\land IdempotencyOk\\
              &\land BudgetOk\\
              &\land LedgerOk
\end{aligned}
$$

- `SchemaValid`：结构校验（`ToolHandler.validate` / JSON Schema）。
- `ApprovalSatisfied`：风险策略要求审批且已满足（绑定操作+参数域+指纹，见 §3.2）。
- `IdempotencyOk`：幂等键未处于"已完成"态，避免重复副作用。
- `BudgetOk`：预算预留成功。
| `LedgerOk`：执行前账本登记成功（"已登记未完成"可识别）。

**铁律**：
- 公式表达**授权/准入**，不表达"执行成功"。`Allow_{auth} ∧ Allow_{exec}=true` **不代表外部副作用已成功**——`executionStatus` 独立记录（见 §0）。
- **能力闭包 ≠ 主体授权**：`AgentSkillAllowed ∧ SkillToolAllowed` 回答"这个 Agent 被配置为可用什么"；`PrincipalAuthorized` 回答"当前主体此刻是否有权"。两者不可互相替代（评审 02 §3.3）。
- "不适用"因子（如 native 调用的 `MCPBindingAllowed`）必须**显式声明跳过**，禁止默认整段跳过安全校验。
- 审批/预算/幂等/账本由**执行闸门**负责，不进入授权公式（评审 G-02；否则 budget/approval 失败会被误报为“主体无权”）。
- **结构校验与业务参数策略分属不同阶段**：`ParamPolicyPassed`（Phase A）= 业务权限策略（如 `in_allowlist`/`lte`），**非结构校验**；`SchemaValid`（Phase B）= **仅一次**结构校验（`ToolHandler.validate` / JSON Schema）。二者不得合并执行，也禁止在 Phase A 做结构校验、Phase B 又重复结构校验（详见 03 §3.2 / 07 §2）。

## 2. 决策顺序与短路（short-circuit）

为可观测与最小开销，按以下**逻辑顺序**短路（任一 false 即对应阶段 DENY，记录最早失败 stage 与 reasonCode）。顺序与 07 §2 的执行链一一对应，07 不得改变其安全语义。

```
[授权 Phase A]
 1. PrincipalAuthorized        (AUTHZ_ROLE_MISSING / AUTHZ_STALE)   # 先判角色集合，再判版本新鲜度；二者为不同因子，最先
 2. AgentSkillAllowed          (SKILL_NOT_ENABLED)
 3. SkillToolAllowed           (TOOL_NOT_DECLARED)
 4. RiskWithinCeiling          (RISK_EXCEEDS_CEILING / RISK_LEVEL_UNKNOWN)  # 风险未知/非法 → 授权 DENY
 5. MCPBindingAllowed          (MCP_NOT_BOUND / MCP_OP_NOT_ALLOWED / MCP_TOOL_DRIFTED)  # 仅 MCP
 6. ParamPolicyPassed          (PARAM_POLICY_FAIL)
 7. ConfigFingerprintValid     (CONFIG_FINGERPRINT_STALE)           # 校验"本 Run 依赖的有效能力闭包指纹"（见 §5），非全局聚合指纹
→ 上述全过 → authorizationDecision = ALLOW

[执行准入 Phase B]
 8. SchemaValid                (PARAM_SCHEMA_FAIL)
 9. ApprovalSatisfied          (APPROVAL_REQUIRED / APPROVAL_DENIED)  # authorizationDecision 仍 ALLOW
10. IdempotencyOk              (IDEMPOTENCY_CONFLICT)
11. BudgetOk                   (BUDGET_EXCEEDED)                       # authorizationDecision 仍 ALLOW
12. LedgerOk(PRE)              (LEDGER_PRE_FAIL)

[执行准入点 / TOCTOU]
13. ExecutionAdmissionCheck    重验 authzVersion + configFingerprint 仍新鲜 → 否则 DENY(EXEC_ADMISSION_STALE)

→ 进入 ToolHandler.execute → executionStatus = SUCCEEDED / FAILED / UNKNOWN
→ LedgerOk(POST) 记录终态；UNKNOWN 进对账队列
```

> **顺序铁律（评审 G-01）**：主体授权 **必须** 先于能力链与配置解析。未授权主体**不得**先进入可能读取敏感配置的分支。07 的执行链编排必须保持此顺序，仅在组件分工上把"闭包计算（PermissionResolver）"作为无副作用的只读辅助，且其结果**仅在主体授权通过后**用于判定。

## 3. 风险等级排序与审批语义（统一规则）

### 3.1 正式排序（配置期与运行期同一套）

`READ(1) < WRITE_PROFILE(2) < WRITE_EXTERNAL(3)`。比较仅按此序；**未知/未登记/非法值 → 拒绝**（见 §3.3，不再误转为合法最高级执行）。

| Tool 风险 | Skill 上限 | 结果 | 审批默认 |
|---|---|---|---|
| READ | READ/WRITE_PROFILE/WRITE_EXTERNAL | 允许继续 | NOT_REQUIRED |
| WRITE_PROFILE | READ | **拒绝**（risk_ceiling） | — |
| WRITE_PROFILE | WRITE_PROFILE/WRITE_EXTERNAL | 允许继续 | OPTIONAL |
| WRITE_EXTERNAL | READ/WRITE_PROFILE | **拒绝** | — |
| WRITE_EXTERNAL | WRITE_EXTERNAL | 允许继续 | **REQUIRED** |
| 未知/未登记/非法 | 任意已知 | **authorizationDecision=DENY**（RISK_LEVEL_UNKNOWN，授权阶段拒绝，**不按最严执行、不降级为 WRITE_EXTERNAL**） | — |

### 3.2 审批绑定语义（防"审批通过后实际执行内容变化" + 防重放，评审 §6.4）

- `REQUIRED` 审批**不能只绑定 Tool id**，必须绑定：审批覆盖的**操作范围**（工具名 + 关键参数域，如收件域白名单）+ **配置指纹/参数快照**。
- 审批通过后，若**关键输入变化**（收件域、目标库表、批量规模等）或**配置指纹变化** → 审批失效，需重新审批。
- `OPTIONAL`：高风险场景可配置为强制审批（trustTier=public/external 时默认升级 REQUIRED）。
- 审批状态不可确认（端口超时/不可用）→ 按 fail-closed **拒绝**（executionDecision=DENY）。

**审批防重放（一次性消费）规则**：
- 每条审批记录含唯一 `approvalId`、状态、有效期、一次性消费标记。
- 审批必须绑定 `tenantId` + `principalId` +（明确 `runId` 或声明"跨 Run 复用范围"）+ `toolId` + 关键参数规范化摘要 + `configVersion`。
- 已使用 / 已撤销 / 已过期 / 上下文不匹配（tenant/principal/tool/参数摘要/指纹任一不符）的审批**不得再次使用**。
- 并发重复消费同一 `approvalId`：只有一个调用能成功完成消费（幂等消费键 + 原子状态机），其余 DENY(APPROVAL_REPLAY_REJECTED)。
- 攻击者不能通过重放已审批调用或并发请求重复触发外部副作用。

### 3.3 未知风险等级语义（评审 §6.1 修正——消除"按最严处理"与"拒绝"的冲突）

- **配置期（发布/校验）**：风险等级未知、非法或未登记 → **直接拒绝发布**（T1 守卫），不进入运行期。
- **运行期**：缺少可信风险元数据或无法确认风险等级（即无法从**已发布、可信的 Tool 定义**读取风险等级）→ **authorizationDecision=DENY**（RISK_LEVEL_UNKNOWN），不进入执行。调用方不得自行提供 `riskLevel` 覆盖服务端定义。
- **可信 Tool 已登记但调用上下文未携带风险值**：从**已发布 Tool 定义**读取风险等级；**不允许**调用方自行提供 riskLevel 覆盖服务端定义。
- **`WRITE_EXTERNAL` 是合法最高风险等级**，不等于"任何未知工具都可按最高风险直接执行"。未知风险的处理是"拒绝"，不是"降级为 WRITE_EXTERNAL 后放行"。

|---|---|---|---|

## 5. 撤权与在途 Run 处理规则（含执行准入点线性化）

定义四类版本（**语义不同，不得合并**，见 06 §4 / 评审 G-03）：
- `agentVersion`：Agent 定义发布版本。
- `configVersion`：能力配置发布版本（单调递增序号）。
- `configFingerprint`：配置内容摘要（检测内容是否变化）。
- `authzVersion`：主体授权状态版本（**DB 单调递增，V1 强制**）。

| 场景 | 处理 |
|---|---|
| **新调用**（未建 Run） | 必须读取**当前** `authzVersion` + `configFingerprint`；陈旧即 DENY。禁止以旧快照代替实时授权。 |
| **已审批、待执行**调用 | `authzVersion` 变化 → 审批失效 → 执行准入 DENY（重走审批）。 |
| **执行中**调用 | 已开始的外部副作用**不可简单撤销**；按幂等键对账，`executionStatus` 记录（SUCCEEDED/FAILED/UNKNOWN），不承诺所有在途可回滚。 |
| **结果回写** | 仅当 `executionStatus` 已终态才允许回写；UNKNOWN 进人工/对账队列。 |
| **多实例传播** | `authzVersion`/`configVersion` 走 **DB 强一致**读取（或具强一致保证的授权服务），非普通异步缓存刷新。 |
| **版本服务不可用** | fail-closed：**拒绝**新调用（不允许"降级放行"）。 |

**配置指纹（configFingerprint）作用范围（评审 P0-6）**：
- **全局发布版本（configVersion）**：追踪发布事件（单调递增序号，见 06 §1.7）。
- **对象版本**：固定单个对象定义（`cap_*_def` 的 `(id, version)`）。
- **有效能力闭包指纹**：基于**当前 Run 实际依赖**的 Agent、Skill、Tool、MCP 配置及必要安全约束（riskCeiling、allowlist、指纹）计算，是 T2 快照与 Phase A 校验真正比对的对象。
- **快照指纹比较范围 = Run 依赖闭包级（非全局聚合）**：一个与某 Run 无关的 Tool/Skill/MCP 变更**不应**使该 Run 的快照失效（否则无关变更会批量击落在途调用）。
- **失效策略**：仅当 Run 依赖闭包内的对象发生版本/指纹变化（含 MCP Schema 不兼容、工具下线）时，该 Run 的新调用才 DENY(CONFIG_FINGERPRINT_STALE)；无关配置变更不影响。
- **执行准入点重验字段**：Phase A 验 `configFingerprint`（闭包级）；执行准入点（步骤 13）重验 `authzVersion` + `configFingerprint`（闭包级），与 T2 快照字段一致（见 06 §1.6 / 07 §4）。

**执行准入点（TOCTOU）线性化边界（评审 §6.5 / 07 §8.3，可测试契约）**：
> 系统承诺的边界（可自动化验证，见 08 §2 S3b/S3f）：
> 1. **撤权先提交**：若撤权事务已提交，且调用的**执行准入检查**在其后发生，则该调用必须读取到**不早于**撤权提交的版本 → 阻断（`EXEC_ADMISSION_STALE`），不启动新副作用。
> 2. **准入已完成、撤权后提交**：若执行准入检查已通过、外部副作用已发出（或正在发出），随后撤权提交 → 该调用属于**已进入执行阶段的在途操作**；系统**不承诺**绝对阻断已发出的副作用，而是记录其 `executionStatus`（SUCCEEDED/FAILED/UNKNOWN）并按幂等/对账/补偿处理。
> 3. **可观测**：每次执行准入检查必须记录**检查时间、当时读取的 authzVersion/configFingerprint 版本、检查结果**，写入决策日志/账本，作为撤权竞态的事后审计依据。

- "开始调用"与"真正产生外部副作用"必须区分。仅调用开始校验一次版本仍可能竞态（授权通过 → 管理员撤权提交 → 调用才发请求）——因此步骤 13 的执行准入点重验是必要的，但它是**尽力阻断新副作用**的契约，不是"消除所有竞态"的保证。
- 系统须定义**执行准入点**（步骤 13）：在真正发送外部请求前，再次校验 `authzVersion` + `configFingerprint` 仍新鲜；失效则 `executionDecision=DENY(EXEC_ADMISSION_STALE)`，不启动新副作用。
- 已启动的外部副作用按对账规则处理，不声称可无条件撤回。
- 若业务要求"撤权提交后绝不允许任何尚未发出的外部副作用"，需进一步设计能协调撤权与执行启动的串行化机制（如撤权事务持有全局写锁或副作用启动前二次确认），不能仅靠普通检查后调用（07 §8.3）。

### 5.2 执行前后故障恢复契约（评审 05-07 / 07 §5）

Phase B 各闸门（审批/预算/幂等/账本）失败时必须给出**明确且可恢复**的处理，禁止"仅告警后继续发外部请求"或笼统"重试"。每个故障的前置状态、是否允许执行、账本状态、预算处理、重试条件、对账动作、最终审计如下：

| 故障点 | 前置状态 | 是否允许执行 | 账本状态 | 预算处理 | 后续动作 | 最终审计 |
|---|---|---|---|---|---|---|
| 审批端口超时/不可用 | Phase B 初 | **否** | 不登记 | 不预留 | fail-closed 拒绝（`executionDecision=DENY(APPROVAL_DENIED)`），不启动副作用 | APPROVAL_DENY |
| 审批一次性消费冲突/重放 | 已消费/并发 | **否** | 不登记 | 不预留 | `executionDecision=DENY(APPROVAL_REPLAY_REJECTED)`，仅一个调用成功消费 | APPROVAL_DENY |
| 预算预留失败/不足 | 预算端口拒绝 | **否** | 不登记 | 不预留（若已预留则回滚释放） | `executionDecision=DENY(BUDGET_EXCEEDED)` | BUDGET_DENY |
| 账本 PRE 写入失败 | 已通过审批/预算 | **否** | 无"已登记未完成" | 释放预算 | 重试 PRE；重试仍失败 → 拒绝执行并告警（**不绕过账本发请求**） | 审计 PRE 失败，标记待人工确认 |
| 账本 POST 写入失败（副作用已发生） | 已执行 | 已发生，不可撤 | 状态未知 | 已预留 | 视为 `executionStatus=UNKNOWN`，进对账队列重查/补偿；禁止记为执行失败而忽略真实副作用 | EXEC_UNKNOWN，对账后定稿 |
| 幂等键重复到达 | 已完成/进行中/未知 | 按状态定 | 沿用首次 | 沿用首次 | 已完成→返回首次结果；进行中→阻塞；未知→进对账 | 按首次 reasonCode |
| 外部响应丢失（UNKNOWN） | 已执行 | 已发生 | POST 待定 | 已预留 | 进对账队列（人工/自动重查），**不得盲目重试**（可能重复副作用），不得记为成功 | EXEC_UNKNOWN |

> 核心原则：**账本 PRE 未成功登记前，绝不允许发送外部副作用**；**外部副作用已发生后账本 POST 失败，必须进入 UNKNOWN 对账，不得归类为"执行失败"而掩盖真实副作用**（07 §5 / 03 §6.3）。

## 6. MCP 工具变更与身份校验规则

V1 为固定清单 + 指纹校验（无动态发现）。规则：

1. **工具身份**：`McpServer.id` + `mcpToolName` → 稳定映射内部 `Tool.id`；同名不同 server 必须区分，禁止冲突。
2. **Schema 变化**：基于工具名绑定；若 server 侧 Schema 变更导致 `inputSchema` 不兼容 → 视为"配置指纹变化" → `config_stale` DENY（需重新发布配置）。
3. **工具下线**：固定清单不含该工具 → `mcp_tool_not_allowed` / `config_stale` DENY（S5a/S5b 分别建模）。
4. **发现超时/缓存失效**：V1 无运行期发现，以"配置指纹不匹配"兜底；未来 V2 引入发现时列举失败按空集→拒（fail-closed）。
5. **重新认证**：凭据轮换后连接级授权须重验；未通过→连接级 DENY，不暴露任何工具。
6. **不可信输出边界**：MCP 返回内容视为不可信，禁止直接当作可信指令执行（防 prompt injection / 工具输出劫持）。
7. **DNS/重定向/SSRF**：见 06 §5（V1 须覆盖 DNS 解析后 IP 校验、DNS rebinding、禁止重定向跳内网/云元数据、stdio 白名单）。

## 7. 继承与组合规则（V2 才启用，V1 禁止）

- `Skill.inherits`：V1 写入即拒。V2 启用时须满足：递归启用（Agent 须显式启用闭包每一个 Skill，防 P3 抬权）、循环依赖拒绝、不可移除父 Skill 工具（收紧棘轮同样适用）。
- `capabilityTags` / `skillBundles`：V1 忽略语义（见 04 §3）；V2 启用时以"显式 allowlist 用于高保证"对冲标签过宽。

## 8. 异常处理矩阵（fail-closed 分类，区分授权/执行）

| 失败类别 | 触发 | authorizationDecision | executionDecision | 审计分类 |
|---|---|---|---|---|
| 配置缺失 | Tool/Skill/Agent 定义缺失、字段非法 | DENY | DENY | CONFIG_ERROR |
| 授权缺失/陈旧 | `authzVersion` 不匹配、角色不足 | DENY | DENY | AUTHZ_DENY |
| 风险越界 | `riskLevel > riskCeiling` | DENY | DENY | RISK_DENY |
| 风险未知/非法 | 风险等级无法从已发布可信定义确定 | DENY | DENY | RISK_DENY |
| 参数越权 | 业务权限策略不满足 | DENY | DENY | PARAM_DENY |
| MCP 操作越界/漂移 | 工具不在 allowlist/未暴露 | DENY | DENY | MCP_DENY |
| 配置指纹失效 | 闭包依赖指纹变化 | DENY | DENY | CONFIG_DENY |
| 超时（授权/配置读取） | 读取超时 | DENY | DENY | TIMEOUT_DENY |
| 审批缺失/拒/重放 | `ApprovalPort` 未满足/冲突 | ALLOW | DENY | APPROVAL_DENY |
| 预算不足 | `BudgetPort` 拒绝 | ALLOW | DENY | BUDGET_DENY |
| 幂等冲突 | 重复请求将产生副作用 | ALLOW | DENY | IDEMPOTENCY_DENY |
| 执行未知 | 外部副作用已发生、响应丢失 | ALLOW | ALLOW（已准入） | EXEC_UNKNOWN |

> 所有异常**不得**归入单一笼统 DENY；按上表细分 `reasonCode` 与审计分类，便于根因分析与 SLA（对应 03 §6.3）。
