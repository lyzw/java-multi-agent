# 06｜配置数据模型与生命周期设计

> 定位：把 03 PRD 的配置模型落到**可持久化、可发布、可回滚、支持多实例强一致撤权**的数据模型。
> 评审依据：03 P0-5、04（V1 边界）、05（版本/指纹/撤权）、G-03/G-04 与 §7.1–§7.7。
> 本轮修订重点：不可变版本化定义、发布原子性、authzVersion 并发自增协议、configVersion 与 configFingerprint 分离、迁移双写回滚、MCP SSRF 深化。

---

## 1. 表结构（V1 最小集）

> 命名约定：`cap_` 前缀表示能力配置域；沿用现有 `agent` / `agent_version` / `execution_snapshot` / `tenant_config_override`。

### 1.1 对象定义表（**方案 A：版本化，不可变版本记录**）

每个 `cap_*_def` 表采用 **`（id, version）复合主键**，每次发布创建一条**不可变版本记录**；当前生效版本由发布头指针指向。草稿编辑不修改已发布版本行。

以 `cap_tool_def` 为例（`cap_skill_def` / `cap_mcp_server_def` 同构）：

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | varchar | 全局唯一 |
| `version` | int | **版本号（与 id 组成复合主键）**；每次发布 +1 |
| `name` | varchar | |
| `kind` | varchar | `native` \| `mcp` |
| `risk_level` | varchar | READ/WRITE_PROFILE/WRITE_EXTERNAL（缺省=WRITE_EXTERNAL，fail-closed；**未知/非法值配置期拒绝发布**，见 05 §3.3） |
| `mcp_server_id` / `mcp_tool_name` | varchar? | kind=mcp |
| `input_schema` | jsonb | 结构校验 |
| `param_policies` | jsonb | V1 仅 `in_allowlist`/`lte`（其他 op 写入即拒） |
| `namespace` | varchar | `platform`（V1 仅 platform 级） |
| `config_fingerprint` | varchar | **本版本内容指纹**（规范化内容摘要，不可变） |
| `created_at` / `updated_at` / `published_at` | ts | |
| `schema_version` | int | 行格式版本，迁移兼容 |

> **发布**：插入新 `(id, version+1)` 行（不可变），并将发布头 `cap_config_release` 指向它；**不 UPDATE 已发布历史行**。
> **回滚**：创建新发布事件指向旧 `version`（新当前版本指针），**不覆盖历史记录**（见 §3）。
> **当前生效版本的权威来源唯一**：对象定义表**不保留** `is_current` 之类需要随切换反复更新的可变标志——切换当前版本**只改变发布头指向**，绝不 UPDATE 历史版本行。运行期当前版本解析见 §1.7 / §3.2。

### 1.5 `cap_authz_version`（DB 化，V1 强制，复合主键 + 并发协议）

| 列 | 类型 | 说明 |
|---|---|---|
| `tenant_id` | varchar | **复合主键 (tenant_id, principal_id)** |
| `principal_id` | varchar | **复合主键** |
| `authz_version` | bigint | **单调递增**；撤权 bump |
| `updated_at` | ts | |
| `version` (乐观锁) | int | 乐观并发控制列（可选，配合 DB 自增） |

**并发更新协议（评审 §7.3）**：
1. **初始值**：首次创建主体授权记录时 `authz_version=1`（由发布/首次授权事务写入）。
2. **单调递增**：版本递增**由 DB 原子操作**（如 `UPDATE ... SET authz_version = authz_version + 1 WHERE tenant_id=? AND principal_id=?` 返回影响行数；或乐观锁 `WHERE version=:old`）实现，**禁止**应用实例先读后加一（避免丢失更新）。
3. **触发递增的事件**：角色变化、主体禁用、授权关系删除/撤销，**均** bump 版本。
4. **事务边界**：撤权与版本递增在**同一事务**内提交，保证要么都可见要么都不可见。
5. **跨租户作用域**：版本按 `(tenant_id, principal_id)` 作用域，主体跨租户身份变化须分别 bump 对应租户记录，避免版本作用域错误。
6. **版本服务不可用**：读取/递增失败 → fail-closed **拒绝**新调用（05 §5），并产出可监控故障信号；**不允许**降级放行。
7. **重复撤权**：多次撤权只继续递增，不产生版本回退或丢失撤权。

## 2. 平台级 vs 租户级引用与唯一性

- **唯一性**：`cap_tool_def` / `cap_mcp_server_def` / `cap_skill_def` 的 `id` **全局唯一**，`namespace=platform` 由平台拥有。
- **版本化引用（统一采用"id-only + 发布头解析"，选项 B）**：所有 `cap_*_def` 之间的引用**仅存对象 id**，被引用对象的有效版本统一由当前 `cap_config_release.object_versions` 解析（见 §3.2）；**禁止在引用中硬编码版本号**（避免版本漂移与多对象发布不一致）。对象定义自身仍按 `(id, version)` 复合主键不可变存储——引用解析出的版本对应其中一行。
- **引用完整性**：`cap_skill_def.declared_tools` 每个 id 必须存在于 `cap_tool_def`（FK 或 T1 校验）；`declared_mcp[].serverId` 必须存在于 `cap_mcp_server_def`。
- **租户级**（V1 仅 platform 定义；V2 开放 `tenant:<id>` 自定义）：若开放须加 `tenant_id` 受 RLS；租户定义仅可引用 platform 或本租户对象，禁止跨租户引用。
- **删除被引用对象**：见 §3.5（禁止物理删除被引用，改 DEPRECATED）。

## 3. 配置生命周期（状态机）

```
DRAFT ──(validate)──▶ VALIDATED ──(approve, 双人复核)──▶ PUBLISHED ──(deactivate)──▶ DEPRECATED
                        │                                  │                          （不可新引用）
                        │(reject)                           │(new version / rollback)
                        ▼                                  ▼
                     REJECTED                          PUBLISHED'(新不可变版本 / 新 release 指针)
                        │
                        └────(revise)──────────────────────┘
```

| 步骤 | 职责 | 校验 |
|---|---|---|
| create/edit | 配置管理 Port | schema + 引用完整性 + 收紧棘轮（放宽即拒） |
| validate | `PermissionResolver` + T1 守卫 | 闭包可达性、riskCeiling/风险等级合法、**allowlist 非空语义（05 §4）**、循环依赖（V2）、未知风险拒绝发布（05 §3.3） |
| approve | `ConfigChangeController`（双人复核 `approver_id <> requester_id`） | 高危变更（trustTier=public / WRITE_EXTERNAL）强制 |
| publish | 配置发布服务 | 插入不可变新版本行 + 写 `cap_config_release`（原子）+ bump `config_publish_seq`；对新 Run 生效 |
| rollback | 配置发布服务 | **创建新 release 指向旧 version**（新当前版本指针），不覆盖历史；回滚**不能**恢复已撤销的主体授权 |
| deactivate/delete | 配置管理 Port | 被引用对象禁止物理删除 → DEPRECATED；新 Run 不可引用 |

### 3.1 生效范围
- **新 Run**：创建时（T2）读取**当前** `config_publish_seq`/`config_fingerprint` 与 `authzVersion` 生成快照（写入 `config_version` + `config_fingerprint`）。
- **已有 Run**：按 `execution_capability_snapshot` 记录的版本/指纹；运行期检测到 `authzVersion` 或 `config_fingerprint` 失效 → 新调用授权 DENY（05 §5），在途按对账处理。

### 3.2 多对象原子发布与当前版本解析（评审 §7.4 / P0-8）

**当前生效版本的权威解析**：运行时当前配置 = **最近一条 `status=PUBLISHED` 的 `cap_config_release` 的 `object_versions`**（按 `config_publish_seq` / `effective_at` 取最新）；**绝不以 `is_current` 之类的可变标志或扫描历史行判断当前版本**（见 §1.1）。

**原子发布事务流程（V1 必须实现）**：
1. 在事务内为本次发布的每个对象插入不可变新版本行 `(id, version+1)`（不修改任何历史行）。
2. 在同一事务内分配**全局单调**的 `config_publish_seq`（由 DB 序列/原子自增保证唯一，禁止应用先读后加一）。
3. 在同一事务内插入一条 `cap_config_release`（`status=PUBLISHED`、`object_versions`=本次各对象版本、`aggregate_fingerprint`、双人复核 `approver_id <> requester_id`）。
4. 提交事务：提交后该 release 即成为"当前发布"，所有实例下一次读取即看到新集合。
5. **失败可见性**：未提交前 release 处于 `PREPARING`；任何对象版本插入失败/校验失败 → 整事务回滚，**运行期绝不可读到 PREPARING 或部分发布的组合**（见 §1.7）。

**回滚协议（与 ROLLED_BACK 状态职责分离）**：
- 回滚 = **创建一条新的 PUBLISHED release**，其 `object_versions` 指向旧的（目标）版本集合；新 release 成为"当前发布"。
- 被回滚掉的旧 release 标记为 `ROLLED_BACK`（**仅审计用途**，不参与当前版本解析；当前版本只认最新 PUBLISHED release）。
- 回滚**不覆盖、不删除**任何历史对象版本或历史 release 记录；历史审计完整保留。
- 回滚**不能**恢复已撤销的主体授权（`cap_authz_version` 独立，05 §5）。
- 回滚后引用一致性：新 release 的 `object_versions` 必须是完整、互相一致的集合（禁止指向不存在或已被 DEPRECATED 禁止新引用的版本），回滚后新调用按新闭包指纹重验（S5a / 08 §5）。

### 3.3 Schema 版本与迁移（双写 + 回滚，评审 §7.5）
- `cap_*` 表带 `schema_version` 列；旧版本读取按迁移脚本向后兼容。
- **从自由 JSONB 迁移**：`agent.definition` 自由 JSONB → 结构化 `cap_agent_def`：
  1. 创建新表与索引；
  2. 为存量 Agent 生成迁移报告（无法解析/缺 Skill 引用/字段冲突）；
  3. 对可迁移数据执行**幂等**迁移（重跑不产生重复对象/错误覆盖）；
  4. 新旧模型只读比对，确认语义一致；
  5. 切换读路径到 `cap_agent_def`；
  6. 观察稳定期；
  7. 停止旧模型写入，再归档/移除旧字段。
  - 迁移失败 → 恢复旧读路径；迁移脚本幂等，禁止因重跑导致重复或丢失授权关系。

### 3.4 删除/停用被引用对象
- 物理删除被 Skill 引用的 Tool / 被 Agent 启用的 Skill → **拒绝**（除非先解除所有引用并 DEPRECATE）。
- 替代：对象置 DEPRECATED，禁止新引用，存量 Run 按版本过渡。

### 3.5 配置收紧规则"比较什么"（评审 §7.6）

| 变更 | 判定 |
|---|---|
| 移除已启用 Skill | 收紧（允许） |
| 移除 Skill 声明的 Tool | 收紧（允许） |
| 降低 `riskCeiling` | 收紧（允许） |
| 扩大 MCP 工具 allowlist | **放宽，拒绝** |
| 新增可调用 Tool | **放宽，拒绝** |
| 放宽参数域白名单 / 增加最大行数 | **放宽，拒绝** |
| 改变 MCP endpoint 或认证凭据 | **不简单归类**：属受控敏感变更，须独立重新审批（不按集合大小判定） |

## 4. 版本与失效模型（闭环 05 §5，四概念分离，评审 §7.2）

| 概念 | 字段 | 存储 | 失效触发 |
|---|---|---|---|
| `agentVersion` | `cap_agent_def.version` | 对象版本 | Agent 定义重发 |
| `configVersion` | `cap_config_release.config_publish_seq` | 发布头（单调序号） | 新发布事件 |
| `configFingerprint` | 本 Run 依赖闭包的 `cap_*_def.config_fingerprint` 摘要 | 内容摘要（Run 依赖闭包级，非全局聚合） | Run 依赖闭包内任一对象内容变更（含 MCP 固定清单变化）；**无关对象变更不影响**（05 §5） |
| `authzVersion` | `cap_authz_version.authz_version`（DB 单调） | 主体授权状态 | 撤权/角色变/主体禁用 |

> **configVersion 与 configFingerprint 不可相互替代**：同内容因回滚重新生效时指纹相同但发布事件/审计不同；版本递增也不一定代表权限必然变化。快照须同时保存两者，分别承担"版本追溯"与"内容一致性校验"。

**失效规则（运行期 T3）**：
- `ctx.authzVersion ≠ current` → 授权 DENY(AUTHZ_STALE)。
- `snapshot.config_fingerprint ≠ current_closure_fingerprint` → 授权 DENY(CONFIG_FINGERPRINT_STALE)（仅本 Run 依赖闭包内对象变化才触发，非全局聚合指纹比较，05 §5 / S5a）。
- `snapshot.config_version` 指向的对象版本与当前 PUBLISHED 集合不一致 → 同按指纹/版本失效处理。
- 三者满足且闭包各边通过 → 进执行闸门（Phase B）；执行准入点（07 §2[8]）再次重验。

## 5. MCP 安全接入补充（评审 03 P1-2 / §7.7）

| 项 | 规则 |
|---|---|
| **SSRF 防护（端点）** | `endpoint` 须落允许范围（内网白名单/域名清单）；禁止 `127.0.0.0/8`、`169.254.0.0/16`、私有 CIDR，除非 `trustTier=internal` 显式授权。 |
| **SSRF（DNS/重定向）** | DNS 解析后对**实际 IP**校验；防 DNS rebinding（解析与连接用同一结果、连接前复验）；禁止未经授权 HTTP 重定向跳内网/云元数据；每次连接与重定向**重新校验**目标地址。 |
| **stdio 安全** | `stdio` transport 须用**可执行文件白名单**，禁止不受控 shell 命令拼接，限制参数/环境变量/工作目录。 |
| **凭据** | `credential_ref` 引用密钥管理；明文禁入库；日志脱敏；支持轮换（轮换后连接级重验）。 |
| **超时/限流** | 连接超时、读超时、响应大小上限、并发上限、失败隔离（单 server 故障不拖垮全局）。 |
| **名称映射** | `McpServer.id + mcpToolName → 内部 Tool.id` 稳定映射；同名不同 server 区分，禁止冲突。 |
| **不可信输出** | MCP 返回内容视为不可信，禁止直接当可信指令。 |
| **Schema 兼容** | server Schema 变更导致不兼容 → 视为 `config_fingerprint` 变化 → DENY（需重发配置）。 |
