# 阶段一：现有代码结构分析（Agent / Skill / Tool / MCP 现状与职责边界）

> 分析基准：`platform/`（Maven 多模块：agent-api / agent-core / agent-application / agent-infra / agent-infrastructure / agent-worker / platform-bootstrap / agent-ports / agent-ports…）与 `rag/`（独立检索子系统）。
> 本文档所有结论均以真实代码落点为依据，标注了文件与行号；凡"不存在"均指全仓 grep 无命中。

## 0. 一句话结论

平台当前 **Tool 层最成熟、Permission 层已分层、Agent 层只是"配置/发布实体"、而 Skill 与 MCP 两层完全缺失**。四层发展极不均衡，因此"统一配置与权限管控体系"实质是：在已有 Tool + Permission 地基上，**引入 Skill 抽象、引入 MCP 接入、并把 Agent 从"自由 JSONB"升级为受校验的能力编排主体**。

---

## 1. 各层现状与职责边界

### 1.1 Agent 层 —— 仅"配置/发布实体"，非运行时可执行实体

| 项 | 现状 |
|---|---|
| 定义落点 | 端口接口 `agent-ports/.../persistence/AgentQueryPort.java`、`AgentManagePort.java`；视图 `AgentItem`、`AgentVersionItem` |
| DB 表 | `agent`（`agent_id, tenant_id, name, description, created_at, updated_at`，复合唯一 `(tenant_id, agent_id)`）；`agent_version`（`definition JSONB NOT NULL`，不可变快照）；`execution_snapshot`（`agent_config / prompt_config / tool_contracts / run_config` JSONB 快照） |
| 关键字段 | `agentId / name / description / versionCount / latestVersionNumber / latestDefinition` —— **无 role、无 tenant 字段、无 permissions、无 skills、无 tools 字段** |
| 创建方式 | REST：`agent-api/.../governance/AgentController.java`（`POST /api/agents`、`POST /api/agents/{id}/versions`） |
| `definition` 形态 | **自由 JSONB**，端口层不定义 schema（"V1 设计现状即自由 JSON，本端口不定义 schema，仅以文本透传"） |

**职责边界**：Agent 目前是一个"发布即冻结的 JSON 配置包"，其"能力"只以 `execution_snapshot.tool_contracts` 的 JSONB 快照形式存在，与运行时 `ToolHandler` Bean 注册是**两套平行体系**。Agent 实体上既没有"可用 Skill"的引用结构，也没有"可用 Tool/MCP"的显式字段。

### 1.2 Skill 层 —— 完全缺失

全仓（含 `platform/` 与 `rag/`）在 `.java` 中搜索 `(?i)skill` **零命中**（仅 `docs/` 规划文档与 `frontend/` 无关字符串）。
- 无 `interface Skill` / `@interface Skill` / `enum Skill` / `class Skill`
- 无 `@Skill` 注解、无 Skill 注册表、无 classpath 扫描
- 无"技能 → 工具"的绑定关系

**结论**：Skill 是**待引入**的抽象。当前平台把"能力"直接建模为 Tool，没有中间层。

### 1.3 Tool 层 —— 最成熟，基于 SPI 接口 + Spring Bean 注册

| 项 | 现状 |
|---|---|
| 抽象 | `agent-ports/.../tool/ToolHandler.java`（端口接口）：`toolName()` / `inputSchema()` / `riskLevel()` / `validate()` / `execute()` / `reconcile()` |
| 实现 | 仅两个：`GetStudentProfileTool`（READ）、`RecordWeaknessTool`（WRITE_PROFILE） |
| 注册 | 显式 `@Bean` 于 `platform-bootstrap/.../ApplicationConfiguration.java`；所有 `ToolHandler` Bean 被收集为 `List<ToolHandler>` 注入 `ToolInvocationGate`，新增工具无需改闸门 |
| 发现/调用 | **唯一入口** `ToolInvocationGate.invokeAll`（`agent-worker/.../execute/ToolInvocationGate.java`）。**明确禁用** Spring AI 自动工具执行（ADR-011） |
| 执行链 | Schema 校验 → 执行时重新授权 → 幂等键 → 账本登记 → 审批 → 预算预留 → 执行 → 账本更新 |
| 风险分级 | `ToolRiskLevel`（READ/WRITE_PROFILE/WRITE_EXTERNAL）；`resolve()` **fail-closed** 未登记工具按最严 `WRITE_EXTERNAL`；yml `agent.tool.risk-level-map` 镜像 + `ToolRiskLevelConsistencyGuard` 强制与代码一致，否则拒绝启动 |

**职责边界**：Tool 是"最小可执行能力单元"，自带风险级别与输入 Schema。它**不感知**自己被哪个 Skill 或 Agent 调用——权限判定完全交给上层闸门。

### 1.4 MCP 层 —— 完全缺失

代码中搜索 `McpClient / McpServer / ModelContextProtocol / mcp server` **零命中**。仅规划文档提及 MCP 为"未来外部工具集成方向"，无任何 `mcp.json`、connector 配置或 transport 实现。

**结论**：MCP 是另一块**待引入**能力。当前"外部工具/集成"只有封闭的 `ToolHandler` SPI，没有可插拔的 MCP client/server 抽象。

### 1.5 Permission 层 —— 已分层，是良好地基

| 层 | 落点 | 机制 |
|---|---|---|
| 认证 | `SecurityConfiguration.java` + `BearerTokenFilter` | 无状态 JWT，解析后写入 `TenantContext`（tenantId/principalId/roles/authzVersion）到请求属性 |
| 授权矩阵 | `agent-ports/.../security/AuthorizationService.java` | `Actions`（run:create / tool:invoke / config:approve …13 个）+ `Roles`（TENANT_ADMIN/AGENT_AUTHOR/APPROVER/VIEWER/WORKER）；`isAuthorized(ctx, action, resourceId)` |
| 角色→动作 | `RoleBasedAuthorizationService.java` | 映射是"数据而非代码分支"；**默认拒绝**；`authzVersion` 重授权 |
| 执行时重授权 | `ToolInvocationGate` | 每次工具执行前 `isAuthorized(..., TOOL_INVOKE, toolName)`（红线 9：撤销后陈旧 Run 不可越权） |
| 多闸门 | `ToolInvocationGate` + `RiskBasedApprovalPolicy` + `BudgetPort` + `RunToolLedgerPort` + `ZeroRetentionGate` + `PromptGuard` | 审批 / 预算 / 账本 / 幂等 / 零保留 / 防注入 |
| 租户隔离 | RLS（`FORCE ROW LEVEL SECURITY`，`tenant_id = current_tenant_id()`，17 张表） | tenantId 只能来自可信认证上下文，绝不取客户端输入 |

> 注：记忆中提到的 "Authority Triple Gate" 在代码中**没有同名类**，它是对上述多层闸门的文档层概念总结。真实"三重"体现为 `SecurityConfiguration`（认证）+ `AuthorizationService`（角色→动作授权，含 authzVersion 重授权）+ `ToolInvocationGate`（执行时授权/审批/预算/账本/幂等）。

### 1.6 Config 层 —— yml（fail-closed）+ DB 覆盖双层

| 项 | 落点 |
|---|---|
| 主配置 | `application.yml`（每项必填，缺失/非法拒绝启动 fail-closed）；`agent.tool.risk-level-map`、`agent.approval.required-by-risk`、`agent.compliance.zero-retention` |
| 注册表 | 无独立 tool registry 文件；工具注册 = Spring `@Bean` 列表 + yml 风险映射 |
| DB 覆盖 | `tenant_config_override` 表（仅存覆盖值，带 RLS）；`ConfigOverridePort` 白名单 `WRITABLE` + 分级 `TIERS`（L2 直写 / L3 审批） |
| 收紧策略 | `ConfigTighteningPolicy`（配置只能收紧不能放松，单向棘轮，写入即显式抛异常） |
| 生效解析 | `EffectiveConfigResolver`（yml ⊕ DB 覆盖），每次 Run 创建快照时读取（R-021 快照隔离） |
| 审批流 | `ConfigChangeController`（request → decide → apply 四步分离，双人复核 `approver_id <> requester_id`） |

## 2. 四层职责边界总览

```
┌──────────────────────────────────────────────────────────────────┐
│ 缺失：Skill（中间层能力编排）  ── 本体系要引入                       │
│ 缺失：MCP（外部工具接入）      ── 本体系要引入                       │
├──────────────────────────────────────────────────────────────────┤
│ Agent   │ "配置/发布实体"：当前只是自由 JSONB；缺 skills/tools 引用  │
│         │ 边界：应成为"能力编排主体"，声明可用 Skill 集合            │
├──────────────────────────────────────────────────────────────────┤
│ Tool    │ 最成熟：SPI + Bean 注册 + 风险分级 + 唯一执行闸门          │
│         │ 边界：最小可执行单元，自带 riskLevel/inputSchema，不感知上层│
├──────────────────────────────────────────────────────────────────┤
│ Permission │ 已分层：JWT 认证 + 角色→动作矩阵 + authzVersion 重授权  │
│            │ + RLS 租户隔离 + 审批/预算/账本多闸门（fail-closed）     │
├──────────────────────────────────────────────────────────────────┤
│ Config   │ yml ⊕ DB 覆盖 + 收紧棘轮 + 生效解析 + 四步审批           │
└──────────────────────────────────────────────────────────────────┘
```

## 3. 阶段一结论（汇报）

1. **Agent 现状**：是"发布即冻结的 JSON 配置包"，`definition` 无 schema，实体上无 skills/tools/permissions 字段；工具契约仅以 `execution_snapshot.tool_contracts` JSONB 快照存在，与运行时 `ToolHandler` 注册平行。
2. **Skill 现状**：不存在；平台直接把能力建模为 Tool，无中间层。
3. **Tool 现状**：最成熟且安全边界清晰（SPI + 风险分级 + 唯一执行闸门 + 执行时重授权），是天然的能力底座。
4. **MCP 现状**：不存在；仅有规划层面的外部集成设想。
5. **Permission / Config 现状**：已具备分层授权、authzVersion 重授权、RLS、收紧棘轮、生效解析——是统一体系可直接复用的地基。

**对后续设计的启示**：本体系不应另起炉灶，而要**在 Tool + Permission + Config 地基上补上 Skill 与 MCP 两层**，并把 Agent 的 `definition` 从"自由 JSONB"升级为"受校验的能力编排结构"，同时复用 `ToolInvocationGate`（执行时重授权）、`EffectiveConfigResolver`（yml⊕DB）、`ConfigTighteningPolicy`（收紧棘轮）、RLS。`ToolHandler` 应作为 Native Tool 与 MCP-backed Tool 的**统一接口**，让外部 MCP 工具天然落入现有闸门（ADR-011 禁止绕过）。

## 7. 事实 / 假设区分 与 评审 P1 增强（评审 01 §2.2）

> 为避免把"目标能力"误读为"已有实现"，本节对结论分级标注（评审 01 §2.3 特别建议）。

### 7.1 三类标注
- **已验证事实**：有代码、数据库迁移或自动化测试证据（如 `ToolHandler`、`ToolInvocationGate`、`AuthorizationService` 内存实现、`agent`/`agent_version`/`execution_snapshot` 表存在）。
- **待确认事实**：有路径线索但运行期未验证（如 `AuthorizationService` 当前为内存版，其"跨实例即时失效"**尚未实现**，仅为内存 map；DB 化是 V1 目标）。
- **目标设计**：当前不存在，仅作为 V1 实施目标（Skill / MCP / `cap_*_def` / DB `authzVersion`）。

### 7.2 `agentVersion`（既有）与 `cap_agent_def.version`（新增）映射（评审 01-02）
- 既有 `agent_version.definition` 是不可变发布快照（自由 JSONB），由 `agent-api` 发布链路写入。
- V1 新增**结构化** `cap_agent_def(agent_id, tenant_id, version)`（不可变版本行，见 06 §1.4）。
- 二者**并存、指向同一发布事实**：迁移期双写（06 §3.3），`cap_agent_def` 为当前结构化真源，`agent_version` 保留历史归档；读取路径最终切到 `cap_agent_def`。**不是两套版本事实源**。

### 7.3 现有接口兼容性清单（评审 01-03）
| 接口/数据 | 变更影响 | 处理 |
|---|---|---|
| `ToolHandler`（toolName/inputSchema/riskLevel/validate/execute/reconcile） | 不变；MCP-backed 新增适配实现 | 复用，新增 MCP 包装实现 |
| `ToolInvocationGate.invokeAll` | 在 `[2]` 前插入 `InvocationValidator`，新增 `[8]` 执行准入点重验 | 扩展（07 §2） |
| `execution_snapshot.tool_contracts` | 扩展为 `effective_closure` + 四版本字段 | 兼容扩展（06 §1.6） |
| `AuthorizationService.isAuthorized` | 内存→DB 实现，强一致读 | 替换实现（06 §1.5） |
| `ConfigTighteningPolicy` / `EffectiveConfigResolver` | 复用，纳入 cap_* 对象 | 扩展读取源 |

### 7.4 RLS 对新增表的实施要求（评审 01-04）
- 现有 17 张表采用 RLS（`tenant_id = current_tenant_id()`）。新增 `cap_*_def` / `cap_authz_version` / `execution_capability_snapshot` / `cap_config_release` **默认开启 RLS**。
- 租户上下文来源：可信认证上下文（`TenantContext`），绝不取客户端输入。
- 跨租户引用约束：`cap_*_def` 平台级（`namespace=platform`）全局可读；租户自定义对象（V2）仅本租户可读写，禁止跨租户引用（06 §2）。

### 7.5 基线回归测试清单（评审 01-05）
新增能力须复用既有回归基线，避免破坏：授权（`AuthorizationService`/`RoleBasedAuthorizationService`）、RLS、配置审批（`ConfigChangeController` 双人复核）、幂等（`RunToolLedgerPort`）、重授权（`ToolInvocationGate` authzVersion 重验）、配置收紧（`ConfigTighteningPolicy`）。新增 R-09/R-13/R-16 等以平台 IT/架构测试补全（09 §3）。

### 7.6 执行链顺序迁移说明（评审 01-06 / 与 07 §2 对齐）

> 当前平台真实执行顺序（01 §1.3 `ToolInvocationGate`）为：
> `Schema 校验 → 执行时重新授权 → 幂等键 → 账本登记 → 审批 → 预算预留 → 执行 → 账本更新`。
> 该顺序是**既有事实**，缺少 V1 目标所需的「能力链逐跳重验（Phase A）」与「执行准入点重验（TOCTOU）」。

**V1 目标顺序（07 §2，对应 03 §3.2）**：

| 阶段 | 步骤 | 与现状差异 |
|---|---|---|
| Phase A 授权 | 主体授权（最先）→ Agent→Skill→Tool/MCP 能力链 → 风险上限 → MCP 绑定 → 参数策略 → 配置指纹 | 现状无"能力链逐跳重验"与"闭包指纹"，须由 `InvocationValidator` 补入（07 §2，在 `[2]` 前插入） |
| Phase B 执行准入 | 结构校验(Schema) → 审批 → 预算 → 账本 → **执行准入点重验(TOCTOU)** → 执行 | 现状"Schema 校验"在最前、无"执行准入点重验"；须把结构校验移至 Phase B 单次，并新增执行准入点重验（07 §2[10]） |

**迁移动作**：`ToolInvocationGate.invokeAll` 扩展（07 §2）——`[1]` 前插 `InvocationValidator`（Phase A），`[2]` 起承接 Phase B，末尾新增 `[8]` 执行准入点重验；既有"执行时重新授权"保留为 Phase A 主体授权重验的一部分（05 §2 顺序铁律）。**不得**把 Phase A 能力链判定与 Phase B 审批/预算混为单一 DENY（05 §0）。

→ 进入阶段二：评估「Agent 限定可用 Skill，Skill 声明可用 Tool 与 MCP」分层授权设计的合理性与正确性。
