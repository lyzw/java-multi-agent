# 阶段二：分层授权设计评估

> 待评估设计：**「Agent 限定可用 Skill，Skill 声明可用 Tool 与 MCP」**（即 Agent → Skill → {Tool, MCP} 的能力禁闭层级）。
> 评估方法：以阶段一的真实代码地基（ToolHandler SPI、AuthorizationService、authzVersion 重授权、RLS、EffectiveConfigResolver、收紧棘轮）为约束，检验该设计的合理性与正确性，并暴露其潜在问题。

---

## 1. 设计本质：能力禁闭（Capability Confinement）层级

该设计是一种**单向能力委托链 / 最小权限（least-privilege）禁闭模型**：

```
Agent ──(限定可用)──▶ Skill ──(声明可用)──▶ { Tool, MCP }
   （编排主体）           （能力包）            （最小可执行单元 / 外部接入）
```

- 上层只向下声明"**我能用到哪些下层**"，不感知下层实现细节；
- 有效权限 = 沿链**逐层取交集**得到的闭包（reachability closure）；
- 任何"越层直接伸手"（如 Agent 直连 Tool/MCP）都被禁止，除非显式授权。

这与平台已有的安全哲学**高度一致**：`ToolInvocationGate` 要求"模型不得绕过服务端授权直接执行工具"、权限"执行时重新授权"而非快照时、配置"只能收紧不能放松"。分层授权是把同一哲学上推到 Agent/Skill 编排层。

---

## 2. 该设计的优势（正确性支撑）

| # | 优势 | 说明 / 与现有地基的契合 |
|---|---|---|
| A1 | **最小权限、攻击面收敛** | Agent 只看到 Skill，不直接触达原始 Tool/MCP。对"用户/第三方编写的 Agent"尤为关键——即便 Agent 被注入恶意指令，它也只能在其已启用 Skill 的能力闭包内活动。 |
| A2 | **单一职责、关注点分离** | Agent 关注"编排什么任务"，Skill 关注"如何组合工具完成一类能力"，Tool 关注"单次原子操作"。三层正交，可独立演进、独立审计。 |
| A3 | **可复用性与组合性** | "发邮件""查学籍"等 Skill 被多个 Agent 复用；Skill 通过声明 Tool/MCP 自动继承其风险级别与审批要求，无需每个 Agent 重复声明。 |
| A4 | **天然契合现有执行闸门** | Skill 声明的 Tool 最终都收敛到 `ToolHandler`（含 MCP-backed Tool 包装），必然经过 `ToolInvocationGate` 的重授权/审批/预算/账本——分层授权**不会绕开**既有纵深防御，而是为其提供"前置白名单"。 |
| A5 | **权限可静态分析** | 因为链路是声明式的，可在配置期计算"某 Agent 的能力闭包"，做可达性检查、权限越界扫描、审计报表，而无需运行。 |

## 3. 潜在问题（必须修正才能落地）

### 3.1 权限越界（Privilege Escalation）

- **P1 仅配置期校验、运行期不重验 → 越界**。若只在"Agent 启用 Skill"时检查一次，而 Skill→Tool 在运行期不复核，则"曾经合法"的 Agent 可在权限被撤销后继续越权（与红线 9 同构）。**必须**在每次工具调用时沿链重验（复用 `authzVersion`）。
- **P2 MCP 动态性导致声明漂移**。MCP server 的工具集可在运行期增删，而 Skill 声明的是"接入该 server"。若仅按声明的 server 放行其**全部**工具，则 server 新增的高危工具会被静默打开。**必须**在 Skill→MCP 边引入"按工具名 allowlist"，并在每次调用时把 server 当前工具集与 allowlist **取交集**（fail-closed：不在 allowlist 即拒）。
- **P3 嵌套 Skill 组合抬权**。若允许 Skill 再组合 Skill，则一个低危 Skill 可能经 transitive 闭包拉入高危 Tool。对策：若要支持嵌套，Agent 的"有效 Skill 集"必须是**传递闭包**，且 Agent 必须显式启用闭包中的**每一个** Skill（即 transitive enablement），否则拒绝——避免"启用一个 Skill 静默获得未授权能力"。
- **P4 高危 Tool 经低危 Skill 透传**。Skill 若无 `riskCeiling`（能力上限），可能把一个 WRITE_EXTERNAL 工具包进"只读助手"Skill。对策：Skill 声明 `riskCeiling`，Tool 的 `riskLevel` 超过上限即拒。

### 3.2 组合爆炸（Combinatorial Explosion）

- 边数 = |Agent→Skill| + |Skill→Tool/MCP|。Agent×Skill 全枚举 + Skill×Tool 全枚举，规模随三者乘积增长。
- **缓解（M1）**：用 **capability tag / 分组 / Skill Bundle / Agent Profile** 代替逐对枚举——Agent 启用"一组 tag"而非逐个 Skill；Skill 引用"一组 tool tag"。但 tag 过宽会引入越界风险，需"显式 allowlist 用于高保证场景 + tag 用于常规场景"的双轨。
- **缓解（M2）**：**引用而非复制**。Tool/MCP 定义为单一事实源（single source of truth），Skill 仅引用其 id；Agent 仅引用 Skill id。闭包在绑定/运行期计算并缓存（以 `authzVersion` 失效），避免 O(边数) 的逐次计算。

### 3.3 配置冗余（Configuration Redundancy）

- 同一 Tool 被多个 Skill 声明、同一 MCP server 被多个 Skill 声明 → 冗余且易漂移（改一处漏一处）。
- **缓解（M3）**：Tool/MCP 集中定义；Skill 只引用 id；支持 Skill `inherits` 基础 Skill 的工具集（但须受 P3 约束）。默认继承 + 必要覆盖，减少重复声明。

### 3.4 粒度控制（Granularity Control）

- **G1 两层粒度耦合**：MCP 实际有"连接 server"（连接级）与"调用 server 内某工具"（操作级）两个粒度，设计把它们混在"声明可用 MCP"里过粗。**必须拆分**：Skill 声明 `mcpServers: [{serverId, toolAllowlist}]`——连接级 + 操作级分离。
- **G2 参数级权限缺失**：Tool 启用 ≠ 任意参数合法。例如"邮件 Skill"应限定收件域白名单、"SQL Skill"应限定库表白名单。**需引入 `paramPolicies`**（参数约束），在 `ToolHandler.validate()` 或独立 `ParamPolicyGate` 执行，与现有 `validate()` 一致。
- **G3 风险级别是布尔开关的替代**：现有 `ToolRiskLevel`（READ/WRITE_PROFILE/WRITE_EXTERNAL）+ `defaultApproval()` 已提供"启用 + 风险驱动审批"的精细度，Skill 层应继承并叠加 `riskCeiling`，而非另设布尔开关。

### 3.5 继承与覆盖语义缺失

- 设计未说明：Agent 模板/Profile 如何覆盖？租户如何覆盖？父子 Skill 如何合并？缺省是"并集"还是"交集"？
- **必须明确**（复用现有地基）：
  - 优先级 **Agent 显式覆盖 > Agent Profile/模板 > Skill 基础继承 > 平台默认**。
  - 收紧棘轮：覆盖**只能收紧**（移除 Skill/Tool、调低 `riskCeiling`），不能放松（复用 `ConfigTighteningPolicy`）。
  - 租户覆盖：沿用 `tenant_config_override` + `EffectiveConfigResolver`（yml ⊕ DB），仅收紧。

## 4. 改进建议汇总（落地点）

| 问题 | 改进 | 复用现有地基 |
|---|---|---|
| P1 运行期不重验 | 每次调用沿链重验 + `authzVersion` 重授权 | `AuthorizationService.currentAuthzVersion`、`ToolInvocationGate` |
| P2 MCP 漂移 | Skill→MCP 拆分连接级/操作级 + 运行期 allowlist 交集 | `ToolHandler`（MCP-backed 包装） |
| P3 嵌套抬权 | transitive enablement（Agent 须启用闭包全部 Skill） | 闭包计算 |
| P4 高危透传 | Skill `riskCeiling` 上限校验 | `ToolRiskLevel` |
| M1 组合爆炸 | capability tag + Skill Bundle + Agent Profile + 引用 | `EffectiveConfigResolver` |
| M3 配置冗余 | Tool/MCP 单一事实源 + Skill `inherits` | — |
| G1 粒度耦合 | MCP 连接级/操作级分离 | `ToolHandler` |
| G2 参数权限 | `paramPolicies` 参数约束 | `ToolHandler.validate` / `ParamPolicyGate` |
| G3 风险粒度 | 继承 `ToolRiskLevel` + `riskCeiling` | `ToolRiskLevel.defaultApproval` |
| 覆盖语义 | 优先级 + 收紧棘轮 + 租户覆盖 | `ConfigTighteningPolicy` / `tenant_config_override` |

## 5. 阶段二结论（汇报）

**结论：该分层授权设计在方向上是正确的、合理的，且天然契合本平台已有的"执行时重授权 + fail-closed + 收紧棘轮 + RLS"安全哲学，应当采纳。** 但它是一个"骨架正确、细节欠缺"的设计，直接落地会引入越界与爆炸风险。须按第 4 节完成 9 项修正后方可工程化，核心三条铁律：

1. **每一跳都必须在运行期重新校验**（不能只在配置期校验一次）——这是红线 9 在编排层的延伸。
2. **MCP 必须拆分为"连接级 + 操作级"，并以运行期 allowlist 交集兜底其动态性**。
3. **配置采用"引用 + 分组 + 收紧棘轮 + 租户覆盖"，复用 `EffectiveConfigResolver` 与 `ConfigTighteningPolicy`，避免组合爆炸与冗余**；同时补上参数级 `paramPolicies` 与 Skill `riskCeiling`。

→ 设计合理，进入阶段三：输出完整 PRD。

## 6. 形式化决策规范要点（评审 02 §3.2 P0，完整版见 05）

阶段二已论证"分层禁闭"方向正确，但其安全规则须**形式化**才能约束开发与测试。要点如下，详细公式/错误码/撤权/异常矩阵见 **05《分层授权决策规范》**。

### 6.1 逐层取交集的严格定义（P0："逐层取交集"不够严格）

> **修订（评审 §3.1）**：本节能**不重复定义整套公式**。一次调用的正式授权公式、判定顺序与稳定错误码**统一以 05《分层授权决策规范》为准**（05 §0/§1/§2/§4）。本节只说明设计依据，避免多份规则源导致实现偏差。
>
> 关键依据摘要：授权 = 主体授权 ∧ 能力链（Agent→Skill→Tool）∧ 风险上限 ∧ MCP 绑定 ∧ 参数策略（Phase A）；审批/预算/幂等/账本属**执行准入（Phase B）**，不与授权混为单一 DENY（05 §0）。主体授权必须**先于**能力链判定（顺序铁律，05 §2）。

- **能力闭包 ≠ 主体授权**：`AgentSkillAllowed ∧ SkillToolAllowed` 回答"Agent 被配置为可用什么"；`PrincipalAuthorized` 回答"当前主体此刻是否有权"。两者不可互相替代（评审 02 §3.3）。
- "不适用"因子（如 native 调用的 `MCPBindingAllowed`）必须**显式跳过**，禁止默认整段跳过安全校验。

### 6.2 权限撤销与在途 Run（P0）

- 三类版本：`agentVersion` / `configVersion`(指纹) / `authzVersion`（**DB 单调，V1 强制**，多实例安全必要条件）。
- 新调用读实时版本，陈旧即 DENY；已审批待执行调用随 `authzVersion` 变化失效需重审；执行中调用按幂等键对账，结果以 `executionStatus` 记录，不承诺可撤销（05 §5）。
- 安全默认值：新调用必须拒绝使用已失效授权状态（05 §5）。

### 6.3 MCP 动态发现的安全边界（P0）

- V1 固定清单 + 配置指纹校验，无运行期发现；server Schema 变更/工具下线 → 视为指纹变化 → `config_stale` DENY（06 §4/§5）。
- **V1 必做 MCP（评审 P0-2 结论，用户决策）**：MCP 接入为 V1 **Must-Implement**（04 A3），非"若本期需 MCP"的可选项；V1 范围为"固定清单 + 指纹"，不实现动态发现（04 N4）。V2 才引入动态发现并承担其 SSRF/漂移缓解（06 §5/§6）。V1 与 V2 边界以 04 为唯一基线，02 仅作设计论证，不得被误读为 V1 可省略 MCP。
- V2 若引入动态发现：工具身份稳定映射、发现超时按空集→拒、凭据轮换后连接级重验、MCP 输出视为不可信（05 §6）。

### 6.4 继承规则消歧（P1）

- `Skill.inherits`：V1 **写入即拒**；V2 启用须递归启用（Agent 须显式启用闭包全部 Skill）+ 循环依赖拒绝 + 不可移除父 Skill 工具（05 §7）。
- `capabilityTags` / `skillBundles`：V1 忽略语义（防标签过宽越界），为 V2 留字段（04 §3）。

### 6.5 可验证威胁模型（P1，评审 §3.2 补充）

每条越权风险对应自动测试（08 §2/§3）；覆盖正向/反向/异常/并发/撤权五类。新增长期威胁与 V1 对应缓解：

| 威胁 | 攻击前提 | 攻击动作 | 预期拒绝位置 | 安全不变量 |
|---|---|---|---|---|
| P1 配置期校验→越权 | 权限曾被授予 | 撤权后凭旧快照继续调用 | Phase A 主体授权（AUTHZ_STALE）/ 执行准入点（EXEC_ADMISSION_STALE） | 实时版本，非快照 |
| P2 MCP 漂移 | MCP 工具集变化 | 借已声明 server 调高危新工具 | 操作级 allowlist / 指纹失效 | 运行期交集 + 指纹 |
| P3 嵌套抬权 | Skill 可组合 Skill | 低危 Skill 拉入高危 Tool | V1 禁 inherits；V2 transitive enablement | 显式启用闭包全部 |
| P4 高危透传 | 低危 Skill 包高危 Tool | 经 Skill 调 WRITE_EXTERNAL | riskCeiling | 上限约束 |
| G2 参数越权 | 工具已启用 | 收件域/库表越界 | paramPolicies | 业务权限层 |
| **租户越权** | 恶意 Agent/Skill | 引用其他租户对象 / 伪造 tenantId / 复用跨租户快照 | RLS + 引用完整性 | 租户上下文仅来自认证 |
| **配置发布竞态** | 校验完成未发布 | 发布前引用对象被改/停用 | PUBLISHED 完整集合才可解析（06 §3.2） | 原子发布 |
| **外部副作用不确定** | MCP 已发请求 | 客户端超时/响应丢失/重复调用 | executionStatus=UNKNOWN 对账；幂等键防重复 | 不承诺可撤销，须对账 |

> **V1 与 V2 安全要求差异（评审 §3.3）**：本文 P1–P4、G1–G3 中的动态 MCP 漂移与嵌套 Skill 继承属**整体架构长期威胁模型**；V1 通过固定清单、配置指纹及禁止 `inherits` 降低风险。V1 的具体实现与验收以 04、05、08 为准，**不得把 V2 设计论证误读为 V1 必须实现的功能**。

> 02 结论不变：**分层禁闭采纳**；上述形式化使 02 从"设计合理性分析"升级为可约束开发/测试的**安全设计依据**（05）。
