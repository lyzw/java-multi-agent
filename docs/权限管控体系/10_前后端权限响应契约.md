# 前后端权限响应契约（401 未认证 / 403 无权限）

> 配套代码改动：后端 `SecurityConfiguration` 401/403 错误体统一、双前端 `client.ts` 按 `code` 分支拦截、无权限整页 `NoPermissionPage`、守卫测试 `apiClient401.test.ts` / `apiClientAuth.test.ts` / `errors.test.ts`。
> 适用范围：租户辅导端 `frontend`、平台管理端 `admin-console`、后端 `platform`（Spring Security 双过滤链）。

---

## 1. 问题背景

历史实现里，前端对 **任意 401 一律清会话 + 跳转登录页**。这把三类本不相同的情形混为一谈：

| 真实情形 | 后端信号 | 正确前端处置 | 旧实现处置（缺陷） |
| --- | --- | --- | --- |
| 用户未登录 / 令牌失效 | `401` + `UNAUTHENTICATED` | 清会话 + 跳登录 | ✅ 跳登录（正确） |
| **业务无权限**（已登录，缺角色/作用域） | `403` + `ACCESS_DENIED` | 提示 / 渲染无权限页，**绝不跳登录** | ❌ 误跳登录，丢失操作现场 |
| 跨身份域 401（平台令牌打租户端点） | `401` + `UNAUTHENTICATED`（Security 过滤器） | 通道边界提示，**不跳登录** | ❌ 误跳登录，草稿与会话一起丢 |

实测后果（2026-10-28 前端端到端）：点「路由策略试跑」「AI 实验室发起执行」被直接踢回登录页，页内写好的「通道不可达」提示永远走不到。

根因不在后端（后端早已用 401/403 区分两类场景），而在**前端不分青红皂白把 401 当未登录**，以及**错误体形状不统一**使「按 code 分支」难以干净实现。

---

## 2. 设计原则（契约的硬约束）

1. **HTTP 状态不混用**：身份认证失败用 `401`，业务权限不足用 `403`。既有平台纪律「拒绝走 4xx、故障走 5xx」保持不变。
2. **错误体统一为 `{code, message}`**：Security 过滤器层（`SecurityConfiguration`）与业务应用层（`ApiExceptionHandler`）**同一形状**，前端只认一套。
3. **前端按 `code` 分支，而非裸 HTTP 状态**：`code` 是语义真相，`status` 只是传输层。即便 `401` 也可能携带 `ACCESS_DENIED`（边界情形），必须由 `code` 决定行为。
4. **fail-closed**：无法识别的 code/形状一律按「不跳登录、原样抛出」处理，绝不静默回落到「跳登录」。
5. **两条铁律**：
   - `UNAUTHENTICATED`（未登录） → 清会话 + 跳登录；
   - `ACCESS_DENIED`（已登录但无权限） → **绝不跳登录**，提示或渲染无权限整页。

---

## 3. 后端响应结构

### 3.1 统一错误体（两种来源一致）

```jsonc
// 身份认证失败（Security 过滤器 / ApiExceptionHandler）
{ "code": "UNAUTHENTICATED", "message": "未认证" }

// 业务无权限（已登录，缺少所需权限）
{ "code": "ACCESS_DENIED", "message": "无权执行该操作" }

// 业务校验失败（可选附带字段级提示）
{ "code": "INVALID_REQUEST", "message": "请求有误，请检查填写内容",
  "fieldErrors": { "key": "只能收紧，不允许放松" } }
```

- `code`：统一错误码（字符串，全大写蛇形）。
- `message`：面向用户的中文文案，可空；空时前端按 `code` 兜底文案。
- `correlationId`（仅 5xx）：排障用，前端透传到日志/界面，绝不进用户可见文案。
- `fieldErrors`（仅 400）：字段级提示。

### 3.2 后端已落实的改动

`platform/platform-bootstrap/.../config/SecurityConfiguration.java` 中：
- 401 体由 `{error:"unauthorized"}` 改为 `{"code":"UNAUTHENTICATED","message":"未认证"}`；
- 403 体由 `{error:"forbidden"}` 改为 `{"code":"ACCESS_DENIED","message":"无权执行该操作"}`；
- HTTP 状态 **保持 401 / 403 不变**（只统一 body 形状）。

> ⚠️ 登录端点（`AuthController` / `PlatformAuthController`）的 `ErrorResponse(String error)` 与 `invalid_credentials` 形状**故意保留不动**——前端 `errors.ts` 已兼容归一化（见 §5.1）。

## 4. 错误码表

| code | HTTP | 含义 | 前端处置 |
| --- | --- | --- | --- |
| `UNAUTHENTICATED` | 401 | 未登录 / 令牌失效 | 清会话 + 跳登录 |
| `ACCESS_DENIED` | 403 | 已登录但缺少所需权限 | **不跳登录**；提示 / 无权限整页 |
| `INVALID_CREDENTIALS` | 401 | 凭据错误（账号/租户/密码任一不符） | 文案收敛为「租户、账号或密码不正确」，不细分 |
| `INVALID_REQUEST` | 400 | 请求参数不合法 | 表单级错误提示 |
| `NOT_FOUND` | 404 | 资源不存在 | 提示；404/501 渲染「能力未接入」而非故障 |
| `IDEMPOTENCY_CONFLICT` | 409 | 幂等冲突 | 提示「刷新后重试」 |
| `CONFIG_RELAXATION_REJECTED` | 409 | 配置只允许收紧 | 提示「只能收紧，不允许放松」，**不是**刷新重试 |
| `COMPLIANCE_BLOCKED` | 422 | 不符合合规要求 | 合规提示 |
| `UNSUPPORTED_MEDIA_TYPE` | 415 | 请求格式不受支持 | 提示 |
| 体缺失 / 无法识别 | — | 降级为 `HTTP_<status>` 或 `NETWORK_ERROR` | 按 status 兜底文案，绝不跳登录 |

## 5. 前端统一拦截方案

双前端都遵循同一契约，但归一化实现不同（租户端有 `NormalizedError`，管理端直接给 `ApiError`）。

### 5.1 租户端 `frontend`

- 归一化：`src/api/errors.ts` 的 `normalizeHttpError(status, body)` 兼容两套形状
  （`{code,message}` 与 `{error}`），产出 `NormalizedError { status, code, message, correlationId?, fieldErrors }`。
- 分支拦截：`src/api/client.ts` 的 `_request` / `openEventStream`：
  ```ts
  if (normalized.code === 'UNAUTHENTICATED') {
    clearSession(); onUnauthorized();   // 仅此一种情形跳登录
  }
  throw new ApiError(normalized);        // ACCESS_DENIED 及其它原样抛出
  ```
- 判定助手：`isAccessDenied(err: NormalizedError)` → `err.code === 'ACCESS_DENIED'`；
  `isAuthError` 用于「需重新登录」类。二者**严格区分**。
- 落地页：`src/components/NoPermissionPage.tsx` 读 `?reason=`；`src/api/permission.ts` 的
  `notifyAccessDenied(err, navigate?)` 在捕获到无权限时跳无权限整页；`App.tsx` 已注册 `/no-permission` 路由。
- 配置页接线：`pages/config/ConfigPages.tsx` 用 `useConfigOverrides()` 的 `accessDenied` 标志渲染整页，
  普通错误继续走 Toast。

### 5.2 管理端 `admin-console`

- 错误类：`src/api/client.ts` 的 `ApiError` 新增 `code` 字段（构造 `new ApiError(status, message, data?, code?)`；
  省略 `code` 时按状态推导：401→`UNAUTHENTICATED`、403→`ACCESS_DENIED`、其余→`HTTP_<status>`）。
- 分支拦截：`_request` 用**双轴**判定是否清会话跳登录：
  ```
  清会话跳登录 ⟺  (路径 ∈ 本控制台会话域 /platform/**) 且 (code === UNAUTHENTICATED)
  ```
  - 跨身份域 401（平台令牌打租户端点）→ `code` 可能为 `UNAUTHENTICATED`，但因**路径不在会话域**，
    **不清会话、不跳登录**，抛出交给 `isTenantChannelBlocked` 提示「需租户级令牌通道」；
  - 任意 `ACCESS_DENIED`（含 `/platform/**` 的 403，已登录但无权限）→ **绝不跳登录**，渲染无权限页。
- 判定助手：`isAccessDenied(cause)` → `cause instanceof ApiError && cause.code === 'ACCESS_DENIED'`；
  `notifyAccessDenied(err, navigate?)` 跳 `/no-permission?reason=...`。
- 落地页：`src/pages/NoPermissionPage.tsx`（antd `Result` 403）；`router.tsx` 已注册 `/no-permission` 路由。
- 兼容性：既有 `new ApiError(status, message)` 调用（测试与部分代码）无需改动，code 自动按状态推导，
  `isTenantChannelBlocked` / `isRejectedInput` / `isRagTimeout` 等状态判定助手不受影响。

---

## 6. 双轴判定速查（管理端）

```
请求返回非 2xx
   │
   ├─ status === 401 且 path 以 /platform/ 开头 且 code === UNAUTHENTICATED
   │       → 清会话 + 跳登录（reason=expired&next=当前路径）
   │
   ├─ status === 401 且 其它路径（租户身份域）
   │       → 抛出（code=UNAUTHENTICATED），交 isTenantChannelBlocked 提示通道边界
   │
   └─ 其它（含 403 + ACCESS_DENIED、400、409、5xx…）
           → 原样抛出，code 透传给页面分支；ACCESS_DENIED 渲染无权限整页，绝不跳登录
```

---

## 7. 反模式（禁止）

- ❌ 对 `response.status === 401` 一律清会话跳登录（租户端旧实现，已修）。
- ❌ 业务无权限返回 HTTP 200 + body code（与「拒绝=4xx」纪律冲突；本方案**保留 401/403 + 统一错误体**）。
- ❌ 在无权限时调用 `clearSession()` 或 `redirectLogin()`。
- ❌ 把 `ACCESS_DENIED` 与 `UNAUTHENTICATED` 在文案/跳转上混为一谈。
- ❌ 在 Security 过滤器层返回 `{error:"unauthorized"}` 之类旧形状（应与应用层统一为 `{code,message}`）。
- ❌ 跨身份域 401 被当成「登录失效」——那是身份域隔离按设计生效。
