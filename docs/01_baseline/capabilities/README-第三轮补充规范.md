## 一、§5.x 深度补充：能力评分卡（量化「领先/持平/落后」）

> **目的**：第一轮第五章用「领先 / 持平 / 落后 / 短板」做定性判定。本节把它**量化成可复算的分数**，让 13 份横向可比、让后续演进有基线。

### 1.1 体例

在第五章末尾追加：

```markdown
### 5.x 深度补充：能力评分卡（把定性判定量化成可复算分数）

> 评分轴直接沿用 1.3 的 N 个评价轴（本维度为 <轴1> / <轴2> / ...），每轴 0–4 分。
> **评分口径（全局统一）**：
> - **0** = 完全缺失（无对应实现，且无缺口登记）
> - **1** = 有痕迹不可用（有类/有表/有配置，但未装配/未写入/未触发 —— 即运行期不可达）
> - **2** = 局部可用（仅单一路径生效，或仅单租户/单场景生效，或靠人工兜底）
> - **3** = 能力完整（默认路径生效 + 有失败语义 + 有测试门禁）
> - **4** = 能力完整且有护栏（默认生效 + 失败语义 + 门禁 + 运行时度量/告警/可观测）
> **每格必须给证据锚点**（`文件:行号` 或「官方文档 URL」），无证据不得给分。
> **加权总分** = Σ(轴分 × 轴权重) / Σ权重；权重取自 1.3 的「加权优先级」（若 1.3 未给权重，按「强制程度 > 可审计性 > 失败可诊断性 > 运维成本 > 生态成熟度」次序分配递减权重，并注明为本轮新设）。

| 评价轴 | 权重 | 我们的得分 | 证据锚点 | 竞品最高分 | 差距 | 差距根因（设计取舍 / 能力缺失 / 证据缺口） |
|---|---|---|---|---|---|---|
| <轴 1> | 0.30 | <0–4> | `<文件:行号>` | <竞品名: n> | <±n> | <一句话> |
| ... | | | | | | |
| **加权总分** | 1.00 | **<x.xx>/4** | — | **<y.yy>/4** | **<±z.zz>** | — |

**判读纪律**：
1. 分数是**工程判断**，不是客观测量；1–2 分的差距不构成「结构性落后」的证据，只构成改进项优先级输入。
2. 「竞品最高分」只取本报告第三章已核实的官方文档事实，**不得凭印象给分**；无官方依据的轴，该格填「不评分」并说明。
3. 若某轴我们得分高于竞品最高分，必须在 §5.2 或本节补一句**机制解释**（为什么能更高），否则按铁律「诚实优先于漂亮」下调 1 分。
```

### 1.2 强制要求

- **每轴至少一条证据锚点**，锚点必须是你**本轮实际 Read/Grep 核对过**的（不得抄抄正文旧锚点而不复核）。
- 差距根因三选一（可并列）：`设计取舍` / `能力缺失` / `证据缺口`（本轮未能核实到证据）。
- 必须有一行「**本轮复核推翻的既有判定**」子表：若本轮证据推翻了 5.1 中某行的「领先/持平/落后」判定，在此列出并说明。

## 二、附录 G：配置项全量矩阵与「生效性」判定表

> **目的**：本项目多次出现「配置项存在但默认不生效」「配置漂移」「有类无注入点」三类静默失真（见 00 总览 §3.2/§3.3）。本附录把**本维度相关的每一个配置键**摊开，逐项判定**是否真的被消费**。

### 2.1 体例

```markdown
### 附录 G：配置项全量矩阵与「生效性」判定表

> **判定四问**（沿用项目新铁律「运行期可达性审计」）：① 谁定义？② 谁读取？③ 读取后改变了什么行为？④ 有没有测试/门禁证明它生效？
> **生效性判定**：`✅ 真生效` / `⚠️ 条件生效`（附条件）/ `❌ 默认不生效`（附默认路径）/ `🟡 漂移风险`（配置源与消费方口径不一致）/ `❓ 本轮未能核实`。
> 配置源：`platform/platform-bootstrap/src/main/resources/application.yml`（平台）、`rag.env`（检索域）、`platform.env`（部署域）。

| # | 配置键 | 默认值 | 定义位置 | 消费方（类:行号） | 生效条件 | 生效性判定 | 静默失效风险 / 处置建议 |
|---|---|---|---|---|---|---|---|
| G-01 | `agent.worker.concurrency` | <默认值> | `application.yml:<行号>` | `WorkerPolicy.java:<行号>` | <条件> | ❌ 默认不生效 | <风险>；<建议> |
| ... | | | | | | | |

**本维度配置项统计**：共 N 项 —— ✅真生效 x / ⚠️条件生效 y / ❌默认不生效 z / 🟡漂移风险 w / ❓未能核实 v。
**「默认不生效」项的共同根因**（一段归纳 + 是否属本项目已知铁律范围）。
```

### 2.2 强制要求

- **至少 8 行**（本维度配置项少于 8 个时，合并相邻键或纳入相关 `env` 变量，并注明「本维度无独立配置段」）。
- 「消费方」必须给出**实际读取该键的类与行号**（本轮 Read/Grep 确认）；**只声明在 yml 里但无人读取的，必须标注 `❓ 未能核实消费方` 或 `❌ 默认不生效`**，这是本附录最有价值的产出。
- 不得凭配置文件名推测生效性；**必须 Grep 配置键名（连字符与 camelCase 两种写法都试）**。
- 注意本项目既有坑：默认消息通道是 `database`（PG 表队列）非 RabbitMQ；`agent.worker.concurrency/prefetch` 默认不生效、有效并发=1；`context.enabled=false` 使富压缩管线处于影子期。

## 三、附录 H：场景级端到端时序推演

> **目的**：把「调用链」从静态调用关系升级为**带时间轴、带分支、带失败路径**的推演，让读者能按图索骥地对照真实运行。

### 3.1 体例

```markdown
### 附录 H：场景级端到端时序推演（3~5 个关键场景）

> 每个场景给出：触发入口 → 逐跳时序（ASCII 时序图）→ 每跳的源码锚点 → 失败分支（错误在哪一跳被捕获/转换）→ 可观测落点（事件/日志/指标）→ 断点位置（排查时该打哪几行）。

#### H-1 场景：<场景名>
- **触发入口**：<HTTP 路径 / 消息类型 / 定时任务>（`文件:行号`）
- **前置状态**：<表/状态字段的初始值>
- **ASCII 时序**：
  ```
  <参与者A>        <参与者B>        <DB>          <MQ/Worker>
     |--- 请求 ----->|               |               |
     |               |-- SELECT ---->|               |
  ```
- **逐跳锚点表**：

| 跳 | 动作 | 源码锚点 | 落点（表/事件/日志） | 失败语义 |
|---|---|---|---|---|
| 1 | <动作> | `文件:行号` | <落点> | <失败时发生什么> |

- **失败分支**：<列出 2–3 条真实存在的失败路径及其错误码/状态转换，锚点可复核>
- **可观测落点**：<事件类型 / 日志 / 指标；若无则明确写「无观测点」>
- **排查断点**：<建议打断的行号 2–4 个>
```

### 3.2 场景选取规则（每个维度必须覆盖以下类别中的 3–5 个）

1. **正常主链路**（最常见的一次成功请求/一次执行）
2. **失败链路**（一次明确的失败：超时、校验失败、权限拒绝、外部依赖异常）
3. **并发/竞态场景**（并发写、重复消息、抢租约、双通道并存）
4. **崩溃/恢复场景**（进程中断后续跑、超时后的对账、孤儿 run 兜底）
5. **权限/安全场景**（越权尝试被拒、RLS 未绑定租户、注入内容被围栏）

### 3.3 强制要求

- **场景必须是本维度真实存在的路径**（有源码锚点），不得虚构。写入前必须实际 Read 相关类确认。
- ASCII 时序图必须与锚点表**逐跳对应**，跳数一致。
- 「失败分支」至少 2 条；若该路径下确有 fail-closed 保护，须明确指出（对应铁律 8）。
- 至少 1 个场景需要覆盖**并发/重复投递**（呼应铁律 5、6）。
