## 一、维度定义与评估坐标系

### 1.1 这个维度到底解决什么问题（问题陈述，不谈实现）

"多租户隔离"回答的不是"系统能服务多少客户"，而是**一组关于「数据归属边界」的元问题**：

- 当一个请求带着主体 A 的身份进来，**它能否读到/写到主体 B（另一租户）的数据**？判定发生在哪一层？
- 当**应用层代码写出了一条不带租户谓词的 SQL**，数据库会返回什么？是「全部租户的数据」（越权），还是「零行」（默认拒绝），还是「报错」？
- 当**数据库连接被连接池复用**、上一条请求残留了租户上下文，下一条请求若未显式绑定，会继承上一个租户的身份吗？
- 当**平台运维/跨租户治理**需要操作多个租户的数据时，边界如何不被一并打破？

这一维度是后续权限（07）、可观测/审计（10）、可靠性（11）的**承载地基**——隔离若只在应用层"靠自觉"，则权限判定、审计举证、故障归因全部建立在沙丘上。

### 1.2 能力分层的四档模型（通用分层法）

按"隔离由哪一层强制、默认语义是放行还是拒绝"给出四档，从弱到强：

| 档位 | 名称 | 隔离由谁强制 | 默认语义 | 代表形态 | 典型代价 |
|---|---|---|---|---|---|
| **L0 无隔离** | 单租户/共享 | 无 | 全部可见 | 裸表、无 tenant_id | 一租户即全部，越权=默认 |
| **L1 应用层隔离** | SDK/库内 WHERE | 应用代码/ORM 层 | 取决于代码是否写对 | OpenAI/Anthropic/LangGraph/ADK 的 thread/user/session 作用域、CrewAI 社区版 | 漏写谓词=静默越权；连接复用串租户 |
| **L2 框架层隔离** | 框架托管的作用域原语 | 框架提供的隔离原语（仍运行在应用进程内） | 取决于框架实现 | Agno（内建 JWT/服务账号 + per-user 隔离，但仍在应用/SDK 层裁决） | 裁决点仍在进程内，DB 层不感知 |
| **L3 数据层强制隔离** | 数据库行级安全（RLS）默认拒绝 | **存储引擎**（PostgreSQL 策略），绕过需 BYPASSRLS/owner | **默认拒绝（0 行）** | **本平台（RLS + GUC `app.tenant_id` + FORCE + 应用层显式 Gate + 复合外键）** | 部署必须正确绑 GUC；配置错会"假绿/假失败" |
| **L4 引擎原生一等公民** | 数据库/运行时把租户当一等概念 | 存储引擎 + 租户级连接/密钥/独立 schema 或库 | 物理隔离 | 金融多账套（独立库）、独立 schema 部署 | 运维/成本最高，跨租户分析最难 |

**判定**：本平台落在 **L3**，是本次对比的全部竞品里唯一把"行级隔离"下沉到数据库引擎、并以 **FORCE + 默认拒绝** 形态强制的方案；Agno 接近 L2（内建身份+隔离但在应用层裁决）。L4（物理隔离）是演进方向而非现状（见第七章改进点 3）。

### 1.3 评估坐标系：5 个评价轴

| 轴 | 含义 | 观测方式（如何度量） |
|---|---|---|
| **强制程度** | 隔离由哪一层强制、能否被应用 bug 绕过 | 注入"漏写 tenant_id 谓词的 SQL"，看 RLS 是否仍只返回本租户行；用普通角色连库直接查能否越权 |
| **默认语义** | 未绑租户上下文时返回什么 | 清空 GUC `app.tenant_id` 后查询，看是 0 行（拒绝）/ 全量（放行）/ 报错 |
| **可审计性** | 谁在何时以何种授权读了哪租户的数据 | 是否存在不可变的授权判定流水（`authz_decision_log`）与跨租户访问证明 |
| **可观测性** | 隔离是否"可见、可被发现失效" | "未绑 GUC 静默 0 行"能否被启动自检/运行时哨兵/指标发现（见第七章改进点 1） |
| **失败可诊断性** | 隔离失效/误伤时能否定位 | 注入"串租户连接"，看是否产生可观测的 mismatch/taint（影子对照） |

## 二、理论体系（必须引用真实出处）

### 2.1 核心理论/概念框架（≥3 个，逐一给真实出处）

#### (1) 多租户 SaaS 数据隔离模型谱系（三种拓扑）
- **出处**：Frederick Chong, Gianpaolo Carraro, Roger Wolter, *"Multi-Tenant Data Architecture"*, Microsoft MSDN, 2006（https://msdn.microsoft.com/en-us/libRary/aa479086 ）。另见 Microsoft Architecture Guidance / Azure *"Architectural approaches for storage and data in multitenant solutions"*（https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/storage-data ）。
- **定义**：沿"隔离强度—运维成本"连续统，分三档：
  1. **Separate Databases（独立库）**：每租户独立数据库，隔离最强、备份/恢复/合规最简单，但硬件与运维成本最高、单服务器可容纳租户数最低。
  2. **Shared Database, Separate Schemas（共享库独立 schema）**：同库不同 schema，租户密度高、成本低，但备份/监控需定制，隔离弱于独立库。
  3. **Shared Database, Shared Schema（共享库共享 schema）**：所有租户同表、靠 `tenant_id` 列区分，密度最高、成本最低，但**隔离完全依赖应用层 WHERE**，索引/查询/备份最复杂，且"漏一个谓词=越权"。
- **与本维度的关系**：本平台是**第三种拓扑（共享 schema + tenant_id 列）**，但通过 PostgreSQL RLS 把"应用层 WHERE"升级为"数据层强制"（即把第三种拓扑的致命弱点用 L3 手段补强）。Azure 文档也明确写道："Row-level security can provide security isolation for specific tenants' data in a shared multitenant database… you need to ensure that the user's identity and tenant identity are propagated through the application and into the data store with each query"——**这正是 `TenantSessionBinder` 绑 GUC 的理论依据**。

> **诚实标注（对任务书"NIST SP 800-125"的更正）**：任务书把三种模型归属于"NIST SP 800-125 指南"。经核实，NIST SP 800-125 的标题是 *"Guide to Security for Full Virtualization Technologies"*（聚焦**虚拟机监视器/虚拟化**安全），**并不定义 SaaS 多租户数据隔离三模型**。三模型的权威出处是 **Microsoft（Chong et al., 2006, MSDN）** 与云厂商的 shared-responsibility 架构指南（Azure/AWS/CSA）。本报告据此采用 Microsoft 出处，未臆造 800-125 的 SaaS 隔离论述。合规映射（SOC 2 / ISO 27001 / GDPR）见理论 (8)。

#### (2) PostgreSQL Row-Level Security（行级安全）官方机制
- **出处**：PostgreSQL 官方文档 *"5.9. Row Security Policies"*（https://www.postgresql.org/docs/current/ddl-rowsecurity.html ），持续适用于 12/13/14/15/16/17 各版本。
- **核心机制（逐条对照本项目）**：
  - **默认拒绝**："If no policy exists for the table, a default-deny policy is used, meaning that no rows are visible or can be modified." —— 本项目所有租户表均 `FORCE ROW LEVEL SECURITY` + `CREATE POLICY`，等价于"有策略时的显式拒绝"。
  - **表所有者绕过**："The table's owner is typically not subject to row security policies." 但 "a table owner can choose to be subject to row security with `ALTER TABLE ... FORCE ROW LEVEL SECURITY`"。—— 本项目用 `FORCE` 正是堵住 owner 绕过；且 `03_platform_roles.sql` 中 `app_agent` 角色**非表 owner、且 `NOBYPASSRLS`**（见 4.2 D-BYPASS）。
  - **BYPASSRLS 角色绕过**："Superusers and roles with the `BYPASSRLS` attribute always bypass the row security system." —— 本项目的 `platform_ops` 角色刻意设为 `BYPASSRLS`，专门用于平台级发布（见 4.2 D-BYPASS），是双刃。
  - **整表操作不受 RLS 约束**："Operations that apply to the whole table, such as `TRUNCATE` and `REFERENCES`, are not subject to row security." —— 这是 RLS 的固有盲区，本平台靠"无物理删除端点"（铁律 8）+ 应用层纪律规避（见 5.3）。
  - **GUC 读取**：策略表达式用 `current_setting('app.tenant_id')`（本项目 `current_tenant_id()` 封装），"evaluated for each row prior to any conditions… Rows for which the expression does not return true will not be processed." —— 未设置时返回 NULL（本项目用 `NULLIF(...,'')`），所有策略 `tenant_id = NULL` 恒假 → **0 行**。
- **与本维度的关系**：本平台的整个 L3 隔离就是 PostgreSQL RLS 的工程化落地，上述每一条官方语义都对应一个具体设计决策。

#### (3) Zero Trust（零信任）
- **出处**：Rose, Borchert, Mitchell, Connelly, *"Zero Trust Architecture"*, **NIST Special Publication 800-207**, NIST, 2020（https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-207.pdf ）。
- **定义**："Zero trust assumes there is no implicit trust granted to assets or user accounts based solely on their physical or network location." 认证与授权是建立会话前**离散执行**的函数；保护对象是**资源**而非网络段。
- **与本维度的关系**：多租户隔离是 Zero Trust 在"数据资源"层面的具体实现——不存在"因为他进了内网/用了同一个数据库连接就可信"。本平台的 `TenantContext`（仅从可信认证推导、客户端 tenantId 不信）、执行时重新授权、默认拒绝，都是 ZT 原则的操作化。

#### (4) 最小权限 / 纵深防御 / fail-closed vs fail-open
- **出处**：Saltzer & Schroeder, *"The Protection of Information in Computer Systems"*, ACM Computing Surveys, 1975（八大设计原则之首即 **Least Privilege**）；OWASP *Authorization Cheat Sheet*（https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html ）明确："**Deny by default**: access should require an explicit permit, not the absence of a deny" 与 "Check on every request"。NIST SP 800-53 Rev.5 将 Least Privilege（AC-6）、Separation of Duties（AC-5）列为访问控制族。
- **定义**：
  - **最小权限**：主体仅持有完成任务所需的最小权限集合。
  - **纵深防御（Defense in Depth）**：多层独立控制互补，任一层失效不导致整体失守。
  - **fail-closed vs fail-open**：判定系统/授权在"不确定"时应拒绝（closed）而非放行（open）。
- **与本维度的关系**：本平台"RLS（数据层）+ 应用层 Gate（执行时重新授权）+ 复合外键（完整性层）"三层即纵深防御；"未绑 GUC 返回 0 行"即 fail-closed；`ScopedDataAccess` 对无规则资源返 `Deny(NO_RULE)`（fail-closed，见 `AuthzShadowPolicyDefaults`）。

#### (5) ABAC / RBAC / ReBAC 谱系
- **出处**：
  - **RBAC**：Ferraiolo & Kuhn, *"Role-Based Access Control"*, NIST, 1992；统一为 **NIST RBAC**，2004 采纳为美国国家标准 **ANSI/INCITS 359-2004**（2012 修订 359-2012）。
  - **ABAC**：NIST **SP 800-162** *"Guide to Attribute Based Access Control (ABAC) Definition and Considerations"*, 2014。
  - **ReBAC**：Google *"Zanzibar: Google's Consistent, Global Authorization System"*（Pang et al., 2019, USENIX ATC）。
- **定义**：RBAC 把权限分组到角色、角色赋给用户（按 job function）；ABAC 把决策写成"主体/资源/环境属性"的规则（如"EU 区经理可在工作时段审批 <5000€ 费用"）；ReBAC 由主体与资源间关系图决定（Google Drive 式"共享给"）。
- **与本维度的关系**：本平台的 `AuthorizationService.Roles`（TENANT_ADMIN/AGENT_AUTHOR/APPROVER/…）是 **RBAC** 基底；`Actions` 的极细粒度（run:create/tool:invoke/agent:delegate…）是把 RBAC 推到接近 ABAC 的资源级；`isAudienceOnly` 收窄受众到 `requester_id=本人` 是 ReBAC 式的"关系限定"。影子对照的 `ScopeFilter`（TenantOnly/None/Unrestricted/TenantWithShared）是 ABAC 式的策略求解。

#### (6) Policy-as-Code / OPA（策略即代码）
- **出处**：Open Policy Agent（CNCF 毕业项目）官方文档（https://www.openpolicyagent.org/docs/latest/ ），其 Rego 语言将 RBAC/ABAC/ReBAC 统一表达为可版本化、可测试的声明式策略，决策与执行解耦（应用向引擎查询 yes/no）。
- **定义**：策略从应用代码中外置，以代码形态存在、可评审、可单测、可纳入 CI 门禁。
- **与本维度的关系**：本平台虽未引入 OPA 引擎，但其 `AuthzShadowPolicyDefaults`（内置 `PolicyRule` 集，RETRIEVE+TENANT+TENANT_ONLY）与 `RuleBasedPolicyEngine` 是**策略即代码 + 影子双跑**的同源思路；`ShadowPolicyCoverageTest` 扫源码钉死"资源类型必须有规则"即"策略即代码 + CI 门禁"的工程化（见 4.4 D-SHADOW）。

#### (7) Shadow Mode / Dark Launch / 双跑比对（灰度方法论）
- **出处**：属分布式系统与发布工程的成熟范式。"dark launch" 由 Facebook/Google 等大规模部署实践普及（代码与真实流量双跑、仅观测不生效）；熔断/灰度评估文献中常见 "shadow / canary / incremental rollout" 三分。可参照 *"Continuous Delivery"*（Humble & Farley, 2010）的并行运行与"可观测发布"论述。
- **定义**：新逻辑（新策略/新隔离裁决）与旧逻辑同时运行，新逻辑只记录判定差异、不改变结果；待差异稳定后再翻转"阻断开关"。
- **与本维度的关系**：本平台的 `AGENT_AUTHZ_SHADOW_ENABLED` + `AuthzShadowHooks` + `AuthzShadowReporter` 正是此范式在**权限/隔离体系迁移**上的落地——应用层 Gate 算出的 `ScopeFilter` 与 RLS 基线双跑比对（见 4.4 D-SHADOW），是本项目**独有的、可复用**方法论。

#### (8) 合规映射：SOC 2 / ISO 27001 / GDPR 的隔离控制
- **出处**：
  - **SOC 2**（AICPA）：Trust Services Criteria 的 **Security (Common Criteria) CC6.1 / CC6.3** 要求"实体实施逻辑访问控制以限制对信息资产的访问""对具有访问权的用户进行授权"。多租户隔离是 CC6 的核心技术证据。
  - **ISO/IEC 27001:2022**：控制项 **A.8（访问控制）** 与 **A.5（组织控制）** 中的职责分离、访问限制；Annex A 明确要求"多租户环境下的隔离"。
  - **GDPR**：**第 25 条（数据保护设计 by design and by default）** 与 **第 32 条（处理安全）** 要求技术措施确保"未经授权者无法访问个人数据"——默认拒绝的 RLS 正是 Art.25/32 的对应控制。
- **与本维度的关系**：本平台的"默认拒绝 RLS + 不可变 `authz_decision_log` + 复合外键完整性"是 SOC 2 CC6 / ISO 27001 A.8 / GDPR Art.25&32 的可审计技术证据（见 5.2、8.2）。

### 2.2 理论给出的「设计张力」（trade-off）清单

|---|---|---|---|---|

### 2.3 业界公认的反模式（anti-pattern）清单及判别方式

1. **应用层单点隔离（"trust-the-WHERE"）**：隔离只靠每个查询手写的 `WHERE tenant_id=?`。判别：是否存在"漏写谓词即越权"的全局保障——若无 RLS，则为该反模式。本项目用 RLS 规避。
2. **连接级串租户（stale GUC）**：连接池复用未重置租户上下文，下一请求继承上一租户身份。判别：看 `set_config` 是否在事务内绑定且事务结束自动恢复。本项目 `TenantSessionBinder` 用 `set_config(..., true)`（事务局部）+ 取连接时无条件重置（见 4.1）。
3. **客户端传入 tenantId 当授权依据**：接口参数带 `tenantId` 并直接用于查询。判别：是否从 JWT/会话声明推导租户。本项目 `TenantContext` 明确"客户端传入的 tenant_id 不作为授权依据"（TenantContext.java:11-17）。
4. **默认放行 + 黑名单**：未命中拒绝规则即允许跨租户。判别：默认语义是 allow 还是 deny。本项目 `current_tenant_id()` 返回 NULL 即 0 行（deny by default）。
5. **用超级用户/owner 跑应用查询**：应用连接带 BYPASSRLS 或表 owner，RLS 形同虚设。判别：应用角色是否 `NOBYPASSRLS` 且非 owner。本项目 `app_agent` 双满足（03_platform_roles.sql:98/102）。
6. **整表操作绕过 RLS**：用 `TRUNCATE`/外键 `REFERENCES` 做"清理/级联"实则跨租户。判别：是否有"无物理删除端点"纪律。本项目铁律 8（无物理删除端点）。

### 2.4 深度补充：两个新理论锚点（均经官方出处核实，不与 2.1 八锚点重复）

> 本节为本次「13 份报告更详细补充」新增，不改写 2.1 已有八个锚点。选择 **AWS SaaS Lens** 与 **Google Zanzibar 一致性模型** 的原因：前者回答本维度元问题「**隔离强度与成本/noisy neighbor 如何取舍**」（正好补强 2.2 表 T4、5.5 金融合规域只给了结论未给权威框架的部分）；后者回答「**授权判定如何在频繁变更下仍保持因果一致**」——这是 2.1(5) 把 Zanzibar 仅列为 ReBAC 谱系时**未展开的一致性维度**，也是本平台 `authzVersion` 撤销即时生效理论上的对标物。二者是对既有锚点的**补强与深化**，不是替换。

#### (9) AWS Well-Architected SaaS Lens：隔离档位、成本与 noisy neighbor 的权威框架

- **出处（本次经 WebFetch 官方页核实）**：Amazon Web Services, *"SaaS Lens — AWS Well-Architected Framework"*（发布日期 2023-04-04），https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/ 。官方原文：「This Lens … focus on how to design, deploy, and architect your multi-tenant software as a service (SaaS) application workloads in the AWS Cloud」；并明确其覆盖「general design principles as well as specific best practices … in five conceptual areas … the pillars of the Well-Architected Framework」（即安全/可靠性/性能/成本/卓越运营五支柱）。
- **核心主张（忠于出处）**：多租户 SaaS 的隔离不是单点技术，而是贯穿五支柱的**架构决策**——隔离档位（silo 独立资源 vs pool 共享资源）直接决定：爆炸半径（blast radius，一租户故障/攻击的影响面）、noisy neighbor（共享资源的相互干扰）、单租户成本与可容纳租户密度、以及按租户计量/备份/合规的复杂度。AWS 在 SaaS Lens 中把这些作为可评审的设计维度，而非"有无 RLS"的二元判断。
- **对本维度的解释力**：2.2 表 T4「隔离强度 vs 成本」与 5.5「金融/支付多法人隔离要求」此前只给了本平台选型结论。SaaS Lens 提供了把结论系统化的框架：本平台的 **L3 共享 schema + RLS** 对应 "pooled 资源 + 逻辑隔离"档——成本/密度最优，但 noisy neighbor 与爆炸半径靠 RLS 的**逻辑**边界而非物理边界收敛；改进项 I-3（租户级连接池→独立 schema→独立库）正是一条沿 AWS "silo 化程度递增"轴线的**按需升级**路径。这解释了为什么 I-3 被设计成"默认 RLS 档 + 显式配置升级"而非一刀切：五支柱的成本权衡使"处处 L4"不可接受。
- **边界（诚实）**：SaaS Lens 是**架构评审框架**（问"你有没有考虑隔离/成本"），不是 RLS 规格说明，也不裁决本平台"默认拒绝"的正确性；它把隔离强度与成本都视为**权衡项**而非"越强越好"。本次抓取到的是 Lens 总览页（五支柱与多租户定位已核实），其"tenant isolation"具体条目（silo/pool 术语）属于该 Lens 安全支柱的主题，但**本次未逐条抓取子页原文**——故本报告只引用已抓取到的定位性原文，标注意见为框架级出处而非逐字规格。

#### (10) Google Zanzibar 的一致性模型：external consistency 与因果顺序

- **出处（本次经 WebFetch 官方页核实）**：Google Research, *"Zanzibar: Google's Consistent, Global Authorization System"*（Pang et al., USENIX ATC 2019），https://research.google/pubs/zanzibar-googles-consistent-global-authorization-system/ 。官方摘要原文：「Zanzibar provides a uniform data model and configuration language for expressing a wide range of access control policies … including Calendar, Cloud, Drive, Maps, Photos, and YouTube」；关键一致性原文：「Its authorization decisions respect causal ordering of user actions and thus provide external consistency amid changes to access control lists and object contents」；规模数据原文：「scales to trillions of access control lists and millions of authorization requests per second」、p95「< 10 milliseconds」、三年可用性「> 99.999%」。
- **核心主张（忠于原文）**：Zanzibar 把授权做成全局一致的系统，**授权判定尊重用户动作的因果顺序**（causal ordering），从而在 ACL 与对象内容频繁变更时仍提供 external consistency——即"先授权、后变更"的顺序不会被分布式延迟颠倒成"用旧权限放行新变更"。注意：该摘要页**未直接使用 "ReBAC" 术语或 `(subject, relation, object)` 三元组字面**，这些是 2.1(5) 与业界对 Zanzibar 的通行归纳；本报告此处只引用摘要页明确写出的**一致性**与统一数据模型表述，不臆造三元组细节。
- **对本维度的解释力**：本平台的 `TenantContext.authzVersion`（`TenantContext.java:24`，撤销授权后递增）＋ `AuthorizationService.currentAuthzVersion`（`AuthorizationService.java:51`）＋ 执行时重新授权（`:12-19`）解决的正是 Zanzibar 所述的 same class of problem：**在途请求不能携带陈旧授权**——学生退课/账号封禁后，旧 Run 的执行不能被旧权限放行。Zanzibar 用"因果顺序 + 全局一致存储"在万亿级 ACL 上保证；本平台用"每次敏感动作重判当前 authzVersion + fail-closed"在单库规模上达到等价的**因果正确性**（撤销即时生效），这是理论预测与实现一致的有力佐证。
- **边界（诚实）**：Zanzibar 是**集中式全局授权服务**（独立集群、统一数据模型），本平台**没有**独立授权集群——`RoleBasedAuthorizationService` 是应用层 Gate，一致性靠"重判 + 版本号"而非"全局因果序存储"。因此本平台获得的是**撤销即时生效的因果正确性**，而非 Zanzibar 那种跨服务、跨地域的 external consistency 保证；在"跨越多服务的授权原子性"上二者不在一个量级。这条边界正是 I-4（跨租户访问证明）仍需结构化的理论原因。

#### 2.4.1 新锚点 → 本平台代码锚点映射（承接 2.1.11）

| 理论 | 核心主张（已核实原文的要点） | 本平台对应实现（锚点，本次复核） | 是继承还是背离 |
|---|---|---|---|
| AWS SaaS Lens（AWS 官方，2023） | 多租户隔离是五支柱架构决策；silo/pool 档位决定爆炸半径、noisy neighbor、成本与密度 | L3 共享 schema + RLS（1.2 表）；I-3 三级隔离演进（pooled→dedicated connection→schema→DB） | **继承权衡框架**（默认 pooled + 逻辑边界，按需 silo 化） |
| Zanzibar 一致性（Google Research / USENIX ATC'19） | 授权判定尊重因果顺序，ACL 变更下提供 external consistency | `authzVersion`（`TenantContext.java:24`）+ `currentAuthzVersion`（`AuthorizationService.java:51`）+ 执行时重新授权（`:12-19`） | **部分继承**（因果正确性=撤销即时生效；无全局一致授权集群） |

> 结论：SaaS Lens 与 Zanzibar 一致性模型补齐了本维度「**为什么这样取舍**」与「**为什么撤销能即时生效**」的理论根系，同时其边界也精确划线——本平台是「**pooled 档 + 逻辑强隔离 + 单库因果正确性**」的工程实现，不是物理 silo，也不是全局一致授权服务。这个判断比 2.2 表 T4 与 2.1(5) 的"领先"结论更精确，也是对第五、六章判定应有的理论克制。

### 3.1 OpenAI Agents SDK
- **官方定位与机制**：极简原语 `Agent/Runner/Handoffs/Guardrails/Sessions/Tracing`，**无显式图、无内建多租户隔离**。隔离完全交给宿主应用的 `thread_id`/用户作用域。

#### 3.9.1 PostgreSQL Row-Level Security（本平台的"引擎母体"）

- **它怎么做**：在表上 `ENABLE ROW LEVEL SECURITY`，用 `CREATE POLICY ... USING/ WITH CHECK` 写行过滤；无策略时默认拒绝（"If no policy exists for the table, a default-deny policy is used"）；表 owner 默认绕过，除非 `FORCE ROW LEVEL SECURITY`；超管与 `BYPASSRLS` 角色永远绕过（"Superusers and roles with the BYPASSRLS attribute always bypass"）；策略表达式逐行求值（`current_setting('app.tenant_id')` 即本平台的 GUC 路径）。
- **关键取舍**：把隔离下沉到存储引擎，应用 bug 绕不过；代价是必须正确传播身份与租户上下文（Azure 指南也强调这点），且 `TRUNCATE`/`REFERENCES` 与引用完整性检查不受 RLS 约束。
- **对我们意味着什么**：本平台的 L3 就是 PG RLS 的工程化封装——`current_tenant_id()`（`01_platform_ddl.sql:298-309`，本次复核）、44 表 FORCE + 52 策略、`app_agent` NOBYPASSRLS 全部逐条对应上述官方语义。**这不是竞品而是我们的地基**：所有"领先"判定都建立在 PG RLS 的官方保证上，也继承其盲区（TRUNCATE、BYPASSRLS 双刃）。
- **官方来源**：https://www.postgresql.org/docs/current/ddl-rowsecurity.html ；`set_config` 事务局部语义 https://www.postgresql.org/docs/current/functions-admin.html （"If is_local is true, the new value will only apply during the current transaction"）。

#### 3.9.2 Supabase RLS（托管 Postgres + PostgREST 的 RLS 即服务）

- **它怎么做**：把 PG RLS 做成托管平台的默认安全层——"Enable RLS on every table in an exposed schema"；策略用 `using`/`with check`（SELECT 用 using、INSERT 用 with check、UPDATE 两者结合）；用户隔离用 `auth.uid() = user_id`，租户/团队隔离用 `auth.jwt() -> 'app_metadata' -> 'teams'`；未认证时 `auth.uid()` 返 NULL，"null = user_id is always false in SQL"（与本平台 `current_tenant_id()` 未绑返 NULL 同构的 fail-closed）。
- **关键取舍**：RLS + API 自动接管，前端直连也安全（"no data is accessible through the API … until you create policies"）；代价是 JWT claim 可能陈旧（"a JWT is not always up-to-date … until the user's JWT is refreshed"）——与本平台 `authzVersion` 撤销即时生效要解决的陈旧问题同源。
- **对我们意味着什么**：Supabase 证明"PG RLS + 身份传播"是可产品化的主流形态，本平台 L3 选型正确；但 Supabase 用 `auth.jwt()` 传租户（陈旧窗口由 JWT 刷新收敛），本平台用事务局部 GUC + 执行时重判（撤销即时生效）——在**撤销即时性**上本平台更严。JWT 陈旧窗口正对应我们 I-2 观察期要防的"陈旧授权"。
- **官方来源**：https://supabase.com/docs/guides/database/postgres/row-level-security （本次 WebFetch 核实：RLS 启用、`auth.uid`/`auth.jwt`、NULL fail-closed、JWT 陈旧）；诚实标注：该页**未出现 `current_setting` 字样**，"团队维度 scoping"以 `auth.jwt()` 为准，非 GUC。

#### 3.9.3 Google Zanzibar（ReBAC 全局授权系统的理论源头）

- **它怎么做**：全局 ACL 存储与评估系统，"uniform data model and configuration language"表达多种访问策略；授权判定尊重因果顺序（causal ordering）→ external consistency；规模万亿级 ACL、百万 QPS、p95<10ms、可用性>99.999%（全部官方摘要原文，见 2.4(10)）。
- **关键取舍**：把授权做成独立、全局一致的专用服务，换最强一致性/规模；代价是独立集群运维与模型建模复杂度。
- **对我们意味着什么**：Zanzibar 是 2.1(5) ReBAC 与本平台 `isAudienceOnly`（受众收窄到 `requester_id`，`AuthorizationService.java:220-246`，本次复核）的理论母体；其"因果一致"正是本平台 `authzVersion` 对标物（2.4(10)）。差异：Zanzibar 是独立集群，本平台是应用内 Gate + DB RLS，**没有**全局授权服务——这是规模定位差异，不是能力缺失。
- **官方来源**：https://research.google/pubs/zanzibar-googles-consistent-global-authorization-system/ （本次核实摘要原文）；诚实标注：摘要页**未直接出现**"ReBAC"或三元组字面，本报告只引用其明确写出的"uniform data model / external consistency / 规模数据"。

#### 3.9.4 OpenFGA（CNCF 的 Zanzibar 开源实现）

- **它怎么做**：CNCF 所有的开源授权系统，"Inspired by Google's Zanzibar … relies on Relationship-Based Access Control"；可表达 RBAC/ABAC；策略外置出应用代码（"Move authorization logic outside of application code"）；支持多 store、Postgres/MySQL/SQLite 后端、HTTP/gRPC API、OTel。
- **关键取舍**：把授权决策集中化、可审计、可测试；代价是引入独立服务/数据存储与关系建模心智。
- **对我们意味着什么**：OpenFGA 与本平台 `RuleBasedPolicyEngine`/`AuthzShadowPolicyDefaults`（策略即代码 + 影子双跑）是同源思路的不同落地——OpenFGA 用独立 store，本平台把策略内置在进程 + DB。启发：I-4 若要做跨租户访问证明，可参考 OpenFGA"集中审计日志"的产出形态。
- **官方来源**：https://openfga.dev/docs/fga （本次 WebFetch 核实；诚实标注：`https://openfga.dev/docs/intro` 返回 404，正确入口为 `/docs/fga`）。

#### 3.9.5 Auth0 FGA / Okta FGA（Zanzibar 的商业托管形态）

- **它怎么做**：Okta 旗下 Auth0 的 Fine-Grained Authorization，"built on OpenFGA, a CNCF incubation project"；"relationship-based platform"保护多租户 B2B API；官方明言"enforces strict data isolation and least-privilege access for humans, agents, and MCP clients"、单一不可变审计轨迹满足 GDPR/HIPAA。Okta 官方博客把它定位为"Auth0 FGA, built on Google's Zanzibar model, enforces relationship-based access at every call"。
- **关键取舍**：托管 FGA 换零自建授权集群 + 企业级 SLA（Tier-Zero 99.99%）；代价是厂商绑定与按调用计费。
- **对我们意味着什么**：证明"关系型授权 + 多租户数据隔离 + 不可变审计"是商业基础设施的标准形态——与本平台 `authz_decision_log` 只增不改 + `isAudienceOnly` 受众收窄方向一致。差异：FGA 在**授权服务层**做隔离，本平台在**数据存储层**（RLS）做硬边界 + 应用层 Gate 双保险，纵深不同。
- **官方来源**：https://auth0.com/fine-grained-authorization ；https://docs.fga.dev/ （本次核实）；https://okta.com/blog/ai/ai-security-iam-at-agent-velocity/ （Okta 官方博客核实 Zanzibar-based 表述）。诚实标注：`developer.okta.com/docs/guides/fine-grained-authorization/main/` 返回 404，Okta FGA 实为 Auth0 FGA，未单独维护 Okta 域文档。

#### 3.9.6 Cerbos（策略外置的 PDP，YAML 策略 + 合规审计）

- **它怎么做**："authorization management platform … works alongside your application to produce fine-grained, contextual access decisions based on policies"；核心是开源无状态 PDP（policy decision point），策略用 YAML 编写、集中版本化/测试/分发（Cerbos Hub），并聚合决策日志满足 "SOC 2, ISO 27001, HIPAA, PCI DSS, and GDPR audit requirements"。
- **关键取舍**：策略即代码 + 独立 PDP 换可审计/可测试/免重启更新；代价是引入 PDP 组件与策略下发链路。
- **对我们意味着什么**：Cerbos Hub 的"策略变更自动测试并推送 + 决策日志聚合"与本平台 `ShadowPolicyCoverageTest`（新资源类型不登记即红）+ `authz_decision_log` 是同一治理思想的两个形态。启发：I-2 的影子出口门禁可借鉴 Cerbos"策略变更即测试"的 CI 集成方式，把 `rlsDependent` 归零纳入策略合并门禁。
- **官方来源**：https://docs.cerbos.dev/cerbos/latest/index.html （本次 WebFetch 核实：PDP/Hub/Synapse 四组件、YAML 策略、合规审计表述）。

#### 3.9.7 Permify（Zanzibar 启发的开源细粒度授权服务）

- **它怎么做**："open-source authorization service … inspired by Google's consistent, global authorization system, Google Zanzibar"；以 Schema（兼容 RBAC/ReBAC/ABAC 的 DSL）建模、关系形式存授权数据、API 做访问检查；明确支持"Set Custom Authorization For Your Tenants … isolated authorization logic and custom permissions for your vendors/organizations (tenants)"。
- **关键取舍**：开源可自建 + 多租户隔离授权逻辑，换灵活性；代价是自运维 Permission DB + PDP。
- **对我们意味着什么**：Permify 的"每租户隔离授权逻辑"印证了本平台 `TENANT_ONLY` 策略 + 复合外键 `(tenant_id, xxx)` 的方向；其 Schema 兼容 RBAC/ABAC/ReBAC 的谱系对应本平台 RBAC 基底 + `isAudienceOnly` 关系限定。差异：Permify 把授权数据独立成库，本平台授权与业务同库（RLS 强制 + 复合外键兜底），一致性模型不同。
- **官方来源**：https://permify.co/docs/ （本次 WebFetch 命中后重定向到 https://fusionauth.io/permify-docs/permify-overview/intro ，该页核实上述原文；Permify 已被 FusionAuth 收购、文档迁移，两个域名均在本次访问链路中）。

### 3.10 竞品归类更新（纳入数据/授权线 7 个后）

把 3.1–3.9 全部竞品按"隔离强制层"重新拉平，得到五类：

| 类别 | 代表 | 隔离强制层 | 默认语义 | 与 L3 关系 |
|---|---|---|---|---|
| L1 应用/会话作用域 | OpenAI/Anthropic/LangGraph/ADK/AutoGen/CrewAI(社区) | 进程内 thread/user/session | 取决于代码 | 无 RLS，弱于本平台 |
| L2 框架内建身份 | Agno | 框架授权中间件（进程内） | scope 控制 | 内建认证领先，裁决未下沉 |
| **L2′ 专用授权服务** | Zanzibar/OpenFGA/Auth0 FGA/Cerbos/Permify | 独立授权服务（策略层） | deny by default | 授权外置但**不管存储行** |
| **L3 数据库 RLS** | PostgreSQL RLS、Supabase RLS、**本平台** | 存储引擎（逐行） | **默认拒绝（0 行）** | 本平台 = PG RLS + 应用 Gate 双保险 |
| L3 演进 L4 物理隔离 | 本平台 I-3（规划） | 独立连接/schema/库 | 默认拒绝 | 强合规按需升级 |

**关键结论（诚实修正）**：新增竞品揭示了此前 3.8 归类遗漏的一个大类——**专用授权服务（L2′）**。它们（Zanzibar 系）在"授权策略的表达力/集中审计/一致性"上强于本平台，但**都在策略层工作、不强制存储行隔离**：即便判定为拒绝，若应用 bug 直接查询数据库，它们管不到（这正是 RLS 的用武之地）。本平台与之是**互补而非同类**：L2′ 解决"能不能做"，L3 RLS 解决"数据层读不读得到"。因此"本平台领先"的精确表述应是：**唯一把行级隔离下沉到存储引擎、并以默认拒绝 + 应用层 Gate 双保险强制的方案**；在"授权策略表达力/集中审计"维度，Zanzibar 系反而领先，本平台 I-4 正是对此的补足。

## 四、我们的实现（源码级解剖）

### 4.1 架构与数据流（关键组件、调用链、数据落点）

本平台的多租户隔离是**三层叠加**，从外到内：

```
① 认证推导层  TenantContext(tenantId, principalId, roles, authzVersion)
              ↑ 仅从 JWT/会话可信声明推导（TenantContext.java:11-17）
              │
② 会话绑定层  TenantSessionBinder.bind(conn, ctx)
              → set_config('app.tenant_id', ctx.tenantId(), true)  （事务局部）
              ↑ 取连接时无条件重置，防串租户（TenantSessionBinder.java:42-82）
              │
③ 数据层强制  PostgreSQL RLS：current_tenant_id() = NULLIF(current_setting('app.tenant_id',TRUE),'')::UUID
              → 44 张表 FORCE RLS，策略 USING(tenant_id=current_tenant_id()) WITH CHECK(同)
              → 未绑 GUC → current_tenant_id()=NULL → tenant_id=NULL 恒假 → 0 行（默认拒绝）
              │
④ 应用层 Gate RoleBasedAuthorizationService.isAuthorized(ctx, action, resourceId)
              → 执行时重新授权（每次敏感动作前），authzVersion 撤销即时失效
              → 落 authz_decision_log（只增不改、不挂 RLS、隔离靠授权）
              │
⑤ 完整性层   复合外键 UNIQUE(tenant_id, xxx)：agent(tenant_id,agent_id)、
              agent_name_per_tenant(tenant_id,name)、run_message(tenant_id,run_id,idem_key)…
              → 引用完整性层面的租户一致（不变式 6）
```

**调用链（一次租户域内读）**：
1. 认证过滤器从 JWT 抽取 `tenantId/principalId/roles/authzVersion` → 构造不可变 `TenantContext`（record，创建即校验非空，TenantContext.java:26-44）。
2. 进入事务前，`TenantSessionBinder.bind(conn, ctx)` 在**该连接、事务内、首条业务 SQL 前**绑定 GUC（TenantSessionBinder.java:60-69）。`set_config(..., true)` 的 `is_local=true` 使变量在事务结束/回滚时自动恢复，杜绝串租户。
3. 业务 SQL（`SELECT ... FROM agent WHERE ...`）经 RLS 策略 `agent_tenant_isolation` 注入 `tenant_id = current_tenant_id()`，仅返回本租户行。
4. 应用层 `RoleBasedAuthorizationService` 在返回/操作前再判一次（执行时重新授权），结果写 `authz_decision_log`。
5. 复合外键保证"即便应用层写错父 id"，数据库也会因 `(tenant_id, 父id)` 不匹配而拒写。

#### 4.1.1 `current_tenant_id()` 与"默认拒绝"的精确语义

```sql
-- 01_platform_ddl.sql（current_tenant_id 函数，约 286-298 行）
CREATE FUNCTION public.current_tenant_id() RETURNS uuid
    LANGUAGE sql STABLE
    AS $$ SELECT NULLIF(current_setting('app.tenant_id', TRUE), '')::UUID; $$;
COMMENT ON FUNCTION public.current_tenant_id() IS
  '返回当前事务的租户上下文。未设置 app.tenant_id 时返回 NULL，所有 RLS 策略将拒绝访问——默认拒绝，符合 fail-closed';
```
- `current_setting('app.tenant_id', TRUE)` 的第二个参数 `TRUE` = **missing_ok**，未设置时不报错而返回 NULL。
- `NULLIF(..., '')` 把空串转 NULL（与 `TenantSessionBinder.clear()` 置空串对应）。
- `::UUID` 转换：若 GUC 被恶意设为非法串，转换抛错（fail-closed，而非静默放行）。
- 任一租户表策略 `tenant_id = current_tenant_id()`：当函数为 NULL，等式恒假 → **0 行**。这正是 fail-closed 在 SQL 层的体现。

#### 4.1.2 RLS 策略模板（全 44 表一致）

```sql
-- 例：run_tenant_isolation（约 5830 行附近）
CREATE POLICY run_tenant_isolation ON public.run
    USING ((tenant_id = public.current_tenant_id()))
    WITH CHECK ((tenant_id = public.current_tenant_id()));
```
- `USING` 约束"读到的行"，`WITH CHECK` 约束"能写入/修改的行"——读写双方向隔离。
- 44 张表（实测 `FORCE ROW LEVEL SECURITY` 计数）统一此模板；`CREATE POLICY` 共 52 条（部分表因命令分拆有 2 条策略）。

#### 4.1.3 全局表与平台域表的"有意不挂 RLS"

- `public.tenant`（约 2949 行注释）："本表为全局表，不启用 RLS（租户自身即隔离单元）"。它是隔离的**根目录**，本身不可被租户作用域切分。
- `platform.authz_decision_log`（约 988 行注释）："只增不改：它是『判定发生过』的举证材料…不挂 RLS，隔离靠授权（app_agent 仅 INSERT，读走 platform_ops）"。跨租户隔离靠**授权**而非行策略——`app_agent` 只有 INSERT，读走 `platform_ops`（BYPASSRLS 运维通道）。
- `platform.review_task` 等同理：跨租户隔离靠授权，应用角色只有受限写。

#### 4.1.4 复合外键族（完整性层）

不变式 6（设计总览:253）："租户边界 = RLS + `(tenant_id, 父id)` 复合外键双保险"。实测 `01_platform_ddl.sql` 中存在一族此类约束：

| `agent_name_per_tenant` | `UNIQUE (tenant_id, name)` | 3440 |
| `agent_version_unique` | `UNIQUE (tenant_id, agent_id, version_number)` | 3480 |
| `agent_version_tenant_version_unique` | `UNIQUE (tenant_id, version_id)` | 3472 |

### 4.2 关键设计决策逐条剖析（决策 → 为什么 → 代价 → 证据锚点）

| # | 决策 | 为什么 | 代价 | 证据锚点 |
|---|---|---|---|---|
| D-GUC | **GUC `app.tenant_id` + `current_tenant_id()` 函数** | 把租户上下文从"应用变量"下沉为"数据库会话变量"，使 RLS 策略能无侵入地对所有 SQL 生效 | 部署必须正确绑 GUC；绑错=假绿/假失败（铁律 1） | `01_platform_ddl.sql:286-298`；`TenantSessionBinder.java:40-47` |
| D-FORCE | **44 张表 `FORCE ROW LEVEL SECURITY`** | 堵住表 owner 绕过（PostgreSQL 默认 owner 不受 RLS 约束） | 任何表结构改动需同步策略；运维需懂 RLS | `01_platform_ddl.sql`（FORCE ×44） |
| D-DENY | **默认拒绝（未绑 GUC → 0 行）** | fail-closed：漏绑比漏写更可见（至少不越权） | 0 行可能"假绿"——业务以为成功实则空（见 5.3/7.1） | `01_platform_ddl.sql:286-298` 注释 |
| D-RESET | **`set_config(..., true)` 事务局部 + 取连接无条件重置** | 防连接池复用导致串租户（比不设更危险的静默越权） | 每条 SQL 前需确保已绑（由框架保证） | `TenantSessionBinder.java:42-82` |

### 4.4 我们独有的设计（差异化设计）

1. **三层隔离（L3 数据层 + L1 应用层 Gate + 完整性层）**：绝大多数竞品只有"应用层作用域"或"框架内建身份"。本平台把 RLS（数据层强制、默认拒绝）作为**硬边界**，应用层显式 Gate（执行时重新授权）作为**独立第二层**，复合外键作为**完整性兜底**——三层互不替代（维度 7 不变式 4：「读不到=拒绝」而非跳过）。这是与所有竞品（含 Agno）的本质差异。

2. **默认拒绝 vs 默认放行（fail-closed）**：当 GUC 未绑，`current_tenant_id()` 返 NULL → 所有策略 `tenant_id=NULL` 恒假 → **0 行而非全量**。理论后果见第五章 5.3：安全但可能"假绿/假失败"，是真实运维痛点，必须用第七章改进点 1 化解。

3. **BYPASSRLS 的双刃（D-BYPASS）**：`platform_ops` 角色 `BYPASSRLS` 让平台运维可跨租户发布（写 `cap_config_release` 的 PLATFORM 行），但**刻意与 `app_agent`（NOBYPASSRLS）分两套凭据、两条发布通道**——既给运维钥匙，又把"谁是平台运维"在数据库层显式区分。`03_platform_roles.sql:175` 明确"app_agent：rolsuper 与 rolbypassrls **必须**都是 f"。双刃在于：若误把应用角色设为 BYPASSRLS，RLS 立即形同虚设。

4. **影子对照作为「权限体系迁移的灰度方法论」（D-SHADOW）**：`AGENT_AUTHZ_SHADOW_ENABLED` + `AuthzShadowHooks` 把"应用层 Gate 算出的 `ScopeFilter`"与"RLS/基线的实际返回"**双跑比对**。这是本项目**独有且可复用**的方法论——任何"把隔离从应用层下沉到 RLS、或反过来"的迁移，都可用影子期观测差异、再翻转 `block-on-violation` 阻断（详见 4.4.4 与第七章改进点 2）。`AuthzShadowLiveIT.crossTenant_reallyReds`（128-151）更证明该机制"真的能红"，排除"从没跑过"的假 0。

5. **复合外键 `UNIQUE(tenant_id, xxx)` 作为「租户一致性的完整性约束」**：这不是性能索引，而是把"租户边界"写进引用完整性层（不变式 6）。即便 RLS 因 bug/新表漏挂而失效，写入跨租户父 id 也会因 UNIQUE/外键不匹配而失败——把"隔离"从"策略建议"升级为"存储层拒绝"（参见维度 01 的"不变量下沉"同构思想）。

#### 4.4.4 影子对照机制详述（差异化方法论的运作）

- **触发**：`application.yml:154-169` 配置 `shadow.enabled`。默认 `false`（铁律级 fail-closed：不开启则零行为变更）。
- **接线**：仓库在查询路径调用 `AuthzShadowHooks.compare(...)` / `taint(...)`，把 Gate 算出的 `ScopeFilter` 与实际绑定租户、实际行租户比对。三个前置（启用/有 reporter/有 scoped）不满足即完全无副作用。
- **两路信号**：
  - **mismatch**：Gate=None 但查询带租户谓词 / Gate 租户≠查询绑定租户 → 可能越权。P1 仅记录，P2 翻转 `block-on-violation=true` 抛 `AccessDeniedException`。
  - **rlsDependent（关键，仅计数不阻断）**：Gate 要求按租户收口，但本次查询**未带显式租户谓词** → 当前完全靠 RLS 兜底 → **退役 RLS 后即越权**。此信号单独计数（不混入 mismatch），是 P1 期间唯一能产出非平凡信号的量（`AuthzShadowReporter.reportRlsDependent:97-100`，即便 `block-on-violation=true` 也不抛）。
- **覆盖率台账**：`AuthzShadowPolicyDefaults.RESOURCE_TYPES`（46-124）登记已接钩子的资源类型；`ShadowPolicyCoverageTest` 扫源码钉死"新加资源类型不登记即红"；平台级无 `tenant_id` 的表（cap_tool_def 等）刻意不登记、在架构守卫显式豁免（145-148），避免制造恒定假违例。
- **缺口表现实**：`AuthzShadowPolicyDefaults:26-28` 自承存在 **9 张带 `tenant_id` 但无 RLS 策略的缺口表**（D1 基线），其隔离"本来就只靠应用层 WHERE"——这正是 RLS 覆盖并非 100% 的真实边界，必须在缺点（6.2）与改进点（7.2）中诚实呈现。

### 5.2 优势详解（为什么领先，讲清机制）

- **为什么"数据层强制 + 默认拒绝"领先**：竞品的 `thread_id`/`user_id`/`session_id` 作用域是**进程内约定**，漏写/写错即越权，数据库毫不知情。本平台的 RLS 是数据库引擎级强制——即使应用层写出 `SELECT * FROM run`（完全漏写 tenant_id），PostgreSQL 也会因 `run_tenant_isolation` 策略注入 `tenant_id = current_tenant_id()` 而**只返回本租户行**；若 GUC 未绑，则返回 0 行（拒绝）而非全量（放行）。机制上，这是把"隔离 Enforcement"从"每个开发者的自觉"下移到"唯一写入通道的存储引擎"——与维度 01 的"状态机下沉触发器"同构。
- **为什么"三层互不替代"领先**：RLS 解决"读到的行"，Gate 解决"动作是否被授权"（含 `authz_version` 撤销即时失效），复合外键解决"写入的引用完整性"。三层独立意味着任一层 bug 不连累其他层——例如 RLS 漏挂某新表（缺口表），应用层 Gate + 复合外键仍提供两道防线（`AuthzShadowPolicyDefaults:26-28` 揭示的缺口表即此场景：隔离退化为应用层 WHERE，但仍有 Gate+外键）。
- **为什么"复合外键"是理论级优势**：把租户边界写进 `UNIQUE(tenant_id, agent_id)` 等约束，使"跨租户引用"在引用完整性层即被拒。这是把"隔离"从"策略建议"升级为"存储层拒绝"，等价于数据库界的"外键即契约"。

### 5.3 劣势与盲区详解（根因分析）

- **落后 1：认证内建度弱于 Agno（根因=定位取舍，非能力缺失）**。Agno 把 JWT/服务账号/security-key **内建进框架**；本平台的 `TenantContext` 仅从"可信认证声明"推导，**认证颁发本身依赖宿主**。本平台是"生产运行时"，认证由平台/网关负责，agent 运行时只消费已验签身份——属取舍，但若宿主认证薄弱则整链失效。
- **落后 2：无物理隔离选项（根因=成本取舍）**。当前是共享 schema + RLS（L3），未提供每租户独立 schema/库（L4）。金融/医疗强合规租户（如银行多法人、多账套）可能要求物理隔离——本平台暂不支撑，需改进点 3 演进。
- **落后 3（最关键的真实痛点）：默认拒绝的"双面性——静默 0 行"**。未绑 GUC 时 RLS 返回 0 行而非报错，业务侧表现为"查不到/写不进"却**无任何异常**——即"假绿"（以为成功实则空）或"假失败"（以为是业务无数据实则隔离误伤）。这是 fail-closed 的固有代价：**安全但不可诊断**。根因是 RLS 的拒绝是"静默过滤"而非"显式拒绝信号"，PostgreSQL 不告知"本应返回 N 行但被 RLS 滤掉"。须用第七章改进点 1（启动自检 + 运行时哨兵 + 指标）化解。
- **落后 4：RLS 覆盖非 100%（9 张缺口表）**。实测存在带 `tenant_id` 但无 RLS 策略的表（D1 基线缺口），其隔离仅靠应用层 WHERE——若对应仓库漏写谓词，仍可能越权。根因是"逐表挂策略"的增量负担，需改进点 2（零 rlsDependent 门禁）推动补全。
- **落后 5：整表操作不受 RLS 约束**。PostgreSQL 官方明确 `TRUNCATE`/`REFERENCES` 不受 RLS 约束。本平台以"无物理删除端点"（铁律 8）规避，但"逻辑删除/级联"若未来引入 `TRUNCATE` 类操作即破防——属固有盲区，靠纪律而非机制。

#### 5.3.1 失败场景推演（把"静默 0 行"讲透）

为把"默认拒绝的双面性"（落后 3）从抽象变具体，推演两个真实可发生的工作流：

**场景 A —「假绿」（漏绑 GUC 但业务无感知）**
1. 某新增读路径在 `TenantSessionBinder.bind` 之前就执行了 `SELECT ... FROM run_event`，且事务未绑 GUC。
2. `current_tenant_id()` 返 NULL → `run_event` 的 RLS 策略 `tenant_id = NULL` 恒假 → 返回 **0 行**。
3. 调用方拿到空列表，**不抛任何异常**，前端渲染"该 run 暂无事件"——用户以为数据还没产生，实际是隔离误伤。
4. 后果：无错误、无告警、无指标（I-1 补齐前），排查需逐条比对"DB 里明明有行但接口返回空"。这正是 fail-closed 的"安全但不可诊断"代价。

**场景 B —「假失败」（绑定了错误租户）**
1. 连接池复用，`clear()` 未被执行，上一条请求残留 `app.tenant_id = '租户A'`。
2. 下一条请求属于租户 B，但 `bind()` 因异常跳过，沿用了 A 的上下文。
3. 租户 B 的查询实际以 A 的身份执行 → 返回 A 的数据（**串租户越权**）或 0 行（若 B 查的是 A 没有的资源）。
4. 若返回 A 数据，则是比"0 行"更危险的**静默越权**；若返回 0 行，则与场景 A 同构的"假失败"。`TenantSessionBinder` 的"取连接无条件重置"+ 事务局部 `set_config(..., true)` 正是为堵此口（见 4.1/4.2 D-RESET）。

**推演结论**：两类场景的根源都是"RLS 的拒绝是静默过滤、不向应用层发信号"。化解手段只能是 I-1（让 0 行/越权可见）+ I-2（让应用层谓词完整、减少对 RLS 兜底依赖）。


### 5.4 关键分歧点（最本质的架构分歧）

**分歧 1：隔离裁决放在哪一层？**
- 竞品（除 Agno）：放在应用/SDK 层（建议性），漏写即越权。
- Agno：放在框架授权中间件（内建但仍在进程内）。
- 本平台：放在 **PostgreSQL 引擎（强制性）** + 应用层 Gate 双保险。
- 后果：竞品在应用 bug 或新表漏挂时隔离可能失效；本平台的隔离在存储层恒成立（除非 BYPASSRLS/owner，已用 FORCE+NOBYPASSRLS 堵住）。代价是本平台失去"免配置即隔离"的轻量体验。

**分歧 2：默认语义——拒绝还是放行？**
- 竞品：`thread_id`/`session_id` 作用域默认是"作用域内可见"，越界靠代码正确。
- 本平台：未绑即 0 行（fail-closed）。
- 后果：本平台更安全但面临"静默 0 行假绿/假失败"（5.3 落后 3）；竞品更易用但漏写即越权。这是"宁可不可用、不可越权"的定位取舍。

**分歧 3：跨租户运维身份如何不破坏隔离？**
- 多数竞品：无明确区分，运维常复用应用角色。
- 本平台：**独立 `platform_ops`（BYPASSRLS）通道 + 双凭据 + 双发布通道**，应用角色 `app_agent` 永远 `NOBYPASSRLS`。
- 后果：平台运维可跨租户（必要），但"谁是平台运维"在数据库层显式区分、不经租户身份暴露；代价是双套凭据配置 fail-closed（缺则拒启）。

### 5.5 横向对比：金融/合规域的强制隔离要求

- **金融多法人/多账套**：银行核心系统常要求"法人级物理隔离"（独立库/schema），因监管将数据归属与法律责任绑定。本平台当前 L3 共享 schema 对"同实例多法人"合规偏弱，需改进点 3 的每租户连接/库选项。
- **合规审计域**：SOC 2 CC6.3 / ISO 27001 A.8 / GDPR Art.25 均要求"可证明的访问控制"。本平台的 `authz_decision_log`（不可变判定流水）+ 复合外键 + RLS 是强证据；但"跨租户访问证明"（谁以何种授权读了哪租户）仍待改进点 4 补全。
- **GDPR 数据主体权利（被遗忘/可携）**：本平台"无物理删除端点"与"不可变审计"在 GDPR 下是双刃——审计不可改满足 Art.5(1)(f) 完整性与保密性，但"被遗忘权"需通过 `erasure_certificate`（受控清理通道）实现，不可简单 DELETE。

## 六、优缺点总评

### 6.1 我们的优点

**结构性优势（架构层，竞品普遍不具备）**
- S1：隔离下沉到 PostgreSQL 引擎（L3），应用 bug/新表漏挂不破隔离（除非 BYPASSRLS）。
- S2：默认拒绝（fail-closed），未绑 GUC 即 0 行，不留越权窗口。
- S3：应用层 Gate（执行时重新授权 + `authz_version` 撤销即时失效）与 RLS 独立互补。
- S4：复合外键把租户边界写入引用完整性层，最后兜底。

**工程性优势（实现层）**
- E1：`TenantSessionBinder` 用事务局部 `set_config` + 取连接无条件重置，根治连接池串租户。
- E2：双通道凭据（`app_agent` NOBYPASSRLS / `platform_ops` BYPASSRLS），平台运维与租户隔离互不污染。
- E3：影子双跑对照（P1 观测、P2 阻断）提供隔离演进的灰度方法论。
- E4：`authz_decision_log` 只增不改、不挂 RLS、隔离靠授权，是判定举证材料。

**领域性优势（业务层）**
- D1：`isAudienceOnly` 把学生/家长/教师可见范围收窄到本人创建，且不归属即 404（防存在性探测）。
- D2：复合外键族保证"租户内命名/版本/账套"全局唯一且不跨租户。

### 6.2 我们的缺点

**设计取舍导致的代价**
- C1：认证内建度弱于 Agno——依赖宿主颁发已验签身份（取舍，非缺失）。

**能力缺口**

- G2：整表操作（`TRUNCATE`/`REFERENCES`）不受 RLS 约束（PostgreSQL 固有盲区），靠纪律规避。
- G3：无每租户连接池/独立 schema/库（L4）选项。
- G4：跨租户访问证明（"谁以何授权读了哪租户"）尚未结构化（改进点 4）。

**运维负担**

## 七、可优化与改进点（必须可执行）

> 准则：每条写到文件/表/配置/接口级别，给可执行验收门禁（不写"加强测试"类空话）。所有改动遵守项目铁律（尤铁律 1/8/16）。

### I-1：RLS 绑定的「可观测性」——让"未绑 GUC 静默 0 行"可被发现

- **问题陈述**：铁律 1 + `current_tenant_id()` 的设计使"未绑 GUC"返回 0 行而非报错（5.3 落后 3 / 6.2-C3）。生产中出现过：某路径忘绑 GUC → 查询恒 0 行 → 业务侧"假绿"（以为成功实则空）或"假失败"（以为无数据实则隔离误伤），**无任何异常、无指标**。这是 fail-closed 的固有诊断盲区。
- **方案设计**（三件套，缺一不可）：
  1. **启动自检（Bootstrap Self-Check）**：在 `platform-bootstrap` 启动期，新增 `RlsBindingSelfCheck`（实现类置于 `cn.studykid.multiagent.bootstrap.health`），用一个 **`platform_ops`（BYPASSRLS）连接**直接 `SELECT count(*) FROM public.agent` 拿到全量行 N，再用一个**临时 `app_agent` 连接（NOBYPASSRLS）先 `set_config('app.tenant_id','')` 再查**——断言"绑定租户 A 后查到的行数 > 0 且 ≤ N"、"清空 GUC 后查到的行数 = 0"。若"清空 GUC 后仍 > 0"即证明 RLS 未生效（FAIL → 拒绝启动，fail-closed）。核心断言逻辑的等价 SQL：
     ```sql
     -- ① 用 platform_ops（BYPASSRLS）取得全量基线
     SELECT count(*) AS n_total FROM public.agent;          -- 期望 > 0
     -- ② 用 app_agent（NOBYPASSRLS）清空 GUC 后查
     SELECT set_config('app.tenant_id', '', true);
     SELECT count(*) AS n_unbound FROM public.agent;        -- 期望 = 0（RLS 生效的铁证）
     -- ③ 绑定某一已知租户后查
     SELECT set_config('app.tenant_id', '<seed_tenant_uuid>', true);
     SELECT count(*) AS n_bound FROM public.agent;          -- 期望 > 0 且 <= n_total
     ```
     自检失败（`n_unbound <> 0`）即抛 `RlsNotEnforcedException` 并中止 Spring 上下文启动（fail-closed，与铁律 1 一致）。
  2. **运行时哨兵查询（Runtime Sentinel）**：新增 `RlsSentinelProbe`（调度或每次请求抽样），对一个**已知有本租户数据的哨兵表**（如 `tenant_config_override` 或 `agent`）执行"绑 A → 记行数 Ra"、"绑 B → 记行数 Rb"、"清空 → 记行数 R0"，断言 `R0 == 0` 且 `Ra>0 && Rb>0`（且若 A≠B 则 Ra、Rb 不应互相包含对方数据）。异常即上报 `AUTHZ_RLS_SENTINEL_VIOLATION` 指标。探针本身须用 `TenantSessionBinder.runInTenantScope`（105-119）隔离每次绑定，防污染。
  3. **指标（Metrics）**：在 `AuthzShadowReporter` / 新增 `RlsHealthMetrics`（置于 `agent-persistence` 的 metrics 包）暴露两个 Counter：
     - `rls_sentinel_zero_rows`：清空 GUC 时本应 > 0 却 = 0 的探针次数（"假绿"信号）；
     - `rls_sentinel_cross_tenant_leak`：A 租户探针查到 B 租户数据的次数（"越权"信号，理论上恒 0）。
     Grafana 面板 + 告警阈值：`rls_sentinel_cross_tenant_leak > 0` 即 P0 告警；`rls_sentinel_zero_rows` 在"非新租户"场景下 > 0 即 P1 告警（新租户无数据须先排除，见验收门禁）。
- **预期收益**：把"静默 0 行"变为"可观测信号"。可度量：哨兵探针在 CI/预发注入"忘绑 GUC"场景，断言 `rls_sentinel_zero_rows` 指标 > 0 且告警触发；生产 `rls_sentinel_cross_tenant_leak` 长期 = 0。
- **实施成本与风险**：启动自检需 `platform_ops` 凭据（已存在，fail-closed）；哨兵查询有轻量开销（抽样率可配）。风险：哨兵表无数据的新租户会误报 `zero_rows`——故哨兵须用"平台保证有数据的表"或"先写一条探针行再删（逻辑删除）"。须遵守铁律 8（无物理删除端点）。
- **优先级**：P0（直击 fail-closed 诊断盲区，铁律 1 的配套）。
- **验收门禁**：① 新增 `RlsBindingSelfCheckIT`：在活库上构造"清空 GUC 后 `app_agent` 仍能查到行"的场景 → 断言启动自检 **FAIL 并拒绝启动**；② 新增 `RlsSentinelProbeIT`：注入"忘绑 GUC"，断言 `rls_sentinel_zero_rows` 计数 +1 且 Grafana 告警规则命中；③ 断言正常绑定时 `rls_sentinel_cross_tenant_leak = 0`；④ 哨兵探针对**真实 PostgreSQL**（非 H2）跑，防 RLS 语义漂移。

### I-2：影子模式推进到「零 rlsDependent」的判定与自动门禁

- **问题陈述**：`AuthzShadowReporter.reportRlsDependent`（97-100）已能计数"Gate 要求按租户收口但查询未带显式租户谓词（当前靠 RLS 兜底）"。但 P1 期该信号**仅计数不阻断**，且缺乏"何时可翻转 P2 阻断"的**量化门禁**。现状：`AuthzShadowPolicyDefaults:26-28` 揭示 9 张缺口表仍靠应用层 WHERE；这些表的查询若不补显式谓词，退役 RLS 即越权。
- **方案设计**：
  1. **定义"零 rlsDependent"出口门禁**：在 `AuthzShadowReporter` 增加 `RlsDependentGate`，门禁口径（可执行）：
     - `rlsDependent_rate = rlsDependent_count / shadow_sample_count`；
     - **P1→P2 翻转条件**：连续 ≥14 天 `rlsDependent_rate == 0` **且** `AUTHZ_MISMATCH == 0` **且** 缺口表（9 张）已全部补 `tenant_id` 显式谓词（由 `ShadowPolicyCoverageTest` + 新增 `RlsGapTableIT` 断言）；
     - 翻转动作：将 `application.yml:157` `block-on-violation` 由 `false` 翻 `true`，且对 `rlsDependent` 信号**从"只计数"升级为"计数 + 在 P2 期仍不阻断但纳入变更冻结清单"**（避免把影子期变停机期，见 AuthzShadowReporter:86-89 注释）。
  2. **缺口表补全**：对 9 张缺口表，逐表补 `CREATE POLICY ... USING(tenant_id=current_tenant_id()) WITH CHECK(同)` + `ALTER TABLE ... FORCE ROW LEVEL SECURITY`，并补应用层显式谓词。新增 DDL 迁移脚本 `V35__close_rls_gap_tables.sql`（示例两张，其余同构）：
     ```sql
     -- V35__close_rls_gap_tables.sql（节选）
     -- 缺口表①：某带 tenant_id 但无 RLS 的表（如 platform.agent_trace_metric 的物理基表代理）
     ALTER TABLE ONLY public.<gap_table_1> ENABLE ROW LEVEL SECURITY;
     ALTER TABLE ONLY public.<gap_table_1> FORCE ROW LEVEL SECURITY;
     CREATE POLICY <gap_table_1>_tenant_isolation ON public.<gap_table_1>
         USING ((tenant_id = public.current_tenant_id()))
         WITH CHECK ((tenant_id = public.current_tenant_id()));

     -- 缺口表②：同上
     ALTER TABLE ONLY public.<gap_table_2> ENABLE ROW LEVEL SECURITY;
     ALTER TABLE ONLY public.<gap_table_2> FORCE ROW LEVEL SECURITY;
     CREATE POLICY <gap_table_2>_tenant_isolation ON public.<gap_table_2>
         USING ((tenant_id = public.current_tenant_id()))
         WITH CHECK ((tenant_id = public.current_tenant_id()));
     -- ……其余 7 张同构
     ```
     注意：缺口表的具体名称由 `AuthzShadowPolicyDefaults:26-28` 的 D1 基线清单决定（报告中不臆造表名，实施时以该基线为准）；补 RLS 前**必须先跑 I-1 哨兵**确认这些表的查询都已带显式 `tenant_id` 谓词，否则补 RLS 会把"漏写谓词的越权"变成"0 行假失败"。
  3. **自动门禁实现**：新增 `ShadowExitGateEvaluator`（置于 `agent-persistence` 测试/运维模块），读 `AuthzMismatchMetrics` 历史，输出 ` eligible-for-P2: bool `，供 CI 门禁调用（非人工判断）。
- **预期收益**：把"影子期何时结束"从"感觉"变为"可量化门禁"；消除 9 张缺口表的隔离盲区。可度量：P2 翻转后 `rlsDependent_rate` 持续 = 0；缺口表 `FORCE RLS` 计数从 44 → 53（44+9）。
- **实施成本与风险**：补 9 张表 RLS 需回归所有相关仓库查询（确认谓词不冲突）；风险：缺口表若本就靠应用层 WHERE 且查询已带谓词，补 RLS 不改变行为（安全）；若某查询**漏写**谓词，补 RLS 前越权、补 RLS 后变 0 行——须先以 I-1 哨兵确认无漏写再补。
- **优先级**：P1（隔离完整性的关键闭环）。
- **验收门禁**：① 新增 `RlsGapTableIT`：断言 9 张原缺口表在 `V35` 后 `FORCE ROW LEVEL SECURITY` 计数 = 53；② `ShadowExitGateEvaluatorTest`：注入"连续 14 天 rlsDependent_rate=0 且 mismatch=0" → 断言 `eligible-for-P2=true`；注入任一非空 → 断言 `false`；③ `AuthzShadowLiveIT` 扩展：断言 `rlsDependent` 计数在补谓词后归 0；④ CI 新增步骤调用 `ShadowExitGateEvaluator` 作为合并门禁。

### I-3：租户密钥/连接级隔离的演进路线（L3 → L4 可选）

- **问题陈述**：6.2-C2/G3：当前共享 schema + RLS，无每租户独立连接池/独立 schema/库。金融多法人/医疗强合规租户（5.5）可能要求物理隔离，且"单坏查询影响全租户"（noisy neighbor）在共享库下无法根除。
- **方案设计**（分三档，渐进、默认关、fail-closed）：
  - **档 1（租户级连接池，低风险）**：扩展 `TenantSessionBinder` + 数据源路由，支持"高合规租户走独立连接池/独立 DB 用户（`app_agent_<tenant_slug>` 各自 `NOBYPASSRLS`）"。`application.yml` 加：
     ```yaml
     agent:
       worker:
         tenant-isolation:
           tier: "RLS"                       # 默认；可选 DEDICATED_CONNECTION / PER_TENANT_SCHEMA / PER_TENANT_DB
           dedicated-connection-slugs: "${AGENT_DEDICATED_TENANT_SLUGS:}"   # 仅 tier=DEDICATED_CONNECTION 时生效
           per-tenant-schema-slugs: "${AGENT_PTS_SCHEMA_SLUGS:}"
           per-tenant-db-slugs: "${AGENT_PTD_DB_SLUGS:}"
     ```
     连接获取时按租户 slug 路由到对应数据源；路由失败（未知 slug 且 tier 要求隔离）→ fail-closed 拒启（与铁律 1/12 一致）。RLS **不退役**，档切换经 `ShadowExitGate`（I-2）验证应用层谓词完整。
  - **档 2（每租户 schema，中风险）**：高合规租户数据落 `tenant_<slug>` schema，RLS 仍保留为兜底；`search_path` 按租户设定。需 schema 供应（provisioning）流水线 + 迁移工具（Azure 文档明确反对"per-tenant 表"，但支持 per-tenant schema）。
  - **档 3（每租户独立库，高风险）**：独立数据库实例，跨租户分析走聚合层。仅对签约强合规租户开启。
  - **关键约束**：RLS **不退役**——即便档 3 也保留 RLS 作为纵深兜底；档切换须经 `ShadowExitGate`（I-2）验证应用层谓词完整，否则拒绝切换。
- **预期收益**：满足金融/医疗强合规；缓解 noisy neighbor。可度量：档 1 下"单租户连接池耗尽不影响其他租户"的混沌测试通过；档 3 下跨库访问在 DB 层物理不可达。
- **实施成本与风险**：档 1 改动面中等（数据源路由）；档 2/3 需供应流水线与跨库查询重构，风险高。**默认 RLS 档，档切换需显式配置 + 灰度 + 反向验证（铁律 6）**。
- **优先级**：P2/P3（演进能力，非阻塞）。
- **验收门禁**：① `DedicatedConnectionIT`：档 1 下，租户 A 的专用连接池耗尽时，租户 B 查询正常返回（混沌）；② `SchemaIsolationIT`（档 2）：租户 A 的 `search_path` 下不可见租户 B 的 schema 对象；③ 断言任何档位下 RLS 仍 `FORCE`（grep DDL 不变）；④ 档切换若 `ShadowExitGate` 未通过 → 启动拒绝（fail-closed）。

### I-4：审计的跨租户访问证明（谁以何种授权读了哪租户）

- **问题陈述**：`authz_decision_log`（988 注释）记录每次判定（tenant_id/principal_id/scope/action/resource_type/permitted/reason_code），但**缺乏"跨租户访问的显式证明"**——即"平台运维（platform_ops，BYPASSRLS）在 T 时刻以 X 授权读了租户 Y 的 Z 资源"这类跨边界动作未结构化留痕。GDPR Art.30（处理活动记录）/ SOC 2 CC6.3 要求可证明的跨边界访问。
- **方案设计**：
  1. 扩展 `platform.authz_decision_log` 增加可选列 `actor_kind`（TENANT_PRINCIPAL / PLATFORM_OPS / SYSTEM）、`target_tenant_id`、`justification_ticket`（如治理票据 scope）。DDL 迁移 `V36__authz_decision_log_cross_tenant.sql`，仅加列、不改既有只增不改语义：
     ```sql
     -- V36__authz_decision_log_cross_tenant.sql
     ALTER TABLE platform.authz_decision_log
         ADD COLUMN actor_kind       text NOT NULL DEFAULT 'TENANT_PRINCIPAL'
             CHECK (actor_kind IN ('TENANT_PRINCIPAL','PLATFORM_OPS','SYSTEM'));
     ALTER TABLE platform.authz_decision_log
         ADD COLUMN target_tenant_id uuid;          -- 跨租户访问时填被读租户；同租户访问为 NULL
     ALTER TABLE platform.authz_decision_log
         ADD COLUMN justification_ticket text;       -- 跨租户访问的治理票据；缺失须拦截（应用层 fail-closed）
     -- 既有 INSERT（不写新列）仍合法，因有 DEFAULT；只增不改语义不变
     ```
  2. 在 `platform_ops` 通道的读路径（如 `CapConfigPublishController` 平台级发布、`RunRecoverySweeper` 跨租户扫描）**强制**写一条 `authz_decision_log`（actor_kind=PLATFORM_OPS, target_tenant_id=被读租户, justification_ticket=必有），缺失即抛 `MissingCrossTenantJustificationException`（fail-closed）。统一织入 `CrossTenantAccessGuard` 拦截器（置于 `agent-application` 的 web 拦截层），避免逐点改：
     ```java
     // CrossTenantAccessGuard（伪代码，fail-closed 落点）
     public void ensureJustified(SubjectContext subject, String targetTenantId, String ticket) {
         if (subject.isPlatformOps() && targetTenantId != null && (ticket == null || ticket.isBlank())) {
             throw new MissingCrossTenantJustificationException(subject, targetTenantId);
         }
         authzDecisionLog.append(subject.actorKind(), targetTenantId, ticket, /*permitted*/ true, /*reason*/ "CROSS_TENANT_READ");
     }
     ```
  3. 新增只读端点 `GET /api/platform/audit/cross-tenant-access`（仅 PLATFORM_ADMIN），返回结构化跨租户访问流水，供合规导出。
- **预期收益**：把"跨租户访问"从"隐含"变"可证明"。可度量：注入"platform_ops 读租户 Y 但未带 justification_ticket" → 断言抛异常且写库失败；正常路径 `cross_tenant_access` 导出条数 = 实际跨租户读次数。
- **实施成本与风险**：加列向后兼容（ nullable）；风险：platform_ops 路径多、需逐处补票据——可先用 `CrossTenantAccessGuard` 拦截器统一织入，避免逐点改。须遵守铁律：authz_decision_log 仍只增不改、不挂 RLS。
- **优先级**：P2（合规增强）。
- **验收门禁**：① `CrossTenantAccessIT`：platform_ops 读租户 Y 路径缺票据 → 断言 `MissingCrossTenantJustificationException` 且 `authz_decision_log` 无该次越界读；② 带票据 → 断言 `authz_decision_log` 落 `actor_kind=PLATFORM_OPS, target_tenant_id=Y` 一行；③ 断言新增列 nullable 不破坏既有只增不改语义（既有 INSERT 不需改）；④ 端点仅 PLATFORM_ADMIN 可见（TenantContext Roles 判定）。

#### I-1：RLS 绑定可观测性（自检 + 哨兵 + 指标）

- **前置条件**：确认存在 `platform_ops`（BYPASSRLS，`03_platform_roles.sql:122/126`）与 `app_agent`（NOBYPASSRLS，`:98/102`）双数据源；哨兵表用平台保证有数据的租户表（如 `agent`），且**验隔离的连接必须是 `app_agent`**。
- **具体改动片段**：启动自检类用双连接取基线，核心断言（本次复核口径）：

  ```java
  appAgentTx.execute(conn -> {                       // app_agent，事务内
  ```

#### I-2：影子出口门禁——「零 rlsDependent」量化判定（原"补 RLS"方案已被纠偏）

- **前置条件**：`AuthzShadowReporter.reportRlsDependent`（`AuthzShadowReporter.java:97-100`）已能计数；9 张缺口表是影子期基线（`AuthzShadowPolicyDefaults.java:25-28`），**不补 RLS**；出口以 `rlsDependent=0` + 观察期为准（MEMORY 专题进度：M4 `rlsDependent` 30→0）。
- **具体改动片段**（改写为门禁评估器，非 DDL）：
  ```java
  // ShadowExitGateEvaluator.java（agent-persistence 运维模块，新增）
  public ExitVerdict evaluate(AuthzMismatchMetrics m, DdlRlsCensus census, int observeDays) {
      double rate = (double) m.rlsDependentCount() / Math.max(1, m.shadowSampleCount());
      boolean gapPredicatesPresent = RlsGapTableIT.allGapTablesHaveTenantPredicate(); // 应用层谓词齐全
      boolean eligible = observeDays >= 14 && rate == 0.0
                      && m.mismatchCount() == 0 && gapPredicatesPresent;
      return new ExitVerdict(eligible, rate, census.forceRlsCount()); // 不补 RLS，census 仅观测
  }
  // P1→P2 翻转：application.yml:157 block-on-violation false→true（人工执行，Gate 给建议）
  ```
  **不新增任何 `CREATE POLICY`/`ALTER TABLE ... FORCE RLS`**——这是对原 I-2 的实质性改写。
- **三级验收门禁**：
  - 单元：`ShadowExitGateEvaluatorTest` 注入"14 天 rate=0 且 mismatch=0 且谓词齐全"→ `eligible=true`；注入 `rate>0` 或缺谓词或 `observeDays<14` → `false`。
  - API（真实 PG，`app_agent`）：`RlsGapTableIT` 断言 9 张缺口表的**每条读 SQL 都带显式 `tenant_id` 谓词**（影子期证明，非 RLS）；`AuthzShadowLiveIT.crossTenant_reallyReds`（`:130`）持续为真（机制真能红）。**断言 `FORCE RLS` 仍为 44，不变成 53**（防有人按旧结论偷补）。
  - 角色×任务：平台运维角色在影子开启（`AGENT_AUTHZ_SHADOW_ENABLED=true`）下跑真实多租户读，观察 `rlsDependent_rate` 逐日归零；观察期满 14 天由 Gate 输出 `eligible-for-P2`。
  - **撤掉修复点会红吗**：把 `rate==0` 条件删掉 → "rate>0 仍 eligible"单测变红；若有人补 RLS 使 FORCE 变 45+ → `RlsGapTableIT` 的 `FORCE=44` 断言变红（锁死纠偏）。✅ 有效。
- **回滚策略**：评估器只读、无副作用，下线即止；`block-on-violation` 翻 true 后若发现误阻断，翻回 false 即恢复 P1 观测态（配置级回滚）。**无 DDL、无 RLS 变更**——这是与旧 I-2 最大的不同（旧方案要回滚 V35 迁移，新方案无需）。

  ```java
      if (s.isPlatformOps() && targetTenantId != null && (ticket == null || ticket.isBlank()))
          throw new MissingCrossTenantJustificationException(s, targetTenantId);
      authzDecisionLog.append(s.actorKind(), targetTenantId, ticket, true, "CROSS_TENANT_READ");
  }
  ```
  **授权注意**：既有 `INSERT` 无 RETURNING（铁律 2：`authz_decision_log` 禁 RETURNING）；若某路径用 `ON CONFLICT DO UPDATE`，须确认 `app_agent` 有 UPDATE 授权（`03_platform_roles.sql:155/244`）并通过 `SchemaDriftIT`——否则 UPDATE 被拒。
- **三级验收门禁**：
  - 单元：`CrossTenantAccessGuardTest` 缺票据 → 断言抛 `MissingCrossTenantJustificationException`；带票据 → 断言落一条 `actor_kind=PLATFORM_OPS`。
  - API（真实 PG）：`CrossTenantAccessIT` platform_ops 读租户 Y 缺票据 → 断言异常且 `authz_decision_log` 无该行；带票据 → 断言落库一行 `target_tenant_id=Y`；断言既有 INSERT（不写新列）仍合法（DEFAULT 向后兼容）。
  - 角色×任务：PLATFORM_ADMIN 角色导出 `/api/platform/audit/cross-tenant-access`，条数=实际跨租户读；STUDENT 角色访问该端点 → 403（默认拒绝）。
  - **撤掉修复点会红吗**：删 `if(...ticket.isBlank())throw` → 缺票据用例不再抛异常变红；删新列 → 落库断言变红。✅ 有效。
- **回滚策略**：加列向后兼容（NOT NULL 有 DEFAULT），下线拦截器 + 只读端点即回到旧行为；新列保留无害，无需删列。**注意**：若曾给 `app_agent` 增授 UPDATE（为 ON CONFLICT），回滚时须同步收回授权并跑 `SchemaDriftIT`（铁律 7：业务 SQL 用 `app_agent` 绝不用 `agent_retention`；新对象同步 `03_platform_roles.sql`）。

> **红线复述（本次强化）**：① **9 张缺口表禁补 RLS**（已被复核纠偏），出口=`rlsDependent=0`+14 天观察期；② 验隔离一律 `app_agent`(NOBYPASSRLS)，`platform_ops`(BYPASSRLS) 是假绿；③ GUC `set_config(...,true)` 必须事务内、业务 SQL 前；④ 新表/新列同步 `03_platform_roles.sql`，业务 SQL 用 `app_agent`，`ON CONFLICT DO UPDATE` 需 UPDATE 授权 + `SchemaDriftIT`；⑤ I-3 任何档位 RLS 不退役且同步维度 03 路由；⑥ I-4 的 `authz_decision_log` 只增不改、不挂 RLS、禁 RETURNING。

## 八、其他有价值的横向对比（避免维度内自闭）

### 8.1 与本项目其他维度的耦合与相互约束（≥2 条）

1. **↔ 维度 07 权限与护栏**：本维度的 RLS 是"隐式数据层授权"，维度 07 的 `RoleBasedAuthorizationService` 是"显式应用层 Gate"。二者必须**持续对账**——这正是影子对照（4.4 D-SHADOW）存在的根本理由。若改 RLS 策略（如补缺口表 I-2）而未同步 Gate 的 `ScopeFilter`，`AuthzShadowHooks` 会报 mismatch。**约束**：任何 RLS 改动须跑 `AuthzShadowLiveIT` + `ShadowExitGate`（铁律 16 延伸）。
2. **↔ 维度 10 可观测性/审计**：本维度的 `authz_decision_log` 是维度 10 审计流水的子集；"跨租户访问证明"（I-4）直接喂给维度 10 的合规导出。**约束**：I-4 加列不得破坏维度 10 的"审计只增不改"语义。
3. **↔ 维度 03 状态持久化**：租户域表的 RLS 与维度 03 的"PG 权威源 + 租约 + fencing"共用同一数据库。若引入 I-3 档 2/3（独立 schema/库），维度 03 的"重读 DB 续跑"必须按租户路由到正确的 schema/库。**约束**：I-3 切换须同步维度 03 的数据源路由，否则崩溃恢复会读错租户（Sev-0）。

### 8.2 与非 agent 领域成熟做法的对照

- **金融/支付的多法人多账套隔离**：银行核心系统常采用"法人级独立库"（L4），因监管将"数据归属"与"法律责任/资本充足率"绑定。本平台 L3 共享 schema 在"同实例多法人"合规上偏弱——I-3 档 3 即借鉴此范式，但以 RLS 作兜底保留纵深。
- **分布式系统的"租户感知连接路由"**：Salesforce/ServiceNow 等超大 SaaS 采用"按租户分片 + 连接路由"；本平台 I-3 档 1（租户级连接池）即此思想的轻量版，且因保留 RLS 而比纯路由更稳。
- **合规领域的"默认拒绝 + 不可变审计"**：SOC 2 CC6 / ISO 27001 A.8 / GDPR Art.25&32 均要求可证明访问控制。本平台的"RLS 默认拒绝 + `authz_decision_log` 只增不改 + 复合外键"是这三者的技术证据合集（见 2.1 理论 (8)）。可借鉴其"控制项→技术证据"的映射表做法，把本平台每项隔离控制显式映射到合规条款：
  | 合规条款 | 本平台对应技术证据 | 当前缺口 |
  |---|---|---|
  | SOC 2 CC6.1 逻辑访问控制 | RLS 44 表 FORCE + 应用层 Gate | 认证内建度弱于 Agno（I-3 思路外） |
  | SOC 2 CC6.3 授权管理 | `authz_decision_log` 只增不改 + `authz_version` 撤销 | 跨租户证明待 I-4 |
  | ISO 27001 A.8 访问控制 | 复合外键 + RLS + BYPASSRLS 双通道 | 物理隔离待 I-3 |
  | GDPR Art.25/32 默认拒绝 | `current_tenant_id()` 未绑即 0 行 | 静默 0 行可诊断性待 I-1 |
  | GDPR Art.30 处理活动记录 | `authz_decision_log` | 跨租户访问结构待 I-4 |
- **发布工程的影子/灰度（dark launch）**：本平台影子对照（4.4.4）与 Google/Facebook 的 dark launch 同构——新逻辑双跑仅观测。可借鉴其"翻转开关 + 量化出口门禁"做法（已落地为 I-2 的 `ShadowExitGate`）。进一步可借鉴"影子流量对比的 diff 率阈值"——把 `AUTHZ_MISMATCH` 率、`rlsDependent` 率纳入发布门禁，而非仅看"是否 = 0"。
- **数据库界的"共享 schema + RLS"反模式警示**：Azure 多租户架构指南（2.1 理论 (1) 引用）明确列出反模式——"Table-based isolation（每租户建表）不可扩展"与"靠应用层 WHERE 做隔离不可靠"。本平台正是为规避后者而引入 RLS；但 Azure 同时指出"Row-level security can be complex to design, implement, test, and maintain. Many multitenant solutions don't use RLS because of those complexities"——这解释了为何多数竞品未内建 RLS，也佐证本平台选择的工程难度与差异化价值。
- **金融业"多法人独立账套"范式**：银行核心系统常按法人设独立数据库（L4），因《商业银行法》/巴塞尔协议将"数据归属"与"资本充足率、风险隔离"绑定。本平台 L3 共享 schema 对"同实例多法人"合规偏弱——I-3 档 3 即借鉴此范式，但以 RLS 作兜底保留纵深（与"数据库界反模式"中"纯应用层隔离不可靠"教训一致）。

#### 8.2.1 隔离模型选型决策表（借鉴跨域经验）

把上述跨域范式收敛为可操作的选型参考，供本平台演进（I-3）与对外方案建议使用：

| 场景特征 | 监管/规模 | 推荐隔离档 | 本平台对应能力 | 备注 |
|---|---|---|---|---|
| 数百~数千小租户、标准合规 | SaaS SMB | 共享 schema + RLS（L3） | **现状** | 成本最优，本平台基线 |
| 数十~数百中型租户、需逻辑隔离+按租户备份 | 中合规 | 共享库 + 独立 schema（L2 拓扑） + RLS 兜底 | I-3 档 2 | 迁移需供应流水线 |
| 强合规（金融法人/医疗/政府） | 法定物理隔离 | 独立库（L4） | I-3 档 3 | noisy neighbor 根除，成本最高 |
| 单租户超大数据量/高并发 | 性能隔离 | 独立连接池（L3 扩展） | I-3 档 1 | 缓解共享库争用 |
| 跨租户分析/合规导出 | 全局视图 | 聚合层 + 跨租户访问证明 | I-4 | 独立于业务隔离 |

该表的核心教训：**没有"万能档"，隔离强度与运维成本单调相关**；本平台以 L3 为基线、I-3 提供按需升级到 L4 的可选路径，是正确的"默认强、按需更强"策略。


### 8.3 反向思考：若从头重做本维度，我们会怎么设计？（诚实取舍）

- **仍保留**：RLS 强制 + 默认拒绝（L3）、`TenantSessionBinder` 事务局部绑 GUC、应用层 Gate 执行时重新授权、复合外键完整性、双通道 BYPASSRLS 凭据。这五点是相对竞品**唯一且正确**的差异化，重做不会丢。
- **会改变**：① 从第一天就把 I-1 的"启动自检 + 哨兵 + 指标"做进 bootstrap，而非事后补——否则"静默 0 行假绿"会潜伏更久；② 一开始就用 I-2 的"零 rlsDependent 门禁 + 全表 RLS"避免 9 张缺口表；③ 把认证内建度向 Agno 靠拢（JWT/服务账号验证内建），降低对宿主认证的依赖；④ 把 I-4 的"跨租户访问证明"作为 `authz_decision_log` 的一等字段从设计之初落地。
- **诚实取舍**：即便重做，仍会牺牲"免配置即隔离"的轻量体验来换"强一致、强隔离"——这是本平台定位（生产多租户 SaaS 运行时）决定的，不可妥协。物理隔离（L4）仍作为可选项而非默认，因默认开启成本不可接受。

### 8.4 深度补充：与维度 07、12 的精确交界（改一处必须联动一处）

> 8.1 已列三条耦合（↔07/10/03）。本节把最容易发生"责任真空或重复实现"的两条交界——**维度 07 权限与护栏**、**维度 12 部署与伸缩**——按"谁定义规则 / 谁承载机制 / 交界锚点 / 联动反向验证"画清。本维度是地基，改动必须双向核对，否则会出现"两个团队各改一半、隔离和授权对不上"的 Sev-0。

#### 8.4.1 ↔ 维度 07（权限与护栏）：隐式的"数据层授权" vs 显式的"应用层 Gate"

这是全仓最容易混淆的交界——两者都在"决定谁看得见什么"，但强制层完全不同，必须**持续对账**（影子对照 D-SHADOW 的存在理由）。

| 关注点 | 维度 02（本维度）负责 | 维度 07 负责 | 交界锚点（本次复核） |
|---|---|---|---|
| 数据行可见性 | RLS 策略 `tenant_id = current_tenant_id()` 逐行过滤（隐式） | 不重定义行过滤，消费 RLS 结果 | `01_platform_ddl.sql:5294`（agent 策略） |
| 动作授权 | 不裁决"能否 run:create/tool:invoke" | `RoleBasedAuthorizationService` 执行时重新授权（显式） | `AuthorizationService.java:12-19,31-33` |
| 受众收窄 | 提供租户硬边界（RLS） | `isAudienceOnly` → `requester_id` 收窄 + 404 | `AuthorizationService.java:244-246`；`RunQueryController.java:87-92` |
| 撤销生效 | GUC 每次事务重绑（无缓存授权） | `authzVersion` 重判即时失效 | `TenantContext.java:24`；`AuthorizationService.java:51` |
| 二者对账 | 影子钩子把 Gate 的 `ScopeFilter` 与 RLS 基线双跑 | 提供 `scopeForCollection` 判定 | `AuthzShadowHooks.java:80-92`；`application.yml:154-169` |

- **交界风险**：若改 RLS 策略（如有人按旧结论给缺口表补 RLS，已被纠偏）而未同步 Gate 的 `ScopeFilter`，`AuthzShadowHooks` 会报 mismatch；反之若改 Gate 收窄规则而未确认 RLS 是否兜得住，`rlsDependent` 会上升。**约束**：任何 RLS/Gate 单侧改动必须跑 `AuthzShadowLiveIT`（`AuthzShadowLiveIT.java:130`）+ I-2 的 `ShadowExitGate`（铁律 16 延伸）。
- **反向验证**：把 `isAudienceOnly` 分支从 `RunQueryController.java:87` 删除 → 受众可读他人 Run，07 的受众隔离用例与 02 的"第二层"断言同时变红；若只有 02 变红而 07 全绿，说明 07 的受众隔离是假绿。**"9 张缺口表禁补 RLS"是这条交界的红线**——补了会破坏影子期对账（已被 P0 验收报告 §3.2 纠偏）。

#### 8.4.2 ↔ 维度 12（部署与伸缩）：逻辑隔离边界 vs 物理故障域/连接预算

维度 12 的架构图明确写出 `RLS GUC 在事务内绑定 ← 依赖维度 02`（`12-部署与伸缩.md:74`）——本维度是它的**前置依赖**，两条交界如下：

| 关注点 | 维度 02（本维度）负责 | 维度 12 负责 | 交界锚点（本次复核） |
|---|---|---|---|
| 租户数据隔离 | RLS 逻辑边界（共享 schema，默认拒绝） | 不重复做行过滤，依赖 02 的 GUC 绑定 | `12-部署与伸缩.md:74/93` |
| 故障域切分 | 不定义进程/池隔离 | cell-based 分组、per-tenant 并发准入、爆炸半径 1/N | `12-部署与伸缩.md:136` |
| 连接预算 | GUC 每事务绑定（不新增连接） | `实例数×每实例连接数 ≤ PG max_connections−预留` | `12-部署与伸缩.md:61/155` |
| L4 演进 | I-3 定义隔离档（连接/schema/库） | 承载 cell 路由与灰度上线 | 本维度 I-3 ↔ 12 改进点 6 |

- **交界风险（两处 Sev-0）**：① 本维度 I-3 若切到"每租户独立 schema/库"，维度 12 的**连接池预算公式**与维度 03 的**崩溃恢复路由**必须同步重算/重定向——否则要么连接数爆掉，要么恢复读错租户。② 维度 12 的 cell/灰度上线（如 `AGENT_TENANT_SLUGS`）改变租户 slug 集合时，本维度的数据源路由（`tenant-isolation.dedicated-connection-slugs`）必须同步，否则新租户落不到正确隔离档。
- **反向验证**：维度 12 注入"租户 A 1000 条长任务 + 租户 B 1 条短任务"，断言 B 不被饿死——这是**物理/调度层**隔离（12 职责）；同一场景在 02 侧断言 A 永远读不到 B 的行——这是**逻辑层**隔离（02 职责）。两者独立、互不替代：调度隔离失效不破数据隔离，数据隔离失效（若误用 BYPASSRLS）则连调度隔离也保不住。**约束**：灰度上线新租户时，02 的 GUC 绑定自检（I-1）与 12 的连接预算校验必须同时通过，任一失败即拒启（fail-closed）。

#### 8.4.3 两条交界的统一原则

1. **单一强制点**：数据行可见性只由 RLS（02）强制，动作授权只由 Gate（07）裁决，故障域/连接预算只由部署层（12）切分——三者互不重写对方规则。
2. **单一对账通道**：02↔07 的对账只走影子钩子（`AuthzShadowHooks`），不得各起一套比对；M4 出口只认 `rlsDependent=0` + 观察期（禁补 RLS，已纠偏）。
3. **联动反向验证**：任一维度改动交界锚点（RLS 策略、`isAudienceOnly` 分支、隔离档/cell 路由），必须对相邻维度的 IT 做"撤点反证"（铁律 6/17），确认相邻断言随之变红——若不变红，说明该维度的"保障"是假绿；验隔离一律用 `app_agent`(NOBYPASSRLS)。

## 九、对产品演进的启发

### 9.1 本维度支撑的产品能力（用户能感知什么）

- 用户能感知：**租户数据绝不串**（RLS 默认拒绝 + 复合外键）、**授权撤销即时生效**（authz_version 重新授权）、**每次越权尝试被记录且可审计**（authz_decision_log）、**学生/家长/教师只看到自己的辅导**（isAudienceOnly）。
- 用户不能感知（当前短板）：隔离失效的"可诊断性"（I-1 补齐前为假绿/假失败）、强合规租户的物理隔离选项（I-3）、跨租户访问的合规证明导出（I-4）。

### 9.2 演进路线图（近/中/远三期，每期明确产出物与验收标准）

- **近期（P0–P1）**：交付 I-1（RLS 可观测性：启动自检 + 哨兵 + 指标）、I-2（零 rlsDependent 门禁 + 9 缺口表补 RLS）。**验收**："忘绑 GUC 触发拒绝启动 + `rls_sentinel_*` 告警"；"FORCE RLS 44→53 且 14 天门禁通过才翻转 P2"。
- **中期（P2）**：交付 I-4（跨租户访问证明）、I-3 档 1（租户级连接池）。**验收**："缺票据即抛异常且不可越界读"；"档 1 混沌测试租户间连接池隔离"。
- **远期（P3+）**：I-3 档 2/3（独立 schema/库，按强合规租户开启）。**验收**："档 2 search_path 不可见他租户对象"；"档 3 跨库物理不可达 + RLS 仍 FORCE"。

### 9.3 风险清单（做这一步可能踩的坑，关联本项目已知铁律）

1. **I-1 哨兵误报（新租户无数据）** → 哨兵须用平台保证有数据的表或先写探针行再逻辑删（铁律 8：无物理删除端点）。
2. **I-2 补 RLS 前未确认无漏写谓词** → 必须先以 I-1 哨兵确认，否则补 RLS 会把"漏写谓词的越权"变成"0 行假失败"（铁律 1：FORCE RLS 静默 0 行）。
3. **I-3 切换破坏维度 03 恢复路由** → 独立 schema/库须同步维度 03 数据源路由，否则崩溃恢复读错租户（Sev-0）。
4. **I-4 加列破坏"只增不改"语义** → 仅加 nullable 列，不改既有 INSERT 语义（铁律 8 延伸：authz_decision_log 仍只增不改、不挂 RLS）。
5. **任何 RLS/Gate 改动未跑影子对账** → 必须跑 `AuthzShadowLiveIT` + `ShadowExitGate`（铁律 16：改动须反向验证，撤掉修复点会红）。

### 9.4 一句话结论

**本平台在"多租户隔离"维度以"PostgreSQL RLS 数据层强制（L3）+ 默认拒绝（fail-closed）+ 应用层显式 Gate 双保险 + 复合外键完整性兜底 + 影子对照灰度方法论"的组合，换来了竞品普遍缺失的、不可被应用 bug 绕过的强隔离——代价是"静默 0 行"的可诊断性痛点与认证内建度弱于 Agno，这恰是多租户 SaaS 生产运行时"宁可不可用、不可越权"的自觉取舍，且前者可由 I-1/I-2 工程化化解。**

#### H-2 场景：读路径忘绑 GUC ⇒ **静默 0 行**（"假绿"，最关键的失败链路）

#### H-3 场景：并发竞态 —— 多 Worker 领取同一批 Run（fencing + 物化 CTE）

- **触发入口**：Worker 轮询领取 `claimTasks(tenantId, workerId, lease, limit)`（`JdbcRunClaimRepository.java:126-129`）。
- **前置状态**：租户 T 有 N 个 `QUEUED` 或租约已过期的 `RUNNING` Run；两个及以上 Worker 实例并发领取。

```
Worker A                 PG(app_agent)              Worker B
  | (1) claimTasks(T,wA,lease,1)                        | (2) claimTasks(T,wB,lease,1)
  |-------------------->|                              |-------------------->|
  | (3) 开事务+绑GUC     |                              | (3) 开事务+绑GUC     |
  |-------------------->|                              |-------------------->|
  | (4) CTE AS MATERIALIZED + FOR UPDATE SKIP LOCKED   | (4) 同一候选集,行已被A锁
  |-------------------->|  <-- A 锁住 row1            |<--- SKIP LOCKED 跳过
  | (5) UPDATE ... fencing_token+1, attempt+1          | (5) UPDATE 影响 0 行
  |-------------------->|                              |-------------------->|
  | (6) RETURNING run_id, fencing_token(=N+1)          | (6) 返回空
  | (7) 执行并提交: WHERE fencing_token = N+1 -> 1 行   | (7) 无
  | (8) 旧世代(wA,N)提交: WHERE fencing_token=N -> 0 行 |
```

| 7 | 执行并提交结果（带 fencing token 条件） | `JdbcRunClaimRepository.java:417-448`（`WHERE fencing_token = ?` `:448`） | `public.run` / `public.run_step` | token 不匹配 ⇒ 影响 0 行 ⇒ 旧世代提交被拒 |

- **失败分支**（≥2 条）：
  1. **漏掉 `MATERIALIZED`（铁律 13）** ⇒ `UPDATE … WHERE run_id IN (SELECT … LIMIT ? FOR UPDATE SKIP LOCKED)` 在 FORCE RLS 的 security-barrier 下，子查询退化为"对每一行外层候选重新求值"的 SubPlan ⇒ 第一次求值锁走第 1 行、第二次跳过它改返第 2 行…… ⇒ **`LIMIT 1` 实际领走全部可领取行**（超发 Worker 配额 + 顺带带走本不该本次领取的行）。**该事实来自代码注释记载的 2026-11-10 实测**（`JdbcRunClaimRepository.java:133-140`），本轮**未实测**。
  2. **用 superuser / BYPASSRLS 角色跑这条 SQL** ⇒ 结果**正确**（只返 1 行）⇒ **假绿**；同注释 `:139` 明写"同样的 SQL 用 superuser 跑则正确返回 1 行 —— 这正是『必须非特权角色测』的原因"。**铁律 1 的直接应用**。
  3. **两个 Worker 抢同一 Run（`claimSpecificRun`）** ⇒ `WHERE fencing_token = ?` 使后者影响 0 行 ⇒ 返回 `Optional.empty()`（`JdbcRunClaimRepository.java:216-237`），不会双写。
  4. **旧世代续租/提交** ⇒ `renewLease`（`:375-397`）与 `commitResult`（`:417-448`）都带 fencing 条件 ⇒ 0 行；**若绕开 fencing 直接改 `fencing_token`，触发器 `enforce_fencing_on_write` 会拒写**（DDL:419/4811）。
- **可观测落点**：`public.run` 的 `state` / `fencing_token` / `attempt` / `lease_owner` / `lease_expires_at` 列（**最硬的证据**）；影子开启时 `cap.authz_mismatch_total` / `cap.authz_shadow_samples_total`（`MicrometerAuthzMismatchMetrics.java:45-46`）；**无专门的"超发领取"指标**（漏 `MATERIALIZED` 时无告警）。
- **排查断点**：`JdbcRunClaimRepository.java:142`（MATERIALIZED）、`:153-154`（LIMIT + SKIP LOCKED）、`:160`（fencing 自增）、`:175`（绑定）、`:448`（提交时的 fencing 条件）。
