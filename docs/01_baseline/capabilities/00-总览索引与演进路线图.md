**结构性优势（对外卖点，5 项）**：① 多租户强隔离（数据层默认拒绝）；② 成本硬不超发（预留-结算 + DB CHECK）；③ fail-closed 故障语义（防静默失真）；④ 不可变审计与合规红线；⑤ 强一致可恢复执行（fencing + 不可变快照）。

**结构性短板（诚实清单，6 项）**：① 开发者体验（缺轻量 SDK/可视化编排）；② 上下文自动压缩未启用 + 无真实 tokenizer；③ RAG 嵌入模型占位 + 向量维度配置漂移；④ 可观测件多处「静默空转」/告警未落地；⑤ 无托管运行时、有效并发=1、租户并发无隔离；⑥ 运行期 HITL 缺任意点中断+状态编辑抽象。

### 2.1 能力评分卡横向对照（第三轮新增 · 把定性判定量化成可复算分数）

> **来源**：各报告第五章新增的「§5.x 能力评分卡」。评分轴沿用各报告 1.3 的评价轴（每维度 4~5 轴），**每轴 0–4 分**，每格必须给 `文件:行号` 或官方 URL 锚点。
> **评分口径（全局统一）**：0=完全缺失 / 1=有痕迹不可用（未装配、未写入、未触发） / 2=局部可用 / 3=能力完整（默认生效+失败语义+测试门禁） / 4=能力完整且有护栏（+运行时度量/告警/可观测）。
> **加权总分** = Σ(轴分 × 轴权重) / Σ权重；**权重为本轮新设**（1.3 只给轴不给权），按「强制程度 > 可审计性 > 失败可诊断性 > 运维成本 > 生态成熟度」递减分配。
> ⚠️ **本表是工程判断，不是测量值**；1–2 分差距不构成「结构性落后」的证据，只作为改进项优先级输入。

**这张表最重要的读法（三条）**：

1. **「领先项往往在竞品生态里不存在」**。10 号的 B 轴（审计不可变性）竞品得 0 分，含义是"这类能力在 agent 框架生态里根本不存在"，不是"竞品做得差"。把"对手没有的赛道"乘 0.30 塞进加权总分会人为抬高自己 —— 所以 **02/06/08/09/10/11/12/13 八份都给出了「可比子集」口径**（11 = A+B+D：2.00 vs 3.00；12 = A+B+C+E：1.93 vs 3.57；13 = A2+A3：2.33 vs 4.00），**只有可比子集的差值可作为结论**。
2. **同口径下我们整体落后 1.2~1.7 分，落点在「观测与度量」而非「安全与一致性」**。可比子集里最大的一笔亏损来自 **10 号 E 轴运维闭环（1 vs 3）**（告警规则数 = 0、无模板变量、无 runbook）与 **06 号全轴落后（−1.70）**。这两项都不是"我们做得不对"，而是"**度量层与压缩层还没建**"。
3. **我们真正的结构优势集中在「强制程度」轴**：02（RLS 默认拒绝）、03（fencing + 不可变快照）、05（闸门不可绕过）、09（预留-结算）四份在这一轴拿到 3~4 分，而竞品普遍在 2 分。**这四项是产品真正的护城河，不应被「总分落后」的表面数字稀释**。

## 六、对项目知识库 / 铁律的增补建议

> 本报告集的源码复核发现，值得回写到 `MEMORY.md` 与「铁律」清单（供后续会话避免重复踩坑）：

1. **「有类 ≠ 被装配」**：`AuditTamperProofGuard.GUARDED_TABLES` 空数组、`AgentMetrics.increment` 零调用、`TraceObserverChain` 无注入点、`ToolOperationReconciliationService`/`RunRecoverySweeper` 无调用方——建议把铁律 17 扩展为「运行期可达性审计」清单（实例化/写入/注入/告警触发四项）。
2. **默认通道是 `database` 表队列，不是 RabbitMQ**；`agent.worker.concurrency/prefetch` 默认不生效、有效并发=1——部署/压测前必查。
3. **HITL 已有完整 PARK/RESUME 闭环**（`WAITING_APPROVAL`），既有文档漏记；演进应复用而非新建 `PAUSED` 态。
4. **RAG 生产链路在 rag 模块**（`JdbcRetrievalRepository`，RRF k=60、阈值 0.38），`agent-infra/RetrievalService` 运行期不可达；嵌入模型是确定性占位。
5. **向量维度漂移**：`application.yml vector/1024` vs DDL `halfvec(4096)`，超 HNSW 4000 维上限。
6. **富上下文压缩管线影子期**（`context.enabled=false`），生产走 legacy 截断器；全程无真实 tokenizer。
7. **MCP 已建未默认接线**（`cap_mcp_server_def` + `McpHandlerProvider` 齐备，缺运行时端到端开启）。
   - ⛔ **第三轮已推翻**（见 §3.6）：MCP **装配是在线的**，真实缺口是**目录未装载**。
8. ⭐ **目录工具 id 与代码 `toolName()` 是两套不重合的命名域**，且 `kind='native'` 的目录行**无解析器** ⇒ 目录里的工具**无法执行**。这是 `record_weakness` / `get_student_profile` 从未被调用（`weakness_record` 13 天零调用）的**机制根因**。⇒ 新铁律候选：**「目录纳管」与「代码注册」必须共享同一套 id 与解析器，且门禁要断言"目录里每条 native 工具都有可解析的实现"**。
9. ⭐ **默认 `database` 通道下 trace id 完全丢失**：`agent_message_queue` **无 `trace_id` 列**，入队只写 7 列 ⇒ 跨进程追踪改造**必须先改队列表**，否则只在切 Rabbit 后生效。
10. ⭐ **配置台账会撒谎**：`ConfigReadService` 把 `concurrency/prefetch` 标 `effective=true`，但唯一读取点在 RabbitMQ 工厂、默认通道走不到。⇒ 新铁律候选：**「配置是否生效」必须以「消费方实际读取」为准，`ConfigReadService` 的 `effective` 标记不得作为证据**（见各报告附录 G）。
11. ⭐ **Worker 走非流式 `complete`**：流式 `streamChat` 只被 SSE 链路与 judge 调用，而**这两条都不走 `BudgetPort`**。⇒ **SSE/路由链路的模型成本不进预算账本**（维度 09 改进项 8 的方案不完整）。
12. ⭐ **流式 usage 恒 null**（MiniMax 实测）⇒ 必须本地估算兜底**且标注「估算」**；同时 **JSON 判空必须判 `node.isObject()`**（`isMissingNode()` 对 `"usage":null` 返回 false）——⚠️ **该铁律在生产代码有一处未落地**（`MiniMaxModelGateway.java:207-210`），需补守卫。
13. **「9 张带 tenant_id 无 RLS」不是权威清单**：DDL 实测 11 张无 FORCE RLS，扣 3 张"有意不挂"后剩 8 张待定性，且该清单**不在** `AuthzShadowPolicyDefaults` 里。⇒ 「禁直接补 RLS」的结论不变，但**清单需重建**。
14. **文档与实现脱节本身就是风险**：`/metrics` 类注释仍写"免认证"（实际需 Bearer）；`application.yml:230` 注释仍写"除 enabled 外未被消费"（实际 7 个键被消费、配错即拒绝启动）。⇒ 建议把**配置注释纳入门禁**（注释与消费方不一致时 CI 报警）。
15. **RLS 表数以 DDL 头注释为准（44）**，旧的"42"口径已作废；`PlatformDdlHeaderCountTest` 是唯一权威门禁。
