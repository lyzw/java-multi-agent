## 一、维度定义与评估坐标系

### 1.1 这个维度到底解决什么问题

工具 / 函数调用解决的是 **「LLM 的推理能力如何安全地延伸到外部世界」** 这一根本问题。LLM 本身只产生 token；要让它「查数据库」「发邮件」「调 API」「写文件」，必须有一个机制：

1. **定义**：把外部能力抽象成模型可理解的「工具契约」（名称、描述、参数 JSON Schema、副作用等级）。
2. **选择**：模型在推理中产出「我要调哪个工具、给什么参数」。
3. **校验**：在真正发出副作用之前，确认参数合法、调用被授权、预算充足、未被注入诱导。
4. **执行**：在受控环境里运行（与 LLM 推理解耦），拿到结果。
5. **回灌**：把结果作为新上下文喂回模型，进入下一轮推理。
6. **可恢复**：任何一步崩溃、超时、结果未知，都要有确定性的账本与对账语义，而非「假装成功」。

本维度的核心张力是 **「能力开放度」与「安全可控度」的博弈**：越方便模型自动调工具（auto-execute），越容易因 prompt injection / 越权 / 重复副作用而失控；越强调闸门拦截，开发者写工具的摩擦越大。

### 1.2 能力分层的四档模型

工具调用的成熟度可分四档（通用分层法，不局限于本项目）：

- **L0 · 无工具（纯生成）**：模型只能产出文本，无法作用于外部世界。安全性最高但能力最弱。
- **L1 · 应用层工具（由宿主应用硬编码调度）**：工具是代码里的分支（如 `if intent==weather: callWeather()`），模型不直接选工具，由规则路由。可控但无泛化。
- **L2 · 框架层工具（Model-driven + 自动执行）**：模型产出 `tool_calls`，框架自动解析并执行（OpenAI function calling、LangChain `@tool`、Spring AI `ToolCallingAdvisor`）。开发体验最佳，但**默认执行即放行**，护栏需使用者自行叠加（多数框架在此档）。
- **L3 · 引擎原生一等公民（调用前强制准入 + 可审计账本 + 失败对账）**：工具调用是「受控操作」，必须穿过统一的权限 / 预算 / 审批 / 幂等 / 账本闸门，且每次调用落持久化账本，结果未知走对账。本平台定位在 **L3**（见 `ToolInvocationGate.java:53` 类头「不可绕过的安全边界」、`docs/Agent设计总览.md:151-169` 的 15 步准入）。

> 注意：四档之间是「安全取向」的递进，不是「能力」的递进——L3 的能力集不比 L2 多，但每一次调用的**可审计性与失败可诊断性**显著更强。

### 1.3 评估坐标系（5 个评价轴）

| 评价轴 | 含义 | 本报告的观测方式 |
|---|---|---|
| **A. 强制程度**（调用前准入是否不可绕过） | 模型能否「自动执行」绕过护栏 | 是否存在统一 Gate 入口；是否禁用自动执行路径（`ToolInvocationGate.java:50` 禁用 `ToolCallingAdvisor`） |
| **B. 可审计性**（每次调用是否可被事后复盘） | 是否有「操作-尝试」双层账本 | `tool_operation` + `tool_operation_attempt` 两表（`01_platform_ddl.sql:2983`/`:3021`）；`agent_trace_tool_call`（`01_platform_ddl.sql:841`） |
| **C. 失败可诊断性**（UNKNOWN / 超时 / 重复如何处置） | 结果未知时是否盲目重试 | `forbid_attempt_after_terminal()`（`01_platform_ddl.sql:516-539`）；UNKNOWN 转 `ToolOperationReconciliationService` 对账 |
| **D. 隔离粒度**（权限能细到多细） | 工具 × 租户 × 角色的最小权限 | `cap_tool_def.risk_level`（`01_platform_ddl.sql:2326`）；`AuthorizationService.Actions.TOOL_INVOKE`（`AuthorizationService.java:59-177`） |
| **E. 生态开放性**（是否标准化工具生态） | 是否支持 MCP / OpenAPI 等开放协议 | `cap_mcp_server_def`（`01_platform_ddl.sql:2036`）；`McpHandlerProvider`（`ports/mcp/McpHandlerProvider.java`）；`kind ∈ {native,mcp,http}`（`01_platform_ddl.sql:2323`） |

**各评价轴的可观测口径（避免「定性空谈」）**：

- **A 轴可观测**：在测试环境注入一个「模型产出未登记工具调用」的脚本，断言 `ToolInvocationGate` 返回 `rejected` 且原因码为 `UNREGISTERED_TOOL`（见 `ToolInvocationGate.java:1143-1149`）。若框架默认会去执行，则 A 轴判「弱」。
- **B 轴可观测**：对一次含 2 个工具、其中 1 个重试 1 次的 Run，断言 `tool_operation` 恰 2 行、`tool_operation_attempt` 恰 3 行（1+2）——这是「双层账本」可数化的证据（`01_platform_ddl.sql:2983,3021`）。
- **C 轴可观测**：制造一次工具执行后连接中断（模拟 UNKNOWN），断言 `tool_operation.state=UNKNOWN` 且**不再产生新 attempt**（`forbid_attempt_after_terminal` 抛 `restrict_violation`），且 `ToolOperationReconciliationService` 生成对账任务。
- **D 轴可观测**：以受众角色（STUDENT）身份请求调用 `WRITE_EXTERNAL` 工具，断言 `AuthorizationService.isAuthorized(TOOL_INVOKE, toolName)` 在 `authzVersion` 撤销后返回拒绝（维度 7 协同）。
- **E 轴可观测**：统计 `cap_mcp_server_def` 中 `lifecycle_state=PUBLISHED` 的行数，以及 Gate 中 `mcpHandlers` 是否非空装配——两者皆为真才判「生态开放」落地，否则只是「定义了协议壳」。

## 二、理论体系（必须引用真实出处）

### 2.1 核心理论 / 概念框架（7 项，均附真实出处）

#### (1) ReAct：推理-行动循环的始祖
- **出处**：Yao, Zhao, Yu, Du, Shafran, Narasimhan, Cao, *《ReAct: Synergizing Reasoning and Acting in Language Models》*, arXiv:2210.03629，**ICLR 2023**（v3 camera-ready 2023-03-10，作者 Shunyu Yao 等，提交于 2022-10-06）。
- **核心**：让 LLM **交错生成「推理轨迹（thought）」与「行动（action，即工具调用）」**。推理帮助模型规划、跟踪、修正行动；行动让模型从外部（知识库 / 环境）获取信息。在 HotpotQA/Fever/ALFWorld/WebShop 上显著优于纯 CoT。
- **对本维度的意义**：工具调用不是「一次性 RPC」，而是**推理-行动循环中的一环**——这正是 `RunExecutionLoop` while 循环（`RunExecutionLoop.java:1011-1165`）的结构原型：模型产出 tool_calls → 闸门执行 → 结果回灌 → 下一轮。

#### (2) Function Calling 协议演进（OpenAI 2023）
- **出处**：OpenAI, *《Function calling and other API updates》*, **2023-06-13**。开发者用 JSON Schema 描述函数，模型智能产出含参数的 JSON 对象。对应模型 `gpt-4-0613` / `gpt-3.5-turbo-0613`。
- **并行工具调用（parallel tool calls）**：OpenAI 在 **2023-11 的模型/API 更新**中引入 `parallel_tool_calls` 参数（允许模型在一轮内产出多个相互独立的 `tool_calls` 并批量执行）。
  - ⚠️ **核实声明**：本报告撰写时 `platform.openai.com/docs` 的实时页面被 Cloudflare 拦截（返回 403），无法逐字截取官方文档；`parallel_tool_calls` 的引入时间与参数名来自公开工程实践（含本平台既有竞品对比报告 §维度5 的引用），属「基于公开工程实践的归纳」而非逐字官方核实。其余 OpenAI 事实（2023-06-13 函数调用发布）已通过官方博客正文核实。
- **意义**：工具调用从「单函数 JSON」演进到「批量并行」，引出本维度改进点 2（并行与 DAG 依赖）。

#### (3) Model Context Protocol（MCP）
- **出处**：Anthropic, *《Introducing the Model Context Protocol》*, **2024-11-25**（Published Nov 25, 2024，官方新闻页）。规范见 `https://spec.modelcontextprotocol.io` 与 `https://modelcontextprotocol.io`。
- **核心机制**：**开放标准**，用「单一协议」取代「为每个数据源写定制集成」。架构为 **MCP Server 暴露（expose）数据与工具，MCP Client（AI 应用）连接这些 Server**，建立安全的双向连接；客户端可**动态发现** Server 提供的工具。
- **对本维度的意义**：工具从「平台私有定义」走向「标准化、可被任意客户端动态发现」的生态。本平台已建 `cap_mcp_server_def`（`01_platform_ddl.sql:2036`）+ `McpHandlerProvider`（`ports/mcp/McpHandlerProvider.java`），但端点执行接线仍可选装配（见 4.4 与改进点 1）。

#### (4) JSON Schema 作为参数校验
- **出处**：JSON Schema 规范，draft-07（2019-09-04 作为 IETF Internet-Draft 发布，非 RFC）、2020-12 版；校验库生态：JS 的 **ajv**、Python 的 **pydantic**、Java 的 **networknt/json-schema-validator**。
- **本平台落点**：`ToolInputSchemaValidator`（`agent-infrastructure/.../tool/ToolInputSchemaValidator.java:27-84`）按 `cap_tool_def.input_schema` 做**闭集校验**（必填的在、未声明的不在、`additionalProperties:false` 被强制）。
- **意义**：工具参数校验的标准解法就是 JSON Schema；关键工程陷阱是「`additionalProperties:false` 漏写会被放行未声明参数」（本平台已在 `ToolInputSchemaValidator.java:15-25` 注释中明确警告）。

#### (5) Tool-augmented LLM 的安全理论（prompt injection 与越权）
- **出处 A（OWASP）**：OWASP *Top 10 for LLM Applications*（现为 OWASP GenAI Security Project，`https://genai.owasp.org/llm-top-10/`）。**LLM01 = Prompt Injection**（在 2023 与 2025 两版中均居首），指恶意指令覆盖系统提示 / 安全规则；间接注入（indirect injection）在 RAG / 工具返回内容中尤其危险。**LLM03** 在两版中含义不同（2023 = Training Data Poisoning；2025 = Supply Chain），但均涉及「不可信外部内容污染模型决策」。工具描述（tool description）与工具返回值（tool result）正是两类典型注入面。
- **出处 B（函数调用越狱实证）**：Wu, Gao, He, Wang, *《The Dark Side of Function Calling: Pathways to Jailbreaking Large Language Models》*, **arXiv:2407.17915**（提交 2024-07-25，v4 2024-12-24）。核心发现：函数调用过程中，**模型生成的参数（arguments）比聊天回复对齐得更弱**，存在「jailbreak function attack」——把越狱内容藏在函数参数里，在 GPT-4o / Claude-3.5-Sonnet / Gemini-1.5-pro 上平均成功率 >90%。
- **出处 C（可信性基准）**：Liu et al.（Yue Huang, Lichao Sun 等）, *《TrustLLM: Trustworthiness in Large Language Models》*, **arXiv:2401.05561**（2024）。将「工具使用可信性（tool-use trustworthiness）」列为 LLM 可信性的独立维度，指出 agent 的工具因能影响真实世界，其风险高于纯 LLM。
  - ⚠️ **核实声明**：任务书提示的 `arXiv:2402.11420`(TrustLLM) 与 `arXiv:2401.05566`(The Dark Side of Tool Use) 两个编号经核验**不准确**——`2401.05566` 实为 *Sleeper Agents*（Hubinger 等），`2402.11420` 并非 TrustLLM。本报告已改用**核实后的真实编号**（TrustLLM = arXiv:2401.05561；函数调用越狱 = arXiv:2407.17915）。「The Dark Side of Tool Use」这一短语与 arXiv:2407.17915 主题高度一致，故采用该文。

#### (6) 工具调用的可靠性（重试 / 超时 / 幂等）
- **出处**：分布式系统经典理论（如 *《Designing Data-Intensive Applications》* Kleppmann, 2017, Ch.8/Ch.11 关于「幂等」「至少一次 vs 恰好一次」「超时后的未知状态」）。核心结论：**超时发生后调用方处于 UNKNOWN 状态，不能盲目重试有副作用操作**，必须通过幂等键 + 对账解决。
- **本平台落点**：`tool_operation` 的 `idempotency_key` + `ToolInvocationGate` 幂等命中闸门（`ToolInvocationGate.java:1203-1292`）+ `forbid_attempt_after_terminal()`（UNKNOWN 禁止新 attempt，`01_platform_ddl.sql:532-536`）。与维度 3 的 fencing 配合（见 4.4）。

#### (7) 并行工具调用与 DAG 依赖
- **出处**：数据流 / 任务编排理论（如 Dryad / TensorFlow 的计算图、LangGraph 的 `Send`/`Topic` 并行）。当一轮内的多个 `tool_calls` 之间**无数据依赖**时可并行；存在依赖时须按 DAG 拓扑序执行。
- **本平台现状**：当前 `invokeAll` 对 `calls.values()` 做**顺序 for 循环**（`ToolInvocationGate.java:1130`），未实现并行或 DAG 依赖。这是改进点 2 的动机。

#### (8) 理论 → 本平台代码锚点映射表

| 理论 | 关键断言 | 本平台对应锚点 | 符合度 |
|---|---|---|---|
| ReAct（推理-行动循环） | 工具调用是推理循环一环 | `RunExecutionLoop` while 循环 + `invokeAll`（`RunExecutionLoop.java:1011-1165`） | 符合（但循环由框架驱动，非模型自驱动 thought） |
| Function Calling（JSON Schema 描述） | 模型产出含参 JSON | `cap_tool_def.input_schema` + `ToolInputSchemaValidator`（`01_platform_ddl.sql:2309`） | 符合 |
| MCP（标准化 server 暴露工具） | 客户端动态发现工具 | `cap_mcp_server_def` + `McpHandlerProvider`（`01_platform_ddl.sql:2036`） | 部分（定义+安全层有，端到端接线可选，改进点 1） |

### 2.2 理论给出的「设计张力」（trade-off 清单）

| 张力 | A 方案（偏开放） | B 方案（偏安全） | 本平台选择 |
|---|---|---|---|
| **执行路径** | 模型自动执行（L2，开发快） | 统一 Gate 强制准入（L3，开发慢） | **B**：禁用 `ToolCallingAdvisor`（`ToolInvocationGate.java:50`） |
| **参数校验** | 尽力解析（宽松，容错） | 错误即拒、闭集校验 | **B**：「Schema 错误必须拒绝，不得尽力解析」（`ToolHandler.java:36`） |
| **结果未知处置** | 重试到底（用户体验好） | 转对账、绝不盲目重试 | **B**：UNKNOWN 停执行、转 `ToolOperationReconciliationService` |
| **工具生态** | 预置大量第三方工具（MCP 全开） | 白名单 + 固定清单 + 指纹校验 | **中间**：支持 MCP 但 `dynamic_discovery=false`（`01_platform_ddl.sql:2056`）、`stdio` 未启用（V1） |
| **权限粒度** | 粗粒度（能调工具即可） | 按工具 × 租户 × 角色最小权限 | **偏细**：`risk_level` + `TOOL_INVOKE` 按工具名授权，但租户/角色级细化仍欠缺（改进点 6） |
| **结果回灌** | 原样回灌（信息完整） | 截断 + 结构化压缩 | **中间**：`ToolOutputLimiter` 8000 封顶，但无结构化压缩（改进点 4） |
| **重试语义** | 应用层透明重试（对模型无感） | 框架层禁用 `@Retryable`，Worker 侧受控 | **B**：维度 3 铁律「重试只在 Worker 侧」（见梳理报告维度 1） |
| **MCP 连接生命周期** | 运行期动态建连/发现 | 配置期固定清单 + 指纹比对 | **B（V1）**：`dynamic_discovery=false` + `stdio` 禁（`McpServerConfigValidator.java:62-79`） |

> 注：上述张力并非「非黑即白」。本平台多数选择 B 端，代价是开发者摩擦与生态广度（维度 5 的「落后」项），但换来维度 2/7/9/11 的强一致与强隔离。这是**产品定位（强治理多租户 SaaS）驱动的设计取向**，而非技术欠账。

### 2.3 业界公认的反模式（anti-pattern）及判别方式

1. **反模式：自动执行即放行（auto-execute without gate）**。判别：框架是否默认在拿到 `tool_calls` 后直接调函数。危害：绕过一切护栏。本项目以「唯一入口 Gate」消除此反模式。
2. **反模式：闭集校验泄漏（additionalProperties 宽松）**。判别：`input_schema` 未强制 `additionalProperties:false`，或校验器在「Schema 非法」时退化为「无约束」。本项目 `ToolInputSchemaValidator.java:37-51` 明确「Schema 非法直接拒绝」。
3. **反模式：每个工具自校验（scattered validation）**。判别：每个 `ToolHandler.validate()` 各自手搓参数检查，与共享 Schema 漂移。判别特征：native 工具不用共享校验器。本项目 `GetStudentProfileTool.java:58-74` **当前即犯此反模式**（详见 4.4 与改进点 3）。
4. **反模式：盲目重试 UNKNOWN（retry-on-unknown）**。判别：超时后无脑重试有副作用工具。危害：重复发邮件 / 重复记账（Sev-0）。本项目以 `forbid_attempt_after_terminal` 在 DB 层杜绝。
5. **反模式：工具描述 / 返回值被当指令（prompt injection via tool）**。判别：工具 description 含可执行指令、工具 result 原样进上下文未清洗。本项目有 `McpUntrustedOutput`（`application/cap/McpUntrustedOutput.java`）与 `ToolOutputLimiter` 做缓解，但无系统性「工具描述注入防护」（改进点 3 覆盖）。
6. **反模式：结果原样回灌撑爆上下文**。判别：工具返回整篇文档未截断。本项目 `ToolOutputLimiter.DEFAULT_MAX_CHARS=8000` 缓解（改进点 4 强化）。
7. **反模式：幂等键缺 run/agent 维度**。判别：幂等键仅含工具名，跨 Run / 跨子 Agent 撞键。危害：父子 Agent 互相吞调用。本项目 `buildIdempotencyKey(runId, call, agentRef)`（`ToolInvocationGate.java:1766`）含 run + agent 维度，规避此反模式。
8. **反模式：账本登记晚于执行**。判别：先执行工具、再写账本，崩溃即丢事实。本项目账本 PRE（步骤 10）早于执行（步骤 14），且 `approval.operation_id`/`budget_reservation.operation_id` 外键指向 `tool_operation` 强制此顺序（`Agent设计总览.md:171-173`）。

### 2.4 深度补充：两个新理论锚点（均本次经官方页核实，不与 2.1 重复）

> 本节为本次「13 份报告更详细补充」新增，不改写 2.1 已有锚点。2.1(1) 用 ReAct 解释了「工具调用是推理循环的一环」、2.1(5) 用越狱论文解释了「参数是对齐弱面」，但二者都只回答「为什么要有闸门」，没有回答两个更根本的问题：**「工具调用能力是模型内生的还是训练出来的？」** 与 **「用什么客观标准判断一个模型的工具调用能力强不强？」** Toolformer 与 BFCL 分别回答这两问，是对 2.1 的补强而非替换。

#### (9) Toolformer：工具调用是「自监督学出来的能力」，不是提示词技巧

- **出处（本次经 WebFetch arxiv 官方页核实）**：Timo Schick, Jane Dwivedi-Yu, Roberto Dessì, Roberta Raileanu, Maria Lomeli, Luke Zettlemoyer, Nicola Cancedda, Thomas Scialom, *"Toolformer: Language Models Can Teach Themselves to Use Tools"*, **arXiv:2302.04761**（Submitted 9 Feb 2023），https://arxiv.org/abs/2302.04761 。
- **定义（忠于摘要原文）**：论文原文——「LMs can teach themselves to use external tools via simple APIs and achieve the best of both worlds... a model trained to **decide which APIs to call, when to call them, what arguments to pass, and how to best incorporate the results into future token prediction**」，且「done in a **self-supervised** way, requiring nothing more than a handful of demonstrations for each API」。内建工具含计算器、QA、两个搜索引擎、翻译系统、日历。
- **对本维度的解释力**：Toolformer 把「工具调用」拆解为四个**可被独立监督**的决策——选哪个 API / 何时调 / 传什么参 / 如何把结果并入后续 token 预测。这恰好映射本平台的四层治理面：
  - 「选哪个 API」→ 能力闭包（`CapabilityClosureGuard`，`ToolInvocationGate.java:1161-1170`）与 `findHandler`（`:1712`）；
  - 「何时调」→ 模型在 `RunExecutionLoop` 循环里产出 `tool_calls`（`RunExecutionLoop.java:897`），但**执行时机由 Gate 的取消/审批/预算闸门决定**（`:1175`/`:1295`/`:1374`）；
  - 「传什么参」→ `ToolInputSchemaValidator`（闭集）+ `ParamPolicyEngine`（三层 AND，`ParamPolicyEngine.java:203-243`）；
  - 「如何并入结果」→ `ToolOutcomeRenderer.renderRound`（`:107`）把结果作为不可信数据回灌。
  - 关键洞察：Toolformer 证明**「传什么参」是模型可以学但会学错的能力**——这正是本平台「模型只提议、参数必须过闭集校验 + 策略引擎」的认识论依据（对照 2.1(5) 的 arguments 对齐弱面）。
- **边界（诚实）**：① Toolformer 研究的是**模型侧能力习得**，本平台不训练模型，只在**平台侧拦截**——二者是「能力的生产者 vs 能力的治理者」，不能互相替代。② 论文的「self-supervised 少量示例即可学会」在闭域 API 上成立；本平台面对的是开放多租户 SaaS，工具集由治理发布，不存在「每个 API 给几个示例即可」的前提。③ 论文未讨论权限/预算/账本/对账——这些是本平台在 L3 档额外叠加的工程约束（1.2 节）。

#### (10) BFCL：工具调用能力的「客观标尺」，含 Hallucination Measurement 类目

- **出处（本次经 WebFetch 官方页核实）**：UC Berkeley Gorilla 团队，*Berkeley Function Calling Leaderboard (BFCL) V4*，https://gorilla.cs.berkeley.edu/leaderboard.html 。
- **定义（忠于页面原文）**：页面原文——「The Berkeley Function Calling Leaderboard (BFCL) V4 **evaluates the LLM's ability to call functions (aka tools) accurately**」，「This leaderboard consists of **real-world data** and will be updated periodically」。评测分 **FC（native function/tool calling）** 与 **Prompt（用文本生成模拟）** 两路；版本演进：v1 引入 AST 指标、v2 引入企业级/OSS 函数、v3 引入多轮交互、v4 引入 **holistic agentic evaluation**。表头类目含 **Agentic / Multi Turn / Single Turn / Hallucination Measurement / Format Sensitivity / Web Search / Memory**；Overall Accuracy 定义为所有子类目的**非加权平均**；另计 Cost（USD）与 Latency（s）。
- **对本维度的解释力**：
  - BFCL 证明「函数调用准确性」是**可量化、可跨模型横比**的一等能力维度——本平台把工具调用收归唯一 Gate（1.2 节 L3），意味着**平台侧的确定性可以补偿模型侧的不确定性**：即使模型在 BFCL 意义上「参数偶发填错」，`ToolInputSchemaValidator` 的错误即拒 + 结果回灌自我纠正（`RunExecutionLoop.java:1153-1165`）也能把错误挡在副作用之前。
  - **Hallucination Measurement 类目**直接对应本维度的「幽灵工具 / 幽灵成功」风险：模型「幻觉出一个不存在的工具名」→ `findHandler` 返回 null → `recordRejected("未登记的工具")`（`:1143-1149`）；执行后连接中断 → UNKNOWN 转对账而非假装成功（`:1442-1452`）。BFCL 的幻觉类目为「为什么要做账本 + 对账」提供了**外部基准证据**。
  - **Format Sensitivity 类目**（「只支持 prompt 非 FC 模型」）解释了本平台为何强制 `ToolInputSchemaValidator` 闭集校验「错误即拒、不尽力解析」——格式敏感正是「尽力解析」的温床。
- **边界（诚实）**：① BFCL 衡量的是**模型**的函数调用准确率，本平台的安全保证来自**平台闸门**——BFCL 分数高不等于本平台可放松闭集校验，二者是不同层。② Overall Accuracy 是「非加权平均」，单一类目（如 Agentic）的高分不代表全维度强，引用时不能拿总分替代分类目分析。③ BFCL 的 v4 agentic 评测属滚动更新的榜单，本次核实的是页面当前形态，具体分数随榜单更新而变化，本报告**不引用任何具体排名数字**（避免臆造）。

#### 2.4.1 新锚点 → 本平台代码锚点映射

| 理论 | 核心主张 | 本平台对应实现（锚点，本次复核） | 是继承还是背离 |
|---|---|---|---|
| Toolformer（arXiv:2302.04761） | 工具调用四决策：选哪个/何时/传什么/如何并入结果；参数可学但会学错 | 闭包 `ToolInvocationGate.java:1161-1170`；闸门 `:1175/:1295/:1374`；闭集校验 `ToolInputSchemaValidator.java:44`；策略 `ParamPolicyEngine.java:203`；回灌 `RunExecutionLoop.java:1164` | **继承其决策分解，但把「学错」交给平台闸门拦截，不做模型侧训练** |
| BFCL（Gorilla V4） | 工具调用准确性可客观横比；含 Hallucination/Format 类目 | 未登记工具拒绝 `ToolInvocationGate.java:1143-1149`；UNKNOWN 转对账 `:1442-1452`；闭集「错误即拒」`ToolInputSchemaValidator.java:37-51` | **不继承其评测角色（本平台是执行侧），但用其类目佐证闸门设计的必要性** |

> 结论：Toolformer 与 BFCL 从「能力从哪来」「能力怎么量」两侧补强了 2.1。二者共同指向一个对本维度最重要的判断——**模型侧的工具调用能力天然带噪声（参数会填错、工具会幻觉、格式会漂移），因此 L3 档「平台侧强制闸门 + 双层账本 + UNKNOWN 对账」不是过度设计，而是对这种噪声的必要对冲**。这个判断比 2.1 单纯「工具调用是循环一环」更精确地解释了本平台为什么选择重治理路线。

## 三、竞品实现全景（每个主流方案一段）

### 3.1 OpenAI Agents SDK
- **官方定位与机制**：极简原语（Agent / Runner / Handoffs / Guardrails / Sessions / Tracing），无显式图。工具分 function tools（开发者定义、模型调度自动执行）、hosted tools（file search / code interpreter / computer use）、MCP 工具、handoffs-as-tools。
- **官方 URL**：https://openai.github.io/openai-agents-python/
- **优点**：开发者体验极佳；原生 tracing + guardrails（并行护栏）；MCP 一等公民；handoff 即工具简化多 Agent。
- **局限 / 代价**：工具执行默认**自动路径**，安全护栏需使用者自行叠加；无内建多租户隔离；预算无常驻治理（见维度 9 对比）。
- **适用**：快速搭生产级单租户 Agent。

### 3.2 Anthropic Claude Agent SDK
- **官方定位与机制**：把 Claude Code 当库用，继承其工具 / 权限 / sessions / hooks / MCP。提供 `canUseTool` 审批回调、`max_budget_usd` / `max_turns` 熔断。
- **官方 URL**：https://docs.anthropic.com/en/api/agent-sdk
- **优点**：**MCP native**（Anthropic 即 MCP 发起方）；权限/审批/预算一体化；工具权限最小化。
- **局限 / 代价**：`max_budget_usd` 是 SDK 级会话熔断，**非多租户配额**；部分官方页地域受限（本报告撰写环境抓取受限，已按竞品对比报告 §1.2 如实标注）。
- **适用**：需强 MCP 生态、终端 Agent 形态。

### 3.3 LangGraph
- **官方定位与机制**：低层图式编排运行时（StateGraph：State/Node/Edge + channels/reducer）。工具用 `@tool` 装饰器（类型注解即 input schema），可混用任意函数节点；ToolNode 预建；`@tool` 属 LangChain 工具生态；通过 MCP adapter 接 MCP。
- **官方 URL**：https://docs.langchain.com/oss/python/langgraph/graph-api 、https://docs.langchain.com/oss/python/langchain/tools
- **优点**：显式状态图，确定性与 LLM 步骤可混排；`time-travel` / 断点续跑标杆级；`trim_messages` 生态成熟。
- **局限 / 代价**：工具执行默认自动（graph 内直接跑 node），护栏靠中间件（`HumanInTheLoopMiddleware` / `AgentMiddleware`）；无内建多租户。
- **适用**：需精细控制流、可调试的复杂 Agent。

### 3.4 Google ADK
- **官方定位与机制**：code-first Agent（LlmAgent）+ Workflow 图（graph/dynamic/collaborative/template）。工具：`FunctionTool`（开发者函数）、预置 Google Search / Code Exec / **MCP** / **OpenAPI**；AgentTool（子 Agent 当工具）。
- **官方 URL**：https://adk.dev/tools-custom/ 、https://adk.dev/integrations/
- **优点**：自带部署（docker / cloud_run / Agent Runtime）；工具生态丰富（含 OpenAPI）；双向 live streaming。
- **局限 / 代价**：编排/框架层无内建预算/成本治理（观测非执行侧管控）；节点级容错语义官方未完全明示（竞品报告已诚实标注）。
- **适用**：Google Cloud 生态内的端到端部署。

### 3.5 Microsoft AutoGen（已归档，仅供参照）
- **官方定位与机制**：分层事件驱动多智能体（Core / AgentChat / Extensions）。工具：Core tools、McpWorkbench（MCP）、DockerCommandLineCodeExecutor（Docker 沙箱）。
- **官方 URL**：https://microsoft.github.io/autogen/stable/
- **优点**：事件驱动、代码执行沙箱化。
- **局限 / 代价**：**已于 2025-10 并入 Microsoft Agent Framework、2026-10 起归档停维护**，结论仅代表 0.4/AgentChat 末代状态，**不应作为新项目选型依据**（竞品报告 §1.2 已明示）。
- **适用**：历史参考、不推荐新选型。

### 3.6 CrewAI
- **官方定位与机制**：角色扮演式 Crew（Agents + Tasks + Process）+ Flows（`@start`/`@listen`）。工具：`tools` 列表 + `function_calling_llm`；`before_tool_call` hooks 拦截；CrewAI Tools + **MCP**；企业 Control Plane 提供 RBAC/审计/IAM。
- **官方 URL**：https://docs.crewai.com/en/concepts/crews 、https://docs.crewai.com/en/concepts/flows
- **优点**：角色化直观；`before_tool_call` 拦截点灵活；企业层有完整权限/审计。
- **局限 / 代价**：工具执行默认自动；`max_rpm`/`max_iter` 等是限流/迭代上限，非强预算治理。
- **适用**：业务流程式多角色协作。

### 3.7 Agno
- **官方定位与机制**：Agent / Team / Workflow 抽象 + 自托管 AgentOS。工具：`tools` / integrations / **MCP**；callable factories 动态解析；内建护栏（pre/post hooks + PII/提示注入/OpenAI Moderation）+ HITL。
- **官方 URL**：https://docs.agno.com/agents/overview 、https://docs.agno.com/agent-os/security/overview
- **优点**：内建多租户安全（JWT/service-account/security-key + 每用户隔离）；Durable Queue（`FOR UPDATE SKIP LOCKED` + 心跳租约）与本项目思路高度相似；开箱护栏库。
- **局限 / 代价**：强护栏依赖其平台；脱离 AgentOS 后治理能力减弱。
- **适用**：需开箱多租户 + 自托管的企业场景。

#### 3.9.1 MCP 规范（Tools）——「model-controlled + 人必须在环」

- **怎么做**：MCP 的 `Tools` 能力由 Server 暴露、Client 通过 `tools/list` 发现（支持 `listChanged`、`nextCursor` 分页、按授权变更工具集），通过 `tools/call{name, arguments}` 调用；工具定义含 `name/description/inputSchema`（JSON Schema，默认 draft 2020-12）。官方定位「Tools in MCP are designed to be **model-controlled**」——模型据上下文自动发现并调用；但安全章节明写「there **SHOULD** always be a human in the loop with the ability to deny tool invocations」，并要求 Server「Validate all tool inputs / Implement proper access controls / Rate limit tool invocations / Sanitize tool outputs」，Client「Validate tool results before passing to LLM / Implement timeouts / Log tool usage for audit」。
- **关键取舍**：把工具发现与调用**协议标准化**（跨厂商互操作），但**刻意不规定交互模型**（「the protocol itself does not mandate any specific user interaction model」）——权限/审批/审计全留给实现方。这是「协议层不管治理」的明确边界。
- **对我们意味着什么**：本平台 `cap_mcp_server_def`（DDL `:2045`，`dynamic_discovery=false` + `cap_mcp_server_def_no_dynamic_ck :2065`）与 `McpServerConfigValidator`（`:59-106`）正好补上了 MCP 规范刻意下放的「治理层」——规范说「SHOULD human in the loop」，本平台用 Gate 的审批（`:1295-1372`）把它变成**强制**。这是本平台对 MCP 生态的正确站位：**做规范之上的治理，而非替代规范**。（注：MCP 端到端接线仍未默认开启，见改进点 1。）
- **官方来源**：https://modelcontextprotocol.io/docs/concepts/tools （本次已访问核实）。

#### 3.9.2 OpenAI Function Calling（官方 API 指南页）

- **怎么做**：开发者以 JSON Schema 把函数描述给模型，模型产出 `tool_calls`，**应用侧执行**并把结果回灌——决策在模型、执行在应用。规范含并行函数调用与 `strict:true` 结构化输出。
- **关键取舍**：极致的开发体验与事实标准地位，但**执行在应用侧**意味着护栏是否叠加完全取决于应用开发者；框架默认「拿到 tool_calls 就调函数」（L2 档）。
- **对我们意味着什么**：Function Calling 是本平台「模型只提议」范式的**协议源头**——`ModelResponse.ToolCallRequest`（`ToolInvocationGate.java:1118`）就是它的 Java 侧投影。差别在于 OpenAI 范式的执行权在应用，本平台把执行权收归唯一 Gate（D1）。
- **官方来源（诚实标注）**：官方 API 文档 https://platform.openai.com/docs/guides/function-calling 本次 WebFetch 被 **Cloudflare 拦截**（返回「Sorry, you have been blocked」，Ray ID a5b21301d81da425），**该页未能核实**；本条陈述以 2.1(2) 已核实的官方发布博客（2023-06-13）与 3.9.3 可访问的 OpenAI Agents SDK 官方工具页为准，**不虚构文档细节**。

#### 3.9.3 OpenAI Agents SDK（工具文档）

- **怎么做**：五类工具——Hosted OpenAI tools（WebSearch/FileSearch/CodeInterpreter/HostedMCPTool/ToolSearch/ProgrammaticToolCalling）、Local/runtime tools、`FunctionTool`（把任意 Python 函数包装成工具，从函数名/docstring/类型注解自动生成 schema）、Agents-as-tools、Codex tool。官方原文：「The model still decides when to call them, but your application or configured execution environment performs the actual work」。亦支持 `needs_approval`、`is_enabled`、tool input/output guardrails、超时与并发限制。
- **关键取舍**：开发体验极佳、工具生态丰富；但官方明写两条边界——「`is_enabled` controls visibility and dispatch; it **does not replace authorization** that depends on the tool arguments or the resource being accessed」与「SDK approval **does not provide a sandbox**」。即：可见性开关≠授权、审批≠沙箱。
- **对我们意味着什么**：这两条官方边界正是本平台「呈现层不是防线」铁律的第三方印证——`CapabilityClosureGuard`（`:1161-1170`）是**强制层**闭包校验，不是 `is_enabled` 式隐藏；Gate 的八道闸门是**强制准入**，不是「审批回调」式可选项。可借鉴其 `ToolSearchTool` 延迟加载大量工具 schema 的思路，缓解本平台闭包过大时的 token 膨胀（关联维度 6）。
- **官方来源**：https://openai.github.io/openai-agents-python/tools/ （本次已访问核实）。

#### 3.9.4 Anthropic Tool Use（官方工具使用文档）

- **怎么做**：开发者提供工具定义（`name/description/input_schema`），Claude 决定调用，客户端执行并把 `tool_result` 回灌，循环至最终答复；支持并行工具使用与客户端执行模型。
- **关键取舍**：与 Claude 权限/预算体系一体（见 3.2），但执行在客户端，治理深度依赖宿主；工具定义中的 `description` 是模型选择的关键输入，也因而成为注入面。
- **对我们意味着什么**：`description` 是注入面这一点直接支撑改进点 3 的 `ToolDescriptionSanitizer`；本平台 `cap_tool_def.description` 在治理发布期即受控（`PlatformCapabilityPublishService`），比「客户端运行时各自写 description」更可控。
- **官方来源（诚实标注）**：官方页 `https://docs.anthropic.com/en/docs/build-with-claude/tool-use` 本次 WebFetch 经 `platform.claude.com` 重定向到 `https://www.anthropic.com/app-unavailable-in-region`（**地域限制**），**未能稳定核实正文**；本条为基于 3.2 已核实信息与通用 tool-use 范式的归纳，**具体字段细节标注为未核实**，不臆造。

#### 3.9.5 LangChain Tools（官方工具文档）

- **怎么做**：`@tool` 装饰器把函数变工具（**类型注解即 input schema，docstring 即 description**）；`ToolNode` 在图内执行，并强制「每次 tool_call 必有配套 `ToolMessage`，否则 `ValueError`」；支持 server-side tools、prebuilt tools、headless tools（中断后由外部/人工执行再 resume）。官方原文：「The model decides when to invoke a tool based on the conversation context」。
- **关键取舍**：生态最大、抽象最全；但类型注解生成 schema 是「尽力推断」，且执行默认在图内 node 直接跑（L2），护栏靠 middleware（`wrap_tool_call`）。
- **对我们意味着什么**：`ToolNode` 强制 `ToolMessage` 配套与本平台 `ToolOutcomeRenderer.renderRound`「每个调用都必须有一条 tool 消息、否则供应商 400」（`:99-101`）是**同一问题的两种解法**——本平台是被真实 MiniMax 400 错误倒逼出来的，比框架约束更贴近生产。类型注解 schema 的宽松也反证本平台 `ToolInputSchemaValidator` 闭集与 `ParamPolicyEngine` 类型强制（`:342-356`）的必要性。
- **官方来源**：https://docs.langchain.com/oss/python/langchain/tools （本次已访问核实）。

#### 3.9.6 Google ADK（自定义工具文档）

- **怎么做**：Tool 是「有结构化输入/输出的函数或代码组件」，Python 用 `FunctionTool(func=...)` 包装；**类型提示生成 schema、docstring 是 LLM 的主要描述来源**；工具经 `tools=[...]` 传给 `Agent`/`LlmAgent`；返回建议 `dict` 且含 `status` 字段。官方原文：「The LLM reasons about which tool to use, when, and with what inputs, but the tool itself just executes its designated function」。
- **关键取舍**：code-first、多语言（Python/TS/Go/Java/Kotlin）、部署一体化；但该自定义工具页**未明示 tool confirmation / approval / guardrails**（认证与 `ToolContext.actions` 是流程控制，非审批治理）。
- **对我们意味着什么**：与 OpenAI/Anthropic 同构——「docstring 即描述」再次说明 description 是注入面（改进点 3）；「页内无审批机制」与本平台把审批做成 Gate 强制环节（`:1295`）形成对照。
- **官方来源**：https://adk.dev/tools-custom/ （本次已访问核实）。

#### 3.9.7 LlamaIndex Tool / ToolSpec

- **怎么做**：`Tool` 是通用接口（`__call__` + metadata：name/description/function schema）；`FunctionTool.from_defaults` 把函数变工具（可从类型与 `Annotated` 推断 schema）；`ToolSpec` 是围绕单一服务的工具包（如 GmailToolSpec）；`QueryEngineTool` 把查询引擎/其他 Agent 包装成工具；utility tools（如 `LoadAndSearchToolSpec`）专门处理「工具返回大数据撑爆上下文」。官方原文：「tool selected (and the arguments written) rely strongly on the **tool name and description**」。
- **关键取舍**：RAG 生态集成深、工具包丰富；但工具选择强依赖 name/description（注入面 + 描述质量敏感），执行默认在 Agent 循环内（L2）。
- **对我们意味着什么**：其 `LoadAndSearchToolSpec`「把大结果先索引再检索」与本平台 `ToolOutputLimiter`（8000 封顶）+ 改进点 4 的结构化压缩是**同一问题（大结果回灌）的两种策略**——本平台选「截断 + 原文按权限回查」，LlamaIndex 选「索引后按需检索」，可借鉴后者做 P2 增强。
- **官方来源**：https://docs.llamaindex.ai/en/stable/module_guides/deploying/agents/tools/ （本次访问重定向到 `developers.llamaindex.ai`，内容已核实）。

#### 3.9.8 Semantic Kernel（函数调用文档，Java 视角）

- **怎么做**：插件函数以 `@DefineKernelFunction`（Java）/ `[KernelFunction]`（C#）标注才暴露给模型；SK 把函数序列化为 JSON Schema 随聊天历史发送，模型产出 `tool_calls`，SK 解析→类型转换（marshaling）→执行→把结果作为 `AuthorRole.TOOL` 消息回写，循环至最终答复。**auto function calling 是默认**；Java 在 `auto-invoke=false` 时应用须自己调用函数并写回 TOOL 消息。官方原文：「Auto function calling is **the default behavior** in Semantic Kernel」。
- **关键取舍**：SDK 自动化程度高、类型转换强；但默认自动执行（L2），且官方提醒「schema 越冗长 → token 越多 → 更慢更贵」「返回结果尽量简洁」。
- **对我们意味着什么**：SK 的「只有标注的函数才暴露」与本平台能力闭包（`:1161-1170`）同属「呈现层收窄」，但本平台另有**强制层**校验；SK 的 auto-invoke 默认值反证本平台「禁用 `ToolCallingAdvisor` 自动执行」（`:50-51`）是一条**逆行业默认**的强治理选择。其「返回结果简洁」建议与本平台 `ToolOutputLimiter` 截断留痕（`:39-41`）目标一致。
- **官方来源**：https://learn.microsoft.com/en-us/semantic-kernel/concepts/ai-services/chat-completion/function-calling/ （本次已访问核实，含 Java pivot）。

## 四、我们的实现（源码级解剖）

### 4.1 架构与数据流（关键组件、调用链、数据落点）

**关键组件**
- `RunExecutionLoop`（`agent-worker/.../execute/RunExecutionLoop.java`）：编排器，主循环 `while (steps < snapshot.maxSteps())`，只串「模型调用 → 工具闸门 → 状态提交」（`RunExecutionLoop.java:68` 类头「只做编排」）。
- `ToolInvocationGate`（`agent-worker/.../execute/ToolInvocationGate.java:53`）：**唯一工具执行入口**，禁用 Spring AI 自动执行路径（`ToolInvocationGate.java:50`）。
- `ToolHandler`（`agent-ports/.../tool/ToolHandler.java`）：工具 SPI 端口，契约明确「模型不得绕过服务端授权直接执行」（`ToolHandler.java:13-23`）。
- `McpHandlerProvider` / `HttpToolHandlerProvider`：动态解析 MCP / HTTP 工具，与 native 共用同一条 Gate 路径（`ToolInvocationGate.java:106-124`）。
- `ToolInputSchemaValidator`：闭集 Schema 校验（`ToolInputSchemaValidator.java:27`）。
- `ParamPolicyEngine`：参数策略引擎（三层 AND 合并，`ParamPolicyEngine.java:50`）。
- `ToolOutputLimiter`：结果回灌长度封顶（`ToolOutputLimiter.java:20`，`DEFAULT_MAX_CHARS=8000`）。
- 数据落点：`cap_tool_def`（工具定义，platform 级）、`cap_mcp_server_def`（MCP Server 定义）、`tool_operation`（逻辑操作账本）、`tool_operation_attempt`（每次重试）、`usage_record`（计量）。

**调用链（模型一轮内）**
1. `RunExecutionLoop` 调 `modelGateway.complete(...)` 拿到 `response.toolCalls()`（`RunExecutionLoop.java:897`）。
2. `toolGate.invokeAll(tenantId, task, response.toolCalls())`（`RunExecutionLoop.java:1018`），外层包 `withinRemaining(task, "TOOL_CALL", ...)` 根截止时间封顶（`RunExecutionLoop.java:1017`）。
3. Gate 内部遍历 `calls`，对**每个**调用走闭合集闸门（见 4.2 与 `ToolInvocationGate.java:1115-1480` 的 `invokeAllLegacy`）。
4. 结果经 `ToolOutputLimiter` 截断 → `ToolOutcomeRenderer.renderRound(...)` 回灌（`RunExecutionLoop.java:1164`）。
5. 逐工具写 `run_message`（TOOL 行，含 `tool_operation_id` 回查主键，`RunExecutionLoop.java:1078-1100`）与 `run_event`（TOOL_INVOKED，含 `operationState`，`RunExecutionLoop.java:1043-1069`）。

### 4.2 关键设计决策逐条剖析

| # | 决策 | 为什么 | 代价 | 证据锚点 |
|---|---|---|---|---|
| D1 | **模型永不自动执行**，所有工具调用穿 `ToolInvocationGate` | 安全边界不可绕过；Spring AI `ToolCallingAdvisor` 会跳过全部闸门 | 开发者写工具须经端口，摩擦大 | `ToolInvocationGate.java:50-51`；`ToolHandler.java:13-23` |

| D10 | **MCP/HTTP 与 native 共用同一条 Gate**（`mcpHandlers`/`httpToolHandlers` 不为 null 时注入） | MCP 工具若另开入口，八道闸门全失效 | MCP 接线复杂度高（见改进点 1） | `ToolInvocationGate.java:106-124`；`McpHandlerProvider.java:9-22` |
| D11 | **`dynamic_discovery=false` 且 `stdio` 未启用（V1）** | 动态发现绕过固定清单+指纹；stdio 拉起子进程需独立管控 | MCP 生态广度受限 | `01_platform_ddl.sql:2056,2057`；`McpServerConfigValidator.java:62-79` |
| D12 | **3 次拒终止（strike-out）** | 同一工具累计被拒 3 次即终止 Run，防模型陷入「被拒→重问→再被拒」死循环 | 正常重试 3 次内仍失败则放弃（保守） | `RunExecutionLoop.java:1142-1151`（`rejectionStrikes`） |

### 4.4 我们独有的设计（差异化设计）

1. **「模型只提议、平台负责执行」的硬边界**（D1/D2）。与 L2 框架「模型产出 tool_calls 即自动执行」的本质分歧：本平台把工具执行权完全收归 `ToolInvocationGate`，模型在运行时**没有任何自动执行通道**。这是维度 5 相对多数竞品（OpenAI/Anthropic/LangGraph/ADK/CrewAI 默认自动执行）最直接的差异化。

2. **「操作-尝试」双层账本 + 终态后禁 attempt**（D6）。`tool_operation`（逻辑操作，幂等同键）与 `tool_operation_attempt`（每次重试）分离；`forbid_attempt_after_terminal` 在 DB 触发器层拒绝终态/UNKNOWN 后的新 attempt。这与维度 3 的 fencing/幂等形成「应用层账本 + DB 触发器 + fencing_token」三重防护。

3. **UNKNOWN 不重放、转对账**（D8）。`ToolExecutionException.isResultUnknown()` 触发的 UNKNOWN，立即 `return`（停止后续工具），`ToolOperationReconciliationService` 按稳定幂等键/业务唯一键查询、人工对账、受控补偿。这是「明确失败优于幽灵成功」在工具维度的体现。

4. **MCP/HTTP 与 native 共用同一条 Gate**（D10）。`mcpHandlers`/`httpToolHandlers` 注入后，MCP 工具**不另开执行入口**，否则八道闸门对其全部失效——这是把「开放生态」与「强制护栏」捏合的关键设计。

5. **`dynamic_discovery=false` + `stdio` 未启用（V1）**（D11）。以「配置期拒」而非「运行期拒」守住授权边界（固定清单 + 指纹校验），避免动态发现悄悄改写授权模型（`McpServerConfigValidator.java:19-34` 解释为何必须在写入时拒）。

### 5.2 优势详解（为什么领先）

- **安全边界不可绕过**：竞品（OpenAI/Anthropic/LangGraph/ADK/CrewAI）默认 `tool_calls` 自动执行，护栏是「可选项」；本平台把执行权收归唯一 Gate，模型在运行期**无任何自动执行通道**（D1）。这是结构性优势，不是调参能补。
- **UNKNOWN 状态机 + 终态后禁 attempt**：多数框架对「超时后结果未知」要么重试（危险）要么抛错（丢失上下文）。本平台在 DB 触发器层（`forbid_attempt_after_terminal`）硬性禁止盲目重试，转对账（D8），与维度 3 的 fencing 形成呼应。
- **预算三律 + 双层账本**：每次工具调用都先预留、失败即拒、UNKNOWN 不释放，账本 PRE 早于审批/预算（外键依据，`Agent设计总览.md:171-173`）。竞品中仅 Anthropic 有会话级熔断，无多租户强不超发。

### 5.3 劣势与盲区详解（根因分析）

- **MCP 生态广度落后（能力缺失，非取舍）**：我们**有** `cap_mcp_server_def` 定义表与 `McpHandlerProvider`/`McpTransportPort`/`McpCredentialPort`/`McpManifestPort`/`McpAddressResolverPort` 端口，及 `McpServerConfigValidator`/`McpAddressPolicy`/`McpOpAllowlistNormalizer`/`McpUntrustedOutput` 安全层（见 `agent-application/.../cap/`）。但 `McpHandlerProvider` 在 `ToolInvocationGate` 中**为可空**（`:113`「MCP 未装配」），即**运行期端到端执行接线仍非默认开启**；且我们没有预置的第三方 MCP server 清单（不像 ADK/CrewAI/Agno 开箱即连 Google Drive/Slack 等）。这是**能力缺口**，根因是 V1 优先把「定义+安全」做扎实，执行接线留作改进点 1。
- **无并行工具调用（设计取舍偏向安全）**：当前 `invokeAll` 顺序遍历（`ToolInvocationGate.java:1130`）。这牺牲了吞吐，换取「每次调用独立过闸、UNKNOWN 立即停」的确定性。属**有意取舍**，但代价是简单多工具轮次延迟高（改进点 2）。
- **工具描述/返回值注入防护不完全（能力缺口）**：有 `McpUntrustedOutput` 处理 MCP 不可信输出，但**缺系统化的「工具 description 注入防护」与「返回值结构清洗」**，对照 The Dark Side of Function Calling（arXiv:2407.17915）的 arguments 注入越狱风险，属待补强（改进点 3）。
- **native 工具自校验反模式（实现漂移）**：`GetStudentProfileTool.validate()` 手搓参数检查（`GetStudentProfileTool.java:58-74`），**未走** `ToolInputSchemaValidator`；共享校验器实际只被 MCP/HTTP 工具路径使用。这是与「统一校验」目标相左的实现漂移（改进点 3 直接修复）。

### 5.4 关键分歧点（1-3 个最本质的架构分歧）

1. **「模型自动执行」vs「平台强制 Gate」**。竞品普遍选前者（开发快），本项目选后者（安全硬）。后果：我们工具维度安全强但开发者摩擦大、生态接入慢。
2. **「运行期动态发现工具」vs「固定清单+指纹」**。MCP 本意是动态发现，我们强制 `dynamic_discovery=false`（`01_platform_ddl.sql:2056`），以配置期拒守住授权边界。后果：安全强但生态灵活度低。
3. **「UNKNOWN 重放」vs「UNKNOWN 对账」**。竞品多重试，我们停执行转对账。后果：我们杜绝重复副作用但需维护对账链路（维度 3/11 协同）。

## 六、优缺点总评

### 6.1 我们的优点

- **结构性优势**：唯一 Gate + 禁用自动执行（安全边界不可绕过）；「操作-尝试」双层账本 + 终态后禁 attempt（DB 触发器兜底）；UNKNOWN 对账（防静默失真）。
- **工程性优势**：闭集 Schema 校验「错误即拒」；参数策略三层 AND 合并；预算预留三律 + DB CHECK；取消双保险。
- **领域性优势**：`risk_level` 强制显式声明、`cap_tool_def` 与 `cap_mcp_server_def` 的 platform 级治理定义、MCP 安全层（config/address/op-allowlist/untrusted-output）已成型。

### 6.2 我们的缺点

- **设计取舍导致的代价**：无并行工具调用（吞吐取舍）；MCP `dynamic_discovery=false`（灵活度取舍）。
- **能力缺口**：MCP 运行期端到端接线非默认开启；工具描述/返回值注入防护不完全；native 工具自校验漂移；租户/角色级工具细粒度授权未闭环（见改进点 6）。
- **运维负担**：双层账本写放大；UNKNOWN 对账需人工/定时链路；每工具闸门的检查开销。

### 6.3 每个竞品的优点（简明，带来源）

- **OpenAI Agents SDK**：开发体验佳、tracing/guardrails 开箱、MCP 一等公民（openai.github.io/openai-agents-python）。
- **Anthropic Claude Agent SDK**：MCP native、权限/审批/预算一体化（docs.anthropic.com/en/api/agent-sdk）。
- **LangGraph**：显式状态图、time-travel、trim_messages 生态（docs.langchain.com/oss/python/langgraph）。
- **Google ADK**：自带部署、OpenAPI/MCP 预置、live streaming（adk.dev）。
- **CrewAI**：角色化直观、before_tool_call 拦截、企业层 RBAC/审计（docs.crewai.com）。
- **Agno**：内建多租户安全 + Durable Queue + 开箱护栏（docs.agno.com）。
- **AutoGen**：事件驱动 + Docker 沙箱（已归档，仅参照）。

### 6.4 每个竞品的缺点（简明，带来源）

- **OpenAI/Anthropic/LangGraph/ADK/CrewAI**：默认工具自动执行，护栏需自选；无内建多租户隔离（维度 2 对比）。
- **OpenAI/Anthropic/ADK/CrewAI/Agno**：编排层无内建多租户强预算治理（维度 9 对比）。
- **LangGraph**：工具执行默认自动，护栏靠中间件；无内建多租户。
- **Agno**：强护栏依赖其平台，脱离 AgentOS 减弱。
- **AutoGen**：已归档停维护，不应新选型（竞品报告 §1.2）。

## 七、可优化与改进点（必须可执行）

> 共 6 项，均具体到「文件 / 方法 / 配置 / 接口级」并给验收门禁。

### 改进点 1：MCP 工具接入的完整路线（端到端执行接线）

- **问题陈述**：`cap_mcp_server_def` 定义表与 `McpHandlerProvider` 等端口已存在，但 `ToolInvocationGate` 中 `mcpHandlers` 为可空（`ToolInvocationGate.java:113`），运行期端到端执行接线非默认开启；且缺「worker 如何发现已发布 MCP Server、连接生命周期、超时/重试、权限映射」的明确实现。当前仅验证了「定义+安全层」，未验证「调用」。
- **方案设计**
  1. **发现**：`McpHandlerProvider` 实现从 `JdbcCapMcpServerDefRepository`（`agent-persistence/.../cap/JdbcCapMcpServerDefRepository.java`）读取 `lifecycle_state=PUBLISHED` 的 Server，按 `(tenant_id, server_id)` 解析其固定 `exposed_tool_allowlist`（`cap_mcp_server_def.exposed_tool_allowlist`，`null≠[]` 语义见 `Agent设计总览.md:48`）。
  2. **连接生命周期**：在 `McpTransportPort.connect(serverDef)` 建立 http/sse 连接，`config_fingerprint` 比对防漂移；连接池受 `agent.worker.tool-mcp-conn-pool-size`（fail-closed，缺失即拒启，沿用 `WorkerPolicy` 风格）。
  3. **超时/重试**：每工具调用超时取自 `cap_tool_def.http_timeout_ms` 类比的 `mcp_call_timeout_ms`（上限 300000，与 `cap_tool_def_http_binding_ck` 一致）；重试仅限 `IN_FLIGHT→UNKNOWN` 经对账，**不盲目重试**（复用 D8）。
  4. **权限映射**：`trust_tier`（internal/partner/public，`01_platform_ddl.sql:2058`）→ `ApprovalPolicy` 默认审批强度（public 强制审批、internal 可降）；`exposed_tool_allowlist` 在 `McpOpAllowlistNormalizer`（`agent-application/.../cap/McpOpAllowlistNormalizer.java`）归一化后于 `ToolInvocationGate` 闭包判定处强制。
  5. **接线点**：`ToolInvocationGate.findHandler(call.toolName())`（`ToolInvocationGate.java:1712`）增加 `mcpHandlers.resolve(toolName)` 分支；`mcpHandlers` 改为**非空必装配**（production 装配失败即拒启，fail-closed）。
- **预期收益（可度量）**：MCP 工具端到端调用成功率 ≥99.5%（集成测试口径）；新增一个 MCP Server 的接入工时从「需改代码」降为「配置 + 治理发布」；通过 `McpSecurityBehaviorTest` 等既有测试套件覆盖。
- **实施成本与风险**：改动面中等（ports 实现 + Gate 接线 + 配置）；迁移影响低（不影响 native/http 路径）；需灰度（先 internal trust_tier）。
- **优先级**：**P1**；排期：里程碑 M（MCP 投产）。
- **验收方式（可执行门禁）**：
  1. 新增 `McpEndToEndIT`：发布一个 `lifecycle_state=PUBLISHED` 的 `cap_mcp_server_def`（http，trust_tier=internal，`exposed_tool_allowlist=[echo]`），worker 自动发现并调用其 `echo` 工具，断言 `tool_operation.state=SUCCEEDED` 且 `tool_operation_attempt` 仅 1 行。
  2. 断言 `McpHandlerProvider` 在 production 装配为**非空**（单元测试 `ToolWiringTest` 已有，扩展断言 mcpHandlers 非 null）。
  3. 当 `dynamic_discovery=true` 时，`McpServerConfigValidator.validate` 仍返回违规（回归 `McpServerConfigValidatorTest`）。
  4. **撤点反证**：临时把 `mcpHandlers` 置 null，重跑 `McpEndToEndIT` 必须 FAIL（证明接线确为唯一通道，而非绕过）。

### 改进点 2：工具级并发与 DAG 依赖（parallel_tool_calls 支持）

- **问题陈述**：`invokeAllLegacy` 对 `calls.values()` 顺序 for 循环（`ToolInvocationGate.java:1130`），无并行、无依赖分析。一轮内多个独立 `tool_calls`（如同时查两个只读资料）被迫串行，延迟随工具数线性增长。
- **方案设计**
  1. 在 `cap_agent_def` / execution_snapshot 增加 `tool_parallelism` 开关（`boolean`，默认 `false`，fail-closed：缺省即串行）。
  2. `ToolInvocationGate.invokeAll` 在开关开启时，对 `calls` 做依赖分析：若调用间无参数依赖（各自参数仅来自模型原文、互不引用返回值）→ 归入同一并行批；存在依赖 → 顺序（DAG 拓扑序，可借鉴 `docs/Agent设计总览.md` 的编排图）。
  3. 并行批内**每个调用仍独立过完整 Gate**（幂等/账本/审批/预算均为 per-operation，天然可并发）；并发度受 `agent.worker.tool-parallelism`（默认 1，>16 拒，沿用 `WorkerPolicy` fail-closed 风格）。
  4. **安全约束**：`risk_level=WRITE_EXTERNAL` 或需审批（`requiresApproval`）的工具**强制串行**且单发（避免并行副作用不可对账）；仅 `READ` 或已预批准工具可并行。
  5. 取消/`CancelGuard` 在并行批内任一工具成功后即整体生效，UNKNOWN 任一个即整批停（沿用 D8/D9）。
- **预期收益（可度量）**：含 N 个独立只读工具的一轮调用 P95 延迟从 `N×单工具` 降至 `ceil(N/parallelism)×单工具`（实测目标 ≥40% 降幅，压测口径）；fencing/幂等语义不变。
- **实施成本与风险**：改动面中（新增依赖分析 + 并发调度）；风险是并行下 UNKNOWN/取消的时序复杂化——故 WRITE/需审批工具强制串行兜底。
- **优先级**：**P2**；排期：里程碑 N（吞吐优化）。
- **验收方式（可执行门禁）**：
  1. 单测 `ToolParallelismTest`：同一轮 3 个 `READ` 无依赖工具，`tool_parallelism=true` 时断言 3 个 `tool_operation` 并发创建（fencing_token 各自有效）、最终均 SUCCEEDED、attempt 各 1 行。
  2. 单测：含 1 个 `WRITE_EXTERNAL` 工具时，无论开关如何，断言其**串行且单独执行**（不进入并行批）。
  3. 集成测试：并行批中第 2 个工具抛 `isResultUnknown()`，断言整批立即停止、`tool_operation` 中该操作 state=UNKNOWN、其余已完成者保持 SUCCEEDED（不回滚）。
  4. **撤点反证**：关掉 `tool_parallelism` 开关，上述测试必须退化为串行行为（证明开关真实生效）。

### 改进点 3：工具参数校验统一框架（抽离自校验 + 注入防护）

- **问题陈述**：`ToolInputSchemaValidator` 是共享闭集校验器，但 **native 工具 `GetStudentProfileTool.validate()` 手搓参数检查**（`GetStudentProfileTool.java:58-74`），未走该器；且缺「工具 description 注入防护」与「返回值结构清洗」（对照 The Dark Side of Function Calling arXiv:2407.17915 的 arguments 注入）。这违反 `ToolInputSchemaValidator.java:15-25` 自己写的「两处各写一遍必然漂移」警告。
- **方案设计**
  1. **统一入口**：`ToolHandler.validate()` 契约改为「由 Gate 统一调用 `ToolInputSchemaValidator.validate(input_schema, args)` + `ParamPolicyEngine.evaluate(...)`」；native 工具的私有校验逻辑删除，`GetStudentProfileTool` 改为只声明 `INPUT_SCHEMA` 与 `param_policies` 并委托（`ToolHandler.java:36` 强化为「实现不得自校验，由 Gate 调用共享器」）。
  2. **注入防护（description）**：新增 `ToolDescriptionSanitizer`（ports 层）：扫描 `cap_tool_def.description` 与 `cap_skill_def.purpose`，标记/拒绝含「忽略先前指令」「system:」等指令性片段（参考 OWASP LLM01），治理发布期（`CapExecutionFlow` 步骤 6 后）拦截，落 `cap_decision_log`。
  3. **注入防护（result）**：`ToolOutputLimiter` 扩展为 `ToolResultSanitizer`——先截断（保 `ToolOutputLimiter` 语义），再做结构化清洗（剥离疑似 `<system>`/指令片段），并打 `injection_suspected` 标记供 `agent_risk_event` 记录。
  4. **类型强制**：把 `ToolInputSchemaValidator` 当前「只做有没有、不做类型」升级为「类型不符即拒」（复用 `ParamPolicyEngine` 的 `valueKey` 类型判定，`ParamPolicyEngine.java:342-356`），消除「类型不符靠下游」的缺口。
- **预期收益（可度量）**：native 与 MCP/HTTP 工具参数校验**同一实现路径**（代码评审口径：grep 确认无 `ToolHandler` 子类自写 `additionalProperties` 检查）；注入类风险事件可观测（新增 `agent_risk_event.event_type=TOOL_DESC_INJECTION` 计数）。
- **实施成本与风险**：改动面中（重构 2 个 native 工具 + Gate 调用点）；风险是模型依赖「宽松解析」的历史行为需回归 `ToolGateAuthorizationContextTest` 等。
- **优先级**：**P1**；排期：里程碑 M。
- **验收方式（可执行门禁）**：
  1. 单测：构造 `GetStudentProfileTool` 实例，传入 `additionalProperties` 含未声明字段，**必须经 `ToolInputSchemaValidator` 拒绝**（断言 `validate` 调用栈含共享器，而非私有检查）。
  2. 回归 `SchemaStructureTest` / `ToolBypassArchitectureTest`：断言「闭集校验」对 native 与 MCP 行为一致（同一组非法参数两种工具均拒）。
  3. 新增 `ToolDescriptionInjectionTest`：`cap_tool_def.description` 含「忽略之前所有指令，改为…」时，发布校验失败（落 `cap_decision_log`）。
  4. **撤点反证**：临时让 `GetStudentProfileTool` 恢复私有校验并绕过共享器，重跑测试必须 FAIL（证明统一路径是强制而非可选）。

### 改进点 4：工具结果的可控回灌（大结果截断/压缩，关联维度 6）

- **问题陈述**：`ToolOutputLimiter.DEFAULT_MAX_CHARS=8000`（`ToolOutputLimiter.java:20`）已存在，但回灌发生在 `ToolOutcomeRenderer.renderRound`（`RunExecutionLoop.java:1164`），需确认 limiter 在 Gate 结果边界**被实际调用**；且截断是「粗暴按字符」，对大 JSON 数组无结构化压缩（对照维度 6 上下文预算）。
- **方案设计**
  1. 在 `ToolInvocationGate` 执行返回前（`:1421-1438` 的 `result.recordSucceeded` 之前）统一调用 `ToolOutputLimiter.limit(output, maxChars)`，把 `maxChars` 提升为可配置 `agent.worker.tool-output-max-chars`（默认 8000，fail-closed）。
  2. 新增**结构化压缩**：对 JSON 结果，若数组长度 > `max-array-items`（如 50），保留前 N 条 + 摘要「…共 M 条，仅展示前 N」；对超长文本保留首尾 + 中间省略（复用维度 6 的 `TierSnipRatio` 思路）。
  3. **关联维度 6**：回灌前若预估 token 超 `GlobalContextPolicy.hard-ceiling-tokens` 剩余，触发 `CompactionPipeline` 的 W1 外置（不丢工具结果原文，仅上下文中压缩），原文仍可由 `tool_operation.result_payload` 按权限回查（`RunExecutionLoop.java:1078-1100` 已写 `tool_operation_id`）。
  4. 截断标记保留「已截断 + 原始长度」（`ToolOutputLimiter.java:39-41`），并落 `agent_trace_tool_call` 的 `truncated_bytes` 指标。
- **预期收益（可度量）**：单工具返回 100KB 时，上下文增量从 100KB 降至 ≤8KB（压测口径）；因「上下文超限」导致的 Run 失败数下降（维度 6 指标）。
- **实施成本与风险**：改动面小（Gate 结果边界 + 新增压缩器）；风险是过度截断致模型基于残缺数据误判——故保留「已截断」标记 + 原文可回查。
- **优先级**：**P1**；排期：里程碑 M。
- **验收方式（可执行门禁）**：
  1. 单测 `ToolOutputLimiterTest`：输入 20000 字符，断言输出长度 = maxChars + 截断标记，且含「原始长度 20000」。
  2. 集成测试 `WorkerToolRoundPruningKeepsPairedMessagesIT`（已存在，扩展）：工具返回超大 JSON 数组，断言回灌后 `run_message` 内容 ≤ 上限且 `tool_operation.result_payload` 存全量。
  3. **撤点反证**：临时移除 Gate 处的 limiter 调用，重跑上述 IT 必须 FAIL（证明截断确在结果边界强制）。

### 改进点 5：工具调用的可观测埋点（每调用延迟/成本/成败，关联维度 10）

- **问题陈述**：`RunExecutionLoop` 已有 `observerChain.onToolCallComplete(...)` 钩子（`RunExecutionLoop.java:1033-1038`），但仅驱动内存观测链；**未持久化每工具调用的延迟/成本/成败**到可聚合的事实表（维度 10 的 `agent_trace_tool_call` 目前只存计数/求和，`01_platform_ddl.sql:841`），缺 P95 延迟与单次成本。
- **方案设计**
  1. 在 `ToolInvocationGate` 执行前后打 `toolStart/toolEnd` 时间戳（复用 `RunExecutionLoop.java:1012,1028` 的 `toolStart/toolEnd` 思路，下沉到 Gate 每个 operation 级），计算 `duration_ms`。
  2. 新增 `ToolCallSpan` 事实（落 `agent_trace_tool_call` 扩列或新表 `tool_call_span`：`tenant_id, run_id, operation_id, tool_name, risk_level, duration_ms, cost_amount, outcome, attempt_count`），写入走 `INSERT ... ON CONFLICT DO UPDATE` 幂等（沿用维度 10 指标确定函数风格）。
  3. 暴露 Prometheus：`tool_call_duration_seconds{tool,risk_level,outcome}`（Histogram）、`tool_call_cost_total{tool}`；复用 `MicrometerAuthzMismatchMetrics` 同类 Micrometer 注册方式。
  4. **关联维度 10**：`ToolCallSpan` 与 `agent_trace_metric` 同源（`tenant_id+run_id`），Grafana 可直接 JOIN。
- **预期收益（可度量）**：工具维度 P95 延迟、单次成本、失败率可在 Grafana 实时看板（维度 10 交付物）；异常工具（高频失败/高成本）可告警。
- **实施成本与风险**：改动面小（Gate 计时 + 持久化 + metric）；风险是写放大——故 `tool_call_span` 仅对**终态 operation** 写一行（attempt 不单列）。
- **优先级**：**P2**；排期：里程碑 N。
- **验收方式（可执行门禁）**：
  1. 集成测试：跑一次含 2 个工具的 Run，断言 `tool_call_span` 出现 2 行，`duration_ms>0`，`outcome` 与 `tool_operation.state` 一致。
  2. 断言 Prometheus `tool_call_duration_seconds` 计数器在非测试环境可被 scrape（或一个单元测试断言 MeterRegistry 注册了 Histogram）。
  3. **撤点反证**：移除 Gate 计时埋点，重跑断言 `tool_call_span` 无 `duration_ms` 写入（证明门禁非装饰）。

### 改进点 6：工具权限的细粒度（按工具 × 租户 × 角色最小授权，关联维度 7）

- **问题陈述**：当前授权是 `AuthorizationService.isAuthorized(TOOL_INVOKE, toolName)`（`ToolInvocationGate.java:1196-1197`），即「能否调某工具」的单维判定；**无租户级工具白名单、无角色级工具约束**。一个租户若被治理授予某工具，其下所有角色（含受众角色 STUDENT/PARENT/TEACHER）均可调，违背最小权限（维度 7 的 `isAudienceOnly` 只收窄可见范围，未收窄工具调用权）。
- **方案设计**
  1. 新增 `tenant_tool_grant`（`tenant_id, tool_id, role, allowed`）——租户级工具白名单（platform 级 `cap_tool_def` 是「存在性」，tenant 级是「可用性」）。表挂 RLS（`FORCE ROW LEVEL SECURITY`，沿用 42 表策略风格）。
  2. 在 `ToolInvocationGate` 闭包判定（`:1161-1170` 的 `closureGuard`）之后、Schema 校验之前，插入 `TenantToolGrantGuard`：查 `tenant_tool_grant`，若 `(tenant, tool, principalRole)` 无 `allowed` 行 → 拒（原因码 `TOOL_NOT_GRANTED_TO_TENANT`）。
  3. **与维度 7 协同**：`AuthorizationService.Actions.TOOL_INVOKE` 升级为带 `(toolName, role)` 维度的判定（参考 `Actions` 已极细的拆分风格，`AuthorizationService.java:59-177`），`authz_decision_log` 记录 `resource_type=tool, resource_id=toolName, scope=role`。
  4. 治理发布期：`cap_tool_def` 发布时可选绑定「默认授权租户/角色」（落入 `tenant_tool_grant` 初始行），`AgentOverrides` 可 `removeTools` 进一步收窄（`01_platform_ddl.sql:1631`）。
- **预期收益（可度量）**：租户 A 被撤销某高风险工具后，其下所有角色（含 ADMIN）调用该工具 100% 在 Gate 被拒（`authz_decision_log` 可查）；越权调用尝试计入 `agent_risk_event.UNAUTHORIZED_CALL`（维度 7/10 协同）。
- **实施成本与风险**：改动面中（新表 + Gate 新守卫 + 授权维度扩展）；迁移：已发布工具的存量授权需初始化 `tenant_tool_grant`（默认「同 closure 即授权」避免误伤）。
- **优先级**：**P2**；排期：里程碑 N。
- **验收方式（可执行门禁）**：
  1. 单测 `TenantToolGrantGuardTest`：某租户 `tenant_tool_grant` 中无某工具 `allowed` 行，断言 `ToolInvocationGate` 返回 `rejected` 且原因码 `TOOL_NOT_GRANTED_TO_TENANT`，即便该工具在 closure 内。
  2. 断言 `authz_decision_log` 新增一行 `resource_type=tool, permitted=false, reason_code=TOOL_NOT_GRANTED_TO_TENANT`。
  3. 回归 `ToolBypassArchitectureTest`：确保新守卫不破坏既有「closure 拦截」语义。
  4. **撤点反证**：临时禁用 `TenantToolGrantGuard`，重跑单测必须 FAIL（证明细粒度授权真实生效，而非被 closure 默认放行掩盖）。

## 八、其他有价值的横向对比

### 8.1 与本项目其他维度的耦合与相互约束

1. **维度 3（状态持久化/可恢复性）**：`tool_operation.idempotency_key` + `fencing_token`（`01_platform_ddl.sql:2991,2995`）与维度 3 的 fencing 共用同一套防脑裂语义；`forbid_attempt_after_terminal`（`:516-539`）与维度 3 的 `enforce_fencing_on_write` 是「应用层账本 + DB 触发器」双重防护的范例。**改工具维度（如加并行）必须同步验证 fencing 在并发下不互相覆盖**（改进点 2 已约束 WRITE 串行）。
2. **维度 7（权限与护栏）**：`TOOL_INVOKE` 是维度 7 动作矩阵的一员；工具调用前「执行时重新授权」（`ToolInvocationGate.java:1195-1201`）即维度 7 的 `authzVersion` 强一致读在工具维度的落地。改进点 6 把维度 7 的「角色×任务」细化到「工具×租户×角色」。
3. **维度 9（成本与预算）**：每次工具调用先预留（`reserve-per-tool-call=0.50`，`application.yml:513`），与维度 9 的 `budget_account`/`budget_reservation` 共用额度域；工具预算失败即拒是维度 9「DB 强制不超发」在工具维度的执行点。
4. **维度 6（上下文管理）**：工具结果回灌直接撑大上下文（改进点 4 关联）；`ToolOutputLimiter` 与维度 6 的 `CompactionPipeline` 是「结果侧截断」与「上下文侧压缩」的互补。
5. **维度 10（可观测性）**：工具调用埋点（改进点 5）是维度 10 指标的事实来源之一；`agent_trace_tool_call` 与 `tool_call_span` 同源。
6. **维度 13（HITL）**：需审批工具在 Gate 内 `requestApproval` → Run 迁 `WAITING_APPROVAL`（`RunExecutionLoop.java:1113-1138`），审批决定到达由 `ApprovalDecidedWakeupConsumer` 唤醒 RESUME——工具维度是 HITL「运行期审批」的主要触发面。

### 8.2 与非 agent 领域成熟做法的对照

- **数据库事务（ACID）**：本平台 `tool_operation`/`tool_operation_attempt` 的「操作-尝试」双层 + 终态不可迁出，类比 DB 的「事务 + 日志（WAL）」——逻辑操作像事务，attempt 像 redo 日志，UNKNOWN 像「事务状态未知」需对账。可借鉴：DB 的「两阶段提交」思想可用于跨工具 DAG 的原子性（改进点 2 的 DAG 可参考 Saga 模式）。
- **金融支付风控**：预算预留三律（失败即拒 / FAILED 非 UNKNOWN / UNKNOWN 不释放）与支付的「预授权-扣款-撤销」语义一致；金融的「对账文件」即本平台的 `ToolOperationReconciliationService`。
- **API 网关**：`ToolInvocationGate` 等同 API 网关的「认证-限流-鉴权-审计」四件套；`rate limit` 对应维度 9，`circuit breaker` 可借鉴为「同一工具连续 N 次 UNKNOWN 自动熔断转人工」（可并入改进点 5 的告警）。
- **合规（SOX/等保）**：「操作-尝试」双层账本 + `audit_record` 不可改，满足等保「操作可追溯、审计不可篡改」要求（维度 10 协同）。

### 8.3 反向思考：若从头重做本维度，我们会怎么设计？

- **保留**：唯一 Gate + 禁用自动执行（这是本平台最值钱的设计，重做也选）；「操作-尝试」双层账本 + UNKNOWN 对账；预算预留三律；`dynamic_discovery=false` 的保守姿态。
- **调整**：① 从第一天就把 **MCP 端到端接线**作为 P0（而非先定义后接线），避免「有定义无调用」的半成品；② 参数校验**从第一版就是统一框架**（不留 native 自校验的漂移窗口，见改进点 3）；③ 工具调用**原生支持并行 + DAG**（而非后期补），因为并行与 fencing/幂等应一并设计而非 retrofit；④ 工具描述/返回值注入防护**作为 Schema 定义的一部分**内建（而非事后补 `McpUntrustedOutput`）。
- **诚实取舍**：若重做仍会牺牲「生态即开即用」（不预置大量第三方工具）以换安全——这是产品定位（强治理 SaaS）决定的，不是技术债。

### 8.4 深度补充：与相邻维度的精确交界（改一处必须联动一处）

> 8.1 已列六条耦合。本节进一步把「工具 / 函数调用（维度 05）」与最容易发生**责任真空或重复实现**的两个维度——**维度 07 权限与护栏**、**维度 11 可靠性与故障处理**——的分工边界画清，并补一条 05→10 的采集交界（铁律 5）。

#### 8.4.1 ↔ 维度 07（权限与护栏）：分工是「谁定义授权规则」 vs 「谁在执行时消费它」

| 关注点 | 维度 05（本维度）负责 | 维度 07 负责 | 交界锚点 |
|---|---|---|---|
| 授权动作定义 | 消费 `TOOL_INVOKE` 动作，不重定义权限矩阵 | 定义 `AuthorizationService.Actions`（含 `TOOL_INVOKE`）与角色集合 | `AuthorizationService.java:59-177` |
| 执行时重授权 | 在 Gate 内**每次工具调用**触发 `isAuthorized(TOOL_INVOKE, toolName)` | 提供 `authzVersion` 强一致读与撤销语义 | `ToolInvocationGate.java:1195-1201` |
| 闭包可见性 vs 强制 | 强制层闭包校验（执行前拦），不依赖「模型看不见」 | 呈现层能力闭包（模型可见工具集） | `ToolInvocationGate.java:1161-1170` |
| 拒绝留痕 | 记录 `rejected` 原因码并回灌模型 | 聚合 `authz_decision_log` 与风险事件 | `ToolInvocationGate.java:1143-1149` |
| 细粒度授权 | 提出「工具×租户×角色」需求（改进点 6） | 承载 `tenant_tool_grant` 与授权维度扩展 | 改进点 6 / 7.7 ⑥ |

- **交界风险**：本维度若在 Gate 内**自行缓存授权结论**（为提速跳过强一致读），会直接破坏维度 07 的「撤销即时生效」——租户撤销权限后旧 Run 仍可执行工具。**约束**：授权判定必须走维度 07 的实时接口，不得在 05 侧缓存。
- **反向验证**：把 `isAuthorized(TOOL_INVOKE, ...)` 换成进程内缓存 → 维度 07 的「撤销后调用被拒」角色×任务用例必须变红；若不变红，说明该保障是假绿（铁律 6/17）。

#### 8.4.2 ↔ 维度 11（可靠性）：分工是「UNKNOWN 的处置决策」 vs 「UNKNOWN 的收敛通道」

这是最易重复实现的交界，也是本次「静默空转」发现的落点：

| 环节 | 维度 05（本维度） | 维度 11 | 交界锚点 |
|---|---|---|---|
| UNKNOWN 判定 | Gate 内 `isResultUnknown()` → 落 `tool_operation.state=UNKNOWN`、禁新 attempt、立即停 | 定义统一失败分类与告警聚合 | `ToolInvocationGate.java:1442-1452`、`DDL:525-544` |
| UNKNOWN 收敛 | **定义策略**：查下游事实、不猜、不盲目重试、不释放预算 | **承载机制**：对账调度 / 差错处理 SLA / 告警 | `ToolOperationReconciliationService.java:86-120` |
| 对账服务接线 | 发现「无生产调用方」缺口，提出装配（I-6） | 落实调度与 SLA 口径一致 | 本维度 4.6.3 / 7.8 I-6 |
| 终态语义 | HTTP 404/403/401 → 显式终态不重试；TIMEOUT → 可重试/UNKNOWN | 统一「终态不得伪装临时故障」 | `HttpBackedToolHandler.java:133-149`、铁律 15 |

- **关键纠偏（诚实）**：本次复核确认 `ToolOperationReconciliationService` **无生产调用方**（4.6.3 四问判定）——它不是「维度 11 已实现的对账通道」，而是「05 定义了对账策略、却没有把策略接到任何执行者」。**约束**：对账逻辑**单一实现**，维度 05 定义策略与落账，维度 11/本维度 bootstrap 承载调度；禁止各起一个 job 造成「对账两次、预算重复释放」（Sev-0）。
- **联动门禁**：I-6 同时属于 05 与 11——实施时维度 11 的对账 SLA 口径必须与 `grace-ms` 一致；两条维度的「UNKNOWN 禁 attempt / 不释放预算」断言必须同时变红/变绿。

#### 8.4.3 ↔ 维度 10（可观测性）：采集交界——双通道按 eventType 分流，绝不复用执行命令

- **交界**：本维度每次工具调用产生两类信号——**业务事件**（`run_event` TOOL_INVOKED，走 SSE/DB 事实源）与**观测指标**（`observerChain.onToolCallComplete` → `agent_trace_tool_call` / `tool_call_span`，`RunExecutionLoop.java:1033-1038`）。二者在改埋点（I-5）时最易混淆。
- **铁律 5 硬约束**：双通道消息必须按 **eventType 分流**，否则终态 Run 被重跑（Sev-0）；**采集绝不复用 `agent.run.execute`**。即：观测埋点走独立钩子/通道，不得借用业务执行的命令路径，也不得让采集消息被当成唤醒/执行命令消费。
- **反向验证**：让采集消息落到 dispatch 消费路径 → 终态 Run 被重跑的角色×任务用例必须变红（铁律 5）；`tool_call_span` 行数与 `agent_trace_tool_call` 同源（tenant+run）断言在维度 10 看板一致性测试中验证。

#### 8.4.4 三条交界的统一原则

1. **单一权威源**：授权判定走 07 的实时接口（不在 05 缓存）；工具事实走 Gate 的账本（不在维度间各写一份）。
2. **单一实现点**：UNKNOWN 对账、参数策略、HTTP 终态分类各只有一份实现（05 定义策略，07/11/10 承载机制），禁止跨维度重复造。
3. **联动反向验证**：任一维度改动交界锚点（`isAuthorized`、`ParamPolicyEngine` 灰度开关、`reconcileAll` 接线、eventType 分流），必须对相邻维度的 IT 做「撤点反证」（铁律 6/17），确认相邻断言随之变红——若不变红，说明该维度保障是假绿。

## 九、对产品演进的启发

### 9.1 本维度支撑的产品能力（用户可感知）

- **可信的工具执行**：用户/租户可确信「每一步工具调用都经过授权、预算、审批」，且可追溯（「点击 TOOL 消息展开 tool_operation 详情」，`RunExecutionLoop.java:1078`）。
- **可控的成本**：每次工具调用占用预算、超预算即停，租户不会被意外账单（维度 9 协同）。
- **安全的人机协同**：高风险工具必须人工审批后才执行（维度 13 协同）。
- **故障可诊断**：工具调用失败/未知均有账本与对账，不出现「幽灵成功」。

### 9.2 演进路线图

- **近期（里程碑 M，P1）**：
  - 改进点 1（MCP 端到端接线）投产；
  - 改进点 3（统一校验 + 注入防护）；
  - 改进点 4（结果可控回灌）。
  - **验收标准**：`McpEndToEndIT`/`ToolDescriptionInjectionTest`/`WorkerToolRoundPruningKeepsPairedMessagesIT` 全绿；native 与 MCP 校验同源（grep 无私有校验）。
- **中期（里程碑 N，P2）**：
  - 改进点 2（并行 + DAG）；
  - 改进点 5（每调用埋点看板）；
  - 改进点 6（租户×角色细粒度授权）。
  - **验收标准**：并行压测延迟降幅 ≥40%；Grafana 工具维度看板上線；`TenantToolGrantGuardTest` 全绿。
- **远期（生态期）**：
  - MCP server 市场 / 预置第三方工具清单（对标 ADK/CrewAI/Agno）；
  - 跨工具 DAG 的 Saga 式原子编排；
  - 工具描述/返回值注入的模型级防护（对照 The Dark Side of Function Calling）。

### 9.3 风险清单（做这一步可能踩的坑）

1. **MCP 接线引入新攻击面**：`stdio` 未启用是 V1 刻意，若远期放开须配套可执行文件白名单（McpServerConfigValidator 注释已警示，`McpServerConfigValidator.java:25-27`）——违反铁律 8（fail-closed）不得静默放行。
2. **并行化破坏 UNKNOWN 语义**：并行批内 UNKNOWN 必须整批停（改进点 2 已约束），否则会出现「部分成功部分未知」难以对账——关联铁律 15（终态/权限错误不得伪装临时故障）。
3. **统一校验回归误伤**：native 工具改为委托共享器后，模型历史「宽松解析」行为需全回归（改进点 3 验收含 `ToolBypassArchitectureTest`）。
4. **细粒度授权初始化遗漏**：存量租户缺 `tenant_tool_grant` 默认行会导致误拒（改进点 6 已要求默认「同 closure 即授权」初始化）。
5. **埋点写放大**：`tool_call_span` 仅终态写一行（改进点 5 已约束），否则高频调用拖慢主链路——关联铁律 17（静态守卫≠运行时成立，需真实交互驱动）。

### 9.4 一句话结论

本平台在「工具调用的**安全可控度**」（唯一 Gate、双层账本、UNKNOWN 对账、预算三律）上是本次对比框架里**最强**的，但在「**生态开放性**」（MCP 端到端接线、并行、预置工具）上仍是**能力缺口**而非设计取舍——补齐这些缺口（改进点 1/2/3）且不牺牲既有的强制护栏，是本维度接下来的核心命题。
