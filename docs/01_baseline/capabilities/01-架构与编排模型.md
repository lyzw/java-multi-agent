## 一、维度定义与评估坐标系

### 1.1 这个维度到底解决什么问题（问题陈述，不谈实现）

"架构与编排模型"回答的不是"agent 能干什么"，而是"**一次 agent 执行的生命周期由谁驱动、由谁决定下一步、状态存在哪里、崩溃后如何恢复**"这一组元问题。它决定了：

- 一个 `run`（执行实例）的**控制流**是显式声明（图、工作流）还是隐式涌现（LLM 自主决定）；
- 多步执行之间的**状态**是落在内存、落在专用持久层、还是落在业务数据库；
- 当进程崩溃、网络分区、消息重投时，**不变量**（终态不可迁出、不重复执行副作用、不越权）由谁、在哪一层保证；
- 多 agent 协作时，**委派关系**是被显式建模为一棵树，还是散落在一堆对话消息里。

这一维度是后续所有维度（状态持久化、流式、工具、权限、可靠性、HITL）的**承载骨架**——骨架选错，后面的能力要么无处附着，要么在每个进程里各自重造一遍。

### 1.2 能力分层的四档模型（通用分层法）

按"状态机/不变量由哪一层强制"给出四档，从弱到强：

| 档位 | 名称 | 状态/不变量由谁持有 | 代表形态 | 典型代价 |
|---|---|---|---|---|
| **L0 无编排** | 一次性请求/响应 | 无状态，调用方自己管 | 纯 `chat/completions` 单轮 | 多步、恢复、隔离全靠调用方手搓 |
| **L1 应用层编排** | SDK/库内编排 | 进程内存 + 应用层 if/状态变量 | OpenAI Agents SDK、Anthropic Agent SDK、AutoGen | 崩了内存丢、不变量靠开发者自律 |
| **L2 框架层持久化编排** | 图 + 持久化 checkpointer | 框架提供的专用持久层（PostgresSaver 等） | LangGraph、Google ADK（Session/Memory） | 状态与业务库分离，跨库一致性需自管 |
| **L3 数据层强制编排** | 状态机下沉到存储触发器 | 业务数据库 + DB 触发器硬守卫 | **本平台（DB 驱动 + 事件唤醒 + 快照定上限）** | 开发侧不够"轻"，缺可视化 DSL |

**判定**：本平台落在 **L3**，是本次对比的全部竞品里唯一把"状态跃迁不变量"下沉到数据库触发器层强制的方案。L0–L2 的不变量本质上是"建议"，L3 的不变量是"存储层拒绝写入"。

### 1.3 评估坐标系：5 个评价轴

| 轴 | 含义 | 观测方式（如何度量） |
|---|---|---|
| **强制程度** | 不变量（终态不可迁出、唯一执行者）由哪一层强制 | 注入非法状态跃迁/重复写入，看是否被拒绝；是否被应用层 bug 绕过 |
| **可恢复性** | 进程崩后能否从任意点续跑、不重复副作用 | 杀 Worker 进程 → 观察 run 是否收敛到终态、副作用是否恰好一次 |
| **状态持有单一性** | 权威状态源是否唯一（避免内存/缓存/DB 多副本分叉） | 检查是否有"内存态 + DB 态"两套真相，更新顺序是否可竞态 |
| **可审计性** | 谁在何时改变了 run 状态、可否复盘 | 是否存在不可变的执行事实表（run_step/run_event） |
| **失败可诊断性** | 卡死/孤儿 run 能否被定位与收敛 | 注入"领取后崩溃"，看是否产生永久卡死或孤儿 |

## 二、理论体系（必须引用真实出处）

### 2.1 核心理论/概念框架（≥3 个，逐一给真实出处）

#### (1) ReAct：推理与行动交织的循环范式
- **出处**：Yao, Zhao, Yu, Du, Shafran, Narasimhan, Cao, *"ReAct: Synergizing Reasoning and Acting in Language Models"*, arXiv:2210.03629, 2022（ICLR 2023 Oral）。
- **定义**：Thought–Action–Observation 三元循环——模型每轮交替产生"思考"（规划/纠错）与"动作"（调用外部工具），动作返回成为"观察"喂回下一轮。它把纯 CoT 推理与工具调用统一到一个轨迹里。
- **与本维度的关系**：ReAct 定义了 agent 编排最底层的"循环单元"。本平台的 `RunExecutionLoop` 主循环（`while (steps < snapshot.maxSteps())`）正是这一循环的工程实现——只不过循环上限取自**快照**而非模型自身意愿。

#### (2) Plan-and-Solve / Plan-and-Execute：先规划后执行的两段式
- **出处（已核实）**：Wang et al., *"Plan-and-Solve Prompting: Improving Zero-Shot Chain-of-Thought Reasoning by Large Language Models"*, arXiv:2305.04091, 2023。另有 LangChain 工程化模式 "Plan and Execute"（2023，把 Planner / Executor / Replanner 拆成角色，允许人工审阅计划后再执行）。
- **定义**：把"列计划"与"执行计划"分离，先让模型产出结构化步骤清单（可审查、可修改），再逐步兑现；失败的步可触发 replan。
- **诚实标注**：任务书引用的 "Plan-and-Execute（Lamping et al. 2023）" **未能核实到对应论文**。可验证的奠基文献是 Wang et al. 的 Plan-and-Solve（arXiv:2305.04091），以及 LangChain 的 Plan-and-Execute 工程模式。**本报告以下采用已核实出处，不臆造 Lamping 论文。**
- **与本维度的关系**：本平台的 `cap_agent_def.orchestration` 声明 `LEAF/ROUTER/SEQUENTIAL`（多步编排），`RunConfigSnapshot` 在创建时固化 `maxSteps/maxLlmCalls/timeout`——这是"计划（声明式编排约束）与执行（运行期快照）分离"的强约束版本，比提示词层面的 Plan-and-Solve 更硬。

#### (3) Reflexion：语言化自我反思的强化
- **出处**：Shinn, Cassano, Berman, Gopinath, Narasimhan, Yao, *"Reflexion: Language Agents with Verbal Reinforcement Learning"*, arXiv:2303.11366, 2023（NeurIPS 2023）。
- **定义**：Agent 在失败后写"反思"文本存入情景记忆，下一轮尝试前回灌，从而不更新权重地"从错误中学习"（HumanEval 91% pass@1）。
- **与本维度的关系**：Reflexion 依赖"失败可重放、反思可持久化"。本平台的 `run_step`/`run_event` 不可变事实表正是这一能力的承载体；但本平台对"UNKNOWN（结果未知）"采取**不重放**策略（见 4.2/5.4），与 Reflexion 的"重放+反思"形成有意分歧——因为本平台有真实副作用（写数据库、记薄弱点），盲目重放=重复副作用=Sev-0。

#### (4) Tree of Thoughts / Graph of Thoughts：搜索式结构化推理
- **出处**：Yao et al., *"Tree of Thoughts: Deliberate Problem Solving with Large Language Models"*, arXiv:2305.10601, 2023（NeurIPS 2023）；Besta et al., *"Graph of Thoughts: Solving Elaborate Problems with Large Language Models"*, arXiv:2308.09687, 2024（AAAI 2024）。
- **定义**：把单链推理扩展为树（ToT，可回溯/BFS/DFS）再到任意图（GoT，可聚合/反馈环）。本质是"在多条候选路径上搜索并回退"。
- **与本维度的关系**：搜索式编排需要"分支状态隔离 + 评估信号 + 回退"——这要求编排引擎持有可寻址的中间状态。本平台当前是线性 `while` 循环 + 委派子树（`agent_invocation`），**不支持 ToT 式的分支回退**；这是与前沿"搜索式编排"的明确差距（见 5.3）。

#### (5) LLM-as-planner / LLMCompiler：模型产出依赖图、并行执行
- **出处**：Kim et al., *"An LLM Compiler for Parallel Tool Calling"*, arXiv:2312.04511, 2024（ICML 2024）。
- **定义**：Planner 产出工具调用的**依赖 DAG**，Task Fetching Unit 在依赖就绪时并行派发，Executor 并行执行独立调用（相对 ReAct 延迟 3.7×、成本 6.7× 优化）。
- **与本维度的关系**：本平台的 `ROUTER`/`SEQUENTIAL` 是串行声明式编排，未做"模型动态产出 DAG + 并行派发"。这是性能维度的已知短板（见 5.3）。

#### (6) 多 agent 协作拓扑：AutoGen / MetaGPT / ChatDev
- **出处**：Wu et al. (Microsoft), *"AutoGen: Enabling Next-Gen LLM Applications via Multi-Agent Conversation"*, arXiv:2308.08155, 2023；Hong et al., *"MetaGPT: Meta Programming for A Multi-Agent Collaborative Framework"*, arXiv:2308.00352, 2023（ICLR 2024 Oral）；Qian et al., *"Communicative Agents for Software Development"* (ChatDev), arXiv:2307.07924, 2023。
- **定义**：
  - **AutoGen**：`ConversableAgent` 对话驱动，GroupChat 群聊拓扑。
  - **MetaGPT**：把人类 **SOP（标准操作流程）** 编码进多 agent 协作，角色专业化 + 结构化产物交接。
  - **ChatDev**："虚拟软件公司"对话链（CEO→CTO→程序员→测试）。
- **与本维度的关系**：本平台的 `agent_invocation`（`depth=1 ⇔ parent_invocation_id IS NULL`，七态状态机，fencing_token CAS）是**显式建模的委派调用树**，等价于把 MetaGPT 的 SOP 拓扑与 AutoGen 的对话拓扑"用数据库记录 + 状态机"固化下来，且每个子树有独立执行作用域（见 4.2 差异化设计）。

#### (7) 事件驱动 vs 图编排的取舍（工程范式）
- **出处**：无单一论文，属分布式系统工程共识。可参照 Pat Helland *"Idempotency Keys"*（2023，提出"接收方必须记住已处理过什么、对重复返回同一答案"）与 durable execution 文献（见下）。
- **定义**：编排可由"显式图/状态机"驱动（确定性、可重放），也可由"事件流/消息队列"驱动（松耦合、崩溃可恢复但顺序弱）。两者的取舍核心是"状态放哪、谁决定下一步"。
- **与本维度的关系**：本平台选择**事件唤醒 + DB 状态机**混合——Outbox 事件只唤醒、不携带状态；权威状态永远在 PostgreSQL。这是把"事件驱动的解耦性"与"图编排的状态完整性"折中到 DB 一层。

#### (8) Workflow-vs-Agent 边界（Anthropic）
- **出处**：Anthropic, *"Building Effective Agents"*, 2024, https://www.anthropic.com/research/building-effective-agents 。
- **定义**：Anthropic 明确区分 **workflow**（LLM/工具沿预定代码路径编排，可预测）与 **agent**（LLM 动态主导自己的流程和工具使用，自治）。并给出五种 workflow 模式：prompt chaining / routing / parallelization / orchestrator-workers / evaluator-optimizer，加 autonomous agent。
- **与本维度的关系**：本平台的 `LEAF/ROUTER/SEQUENTIAL` 实质是"workflow 侧"的强约束编排（声明式、可预测），而运行期 `while` 循环里模型仍可动态决定工具调用（agent 侧）。即本平台在同一 run 内同时容纳 workflow 与 agent 两种形态——这与 Anthropic 的二分法兼容，但把"约束"下沉到了治理期（`cap_agent_def` 发布）与运行期快照两层。

#### (9) Durable Execution（持久执行）与 fencing token
- **出处**：Temporal, *"Durable Execution"*, https://temporal.io/ ；以及 durable-execution 概念词典（fencing token 定义），"Concepts and Vocabulary", https://sparkles-docs.pages.dev/research/algebraic-effects/durable-execution/concepts 。另 Burckhardt et al. 证明了 durable function 内部状态 exactly-once、外部调用 at-least-once 的结论。
- **定义**：durable execution 指函数在所在机器崩溃后仍能从已到达的那一行继续，平台记录每一步 Event History，崩溃后另一机器重放历史重建状态。其中 **fencing token** 被明确定义为"标识写者占有的、单调递增的值，携带过期 token 的写入即使写者未察觉失权也应被拒绝"（Temporal 的 shard RangeID、Restate 的 LeaderEpoch 即其例）。**plain lock 不是 fencing token**，因为持有过期锁的进程仍相信自己持有。
- **与本维度的关系**：本平台的 `enforce_fencing_on_write()`（`NEW.fencing_token < OLD.fencing_token → RAISE`）与 `lease_owner/lease_expires_at` 租约，正是 fencing token 范式的数据库内实现——这正是本平台"防脑裂/双 Worker 写同一 Run"的理论根（见 4.2、5.4）。

#### (10) Workflow 引擎三要素（控制流 / 持久化 / 可观测）
- **出处**：工作流引擎（Temporal、AWS Step Functions、DBOS）的工程共识；DBOS 明确把"step at-least-once、outcome exactly-once"作为引擎交付属性。
- **定义**：一个生产级编排引擎必须同时具备：①**控制流**（谁决定下一步、分支/循环/并行）；②**持久化**（状态在崩溃后不丢、可重放）；③**可观测**（每步的执行历史、输入/输出可见）。缺任一即退回"脆弱服务 + 一堆对账脚本"。
- **与本维度的关系**：本平台的"DB 状态机（控制流）+ PostgreSQL 权威源（持久化）+ run_step/run_event/agent_trace_metric（可观测）"恰好对齐这三要素，但"控制流"是用 `while` 循环而非可视化图表达（见 5.3 短板）。

#### 2.1.11 理论 → 本平台代码锚点映射表

| 理论 | 核心主张 | 本平台的对应实现（锚点） | 是继承还是背离 |
|---|---|---|---|
| ReAct | Thought-Action-Observation 循环 | `RunExecutionLoop` 主循环 `while steps<maxSteps`，每轮模型调用+工具 | **继承**（工程化循环） |
| Plan-and-Solve | 计划与执行分离、约束冻结 | `RunConfigSnapshot` 创建时冻结 maxSteps/maxLlmCalls/timeout；`cap_agent_def.orchestration` 声明式 | **继承并强化**（DB 固化） |

| LLMCompiler | 并行 DAG 派发 | 当前串行 `ROUTER/SEQUENTIAL` | **缺口**（I-7） |
| AutoGen/MetaGPT/ChatDev | 多 agent 拓扑 | `agent_invocation` 显式调用树 + 状态机 + 独立作用域 | **继承并强化**（DB 固化 SOP） |
| Workflow vs Agent | 预定路径 vs 模型自驱 | 快照定硬上限（workflow 侧）+ 模型建议工具（agent 侧） | **兼容二分** |

| Workflow 引擎三要素 | 控制流/持久化/可观测 | DB 状态机 + PostgreSQL + run_step/run_event/agent_trace_metric | **对齐**（控制流表达弱） |

### 2.2 理论给出的「设计张力」（trade-off）清单

|---|---|---|---|---|
| T1 | 谁决定"继续/停止" | 图结构静态决定（可预测、易调试） | LLM 动态决定（灵活、自适应） | **混合**：快照定硬上限 + 模型建议工具，模型不能无限自驱 |

| T7 | 并发派发 | 串行（简单、一致） | 并行 DAG（LLMCompiler，快） | **当前串行**（ROUTER/SEQUENTIAL 串行，未做并行 DAG） |

### 2.3 业界公认的反模式（anti-pattern）清单及判别方式

1. **静默重放有副作用的步骤**（double-execution）：崩溃恢复时无条件重跑全部步骤。判别：检查恢复路径是否区分"已确定的副作用"与"可重入的读"。本平台用 `Outcome.UNKNOWN_RESULT → ack 丢弃` 规避。
2. **把内存态当权威源**（split-brain on restart）：进程重启后从内存而非 DB 续跑。判别：看恢复入口是否先 `SELECT` DB。本平台 `claimSpecificRun` 必重读 DB。
3. **终态后还能改状态**（inconsistent terminal）：`FAILED` 后被并发写回 `RUNNING`。判别：状态机是否有"终态不可迁出"硬约束。本平台 `enforce_run_state_transition` 拒绝。
4. **用普通锁替代 fencing token**：崩溃的 Worker 仍相信自己持有锁并写入。判别：锁是否带单调递增代次且由存储层校验。本平台用 `fencing_token` 而非裸锁。
5. **Outbox 与业务不同事务**（lost wakeup）：run 已建但唤醒事件未提交 → 永久卡死。判别：看 run 创建与 outbox 是否同一事务。本平台四者同事务（红线 3）。
6. **把队列消息当可信状态**（trust-the-payload）：Worker 直接信 MQ 里的 tenant_id/权限。判别：Worker 是否重读 DB 并绑 RLS。本平台 `RunDispatchConsumer` 只用消息 `tenant_id` 绑 RLS 上下文，状态重读 DB（架构图 :245/:349）。

#### 2.3.1 反模式 → 本平台规避手段映射

### 2.4 深度补充：两个新理论锚点（均经官方出处核实，不与 2.1 重复）

> 本节为本次「13 份报告更详细补充」新增，不改写 2.1 已有十个锚点。选择 Saga 与 Event Sourcing 的原因：它们分别回答的本维度元问题是「**有真实副作用的步骤失败后，如何收敛而不重复执行**」与「**为什么不可变事实表可以成为唯一权威源**」——这正是 2.1(7)（事件驱动 vs 图编排）、2.1(9)（durable execution）、2.1(10)（工作流三要素）三处只给了结论、未给理论根系的部分。二者是对既有锚点的**补强**，不是替换。

#### (11) Saga / 补偿事务：长事务拆成可交织子事务 + 显式补偿

- **出处（本次经 WebSearch + ACM DL 官方页核实）**：Hector Garcia-Molina, Kenneth Salem, *"Sagas"*, ACM SIGMOD International Conference on Management of Data, 1987, pp.249–259, DOI `10.1145/38713.38742`（ACM 数字图书馆 https://dl.acm.org/doi/10.1145/38713.38742 ；Cornell CS711 扫描副本 https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf ）。
- **定义（忠于原文）**：长活事务（LLT）长期持有锁、显著拖慢短事务。Saga 把一个 LLT 写成**一串可与其他事务交织的子事务 T1..Tn**，并为每个 Ti 配一个**补偿事务 Ci**；系统保证「要么 T1..Tn 全部成功，要么执行 T1..Tj, Cj..C1 向前回滚」。论文明确：补偿是**语义撤销**而非物理回滚（"Ci cannot simply store ... the number of seats that existed when Ti ran"），且**放弃 saga 级隔离**——「其他事务可能看到部分 saga 执行的结果，补偿时不通知也不回滚那些事务」。
- **对本维度的解释力**：本平台 `run` 的每一步都是**真实副作用**（写 `run_step`、记薄弱点、发消息），天然是 saga 而非 ACID 事务。第 5.4 节「UNKNOWN 转对账、绝不重放」的本质，就是 Saga 的「ci 必须被显式设计、不能靠自动回滚」：本平台没有让重试引擎盲目重放，而是把结果未知的步骤挂账转人工/规则对账（I-3），这正是补偿事务范式的工程落地。此外，`outbox_event` 与 run **同事务**提交（2.3 反模式 5）划出了一条清晰的「saga 边界」——边界内是 ACID（四者原子），边界外是 saga（每步独立提交 + 幂等/补偿）。
- **边界（诚实）**：Saga 理论假设补偿动作**可被业务定义**。本平台对「不可幂等且无业务唯一键」的副作用**没有自动补偿**，只能转人工（`MANUAL_DISPOSED`，见 7.9）——即补偿能力是**部分**的，不是 Saga 论文的完整保证。这条边界正是 I-3 只做「半自动对账」的理论依据。

#### (12) Event Sourcing：append-only 事件存储即权威事实源

- **出处（本次经 WebFetch 官方页核实）**：Microsoft Azure Architecture Center, *"Event Sourcing pattern"*, https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing 。官方原文：「store the full series of actions taken on an object in an append-only store. The store acts as the system of record ... the authoritative data source.」
- **定义（忠于原文）**：不保存对象的当前状态，而是把作用于对象的**完整事件序列追加写入**事件存储；当前状态由**回放（rehydration）**事件重建。更正通过**补偿事件**而非修改历史事件；常与 CQRS/物化视图搭配缓解回放成本。官方同时列出代价：复杂度高、最终一致性、事件版本演进困难、查询不便、需要快照优化、**「事件通常至少一次投递，消费者必须避免重复处理」**、与「被遗忘权」合规冲突。
- **对本维度的解释力**：本平台的 `run_event`（事件流）+ `run_step`（步骤既成事实）+ `agent_invocation`（委派子树）就是**用 PostgreSQL 业务表实现的 event store**——`run_step.state` 恒 `RUNNING` 表示「该步骤已发生」（铁律 16），单条 INSERT 后不改，等价于 append-only；`WAITING_APPROVAL` 的暂停/恢复（8.1）依赖从这些事实重建 run 状态。Event Sourcing 理论解释了为什么本平台敢把「执行事实」与「业务状态」分离：`run` 是可变状态，`run_step/run_event` 是不可变事实，二者职责分明——这正是 5.0 表中「状态持有单一性」拿满分的根本原因。
- **边界（诚实）**：① 本平台**没有**做完整的「事件回放重建状态机」——恢复靠 `claimSpecificRun` **重读当前 DB 状态**而非从 `run_event` 从头回放（见 4.1.4）；`run_event` 目前主要服务于 SSE 续传与审计，**不是**恢复的权威输入。这是与纯 Event Sourcing 的实质差异。② 官方「append-only 与被遗忘权冲突」在本平台由**保留期脱敏**（`run_step.output_payload` 脱敏写 `{}`，DDL :2843）承接，属部分缓解。③ 官方「事件至少一次投递→消费者须幂等」正对应本平台 `DUPLICATE_DISCARDED`（D4）——理论预言与实现一致。

#### 2.4.1 新锚点 → 本平台代码锚点映射（承接 2.1.11）

| 理论 | 核心主张 | 本平台对应实现（锚点，本次复核） | 是继承还是背离 |
|---|---|---|---|
| Saga（SIGMOD 1987） | 长事务拆子事务 + 显式补偿，放弃 saga 级隔离 | run/outbox 同事务划 ACID 边界（RunCreationService:303）；边界外每步独立提交；UNKNOWN 挂账转对账（I-3） | **继承**（补偿=对账，且承认隔离放弃） |
| Event Sourcing（Azure AC） | append-only 事件存储即权威源，状态由回放重建 | `run_step` 恒 RUNNING 单条 INSERT（DDL:2815-2843）；`run_event` 事件流；`agent_invocation` 调用树 | **部分继承**（事实表是 append-only，但恢复靠重读 DB 态而非回放事件） |

> 结论：Saga 与 Event Sourcing 补齐了本维度「**为什么这样设计**」的理论根系，同时其边界也精确划线——本平台是「**saga 边界内的 ACID + append-only 事实表 + 重读当前态恢复**」的混合体，不是任何单一理论的纯粹实现。这个判断比 2.1 的「对齐三要素」更精确，也是对第五章「领先」判定应有的理论克制。

### 3.1 OpenAI Agents SDK（Handoffs）
- **官方定位与机制**：极简原语 `Agent / Runner / Handoffs / Guardrails / Sessions / Tracing`，**无显式图**。编排靠代码（asyncio）或 LLM 自主 `Handoffs`（一个 agent 把对话交给另一个 agent）。状态由 SDK 在内存/会话层维护，恢复依赖调用方。

### 3.8 竞品编排范式综合归类

把 3.1–3.7 横向拉平，可归为三类底座：

- **A 类 · 内存态编排（L1）**：OpenAI SDK、Anthropic SDK、AutoGen。状态主要在进程内存，不变量在 SDK/应用层，崩溃可恢复性弱，多租户无内建。优点是极简、开发者体验好。
- **B 类 · 专用持久层编排（L2）**：LangGraph（Checkpointer）、ADK（SessionService）、Agno（AgentOS DB）。状态外置到框架自带持久层，可重放/续跑，但与业务库分离、跨库一致需自管；状态机守卫多在应用/SDK 层。
- **C 类 · 业务数据库 + 触发器编排（L3，仅本平台）**：状态落在业务 PostgreSQL，不变量由 DB 触发器强制，单一权威源、崩溃免疫、强隔离内建。代价是开发侧不轻、缺可视化 DSL。

值得注意的是：**没有任何一个竞品把"状态机守卫"下沉到存储触发器层**——这是本平台在编排维度的唯一性差异，也是本维度"领先"判定的根本依据。Agno 的 Durable Queue 与本平台的 durable execution 思路最接近，但其 fencing 仍主要靠应用层心跳 + `FOR UPDATE SKIP LOCKED`，未做"触发器级状态机"这一层。

#### 3.9.1 Temporal（Durable Execution 的教科书）

- **它怎么做**：Workflow 的执行进度由 Temporal Service 以 **Event History（append-only 事件日志）** 持久化；进程崩溃后，新的 Worker 重放 Event History 重建状态并从最后一条事件续跑。Activity（有副作用的外部调用）默认 **at-least-once**，靠 Retry Policy + 业务幂等承接；Workflow Definition 必须**确定性**（非确定操作用 Side Effect 记录结果，重放时不再执行）。官方原文：「Event History is durably persisted ... so your application state survives crashes ... it also serves as an audit log」；Side Effect「does not re-execute upon replay, but instead returns the recorded result」。
- **关键取舍**：把"编排状态"和"重放引擎"做成**独立的专用平台**（Temporal Service + 数据库），换来最强的崩溃续跑与可审计性；代价是引入一整套外部集群运维与确定性编程约束（代码里不能直接用 `now()`/随机数，须走 Side Effect）。
- **对我们意味着什么**：Temporal 是 2.1(9) durable execution 与 fencing token 理论的**工程母体**，本平台的「DB 权威源 + 重读 + 租约 + fencing」可视为把 Temporal 的 Event History 重放**压缩进单一 PostgreSQL**的低成本近似。差异：Temporal 重放事件日志恢复；本平台重读当前 DB 态 + 租约续跑（无 Event History 重放，见 2.4 边界）。**启发**：I-3 的 UNKNOWN 对账可借鉴 Temporal「Side Effect 记录结果、重放不重执行」的纪律——副作用结果落 `run_step.output_payload`（I-1）后，恢复只读结果不重跑。
- **官方来源**：https://docs.temporal.io/temporal （Durable Execution / Event History）；https://docs.temporal.io/workflow-execution/event#event-history （Event History 为 append-only、支持崩溃恢复与审计，本次已访问核实）。

#### 3.9.2 Dify（可视化图编排的开源代表）

- **它怎么做**：以**共享可视化画布 + 节点系统**构建 agentic workflow / chatflow——"connect nodes that each handle a specific step ... branching on conditions"，拖拽连线配置，代码仅在自定义逻辑时需要。Workflow（一次性执行）与 Chatflow（带对话层）共享节点体系；Trigger 支持定时/webhook/集成事件触发。
- **关键取舍**：把编排做成**面向应用开发者的可视化 DSL**，极大降低搭建门槛、流程直观可调试；代价是编排状态与治理深度弱于生产级运行时（官方文档未明示状态机硬守卫/强一致/多租户隔离的内建保证）。
- **对本维度意味着什么**：Dify 正是本平台 5.3「落后 1：缺可视化 DSL」所指的对照物——它证明"可视化图编排"是可行且流行的产品形态，但定位是**低代码应用搭建**而非**多租户强一致生产骨架**。本平台 I-6 的「状态机只读导出端点」是向 Dify 式可视化**靠近一步**（让前端能画状态图），但不打算改成图执行引擎——这是定位差异，不是要补的短板。
- **官方来源**：https://docs.dify.ai/en/cloud/use-dify/build/workflow-chatflow （Workflow & Chatflow，可视化画布与节点编排，本次已访问核实）。

#### 3.9.3 Microsoft Agent Framework（AutoGen / Semantic Kernel 的合并后继）

- **它怎么做**：微软把 AutoGen 与 Semantic Kernel 的 agent 能力合并为 **Microsoft Agent Framework**（Semantic Kernel Agent Framework），提供 `ChatCompletionAgent` 等 agent 抽象与 **agent orchestration**（Sequential/Concurrent/GroupChat/Magentic 等编排模式）；Agent 可收发消息、协作、HITL、流程编排。
- **关键取舍**：作为**框架/库**交付，编排在代码层（多 agent 消息协作 + orchestration 类），灵活、与 .NET/Python 生态一体；状态机硬守卫与强一致**未在框架层保证**（依赖宿主/应用），多租户隔离交给上层。这也是原报告 3.5 判定 AutoGen「已归档停维护、并入新框架」的**后继落点**。
- **对我们意味着什么**：印证原报告 3.5 的时效判断——AutoGen 作为独立产品已停维护，其思想由 Agent Framework 承接，但**编排范式的根本问题未变**（状态在应用/框架层，不变量靠自律）。对本平台"领先"判定无冲击：竞品阵营里依然没有把状态机下沉到存储触发器的方案。**纠偏提示**：原报告「AutoGen 已归档停维护」结论成立，但其"后继是什么"在本次补充中明确为 Microsoft Agent Framework。
- **官方来源**：https://learn.microsoft.com/en-us/semantic-kernel/frameworks/agent/agent-framework/ （Agent Framework 与 orchestration，本次已访问核实）。

#### 3.9.4 CrewAI Flows（事件驱动状态流的补充核实）

- **它怎么做**：3.6 已述 Crew/Flows 基本形态。本次进一步核实 Flows 官方页：Flow 是「structured, event-driven workflows」，通过 `@start()` 定义入口、`@listen()` 监听上游输出触发、`@router()` 条件路由、`and_()/or_()` 汇聚，并支持 `@persist` 做状态持久化/恢复/fork，还提供 `flow.plot()` 可视化。
- **关键取舍**：Flows 把多步编排做成**事件驱动 + 共享 state**的轻量状态流（比纯图更松耦合），企业层补 RBAC/审计；但官方页**未使用 "state machine" 术语**，状态机硬守卫/强一致**未明示**（诚实标注）。
- **对我们意味着什么**：Flows 的「`@listen` 事件触发下一节点」与本平台「Outbox 事件唤醒 Worker」在**解耦思路上同构**——都用事件驱动而非硬编码调用链。差异：Flows 的事件在框架内存/持久层，本平台的唤醒事件在业务库且只携带 `tenant_id + run_id + message_id`（载荷最小化，架构图 :245），权威状态始终重读 DB。**启发**：本平台的 Outbox 是"唤醒信号"，与 Flows 的"携带 state 的事件"是两种事件粒度，前者更安全（无状态可失真）。
- **官方来源**：https://docs.crewai.com/en/concepts/flows （Flows 事件驱动、`@start/@listen/@persist`，本次已访问核实）。

### 3.10 竞品归类更新（纳入新增 4 个后）

- **A 类 · 内存态/框架层编排（L1）**：OpenAI SDK、Anthropic SDK、AutoGen（已归档）、Microsoft Agent Framework、CrewAI（社区版）。状态在进程内存/框架层，不变量靠自律，崩溃可恢复性弱，多租户多无内建。
- **B 类 · 专用持久层编排（L2）**：LangGraph（Checkpointer）、Google ADK（SessionService）、Agno（AgentOS DB）、Temporal（Event History，最强形态）、Dify（图 DSL + 应用数据库）。状态外置，可重放/续跑，但与业务库分离、跨库一致需自管。
- **C 类 · 业务数据库 + 触发器编排（L3，仅本平台）**：状态在业务 PostgreSQL，不变量由 DB 触发器强制。**注意**：Temporal 的 Event History 在"可重放/可审计"上强于本平台，但它仍是**专用持久层**（L2），状态机守卫不在业务存储触发器层——本平台的唯一性差异依然成立，但表述应精确为"**唯一把状态机硬守卫下沉到业务存储触发器层**"，而非"唯一做 durable execution"。

> **结论修正（诚实）**：原 3.8 说「没有任何竞品把状态机守卫下沉到存储触发器层」仍成立；但「本平台是唯一做 durable execution 的」不成立——Temporal/Agno 都是成熟 durable execution 实现。本平台的准确差异点是：**把 durable execution 的状态源与不变量守卫合并进业务数据库**（单库、无额外引擎），这是工程取舍，不是能力独占。

## 四、我们的实现（源码级解剖）

### 4.1 架构与数据流（关键组件、调用链、数据落点）

**控制流（同步侧）**：`RunCreationService` 将 `run + 初始 run_event + idempotency_record + outbox_event` **四者同事务**提交（`docs/系统架构图.md:199`），提交后返回 HTTP 202。

**唤醒流（异步边界）**：`OutboxRelay` 轮询 `outbox_event`（`application.yml:191` `relay-interval-ms=200`），投递到 MQ。MQ 消息**只携带 `tenant_id + run_id + message_id`**，不携带可信权限（`docs/系统架构图.md:245`）。

**执行流（Worker 侧）**：`RunDispatchConsumer` **只负责把消息变成一次租约领取**（`RunDispatchConsumer.java:27-57`），业务执行抽成 `RunExecutor`。领取后调 `RunExecutionLoop` 真正执行。`RunExecutionLoop` **只做编排**：串联模型调用 → 工具闸门 → 状态提交（`RunExecutionLoop.java:68` 类头）。主循环 `while (steps < snapshot.maxSteps())`（`RunExecutionLoop.java:725`）——**步数上限取自 Run 快照**而非动态配置。

**委派流**：`cap_agent_def.orchestration` 声明 `LEAF/ROUTER/SEQUENTIAL`（`docs/Agent设计总览.md:60-69`），`agent_invocation` 记录委派调用树（`depth=1 ⇔ parent_invocation_id IS NULL`），子 Agent 经 `WorkerChildAgentRunner` 起多轮小循环（默认 `DEFAULT_MAX_CHILD_STEPS=4`，`WorkerChildAgentRunner.java:71`）。

**数据落点**：权威事实源全部在 PostgreSQL——`run`（状态机主体）、`run_step`（每轮既成事实）、`run_event`（事件流）、`agent_invocation`（委派树）、`outbox_event`（唤醒）。MQ 仅为"唤醒/分发"管道（`docs/系统架构图.md:401`）。

#### 4.1.1 Run 全生命周期状态跃迁（来自 `enforce_run_state_transition`，DDL:453-475）

DB 触发器只允许以下跃迁，其余一律 `RAISE EXCEPTION 'restrict_violation'`：

```
        ┌─────────────┐
        │   QUEUED    │  (Run 创建事务提交后的初始态)
        └──────┬──────┘
       ┌───────┴────────┐
       ▼                ▼
  ┌─────────┐      ┌──────────┐
  │ RUNNING │      │ CANCELLED │ (终态)
  └────┬────┘      └──────────┘
   ┌───┼───────────┬──────────┬─────────────┐
   ▼   ▼           ▼          ▼             ▼
┌────────┐ ┌────────┐ ┌──────────┐ ┌─────────────┐ ┌──────────────────┐
│SUCCEEDED│ │ FAILED │ │CANCELLED │ │  TIMED_OUT  │ │WAITING_APPROVAL │
│ (终态) │ │ (终态) │ │ (终态)   │ │  (终态)     │ │ (可回 RUNNING)  │
└────────┘ └────────┘ └──────────┘ └─────────────┘ └────────┬─────────┘
                                                           │ 仅可从 WAITING_APPROVAL
                              ┌────────────────────────────┤ 回到 RUNNING / 终态
                              ▼                            │
                        ┌──────────┐                       │
                        │ CANCELLED│ (从 WAITING_APPROVAL)  │
                        │ TIMED_OUT│                       │
                        │  FAILED  │                       │
                        └──────────┘                       │
                                                          ▼
                                                  (WAITING_APPROVAL 自身
                                                   非终态，待审批消费)
```

要点：① `WAITING_APPROVAL` 是唯一"可回转"的非终态——审批消费后可回 `RUNNING` 继续，或转 `CANCELLED/TIMED_OUT/FAILED`；② 三个终态 `SUCCEEDED/FAILED/CANCELLED/TIMED_OUT` 一旦写入，**任何 NEW.state 改变都会被触发器拒绝**（终态不可迁出）；③ `CANCELLED` 可从 `QUEUED` 或 `RUNNING` 或 `WAITING_APPROVAL` 到达，覆盖"未开始取消/执行中取消/审批中取消"三态。这把"取消"建模为状态机的一等公民，而非应用层 flag。

#### 4.1.2 主循环单次迭代的 7 道闸门（来自 `RunExecutionLoop.java:724-950` 实测）

一个 `run` 的每一轮迭代（`while steps < snapshot.maxSteps()`，`RunExecutionLoop.java:725`）在进入模型调用前、依次执行以下顺序固定的检查，任何一道不通过即终止或收敛：

1. **租户生命周期再校验**（`rejectIfTenantBlocked`，:728-734）：运行中租户被暂停/退役 → 立即停止，不再发模型调用/工具。避免白烧成本与副作用。
2. **取消检查**（`claimPort.isCancelled`，:741-747）：每轮开头查取消；状态终态已由 `requestCancel` 置 `CANCELLED`，双重保险。
3. **根层业务超时**（`task.deadlineAt()`，:755-764）：租约过期≠业务 deadline 过期；业务 deadline 过期即 `commitFailure(TIMEOUT)`，防止已超时 run 被无限续租。
4. **模型调用次数闸门**（`snapshot.allowsLlmCall`，:841-849）：放在**发起调用之前**而非之后——超限意味着"这次调用根本不该发生"，放之后等于先花钱再发现超限。与 steps 上限是**两个独立闸门**（maxSteps=20 vs maxLlmCalls=12 不等值）。
5. **成本上限闸门**（`accumulatedCost > snapshot.maxCostPerRun()`，:930-937）：整树共享预算，超 `maxCostPerRun` 即收敛 FAILED。
6. **上下文裁剪/装配**（`ContextBudgetTrimmer.trim` + `assembleRequest`，:777-802）：记忆占用先从裁剪预算扣（防"预算说 16000 实际塞 16000+记忆"），裁剪失败（扣到 ≤0）会让**每个 run 第一步失败**——故用 `MIN_TRIM_BUDGET` 夹紧并告警（:704-707）。
7. **工具结果回灌 + 工具调用闸门**：模型返回工具调用后，进 `ToolInvocationGate` 的 15 步准入（维度 05/07），结果回灌下一轮上下文（带不可信标记 + 长度封顶，防注入/顶爆）。

这一序列把"取消/超时/步数/模型次数/成本/上下文"六类终止条件全部前置到"花钱之前"，是本平台"fail-closed + 不超发"在编排层的直接落地。

#### 4.1.3 委派子树执行（来自 `WorkerChildAgentRunner.java` + `agent_invocation`）

父 Agent 在工具调用中触发委派时，走 `DelegationExecutor`（架构图 :201）八步：幂等检查 → 解析父 → 以父声明为准定目标固定版本 → `DelegationGuard` → 解析子闭包 → 落 `agent_invocation` → 调度子 → 输出契约校验 → 写终态。子 Agent 经 `WorkerChildAgentRunner` 跑**有界串行**小循环（默认 `DEFAULT_MAX_CHILD_STEPS=4`，`WorkerChildAgentRunner.java:71`；`for step < maxChildSteps`，:270）：

- 子 Agent 的工具调用**仍走 `ToolInvocationGate`**，且带**自己的执行作用域**（固定 release + 闭包指纹）——既不能调父工具（权限下放=Sev-0），也不能调未声明工具（:36-44）。
- 子 Agent 只收到**最小必要上下文**（不继承父全部 Prompt/工具集/权限）（:42-44）。
- 子 Agent 的取消/超时**必须自己实施**（:48-54）：父取消后子若继续跑，其工具仍产生副作用——取消若只退化成"不再发起新委派"是无效的。
- `agent_invocation.depth=1 ⇔ parent_invocation_id IS NULL`（:1332 CHECK）：否则调用树无法重建；`fencing_token` 供终态 CAS（:1323, :1331）。

#### 4.1.4 一次 run 的端到端时序（实测路径）

```

   │ RunCreationService.create()                │                       │                  │

   │ │  INSERT outbox_event (PENDING)  ─────────┤                       │                  │
   │ ├─ COMMIT  ── 返回 HTTP 202               │                       │                  │

   │                                    (每 200ms 轮询)                 │                  │
```

关键不变量在这条链上处处兑现：① run 与 outbox **同事务** → 无"建了不唤醒"；② claimSpecificRun 条件更新带 fencing+1 → 重复消息/Double Worker 被去重；③ run_step 单条 INSERT 恒 RUNNING → "已发生"不可变；④ 主循环 7 道闸门前置到花钱前 → 不超发/不超时；⑤ UNKNOWN/STALE 映射 CLAIMED 丢弃 → 不重放副作用；⑥ commitResult 写终态经 `enforce_run_state_transition` → 终态不可迁出。

### 4.4 我们独有的设计（差异化设计）

1. **状态机下沉到存储触发器（L3）**：这是与所有竞品（L0–L2）的本质差异——`enforce_run_state_transition` 在 DB 层拒绝非法跃迁，应用崩了也不破坏不变量（"不变量下沉到存储层"理论，见 5.4）。
2. **fencing_token 而非裸锁**：`enforce_fencing_on_write` 用单调递增代次拒绝旧世代写入，规避"持有过期锁的进程仍相信自己持有"的 split-brain（Temporal 概念词典明确区分 fencing token 与 plain lock）。
3. **UNKNOWN 不重放、转对账**：对结果未知的步骤，宁可停执行转人工/自动对账，也绝不盲目重投——这是在有真实副作用前提下对 Reflexion"重放学习"的有意背离（见 5.4）。
4. **显式委派调用树 + 独立执行作用域**：`agent_invocation` 把多 agent 协作从"对话消息流"固化为"数据库记录的状态机子树"，且子 agent 带自己的闭包（不能调父工具、不能调未声明工具）。
5. **快照定上限**：`maxSteps/maxLlmCalls/timeout` 在 Run 创建时冻结，模型无法突破，旧 run 不受新配置影响。

## 五、正面对比分析

### 5.0 三条编排路线的本质差异（任务书重点）

本平台、LangGraph、Anthropic 代表了 agent 编排的三种底层范式。它们最本质的分歧不是"语法糖"，而是**谁持有状态、谁决定继续、重放在哪**这三个元问题：

| 元问题 | LangGraph（图 + Checkpointer） | Anthropic（agent loop） | 本平台（DB 驱动 + 事件唤醒 + 快照定上限） |
|---|---|---|---|
| **状态由谁持有** | Checkpointer（PostgresSaver/SqliteSaver，**专用持久层**） | 进程内存（Claude Code 二进制 / SDK 维护 session） | **PostgreSQL 业务库**（`run/run_step/agent_invocation`） |
| **谁决定"继续/停止"** | **图结构**静态决定（节点/边/条件边） | **LLM 自主**决定（model-directed），仅 `max_turns` 熔断 | **快照硬上限**（`while steps<maxSteps`）+ 模型建议工具（不能突破） |
| **重放在哪发生** | 从 Checkpointer 重放 graph state（time-travel） | 重跑 loop（内存态丢，需重新取上下文） | **重读 DB + 租约 + fencing**（无内存态可丢） |
| **不变量（终态/唯一执行者）由谁强制** | 应用/SDK 层 | SDK 层 | **DB 触发器**（`enforce_run_state_transition`） |
| **状态机可不可被应用 bug 绕过** | 可能（应用层漏判） | 可能（SDK 层漏判） | **不可能**（写入即被 DB 拒绝） |
| **崩溃后是否丢状态** | 否（Checkpointer 在） | **是**（内存丢，除非外部持久化） | **否**（DB 在） |
| **多租户隔离是否内建** | 否（session/thread 作用域） | 否 | **是**（RLS 默认拒绝 + 显式 slug） |

**结论**：LangGraph 把"状态"外置到专用持久层、用图结构静态编排，换取可重放/可调试；Anthropic 把"状态"留在内存、用 LLM 动态编排，换取极简与自治；本平台把"状态 + 不变量守卫"一起沉到业务数据库，换取**强一致、崩溃免疫、强隔离**——代价是失去图式可视化的轻体验与 LLM 完全自驱的灵活。这是定位差异，不是优劣排名：选哪条路取决于"你更怕乱（生产 SaaS）还是更怕重（研究/实验）"。

### 5.2 优势详解（为什么领先，讲清机制）

- **为什么"状态机硬守卫"领先**：LangGraph/Anthropic/OpenAI 的不变量（终态不可迁出、唯一执行者）写在应用层或 SDK 层。一旦应用层出 bug（忘了判终态、并发 double-commit），不变量就被破坏。本平台把同一组约束写进 `enforce_run_state_transition` 触发器——**即使 Worker 进程在判终态之前崩溃、即使有两份并发写入，DB 在写入那一刻拒绝非法跃迁**。机制上，这是把"不变量的 Enforcement 点"从"每个进程的自律"下移到"唯一写入通道的存储层"。
- **为什么"fencing_token"领先**：竞品的锁（若有）多为租约/锁表，崩溃的 Worker 持有过期锁仍可能写入。本平台 `enforce_fencing_on_write` 要求 `NEW.fencing_token >= OLD.fencing_token`，旧世代（代次更低）的任何 UPDATE 被 DB 拒绝——等价于 Temporal/Restate 的 fencing token 范式，且**在数据库内零额外组件**实现。
- **为什么"UNKNOWN 转对账"是结构性优势**：在真实副作用（写库、记薄弱点）存在的场景，盲目重放=重复写入=Sev-0。本平台用 `Outcome.UNKNOWN_RESULT → ack 丢弃` 切断重放，代价只是"需要对账通道"，换来的是**账实相符、可对账、不重复副作用**的硬保证。这正是 durable-execution 文献承认的"at-least-once 执行 + exactly-once 记录结果"的现实形态（见 5.4）。

### 5.3 劣势与盲区详解（根因分析）

- **落后 1：缺可视化编排 DSL（根因=设计取舍，非能力缺失）**。本平台刻意选择"声明式 `LEAF/ROUTER/SEQUENTIAL` + 运行期 `while` 循环"而非图式 DSL。这是为强一致/强治理付出的"开发侧不轻"代价，属**取舍**而非缺失。但确实牺牲了 LangGraph StateGraph 那种"可视化、可组合"的调试体验。
- **落后 2：未做并行 DAG 派发（根因=能力缺口 + 取舍）**。当前 `ROUTER/SEQUENTIAL` 是串行。LLMCompiler（arXiv:2312.04511）证明并行派发可带来 3.7× 延迟/6.7× 成本优化。本平台**尚未实现**"模型动态产出依赖 DAG + 并行派发"，属**能力缺口**，且受限于"快照定上限 + 串行主循环"的骨架——要补需改编排引擎核心（见第七章 I-7）。
- **落后 3：缺 time-travel 调试（根因=取舍）**。LangGraph 的 time-travel/断点续跑是标杆。本平台有不可变 `run_step/run_event`（已具备重放数据基础），但**未提供"回到某步、改状态、再跑"的交互**，属取舍——生产运行时优先强一致而非交互式调试。
- **落后 4：开发者体验重（根因=定位差异）**。本平台是"生产运行时"而非"库"，写 agent 需走治理发布（`cap_agent_def` + 双人复核 + 不可变发布）。这是定位差异，非短板，但与 OpenAI/Anthropic "几行搭好"相比确实重。

### 5.4 关键分歧点（最本质的架构分歧）

**分歧 1：状态机守卫放哪一层？**
- LangGraph/Anthropic/OpenAI：放在应用/SDK 层（建议性）。
- 本平台：放在 **DB 触发器层**（强制性）。
- 后果：竞品在应用 bug 或崩溃瞬间可能破坏不变量；本平台的不变量在存储层恒成立，应用崩了也不破。代价是本平台失去"应用层自由摆弄状态"的灵活度。

**分歧 2：未知结果（UNKNOWN）怎么办？**
- Reflexion 式：重放 + 反思学习。
- 本平台：转对账、绝不重放。
- 后果：本平台在"有真实副作用"场景下避免了重复写入 Sev-0，但放弃了"从失败中学习"的自动能力——**UNKNOWN 的自动学习需由对账通道 + 人工/规则补**，而非运行期重放。这对应 **exactly-once 的不可能三角**：在一个"至少一次投递 + 副作用不可幂等 + 无全局事务跨进程"的系统中，你无法同时保证"不漏执行、不重复执行、结果确定"。本平台选择牺牲"结果确定（UNKNOWN 时停）"来保"不重复执行"——这是"副作用不可幂等时的三难"下的显式取舍（第三难：若副作用可幂等，则可重放；不可幂等则只能停+对账）。

**分歧 3：谁决定"继续/停止"？**
- Anthropic agent loop：LLM 自主决定（model-directed），仅 `max_turns` 熔断。
- LangGraph：图结构静态决定。
- 本平台：快照定**硬上限**（maxSteps/maxLlmCalls/timeout）+ 模型建议工具（不能突破上限）。
- 后果：本平台最可控、最可预测，但灵活性最低——适合"可审计、强一致"的生产场景，不适合"探索式、模型自驱"的研究场景。

**判读纪律与结论**：

1. **按 0–4 口径，本平台在编排维度的总分低于 Temporal（2.90 vs 3.20），差距 0.30，集中在「可审计性」与「失败可诊断性」两轴**——不是「强制性」或「状态单一性」不足。机制解释：Temporal 把「状态机 + 审计 + 重放 + 诊断」四件事**打包成一个外部专用平台**，代价是引入一整套集群运维与确定性编程约束；本平台把「强制性 + 状态单一性」下沉到业务库而不引入第二引擎，代价是**可审计性的最后一公里（`output_payload`）与诊断的最后一米（恢复链路无告警）留在了应用侧**。两者是同一张账的两端。
2. **按本报告 5.1 的定性口径（强制/可恢复/单一性/可审计 四轴）本平台仍判「持平偏领先」，与本评分卡不矛盾**：5.1 比较的是**相对位次**（竞品无状态机硬守卫），本评分卡比较的是**绝对完备度**（0–4 含观测/告警一档）。**两张表必须并读**，任一单独引用都会失真。
3. **本评分卡纠正了 6.5 星级自评的量纲漂移**：6.5 给「强制程度 ★★★★★」，但按 0–4 口径（4 分要求「运行时度量/告警」）只能给 3 分；给「失败可诊断性 ★★★☆☆」，按 0–4 口径给 2 分。星级是序数刻度，分数是基数刻度——**本轮以分数为准，星级保留不改写**。
4. 「竞品最高分」只取**本轮经 `web_fetch` 实际抓取的官方页**（LangGraph / Temporal / Agno / Anthropic，见本节末「本轮新增竞品取证」）；未在本轮复核的竞品（OpenAI SDK / ADK / CrewAI / AutoGen / Dify / Microsoft Agent Framework）**该格不评分**，理由见「竞品未复核声明」。
5. **未实测声明**：本轮未运行任何测试、未做故障注入、未做压测（遵循本轮规范 §五.9）。所有「期望可达」的表述均为**源码层推演**，实测需按第七章三级门禁口径在实施阶段验证。

## 六、优缺点总评

### 6.1 我们的优点

**结构性优势（架构层，竞品普遍不具备）**
- S1：状态机下沉 DB 触发器，不变量崩了也成立（L3）。
- S2：fencing_token 防脑裂，旧世代写被 DB 拒绝。
- S3：权威状态源唯一（PostgreSQL），无内存/DB 双副本分叉。
- S4：UNKNOWN 不重放，账实相符、可对账。

**工程性优势（实现层）**
- E1：Outbox 与 run 同事务，杜绝"建了不唤醒"永久卡死。
- E2：重复消息丢弃 + 幂等领取，防 Worker 间打转。
- E3：部署参数 fail-closed（不退回默认值），防静默越权/过载。
- E4：不可变 `run_step/run_event` 提供重放与审计底座。

**领域性优势（业务层）**
- D1：多租户 RLS 默认拒绝 + 显式 slug 清单，越权降级为不可用。
- D2：快照定上限，旧 run 不受新配置影响，治理可追溯。

### 6.2 我们的缺点

**设计取舍导致的代价**
- C1：开发侧不轻（治理发布 + 配置先验），牺牲 SDK 式开发者体验。
- C2：缺可视化 DSL / time-travel，调试体验弱于 LangGraph。
- C3：模型灵活性受限（快照硬上限），不适合探索式自治 agent。

**能力缺口**
- G1：未做并行 DAG 派发（无 LLMCompiler 式优化）。
- G2：未做 ToT/GoT 式分支回退搜索。
- G3：`run_step.output_payload` 当前**无写入方**（DDL 注释已自承），结果页依赖前端 workaround。
- G4：无托管运行时，伸缩靠手动起多 Worker 实例。

**运维负担**
- O1：DB 触发器逻辑与代码逻辑需双维护（D7）。
- O2：OutboxRelay 轮询带来 200ms 级唤醒延迟（可调但存在）。
- O3：UNKNOWN 对账目前偏人工/规则，缺乏自动化 SLA。

## 七、可优化与改进点（必须可执行）

> 准则：每条均写到文件/表/配置/接口级别，并给可执行的验收门禁（不写"加强测试"类空话）。所有改动须遵守项目铁律（见 README 速查表，尤其铁律 2/5/16）。

### I-1：补全 `run_step.output_payload` 写入方（消除已知"无写入方"缺口）

- **问题陈述**：`01_platform_ddl.sql:2834` 注释明确"当前生产链路无写入方，NULL 表示未采集"，导致结果页曾误显"执行中"且无正文。这是已自承的数据断层。
- **方案设计**：在 `RunExecutionLoop` 每步结束时，经 `RunStepPort`/`JdbcRunStepRepository` 更新该步的 `output_payload`（写**摘要**而非全文，参照 `TOOL_OUTPUT_SUMMARY_LIMIT=2000` 上限，避免 `run_message` 膨胀）。具体：在 `RunExecutionLoop.java:850` 之后（模型调用/工具执行完成后）增加 `runStepPort.markCompleted(runId, stepId, summaryPayload, completedAt)`，DDL 不改（列已存在）。
- **预期收益**：结果页/回放端点能取到每步结构化产出；消除"已完成步骤显示为执行中"的误显。可度量：E2E 断言"已完成 run 的每步 `output_payload IS NOT NULL` 比例 = 100%"。
- **实施成本与风险**：改动面小（仅执行循环写入点 + Repository 方法）。风险：写入增大 `run_step` 体积——用 2000 字符摘要封顶规避。无需灰度（仅增加写入）。
- **优先级**：P1（属数据完整性）。
- **验收门禁**：① 新增 `RunStepCompletionIT`，构造一个 ≥2 步的 run，断言 `SELECT count(*) FROM run_step WHERE run_id=? AND output_payload IS NULL AND completed_at IS NOT NULL = 0`；② 断言 `output_payload` 长度 ≤ 2000；③ 该 IT 须走真实 PostgreSQL（非 H2），防止 `jsonb` 语义漂移。

### I-2：租约续期失败显式降级（`renewLease=false` 时主动终止，防静默双执行）

- **问题陈述**：`RunExecutionLoop.java:1170` 调 `renewLease`，若不显式处理失败（仅记日志继续），可能出现"租约已过期被他人接管、本 Worker 仍继续写"的 split-brain 窗口（虽被 fencing 拒绝写入，但算力/模型调用被浪费，且可能触发孤儿 Run）。
- **方案设计**：在 `RunExecutionLoop.java:1170` 续期调用处，若 `renewLease` 返回 `false`，抛 **`LeaseLostException`**（新异常类，置于 `cn.studykid.multiagent.worker.execute`），由 `RunDispatchConsumer.tryFailRunAsOrphan` 走孤儿收敛（已存在，:127-136）或静默退出。即在 `renewLease` 块：
  ```java
  if (!claimPort.renewLease(tenantId, task.runId(), workerId, leaseDuration)) {
      throw new LeaseLostException(task.runId()); // 由消费端孤儿兜底或干净退出
  }
  ```
- **预期收益**：消除"续期失败但继续跑"的隐患；多步 run 在第二步不会再被误判为"已被接管"后还硬写。可度量：Chaos 测试"在 step=2 时让 renewLease 返回 false"，断言 run 不进入重复终态、且后续步骤不再执行。
- **实施成本与风险**：新增 1 个异常类 + 1 处分支。风险：续期 RPC 瞬时失败可能误终止——故 `renewLease` 实现须区分"过期（确失权）"与"RPC 错误（可重试）"，仅前者抛 `LeaseLostException`。须同步看 `RunClaimPort.renewLease` 的语义。
- **优先级**：P1。
- **验收门禁**：① 单测模拟 `renewLease=false` → 断言 `RunExecutionLoop` 抛 `LeaseLostException` 且 step 计数停在续期失败那步；② 单测模拟 `renewLease` 抛 RPC 异常 → 断言**不**抛 `LeaseLostException`（走既有重试/超时）；③ 断言 `workerId` 与领取时一致（铁律：身份不一致致续租失败）。

### I-3：UNKNOWN 自动化对账（半自动，含预算不误释放的硬断言）

- **问题陈述**：`Outcome.UNKNOWN_RESULT` 当前 ack 丢弃、转人工/规则对账（`RunDispatchConsumer.java:70-71`）。缺少"对可幂等/可查的重放型 UNKNOWN 自动收敛"的自动化，且需保证"无幂等键的 UNKNOWN 绝不自动释放预算"（铁律 + `ToolInvocationGate` 预算三律之三）。
- **方案设计**：新增调度 `ToolOperationAutoReconciliationJob`（可挂现有 cron/调度口），逻辑：对 `tool_operation.state='UNKNOWN'` 且超过宽限期（如 `application.yml` 加 `reconciliation.unknown-grace-ms`）的记录，若命中稳定幂等键或业务唯一键（`ToolOperationReconciliationService` 已有能力）→ 置 `RECONCILED_SUCCEEDED`/`RECONCILED_ABSENT`；**若未命中幂等键 → 仅置 `MANUAL_DISPOSED` 待人工，绝不自动释放 `budget_reservation`**。新增配置：
  ```
  agent.worker.reconciliation.unknown-grace-ms: "300000"
  agent.worker.reconciliation.enabled: "true"
  ```
- **预期收益**：可幂等的 UNKNOWN 自动闭环，减少人工；不可幂等的 UNKNOWN 仍受控不误释放预算。可度量：IT 模拟"UNKNOWN + 幂等键命中"→ 自动 `RECONCILED_SUCCEEDED` 比例；"UNKNOWN + 无幂等键"→ `budget_reservation` 仍 `RESERVED` 比例 = 100%。
- **实施成本与风险**：新增 job + 配置。风险：自动对账若误判副作用已发生会错账——故**只有命中幂等/业务唯一键才自动**，否则人工。须遵守铁律 2（`run_step` 必填 fencing_token、UNKNOWN 禁 attempt）。
- **优先级**：P2。
- **验收门禁**：① `ReconciliationIT`：构造 `tool_operation` UNKNOWN + 同幂等键已有 SUCCEEDED → 跑 job → 断言变 `RECONCILED_SUCCEEDED` 且 `budget_reservation` 仍 `RESERVED`（不释放）；② 构造 UNKNOWN + 无幂等键 → 跑 job → 断言仍为 UNKNOWN/MANUAL_DISPOSED 且 budget 仍 RESERVED；③ 断言 job 对 `state<>'UNKNOWN'` 的记录零影响（幂等）。

### I-4：快照约束 `maxLlmCalls ≤ maxSteps` 构造期强制（防配置倒置）

- **问题陈述**：`RunExecutionLoop.java:838-840` 注释指出 `maxSteps=20` 与 `maxLlmCalls=12` 不等值，两个独立闸门缺一不可；但 `RunConfigSnapshot` 构造期未强制 `maxLlmCalls ≤ maxSteps`，理论上可配出倒置（maxLlmCalls>maxSteps 使模型调用闸门永远先于步数闸门触发，语义混乱）。
- **方案设计**：在 `RunConfigSnapshot` 构造器（或 `RunCreationService` 构建快照处）加入校验：
  ```java
  if (maxLlmCalls() > maxSteps()) {
      throw new IllegalArgumentException("maxLlmCalls 不得大于 maxSteps");
  }
  ```
  并在 `application.yml` 注释中明确两值语义独立。
- **预期收益**：消除配置倒置导致的"步数闸门被模型调用闸门架空"。可度量：单测传 `maxLlmCalls=25, maxSteps=20` → 断言抛异常。
- **实施成本与风险**：极小（一行校验）。风险：无。
- **优先级**：P2。
- **验收门禁**：① 单测 `RunConfigSnapshotTest`：合法区间正常构造；② 倒置区间断言 `IllegalArgumentException`；③ 现有依赖 `maxLlmCalls/maxSteps` 的 IT 不受影响（确认默认 12/20 合法）。

### I-5：低延迟唤醒双通道（LISTEN/NOTIFY 叠加，可选开启）

- **问题陈述**：`OutboxRelay` 轮询带来 `relay-interval-ms=200`（上限 10ms）的固定唤醒延迟（`application.yml:191`）。对延迟敏感场景（对话首响）200ms 偏保守，且"轮询"不是真零延迟。
- **方案设计**：在 `RunCreationService` 同事务提交后，**额外**发 `NOTIFY run_dispatch, run_id`（PostgreSQL `LISTEN/NOTIFY`，同一连接事务内 `NOTIFY` 在 commit 后投递）；新增 `PgNotifyDispatchListener` 订阅该 channel，收到即触发对应 tenant 的 `OutboxRelay` 即时扫描或直发 MQ。保留轮询作为兜底（防 NOTIFY 丢失）。配置：
  ```
  agent.worker.dispatch.notify-enabled: "false"   # 默认关，灰度开启
  ```
- **预期收益**：开启后 dispatch 延迟从 ≤200ms 降到 ≤50ms（P99）。可度量：基准测试对比 `notify-enabled=true/false` 的 `run_created → worker_picked` 延迟 P99。
- **实施成本与风险**：新增 listener + 配置；风险：NOTIFY 在连接池/事务边界下可能丢失或乱序——故轮询兜底必须保留，NOTIFY 仅作加速。须验证 `NOTIFY` 与 RLS（`app.tenant_id`）绑定上下文不冲突。
- **优先级**：P3（P4 期，对应"真零轮询"已在梳理报告标注）。
- **验收门禁**：① `NotifyDispatchIT`：开启 NOTIFY，断言 `run_created → worker 领取` 延迟 P99 < 50ms；② 关闭 NOTIFY（仅轮询）→ 断言延迟回落 ≤200ms 且功能不退化；③ 断言 NOTIFY 丢失场景下轮询兜底仍能唤醒（注入"NOTIFY 丢弃"→ run 最终被轮询消费，无永久卡死）。

### I-6：编排状态机可观测导出（DDL 触发器约束 → 只读端点，防前端硬编码）

- **问题陈述**：前端/API 对 run 状态机的理解曾因"run_step.state 恒 RUNNING"的非常规语义而出错（DDL :2830-2831 自承）。状态允许跃迁目前只存在于 `enforce_run_state_transition`（DB 触发器），前端/测试各按字面解释，易漂移。
- **方案设计**：新增只读端点 `GET /api/agent/runs/state-machine`（或文档生成），内容由**解析 DDL 触发器逻辑**或硬编码同源常量导出，返回：
  ```json
  { "QUEUED": ["RUNNING","CANCELLED"],
    "RUNNING": ["SUCCEEDED","FAILED","CANCELLED","TIMED_OUT","WAITING_APPROVAL"],
    "WAITING_APPROVAL": ["RUNNING","CANCELLED","TIMED_OUT","FAILED"] }
  ```
  并新增 `RunStateMachineConsistencyTest` 断言端点返回与 `01_platform_ddl.sql:453-475` 文本解析结果一致（防 DDL 改了端点没改）。
- **预期收益**：状态机"单一真相"对前端/测试可见，消除语义漂移。可度量：一致性测试在 CI 阻断 DDL 与端点分叉。
- **实施成本与风险**：新增端点 + 一致性测试。风险：DDL 注释与端点需同步维护——故用测试强制同源。
- **优先级**：P2。
- **验收门禁**：① 端点返回含 3 组允许跃迁，且 `FAILED` 不在任何 `NEW.state` 列表（终态不可迁出）；② `RunStateMachineConsistencyTest` 解析 `enforce_run_state_transition` 文本，与端点返回比对，差异即失败；③ 断言 `run_step.state` 语义（恒 RUNNING=已发生）在该端点/文档中有专门说明字段。

### I-7：并行 DAG 派发探索（LLMCompiler 式，长期，骨架级）

- **问题陈述**：当前 `ROUTER/SEQUENTIAL` 串行（G1），无"模型产出依赖 DAG + 并行派发"能力，缺失 LLMCompiler（arXiv:2312.04511）证明的 3.7×/6.7× 优化。
- **方案设计（探索，非本期落地）**：在 `RunConfigSnapshot` 增加 `parallelDispatch: boolean`（默认 false，铁律级 fail-closed），当开启且模型返回 DAG 时，`RunExecutionLoop` 按依赖并行派发工具调用（各自仍过 `ToolInvocationGate`）。**仅在 L2/L3 治理发布声明允许时启用**；不改变默认串行语义。
- **预期收益**：可并行独立调用的场景延迟/成本显著下降。可度量：基准对比"串行 vs 并行"同任务的 wall-clock 与 token 成本。
- **实施成本与风险**：骨架级改动，影响维度 05/11（工具并发、对账），需灰度 + 反向验证（铁律 6）。风险高，**仅作研究方向**，不计入本期交付。
- **优先级**：P4（研究）。

### 7.9 UNKNOWN 对账逻辑参考实现（I-3 伪代码）

```java
// ToolOperationAutoReconciliationJob（新增，挂现有调度）
void reconcile() {
    for (ToolOperation op : ledger.findStaleUnknown(graceMs)) {       // state='UNKNOWN' 且超宽限
        if (op.hasStableIdempotencyKey()
                && ledger.existsCompletedWithSameKey(op)) {            // 幂等键命中已有成功
            ledger.transition(op, RECONCILED_SUCCEEDED);              // 自动闭环，预算仍 RESERVED
        } else if (op.hasBusinessUniqueKey()
                && ledger.existsAbsentWithSameKey(op)) {              // 业务唯一键证明未生效
            ledger.transition(op, RECONCILED_ABSENT);
        } else {
            ledger.transition(op, MANUAL_DISPOSED);                   // 不可幂等 → 人工，绝不释放预算
            // 注意：budget_reservation 保持 RESERVED，直到人工 MANUAL_DISPOSED 显式释放
        }
    }
}
```

该实现严格遵循 `ToolInvocationGate` 预算三律之三（UNKNOWN 绝不释放预留）与铁律 2（UNKNOWN 禁 attempt），只对"可证明幂等/可证明未生效"的 UNKNOWN 自动收敛，其余挂人工——把金融差错处理的"挂账/冲正/转人工"范式落到 agent 对账。

## 八、其他有价值的横向对比（避免维度内自闭）

### 8.1 与本项目其他维度的耦合与相互约束（≥2 条）

1. **↔ 维度 03 状态持久化与可恢复性**：本维度的"DB 权威源 + fencing + 不可变快照"**直接就是**维度 03 的承载体。改本维度（如把状态机下移/上移）会直接改变维度 03 的"可恢复性"口径——例如若把状态机从 DB 触发器撤到应用层，维度 03 的"崩了也不破不变量"优势立刻消失。**约束**：任何本维度改动不得削弱维度 03 的 fencing/不可变快照保证（铁律 16）。
2. **↔ 维度 07 权限与护栏**：`ToolInvocationGate`（维度 05/07）是 `RunExecutionLoop` 每步必过的闸门。本维度若引入并行 DAG（I-7），每个并行分支都必须独立过 Gate——否则并行会放大越权面。**约束**：并行化不得旁路 Gate（铁律 2/8）。
3. **↔ 维度 11 可靠性**：`Outcome.UNKNOWN_RESULT → 丢弃` 与维度 11 的"UNKNOWN 转对账、绝不重放"同源。本维度的 UNKNOWN 处置逻辑若改（如允许重放），会直接破坏维度 11 的"防静默失真"优势。**约束**：UNKNOWN 处置必须与维度 11 对账通道一致。

### 8.2 与非 agent 领域成熟做法的对照

- **金融/支付系统的 fencing token**：银行核心系统的"记账幂等 + 流水号单调递增拒绝旧批次"与本平台 `enforce_fencing_on_write` 同构。可借鉴：支付系统的"对账文件 + 差错处理"机制，本平台 I-3 的 UNKNOWN 自动化对账即借鉴此范式（差错交易挂账、可幂等交易自动冲正、不可幂等转人工）。
- **分布式系统的 durable execution（Temporal/AWS SWF/Azure Durable Functions）**：本平台的"DB 权威源 + 重读 + 租约 + fencing"正是 durable execution 思想的数据库内重实现，区别是本平台未提供 Temporal 式"Event History 全量重放 + 中途改状态续跑"。可借鉴 Temporal 的"Activity 必须幂等"纪律——本平台 `ToolInvocationGate` 的预算三律 + 幂等键已等价。
- **合规领域的工作流引擎三要素**（控制流/持久化/可观测）：本平台对齐，但"控制流"表达弱（无可视化）。可借鉴 BPMN/Step Functions 的"可视化状态机 + ASL 声明"提升维度 6.2-C2 的调试体验。

### 8.3 反向思考：若从头重做本维度，我们会怎么设计？（诚实取舍）

- **仍保留**：DB 权威源 + 状态机触发器 + fencing + 快照定上限 + Outbox 同事务——这四点是本平台相对竞品**唯一且正确**的差异化，重做不会丢。
- **会改变**：① 从第一天就提供"状态机只读导出端点 + 一致性测试"（I-6），而非让前端各自猜语义；② 一开始就把 `run_step.output_payload` 写入方做进执行循环（I-1），而非事后补；③ 考虑把编排主循环从"裸 `while`"升级为"可序列化的步骤计划（plan）结构"，使并行 DAG（I-7）成为一等公民而非后期改造；④ 把"UNKNOWN 对账"做成平台内建的自动差错处理服务（I-3），而非依赖外部脚本。
- **诚实取舍**：即使重做，仍会牺牲"可视化 DSL 的轻开发体验"来换"强一致/强治理"——这是本平台定位（生产多租户 SaaS 运行时）决定的，不是可妥协项。

### 8.4 深度补充：与相邻维度的精确交界（改一处必须联动一处）

> 8.1 已列三条耦合。本节进一步把"架构与编排（维度 01）"与最容易混淆的两个相邻维度——**维度 03 状态持久化与可恢复性**、**维度 11 可靠性与故障处理**——的分工边界画清，避免改动时责任真空或重复实现。

#### 8.4.1 ↔ 维度 03（状态持久化）：分工是"谁定义状态机" vs "谁保证状态不丢"

| 关注点 | 维度 01（本维度）负责 | 维度 03 负责 | 交界锚点 |
|---|---|---|---|
| 状态机规则 | 定义允许跃迁（`enforce_run_state_transition`，DDL:462-484） | 不重定义规则，只消费 | DDL:462-484 |
| 状态落盘 | 决定"权威源=业务 DB"（设计决策 D2/E1） | 实现持久化细节（连接池/事务/WAL） | RunCreationPort:14-32 |
| 崩溃恢复 | 决定"重读 DB + 租约 + fencing"的恢复**策略**（4.5.2 链 B） | 实现恢复**机制**（checkpoint/重放口径） | RunDispatchConsumer.java:201-210 |
| 不可变事实 | 决定 `run_step` 单条 INSERT 语义（铁律 16） | 决定保留期/归档/脱敏 | DDL:2815-2843 |

- **交界风险**：若维度 03 引入"应用层状态缓存"作为加速，必须与本维度的"权威源唯一"（5.0）对齐——缓存只能是只读投影，不能反向写入 run 状态，否则破坏 `enforce_run_state_transition` 的前提（唯一写入通道）。
- **反向验证**：把状态机从 DB 触发器撤到应用层 → 维度 03 的"崩了不破不变量"口径立即失效（8.1 已述）。**联动门禁**：任何 DDL 状态机改动，维度 03 的恢复 IT 必须重跑。

#### 8.4.2 ↔ 维度 11（可靠性）：分工是"UNKNOWN 的处置决策" vs "UNKNOWN 的检测与对账通道"

这是最容易重复实现的交界。本次 P0 纠偏恰好落在这里：

| 环节 | 维度 01（本维度） | 维度 11 | 交界锚点 |
|---|---|---|---|
| 检测失败 | 主循环 7 道闸门、租约过期、fencing 回退（4.1.2/4.5.3） | 统一的失败分类/告警聚合 | RunExecutionLoop.java:725-946 |
| UNKNOWN 处置决策 | **定义**"UNKNOWN 绝不重投、转对账"（D5，D:106-112） | **执行**对账通道、差错处理 SLA | RunDispatchConsumer.java:70-71 |
| 重复投递 | 用 `DUPLICATE_DISCARDED` 幂等承接（4.5.2） | 统计"重复率"并告警 | OutboxPublisher.java:117-126 |
| 孤儿收敛 | `tryFailRunAsOrphan` best-effort（:127-136） | 孤儿扫描/复活调度 | RunDispatchConsumer.java:127-136 |

- **P0 纠偏对齐点**：原报告把"Outbox 发布侧无锁 SELECT"列为可靠性缺陷，建议加 `FOR UPDATE SKIP LOCKED`。**已被 P0 验收报告推翻**：重复投递由 `DUPLICATE_DISCARDED` 幂等承接，无锁 SELECT 不是安全缺陷；真实问题是"账目失真"（重复发布计为成功），已用 `markOutboxPublished` 条件转换修复（4.5.2 链 B）。**引用旧结论时必须标注"已被复核纠偏"**，不得再按旧判断改代码。
- **联动门禁**：I-3（UNKNOWN 自动对账）同时属于本维度与维度 11——实施时维度 11 的对账 SLA 口径必须与 I-3 的 `unknown-grace-ms` 一致；两者若各起一个 job 会造成"对账两次、预算重复释放"（Sev-0）。**约束：对账逻辑单一实现，维度 01 定义策略、维度 11 承载调度**。

#### 8.4.3 三条交界的统一原则

1. **单一权威源**：状态写只走业务 DB 触发器通道（01/03），缓存/投影只读。
2. **单一实现点**：UNKNOWN 对账、重复投递去重、孤儿收敛各自只有一份实现（01 定义策略，11/03 承载机制），禁止跨维度重复造。
3. **联动反向验证**：任一维度改动交界锚点（DDL 状态机、`DUPLICATE_DISCARDED`、`output_payload` 语义），必须对相邻维度的 IT 做"撤点反证"（铁律 6/17），确认相邻维度断言随之变红——若不变红，说明该维度的"保障"是假绿。

## 九、对产品演进的启发

### 9.1 本维度支撑的产品能力（用户能感知什么）

- 用户能感知：**run 不会因平台崩溃而卡死或重复执行**（强可恢复性）；**多租户数据绝不串**（RLS 默认拒绝）；**预算绝不超发**（UNKNOWN 不释放）；**每次辅导的执行过程可复盘**（不可变 run_step/run_event）。
- 用户不能感知（当前短板）：编排的"可视化/可组合"调试、低延迟首响（受 200ms 轮询）、并行加速。

### 9.2 演进路线图（近/中/远三期，每期明确产出物与验收标准）

- **近期（P1–P2，本里程碑）**：交付 I-1（output_payload 写入）、I-2（租约续期降级）、I-4（快照约束）、I-6（状态机导出）。**验收**：四项均有 IT + CI 一致性测试通过；"已完成步骤 output_payload 非空率 100%"、"状态机端点与 DDL 同源"。
- **中期（P2–P3）**：交付 I-3（UNKNOWN 自动化对账）、I-5（NOTIFY 低延迟唤醒，灰度）。**验收**："可幂等 UNKNOWN 自动闭环率 ≥ 95%"、"开启 NOTIFY 后 dispatch P99 < 50ms 且轮询兜底不退化"、"无幂等 UNKNOWN 预算误释放率 = 0"。
- **远期（P4，研究）**：I-7（并行 DAG 探索）、可视化编排 DSL 预研。**验收**：`ParallelDispatchIT` 并行正确性 + 回归一致性；DSL 预研产出设计文档 + 反向验证方案（铁律 6）。

### 9.3 风险清单（做这一步可能踩的坑，关联本项目已知铁律）

1. **I-5 NOTIFY 丢失导致永久卡死** → 必须保留轮询兜底（铁律 5：双通道按 eventType 分流，采集不复用 `agent.run.execute`；此处 NOTIFY 仅加速不得替代轮询）。
2. **I-2 续期 RPC 瞬时失败误终止** → 须区分"过期"与"RPC 错误"，仅前者抛 `LeaseLostException`（铁律：身份不一致致续租失败，须与领取时 workerId 一致）。
3. **I-3 自动对账误判副作用已发生** → 仅命中幂等/业务唯一键才自动，否则人工（铁律 2：终态后禁补 attempt；铁律 8：UNKNOWN 绝不释放预算预留）。
4. **I-7 并行绕过 Gate** → 每个并行分支独立过 `ToolInvocationGate`（铁律 2/8），且默认关闭，回归须逐字节一致。
5. **任何 DDL 改动（如 I-6 端点同源）** → 改动 `enforce_run_state_transition` 必须同步更新端点 + 一致性测试（铁律 16：`run_step.state` 恒 RUNNING 语义不变）。

### 9.4 一句话结论

**本平台在"架构与编排模型"维度以"DB 驱动 + 事件唤醒 + 快照定上限 + 触发器级状态机 + fencing 防脑裂"的组合，换来了竞品普遍缺失的强一致、强可恢复、强隔离的生产级骨架——代价是牺牲了可视化 DSL 的轻开发体验与并行/分支搜索的执行弹性，这恰是多租户 SaaS 生产运行时"宁可重、不可乱"的自觉取舍。**

**「默认不生效」项（3 项）的共同根因**：

1. **两项（G-02 `concurrency` / G-03 `prefetch`）同属「参数绑定在通道实现细节上，而不是绑定在语义上」**：它们描述的是「消费并发/预取」这一**语义**，但代码只把它们接到 **RabbitMQ 监听容器工厂**这一个实现上；而本项目默认通道是 PG 表队列（`application.yml:457`），DB 通道用 `PgQueueListener` 单线程轮询（`PgQueueListener.java:342-370`）。⇒ **默认路径下「消费并发」这一语义根本没有参数化入口**，运维在配置页把 `concurrency` 调到 64 也不会有任何变化。
2. **第三项（G-18 `max-concurrent-runs`）属「只有常量、没有读取点」的纸面配额**：连实现层都没有，是声明先行。
3. **归纳出的共同根因（一条）**：**本项目的配置契约写在 yml 的「实现细节层」，而生效性由「运行期通道选择 + 装配期 Bean 条件」共同决定**；中间缺少一道「配置键 → 生产读取点」的可达性审计。更严重的是，**项目自身的 `ConfigReadService` 目录把 G-02/G-03 标为 `effective=true`**（`ConfigReadService.java:72-75`），即**目录比源码乐观**——运维从配置页读到的是「已生效」，运行期却不是。这正是本轮规范开头点名的「配置项存在但默认不生效 / 配置漂移 / 有类无注入点」三类静默失真在本维度的具体落点。
4. **是否属本项目铁律范围**：**不属 26 条铁律的显式条目**，但属项目新铁律「运行期可达性审计」（四问：谁实例化 / 谁写入 / 被注入 / 触发告警）的同类形态。**建议**（本轮新提，不改写既有正文）：在 `ConfigReadService` 目录生成时，对每个 `Spec` 强制执行「是否存在非测试的生产读取点」的存在性检查，缺失即 `effective=false` + 强制附条件说明；**因涉及铁律 6「撤掉修复点会红吗」的验收纪律，该建议须配反向验证守卫**（把某键的读取点删掉 ⇒ 目录断言必须变红），**故不作为本轮已落地结论**。
