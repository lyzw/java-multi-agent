# P4-D17 · 消息通道可切换（RabbitMQ ⇄ PostgreSQL 队列）

> **日期**：2026-10-22
> **状态**：✅ 代码完成并本机实跑验证（database / rabbitmq / 无 broker / 小客群灰度 四种场景全绿）
> **一句话**：把「消息走 RabbitMQ」从**硬编码**变成**配置项**，并新增一条**零外部依赖**的等价通道（PostgreSQL 队列），
> 使 CI / 本地开发 / 试运营小客群三个阶段都能无 broker 运行，且切换可回滚。

---

## 1. 为什么做这件事

原状：交换机、quorum 队列、消费容器工厂、`@RabbitListener` 端点**全部无条件装配**。代价：

| 代价 | 表现 |
|---|---|
| **无 broker 的环境跑不起来** | CI 必须起 RabbitMQ service，或把整套 worker 关掉——而「关掉 worker」= 回到「消息永不消费」的断链形态 |
| **换一种异步载体要改代码** | 改代码 + 重新发版 + 把全链路重验一遍 |
| **灰度无路可走** | 试运营阶段想「先让几个租户用新通道、稳了再全量」做不到——通道是全局写死的 |

本片把这三件事一次性解决，且**不改变任何业务语义**。

---

## 2. 两条通道（语义等价，可互换）

| | `rabbitmq`（保留） | `database`（新增，暂时替代） |
|---|---|---|
| 载体 | RabbitMQ quorum 队列 | PostgreSQL 表 `agent_message_queue` |
| 持久化 | broker 落盘 + publisher confirms | 事务提交（提交后才算「已确认」） |
| 至少一次 | unacked 重投 | `claimed_at` + 可见性超时回收 |
| 有限重试 | `x-delivery-limit=3` → DLX | `attempts` 达上限 → 死信表 |
| 死信 | `agent.run.dead` 队列 | `agent_message_dead_letter` 表（只进不出） |
| 背压 | 队列 ready 深度 | **同口径**：各租户 PENDING 行数之和 |
| 外部依赖 | RabbitMQ 实例 | **无**（PostgreSQL 本就是强依赖） |

> ⚠️ **语义必须逐条对齐**，否则「切换通道」就等于「改变行为」——那不是切换，是换 bug。

## 3. 关键设计决策

### 3.1 端口不变（不新增端口）

复用既有三个端口，**业务代码零改动**：

```
MessageSender     ← 出队/入队        （RabbitMessageSender | PgQueueMessageSender）
MessageHandler    ← 消费语义         （RunDispatchConsumer，实现不变）
QueueDepthProbe   ← 背压输入         （RabbitQueueDepthProbe | PgQueueDepthProbe | 组合）
```

> 这正是本项目「端口前移到 `agent-ports`」的价值兑现：
> 当初把 `MessageSender` 从 `agent-worker` 前移，就是为了今天能不碰业务层换载体。

### 3.2 按租户路由（支撑「小客群灰度」）

`TenantRoutingMessageSender` 按 `tenantId` 选通道：

- 命中 `agent.messaging.tenant-modes` 覆盖 → 用该租户指定的通道；
- 未命中 → 用全局默认通道。

**为什么必须按租户**：试运营阶段只能「整个部署一起换」等于没有灰度。
小客群试点需要的正是「先让几个租户走新通道」。

### 3.3 背压必须同时看到两条通道

切换/灰度期间两条通道可能同时有在途消息。只探测一条 → 另一条无限堆积而无人看见（L-6 护栏失效）。
故用 `CompositeQueueDepthProbe` 求和，但**只纳入活动通道**：

> ⚠️ 纯 DB 部署若把 Rabbit 探测纳入 → broker 不存在 → 探测必抛异常 → 背压恒超限 → **消息永不发布**。

### 3.4 切换前必须排空旧通道（守卫强制）

两条通道各有各的积压，切换后旧通道的消息**不会被新通道接管**——它们会安静地滞留，
Run 永不执行，而系统表面完全正常。

因此 `MessagingSwitchGuard` 在**启动期**做两项检查，失败即**拒绝启动**：

| 检查 | 精度 | 规则 |
|---|---|---|
| DB 侧残留 | **精确到租户** | 某租户已是 rabbitmq 模式，但其 DB 队列仍有待消费消息 → 拒绝启动 |
| Rabbit 侧残留 | 只能整体检查 | 存在 database 模式租户时，Rabbit 队列**必须为空**（队列跨租户共享，无法分辨归属）→ 拒绝启动 |

> ⚠️ 「无法检查」≠「通过」：broker 不可达时，
> Rabbit 通道**在用** → 拒绝启动（通道启用却连不上 = 消息永远不消费）；
> Rabbit 通道**不在用**（纯 DB 部署）→ 放行 + WARN（消息仍在 broker 里，**没有丢失**，只是无人消费）。

### 3.5 配置一律 fail-closed

| 配置 | 缺省 | 非法时的行为 |
|---|---|---|
| `agent.messaging.mode` | `database`（`${AGENT_MESSAGING_MODE:database}`） | **拒绝启动**（回落 = 悄悄用了一个没人审过的通道） |
| `agent.messaging.tenant-modes` | 空（全部跟随全局） | 模式值非法 → **拒绝启动**；slug 不在本实例清单 → 启动日志**点名告警** |
| 时长类（poll/batch/attempts/visibility/backoff） | yml 显式声明 | 缺失/越界 → **拒绝启动** |

## 4. 三个阶段怎么切

| 阶段 | 配置 | 说明 |
|---|---|---|
| **CI** | `AGENT_MESSAGING_MODE=database`（ci.yml 已显式声明） | **不需要 RabbitMQ service**；broker 端到端仍由 `RealBrokerEndToEndIT` 在有 broker 的环境单独验 |
| **dev（本地）** | 改 `AGENT_MESSAGING_MODE` 环境变量即可 | 两个容器都在本机时，`./scripts/dev-rabbitmq.sh start` 可随时切回 Rabbit 通道 |
| **试运营小客群** | `AGENT_MESSAGING_MODE=rabbitmq` + `AGENT_MESSAGING_TENANT_MODES=t-a=database` | 存量租户不动，灰度租户单独走数据库队列；**回滚 = 改一个环境变量** |

### 切换操作手册（重要）

```bash
# ① 停止 worker（不再领取新任务）
# ② 用旧通道启动一次，让旧通道排空
#    - 旧通道是 database：等 agent_message_queue 的 PENDING 归零
#    - 旧通道是 rabbitmq：等 agent.run.execute 深度归零
# ③ 改通道配置并重启
# ④ 未排空就切 → 守卫会**拒绝启动**并给出处置指引（这正是设计意图）
```

## 5. 数据库变更（V13）

新增两张表（`agent_message_queue` / `agent_message_dead_letter`）+ 枚举 `agent_message_state`：

- **RLS + FORCE**（与其他表一致，owner 不得绕过隔离）；
- **GRANT 给 `app_agent`**（逐条执行，不放进同一事务）；
- 部分索引：待领取（`next_attempt_at`）/ INFLIGHT 回收（`claimed_at`）/ 租户维度；
- 约束 `agent_message_claim_complete`：领取态必须同时给出领取者与时刻——
  否则「是否超时可回收」无从判断。

> ⚠️ **为什么独立成表而不复用 `outbox_event`**：
> `outbox_event` 是**发布侧**的事务日志（状态机 PENDING→PUBLISHED/FAILED，语义是「是否已交给通道」）；
> 本表是**通道侧**的队列（语义是「是否已被消费」）。混用会导致切换时旧状态机残留、
> 新旧消费端争抢同一批行，且「已发布但未消费」这一最危险的状态无法表达。

## 7. 诚实边界（不得扩大解释）

- ⚠️ **broker 端到端（E-1/E-2/E-3）不在 CI 覆盖内**——CI 无 rabbitmq service；
  该 IT 需在有 broker 的环境单独跑（本机已验通 3/3）。
- ⚠️ **数据库队列的吞吐上限受库写入能力约束**；本项目量级（单租户并发 Run ≤ 5）够用，
  但**未经压测**——调优点在 P4 压测。
- ⚠️ **可见性超时（默认 5 分钟）必须显著大于单次 Run 执行耗时**；
  超时导致的重复消费由既有**租约 + fencing** 保证安全，但会浪费一个租约周期。
- ⚠️ **切换不是热切**：必须先排空旧通道（守卫强制），不支持运行期零停机切换。
- ⚠️ **多实例部署下按租户覆盖需注意**：覆盖表是全局配置，
  各实例只对自己清单内的租户生效（清单外的 slug 会告警，不会静默失效）。
