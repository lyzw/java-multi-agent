## 0. 为什么本切片可以成立（实测基线，非推断）

FE-02 §0 判定「后端配置体系几乎完全不存在」，并把 C2 列为「**体系没建**」。
本切片开工前先做了实测复核，结论有两处**必须先更正**，否则设计会建立在错误前提上：

| FE-02 §0.1 的记载 | 本切片实测 | 判定 |
|---|---|---|
| 配置表 **0 张** | 仍为 0 张 | ✅ 成立 |
| 配置 HTTP 端点 **0 个** | 已有 `GET /api/config`（P4-D07 / C1），含 `effective` 真实接线标注 | ⚠️ **已过时** |
| 审批只能收紧「算法未接线」 | **`maxWith` 已有 3 处生产调用点**（`PlatformConfig` / `RiskBasedApprovalPolicy` / `WorkerExecutionConfig`）| ⚠️ **已过时** |
| 「改 yml + 重启」是唯一生效方式 | 配置快照在**每次 Run 创建时**构造（`RunConfigSnapshotFactory.snapshotFor`）| ⚠️ **已过时** |

> ⚠️ **最后一条是本切片成立的关键**：FE-02 §5 把生效方式列为
> 「yml + 重启 / DB 存储（待建）/ 快照隔离」三选一。
> 实测发现**第三种早已存在且已接线**——`snapshotFor` 在每个 Run 被 claim 时
> 重新读取配置并固化快照。因此「DB 覆盖 + 快照隔离」是**在既有架构上叠加**，
> 而非改造运行时。

## 1. 决策记录

| 维度 | 选择 | 理由 |
|---|---|---|
| **生效机制** | **DB 覆盖层 + 快照生效** | 快照已在 Run 创建时构造（R-021），改动天然只影响新 Run，**不需重启**。另两方案：yml+重启会让管理员改完看不到变化（误导，FE-02 §5 明列）；接进 Spring Environment 会让快照与全局状态耦合，多实例下无同步机制 |
| **存储形态** | `tenant_config_override` 表，仅存**覆盖值**，yml 保留为默认值 | 不搬走 yml，避免破坏既有 56 个叶子键的启动守卫与契约测试；DB 只做「覆盖层」，删除覆盖即回到 yml 默认 |
| **多租户** | 按 `tenant_id` 隔离（RLS） | 与平台其余表一致；`tenant_config_override` 启用 RLS |
| **收紧约束** | **服务端硬拒绝放松写入**（C5） | FE-02 §0.4 承认后端当前无拦截；`ApprovalRequirement.isRelaxationTo` 算法已存在，缺口只在「写入路径没调用」 |
| **C7 审批** | 本切片**只做 CHG 理由强制 + 审计**，不做人工审批工作流 | 技术可强制的部分（棘轮 / 审计 / 快照隔离）先落地；审批属流程而非技术，独立切片更清晰 |
| **范围** | 后端先行，前端在 D16 接线 | 先用真实配置项打通全链路并做反证，再横向扩展 |

## 2. 数据模型（V11 迁移）

```sql
CREATE TABLE tenant_config_override (
    tenant_id   UUID NOT NULL REFERENCES tenant(tenant_id),
    config_key  TEXT NOT NULL,                       -- 如 'agent.run.max-steps'
    value_text  TEXT NOT NULL,                       -- 统一文本；按配置键的类型解析
    value_type  TEXT NOT NULL,                       -- INTEGER | DECIMAL | ENUM | DURATION
    reason      TEXT NOT NULL,                       -- ⛔ CHG 变更理由（≥10 字）
    changed_by  TEXT NOT NULL,                       -- 操作者（来自认证上下文）
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (tenant_id, config_key)
);
```

**设计要点**

| 要点 | 理由 |
|---|---|
| `PRIMARY KEY (tenant_id, config_key)` | 每个租户每个键**至多一条覆盖**——「删除覆盖即回默认」无需区分历史 |
| `value_type` 显式存 | 解析失败时能报「类型不匹配」而非神秘的值解析异常（fail-closed 的可诊断性） |
| `reason` NOT NULL | C7 的技术落点：理由缺失在**数据库层**就写不进去，不依赖应用层自觉 |
| RLS + GRANT | 与 V1–V10 一致；**新表漏 GRANT 会导致写入 permission denied**（P3-D08 踩过：限流自身故障反成 DoS 入口）|
| 无 `deleted_at` | 不做软删除——覆盖的「历史」由 `audit_record` 承担，配置表只管当前值 |

## 3. 端口契约

### 3.1 `ConfigOverridePort`（agent-ports，新增）

```java
public interface ConfigOverridePort {
    /** 读某租户的全部覆盖（缺省 = 无覆盖 → 回 yml 默认）。 */
    @NonNull Map<String, String> overridesFor(@NonNull String tenantId);

    /** 写入覆盖；返回生效值。 */
    @NonNull AppliedConfig apply(@NonNull String tenantId,
                                  @NonNull String key,
                                  @NonNull String value,
                                  @NonNull String reason,
                                  @NonNull String actorId) throws RelaxationRejectedException;

    /** 删除覆盖（回落到 yml 默认）。 */
    void clear(@NonNull String tenantId, @NonNull String key, @NonNull String actorId);
}
```

**收紧约束落在哪**：端口层抛 `RelaxationRejectedException`，
但**收紧判定的算法权威在 application 层**（见 3.2），
端口只负责执行 + 留痕。这样 application 可复用既有
`ApprovalRequirement.isRelaxationTo`，不重复实现安全语义。

### 3.2 `ConfigTighteningPolicy`（agent-application，新增）

| 规则 | 判定 |
|---|---|
| **审批矩阵只能收紧** | 新值 `strictness` < 当前值 → 拒绝（`ApprovalRequirement.isRelaxationTo`）|
| **上限类只能收紧** | 成本上限 / 调用数 / 步数 / 并发数 / 试点租户数**只能变小** |
| **TTL 只能缩短** | 审批有效期只允许调小 |
| **L1 锁定键** | 工具风险级别、审批人范围**不可写**，直接拒绝 |

> ⚠️ **「只能收紧」的语义是单向棘轮**：与 `maxWith` 同源——
> 配置试图放松时取**更严格者**。本切片选择在**写入时拒绝**而非静默取严，
> 因为静默取严会让管理员以为自己改成功了（FE-02 §4「误导性文案比功能缺失更有害」）。

## 4. 生效链路

```
写入 PUT /api/config/overrides/{key}
   → ConfigTighteningPolicy 校验（放松 → 拒绝）
   → ConfigOverridePort.apply()            [写 tenant_config_override + 审计 fail-closed]
   → 返回 { key, 声明值, 生效值, 来源: "db_override" }

Run 创建
   → WorkerExecutionConfig.snapshotFor()
        改为读 EffectiveConfigResolver.current(tenantId)  ← 本切片新增接线
        （行为等价：DB 无覆盖时结果与现状逐位相同）
   → RunConfigSnapshotFactory.create() 固化 → 改动不影响在途 Run（R-021）
```

> ⚠️ **接线安全性**：`WorkerExecutionConfig` 当前的 `@Value` 字段是**构造期注入**。
> 若直接改为读 DB，将把「启动期 fail-closed 校验」变成「运行期」——
> **这是一个真实的回归风险**（原本 yml 配错 = 启动失败，改后 = 运行时才失败）。
> 故取法：**`@Value` 继续作为启动守卫 + DB 覆盖在快照时叠加**，
> 两者都缺失才拒绝。启动期行为**零变化**。

## 5. 端点契约

| 端点 | 鉴权 | 限流桶 | 说明 |
|---|---|---|---|
| `GET /api/config/overrides` | `agent:manage` | `GOVERNANCE_QUERY` | 列当前租户的全部覆盖 + 生效来源 |
| `PUT /api/config/overrides/{key}` | `agent:manage` | `GOVERNANCE_QUERY` | 写覆盖；**放松 → 409**；理由缺失 → 400 |
| `DELETE /api/config/overrides/{key}` | `agent:manage` | `GOVERNANCE_QUERY` | 清除覆盖（回 yml 默认）|

**错误语义**（与 P4-D13 治理端点一致）

| 情形 | HTTP | 说明 |
|---|---|---|
| 理由 < 10 字 | 400 | C7 |
| 试图放松 | **409** | 与「参数错」区分——这是**安全门禁降级**，不是输入错误 |
| 键为 L1 锁定 | 409 | 明确告知不可写 |
| 键不存在 / 类型不匹配 | 400 | fail-closed，不取默认值兜底 |

> ⚠️ **审计 `detail` 铁律（P4-D14 教训）**：`recordRequired` 的 `detail`
> 写入前会跑 `IdentifyingPattern` 检测，**命中可识别信息即拒绝整条写入**。
> 故 `detail` **不得**放用户自由文本；
> 本切片只放**键名 + 类型 + 是否放松**，理由本身进 `reason` 列（不做 PIPL 扫描的对象）。

## 6. 已知限制（诚实边界）

| # | 限制 |
|---|---|
| **L-1** | **无人工审批工作流**：L3 写入直接生效，仅靠「只能收紧」+ 理由 + 审计兜底。FE-02 §6 C7 的完整 CHG 流程**未实现**，须走后续切片 |
| **L-2** | **无动态生效**：覆盖值在**下次 Run 创建**时读取；正在跑的 Run 不受影响（这是 R-021 的正确行为，但前端须如实说明）|
| **L-3** | **多实例一致**：本切片每次快照都读 DB（无本地缓存），故多实例天然一致；代价是每次 Run 多一次查询 |
| **L-4** | **只覆盖可写键**：L1 锁定项（工具风险级别 / 审批人范围）本就不可写，不纳入本体系 |
| **L-5** | **无配置回滚历史查询**：`audit_record` 有写入但无「按键查历史」的便捷聚合 |

### 8.2 ⛔ 本轮抓到的三个真实缺陷

| # | 缺陷 | 危害 | 修复 |
|---|---|---|---|
| **D15-B1** | `parseMatrix` 不剥 yml map 花括号 | 当前值形如 `{READ=NOT_REQUIRED, ...}`（来自 `ConfigReadService.declaredValueOf` 的 `Map.toString()`）→ 第一段被解析成 `"{READ"` → 抛「风险等级非法」→ **审批矩阵完全不可写** | `parseMatrix` 先剥花括号；单元 + IT 双向回归 |
| **D15-B2** | 上限类只判「变大」，漏掉**非正数** | `-1 < 20` 看似是收紧而放行，但**负上限会让 Run 永远无法执行**——把「保护」换成了「停摆」 | 先 `signum() <= 0` 拒绝，再比较大小 |
| **D15-B3** | 反证 **S-4 指向错误的测试**（详见下） | 「写入即生效」这一核心承诺**当时没有任何测试保护**，注入后全套仍绿 | 新增 `ConfigOverrideSnapshotWiringTest`（D15-9）并改指反证 |

> ⚠️ D15-B2 是**写测试时才暴露**的：单元用例 `negativeRejected` 首次跑红。
> 若只写 IT（走端到端写入），这条会晚得多才被发现——
> **安全逻辑必须有独立的、不依赖 DB 的单元层**。

#### D15-B3 详情：本切片自己踩了「假绿」

反证 S-4（把 `if (effectiveResolver != null && tenantId != null)` 改成 `if (false)`，
模拟「快照路径不读覆盖」）首轮注入后 **未转红**。

**根因**：S-4 当时指向 `ConfigOverrideEndpointIT`，而该 IT 只验证
「`GET /api/config/overrides` 显示新值」——**不验证「Run 快照真的用了覆盖值」**。

**危害**：这正是 §7 反证 S-4 被设计出来要防的形态——
**读接口如实显示新值，运维看不出异常，但每一笔 Run 用的都是旧额度。**
讽刺的是，这段警告是本切片自己写的，测试却恰好漏在同一处。

**修复**：新增 `ConfigOverrideSnapshotWiringTest`（6 项，不连库）作为行为层承重，
反证改指它。复验：注入后 **如期 RED**。

> **教训**：本项目第四次同形态失效（F-14 → CP-1/CP-2 → A-2 → 本次）。
> 前三次都发生在**别处**，这一次发生在**自己新写的测试上**——
> 说明这不是「前人的坑」，而是**默认的思维盲区**：
> **验证读接口很容易，验证写路径真的生效很难，而后者才是功能本身。**
