## 0. 范围决策（为什么只做 C9 + C1 这一片）

用户选择「以上全部」解锁 F4–F8 的后端缺口（C1/C8/C9 + G3/G5/G6/G7）。
经实测后端现状，将其拆为**三片**，本片为第一片：

| 片 | 缺口 | 性质 | 说明 |
|---|---|---|---|
| **本片** | **C9（零保留注册表接线）+ C1（配置读取端点）** | 配置诚实化 | 让配置页能区分「yml 声明值」与「运行时实际值」，且零保留页不再把三家供应商误显示为「空注册表全拒」 |
| 第二片 | G3 / G5 / G6 / G7（run:read / result:read / 画像 / 列表分页） | 新业务端点 + DB 查询 + RLS | 解锁 F5 结果/画像、检索台；需确认 Run 结果是否落库 |
| 第三片 | **C8 全量运行时强制** | **大型特性** | 把 `max-cost-per-run` / `max-llm-calls` / `max-steps` / `max-concurrent-runs` 等 16 个限键真正接入运行时**执行**（成本上限/调用上限/步数上限/并发上限），而非仅读配置。这是新业务能力，非"读配置"，单独排期 |

> ⚠️ **本片绝不构成「配置已生效」的误判**。C1 端点返回的每条配置都带
> `effective`（是否接入运行时）标志，未接线的键显式为 `false`——
> 这正是 FE-02 §0.3 要求的诚实性：配置页不得把 yml 摆设值当作已生效。

## 1. C9 — 零保留注册表接线（声明值 → 注册表）

### 1.1 现状（缺陷）

`ApplicationConfiguration.zeroRetentionGate()` 硬编码：

```java
return new ZeroRetentionGate(ZeroRetentionRegistry.empty(), Clock.systemUTC());
```

yml 已声明 `agent.compliance.zero-retention.confirmed-providers: "deepseek,minimax,workbuddy"`（DEC-10 GATE-2 三家书面承诺），
但**从未接线** → 注册表恒空 → 合规页（P17）无法展示真实状态，
只能显示「所有供应商调用均被拒绝（设计内 fail-closed）」—— 与 yml 声明矛盾，且让人以为系统有 bug。

### 1.2 接线方式（诚实、fail-closed 安全）

`ZeroRetentionRegistry.confirm()` **强制 `evidenceRef` 非空**（CM-1 红线）。
yml 仅提供 CSV 供应商清单、**不含证据出处** → 本片**不伪造证据**，
把声明的每家注册为 `pending()`（已登记但未确认）：

```java
@Bean
public ZeroRetentionGate zeroRetentionGate(
        @Value("${agent.compliance.zero-retention.confirmed-providers:}") String confirmedProviders) {
    ZeroRetentionRegistry.Builder b = ZeroRetentionRegistry.builder();
    if (confirmedProviders != null && !confirmedProviders.isBlank()) {
        for (String id : confirmedProviders.split(",")) {
            String trimmed = id.trim();
            if (!trimmed.isEmpty()) {
                b = b.pending(trimmed);   // ⚠️ 声明但未确认 → 仍 fail-closed 拒绝真实数据
            }
        }
    }
    return new ZeroRetentionGate(b.build(), Clock.systemUTC());
}
```

**安全性**：`pending` 不等于 `confirmed`，`allows()` 对 pending 返回 false →
闸门仍拒绝真实学生数据，**行为不变（fail-closed 维持）**，仅注册表不再为空。

**诚实性**：配置读取端点（C1）将同时返回
「yml 声明的 confirmed-providers」与「注册表实际状态（pending）」，
前端 P17 据以显示：「已声明 3 家，当前均无有效确认证据 → 仍 fail-closed 拒绝」。
这正好满足 CM-4（区分配置声明值与运行时实际值），**不误导**。

### 1.3 后续（不在本片）

真正按证据确认需新增证据承载配置（如 `agent.compliance.zero-retention.provider-evidence.<id>`），
属第二/三片或独立 CHG，本片不引入。

### 2.2 `effective` 判定依据（严格按 FE-02 §2「生产是否生效」列 + P4 已接线事实）

| 配置键 | effective | 依据 |
|---|---|---|
| `agent.backpressure.*` | ✅ true | P4-D05 已实现并接入运行时 |
| `agent.rate-limit.*` | ✅ true | P3-D08 已实现 |
| `agent.retention.*` | ✅ true | P4-D04 已实现 |
| `agent.worker.*`（relay/concurrency/prefetch 等）| ✅ true | P4-D03 已实现 |
| `deployment.pilot.max-tenants` | ✅ true | P4-D05 校验 |
| `auth.jwt.token-ttl-seconds` | ✅ true | AuthConfiguration 已读（仅暴露 ttl，不暴露密钥）|
| `agent.run.max-cost-per-run` 等 4 个限键 | ❌ false | FE-02 §2：生产无读取点 |
| `agent.tool.risk-level-map` | ❌ false | 校验镜像，权威在代码 |
| `agent.approval.*` | ❌ false | 收紧算法未接线 |
| `agent.compliance.zero-retention.*` | ❌ false | 注册表本片仅接声明（pending），未确认 |

> ⚠️ **绝不暴露任何密钥/口令**：`auth.jwt.private-key`、`RABBITMQ_PASSWORD` 等一律不出现在响应中。
> 仅暴露非敏感的声明值 + 生效标志。

### 2.3 实现位置

- `agent-api`：`ConfigController`（`GET /api/config`）+ `ConfigView`/`ConfigGroup`/`ConfigEntry` 记录类型。
- `agent-application`（或 `agent-api` 内 `@Service`）：`ConfigReadService`，通过 `Environment` 读取 yml 键并据上表计算 `effective`。
- 测试：`ConfigReadServiceTest`（声明值 + effective 正确性，含零保留声明值映射）、
  `ConfigEndpointIT` 或上下文测试（端点存在、需认证、结构正确）。

## 3. 安全与诚实边界

| # | 边界 |
|---|---|
| B-1 | 端点默认受 `anyRequest().authenticated()` 保护；后端授权由 Security 兜底（前端 `RequireRole` 因 G1 未强制，属已知体验缺口，非安全缺口）|
| B-2 | 响应**绝不**含密钥/口令/私钥；仅非敏感声明值 + 生效标志 |
| B-3 | `effective=false` 的键必须如实标注「改后不影响行为」，不得让前端误以为配置已生效 |
| B-4 | 零保留页不得把 yml 三家名单显示为「已确认」；只显示「已声明未确认 → 仍 fail-closed」|
| B-5 | 本片**不**改变零保留闸门运行时行为（pending 仍拒绝），仅使注册表反映声明 |
