## 1. M-1：终止信号的形式不一致（**实测确认**）

### 1.1 契约与实现的对照

| 侧 | 约定的终止信号 | 证据 |
|---|---|---|
| **契约（FE-01 §P4 轮询策略）** | 「终止：收到 `: run-terminal` **注释行** → 关闭连接，停止轮询」| FE-01 §P4 轮询策略表 |
| **契约（前端解析器注释）** | 「后端追加**注释行** `: run-terminal` 后关闭流，故解析器必须识别注释行——它是『可以停止轮询』的**唯一信号**」| `frontend/src/features/run/sse.ts` 文件头 |
| **后端实现** | ❌ 发的是 SSE **事件帧**：`SseEmitter.event().name("run-terminal").data({state})` → 线上是 `event: run-terminal\ndata:{...}` | `RunEventStreamer.sseSender()` |
| **前端解析器** | ❌ 只在**注释行**分支置 `terminal = true`；事件帧走 `toRunEvent()` → 因无 `id` 行被**丢弃** | `sse.ts` `parseFrame()` |

### 1.2 后果链

```
后端发 event 帧 → 前端解析器丢弃（无 id 行）→ sawTerminal 永远 false
   → snapshot.done 永远 false
      → ① 页面状态标签停在「正在处理」（真实终态是 FAILED/CANCELLED 也一样）
      → ② 降级提示「正在处理，请稍候」常驻
      → ③ SSE 轮询每 3 秒重连一次，**永不停止**（直到用户离开页面）
```

> ⚠️ ③ 的资源浪费是实打实的：一次进度页访问 = N×20 次/分钟的后端请求，
> 而限流桶只有 **30 次/60 秒**（FE-D9 §2.3 配额表）——
> **光 SSE 一条链就占了 20 次/分**。
> FE-D9 用 G3 主动 `stop()` 绕过了这个坑，**但根因仍在**：
> 任何按 FE-01 契约实现的客户端都会挂在那里。

### 1.3 修法选择

| 选项 | 评价 |
|---|---|
| **A. 后端改发注释行**（本片采用）| ✅ 符合**已冻结的契约**（FE-01 + 前端解析器注释）；前端**零改动**；语义上「终止信号」本就是控制帧，不是业务事件 |
| B. 前端解析器兼容事件帧 | ⚠️ 与契约文本冲突，且**前后端两处都要改**；放弃已冻结的契约没有收益 |
| C. 两者都改 | ❌ 无收益（冗余分支）|

> ⚠️ **不选 B/C 的理由**：契约已经写明是注释行，且**前端注释明说它是「唯一信号」**——
> 改前端等于推翻既有契约，而没有任何好处。

## 2. M-2：G4 —— Worker 写 run_event

### 2.1 现状

`run_event` 表**只有** `RUN_CREATED` 由 `JdbcRunCreationRepository` 写入；
Worker **不写该表** → 进度页时间线**永远只有一条**。

### 2.2 事件类型与载荷（严格限既有白名单）

> 后端 SSE 白名单：`state, attempt, stepType, toolName, operationState, errorCode, phase`，
> 且**仅标量**（String/Number/Boolean）——其余一律丢弃（P3-D10 §5.2 S-6，fail-closed）。

| 事件类型 | 载荷 | 触发时机 |
|---|---|---|
| `RUN_STARTED` | `state=RUNNING`, `attempt=<n>` | Worker 领取租约后开始执行 |
| `TOOL_INVOKED` | `toolName`, `operationState` | 每次工具调用结束（含 UNKNOWN）|
| `RUN_SUCCEEDED` | `state=SUCCEEDED` | 执行成功 |
| `RUN_FAILED` | `state=FAILED` | 执行失败 |
| `RUN_CANCELLED` | `state=CANCELLED` | 已取消 |

> ⚠️ **不写事件的三种结局**（各有理由，不可偷懒全写）：

| 结局 | 不写的理由 |
|---|---|
| `unknownResult` | Run **不进入终态**（停在 RUNNING 等对账）→ 写「终态」事件是**撒谎**。改由 `TOOL_INVOKED` 的 `operationState=UNKNOWN` 表达 |
| `skippedStaleGeneration` | 世代失效 → 这次执行**没有产生结果**，写失败事件会**污染别人的 Run** |
| `retryableFailure` | 会重投 → 写终态事件会让前端**误判已结束** |

> ⚠️ **失败原因不进事件**：`commitFailure` 的 `reason` 是内部原文（如「模型调用失败：TIMEOUT」），
> 白名单里的 `errorCode` 要求是**码**而非原文。
> 且当前 `run.error_code` 列**根本没被写入**（`commitResult` 只写 state + result_payload）
> → 本片**如实登记**该缺口（同时影响 G3 的 `errorCode` 字段）。

### 2.3 序号分配（并发安全）

`run_event.sequence_no` 在 `(tenant_id, run_id)` 内唯一且单调递增（SSE 续传依据）。

| 方案 | 评价 |
|---|---|
| **A. 锁 run 行 + MAX+1 + INSERT（同事务）**（本片采用）| ✅ 序列化天然成立；run 行本就是热点（租约续期也在写它），锁粒度天然按 run |
| B. `pg_advisory_xact_lock` | ⚠️ 有效但引入 PG 专有依赖，且与项目「按 run 串行」的既有模型不直观 |
| C. `INSERT ... MAX+1`（无锁）| ❌ 并发下撞唯一约束（`run_event_seq_unique`）|

### 2.4 写入失败的处理

> 事件是**观测**，不是业务事实。Run 的成败**不依赖**事件是否写成功。

| 处置 | 理由 |
|---|---|
| **吞掉异常 + WARN 日志，不影响主流程** | 事件写失败不应让一次**已成功**的辅导变成失败（那会误触发重试 → 重复副作用）|
| **但不得静默** | 必须留 WARN：否则「时间线空了」无人知晓——这正是本项目反复吃的「静默失效」亏 |

| 项 | 实测 |
|---|---|

### ⛔⛔ 本片最重要的产出：补上 G4 最大的验证空洞

`JdbcRunEventAppendRepository` 落地时**零测试**——
「类写完了、端口定义了、Worker 也调用了」看起来全对，
但**没有任何一个测试连过真实 Postgres**。

这是 P4-D08 R-1（工具未注册为 Bean → 工具从不执行 → 表永远为空）的**又一次翻版**：
「表建了 ≠ 表里有写入方」。

补 `RunEventAppendIT`（10 项）：落库回读 / 序号单调 / **并发追加不撞唯一约束** /
跨租户不可见 / 非标量载荷 fail-closed / Run 不存在拒绝写 / 转义 / 空载荷。

### ⛔⛔ 新测试当场抓到 3 个 SSE **读路径**真实缺陷

`JdbcRunEventQueryRepository.parsePayload` 是一段**手写字符串切分器**，
注释写着「为一个扁平对象拖入 Jackson 不划算」——
但 `agent-infrastructure` **本来就依赖 Jackson**，「不引入」的收益是 0：

| 缺陷 | 危害 |
|---|---|
| `body.split(",")` 不识别字符串内逗号 | `errorCode="E1,E2"` 被读成 `{errorCode=E1, E2=null}` → **错误码被静默改写** |
| `unquote` 只处理 `\"` 和 `\\` | 含换行的值回读为**字面量两字符 `\n`** |
| 手写 `coerce` 把整数全当 `Long` | 写入 `Integer` / 读取 `Long` 不对称，下游 `==` 静默失败 |

三者都**不抛异常**，原有断言也抓不到——已补 2 项专项用例锁死。

> **方法论**：**静默失效靠「逐行看断言」抓不到，只能靠「针对可疑行为的专项用例」抓**。
