## 0. 范围决策：为什么本片做 G5、且不做 G7

### 0.1 为什么是现在

P4-D09 关闭了 **G3**（Run 状态）与 **G6**（画像），FE 侧仍有 **3 个页面**停留在
`Unavailable` 占位，且**占位内渲染的是硬编码假数据**（FE-D09 L-5）。

| 前端页面 | 阻塞缺口 | 后端状态 |
|---|---|---|
| **P4 进度页** | G3 | ✅ P4-D09 已关闭 |
| **P6 画像页** | G6 | ✅ P4-D09 已关闭 |
| **P5 结果页** | **G5** | ⬜ **本片关闭** |
| **P7 检索台** | G7 | ⬜ 不在本片 |

> ⚠️ **P5 的假数据是本片最直接的动机**：
> `RunResultPage` 当前把「分子分母同乘 √3」「根式分母有理化时符号丢了」
> 等**编造的解题过程**渲染给用户。占位组件的结构是 `{children}` 在前、
> 提示框在后 → **假数据在提示之前就被用户看到**。
> 这不是「占位不够优雅」，是**向学生展示不存在的内容**。

### 0.2 为什么不做 G7

| 缺口 | 数据源现状（实测）| 决定 |
|---|---|---|
| **G7** Run 列表 / 分页 / 排序 | `run` 表**无 `subject` 列**（只能从 `input_payload` JSONB 取，无索引）、**无 duration 列**（须 `completed_at - created_at` 计算）、**无 `created_at` 索引** | ❌ **不做** |

> ⚠️ 强行做会得到「**慢查询伪装成可用功能**」：
> 学科筛选在 JSONB 上无索引支撑，页面上看起来能筛，实际是全表扫。
> G7 须**独立排期 + 先补索引与列**，本片不解除该阻塞。

## 1. 现状实测（数据源的真实生产状态）

> ⚠️ **本节是全文的问题陈述**。下表逐项核实「哪个表在生产中真的有数据」，
> 而不是「哪个表建了」。

### 1.1 四个候选数据源

| 数据源 | 表/列 | 生产写入方 | 生产实际状态 |
|---|---|---|---|
| 结论文本 | `run.result_payload` | `RunExecutionLoop.commitSuccess`（`{"content":"…"}`）| ✅ **有数据** |
| 讲解内容 | 同上 | 同上 | ✅ **有数据**（与结论同源）|
| **解题步骤** | `run_step` | ⛔ **无任何生产写入方**（全仓仅 `JdbcErasureRepository` 的删除语句提到它）| ❌ **恒空** |
| **错因 / 知识点** | `weakness_record` | `RecordWeaknessTool`（唯一写入方）| ❌ **恒空**（`FakeModelGateway` 的 `toolCalls` 恒空 → 模型永不发起工具调用）|
| **待核对（UNKNOWN）** | `tool_operation.state='UNKNOWN'` | `JdbcToolOperationLedger` | ✅ **有权威来源** |

> ⚠️ **「表建了」≠「表里有数据」**。
> `run_step` 与 `weakness_record` 都**有完整的表、约束、RLS 策略与索引**，
> 但**生产写入方不存在或永不触发**——
> 与 P4-D08 的 R-1（工具从未注册为 Bean）**完全同构**：
> *静默不执行，系统表面正常*。

### 1.2 `weakness_record` 的索引缺口（实测）

| 表 | 按 `(tenant_id, run_id)` 查询的索引 | 结论 |
|---|---|---|
| `run_step` | `idx_run_step_run (tenant_id, run_id, step_number)` ✅ | 够用 |
| `tool_operation` | `idx_tool_operation_run (tenant_id, run_id)` ✅ | 够用 |
| **`weakness_record`** | ❌ **无**（三个索引分别以 `student_id` / `knowledge_point` / `created_at` 开头）| **须补 V9 迁移** |

> ⚠️ `weakness_record.run_id` 上有指向 `run(run_id)` 的**外键**，
> 但 PostgreSQL **不会**为外键的引用侧自动建索引 → 按 run 查会全表扫。
> 这一点在 P4-D09 §0 已被记录为 G5 的前置条件。

### 1.3 `result_payload` 的两种形状（⚠️ 决定契约的关键）

`RunExecutionLoop` 的两个提交路径写入**不同形状**的 `result_payload`：

| 路径 | 写入内容 | 语义 |
|---|---|---|
| `commitSuccess` | `{"content":"<模型输出>"}` | 正常结果 |
| `commitFailure` | `{"reason":"<内部失败原因>"}` | ⚠️ **内部错误原文** |

失败原因的实际取值包括：`模型调用失败：TIMEOUT`、`工具调用被拒绝`、
`输出涉嫌编造资料出处`、`步数超限`、`工具执行异常`。

> ⚠️ **这些字符串是内部错误细节**，与 P4-D09 对 `run.error_message` 的处置一致
> （「不得返回 `error_message` 原文——避免内部细节泄漏到客户端」），
> **本片对 `result_payload` 采用同一纪律**：
> **仅在 `state='SUCCEEDED'` 时返回 `content`，失败时一律不返回载荷原文。**

### 1.4 待核对分区的权威来源（实测）

`RunDispatchConsumer.toConsumeResult` 把 `UNKNOWN_RESULT` 映射为
`ConsumeResult.CLAIMED`——**ack 丢弃，绝不重投**（重投 = 重复副作用 = Sev-0）。

> ⚠️ 由此得到一个**必须写进契约**的事实：
> **工具结果 UNKNOWN 时，Run 不会进入终态**，它停留在 `RUNNING`，
> 等待人工/自动对账（`tool_operation` 保留 `UNKNOWN` 状态）。
>
> 故「未决」状态的权威来源是 **`tool_operation.state='UNKNOWN'`**，
> **不是** `run.state`（`run_state` 枚举里**根本没有** `RECONCILIATION_REQUIRED`）。

## 2. 契约冻结

### 2.1 端点

```
GET /api/runs/{runId}/result
```

| 项 | 值 |
|---|---|
| 授权动作 | `result:read`（**已存在于** `AuthorizationService.Actions`，且已授予 TENANT_ADMIN / AGENT_AUTHOR / VIEWER / WORKER）|
| 限流 | 复用 `EVENT_QUERY` 桶（与 G3 同属「只读轮询」类，不新增桶以免改动配额基线）|
| 不存在 / 跨租户 | 统一 **404**（不区分，否则构成存在性探测通道）|
| 命名 | camelCase（与 P4-D09 冻结一致）|

### 2.2 响应体

```jsonc
{
  "runId": "3f2b…",
  "state": "SUCCEEDED",              // run_state 枚举字符串
  "completedAt": "2026-10-20T08:12:33Z",  // ⚠️ 非终态为 null（不可退化成 EPOCH）
  "errorCode": null,                 // ⚠️ 仅失败时有值；**不是** error_message 原文
  "explanation": "……",              // ⚠️ 仅 state=SUCCEEDED 时非 null；否则 null
  "weaknesses": [                    // weakness_record（真实模型接入前恒空数组）
    { "knowledgePoint": "二次函数顶点坐标", "errorType": "符号错误", "confidence": 0.80 }
  ],
  "steps": [                         // run_step（无生产写入方 → 恒空数组）
    { "number": 1, "state": "SUCCEEDED", "stepType": "MODEL", "output": "……" }
  ],
  "reconciliation": {                // ⛔ **恒存在**，不是「有才显示」
    "pending": false,
    "operations": [
      { "operationId": "9a1c…", "toolName": "record_weakness", "state": "UNKNOWN" }
    ]
  }
}
```

### 2.3 契约条款（逐条可被断言）

| # | 条款 | 依据 |
|---|---|---|
| **K-1** | `completedAt` **非终态必须为 `null`**，不得退化为 `Instant.EPOCH` | P4-D09 §2.1 同款缺陷曾真实发生（返回 `1970-01-01T00:00:00Z`）|
| **K-2** | `explanation` **仅在 `state='SUCCEEDED'` 时非 null**；失败时**不返回 `result_payload` 原文** | §1.3 内部错误细节纪律 |
| **K-3** | `errorCode` **只给错误码**，绝不给 `error_message` / `reason` 原文 | P4-D09「不得返回 error_message 原文」|
| **K-4** | `weaknesses` / `steps` **恒为数组**（空即空数组，**不是 `null`**）| 前端不得区分「没有」与「接口坏了」|
| **K-5** | `reconciliation` **恒存在**（结构固定）| P0-D00 §3.4：终态存在未决 UNKNOWN 时**必须独立暴露**，不得隐藏在普通成功响应中 |
| **K-6** | `weaknesses[]` 为**结构化对象**（含 `knowledgePoint` / `errorType` / `confidence`）| 与 G6 冻结一致（P4-D09 §2.2）|
| **K-7** | 响应**不含** `input_payload`（学生提交的题目与解答，敏感载荷）| P4-D09 同款纪律 |
| **K-8** | 响应**不含** `tenantId`（租户只取自认证上下文）| 红线 9 |
| **K-9** | 响应**不含**任何教材引用 / 页码 / 出处字段 | **C5 硬红线**（DEC-5 不做 RAG，编造出处即判失败）|
| **K-10** | `explanation` 的内容**原样返回**，不做服务端改写 | 服务端改写 = 不可解释；C6 的兜底扫描在**前端渲染前**执行（职责划分见 §2.4）|

### 2.4 C5 / C6 / C7 三条红线的职责划分

| 红线 | 后端职责 | 前端职责 |
|---|---|---|
| **C5** 不显示教材引用/页码/出处 | ① 响应**不提供**任何引用字段；② 入库侧的 `HallucinationDetector` 已保证 `result_payload` 无引用形态 | UI **不设**引用展示位 |
| **C6** 结果不得含学生身份信息 | 原样返回模型输出（**不**因命中模式而静默截断——静默截断会让学生看到「缺了一截」的答案）| 渲染前用 `findLeakedFields` 扫描，命中则**拦截该字段并明确提示**（既有机制，`RunResultPage` 已导出该函数）|
| **C7** 结果不落 localStorage | — | 仅内存 |

> ⚠️ **C6 的分工是刻意的**：后端命中即**拒绝整个请求**会让「模型偶然复述了学号」
> 变成**整页不可用**；前端命中则**只拦该字段**并说明原因。
> 二者都不接受「静默删除内容」——那会让学生以为模型没提到这件事。

### 2.5 与前端的契约差异登记

| # | 差异 | 处置 |
|---|---|---|
| 1 | 前端 P5 现有占位内容是**硬编码的编造解题过程**（分子分母同乘 √3 等）| ⛔ **必须整体替换**，不得「只加外层取数」（FE-D09 L-5）|
| 2 | 前端 `pickWhitelisted` 按 `string[]` 处理 `weaknesses` | 本片冻结为**结构化对象**（K-6），前端须改为对象字段白名单 |
| 3 | FE-01 提到「未决 `UNKNOWN`/`RECONCILIATION_REQUIRED`」 | ⚠️ **`RECONCILIATION_REQUIRED` 在 `run_state` 枚举中不存在**；本片以 `tool_operation.state='UNKNOWN'` 为准（§1.4），前端**不得**等待一个不会出现的状态值 |
| 4 | 前端 P5 预期「解题步骤区」有内容 | `run_step` 无写入方 → `steps` 恒空 → 前端须显示**真实空态**（见下）|
| 5 | 前端预期「归因结论卡」有错因与置信度 | `weakness_record` 恒空 → `weaknesses` 恒空 → 同上 |

> ⚠️ **第 4、5 条的前端处置是本片的关键约定**：
> **空数组 → 显示「尚未记录」+ 解释原因（真实模型未接入）**，
> **不是**「系统故障」，**更不是**编造一条步骤来填版面。
> 后者与当前占位页的假数据**是同一个错误**。

### 3.1 为什么 `explanation` 从 `result_payload` 取、而不用 `run_step`

`run_step` 有 `output_payload` 列，语义上更像「步骤」。
但它**无生产写入方**（§1.1）→ 恒空。
若本片改为「只读 `run_step`」，端点在生产中**恒返回空**，
连「模型给了讲解」这一唯一真实存在的内容都读不到。
故本片**以 `result_payload.content` 为讲解来源**（真实有数据），
`run_step` 作为**结构化步骤来源一并读取**（为将来写入方预留），
并**诚实登记**「`steps` 目前恒空」。

### 5.1 反证实测记录

| 反证 | 注入 | 转红项数 | 关键转红用例 |
|---|---|---|---|
| **A-1** | SQL 去掉 `tenant_id` 条件 | **11 / 12** | `crossTenantRunIs404`、`crossTenantWeaknessesHidden` |
| **A-2** | `completedAt` 用 `Instant.EPOCH` 兜底 | 1 | `nonTerminalHasNoCompletedAtNorExplanation` |
| **A-3** | 取**整段载荷** + 移除 Java 纵深防御 | 2 | `failureExposesCodeButNotReason` |
| **A-4** | 去掉未决操作查询 | 1 | `unresolvedOperationIsExposed` |
| **A-5** | 集合字段返回 `null` | 2 | `collectionsAreAlwaysArrays`、`weaknessesAreStructured` |
| **A-6** | 端点路由不注册 | **11 / 12** | `resultReturnsExplanation` 等 |
| 还原后 | — | **0** | 基线复跑全绿 |

> ⚠️ **A-3 的第一次注入是空操作**（no-op mutation）：
> 把 `CASE WHEN state='SUCCEEDED' THEN result_payload->>'content' END`
> 改成 `result_payload->>'content'`（去掉 CASE）**并不会**泄露失败原因——
> 因为失败载荷是 `{"reason":…}`，**没有 `content` 键**，`->>'content'` 返回 NULL。
> 真正危险的改法是取**整段载荷** `result_payload::text`，
> 那样才会把 reason 原文带出去。**「注入缺陷」必须真的注入缺陷**——
> 否则会得到「反证通过」的假结论（与 P3-D04 的 T-1b 教训同源：
> 判据是**反证能否转红**，不是「反证跑过了」）。

> ⚠️ **A-3 还暴露了「两层防御」的效应**：只破 SQL 层时用例**不红**
> （Java 侧的 `if (!"SUCCEEDED".equals(state)) explanation = null;` 挡住了）。
> 这说明纵深防御是有效的，但**也意味着反证必须同时破坏两层**才有效——
> 记录于此，避免后来者误以为「A-3 不转红 = 用例没覆盖」。

> ⛔ 遵循项目铁律：**文档先于代码**（`P0-D06` DoD §8.0）。
> 实现偏离本文档时须先改文档再改代码。

### 6.1 本片顺带修掉的**测试基础设施缺陷**（比端点本身更重要）

> ⚠️ 这三项都不是本片的目标，但它们**直接威胁本片结论的有效性**——
> 若不修，反证结果会因环境噪声而失真。

| # | 缺陷 | 现象 | 根因 | 修法 |
|---|---|---|---|---|
| **T-1** | ⛔ **IT 的清理从未生效** | IT 库累积 **961 条 run**（t-a 占 929）| RLS `FORCE ROW LEVEL SECURITY` + 策略 `tenant_id = current_setting('app.tenant_id', TRUE)::uuid`；**未绑定租户时该设置返回 NULL → 恒不匹配 → `DELETE 0`**。清理代码「执行了」却**什么都没删** | 清理改为**绑定租户**（`inTenantTx`）后执行；实测 `DELETE 0` → 正常删除 |
| **T-2** | ⛔ **限流桶跨轮次累积** | 反复跑 IT 时随机 **429**，失败现场指向「限流坏了」| `rate_limit_bucket` 是 DB 状态，前一轮的计数**留在库里**，把「30 次/60 秒」配额吃光 | IT 的 `@AfterEach` 一并清 `rate_limit_bucket`；实测连跑两轮均 0 红 |
| **T-3** | ⚠️ **`dev-postgres.sh` 的迁移清单硬编码** | 脚本写死 `for version in 1 2 3 4 5 6 7` → **V8/V9 永不生效**，重建环境会缺迁移 | 清单与迁移目录**脱节**，且系统表面正常 | 改为**扫描目录自动发现**并按版本号排序；新增迁移自动生效 |

> ⚠️ **T-1 是本片最深的教训**：
> 清理代码**看起来在工作**（没有报错、语句执行了），
> 但因 RLS 恒不匹配而**一行都没删**——
> 这与 P4-D08 的 R-1（工具未注册为 Bean）、RAG-D09 的 R-D1（挂接方向反了）
> **完全同构**：*静默失效，系统表面正常*。
>
> **「测试通过」与「测试真的跑过」是两件事**——
> 本项目已第 **3** 次因「静默不执行」栽在同一形态上。

### 6.2 残留清理纳入 IT 库准备流程

多个 `agent-infrastructure` 集成测试**没有 `@AfterEach` 清理**（如 `RunClaimFencingIT` 只创建不删除），
每跑一轮全量构建残留 ~54 行 `run`。
累积到 1000 行左右即会占满 `claimTasks` 的 `ORDER BY created_at LIMIT 1000` 窗口 →
**后来者报「任务未被领取」**（F-9 形态第三次）。

**处置**：`scripts/dev-it-db.sh` 新增「清理测试残留」步骤（建库流程内，种子数据随后幂等重建）。
> ⚠️ **`audit_record` 刻意不清**：它有「追加不可改」触发器（R-3 不变式），
> `DELETE` 会被 `forbid_audit_mutation()` 拒绝。
> **绕过该不变式来「方便清库」＝用便利换掉一条安全不变量**，本项目不这么做；
> 审计残留在隔离库中惰性无害（不参与任务窗口、不占限流配额）。
