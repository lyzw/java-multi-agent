## 0. 范围决策：为什么本片只做 G3 + G6

P4-D08 修通了工具链路，下一片按 P4-D07 §0 的规划是「第二片：G3 / G5 / G6 / G7」。
经**实测后端现状 + 实测前端页面需求**后，逐项判定：

| 缺口 | 数据源现状（实测） | 本片决定 | 理由 |
|---|---|---|---|
| **G3** Run 状态查询 | ✅ **100% 就绪**：`run` 表字段齐全（`state`/`created_at`/`completed_at`/`attempt`/`error_code`）；`RunEventQueryPort.findState` 已实现真实 SQL | ✅ **做** | 改造量最小；且 **P4 进度页当前只能靠 SSE 推断状态**，而 `run_event` 只有 `RUN_CREATED` 有生产写入方（Worker 不写）→ 进度页长期无进展，G3 是刚需 |
| **G6** 画像查询 | 🟡 读取代码已就绪（`StudentDataRepository.loadProfile` 完整实现，含事务绑定 RLS + 防枚举空画像）；但**生产数据源当前为空**（见 §1.2）| ✅ **做** | 端点本身是刚需；**须诚实标注数据源现状**，不得让前端以为「有接口=有数据」 |
| **G5** 结果读取 | 🟡 `run.result_payload` 存在，但实际内容只有 `{"content":"…"}`（`RunExecutionLoop.java:211`）——**无步骤、无错因、无知识点** | ❌ **不做** | 归因数据在 `weakness_record` 多行里，须**联表**；而该表**无 `run_id` 索引**（V2 三个索引分别以 `student_id`/`knowledge_point`/`created_at` 开头）→ 按 run 查会全表扫。属独立一片 |
| **G7** 列表分页 | 🔴 **零代码**：端口层、应用层、SQL 约定三处全空白；`run` 表**无 `subject` 列**（只能从 `input_payload` JSONB 取，无索引）、**无 duration 列**（须 `completed_at - created_at` 计算）、**无 `created_at` 索引** | ❌ **不做** | 成本最高；且「学科筛选」在 JSONB 上无索引支撑，强行做会得到**慢查询伪装成可用功能**。须独立排期 + 补索引 |

> ⚠️ **不做 ≠ 不存在**：G5/G7 仍是 FE F5 的阻塞项，本片不解除该阻塞。
> 本片**只**解除 P4 进度页（P4）与画像页（P6）的**端点**阻塞。

## 1. 现状实测（缺陷与约束证据）

### 1.1 G3：数据源就绪，但「状态查询」从未暴露为端点

`RunEventQueryPort.findState` 已实现（`JdbcRunEventQueryRepository.java:120`，真实 SQL `SELECT state::text`），
但**只在 SSE 控制器内部用于 404 判定**（`RunEventController.java:212-216`）——状态**从不被返回给客户端**。

而前端 **P4 进度页**（`RunProgressPage.tsx:36-39`）**只**调用 SSE，从不查状态；
`frontend/src/features/run/eventStream.ts:8-11` 明确注释：

> `run_event` 表**只有 RUN_CREATED 由生产代码写入**，Worker 不写该表。
> 故进度页长期拿不到执行中事件 —— 必须能优雅降级。⛔ 绝不编造进度百分比。

**即：G3 是 P4 进度页的唯一可靠信息来源。**

### 1.2 G6：读取代码就绪，但**生产数据源当前为空**

`StudentDataRepository.loadProfile` 实现完整（含 `TenantSessionBinder` 事务绑定 RLS + `ProfileView.empty` 防枚举），
但其唯一写入方是 `record_weakness` 工具；而**模型当前永不发起工具调用**：

```java
// WorkerExecutionConfig.java:77-84（生产装配）
return new FakeModelGateway(
        FaultMode.NONE,
        new ModelResponse(
                "这道题考查一元一次方程。请移项求解。",
                java.util.Map.of(),          // ⚠️ toolCalls 为空
                new ModelResponse.ModelUsage(10, 20),
                ModelResponse.FinishReason.STOP));
```

`ModelResponse` 第 2 个参数即 `toolCalls`（`ModelResponse.java:18`）→ **模型从不请求任何工具** →
`record_weakness` 不执行 → `weakness_record` 表在生产中**永远为空**。

> ⚠️ **这是本片最重要的诚实边界**：
> G6 端点**能返回正确数据**，但**在真实模型接入（D-002）前返回空画像**。
> 端点必须**如实返回空**，**不得**为了「看起来有数据」而伪造画像。
> 前端**不得**把「接口返回空」渲染成「系统故障」——那是**真实状态**（该学生还没被辅导过）。

### 1.3 ⚠️ 前后端契约 12 处不一致（实测，本片须冻结或登记）

前端三页（P5/P6/P7）**全为 `Unavailable` 占位**，且**占位内的硬编码假数据仍会渲染给用户**
（`states.tsx:147-169` 的 `Unavailable` 结构是 `{children}` **在前**、提示框**在后**）。

| 1 | 🔴 高 | **`weaknesses` 类型冲突**：前端要 `string[]`（`ProfilePage.tsx:34-36` 过滤非字符串），后端产 `{knowledgePoint, errorType, confidence}[]` | **本片冻结为结构化对象**（置信度/错因类型有业务价值）；前端下片改造 `pickWhitelisted` |

| 4 | 🟠 中 | P7 下拉**漏 `CANCELLED`**（后端真实终态，用户无法筛选）| **本片补上** |
| 5 | 🟠 中 | P5「待核对分区」**无字段名约定**（只有 `data-testid` + 两个状态字面量）| G5 片处理；本片登记 |

### 1.4 ⚠️ JSON 命名必须 camelCase（实测依据）

前端**零转换**直接取值（`client.ts:97` `return body as T`），
后端**无任何** `property-naming-strategy` / `@JsonNaming` 配置（全仓零命中）→
**Java record 组件名直接序列化为 camelCase**。
已验证样本：`CreateRunResponse(runId, replayed, state, correlationId)`、`ConfigResponse(groups, zeroRetention, effectiveFlags)`。

→ **本片两个端点的 JSON 字段全部 camelCase**：`runId` / `state` / `createdAt` / `completedAt` / `attempt` / `errorCode` / `studentId` / `grade` / `subject` / `weaknesses` / `notFound`。

### 1.5 授权动作缺 `profile:read`（实测）

`AuthorizationService.Actions` 现有 10 个动作（`run:create`/`run:read`/`run:cancel`/`event:subscribe`/
`result:read`/`tool:invoke`/`approval:consume`/`unknown:dispose`/`audit:read`/`agent:manage`），
**无画像读取动作**。

G6 需要**新动作** `profile:read`。⚠️ **必须同时更新 `Actions.ALL`**（启动期自检用），
且**默认拒绝**原则要求：新动作**不**自动加入任何角色的权限集，除非显式登记。

## 2. 契约冻结（本片的正式约定）

### 2.1 G3：`GET /api/runs/{runId}`

**请求**：`GET /api/runs/{runId}`，需 Bearer 令牌。

**响应 200**：
```json
{
  "runId": "uuid",
  "state": "SUCCEEDED",
  "createdAt": "2026-10-20T04:00:00Z",
  "completedAt": "2026-10-20T04:00:03Z",
  "attempt": 1,
  "errorCode": null
}
```

| 字段 | 类型 | 来源 | 说明 |
|---|---|---|---|
| `runId` | string | `run.run_id` | |
| `state` | string | `run.state` | `run_state` 枚举 6 值之一（**不含 `UNKNOWN`**）|
| `createdAt` | string | `run.created_at` | ISO-8601 |
| `completedAt` | string \| null | `run.completed_at` | 非终态为 `null` |
| `attempt` | number | `run.attempt` | 领取次数 |
| `errorCode` | string \| null | `run.error_code` | 失败原因码；**不含 `error_message` 原文**（避免泄漏内部细节）|

**响应 404**：Run 不存在**或**不属于当前租户 → **统一「资源不存在」**，
**不区分「不存在」与「无权限」**（否则构成存在性探测通道——同 `RunEventController.java:212-216` 的既有纪律）。

> ⚠️ **`state` 绝不可返回 `UNKNOWN`**：`UNKNOWN` 是 `tool_operation_state` 而非 `run_state`
> （`RunState.java:31-32` 明文）。若返回 `UNKNOWN`，前端 `isTerminalState()` 判 false → **轮询永不停止**。

### 2.2 G6：`GET /api/profiles/{studentId}`

**请求**：`GET /api/profiles/{studentId}`，需 Bearer 令牌。

**响应 200**：
```json
{
  "studentId": "stu_0123456789abcdef",
  "grade": "初二",
  "subject": "数学",
  "weaknesses": [
    { "knowledgePoint": "根式分母有理化", "errorType": "符号错误", "confidence": 0.82, "createdAt": "..." }
  ],
  "notFound": false
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `studentId` | string | 随机匿名标识（`^stu_[a-z0-9]{16}$`）|
| `grade` | string \| null | `student_profile.grade` |
| `subject` | string \| null | `student_profile.subject` |
| `weaknesses` | object[] | **结构化**：`knowledgePoint` / `errorType` / `confidence` / `createdAt`（见 §1.3-1）|
| `notFound` | boolean | 学生不存在 → `true` 且 `grade`/`subject` 为 `null`、`weaknesses` 为 `[]` |

> ⚠️ **不存在返回 200 + `notFound:true`，不返回 404**：
> 若不存在报错、存在返回数据，攻击者可据此**枚举有效 studentId**（`GetStudentProfileTool.java:82-83` 的既有纪律）。
> 画像页对「学生不存在」应显示**空态**，不是错误。

> ⚠️ **只返回 DEC-6 白名单四类**：随机 `studentId` / 年级 / 学科 / 薄弱点。
> **不得**返回姓名、学校、班级、身份证、手机、定位、生物识别。
> DB 层亦**结构上无法采集**（V2 迁移刻意不建此类列）。

## 3. 实现方案

### 3.1 新增端口（agent-ports）

| 端口 | 方法 | 说明 |
|---|---|---|
| `RunQueryPort` | `@Nullable RunStatus findStatus(tenantId, runId)` | G3 数据源；SQL **必须显式带 `tenant_id`**（即便 RLS 隔离，应用侧条件仍是第一道防线）|
| `ProfileQueryPort` | `@NonNull ProfileView loadProfile(tenantId, studentId)` | G6 数据源；**返回空画像而非 null**（防枚举）|

### 3.2 新增授权动作

```java
/** 读取学习画像。 */
public static final String PROFILE_READ = "profile:read";
```
并加入 `Actions.ALL`。⚠️ **不**自动加入任何角色权限集——
按「默认拒绝」原则，须在 `RoleBasedAuthorizationService.ROLE_PERMISSIONS` 中**显式**登记。

> ⚠️ **选 `profile:read` 而非复用 `run:read`**：画像是**学生维度**数据，Run 是**执行维度**数据，
> 二者授权范围不同（家长/教师可读画像，未必可读所有 Run）。**不得**为省事复用。

### 3.3 新增端点（agent-api）

- `RunQueryController`：`GET /api/runs/{runId}`
- `ProfileController`：`GET /api/profiles/{studentId}`

**沿用既有范式**（`RunEventController` / `RunController`）：
1. `authorization.requireAuthorized(context, Actions.RUN_READ / PROFILE_READ, resourceId)`
2. 限流（`RateLimitPort.Buckets`）
3. 不存在 → `ResponseStatusException(NOT_FOUND, "资源不存在")`（**不区分无权限**）

### 3.4 装配

沿用 P4-D07/P4-D08 惯例：**显式 `@Bean`**（不用 `@Service`/`@Component`），避免测试切片扫描冲突。

## 4. 前端侧同步（本片一并修，因为都是低成本且确凿的缺陷）

### 4.1 P7 状态筛选的死选项 `UNKNOWN`（🔴 高）

`RunSearchPage.tsx:43` 的 `<option value="UNKNOWN">待核对</option>`：
后端 `run_state` 枚举**没有** `UNKNOWN`（`RunState.java:31-32` 明文它是 `tool_operation_state`）。
按此筛选 → **恒空集**，用户会以为系统坏了。

**处置**：**移除该选项**。待核对数据属 `tool_operation`，将在 G9 处置台呈现，**不属于 Run 列表筛选**。

### 4.2 P7 漏掉 `CANCELLED`（🟠 中）

后端 `run_state` 有 `CANCELLED`（终态），前端 `runState.ts:16` 的 `RUN_STATES` 也有，
但 P7 下拉**没有该选项** → 用户**无法筛出已取消的 Run**。**补上**。

### 4.3 P7 状态中文标签统一（🟡 低）

下拉「分析中/超时」与全局映射「执行中/已超时」不一致 → **统一为全局映射**。

## 6. 已知限制（诚实边界）

| # | 限制 | 说明 |
|---|---|---|
| L-1 | **G6 在真实模型接入前返回空画像** | `FakeModelGateway` 的 `toolCalls` 为空 → 模型永不发起工具调用 → `weakness_record` 永远为空（见 §1.2）。**端点如实返回空**，前端须显示「还没被辅导过」而非「系统故障」 |

## 8. 修复记录（2026-10-20 14:30 · 实测）

> 本片实施过程中实测发现并修复的构建级缺陷，**必须留档**——
> 它使本模块的**全部**集成测试在 `mvn verify` 中无法引导，而构建仍把其它模块报 SUCCESS。

### 8.1 F-15：fat jar 布局导致 failsafe 无法引导

| 项 | 内容 |
|---|---|
| 现象 | `platform-bootstrap` 下**每一个** `*IT` 类报「Failed to find merged annotation for @BootstrapWith」；同一个类走 surefire（`mvn test`）完全正常 |
| 根因 | `repackage` 在 package 阶段把主构件替换成 Spring Boot **fat jar**，类位于 `BOOT-INF/classes/`——那是 Spring Boot 自定义类加载器的布局，**failsafe 的普通 classloader 读不到** `PlatformApplication` → `@SpringBootTest(classes=…)` 内省抛 `TypeNotPresentException` → 元注解 `@BootstrapWith` 无法内省 |
| 修法 | `spring-boot-maven-plugin` 的 `repackage` 挂 `<classifier>exec</classifier>` → 主构件保持 **thin jar**（类在根目录），可执行胖包另出 `platform-bootstrap-…-exec.jar`（Spring Boot 官方标准做法）|
| 效果 | **本模块集成测试整体复活**：`ReadEndpointIT` 12 项 + `ConfigEndpointIT` 4 项首次真正进入 failsafe，基线 **127 → 143** |
| 部署影响 | 部署时使用带 `exec` 后缀的包，见 `docs/本地启动指南.md` |

### 8.2 `ConfigEndpointIT` 的 4 项断言：曾被误删，本片**恢复**

曾一度被清空成空壳（`@Nested` 包裹 + 4 项断言消失），类不再出现在 failsafe 报告中，
**看着像「修好了」，实际是把测试删了**。本片**恢复全部 4 项**，其中 **E-2c 是密钥泄露防护断言**：

| 编号 | 断言 | 性质 |
|---|---|---|
| E-1a | 无令牌访问 → 401 | 安全链 |
| E-2a | 带令牌 → 200 且含 `groups` / `zeroRetention` | 结构契约 |
| E-2b | 零保留声明三家且均为 `PENDING` | 合规状态 |
| **E-2c** | **响应不含私钥 / 口令** | **密钥泄露防护** |

> **测试消失 ≠ 问题解决。** 这是本项目铁律「不得因代码做完而宣称风险消除」的反面样本。
