# P4-D04 数据保留与删除机制（Retention & Erasure）

> **阶段**：P4-D04　**验收**：FR-019（未成年人数据合规）· NFR-008（脱敏/保留）· P0-D00 §4.4
> **威胁**：R-012（未成年人个人信息处理不合规）· R-015（数据超期留存扩大泄露面）
> **状态**：🔄 进行中

## 0. 本片要解决的缺口：保留期是**承诺**，不是**机制**

### 0.1 实测证据（2026-10-19）

| 检查项 | 方法 | 结果 |
|---|---|---|
| 删除 / 清理实现 | 主源码检索 `delete` / `DELETE FROM` / `purge` / `retention` | ❌ **零命中** |
| 保留期列 | 19 张表检索 `expires_at` / `retain_until` | ❌ **零命中** |
| 清理定时任务 | 检索调度/后台线程 | ❌ 零 |
| 保留期承诺 | P0-D00 §4.4 / P0-D02 §5 | ✅ **已冻结四类数值** |

已承诺但无执行的四类数据：

| 数据 | 保留期 | 出处 |
|---|---|---|
| 学习画像 | 12 个月 | P0-D00 §4.4 |
| Prompt / 工具结果 | 90 天 | 同上 |
| 审计日志 | 180 天 | 同上 |
| Trace / 指标 | 30 天 | 同上 |

> ⚠️ **「有承诺、无机制」是合规审计中最难辩解的一种形态**：
> 文档写得越齐全，审计方越会默认机制也存在；而检测方只需要执行一句
> `SELECT count(*) FROM student_profile WHERE created_at < now() - interval '1 year'`
> 就能得到结论。这不是「未来要做」，而是**每天都在累积违约行数**。

## 1. 本片的核心张力：审计不可改 **vs** 审计必须到期删除

V6 迁移的 `audit_record` 触发器：

```sql
BEFORE UPDATE OR DELETE ON audit_record
FOR EACH ROW EXECUTE FUNCTION forbid_audit_mutation();   -- 直接 RAISE
```

而 V6 自己的 `COMMENT` 写着：

> 180 天保留期到期清理须走受控运维流程（**临时禁用触发器** + 记录操作主体），
> 本层刻意不提供自动清理。

这段注释承认了欠账，但给出的解法留下三个未定义问题：

| # | 未定义项 | 后果 |
|---|---|---|
| 1 | 谁来临时禁用触发器、依据什么授权 | 清理动作**无授权链** |
| 2 | 删了哪些行、多少行 | 清理动作**无凭证**，事后无法举证 |
| 3 | 禁用窗口内其他会话的篡改同样不被拦 | **为合规而执行的操作，反而关闭了 R-3 防篡改** |

> ⚠️ 第 3 条是本片最重要的一条：
> 一个「按流程执行合规清理」的人，恰好拥有在该窗口内篡改审计日志的能力，
> 且篡改不留痕迹。这与 D07 建立 R-3 防线的初衷正面冲突。

## 2. 决策

### D-1 审计清理走「受控通道」，**不做**「临时禁用触发器」

**决策**：改造 V6 触发器，`DELETE` 时检查 `current_setting('agent.retention.actor', TRUE)`：

- 非空 → 放行，该值即为操作主体，须落凭证；
- 空 → 拒绝（保持 V6 原语义不变）。

**理由**：
- ✅ 触发器**永不被禁用** → 不存在「清理窗口内失去 R-3 防护」的时间段；
- ✅ 每次删除都必须**显式声明操作主体**，否则语句直接失败；
- ✅ 与 D07 同一手法（应用层 + DB 双保险）：`JdbcAuditRepository` 仍刻意不提供 delete 方法。

**否决方案**：改造为按月分区表 + `DROP PARTITION`。
理由是改造面过大（V6 已上线），且分区与既有 `FORCE RLS` + `(tenant_id, created_at)` 索引组合需重新验证；
本片先用最小侵入方案闭合缺口，分区改造列为 P5 候选。

> ⚠️ **诚实降级**：`set_config()` 任何会话都能调用，
> 因此这条**不是访问控制，而是「意图声明 + 强制留痕」**。
> 真正的防线是 DB 权限分离（清理任务专用凭据），属外部事项，见 §8 L-2。

### D-2 Prompt 90 天：**字段级置空**，不是删行

**决策**：清理 `run.input_payload`、`run_step.input_payload|output_payload`、
`tool_operation.tool_arguments|result_payload`，统一置为 `'{}'::jsonb`，**保留 run 行**。

**理由（全部来自实测 schema，非推测）**：

| 约束 | 证据位置 | 若采用「天真删行」的后果 |
|---|---|---|
| `weakness_record.run_id → run(run_id) ON DELETE CASCADE` | V2 §2 | ⚠️ **删 run 行会级联删除学生薄弱点**——那是业务数据，不是 Prompt |
| `run.input_payload JSONB NOT NULL` | V1 §5 | 不能置 `NULL` |
| `run_result_consistent CHECK (state <> 'SUCCEEDED' OR result_payload IS NOT NULL)` | V1 §5 | `SUCCEEDED` 的 run 不能把 `result_payload` 置 `NULL` |

> ⚠️ 天真删行的失败形态是**静默**的：90 天后批量抹除学生薄弱点，
> 报错信息不会指向真正原因，而被删除的业务数据已经无法恢复。
> 这是本片选择「置空」而非「删行」的唯一理由。

### D-3 撤回同意：登记 → 30 天宽限 → 到期强删 → 全程可举证

**决策**：新增 `consent_withdrawal` 登记撤回，30 天宽限期届满后由清理任务执行删除，
全过程写 `erasure_certificate` 凭证。

**理由**：FR-019 要求「监护人单独同意可撤回 + 撤回后 30 日内删除」。
「30 日内」是**上限而非目标值**，但不能是无限期——
故本片取：**登记当日即可删，但最迟必须在第 30 天删**（否则保持
證書 Measurable）。

⚠️ **同一学生重复撤回**：用 `UNIQUE (tenant_id, student_id)` 约束，
第二次登记直接冲突，避免「撤回两次产生两条凭证」的举证混乱。

### D-4 清理必须经过租户连接，禁止 ADMIN 连接跨租户删

**决策**：所有清理走 `tenantConnection(tenantId)`，逐租户执行。

**理由**：ADR-006 的 RLS `USING` 子句同时约束 `DELETE` 的可见行。
用 ADMIN（超管）连接做批量删除，等于**用一个错误的 tenant_id 就可能删掉全校数据**，
且不受 surefire 的本机Falha保护。这与 Pandas▍的铁律同源：
若常开的自动化任务绕过了这条数据边界，一次配置错误的影响面就是全租户。
> 这与记忆第 1 条（RLS 事务铁律）同源：**批量操作的便捷性不能换来隔离性**。

### D-5 保留期配置 fail-closed

**决策**：`agent.retention.*` 五项**缺失或非法即拒绝启动**。

**理由**：与 D8 `RateLimitPolicy` / D4 `BudgetPolicy` / D03 `WorkerPolicy` 同一取舍——
退回默认值等于「悄悄用了一个没人审过的保留期」。
对未成年人数据而言，**过短是违规删除（破坏举证），过长是违规留存**。
两者都不是「保守」的方向，因此不存在安全默认值。

### D-6 清理必须幂等且可重复执行

同一租户同一天、同一原因，只产生**一张**凭证；重复运行只更新行数，不新增凭证。
理由：凭证数量失控会让「发生了什么」无法判读——
而 duplicated 凭证会被误读为「删了两次」，即 claimed double erasure。

## 3. 数据处置矩阵

| 数据类别 | 目标 | 保留期 | 处置 | 所属对方 autre |
|---|---|---|---|---|
| 学习画像 | `student_profile` | 12 月 | **删行** | 按 `created_at` |
| 学习画像明细 | `weakness_record` | 12 月 | 删行 / 随画像 CASCADE | 与画像一致 |
| Prompt | `run.input_payload`、`run_step.input_payload` | 90 天 | **置空 `'{}'`** | 见 D-2 |
| 工具结果 | `run_step.output_payload`、`tool_operation.result_payload`、`run.result_payload` | 90 天 | **置空 `'{}'`** | 见 D-2 |
| 审计日志 | `audit_record` | 180 天 | **删行**（受控通道）| 见 D-1 |
| Trace | `run_event` | 30 天 | 删行 | ⚠️ 见下方注 1 |
| 幂等键 | `idempotency_record` | **不定** | 本片**不清理** | ⚠️ 见下方注 2 |
| 删除凭证 | `erasure_certificate` | **不定** | 本片**不清理** | ⚠️ 见下方注 3 |

**注 1（run_event 删除的副作用）**：`run_event` 是 SSE `Last-Event-ID` 续传依据。
删除后客户端重连时游标不存在，V1 已约定「游标过期按协议重置」——
删除 Trace 与该约定一致，ADR 不变。

**注 2（幂等键为何不清）**：删除幂等键 = **解除有副作用工具的重复执行保护**。
`NFR-004` 提到幂等键有保留期但未定值；
在「重复请求的最晚到达窗口」得到业务确认前，清理幂等键会把
90 天前的 `record_weakness` 请求重新转为可写（Sev-0 风险）。
本片刻意不动它，列为 L-3。

**注 3（凭证为何不清）**：凭证是「删除确实发生」的唯一证据。
自清理会销毁自己的证据链。凭证量级极小（每日数条），故本片不实现其清理，
列为 L-4。

## 4. V8 迁移

新建两张表 + 改造 V6 触发器。三处都必须遵循既有纪律：

| 纪律 | 出处 | 后果 |
|---|---|---|
| `ENABLE` **且** `FORCE ROW LEVEL SECURITY` | V2 §4 | 只 ENABLE 时表 owner 绕过 → Sev-0 |
| `DROP POLICY IF EXISTS` 再 `CREATE` | V2 §4 | 缺则二次运行中断，**后续语句静默跳过** |
| `GRANT` 逐条执行 | V2 §4.1 | 整段事务中任一条失败会回滚全部 GRANT，表现为「授权数 = 0」且无明显报错 |

### 4.1 表

```
consent_withdrawal  撤回登记：(tenant_id, student_id) 唯一，含 withdrawn_at / due_at / state / erased_at
erasure_certificate 删除凭证：reason / actor / executed_at / dry_run / detail(JSONB 行数明细)
```

`erasure_certificate.reason` 的 CHECK 限定为
`RETENTION_EXPIRED` / `CONSENT_WITHDRAWN` 两值。
⚠️ 只允许这两个值——「临时」「调试」之类 reason 一旦被允许，
凭证就从「举证材料」退化为「清理日志」。

### 4.2 触发器改造（最小侵入）

```sql
CREATE OR REPLACE FUNCTION forbid_audit_mutation() RETURNS TRIGGER AS $$
BEGIN
    -- ⚠️ P4-D04 D-1：受控清理通道。
    --    仅当会话显式声明操作主体时才放行 DELETE，该主体须落凭证。
    IF TG_OP = 'DELETE'
       AND NULLIF(current_setting('agent.retention.actor', TRUE), '') IS NOT NULL THEN
        RETURN OLD;
    END IF;
    RAISE EXCEPTION '审计记录为追加不可改（R-3）：禁止 % 操作 audit_record（audit_id=%）。',
        TG_OP, OLD.audit_id USING ERRCODE = 'restrict_violation';
END;
$$ LANGUAGE plpgsql;
```

> ⚠️ **`UPDATE` 仍然一律拒绝**：清理只删不改。
> 若某天有人声称「我只是修正一条审计」，答案仍然是不行——这是 R-3 的底线。

### 5.1 ⚠️ 必须提供调度，否则是第三次断链

> 记忆第 15 条：D01 断链第一层（consumer 不执行）、D03 断链第二层（无人调用 consumer）。
> **共同形态**：机制存在、行为测试全绿、但不在链路上。

本片若只交付 `RetentionPurgeService` 而不交付调用它的东西，
就会第三次复制同一个错误——且这次更隐蔽，因为它表现为
**「数据按承诺被保留，实际从未被删除」，而系统表面完全正常**。

因此本片必须同时给出：
1. `RetentionJob` 后台线程（与 D03 `OutboxRelay` 同形态，显式 `start/stop`）；
2. **连通性测试**：断言 `RetentionJob` Bean 存在 **且** 持有真实清理服务；
3. **端到端测试**：写入到期数据 → 运行一轮 → 断言数据真的消失。

### 7.0.1 ⚠️ 本片实测发现的真实缺陷：F-12

**`Instant.minus(months, ChronoUnit.MONTHS)` 抛 `UnsupportedTemporalTypeException`。**

`Instant` 只支持基于**固定时长**的时间单位，「月」的长度随日历变化，故不被支持。
失败链条：

```
RetentionPurgeService.runOnce
  → runCategory("画像", ...)            ← try/catch 吞异常
      → now.minus(12, ChronoUnit.MONTHS) ← 抛 UnsupportedTemporalTypeException
  → 记录 ERROR 日志，返回 -1
  → 画像清理类别永远为 0 行
```

**为什么危险**：异常的表现形态与「本轮确实没有到期数据」完全一致——
任务不报错、其余三类正常、健康检查全绿，**画像永远不会被清理**。
这是本项目反复治理的「存在但不生效」的又一实例，
且它是被**新增的 `RetentionJobTest` 直接暴露**的——
在写这个测试之前，所有代码都是「看起来正确」的。

**修复**：经 `atZone(WINDOW_ZONE)` 转到带日历语义的类型后再回退到 `Instant`。

**反证（已执行）**：把修复改回原写法 →
`RetentionPolicyTest.profilePurgeActuallyRuns` 与 `certificateWrittenWhenChanged`
**如期转红**（2 项），恢复后转绿。
> ⚠️ 这条反证的价值在于：它证明这两条用例确实有牙齿。
> 若它们仍然全绿，那说明测试只是「写了」，与本片要根治的缺陷同源。

故 V8 是**手工应用**到开发库的；真实部署环境由 Flyway 自行执行同一脚本。
迁移脚本本身幂等，两种方式结果一致。

> ⚠️ **反证 6 的一处陷阱（实测踩到）**：第一次注入时用
> `t.replace('@Bean', '// @Bean', 1)`，**命中的是 Javadoc 注释里的 `@Bean` 示例文本**，

### 7.5 ⚠️ 本片实测发现的第二个真实缺陷：F-13（枚举与数组比较）

```
ERROR: operator does not exist: run_state = text
```

`run.state` 是枚举 `run_state`，而 JDBC `createArrayOf("text", …)`
送入的是 `text[]`，两者之间没有比较算子。

**危害形态**：这条 SQL 位于 `selectExpiredTerminalRunIds`——
即 Prompt 90 天清理的**选行阶段**。它一失败，
异常被 `runCategory` 转成一条 ERROR 日志吞掉，
**Prompt 清理永远为 0 行**，而其余三类照常、任务不报错、健康检查全绿。
与 F-12 **完全同源**：都是「异常被吞 → 静默失效」。

**修复**：`state = ANY (?::run_state[])`（显式 cast）。
刻意**不用** `state::text = ANY (?)`——那会让 `state` 上的索引失效。

**为什么免 DB 的测试发现不了**：`RetentionJobTest` 用的是
`ErasurePort` 桩实现，真实 SQL 从未被执行过一次。

### 7.6 ⚠️ 本片实测发现的第三个真实缺陷：F-13b（UUID 数组类型推断）

```
ERROR: cannot cast type boolean to uuid[]
```

`conn.createArrayOf("uuid", ...)` —— PG 驱动**不认识** `"uuid"` 这个类型名，
退化成 `boolean` 发送，于是 `(?)::uuid[]` 报「无法把 boolean 转成 uuid[]」。

**定性实验**（直接对真实库跑四种写法）才定位到：

| 写法 | 结果 |
|---|---|
| `state = ANY (?::run_state[])` + `createArrayOf("text", …)` | ✅ 命中 48 行 |
| `run_id = ANY (?)::uuid[]` + `createArrayOf("uuid", …)` | ❌ cannot cast boolean to uuid[] |
| `run_id = ANY (?)::uuid[]` + 空数组 | ❌ 同上（与是否为空无关）|
| `run_id = ANY (?)` + `createArrayOf("uuid", …)` | 执行但不报错（隐式，不可靠）|

**修复**：统一改为 `createArrayOf("text", …)` + SQL 侧显式 `?::uuid[]`。
三处（`run` / `run_step` / `tool_operation`）一并修正。

### 7.7 ⚠️ 本片实测发现的第四个真实缺陷：F-14（IT 从未在构建中执行）

**这是本片影响面最大的一个发现，且它不属于保留期功能本身。**

```
mvn clean verify  →  BUILD SUCCESS
但 14 个 *IT.java 集成测试类，一条都没有执行（实测 tests=0）
```

**根因**：项目**从未配置 `maven-failsafe-plugin`**，
而 surefire 的默认 include 是 `Test*` / `*Test` / `*Tests` / `*TestCase`，
**不含 `*IT.java`**。于是全部 124 项集成测试在 CI 里静默跳过，构建依然全绿。

**为什么危险**：这是最坏的失效形态——不是「测试红」，而是「测试从未运行」。
台账上登记的「集成测试 104 项」在 CI 里**实际等于 0**。
P1–P3 所有依赖 IT 断言的不变量（RLS 隔离、fencing、审计链、预算、取消竞态……）
**从来没有被构建验证过**，只是被人工跑过时验证过。

**修复**：父 `pom.xml` 注册 failsafe，`includes` 显式纳入 `**/*IT.java`，
绑定 `integration-test` + `verify`。

**验证**（实测，修复前后对比）：

| | 修复前 | 修复后 |
|---|---|---|
| `mvn clean verify` 中执行的 IT | **0** | **124**（14 个类，全部 ✅）|
| 单测（surefire） | 414 | 414 |
| **构建总用例** | 414 | **538** |

> 巧合的是：若非本片坚持「DB 层代码必须真跑」，
> 这个缺陷还会继续潜伏——因为 `-Dtest=XXX` 显式指定时 surefire 会跑，
> 人工验证永远是绿的，**只有默认构建路径暴露它**。

### 7.8 测试辅助方法的同源缺陷（F-12 在测试侧）

`RetentionErasureIT` 自己的 `monthsAgo()` 也写了
`Instant.now().minus(months, ChronoUnit.MONTHS)` —— 与生产代码 F-12 同一个坑。
生产侧修好后测试侧仍崩，暴露于首次真实执行。已一并修正（经 `ZoneId` 转换）。

> 这说明 F-12 不是「某处手误」，而是**这个 API 的直觉用法就是错的**；
> 任何按「12 个月前」直译的写法都会中招。
