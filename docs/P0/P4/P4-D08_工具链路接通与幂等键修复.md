## 0. 背景：为什么本片优先于 G3–G7 端点

原计划第二片是 G3/G5/G6/G7（run:read / result:read / 画像 / 列表分页）以解锁 FE F5。
但**实测后端现状时先发现了三项更靠前的缺陷**：

| 编号 | 缺陷 | 位置 | 实测证据 |
|---|---|---|---|
| **R-1** | 两个工具**从未注册为 Bean** → `List<ToolHandler>` 在生产中恒空 | `GetStudentProfileTool` / `RecordWeaknessTool` / `StudentDataRepository` 三个类**均无 Spring 注解**，且全仓非测试代码**零处** `new` | 见 §1.1 |
| **R-2** | 幂等键**缺真实 runId** → 跨 Run 撞键 | `ToolInvocationGate.buildIdempotencyKey` 第 526 行硬编码 `"pending-run"` | 见 §1.2 |
| **R-3** | 审批策略**与配置矛盾** → 工具修好仍被拒 | `RiskBasedApprovalPolicy` 硬编码「非 READ 一律需审批」，而 yml 声明 `WRITE_PROFILE: OPTIONAL` | 见 §1.3 |
| **R-4** | 闸门内**授权上下文角色集为空** → 工具修好仍被「无权调用」拒 | `ToolInvocationGate.systemContext` 传 `Set.of()`（空角色集），而 `Roles.WORKER` 才是含 `TOOL_INVOKE` 的角色 | 见 §1.4 |

**四者构成一条链，必须同片修复**：

```
R-1（工具未注册）──修──▶ 工具进入闸门
                            │
                            ├─▶ R-4 激活：授权上下文角色集为空 → isAuthorized 恒 false
                            │      → 「无权调用该工具」→ 工具仍不执行
                            │
                            ├─▶ R-2 激活：幂等键缺 runId → 跨 Run 撞键 → 复用旧 operation
                            │      → 账本把新 Run 的调用记到旧 Run 的 operation 上 → 重复副作用 Sev-0
                            │
                            └─▶ R-3 激活：审批恒 FAIL_CLOSED → record_weakness 仍被拒
                                   → 工具注册了却依然不执行
```

> ⚠️ **只修 R-1 是最危险的组合**：它把一个「静默不执行」的缺陷，
> 换成一个「执行但跨 Run 撞键」的缺陷——**从"没发生"变成"发生了但记错账"**。
> 后者比前者更难发现，且直接触及 Sev-0 判据（重复副作用）。
>
> ⚠️ **R-4 尤其隐蔽**：它在 R-1 修好之前**完全不可见**——
> 因为工具压根没进闸门，谁也不会去看授权上下文。
> 换言之，**任何"只修第一层"的方案都会被后面三层依次挡下**，
> 且每一层都表现为"工具不执行"这一个症状，极易误判为"修了但没用"。

**因此本片优先于 G3–G7**：G6（画像端点）的数据源是 `weakness_record`，
而该表在生产中**永远为空**（R-1）→ 做完 G6 端点，前端画像页仍显示「还没有记录到薄弱点」，
只是把一个诚实占位换成一个**看起来能用的空页面**。

## 1. 现状实测（缺陷证据）

### 1.1 R-1：工具从未注册

**证据链（三步，每步都可独立复现）**：

```bash
# ① 三个类无 Spring 注解
grep -rn --include='*.java' -E '@(Component|Service|Repository|Configuration|Bean)' \
  platform/agent-infrastructure/src/main/java/cn/studykid/multiagent/infrastructure/tool/
# → 零命中

# ② 非测试代码零处实例化
grep -rn --include='*.java' -E 'new (StudentDataRepository|GetStudentProfileTool|RecordWeaknessTool)\(' \
  platform/ | grep -v '/src/test/'
# → 零命中

# ③ 闸门注入点存在，但无任何产出
grep -rn --include='*.java' 'List<ToolHandler>' platform/
# → 仅 ToolInvocationGate 字段 + WorkerExecutionConfig:118 注入点
```

**后果路径（运行时）**：
`WorkerExecutionConfig.toolInvocationGate` 收到**空 List** →
`ToolInvocationGate.findHandler` 返回 `null` → 第 239–244 行
`recordRejected(toolName, "未登记的工具")` → **工具永不执行**。

> ⚠️ **系统表面完全正常**：Run 仍 `SUCCEEDED`、模型仍返回文本、闸门仍记「已拒绝」，
> 全部测试仍全绿。`weakness_record` 表在生产中**永远为空**。
> 这与 P4-D01 修复的断链是**同一族**（代码在、测试绿、运行时不对），
> 差别仅在于这次断的是**工具注册**而非执行链。

**为什么测试全绿**：`StudentToolsTest` 全部直接 `new GetStudentProfileTool(null)`，
`ToolLedgerReconciliationIT` 直接 `new StudentDataRepository(appPool)`——
**行为测试**（被直接调用时正确）齐备，**连通性测试**（它是否真被调用）缺失。

### 1.2 R-2：幂等键缺真实 runId

```java
// ToolInvocationGate.java:520-532
private String buildIdempotencyKey(ModelResponse.ToolCallRequest call) {
    Object studentId = call.arguments().get("studentId");
    Object knowledgePoint = call.arguments().get("knowledgePoint");
    if (studentId != null && knowledgePoint != null) {
        return IdempotencyKey.forRecordWeakness(
                String.valueOf(studentId), "pending-run",      // ⚠️⚠️ 硬编码
                String.valueOf(knowledgePoint)).composite();
    }
    return IdempotencyKey.forRunCreate(                        // ⚠️ 命名空间错 + 无 runId
            call.toolName() + "-" + Optional.ofNullable(call.callId()).orElse("no-call-id")
    ).composite();
}
```

**两处缺陷**：

| 分支 | 问题 | 违反 |
|---|---|---|
| `record_weakness` | runId 恒为 `"pending-run"` | ADR-003：键 = `student_id + run_id + knowledge_point` |
| 其他工具 | 用 `NS_RUN_CREATE`（`run.create`）命名空间，且**无 runId** | ADR-003 命名空间隔离：工具键不得与 Run 创建键同域 |

**危害**：`tool_operation` 有 `CONSTRAINT tool_operation_idempotency_unique UNIQUE (tenant_id, idempotency_key)`，
而 `JdbcToolOperationLedger.register` 命中重复键时**复用既有 operation**（不新建）。

于是：同租户下，**Run A 与 Run B 对同一 studentId + 同一 knowledgePoint 的 record_weakness
会撞成同一个 operation** → Run B 的调用被记到 Run A 的 operation 上 →
`RecordWeaknessTool` 侧的 `insertWeakness` 虽按真实 runId 写入，但**账本与对账链路已错乱**，
且 Run A 的重试会误判 Run B 的调用为「已完成」→ 副作用语义破裂。

> ⚠️ `ToolOperationReconciliationService.parseRecordWeaknessKey` 解析
> `tool.record_weakness:<studentId>/<runId>/<knowledgePoint>` 并按 runId 对账——
> 硬编码 `"pending-run"` 会让它**永远查不到真实 Run**，对账退化为「转人工」。

### 1.3 R-3：审批策略与配置矛盾

| 位置 | 声明 | 实际 |
|---|---|---|
| `application.yml:189-191` | `WRITE_PROFILE: OPTIONAL` | — |
| `RecordWeaknessTool.riskLevel()` 注释 | 「DEC-11：WRITE_PROFILE，审批 OPTIONAL（当前配置不需审批）」 | — |
| `RiskBasedApprovalPolicy:32` | — | `NO_APPROVAL_LEVELS = Set.of(READ)` → **WRITE_PROFILE 一律 required** |
| `RiskBasedApprovalPolicy:44` | — | 走 `ApprovalDecision.required(level.name())` |
| `WorkerExecutionConfig:107-109` | — | `new PolicyEngineApprovalSource()` **空策略** → `verdictFor` 恒 `FAIL_CLOSED` |
| `ToolInvocationGate:311-317` | — | `FAIL_CLOSED` → `recordRejected("审批未批准:FAIL_CLOSED")` |

**即：修好 R-1 + R-2 后，`record_weakness` 仍会被审批闸门拒绝。**
配置里的 `OPTIONAL` 语义（`ApprovalRequirement` 枚举：`OPTIONAL(1)` =「默认不阻塞，但满足条件时仍可触发」）
**从未被任何代码读取**——`agent.approval.required-by-risk` 只在
`RunConfigSnapshotFactory` 里用于生成 Run 快照，**不参与运行时审批判定**。

### 1.4 R-4：闸门内授权上下文角色集为空

`ToolInvocationGate` 在**执行时重新授权**（红线 9）时构造上下文：

```java
// ToolInvocationGate.java:542-545
private cn.studykid.multiagent.core.tenant.TenantContext systemContext(String tenantId) {
    return new cn.studykid.multiagent.core.tenant.TenantContext(
            tenantId, "worker", java.util.Set.of(), 0L);   // ⚠️ 角色集为空
}
```

而授权实现按**角色**判定：

```java
// RoleBasedAuthorizationService.java:67-70
return context.roles().stream()
        .map(ROLE_PERMISSIONS::get)
        .filter(Objects::nonNull)
        .anyMatch(actions -> actions.contains(action));
```

空角色集 → `anyMatch` 恒 `false` → **授权必然被拒** →
第 268–272 行 `recordRejected(toolName, "无权调用该工具")`。

> ⚠️ **`Roles.WORKER` 本就含 `TOOL_INVOKE`**（`RoleBasedAuthorizationService` 第 48–50 行），
> 且注释明写「Worker 服务账号：需要执行与处置能力」——
> **权限模型本就为 Worker 设计了这条通路，只是上下文没带上该角色**。

## 2. 修复方案

### 2.1 R-1：显式 `@Bean` 注册三个工具

**沿用 P4-D07 的装配惯例**：业务 Bean 统一在 `ApplicationConfiguration` 显式 `@Bean`，
**不加 `@Service`/`@Component`**（避免测试切片扫描冲突，见 P4-D07 §2 装配说明）。

```java
@Bean
public StudentDataRepository studentDataRepository(DataSource dataSource) {
    return new StudentDataRepository(dataSource);
}

@Bean
public ToolHandler getStudentProfileTool(StudentDataRepository repository) {
    return new GetStudentProfileTool(repository);
}

@Bean
public ToolHandler recordWeaknessTool(StudentDataRepository repository) {
    return new RecordWeaknessTool(repository);
}
```

> ⚠️ **两个工具都声明为 `ToolHandler` 类型**（而非各自具体类型）：
> Spring 收集 `List<ToolHandler>` 时按接口类型注入，具体类在容器内仍可按类型取到。
> 这样闸门拿到的是**接口列表**，后续新增工具只需再加一个 `@Bean`，
> 不必改动闸门装配——符合「闸门是唯一入口」（ADR-011 §3.3）的设计。

> ⚠️ **DataSource 用主池**（Spring Boot 自动配置），**不是 adminPool**：
> `StudentDataRepository.inTenantScope` 走 `TenantSessionBinder`（关自动提交 + 事务内绑定租户），
> 必须在**应用角色**连接上执行，RLS 策略才生效。

### 2.2 R-2：幂等键纳入真实 runId

**改动点**：`ToolInvocationGate.buildIdempotencyKey` 增加 `runId` 参数，
调用点（第 276 行）传入 `task.runId()`。

```java
private String buildIdempotencyKey(String runId, ModelResponse.ToolCallRequest call) {
    Object studentId = call.arguments().get("studentId");
    Object knowledgePoint = call.arguments().get("knowledgePoint");
    if (studentId != null && knowledgePoint != null) {
        // ⚠️ runId 必须是真实 Run 标识：硬编码占位会让同租户跨 Run 撞键
        //    （tool_operation 的 UNIQUE(tenant_id, idempotency_key) 命中即复用旧 operation）
        return IdempotencyKey.forRecordWeakness(
                String.valueOf(studentId), runId,
                String.valueOf(knowledgePoint)).composite();
    }
    // ⚠️ 其他工具也必须含 runId：否则同一工具名 + 同一 callId 跨 Run 撞键
    return IdempotencyKey.forToolInvoke(
            runId, call.toolName(),
            Optional.ofNullable(call.callId()).orElse("no-call-id")).composite();
}
```

**新增命名空间**（`IdempotencyKey`）：

```java
/** 工具调用的命名空间（区别于创建 Run 与 record_weakness）。 */
public static final String NS_TOOL_INVOKE = "tool.invoke";

public static @NonNull IdempotencyKey forToolInvoke(@NonNull String runId,
                                                    @NonNull String toolName,
                                                    @NonNull String callId) {
    requirePart(runId, "runId");
    requirePart(toolName, "toolName");
    requirePart(callId, "callId");
    return new IdempotencyKey(NS_TOOL_INVOKE, runId + SEPARATOR + toolName + SEPARATOR + callId);
}
```

> ⚠️ **为什么必须新增命名空间而不能复用 `run.create`**：
> `IdempotencyKey` 类注释明确写「命名空间不可省略……`run:xxx` 与 `tool:xxx` 可能在同一租户内撞值」。
> `run.create` 的键在 `run` 表，`tool.invoke` 的键在 `tool_operation` 表——两张表约束独立，
> 但**若共用命名空间，日志与排障时无法区分二者来源**，且违背 ADR-003 的隔离意图。

> ⚠️ **对账服务兼容性**：`ToolOperationReconciliationService.parseRecordWeaknessKey`
> 只解析 `tool.record_weakness:` 前缀，且按 `split("/")` 要求**恰好 3 段**
> （`studentId` / `runId` / `knowledgePoint`）。
> `record_weakness` 分支的键格式**保持不变**（只是把 `"pending-run"` 换成真实 runId），
> 故对账解析**不受影响**。`tool.invoke` 键不被该解析器消费，属预期。

### 2.3 R-3：审批策略与配置对齐

**原则**：**只能收紧不能放松**（P0-D03 红线 15）。
本片做的是**让运行时判定与 yml 声明一致**，而不是降低门禁强度。

**改法**：`RiskBasedApprovalPolicy` 接受「风险等级 → 审批要求」映射，
`REQUIRED` → 需审批；`OPTIONAL` → 默认不阻塞；`NOT_REQUIRED` → 不需审批。

```java
public final class RiskBasedApprovalPolicy implements ApprovalPolicy {

    /** 风险等级 → 审批要求（来自 agent.approval.required-by-risk）。 */
    private final Map<ToolRiskLevel, ApprovalRequirement> byRisk;

    public RiskBasedApprovalPolicy(@NonNull Map<ToolRiskLevel, ApprovalRequirement> byRisk) { ... }

    /** fail-closed 兜底构造：未登记等级一律按最严（REQUIRED）。 */
    public RiskBasedApprovalPolicy() {
        this(Map.of());
    }

    @Override
    public @NonNull ApprovalDecision evaluate(@NonNull ToolHandler handler) {
        ToolRiskLevel level = handler.riskLevel();
        if (level == null) {
            return ApprovalDecision.required("风险等级未知，按最严处理");
        }
        ApprovalRequirement req = byRisk.get(level);
        if (req == null) {
            // ⚠️ 未登记等级 → 最严（fail-closed）
            return ApprovalDecision.required(level.name());
        }
        return switch (req) {
            case NOT_REQUIRED -> ApprovalDecision.notRequired();
            case OPTIONAL -> ApprovalDecision.notRequired();   // 默认不阻塞，可被显式收紧
            case REQUIRED -> ApprovalDecision.required(level.name());
        };
    }
}
```

**装配**（`WorkerExecutionConfig`）：从 yml 读 `agent.approval.required-by-risk` 构造映射。

> ⚠️ **OPTIONAL 语义为何是「默认不阻塞」**：`ApprovalRequirement.OPTIONAL` 枚举注释写明
> 「可选审批：默认不阻塞，但满足条件时仍可触发」。`OPTIONAL` 的**收紧程度(1)**
> 介于 `NOT_REQUIRED(0)` 与 `REQUIRED(2)` 之间，**不是放松到「无需审批」**——
> 审批记录与审计链仍可由外部流程触发，运行时默认不阻塞。
>
> ⚠️ **这不是门禁降级**：`WRITE_PROFILE: OPTIONAL` 是 **yml 中已有的声明**，
> 本片只是让代码**读到并遵守**它。变更方向是「代码对齐配置」，不是「配置对齐代码」。
> 反向（把 yml 改成 REQUIRED）才是放松，本片不做。
>
> ⚠️ **`WRITE_EXTERNAL: REQUIRED` 保持最严**：未登记工具按 `WRITE_EXTERNAL` 兜底
> （`ConfigFailClosedTest` 既有语义），仍是「需审批」。

**审批来源仍为 fail-closed**：`PolicyEngineApprovalSource` 空策略 → 恒 `FAIL_CLOSED`。
即：**需要审批的工具（`WRITE_EXTERNAL`）仍会被拒绝**——这是真实审批权威未接入前的**设计内安全状态**，
本片**不放宽**。`record_weakness` 因 `WRITE_PROFILE: OPTIONAL` 而不再被审批拦截。

### 2.4 R-4：闸门授权上下文带上 Worker 角色

```java
private cn.studykid.multiagent.core.tenant.TenantContext systemContext(String tenantId) {
    // ⚠️⚠️ 必须携带 WORKER 角色：授权按角色判定（RoleBasedAuthorizationService），
    //    空角色集 → isAuthorized 恒 false → 工具执行时必被「无权调用该工具」拦下。
    //    Roles.WORKER 本就含 TOOL_INVOKE（P4-D08 R-4 修复）。
    return new cn.studykid.multiagent.core.tenant.TenantContext(
            tenantId, "worker",
            java.util.Set.of(cn.studykid.multiagent.ports.security.AuthorizationService.Roles.WORKER),
            0L);
}
```

> ⚠️ **这不是「给 Worker 开后门」**：
> - `Roles.WORKER` 是**权限模型中既有角色**，其动作集合**未因本次修复而扩大**
>   （`RUN_READ` / `RUN_CANCEL` / `TOOL_INVOKE` / `EVENT_SUBSCRIBE` / `RESULT_READ`，与修复前完全一致）；
> - 修复前 Worker 上下文**根本没有任何角色**，等于「Worker 无任何授权」——
>   那不是更严的安全姿态，而是**授权链路根本没接上**（与 R-1 同族：看起来有防线，实际不存在）；
> - 授权仍在**每次工具调用时重新判定**（红线 9），且 `authzVersion` 校验照常生效。
>
> ⚠️ **不扩大到其他角色**：只加 `WORKER`，不加 `TENANT_ADMIN`——
> Worker 不该持有人工审批与 Agent 管理权限。

## 3. 测试设计（行为测试 + 连通性测试）

> ⚠️ 依 P4-D01 确立的方法论：**测试必须分两类**——
> **行为测试**（被直接调用时行为正确）+ **连通性测试**（它是否真被调用）。
> R-1 之所以能长期潜伏，正是因为只有前者。

### 3.1 连通性测试（新增，本片核心）

`platform-bootstrap` 新增 `ToolWiringIT`（**Spring 上下文真实装配**）：

| 编号 | 断言 |
|---|---|
| W-1 | Spring 上下文中 `List<ToolHandler>` **恰好 2 个**，且含 `get_student_profile` 与 `record_weakness` |
| W-2 | `ToolInvocationGate` 持有的 handlers **非空**（用反射或经由实际调用验证） |
| W-3 | 真实执行一次 `get_student_profile`（空画像场景）→ 闸门**不再记「未登记的工具」** |
| W-4 | 真实执行一次 `record_weakness` → `weakness_record` **真落库一行**（最强证据） |
| W-5 | 幂等键含**真实 runId**（断言 `tool_operation.idempotency_key` 中出现该 runId） |
| W-6 | **跨 Run 不撞键**：同一 studentId + 同一 knowledgePoint，Run A 与 Run B → **两个不同 operation** |

> ⚠️ W-4/W-6 需要真实 PG（`IT_PG_URL` 守门），与既有 IT 一致：本地无 PG 时跳过，CI 有 PG 时真跑。
> **不得用 mock 替代**——mock 就退化成行为测试，W-1/W-2 的连通性价值会消失。

| 反证 | 既有测试为什么抓不到 |
|---|---|
| A-2 | `IdempotencyProtocolTest` 测的是 **`IdempotencyKey` 类本身**的构造规则，而 R-2 的缺陷在**闸门是否把真实 runId 传进去**——那是**调用方**的责任，类测试**原理上**覆盖不到 |

> 「被测单元正确，调用方传错参数，全绿照旧」——
> **行为测试无法覆盖调用方契约**，无论写多少个类测试都不行。
> 必须新增**直接断言调用方传了什么**的测试：

## 4.1 ⚠️ 一次全量构建失败：如何区分「环境干扰」与「代码回归」

全量 `mvn clean verify` 首跑时，`RealBrokerEndToEndIT`（P4-D06 交付的**真实 broker** IT）失败：
`expected: 1 but was: 0`（发一条后队列深度未 +1）。

**该测试与本片改动零交集**（`git status` 显示 `RealBrokerEndToEndIT` 未被修改），
但**不能靠「看起来无关」就下结论**——必须实测归因：

| 步骤 | 操作 | 结果 |
|---|---|---|
| ① | `git stash push -- platform/`（暂存本片**全部**改动）后重跑该 IT | ❌ **同样失败** → 归因指向基线/环境，而非本片 |
| ② | 查 broker 管理 API `/api/queues/agent` | `agent.run.execute` 队列有 **4 个活跃消费者** |
| ③ | 查 `/api/consumers` + `jps -lv` + `lsof` | 消费者来自 **PID 21569 = IntelliJ 里调试运行的 `PlatformApplication`**（JDWP 调试代理，worker 监听容器默认并发 4）|

**结论**：消息一投递就被用户正在调试的实例抢走 → 深度探测恒读到 0 → IT 失败。
**这不是代码缺陷，也不是本片引入的回归**，而是**本机环境被占用**。

> ⚠️ **两条重要纪律**：
> ① **不得擅自杀掉用户正在使用的进程**（那是他的调试会话）。
>    正解是**换隔离 vhost**：新建 `agent-test` vhost 并授予 `agent` 用户权限，
>    用 `RABBITMQ_VHOST=agent-test` 跑测试 → 测试与用户实例**互不干扰**。
> ② **「看起来无关」不等于「已证明无关」**——必须用
>    **stash 全部改动跑基线**来证伪，否则就是把环境问题误记成代码回归（或反之）。

> ⚠️ 另一条环境坑：`config.env` 在**仓库根**，而构建在 `platform/` 目录执行。
> 在 `platform/` 内执行 `. ./config.env` 会**静默失败**（找不到文件），
> 导致 `RABBITMQ_PASSWORD` 为空 → `ACCESS_REFUSED`（3 项全错）。
> **必须回到仓库根加载凭据再 `cd platform`**。
