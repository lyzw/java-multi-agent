## 0. 本切片关闭什么

P4-D15 与 FE-D11 都诚实登记了同一条限制：

> **L-1**：C7 人工审批工作流未实现，L3 写入**直接生效**。

本切片关闭它。关闭后前端**才可以**显示「待审批」，且必须同步更新。

## 1. 实测基线（开工前复核，非推断）

| 项 | 实测 | 影响 |
|---|---|---|
| `approval` 表 | 存在，但 **`operation_id UUID NOT NULL`** 强绑定工具操作 | ⛔ **不可复用**——配置变更无 operation_id。须新建表 |
| `AuthorizationService.Actions` | 10 个动作，**无 config 相关** | 须新增 `config:request` / `config:approve` |
| 终态守卫 | V5 `enforce_approval_state_transition` 模式成熟 | 直接复用其形态 |
| 治理端点 | P4-D13 已建立游标分页 + 三态 + 限流模式 | 新端点沿用同一模式 |

> ⚠️ **不复用 `approval` 表是本切片第一个设计决策**：
> 它是**工具操作**的审批（`operation_id` → `tool_operation`），
> 配置变更没有「工具操作」实体。硬塞会引入伪造的 operation_id
> 或加可空列——前者是数据造假，后者会破坏既有约束的强度。

### 2.1 P4-D15 新增键的分级判定

这 8 个键不在 FE-02 §2 原表（P4-D15 依实测新增），分级**必须显式判定**而非默认继承：

| 键 | 判定 | 理由 |
|---|---|---|
| `agent.rate-limit.limit-per-window` | **L3** | 放宽限流 = 失去过载保护 |
| `agent.worker.concurrency` | **L3** | 放宽并发 = 下游过载 |
| `agent.backpressure.high-watermark` | **L3** | 放宽背压阈值 = 队列堆积后才保护 |
| `agent.retention.profile-months` | **L3** | 延长留存 = **合规风险**（PIPL）|
| `agent.retention.prompt-days` | **L3** | Prompt 留存越久风险越高 |
| `agent.retention.trace-days` | **L3** | 同上 |
| `agent.retention.audit-days` | **L3** | 审计留存期，**法定不可任意缩短** |
| `agent.retention.batch-size` / `interval-ms` | **L2** | 纯执行节奏，无安全语义 |

> ⚠️ **保留期全部判 L3**：`retention.*` 直接关联 PIPL 留存义务，
> 即便「收紧」也应留痕审批（收紧也可能是误操作导致数据过早删除）。
> **审计留存期尤其不可仅凭「能变小」就自动执行。**

> ⛔ **默认方向必须是 L3**：新增配置键若忘记分级，
> 默认应落在「需审批」（安全方向），而非「直接生效」。

## 3. 数据模型（V12）

```sql
CREATE TYPE config_change_state AS ENUM ('PENDING', 'APPROVED', 'REJECTED', 'APPLIED');

CREATE TABLE config_change_request (
    change_id    UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id    UUID NOT NULL REFERENCES tenant(tenant_id),
    config_key   TEXT NOT NULL,
    -- 拟写入的值（文本，按键的类型解析）；⛔ 不落库的申请不存在
    proposed_value TEXT NOT NULL,
    value_type   TEXT NOT NULL,
    -- CHG 理由（P4-D15 已强制 ≥10 字，此处再存一份供审批人阅读）
    reason       TEXT NOT NULL,
    requester_id TEXT NOT NULL,
    requested_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    state        config_change_state NOT NULL DEFAULT 'PENDING',
    approver_id  TEXT,
    decided_at   TIMESTAMPTZ,
    decision_note TEXT,
    applied_at   TIMESTAMPTZ,
    -- ⛔ 双人复核：申请人不得审批自己的申请
    CONSTRAINT chg_no_self_approval CHECK (approver_id IS NULL OR approver_id <> requester_id)
);
```

**状态机**

```
PENDING ──approve──> APPROVED ──apply──> APPLIED（终态）
   │
   └──reject──> REJECTED（终态）
```

> ⚠️ **为何多一个 `APPLIED` 而非 APPROVED 即生效**：
> 「批准」与「已写入配置表」是两件事。把二者合并会让审批人无法区分
> 「我批了」与「配置真的变了」——而 P4-D15 D15-B3 正是这类
> 「看起来生效了其实没生效」的形态。**分两步且各自留痕。**

## 4. 端点契约

| 端点 | 动作 | 桶 | 说明 |
|---|---|---|---|
| `POST /api/config/changes` | `config:request` | `GOVERNANCE_QUERY` | L3 写入 → 创建 PENDING 申请 |
| `GET /api/config/changes` | `config:request` | `GOVERNANCE_QUERY` | 游标分页列出申请 |
| `POST /api/config/changes/{id}/decision` | **`config:approve`** | `GOVERNANCE_QUERY` | 批准/拒绝 |
| `POST /api/config/changes/{id}/apply` | `config:approve` | `GOVERNANCE_QUERY` | APPROVED → 实际写入 |

**错误语义**

| 情形 | HTTP | 理由 |
|---|---|---|
| 审批自己的申请 | **409** | 双人复核，DB CHECK + 应用层双保险 |
| 对终态决定 | 409 | 状态冲突 |
| 已 APPROVED 再决定 | 409 | 同上 |
| 非 APPROVED 就 apply | 409 | 状态机非法 |
| 键为 L2（无需审批） | 409 | 提示「该键可直接写入，不必申请」 |

> ⚠️ **L3 的写入路径改造是本切片最敏感的改动**：
> `PUT /api/config/overrides/{key}` 对 L3 键必须**拒绝直接写入**
> （409 + 提示走审批），而不是「也写进去，只是留个申请记录」——
> 后者等于审批形同虚设。

---

## 5. 双人复核（FE-02 §9.3）

| 层 | 强制 |
|---|---|
| 应用层 | `approverId.equals(requesterId)` → 409 |
| DB | `CHECK (approver_id IS NULL OR approver_id <> requester_id)` |

> ⚠️ 单人审批 = 没有审批：同一个人既能提又能批，
> 等于把「双人复核」降级为「两次点击」。
> 双重强制是刻意的——应用层可被绕过，DB 不会。

## 6. 审计

| 动作 | 时机 | fail |
|---|---|---|
| `CONFIG_CHANGE_REQUEST` | 创建申请 | **fail-closed** |
| `CONFIG_CHANGE_APPROVE` | 批准 | **fail-closed** |
| `CONFIG_CHANGE_REJECT` | 拒绝 | **fail-closed** |
| `CONFIG_CHANGE_APPLY` | 实际写入覆盖 | **fail-closed**（与 P4-D15 的 `CONFIG_UPDATE` 同路径）|

## 7. 已知限制（诚实边界）

| # | 限制 |
|---|---|
| **L-1** | **无过期机制**：`PENDING` 申请永不自动过期。实现 EXPIRED 需要定时任务，当前切片不做 |
| **L-2** | **一次性**：批准的变更立即写入；不引入「多申请打包审批」|
| **L-3** | **前端接线在 D17**：本切片只交付后端 + 契约；FE-D11 的 L-1 限制**在 D17 前仍然成立**（页面不得显示「待审批」）|
| **L-4** | **申请值不预校验**：审批时才做棘轮校验（避免申请人通过反复申请探测当前值）|

## 8. 验收标准

| # | 标准 |
|---|---|
| D16-1 | L3 键直接 PUT → **409**（提示走审批）|
| D16-2 | L2 键直接 PUT → **仍直接生效**（不受本切片影响）|
| D16-3 | 创建申请 → PENDING，且**未写入** `tenant_config_override` |
| D16-4 | 批准 → APPROVED，但**仍未写入**配置表（分两步）|
| D16-5 | apply → 写入配置表 + 状态 APPLIED |
| D16-6 | **审批自己的申请 → 409**（应用层 + DB 双保险）|
| D16-7 | 终态再决定 → 409 |
| D16-8 | 审计四条动作全部落 `audit_record` |
| D16-9 | 跨租户不可见（RLS）|
| D16-10 | 反证 **U-1 ~ U-5** 全部如期转红 |

**反证设计**

| # | 注入 | 期望转红 |
|---|---|---|
| **U-1** | 去掉「L3 拒直接写入」 | D16-1 |
| **U-2** | 去掉双人复核（应用层） | D16-6 |
| **U-3** | 去掉 APPROVED→APPLIED 分步（批准即写入） | D16-4 |
| **U-4** | 去掉终态守卫 | D16-7 |
| **U-5** | 去掉 RLS | D16-9 |

> ⚠️ **U-3 是最关键的一条**：若批准即写入，
> 「审批」与「生效」绑死，审批人无法区分自己批的是否真的生效——
> 这正是 D15-B3 的同构形态，必须锁死。
