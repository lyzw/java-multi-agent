# P4-R022 RabbitMQ 停维残余风险安全复核登记

> 阶段：P4（生产化）　**类型**：安全复核 + 残余风险登记
> 触发：P4 生产化收尾，对「RabbitMQ 进入停维 / 下线」场景做残余风险复核并正式登记
> 复核基准：ADR-001（RabbitMQ 4.3.6 + Quorum Queue）、D03（OutboxRelay + 优雅停机）、
> D05（多租户中继 + 背压 fail-closed）、D06（真实 broker 端到端 + 生产者 PERSISTENT 验证）

---

## 0. 复核结论摘要

| 项 | 结论 |
|---|---|
| 停维期间是否丢消息 | ⚠️ **默认不丢**（Outbox 以 PG 为事实源，broker 不可达时消息留在 PG）|
| **最严重残余风险** | ⚠️ **R-022-R2（Sev-0）**：broker 数据卷丢失/重建（非优雅停维）时，已标 `published` 但未消费的确认消息**永久丢失且 Outbox 不重发** |
| 启动门禁残余 | ⚠️ **R-022-R3**：应用启动**不校验 broker 可达**，broker 永久下线时 Outbox 静默积压而不报错 |
| 安全面残余 | ⚠️ **R-022-R5**：停维窗口无显式审计/凭证回收，存在未授权 broker 被重连（中间人）的盲区 |
| 整体评级 | **Accepted with conditions** —— 残余风险均有明确触发条件与建议处置，但**无一项在当前代码中被自动闭环** |

> ⚠️ 本片是**登记**，不是**修复**：所有 R-022-Rx 的「建议处置」均为运维/后续开发动作，
> 不得在台账里记为「已缓解」除非对应动作落地。本片只负责把风险**显式写出来并定级**。

## 1. 与停维相关的架构事实（复核依据）

| 事实 | 来源 | 对停维的含义 |
|---|---|---|
| Outbox 以 PG 为事实源，relay 轮询发布 | D03 / ADR-001 | broker 不可达 → 消息留在 PG，**不丢** |
| `RabbitMessageSender` 等 publisher confirms 才返回 | D03 D-2 / D06 P-2 | 未确认 → 抛 `MessagePublishException` → Outbox 标 `failed` → 可重发 |
| 队列为 quorum + delivery-limit=3，生产者设 `PERSISTENT` | ADR-001 / D06 P-1 | broker 正常重启后消息仍在；但**数据卷丢失即丢** |
| 背压 fail-closed：探测失败=超限→整轮停发 | D05 | broker 不可达时探测抛异常 → 停发（**可见的不可用**）|
| 优雅停机：SIGTERM 等待 in-flight 完成 | D03 | 停维流程应触发优雅停机，避免 in-flight Run 中断 |
| 应用启动**不检查 broker 可达** | 实测（无 `RabbitMQ` 健康门禁）| broker 永久下线也能启动 → 静默积压（**R-022-R3**）|
| 多租户中继：每租户一个 `OutboxPublisher` | D05 | 停维时所有租户同时不可发（公平，无跨租户越权）|

## 2. 残余风险登记

### R-022-R1　停维期间 Outbox 积压、Run 不被调度（可用性）

- **触发**：broker 进入停维（维护/下线），relay 无法发布。
- **影响**：⚠️ **Sev-2（可用性）**。业务停滞，但**不丢消息**（消息留在 PG Outbox）。
- **现有缓解**：背压 fail-closed（D05）使 relay 在 broker 不可达时**停发并暴露指标**，而非无界重试；Outbox 留在 PG 可后续排空。
- **残余风险**：积压无上限增长 → PG 存储压力；无「停维窗口」概念，监控会把积压当异常告警造成疲劳。
- **建议处置**：运维手册规定停维窗口内暂停 relay（或置 `agent.worker.enabled=false`）；停维结束按租户顺序排空 Outbox 后再恢复调度。

### R-022-R2（Sev-0）　broker 数据卷丢失/重建导致已确认消息永久丢失

- **触发**：broker 被**删除数据卷 / 重建**（区别于优雅停维），而部分消息已被 Outbox 标 `published` 但**尚未被消费侧处理完**。
- **影响**：⚠️ **Sev-0（数据丢失 + 业务不一致）**。Outbox 已标记 `published` → **不会重发**；quorum 队列数据随卷丢失 → 该批 Run 永远不被执行，**且不报错**。
- **现有缓解**：publisher confirms 保证「标 published 前 broker 已确认复制」；正常重启（数据卷在）消息不丢（D06 验证 PERSISTENT）。
- **残余风险**：⚠️ **确认 ≠ 已消费**。confirms 只证明「入队并多数派复制」，不证明「Worker 已处理」。卷丢失跨越了这条线。
- **建议处置（必须）**：停维/下线**前**执行「排空闸门」——确认 Outbox 中 `published` 行对应的队列深度为 0（消费侧无积压），或显式 fail-closed 拒绝启动直到闸门通过；数据卷必须随 broker 生命周期一并备份，禁止单独重建 broker 容器。

### R-022-R3　应用启动不校验 broker 可达（静默积压）

- **触发**：broker 被**永久下线**，但应用照常重启。
- **影响**：⚠️ **Sev-1**。应用启动成功，relay 持续发布失败 → Outbox 静默积压，**无任何启动期失败信号**；与本项目反复根治的「静默失效」同源。
- **现有缓解**：发布失败抛异常 → Outbox 标 `failed` → 可重发；背压探测失败→停发。但这些都是**运行期**信号，启动期无门禁。
- **残余风险**：运维可能误以为系统正常（进程在、PG 在），实则消息永不动。
- **建议处置**：新增启动健康门禁 `RabbitMQReachableGuard`（参照 D05 的 fail-closed 取向）——`deployment.rabbitmq.required=true` 时 broker 不可达即**拒启**；或至少启动即打 `WARN` 并触发告警。

### R-022-R4　重发无上限空转 + 日志噪音

- **触发**：broker 长期不可达，Outbox 标 `failed` 后重发机制持续重试。
- **影响**：⚠️ **Sev-3（运维噪声）**。CPU/日志空转，掩盖真实故障信号。
- **现有缓解**：D05 背压在**高水位**时拉长轮询间隔（降级），但 broker 不可达触发的探测失败走的是「停发」而非「退避重发」路径——重发退避依赖 Outbox 自身重发策略。
- **残余风险**：若重发无上限退避，broker 恢复瞬间触发积压爆发重发。
- **建议处置**：Outbox 重发加指数退避 + 上限；与 D05 背压降级联动。

### R-022-R5（安全面）　停维窗口凭证残留与未授权重连

- **触发**：broker 停维后应用仍持有 `RABBITMQ_*` 凭据；停维期间 broker 被**未授权方**以同名/同地址重新拉起。
- **影响**：⚠️ **Sev-1（安全）**。应用自动重连到被篡改的 broker（中间人）→ 出口消息（含租户坐标 `runId/tenantId`，**无学生 PII**，符合白名单）流入不可信 broker；反向可能接收伪造的 `RUN_DISPATCH`。
- **现有缓解**：消息体仅含 5 个坐标字段（D06 验证出口白名单），无业务数据泄露面；quorum + 认证（`RABBITMQ_USER`）。
- **残余风险**：⚠️ 未启用 **TLS**（ADR-001 未要求），重连无服务端身份校验；停维/恢复无操作审计。
- **建议处置**：停维流程显式回收/轮转应用凭据；生产启用 AMQPS（TLS）做服务端身份校验；停维与恢复动作记入审计日志（谁、何时、何因）。

### R-022-R6　优雅停机未在停维流程中固化

- **触发**：运维直接 `kill -9` 或停容器，未走 SIGTERM 优雅停机。
- **影响**：⚠️ **Sev-2**。in-flight Run 被中断；若中断在「标 published 后、消费前」窗口，恢复后重复执行（幂等键可缓解但非零风险）。
- **现有缓解**：D03 已实现 SIGTERM 优雅停机（等待 in-flight 完成）。
- **残余风险**：运维手册未强制「停维前先 SIGTERM 等待」，流程依赖人。
- **建议处置**：运维手册固化「停维 = SIGTERM → 等待优雅停机超时 → 再停 broker」顺序；禁止 `kill -9`。

### R-022-R7　监控盲区：停维（预期）vs 异常（需响应）未区分

- **触发**：broker 停维期，`/metrics` 中连接/队列深度指标异常。
- **影响**：⚠️ **Sev-3**。告警规则无法区分「计划内停维」与「意外故障」→ 告警疲劳或漏报真实故障。
- **现有缓解**：C-4（D02）已落地 `/metrics` 出口，但**无告警规则**（P4 已知部分）。
- **残余风险**：停维期间的指标异常淹没真实故障信号。
- **建议处置**：告警规则接入「停维窗口」标记（维护模式开关），窗口内抑制 broker 相关告警。

## 3. 风险定级汇总

| 编号 | 风险 | Sev | 现有缓解 | 残余（是否自动闭环）|
|---|---|---|---|---|
| R-022-R1 | 停维期间 Outbox 积压 | 2 | 背压 fail-closed + PG 兜底 | 否（需运维窗口）|
| **R-022-R2** | **卷丢失致已确认消息永久丢** | **0** | publisher confirms + PERSISTENT | **否（需排空闸门）** |
| R-022-R3 | 启动不校验 broker 可达 | 1 | 运行期失败信号 | 否（需启动门禁）|
| R-022-R4 | 重发空转 | 3 | 背压降级 | 否（需退避上限）|
| **R-022-R5** | **凭证残留/未授权重连** | **1** | 出口白名单 + 认证 | 否（需 TLS + 审计）|
| R-022-R6 | 未走优雅停机 | 2 | D03 已实现 | 否（需运维固化）|
| R-022-R7 | 监控盲区 | 3 | /metrics 出口 | 否（需告警规则）|

> ⚠️ **无任何一项 R-022-Rx 在当前代码中被自动闭环**——全部依赖运维动作或后续开发。
> 本片评级 **Accepted with conditions**，条件即上表「建议处置」逐条落地。
> 不得因「架构用了 Outbox / quorum / confirms」而宣称停维风险已消除——
> 这些只覆盖「broker 正常重启」，**不覆盖「卷丢失 / 永久下线 / 未授权重连」**。

## 4. 与 D03/D05/D06 的关系（诚实边界）

- **D03/D05/D06 解决的是「broker 在线时正确」**：装配完整、多租户不越权、背压可见、端到端可达。
- **R-022 暴露的是「broker 不在时」的残余**：上述保证在 broker 停维/下线场景下**部分失效**，
  且失效形态多为**静默**（积压不报错、卷丢失不报错、未授权重连不报错）——正是本项目反复根治的那类。
- ⚠️ 故 R-022 是 D03/D05/D06 的**必要补足**，不是重复；三者完成 ≠ 停维安全。
