## 1. 背景

多级 Agent 的每一次委派都落一条 `agent_invocation` 记录。这张表要回答的问题只有一个：**这次委派到底怎么了**。

在 ADR-012 之前，这套语义是**只存在于实现里的**：状态枚举写在 `AgentInvocationStatus` 的 javadoc 里、取消语义写在 `CancellationProbe` 的 javadoc 里、UNKNOWN 的红线写在 `InFlightDelegationAdopter` 的 javadoc 里、预算处置矩阵写在 `DelegationBudgetReconciliationService` 的 javadoc 里。

⚠️ **「只存在于实现里」是三个具体的问题**：

1. **没有一份可以对照的权威文本**。实现分散在四个类里，任何一处改动都要靠读四个 javadoc 才能确认「语义是否还是原来那个」。评审无法对着一份文档签字。
2. **口径可能已经漂移**。例如「终态一律结算」这条（`DelegationBudgetReconciliationService` 的处置矩阵）与「工具侧成功结算、其余释放」这两条**看起来相反**的规则并存 —— 它们其实不矛盾（委派侧「有记录行」等价于「子执行已启动」），但这个前提只写在 javadoc 的注释里，任何人只看工具侧的规则都会判错。
3. **UNKNOWN 的触发条件是散落的**。它是整个多级 Agent 里最危险的一个状态（猜错方向就是重复副作用 = Sev-0），但触发条件分散在「终态写失败」「token 过期」「记录不存在」「Worker 崩溃被接管」四处代码里，**没有一处列出完整清单**。

本 ADR 把这些**已经实现并被用例钉住**的语义正式冻结下来，是评审前置决策 3 的闭环产物。

⚠️ **本 ADR 不改任何实现**：它冻结的是**现状**，不是新设计。凡与实现不一致的，以本 ADR 为准去修实现（本次核对结果：逐条一致，无需改动）。

## 2. 决策

### 2.1 状态集合：封闭的七态

`agent_invocation.status` 的取值集合**封闭为以下七个**，不多不少：

| 状态 | 含义 | 终态 | 含义要点 |
|---|---|---|---|
| `QUEUED` | 已受理，尚未开始执行 | 否 | 重复投递时不得创建第二条逻辑调用（MA-T10） |
| `RUNNING` | 执行中 | 否 | 唯一可以被接管方收敛的中间态 |
| `SUCCEEDED` | 成功结束，且结果通过输出契约校验 | 是 | 契约校验不过就**不是** SUCCEEDED（MA-T16） |
| `FAILED` | **确定**失败（结果已知，无需对账） | 是 | 与 UNKNOWN 严格区分 |
| `CANCELLED` | 被取消（协作式取消） | 是 | **不承诺撤销已发出的外部副作用** |
| `TIMED_OUT` | 超时终止 | 是 | 墙钟截止时间到期 |
| `UNKNOWN` | 结果不确定，进入对账 | 是 | **不得盲目重放**（MA-T13 / R-007） |

⚠️ **集合是封闭的**：非法状态由数据库约束直接拒绝（`MultiAgentSchemaIT` 断言状态集合**恰好七态**），应用层不可能写入第八个值。

⚠️ **终态不可覆盖**：非终态 → 终态是唯一的合法转移；已是终态则**不覆盖**（第一次写入的终态是权威事实，重复投递不得改写结果）。这由 `AgentInvocationPort.markTerminal` 的 CAS 语义保证。

### 2.2 取消语义：协作式，且取消 ≠ 撤销

**取消必须传播到子执行内部**（MA-T11）。父 Run 被取消时，正在运行的子 Agent 若继续跑，它调用的工具仍会产生副作用 —— 取消就会退化成「不再发起新委派」，而已启动的子调用仍在烧预算、做副作用。

冻结的机制：

- 取消探针 `CancellationProbe` 接 Run 取消状态（**取消是 Run 级状态，父子共享**）；
- 子执行**每轮开头**检查一次；命中即停，终态写 `CANCELLED`；
- 探针**不得抛异常**：读不到取消状态时返回 `false` 并告警，不得把取消变成「整个 Run 崩掉」。

⚠️ **取消 ≠ 撤销**：协作式取消只保证「停止启动新的副作用」，**不能保证已发出的外部副作用被撤销**。已启动的 `tool_operation` 仍须进入可解释状态（成功 / 失败 / 待对账）。

⚠️ **CANCELLED 与 FAILED 严格区分**：两者都是终态，但一个是「被叫停」、一个是「确定失败」。合并它们会让审计把「人工/上游取消」说成「系统故障」，重试策略也会跟着错（被取消的委派不该被自动重试）。

### 2.3 超时：墙钟截止

本级委派链路的超时预算（`timeoutMs`）**逐跳下传**，按**墙钟截止时间**实施；剩余预算被上层（根 Run 剩余时间）封顶（`min(根 Run 剩余, 本级声明值)`）。超时终止写 `TIMED_OUT`。

⚠️ **租约到期 ≠ 业务截止**：`LeasedTask.deadlineAt`（业务截止）与 `leaseExpiresAt`（租约到期）分列 —— 租约过期只是换手（另一个 worker 继续跑），业务截止才是「该结束了」。混用会把「换手」误判成「超时」。

### 2.4 重试与幂等

- **幂等键**：`DelegationInvocationId.derive(runId, parentInvocationId, toolCallId)` —— 同一 Run + 同一父调用 + 同一模型 tool call，派生出同一个 `invocationId`。
- **重复投递 → 返回既有结论，不重复执行**（MA-T10）。既有记录存在 ⇒ 该次委派**已经启动过**子执行 ⇒ 不得重跑（重跑可能产生重复副作用）。
- **终态写入三态可区分**（`TerminalWriteOutcome`）：`WRITTEN` / `ALREADY_TERMINAL`（幂等重放，返回既有终态作为结论）/ `TOKEN_EXPIRED` / `NOT_FOUND`。
  ⚠️ 必须是三态而不是布尔值：布尔值会把「已是终态（幂等重放）」和「fencing token 过期（旧世代越权提交）」混成一件事 —— 后者若被当成幂等重放而静默接受，就是一次 Sev-0 越权提交被当成合法结果。

⚠️ **UNKNOWN 永不自动重放**（R-007 红线）：结果不确定时，重跑子 Agent 可能产生重复副作用。宁可交人工对账，也不自动重试。

### 2.5 UNKNOWN 的完整触发清单

UNKNOWN 是本 ADR 中**最需要精确**的部分 —— 猜错方向就是 Sev-0。冻结为**五类**：

| # | 触发条件 | 代码落点 | 为什么是 UNKNOWN 而不是 FAILED |
|---|---|---|---|
| 1 | **fencing token 过期**：旧世代带更小的 token 提交终态 | `markTerminal` 返回 `TOKEN_EXPIRED` | 子执行可能已经发生（副作用可能已存在），但结论不是权威事实 → 对外只能报「不确定」 |
| 2 | **记录不存在**：终态提交时找不到可对账的行 | `markTerminal` 返回 `NOT_FOUND` | 没有行可供对账 → 既不能说成功，也不能说「什么都没发生」 |
| 3 | **终态写失败**：数据库异常导致终态没能落库 | `DelegationExecutor` 捕获 `markTerminal` 异常 | 记录仍在 `RUNNING`，真相不可知 → 交恢复流程接管 |
| 4 | **Worker 崩溃被接管**：在途记录由新世代收敛 | `InFlightDelegationAdopter.adopt` | 子执行是**同步**跑在委派调用栈里的 → Worker 崩溃意味着子执行也中断 → 结果不可知 |
| 5 | **子执行自身结果不确定**：子 Agent 内部工具调用出现不确定结果 | `WorkerChildAgentRunner` → `toolResult.unknownResultOccurred()` | 子 Agent 的工具副作用**可能已经发生**，但结果不可知 → 整条委派收敛为 UNKNOWN（MA-T13） |

⚠️ **第 5 类最容易被漏掉**：子执行返回的 UNKNOWN 会**直接流入**委派记录的终态
（`DelegationExecutor` 取子执行的 status 作为本次终态），所以「子 Agent 内部出了
一次不确定的工具调用」会让**整条委派**变成 UNKNOWN —— 它不只影响那一次工具调用。

⚠️ **收敛成 UNKNOWN 而不是 FAILED 的理由**：`FAILED` 意味着「确定失败、无副作用」；崩溃中断时**副作用可能已经发生** —— 报 `FAILED` 会让对账流程以为「什么都没发生」而直接放行。

⚠️ **UNKNOWN 对外不带任何内容**：结果不被承认时把内容交出去，等于让一个未经确认的结论进入父 Agent 的推理。`unknownOutcome` 一律返回空输出 + `EXEC_UNKNOWN` 原因码。

⚠️ **UNKNOWN 只统计、不自动处置**（R-007）：成本是否发生**未知** → 既不能认定已花（结算），也不能当没花（释放）。只有拿到**明确的收敛结论**（`RECONCILED_SUCCEEDED` = 确认已发生 → 结算 / `RECONCILED_ABSENT` = 确认未发生 → 释放）才可处置。

⚠️ **注意与「拒绝」区分**：委派记录**根本没写进去**（插入失败）走的是**拒绝**路径
（`EXECUTION_PERSISTENCE_FAILED`，子执行从未启动 → 额度释放），**不是** UNKNOWN ——
两类都不能混：把「确定拒绝」说成「结果不确定」，会让额度既不花也不退。

### 2.6 接管：提升世代 ≠ 放弃 fencing

Worker 崩溃后由新世代接管时：

1. **提升在途记录的世代令牌**（`adoptInFlight`）：只动**非终态**记录；已是终态的记录**不动**（终态是权威事实，接管方没资格改写）。
2. **收敛在途记录为 UNKNOWN**（见 2.5 第 4 类）。
3. **绝不重放**。

⚠️ **提升 ≠ 放弃 fencing**：提升后**新世代**才能写终态，**旧世代**带着更小的 token 依然被 CAS 拒绝（MA-T12 语义不变）。

⚠️ **提升失败 → 不收敛**：提升失败就没有写权限，此时记录留在 `RUNNING` 等人工处置 —— 不得为了「干净」而强行写终态（那样可能覆盖别人的结果）。

### 2.7 预算处置矩阵（按委派调用状态）

| 委派调用状态 | 含义 | 处置 |
|---|---|---|
| `QUEUED` / `RUNNING` | 子执行可能还在跑 | ⚠️ **不动**：可能仍在执行，动了就是凭空吞额度 |
| `UNKNOWN` | 结果不确定（R-007） | ⚠️ **不动**，只统计并转人工；须有明确的收敛结论才可处置 |
| 终态（`SUCCEEDED`/`FAILED`/`CANCELLED`/`TIMED_OUT`） | 子执行已启动并结束 | **结算**：子执行跑过 → 成本可能已发生 |
| 无锚点（连 `agent_invocation` 行都没有） | 委派终态提交报 `NOT_FOUND` | ⚠️ **不动**，只统计；查无实据 → 不自动改账 |

⚠️ **为什么终态一律「结算」而不是照抄工具侧的「成功结算、其余释放」**：`agent_invocation` 行是在**调度子 Agent 之前**落下的（`DelegationExecutor` 第 6 步插记录、第 7 步才调度）—— 所以凡是**有记录行**的委派，子执行都已被调度过。照抄工具侧的「其余释放」会把这笔钱**白送**出去。

⚠️ **闸门侧的口径与本表一致**：被拒（子执行**从未启动**）→ **释放**（零成本）；执行失败（子执行**已启动**）→ **结算**（模型调用的钱已经花出去）；UNKNOWN → **既不结算也不释放**。

### 2.8 明确不予决策的事项

本 ADR **只冻结状态机与失败语义**。以下三项由其它决策分别拍板，不在本 ADR 内冻结：

- **多子结果聚合（`SEQUENTIAL`）**：由评审前置决策 1 拍板。
- **最大深度 / 子调用数 / 超时 / 预算默认值**：由评审前置决策 2 拍板。
- **`cap_agent_child_ref` 是否存储**：由评审前置决策 4 拍板。

## 3. 影响面

**实现：不变。** 本 ADR 冻结的是既有实现 —— 逐条核对结果：七态集合、终态不可覆盖、协作式取消、墙钟超时、幂等重放、三态终态写入、五类 UNKNOWN、接管三步、预算处置矩阵，与代码**逐条一致**，无需改动。

⚠️ **核对本身抓到了本 ADR 的一处错**：初稿写的是「UNKNOWN 四类，穷举」，
而代码里还有**第五类** —— 子执行自身返回 UNKNOWN（子 Agent 内部工具调用结果不确定）
会**直接流入**委派记录的终态。已按代码补正。
这正说明「冻结」必须**对着代码逐条核**，否则冻进去的是一份**看起来很权威的错文档**。

**文档**：

- 08 验收矩阵补 MA-T24a～MA-T24i（把本 ADR 的每条语义变成**可验证**的验收项，而不是散文）；
- 00 评审前置决策第 3 条标记为已闭环并指向本 ADR；
- 09 需求追踪矩阵补 FR-045 行。

**代码**：新增的验收项由既有用例直接引用（不新增用例）—— 因为本 ADR 冻结的是**已被用例钉住**的语义，验收项的作用是把「这些用例钉住的是哪条语义」写清楚，并让缺口（若有）显式暴露。

## 4. 复审触发条件

- 出现「必须自动重放 UNKNOWN」的强需求 —— 与 R-007 直接冲突，须重新评审；
- 新增第七个委派终态（封闭集合被打破）；
- 取消语义从**协作式**改为**抢占式**（那会改变「取消 ≠ 撤销」这条底线）；
- 接管策略从「提升世代 + 收敛 UNKNOWN」改为其他方式。
