## 1. 背景与为什么必须做

P0-D05 R-017（3/5/高）：**学生数据被用于模型训练或出境**。  
影响是**合规违规 + 隐私泄露**。

对**未成年人**而言，这一条尤其不可逆 —— 数据一旦出境或被用于训练，  
无法撤回，也无法向监护人交代。

因此 P0-D00 §1.3 设置了三道闸门：

| 闸门         | 规则                                   | 当前状态           |
| ---------- | ------------------------------------ | -------------- |
| **GATE-1** | P1 阶段全部使用模拟/合成数据，禁止任何真实学生数据进入 Prompt | ✅ 技术强制已生效 |
| **GATE-2** | 接入真实学生数据前，必须取得供应商零保留书面条款 | ✅ **已取得**（deepseek / minimax / workbuddy） |
| **GATE-3** | 确认截止 W2 D5（M1 门禁） | ✅ 按期完成 |

> ✅ **GATE-2 已闭环**：三家供应商均由项目负责人取得书面合同承诺。
> P2 可按需接入真实数据，但仍受两道防线约束（见 §2.1）。

---

## 2. 已完成的技术部分

代码层闸门已落地，不依赖流程自觉：

| 组件                      | 作用                                                    |
| ----------------------- | ----------------------------------------------------- |
| `ZeroRetentionStatus`   | 四态模型：`PENDING` / `CONFIRMED` / `REJECTED` / `EXPIRED` |
| `ZeroRetentionGate`     | 调用点强制拒绝；`fail-closed`，未确认即禁止真实数据                      |
| `DataClassification`    | 数据分级 + 可识别信息检测（身份证/手机号/学号/邮箱）                         |
| `ZeroRetentionGateTest` | **21 项测试，含证伪尝试**                                      |

### 2.1 三条设计要点

1. **fail-closed**：`CONFIRMED` 之外的一切状态（含过期）都拒绝真实数据。
2. **必须留证据**：`confirm()` 强制要求 `evidenceRef`（合同条款号/工单号），  
   **口头承诺不构成合规证据** —— 类型层面拒绝无证据的确认。
3. **两道防线**：即便已确认，Prompt 中检出可识别学生信息仍会被拒绝。  
   零保留条款解决的是「供应商不存」，**不是「我们不传」**。

### 3.2 核心确认项（已逐项书面答复）

合同覆盖以下各项：

| # | 确认项           | 判定标准                               |
| - | ------------- | ---------------------------------- |
| 1 | 请求内容是否被用于模型训练 | 必须为「否」。若为「是」或「可能为是」→ `REJECTED`    |
| 2 | 是否存储请求/响应内容   | 必须为「不存储」或「短期缓存后删除（≤N 天）」           |
| 3 | 缓存的具体期限       | 若有缓存，需明确 N 天，并评估是否与保留期冲突           |
| 4 | 是否用于人工审核      | 必须为「否」（人工审核意味着人工接触）                |
| 5 | 数据存储位置        | 必须为**境内**                          |
| 6 | 是否存在第三方共享/转授权 | 必须为「否」，或有明确的传输机制评估                 |
| 7 | 是否有安全事件通知义务   | 需明确通知时限（建议 ≤72 小时）                 |
| 8 | 条款有效期         | 需明确到期日 —— **过期后闸门自动失效**（`EXPIRED`） |
| 9 | 子处理者清单        | 需取得完整清单，随供应商变更同步更新                 |

### 3.3 证据形式（按可信度排序）

| 形式              | 可信度 | 说明                              |
| --------------- | --- | ------------------------------- |
| **合同/DPA 明确条款** | ★★★ | 最优。条款号写入 `evidenceRef`          |
| **服务商书面工单答复**   | ★★  | 可接受。工单号 + 完整邮件存档                |
| **服务商官网公开文档**   | ★   | 仅作辅助，需确认与本账户实际适用                |
| 口头/电话确认         | ✗   | **不可作为证据**（`confirm()` 在类型层面拒绝） |

## 4. 确认后的登记方式

取得证据后，在 `ZeroRetentionStatus` 中登记：

```java
ZeroRetentionStatus status = ZeroRetentionStatus.pending().confirm(
    "服务商名称",
    "DPA 条款 8.3 / 工单 SUP-12345",   // 证据出处，必填
    Instant.now(),                      // 确认时间
    Instant.now().plus(Duration.ofDays(365)));  // 条款有效期
```

### 4.1 登记后仍须同步的事项

- [ ] 更新 P0-D05 D-002 的「状态」列为「零保留已确认」
- [ ] R-017 状态由 `Open（延后确认）` 改为 `Mitigated（条款已取得）`
- [ ] 在本文件第 3.1 节填入供应商信息
- [ ] 存档证据文件（PDF/邮件导出），路径写入 `evidenceRef`

### 4.2 ⚠️ 有效期到期前必须处理

闸门按 `expiresAt` 自动判定过期，到期即拒绝真实数据 —— **这是刻意设计**：

> 宁可误伤（需重新确认），不可放过（条款已失效仍在传数据）。

建议在**到期前 30 天**开始提醒，避免业务中断。

## 5. 决策提示

### 5.1 若服务商拒绝零保留

该服务商**不可用于真实学生数据**（`REJECTED`，永久）。  
可选路径：

| 路径         | 说明                |
| ---------- | ----------------- |
| 换服务商       | 选择明确支持零保留的企业版/API |
| 改用自托管模型    | 数据不出内网，但需评估算力成本   |
| 保持 P2 模拟数据 | 技术闭环照常，业务验收顺延     |

### 5.2 若确认逾期（GATE-3）

按 P0-D00 §1.3：**P2 阶段仅用模拟数据做技术闭环，业务验收顺延**，  
P2 退出条件记 `Accepted with conditions`。

**不是**「先接入再补确认」—— 那将使闸门失去意义。
