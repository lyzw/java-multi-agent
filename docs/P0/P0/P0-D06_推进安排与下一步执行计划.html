2首个业务场景：初中生错题归因与个性化辅导

场景一句话

学生提交一道错题（题目 + 自己的解题过程 + 正确答案），Agent 读取学习画像 → 归因错因 → 生成可执行讲解 → 记录薄弱点 → 返回结构化结果。

不使用 RAG：全部基于模型参数内知识，不引入向量库、不做文档切分入库、不引用教材原文（DEC-5）。

2.1 工具契约（2 个，1 个有副作用）

工具副作用幂等键授权要求验证的最高风险协议
get_student_profile只读—学生仅可读本人画像；跨学生访问拒绝执行时授权（FR-008）、跨租户隔离（FR-010）
record_weakness有副作用student_id + run_id + knowledge_point仅本人；执行时重新授权；是否需审批待定Attempt 区分、fencing、UNKNOWN 对账、预算并发、审批/取消竞态（R-003/R-007/R-008）

为什么刻意保留一个有副作用的工具

若首期全用只读工具，P0-D03 §4 红线 4/5/7（Attempt 区分、fencing、UNKNOWN 对账）与 R-003/R-007/R-008 将只能靠玩具 PoC 验证，而这些恰恰是返工成本最高的协议。record_weakness 让最高风险协议有真实业务场景承载，同时幂等键天然（student_id + run_id + knowledge_point）使重复调用可安全去重。

3.1 ISO-1～ISO-5 强制隔离规则

规则内容违反后果
ISO-1AG-QA / AG-SEC 的上下文不得包含 AG-BE / AG-AI / AG-SRE 的实现过程、推理记录或设计草案审查结论作废，任务退回

残余风险声明（不可省略）

同基座模型存在相关盲区：AG-SEC 与 AG-BE 若基于同一模型，可能共享同类错误。因此：

  • Sev-0（跨租户泄露、未授权副作用、UNKNOWN 盲目重放、预算/审批绕过）的判定不得仅依赖 AI，必须有自动化测试证据 + 外部抽检。
  • ISO-5 的季度抽检是补偿控制，不是形式要求；抽检须逐条留痕（样本、结论、异议、处理）。
  • 若后续更换模型基座，须重新评估隔离有效性并更新 ADR。

4.3 ModelGateway 与 Spring AI 2.0 的边界

天然对齐，但要主动利用其约束

  • Spring AI 2.0 要求 Java 21 + Spring Boot 4.x + Spring Framework 7，与本基线完全对齐；统一 ChatClient 有利于满足 v3.1「领域层不依赖框架专属类型」。
  • 关键机会：Spring AI 2.0 移除了内置工具执行循环，工具不再按 Bean 名自动解析，必须显式注册 ToolCallback。本项目应利用该约束——在 ToolCallback 注册环节插入服务端授权、Schema 校验与 ToolOperation 账本写入，从架构上保证「模型不能绕过服务端授权直接执行工具」（P0-D03 §2 不可妥协边界）。
  • 注意：Spring AI 2.0 的 Tool Calling Advisor 会自动执行工具循环，若直接使用会绕过上述授权闸门。必须在 ADR-011 中明确不使用其自动执行路径，或在其前后强制插入授权检查。

7.1 DEC-9 成本与容量配置基线

一个必须点明的前提

「配置化」解决的是「后续谁来调」，不解决「初始值是多少」。配置项必须有初值，而初值本身就是决策——若缺省过大，系统上线首日即可能失控。故本决策同时给出保守初值与调优路径，而非把问题推给配置表。

配置项配置键（建议）保守初值依据调优时点
单 Run 成本上限agent.run.max-cost-per-run¥2.00错题归因为单轮短任务，按 7 次调用 × 混合单价估算P4 实测 usage 后
单 Run 模型调用上限agent.run.max-llm-calls12覆盖 5 步 Loop + 重试余量P2 评测集实测
单 Run 最大步数agent.run.max-steps20防异常循环；超出即失败且可解释P2
租户并发 Run 上限agent.tenant.max-concurrent-runs5保守起步，防下游过载P4 压测后
试点租户数deployment.pilot.max-tenants1灰度起步P5 灰度扩量
RPOdr.rpo24 小时无外部约束时的保守值P4 演练后确认
RTOdr.rto4 小时同上P4 演练后确认

配置化带来的三个副作用（不处理，配置化本身会成为新的风险源 → R-020 / R-021）

  • 配置错误导致预算失控或误拒 → 预算预留/结算仍以 DB 原子条件更新为准，配置仅作上限输入；配置缺失时拒绝而非放行（fail-closed）。
  • 运行中改配置导致同一 Run 前后不一致 → Run 创建时快照配置值写入 ExecutionSnapshot，改配置只影响新 Run。
  • 配置被当作绕过安全门禁的后门 → 高风险阈值变更须走 CHG 模板 + 审计留痕 + ISO-5 抽检；未成年人保护强度禁止运行时下调。

配置项配置键（建议）初值说明

这个设计的好处

首期 record_weakness 按 OPTIONAL 快速跑通闭环（不阻塞 P2）；P3 验证审批/取消竞态时只需把配置切为 REQUIRED，无需改代码。FR-013 审批消费因此有真实业务场景承载。

硬约束：审批策略只能收紧、不能放松。将 WRITE_EXTERNAL 从 REQUIRED 调为非 REQUIRED 属安全门禁降级，必须走范围变更模板 + ISO-5 外部抽检，不得作为普通配置调整处理。

7.3 DEC-10 零保留确认：允许延后，但设三道硬闸门

闸门规则违反后果
GATE-1P1 阶段全部使用模拟/合成数据，禁止任何真实学生数据进入 PromptP1 门禁不通过
GATE-2接入真实学生数据前，必须取得供应商零保留书面条款或确认使用境内实例禁止接入，业务验收延期
GATE-3确认截止点 W2 D5（M1 门禁）。逾期未确认则 P2 仅用模拟数据做技术闭环，业务验收顺延至确认完成P2 退出条件记 Accepted with conditions

延后不等于无约束。该闸门设计与 R-017、A-009 联动，不允许以「稍后确认」为由在 P1/P2 直接接入真实学生数据。这正是 DEC-10 虽可延后却仍需写入文档的原因——没有闸门的「稍后」会变成「一直没有」。

7.4 ISO-5 季度抽检日历

每阶段门禁后执行一次抽检，抽样比例 ≥ 30% 且必须包含全部 Sev-0 项：

M0（W1 D5）→ M1（W2 D5）→ M2 → M3 → M4 → M5，每季度汇总一次归档至 P4-D09 风险接受单。

配置类变更（DEC-9/DEC-11）若触及高危阈值，同样纳入 ISO-5 抽检范围。
