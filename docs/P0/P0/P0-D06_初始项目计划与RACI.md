## 1. 计划原则

- 先完成 P0 范围/验收基线，再并行推进 P1 的 PoC 和架构决策。
- 端到端优先，但不以牺牲授权、幂等、审计或 UNKNOWN 安全边界换取演示速度。
- 每个任务需有唯一 DRI（直接负责人）、依赖、可验收产物和测试证据。
- 日期按团队可用投入和外部依赖重新校准；下表周数是相对项目启动周，不是承诺日期。
- 十角色全部由独立 AI Agent 承担（DEC-1），因此 §5.1 的隔离规则与外部抽检是**强制门禁**，不是可选建议。
- 排期采用两段式（DEC-8）：段一 P0+P1 固定 2 周；段二 P2–P5 在 P1-10 门禁按实测吞吐重估，不沿用人类团队的 18 周估算。

## 1.1 AI 全角色承担下的隔离规则

P0-D06 §5 允许一人承担多角色，但要求「安全审批、代码作者自审和高风险验收应尽量避免利益冲突」。AI 全角色承担时，通过上下文隔离落实该要求：

| 规则 | 内容 | 违反后果 |
|---|---|---|
| ISO-1 | AG-QA / AG-SEC 的上下文不得包含 AG-BE / AG-AI / AG-SRE 的实现过程、推理记录或设计草案 | 审查结论作废，任务退回 |
| ISO-2 | 审查方输入仅限：需求 ID、代码、测试结果、运行日志、数据库断言 | 同上 |
| ISO-3 | 同一 Agent 不得在同一任务中同时承担 R 与 C/A | DoD 不通过 |
| ISO-4 | AG-ARC 设计的协议由 AG-QA + AG-SEC 交叉审查，AG-ARC 不得自审 | 门禁不通过 |
| ISO-5 | Sev-0/Sev-1 结论每阶段需项目负责人外部抽检复核，比例 ≥ 30% 且必须包含全部 Sev-0 项 | 阶段门禁不通过 |

**残余风险**：同基座模型存在相关盲区，AG-SEC 与 AG-BE 可能共享同类错误。因此 Sev-0 判定不得仅依赖 AI，须有自动化测试证据 + 外部抽检；抽检记录归档至 P4-D09 风险接受单。

## 5. RACI 角色定义

- **R（Responsible）**：实际执行工作的人/团队，可多个。
- **A（Accountable）**：对结果最终负责的人，每项原则上只有一个。
- **C（Consulted）**：需参与讨论并提供专业意见。
- **I（Informed）**：需要知会。

角色缩写：`BUS` 业务负责人；`PO` 产品负责人；`PM` 项目经理；`ARC` 架构负责人；`BE` 后端负责人；`AI` AI/模型接入负责人；`QA` 测试负责人；`SEC` 安全负责人；`SRE` 运维/平台；`EXT` 外部系统/IAM owner。

## 7. 任务级 Definition of Ready

任务开始前至少满足：
- 有任务 ID、目标、范围和唯一 DRI。
- 有可验证验收条件与关联需求 ID。
- 前置依赖、测试数据、权限和环境已准备或有明确计划。
- API/DDL/状态机/安全影响已识别；涉及未决架构决策时先建立 ADR/验证任务。
- 估算和目标 Sprint 明确。
- 涉及配置项时（DEC-9/DEC-11）已明确：配置键、**保守初值**、生效范围、快照策略、fail-closed 行为；且已确认该配置**不是**安全门禁降级。

## 8. 任务级 Definition of Done

### 8.0 ⛔ 文档前置（2026-10-19 追加）

**每个需求必须先有文档，再有代码。** 文档不是事后补记的产物。

| 序 | 要求 | 说明 |
|---|---|---|
| 1 | **设计文档先行创建** | 编码前先写 `P2-DNN_<主题>.md`，哪怕是草稿 |
| 2 | 文档须含**决策与理由** | 写「为什么这样设计」，而非「代码做了什么」 |
| 3 | 代码实现**对照文档执行** | 实现偏离文档时，先改文档再改代码 |
| 4 | 完成后回填**验证证据与已知限制** | 测试结果、遗留问题、阻塞项 |
| 5 | ⛔ **同步更新进度** | 每完成一个阶段/任务，必须更新进度台账与索引 |

**同步进度的范围**（第 5 条，2026-10-19 追加）：

| 文件 | 更新内容 |
|---|---|
| `../../项目进度台账.md` | 阶段完成度、代码统计、测试数、红线证据表 |
| `docs/P0/P{阶段}/README_*.md` | 文档索引与逐项进度 |
| `docs/P0/P{阶段}/P{阶段}-01_*.md` | 执行计划的每日状态 |

> **所有数字必须实测核对**（`find`/`wc -l`/数据库查询），不得凭印象填写。
> 台账中的数据若与实际不符，会直接误导后续决策。
>
> **为何强调前置**：事后补记的文档会退化为「代码注释的复述」，
> 丢失设计取舍的**理由** —— 而理由恰恰是后续维护者最需要的。
> D1 曾出现过「代码提交后才补文档」的返工，本条据此设立。

**文档命名**：`P{阶段}-D{序号}_{主题}.md`，置于 `docs/P0/P{阶段}/`

### 8.1 完成条件

任务完成需满足：
- **对应设计文档已存在且内容与实现一致**（见 §8.0）
- 代码合并且经过非作者 Review（AI 承担时须满足 ISO-1/ISO-2/ISO-3，见 §1.1）。
- 相关单元/集成/契约/安全测试通过；测试证据可定位。
- API、DDL、状态机、配置和运维文档同步更新。
- 日志、指标、Trace、审计与错误分类满足需求。
- 数据迁移已在目标版本验证，失败处理/前向修复策略明确。
- 涉及副作用时幂等、超时、重试、UNKNOWN/对账语义有测试。
- 涉及权限时包含授权成功和越权拒绝测试。
- 涉未成年人数据时，采集项在白名单内、无直接身份信息、保留期已配置（P0-D00 §4）。
- 涉及配置项时（DEC-9/DEC-11）：配置**缺失/非法时拒绝而非放行**（fail-closed）有测试；配置值已在 Run 创建时快照且可查询；审批类配置只能收紧不能放松；高危阈值变更已留痕并经 ISO-5 抽检。
- 未完成项、风险、临时开关和回滚方式被明确记录。

## 9. 计划调整规则

- 每周基于实际吞吐和依赖状态更新预测完成日期。
- 关键路径延迟超过 2 个工作日时，PM 组织影响评估：范围调整、资源调整或里程碑重排。
- 不通过减少安全/一致性验收项“追赶进度”。
- 任何阶段退出条件未满足时，需记录 `Blocked` 或 `Accepted with conditions`，明确批准人和限制范围。
