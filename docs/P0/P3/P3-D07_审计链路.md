## 2. 设计

### 2.1 D-1 审计写入必须「失败不放行主流程」，但也不阻塞业务

审计与主流程的关系有两种极端，**都不可接受**：

| 方案 | 后果 |
|---|---|
| 审计失败 → 放行主流程 | 审计可被「故障」绕过 → 抵赖风险回归（R-1）|
| 审计失败 → 阻断主流程 | 审计表故障导致整个平台不可用 → 可用性事故 |

**本片采用「关键审计 fail-closed，非关键 fail-open + 告警」**：

| 类别 | 语义 | 失败处置 |
|---|---|---|
| **关键审计**（`AuditPort.recordRequired`）| 审批授予/撤销/消费、取消 | ⚠️ 抛异常 → 主流程中止（安全动作无审计 = 不许发生）|
| **访问日志**（`recordAccess`）| 读学生画像等 | 记 WARN 不抛（读日志丢失不构成安全漏洞，但须可观测）|

> ⚠️ 为何审批类必须 fail-closed：审批是**授权行为**，无审计的授权等于
> 「谁都能批准且无痕迹」，正是 R-1 的场景。而访问日志失败只是**举证能力下降**，
> 阻断用户读数据得不偿失。

### 2.2 D-2 追加约束用 DB 触发器实现（R-3 的唯一可靠防线）

应用层「只提供 insert 方法」**不是**防篡改——任何 SQL 客户端都能直接
`UPDATE audit_record SET detail = ...`。故用 V6 迁移加触发器：

```sql
-- UPDATE 一律拒绝
-- DELETE 一律拒绝（除非保留期到期，由 DBA 显式关闭触发器，属受控运维流程）
CREATE TRIGGER trg_audit_record_append_only
    BEFORE UPDATE OR DELETE ON audit_record
    FOR EACH ROW EXECUTE FUNCTION forbid_audit_mutation();
```

**为什么是触发器而不是权限**：`GRANT` 是**按表**的，无法区分
「本平台的正常写入」与「事后篡改」；而触发器作用于**所有**写入路径，
包括超级用户与直连 SQL。

> ⚠️ 保留期（PIPL：审计 180 天）到期后需要删除——本片**刻意不做自动清理**
> （自动删除 + 追加约束 = 需要在删除时临时关触发器，风险高）。
> 清理归 D7 后续运维切片，且必须留下「谁删的」痕迹（见 §4 L-1）。

### 2.3 D-3 审计 detail 用**白名单**序列化，不用黑名单

`detail` 是 JSONB，若直接序列化入参，将来新增字段（如 `studentName`）会被自动写入
——P2-D05 的 SSE 载荷已因「保留标量透传」被证伪过一次（`studentName`/`idCard`
都是字符串标量会原样输出）。

**本片只接受显式传入的 `Map<String,Object>`，且在写入前跑 `DataClassification` 检测**：
检出可识别信息（身份证/手机/学号/邮箱）→ **拒绝写入并抛异常**（fail-closed）。

> ⚠️ 审计「拒写」比「写了敏感信息」安全：宁可少一条审计，
> 不可在审计里留下未成年人可识别信息（PIPL）。

### 2.4 D-4 访问日志覆盖「读学生画像」这一最高危读路径

R-2 的核心场景是「跨租户/越权读学生数据」。本片在
`get_student_profile` 工具执行路径写入访问日志：

- `action = 'TOOL_INVOKE_READ'`，`resource_type = 'student_profile'`；
- `actor_id` 取 Worker 系统身份 + runId（可追溯到具体 Run）；
- `detail` 只记 `student_id`（随机 ID，白名单允许），**不记任何姓名/学校/班级**。

## 3. 端口与实现

### 3.1 `AuditPort`（ports 层，新增）

| 操作 | 语义 | 失败行为 |
|---|---|---|
| `recordRequired` | 关键审计（审批/取消）；失败抛异常 | fail-closed |
| `recordAccess` | 访问日志；失败记 WARN 不抛 | fail-open + 可观测 |

### 3.2 `JdbcAuditRepository`（infrastructure 层，新增）

- 全部经 `TransactionalConnectionHolder.inTransaction`（P2-D05 连接所有权铁律）；
- 写入前跑 `DataClassification`，命中可识别信息 → 抛异常（D-3）；
- `actor_id` / `resource_type` **非空且长度有界**（防超长注入与日志膨胀）。

### 3.3 接入点

| 接入 | 类别 | 说明 |
|---|---|---|
| `JdbcApprovalRepository.grant` / `revoke` | 关键 | 审批授予/撤销留痕（R-1）|
| `JdbcApprovalRepository.consume` 成功时 | 关键 | 消费留痕 |
| `JdbcRunClaimRepository.requestCancel` | 关键 | 取消留痕（补 D6 的 L-2）|
| `get_student_profile` 工具 | 访问 | R-2 |

### 5.1 反证记录

| # | 注入的缺陷 | 结果 |
|---|---|---|
| 1 | 运行时 `DROP TRIGGER trg_audit_record_append_only` → 同一条 UPDATE/DELETE | ✅ **被静默放行**，且 `actor_id` 确实被改写为 `tampered`、行确实被删除（断言 `.doesNotThrowAnyException()` + 值变化双重确认）。**证明 T-2/T-3 不是「恰好有约束」，而是触发器真正在起作用** |

### 6.1 实现过程中抓到的产品级缺陷

**F-6（新增构造参数导致 Spring 上下文启动失败）**：
`JdbcRunClaimRepository` 原本带 `@Repository`（组件扫描注册）。D7 为其新增
`AuditPort` 构造参数后变成**两个构造器**，组件扫描无法选择 →
`No default constructor found` → **Spring 上下文启动失败，`PlatformSecurityE2ETest`
15 项全红**。

**修复**：去掉 `@Repository`，改为在 `ApplicationConfiguration` 显式 `@Bean` 注册
（与 `budgetPort` / `approvalPort` 风格一致）。此举**同时**解决了第二个问题：
若继续用组件扫描，`audit` 字段会拿到 `NO_AUDIT` 空实现，
**生产中取消动作将永久无痕（R-1 名存实亡）**。

> ⚠️ **教训**：给 `@Repository`/`@Service` 类加构造参数前必须先确认装配方式。
> 本项目的既定约定（`ApplicationConfiguration` 类注释已写明）是
> **「装配统一归本类，避免被测试切片的组件扫描意外拾取」**——
> 本次是该约定被违反后的一次真实回退。
> ⚠️ **连带效应**：此类缺口**只有 E2E / 上下文加载测试能发现**，
> 单元测试全部 `new` 对象，永远不会触发（与 FE 阶段
> 「`client.ts` 形参遮蔽 → HTTP 调用静默失败」的教训同源：
> **不经过装配层的测试测不到装配层缺陷**）。
