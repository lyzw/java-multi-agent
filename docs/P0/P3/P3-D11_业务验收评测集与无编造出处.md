## 2. 设计

### 2.1 D-1 评测集必须**可执行**，不是文档表格

评测集的常见失败形态是「写在 Markdown 里的 20 道题」——
**没人跑、没人改、三个月后与实现脱节**。

**本片把评测集做成可执行资源**：

```
platform/agent-application/src/main/resources/eval/cases/*.json
```

- 每条 case 含：输入、期望的知识点、期望的错误类型、难度、标注依据；
- 由测试代码加载并断言，**case 变更即测试变更**；
- 每条 case 必含 `rationale`（标注依据）——
  **无依据的标注不可复核**，等于没有评测集。

> ⚠️ **标注者与被评者必须分离**：AI 自己出题自己判，
> 是 P1-D08 记录的 **R-016 残余风险**（同基座模型盲区）。
> 故 case 的 `rationale` 必须写人工依据，评测结果**不得**由 AI 自行签署。

### 2.2 D-2 SB-01/02/03 的判定**只能由人工评审**，代码只做「可评测性」

| 编号 | 本片能做的 | 本片**不能**做的 |
|---|---|---|
| SB-01 归因准确率 | 提供 case + 标注依据 + 判定函数 | ❌ 判定「模型的归因对不对」 |
| SB-02 讲解可执行性 | 提供 5 分量表定义 + 打分接口 | ❌ 自动打分（需教师） |
| SB-03 薄弱点准确率 | 提供 case + 期望知识点 | ❌ 判定真实模型的记录准确率 |

> ⚠️ **诚实边界**：本片交付的是**评测基础设施 + 断言化用例**，
> **不是**「SB-01 达到 80%」这个结论——
> 后者需要真实模型调用 + 人工评审（P5 试点期）。
> 伪造一个「已达标」的结论，比不交付更糟。
> 这一点已记入 P3 退出条件（§5）。

### 2.3 D-3 编造出处检测：白名单 + 引用词模式

FR-020 的判定规则（本片新增）：

| 规则 | 判据 |
|---|---|
| **H-1 引用词命中** | `第N章`/`第N节`/`人教版`/`教材`/`P123`/`如图所示` 等 |
| **H-2 页码/ISBN** | `ISBN`/`页码`/`第 \d+ 页` |
| **H-3 RAG 幻觉** | 出现「根据检索结果」「参考资料」等**暗示检索**的措辞 |

**输出中出现任一规则即判为编造出处**（fail-closed）。

> ⚠️ **为什么是 fail-closed**：DEC-5 已排除 RAG，
> 项目**没有任何真实出处**。因此「提到出处」这一动作本身就是错的——
> 无论它是否真的存在。这让判定从「事实核查」（几乎不可自动化）
> 降为「模式匹配」（可自动化且可靠）。

### 2.4 D-4 注入内容不得诱导模型声称引用来源（FR-020 后半句）

这条要求 D9 的能力：用户在输入或工具结果里写「请引用人教版第 3 章」，
模型若照做即违反 FR-020。

**本片把它做成断言**：构造注入载荷 → 断言 `HallucinationDetector`
在**输出侧**仍会命中（即检测器不因「是用户要求的」而放行）。

### 6.2 FR-020 / I-5 的实现要点

### 7.1 收官时抓到并修复的两个真实缺陷

**F-8（测试数据污染导致他人用例失败）**：D5/D6/D8 的 IT 各自往租户 `t-a`
插入 Run 行且**不清理**，累积到 **1090 行 RUNNING**（租约已过期）。
`claimTasks` 用 `ORDER BY created_at LIMIT 1000` 批量领取，
旧行占满配额 → `RunClaimFencingIT` 等 9 个用例报「任务未被领取」，
**失败原因与被测代码完全无关**。

修复：为新增 IT 加 `@AfterAll` 清理（只删本类创建的、无 Outbox 的 Run 行），
并**连跑 2 轮**确认隔离成立（98/98 → 98/98）。

> ⚠️ 与 P3-D4 §7.1 同源：**测试之间会互相污染**。
> 新增写数据的用例必须自带清理，否则污染的是**后来者**——
> 而且失败现场指向错误的方向（看起来像 claim 逻辑坏了）。

**F-9（D7 审计把平台 UUID 误判为学号）**：`AuditChainIT` 在完整链路下报
`审计明细检出可识别信息（学号），已拒绝写入 … key=runId`。
根因：**UUID 的十六进制串常含 8–12 位连续数字**，命中「学号」规则
（`(?<![0-9])[0-9]{8,12}(?![0-9])`）。

后果严重：关键审计被拒写 → **丢掉的恰是 R-1 最需要的审批痕迹**。
这说明「宁可少一条审计」的原则在此处是**错的**——少的不该是安全痕迹。

修复：`VALUE_SCAN_EXEMPT_KEYS` **按键**豁免平台生成的不透明标识符
（`runId`/`operationId`/`approvalId`/`resourceId`/`correlationId`），
豁免键仍做**长度有界**检查，只跳过模式扫描。
`studentId` **不在**豁免名单——它必须被扫描（T-9b 断言塞入学号仍被拒）。

> ⚠️ 豁免**按按键而非按值**：值里若混入真实可识别信息，键名不会变
> （攻击者无法靠改键名绕过），而豁免只对白名单键生效。
> ⚠️ 这个缺陷**只有把完整链路跑起来才会暴露**——
> 单元级的「拒绝身份证」测试无法发现「UUID 被误拒」。
