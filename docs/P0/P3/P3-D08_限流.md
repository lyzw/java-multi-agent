# P3-D08 限流（D-2 预算击穿 / DoS）

> **阶段**：P3 可靠性与安全
> **切片**：D8（依赖 D1 故障注入框架、D4 预算预留）
> **验收**：D-2 ——「单租户无法通过高频调用耗尽预算或压垮共享资源」
> **威胁**：STRIDE Denial of Service（另含 P2-D05 §6 L7「SSE 无每租户连接数限流」）
> **状态**：✅ 完成（2026-10-19 · 9 IT + 4 单测全绿 + 确定性交错反证）

---

## 1. 现状：预算有上限，但**频率无上限**

D4 已实现预算预留（`budget_no_overspend` 保证**总额**不超发），但：

| 资产 | 状态 |
|---|---|
| 预算总额约束（D4） | ✅ 已有——**慢速**花完额度会被拒 |
| **请求速率约束** | ❌ **完全缺失** |
| 登录防爆破（`AuthenticationService`）| ✅ 已有——但仅覆盖登录 |
| SSE 每租户连接数限流（P2-D05 L7）| ❌ 缺失 |

**关键区别（也是本片的核心论点）**：

> **预算约束管「总量」，限流管「速率」。二者不可互相替代。**
>
> 攻击者若以 1000 QPS 发起调用，每个调用都远低于单次预留额：
> `budget_no_overspend` **一次都不会触发**（因为每笔都合法），
> 但预算会在**几分钟内**被打穿。反之，若只有限流而无预算约束，
> 慢速长跑仍会超额。

**后果**：单个恶意/失控租户可在预算耗尽前先打穿**共享资源**——
连接池（`HikariCP` 有限）、模型网关配额、DB 连接。D-4 的残余风险
（连接池耗尽）在无速率约束下从「低」升为实际可利用。

## 2. 设计

### 2.1 D-1 限流用「令牌桶」，且判定必须在 DB 内原子完成

朴素实现（先 SELECT 计数、再判断）是 check-then-act 的限流版，
**与 D4 §2.1 同一反模式**——并发下必然超发。

**本片采用单条原子 SQL**：

```sql
INSERT INTO rate_limit_bucket (tenant_id, bucket_key, window_start, count)
VALUES (?, ?, to_timestamp(floor(extract(epoch from now()) / ?)::bigint * ?), 1)
ON CONFLICT (tenant_id, bucket_key, window_start)
DO UPDATE SET count = rate_limit_bucket.count + 1
RETURNING count;
```

- 返回的 `count` 即当前窗口内的第 N 次调用；
- `count > limit` 即拒绝（**fail-closed**）；
- **无锁、无竞态窗口**（PG 单语句原子）。

> ⚠️ 拒绝时**必须回滚计数**吗？**不**——已消耗的令牌不应退还，
> 否则攻击者可通过「被拒的请求本身」维持连接，限流退化为仅计数不设防。

### 2.2 D-2 固定窗口 vs 滑动窗口：选固定窗口并显式记录边界代价

| 方案 | 优点 | 代价 |
|---|---|---|
| 固定窗口（本片）| 单条 SQL 原子、实现简单 | ⚠️ **窗口边界可突发 2×**（前后各打满一个窗口）|
| 滑动窗口/令牌桶 | 无边界突发 | 需多行状态或 Redis，复杂度高 |

**本片选固定窗口**，理由：
- 边界突发的最大幅度是 **2× limit**，是**有界的**——
  而「无上限」（现状）是**无界的**。用有界换实现正确性是净收益；
- 滑动窗口的精确实现需要行锁（`SELECT..FOR UPDATE`），
  会让限流本身成为**锁竞争点**——限流系统不该成为新的 DoS 入口。

> ⚠️ 边界突发已显式记录为已知限制（§4 L-1），不假装消除。

### 2.3 D-3 限流键按「租户 + 动作」，不做全局单例

| 维度 | 取值 | 理由 |
|---|---|---|
| `tenant_id` | 必带 | 单租户失控不应影响其他租户 |
| `bucket_key` | 动作名（如 `RUN_CREATE` / `SSE_CONNECT` / `TOOL_INVOKE`）| 不同资源限额不同；单键全局限会让 SSE 挤占 Run 创建 |

### 2.4 D-4 限流失败必须 **fail-closed**

限流组件故障时放行 = 限流形同虚设（D-2 与 D4 的 `FAIL_CLOSED` 同源）。
但**访问类动作例外**见 §2.5。

### 2.5 D-5 三类动作，三种失败语义

| 动作类别 | 限流失败时 | 理由 |
|---|---|---|
| **写入类**（`RUN_CREATE` / `TOOL_INVOKE`）| **fail-closed 拒绝** | 无速率约束 = 预算可被打穿 |
| **连接类**（`SSE_CONNECT`）| **fail-closed 拒绝** | 连接数失控会耗尽连接池（P2-D05 L7）|
| **读取类**（`EVENT_QUERY`）| **fail-closed 拒绝** | 统一语义，避免「读取无限流」成为绕过口 |

> ⚠️ 本片**全部 fail-closed**，不设例外。理由：
> 「读取不限流」会成为攻击者主动选择的绕过路径——
> 只要有一个可无限读取的端点，整个限流体系就有缺口。
> 宁可统一严格。（P2-D05 曾以「日志脱敏已完成」为由把限流后置，
> 但那是**日志**不是**速率**，两者不同。）

## 3. 端口与实现

### 3.1 `RateLimitPort`（ports 层，新增）

```java
enum Decision { ALLOWED, REJECTED, FAIL_CLOSED }
Decision check(String tenantId, String bucketKey);
long currentCount(String tenantId, String bucketKey);  // 可观测
```

**用枚举而非 boolean**（与 D4 `ReserveOutcome` / D5 `ApprovalOutcome` 同源）：
「被限流拒绝」与「限流组件故障」在运维处置上完全不同——
前者要等窗口重置，后者要修组件。

### 3.2 `JdbcRateLimiter`（infrastructure 层，新增）

- 单条原子 SQL（D-1），经 `TransactionalConnectionHolder.inTransaction`；
- `window_start` 按 `floor(epoch / windowSeconds) * windowSeconds` 对齐；
- 表级 RLS 保护跨租户隔离。

### 3.3 数据模型（V7 迁移）

| 变更 | 目的 |
|---|---|
| 新建 `rate_limit_bucket` | 固定窗口计数 |
| `UNIQUE (tenant_id, bucket_key, window_start)` | 原子 upsert 的冲突目标 |
| `idx_rate_limit_cleanup (window_start)` | 过期窗口清理入口 |
| 启用 RLS | 跨租户隔离 |

> ⚠️ 迁移须**幂等**（`CREATE TABLE IF NOT EXISTS` / `DROP POLICY IF EXISTS`）。

### 3.4 接入点

| 接入 | bucket_key | 限额 |
|---|---|---|
| `POST /api/runs` | `RUN_CREATE` | 配置项 |
| SSE 端点 | `SSE_CONNECT` | 配置项 |

### 5.3 ⚠️ 反证的三次失败与最终解法（本片最有价值的部分）

**目标**：证明唯一索引（`rate_limit_bucket_unique`）是原子 upsert 的真正基础。

| 版本 | 做法 | 结果 | 结论 |
|---|---|---|---|
| v1 | 断言「无唯一索引时 `ON CONFLICT` 报错」 | ❌ **假设不成立** | ⚠️ PG 的 `DO UPDATE SET` 在**无冲突时不触发冲突检查**，单行场景正常执行 |
| v2 | 6 线程并发跑 check-then-act | ❌ 只得到 **1 行** | ⚠️ 后到线程的 SELECT **看得见**先到线程已提交的数据 → 走 UPDATE 分支 |
| v3 | 改用独立连接池（`maxPoolSize=16`） | ❌ 仍是 **1 行** | ⚠️ 池大小不是根因 |
| **v4（采用）** | **确定性交错**：A 与 B 两个裸连接各自 `check` 到「不存在」→ 各自 `INSERT` → 同键两行 | ✅ **恰好 2 行** | 约束 load-bearing 得证 |

> ⚠️ **教训（第四次印证「反证不红先怀疑注入点」）**：
> 前三次都在**猜测失效形态**上出错——先假设「会报错」，再假设「会并发冲突」。
> 正确路径是回到 D4 T-1b 的做法：**不依赖线程调度运气，手工编排必然命中的交错**。
> ⚠️ 附带发现：`FaultInjectionSupport.adminPool()` 的
> **`maximumPoolSize=1`**，任何需要多连接的用例都必须另建宽池——
> 否则「并发」用例会静默退化为串行，而断言仍可能通过（**假阴性**）。

### 6.1 实现过程中的两处配置陷阱（均已修）

**陷阱 1：新表缺 `GRANT` → 限流变 DoS**。`app_agent` 无 `rate_limit_bucket` 权限时，
每次 `check` 都抛 `permission denied`，而限流实现把异常当 `fail-closed`
→ **全量请求被拒**。限流组件自身故障反而成了拒绝服务的入口。
修复：`V7` 末尾补 `GRANT SELECT, INSERT, UPDATE, DELETE ON rate_limit_bucket TO app_agent;`
（**逐条 `-c` 执行**，整段事务任一失败会连带回滚全 GRANT）。

**陷阱 2：`application.yml` 追加了第二个顶层 `agent:` 键**。
直接被 `ApplicationConfigTest` 的解析失败挡住——正是 MEMORY 里
「顶层键不可重复」的既有约束。修复：合并进既有 `agent:` 块。
数值同样**必须加引号**（`YamlPropertiesFactoryBean` 丢弃裸标量，
P1 已在 `delivery-limit` 上踩过）。

### 6.2 与 F-6 同源的第二个实例（本次再次印证）

`RunController` 因新增限流构造参数变成**两个构造器**，而它是 `@RestController`
组件扫描注册 → Spring 无法选择 → `No default constructor found` →
上下文启动失败、**E2E 15 项全红**。

修复：用 `@Autowired` 显式标记注入用的构造器。
> ⚠️ 这是 D7 F-6 的**第二次**发生。**通用规则**：
> 给组件扫描注册的类加构造参数前，必须确认注入方式
> （或改为显式 `@Bean`，或用 `@Autowired` 标记）。
