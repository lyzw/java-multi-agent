## 1. 为什么 D1 必须先做

P1-10 §2.3 的核心结论是：**P1 发现的 8 个缺陷中 4 个是 Sev-0，且大多只在特定输入/故障下暴露**。
正常运行下的测试抓不到它们——6 处 RLS 失效、正则锚定致零保留失效，都是在
"换角色 / 用真实句子" 时才暴露。

因此 P3 的"可靠性"断言**必须能在故障下成立**。若没有注入故障的能力，
D2–D9 只能写"正常运行下通过"的测试，等于把 P1 的 Sev-0 推到生产。
本片建立的 `FaultInjectionSupport` 是后续每片"可证伪"断言的承载底座。

---

## 2. 设计决策（D-1）

### D-1.1 注入手段只用"真实基础设施"，不 mock 故障
- **DB 故障**用真实 PostgreSQL 17 + 真实连接 kill（`Connection.close()` 不提交 → PG 自动回滚）。
- **池扰动**用真实 HikariCP 配置（`maxPoolSize` / `maxLifetime`）制造连接复用与回收。
- **重投/重放**用真实幂等键重放（`RunCreationService.createRun` 同键两次 = 模拟 MQ 重投）。
- **超时/5xx** 用测试桩 Client 注入时延/错误（D1 先留接口，D3/D9 复用）。

> ⚠️ 不为"故障"单独引入混沌工程中间件（如 chaos-mesh）。
> 本项目的故障维度有限且可控，自建轻量 `FaultInjectionSupport` 即可，
> 避免引入重依赖与 CI 复杂度。

### D-1.2 非特权角色强制（继承 P2 铁律）
所有 IT 用 `app_agent`（NOSUPERUSER NOBYPASSRLS）。`FaultInjectionSupport` 在 `@BeforeAll`
做**启动自检**：若连接是超级用户/`BYPASSRLS`，测试直接 fail —— 否则会得到"隔离失效"的虚假结论。

### D-1.3 池扰动与池=1 是互补证伪，不是重复
- 既有 `TransactionBoundaryIT` 用 `maxPoolSize=1`：证伪"连接复用分支真的复用外层"。
- 本片 `FI-RLS-001` 用 `maxPoolSize=N` + 跨租户交错：证伪"绑定按事务而非连接隔离"
  （即连接服务完租户 A 归还后，服务租户 B 时若忘记重绑会泄漏）。
- 两者方向不同，**不可互相替代**。

## 3. 故障维度与证伪矩阵

| 用例 | 注入 | 证伪的不变量 | Sev-0 类 |
|---|---|---|---|
| **FI-RLS-001** | 大池 + 跨租户交错 + 连接回收 | RLS 绑定按事务隔离，复用连接不泄漏 | 跨租户泄露 |
| **FI-ATOMIC-001** | 写入后、提交前 kill 物理连接 | 崩溃时原子回滚，无半成品 | 数据不一致 |
| **FI-IDEM-001** | 同幂等键重放（模拟 MQ 重投） | 重复投递不重复创建 Run | 重复副作用 |
| **FI-LEASE-001** | Worker 失联 → 新世代接管 → 旧世代写回 | fencing 拒旧世代、新世代安全接管 | 旧世代覆盖新结果 |

## 4. 四个用例的实现要点

### 4.1 FI-RLS-001 连接复用下跨租户隔离
1. 起一个 `maxPoolSize=4` + `maxLifetime=2s` 的 Hikari 池（强制连接回收）。
2. 租户 A、B 各创建 1 个 Run。
3. 用**交错线程**反复执行"取连接→开事务→绑本租户→查 own rows→提交→归还"，每轮随机租户。
4. 断言：任一租户查询只返回自己的行；且通过 `pg_stat_activity`/`set_config` 观察，
   被复用的物理连接在服务 B 时已重绑 `app.tenant_id=B`（不沿用 A）。
5. **反证**：临时移除 `TransactionRunner` 的 `TenantSessionBinder.bind`（注入点 = 事务开头），
   断言应失败（看到他租户行）—— 证明测试真能抓住泄漏。

### 4.2 FI-ATOMIC-001 事务中断回滚
1. 取一条受 `FaultInjectionSupport` 管理的"裸连接"（不走池）。
2. `setAutoCommit(false)` → 插入 Run 主记录（仅主记录，模拟"写了一半"）。
3. **不 commit**，`connection.close()`（模拟 JVM/连接崩溃）。
4. 用独立连接查询该 Run → 断言**不存在**（PG 已回滚未提交事务）。
5. 反证：若实现误在写入后提前 commit，则崩溃后行残留 → 断言失败。

### 4.3 FI-IDEM-001 重复 Outbox 仅建一个 Run
1. 构造同 `IdempotencyKey` + 同 `RequestDigest` 的请求。
2. 调用 `RunCreationService.createRun` **两次**（模拟 MQ 将该 outbox 投递两次）。
3. 第二次必须返回 `replay(resourceId=第一次的 runId)`。
4. 断言 `run` 表对该租户只有 **1 行**，且 `idempotency_record` 无重复。
5. 反证：临时移除幂等短路（注入点 = `JdbcRunCreationRepository.decideIdempotency`），
   断言失败（建出 2 个 Run）。

### 4.4 FI-LEASE-001 fencing 旧世代拒写
1. Worker-1 领取 Run（lease + `fencing_token=1`），随后"失联"（lease 过期）。
2. Worker-2 领取（同 Run，`fencing_token=2`），正常执行。
3. **旧 Worker-1 复活**，用 `fencing_token=1` 尝试提交结果。
4. 断言：`enforce_fencing_on_write` 拒绝该写入（旧世代）；`fencing_token=2` 的写入成功。
5. 复用 `RunClaimFencingIT` 的领取/提交 API；本片新增"失联后复活"注入点。

## 5. 已知限制（先写清，后人不会误判）

- **L1 不注入网络层故障**：不模拟 TCP 断连/磁盘满，仅注入连接 kill 与逻辑故障。
  理由：网络层故障由 PG/Hikari 的超时与重试语义覆盖，非本项目独有风险。
- **L2 FI-LEASE 复用现有 fencing 仓储**：D2 会在此之上补"并发抢占"注入，本片只证明单点复活。
- **L3 模型网关超时注入留接口未全量**：D3（UNKNOWN）与 D9（Prompt 注入）会落地完整网关故障桩。
- **L4 池扰动断言基于"观察 set_config 值"**：若 PostgreSQL 未来改变 `is_local` 语义需复审（P1-D08 §7）。

## 6. 测试证据（实现后回填）

> 运行：`IT_PG_URL=jdbc:postgresql://127.0.0.1:5433/agent_dev IT_PG_USER=app_agent mvn -pl agent-infrastructure test -Dtest=FaultInjectionIT`
> 结果：**5/5 全绿**（2026-10-19，PG17 `agent-pg17` / `app_agent` 非特权角色）。

| 用例 | 结果 | 说明 |
|---|---|---|
| FI-RLS-001 | ✅ | 大池（maxPoolSize=4 / maxLifetime=1s）下 50 轮跨租户交错，隔离始终成立 |
| FI-RLS-001b | ✅ | 同一物理连接复用给另一租户时，RLS 绑定按事务重置（不沿用残留上下文）|
| FI-ATOMIC-001 | ✅ | 裸连接写入后崩溃关闭 → 服务端回滚，无半成品 Run |
| FI-IDEM-001 | ✅ | 同幂等键重放 → REPLAY，仅建 1 个 Run |
| FI-LEASE-001 | ✅ | 池扰动下旧 fencing 世代提交被拒、新世代接管成功 |

**反证（不只测"通过"）**：FI-ATOMIC 改用池化连接后**仍通过**——
证实 HikariCP 归还连接时会回滚未提交事务，故本用例覆盖的是"连接级崩溃"
（连接被切断而非归还池）这一异常路径，与 `TransactionBoundaryIT` 的异常触发回滚互补。

**全部通过条件**：`mvn clean verify` + `IT_PG_URL` 设 `*IT` 全绿（含 E2E 15 项）。
