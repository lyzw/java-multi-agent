## 1. 现状：取消字段建好了，但没有触发、没有检查

`run` 表已有 `cancel_requested_at` 列，`RunState.CANCELLED` 已是终态，
`enforce_run_state_transition` 触发器已允许 `QUEUED/RUNNING → CANCELLED`。但：

| 资产 | 位置 | 状态 |
|---|---|---|
| `cancel_requested_at` 列 | V1 基线 | ✅ 存在，**零写入** |
| `RunState.CANCELLED` 终态 | `RunState` | ✅ 定义，**未被任何代码置位** |
| `RunClaimPort.requestCancel` / `isCancelled` | — | ❌ **完全缺失** |
| `RunExecutionLoop` 取消检查 | `execute()` | ❌ **无**——循环从不检查取消，模型可一直调用到步数上限 |
| `ToolInvocationGate` 取消检查 | `invokeAll()` | ❌ **无**——即使审批消费（D5）会查取消，非审批工具完全不查 |

**后果**：用户在 UI 点「取消」后，**没有任何代码响应**——Run 会一直跑到 `maxSteps`
耗尽，期间 `record_weakness` 等副作用照常发生。FR-011 在代码中完全悬空。

> ⚠️ 与 D3 F-2 / D4 F-3 / D5 F-5 同源：*字段/状态建了 ≠ 约束被证明有效*。

## 2. 设计

### 2.1 D-1 取消是「协作式 + 状态终态」双保险

`requestCancel` **原子**将 `RUNNING/QUEUED → CANCELLED` 并置 `cancel_requested_at`：

- **状态终态**：`CANCELLED` 是终态（`legalTargets()` 空集），
  `claimSpecificRun` 的 WHERE 只收 `QUEUED/RUNNING`，**已取消的 Run 不会被重新领取**；
  `commitResult` 的 WHERE 要求 `state='RUNNING'`，已取消 Run 的后续提交必然影响 0 行。
- **协作式**：Worker 在每轮迭代开头（模型调用前）与每个工具执行前检查取消，
  一旦观察到即停止，不再启动新动作。

> ⚠️ 为何「直接置终态」而非「只置 flag 等 Worker 自己切」：
> 直接置 `CANCELLED` 能**立即**阻止重新领取与提交覆盖，即使 Worker 进程已死，
> 取消也不会被「复活」。Worker 的协作检查是第二道（更快停止当前循环）。

### 2.2 D-2 两处取消检查：循环级 + 闸门级

| 检查点 | 位置 | 作用 |
|---|---|---|
| 循环级 | `RunExecutionLoop.execute()` 每轮迭代开头 | 模型调用前即停，避免再发一轮工具调用 |
| 闸门级 | `ToolInvocationGate.invokeAll()` 每个工具开头 | **批次内**取消——模型已返回 N 个工具调用后取消到达，第 2 个工具不得启动 |

闸门级用 `CancelGuard` 函数式接口（默认桩 `NO_CANCEL` = 永不取消，与 D5 的
`NO_APPROVAL_PORT` 同源手法），生产装配为 `RunClaimPort.isCancelled`。
**默认桩 = 不取消**：审批权威/取消链路未接入前不改变既有行为，接入后即生效。

### 2.3 残余在途竞态：副作用对账覆盖，不假装零副作用

`requestCancel` 提交后、闸门检查前存在微小时窗——若取消恰好在某工具**执行过程中**
提交，该工具副作用可能已完成（如 `record_weakness` 已写入）。

- 本片**不假装消除该时窗**（那需要在每个工具事务内再锁一次 Run，收益极低）；
- 该时窗至多导致**一个已发起的工具**副作用落地，而 `record_weakness` 是**幂等**的
  （student_id + run_id + knowledge_point），重复写入无害；
- 取消后落入的副作用由 **D7 审计链路**记录、由对账确认，符合 FR-011「已发生副作用可对账」。

> ⚠️ 这是**诚实的已知限制**（见 §5 L-1），不是缺陷。要求是「取消后不**启动**新动作」，
> 本片在两处（循环 + 闸门）保证「不启动」，残余「已启动未结束」由对账兜底。

## 3. 端口与实现

### 3.1 `RunClaimPort`（ports 层）新增

```java
/** 协作式取消：RUNNING/QUEUED → CANCELLED，置 cancel_requested_at。@return 是否生效。 */
boolean requestCancel(String tenantId, String runId);

/** 是否已取消（state=CANCELLED 或 cancel_requested_at 已置）。 */
boolean isCancelled(String tenantId, String runId);
```

### 3.2 `JdbcRunClaimRepository`（infrastructure 层）

- `requestCancel`：`UPDATE run SET state='CANCELLED', cancel_requested_at=now(),
  completed_at=now() WHERE tenant_id=? AND run_id=? AND state IN ('QUEUED','RUNNING')`，
  返回受影响行数 > 0。触发器 `enforce_run_state_transition` 已允许该迁移，不冲突。
- `isCancelled`：`SELECT state, cancel_requested_at ...`，`state='CANCELLED' OR
  cancel_requested_at IS NOT NULL`。全部经 `TenantSessionBinder.bind`（RLS 铁律）。

### 3.3 `RunExecutionLoop`（worker 层）

`execute()` 每轮迭代开头（模型调用前）新增：
```java
if (claimPort.isCancelled(tenantId, task.runId())) {
    log.info("检测到取消请求，停止执行: runId={}", task.runId());
    return ExecutionOutcome.cancelled();
}
```
新增 `ExecutionOutcome.Kind.CANCELLED`（与 `SUCCEEDED/FAILED` 同级，区别于
`SKIPPED_STALE_GENERATION`——后者是「被接管」，前者是「被用户取消」）。

### 3.4 `ToolInvocationGate`（worker 层）

新增 `CancelGuard` 函数式接口（默认 `NO_CANCEL`），`invokeAll()` 每个工具开头：
```java
if (cancelGuard.isCancelled(tenantId, task.runId())) {
    result.recordRejected(call.toolName(), "Run 已取消");
    continue; // 不注册账本、不预留、不执行
}
```
新增带 `CancelGuard` 的构造器（保留既有构造器，默认 `NO_CANCEL`）。

## 5. 测试与反证计划

### 5.1 集成测试（`CancellationRaceIT`，8 项）

| 用例 | 证明什么 |
|---|---|
| T-1 `requestCancel` 后 `isCancelled=true`、state=CANCELLED、`cancel_requested_at` 非空 | D-1 状态终态生效 |
| T-2 已终态（SUCCEEDED）Run `requestCancel` 返回 false，状态不回退 | 终态不可覆盖 |
| T-2b 重复取消幂等（第二次 false，状态仍 CANCELLED）| 取消幂等 |
| **T-3 已取消的 Run 不可被 `claimSpecificRun` 接管**（租约已过期仍不接管）| ⚠️ 取消不被「复活」 |
| T-3b 批量领取同样跳过已取消的 Run | 批量路径不漏 |
| **T-4 在途 Worker（持有正确 fencing token）提交被拒** | ⚠️ 在途结果不覆盖取消 |
| T-5 取消后续租失败（在途 Worker 应停止）| 续租路径同守 |
| T-6 跨租户：B 无法取消 / 读取 A 的 Run 取消状态 | RLS 隔离 |

> ⚠️ **T-3 的夹具关键点**：Run 夹具的 `lease_expires_at` 被显式设为**过去**
> （`now() - 1 hour`）。若租约有效，`claimSpecificRun` 本就会因「未过期」而失败，
> 用例将退化为「什么都没证明」。**前提必须显式构造**，否则测试等于没有测试
> （P3-D4 §7.1 教训）。

### 5.2 单元测试（`RunExecutionLoopTest.CancellationRace`，5 项）

| 用例 | 证明什么 |
|---|---|
| 循环级：已取消 → 模型 0 调用、工具 0 执行、outcome=CANCELLED | D-2 循环级 |
| 闸门级：取消在模型返回后到达 → 批次内 2 个工具全被拒、`allRejected` | D-2 闸门级 |
| **反证对照**：默认 `NO_CANCEL` 桩 → 已取消 Run 的工具**照常执行** | 闸门级检查 load-bearing |
| 控制组：未取消 → 工具正常执行 | 闸门不被误伤 |
| 取消幂等：第二次 `requestCancel` 返回 false | 幂等 |

> ⚠️ D6 与 D5 的检查点**必须能分别证伪**：本组一律用 `notRequired` 审批策略 +
> 「永不批准」审批端口（若被调用即 `AssertionError`），
> 使取消路径的断言不可能被审批逻辑误打误撞地「通过」。

### 6.1 实现过程中被 DB 约束抓到的两处夹具错误（非缺陷，但值得记录）

首次运行 T-2 时报 `run_completed_at_consistent` 违规——终态 Run 夹具未写
`completed_at`。修复时又因在 SQL 里内联 `CASE WHEN ... END` **打乱参数序号**
（`correlation_id` 被当作 `run_state` 传入，报 `invalid input value for enum run_state`）。

> ⚠️ 两条 CHECK（`run_completed_at_consistent` / `run_result_consistent`）
> **在本片首次被测试夹具真实触发**——虽是误伤，但证明它们是活的约束而非摆设
> （与 P3-D4 T-2 首次触发 `budget_no_overspend` 同等价值）。
> ⚠️ 教训：SQL 内联 `CASE` 里的 `?` 占位符同样计入参数序号，
> 与外层列的 `?` 混排极易错位。**条件值在 Java 侧算好再绑定**，比在 SQL 里分支更安全。
