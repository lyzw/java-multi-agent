| `tool_operation.budget_reservation_id` 列 + 注释（UNKNOWN 不释放）| V1 基线 | ✅ 已建列，**零写入** |
| **`BudgetReserver` 端口** | `ToolInvocationGate` 内嵌 `@FunctionalInterface` | ⚠️ **返回 boolean 的空壳** |
| **`BudgetReserver` 生产实现** | — | ❌ **完全缺失** |
| **预留/结算/释放的持久层** | — | ❌ **完全缺失** |
| **预算对账（悬挂预留、账实一致）** | — | ❌ **完全缺失** |

**这意味着**：闸门第 ⑥ 环「预算预留」在生产中不存在，
唯一的实现是测试里的 `(t, r, n) -> true` —— **恒真放行**。
若有人把该替身接入生产，`record_weakness` 可以被无限调用直到
租户账单爆掉，而 `budget_no_overspend` 这条「并发超发的最后防线」
**从未被真实触发过一次**（与 D3 之前的 `forbid_attempt_after_terminal` 同一处境）。

> ⚠️ 这正是 P1-10 点名的失败模式：*表建了 ≠ 约束被证明有效*。
> D4 的核心不是「补一个 DAO」，而是**让预算约束第一次被真实触发并可证伪**。

## 2. 设计

### 2.1 D-1 预留必须是「单条原子条件更新」，禁止「先查后写」

**反模式（check-then-act）**：

```sql
SELECT total_limit - reserved_amount - settled_amount FROM budget_account WHERE ...;  -- ①
-- 应用层判断余额够
UPDATE budget_account SET reserved_amount = reserved_amount + ? WHERE ...;          -- ②
```

① 与 ② 之间存在窗口。N 个并发预留可同时读到「余额充足」，
随后全部执行 ② —— **超发**。`budget_no_overspend` CHECK 会在
② 处拒绝后来者，但**先成功的那批已经多花了钱**，且拒绝时机不可预期
（可能第 3 个请求被拒而第 5 个成功，业务表现为「随机预算不足」）。

**本片采用的唯一写法**（条件在 UPDATE 内，判定与写入同一语句）：

```sql
UPDATE budget_account
SET reserved_amount = reserved_amount + ?, updated_at = now()
WHERE tenant_id = ?::uuid AND currency = ?
  AND reserved_amount + settled_amount + ? <= total_limit
RETURNING account_id::text, reserved_amount, settled_amount;
```

- 返回 0 行 = 额度不足（**与「账户不存在」区分**：见 D-2）；
- 返回 1 行 = 预留成功，RETURNING 直接给出新的账户余额，**无需回查**；
- CHECK 约束仍在，作为最后防线（应用层 SQL 写错时的兜底）。

> ⚠️ 预留**不用 `SELECT ... FOR UPDATE`**：行锁会让并发预留串行化，
> 而条件更新在 PG 的行级 MVCC 下已经是原子的，且失败方无需等待即可返回。
> 加锁只是把「并发拒绝」换成「并发排队」，在 DoS 场景下更糟（D-2 限流）。

### 2.2 D-2 「账户不存在」与「额度不足」必须区分，且都拒绝

`UPDATE ... WHERE currency = ?` 在账户不存在时同样返回 0 行。
若把两者混为一谈，运维看到「预算不足」会以为要加额度，
而真实原因是**该租户根本没有开通预算账户**（漏了种子数据或开通流程）。

| 情形 | 处理 | 对外表现 |
|---|---|---|
| 账户存在、额度充足 | 预留成功 | 放行 |
| 账户存在、额度不足 | 拒绝 | 「预算不足」 |
| **账户不存在** | 拒绝（fail-closed）| 「未开通预算账户」 |

**fail-closed 的理由**：P0-D00 §决策已定「配置缺失时拒绝而非放行」。
若账户不存在时放行，等于「没登记额度的租户无限花钱」——
这正是 P1-10 记录的 Sev-0 类「预算失控」。

### 2.3 D-3 预留必须有唯一记录：一个 ToolOperation 至多一条预留

「预留有唯一记录」（FR-012 验收原文）要求
**同一逻辑操作重复调用不得产生多条预留**（否则重复调用 = 重复扣额度）。

- `budget_reservation` 新增 `operation_id` 列 +
  `UNIQUE (tenant_id, operation_id)` 部分唯一索引（`operation_id IS NOT NULL`）；
- 预留时先按 `operation_id` 查既有预留：命中即**返回该预留**（幂等），
  不重复扣减、不新建行；
- 并发下两个请求同时「查不到」→ 都尝试 INSERT → 唯一索引让**后者失败**，
  后者转为「回查既有预留并复用」。这与 D3 账本 `register` 的命中逻辑一致。

> ⚠️ 部分唯一索引用 `WHERE operation_id IS NOT NULL`：
> 存量数据（种子/手工插入）可能没有 operation_id，
> 用全表唯一索引会让多行 NULL 冲突（PG 中 NULL 不冲突，
> 但显式声明意图更清晰，且未来 operation_id 改为 NOT NULL 时索引无需重建）。

### 2.4 D-4 三种结局对应三种预算处置，且**只有一种可自动释放**

| 工具结局 | 预留处置 | 理由 |
|---|---|---|
| `SUCCEEDED` | **结算**（RESERVED → SETTLED，reserved 转入 settled）| 成本真实发生 |
| `FAILED`（确定失败）| **释放**（RESERVED → RELEASED，额度退回）| 无副作用，成本未发生 |
| `UNKNOWN` | ⚠️ **保持 RESERVED，绝不自动释放** | 成本可能已发生（R-007 / V1 注释已写明）|

UNKNOWN 的预留**只能由对账收敛后处置**：
- `RECONCILED_SUCCEEDED` → 结算；
- `RECONCILED_ABSENT` → 释放；
- `MANUAL_DISPOSED` → 按人工结论处置（D5）。

> ⚠️ 这条与 D3 的 `tool_operation.budget_reservation_id` 注释一致：
> *「UNKNOWN 状态下不得自动释放预留——成本可能已发生（R-007）」*。
> V1 建表时就写下的约束，D4 把它变成代码。

### 2.5 D-5 重复结算不重复计费：`usage_record` 唯一索引是唯一权威

「重复结算不重复计费」（FR-012 验收原文）有两层：

1. **预留层**：同一 `operation_id` 只有一条预留（D-3）→ 不重复占用额度；
2. **计量层**：`usage_record` 的 `idx_usage_operation_once`
   （`UNIQUE (tenant_id, operation_id) WHERE operation_id IS NOT NULL`）
   → 同一操作重复写用量**必然被 DB 拒绝**。

结算实现必须用 **`INSERT ... ON CONFLICT DO NOTHING` + RETURNING**，
而不是「先查后插」：前者原子，后者又是 check-then-act。
命中冲突时返回既有 `usage_id`（幂等重放），**不重复累加 `settled_amount`**。

> ⚠️ 这是「重复结算」最危险的实现陷阱：
> 若结算写 `UPDATE budget_account SET settled_amount = settled_amount + x`
> 而 `usage_record` 插入被静默吞掉，重复调用会**凭空多计费**，
> 且 `usage_record` 与账户金额**永久不一致**——对账能发现，但已经错了。
> 故结算的账户更新必须与 usage 插入**在同一事务**，
> 且「usage 插入失败 → 整个结算回滚」，绝不允许半边落地。

### 2.6 D-6 预留额度的来源：配置只作上限输入，DB 原子更新才是准

P0-D00 §决策：**「预算预留/结算仍以 DB 原子条件更新为准，配置只作上限输入」**。

- 单次工具调用的预留额 = **配置项** `agent.budget.reserve-per-tool-call`（保守初值）；
- 该值**只是传给 DB 的输入**，能否预留由 `budget_no_overspend` 与
  D-1 的条件更新裁决；
- 未登记工具按**同一保守值**预留（不按 0，也不按工具自报值——
  工具自报金额是「被约束方申报约束额度」，等同让它自己决定花多少）。

> ⚠️ 预留额配置项缺失 → fail-closed（拒绝工具），不退 DEFAULT。
> 与 `PlatformConfig.Resolver` 的既有语义一致。

## 4. 端口与实现

### 4.1 `BudgetPort`（ports 层）

| 操作 | 语义 | 幂等 |
|---|---|---|
| `reserve` | 预留额度，返回 `Reservation` 或失败原因 | ✅ 同 operation 重复调用返回同一预留 |
| `settle` | 结算（RESERVED → SETTLED + 写 usage_record）| ✅ 重复结算不重复计费 |
| `release` | 释放（RESERVED → RELEASED + 额度退回）| ✅ 重复释放不重复退 |
| `findByOperation` | 按 operation 查预留（对账用）| — |
| `findOrphaned` | 扫描悬挂预留（RESERVED 且关联操作已终态）| — |
| `accountSnapshot` | 账户余额快照（对账用）| — |

**失败原因用枚举而非 boolean**（D-2）：

```java
enum ReserveOutcome { RESERVED, REPLAYED, INSUFFICIENT, NO_ACCOUNT, FAIL_CLOSED }
```

> ⚠️ 原 `BudgetReserver.reserve(...) → boolean` 无法表达
> 「未开通账户」与「额度不足」的差异，**必须替换**——
> 保留 boolean 会让运维在排查时拿到无信息量的 false。

### 4.2 `JdbcBudgetRepository`（infrastructure 层）

三条铁律：

1. **全部经 `TransactionalConnectionHolder.inTransaction`**
   （P2-D5：禁止直接 `dataSource.getConnection()`）；
2. **reserve / settle / release 各自单事务**——
   结算尤其不能把「usage 插入」与「账户更新」拆成两个事务（D-5）；
3. **不复用外层连接时用 `TenantConnectionLease.borrowed()`**——
   误 `close()` 会关掉外层事务连接、误 `rollback()` 会回滚外层未提交写入，
   **两者都是静默失效**（不报错，数据莫名消失）。

### 4.3 `BudgetReconciliationService`（infrastructure 层）

对账三类差异：

| 差异 | 判定 | 处置 |
|---|---|---|
| **悬挂预留**：state=RESERVED 且关联操作已终态（SUCCEEDED/FAILED/RECONCILED_*）| 查 `tool_operation.state` | 按 D-4 结算或释放 |
| **UNKNOWN 预留** | 关联操作 state=UNKNOWN | ⚠️ **不处置**，转人工（D5），只统计 |
| **账实不符**：`SUM(预留) ≠ account.reserved_amount` | SQL 聚合比对 | **只报不改**（账实不符是数据损坏，自动「修正」会把差异掩盖）|

> ⚠️ 第三项是刻意的：**对账发现差异时绝不自动改账户**。
> 自动修正 = 把「钱账不符」变成「看起来钱账相符」，差异被永久掩盖。
> 正确做法是告警 + 人工介入（D7 审计链路）。

## 5. 闸门接入（worker 模块）

`ToolInvocationGate` 第 ⑥ 环改造：

```
① Schema → ② 授权 → ③ 幂等键 → ④ 账本登记
  → ⑤ 审批 → ⑥ [D4] 预算预留（失败即拒绝，fail-closed）
  → ⑦ 执行 → ⑧ 账本记结果
  → [D4] 结算 / 释放（随 ⑧ 的结局分支）
```

| 分支 | 预算动作 |
|---|---|
| 预留失败 | **拒绝执行**（不放行），账本记 FAILED（预留未发生 ≠ 结果未知）|
| 执行成功 | `settle`（写 usage_record + 账户结算）|
| 确定失败 | `release`（额度退回）|
| UNKNOWN | ⚠️ **不动预留**（保持 RESERVED），转对账 |

> ⚠️ **预留失败时账本记 FAILED 而非 UNKNOWN**：
> 预留在 ⑦ 之前失败，工具**根本没有发出**，结果确定是「未执行」。
> 记 UNKNOWN 会凭空造出一个待对账的幽灵操作，污染对账队列。

## 7. 测试与反证计划（`BudgetReservationIT`）

| 用例 | 证明什么 |
|---|---|
| T-1 并发 N 路预留，总额超限 → **恰好一部分成功**，账户余额 = 成功数 × 预留额，**绝不超过限额** | 并发不超发（AT-BUDGET-001 前半，FR-012 核心）|

| T-5 释放 → 额度退回；重复释放**不再退**（不变成负数/虚增额度）| 释放幂等 |
| T-6 UNKNOWN 后预留**仍为 RESERVED**，账户 `reserved_amount` 不变 | D-4 / R-007 |
| T-6b 对账收敛后：ABSENT→释放 / SUCCEEDED→结算 | 对账驱动处置 |
| T-7 账户不存在 → 返回 `NO_ACCOUNT`（**不是** `INSUFFICIENT`），工具被拒 | D-2 fail-closed |

| T-8 跨租户：A 的预留 B 不可见、不可结算 | 预算不跨租户 |
| T-9 崩溃注入：账户写入后连接 kill → 整体回滚，无「扣了额度没记录」| 原子性（D1 框架）|
| T-10 对账：悬挂预留被识别处置；UNKNOWN 预留**不被自动处置**；账实不符只报不改 | §4.3 |
| T-10b 账实不符 → `isConsistent=false` 且**账户金额一字未改** | 不自动掩盖差异 |
| T-11 已结算预留不可迁回 RESERVED（DB 触发器）| 防额度二次占用 |
| T-11b `state` 拼写错误（`'resrved'`）被 CHECK 拒绝 | state 收紧为三值 |

### 7.1 ⚠️ 反证中的重大发现：T-1 是**假阴性**，必须补 T-1b

**首次反证失败**：把 `tryAtomicReserve` 换成 check-then-act
（先 `SELECT` 判断、再无条件 `UPDATE`）后，**T-1 连跑 3 次仍全绿**。

- 若就此收工，会得出「并发下不会超发」的**错误结论**——
  而 check-then-act 恰恰是最经典的超发写法；
- 根因：竞态窗口只有「SELECT 返回 → UPDATE 发出」之间的**微秒级间隙**。
  另写独立探针（20 轮 × 24 线程、并在 check 与 act 之间插入 50ms sleep）
  复现，才确认 check-then-act **确实会超发**——
  但 sleep 放宽窗口的做法不能进正式测试（等于把被测行为改成被造行为）。

**正确解法：确定性交错**（T-1b）。不依赖线程调度运气，而是手工编排：

1. 连接 A：`SELECT ... FOR UPDATE` 锁住账户行 → 扣减 0.60 → **不提交**；
2. 连接 B（独立线程）：发起真实预留 → 它读到旧值判定「够」→ UPDATE **阻塞在行锁上**；
3. 主线程 `A.commit()` → B 被唤醒，在**最新行版本**上重新判定 → 必须返回 `INSUFFICIENT`；
4. 断言 B 未抛异常、结局为 `INSUFFICIENT`、账户预留额恰为 0.60。

反证验证：注入 check-then-act 后，T-1b **如期转红**
（B 依据过期判断继续扣减 → 触发 `budget_no_overspend`，1.20 > 1.00）。

> ⚠️ **教训（与 P3-D3 F-2 同源）**：
> 「测试通过」不等于「不变量被证明」。判据是**反证能否转红**，
> 而反证能否转红取决于**测试是否真的击中了失效路径**。
> 并发测试尤其危险——它可能只是在**验证一个从未被触发的分支**。
> 当反证不红时，第一反应应是**怀疑注入点选错 / 窗口太窄**，
> 而不是认为实现正确。

### 8.1 实现过程中的两处产品级缺陷（测试抓出）

**F-3（预算链路无实现）**：闸门第 ⑥ 环的 `BudgetReserver` 是返回 `boolean` 的
空壳，生产无实现，唯一「实现」是测试里的 `(t, r, n) -> true` **恒真放行**。
`budget_no_overspend` 这条「并发超发的最后防线」**从未被真实触发过一次**。
与 D3 之前的 `forbid_attempt_after_terminal` 完全同构 —— *表建了 ≠ 约束被证明有效*。

**F-4（预留额配置用可变静态状态）**：初版把预留额放进 `BudgetPolicy` 的
`static volatile` 字段，闸门在工具调用时才读。结果：
① 「未装配」与「已装配为 0」无法区分；
② 无法在测试中构造「配置缺失 → fail-closed」路径（测试全红）；
③ 并发装配不安全。
**修复**：改为构造参数注入 + 构造期校验（非正数即拒绝），
配置解析留在 `BudgetPolicy.requireReserveAmount`（装配期调用，缺失即抛）。

> ⚠️ **教训**：安全相关的「配置是否生效」不应依赖运行期可变全局状态——
> 它把一个装配期可判定的问题推迟到运行期，且让 fail-closed 路径不可测。
