## 1. 现状：审批表建好了，但一行都没写过、闸门恒拒

P2 已把 `approval` 表建齐（state 枚举 PENDING/APPROVED/REJECTED/EXPIRED/CONSUMED；
绑定 operation_id + argument_digest + target_resource + expires_at），但：

| 资产 | 位置 | 状态 |
|---|---|---|
| `approval` 表 + `approval_state` 枚举 | V1 基线 | ✅ 已建表，**零写入、零消费** |
| `ApprovalPort`（审批消费端口） | — | ❌ **完全缺失** |
| `JdbcApprovalRepository`（JDBC 实现） | — | ❌ **完全缺失** |
| 闸门第 ⑤ 环「审批」 | `ToolInvocationGate` | ⚠️ **恒 fail-closed 拒绝**（审批流未实现，need-approval 的工具一律拦下）|

**这意味着**：FR-013 在代码中**完全没有落地**。闸门第 ⑤ 环对「需要审批」的工具
一律拒绝，行为虽安全，但**路径是「恒拒」而非「查不到有效审批即拒」**——
审批权威（人类审批台 / 策略引擎，E-2）接入后，没有任何代码能消费审批。

> ⚠️ 这正是 P1-10 点名的失败模式又一次重演：*表建了 ≠ 约束被证明有效*。
> D5 的核心不是「补一个 DAO」，而是**让审批消费的全套约束第一次被真实触发并可证伪**。

## 2. 设计

### 2.1 D-1 消费与取消检查必须同事务原子（红线：取消后不得启动新动作）

**反模式**：先查审批状态决定是否执行，再查 Run 是否已取消。两步之间存在窗口——
若审批在「已取消 Run」上被消费，会制造一个「已批准但 Run 已废」的幽灵审批，
且工具动作可能在取消信号之后启动（FR-011 取消竞态的审批侧同源缺陷）。

**本片采用的唯一顺序**（均在单事务内、按 `SELECT..FOR UPDATE` 串行化）：

```
① 锁 Run（FOR UPDATE）→ 校验取消 → 已取消则 RUN_CANCELLED，绝不消费审批
② 锁审批（FOR UPDATE）→ 状态校验
③ 有效期校验（过期则 markExpired → EXPIRED）
④ 绑定防篡改（argument_digest / target_resource）
⑤ 标记消费（CONSUMED），幂等命中则返回 CONSUMED
```

- 取消检查**在消费之前**——已取消的 Run 不会消费任何审批（T-5 断言）；
- `FOR UPDATE` 两锁串行化同一 operation 的并发消费，杜绝「双花」。

### 2.2 D-2 绑定防篡改：审批后参数 / 目标被改则消费失败

审批授权时绑定 `argument_digest` 与 `target_resource`。消费时比对：

- `argument_digest` 不符 → `ARGUMENT_MISMATCH`，审批保持 APPROVED（**不被消费**）；
- `target_resource` 不符 → `TARGET_MISMATCH`，同上。

> ⚠️ 闸门侧 `argumentDigest` 与 `RunToolLedgerPort` 的 `requestDigest` **同源**
> （均来自 `call.arguments()`），`targetResource` 取工具名。两者都被篡改的调用
> 不得复用既有审批——否则审批变成「一次批准、任意调用」的通行证（Sev-0）。

### 2.3 D-3 幂等消费：提交后崩溃、重启重放仍为 CONSUMED

审批按 operation_id **1:1 绑定**，不存在「两个不同操作抢同一审批」的双花可能。
已 CONSUMED 的审批再次消费返回 `CONSUMED`（不报错、不新建、不重复计费），
支持「消费提交后进程崩溃、Run 重启重放」的崩溃恢复场景（T-1 断言）。

### 2.4 D-4 应用层 + DB 双保险：V5 触发器禁止终态非法迁出

应用层（`JdbcApprovalRepository`）已实现审批消费全套校验，但**任何应用层校验
都可能被绕过**（直接 SQL、批量脚本、未来新路径）。`V5__approval_state_guard.sql`
在 DB 层加 `enforce_approval_state_transition` 触发器：

- 终态（CONSUMED / REJECTED / EXPIRED）不可迁出；
- PENDING 只能进 APPROVED/REJECTED/EXPIRED；
- APPROVED 只能进 CONSUMED/EXPIRED/REJECTED。

与应用层校验构成双保险（与 D4 的 `enforce_reservation_state_transition` 同源手法）。

### 2.5 默认 fail-closed 桩：审批权威接入前的占位

`ToolInvocationGate` 新增 `ApprovalPort approvalPort` 字段，默认桩
`NO_APPROVAL_PORT`（匿名类，恒返回 `NO_APPROVAL`）。在 E-2 审批权威接入前，
需要审批的工具在「查不到有效审批」时一律被拒——这与既有恒拒行为一致，
只是路径从「恒拒」变为「查不到有效审批即拒」，且**具备了被真实审批驱动的能力**。

> ⚠️ 闸门第 ⑤ 环的触发条件 `approvalPolicy.evaluate(handler).requiresApproval()`
> 当前生产未装配真实 `ApprovalPolicy`（gate 缺 bootstrap 装配，见 §5 L-4）。
> 单测用 `ScriptedApproval` 驱动；生产装配是 Worker 主循环切片职责。

## 3. 端口与实现

### 3.1 `ApprovalPort`（ports 层）

| 操作 | 语义 | 幂等 |
|---|---|---|
| `grant` | 绑定并授予审批（APPROVED），须带 approver_id + decided_at（DB CHECK 强制）| — |
| `consume` | 原子消费（§2.1 五步），非 CONSUMED 不标记、不抛异常 | ✅ 已消费命中 CONSUMED |
| `revoke` | APPROVED → REJECTED（**只撤销未消费的**；已消费不可撤销，须走对账）| — |
| `findActive` | 仅返回 APPROVED/PENDING 视图 | — |

**消费结果用枚举而非 boolean**（与 D4 的 `ReserveOutcome` 同源取舍）：

```java
enum ApprovalOutcome {
    CONSUMED, NO_APPROVAL, REJECTED, EXPIRED,
    NOT_APPROVED, ARGUMENT_MISMATCH, TARGET_MISMATCH, RUN_CANCELLED
}
```

> ⚠️ 每个枚举值都对应一个可被反证的不变量（§6）。用 boolean 会把
> 「已取消」「参数被篡改」「过期」全部折叠成同一个 false，排查时方向全错。

### 3.2 `JdbcApprovalRepository`（infrastructure 层）

连接所有权铁律：**全部经 `TransactionalConnectionHolder.inTransaction`**
（P2-D05：禁止直接 `dataSource.getConnection()`）。`consume` 内五步
（§2.1）在同一事务内完成，任一不满足即按对应 `ApprovalOutcome` 拒绝。

### 3.3 闸门接入（worker 模块 `ToolInvocationGate`）

第 ⑤ 环改造：

```
① Schema → ② 授权 → ③ 幂等键 → ④ 账本登记
  → ⑤ [D5] 审批消费（requiresApproval 时调用，非 CONSUMED 即 fail-closed 拒绝）
  → ⑥ 预算预留 → ⑦ 执行 → ⑧ 账本记结果
```

| 分支 | 审批动作 |
|---|---|
| outcome == CONSUMED | 放行，进入预算预留 |
| 其他 7 种 | **拒绝执行**（不放行），账本记 FAILED，工具不发出 |

> ⚠️ 拒绝时账本记 FAILED 而非 UNKNOWN：审批被拒时工具**根本没有发出**，
> 结果确定是「未执行」。记 UNKNOWN 会造出待对账的幽灵操作（与 D4 §5 同源）。

### 6.1 反证记录

| # | 反证 | 结果 |
|---|---|---|
| 1 | 去掉 V5 的 `trg_approval_state_guard`（dropTrigger）后，将终态 CONSUMED 非法迁回 APPROVED → T-DB 的「反证段」断言该 UPDATE 被静默放行 | ✅ 触发器是 load-bearing（去掉后才放行，证明约束生效）|
| 2 | `consume` 去掉 ① 取消检查（先消费后查 Run）→ T-5 断言「审批不被消费」将失效 | ✅ 设计内（取消检查前置是原子性的关键）|
| 3 | `consume` 去掉 ⑤ 绑定比对（argumentDigest 不再比对）→ T-4 断言转为 CONSUMED | ✅ 防篡改约束被绕过即红 |

> ⚠️ 反证 1 采用的**运行时注入**范式：测试在事务内 `DROP TRIGGER`，

> 这是 D4 T-2 / T-11 同款手法——**让 DB 第二道防线在被证明有效前先被证明是负载-bearing 的**。

### 7.1 实现过程中的产品级缺陷（测试抓出）

**F-5（审批消费零实现）**：`approval` 表建好却无任何 Java 消费路径，闸门第 ⑤ 环
恒拒。`FR-013` 在代码层面完全悬空——审批权威接入后无任何代码能驱动。
D5 把端口、JDBC 实现、闸门接入、DB 双保险一次性补齐。

> ⚠️ 教训（与 D3 F-2 / D4 F-3 同源）：*表建了 ≠ 约束被证明有效*。
> 闸门对「需要审批」工具的「恒拒」是一种**安全的假象**——
> 它把「审批流未实现」伪装成「审批在生效」，直到 E-2 接入才发现毫无消费逻辑。
