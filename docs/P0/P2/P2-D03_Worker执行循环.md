## 2. 执行循环

```
领取租约（D2 已完成，token=N）
      ↓
执行前检查：租约是否仍属当前世代？
      ↓ 否 → 放弃，不执行（已被接管）
      ↓ 是
┌─────────────────────────────────────────────┐
│ 循环（上限 = maxSteps，来自配置快照）        │
│   ① 构建 ModelRequest（含执行快照配置）      │
│   ② 调用 ModelGateway                        │
│   ③ 若返回 toolCalls → 逐个执行（见 §4）    │
│   ④ 若无 toolCalls → 生成结果，退出循环      │
│   ⑤ 续租（长任务必须，否则会被接管）         │
└─────────────────────────────────────────────┘
      ↓
提交结果（携带 token=N，世代不符则被拒）
```

### 2.1 ⚠️ 为何执行前必须检查世代

租约可能在「检查」与「执行」之间过期并被他人接管。

若不检查就执行，白白消耗模型成本（真金白银），
且提交时会被 fencing 拒绝 —— 产出全部作废。

> **检查只是优化，不是安全保证**。真正的保证在提交环节：
> `commitResult` 带 token，世代不符时数据库直接拒绝。
> 执行前检查是为了**省成本**，不是防越权。

## 3. 三个必须区分的异常语义

这是 D3 最核心的设计点。

| 情形 | 判定 | 后果 | 可否重试 |
|---|---|---|---|
| 模型超时 | `TIMEOUT` | 未产生副作用 | ✅ 可重试 |
| 模型限流 | `RATE_LIMITED` | 未产生副作用 | ✅ 可重试 |
| 工具**确定失败** | `definitelyFailed()` | 未产生副作用 | ✅ 可重试 |
| **工具结果未知** | `unknownResult()` | **可能已产生副作用** | ❌ **禁止重试** |

### 3.1 ⚠️ 为什么必须严格区分

混淆二者是最易出现的 **Sev-0**：

| 若混淆 | 后果 |
|---|---|
| 把 `unknownResult` 当可重试 | **重复写入** `record_weakness` → 重复副作用 |
| 把 `definitelyFailed` 当不可重试 | 瞬时故障不重试 → 任务莫名失败 |

前者不可逆（数据已重复写入），后者可人工补救。

### 3.2 UNKNOWN 处置

工具抛 `unknownResult()` 时：

```
标记该 ToolOperation 为 UNKNOWN
      ↓
⚠️ 停止本次 Run 的工具执行（不继续下一个工具）
      ↓
不得释放预算预留（成本可能已发生）
      ↓
进入对账队列，由 reconcile() 确定结果
```

**绝不允许**：当作普通失败重试、跳过继续、直接标记 FAILED。

## 4. 工具调用的闸门顺序（红线 9）

模型返回 `toolCalls` 时，每个工具**独立**走完整链条：

```
① Schema 校验（ToolHandler.validate）
      ↓ 失败 → 拒绝该工具调用，把错误回给模型，不执行
② ⚠️ 执行时重新授权（ToolsInvocationAction）
      ↓ 拒绝 → 拒绝该工具调用
③ 幂等键构造（student_id + run_id + knowledge_point）
④ 账本：创建/更新 ToolOperation（PENDING）
      ↓
⑤ 审批检查（按 riskLevel，DEC-11）
      ↓ 需要审批 → 进入审批流，本次 Run 挂起
⑥ 预算预留
      ↓ 不足 → 拒绝
⑦ 执行（携带 fencing_token）
⑧ 账本更新为 SUCCEEDED / UNKNOWN
```

> ⚠️ **禁止使用 Spring AI `ToolCallingAdvisor` 的自动执行路径**——
> 它会绕过上述全部闸门（ADR-011 §3.3）。

### 4.1 ⚠️ 唯一重试点

本阶段明确：**重试只在 Worker 侧实现**，不引入 Spring 的 `@Retryable`。

原因：两者同时生效会**双重重试** ——
每次失败重试 2 次而非 1 次，对 `record_weakness` 意味着**重复写入 = Sev-0**。

## 5. 状态迁移

```
QUEUED ──领取──> RUNNING ──成功──> SUCCEEDED
                    │
                    ├──确定失败──> FAILED
                    ├──可重试异常──> RUNNING（下一步重试，受 maxSteps 约束）
                    ├──超时──> TIMED_OUT
                    └──取消──> CANCELLED
```

⚠️ 终态（SUCCEEDED / FAILED / TIMED_OUT / CANCELLED）**不可迁出**，
由 `enforce_run_state_transition` 触发器强制。

### 5.1 步数上限

⚠️ 必须有 `maxSteps` 上限。否则模型可能反复请求工具直到耗尽预算。

配置来自 **Run 创建时的快照**（`RunConfigSnapshot`），
不是执行时读当前配置 —— 否则改了配置会影响在途 Run。

## 6. 失败与边界

| 情形 | 行为 | 理由 |
|---|---|---|
| 租约已失效 | 不执行，放弃 | 已被接管，执行是浪费 |
| 步数超限 | 标记 FAILED | 防止无限循环 |
| 模型错误（可重试） | 重试，受 maxSteps 约束 | 瞬时故障 |
| 模型错误（不可重试） | 标记 FAILED | 重试无意义 |
| 工具 `unknownResult` | 标记 UNKNOWN，停止工具执行 | 可能有副作用 |
| 工具 Schema 错 | 拒绝该调用，回错给模型 | 让模型自我纠正 |
| 预算不足 | 拒绝工具调用 | DEC-9 |
| 提交时世代不符 | 数据库拒绝 | fencing 是最终保证 |

## 7. 测试覆盖计划

| 分组 | 命题 |
|---|---|
| 执行前检查 | 世代失效 → **不执行模型调用** |
| 异常分类 | 4 种异常各自的状态与可重试性 |
| **UNKNOWN** | 标记 UNKNOWN、**停止工具执行**、不释放预算 |
| 工具闸门 | 授权在执行前；Schema 错不执行 |
| 步数上限 | 超限 → FAILED，不无限循环 |
| 提交 | 世代不符 → 被拒（已有 IT 覆盖） |

> ⚠️ 核心断言：
> 「`unknownResult` **不重试**」比「工具抛异常时状态为 FAILED」更重要。
