## 0. 为什么要单独一份文档

上一份 D-001 文档解决的是**「上下文不可伪造」** —— 代码层根因已解除。

但从「测试全绿」到「可部署」还差三段：

```
逻辑正确 → Bean 已装配 → HTTP 链路通 → 端到端验证
   ✅        ❌            ❌           ❌
```

⚠️ **没有 Security 配置类，Spring Security 的默认行为是放行所有请求**。
也就是说：即使上下文构造正确，若过滤器未装配，实际请求根本到不了它。

> 这类「装配缺失」不会体现在任何单元测试里 —— 测试直接 new 对象，
> 绕过了整个容器。**只有端到端测试能发现。**

## 2. Security 过滤链设计

### 2.1 端点分级

| 端点 | 要求 | 理由 |
|---|---|---|
| `POST /api/auth/token` | **permitAll** | 登录本身无凭据 |
| `GET /api/auth/jwks` | **permitAll** | 公钥本就公开 |
| `/actuator/health` | permitAll | 探活 |
| 其余全部 | **authenticated** | 默认拒绝 |

> ⚠️ 用 `.anyRequest().authenticated()` 而非逐个端点声明 ——
> **新增端点默认受保护**，漏配置即拒绝，而非漏配置即放行。

### 2.2 关键配置项

| 配置 | 值 | 理由 |
|---|---|---|
| CSRF | **禁用** | 无 Cookie 会话，令牌在 Authorization 头 |
| Session | `STATELESS` | 不建会话，避免会话固定攻击 |
| 认证入口 | `BearerTokenAuthenticationFilter` | 令牌解析 |
| 401 vs 403 | 分开处理 | 语义不同，混淆致客户端误判 |

### 2.3 错误响应须与业务层一致

未认证返回 **401 + `application/json`**，而非 Spring 默认的 HTML 错误页。

> 理由：客户端按 JSON 解析，收到 HTML 会抛出难以定位的解析异常。
> 且 HTML 错误页可能泄露框架版本信息。

## 3. 登录端点设计

### 3.1 请求/响应

```jsonc
// POST /api/auth/token
{ "loginName": "student01", "password": "..." }

// 200
{ "accessToken": "...", "tokenType": "Bearer", "expiresIn": 900 }
```

### 3.2 ⚠️ tenantId 从哪里来

**这是一个未决的安全问题**，须显式记录：

方案 A：请求体带 `tenantId` —— ❌ **客户端可指定，等于可尝试任意租户**
（虽然登录失败，但会产生跨租户的账号枚举面）

方案 B：登录名里含租户前缀（`t-a.student01`）—— 需发号时约束

**本期决策**：请求体**必须**带 `tenantId`，但——
- 登录名**全局唯一**，跨租户登录必然失败
- 失败响应**不区分**「租户不存在」/「账号不存在」/「密码错误」
- 所有失败路径**耗时一致**

> 即：允许客户端指定租户，但**不产生可利用的枚举面**。
> 这是「用错误设计换正确结果」的取舍，已记录。

### 3.3 响应绝不包含

- `password_hash`
- 失败的具体原因
- `principalId`（登录响应不需要，客户端拿不到也无害，
  但也不提供 —— 最小化原则）

## 4. 密钥管理

| 环境 | 私钥来源 | 风险 |
|---|---|---|
| 本地/测试 | **启动时生成** | 重启后已签发令牌全部失效（本地可接受） |
| 生产 | `${JWT_PRIVATE_KEY}` 环境变量注入 | **未实现，P4 接入 KMS** |

> ⚠️ 生产若用启动生成，滚动重启会导致全员掉线。
> 故配置项 `agent.auth.jwt.private-key` **缺省为空**：
> 为空则仅在 `dev` profile 下允许启动生成，其余环境**启动失败**。

### 4.1 fail-closed 配置

以下配置**缺失或非法一律启动失败**，不接受默认值：

| 配置 | 校验 |
|---|---|
| `issuer` | 非空 |
| `audience` | 非空 |
| `token-ttl` | 1 ~ 60 分钟 |
| `private-key` | 非 dev 环境必填 |

> 沿用项目铁律：**fail-closed**。认证配置错误会导致全站 401，
> 与其启动后才发现，不如启动即失败。

## 5. 端到端验证计划

⚠️ **本节是本文档的重点**。单元测试无法覆盖装配缺陷。

| # | 场景 | 期望 |
|---|---|---|
| E2E-1 | 无令牌 POST /api/runs | **401** |
| E2E-2 | 登录成功 → 带令牌 POST | **201** |
| E2E-3 | 令牌为 `alg=none` 伪造 | **401** |
| E2E-4 | 令牌被篡改（换租户） | **401** |
| E2E-5 | **登录失败后立即用该令牌调 Run** | **401**（不得因缓存而通过） |
| E2E-6 | 有效令牌但角色不足 | **403** |
| E2E-7 | 错误口令 | **401**，且响应时间与「账号不存在」相近 |
| E2E-8 | /api/auth/jwks 无令牌可访问 | **200** |

> E2E-5 是关键：**令牌校验失败后不得有任何缓存残留**。
> 若某处缓存了「已认证」状态，令牌撤销机制完全失效。

## 6. 已知限制（编码前预判）

| # | 限制 | 影响 | 处置 |
|---|---|---|---|
| 1 | 无 refresh token | 15 分钟需重新登录 | P3 |
| 2 | 无 MFA | 撞库风险 | P3+ |
| 3 | 无令牌撤销列表 | 已签发令牌在有效期内不可撤回 | 靠短时效 + 执行时授权 |
| 4 | 登录端点无限流 | 分布式撞库 | **P3 网关层必做** |
| 5 | 角色管理无接口 | 需手工 SQL 分配角色 | P3 |
| 6 | 生产私钥未接 KMS | 重启即掉线 | P4 |

## 7. 不做什么

| 不做 | 理由 |
|---|---|
| 注册自助端点 | 涉及监护人同意流程（P3+），本期只做受控发号 |
| 密码找回 | 需要邮箱/手机号，而 PIPL 要求我们**不采集**这些 |
| 多租户切换 | 会让一次登录可访问多租户，风险过大 |
| HTTP Basic | 与令牌模型并存易混淆 |

> **密码找回这一条尤其值得注意**：它需要一个我们刻意不采集的字段。
> 这正是「结构上不提供」的价值 —— 需求来了会发现做不了，
> 从而走 CHG 评审，而不是顺手加个列。
