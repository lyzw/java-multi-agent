## 1. 职责边界

D1 只做一件事：**把外部请求安全地转成一次 Run 创建**。

| 属于 D1 | 不属于 D1 |
|---|---|
| 请求校验 | 模型调用（D3） |
| 内容合规检查 | 工具执行（D4） |
| 执行时授权 | MQ 消费（D2） |
| 幂等判定与原子提交 | SSE 推送（D5） |

> **刻意不做**：不引入业务逻辑、不做结果查询、不处理审批。
> 每多一件事，就多一处可能绕过闸门的地方。

---

## 2. 执行链（红线 9，不可跳过）

```
① 请求结构校验
      ↓
② 内容合规检查（纵深防御：可识别学生信息）
      ↓
③ 零保留闸门（ZeroRetentionGate）
      ↓
④ 执行时授权  ← ⚠️ 必须在创建之前
      ↓
⑤ 用例：原子提交 + 幂等判定
      ↓
⑥ 返回 201（新建）或 200（幂等重放）
```

### 2.1 ⚠️ 为何授权必须在创建之前

若授权放在创建**之后**，会出现一个窗口：

```
Run 已落库 → 授权失败 → 调用方收到 403
```

攻击者可用一个**被拒绝但已创建**的 Run 消耗资源 ——
攻击成本极低（只需反复发请求），而系统已付出写库代价。

测试用 `AtomicBoolean` 断言**授权失败时用例绝不被调用**，
而非仅断言「抛了异常」—— 后者无法区分「拒绝了但已创建」。

### 2.2 三道检查的分工

| 检查 | 拦截什么 | 位置 |
|---|---|---|
| ① 结构校验 | 缺字段、类型错、长度超限 | `CreateRunRequest` 构造器 |
| ② 内容合规 | 身份证/手机号/学号/邮箱 | `assertNoIdentifyingContent()` |
| ③ 零保留闸门 | 未确认供应商的真实数据 | `ZeroRetentionGate` |

> ② 是**纵深防御**，主防线是 ③。
> 正则无法穷尽编码与隐写形式，故不能只依赖它。

## 3. 关键设计决策

### 3.1 请求对象不含 tenantId（ADR-006 / NFR-001）

`CreateRunRequest` 的 record 组件中**没有** `tenantId` 字段。

| 决策 | 理由 |
|---|---|
| 不提供该字段 | 从类型层面杜绝「客户端指定租户」的可能 |
| 反射断言组件不存在 | 防止日后「顺手加一个」时无人察觉 |
| 拒绝未知字段 | 越权尝试**报错**而非静默忽略 |

> **为何拒绝未知字段是关键**：若宽松忽略，客户端传
> `tenantId=别人的租户` 会被静默丢弃。看似"安全"，
> 实则**掩盖了攻击痕迹** —— 监控里看不到任何异常。

### 3.2 错误消息不泄漏内部结构

| 场景 | HTTP | 消息内容 | 为何 |
|---|---|---|---|
| 授权拒绝 | 403 | 「无权执行该操作」 | 不含资源标识，防枚举 |
| 幂等冲突 | 409 | 「该幂等键已被不同请求占用」 | 不含键值/摘要（可能含业务信息） |
| 零保留拦截 | **451** | 「当前合规状态不允许」 | Legal Obstacle ≠ 权限不足 |
| 请求体错误 | 400 | 通用 | 不回显字段值 |
| 兜底 | 500 | 通用 | 堆栈只进日志 |

> **451 而非 403**：合规阻断与权限不足是**不同性质**的问题。
> 451 准确表达「不是没权限，是法律不允许」，便于监控分类。

> **合规事件留痕但不记录数据**：`ZeroRetentionViolationException`
> 的日志只记状态、供应商、分级，**不记被拦截的内容**。

### 3.3 异常与拒绝必须可区分

| 混淆方式 | 后果 |
|---|---|
| 拒绝 → 伪装成故障（500） | 监控误报，真实拒绝被噪声淹没 |
| 故障 → 伪装成拒绝（403） | 问题被忽略，线上故障无人察觉 |

故 `AccessDeniedException`（明确拒绝）→ 4xx，
其余未预期异常 → 5xx。

### 3.4 CurrentPrincipal 独立于 TenantContext

| 类型 | 职责 | 为何分开 |
|---|---|---|
| `TenantContext` | 租户 + 主体 + 角色 | 领域概念 |
| `CurrentPrincipal` | providerId / snapshotId / correlationId | 调用侧上下文 |

避免领域层被 API 概念污染（`AgentCorePurityTest` 的精神延伸）。

## 4. 接口契约

### 4.1 请求

```json
POST /api/runs
{
  "idempotencyKey": "uuid",
  "agentId": "agent-uuid",
  "input": { "question": "一元二次方程", "process": "..." }
}
```

**约束**：

| 字段 | 规则 |
|---|---|
| `idempotencyKey` | 非空，≤128 字符 |
| `agentId` | 非空 |
| `input` | 非空 Map |
| 未知字段 | **拒绝**（含 `tenantId`） |

### 4.2 响应

| 情况 | 状态码 | `replayed` |
|---|---|---|
| 首次创建 | 201 | `false` |
| 幂等重放 | 200 | `true` |

> 让客户端能区分「新建」与「重放」——
> 前者应更新 UI，后者不应重复触发副作用。

| 分组 | 项数 | 关键命题 |

> 例：授权测试断言用例未被调用，而非仅断言 `AccessDeniedException`。
