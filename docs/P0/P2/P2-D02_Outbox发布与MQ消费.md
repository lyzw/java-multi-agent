## 2. 核心问题：为什么必须用 Outbox

### 2.1 若直接发消息

```
BEGIN → INSERT run → COMMIT → 发 MQ
                        ↑
                   这里崩溃 →
              Run 已创建但无人知晓，任务静默卡死
```

消息发出前进程崩溃 → **任务永久丢失**，且无任何报错。

### 2.2 Outbox 模式

```
BEGIN → INSERT run + INSERT outbox_event → COMMIT
                                              ↓
                                    轮询器读 PENDING
                                              ↓
                                        发 MQ → 标记 PUBLISHED
```

**关键**：Run 与 Outbox 在**同一事务**（红线 3，D1 已实现并验证）。
发消息失败时 Outbox 仍是 PENDING，下次轮询继续 —— **任务不会丢**。

> 代价是**至少一次投递**而非恰好一次。因此消费端必须**幂等**
> （这正是 D2 需要租约领取的原因）。

## 3. 发布器设计

### 3.1 轮询查询

```sql
SELECT outbox_id, run_id, payload, attempts
FROM outbox_event
WHERE tenant_id = ?::uuid AND state = 'PENDING'
ORDER BY created_at
LIMIT ?
```

⚠️ **必须带 tenant_id** —— RLS 生效，未绑定上下文时返回 0 行。

已有索引 `idx_outbox_pending (tenant_id, created_at) WHERE state='PENDING'`
与查询条件匹配，无需新增。

### 3.2 单租户隔离

⚠️ **一个实例只处理一个租户**。多租户轮询的实现方式有两种：

| 方案 | 说明 | 本期选择 |
|---|---|---|
| A. 单租户循环 | 每个租户一个发布器实例 | ✅ **采用** |
| B. 全租户轮询 | 一个发布器遍历所有租户 | ❌ 需跨租户权限，破坏隔离 |

**理由**：方案 B 需要能读取所有租户的权限，
一旦该连接配置错误，就会跨租户发布消息 —— **隔离在最弱的地方被打破**。

> 代价：租户数增加时需要多实例。但首期 `deployment.pilot.max-tenants=1`，
> 租户规模问题推到 P4。

### 3.3 状态流转

```
PENDING ──发布成功──> PUBLISHED（published_at 记录）
   │
   └──发布失败──> FAILED（attempts+1，记录 last_error）
                    │
                    └── attempts 超阈值 → 告警，转人工
```

⚠️ **不自动重置 FAILED 为 PENDING**：

自动重试会让坏消息无限循环。若某事件因数据问题永久失败，
应人工介入而非掩盖。

### 3.4 publisher confirms（可靠性前提）

⚠️ **必须等待 broker 确认**才能标记 PUBLISHED。

若发出即标记，而消息实际未到达 —— Outbox 认为已发布，
但消息不存在 → **任务静默丢失**，且 Outbox 已不再重试。

Spring 配置已开启 `publisher-confirm-type: correlated`，本设计依赖它。

## 4. 消费者设计

### 4.1 消费即领取租约

```
收到消息 → 解析 payload → 领取租约（fencing_token +1）→ 确认消息
                ↓
        领取失败（已被他人领取）→ 确认消息并丢弃（不是错误）
```

> ⚠️ **重复投递是正常现象**（at-least-once）。
> 领取失败说明别人已领走，直接确认丢弃即可 —— **不重试**。
> 重试会导致消息在多个 Worker 间来回打转。

### 4.2 消息体最小化

消息**只含唤醒信号**：

```json
{ "runId": "...", "tenantId": "...", "attempt": 0,
  "fencingToken": 0, "enqueuedAt": "..." }
```

⚠️ **禁止携带**：Prompt、工具参数、学生数据、答案。

理由：消息一旦进入 MQ 就**难以精确删除**，携带即扩大泄露面。
Worker 收到后按 runId **回数据库查询权威状态**。

已由 `OutboxMessage` 在**类型层面**强制（白名单 + 禁止字段黑名单）。

### 4.3 手动确认

⚠️ **禁止自动确认**：自动 ACK 会在业务处理失败时丢失消息。
必须业务处理完成后显式 ACK。

### 4.4 拒绝后不重新入队

| 情形 | 处置 | 为何不重试 |
|---|---|---|
| 消息格式非法 | 拒绝 → 死信 | 重试同一坏消息无意义 |
| 租约已被领取 | ACK 丢弃 | 别人已领，重试会打转 |
| 业务处理失败 | NACK → 重试至 `delivery-limit` → 死信 | 可能瞬时失败 |

⚠️ **`delivery-limit` 必须显式设为 3**（quorum 默认 20）。
`record_weakness` 重复写入 = **Sev-0**。

### 4.5 死信处理

死信队列 `agent.run.dead` **不挂 DLX**，避免死信循环。

进入死信 = 需要人工介入。**不自动消费**。

## 5. 失败与边界

| 情形 | 行为 | 理由 |
|---|---|---|
| MQ 不可用 | 发布器标记 FAILED，不阻塞 D1 | 任务已落库，重启后继续 |
| 轮询到坏消息 | 标记 FAILED + last_error | 不静默跳过 |
| attempts 超阈值 | 告警，不自动重置 | 避免无限循环 |
| 消费者收到重复消息 | 领取失败 → ACK 丢弃 | at-least-once 的正常形态 |
| 租约已过期被接管 | 新 Worker 领取，token+1 | 旧 Worker 提交会被拒 |
| 死信消息 | 不自动消费 | 需人工判断 |

## 6. 测试覆盖（12 项，实际结果）

| 分组 | 项数 | 命题 | 结果 |
|---|---|---|---|
| 发布器 | 6 | 发布成功标记 PUBLISHED；无事件返回 0 | ✅ |
| | | 失败标记 FAILED；**达阈值不自动重置** | ✅ |
| | | 未预期异常也标记失败（不吞异常） | ✅ |
| | | **消息含敏感字段 → 拒绝发布** | ✅ |
| 消费者 | 6 | 正常消息 CLAIMED | ✅ |
| | | **重复投递 → 丢弃且只尝试一次** | ✅ |
| | | 敏感字段 / 非本消费者事件 / 缺 runId → REJECTED | ✅ |
| | | 非法消息**不触碰数据库** | ✅ |
| 端口扩展 | — | `claimSpecificRun` 返回 `Optional` | ✅ |

> ⚠️ **断言针对「不可绕过的性质」**：
> 「不自动重置 FAILED」比「状态变为 FAILED」更重要；
> 「重复消息只尝试领取一次」比「消费返回了结果」更重要。

### 6.1 实现中新增的端口方法

设计阶段遗漏，实现时补上：

```java
Optional<LeasedTask> claimSpecificRun(tenantId, runId, workerId, leaseDuration)
```

**原因**：消息已指名 runId，若走批量 `claimTasks` 会拿到
**消息里没有的任务** —— 消息与执行错配，执行的不是消息指定的那个。

**返回 `Optional` 而非 `null`**：空是**正常语义**（重复投递），
不是错误。调用方不应重试。

### 6.2 实现中发现的一个隐患

`claimSpecificRun` 需要用 `fencing_token` 做乐观校验，
但不能先读后写（中间可能被他人接管）。
现实现为：同事务内先读 token 再条件更新 —— 
**事务内的读+写仍是两个快照**，理论上存在窗口。

> P3 故障注入时须验证此并发路径。
> 当前实现对「同一 Run 被两个 Worker 同时领取」是安全的
> （条件更新只有一方成功），但 token 读取与更新的原子性需进一步收紧。

## 7. 已知限制（编码前预判）

| # | 限制 | 影响 | 处置 |
|---|---|---|---|
| 1 | 单租户发布器 | 多租户需多实例 | P4 处理（试点期 max-tenants=1） |
| 2 | 无 FAILED 自动恢复 | 永久失败需人工 | 设计如此，见 §3.3 |
| 3 | 死信无处理工具 | 人工介入成本高 | P3 补 |
| 4 | 轮询间隔固定 | 延迟不可调 | 配置化 |

> **限制 3 需要注意**：若死信无处理入口，
> 就只能靠查数据库人工处置。P3 应补一个运维端点。
