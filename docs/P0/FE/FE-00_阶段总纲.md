## 1. 为什么独立成阶段

### 1.1 原计划中前端缺位

`P0-D06`（初始项目计划）的 P0～P5 阶段划分**全部是后端/平台维度**，
改造版规划 §701 曾提到「前端 | 1 人 | Agent 配置、运行详情、审批台」，
但**未进入任何阶段的任务分解**，也未定义交付物与验收标准。

后果是：后端 FR-001～FR-020 逐条推进，前端始终在"最后补"的位置。

### 1.2 独立立项的三个理由

| # | 理由 |
|---|---|
| 1 | **技术栈与验收标准不同**：React/TS 的验收是构建、类型、单测覆盖率、契约 mock，与 Java 侧的 `mvn verify` 无法互相替代 |
| 2 | **可并行**：前端 F1–F3 不被任何后端缺口阻塞，可与 P3 完全并行（见 §3） |
| 3 | **缺口需要独立台账**：前端依赖的后端缺口（`G1~G13` + 配置类 `C1~C9`）此前散落在文档中无人跟踪 |

## 2. 阶段范围

### 2.1 做什么

| 能力域 | 内容 |
|---|---|
| FE-A 基础框架 | 工程脚手架、路由、令牌管理、全局错误、API 适配层 |
| FE-B 业务闭环页面 | 登录、发起辅导、进度追踪、结果、画像（§FE-01） |
| FE-C **配置管理**（本次新增） | 平台配置、租户配置、工具风险级别、审批策略、Agent 配置、合规状态（§FE-02） |
| FE-D 治理与运营 | Run 检索、审批台、UNKNOWN 处置台、审计查询 |
| FE-E 合规专项 | 监护人同意与撤回入口（PIPL 硬要求） |

### 2.2 明确不做

| 非目标 | 理由 |
|---|---|
| 多租户切换器 | **架构上不存在**（`principal.tenant_id` 单列 + `login_name` 全局唯一），是 schema 变更而非 UI 问题 |
| 密码找回 | 需要邮箱/手机号，而 PIPL 要求**不采集**这些（D-001 §7）。结构性约束，不是有意遗漏 |
| 自助注册 | 涉及监护人同意流程，本期只做受控发号 |
| BFF / SSR 代理层 | 保持与后端同源部署即可（后端 CORS 禁用）；引入 Node 服务会扩大运维面 |
| 前端替代后端做授权 | 服务端才是授权边界（`P0-D03` 红线 9），前端矩阵仅用于界面显隐 |

## 3. 排期与依赖

### 3.1 批次划分

| 批次 | 内容 | 后端依赖 | 可否立即开工 |
|---|---|---|---|
| **F1** | 脚手架 + 登录页 + 令牌管理 + 路由守卫 + 全局错误 | 无 | ✅ |
| **F2** | 发起辅导页 + 幂等键策略 + 敏感信息预检 | 无 | ✅ |
| **F3** | 进度页（SSE 轮询）+ 六态映射 + 降级占位 | 无 | ✅ |
| **F4** | 配置管理**只读视图**（§FE-02 四区 L1） | `C1` 需后端提供配置读取端点 | 🟡 骨架可先做 |
| **F5** | 结果页 / 画像页 | `G5` `G6` | 🔴 |
| **F6** | 配置**写入**与治理流程 | `C2`~`C9` | 🔴 |
| **F7** | Run 检索 / 审批 / UNKNOWN / 审计 | `G7`~`G10` | 🔴 |
| **F8** | 合规同意与撤回 | 产品确认流程 | 🔴 |

> **关键判断**：**F1–F3 完全不被后端缺口阻塞**，可与 P3 立即并行启动。
> 这是 FE 阶段第一阶段的目标，应尽早开工。

### 3.2 与后端阶段的并行关系

```
P3（可靠性与安全，后端）        FE（前端）
├── D1 ✅ 故障注入框架          ├── F1 ✅ 可立即开工
├── D2 ✅ fencing 终态接管     ├── F2 ✅ 可立即开工
├── D3 ⬜ UNKNOWN 对账          ├── F3 ✅ 可立即开工
├── …                          └── F4–F8 ⏸ 等待后端缺口
         ↑
         └── 需同步补齐 G1–G13 / C1–C9 接口（见 FE-01 §5 / FE-02 §6）
```

## 4. 缺口台账（前端视角汇总）

> 详细清单见 `FE-01 §5`（G1~G13）与 `FE-02 §6`（C1~C9）。此处仅汇总统计。

| 类别 | 数量 | 高优先级 | 说明 |
|---|---|---|---|
| 业务侧缺口（G） | 13 | 6 | 无列表/详情/结果/事件写入/角色/CORS |
| 配置侧缺口（C） | 9 | 7 | **后端配置体系几乎完全不存在**，见 FE-02 |

> ⚠️ 配置侧缺口的严重性显著高于业务侧：**不是"接口没写"，而是"体系没建"**。
> 后端目前 0 个 `@ConfigurationProperties`、0 张配置表、0 个配置端点、0 条配置审计。

## 5. 阶段验收标准

| # | 标准 | 验证方式 |
|---|---|---|
| FE-DOD-1 | F1–F3 全部完成且有自动化测试 | 单测 + 组件测试 |
| FE-DOD-2 | 后端缺口清单**逐项有状态**（已补/待补/不补） | 台账更新，非口头承诺 |
| FE-DOD-3 | 配置页的每条红线**有对应 UI 约束且可被测试证伪** | 反证测试（见 FE-02 §7） |
| FE-DOD-4 | 构建产物不含任何硬编码密钥/口令 | CI 扫描 |
| FE-DOD-5 | 无「假装有数据」的降级（未开放 ≠ 暂无数据） | 组件测试断言 |
| FE-DOD-6 | TypeScript 严格模式，零 `any` 逃逸 | `tsc --noEmit` 门禁 |

> 沿用项目铁律（`P0-D06` DoD §8.0）：**文档先于代码**，
> 实现偏离本文档时须先改文档再改代码。
