## 1. 核心设计：约束落在「控件不存在」

FE-02 §4 的核心纪律：**约束要落在「控件不存在」或「选项不可选」，而不是「选了会报错」**。

| 约束 | ❌ 错误做法 | ✅ 本切片做法 |
|---|---|---|
| 审批只能收紧 | 下拉列出全部，提交时报错 | **`allowedApprovalLevels()` 只返回收紧子集**——放宽值不在 DOM 中 |
| 上限只能变小 | 输入任意值，提交后 409 | `isNumericTightening()` 前置校验 + **提交按钮 disabled** + 当场说明 |
| 理由必填 | 可空提交，后端 400 | **按钮 disabled** + 行内提示 |
| L1 锁定项 | 可编辑文本框 | **本页 `keys` 清单不含它们** → 根本不渲染 |

> ⚠️ **前端校验不是安全边界**：真正的强制在后端 `ConfigTighteningPolicy`，
> 任何绕过 UI 的请求都会被 409 拒绝。前端只做**提前收敛**。

## 2. 诚实呈现（FE-02 §5）

⛔ **本体系不是「保存即生效」**，而是「**下一个新建的 Run** 使用新值」。

已在 UI 显著位置写明：

> 保存后**下一个新建的 Run** 会使用新值；已经开始执行的 Run 不受影响
> （配置在 Run 创建时即被快照固化）。

并由反证 **T-5** 锁定：把该文案改成误导性的「立即生效」→ F14 转红。

> ⚠️ **误导性文案比功能缺失更有害**（FE-02 §4）：
> 若不写明快照隔离，管理员会以为保存后所有在途 Run 都变了。

### 3.1 两处值得单独说明的实现

**① 优化更新一律不做**：写配置是高危操作，
界面先变而后端拒绝 = 「看起来生效了其实没生效」——
正是 P4-D15 D15-B3 描述的危险形态。故一律**先等服务端响应，成功后重载**。

**② 409 文案强制收敛**：`errors.ts` 原逻辑是「服务端 message 优先」，
导致 `defaultMessage` 里的 409 映射成为**死代码**（反证 T-4 实测发现）。
现改为：`CONFIG_RELAXATION_REJECTED` **无条件覆盖**为固定文案，
与既有 `INVALID_CREDENTIALS` 的处理同构——
**因为「刷新后重试」对安全拒绝是无效建议**（刷新不会让「只能收紧」变松）。

## 5. ⛔ 本轮抓到的两个真实缺陷（反证暴露，非测试失败暴露）

### D11-B1：`field__error` 之外，CSS 完整性不变式抓到 3 个未定义类名

`row-actions` / `editor` / `table` 三个类被组件使用但主样式层无定义。

**处置**：**定义真实样式而非加豁免**（豁免会让下次同类问题继续漏网）。
`table` 改为沿用既有**裸 `<table>`** 约定（`ConfigTable` 就是这么做的），
另两个新增 `.btn-row` / `.editor-panel`，遵循纸感体系（线 + 留白，⛔ 无阴影）。

### D11-B2：T-4 反证转不了红 → 发现 409 文案映射是**死代码**

**现象**：注入 `defaultMessage` 的 409 分支后，F17 **仍然绿**。

**根因**：请求带非空 `message` 时走的是「服务端 message 优先」分支，
**根本不会到达** `defaultMessage`。那条精心写的映射从未生效。

**危害**：若后端某天把 409 文案改成通用冲突，管理员就会看到
「请求冲突，请刷新后重试」并反复重试一个**注定被拒**的操作。

**修复**：`CONFIG_RELAXATION_REJECTED` 改为**无条件覆盖**（与凭据错误同构）；
F17 改为让 `fetch` 返回**故意写错的**服务端文案，断言前端仍收敛为正确提示。

> ⚠️ 这与 P4-D15 D15-B3 是**同一类**问题：
> **断言绕过了真正承重的分支**，于是保护看似存在、实则失效。
