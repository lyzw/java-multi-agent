## 0. 为什么做这件事

用户反馈：「规划完善的页面，不要用这种简单的页面」。

### 0.1 差距实测（不得凭印象）

| 项 | 规划（FE-01/FE-02） | 现状 | 缺口 |
|---|---|---|---|
| 页面数 | **19**（P1–P19）| **4** | **15** |
| 统一布局 | 需要 | 无侧边导航/顶栏 | 全缺 |
| 工作台 P2 | 任务列表 | 仅一个「未开放」占位 | 缺结构 |

现有 4 页共 558 行，其中 `DashboardPage.tsx` 仅 44 行 —— 属实是骨架级。

### 0.2 关键约束：多数页面被后端阻塞

| 页面 | 缺口 | 级别 |
|---|---|---|
| P5 结果页 | `G5` 无 `result:read` | 🔴 |
| P6 画像页 | `G6` 无画像端点 | 🟡 |
| P7 检索台 | `G7` 无 `run:read`、**无分页契约** | 🔴 |
| P8/P9/P10 治理页 | `G8`/`G9`/`G10` | 🟡🔴🟡 |
| P14–P19 配置页 | `C1`–`C9` | 🔴 |

**用户已确认处置方式**：**骨架 + 明确的未开放占位**。

> ⛔ **这不是妥协，而是诚实**：
> 做一个能渲染的骨架，并在数据区显式说明「功能尚未开放 + 原因 + 阻塞编号」。
> 比留空白页或编造假数据安全得多 —— 后者会让用户以为系统正常。

## 2. 架构决策

### 2.1 骨架的统一表达：`DataUnavailable`

新增组件，**取代散落的 `NotAvailable`**：

```tsx
<DataUnavailable
  blockedBy="G5"                       // 缺口编号，可点击查看
  feature="归因结果"
  reason="后端尚未提供 result:read 端点"
  eta="P3"                             // 承接阶段
  partial={<ResultSkeleton />}         // 可选：仍展示结构
/>
```

> **为什么必须统一**：散落的占位文案会导致
> 「有的页说未开放、有的页空白、有的页有假数据」——
> 用户无法判断哪些是能用哪些是待开发。**一致性本身就是信息。**

### 2.2 页面结构与数据解耦

⛔ **关键决策**：页面**结构**现在就定死（区块、标题、字段位），
数据用 `null` 表示「未就绪」。接口来了只替换取数逻辑。

| 现在 | 接口就绪后 |
|---|---|
| `<ResultPage />` 渲染区块骨架 + `DataUnavailable` | 同一组件，区块填数据 |
| **零结构改动** | 零结构改动 |

> 若等接口来了再定结构，必然出现「结构与数据耦合」，
> 导致接入时重写 UI —— 这正是「骨架先行」的收益。

### 2.3 路由与守卫

```tsx
// 权限分层（依据 ROLE_PERMISSIONS 实测）
/            STUDENT 可见
/runs/new    STUDENT
/runs/:id    STUDENT
/runs/:id/result  STUDENT
/profile/:id STUDENT
/config/*    TENANT_ADMIN, AGENT_AUTHOR
/agents      TENANT_ADMIN, AGENT_AUTHOR
/approvals   TENANT_ADMIN, APPROVER
/reconciliation TENANT_ADMIN, APPROVER
/audit       TENANT_ADMIN
/health      TENANT_ADMIN
```

⛔ **前端路由守卫只是体验优化，不是安全边界**（FE-01 §4.2 G-1）。
真正的授权在后端（红线 9：执行时重新授权）。

> ⚠️ **路由级权限不引入新依赖**：手写 `RequireRole`，
> 理由同 FE-D1 —— 依赖越少，攻击面越小。

## 3. 各页关键约束（逐条来自规划，不是通用模板）

### 3.1 P5 归因结果页 ⛔ 三条合规红线

| 红线 | 落实方式 |
|---|---|
| **C5 不得显示教材引用/页码/出处** | ⛔ **结构上不设「来源」区块**。不做隐藏，是没有这个位置 |
| **C6 结果不含身份信息** | 渲染前对模型输出做敏感词兜底扫描 |
| **C7 结果不落 localStorage** | 仅内存；导出须用户主动触发 |

**⛔ 必须预留「待核对」分区**（`P0-D00` §3.4）：

```
结果区 ├─ 正常结论
        └─ ⚠️ 待核对（UNKNOWN / RECONCILIATION_REQUIRED）  ← 独立、不可折叠、不可合并
```

> 接口来了再补这个分区 = 违反禁令。**必须现在就定死。**

### 3.2 P9 UNKNOWN 处置台 ⛔ 禁止一键重试

- 显式区分 `UNKNOWN` 与 `RECONCILIATION_REQUIRED`
- **不提供「一键重试」按钮** —— 盲目重放 = Sev-0
- 处置动作须逐条确认（对账/标记完成/上报）

### 3.3 P10 审计页 ⛔ 无请求体入口

- 审计日志不含 Prompt 原文（保留 180 天）
- **不提供「查看完整请求体」入口** —— 从结构上杜绝

### 3.4 P8 审批台

审批必须展示：**参数摘要 + 目标资源 + 有效期**。
过期/撤销 → **拒绝而非静默通过**。

### 3.5 P6 画像页 ⛔ 白名单渲染

即便后端将来返回姓名/学校/班级，**前端也应拒绝渲染**（纵深防御）。
实现：`pickWhitelisted()` 只取 `studentId`/`grade`/`subject`/`weaknesses`。

### 3.6 P7 检索台 ⛔ 分页契约占位

后端**无分页接口**（无 `page`/`size`/`sort`）。规划建议**游标分页**
（与 `Last-Event-ID` 语义一致）。

⚠️ **不擅自定契约** —— 只在 UI 上标注「待分页契约冻结」，不写假分页控件。

### 3.7 P13 系统健康 ✅ 唯一可真实实现

后端有 `/actuator/health`（`show-details: never`，匿名可访问）。

> ⚠️ **不得**规划依赖详细健康信息的运维页 —— 后端未暴露（G14）。

### 6.3 ⚠️ 实施中修复的测试基础设施缺陷

**症状**：单文件运行全绿，全量运行则大面积失败（报 "Found multiple elements"）。

**根因**：`setup.ts` **未显式注册 Testing Library 的 `cleanup`**。
自动 cleanup 依赖全局 `afterEach` 是否存在，而 setup 显式从 vitest 导入钩子后，
该自动注册路径不保证生效 —— 单文件时侥幸正常，多文件共存时 DOM 跨用例累积。

**修复**：`setup.ts` 中 `afterEach(() => cleanup())` 显式注册。

> ⚠️ **典型「单跑绿、联跑红」缺陷**：
> 只单跑测试文件**永远发现不了**，必须全量跑才能暴露。
> 已固化：每次改动测试基础设施后必须连跑 2 轮全量。
