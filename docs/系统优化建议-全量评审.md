# 系统优化建议 · 全量代码评审

> 评审范围：`java-multi-agent` 全仓库（platform 778 个 Java 文件 / 16.1 万行 + RAG 子系统 + 两个前端工程 `admin-console`、`frontend` + 54 个 SQL）。
> 评审日期：2026-10-27。方式：6 路并行只读审查（后端分层、DB/持久化、安全、UI/UX、业务逻辑/RAG、前端），结论均带具体文件:行号。
> 评级：**P0** = 安全/数据正确性硬伤，必须修；**P1** = 严重质量/可维护/可扩展风险，应修；**P2** = 技术债/一致性，排期修。

---

## 0 · 总体健康度与亮点

| 维度 | 结论 |
|---|---|
| 分层架构 | **优秀**。core/ports/application 完全不依赖 infrastructure（反向依赖 0 处），78 个端口接口清晰，是标准的六边形架构。 |
| 代码纪律 | **优秀**。全仓库无 TODO/FIXME/XXX、无空 catch、无 Repository 自 commit、无事务内远程调用、无 SQL 字符串拼接注入、无 `dangerouslySetInnerHTML`、admin-console **零 `any`/`@ts-ignore`**。 |
| 事务/RLS | **扎实**。`set_config('app.tenant_id',?,true)` 铁律有专门 IT 守护（CapTransactionContractIT 等），租户身份回滚/隔离有契约测试。 |
| 配置发布 | **严谨**。草稿→审批→发布三步不可合并、CAS 基线、双人复核异常、终态不自动重试，属于本仓最强实现。 |
| 测试基线 | **可建**。platform 543 单测 + 14 IT 类；admin-console 25 测试文件 / 310 项全绿。 |

**一句话**：架构地基非常干净，问题集中在「运维落地（DDL 没进 Flyway）」「安全边界（RAG 裸奔 + 令牌无吊销）」「业务闭环（错题归因模型缺口）」「前端一致性与底座」四类，而非代码脏乱。

## 1 · UI / UX（两套前端）

### 1.1 双设计语言并存（P1）
- **A** `admin-console` 用 antd 5，全局样式仅 16 行，主色裸 hex `#2f6df6`（`App.tsx`）。
- **B** `frontend` 用自写 CSS，有完整 token 层（`styles/tokens.css`，语义色/字阶/间距/圆角/动效）。
- 同一语义在两套里表现不同：版本 `<Tag color="blue">` vs `<Tag color="geekblue">`、状态中文直出 vs `displayBits` 中英混排、loading 全 Spin vs 统一 `Loading/LoadingRows`。
- **重复造轮子已发生**：A 的 `pages/catalog/*`（ToolCatalog 133 / SkillCatalog 103 / McpCatalog 122 / AgentRegistry 188 行）与 `pages/console/*` 是同一组页面的两套实现，且 `catalog/*` **零引用**（router 只引 console）。`features/rag/useRagManagement.ts` 两边各一份（350 vs 374 行，diff 131 行）。

### 1.2 信息架构（P0/P1）
- **P0**：A 的 `router.tsx` 无 `path="*"` 兜底 → 输错 URL 白屏（B 有 `NotFoundPage`）。
- **P1**：A 的 6 个分组里 `knowledge/system/observability/lab` 各只有 1 子项，白白多一层点击，应提升为一级。
- **P1**：A 至少 14 个**孤儿页面**（`SettingsPage`、`DashboardPage`、`PlaceholderPage`、`monitoring/*(2)`、`dependencies/*(3)`、`publish/*(3)`、`catalog/{Tool,Skill,Mcp}DetailPage`、`ResultContractPage`）零引用，误导维护。
- **P1**：同名不同义——A 技术名词「Tool/Skill/MCP Server」与「租户管理/字典配置」同级中英混排；B 的「检索记录」与「知识检索」并列；「语料管理」(B) vs「RAG 语料管理」(A) 同义不同名。

### 1.3 交互一致性缺陷（P1）
- 搜索：A 的工具/技能/MCP/Agent 有本地搜索，**租户表无关键词**（只有生命周期下拉）、**用户表无搜索**。
- 二次确认：A `DictionaryAdminPage.tsx:147` 停用语录**零确认**（影响全站下拉枚举！），而 UsersManagePage/TenantRegistryPage 有 Popconfirm。
- 刷新入口：`ToolCatalogPage`、`McpCatalogPage`、`AgentRegistryPage`、`TenantRegistryPage`、`UsersManagePage` **整页无刷新**。
- loading：A 全 Spin（15+ 处）零 Skeleton，三种形态混用；B 统一 `Loading/LoadingRows`。
- 成功提示：A 全 `message.*` 3 秒即逝，零 `notification.*`（"申请已入队"这类需留痕可跳转的结果不该用 message）。

### 1.4 可访问性与响应式（P0）
- **P0**：A 全仓仅 16 处 aria，60+ 页面为零；`AdminLayout.tsx:139` 侧栏折叠是 `<span onClick>`，不可键盘聚焦、无 aria-label/expanded（B 实现是完整 button）。
- **P0**：A 基本无响应式——仅一处 Sider breakpoint；**20+ 张表缺 `scroll.x`**，窄屏撑破整页触发 body 横向滚动。这正是 B 在 `layout.css:742-774` 已修过的同型缺陷，A 未迁移经验。
- **P1**：无 skip link、无 `<main>`、无面包屑、切换菜单后浏览器标签不变（无 `usePageTitle`）；双击行作详情入口，键盘/触屏/读屏不可用。

> **投入产出比最高的 5 个 UX 改进**：① 给 A 补 table-wrap / `scroll.x` + 把 `<span onClick>` 换成 `<button>`（半天，消除最刺眼窄屏/键盘黑洞）；② 抽共享 `@shared/design-tokens`，A 用同一批 CSS 变量覆盖 antd `ConfigProvider`；③ 删 A 的 `catalog/*` + 10 个孤儿页面；④ 统一空态/确认/通知三层交互原语；⑤ A 补 404 + 分组扁平化。

## 2 · 前端（admin-console · 工程与代码）

### 2.1 数据获取层缺失（P1）
- **无 react-query/swr**，纯手写 `useEffect + useState` 拉取。
- **`AbortController` 使用数 = 0** → 无请求取消/竞态保护。快速切换筛选/分页时旧响应可能覆盖新数据。
- 每页重复实现「fetch + loading + error + 空态」样板，缺少统一封装（如 `<AsyncBoundary>` 或 hook `useQueryLike`）。

### 2.2 构建/性能（P2）
- `vite.config.ts` 的 `build` 仅 `outDir/sourcemap`，**无 `manualChunks`、无路由懒加载** → 16k 行 SPA 打成一个包，首屏体积大、无缓存切分。
- 大数据量列表（租户/用户/审计/语料）未做虚拟滚动。

### 2.3 组件规模（P2）
超过 450 行的页面：`UsersManagePage 613`、`AgentMetricsPage 600`、`AgentDraftPanel 563`、`AgentLabPage 501`、`DictionaryAdminPage 464`、`AgentDetailPage 459`、`RagMaintenancePanel 438`、`platformDetailDrawer 411`、`SkillCatalogPage 410`。建议按「筛选区 / 列表 / 抽屉 / 表单」拆分，抽通用 Table/Empty/Confirm 组件。

### 2.4 测试覆盖（P1）
- 25 测试文件 vs 77 页面文件，覆盖率偏薄。**治理纪律类断言稀缺**：字典「停用≠删除」、指标「未采集≠0」这类核心铁律目前只有 1-2 个测试守护，多页无行为断言（仅断言渲染成功）。

### 2.5 正向结论
- 类型安全极好（零 `any`/`@ts-ignore`），中文枚举集中化（`ragTypes`/`useDictionaries`）已起步；RAG 管理页的五态（idle/loading/success/empty/error）+ 409 不提示刷新的纪律是全仓交互范本。

## 4 · 数据库与持久化（PostgreSQL + RLS + Flyway）

### 4.1 ⚠️ P0：DDL 双源分裂（最该先修）
`05_platform_identity_ddl.sql`、`07_platform_dictionary_ddl.sql`、`08_platform_agent_metrics_ddl.sql` **完全不在 Flyway V1–V29 中**，而 `deploy/sql/README.md` 要求生产走 Flyway → **线上根本没有这些对象**（指标表、`run.trace_id`、字典表），`JdbcAgentMetricRepository` 会 `relation does not exist`。**必须新建 V30+ 收编**。

### 4.2 外键缺索引（P1）
PG 不自动给外键建索引，DELETE 父表会全表扫子表：
- `budget_reservation(account_id)`、`usage_record(run_id)`、`approval(operation_id)`、`cap_approval(operation_id/run_id)`（`deploy/sql/platform/01_platform_ddl.sql:3592/3672/3448/3488/3496`）
- RAG：`rag_answer_citation(chunk_id)`、`rag_edition(source_id)`、`rag_ingest_job`（**零二级索引**）
- 建议 `CREATE INDEX CONCURRENTLY ...` 建。

### 4.3 RLS 策略缺口（P1）
- `cap_config_pointer` / `cap_config_publish_request` / `cap_config_release` / `cap_decision_log`（`01_platform_ddl.sql:3892–4028`）**只有 SELECT/INSERT/UPDATE，缺 DELETE 策略** → 默认拒绝下 DELETE 被完全禁止；`cap_decision_log` 最高频追加日志只增不减，只能靠 BYPASSRLS 清理。

### 4.4 迁移卫生（P1）
- 锁表风险：`V23`/`rag V3` 改列类型 = 表重写 + ACCESS EXCLUSIVE；全仓库 `CREATE INDEX CONCURRENTLY` **0 处**（应 CONCURRENTLY 建索引避免锁表）。
- `deploy/sql/platform` 有两个 `04_` 前缀文件，按名排序执行顺序不确定。
- 冗余索引：`idx_audit_tenant_time`（`:2889`）是 `idx_audit_tenant_time_id`（`:2896`）前缀，可删。

### 4.5 连接池（P1）
`platform-bootstrap/.../application.yml`、`rag-bootstrap/.../application.yml` 只配 `connection-init-sql`，**未设 `maximumPoolSize`/`minimumIdle`/`connectionTimeout`/`leakDetectionThreshold`** → 全落 Hikari 默认 10 连接且无泄漏检测。生产侧遗漏（test 配置反而配了 minIdle）。

### 4.6 平台审计翻页（P1）
`security/JdbcPlatformAuditRepository.java:96` 既无 OFFSET 也无 cursor，只能看首页，且丢弃 `limit+1` 的 hasMore → 无法翻页。其余 9 个仓库已用 keyset，这里漏了。

## 5 · 安全与权限（P0/P1）

### 5.1 P0：RAG 服务裸奔 + 租户头不校验归属
- RAG（`rag-bootstrap/pom.xml`）**无 Spring Security 依赖、全目录无 `SecurityFilterChain`**。
- `RagManagementController.java` 读取 `X-Tenant-Id`（端点 153/189/251/.../647+），唯一校验 `requireTenantContext`（`:705-718`）= 只 `UUID.fromString()`，**不校验「该主体是否属于该租户」** → 能触达 8081 者改一个头即可对任意租户登记/校验/撤回/删字典/重索引。
- `X-Tenant-Min-Trust-Tier`（`:726-737`）同样可伪造 → 放行未核验语料进检索。
- **修复**：8081 前加令牌校验（或仅内网 mTLS），`X-Tenant-Id` 与已验签主体做归属绑定；trust-tier 改由服务端查权威源。
- **处置（2026-10-27）**：✅ 已修——`RagJwtAuthFilter`（纯 JDK RS256 验签，无新增运行时依赖）：双令牌域（tenant 令牌强制 `X-Tenant-Id` == tenant_id claim，归属不符 403；platform 令牌跨租户豁免）；先验签再比 aud/iss；exp 校验；健康探针豁免；未配公钥时 fail-closed（构造期抛异常）；`enabled=false` 显式逃生门打 ERROR 横幅。12 项过滤器测试。trust-tier 门槛已改服务端配置（见 §7.1）。

### 5.2 P0：BYPASSRLS 明文口令落盘
- `config.env:52` `platform_ops` 凭据可绕过全部 RLS；`rag.env`、`.env.rag-online` 也含明文。虽被 `.gitignore` 排除（未入库），但明文落盘 + 无 KMS 仍属高危。立即轮换并迁入密钥库。
- **处置（2026-10-27）**：运维执行清单已出 → `docs/安全-P0-3-密钥轮换操作清单.md`（含 6 项资产盘点、按账号轮换步骤、`*.env.example` 模板结构、KMS/Keychain 选型与验收标准）。轮换动作须在阿里云 RDS 侧人工执行。

### 5.3 P1：令牌无吊销 / 无登出 / 无刷新
- `AuthController` 仅 `/token`、`/jwks`、`/roles`；`SecurityConfiguration.java:172` 显式 `logout.disable()`。
- 签发时生成 `jti`（`JwtTokenService.java:147`）但 `verify()` 从不校验 → 无黑名单，截获令牌在 900s 内全效。
- `authzVersion` 撤权依赖**内存** `ConcurrentHashMap`（`RoleBasedAuthorizationService.java:98/133-135`）→ 多实例部署撤权不跨节点。**应迁到 DB**（`JdbcAuthzVersionRepository` 已有）。

### 5.4 P1：MFA 形同虚设
`PlatformCredentialAuthenticationService.java:74` `mfaVerified = !record.mfaRequired()`——`mfaRequired=true` 时不发起任何质询即置 false 并签发令牌；授权链从未读 `mfaVerified()`。`mfaRequired` 账号被撞库即直达超管。

### 5.5 P1：审计盲区
- `PlatformDictionaryController.java:95/124/150/186/236` 5 个写端点**只有 `security.require`，零审计**（含字典停用、删条目）。
- RAG 管理面：仅检索与 `REVOKE` 落 `rag_access_audit`；登记/校验决定/字典变更未落（文档自认未实现）。

### 5.6 正向结论
- JWT：RS256、先验签后解析、iss/aud/exp/nbf 全校验、角色与库白名单取交集防自封管理员；平台/租户双链路隔离良好。SQL 注入、前端 XSS 均**未发现**。

## 6 · 业务逻辑与领域模型

### 6.1 状态机未强制（P0）
- 见 §3.3：`RunState.requireTransitionTo` 生产零调用；`TenantRegistry.java:38` 的 `tenant.status` 是**裸 `String`** 无枚举无转移表，直接 `SET status=?`（`JdbcPlatformTenantRepository.java:184/206`）。
- **修复**：让 `RunState.requireTransitionTo` 在迁移点真正被调用（或下沉 DB 触发器统一守卫）；`tenant.status` 改枚举 + 转移表。

### 6.2 两套审批模型并存（P1）
legacy `approval`/`JdbcApprovalRepository` 与 `cap_approval` 双轨；申请/审批/执行权**未分离**（`CONFIG_PUBLISH` 共用），而 legacy `ConfigChangeController` 反而用 `config:change`/`config:approve` 分离。SoD 不彻底。

### 6.3 P0：配置发布旁路
`api/governance/AgentController.java:170-195` `POST /api/agents/{id}/versions` 以 `AGENT_MANAGE` 直写自由 JSONB definition，**无门禁无复核**；`CapDualWriteService` 双写会把它带进权威表。与「三步发布」自相矛盾。

### 6.4 业务模型缺口（针对「错题归因辅导」场景，P0）
| 能力 | 现状 | 级别 |
|---|---|---|
| 学情画像 | `student_profile` 仅 `(student_id,grade,subject)`，无掌握度/轨迹 | **P0** |
| 知识点体系 | `weakness_record.knowledge_point` 是 1–100 字**自由文本**，无字典/层级/教材版本；真正的 `KnowledgePoint` 实体只在 `rag-core`，平台侧不通 | **P0** |
| 归因结论结构化 | 仅 `error_type` 六值 + `confidence`（SQL 注释自认"不可靠不参与判定"）→ **归因本质纯文本**，不可评估/统计/回放 | **P0** |
| 效果闭环 | `weakness_record` 单向写入，无 `resolved/mastered`/复测；`agent_task_outcome`/`agent_eval_sample` 未落地 → **"学生是否进步"当前无数据** | **P0** |
| 平台↔RAG 通路 | 平台仅 2 个业务工具（`get_student_profile`/`record_weakness`），**无任何调用 RAG 检索的工具**；`agent-infra` 另有一套孤立 TF-IDF 检索未接入 Run 循环 | **P0** |

> 结论：当前系统能「跑通 Agent 执行」，**但不能证明「辅导有效」**——这正是 P7 文档里 BIZ-1~BIZ-5 标 P7-3 的原因。

## 7 · RAG 子系统

### 7.2 三个占位 Port 的上线风险（✅ P0 已 fail-closed 化，2026-10-27）

|---|---|---|
